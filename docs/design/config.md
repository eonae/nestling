## 1. Секция: рекорд полей, source-agnostic

```typescript
// orders.config.ts — из пакета наружу идёт только хэндл ключей
export const OrdersConfig = makeConfig('orders', {
  maxItems:    z.coerce.number().default(100),          // ← ключ ORDERS_MAX_ITEMS
  databaseUrl: secret(from('DATABASE_URL', z.url())),   // точное имя + секрет
  apiToken:    secret(z.string()),                      // редактируется в выводе
});
export const ordersKeys = OrdersConfig.keys;        // экспортируемая capability привязки

@Injectable([OrdersConfig])
export class OrdersService {
  constructor(private cfg: Config<typeof OrdersConfig>) {}
}
```

- Секция — **рекорд полей**: перечислимость полей живёт на уровне
  JS-объекта, листья — произвольные Standard Schema
  ([schemas.md](./schemas.md)), `from()`/`secret()` — обёртки листьев.
  Деривация ключей, реестр для доков и привязка не требуют интроспекции
  вендорских схем. Поля валидируются независимо.
- Обёртки композируются **единственным** порядком: `secret()` снаружи,
  `from()` внутри. Секретность — свойство **поля**, `from()` называет его
  **ключ**, поэтому модификатор стоит снаружи, имя — внутри, схема — в
  листе. Обратный порядок отвергается типами и даёт ошибку в точке
  объявления, называющую канонический порядок. Ни одна обёртка не
  участвует в валидации: проверяет только лист-схема.
- Префикс строит имена ключей (`maxItems` → `ORDERS_MAX_ITEMS`);
  `from('KEY')` задаёт точное имя. **Источник не называется** — секция
  провенанс-слепа: читает ключ, не зная, откуда пришло значение
  (syscall-граница, как чтение `fd`).
- Конфиг — частный случай token families: секция авто-дискаверится из
  инжекта, отдельной регистрации в модуле нет.

## 2. Две capability — инжект и привязка

Приватность — не проверка на `build()`, а невозможность-по-построению:

- **токен секции** (право инжекта) не экспортируется из пакета — чужой
  инжект невозможно даже написать (ES-видимость);
- **`.keys`** (право привязки) — экспортируемый branded-хэндл набора
  ключей; инжектировать его нечем, поэтому экспорт безопасен.

Понятия «владение» и ключа `configs:` у модуля нет. Вспомогательное
ESLint-правило: «экспортируй `.keys`, не результат `makeConfig`».

Форма токена: `makeConfig` возвращает **не-инстанцируемый класс**, у
которого `name` перекрыт id члена семейства (`'ConfigSection:orders'`), а
`.keys` лежит на статике. Класс-как-токен — обычная DI-идиома:
`InjectionToken` это `TokenString | Constructor`, и строковый токен не мог
бы нести `.keys`. Конструктор бросает — секцию не инстанцирует никто, кроме
фреймворкового рецепта; ошибка называет причину и способ починки.
`.keys` — экземпляр `ConfigKeys<Prefix>`: не строка и не конструктор,
поэтому в `deps` он не проходит по типам.

## 3. Источники и привязка в корне

Источники — **не провайдеры**, а объекты
`ConfigSource { get; init?; close?; watch? }` в одной приватной читалке
(kernel). `env` — неявный пол; свои координаты (`path`, `addr`) источник
читает из примордиального `process.env` в `init()` — единственный его
контакт с env.

```typescript
// только env → про конфиг в корне ничего не пишешь
await assemble({ modules: [OrdersModule], transports: [http()] }).run();

// появились другие источники → плоский список, порядок = приоритет
await assemble({
  config: [
    [vault(), [ordersKeys]],            // хэндлы секций
    [file('config.yaml'), ['*_URL']],   // и глобы ключей
  ],
  /* ... */
}).run();
```

Привязка адресует **ключи** (хэндлы и глобы), не токены — читалка работает
в своём домене. Жадный контейнер инстанцирует все потреблённые секции
выбранных фич на `build()` → валидация eager → **невалидный конфиг на
старте = FAIL-FAST**.

Пока `assemble()` не появился, точка привязки живёт в `AppConfig.config` —
той же плоской формой `[[src, keys | glob]]`; kernel-модуль конфига `App`
регистрирует **всегда**, иначе «только env → в корне ничего не пишешь» не
работало бы. Переезд в `assemble()` — одна строка.

Глоб, не покрывший ни одного объявленного ключа, даёт на старте
**предупреждение** (опечатка в `'*_UR'` иначе молча не привязывала бы
ничего), но не ошибку: глоб легитимно смотрит на unbound-ключи семейств.
Канал предупреждений подменяем (`onWarn`), по умолчанию — `console.warn`
с префиксом `[nestling/config]`.

## 4. Reloadable

```typescript
export const Runtime = makeConfig.reloadable('runtime', {
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  rps:      z.coerce.number().default(100),
});

// (а) read-latest — читаем при каждом использовании, подписка не нужна
@Injectable([Runtime])
class Logger {
  constructor(private cfg: Config<typeof Runtime>) {}
  debug(m: string) { if (gte(this.cfg.logLevel, 'debug')) this.write(m); }
}

// (б) react — перестроить ресурс при изменении
@Injectable([Runtime])
class RateLimiter {
  #bucket = new TokenBucket(100);
  constructor(private cfg: Config<typeof Runtime>) {}
  @OnStart() start(signal: AbortSignal) {
    this.#bucket.refill(this.cfg.rps);
    this.cfg.onChange(signal, (next) => this.#bucket.refill(next.rps)); // отписка по signal
  }
}

// корень: reloadable-источник — то, что включает reload
await assemble({ config: [[reloadableFile('runtime.yaml'), [Runtime]]], /* ... */ }).run();
```

Источник с наблюдением даёт читалке новое значение, та пере-проецирует
reloadable-секции: инстанс стабилен, поля обновляются на месте. Две
асимметрии со стартом:

- **старт: невалидный → die; reload: невалидный → keep last-good + warn** —
  живой процесс не падает из-за плохого горячего значения;
- **вступит ли изменение в силу — ответственность потребителя**: read-latest
  и `onChange` — да; значение, захваченное в конструкторе, — нет. Поэтому
  reloadable — opt-in.

## 5. Секреты

`secret(leaf)` помечает поле секретным; реестр конфига знает секретные
ключи. Для потребителя значение остаётся обычным (без брендирования типа) —
бренд возможен позже как аддитивное ужесточение.

Редактируется **вывод, произведённый фреймворком**, — ровно три поверхности:

- **`ConfigValidationError`** — сообщения issue'ев секретного поля
  заменяются на `'<redacted>'` **и в тексте, и в объекте**
  `failures[].issues`: гарантировать отсутствие значения в тексте вендора
  нельзя, а `failures` — публичное поле. Имя ключа, имя поля и число
  отказов остаются всегда. Исключение: если значение не было задано
  (`undefined`), редактировать нечего и сообщение показывается целиком —
  «ключ не задан» и есть главный сценарий отладки секрета;
- **проекция секции** — `toJSON()` и `nodejs.util.inspect.custom` отдают
  копию с `'***'` вместо секретных полей, поэтому `console.log(cfg)` и
  `JSON.stringify(cfg)` безопасны. Оба члена неперечислимы, форма объекта
  не меняется, чтение поля отдаёт настоящее значение. Секция без секретных
  полей этих членов не получает вовсе;
- **снимок `describeConfig()`** — ключ несёт флаг `secret`; значений в
  снимке нет и не было.

**Граница гарантии названа явно:** `{ ...cfg }`, `Object.values(cfg)`,
чтение поля и передача его в свой логгер отдают настоящее значение.
Фреймворк отвечает за то, что печатает сам; закрыть остальное мог бы
только брендированный `Secret<T>`, который отвергнут.

## 6. Общие ключи

Один ключ (`DATABASE_URL`) могут читать несколько секций — ключ является
**разделяемым read-only ресурсом** (прямое продолжение capability-модели:
право читать ≠ владение). Второй читатель объявляется без ведома первого:
ошибки «ключ уже занят» не существует.

- каждая секция валидирует сырое значение **независимо** своей схемой (две
  секции законно видят ключ по-разному: `z.string()` и `z.coerce.number()`);
  любая упавшая валидация — fail-fast на старте;
- единственный конфликт сборки — **несогласованный `reloadable`**: одна
  секция объявила ключ reloadable, другая нет → ошибка на сборке
  (семантика «значение может измениться под ногами» должна быть согласована
  всеми читателями). Ошибка называет ключ, обе секции, оба поля и обе
  починки, а её текст симметричен относительно порядка материализации;
- **область проверки — одна сборка и только материализованные секции**:
  объявление, не попавшее в выбранную топологию, конфликта не создаёт, и
  состояние одной сборки не протекает в следующую в том же процессе;
- секретность общего ключа — **по объединению читателей**, причём по
  **объявленным**, а не по материализованным: хоть одна секция объявила
  `secret()` → ключ редактируется везде. Асимметрия с предыдущим пунктом
  намеренна: редактирование ошибается в безопасную сторону, запрет — в
  опасную;
- `describeConfig()` показывает всех читателей ключа: key-центричный индекс
  `keys: [{ key, secret, readers: [{ section, field, exact, reloadable,
  secret }] }]` считается по объявленным секциям и потому остаётся
  поверхностью аудита и для читателей вне выбранной топологии.

## 7. On-demand инфраструктура и unbound-ключи

`GrpcClient(server)` — член семейства, транзитивно тянущий
`Config(addressKey(server))`: инжектнул клиент → env-адрес пришёл сам,
жадный билдер инстанцирует всё на `build()`. Unbound-паттерны экспортируют
свои глобы симметрично секциям (`'*_GRPC_ADDRESS'`). Runtime-параметр
(адрес из БД) — не семейство, а фабрика вне жадного графа.

## 8. Интроспекция и доки

Реестр свойств конфига — источник генерируемой документации: ключи, схемы,
дефолты, атрибуция фиче (выводится из графа), читатели общих ключей, пометки
секретов. Без значений и без сети.

Интроспекция конфига — `describeConfig()`: две проекции одних данных,
section-центричный перечень (`sections`) и key-центричный индекс (`keys`),
обслуживающие два разных вопроса — «что читает эта секция» и «кто читает
этот ключ». Графовый `explain()` контейнера читает тот же индекс реестра:
второго источника истины не заводится.
