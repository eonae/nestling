## Context

Фаза 0 BOOTSTRAP поднимает источники конфигурации одним циклом по списку
привязок: `ConfigReader.init()` зовёт `init()` каждого источника в порядке
`bind()`, затем снимает снимок объявленных ключей. Аргументов у `init()`
нет, поэтому источник знает только то, что ему передали конструктором.

Отсюда два следствия. Источник, чьи координаты лежат в другом источнике,
написать нечем: адрес Vault приходит из `.env`, а прочитать `.env` до
своего подъёма Vault не может. И порядок списка сейчас перегружен — он
задаёт и приоритет разрешения ключа, и очерёдность ввода-вывода, хотя
приоритет Vault («выше `.env`») противоположен его очерёдности («после
`.env`»).

Целевое состояние описано в
[design/config.md §3](../../../docs/design/config.md) и в записи
[ideas.md [2026-09-13]](../../../docs/decisions/ideas.md) «Конфигурация»,
пункты 6–8. Код от него отстаёт ровно на этот change: `bind()`, `env()`,
`dotenv()`, `defaultSources`, `timeout` и `optional` уже поставлены
change'ем `config-run-bind`.

Ограничения, которые change не двигает: `get()` источника синхронен;
читалка приватна и живёт время `run()`; фаза 1 ввода-вывода не делает;
повторы принадлежат источнику, а не ядру.

## Goals / Non-Goals

**Goals:**

- Источник объявляет зависимость от секции и получает её проверенные
  значения аргументом `init(values)`.
- Очерёдность подъёма выводится из зависимостей; порядок списка остаётся
  приоритетом разрешения ключа.
- Дефект списка — цикл — виден до первого байта ввода-вывода.
- Отказ проекции секции координат называет источник и недостающие ключи.
- В репозитории есть сетевой источник, проверенный против живого сервера:
  `@nestlingjs/config.vault`.

**Non-Goals:**

- Наблюдение (`watch`) у сетевого источника.
- Способы аутентификации Vault, кроме заголовка `X-Vault-Token`.
- Повторы, таймауты и кэш на стороне ядра.
- `needs` у reloadable-секции.

## Decisions

### 1. `needs` — DI-токен секции, а не префикс и не `.keys`

```typescript
export interface ConfigSource<Needs = void> {
  get(key: string): unknown;
  readonly name?: string;
  readonly needs?: ConfigSectionToken<Needs>;
  init?(values: Needs): void | Promise<void>;
  watch?(notify: () => void): void;
  close?(): void | Promise<void>;
}
```

DI-токен секции несёт обе вещи, которые нужны фазе 0: `.keys` с префиксом и
именами ключей — читалке, параметр `Values` — типу `init(values)`. Тип
источника параметризуется этим же значением, поэтому `vault(VaultConfig)`
возвращает `ConfigSource<VaultValues>`, и `init`, принявший не ту форму, —
ошибка компиляции.

Умолчание `Needs = void` оставляет прежнюю форму источника без
зависимостей: `needs` не объявляется, `init()` пишется без параметров.

Альтернативы. Префикс строкой — теряется тип значений, а опечатка в
префиксе ловится только рантаймом. `ConfigKeys` (право привязки) — несёт
имена ключей, но не тип значений: на `.keys` проекции секции нет.

### 2. Очерёдность подъёма — топологический порядок, порядок списка — приоритет

Привязка `A` поднимается после привязки `B`, если `A` объявила `needs` и
`keys` привязки `B` покрывают хотя бы один ключ секции `A.needs`.
Покрытие считается таргетом привязки (`ConfigKeys` или глоб), а не
наличием значения: значения до подъёма неизвестны.

Сортировка стабильна — при отсутствии зависимостей сохраняется порядок
списка. Так `[bind(vault(VaultConfig)), ...defaultSources]` поднимает
`env()`, затем `dotenv('.env')`, затем Vault, а ключ, который знают и
Vault, и `.env`, по-прежнему разрешается значением Vault.

Альтернатива — требовать от приложения писать список в порядке подъёма —
отвергнута записью [2026-09-13]: она заставляет держать в голове два
несовпадающих порядка одного списка.

### 3. Цикл — отказ до ввода-вывода

Порядок считается один раз, до первого `init()`. Цикл в зависимостях даёт
`ConfigSourceCycleError` с цепочкой имён источников. Отказ безусловен:
`optional` его не проглатывает, потому что это дефект списка привязок, а
не недоступность внешней системы.

Самозависимость циклом не считается — её снимает решение 4.

### 4. Зависимый источник свои `needs`-ключи не обслуживает

`bind(vault(VaultConfig))` без `keys` покрывает всё, включая `VAULT_ADDR`.
Читалка исключает привязку из разрешения тех ключей, которые называет её
собственная секция `needs`. Правило живёт в одной точке — в поиске
значения — и потому действует и на проекцию секции координат, и на любое
последующее чтение.

Иначе координаты Vault пришлось бы искать в самом Vault, и тривиальная
запись давала бы цикл.

### 5. Секция координат проецируется один раз и фиксируется в снимке

Перед `init()` зависимого источника читалка:

1. находит декларацию секции по префиксу `needs.keys` — отсутствие
   декларации означает, что модуль с `makeConfig` не импортирован, и
   отказ называет префикс;
2. отказывает, если секция объявлена `makeConfig.reloadable`: секция
   координат не перепроецируется, и обещание reloadable здесь пустое;
3. читает значения ключей секции из привязок, поднятых **раньше**, и
   кладёт их в снимок;
4. проецирует и валидирует секцию тем же кодом, что и граф на фазе 1;
5. помечает декларацию потреблённой — секцию читает источник, а не узел
   графа, но прочитана она по-настоящему.

Финальный проход по объявленным ключам не перечитывает то, что уже лежит
в снимке. Поэтому источник, поднявшийся позже, значения координат не
меняет: «после подъёма секция не перепроецируется» держится снимком, а не
договорённостью.

Отказ валидации оборачивается в `ConfigSourceNeedsError`: сообщение
называет источник, секцию, ключи, значений которых не нашлось, и перечень
поднятых источников. `optional` эту ошибку проглатывает, как и отказ
`init()`: источник просто не поднялся.

### 6. Сателлит `@nestlingjs/config.vault` — один источник и одна секция

```typescript
export const VaultConfig = makeConfig('vault', {
  addr: z.url(),
  token: secret(z.string()),
  mount: z.string().default('secret'),
  path: z.string(),
});

export const vault = <T extends VaultCoordinates>(
  section: ConfigSectionToken<T>,
  options?: VaultOptions,
): ConfigSource<T> => …;
```

Секция передаётся аргументом, а не берётся источником из себя: связь
«источник ↔ его координаты» видна в строке вызова. Пакетная `VaultConfig`
— готовая секция на обычный случай; приложение с двумя Vault объявляет
свою секцию любой формы, подходящей под `VaultCoordinates`.

`init(values)` читает секрет KV v2 одним запросом
`GET {addr}/v1/{mount}/data/{path}` с заголовком `X-Vault-Token` и
запоминает рекорд `data.data`. `get(key)` отдаёт значение этого рекорда,
не обращаясь к сети: контракт синхронного `get()` выполняется. HTTP идёт
штатным `fetch` — клиента Vault в зависимостях нет.

Опция `retries` — число дополнительных попыток при сетевом отказе и
ответе `5xx`; пауза удваивается от 250 мс. `401`, `403` и `404`
повторов не вызывают: они не проходят сами. Граница времени остаётся у
привязки — `timeout` у `bind()`.

### 7. Прогон против живого Vault

`docker-compose.yml` пакета поднимает Vault в dev-режиме на нестандартном
порту; каталог `e2e` пишет секрет через HTTP API и читает его источником.
Без переменной `TEST_VAULT_ADDR` каталог пропускается — как у
`@nestlingjs/drizzle.pg` с `TEST_DATABASE_URL`. CI поднимает Vault
сервисом и переменную задаёт, поэтому расхождение с настоящим API ловится
прогоном, а не первым пользователем.

Спеки на подставном `fetch` пакет тоже получает — ими проверяются
повторы и разбор отказов, которые живой сервер по команде не выдаёт.

## Risks / Trade-offs

- **Порядок подъёма перестаёт читаться из списка глазами** → читалка
  пишет порядок подъёма в логгер ядра уровнем `debug`, а отказ фазы 0
  называет источник по имени.
- **Глоб `'*'` делает предшественником любую привязку без `needs`** →
  рёбер много, но цикл появляется только при взаимной зависимости; цена —
  один проход по спискам ключей, он считается до ввода-вывода.
- **Координаты Vault лежат в `.env` открытым текстом** → поле `token`
  объявлено `secret()`, поэтому в диагностику и снимок реестра оно не
  попадает; хранение самого файла — забота стенда.
- **Живой Vault в CI — ещё один сервис** → прогон пропускается без
  переменной окружения, поэтому локальный `yarn verify` от docker не
  зависит.
- **`fetch` вместо клиента Vault** → поддерживается один путь KV v2;
  расширение до других движков потребует кода, зато у пакета нет
  зависимостей и версионных конфликтов.

## Migration Plan

Обратной совместимости нет и не планируется: `init()` меняет сигнатуру во
всех реализациях сразу. Затронуты `env()` и `dotenv()` ядра, `vars()`
тестового пакета и подставные источники спеков — все они остаются без
`needs` и правятся типом, а не логикой.

## Open Questions

1. Нужен ли `watch` у Vault опросом с интервалом — и не лучше ли вместо
   него сигнал извне (SIGHUP, админский endpoint). Ответ — в записи
   `deferred.md` этого change'а.
2. Стоит ли читалке предупреждать о секции `needs`, которую никто, кроме
   источника, не инжектит. Пока нет: секция координат ровно для того и
   объявлена.
