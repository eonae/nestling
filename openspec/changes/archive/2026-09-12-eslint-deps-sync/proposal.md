# eslint-deps-sync

## Why

Список `@Component([…])`, `@Handler([…])` и `@Resource([…])` повторяет то,
что конструктор уже сказал типами параметров, и платит за это каждый файл.
Компилятор сверяет список с конструктором по типам, порядку и длине
(capability `injectable-dependency-list`), но расхождение чинит человек:
ошибка приходит после сборки, а не в редакторе, и не называет DI-токен,
который нужно написать. Агент по привычке из NestJS пишет `@Component()` с
пустым списком и узнаёт об этом от компилятора — пункт B3 первого внешнего
прогона ([d/14](../../../docs/history/discussions/14-first-external-run.md)).

Решение зафиксировано записью
[ideas.md [2026-09-12] «Правило линтера: список зависимостей из параметров
конструктора, с автофиксом»](../../../docs/decisions/ideas.md): правило
`dependency-list` в `@nestlingjs/eslint-plugin` выводит ожидаемый список из
аннотаций типов параметров по синтаксической таблице. Принцип «no runtime
magic» это не задевает: рантайм не меняется, список остаётся явным, а правило
подсказывает автору то, что он и так обязан написать.

## What Changes

- `@nestlingjs/eslint-plugin` получает третье правило `dependency-list`.
  Для класса с `@Component`, `@Handler` или `@Resource` правило выводит
  ожидаемый список DI-токенов из типов параметров конструктора (у
  `@Resource` — из параметров `static acquire` без последнего, сигнала) по
  таблице: класс `X` даёт `X`, `Config<typeof X>` даёт `X`, `Port<typeof Op>`
  даёт `Op.caller`, `Emitter<typeof Op>` даёт `Op.emitter`, `Logger` даёт
  `Logger$.auto`, интерфейс `X` при видимом в файле `X$` даёт `X$`, массив
  `readonly X[]` при видимом `X$` даёт `X$.all`. Остальные типы непрозрачны.
- Правило синтаксическое, как `endpoint-has-layer`: класс от интерфейса оно
  отличает по форме объявления и импорта (`class`, `import type`,
  `interface`) и по видимому в файле `X$`, а не по типам. Список сверяется
  по позициям: непрозрачная позиция принимает любой написанный DI-токен, а
  правило продолжает проверять остальные. Молчит правило там, где
  непрозрачен сам список (идентификатор, spread) или нет конструктора.
- Расхождение длины сообщается всегда: длина — то, что компилятор сверяет
  тоже, и ложного срабатывания здесь нет. Пустой или отсутствующий список
  при известных позициях чинится автофиксом. Замена написанного DI-токена
  предлагается как suggestion ESLint, а не как автофикс: написанный элемент —
  решение автора, и молчаливая замена, которая компилируется, была бы худшим
  исходом.
- Уровень `warn`; гарантией остаётся компилятор. Сообщение называет свой
  статус подсказки.
- Правило подключается в общий конфиг репозитория `.config/eslint.config.js`
  уровнем `warn` рядом с `import-through-barrel`: соглашение общее для всех
  пакетов и примеров. Прогон по репозиторию даёт ноль предупреждений.
- Скилл агента называет третье правило: раздел ESLint в
  `references/setup.md` и строка пакета в таблице `SKILL.md`.
- Документация: README плагина, строка пакета в `docs/README.md`, абзац о
  дублировании списка в `docs/design/container.md`, глава 6 гайда, правило о
  суффиксе `$` в `docs/conventions.md`, пометка «РЕАЛИЗОВАНО» в записи
  журнала.

## Capabilities

### New Capabilities

- `dependency-list-rule`: правило `dependency-list` плагина — таблица вывода
  DI-токена из типа параметра, классификация класса и интерфейса по
  синтаксису, проверка по позициям, границы молчания, форма сообщений,
  автофикс пустого списка и suggestion для замены, уровень `warn`.

### Modified Capabilities

- `agent-skill-content`: `references/setup.md` называет три правила плагина,
  включая `dependency-list`; строка `@nestlingjs/eslint-plugin` в таблице
  пакетов `SKILL.md` называет три правила.

## Non-goals

- Правило с информацией о типах (typed linting). Оно отличало бы класс от
  интерфейса надёжно, но требует программы TypeScript в линтере и делает
  плагин зависимым от проекта. Возврат — если синтаксическая таблица молчит
  слишком часто.
- `emitDecoratorMetadata`, `reflect-metadata` и генерация списка шагом
  сборки: исключены принципом «no runtime magic» и записью журнала.
- Вывод DI-токена для типов, которые его не называют: `CtxReader<T>`,
  `Set<string>`, `PgConnection<S>`, `OutboxEmitter<typeof Op>`, объединения
  типов. Такая позиция непрозрачна, и правило принимает то, что написано.
- Знание о сателлитах: таблица содержит только имена ядра. Типы сателлитов
  (`OutboxEmitter`) остаются непрозрачными.
- Настройка таблицы опциями правила. Таблица фиксирована именами ядра, как
  имя `httpEndpoint` у `endpoint-has-layer`.
- Изменение проверки в типах (`injectable-dependency-list`) и декораторов
  ролей: контейнер не меняется.
- Правило для функциональных провайдеров (`factoryProvider`, `useFactory` с
  `deps`): у них нет конструктора, из которого выводить список.
- Правило для классов без декоратора роли и для декораторов, вызванных
  через член (`container.Component([…])`) или под другим именем.

## Impact

- `packages/nestling.eslint-plugin`: новый файл `src/dependency-list.ts` и
  спека `src/dependency-list.spec.ts`; `src/index.ts` экспортирует
  `dependencyList` и регистрирует правило; `README.md` описывает три правила;
  `package.json` получает `@typescript-eslint/utils` в `devDependencies`
  ради типов AST (`import type`, в `dist` зависимости нет).
- `.config/eslint.config.js`: правило включено уровнем `warn` для всего
  репозитория. Классы примеров и пакетов, которые правило подсветит,
  приводятся к таблице.
- `packages/nestling.agent-skill`: `skill/references/setup.md` и
  `skill/SKILL.md`; спека `src/skill.spec.ts` сверяет имена правил с
  плагином автоматически.
- Документация: `docs/README.md` (строка пакета), `docs/design/container.md`
  (абзац о дублировании списка), `docs/conventions.md` (раздел «DI-токены и
  провайдеры»), `docs/guide/06-repository.md` (абзац о правиле и дата
  плашки), `docs/decisions/ideas.md` (пометка «РЕАЛИЗОВАНО» в записи
  [2026-09-12]), `docs/decisions/roadmap.md` (строка 70).
- Спеки: новая `dependency-list-rule`, дельта `agent-skill-content`.
