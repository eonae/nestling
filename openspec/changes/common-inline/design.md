# common-inline — дизайн

## Context

`packages/` держит три пакета скоупа `@common`, и ни один не помечен
`private: true`. Скоуп в npm репозиторию не принадлежит, поэтому первый же
`lerna publish` упрётся в чужое имя. Это блокер публикации, а не вопрос
вкуса.

Потребители у трёх пакетов разные, и это определяет три разных решения.

| Пакет | Строк | Потребители в рантайме |
| --- | --- | --- |
| `@common/graphs` | 264 | `container` |
| `@common/misc` | 419 | `config`, `operations`, `pipeline`, `ports`, `subscriptions` |
| `@common/static-server` | 317 | `viz` |

Из `@common/misc` берут десять символов: `Schema`, `Infer`, `DomainType`,
`StandardSchemaV1`, `validateSync`, `assertStandardSchema`,
`SchemaValidationError`, `SchemaIssue`, `Constructor`, `Optional`. Первые
восемь — слой Standard Schema; `Constructor` и `Optional` — типы-утилиты.

Change идёт вторым в серии и готовит дерево для #42
`package-consolidation`, где `container`, `operations` и `app` соберут
ядро.

## Goals / Non-Goals

**Goals:**

- Скоуп `@common` исчезает из публикуемой поверхности.
- `yarn verify` остаётся зелёным на каждом шаге.
- Публичный API `@nestling/*` не меняется, кроме новых экспортов.
- Объявленные зависимости совпадают с импортируемыми.

**Non-Goals:**

- Слияние пакетов ядра — #42.
- Переименование публикуемых пакетов.
- Изменение поведения слоя Standard Schema: код переезжает как есть.

## Decisions

### D1. `@common/graphs` переезжает в `container`, а не остаётся пакетом

Потребитель один, и он же единственный мыслимый: `DAG` описывает граф
провайдеров. Модули `dag.class.ts` и `interfaces.ts` кладутся в
`packages/nestling.container/src/graph/`, где уже лежат `graph.class.ts`
и `node.class.ts`, — коллизий имён нет.

Наружу `DAG` не экспортируется: сегодня его не видно из барреля
контейнера, и change это не меняет. Из `index.ts` каталога `graph/`
переехавшие модули видны только внутри пакета.

**Отвергнуто:** оставить пакетом с `private: true`. Флаг закрыл бы
публикацию, но оставил бы лишнюю единицу сборки ради одного потребителя.

### D2. `@common/misc` переезжает в `operations` и становится его экспортом

Слой Standard Schema — это то, из чего собраны схемы операций, поэтому
`@nestling/operations` его естественный дом. Модули `errors.ts`,
`types.ts`, `validate.ts` кладутся в `packages/nestling.operations/src/`
(имена свободны) и реэкспортируются из `index.ts`.

Пять потребителей переключаются на `@nestling/operations`. Четверо уже
зависят от него; новым становится только `@nestling/config`.

**Отвергнуто — оставить пакетом с `private: true`:** имя `misc` неверно
описывает содержимое, и в #42 этот код всё равно окажется внутри
`operations`. Переезд сейчас снимает шаг оттуда.

**Отвергнуто — разложить по потребителям:** десять символов на пять
пакетов дали бы пять копий `validateSync` и пять разных
`SchemaValidationError`. Отказ перестал бы ловиться одним `instanceof`.

### D3. Ребро `config → operations` принимается как временное

`@nestling/config` сегодня не зависит от `@nestling/operations`; после
переезда будет. Цикла это не создаёт: `operations` не импортирует
`config` ни прямо, ни транзитивно.

Ребро временное по построению: в целевой раскладке `config` входит в
`@nestling/app`, а `app` зависит от `operations`. Тест границы
`operations` продолжает запрещать обратное направление, поэтому ошибку
поймает сборка, а не ревью.

**Отвергнуто — тащить слой Standard Schema в отдельный публикуемый
пакет `@nestling/schema`:** это заменило бы один чужой скоуп на ещё один
пакет, тогда как серия занята уменьшением их числа.

### D4. `subscriptions` импортирует `StandardSchemaV1` из спецификации

В рантайме `subscriptions` берёт из `@common/misc` один тип —
`StandardSchemaV1`, а он и там реэкспортирован из `@standard-schema/spec`.
Пакет импортирует его напрямую из спецификации: одна зависимость вместо
двух, и тип тот же.

`Constructor` в `subscriptions` встречается только в спеках — там импорт
переключается на `@nestling/operations`.

### D5. `@common/static-server` остаётся пакетом с `private: true`

`@nestling/viz` бандлит его в `dist/cli.js` через esbuild, где external
только `commander`. Кода в опубликованном `viz` он не меняет, поэтому
переносить нечего, а `private: true` закрывает и публикацию, и вопрос
чужого скоупа.

Имя пакета не меняется: переименование в `@nestling/*` сделало бы
приватный служебный пакет похожим на публикуемый.

### D6. Карта jest теряет две ветки, а не всю строку

`jest.config.base.js` мапит `^@common/(.*)$` на `packages/common.$1/src/index.ts`.
Строка остаётся: `@common/static-server` никуда не уходит.

## Risks / Trade-offs

- **Сборка `container` тянет `dist` удалённого пакета** → каталоги
  `packages/common.graphs` и `packages/common.misc` удаляются целиком,
  вместе с `dist`; `yarn clear` перед сборкой ловит остаток.
- **Импорт `@common/misc` остаётся в спеках и не виден типам** →
  `yarn verify` гоняет спеки; удалённый пакет не резолвится ни в jest, ни
  в tsc.
- **`config → operations` кажется регрессом слоистости** → зафиксировано
  решением D3 и снимается в #42; тест границы `operations` держит
  направление.
- **Реэкспорт десяти символов расширяет поверхность `operations`** →
  символы уже были публичными, менялся только пакет; таблица экспортов в
  README обновляется тем же change'ем.

## Migration Plan

Порядок шагов выбран так, чтобы `yarn verify` был зелёным после каждого:

1. `@common/graphs` → `container` (потребитель один, шаг изолирован).
2. `@common/misc` → `operations`, реэкспорт из `index.ts`.
3. Потребители переключаются на новый источник, по одному пакету.
4. Удаление `packages/common.graphs` и `packages/common.misc`.
5. `private: true` у `@common/static-server`.
6. Чистка `package.json` и списка `ALLOW` в тесте границы.
7. Документация: таблицы пакетов и экспортов.

Откат — обратный переезд модулей; публичный API не менялся, поэтому
внешних потребителей откат не задевает.
