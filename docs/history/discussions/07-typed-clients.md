# 07 · Типизированные клиенты из контрактов

Дата: 2026-07-13. Вопрос-триггер: «можем ли мы из наших контрактов создавать
типизированные клиенты?» Реализация сознательно вынесена за скобки — обсуждался
целевой дизайн для документации.

Итог: решения записаны в [ideas.md [2026-07-13]](../../decisions/ideas.md)
(«Канонизация HTTP-input», «Типизированные клиенты из контрактов»),
план — roadmap 21 (`input-bind`) и 22 (`contract-clients`).

---

## Постановка: дыра ровно одна

Контракт в принятом дизайне (d/05 §3) уже центральное значение, но из него
«растут» только два потребителя:

```
                    makeContract({ name, kind, input, output, errors })
                                        │
        ┌───────────────┬───────────────┼────────────────────┐
        ▼               ▼               ▼                    ▼
   РЕАЛИЗАЦИЯ      ВНУТРЕННИЙ       ВНЕШНИЙ КЛИЕНТ        ДОКИ
   (inbound)       ПОТРЕБИТЕЛЬ      (вне nestling-        OpenAPI /
                   (outbound)        процесса)            AsyncAPI
   @ContractEndpoint  Contract.port   makeClient(...)
        │               │               │                    │
     решено (d/05)   решено (d/05)   НЕ спроектировано    roadmap 20
```

`Contract.port` — уже типизированный клиент (биндинг local/remote на сборке,
call-site идентичен). Не хватало **внешнего потребителя**: фронт, сервис на
другом стеке, скрипт. Ему недоступен DI, и в контракте нет HTTP-адреса
(`name` — адрес шины/subject).

Второе препятствие — сегодняшний `makeEndpoint` сращивает контракт с
реализацией (`handle` — обязательное поле `EndpointDefinition`): «только
контракт» неимпортируем без серверного кода и его зависимостей.

## Развилки первого захода

1. **Где живёт HTTP-паттерн** — (а) в контракте / (б) отдельным
   `httpBind`-значением / (в) в endpoint'е, как сейчас. Лен — (а): `name` уже
   адресация (NATS subject), `http:` — та же адресация для другого провода;
   нейтральность контракта — про направление, не про транспорт. (б) — два
   артефакта разъедутся, клиенту нужны оба; (в) — клиент не видит адреса.
2. **Форма клиента** — record → API-объект:
   `makeClient({ createUser: CreateUser }, { baseUrl })`; методы именует
   потребитель (explicit over implicit, без парсинга `'users.create'` в
   nested-объекты). Возврат `Promise<Ok | Fail<E ∪ UnknownError>>` — **тип
   call-site идентичен порту**, дисциплина портов распространяется наружу.
3. **Разложение input на провод** — сервер сливает body+query+params
   (`mergePayload`), клиенту нужна обратная операция; первый заход — правило +
   инвариант `merge(split(x)) ≡ x`.
4. **Ошибки** — рематериализация `Fail` по `code`: code-идентичность
   `defineFail` (error-model, [2026-07-10]) выбрана ровно потому, что
   instanceof не переживает сериализацию — «дизайн словно писался под
   клиентов».
5. **`makeEndpoint`** — остаётся инлайн-формой «анонимный контракт +
   реализация» (L0 прогрессивного раскрытия); клиента из него не сделать —
   осознанно.
6. **Пакетирование** — контракт не может жить в `@nestling/pipeline`; нужен
   лёгкий пакет контрактов + браузерный `@nestling/client`.

## Сверка с параллельным треком (Standard Schema / OpenAPI, тот же день)

Трек [ideas.md [2026-07-13]](../../decisions/ideas.md) + продолжение
[d/06 П.4](./06-critical-design-review.md) закрыл половину развилок:

- **№3 снят полностью и строже**: принят «канон + bind-карта» — сахар-пометки
  разворачиваются в плоскую bind-карту, которую потребляют
  транспорт/OpenAPI/**клиент** (клиент прямо назван потребителем); merge
  умирает, приём strict, `PayloadConflictError` исчезает как класс.
- **№6 усилен**: с переходом ядра на Standard Schema (roadmap 19) пакету
  контрактов не нужен даже zod — `StandardSchemaV1` types-only ⇒ zero runtime
  deps; валидация ответа клиентом — `~standard.validate`, вендор-нейтрально.
- **Auth/headers уже зафиксированы** в [deferred.md](../../decisions/deferred.md):
  ambient-заголовки — конфиг создания клиента; per-call `header()` отложен,
  «дизайн типизированного клиента» — записанный триггер возврата. Там же
  несущий принцип: **всё, что клиент передаёт per-call, живёт в декларации
  (input + bind)** — декларация интроспектируема, pre-юнит непрозрачен.
- **Нога «не-TS потребители»** уже спроектирована — roadmap 20 (конвертеры по
  `~standard.vendor`, `errors:` → responses).

## Новое следствие, которого не было в d/06

В П.4 разворачивание пометок в bind-карту привязано к **регистрации**
endpoint'а — серверной точке. Клиенту bind-карта нужна **без сервера**, из
одного импорта. Отсюда уточнение: точка разворачивания (и fail-fast канона) —
**создание контракта** (`makeContract`); все три потребителя едят готовую
карту. Для инлайн-`makeEndpoint` ничего не меняется (создание = регистрация).

Это же закрыло развилку №1: **bind-карта обязана быть выводима из значения,
которое импортирует клиент** ⇒ HTTP-биндинг — в контракте. Контраргумент
«контракт станет свалкой транспортных биндингов» ослаб: биндинг — данные для
bind-карты, а не транспортное поведение.

## Остаток клиентской дельты (вошёл в запись ideas.md)

1. форма секции: `http: 'POST /users'` | `{ method, path, bind? }`;
2. `makeClient(record, config)` → API-объект, `Ok|Fail`;
3. рематериализация `Fail` по `code` из `errors:`;
4. валидация ответа по `output`-схеме (default vs opt-in — открыт).

Streaming-клиент (`stream` → NDJSON `AsyncIterable`, `events` → SSE +
`Last-Event-ID`) — v2, вместе с AsyncAPI после roadmap 6. Коерсия
провод-строк — общий открытый вопрос с канонизацией.
