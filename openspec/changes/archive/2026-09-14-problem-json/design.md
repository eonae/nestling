# problem-json — дизайн

## Context

Отказ уходит клиенту из трёх мест пакета `@nestlingjs/transport.http`, и
каждое пишет своё тело:

| Место | Что пишет сейчас |
| --- | --- |
| `adapter.ts`, `sendResponse` | `ErrorDetails` контекста ответа как есть: `{ error, code, details?, stack? }` |
| `transport.ts`, `sendError` | `{ error, code, details? }` — ошибки до пайплайна: битый JSON, превышенный лимит, внутренняя ошибка |
| `adapter.ts`, `midStreamBody` | `{ error, code? }` в кадре `event: error` у SSE |

Медиатип у всех трёх — `application/json`. Читателей тела двое:
типизированный клиент (`@nestlingjs/client`, `readFailure`) и генератор
документа (`@nestlingjs/openapi`, `failSchema`); оба знают форму наизусть.

Ограничения. Модель ошибок ядра трогать нельзя: `ErrorDetails` несёт
отказ до транспорта и служит формой отказа у шины NATS и у результата
MCP. Сериализация тела — концерн HTTP-транспорта, там же лежит таблица
`httpCodeOf`, которая переводит категорию в код ответа.

## Goals / Non-Goals

Цели:

- Одно тело отказа на HTTP-границе вместо трёх, в форме документа
  RFC 9457 под медиатипом `application/problem+json`.
- Идентичность отказа читается штатным полем стандарта, без разбора
  расширений.
- Документ OpenAPI описывает ровно то, что уходит по сети: схема
  строится из того же кода, что и ответ.

Вне целей — перечень `## Non-goals` предложения: сериализация у шины и
MCP, модель ошибок ядра, член `instance`, настраиваемая база URI, поле
`title` у `makeFail`.

## Decisions

### 1. Документ RFC 9457 с медиатипом `application/problem+json`

Тело отказа:

```json
{
  "type": "urn:error:not_found:user",
  "title": "Not Found",
  "status": 404,
  "detail": "User 9 not found",
  "details": { "id": "9" }
}
```

Отображение: `Fail.code` → `type`, категория → `title` и `status`,
`Fail.message` → `detail`, `Fail.details` → расширение `details`,
стек при `exposeErrorDetails` → расширение `stack`.

Альтернативы. Оставить свой формат — потребитель на чужом стеке пишет
разбор руками, а три тела остаются тремя. Свой формат под
вендорным медиатипом (`application/vnd.nestling.error+json`) — та же
работа, что и стандарт, но без готовых читателей на другой стороне.

### 2. Идентичность — в `type`, поля `code` в теле нет

`type` равен `urn:error:<код отказа>`: `urn:error:not_found:user`,
`urn:error:bad_request`, `urn:error:internal_error`. Форма фиксирована
пакетом и ничем не настраивается.

Причина в самом стандарте: `type` объявлен первичным идентификатором типа
проблемы, и потребитель обязан различать проблемы по нему. У чужих
стеков это штатное поле (`ProblemDetails.Type` в .NET,
`ProblemDetail.getType()` в Spring): оно разбирается без нашего кода,
тогда как расширение требует своего типа на другой стороне.

Альтернативы:

- `type: "about:blank"` плюс расширение `code`. Отвергнуто: стандартная
  ось типа остаётся пустой, а идентичность живёт в своём поле — это
  нынешнее положение дел под новыми именами.
- Голый код в `type` (`"not_found:user"`). Невозможно синтаксически:
  по RFC 3986 такая строка читается как схема `not_found` с путём
  `user`, а подчёркивание в схеме запрещено; относительной ссылкой она
  тоже не проходит — двоеточие в первом сегменте пути запрещено.
  Отсюда префикс.
- База URI опцией транспорта (`https://api.example.com/errors/` + код).
  Отвергнуто: форма идентификатора начинает зависеть от настройки, и
  клиент, сверяющий код, ломается при переезде домена; страницы с
  описанием каждого отказа у API обычно нет вовсе.

Префикс `urn:error:` читается без знания RFC. Формально NID `error` в
IANA не зарегистрирован — см. «Риски».

### 3. `title` — фраза статуса HTTP по категории

`not_found` → `Not Found`, `conflict` → `Conflict`,
`internal_error` → `Internal Server Error`. Таблица лежит рядом с
`httpCodeOf` и строится по тому же перечню категорий.

Стандарт требует от `title` короткого описания **типа** проблемы, одного
на все случаи этого типа; конкретный случай описывает `detail`. Фраза
статуса этому условию отвечает и не требует ничего от автора отказа.

Альтернативы. Код отказа в `title` — повторяет `type` и читается
человеком хуже. Поле `title` у `makeFail` — точнее всех, но расширяет
публичный API ядра и добавляет автору обязанность; тема отдельной
записи, если фразы статуса окажется мало.

### 4. Модуль формата — в `@nestlingjs/operations`, вызовов три

Документ собирает и разбирает один модуль
`packages/nestling.operations/src/http/problem.ts`:

- `PROBLEM_MEDIA_TYPE = 'application/problem+json'`;
- `PROBLEM_TYPE_PREFIX = 'urn:error:'`;
- `problemTypeOf(code: string): string` — код в `urn:error:<код>`;
- `failCodeOf(type: unknown): string | undefined` — обратный разбор для
  читателя; строка без префикса даёт `undefined`;
- `problemTitleOf(category: Category): string` — фраза статуса;
- `problemOf(error: ErrorDetailsLike, status: number): ProblemDocument` —
  документ из деталей отказа и кода ответа;
- тип `ProblemDocument`.

Место выбрано зависимостями. Читателей документа двое, и один из них —
`@nestlingjs/client`, который зависит только от `@nestlingjs/operations`:
клиент работает в браузере, и тянуть в него `transport.http` вместе с
`busboy`, `find-my-way` и `node:http` нельзя. Пакет операций уже держит
HTTP-специфику деклараций — bind-карту, `RedirectStatus`, `SseConfig`, —
и `transport.http` реэкспортирует её, чтобы автор брал имена оттуда же,
откуда транспорт. Формат документа ложится тем же приёмом.

Код ответа модулю передаёт вызывающий: таблица `httpCodeOf` остаётся в
`transport.http`, и второй её копии не появляется.

Вызовов три, все в `transport.http`: ответ пайплайна (`sendResponse`),
ответ до пайплайна (`sendError`) и кадр `event: error` (`midStreamBody`).
Кадр SSE несёт тот же документ целиком, включая `status`, хотя статус
ответа уже отправлен и равен 200. Документ самодостаточен: читатель кадра
классифицирует отказ, не сопоставляя его со статусом потока. Вторая форма
«без `status`» дала бы два документа вместо одного.

### 5. Клиент: код из `type`, сообщение из `detail`

`readFailure` берёт `type`, получает код через `failCodeOf` и ищет
определение с этим кодом в `errors:` операции. Строка без префикса или
код, не объявленный операцией, дают `InternalError` с текстом, называющим
ответ, — правило не меняется. `details` проверяются схемой определения,
как сейчас; `title` и `status` клиент не читает: категорию и текст он
берёт из определения и `detail`.

### 6. OpenAPI: схема того же документа

`failSchema` описывает problem-документ: `type` константой
`urn:error:<код>`, `title` константой, `status` константой кода ответа,
`detail` строкой, `details` по схеме определения. Медиатип и построение
`type` генератор берёт из `@nestlingjs/operations`, как сегодня берёт
`httpCodeOf` из `transport.http`. Константы `type` дают потребителю
документа ту же ось различения, что и ответ по сети: два отказа на одном
коде ответа сводятся в `oneOf`, и ветки различимы.

## Risks / Trade-offs

- **NID `error` не зарегистрирован в IANA** → идентификатор
  непрозрачный: потребитель сравнивает строку целиком, а не разбирает
  её. Регистрация нужна тому, кто хочет разрешать URN в сети; здесь имя
  служит меткой типа.
- **Расширения `details` и `stack` носят наши имена** → будущий член
  стандарта с тем же именем столкнулся бы с ними. Вероятность низкая:
  перечень членов RFC 9457 закрыт и расширяется через регистрацию.
- **Ломается всякий существующий разбор тела** → пользователей нет,
  а гайды, рецепты, примеры и e2e правятся этим же change'ем. Проверка —
  `yarn verify` и e2e примера `app-with-http`.
- **`title` не называет конкретный отказ** → для человека ось точности —
  `type` и `detail`; если этого окажется мало, поле `title` у `makeFail`
  добавится отдельной работой.

## Migration Plan

Совместимости нет: старое тело удаляется целиком. Порядок работ —
формат, потом его читатели:

1. Модуль `problem.ts` и его тесты.
2. Три места сериализации переведены на `problemOf`, интеграционные
   спеки пакета обновлены.
3. Клиент и его спеки.
4. Генератор OpenAPI и снимки документа.
5. Тексты (design, гайды, рецепты, README) и примеры с e2e.

Откат — откат ветки: промежуточных состояний, в которых один читатель
уже на новом формате, а другой на старом, в `main` не попадает.

## Open Questions

- Корреляция запроса в теле отказа (`instance` или расширение
  `requestId`). Нужен доступ к `RequestId` в момент ответа; вернуться,
  когда наблюдаемость положит идентификатор в контекст ответа.
- Ссылки на документацию в `type` (`https://…/errors/<код>`). Вернуться,
  если у сайта документации появятся страницы по кодам отказа.
