# typed-http-client

## Purpose

`makeClient` превращает record операций в API-объект, у которого call-site
неотличим от вызова порта: `request` даёт `Ok | Fail`, `command` —
`Promise<void>`, и ветвящаяся логика, написанная для `.caller`, работает без
правок. Кодогенерации нет — типы приходят прямо из операции, а запрос
собирается по той же bind-карте, по которой транспорт его разбирает.
Клиент — значение: ни контейнера, ни `makeApp`, ни серверных пакетов.
Множество результата закрыто как `E ∪ InternalError`: задекларированный отказ
рематериализуется по коду, всё остальное — включая сетевой сбой и ответ, не
прошедший схему, — становится `InternalError` с оригиналом в `cause`.
Непригодность операции (нет `http:`, вид `event`, потоковая форма)
диагностируется в момент создания клиента, а не при первом вызове.

## Requirements

### Requirement: `makeClient` строит API-объект из record'а операций

`@nestlingjs/client` SHALL экспортировать
`makeClient(record, { baseUrl, headers?, fetch?, validateOutput? })`,
возвращающий объект с методом на каждый ключ `record`.

Методы SHALL именоваться **потребителем** — ключами записи. Вывод имён из
`name` операции (парсинг `'users.create'` во вложенные объекты) SHALL NOT
применяться.

Клиент SHALL быть значением: он ничего не регистрирует, не требует DI и не
зависит от серверного кода.

#### Scenario: Методы именует потребитель

- **WHEN** вызвано `makeClient({ createUser: CreateUser, getUser: GetUser }, { baseUrl })`
- **THEN** результат имеет ровно методы `createUser` и `getUser`

#### Scenario: Клиент собирается без приложения

- **WHEN** клиент создан в скрипте, импортировавшем только
  `@nestlingjs/operations` и `@nestlingjs/client`
- **THEN** он работает: ни контейнер, ни транспорт, ни `makeApp` не нужны

### Requirement: Call-site метода эквивалентен вызывателю вида операции

Тип и поведение вызова SHALL совпадать с вызывателем операции его вида:

- `request` → `Promise<Ok<Output> | Fail<E ∪ InternalError>>`, как
  `port.call(...)`;
- `command` → `Promise<void>`, отказ бросается, как `emitter.emit(...)`.

Второй аргумент SHALL быть словарём `{ signal?, deadline? }`. `signal` SHALL
уезжать в запрос и отменять его. `deadline` SHALL быть абсолютным моментом
(`Date`) и SHALL проверяться **до** отправки: истёкший бюджет SHALL давать
`Timeout` без похода в сеть.

Вид `event` SHALL отвергаться в момент `makeClient`: событие — broadcast-факт
с 0..N подписчиками, а HTTP-вызов адресует ровно одного получателя. Текст
ошибки SHALL называть ключ метода и предлагать `command`.

#### Scenario: Результат запроса разбирается как у порта

- **WHEN** вызвано `const result = await api.createUser({ email })`
- **THEN** `result` — `Ok` либо `Fail`, и та же ветвящаяся логика, что
  написана для `.caller`, работает без правок

#### Scenario: Команда не возвращает значения

- **WHEN** метод построен на `command`-операции и сервер ответил успехом
- **THEN** вызов резолвится `undefined`

#### Scenario: Истёкший бюджет не идёт в сеть

- **WHEN** вызвано `api.createUser(payload, { deadline: прошедший момент })`
- **THEN** результат — `Fail` с кодом бюджета, и запрос не отправлялся

#### Scenario: Событие отвергается при создании клиента

- **WHEN** в record передана операция вида `event`
- **THEN** `makeClient` бросает ошибку, называя ключ метода

### Requirement: Запрос собирается по bind-карте операции

Клиент SHALL раскладывать payload по bind-карте операции, выполняя
операцию, обратную strict-приёму транспорта:

- поля с размещением `path` — подстановкой в шаблон с
  `encodeURIComponent`;
- поля с размещением `query` — в query-строку;
- поля с размещением `body` — в тело;
- остальные поля — в источник, заданный правилом карты (`query` или
  `body`).

Инвариант SHALL держаться: разбор собранного клиентом запроса тем же
транспортом по той же карте SHALL давать исходный payload для любого
payload, представимого на проводе.

Тело SHALL сериализоваться как JSON, и заголовок `Content-Type:
application/json` SHALL ставиться только когда тело есть.

`baseUrl` и шаблон пути SHALL склеиваться буквально (`baseUrl` без
хвостового слэша плюс путь), без разрешения относительных URL.

#### Scenario: Path-параметр уходит в путь

- **WHEN** операция объявляет `http: 'PATCH /users/:id'`, а вызов передаёт
  `{ id: '42', name: 'Alice' }`
- **THEN** запрос уходит на `PATCH <baseUrl>/users/42` с телом
  `{"name":"Alice"}`

#### Scenario: Метод без тела кладёт остальное в query

- **WHEN** операция объявляет `http: 'GET /users'`, а вызов передаёт
  `{ limit: 10 }`
- **THEN** запрос уходит на `GET <baseUrl>/users?limit=10` без тела и без
  заголовка `Content-Type`

#### Scenario: Помеченное поле уходит в своё место

- **WHEN** операция объявляет `bind: { dryRun: query() }` при `POST`
- **THEN** `dryRun` уходит в query-строку, остальные поля — в тело

#### Scenario: Round-trip совпадает с приёмом транспорта

- **WHEN** запрос, собранный клиентом, разобран HTTP-транспортом по той же
  карте
- **THEN** полученный payload равен исходному

### Requirement: Коерсия значений query определена и не догадывается

При сборке query-строки клиент SHALL применять правила:

- `undefined` и `null` — ключ SHALL NOT записываться (отсутствие остаётся
  отсутствием, и `.optional()`/дефолты схемы продолжают работать);
- скаляр (`string`, `number`, `boolean`) → `String(value)`;
- массив скаляров → повторяющиеся вхождения ключа в порядке следования;
- любое другое значение (объект, вложенный массив) SHALL быть ошибкой
  `TypeError` в момент вызова, называющей поле.

Молчаливое приведение непредставимого значения к строке SHALL NOT
применяться.

#### Scenario: Массив даёт повторяющийся ключ

- **WHEN** query-поле `tag` равно `['a', 'b']`
- **THEN** запрос содержит `?tag=a&tag=b`

#### Scenario: Отсутствующее поле не пишется

- **WHEN** query-поле равно `undefined`
- **THEN** ключа в query-строке нет

#### Scenario: Объект в query — ошибка вызова

- **WHEN** query-поле равно `{ from: 1 }`
- **THEN** вызов бросает `TypeError`, называющий поле, и запрос не
  отправляется

### Requirement: Ответ валидируется по `output`-схеме операции

Успешный ответ SHALL валидироваться по форме `output` операции через
`~standard.validate` — **по умолчанию**. Валидация SHALL быть синхронной:
`Promise` из `validate` SHALL трактоваться как ошибка, как в ядре.

Отключение SHALL быть явным: `makeClient(record, { validateOutput: false })`.

HTTP-код успеха SHALL отображаться обратно в статус `Ok` той же таблицей,
которой пользуется транспорт. Полученный статус SHALL сверяться с
объявленными исходами операции (capability `declared-success-status`):
статус вне объявленного множества SHALL давать `InternalError` с телом
ответа в `cause`, а не молча схлопываться в `ok`.

У операции с развилкой `outputs(...)` тело SHALL валидироваться формой той
ветки, чей статус пришёл, а результат вызова SHALL быть дискриминированным
юнионом `Ok` по статусу: `outputs({ ok: User, accepted: JobAccepted })` даёт
`Ok<User, 'ok'> | Ok<JobAccepted, 'accepted'>`.

#### Scenario: Валидный ответ даёт `Ok`

- **WHEN** сервер ответил `200` телом, удовлетворяющим `output`, а операция
  объявляет `status: 'ok'` или не объявляет `status` вовсе
- **THEN** метод резолвится `Ok` со значением, прошедшим схему

#### Scenario: Ответ, не прошедший схему

- **WHEN** сервер ответил `200` телом, не удовлетворяющим `output`
- **THEN** метод резолвится `Fail` с кодом `internal_error`, а issue'ы схемы
  доступны в `cause`

#### Scenario: Валидация отключена явно

- **WHEN** клиент создан с `validateOutput: false`
- **THEN** тело отдаётся как есть, схема не применяется

#### Scenario: Пустой ответ

- **WHEN** сервер ответил `204` без тела, а операция объявлена без `output`
- **THEN** метод резолвится `Ok` со статусом `no_content`

#### Scenario: Код успеха вне объявленного множества

- **WHEN** операция объявляет `status: 'ok'`, а сервер ответил `201`
- **THEN** метод резолвится `InternalError`: ответ разошёлся с декларацией,
  и исходное тело доступно в `cause`

#### Scenario: Тело разбирается схемой своего исхода

- **WHEN** операция объявляет `output: outputs({ ok: User, accepted: JobAccepted })`,
  а сервер ответил `202` телом, удовлетворяющим `JobAccepted`
- **THEN** метод резолвится `Ok` со статусом `accepted`, а `result.value`
  типизирован `JobAccepted`

#### Scenario: Тело не сошлось со схемой своего исхода

- **WHEN** та же операция получила `202` телом, которое проходит схему
  `User`, но не проходит `JobAccepted`
- **THEN** метод резолвится `InternalError`: ответ разошёлся со схемой
  объявленного исхода

### Requirement: Отказ рематериализуется по коду и контракт результата закрыт

Ответ вне диапазона `2xx` SHALL разбираться как отказ по документу
RFC 9457: `type` несёт код отказа в форме `urn:error:<код>`, `detail` —
сообщение, расширение `details` — детали.

Если код, полученный отбрасыванием префикса `urn:error:`, объявлен в
`errors:` операции, клиент SHALL восстановить отказ этим определением:
`code` SHALL совпадать с проводным, `category` SHALL выводиться из кода
(его первый сегмент) — отдельного поля `status` у отказа нет, `message` —
из `detail`, `details` — из одноимённого расширения и SHALL
валидироваться схемой определения, если она объявлена. Идентичность SHALL
проверяться предикатом `.is(...)` определения — то есть по коду, а не по
`instanceof`. Члены `title` и `status` документа клиент SHALL NOT читать:
категория выводится из кода определения.

Во всех остальных случаях — незадекларированный код, `type` без префикса
`urn:error:`, отсутствующий `type`, тело не JSON, сетевой сбой, отмена,
невалидный по схеме ответ — клиент SHALL возвращать `InternalError` с
оригиналом в `cause`. Иных кодов клиент вводить SHALL NOT: множество
результата SHALL быть закрыто как `E ∪ InternalError`, симметрично
серверной границе.

Клиент SHALL NOT бросать исключение на транспортных сбоях и отказах операции у
`request`-операции: они выражаются возвращённым `Fail`.

#### Scenario: Задекларированный отказ восстанавливается

- **WHEN** сервер ответил `409` телом
  `{"type":"urn:error:conflict:email_taken","title":"Conflict","status":409,"detail":"Email taken","details":{"email":"a@b"}}`,
  а операция объявляет `errors: [EmailTaken]`
- **THEN** метод резолвится `Fail`, для которого `EmailTaken.is(result)`
  истинно, сообщение равно `Email taken`, а `details` типизированы схемой
  определения

#### Scenario: Незадекларированный код

- **WHEN** сервер ответил типом, код которого отсутствует в `errors:`
  операции
- **THEN** метод резолвится `InternalError`, а исходное тело доступно в
  `cause`

#### Scenario: Чужой тип проблемы

- **WHEN** сервер ответил документом, чей `type` не начинается с
  `urn:error:`
- **THEN** метод резолвится `InternalError`, а исходное тело доступно в
  `cause`

#### Scenario: Детали не сошлись со схемой определения

- **WHEN** код объявлен, но `details` не проходят схему определения
- **THEN** метод резолвится `InternalError`, а не отказом с невалидными
  деталями

#### Scenario: Сеть недоступна

- **WHEN** `fetch` отвергается сетевой ошибкой
- **THEN** метод резолвится `InternalError` с этой ошибкой в `cause`, а не
  бросает

### Requirement: Ambient-заголовки и `fetch` — конфиг создания клиента

Заголовки, общие для всех вызовов (авторизация, трассировка), SHALL
задаваться при создании клиента и SHALL приниматься в двух формах: записью
и функцией, вызываемой на каждый запрос (в том числе асинхронной).

Per-call заголовков в V1 SHALL NOT существовать: всё, что клиент передаёт
на каждый вызов, живёт в декларации (`input` плюс bind-карта).

Реализация `fetch` SHALL быть подменяемой опцией; по умолчанию SHALL
использоваться глобальный `fetch`.

Клиент SHALL принимать читалку трассы опцией `trace: () => string | undefined`
и SHALL ставить её значение заголовком `traceparent`. Заголовок, заданный
полем `headers`, SHALL быть сильнее. Читалка, вернувшая `undefined`, и
отсутствие опции SHALL давать запрос без этого заголовка.

Читалка приходит опцией, а не читается клиентом самостоятельно: пакет
зависит только от `@nestlingjs/operations` и собирается для браузера, а
ambient-контекст запроса живёт в `@nestlingjs/app`. Готовую читалку
SHALL экспортировать `@nestlingjs/app` под именем `traceparent`
(capability `trace-context`).

#### Scenario: Ротируемый Bearer-токен

- **WHEN** `headers` задан функцией, возвращающей свежий Bearer-токен
- **THEN** функция вызывается на каждый запрос, и заголовок в запросе
  свежий

#### Scenario: Подменённый `fetch`

- **WHEN** клиент создан с собственной реализацией `fetch`
- **THEN** все запросы идут через неё, и сеть не требуется

#### Scenario: Трасса продолжается за границей клиента

- **WHEN** клиент создан с `trace: traceparent`, а обработчик с трассой в
  контексте зовёт его метод
- **THEN** запрос несёт заголовок `traceparent` с тем же `traceId` и с
  идентификатором участка вызывающего в позиции родителя

#### Scenario: Читалка зовётся на каждый вызов

- **WHEN** два вызова клиента идут из разных запросов
- **THEN** заголовок каждого несёт трассу своего запроса

#### Scenario: Явный заголовок сильнее

- **WHEN** клиент создан с `headers: { traceparent: '…' }` и с опцией
  `trace`, а вызов идёт внутри трассируемого запроса
- **THEN** в запрос уходит значение из конфигурации

#### Scenario: Вне запроса заголовка нет

- **WHEN** метод клиента вызван из `@OnStart`
- **THEN** читалка возвращает `undefined`, и заголовка `traceparent` в
  запросе нет

#### Scenario: Без опции клиент трассу не ставит

- **WHEN** клиент создан без `trace`
- **THEN** заголовка `traceparent` в запросе нет

### Requirement: `makeClient` проверяет пригодность операций при создании

`makeClient` SHALL отвергать в момент создания клиента, называя ключ метода
в record'е:

- операция без секции `http:` — HTTP-адреса у неё нет;
- операция вида `event`;
- операция, у которой `input` или `output` объявлены потоковой формой
  (`stream`, `events`) либо `multipart`/`upload` — текст SHALL указывать,
  что streaming-клиент проектируется отдельно;
- `baseUrl`, не являющийся абсолютным URL.

Отложенная диагностика («упадёт при первом вызове») SHALL NOT применяться.

#### Scenario: Операция без `http:`

- **WHEN** в record передана операция без секции `http`
- **THEN** `makeClient` бросает ошибку, называя ключ метода и операцию

#### Scenario: Потоковая форма

- **WHEN** в record передана операция с `output: stream(Chunk)`
- **THEN** `makeClient` бросает ошибку, называя ключ метода и форму

#### Scenario: Относительный `baseUrl`

- **WHEN** передан `baseUrl: '/api'`
- **THEN** `makeClient` бросает ошибку в момент создания
