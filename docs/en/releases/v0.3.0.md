# 0.3.0

> All `@nestlingjs/*` packages ship as one version. The release carries
> the commits from the `v0.2.0` tag to the `v0.3.0` tag, 13–14 September
> 2026. An old name is removed together with its replacement: there are
> no aliases or wrappers in the packages.

## Upgrading

```bash
yarn up '@nestlingjs/*'
```

The version is one for all packages: a package of the previous version
does not work next to a new one. The Node requirement is the same, 24
and above. Three new packages are installed separately, as needed:

```bash
yarn add @nestlingjs/logging.pino pino  # a logger on top of pino
yarn add @nestlingjs/prometheus         # the metrics exposition
yarn add @nestlingjs/otel               # trace spans and a metrics push
```

`@nestlingjs/logging` arrives as a dependency of the kernel and needs no
separate installation. `pino` is a peer dependency of `^10.0.0`. The
application installs the OpenTelemetry exporters itself: `@nestlingjs/otel`
carries the SDK, but not the `exporter-*` packages. The full reference of
the environment is [compatibility.md](../compatibility.md).

## In brief

- The entry point is written `build(argv(process.argv))` instead of
  `assemble(load(RootConfig))`, and the composition of the process
  arrives as command line flags — [section](#build-and-run).
- Configuration bindings moved from `makeApp` to `run({ config })`, and
  the form of a binding is one, `bind()` — [section](#build-and-run).
- The server is declared by `server()` and is not listed in
  `transports:` — [section](#build-and-run).
- The success status is declared by the `status` field, and different
  bodies for different outcomes by the branching `outputs({ … })` —
  [section](#the-endpoint-declaration).
- An HTTP failure leaves as an RFC 9457 document under the
  `application/problem+json` media type —
  [section](#the-endpoint-declaration).
- The logger is declared by the `logging` option, and the kernel sets
  the correlation fields; the `@nestlingjs/logging` and
  `@nestlingjs/logging.pino` packages appeared — [section](#logging).
- A metric became a declaration with a DI token: `@nestlingjs/prometheus`
  gives the exposition, `@nestlingjs/otel` the push and the trace spans —
  [section](#metrics-and-traces).
- The plugin factory is named `make*` — [section](#names).
- There are three examples instead of six, and the documentation site has
  a new theme — [section](#examples-and-documentation).

## The entry point: before and after

Two files show most of the renames at once.

```typescript
// src/app.ts — 0.2.0
import { makeApp } from '@nestlingjs/app';
import { openapi } from '@nestlingjs/openapi';
import { zodConverter } from '@nestlingjs/schema.zod';
import { http, httpServer } from '@nestlingjs/transport.http';

const api = httpServer();

export const app = makeApp({
  features: [UsersFeature],
  plugins: [
    openapi({
      info: { title: 'Users API', version: '1.0.0' },
      converters: [zodConverter()],
    }),
  ],
  transports: [api, http({ server: api })],
  config: [[vault, appConfigKeys]], // process.env was always read last
  logger: pinoAdapter(pino()), // the application wrote the adapter itself
  metrics: prometheusExporter(), // and the metrics exporter too
});

// src/main.ts — 0.2.0
const cfg = load(RootConfig); // the section with APP_FEATURES, read before the build

await app.assemble({ ...cfg, includeDeps: true }).run();
```

```typescript
// src/app.ts — 0.3.0
import { makeApp } from '@nestlingjs/app';
import { pinoLogger } from '@nestlingjs/logging.pino';
import { makeOpenapi } from '@nestlingjs/openapi';
import { makePrometheus } from '@nestlingjs/prometheus';
import { http, server } from '@nestlingjs/transport.http';

const api = server();

export const app = makeApp({
  features: [UsersFeature],
  plugins: [
    makeOpenapi({ info: { title: 'Users API', version: '1.0.0' } }),
    makePrometheus(),
  ],
  transports: [http({ server: api })],
  logging: { logger: pinoLogger() },
});

// src/main.ts — 0.3.0
import { argv, bind, defaultSources } from '@nestlingjs/app';

await app.build(argv(process.argv)).run({
  config: [bind(vault, { keys: appConfigKeys }), ...defaultSources],
});
// node main.js --features users --include-deps
```

Each change is described separately below: what it is now, how to use
it, and where to read the details.

## Breaks silently

The compiler will not show these changes: the code builds and behaves
differently.

- The list in `run({ config })` replaces the default entirely, and the
  former implicit reading of `process.env` at the end of the list is
  gone — [section](#configuration-bindings-are-an-option-of-run).
- An empty value of a key means a missing value: `DB_POOL_MAX=` gives
  the default, not zero —
  [section](#zod-inside-the-framework-standard-schema-at-the-boundary).
- The HTTP failure body changed its form: there is no `code` field in
  it, and the failure code lives in the `type` member. A foreign client
  that reads `code` breaks at runtime —
  [section](#the-http-failure-body-is-an-rfc-9457-document).
- An `Ok` with a status outside the declared set is replaced by the
  boundary with `internal_error`: a call from JavaScript is not covered
  by types — [section](#the-success-status-is-a-field-of-the-declaration).
- The test run became quiet: `buildTest` brings the application up with
  the `silent` level, and the former output of a test is gone —
  [section](#testing).

## Build and run

### `build` instead of `assemble`

The method of the declaration that builds the application is called
`build`. The argument is called `BuildArgs`, the result `BuiltApp`. The
lifecycle phase `1 ASSEMBLE` is called `1 BUILD`, and the texts of
build failures name it the same way. The same word left the
neighboring packages: `assembleTest` became `buildTest`,
`assemblePayload` became `buildPayload`.

Together with the method, the vocabulary of the pipeline changed. One
function or class in the pipeline is called a step, and the types are
named after it: `PreStepFn`, `FinallyStepFn`, `DeferredPreStepFn`,
`StepResolver`, `InboxClaimStep`. The `testUnit` function from `@nestlingjs/testing` is
called `testBundle`: it brings up a feature or a plugin, not a step.
The full list is the [renames table](#renames) at the end.

> Upgrade: mechanical — `assemble` is replaced by `build`, and the
> vocabulary of the pipeline follows it by the [renames table](#renames).
> Why: [ideas.md, `[2026-09-13] Термины: шаг, токен семейства, build`](../../decisions/ideas.md#2026-09-13-%D1%82%D0%B5%D1%80%D0%BC%D0%B8%D0%BD%D1%8B-%D1%88%D0%B0%D0%B3-%D1%82%D0%BE%D0%BA%D0%B5%D0%BD-%D1%81%D0%B5%D0%BC%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D0%B0-build).

### The build argument comes from the command line

`argv(process.argv)` is a marker value from `@nestlingjs/app`. The
entry point passes the command line into `build`, `discover` or
`check` with it, and the build derives the schema of the flags from
the declaration. `--features` accepts `all` or feature names separated
by a comma, `--include-deps` adds the features whose operations the
selected ones call, and every switch becomes a flag with its own name
and the values from `makeSwitch`. An unknown flag, an unknown feature
and a value outside the list are a failure before phase 0. `--help`
prints the schema and exits the process with code 0.

```typescript
// src/main.ts — 0.2.0
const RootConfig = makeConfig('root', {
  features: from('APP_FEATURES', z.string().default('all')),
  docs: from('APP_DOCS', Docs.schema),
});

const cfg = load(RootConfig);

await app.assemble({ ...cfg, includeDeps: true }).run();
```

```typescript
// src/main.ts — 0.3.0
await app.build(argv(process.argv)).run();
// node main.js --features users --include-deps --docs off
// node main.js --help
```

The object form `build({ features: 'users', docs: 'off' })` stays: it
is used by tests and by an application with its own command-line
parsing. The string form `build('users')` and the array of names
`build(['users', 'billing'])` are removed. The `load()` function is
removed: its only role was reading a section before the build for the
sake of the build argument. The kernel no longer reads `process.argv`
or `process.env` itself: the entry point passes the first one as a
marker, the second is read by the `env()` source.

From here comes the guarantee recorded in
[guarantees.md](../guarantees.md): only the build argument determines
the composition of the process, the configuration does not affect it.
More detail is in [chapter 19](../guide/19-select.md).

> Upgrade: needs a decision — the composition of the process arrives
> either by the `argv()` marker or by the object form, for an application
> with its own parsing of the command line.
> Why: [ideas.md, `[2026-09-13] Аргумент сборки: argv() по схеме декларации`](../../decisions/ideas.md#2026-09-13-%D0%B0%D1%80%D0%B3%D1%83%D0%BC%D0%B5%D0%BD%D1%82-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B8-argv-%D0%BF%D0%BE-%D1%81%D1%85%D0%B5%D0%BC%D0%B5-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8).

### Configuration bindings are an option of `run()`

The `config:` field of `makeApp` is removed. The bindings of the
sources are accepted by the method that runs the application:
`run({ config })`. The same option exists on `check(args, { config })`
and `buildTest(app, { config })`.

```typescript
// src/main.ts — 0.2.0
const app = makeApp({
  features: [AppFeature],
  config: [
    [defaults, appConfigKeys],
    [runtime, runtimeConfigKeys],
  ],
}).assemble();

await app.run();
```

```typescript
// src/main.ts — 0.3.0
const app = makeApp({ features: [AppFeature] }).build();

await app.run({
  config: [
    bind(defaults, { keys: appConfigKeys }),
    bind(runtime, { keys: runtimeConfigKeys }),
    bind(env()),
  ],
});
```

There is one binding shape: `bind(source, { keys?, optional?, timeout? })`.
`keys` is the `.keys` of a section or a glob, `'*'` by default.
`optional` skips the binding if the source did not come up. `timeout`
limits the `init()` of the source, ten seconds by default. The
`[source, target]` tuple, the `ConfigInput` union, `isBinding()` and
`toBindings()` are removed.

Without the option, `run()` takes `defaultSources` — the public value
`[bind(env()), bind(dotenv('.env'), { optional: true })]`: the
environment ranks above the file, the file is optional. The list in
the option replaces the default entirely, so a custom source is
appended right next to it:
`config: [bind(vault, { keys }), ...defaultSources]`.

`env()` became an ordinary source: the kernel reads `process.env` only
inside it, there is no more implicit read at the end of the list.
`dotenv(path)` is a new kernel source built on `parseEnv` from
`node:util`; a missing file at a mandatory binding is a phase 0
failure with the path in the message.

`objectSource` moved to `@nestlingjs/testing` under the name
`vars(values, name?)`. A test application reaches the RUN phase:
`testApp.run()` opens the socket, `testApp.baseUrl(name?)` returns its
address. There is no default for the test root: without `config` a
test reads neither the environment nor the file. More detail is in
[chapter 7](../guide/07-config.md) and the recipe
["Configuration from a file and without a restart"](../recipes/config-sources.md).

> Upgrade: needs a decision — the list in `config` replaces the default
> entirely, so an own source is written next to `defaultSources`.
> Why: [ideas.md, `[2026-09-13] Конфигурация: привязки на run(), env() и dotenv() умолчанием, bind(), needs у источника`](../../decisions/ideas.md#2026-09-13-%D0%BA%D0%BE%D0%BD%D1%84%D0%B8%D0%B3%D1%83%D1%80%D0%B0%D1%86%D0%B8%D1%8F-%D0%BF%D1%80%D0%B8%D0%B2%D1%8F%D0%B7%D0%BA%D0%B8-%D0%BD%D0%B0-run-env-%D0%B8-dotenv-%D1%83%D0%BC%D0%BE%D0%BB%D1%87%D0%B0%D0%BD%D0%B8%D0%B5%D0%BC-bind-needs-%D1%83-%D0%B8%D1%81%D1%82%D0%BE%D1%87%D0%BD%D0%B8%D0%BA%D0%B0).

### The server is declared by `server()` and is not part of `transports:`

`httpServer()` is called `server()`, `httpServerKeys()` is called
`serverKeys()`. The default instance name stays `'default'`, the
configuration section stays the `http` family (`HTTP_PORT`,
`HTTP_HOST`).

```typescript
// src/app.ts — 0.2.0
export const api = httpServer();

export const app = makeApp({
  features: [UsersFeature, OpsFeature],
  transports: [api, http({ server: api }), mcp({ server: api })],
});
```

```typescript
// src/app.ts — 0.3.0
export const api = server();

export const app = makeApp({
  features: [UsersFeature, OpsFeature],
  transports: [http({ server: api }), mcp({ server: api })],
});
```

The `transports:` field accepts only transports. The server enters the
build through the transport's `server` reference: one server for two
transports is created once, and a server with no references is not
created at all. A server listed in the transports array is rejected on
the BUILD phase with a message naming the replacement. The
`TransportEntry` type and the `isTransport` predicate are removed.

> Upgrade: mechanical — `httpServer()` becomes `server()`, and the server
> itself leaves the list of transports.
> Why: [ideas.md, `[2026-09-13] Сервер: server(), не перечисляется в transports:`](../../decisions/ideas.md#2026-09-13-%D1%81%D0%B5%D1%80%D0%B2%D0%B5%D1%80-server-%D0%BD%D0%B5-%D0%BF%D0%B5%D1%80%D0%B5%D1%87%D0%B8%D1%81%D0%BB%D1%8F%D0%B5%D1%82%D1%81%D1%8F-%D0%B2-transports).

## The endpoint declaration

### The success status is a field of the declaration

The success status is declared by the top-level `status` field of
`httpEndpoint` and of the operation constructor. The `doc.status`
field is removed: the status is a contract of the response, not a
line of documentation. There is one default for the runtime, the
document and the client: `ok` when `output` is declared, `no_content`
without it.

```typescript
// src/users/operations.ts — 0.2.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: User,
  doc: { summary: 'Создать пользователя', status: 'created' },
});
```

```typescript
// src/users/operations.ts — 0.3.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: User,
  status: 'created',
  doc: { summary: 'Создать пользователя' },
});
```

A bare value from the handler gets the declared status. `Ok` is
parametrized by the status: `Ok<TValue, TStatus>`. `new Ok(value)`
gives `Ok<T, 'ok'>`, `Ok.created(value)` gives `Ok<T, 'created'>`,
`Ok.accepted(value)` gives `Ok<T, 'accepted'>`, `Ok.noContent()` gives
`Ok<null, 'no_content'>`. The boundary replaces an `Ok` with a status
outside the declared set with `internal_error`: a call from JavaScript
is not covered by the types.

A branching in the `output` slot declares different bodies for
different outcomes:

```typescript
// src/users/operations.ts — 0.3.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: outputs({ ok: User, created: User, no_content: none() }),
  // …
});
```

The keys of the branching are statuses from the kernel dictionary
(`ok`, `created`, `accepted`, `no_content`), the values are io shapes,
`none()` declares an outcome with no body. A handler with a branching
picks the outcome explicitly, returning `Ok.created(user)` or
`new Ok(user)`; a bare value does not compile under a branching, and
the result of the handler is a union over the `status` field. The
`stream` and `events` io shapes are declared only with a single
outcome.

The OpenAPI document prints a response for every declared outcome with
its own schema. The typed client validates the body with the schema of
the outcome that arrived, and rejects a code outside the declared set
as a mismatch with the declaration. More detail is in
[chapter 4](../guide/04-errors.md) and
[chapter 13](../guide/13-openapi-and-client.md).

> Upgrade: mechanical — `doc.status` rises to the top level of the
> declaration as the `status` field.
> Why: [deferred.md, `[2026-08-01] Типизированный успешный статус декларации`](../../decisions/deferred.md#2026-08-01-%D1%82%D0%B8%D0%BF%D0%B8%D0%B7%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9-%D1%83%D1%81%D0%BF%D0%B5%D1%88%D0%BD%D1%8B%D0%B9-%D1%81%D1%82%D0%B0%D1%82%D1%83%D1%81-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8).

### The HTTP failure body is an RFC 9457 document

The HTTP boundary answers a failure with a Problem Details document
under the `application/problem+json` media type.

```bash
# 0.2.0
curl localhost:3000/users/9
# {"error":"User 9 not found","code":"not_found:user","details":{"id":"9"}}
```

```bash
# 0.3.0
curl -i localhost:3000/users/9
# HTTP/1.1 404 Not Found
# content-type: application/problem+json
#
# {"type":"urn:error:not_found:user","title":"Not Found","status":404,
#  "detail":"User 9 not found","details":{"id":"9"}}
```

There is no `code` field in the body: the failure code lies in the
`type` member.

| Member | What it carries |
|---|---|
| `type` | the failure code with the `urn:error:` prefix |
| `title` | the HTTP status phrase |
| `status` | the HTTP code as a number |
| `detail` | the failure message |
| `details` | the details by the schema of the definition |
| `stack` | an extension, only with `exposeErrorDetails` |

There is one shape for all three places where the boundary writes a
failure: the response of the handler, an error before the pipeline (a
broken JSON body, an exceeded `maxBodySize`) and the `event: error`
frame in SSE.

The typed client from `@nestlingjs/client` restores a failure from the
document, and the OpenAPI document describes failures with the
`application/problem+json` media type. The format itself lives in
`@nestlingjs/operations` — `PROBLEM_MEDIA_TYPE`, `PROBLEM_TYPE_PREFIX`,
`problemOf`, `problemTypeOf`, `problemTitleOf` and the
`ProblemDocument` type — and is re-exported by the transport. The
NATS, CLI and MCP transports serialize a failure as before.

> Upgrade: needs a decision — an own consumer of the API reads the failure
> code from the `type` member; the typed `@nestlingjs/client` moves by
> itself.
> Why: [deferred.md, `[2026-07-14] Wire-формат ошибок: RFC 9457`](../../decisions/deferred.md#2026-07-14-wire-%D1%84%D0%BE%D1%80%D0%BC%D0%B0%D1%82-%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA-rfc-9457-problemjson).

### `errorsOf` pulls in the failures of a neighboring operation

`errorsOf(operation)` from `@nestlingjs/operations` returns the
`errors:` list of an operation as the same value; the type of the
result keeps the union of the concrete `makeFail` definitions.

```typescript
// src/users/operations.ts — 0.2.0: the neighbor's failure was copied by hand
import { AddressRejected } from '../addresses/operations.js';

errors: [EmailTaken, AddressRejected, Unauthorized],
```

```typescript
// src/users/operations.ts — 0.3.0
errors: [EmailTaken, ...errorsOf(CheckAddress), Unauthorized],
```

The list is read from the declaration, so a new failure of
`CheckAddress` reaches `CreateUser` without an edit. More detail is in
[chapter 14](../guide/14-features.md).

## Logging

### The `logging` option and the `@nestlingjs/logging` package

The root's `logger:` option is replaced by
`logging: { logger?, fields? }`. `logger` is a ready implementation of
`Logger`, the default is unchanged: the standard logger into `stderr`.
`fields` is a list of context variables whose values the kernel mixes
into every record. The default is
`[RequestId, logField(Trace, 'traceId', (trace) => trace.traceId)]`.

```typescript
// src/app.ts — 0.2.0
export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logger: myLogger, // only the standard logger wrote requestId and traceId
});
```

```typescript
// src/app.ts — 0.3.0
export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logging: {
    logger: myLogger,
    fields: [
      RequestId,
      logField(Trace, 'traceId', (trace) => trace.traceId),
      logField(TenantId, 'tenant'),
    ],
  },
});
```

The kernel sets the correlation fields with a decorator around the
logger, so any implementation gets `requestId` and `traceId` without
knowing the internals of the kernel. `logField(Var, name, select?)`
sets the name of the field and picks the needed part from the value; a
variable with no wrapper gives a field named after the variable. A
plugin declares its own fields with the `logFields` field; two fields
with the same name are a build failure naming those who declared them.

The `Logger` interface and the `Fields`, `LogLevel`, `LogMethod` types
moved into the `@nestlingjs/logging` package with no dependencies. The
same package holds `makeConsoleLogger({ level?, format? })`, the
standard logger for a script outside the application, and the line
format as a single instance: `formatLine`, `serializeError`, the
`LogEntry` type. `@nestlingjs/app` re-exports the types and
`makeConsoleLogger`; `Logger$` and `RootLogger$` stay in the kernel.

The `nestlingLog` section accepts the `silent` level. The `buildTest`
test root brings up the application with it by default; a test sets
its own level through `config`. More detail is in
[chapter 9](../guide/09-logging.md).

> Upgrade: mechanical — `logger:` becomes `logging: { logger }`, and the
> correlation fields leave an own implementation: the kernel sets them.
> Why: [ideas.md, `[2026-09-13] Логгер: опция logging, пакет @nestlingjs/logging, поля-декларации, pino сателлитом`](../../decisions/ideas.md#2026-09-13-%D0%BB%D0%BE%D0%B3%D0%B3%D0%B5%D1%80-%D0%BE%D0%BF%D1%86%D0%B8%D1%8F-logging-%D0%BF%D0%B0%D0%BA%D0%B5%D1%82-nestlingjslogging-%D0%BF%D0%BE%D0%BB%D1%8F-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8-pino-%D1%81%D0%B0%D1%82%D0%B5%D0%BB%D0%BB%D0%B8%D1%82%D0%BE%D0%BC).

### `@nestlingjs/logging.pino`

A package with one value: `pinoLogger({ level?, format?, pino? })`
returns a `Logger` on top of a pino instance.

```typescript
// src/app.ts
import { pinoLogger } from '@nestlingjs/logging.pino';

export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logging: {
    logger: pinoLogger({ format: 'json', pino: { redact: ['password'] } }),
  },
});
```

Records leave into `stderr` through a synchronous writer. The `text`
format matches the standard logger byte for byte: one function prints
the line. The `json` format is written by pino with its own line, with
the same keys. `level` also accepts pino's levels: `trace` maps onto
`debug`, `fatal` onto `error`. The `pino` field passes the remaining
options to the library. The keys the format rests on (`level`,
`timestamp`, `formatters`, `base`, `messageKey`, `errorKey`,
`transport`, `serializers.err`) are taken by the adapter and rejected
when the logger is created. `pino` is a peer dependency `^10.0.0`.

## Metrics and traces

### A metric is a declaration

A metrics group is declared by the `makeMetrics(prefix, { … })` value.
The name of a metric adds up from the prefix of the group and the key
of the entry, there are no other names.

```typescript
// src/orders/orders.service.ts — 0.2.0
@Component([Metrics$.auto])
export class OrdersService {
  constructor(private readonly metrics: Metrics) {}

  create(): void {
    this.metrics.counter('orders.created'); // the series appeared at the first write
  }
}
```

```typescript
// src/orders/orders.metrics.ts — 0.3.0
import { counter, histogram, makeMetrics, open } from '@nestlingjs/app';

export const OrdersMetrics = makeMetrics('orders', {
  created: counter({
    help: 'Created orders',
    attributes: { tier: ['free', 'paid'], source: open },
  }),
  'checkout.duration': histogram({
    help: 'Checkout duration',
    unit: 'ms',
    buckets: [5, 25, 100, 500, 1000],
  }),
});

// src/orders/orders.service.ts — 0.3.0
@Component([OrdersMetrics])
export class OrdersService {
  constructor(private readonly metrics: MetricsOf<typeof OrdersMetrics>) {}

  create(): void {
    this.metrics.created.add({ tier: 'paid', source: 'web' });
    this.metrics['checkout.duration'].record(42);
  }
}

// src/orders/orders.feature.ts — 0.3.0
export const OrdersFeature = makeFeature({
  name: 'orders',
  metrics: [OrdersMetrics],
  providers: [OrdersService],
  endpoints: [CreateOrder],
});
```

An attribute is declared by a list of values or by the `open` mark.
The list gives the set of series at build: the exposition shows zeros
before the first request, and a value outside the list does not
compile. The group serves as a DI token: `@Component([OrdersMetrics])`
gives a writer where a metric is picked by a field, and an undeclared
write is inexpressible. The group is contributed with the `metrics:`
field of a feature, a module, a plugin or the root; the catalog is
collected on the BUILD phase, a name clash between groups is a build
failure.

The kernel holds what accumulates. `MetricsStore$` is a graph node
that is always present, with a single output, `snapshot()`. The four
kernel metrics are declared by the same mechanism, instrumentation is
always on. The `makeApp({ metrics })` option, the `RootMetrics$` and
`Metrics$` DI tokens, the `Metrics` interface and `spyMetrics()` from
`@nestlingjs/testing` are removed. A test reads the snapshot:
`testApp.metrics.counter(OrdersMetrics.members.created, { tier: 'paid' })`;
a unit test of a class without a container takes the writer from
`metricsFor`.

The exposition format is the `@nestlingjs/prometheus` package.
`makePrometheus({ path? })` in `plugins:` gives `GET /metrics` on the
socket of the application; the endpoint is marked `detached` and does
not reach the API document. A histogram is printed as `_bucket`,
`_sum` and `_count` series with the buckets from the declaration. More
detail is in [chapter 22](../guide/22-metrics.md).

> Upgrade: needs a decision — the name of a metric is made of the prefix
> of the group and the key of the entry, and attributes are declared by a
> list of values.
> Why: [ideas.md, `[2026-09-14] Метрика — декларация: группа-значение, каталог сборки, store в ядре`](../../decisions/ideas.md#2026-09-14-%D0%BC%D0%B5%D1%82%D1%80%D0%B8%D0%BA%D0%B0--%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D1%8F-%D0%B3%D1%80%D1%83%D0%BF%D0%BF%D0%B0-%D0%B7%D0%BD%D0%B0%D1%87%D0%B5%D0%BD%D0%B8%D0%B5-%D0%BA%D0%B0%D1%82%D0%B0%D0%BB%D0%BE%D0%B3-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B8-store-%D0%B2-%D1%8F%D0%B4%D1%80%D0%B5).

### `@nestlingjs/otel`: trace spans and metric push

A satellite for exporting telemetry. The
`otel({ service, version?, traces?, metrics?, intervalMs? })` entry
point gives two parts: the `spans` pipeline layer and the `plugin`
plugin.

```typescript
// src/telemetry.ts
import { otel, Span } from '@nestlingjs/otel';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

export const telemetry = otel({
  service: 'orders',
  version: '1.0.0',
  traces: new OTLPTraceExporter(),
});

// src/observability.ts
export const traced = compose(
  makePipeline().pre(withRequestId()).pre(withTracing()),
  telemetry.spans,
);

// src/app.ts
export const app = makeApp({
  features: [OrdersFeature],
  plugins: [telemetry.plugin],
  transports: [http({ server: api })],
  policies: [everyEndpoint().hasVar(Span, 'span')],
});
```

The layer opens a span with a pre-step and closes it with a `.finally`
step, deriving the status from the outcome. The identifiers come from
the `Trace` variable that `withTracing()` puts in, so the spans of
neighboring processes converge into one tree; a layer without
`withTracing()` higher in the composition does not compile. The
`everyEndpoint().hasVar(Span)` policy turns a forgotten layer into a
build failure. A service reads the span through `Ctx(Span)` and sets
attributes and events.

The plugin closes the exporters on shutdown. With the `metrics` option
it reads `MetricsStore$.snapshot()` once every `intervalMs` (60 000 ms
by default) and sends the snapshot to a `PushMetricExporter`; the last
snapshot leaves on shutdown, and a failure of the exporter does not
break the shutdown. The buckets, `help` and `unit` come from the
declaration, so the push and the Prometheus exposition show the same
thing. The application sets up the exporters itself: the package
carries the SDK (`@opentelemetry/sdk-trace-base`, `sdk-metrics`,
`resources`), but not the `exporter-*` packages. More detail is in
[chapter 23](../guide/23-tracing.md).

> Why: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), point 2.

## Schemas

### zod inside the framework, Standard Schema at the boundary

The public boundary stays on Standard Schema: an application writes
schemas in whatever it wants, no public type names zod. The schemas
the framework itself writes are written in zod: the configuration
sections of the kernel and the satellites, the fact records of `inbox`
and `outbox`. Everything the framework does with zod is collected in
`@nestlingjs/schema.zod`: `zodConverter()`, the `int()` and `flag()`
field builders, `withZodDefault()`, the `fromType`, `fromScratch` and
`makeModel` models. The `@nestlingjs/models` package is removed, its
three names moved here.

The field builders return an open zod value, the caller adds the
boundary and the default:

```typescript
// src/db/db.config.ts — 0.2.0
poolMax: int(10, 1),
```

```typescript
// src/db/db.config.ts — 0.3.0
poolMax: int().min(1).default(10),
enabled: flag().default(true),
```

The rule "an empty value of a key is a missing value" moved from
hand-written helpers into one point of the kernel: `DB_POOL_MAX=`
gives the default, not zero.

The zod converter is the default for `makeOpenapi()`, `mcp()` and
`cli()`: the `converters: [zodConverter()]` line is no longer needed,
the `converters` field stays for schemas of another vendor. The
declared plugin builds the OpenAPI document:

```typescript
// scripts/openapi.ts — 0.2.0
const { endpoints } = app.discover(args);
const document = buildOpenApiDocument(endpoints, openapiOptions);
```

```typescript
// scripts/openapi.ts — 0.3.0
const document = openapi.document(app.discover(argv(process.argv)));
```

`buildOpenApiDocument` is removed, `info` is written in one place.
`describeConfig({ converters: [zodConverter()] })` returns a JSON
Schema for the framework's sections too.

> Upgrade: mechanical — `int(10, 1)` is written `int().min(1).default(10)`,
> and the `converters: [zodConverter()]` line is removed.
> Why: [ideas.md, `[2026-09-13] Схемы: Standard Schema на границе, zod внутри; один пакет schema.zod`](../../decisions/ideas.md#2026-09-13-%D1%81%D1%85%D0%B5%D0%BC%D1%8B-standard-schema-%D0%BD%D0%B0-%D0%B3%D1%80%D0%B0%D0%BD%D0%B8%D1%86%D0%B5-zod-%D0%B2%D0%BD%D1%83%D1%82%D1%80%D0%B8-%D0%BE%D0%B4%D0%B8%D0%BD-%D0%BF%D0%B0%D0%BA%D0%B5%D1%82-schemazod).

## Embedding into a foreign process

`@nestlingjs/transport.http` got a transport with no server.
`adapter({ name? })` is declared instead of `http()`, the
`httpEndpoint` declarations move onto it with no edits, and the
application opens no socket.

```typescript
// src/app/api/[[...path]]/route.ts
import { adapter, toFetchHandler } from '@nestlingjs/transport.http';

const app = makeApp({ features: [Users], transports: [adapter()] }).build();

await app.run({ signals: false });

const handler = toFetchHandler(app);

export const GET = handler;
export const POST = handler;
```

The handler is taken from the running application in two shapes.
`toFetchHandler(app, { name? })` returns
`(Request) => Promise<Response>` for Next.js, Hono and Elysia.
`toNodeHandler(app, { name? })` returns
`(req, res) => Promise<boolean>` for Express and Fastify, where
`false` means "not the application's route". Both work with every io
shape: `value`, `stream`, `events`, `multipart`, `rawBody`.

`BuiltApp` got a `transports: ReadonlyMap<string, ITransport>` map,
paired with `servers`. `run({ signals: false })` sets no `SIGTERM` and
`SIGINT` handlers: the signals stay with the process owner. Parsing
the request and framing the response are described by the package's
`HttpSource` and `HttpSink` interfaces; `node:http` and `fetch` are
their two implementations. Runtimes other than Node are outside the
boundary for now: `multipart` reads through `busboy`, the body is
collected into a `Buffer`. More detail is in the recipe
["An application inside a foreign process"](../recipes/embedded.md).

> Why: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), point 4.

### Vocabulary

One function or class in the pipeline is called a step. One DI token
of a family is called a "family token": `Logger$('orders')` is itself
a DI token.
Both [glossaries](../glossary.md) are updated, the former words stand
in the column of forbidden synonyms.

## The subscription registry: `identity` is a context variable

`makeSubscriptions({ identity })` accepts a context variable. The
registry reads its value by key and knows nothing of the shape of
`input`.

```typescript
// src/ops/ops.plugin.ts — 0.2.0
identity: (ctx) => (ctx.input as { requestId?: string }).requestId,
```

```typescript
// src/ops/ops.plugin.ts — 0.3.0
identity: RequestId,
```

A function stays the second shape and is typed by the accumulated
context. A key from several variables is built by
`computed([TenantId, UserId], (_ctx, tenant, user) => …)`; the same
shape works in `labels`. `@nestlingjs/app` exports the `isContextVar`
predicate. The `everyEndpoint({ … }).hasVar(RequestId)` policy checks
that the variable is present at every endpoint. More detail is in the
recipe ["Who is connected right now and how to disconnect them"](../recipes/ops.md).

> Upgrade: mechanical — a function over `ctx.input` is replaced by a
> context variable; the form with a function stayed as the second one.

## Removed

- `withIdentity`, `withPermissions` and `withRequestLogging` from
  `@nestlingjs/app`. There is no replacement: an authentication layer
  with a typed `Caller` variable is a separate piece of work.
- `load()`, the string form and the array of names of `build()`.
- The `config:`, `logger:` and `metrics:` fields of `makeApp`.
- `objectSource` and `ObjectSource` from `@nestlingjs/app`; in
  `@nestlingjs/testing` their place is taken by `vars`.
- `TransportEntry` and `isTransport`.
- `doc.status`.
- `RootMetrics$`, `Metrics$`, the `Metrics` interface, `spyMetrics()`.
- `buildOpenApiDocument` and the `@nestlingjs/models` package.
- The builder signatures `int(fallback, min)` and `flag(fallback)`.

## Testing

- `buildTest(app, options)` instead of `assembleTest`; the `config`
  option is a list of `bind()`, like in `run()`.
- `testBundle` instead of `testUnit`.
- `vars(values, name?)` is a source from an object, bound through
  `bind(vars({ … }))`.
- `testApp.run()` reaches the RUN phase, `testApp.baseUrl(name?)`
  returns the address of the server.
- A test run is quiet: the `silent` level by default.
- `testApp.metrics` and `metricsFor` instead of `spyMetrics()`.
- The `testing` condition for the `@nestlingjs/app/testing` subpath is
  turned on in vitest by the `resolve.conditions` field:
  `['testing', 'node', 'node-addons', 'import', 'default']`.

More detail is in [chapter 8](../guide/08-testing.md) and
[chapter 18](../guide/18-testing-features.md).
