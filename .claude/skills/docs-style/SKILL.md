# Стиль текстов Nestling

Один читатель, один порядок изложения, один словарь. Всё остальное —
следствия.

## Для кого пишем

Читатель — backend-разработчик на TypeScript. Он знает Nest или Express,
умеет читать код, но не участвовал в наших обсуждениях и не читал
`docs/decisions/`. Всё, что нельзя вывести из общей практики, должно быть
определено: в документе при первом употреблении или в
[`docs/glossary.md`](../../../docs/glossary.md).

Проверка абзаца: покажите его такому читателю отдельно от документа. Если
для понимания нужно знать историю решения или наш внутренний словарь —
абзац написан для нас, а не для него.

## Порядок изложения

1. **Что** это и что делает.
2. **Как** этим пользоваться — код.
3. Нюансы и ограничения.
4. **Почему** так — одна-две фразы и ссылка на запись в `decisions/ideas.md`.

«Почему» никогда не идёт раньше «что». Абзац, который начинается с
обоснования или с отрицания («Поля X здесь нет, потому что…»), нужно
переставить: сначала описать, что есть.

## Предложения

- Одно предложение — одна мысль. Точка с запятой или второе тире в
  предложении означают, что это два предложения.
- В каждом предложении есть глагол. Конструкция «X — Y» без глагола
  допустима только как определение при первом упоминании термина.
- Не больше одного тире на предложение.
- Скобки — только для короткого пояснения. Вложенных скобок и стрелок
  внутри скобок не бывает.
- Стрелки `→` — только в таблицах, схемах и коде. В прозе — словами.
- Список — для однородных вещей. Абзац из трёх связанных мыслей списком
  не становится.

## Слова

- Термины берутся из [`docs/glossary.md`](../../../docs/glossary.md).
  Один термин — одно слово, всегда одно и то же. Нет термина в глоссарии —
  определите его при первом употреблении и добавьте в глоссарий.
- Запрещённые слова и их замены — в таблице ниже. Их находит линтер.
<!-- docs-style: off -->
- Метафора допустима, только если рядом стоит буквальное объяснение.
  Нет: «шина — репетиция провода». Да: «in-process шина копирует сообщения
  и контекст так же, как это делал бы брокер».
<!-- docs-style: on -->
- Афоризм не заменяет объяснение. Нет: «имя и есть адрес». Да: «У
  контракта нет отдельного поля версии: версия входит в имя
  (`users.create.v2`), потому что имя используется как subject шины».
- Латиницей пишем идентификаторы из кода и устоявшиеся термины без
  русского аналога: endpoint, discovery, fail-fast, composition root,
  Standard Schema. Остальное — по-русски: пайплайн, юнит, хендлер, фича,
  транспорт, контейнер.

## Чего не пишем

- **Спора с невидимым оппонентом.** «Поля X нет и не будет», «различие
  ложное», «слово убрано из словаря» — убрать. Если читатель с опытом Nest
  ждёт X, хватит одной фразы: «`forwardRef` нет: циклическая зависимость —
  ошибка сборки». Аргументы живут в `decisions/ideas.md`.
- **Описания через отрицание.** Сначала что есть, потом, если нужно, чего
  нет.
- **Истории решения** в `design/`, `guide/`, README и комментариях. Ей
  место в `decisions/`.
- **Оценок** вместо описания: «здоровый дефолт», «честный кадр»,
  «правильный способ». Описываем поведение и его следствия.

## Оформление

- Жирный — не больше одного на раздел, только для предупреждения или
  инварианта, который читатель обязан знать. Не для интонации.
- Курсив не используем.
- В обратных кавычках — идентификаторы (`assemble`, `.keys`), не обычные
  слова.
- Заголовок называет предмет («Реализация контракта»), а не тезис
  («Реализация — обычная декларация»).

## По типам текстов

### `docs/design/` — целевое состояние

Безлично, в настоящем времени, поведение описывается как факт. Структура:
назначение подсистемы (два-три абзаца) → механизм по разделам → границы с
соседними подсистемами. Плашка «Целевое состояние V1» обязательна.

Обоснования и отвергнутые варианты в design-доке — лишние. Если запись
`ideas.md` из плашки уже содержит их — удалить, оставив ссылку. Если не
содержит — перенести в `ideas.md` новой записью (журнал append-only) и
сослаться на неё из плашки.

### `docs/guide/` — по текущему API

Обращение на «вы», императив: «объявите», «откройте». Раздел начинается с
кода из примера, за кодом идёт объяснение. Плашка «сверено с кодом
`<пример>` (дата)» обязательна; дату меняйте только после фактической
сверки сниппетов с кодом примера.

### README пакета

Для того, кто пользуется пакетом сегодня. Структура: одна фраза «что это»
→ плашка статуса со ссылками на design-док и гайд → установка →
минимальный пример → основные понятия → справочник API (таблицы) →
границы пакета (чего он не делает, одной строкой, без аргументов).
Язык — русский.

### JSDoc

- Первая строка — что делает, глагол в настоящем времени: «Собирает
  приложение», «Копирует контекст вызова». Для типов и интерфейсов —
  что это: «Отчёт структурной проверки».
- Дальше — контракт: аргументы, возвращаемое значение, ошибки,
  инварианты, которые обязан соблюдать вызывающий.
- «Почему» — одна фраза и только если без неё код удивляет. Длиннее —
  ссылка на `docs/design/<док>.md`.
- Шапка файла: что в файле лежит и как части связаны. Не манифест.

### Комментарии в коде и тестах

- Строчный комментарий говорит то, чего не видно из кода: неочевидное
  условие, причина обходного пути, ссылка на инвариант.
- В тестах комментарий называет проверяемое поведение. Название `it(...)`
  тоже: глагол и поведение, без философии.
- Сообщение ошибки: что не так → где → как починить. Без метафор.

## Чек-лист перед завершением

1. `node .claude/skills/docs-style/scripts/lint.mjs <файлы>` — 0
   запрещённых слов.
2. Первый абзац каждого раздела отвечает «что это», а не «почему не иначе».
3. В каждом предложении есть глагол (кроме определений).
4. Ни одного `→` в прозе.
5. Жирный — не больше одного на раздел.
6. Каждый термин — из глоссария или определён при первом употреблении.
7. Факты не изменились: имена API, сигнатуры, поведение — те же, что до
   правки. Стиль — не повод менять смысл.
8. Ссылки и плашки на месте: `yarn docs:audit quick` — 0 ERROR.

## Примеры

<!-- docs-style: off -->
**Design-док, фаза жизненного цикла.**

Было: «**3 · WIRE** — декларации endpoint'ов гасят зависимости контейнером
(`endpoint.resolve(resolver)`: токены `deps`, класс-хендлер, классы-юниты
пайплайна); таблица `pattern→handler` строится по одному `dispatch` на
транспорт. **`dispatch` рождается здесь**, но никому ещё не передан —
кроме одного явного шага: вызыватели контрактов связываются с `dispatch`
шины, и шина подписывается на subject'ы своих маршрутов. Иначе `@OnStart`,
который уже вправе звать порт, оказался бы раньше go-live шины. Вызов
порта до WIRE — внятная ошибка.»

Стало: «**3 · WIRE.** Каждая декларация endpoint'а получает свои
зависимости из контейнера: токены из `deps`, класс хендлера, классы юнитов
пайплайна. Затем для каждого транспорта собирается таблица «паттерн →
хендлер» — объект `dispatch`. На этой фазе `dispatch` уже существует, но
транспортам ещё не передан.

Единственное исключение — шина контрактов. Она получает свой `dispatch`
прямо здесь и подписывается на subject'ы своих маршрутов, чтобы на
следующей фазе порты уже можно было вызывать из `@OnStart`. Вызов порта
раньше WIRE (например, из `@OnInit`) завершается ошибкой.»

**Гайд, вступление.**

Было: «Соседняя фича зовётся не токеном её сервиса, а **контрактом**.
Разница видна в день, когда фичи разъедутся по процессам: общий токен
переезд не переживёт, контракт переживёт — потому что вызов уже async, уже
Fail-able и уже не транзакционен.»

Стало: «Когда одной фиче нужна операция другой, она не инжектит чужой
сервис по токену, а вызывает его через **контракт**: описание операции с
именем, схемами входа и выхода и списком ошибок.

Пока обе фичи работают в одном процессе, разница невелика. Она становится
важной, когда фичи разносят по разным сервисам. Прямой вызов сервиса тогда
придётся переписывать: он синхронный, бросает исключения и выполняется в
транзакции вызывающего. Вызов через контракт с самого начала асинхронный,
возвращает ошибки значением `Fail` и в транзакцию вызывающего не входит —
поэтому при переезде код фичи не меняется.»

**JSDoc, шапка файла.**

Было: «Шина: `IMessageBus` как LCD глаголов брокера и `InProcessBus` как
одно значение с двумя способностями. Дихотомия «messaging vs transports»
ложная: шина — транспорт с двумя способностями. […] Ровно та форма, которую
примет NATS-транспорт, — поэтому V1-шина не заглушка, а репетиция
интерфейса.»

Стало: «Шина сообщений.

`IMessageBus` — минимальный интерфейс брокера: только операции, которые
есть у любого брокера (`request`, `publish`, `subscribe`). Специфика
конкретного брокера (JetStream, ack, wildcard-subject'ы) сюда не входит.

`InProcessBus` — реализация шины внутри одного процесса. Она же является
транспортом (`ITransport`): в `serve(dispatch, signal)` подписывает
маршруты реализаций контрактов на их subject'ы, а через `request`/`publish`
отправляет вызовы портов. NATS-транспорт реализует те же два интерфейса,
поэтому замена in-process шины на брокер не меняет код приложения.»

## Линтер

```bash
node .claude/skills/docs-style/scripts/lint.mjs                      # всё по умолчанию
node .claude/skills/docs-style/scripts/lint.mjs docs/guide/11-features.md packages/nestling.ports/src
node .claude/skills/docs-style/scripts/lint.mjs --warn               # плюс стрелки и цепочки тире
```

Проверяет прозу Markdown (без code-блоков), комментарии `.ts` и заголовки
тестов (`describe`/`it`/`test`).
`docs/history/` и `docs/decisions/` не проверяются: первая папка
заморожена, вторая — append-only. Findings переносите в отчёт как есть.
Список слов — массив `BANNED` в скрипте; новое слово-паразит добавляйте
туда вместе с заменой и в таблицу выше.
