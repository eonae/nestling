## Context

Корневой логгер создаётся на фазе 0 в `App.#bootstrap`: это либо значение
опции `logger`, либо `ConsoleLogger` от снимка секции `nestlingLog`. Тот же
объект регистрируется провайдером значения под `RootLogger$`, а члены
`Logger$(scope)` строятся как `root.child({ scope })`.

Поля корреляции ставит `ConsoleLogger`. В методе `#write` он зовёт
`ambientRequestId()` и `ambientTrace()` — внутренние функции
`pipeline/core/context/reader.ts`, которые читают ячейку запроса мимо
графа. Из пакета они не экспортируются, поэтому логгер из опции `logger`
пишет записи без `requestId` и `traceId`.

Интерфейс `Logger`, `Fields`, `LogLevel` и `LogMethod` объявлены в
`packages/nestling.app/src/logger/interface.ts` и экспортируются из
`@nestlingjs/app`. Реализация `ConsoleLogger` приватна: наружу идут
интерфейс, DI-токены и `logConfigKeys`.

Ограничения, которые держит любое решение:

- корень существует раньше графа и не может зависеть от его узлов;
- объект корня один на всё приложение: записи фаз 0 и 1 и записи фазы RUN
  уходят в него же;
- подмена `[RootLogger$, spy.logger]` в тестовом прогоне продолжает
  перехватывать записи всех членов семейства.

## Goals / Non-Goals

**Goals:**

- Любая реализация `Logger` получает поля корреляции, не зная внутренностей
  ядра.
- Состав полей объявлен: корень называет свои, плагин — свои.
- Интерфейс логгера доступен пакету без зависимости от `@nestlingjs/app`.
- Тестовый прогон молчит, пока тест не попросит записи.
- Примеры пишут логгером.

**Non-Goals:**

- Сателлит `@nestlingjs/logging.pino`.
- Новые уровни записи и новые формы вызова.
- Редакция значений, сериализаторы и семплирование в штатном логгере.
- Перенос `Logger$` и `RootLogger$` из `@nestlingjs/app`.

## Decisions

### Опция `logging: { logger?, fields? }`

Поле `logger:` корня заменяется словарём `logging`. Логгер и состав его
полей — одна настройка, и стоять они должны рядом.

```typescript
export const app = makeApp({
  features: [UsersFeature],
  logging: {
    logger: pinoLogger(),
    fields: [RequestId, logField(Trace, 'traceId', (t) => t.traceId)],
  },
});
```

Оба поля необязательны. Без `logger` корнем служит штатный логгер от
снимка секции `nestlingLog`. Без `fields` список берётся умолчанием —
`[RequestId, logField(Trace, 'traceId', (t) => t.traceId)]`: те же два
поля, что ставит сегодняшний `ConsoleLogger`. Пустой список `fields: []`
отключает корреляцию.

Альтернатива — оставить `logger:` и добавить соседнее поле `logFields:`.
Отвергнута: два поля корня об одном предмете расходятся при первой правке,
а порядок их чтения читателю корня не виден.

### Декоратор корреляции вместо чтения контекста реализацией

Корень оборачивается декоратором сразу после создания, в `#bootstrap`.
Декоратор читает значения объявленных переменных из ячейки запроса и
подмешивает их в поля записи, после чего зовёт метод обёрнутого логгера.

```typescript
const root = withLogFields(spec.logging?.logger ?? makeKernelLogger(reader), plan);
```

`child(bindings)` декоратора возвращает `withLogFields(inner.child(bindings), plan)`:
дочерний логгер несёт те же поля, а привязки складывает обёрнутая
реализация. Двойного подмешивания не происходит — поля ставит только
внешний слой.

Поле корреляции не ставится, если имя занято полем вызова: явное значение
вызывающего важнее значения из контекста. Вне запроса ячейки нет, и полей
в записи тоже нет.

`ConsoleLogger` перестаёт звать `ambientRequestId` и `ambientTrace`.
Функция `ambientTraceId` удаляется: её единственным потребителем был
`ConsoleLogger`. Вместо двух именованных читалок остаётся одна внутренняя
`ambientValue(key)`, которая отдаёт значение поля ячейки по ключу
переменной.

Альтернатива — экспортировать `ambientRequestId` и `ambientTrace` наружу.
Отвергнута: каждая реализация логгера повторяла бы чтение контекста, а
состав полей задавался бы кодом сателлита, а не декларацией приложения.

### `logField(Var, name, select?)` — переименование и проекция

Переменная в списке `fields` без обёртки даёт поле с именем переменной и
значением целиком: `RequestId` — это `requestId: 'abc'`. Обёртка задаёт имя
и, если нужно, проекцию значения:

```typescript
logField(Trace, 'traceId', (t) => t.traceId);
logField(Caller, 'user', (c) => c.id);
```

Третий аргумент нужен переменным-объектам. `Trace` несёт `traceId`,
`spanId` и `sampled`, а в записи полезен идентификатор трассы: по нему
ищут записи двух процессов. Без проекции строка лога несла бы вложенный
объект, и поиск по `traceId=` перестал бы работать.

Проекция вызывается на каждой записи, только когда значение переменной
есть. Отказ проекции не гасится: она читает значение объявленной
переменной, и ошибка в ней — ошибка кода приложения.

Альтернативы:

- **Значение целиком, только переименование.** Меньше API, но формат
  записи меняется, а `traceId` перестаёт быть полем верхнего уровня.
- **Проекция на объявлении переменной** (`contextVar(key, { logAs })`).
  Объявление переменной начало бы знать про логгер, хотя переменная нужна
  политике, порту и пайплайну.

### Поля плагина и проверка имён на сборке

`makePlugin({ logFields: [...] })` объявляет поля наравне с модулями и
endpoint'ами. Плагин наблюдаемости ставит своё поле сам, приложению об
этом писать не нужно.

Списки собираются на ASSEMBLE, после раскрытия веток переключателей: до
раскрытия состав плагинов неизвестен. Собранный список кладётся в тот же
объект плана, который декоратор читает на каждой записи. До ASSEMBLE
декоратор работает с полями корня: запросов на фазах 0 и 1 ещё нет, и
полям корреляции неоткуда взяться.

Два объявления с одним именем — отказ сборки. Сообщение называет имя поля
и обоих объявивших: корень или имя плагина.

Альтернатива — молча брать последнее объявление. Отвергнута: гарантия
дороже удобства, а расхождение нашлось бы только в логе.

### Пакет `@nestlingjs/logging`

Новый пакет `packages/nestling.logging` без зависимостей содержит:

| Имя | Что это |
| --- | --- |
| `Logger`, `Fields`, `LogLevel`, `LogMethod` | интерфейс и его типы |
| `makeConsoleLogger(options)` | штатная реализация: `stderr`, форматы `text` и `json` |

Класс `ConsoleLogger` остаётся приватным: наружу идёт фабрика. Опции
фабрики — `level` и `format`; умолчания `info` и `text`.

`@nestlingjs/app` зависит от пакета и реэкспортирует его типы поимённо.
`Logger$`, `RootLogger$`, секция `nestlingLog` и декоратор корреляции
остаются в `app`: первым двум нужен контейнер, секции — конфиг, декоратору
— ячейка запроса.

Сателлит логирования зависит только от `@nestlingjs/logging`. Скрипт вне
приложения берёт `makeConsoleLogger()` и пишет тем же форматом, что и
приложение.

### Уровень `silent` и тихий тестовый прогон

Секция `nestlingLog` принимает пятое значение уровня — `silent`. Оно
отсекает записи всех четырёх уровней. Тип `LogLevel` остаётся четырьмя
значениями: писать уровнем `silent` нечем, это порог, а не уровень записи.

`assembleTest` подставляет источник с `NESTLING_LOG_LEVEL=silent` низшим
приоритетом. Тест, которому записи нужны, задаёт уровень своим `config:`
или подменяет корень на `spyLogger()`.

Альтернатива — подменять корень пустым логгером в тестовом прогоне.
Отвергнута: подмена заняла бы `RootLogger$`, и `overrides` теста
столкнулись бы с ней.

### Примеры пишут логгером

Приложения примеров берут `Logger$.auto` и пишут через него. Скрипты вне
приложения — `client.ts`, `openapi.ts`, `publish.ts`, `graph.ts`,
`compat.ts` — создают `makeConsoleLogger()`.

Вывод команд `examples/cli` остаётся на `stdout` через транспорт: текст
`help` и ответ на ввод — результат команды, а не запись лога. Файлы
`main.ts` и `help.command.ts` теряют `eslint-disable no-console` вместе с
вызовами `console`, кроме тех, что печатают результат команды.

## Risks / Trade-offs

- **Список полей заполняется на ASSEMBLE, а объект декоратора создан на
  фазе 0.** → Записи фаз 0 и 1 идут вне запроса, полей корреляции у них не
  бывает. Спека это фиксирует сценарием.
- **Проекция выполняется на каждой записи.** → Список полей короткий, а
  чтение ячейки и так делалось на каждой записи. Замер горячего пути в
  задачах: порог — отсутствие регрессии на `GET`.
- **Поле корреляции против привязки `child`.** → Правило одно: поле вызова
  сильнее поля корреляции, привязка `child` проходит через обёрнутую
  реализацию и в конфликт не вступает.
- **Ветка `terminology` переименовывает `assemble` в `build`.** → Change
  пишется текущими именами. После слияния той ветки rebase переименует
  затронутые строки механически.
- **Ветка `pipeline-stale-units` решает судьбу `withRequestLogging`.** →
  Юнит здесь не трогается; если он к моменту слияния удалён, пропадает
  один сценарий спеки `kernel-logger`.

## Migration Plan

Ломающих шагов два, оба видны компилятору.

1. `makeApp({ logger })` → `makeApp({ logging: { logger } })`. Поле
   `logger` удаляется из `APP_SPEC_FIELDS`, и корень с ним падает на
   объявлении.
2. `import type { Logger } from '@nestlingjs/app'` продолжает работать:
   типы реэкспортируются. Сателлит, которому ядро не нужно, переходит на
   `@nestlingjs/logging`.
