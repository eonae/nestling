## Context

Состав приложения выбирается сегодня одним измерением — фичами.
`app.assemble(select)` принимает имена фич, а всё остальное в графе
безусловно. Провайдер, который в одном окружении берётся из S3, а в другом
из локальной папки, выражается либо фабрикой `providers` модуля, либо
отдельной фичей.

Фабрика непрозрачна для сборки: `ContainerBuilder` разворачивает её внутри
`build()`, поэтому перечислить составы, не выполнив функцию, нельзя.
`check()` видит одну ветку — ту, что выбрало окружение прогона. Отдельная
фича ради одного провайдера навязывает маленькому сервису понятие, ради
которого он не заводился.

Второе ограничение — форма корня. `makeApp` принимает `features:` и
`providers:`, но не `endpoints:`. Сервис из трёх endpoint'ов обязан
объявить фичу с именем, которое нигде не используется: `select` в таком
приложении не вызывается ни разу.

Change вводит второе измерение состава — переключатель — и три формы
корня. Целевое описание уже написано:
[design/composition.md §2–3](../../../docs/design/composition.md).
Решение и отвергнутые варианты:
[ideas.md [2026-09-06] «Переключатели состава»](../../../docs/decisions/ideas.md).

Ограничения, в которых работает решение:

- Фаза ASSEMBLE синхронна и не выполняет ввод-вывод (capability
  `synchronous-assembly`).
- Аргумент сборки — единственный вход, который читается до контейнера;
  читает его пользовательский код через `load(RootConfig)`.
- Идентичность модуля — его значение: два разных значения с одним `name`
  роняют сборку (capability `module-identity`).
- Ядро занимает три пакета, пакетов-заглушек не заводится (capability
  `core-package-layout`).

## Goals / Non-Goals

**Goals:**

- Выразить выбор ветки состава значением, которое видно статически: и
  `check()`, и человек читают обе ветки, не выполняя кода.
- Дать корню три формы состава, чтобы сервис без фич писался без
  `makeFeature`.
- Сохранить одно место чтения окружения: значения переключателей приходят
  аргументом сборки, как выбор фич.
- Оставить состав вне рантайма: выбор не инжектируется и не читается из
  графа.

**Non-Goals:**

- Привязки `config:` под переключателем.
- Показ невыбранных веток в `@nestling/viz`.
- Переключатель в `features:` и в `policies:`.
- Реэкспорт `makeSwitch` из `@nestling/app` — имя экспортирует один пакет.

## Decisions

### 1. Переключатель живёт в `@nestling/container`

Ветка стоит в `providers:` и `dependsOn:` модуля, а `Module` объявлен в
`@nestling/container`. Чтобы список принимал ветку, её тип обязан быть
известен контейнеру. Пакет уже держит модули, поэтому переключатель
кладётся туда же — в `src/switches` со своим баррелем.

`@nestling/app` импортирует `Switch`, `SwitchBranch` и `resolveBranches`
из контейнера и применяет их к своим спискам. Автор приложения импортирует
`makeSwitch` оттуда же, откуда `makeModule` и `Component`.

Альтернативы:

- **`makeSwitch` в `@nestling/app`, бренд ветки в контейнере.**
  Конструктор и тип значения оказались бы в разных пакетах, а проверка
  «ветка создана нашим конструктором» — структурной.
- **`makeSwitch` в `@nestling/operations`.** Контейнер не зависит от
  `operations` и не может зависеть: направление обратное.

### 2. Ветка — брендированное значение, а не функция

`pick(table)` возвращает значение с неперечислимым symbol-свойством:
именем переключателя и таблицей веток. Значение не вычисляет состав и не
знает, что выбрано.

```typescript
// @nestling/container/src/switches
const BRANCH = Symbol.for('nestling:switch-branch');

export interface SwitchBranch<T> {
  readonly [BRANCH]: {
    readonly switch: Switch<string, string>;
    readonly table: Readonly<Record<string, readonly T[]>>;
  };
}
```

Список единиц типизируется как `readonly (T | SwitchBranch<T>)[]`. Ветка
раскрывается в ноль и больше элементов того же типа, поэтому вложенная
ветка внутри ветки разворачивается тем же проходом.

Альтернатива — функция `(values) => T[]`: она вернула бы состав только по
вызову, и `check()` снова видел бы одну ветку.

### 3. Раскрытие — одна чистая функция, вызываемая в двух местах

```typescript
export function resolveBranches<T>(
  items: readonly (T | SwitchBranch<T>)[],
  values: SwitchValues,
): T[];
```

`SwitchValues` — карта «имя переключателя → выбранное значение»,
построенная на фазе ASSEMBLE из аргумента сборки и умолчаний.

Вызывается функция там, где список читается:

| Список | Кто раскрывает |
|---|---|
| `providers:` и `dependsOn:` модуля | `ContainerBuilder.registerModule` |
| `modules:` и `endpoints:` фичи и плагина | `@nestling/app`, проход состава |
| `endpoints:`, `providers:`, `modules:`, `plugins:`, `transports:` корня | `@nestling/app`, нормализация плана |

Модуль при раскрытии не копируется: билдер читает его списки и регистрирует
результат. Идентичность модуля остаётся значением, и правило «два разных
значения с одним именем — ошибка» работает как прежде.

`ContainerBuilder` получает значения опцией конструктора:
`new ContainerBuilder({ switches })`. Без опции карта пуста, и ветка в
списке роняет сборку с именем переключателя: контейнер, собранный напрямую
(`examples/container`), веток не поддерживает, пока ему их не передали.

Альтернатива — раскрывать модули в `@nestling/app` копией: копия модуля
завела бы второе значение с тем же именем, и дедупликация по значению
перестала бы работать.

### 4. Значения считаются до discovery и до замыкания

Порядок на фазе ASSEMBLE:

1. Аргумент сборки разбирается: выбор фич, флаг `includeDeps`, значения
   переключателей.
2. Каждому переключателю из `switches:` сопоставляется значение: из
   аргумента или умолчание. Отсутствие того и другого — ошибка.
3. Списки корня и выбранных единиц раскрываются `resolveBranches`.
4. Discovery проходит по раскрытому составу.
5. `includeDeps` замыкает выбор по вызываемым операциям.
6. Модули регистрируются, граф строится, политики проверяются.

Замыкание видит уже раскрытый состав: ветка может привезти endpoint,
который вызывает операцию соседней фичи, и без раскрытия до шага 5 такая
фича не подключилась бы.

### 5. Аргумент сборки — объект с закрытым перечнем полей

```typescript
app.assemble({ features: 'all', storage: 's3', metrics: 'on' });
app.assemble('orders');          // только выбор фич
app.assemble(load(RootConfig));  // поля названы как переключатели
```

Тип выводится из `switches:` декларации: `makeApp` становится generic по
списку переключателей, как сегодня по списку транспортов. Поле
переключателя с умолчанием опционально, без умолчания обязательно.

```typescript
type AssembleArgs<S extends readonly AnySwitch[]> = string | readonly string[] | ({
  features?: string | readonly string[];
  includeDeps?: boolean;
} & SwitchFields<S>);
```

Неизвестное поле объекта — ошибка ASSEMBLE, называющая известные поля.
Правило то же, что у словаря `makeApp`: перечень закрыт. Молчаливое
игнорирование пропустило бы опечатку в имени переключателя с умолчанием —
приложение поднялось бы с другим составом, чем просил автор.

Имена `features` и `includeDeps` заняты: переключатель с таким именем
отвергается при создании декларации.

### 6. Три формы корня и единица с именем `app`

```typescript
interface RootCommon { plugins?; switches?; transports?; intercom?; config?; policies?; logger?; }

type AppSpec =
  | (RootCommon & { endpoints: […]; providers?: […]; modules?: never; features?: never })
  | (RootCommon & { endpoints: […]; modules?: […]; providers?: never; features?: never })
  | (RootCommon & { features: […]; endpoints?: never; providers?: never; modules?: never });
```

Формы взаимоисключающие: `never` в неиспользуемых полях даёт ошибку
компиляции на смешанной записи, а рантайм повторяет проверку сообщением с
перечнем форм.

Корень первых двух форм нормализуется во внутреннюю единицу с именем `app`
и ролью `feature`. Дальше состав однороден: discovery, атрибуция модулей,
карта владельцев и проверка границ работают одним кодом. Имя `app`
попадает в метку модуля и в отчёт `check()`.

Альтернативы:

- **Поле `name` у `makeApp`.** Имя приложения нигде не выбирается: `select`
  в приложении без фич не вызывается. Поле пришлось бы заполнять ради
  метки в графе.
- **Провайдеры корня без единицы, как сегодня.** Endpoint'ы корня остались
  бы без атрибуции, и отчёт проверки называл бы их модулем пустой строкой.

Поле `providers:` в форме с `features:` больше не принимается: провайдер,
общий для фич, объявляется плагином. Так проверка границы фичи сохраняет
смысл — иначе у ребра «фича → провайдер корня» не было бы владельца.

### 7. `Switch.schema` — Standard Schema без валидатора

Схема реализуется вручную: объект с `~standard.validate`, который сверяет
строку со словарём значений и подставляет умолчание. Тип
`StandardSchemaV1` берётся из `@standard-schema/spec` — пакет типов, он
уже стоит в репозитории транзитивно через `@common/misc`. Контейнер
объявляет его прямой зависимостью.

```typescript
export const RootConfig = makeConfig('app', {
  features: z.string().default('all'),
  storage: Storage.schema,   // APP_STORAGE: 's3' | 'local'
});
```

`makeConfig` принимает любую Standard Schema, поэтому код конфига
не правится. Сообщение об ошибке валидации перечисляет допустимые
значения — то же сообщение, что бросает сборка при значении не из словаря.

### 8. Выбор виден в отчёте и в строке старта

`CheckReport` получает поле `switches: Readonly<Record<string, string>>` —
измерение на каждый переключатель декларации. `checkTopologies` принимает
`readonly AssembleArgs[]` вместо `readonly FeatureSelection[]`: топология
описывается выбором фич и значениями переключателей вместе.

Строка старта печатает выбор рядом с фичами:

```
[nestling] features: users, uploads; storage=s3 metrics=on debug=off
```

Порядок переключателей — порядок объявления в `switches:`.

### 9. Гайд: глава о композиции и сдвиг нумерации

Новая глава 2 «Из чего состоит приложение» показывает одну схему:
endpoint'ы и провайдеры корня, модули как группировка, фичи как единицы
выбора, переключатели как второе измерение, split как следствие. Она стоит
после главы 1, потому что читатель встречает `makeApp` там же.

Главы 02–25 переименовываются в 03–26, приложения А и Б остаются со своими
именами. Правятся ссылки: внутри глав, в `docs/guide/README.md`,
`docs/README.md`, README пакетов и плашках design-доков. Проверка —
`yarn docs:audit`, который ловит битые ссылки.

Глава 1 собирает сервис формой `{ endpoints, transports }` — без
`makeFeature`. Фича вводится главой 2 как понятие и главой 13 (прежней 12)
как задача.

### 10. Опция тестового корня называется `args`

`assembleTest(app, { select })` переименовывается в
`assembleTest(app, { args })`. Опция принимает то же значение, что
`app.assemble(args)`, поэтому прежнее имя описывало бы только одно из двух
измерений состава. `checkTopologies` принимает список тех же значений.

## Risks / Trade-offs

- **Ветка в типе `Module` меняет публичный тип контейнера.** → Тип
  расширяется объединением, поэтому существующие модули продолжают
  проходить по типам; ветка добавляет вариант, а не заменяет элемент.
- **Раскрытие в `ContainerBuilder` без переданных значений роняет прямую
  сборку контейнера.** → Ошибка называет переключатель и опцию
  `switches`; `examples/container` веток не использует.
- **Вывод типа аргумента сборки усложняет сигнатуру `makeApp`.** → Второй
  generic-параметр выводится из литерала `switches:`, как сегодня
  выводится словарь `intercom` из `transports:`. Бюджет типов меряется
  `yarn type-budget` до и после.
- **Сдвиг нумерации глав ломает внешние ссылки на гайд.** → Гайд собирается
  одним файлом с якорями по номеру главы, поэтому ссылки меняются в любом
  случае; репозиторий проверяется `yarn docs:audit`, внешних потребителей
  у документации пока нет.
- **Три формы корня удваивают перечень проверок словаря.** → Проверки
  формы делаются одной функцией, которая называет найденные поля и
  перечисляет три допустимые записи.
- **`providers:` рядом с `features:` перестаёт компилироваться.** →
  Ломается один пример и одна глава гайда; замена — плагин, и она названа
  в сообщении об ошибке.

## Migration Plan

1. `@nestling/container`: переключатели, раскрытие, опция билдера, типы
   `Module`.
2. `@nestling/app`: формы корня, `switches:`, аргумент сборки, единица
   `app`, discovery по корню, отчёт и строка старта.
3. `@nestling/testing`: `assembleTest` и `checkTopologies`.
4. Примеры: `users-service`, `app-with-http`, `split-nats`.
5. Документация: `design/composition.md`, README трёх пакетов, глава о
   композиции, сдвиг нумерации, шаг-формы глав 2 и 5.

Отката не предусмотрено: пользователей у фреймворка нет, старые формы
удаляются целиком.
