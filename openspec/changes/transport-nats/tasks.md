# tasks — transport-nats

Порядок продиктован зависимостями: сначала ядро (шина умеет объявлять
способности и провозить контекст, биндинг умеет remote), потом пакет
транспорта, потом durable, потом витрина и доки. Первые три группы —
аддитивные правки существующих пакетов, наблюдаемого поведения без брокера
не меняют.

## 1. Ядро: конверт, способности шины, `durable` в контракте

- [x] 1.1 `@nestling/ports`, `bus.ts`: `IMessageBus` получает объявляемые
  значением способности `remote` и `durable`; `InProcessBus` объявляет обе
  ложными
- [x] 1.2 Конверт глаголов: `context?: Record<string, unknown>` в
  `RequestOptions`/`PublishOptions` и в `BusMessageMeta`; `durable?: boolean`
  в `PublishOptions`; `InProcessBus` провозит контекст через тему и кладёт
  его в атрибуты на приёме
- [x] 1.3 `profileAttributes` расширяется провозимым контекстом — одной
  процедурой для обоих путей биндинга, чтобы обработчик видел одинаковые
  атрибуты
- [x] 1.4 `contract.ts`: поле `durable` в `makeContract`, fail-fast у вида
  `request` с текстом, называющим контракт и вид
- [x] 1.5 `transport.ts`: `durable` в `BusBinding`, копируется из контракта
  в `implement`; `busBindingOf` его отдаёт
- [x] 1.6 Строка деградации на go-live: шина без способности `durable`,
  обслуживающая долговечные контракты, печатает перечень — рядом с
  существующей строкой состава транспортов
- [x] 1.7 Тесты: конверт с контекстом на `InProcessBus` (провоз, атрибуты,
  пустой контекст), `durable` у `request` отвергается, деградация печатается
  один раз и только при наличии долговечных контрактов

## 2. Ядро: remote-биндинг вызывателей

- [x] 2.1 `kernel.ts`: третий вход биндинга — способность шины `remote`;
  `buildPort`/`buildEmitter` строят remote-клиент при отсутствии co-located
  реализации
- [x] 2.2 `assertReachable` падает только когда шина не remote; текст
  подсказывает обе починки (объявить реализацию либо подключить remote-шину)
- [x] 2.3 `event` при remote-шине биндится remote всегда — с комментарием,
  объясняющим, что множество подписчиков открыто; двойной доставки нет
- [x] 2.4 Шина регистрируется kernel-модулем портов только если корень не
  поставил транспорт шины; `MessageBus$` становится алиасом инстанса
  `BusTransport$`
- [x] 2.5 `@nestling/app`: в `portsKernel(...)` уезжает признак «корень
  поставил транспорт шины», выведенный из `transportTokens`; процесс без
  единой реализации контракта, но с корневой шиной, собирается
- [x] 2.6 Тесты: матрица «вид контракта × co-located × природа шины» на
  фейковой remote-шине; чистый потребитель собирается; двойная доставки
  события нет; поведение без брокера не изменилось

## 3. Ядро: `propagate` в `@nestling/pipeline`

- [x] 3.1 `contextVar<T>()(key, options?)`: опция `propagate`, реестр
  провозимых переменных (модульное состояние — тот же приём, что реестр
  контрактов), fail-fast у read-only переменных
- [x] 3.2 `Var.propagated()` — второй конструктор писателя: pre-юнит, берущий
  значение из `ctx.raw.attributes`, с той же рантайм-пометкой переменной;
  у непровозимой переменной — внятный отказ
- [x] 3.3 Kernel-функция чтения провозимых значений из ячейки текущего
  запроса — то, чем пользуется вызыватель; вне запроса возвращает пусто
- [x] 3.4 `@nestling/ports`: оба вызывателя собирают провозимые значения и
  кладут в конверт; несериализуемое значение отвергает вызов с текстом,
  называющим переменную
- [x] 3.5 Рантайм-тесты (не только типовые): провоз через `local-first` и
  `always-remote` даёт одинаковый результат; непровозимая переменная не
  едет; `hasVar` засчитывает `propagated()`; вызов вне запроса проходит;
  payload не мутируется

## 5. Пакет: outbound и inbound

- [x] 5.1 `wire.ts`: кодирование конверта в headers (`timeoutMs`,
  `idempotencyKey`, провозимые переменные) и обратное чтение; кодек (JSON по
  умолчанию, заменяем опцией фабрики)
- [x] 5.2 `NatsBus.request`/`publish`: subject с префиксом, потолок
  ожидания (`min(остаток, потолок)`), ответ `ResponseContext` тем же кодеком
- [x] 5.3 Отображение брокерских отказов: `no responders` →
  `SERVICE_UNAVAILABLE`, исчерпание ожидания → `DeadlineExceeded`, потеря
  соединения → отказ плюс диагностический хук
- [x] 5.4 `NatsBus.subscribe` и inbound-путь: группа по виду контракта,
  пересчёт `timeoutMs` в момент приёма, fail-fast исчерпанного бюджета до
  `dispatch.call`, атрибуты запроса (subject, профиль, провозимый контекст)
- [x] 5.5 Фазы: `@OnInit` — соединение, `attach(dispatch)` — маршруты и
  проверка форм io, `serve` — подписки после `@OnStart`, `close`/сигнал —
  дренаж
- [x] 5.6 `capabilities` — только `value`; `remote: true`
- [x] 5.7 Фабрика `nats(options?)` — транспорт-провайдер под `BusTransport$`,
  явные опции сильнее конфига
- [x] 5.8 Тесты на двойнике: req-reply с ре-гидрацией задекларированного
  `Fail`; queue-группы `request`/`command`/`event`; бюджет и потолок;
  провозимый контекст через headers; подписки не появляются до go-live;
  дренаж на SHUTDOWN

## 6. Пакет: durable-доставка через JetStream

- [x] 6.1 Именование потока из subject'а и durable-потребителя из группы;
  `ensureStream` идемпотентен, существующий поток принимается как есть,
  конфликт состава subject'ов — fail-fast с внятным текстом
- [x] 6.2 Публикация долговечного контракта с ожиданием подтверждения записи
- [x] 6.3 Потребление: durable-потребитель, ack по факту решения (успех и
  задекларированный `Fail`), nak при необработанном исключении и при
  остановке процесса, `term` с отчётом при исчерпании попыток
- [x] 6.4 `durable: true` объявляет шина (`IMessageBus.durable`), и вызыватель
  кладёт признак в конверт публикации
- [x] 6.5 Тесты на двойнике: сообщение переживает простой подписчика; реплики
  подписчика делят поток; разные подписчики независимы; `Fail` не
  повторяется, исключение повторяется; конфликт определения потока падает
