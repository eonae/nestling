## Context

Наблюдаемость Nestling собрана двумя change'ами, и оба остановились на
границе экспорта.

`observability` (#77) дал трассы: well-known переменная `Trace` с полями
`traceId`, `spanId`, `parentSpanId` и `sampled`, pre-шаг `withTracing()`,
формат W3C по HTTP и полем конверта по шине, поле `traceId` в каждой записи
логгера. Идентификаторы едут между процессами, но интервал участка — когда
он начался и сколько шёл — не записывает никто. Показать трассу в Jaeger или
Tempo нечем: она видна только грепом по логам.

`declared-metrics` дал метрики: метрика — декларация-значение, каталог
собирается на BUILD, накопленное держит `MetricsStore$` — узел графа с
выходом `snapshot()`. Формат экспозиции Prometheus живёт в
пакете `@nestlingjs/prometheus`. Наружу метрики уходят только по запросу
сборщика: push в коллектор не умеет никто.

Этот change закрывает обе границы одним пакетом — `@nestlingjs/otel`.

Ограничения, в которых он делается:

- Ядро не трогается. Строка 85 roadmap: «ядро даёт интерфейс и переменную,
  формата экспорта не знает».
- Приложение не обязано ставить сателлит целиком: трассы без метрик и
  метрики без трасс — рабочие сочетания.
- Сателлит — читатель store, а не его замена. Приложение без сателлита
  считает метрики ровно так же.

## Goals / Non-Goals

**Goals:**

- Один пакет закрывает оба экспорта: участки трассы и push метрик по OTLP.
- Участок уходит экспортёру с теми же идентификаторами, которые ядро везёт
  по сети, — иначе дерево не сходится.
- Отсутствие экспорта участков на endpoint'е ловится на сборке, а не в
  проде.
- Сервис может дописать атрибут на текущем участке, не зная про OTel SDK.
- Корзины и описания метрик в OTLP те же, что в экспозиции: две картины
  одного приложения совпадают.

**Non-Goals:**

- Новый шов в ядре под участки. Разобран ниже, решение D1.
- Участок на вызов порта. Решение D5.
- Формат экспозиции Prometheus и endpoint `/metrics`: их даёт
  `@nestlingjs/prometheus`.
- Экспорт логов по OTLP. Логгер пишет в `stderr`, сбор строк — дело
  развёртывания.
- Автоматическая инструментовка `pg`, `fetch` и прочих библиотек. Пакеты
  `@opentelemetry/instrumentation-*` приложение подключает само.

## Decisions

### D1. Участок пишет слой сателлита, гарантию даёт политика

Участок — интервал: у него есть начало и конец. Метрика — одно значение в один
момент, и потому корня метрик под неё хватило. Под интервал шва в ядре нет.

**Решение.** Сателлит отдаёт слой пайплайна. Pre-шаг открывает участок,
`.finally`-шаг закрывает его исходом. Что слой есть у каждого endpoint'а,
утверждает политика сборки — `everyEndpoint(…).hasVar(Span)`.

```typescript
// пакет
export const Span = contextVar<OtelSpan>()('span');

// сателлит: слой требует trace в контексте и добавляет span
const spans = makePipeline<{ trace: TraceContext }>()
  .pre(Span.provide((ctx) => open(ctx.input.trace)))
  .finally((outcome, res, ctx) => close(ctx.input.span, outcome, res, ctx));
```

```typescript
// приложение
export const observabilityLayer = compose(
  makePipeline().pre(withRequestId()).pre(withTracing()).finally(AuditOutcome),
  telemetry.spans,
);

makeApp({
  policies: [everyEndpoint().hasVar(Span, 'span')],
});
```

**Почему не шов ядра `makeApp({ spans })`.** Вариант рассматривался всерьёз:
рантайм пайплайна в `settle` уже знает шаблон маршрута, исход, длительность и
значение `Trace`, и второй вызов рядом с записью метрики покрыл бы все
endpoint'ы разом. Отвергнут по двум причинам. Первая: гарантию даёт политика,
и она сильнее умолчания — забытый слой падает на фазе BUILD с именем модуля и
паттерном, а не молча не экспортируется. Вторая: третий интерфейс
наблюдаемости в ядре стоит дороже, чем строка в `policies:`, и формат участка
пришлось бы фиксировать в спеке ядра — то самое знание об экспорте, от
которого ядро отгорожено.

**Почему довод #77 против `.finally`-шага здесь не работает.** В #77
отказались писать метрику шагом, и три довода были такие: слой в каждом
пайплайне, незамеченный endpoint, отложенная фаза потока. Первые два снимает
политика. Третий снимает сам рантайм: `.finally`-шаг у потокового ответа
вызывается после закрытия итератора (`runFinals` откладывается вместе с
`settle`), так что длительность участка покрывает доставку целиком — ровно как
у метрики. Воспроизводить фазу заново не приходится.

### D2. Идентификаторы участка принадлежат ядру

`Tracer.startSpan` из OTel SDK минтит `spanId` своим `IdGenerator`. Ядро уже
сминтило свой в `withTracing()` и увезло его соседу заголовком `traceparent`.
Два разных идентификатора на один участок — разорванное дерево: участок соседа
ссылается на родителя, которого в экспорте нет.

**Решение.** Сателлит не зовёт `startSpan`. Он собирает значение формы
`ReadableSpan` из `TraceContext` и отдаёт его напрямую `SpanExporter`:

| Поле участка | Откуда |
| --- | --- |
| `spanContext().traceId`, `spanId` | `Trace` |
| `parentSpanContext.spanId` | `Trace.parentSpanId` |
| `spanContext().traceFlags` | `Trace.sampled` |
| `name` | `ctx.endpoint.pattern` |
| `startTime`, `endTime` | часы pre-шага и `.finally`-шага |
| `status` | исход шага |
| `attributes` | транспорт, паттерн, исход и то, что дописал сервис |

`ReadableSpan` — интерфейс, а не класс: значение собирается объектным
литералом. Это та же форма, которую `SpanExporter` получает от SDK, поэтому
любой готовый экспортёр (OTLP, консольный, свой) работает без переходника.

**Альтернатива:** свой `IdGenerator` в `BasicTracerProvider`. Отвергнута:
генератор вызывается без контекста запроса и не знает, какой идентификатор
нужно вернуть.

### D3. Исход шага в статус участка

`.finally`-шаг получает исход одного из четырёх значений. Отображение:

| Исход | Статус участка | Почему |
| --- | --- | --- |
| `completed` | `OK` | запрос обработан |
| `failed` | `ERROR` | отказ объявленный или нет — для наблюдателя провал |
| `aborted` | `ERROR` | работу прервали, результата нет |
| `disconnected` | `UNSET` | клиент ушёл; сервис ни при чём |

`disconnected` не красится в `ERROR` намеренно: иначе процент ошибок в дашборде
растёт от поведения клиентов, и сигнал теряется. Исход остаётся атрибутом
участка, поэтому отфильтровать его можно.

### D4. Переменная `Span` — и обогащение, и политика

Участок кладётся в контекст переменной `Span`, а не в замыкание слоя. Это даёт
две вещи одним значением.

Сервис дописывает атрибут, не зная про SDK:

```typescript
@Component([Ctx(Span)])
export class UsersService {
  constructor(private readonly span: CtxReader<OtelSpan>) {}

  find(id: string) {
    this.span.get()?.setAttribute('user.id', id);
  }
}
```

Политика проверяет присутствие по переменной: `hasVar` засчитывает объявление
через `Var.provide`, и переживает перекомпозицию слоя — в отличие от
`hasLayer`, который сравнивает значение по ссылке.

Поверхность значения — два метода, `setAttribute` и `addEvent`. `end` наружу
не выходит: закрывает участок слой, и второй закрыватель означал бы два
участка с одним идентификатором.

### D5. Вызов порта своего участка не получает

Слой живёт в пайплайне, а у вызова порта пайплайна нет. Дерево от этого не
рвётся: вызыватель везёт `Trace` в конверте, получатель продолжает трассу
своим `withTracing()`, и участок его endpoint'а встаёт ребёнком участка
вызывателя. Пропадает только промежуточное звено — время, проведённое в сети
и в очереди брокера. Его показывает пара метрик `nestling.port.duration` и
`nestling.request.duration`: разность и есть накладные расходы доставки.

Условие возврата: когда разность метрик перестанет отвечать на вопрос «где
запрос провёл время» — например, понадобится разложить задержку по конкретным
вызовам внутри одного обработчика.

### D6. Один вход, две части

`declared-metrics` забрал у сателлита корень метрик и экспозицию. Осталось
две части, и обе — читатели того, что уже держит ядро.

```typescript
export interface Otel {
  /** Слой участков: композируется в слой наблюдаемости приложения */
  readonly spans: Pipeline<{ trace: TraceContext }, { span: OtelSpan }>;

  /** Плагин: ресурс подписки на store и сброс на остановке */
  readonly plugin: Plugin;
}

export interface OtelOptions {
  /** Имя сервиса: атрибут ресурса `service.name` */
  readonly service: string;

  /** Версия сервиса: атрибут ресурса `service.version` */
  readonly version?: string;

  /** Куда уходят участки; без него слой не экспортирует ничего */
  readonly traces?: SpanExporter;

  /** Куда уходят метрики; без него подписки на store не возникает */
  readonly metrics?: PushMetricExporter;

  /** Интервал отправки метрик, мс; умолчание — 60000 */
  readonly intervalMs?: number;
}
```

Один вход остаётся, потому что `service` и `version` нужны обеим частям:
атрибуты ресурса у трасс и у метрик одни и те же, и разводить их по двум
фабрикам значило бы писать имя сервиса дважды.

Приложение, которому нужны и push, и экспозиция, ставит два плагина:
`telemetry.plugin` и `prometheus()`. Они читают один store и друг о друге не
знают.

### D7. Метрики берутся снимком по таймеру

`MetricsStore$` отдаёт `snapshot()` — состояние всех рядов на момент
вызова, с каталожными полями метрик. Сателлит читает его раз в
`intervalMs` и переводит в `ResourceMetrics`.

**Почему не поток записей.** Альтернативу разбирали: store мог бы отдавать
подписчику каждую запись. OTLP принимает не приращения, а точки с
накопленным значением — счётчик суммой, гистограмму парой `count`/`sum` и
корзинами. Получатель потока обязан сложить их сам, то есть завести второй
агрегат рядом со store: те же ряды, те же корзины, второй раз. `snapshot()`
отдаёт уже посчитанное, и агрегат остаётся один.

Довод принят change'ем `declared-metrics`: выход `tap(sink)` и интерфейс
`MetricSink` из ядра убраны, у store остался один выход. Поток записей
отложен записью
[deferred.md [2026-09-14]](../../../docs/decisions/deferred.md) с триггером
«получатель, которому важен момент записи: exemplars, сэмплирование,
событие в шину».

**Временна́я привязка — кумулятивная.** Store копит от старта процесса,
снимок это отражает, дельту считает бэкенд. Это же умолчание у экспозиции
Prometheus, поэтому две картины одного приложения совпадают.

### D8. Ресурс сброса объявляет сателлит

Отправка периодическая, поэтому процесс, выключенный между отправками,
потерял бы последний интервал.

**Решение.** Плагин объявляет `@Resource`, зависящий от `MetricsStore$`.
Освобождение снимает таймер, отправляет последний снимок и закрывает
экспортёров.

Зависимость от store — не формальность, а то, что задаёт порядок: в реверсе
освобождения сателлит закрывается раньше store, поэтому снимок на остановке
ему ещё доступен. Причина найдена разбором сессии `change/rewrite-metrics`
при обсуждении `declared-metrics`.

Ресурс не принадлежит store намеренно: получателей может быть несколько, и
каждый закрывается своим ресурсом, а store не ведёт их список.

### D9. Зависимости — OTel SDK без экспозиции

Пакет зависит от `@opentelemetry/api`, `sdk-trace-base`, `sdk-metrics`,
`resources` и `semantic-conventions`; внутренние — `app` и `container`.

Против первой редакции ушли два: `exporter-prometheus` (формат экспозиции
живёт в `@nestlingjs/prometheus` и OpenTelemetry не требует) и
`transport.http` (своего endpoint'а у пакета больше нет).

`sdk-metrics` остаётся ради типов `ResourceMetrics` и `PushMetricExporter`:
значение собирается руками, ровно как `ReadableSpan` у трасс (решение D2).
Одна и та же причина в обоих случаях — данные принадлежат ядру, а SDK даёт
форму, которую понимают готовые экспортёры.

### D10. Глава гайда — одна, про трассы

Глава 22 «Считать запросы и вызовы между процессами» переписана change'ом
`declared-metrics`: объявление группы, писатель из графа, экспозиция
пакетом. Дублировать её нечем — push по OTLP это те же метрики, снятые
другим способом, и место ему абзацем в главе 22, а не главой.

Глава 23 «Увидеть, где запрос провёл время» — новая: слой участков,
политика `hasVar(Span)`, `Ctx(Span)`, просмотр дерева в Jaeger.

Одна глава — одна задача: «посчитать» и «увидеть, где время» — разные
вопросы, и приходят они к читателю в разные моменты.

## Risks / Trade-offs

- **Формы `ReadableSpan` и `ResourceMetrics` — внутренний контракт SDK, а не
  публичный протокол** → обе собираются в одном месте каждая, и оба места
  закрыты тестом против настоящего экспортёра. Смена формы в мажоре SDK
  падает тестом, а не в проде.
- **Слой участков на каждом endpoint'е забывается** → политика
  `hasVar(Span)` в обоих примерах и в главе 23. Осознанный отказ —
  `detached`, как у остальных политик.
- **Снимок по таймеру копирует все ряды каждый интервал** → состав рядов
  задан каталогом и от трафика не растёт, а интервал по умолчанию — минута.
  Ряды открытых атрибутов растут по факту записи; это свойство store, и
  сателлит его не усугубляет.
- **Последняя точка перед падением процесса теряется** → ресурс сброса отправляет снимок на остановке (D8). Падение
  без остановки теряет интервал — цена периодической отправки, и её платит
  любой push-экспортёр.
- **`Ctx(Span)` возвращает `undefined` вне запроса и на endpoint'е без
  слоя** → тип читалки это называет, вызов пишется через `?.`. Обязательным
  значение сделать нельзя: пайплайна у `@OnStart` нет.

## Migration Plan

Обратной совместимости в проекте нет. Пакет новый, ядро не меняется, поэтому
миграция сводится к двум примерам.

1. `declared-metrics` доходит до `main`: `MetricsStore$`, каталог и
   `@nestlingjs/prometheus` на месте.
2. Пакет заводится и проходит `yarn verify` со своими спеками.
3. `examples/microservice` и `examples/modular-app`: слой участков
   композируется в слой наблюдаемости, в `policies:` добавляется
   `hasVar(Span)`. Экспозиция там уже подключена пакетом формата — её этот
   change не трогает.
4. Глава 23 и её английская пара, README пакета парой, строка
   `@nestlingjs/otel` в таблице пакетов `docs/README.md`, справочник
   `docs/compatibility.md` парой.

Откат — снятие ветки: в `main` change попадает одним merge-коммитом.

## Open Questions

Оба вопроса закрыты на apply; решения записаны ниже.

### Q1. Совместимость экспорта доказывается двумя проверками

**Решение.** Подставные `SpanExporter` и `PushMetricExporter` в спеках
пакета плюс проверка типов против настоящих экспортёров OTLP по HTTP
(`compat.type-test.ts`).

Подставной экспортёр показывает числа: какие атрибуты у участка, какие
корзины у точки, когда уходит участок потокового ответа. Проверка типов
показывает форму: `OTLPTraceExporter` и `OTLPMetricExporter` подходят
опциям `traces` и `metrics` как есть, а значения, собранные пакетом,
проходят в их `export` без переходника. Смена формы в мажоре SDK падает
компиляцией.

Коллектор в контейнере отложен: он проверяет сеть и протокол, а их держит
SDK. Условие возврата — расхождение, которое эти две проверки пропустили.

### Q2. Опция названа `service`

**Решение.** `service` и `version`, а не `serviceName` и `serviceVersion`.

Пара читается вместе и повторяет то, как о сервисе говорят в коде.
Атрибуты ресурса `service.name` и `service.version` пакет проставляет сам:
имя опции и имя атрибута связаны JSDoc, и знать второе автору приложения
не нужно.
