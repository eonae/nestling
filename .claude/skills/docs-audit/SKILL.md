# Аудит консистентности docs/

Документация ведётся documentation-first во многих сессиях; скилл находит
рассинхрон между её частями. Два слоя: механические инварианты (скрипт,
детерминированно) и семантический дрейф (проверяется по рецептам ниже).

| Вызов | Что делать |
|---|---|
| `/docs-audit quick` | только слой 1 (скрипт), отчёт |
| `/docs-audit` | слои 1 + 2, отчёт |
| `/docs-audit fix` | слои 1 + 2, затем починки по правилам «Fix-режима» |

## Слой 1 — скрипт (всегда первым)

Из корня репозитория:

```bash
node .claude/skills/docs-audit/scripts/check.mjs
```

Проверяет: плашки «**Целевое состояние V1**» в `design/` (старые
«**Статус:**» там запрещены — статусы живут в roadmap), плашки «сверено с
кодом … (дата)» в `guides/` и их свежесть против git-истории примеров,
полноту карт в обе стороны (гайды — таблица в `docs/README.md`, design-доки —
карта в `docs/design/README.md`), битые относительные ссылки,
незакоммиченные правки замороженного `docs/history/`, посторонние `.md`
в корне, нумерацию `history/discussions/NN-*`. Exit 1 — есть ERROR.
Findings скрипта переноси в отчёт как есть, не перепроверяя вручную.

## Слой 2 — семантический дрейф

Пять независимых проверок. S1–S4 можно раздать параллельными
Explore-субагентами; каждый возвращает findings в формате
«файл:строка — проблема — рекомендация».

### S1. Гайды ↔ код примеров

Для каждого гайда, помеченного скриптом `guide-stale` (в fix-режиме — для
всех): прочитай гайд и исходники его примера (`packages/<пример>/src/`,
пример указан в плашке). Сверь каждый сниппет: импорты, имена API, сигнатуры,
описанное поведение. Расхождение = finding. Дату в плашке разрешено обновлять
**только** после фактической сверки содержимого — «просто поднять дату» ложь.

### S2. design/ ↔ decisions/ideas.md

Для каждого дока в `docs/design/`:

1. `LAST=$(git log -1 --format=%H -- docs/design/<док>.md)`
2. `git diff $LAST..HEAD -- docs/decisions/ideas.md` — записи журнала,
   появившиеся **после** последней правки этого design-дока.
3. Прочитай эти записи и сам док: противоречит ли новая запись доку? Должна
   ли попасть в него? Если да — finding с предложением правки дока по месту
   (design/ правится тем же изменением, что и решение; пометок дрейфа в
   плашках нет). Проверь и обратное: всё «что» в доке обязано опираться на
   записи, перечисленные в его плашке.

### S3. roadmap.md ↔ openspec + archlog.md

Сравни список и статусы changes в `docs/decisions/roadmap.md` с содержимым
`openspec/changes/` (активные и архив). Заархивированный change обязан иметь
финальный статус в roadmap.md **и** абзац в `docs/decisions/archlog.md`;
активный — не должен числиться завершённым.

### S4. deferred.md ↔ ideas.md

Для каждой темы в `docs/decisions/deferred.md` поищи в `ideas.md` записи
новее её даты. Если тема фактически принята или решена — finding: пометить
запись в deferred.md ссылкой на решение.

### S5. decisions/ append-only

`git diff HEAD -- docs/decisions/` плюс последние коммиты по этим файлам:
удаление содержательных строк из `ideas.md`/`archlog.md`/`deferred.md` без
пометки `~~…~~ — РЕШЕНО/СУПЕРСИД` = finding. Уровень WARN — возможны ложные
срабатывания на правках опечаток.

## Отчёт

Один итоговый блок, пустые секции опускай:

```
## Аудит docs/ — YYYY-MM-DD

### Нарушения инвариантов        ← ERROR скрипта + семантические противоречия
### Дрейф                        ← WARN: устаревшие плашки, расхождения, отставание roadmap
### Требует решения пользователя ← суперсид-пометки, записи в ideas.md, спорные случаи

Итог: N ERROR, M WARN, K на решение.
```

Каждый пункт: `файл:строка` — суть — рекомендация одним предложением.

## Fix-режим

Применять только после полного аудита.

**Чинить автоматически:** строки таблиц `docs/README.md` (добавить
недостающие, убрать мёртвые); битые относительные ссылки, если новый путь
однозначен (файл переехал внутри docs/); опечатки в формате плашек.

**Чинить только после пересверки:** сниппеты и дату плашки гайда — по итогам
S1; текст design-дока и его плашку — по итогам S2. Если правка design-дока
меняет смысл (не только фиксирует уже принятое в ideas.md) — нужна запись
в decisions, а её без явного «запиши» не делаем: тогда только предложи.

**Никогда:** любые правки `docs/history/` (immutable); переписывание записей
`decisions/` (суперсид-пометку — только предложить); новые записи в
`ideas.md` без явного «запиши» пользователя; переименование закоммиченных
файлов `history/discussions/` ради нумерации.

Всё, что не попало в «чинить автоматически», выноси в отчёт в секцию
«Требует решения пользователя».

## Ограничения (дублируют CLAUDE.md — нарушать нельзя)

- `history/` — immutable, `decisions/` — append-only.
- В `decisions/ideas.md` записывать только после явного «запиши».
- «Что» живёт в `design/`, «почему» — в `decisions/`; параллельных описаний
  API не заводить.
