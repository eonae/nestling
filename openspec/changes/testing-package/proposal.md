# testing-package: ядро `@nestling/testing`

## Why

Тестировать приложение целиком сегодня нечем. Единственный composition root —
`assemble({ … })`, и он ведёт приложение сразу до RUN: `run()` гоняет фазы 0–5,
поднимает сокеты и вешает обработчики `SIGTERM`/`SIGINT`. Всё, что остаётся
тесту, — либо юнит на голых классах (это работает и должно работать), либо
настоящий e2e с портом и HTTP-клиентом. **Середины нет**: прогнать запрос через
полный пайплайн, но без сокета, — не через что; подменить репозиторий на фейк —
нечем (контейнер жадный, `overrides` в `assemble` нет и не будет); проверить,
что топология `select: 'orders'` вообще собирается, — только подняв её.

Хуже того, жадный контейнер без прунинга **анти-тестовый**: даже будь
подстановка, замена репозитория фейком не помешала бы pg-пулу
проинстанцироваться и открыть соединение — он остаётся зарегистрированным
узлом графа.

Логика решений зафиксирована в `docs/decisions/ideas.md`, секция
«[2026-07-10] Пакет тестирования (`@nestling/testing`)»; целевое состояние —
[`docs/design/testing.md`](../../../docs/design/testing.md). Это change #18 из
[roadmap](../../../docs/decisions/roadmap.md), третий в волне 4. Он поставлен
**раньше, чем требует граф зависимостей**, по одной причине: `assembleTest` /
`vars()` / `.check()` удешевляют каждый следующий change волн 4–6 — их тесты
пишутся против собранного приложения, а не против ручной обвязки контейнера.
Обе предпосылки готовы: `assemble` с фазовым lifecycle (#10, архив
`2026-07-31-features`) и конфиг с `ConfigSource`/`objectSource` (#9, архив
`2026-07-31-config-module`).

## What Changes

- **Новый пакет `@nestling/testing`** — тонкий по построению: тестируемость
  здесь следствие архитектуры, а не машинерии пакета.
- **`assembleTest(spec) → Promise<TestApp>`** — тестовый composition root:
  тот же план сборки, что у `assemble`, плюс `overrides:`, и остановка после
  фазы 3 WIRE. `dispatch` рождён, START не выполняется, транспорты не в эфире,
  обработчики сигналов процесса не ставятся.
- **`overrides: [[Token, fake]]` — подстановка в графе на ASSEMBLE**, до
  инстанциации: не патчинг, не перехват module system. Ключ существует
  **только** у тестового корня. Подстановка типизирована: фейк, не
  совместимый с типом токена, — ошибка компиляции. Override токена, которого
  нет в графе, — ошибка сборки (переименовали провайдер → тест не мокает
  молча пустоту).
- **Прунинг осиротевших поддеревьев** в `ContainerBuilder`: узлы, достижимые
  только через зависимости заменённого узла, не инстанцируются и в граф не
  попадают. Инвариант, который делает прунинг безопасным: **без `overrides`
  прунинг тождественен** — множество узлов графа не меняется ни на один узел.
- **`app.call(Endpoint, input, options?)`** — in-proc исполнение ручки через
  **полный пайплайн** (этим app-тест и отличается от юнита). Типизировано
  схемами декларации: `input` — по `input`-форме, результат —
  `ResponseContext<InferOutput<O>>`, где ветка отказа несёт `status` и `code`
  из закрытого контракта `errors:`. Плюс `unwrap(response)` — value или
  бросок с деталями.
- **`await using` → SHUTDOWN**: `TestApp[Symbol.asyncDispose]()` выполняет
  честный `@OnDestroy` в реверсе топосорта; `close()` доступен явно.
- **`vars({ … })`** — именованный объектный `ConfigSource` с `watch`/`set`
  (поверх существующего `objectSource`): reload-механика тестируется, а
  `process.env` не трогается — параллельные тесты бесплатно. В тестовом корне
  `config: vars({ … })` — сахар для `[[source, '*']]`.
- **`familyOverride(Family, (param) => value)`** — подмена рецепта семейства
  (cross-cutting: `familyOverride(ILogger, () => noop)`); едет в том же
  списке `overrides:`.
- **`App.check()`** — структурный смок на **честном графе**: фазы 0–1
  (конструкторы, без `@OnInit` → без захвата ресурсов), все fail-fast'ы
  сборки, отчёт о составе. Метод корня, а не тестового приложения: `.check()`
  компенсирует прунинг, поэтому обязан гонять граф без подстановок.
- **`checkTopologies(spec, selections)`** — матрица `select`-топологий одним
  тестом: `'all' | 'orders' | 'billing'` валидируются в CI без деплоя, все
  отказы перечисляются разом, а не по первому.
- **`testModule(M, { stubs })`** — мини-app вокруг одного модуля;
  неудовлетворённые импорты обязаны быть застабаны явно, ошибка перечисляет
  **все** недостающие токены.
- **Неудовлетворённые зависимости перечисляются одной ошибкой** и на обычной
  сборке: сейчас `build()` падает на первой попавшейся при инстанциации.
- **Конвенция `./testing`-subpath** — тестовая capability модуля через
  conditional export (условие `"testing"` включено только в тест-раннере,
  прод-импорт не резолвится на уровне Node resolution). Догфудится на самом
  ядре: внутренний шов, которым `@nestling/testing` заводит фазы 0–3, живёт
  в `@nestling/app` именно таким subpath'ом, а не публичным экспортом.

## Non-goals

- **`stub(Contract, impl)`** — фейк-порт, валидируемый схемой контракта:
  контрактов (`makeContract`) в V1 ещё нет, они приезжают с change `ports`
  (#11). Остаток — change `testing-stub-contract` (#18-остаток, волна 6).
  Поле `stubs:` вводится уже сейчас (в `testModule` и `assembleTest`) в форме
  «токен → значение», чтобы контрактные стабы легли в него аддитивно.
- **`app.emit(Event, payload)`** — по той же причине: понятия `Event`
  (контракт вида `event`, `Emitter`, шина) в ядре не существует, эмитить
  нечего. Приезжает вместе с `stub(Contract)` после #11; форма `app.call`
  выбрана так, чтобы `emit` встал рядом без переделки. **Это единственный
  пункт исходного скоупа change'а, который переносится.**
- **Отчёт совместимости схем контрактов** в `.check()` — change
  `contract-versioning` (#26).
- **`valueProvider(Ctx(X), value)`** как шов request-контекста — `contextVar`
  приезжает с change `async-context` (#16); механика подстановки, которой он
  воспользуется, вводится здесь.
- **Policy-check в `.check()`** — `policies:` приезжают с change
  `policy-check` (#28); `.check()` проектируется так, чтобы прогон политик
  добавлялся в него аддитивно.
- **Раннер, ассерты, snapshot-механика** — jest остаётся jest'ом; пакет не
  вводит ни своего `describe`, ни матчеров.
- **Автоподстановка транспортов** в тестовом корне: транспорты перечисляются
  так же, как в проде. Ручка на транспорте, которого нет в графе, — тот же
  fail-fast на ASSEMBLE, что и в бою; сокет всё равно не откроется, потому
  что START не выполняется.
- **Мок чужого неэкспортированного провайдера** — никак, и это фича
  (см. `docs/design/testing.md` §1). Жёсткий выход — подменить модуль целиком.

## Capabilities

### New Capabilities

- `test-composition-root`: `assembleTest(spec)` — состав словаря
  (`modules`/`features`/`select`/`transports`/`config`/`overrides`),
  остановка после WIRE, отсутствие go-live и обработчиков сигналов;
  `app.call(Endpoint, input)` через полный пайплайн с типизацией по схемам;
  `app.get(token)`; `unwrap`; `await using`/`close()` → SHUTDOWN;
  `vars()` и форма `config: source`; `familyOverride`.
- `graph-overrides-pruning`: подстановка провайдера до инстанциации;
  типизация пары `[Token, fake]`; fail-fast на override отсутствующего
  токена и на двух override'ах одного токена; алгоритм прунинга и его
  инварианты (без `overrides` — тождество; заменённый узел не прунится;
  узел, достижимый не только через заменённый, остаётся; циклы продолжают
  падать, а не исчезать вместе с прунингом); прунинг не выполняет
  `@OnInit`/`@OnDestroy` выпавших узлов.
- `structural-check`: `App.check()` — фазы 0–1 без `@OnInit`; что именно
  проверяется (граф, циклы, наличие транспортов, формы io, полнота
  конфигурации); форма отчёта; `checkTopologies(spec, selections)` — матрица
  `select`-топологий с перечислением всех отказов.
- `module-isolation-testing`: `testModule(M, { stubs })` — мини-app вокруг
  одного модуля; обязательность явного стаба для каждого неудовлетворённого
  импорта; ошибка перечисляет все недостающие токены разом.
- `testing-subpath-convention`: конвенция `./testing`-subpath через
  conditional export — что экспортируется (курируемые токены и готовые
  фейки), почему граница структурная (прод-импорт не резолвится), и
  репо-обвязка, включающая условие в тест-раннере.

### Modified Capabilities

- `composition-root`: `assemble` SHALL NOT принимать `overrides` — требование
  фиксируется явным негативом; публичная поверхность `App` пополняется
  `check()` рядом с `run()`/`close()`.
- `lifecycle-phases`: фазовая модель получает две адресуемые точки останова —
  тестовый прогон (0–3, без START) и структурная проверка (0–1, без `@OnInit`),
  с описанием того, что в этих режимах гарантированно **не** происходит.
- `container-accessor-contract`: неудовлетворённая зависимость сборки SHALL
  диагностироваться перечнем **всех** недостающих токенов до инстанциации, а
  не первой попавшейся ошибкой в её процессе.

## Impact

- **Новый пакет `packages/nestling.testing`** (`@nestling/testing`):
  `assembleTest`, `vars`, `familyOverride`, `testModule`, `checkTopologies`,
  `unwrap`. Зависимости — `@nestling/app`, `@nestling/container`,
  `@nestling/config`, `@nestling/pipeline`, `@nestling/transport`.
- **`@nestling/container`** — `ContainerBuilderOptions`: `overrides` и
  `familyOverrides`; подстановка и прунинг в `build()`; предвалидация
  недостающих зависимостей с перечнем; API отчёта о выпавших узлах.
- **`@nestling/app`** — `App.check()`; внутренний шов «пройти фазы 0–3 и
  остановиться» + `dispatch`/`container` для in-proc вызова, вынесенный в
  subpath `@nestling/app/testing` (conditional export, условие `"testing"`).
- **Репо-обвязка тестов** — `jest.config.base.js`:
  `testEnvironmentOptions.customExportConditions` с условием `"testing"`,
  `moduleNameMapper` для `@nestling/*/testing`, `lib` для `await using`;
  `tsconfig` пакетов, которым нужен условный резолв (`customConditions`).
- **`packages/examples.app-with-http`** — витрина: app-тесты через
  `assembleTest` с `overrides` и `vars()`, `./testing`-subpath модуля
  пользователей с фейком репозитория, тест-матрица `checkTopologies` по
  `select: 'all' | 'users' | 'logging'`.
- **Документация** — `docs/design/testing.md` уточняется по факту
  реализованного (`await assembleTest`, `.check()` как метод корня,
  перенос `emit`/`stub`), отметка «РЕАЛИЗОВАНО» в секции ideas.md
  [2026-07-10], новый гайд `docs/guides/testing.md` + строка в таблице
  `docs/README.md`, README пакетов `testing`, `app`, `container`.
