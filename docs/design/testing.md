## 1. Уровни тестов и граница видимости

Тестовая поверхность совпадает с экспортной. Внутри пакета видно всё,
поэтому unit- и модульные тесты подменяют любой провайдер. Приложению
видны только публичные токены и тестовые поверхности модулей, поэтому
app-тесты подменяют зависимости на границах между модулями и фичами.
Приватный провайдер чужого модуля подменить нельзя: либо модуль
экспортирует тестовую поверхность (§5), либо подмена делается на границе,
либо тест нужно писать на другом уровне. Сам пакет небольшой:
тестируемость обеспечивает архитектура, а не пакет.

## 2. Уровень 0: без фреймворка

У юнит-теста нет импортов из `@nestling/*`. Всё, что нужно тесту,
создаётся руками:

- провайдер — класс или фабрика с явными зависимостями;
- конфиг — объектный литерал;
- порт — объект с методом `call`;
- хендлер — вызов фабрики или класса с фейками.

## 3. `assembleTest`: тестовый composition root

```typescript
import { app } from './app';   // та же декларация makeApp, что у main.ts

await using testApp = await assembleTest(app, {
  overrides: [
    [OrdersRepository, inMemoryOrdersRepo()],
    familyOverride(ILogger, () => noopLogger),
  ],
  config: vars({ ORDERS_MAX_ITEMS: '10' }),
  stubs: [stub(ChargeCard, async () => ({ chargeId: 'test' }))],
});

const res = await testApp.call(CreateOrder, { items: [...] });
```

### Подмена: `overrides`

Подмена — это замена узла графа на фазе ASSEMBLE, до создания
экземпляров. Поле `overrides: [[Token, fake]]` есть только у тестового
корня; `makeApp` его не принимает. Подменить можно только токен, на
который есть ссылка; строковой формы вроде `overrideByName('…')` нет. Пара
типизирована: фейк, не совместимый с типом токена, — ошибка компиляции.
Подмена токена, которого нет в графе, — ошибка сборки: после
переименования провайдера тест не подменяет молча пустоту.

### Поставка недостающего: `stubs`

`stubs:` поставляет то, чего в графе нет, и в отличие от `overrides:` не
требует, чтобы у токена уже был провайдер. Один список принимает и пары
из токена и значения, и стабы операций `stub(Operation, impl)` (§4).

### Прунинг

Поддерево, которое зависело только от заменённого узла, выпадает из
графа: после подмены репозитория pg-пул не создаётся и не подключается.
Что именно выпало, показывает `testApp.pruned` (список id узлов); какие
операции застабаны — `testApp.stubbed` (имена по алфавиту). Оба поля —
значения, а не вывод в консоль: их сверяют с матрицей `.check()` (§6).
Без `overrides` прунинг ничего не меняет: граф остаётся тем же до
последнего узла ([container.md](./container.md)).

### Прогон без сокетов

Тестовое приложение проходит фазы 0–3 (BOOTSTRAP…WIRE): `dispatch`
создан, START не выполняется, транспорты не принимают запросы,
обработчики `SIGTERM`/`SIGINT` не ставятся. Следствие: ресурс, который
провайдер открывает в `@OnStart`, в app-тесте открыт не будет. Ресурсы,
нужные и в тесте, открываются в `@OnInit`.

`await using` выполняет SHUTDOWN в обратном порядке. `close()` доступен и
явно; повторный вызов безопасен. Настоящий e2e — обычный `run()` на
случайном порту, вне пакета.

### `testApp.call` и `testApp.emit`

`testApp.call(Endpoint, input)` и `testApp.emit(Operation, payload, meta?)`
типизированы схемами декларации: `input` — по `input`-форме, результат —
`ResponseContext<InferOutput<O>>`, ветка отказа несёт `status` и `code`
из закрытого списка `errors:`. Запрос проходит через полный пайплайн; этим
app-тест отличается от юнит-теста. `unwrap(res)` покрывает частый случай
«ожидаю успех».

Транспортный биндинг при этом не выполняется: `call` принимает готовый
payload. Раскладку path/query/body по bind-карте проверяют e2e-тесты и
юнит-тесты bind-карты.

`emit` доставляет событие или команду всем подписчикам в этом процессе,
каждому через его собственный пайплайн, и возвращает их ответы с именем
каждого: `{ subscriber, response }[]`. Боевой `emit` не ждёт обработки,
потому что издатель за неё не отвечает; тест отвечает именно за неё, а
ждать здесь безопасно — сокета нет, подписчики в том же процессе. Ноль
подписчиков у `event` — допустимый broadcast и пустой список; у `command`
— ошибка адресации.

### Политики

Политики берутся из декларации `makeApp` и проверяются тем же проходом
фазы ASSEMBLE. Тестовый корень инварианты не ослабляет: приложение,
которое не собирается в проде, не должно собираться и в тесте
([pipeline.md §7](./pipeline.md)).

### Асинхронность

`assembleTest` асинхронна: `await using` ждёт dispose, а не инициализатор,
поэтому `await` перед вызовом обязателен. Форма без `using`
(`const testApp = await assembleTest(app, …)` и `await testApp.close()`) тоже
поддерживается — для `beforeEach`/`afterEach`.

## 4. Границы подмены в app-тесте

Чужие токены не нужны: подмена делается на публичных границах.

### Конфиг: `vars`

`vars({...})` — объектный `ConfigSource` с `watch` и программным `set()`.
Через него тестируется и механика перезагрузки: повторная проекция,
keep-last-good, `onChange`. `process.env` не трогается, поэтому тесты
можно запускать параллельно. В тестовом корне `config:` принимает три
формы: источник (сокращённая запись для `[[source, '*']]`), одну привязку
и список привязок. В декларации `makeApp` сокращённой записи нет.
Привязка из тестового корня заменяет привязку декларации.

### Вызовы между фичами: `stub`

`stub(Operation, impl)` создаёт фейковый вызыватель как значение. Он
возвращает пару из токена вызывателя и фейка (`[C.caller, …]` у `request`,
`[C.emitter, …]` у `command`/`event`), которая передаётся полем `stubs:`.
Провайдер стаба имеет приоритет над рецептом семейства вызывателей,
поэтому боевой `buildPort`/`buildEmitter` для этой операции не
вызывается и проверка достижимости не срабатывает: фича-потребитель
собирается и работает, даже если операция в этой сборке не реализован, а
шина наружу не доставляет.

Фейк проверяется схемами своего операции при каждом вызове: вход —
`input`-формой, успешный результат — `output`-формой. Возвращённый или
брошенный отказ обязан входить в `errors:` операции (плюс kernel-коды),
иначе стаб бросает исключение. Так стаб не может разойтись с операцией.
Проверка выхода делает стаб строже боевого порта в том же процессе: у
боевого ответа позади пайплайн реализации, у стаба пайплайна нет.

Профиль вызова соблюдается: исчерпанный `meta.deadline` даёт
`DeadlineExceeded` до вызова фейка, `emit` команды всегда несёт
`idempotencyKey`. Тип на стороне вызова совпадает с боевым
(`Port<C>`/`Emitter<C>`, результат — `PortResult<C>`); несовместимый фейк
— ошибка компиляции. Собственного spy у стаба нет: `impl` — обычная
функция, поэтому в этой роли работает `jest.fn()`.

### Контекст запроса: `contextValue`

`contextValue(RequestId, 'req-1')` — сокращённая запись для
`valueProvider(Ctx(X), reader)`. Ридер ambient-переменной — обычный узел
графа, поэтому подменяется тем же списком `overrides:`, что и всё
остальное. Подставленное значение имеет приоритет над рецептом семейства
и работает вне запроса, так что ALS в тестах не нужен. Тест, который
ридер не подменил, видит на `testApp.call` боевую проекцию
([container.md](./container.md)).

### Сквозные зависимости: `familyOverride`

`familyOverride(ILogger, () => noop)` подменяет рецепт семейства целиком,
до создания его членов, поэтому боевой рецепт не вызывается ни разу.
Передаётся тем же списком `overrides:`.

### Транспорт

Транспорт не подменяется: запросы идут через `dispatch` внутри процесса.
Автоматической подстановки транспортов тоже нет: они перечисляются так
же, как в проде, и endpoint на транспорте вне графа даёт тот же fail-fast
на фазе ASSEMBLE.

## 5. Тестовая поверхность модуля: subpath `./testing`

Модуль экспортирует тестовую поверхность через conditional export с
условием `"testing"`. Условие включено только в тест-раннере, поэтому
импорт из прода не резолвится на уровне Node resolution: граница
структурная. Поверхность содержит токены, разрешённые к подмене, и
готовые фейки (`inMemoryOrdersRepo()`), которые автор модуля держит в
соответствии с реализацией.

Ядро следует той же конвенции: внутренняя граница, через которую
`@nestling/testing` проводит приложение по фазам 0–3, экспортируется из
`@nestling/app` subpath'ом `@nestling/app/testing`, а не публичным
экспортом.

## 6. `.check()`: структурная проверка топологий

`.check()` проходит фазы 0–1: конструкторы выполняются, `@OnInit` — нет,
поэтому ресурсы не захватываются. Проверяются циклы, биндинг портов,
полнота env и объявленные `policies:` — по одному тесту на вариант деплоя.
Это метод декларации `makeApp`, а не собранного или тестового
приложения: `check()` компенсирует прунинг, поэтому работает на полном графе и подстановок не
принимает. Метод возвращает отчёт о составе: фичи, endpoint'ы по
транспортам с причинами `detached`, транспорты. Ошибки он бросает те же,
что бросил бы `run()` на этих фазах, и на последующий `run()` того же
приложения не влияет. Аргументы `check(select?, options?)` необязательны: первый — выбор фич,
второй — конвертеры схем.

```typescript
for (const select of ['all', 'orders', 'billing'] as const) {
  await app.check(select);
}
```

Матрица `select`-топологий проверяется в CI без деплоя одним хелпером —
`checkTopologies(app, selections, options?)`. Ядро падает на первой
ошибке, а хелпер собирает все отказы и падает одним сообщением, называя
топологию для каждого. Политики из декларации проверяются в каждой топологии,
поэтому нарушение, которое возникает только на подмножестве фич, тоже
ловится в CI. Состав detached-endpoint'ов сравнивается значением из
отчёта; парсить stdout не нужно.

Отчёт каждой топологии содержит поле `operations` — дескрипторы
опубликованных ею операций. По нему же проверяются стабы: каждый
застабанная операция обязан быть опубликован хотя бы одной полной
топологией, иначе стаб прикрывает отсутствующую реализацию.

```typescript
const published = new Set(
  (await checkTopologies(app, ['all', 'orders', 'quotas']))
    .flatMap(({ report }) => report.operations.map((c) => c.name)),
);

expect(testApp.stubbed.filter((name) => !published.has(name))).toEqual([]);
```

Это машинная форма правила «подменяешь — проверь топологию». Отдельного
хелпера для неё нет: обе стороны сравнения — уже значения.

Из тех же отчётов собирается проверка совместимости схем, без пересборки
приложения:

```typescript
const reports = await checkTopologies(app, ['all', 'orders'], {
  converters: [zodConverter()],
});

const report = diffOperations(readBaseline(), snapshotOperations(reports));
console.log(formatCompatibility(report));

expect(report.breaking).toEqual([]);   // падать или нет — решает тест
```

Отчёты топологий объединяются; вердикты и правила описаны в
[operations.md](./operations.md) §1. Фреймворк отчёт печатает; флага «падать
на breaking» нет, падение теста задаёт пользователь через `expect`.
`snapshotOperations`, `diffOperations` и `formatCompatibility`
реэкспортируются из `@nestling/testing`, чтобы CI-тест писался одним
импортом.

Ограничение: конструктор с побочным эффектом ломает `.check()`. Такой
конструктор нарушает фазовую модель: ресурсы открываются в `@OnInit`.

## 7. `testUnit(U, { stubs })`: единица в изоляции

Мини-приложение вокруг одной фичи или одного плагина — с её модулями и их
`dependsOn`, kernel-модуля конфига и стабов. Те же фазы 0–3 и тот же
результат, что у `assembleTest`. Неудовлетворённые зависимости должны быть
застабаны явно; ошибка перечисляет все недостающие токены с потребителем
каждого, а не первый попавшийся. `testUnit` живёт внутри пакета единицы,
поэтому токены видны без экспорта. Поле `stubs` принимает и стабы
операций: вызов другой фичи, объявленный этой единицей, поставляется тем
же полем, что и недостающий провайдер.
