## Context

Типовая машинерия pipeline держится на трёх приёмах, введённых change #17
(`pipeline-v2`) и живущих в `packages/nestling.pipeline/src/core/pipeline.ts`:

```typescript
export type AnyPipeline = Pipeline<any, any, any>;

type ReqOf<P>   = P extends { $types?: PipelineTypes<infer R, any, any> } ? R : never;
type AccOf<P>   = P extends { $types?: PipelineTypes<any, infer A, any> } ? A : never;
type NeedsOf<P> = P extends { $types?: PipelineTypes<any, any, infer N> } ? N : never;

type ValidateCompose<Outer extends AnyPipeline, Inner extends AnyPipeline> =
  [AccOf<Outer>] extends [ReqOf<Inner>] ? Inner : { ERROR: …; MISSING_FIELDS: …; … };

type ComposeResult<Outer extends AnyPipeline, Inner extends AnyPipeline> =
  Pipeline<ReqOf<Outer>, AccOf<Outer> & AccOf<Inner>, NeedsOf<Outer> | NeedsOf<Inner>>;

export function compose<A extends AnyPipeline, B extends AnyPipeline>(
  outer: A,
  inner: ValidateCompose<A, B> & B,
): ComposeResult<A, B>;
```

Слой объявляется как `A extends AnyPipeline` — **весь пайплайн одним
тип-параметром**, — а его `TReq`/`TAcc`/`TNeeds` достаются обратно условными
типами над фантомным `$types`. Каждый уровень вложенности
(`compose(compose(a, b), c)`) подставляет в `A` целиком результат
предыдущего `compose`, то есть `ComposeResult<…>`, и компилятор
переразворачивает всю цепочку `ReqOf`/`AccOf`/`NeedsOf` заново, на каждом
уровне.

### Замеры (TS 5.7.3, `tsc --extendedDiagnostics`, macOS/Node 22)

Фикстура — цепочка `compose(compose(…, lN‑1), lN)` из слоёв
`makePipeline().pre(uI)`, где каждый `uI` добавляет своё поле.

| Фикстура | Instantiations | Δ к базе | Check time | Диагностики |
|---|---:|---:|---:|---|
| база (пустой файл) | 408 756 | — | 2.25 s | — |
| **20 слоёв, текущая `compose`** | **22 214 827** | **+21 806 071** | **4.68 s** | **2× TS2589** |
| 20 слоёв, прототип прямого вывода | 417 664 | +8 908 | 2.37 s | — |
| 50 слоёв, прототип прямого вывода | 429 124 | +20 368 | 2.29 s | — |
| 50 слоёв, прототип с алиасом-сторожем | 429 342 | +20 586 | 2.47 s | — |

Главный факт, который дороже цифр: **на 20 слоях текущая сигнатура уже даёт
`TS2589: Type instantiation is excessively deep and possibly infinite`.**
Потолок не «медленно», а «не компилируется» — и он ближе, чем выглядел в
момент фиксации фазовой модели. Прототип на 50 слоях остаётся в пределах
+20 K инстанциаций к базе (×1000 к текущему приросту) и без ошибок.

Pre-тракт (`.pre` цепочкой) при этом дёшев: рост линейный и в пределах
десятков тысяч инстанциаций. Дорога **только вложенная композиция** — то
есть ровно то место, ради которого `AnyPipeline`-форма и вводилась.

### Текст диагностики сегодня

```
Argument of type 'PipelineBuilder<{ identity: User; requestId: string; }, …>'
is not assignable to parameter of type '{ ERROR: "Inner layer requirements
are not satisfied by outer layers"; MISSING_FIELDS: "identity";
OUTER_PROVIDES: { requestId: string; }; INNER_REQUIRES: { identity: User;
requestId: string; }; } & PipelineBuilder<...>'.
```

Проблема названа, но тонет: `MISSING_FIELDS` — юнион ключей без типов, два
поля дублируют то, что видно наведением на аргументы, хвост
`& PipelineBuilder<...>` удлиняет первую строку вдвое. Хуже того,
несовместимость по *типу* существующего поля (`requestId: string` против
`requestId: number`) даёт `MISSING_FIELDS: never` — сообщение перестаёт
называть причину.

### Ограничения площадки

- **Публичная поверхность вызова заморожена.** Change #23 — последний в
  breaking-окне волны 2; `compose(outer, …, inner)`, арности 2–4, словарь
  `.pre/.ok/.catch/.finally` и `makePipeline<TReq>()` остаются как есть.
  Переписывается **внутренняя форма типизации**, не API.
- **Та же техника уже растиражирована.** `ValidateStart` в
  `@nestling/transport.http` (`helpers.ts:79`) построен по образцу
  `ValidateCompose` и в комментарии прямо на него ссылается: форма
  литерала — уже конвенция, а не локальная деталь.
- **Снапшоты имеют смысл только поверх финальных типов** — поэтому change
  идёт последним в окне, а не первым.
- TS 5.7.3, ESM, jest с `--experimental-vm-modules`; `typescript` есть в
  devDependencies корня, компилятор доступен как библиотека.

## Goals / Non-Goals

**Goals:**

- Первая строка диагностики в точке `compose` называет проблему и
  недостающие поля **с их типами**, а не трассировку дженериков.
- Несовместимость по типу существующего поля диагностируется наравне с
  отсутствием поля.
- Форма литерала одинакова во всех точках проверки pipeline (`compose`,
  pre-тракт).
- Потолок вложенной композиции снимается: ~50 слоёв компилируются без
  `TS2589` и без заметного вклада в check time.
- Тексты диагностик зафиксированы снапшотами: деградация сообщения ловится
  дифом, а не жалобой пользователя.
- Стоимость типовой машинерии измеряется числом с порогом, падающим в CI,
  а не наблюдается.

**Non-Goals:**

- Рантайм-семантика pipeline (порядок фаз, применимость юнитов, `Ok`/`Fail`,
  `bind`/`resolve`, `PipelineImpl`) не трогается.
- Публичный API фаз и слоёв не перерабатывается; call-site `compose` не
  меняется.
- Вариадический `compose(...layers)` — расширение публичного API, не здесь.
  Замеры показали, что дорога вложенность, а не арность; вопрос возвращать
  отдельной записью, если 4 слоя за вызов окажутся тесными.
- Правило «типы-ошибки в этой форме» на весь фреймворк не вводится;
  `ValidateStart` приводится к общей форме как потребитель той же техники,
  остальные подсистемы — по мере надобности.
- `expectTypeOf`/`tsd` как замена снапшотам — отвергнуто в журнале:
  проверяют факт ошибки, не читаемость текста.
- Оптимизация типов вне pipeline (`@nestling/container`, `httpEndpoint`) —
  бенчмарк меряет только граф pipeline и эндпоинтов.

## Decisions

### D1. `compose` переписывается на прямой вывод тип-параметров

Вместо «пайплайн одним параметром + извлечение условными типами» —
тип-параметры выводятся напрямую из формы аргумента:

```typescript
type Guard<Provided, R extends AnyInput, A extends AnyInput, N> =
  [Provided] extends [R]
    ? Pipeline<R, A, N>
    : ComposeError<Provided, R>;

export function compose<
  RA extends AnyInput, AA extends AnyInput, NA,
  RB extends AnyInput, AB extends AnyInput, NB,
>(
  outer: Pipeline<RA, AA, NA>,
  inner: Guard<AA, RB, AB, NB>,
): Pipeline<RA, AA & AB, NA | NB>;
```

`ReqOf`/`AccOf`/`NeedsOf` из сигнатуры уходят; `ComposeResult<…>` уходит
тоже — накопление выражается прямо в возвращаемом типе
(`AA & AB`, `NA | NB`), а для арности 3–4 просто продолжается
(`AA & AB & AC`). Вложенность перестаёт быть рекурсивным разворачиванием:
каждый уровень выводит три параметра из уже вычисленного `Pipeline<…>`.

Проверено прототипом: 50 слоёв — 429 342 инстанциации / 2.47 s вместо
`TS2589` уже на 20 слоях. Арность 3 сохраняет и позитивный вывод
(накопленный `TAcc` = `AA & AB & AC`), и негативную диагностику на третьем
аргументе.

`AnyPipeline` **остаётся экспортом** — им пользуются рантайм-сигнатура
`compose(...pipelines: AnyPipeline[])` и внешний код; из сигнатур перегрузок
он уходит.

*Альтернатива — оставить форму и лечить симптом* (`Simplify` в `ComposeResult`,
кэширующие алиасы, повышение `--maxNodeCount`): не устраняет причину.
Переразворачивание цепочки — свойство самой формы «пайплайн одним
параметром», а не деталь реализации.

*Альтернатива — фантомный `$types` заменить на явные поля-носители:*
поменяло бы публичный тип `Pipeline`; прямой вывод даёт тот же выигрыш, не
трогая структуру.

### D2. Форма литерала — `{ __error; missing }`, `missing` — рекорд полей с типами

```typescript
type ComposeError<Provided, Required> = Simplify<{
  __error: 'Слой требует контекст, которого нет во внешних слоях';
  missing: MissingFields<Provided, Required>;
}>;

type MissingFields<Provided, Required> = Simplify<{
  [K in keyof Required as K extends keyof Provided
    ? [Provided[K]] extends [Required[K]] ? never : K
    : K]: Required[K];
}>;
```

Два поля вместо четырёх. `OUTER_PROVIDES`/`INNER_REQUIRES` уходят: полные
контексты видны наведением на аргументы, в первой строке диагностики они
только шум. `missing` — **рекорд `имя → тип`**, а не юнион ключей:

```
Argument of type 'PipelineBuilder<{ identity: User; requestId: string; }, …>'
is not assignable to parameter of type '{ __error: "Слой требует контекст,
которого нет во внешних слоях"; missing: { identity: User; }; }'.
```

Ключевой побочный эффект `as`-фильтра: в `missing` попадают **и** отсутствующие
поля, **и** присутствующие с несовместимым типом. Проверено — слой,
требующий `{ requestId: number }` от внешнего, дающего `{ requestId: string }`,
даёт `missing: { requestId: number }` там, где сегодня `MISSING_FIELDS: never`.

*Альтернатива — оставить `MISSING_FIELDS` как юнион ключей:* имя поля без
типа не отвечает на вопрос «а что туда положить», и случай несовпадения
типов остаётся немым.

### D3. Литерал разворачивается принудительно; `Simplify` — часть контракта

Замер показал: если в ветке условного типа вернуть **именованный
дженерик-алиас**, TypeScript печатает его именем и текст сообщения
пропадает:

```
… is not assignable to parameter of type
'ComposeErr<EmptyInput & { requestId: string; }, { identity: User; … }>'.
```

Разворачивание даёт обёртка `Simplify<…>` (гомоморфный mapped type
`{ [K in keyof T]: T[K] } & {}`) **вокруг самого литерала**, внутри алиаса.
Алиас-сторож (`Guard<…>` из D1) при этом безвреден: он резолвится либо в
`Pipeline<…>`, либо в уже развёрнутый `Simplify<{…}>`.

Правило формулируется как инвариант: **тип-ошибка обязана быть анонимным
развёрнутым литералом в точке печати**. Снапшот-тест — его исполнимая
проверка; иначе рефакторинг «вынести литерал в именованный алиас» тихо
съедает сообщение.

### D4. Из позиции параметра уходит `& B`

Сегодня параметр — `ValidateCompose<A, B> & B`: пересечение нужно было,
чтобы TypeScript вывел `B` из аргумента. При прямом выводе (D1) параметры
`RB`/`AB`/`NB` выводятся из ветви `Pipeline<RB, AB, NB>` условного типа, и
пересечение становится лишним. Первая строка диагностики перестаёт тащить
хвост `& PipelineBuilder<...>`.

Вывод в успешной ветке сохраняется — проверено позитивным тестом: результат
`compose(base, authed)` даёт `TAcc = { requestId: string } & { identity: User }`,
пропуск поля в присваивании — ошибка. Это закрепляется позитивными
type-тестами, а не остаётся допущением.

### D5. Pre-тракт приводится к той же форме

`CheckPreCompatibility` уже возвращает анонимные литералы (в отличие от
`ValidateCompose`, их печать не ломается), но словарь полей другой:
`ERROR`/`CONFLICTING_KEYS`/`CURRENT_INPUT`/`UNIT_ADDITION`/`UNIT_EXPECTS`.
Приводится к общей форме:

| Случай | Было | Стало |
|---|---|---|
| input не покрывает `TReq` юнита | `ERROR` + `CURRENT_INPUT` + `UNIT_EXPECTS` | `__error` + `missing` (рекорд полей) |
| юнит перезаписывает поле | `ERROR` + `CONFLICTING_KEYS` + … | `__error` + `conflicting` (рекорд `имя → [было, стало]`) |

`missing` считается тем же `MissingFields` из D2. Мотив — диагностика
pipeline должна читаться одинаково во всех точках; два словаря полей на
одну подсистему сами по себе шум.

### D6. `ValidateStart` в HTTP-транспорте приводится к общей форме

`packages/nestling.transport.http/src/helpers.ts` строит `ValidateStart` «по
образцу `ValidateCompose`» и несёт свой пятиполевой литерал с `HINT`.
Приводится к `{ __error; missing; hint }`: `hint` сохраняется (он несёт
конкретное действие — «объяви `rawBody: true`»), остальное схлопывается.
Это единственный существующий потребитель техники; оставить его с прежним
словарём — значит с первого дня иметь две формы.

*Альтернатива — не трогать транспорт:* дешевле на один файл, но фиксирует
расхождение внутри того же breaking-окна, где его чинить бесплатно.

### D7. Снапшоты — одна программа компилятора на весь каталог фикстур

`packages/nestling.pipeline/type-tests/fixtures/*.ts` — по файлу на случай;
тест создаёт **одну** `ts.createProgram` над всем каталогом,
`getPreEmitDiagnostics` группируются по файлу, каждая группа сравнивается со
своим снапшотом. Программа на фикстуру — 2+ s каждая; одна программа на
каталог — единичные секунды на весь набор.

Каталог фикстур (первая версия):

| Фикстура | Что фиксирует |
|---|---|
| `compose-missing-field` | поля нет ни в одном внешнем слое |
| `compose-wrong-type` | поле есть, тип несовместим (сегодня — `never`) |
| `compose-wrong-order` | слои переставлены местами |
| `compose-arity3-inner` | нарушение на третьем слое |
| `pre-after-response` | `.pre` после ответного метода |
| `pre-overrides-field` | pre-юнит перезаписывает существующее поле |
| `pre-requires-missing` | pre-юнит требует поля, которого нет в input |
| `unresolved-class-unit` | класс-юнит без `bind()` у транспорта |

**Нормализация перед сравнением:** абсолютные пути → относительные;
номера строк/колонок остаются (они часть полезного сигнала); переводы строк
приводятся к `\n`. Труncation типов компилятором **не отключается**
(`--noErrorTruncation` не ставится) — снапшот обязан фиксировать текст
таким, каким его видит пользователь в редакторе.

*Альтернатива — `expectTypeOf`/`tsd`:* отвергнута в журнале — проверяет факт
ошибки, не читаемость.

*Альтернатива — `// $ExpectError`-комментарии в обычных spec-файлах:* это
`@ts-expect-error`, который в репозитории уже есть и остаётся; он ловит
исчезновение ошибки, но не её текст.

### D8. Бюджет — два измерения с разной строгостью

| Измерение | Инструмент | Порог |
|---|---|---|
| `Instantiations`, `Types` | `ts.createProgram` + `--extendedDiagnostics`-эквивалент, **дельта к пустой базе** | **жёсткий** — превышение валит CI |
| латентность hover / автокомплита | tsserver по его протоколу (`quickinfo`, `completionInfo`) | **щедрый потолок** — ловит регрессию на порядок |

Счётчики детерминированы и от машины не зависят — на них жёсткий порог.
Меряется **дельта к базе** (пустой файл с тем же tsconfig), потому что
абсолютное число зависит от версии TS и `lib.d.ts`. Латентность tsserver
дрожит от машины и загрузки — на ней потолок, отсекающий обвал, а не шум.

tsserver гоняется **напрямую по протоколу** (spawn
`node_modules/typescript/lib/tsserver.js`, обмен JSON-сообщениями) — новой
зависимости не появляется.

Синтетический граф — генератор, а не закоммиченные 50 файлов: ~50 слоёв
вложенной композицией и ~50 эндпоинтов, параметр — число слоёв.

Бюджет живёт отдельным файлом (`type-tests/BUDGET.md`) с **записанными
замерами, датой, версией TS и обоснованием каждого порога**: порог без
истории через полгода никто не решится подвинуть, и он превращается либо в
священную корову, либо в `--skip`.

### D9. `type-tests/` — отдельный каталог вне `src`, отдельный nx-таргет

Каталог исключён из `build` и `lint` пакета (фикстуры **обязаны** не
компилироваться — они сломали бы и то и другое). `tsconfig.json` пакета
получает явный `include: ["src"]` вместо неявного «всё подряд».

Прогон — отдельный nx-таргет `type-budget` у `@nestling/pipeline`, с
`inputs`, включающими `src` пакета и сам каталог; корневой `verify`
становится `nx run-many -t build lint test type-budget`. Отдельный таргет
(а не «внутри `test`») — потому что кэшируется независимо и запускается
руками при работе над типами, не таща за собой весь jest-прогон.

`typescript` добавляется в devDependencies пакета явно: компилятор
используется как библиотека, а не как инструмент сборки, — неявное
наследование из корня здесь читалось бы как случайность.

*Альтернатива — снапшоты внутри `src/**/*.spec.ts`:* фикстуры с намеренными
ошибками пришлось бы держать за `@ts-expect-error`, а именно текст ошибки и
нужно прочитать.

## Risks / Trade-offs

- **Переписывание горячей сигнатуры может сломать вывод типов в неочевидном
  случае** → позитивные type-тесты (накопление `TAcc`, `TNeeds`, тип меты
  хендлера, все арности 2–4) пишутся **до** правки и обязаны остаться
  зелёными; `yarn verify` по всем пакетам ловит потребителей.
- **Три тип-параметра на слой × 4 арности = 12 параметров в последней
  перегрузке** → сигнатура многословнее; читаемость `compose` в редакторе
  падает. Цена принята: тип-параметры перегрузок пользователь не пишет
  руками, а `TS2589` он видит.
- **Снапшоты диагностик хрупки к обновлению TypeScript** → это их
  назначение, а не дефект: диф при обновлении — сигнал посмотреть, что
  ухудшилось. Смягчение — нормализация (D7) убирает шум, не относящийся к
  тексту.
- **Жёсткий порог на счётчики может ложно сработать при мажорном
  обновлении TS** → порог на дельту к базе (D8) снимает большую часть
  дрейфа; остаток обновляется вместе с записью в `BUDGET.md`.
- **Латентность tsserver в CI шумит** → потолок щедрый и намеренно ловит
  только порядок; при повторной флакующести измерение переводится в
  «печатать, не валить», а гарантией остаются счётчики.
- **Снапшоты пишутся с текущей формы типов, а форма меняется в этом же
  change** → порядок работ: сначала фикстуры + снапшоты текущих текстов
  (фиксируют «как есть»), потом правка формы, потом обновление снапшотов
  осознанным дифом. Иначе новую форму нечем сравнить со старой.
- **`ValidateStart` меняет словарь полей** → чисто внутренний тип
  транспорта (не экспортируется); ломается только type-тест на
  отрицательный случай, который тем же change и обновляется.
- **`__error` как имя поля наблюдаемо** → код, ссылающийся на
  `ERROR`/`MISSING_FIELDS`/`OUTER_PROVIDES`/`INNER_REQUIRES` (только
  type-тесты внутри репозитория), ломается; это внутри breaking-окна.

## Migration Plan

Каждый шаг оставляет репозиторий собираемым:

1. **Оснастка без правки типов.** `type-tests/` (генератор графа, раннер
   снапшотов, раннер бюджета, `BUDGET.md`), `tsconfig.json` пакета с явным
   `include`, nx-таргет `type-budget`, `typescript` в devDependencies
   пакета, `verify` в корне.
2. **Фикстуры + снапшоты текущих текстов.** Снимаются с сегодняшней формы —
   это база сравнения. Первый замер бюджета записывается в `BUDGET.md` как
   «до» (включая `TS2589` на 20 слоях).
3. **Позитивные type-тесты вывода** для всех арностей — расширение
   `pipeline.spec.ts` до правки сигнатуры.
4. **Переписывание `compose`** (D1, D4) — сигнатуры перегрузок,
   `Guard`/`ComposeError`/`MissingFields`; удаление `ValidateCompose` и
   `ComposeResult` из сигнатур. Замер бюджета обновляется, порог ставится.
5. **Форма литерала** (D2, D3) и приведение pre-тракта (D5); снапшоты
   обновляются осознанным дифом.
6. **`ValidateStart`** в `@nestling/transport.http` (D6) + его type-тест.
7. **Доки:** `docs/design/pipeline.md` §4 сверяется с реализацией
   (форма литерала и бюджет уже описаны как целевое — проверить точность),
   README `@nestling/pipeline` (раздел о диагностике и о том, где живёт
   бюджет), `TYPE-TESTS.md`, статус #23 и закрытие breaking-окна волны 2
   в `docs/decisions/roadmap.md`.

Откат — ветка целиком; промежуточного режима «две формы литерала» нет
намеренно.

## Open Questions

- **Порог латентности tsserver в цифрах** — назначается по первому замеру на
  CI-раннере; до этого момента измерение печатает результат, но не валит.
  Решается в шаге 1–2 миграции, фиксируется в `BUDGET.md`.
- **Нужен ли `hint` в общей форме литерала.** `ValidateStart` его несёт по
  делу (конкретное действие), у `compose` действия нет («добавь слой,
  который положит поле» — не действие). Пока `hint` остаётся
  необязательным полем формы, а не частью её ядра; если у `compose`
  появится осмысленная подсказка — вернуть аддитивно.
- **Вариадический `compose(...layers)`** — прямой вывод (D1) делает
  variadic tuple types реалистичными (`...rest: Pipelines<…>`), но это
  расширение публичного API за границей окна. Кандидат в отдельную запись,
  если 4 слоя за вызов окажутся тесными.
- **Распространение формы `__error` на остальные подсистемы**
  (`endpoint`-словари, `bind`-карта, будущие `makeContract`/`makeConfig`) —
  здесь фиксируется только для pipeline и её единственного существующего
  потребителя; общее правило заводить рано, пока не набралось трёх точек.
