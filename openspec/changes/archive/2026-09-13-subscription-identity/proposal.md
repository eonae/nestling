## Why

Реестр подписок узнаёт подписанта экстрактором, типизированным общим
контекстом: `SubscriptionContext = ExtendableContext<AnyInput>`, где
`AnyInput = Record<string, unknown>`. Форму `input` знает приложение, но
выразить её в опциях плагина негде, поэтому и пример, и JSDoc пакета, и
спеки пишут приведение:

```typescript
identity: (ctx) => (ctx.input as { requestId?: string }).requestId
```

`as` отключает проверку: переименованное поле даёт `undefined` молча, и
подписки теряют подписанта в рантайме. Это нарушает «guarantee over
convention», а приведение здесь — рекомендованный способ, а не недосмотр
одного примера.

Решение зафиксировано записью
[ideas.md [2026-09-13]](../../../docs/decisions/ideas.md) «Разбор фидбэка по
коду d/15», п. 10 (строка 95 [roadmap](../../../docs/decisions/roadmap.md)):
`identity` принимает переменную контекста. Приложение уже объявляет
`RequestId` штатным слоем наблюдаемости и требует её политикой
`everyEndpoint(…).hasVar(RequestId)` — реестру достаточно назвать эту
переменную, а не пересказывать форму `input` приведением.

## What Changes

- **BREAKING** `identity` опций плагина принимает контекстную переменную:
  `subscriptions({ identity: RequestId })`. Реестр хранит значение
  переменной и формы `input` не знает.
- Функция остаётся второй формой — для вычисляемого ключа
  (`(ctx) => ctx.input.tenant + ':' + ctx.input.userId`). Она типизируется
  накопленным контекстом, объявленным аннотацией `ctx`, а не `AnyInput`:
  приведения не требует ни одна из форм.
- `labels` получает ту же типизацию контекстом. Формы переменной у него нет:
  метки — словарь, переменная такого типа не встречается.
- Приведение `as` исчезает из примера `examples/microservice`, JSDoc
  `module.ts`, README пакета на обоих языках, спеков и глав документации.
- Реестр читает значение переменной по её ключу из накопленного `input`.
  Нестроковое значение и отсутствие поля дают подписку без `identity` —
  тот же исход, что у экстрактора, вернувшего `undefined`.
- `@nestlingjs/app` публикует предикат `isContextVar`: различать переменную
  и функцию должен тот, кто владеет формой переменной, а не сателлит.

## Capabilities

### New Capabilities

Новых способностей нет.

### Modified Capabilities

- `subscription-registry`: требование «Снимок подписки — замороженное
  значение» и требование «Реестр — параметризованный инфра-модуль» меняют
  формулировку источника `identity`: не «экстрактор», а «контекстная
  переменная либо экстрактор, типизированный накопленным контекстом».
  Добавляется правило чтения значения переменной и исход для отсутствующего
  значения.
- `async-context-vars`: публичным становится предикат `isContextVar` —
  потребителю переменной нужно отличать её от функции в рантайме.

## Impact

**Код.** `packages/nestling.subscriptions`: `registry.ts` (типы
`IdentitySource`, `LabelsSource`, чтение значения в `open`), `module.ts`
(JSDoc, параметры типа фабрики), `index.ts` (экспорт новых типов),
`registry.spec.ts`, `module.spec.ts`, `boundary.spec.ts` (список
импортируемых имён). `packages/nestling.app`: экспорт `isContextVar` из
корневого barrel.

**Примеры.** `examples/microservice/src/ops/ops.plugin.ts` —
`identity: RequestId`.

**Документация.** README пакета обоих языков, `docs/design/streaming.md`
§4.1, `docs/guide/14-features.md`, `docs/recipes/ops.md`,
`docs/recipes/extending.md` и их английские зеркала.

**Совместимости не требуется.** Старая форма экстрактора с приведением
удаляется вместе с примерами, где она стояла.

## Non-goals

- Параметр типа у реестра (`subscriptions<TInput>({…})`) — отвергнут в той
  же записи ideas.md: он убирает `as`, но заставляет приложение объявить
  форму `input` руками второй раз.
- Переменная в `labels`: метки остаются функцией.
- Проверка на сборке, что переменная `identity` объявлена пайплайном
  трекаемого endpoint'а. Такую гарантию уже даёт политика
  `everyEndpoint(…).hasVar(…)`; своей политики пакет не заводит.
- Фильтр `list({ identity })` и снимок `SubscriptionInfo.identity`: остаются
  строкой. Меняется источник значения, не его тип.
