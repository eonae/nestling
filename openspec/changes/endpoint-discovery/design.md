## Context

Сегодня список эндпоинтов приложения живёт в модульном глобальном `Set`:

- `packages/nestling.pipeline/src/metadata/endpoint-registry.ts:10` —
  `const endpointRegistry = new Set<Constructor<IEndpoint>>()`;
- `metadata/endpoint.ts:111` — декоратор `@Endpoint` вызывает
  `registerEndpoint(target)` **в момент вычисления декоратора**, то есть при
  импорте файла; то же делает `@HttpEndpoint`
  (`packages/nestling.transport.http/src/helpers.ts:110`);
- `packages/nestling.app/src/app.ts:200` — `App.#registerEndpoints()`
  итерирует `getAllEndpoints()`, для каждого класса делает
  `container.get(EndpointClass)` и **бросает**, если инстанса нет.

Следствие: множество «известных эндпоинтов» определяется графом импортов,
а не составом контейнера. Импортнул barrel соседней фичи (или её тест) —
её эндпоинты в реестре — `App` пытается их инстанцировать — падение.
Тесты вынуждены звать `clearEndpointRegistry()` в `beforeEach`
(`packages/nestling.app/src/app.spec.ts:28`) — это прямой симптом
глобального состояния.

Вторая половина проблемы — **носитель списка**. `makeAppModule`
(`packages/nestling.app/src/module.ts`) принимает `endpoints: [...]`, но
возвращает `makeModule({ ...cfg, providers: [...providers, ...endpoints] })`:
поле `endpoints` **исчезает** из возвращаемого значения. То есть обойти
дерево модулей сегодня нельзя даже при желании — списка там нет, он
растворён в провайдерах. Именно поэтому реестр и понадобился.

Что даёт опору:

- **Модули — plain values**, дерево строится полем `imports: Module[]`;
- `ContainerBuilder.registerModule` (`container.builder.ts:219`) обходит
  дерево сам: сначала `imports` (рекурсивно), затем свои `providers`,
  дедупликация **по имени модуля** (`#modules: Set<string>`);
- метаданные эндпоинта лежат на конструкторе под `Symbol.for('nestling:handler')`
  и читаются одним `getEndpointMetadata()` — и для `@Endpoint`,
  и для `@HttpEndpoint`;
- `@nestling/app` уже зависит и от `@nestling/container`, и от
  `@nestling/pipeline`, так что дискавери есть где поселить, не заводя
  новых рёбер между пакетами.

Логика решения — [ideas.md](../../../docs/decisions/ideas.md),
«[2026-07-08] Модульный монолит: фичи, `select`, дискавери из дерева
модулей»; разбор — [d/05 §1](../../../docs/history/discussions/05-modular-monolith-features-ports.md).
Целевые формулировки уже записаны: [design/container.md](../../../docs/design/container.md)
(«Дискавери провайдеров, endpoints и транспортов — обходом дерева
зарегистрированных модулей; глобальных реестров-при-импорте нет») и
[design/composition.md](../../../docs/design/composition.md) §1 (инвариант
«дискавери из дерева модулей, не глобальный registry» на фазе ASSEMBLE).
Change #8 из roadmap, breaking-окно волны 2, размер S.

## Goals / Non-Goals

**Goals:**

- Сделать состав контейнера единственным источником истины о том, какие
  эндпоинты обслуживает приложение; импорт файла перестаёт что-либо значить.
- Удалить глобальный реестр целиком, вместе с публичными функциями.
- Дать дискавери **форму значения** (список эндпоинтов с атрибуцией к
  модулю + карта требуемых транспортов), пригодного для `features` (#10)
  и policy-check на полном графе (#28), и тестируемого без контейнера.
- Превратить два молчаливых режима (класс без метаданных; эндпоинт мимо
  `endpoints:`) в ошибки старта.
- Сохранить всё остальное поведение `App` бит-в-бит: порядок фаз
  `build → init → регистрация → listen`, резолюцию классов-юнитов через
  `bind`, тексты и семантику остальных ошибок.

**Non-Goals:**

- Форма деклараций: `@Endpoint`/`@HttpEndpoint`/`IEndpoint` остаются,
  `endpoints:` принимает конструкторы. Перевод на значения — #24.
- Транспорты-провайдеры, ссылка на транспорт токеном,
  `serve(dispatch, signal)` вместо `listen()`, фазовый жизненный цикл —
  #10.
- `makeFeature`/`select`/`assemble`, отбор транспортов по топологии — #10.
- Предикаты policy-check — #28; здесь только полный граф для них.
- Перенос `endpoints` в `Module` пакета `@nestling/container` — это
  затащило бы типы эндпоинтов в DI-пакет; вопрос решается вместе с #24,
  когда декларация станет транспорт-нейтральным значением.

## Decisions

### 1. Дискавери живёт в `@nestling/app` и читает поле `endpoints` структурно

Обход дерева — код `@nestling/app`, а не `@nestling/container`. Контейнер
не должен знать про эндпоинты: он собирает граф провайдеров, а эндпоинт —
понятие транспортного этажа. Обход читает поле `endpoints` с **любого**
значения-модуля в дереве (структурно, через type guard), а не только с
результата `makeAppModule` — так дискавери не зависит от того, какой
конструктор модуля использован.

**Альтернатива (отвергнута):** добавить `endpoints?: unknown[]` в
`Module` контейнера и обходить дерево там. Даёт «дискавери из одного
места», но либо тащит `IEndpoint` в DI-пакет, либо типизирует поле как
`unknown[]` — обе цены платятся сейчас, а через change #24 форма
декларации всё равно поменяется.

### 2. `makeAppModule` перестаёт терять `endpoints`

```ts
export interface AppModule extends Module {
  endpoints?: Constructor<IEndpoint<any, any, any>>[];
}

export function makeAppModule(config: AppModule): AppModule;
```

Возврат — `AppModule` (было: `Module`), поле `endpoints` сохраняется,
эндпоинты **по-прежнему** дублируются в `providers`, чтобы контейнер их
инстанцировал. Расширение assignable к `Module`, поэтому `imports`,
`ContainerBuilder.register` и существующий пользовательский код
компилируются без правок; контейнер лишнее поле игнорирует.

Модуль, собранный вручную (`makeModule({ name, providers, endpoints })`),
дискавери увидит, но контейнер эндпоинты не зарегистрирует — получится
понятная ошибка «объявлен в `endpoints:` модуля X, но недоступен в
контейнере». Это приемлемо: канон — `makeAppModule`, а ошибка называет
и модуль, и способ починки.

**Альтернатива (отвергнута):** отдельный реестр «модуль → эндпоинты»
(`WeakMap`), заполняемый в `makeAppModule`. Тот же глобальный
side-channel, только спрятанный; значение-модуль должно быть
самоописательным.

### 3. Обход зеркалит `ContainerBuilder.registerModule`

Правила обхода буквально те же, что у контейнера, чтобы «что собрано» и
«что обнаружено» не могли разъехаться:

- depth-first, `imports` обходятся **до** собственных эндпоинтов модуля;
- дедупликация модулей **по имени** (`Set<string>`), как `#modules` в
  билдере, — цикл `A → B → A` завершается, повторный импорт одного
  модуля обходится один раз;
- эндпоинты одного модуля — в порядке объявления в массиве;
- один и тот же класс, перечисленный дважды **внутри** модуля,
  регистрируется один раз (дедуп по ссылке на конструктор).

Порядок результата детерминирован и воспроизводим — на этом стоит
воспроизводимость `explain()`/viz в следующих changes.

Дубль **между** модулями отдельного правила не требует: оба модуля кладут
класс в `providers`, и контейнер падает раньше дискавери своим
`Provider for token '…' is already registered`.

**Альтернатива (отвергнута):** дедуп модулей по ссылке на объект. Разошлось
бы с контейнером: два разных объекта с одним именем контейнер считает
одним модулем (второй молча игнорируется), а дискавери увидела бы оба и
зарегистрировала эндпоинты, которых в графе нет.

### 4. Результат дискавери — значение, а не побочный эффект

```ts
interface DiscoveredEndpoint {
  endpoint: Constructor<IEndpoint<any, any, any>>;
  metadata: EndpointMetadata;
  moduleName: string;              // кто объявил — для текстов ошибок и аудита
}

interface EndpointDiscovery {
  endpoints: DiscoveredEndpoint[];             // детерминированный порядок
  transports: Map<string, DiscoveredEndpoint[]>; // требуемый транспорт → его ручки
}

function discoverEndpoints(modules: readonly Module[]): EndpointDiscovery;
```

Чистая функция без контейнера и без транспортов: её видно тестами
напрямую (обход, дедуп, порядок, циклы, атрибуция), и она — тот самый
шов, на который встанут `select` (#10) и предикаты по полному графу
(#28). `App.#registerEndpoints` становится потребителем этого значения,
а не местом, где дискавери спрятан.

Карта `transports` строится сразу здесь, потому что «какие транспорты
затребованы» — свойство дерева, а не рантайма `App`.

**Альтернатива (отвергнута):** приватный метод `App`, возвращающий плоский
массив. Дешевле на пару строк, но #28 нужен именно граф с атрибуцией,
а тестировать обход пришлось бы через поднятие приложения.

### 5. Транспорты: требуемое множество — из дерева, поднимаются все сконфигурированные

`App` сверяет ключи `discovery.transports` с `config.transports`.
Отсутствующий транспорт — ошибка старта, называющая транспорт, модуль и
паттерн ручки (сейчас текст называет только класс эндпоинта).

Обратное направление — сконфигурированный транспорт, на который дискавери
ничего не дала — **не ошибка и не повод его не поднимать**: у транспорта
есть маршруты помимо дискавери (`HttpTransport.route()`,
`registerEndpoint()` напрямую), а отбор транспортов по топологии — прямое
следствие `select` и приезжает с #10 вместе с транспортами-провайдерами.
Ужесточать здесь — значит принять решение #10 задним числом и без `select`.

**Альтернатива (отвергнута):** поднимать только затребованные транспорты.
Выглядит как «то самое» поведение модульного монолита, но без `select`
множество затребованных транспортов задаётся вручную тем же, кто задаёт
мешок, — то есть проверка ловит опечатку, а не топологию, ценой поломки
легитимного сценария «транспорт с ручными маршрутами».

### 6. Отсутствие метаданных — ошибка, а не `console.warn`

Сегодня класс в реестре без метаданных пропускается с `console.warn`
(`app.ts:206`) — разумно, когда список формировался импортами и мог
содержать мусор. Когда класс перечислен в `endpoints:` **явно**,
отсутствие `@Endpoint`/`@HttpEndpoint` — ошибка декларации, и молчать
про неё нельзя: приложение поднимется без ручки. Fail-fast с именем
класса и модуля.

### 7. Эндпоинт-класс мимо `endpoints:` — тоже ошибка старта

Главный риск перехода: класс с `@HttpEndpoint`, который раньше
обслуживался «просто потому что импортнут», после change молча перестаёт
обслуживаться. Поэтому `App` линтует объявленные `providers` дерева
(и корневой `AppConfig.providers`): конструктор, несущий метаданные
эндпоинта и **не** перечисленный ни в одном `endpoints:`, — ошибка старта
с указанием модуля и подсказкой «добавь в `endpoints:`».

Ограничение честное и документируется: провайдеры, порождённые
`ProvidersFactory` (функция, разворачиваемая билдером), до `build()`
не видны — эта форма не линтуется.

**Альтернатива (отвергнута):** предупреждение вместо ошибки. Молчаливо
необслуживаемая ручка — ровно тот класс дефектов, который change и
устраняет; предупреждение в логе старта его не устраняет.

### 8. Реестр удаляется целиком, без deprecation-периода

`endpoint-registry.ts`, его реэкспорт и оба вызова `registerEndpoint`
уходят одним шагом. Оставить `getAllEndpoints()` как deprecated нельзя:
любой оставшийся вызов `registerEndpoint` сохраняет ровно ту протечку,
ради которой затевается change. Пакет доrelease'ный, потребители внутри
репозитория — только `App` и два декоратора; change идёт в breaking-окне
волны 2, а сам реестр умрёт вместе с декораторами в #24.

### 9. Тексты ошибок получают атрибуцию к модулю

Все три fail-fast'а (нет метаданных · нет транспорта · класс объявлен, но
не резолвится контейнером) называют **модуль-объявитель**. Это дешёвое
следствие того, что дискавери и так носит `moduleName`, и оно же —
разница между «endpoint X недоступен» и «endpoint X, объявленный
в module:users, недоступен: добавь @Injectable или положи в providers».

### 10. Изоляция тестов становится структурной

`clearEndpointRegistry()` из `beforeEach` уходит вместе с реестром:
два теста, объявляющие эндпоинты внутри `it()`, больше не влияют друг на
друга, потому что видимость эндпоинта задаётся значением модуля,
переданного в конкретный `App`. Тест «в реестре, но не в контейнере»
переписывается в «объявлен в `endpoints:` модуля, но не резолвится» —
он проверяет тот же fail-fast, но по новому источнику.

## Risks / Trade-offs

- **[Молчаливая потеря ручки при миграции]** Эндпоинт, работавший «за
  счёт импорта», после change не обслуживается → Митигация: решение 7 —
  fail-fast на классе с метаданными вне `endpoints:`; плюс задача сверки
  всех девяти эндпоинтов `examples.app-with-http` со списком в
  `users.module.ts` и ручная проверка поднятия примера.

- **[Расхождение обхода дискавери и контейнера]** Разные правила
  дедупликации дали бы «обнаружен, но не собран» (или наоборот) →
  Митигация: решение 3 фиксирует правила как зеркало
  `ContainerBuilder.registerModule`; тест на два разных объекта модуля с
  одним именем и тест на цикл `imports` — в дельта-спеке и в задачах.

- **[Breaking для внешних потребителей `@nestling/pipeline`]** Уходят три
  публичные функции → Митигация: breaking-окно волны 2 до фиксации API
  V1; миграция механическая («перечисли эндпоинты в `endpoints:` модуля»),
  описана в proposal; внутри репозитория потребителей три и все правятся
  этим же change.

- **[`ProvidersFactory` не линтуется]** Эндпоинт, порождённый фабрикой
  провайдеров, проверку решения 7 не проходит и остаётся молча
  необслуженным → Митигация: ограничение фиксируется в дельта-спеке
  явным требованием и в README; фабрики провайдеров в репозитории
  эндпоинтов не порождают.

- **[Тип возврата `makeAppModule` сузился с `Module` до `AppModule`]**
  Код, аннотировавший переменную как `Module`, продолжает
  компилироваться (расширение assignable), но код, полагавшийся на
  **отсутствие** поля (точное равенство типов, `exactOptionalPropertyTypes`
  на своих обёртках), может потребовать правки → Митигация: риск
  теоретический, внутри репозитория таких мест нет; отмечается в
  «What Changes».

## Migration Plan

1. `@nestling/app`: модуль дискавери (`discoverEndpoints`, типы), юнит-тесты
   обхода без контейнера.
2. `@nestling/app`: `makeAppModule` сохраняет `endpoints`; `App` переходит
   на результат дискавери, добавляются три fail-fast'а и проверка
   требуемых транспортов; тесты `app.spec.ts` переписываются.
3. `@nestling/pipeline` и `@nestling/transport.http`: удаление
   `endpoint-registry.ts`, реэкспорта и обоих вызовов `registerEndpoint`;
   `grep` на остатки.
4. Дельта-спек `endpoint-discovery`, README пакетов, гайд
   `docs/guides/http-app-di.md` (+ дата плашки), статус #8 в roadmap.
5. `examples.app-with-http`: сверка списка `endpoints:` и ручная проверка
   `yarn start`; `yarn verify` + `yarn docs:audit` (0 ERROR).

Порядок 1→2→3 важен: пока `App` не переехал на дискавери, удаление
реестра ломает сборку. Откат — revert коммитов ветки: change ничего не
мигрирует на диске и не меняет формат данных.

## Open Questions

Нет. Форма декларации (`endpoints:` конструкторами против значений),
транспорты-провайдеры и `select` — предмет changes #24 и #10, их
целевое состояние уже зафиксировано в `design/` и в журнале; этот change
намеренно не решает их заранее.
