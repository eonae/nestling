## Context

Декларация операции уже содержит всё, из чего состоит определение
MCP-инструмента. `makeRequest` требует `name`, принимает `input`, `output`,
`errors` и секцию `doc`; определение инструмента в протоколе требует `name`,
`inputSchema` и принимает `description`, `outputSchema` и `annotations`.
Соответствие полное, и переводить приходится только схемы — из Standard
Schema в JSON Schema.

Механизм не новый. `@nestlingjs/openapi` читает декларации и отдаёт документ,
`@nestlingjs/client` читает те же декларации и отдаёт типизированный клиент.
Сателлит MCP — третий потребитель того же значения.

Роль сателлита задают три свойства ядра:

- **Транспорт получает `Dispatch` аргументом `serve`.** Таблица маршрутов
  строится на фазе WIRE по одному диспетчеру на транспорт и только из
  endpoint'ов этого транспорта
  (`packages/nestling.app/src/transport/dispatch.ts`). Исполнить чужой
  endpoint нельзя, свои — можно, и другого способа исполнять их не нужно.
- **Несколько транспортов делят один сокет.** Сокетом владеет `HttpServer`,
  транспорты присоединяют обработчики в `serve`, а обработчик сообщает,
  взял ли он запрос (`packages/nestling.transport.http/src/server.ts`).
  Пример из [transports.md §4.2](../../../docs/design/transports.md) —
  `http({ server: api })` и `graphql({ server: api })`.
- **Проекция маршрута несёт не всё.** `toRouteDeclaration` копирует
  `transport`, `pattern`, `input`, `output`, `binding` и `errors`. Секции
  `doc` в ней нет, поэтому описание инструмента обязано ехать в `binding` —
  там же, где у HTTP едет bind-карта.

Образец формы — `cli(...)`: транспорт с собственным конструктором
деклараций, собственным биндингом (`cliBindingOf`) и построением плана
вопросов в `serve` из JSON Schema, полученной конвертером из
`cli({ converters })`.

## Goals / Non-Goals

**Goals:**

- Определение инструмента выводится из декларации; второго описания для
  агента не пишется.
- Состав инструментов виден там же, где состав любого транспорта, —
  в `endpoints:` фич.
- Инструмент исполняется пайплайном своей декларации, без второго пути
  исполнения.
- Отказ операции попадает к агенту отказом, а не исключением протокола.
- Ошибка объявления обнаруживается до того, как сервер откроет сокет.
- Зависимостей рантайма от валидатора и от SDK у пакета нет.

**Non-Goals:**

Перечислены в [proposal.md](./proposal.md), раздел «Non-goals». Коротко:
только `tools`, только ответ на запрос клиента, без аутентификации, без
stdio, без полей MCP в секции `doc`, без собственного сокета.

## Decisions

### 1. MCP — транспорт, инструмент — endpoint

```typescript
const api = httpServer();

makeApp({
  features: [UsersFeature],
  transports: [
    http({ server: api }),
    mcp({
      server: api,
      info: { name: 'users-service', version: '1.0.0' },
      converters: [zodConverter()],
    }),
  ],
});
```

Транспорт объявляется `makeTransportDeclaration` — тем же примитивом, что
`http()` и `nats()`. Способности — `value` в обе стороны: аргументы и
результат инструмента это значения.

**Почему транспорт, а не плагин.** Агент присылает запрос, сервер выбирает
маршрут, исполняет его пайплайном и отвечает. Это и есть работа транспорта.
Плагину пришлось бы исполнять чужие endpoint'ы, а `Dispatch` ему недоступен.

**Отвергнуто: плагин со списком `tools:` и вызовом через
`Operation.caller`.** Вызыватель доходит только до реализации на интеркоме:
топология считает реализациями декларации с bus-биндингом
(`packages/nestling.app/src/ports/topology.ts`), поэтому операция,
реализованная `httpEndpoint.implement`, вызывателю недоступна, и сборка
падает на ASSEMBLE. Кроме того, вызов через порт добавлял бы второй путь
исполнения рядом с пайплайном декларации.

### 2. Две формы декларации, как у каждого транспорта

```typescript
// Анонимная: инструмент объявлен вместе со схемами
export const SearchUsers = mcpTool('search_users', {
  description: 'Найти пользователей по подстроке в адресе почты.',
  annotations: { readOnlyHint: true },
  input: z.object({ query: z.string() }),
  output: z.object({ total: z.number() }),
  handler: SearchUsersHandler,
});

// Операционная: схемы, отказы и описание берутся с операции
export const CreateUserTool = mcpTool.implement(CreateUser, {
  annotations: { idempotentHint: false },
  handler: CreateUserHandler,
});
```

Форма повторяет `httpEndpoint`: анонимный конструктор с адресом первым
аргументом и `implement` для объявленной операции
([endpoints.md §1](../../../docs/design/endpoints.md)). Секции `mcp:` на
операции нет: адрес инструмента выводится из `operation.name` заменой точек
на подчёркивания, потому что протокол принимает имя из `[a-zA-Z0-9_-]`.

`mcpTool.implement` принимает операцию вида `request`. У `command` и `event`
результата, который агент мог бы прочитать, нет.

**Одна операция на двух поверхностях.** `httpEndpoint.implement(CreateUser,
…)` и `mcpTool.implement(CreateUser, …)` в одном приложении дают две
входящие поверхности у одной операции и один класс-хендлер. Запрет «два
владельца» срабатывает на двух bus-биндингах, а у этих деклараций биндинги
транспортные и разные. Это проверяется спекой: свойство неочевидное, и
держать его нужно тестом.

### 3. Метаданные инструмента — в биндинге декларации

`toRouteDeclaration` не копирует `doc`, поэтому имя, описание и подсказки
агенту складываются в `binding` конструктором декларации — так же, как
`computeHttpBinding` складывает туда карту размещения полей:

```typescript
interface McpBinding {
  readonly tool: string;
  readonly description: string;
  readonly annotations?: McpToolAnnotations;
}
```

Описание вычисляется в точке объявления: `options.description`, иначе
`operation.doc.description`, иначе `operation.doc.summary`. Требование
строже, чем у документа OpenAPI, намеренно: агент выбирает инструмент по
описанию, и инструмент без описания он выбрать не может.

### 4. Уникальность имени инструмента обеспечивает ядро

`pattern` декларации — имя инструмента. Уникальность пары «экземпляр
транспорта, паттерн» ядро проверяет на ASSEMBLE
(`pattern-uniqueness.spec.ts`), поэтому собственной проверки имён пакету не
нужно. Два инструмента с одним именем валят сборку до INIT.

### 5. Определения инструментов строятся в `serve`

`tools/list` собирается один раз из `dispatch.routes`, когда транспорт
получает диспетчер. Там же проверяются формы io
(`assertFormsSupported`) и собственные правила пакета:

- схема входа переводится в JSON Schema;
- переведённая схема входа объектная — этого требует протокол;
- у инструмента есть непустое описание.

Нарушения копятся и сообщаются одним списком, как у генератора OpenAPI.
`serve` идёт раньше `listen`, поэтому сборка падает до того, как сокет
открыт.

**Почему не ASSEMBLE.** Провайдера у транспорта нет, а определения нужны
ему самому. `cli(...)` строит план вопросов ровно там же и по той же
причине.

### 6. Схемы — те же конвертеры, что у OpenAPI

`inputSchema` и `outputSchema` получаются вызовом `leafJsonSchema(converters,
leaf, { io })` — публичного помощника ядра. Пакет не зависит ни от одного
валидатора: конвертер приходит данными в `converters:`.

`outputSchema` объявляется тогда и только тогда, когда форма выхода
переводится в объектную JSON Schema. Клиент, увидев `outputSchema`,
проверяет по ней `structuredContent`; выход-число или выход-массив под это
не подходят, и объявлять схему было бы обещанием, которого сервер не
сдержит.

### 7. Протокол своей реализацией, SDK в `devDependencies`

`@modelcontextprotocol/sdk@1.30.0` объявляет семнадцать зависимостей, среди
них `express`, `hono`, `cors`, `jose`, `ajv` и `zod`. Они ставятся все, даже
если импортируется один модуль. У `@nestlingjs/transport.http` зависимостей
две, у ядра ноль; сателлит с двумя HTTP-фреймворками в дереве выпадает из
этого ряда. Транзитивная зависимость от zod вдобавок сняла бы у пакета то
свойство, которое `@nestlingjs/openapi` держит тестом.

Поэтому протокол реализуется в пакете, а SDK стоит в `devDependencies` и
работает доказательством:

- **Сверка типов.** `mcp.type-test.ts` присваивает наши `McpToolDefinition` и
  `McpCallToolResult` типам `Tool` и `CallToolResult` из
  `@modelcontextprotocol/sdk/types.js`. Расхождение — ошибка компиляции.
- **Интеграционный прогон.** Тест поднимает приложение, соединяет с ним
  `Client` из SDK по HTTP и вызывает `listTools()` и `callTool()`. Ответ
  сервера проверяет настоящая реализация клиента, а не наши ожидания.

Объём собственной реализации — конверт JSON-RPC 2.0 и пять методов:
`initialize`, `notifications/initialized`, `ping`, `tools/list`,
`tools/call`.

**Отвергнуто: SDK в `dependencies`.** Дешевле в коде и дороже в установке;
цена платится каждым, кто ставит пакет.

**Отвергнуто: отказаться от SDK вовсе.** Тогда соответствие протоколу
подтверждали бы только наши тесты, написанные по нашему же прочтению
спецификации.

### 8. Один путь `POST`, потока событий нет

Транспорт присоединяет к серверу один обработчик и берёт запросы `POST` по
`options.path` (умолчание `/mcp`) и `DELETE` по нему же. Тело запроса —
одно сообщение JSON-RPC, ответ — сообщение JSON-RPC со статусом 200.
Нотификация (сообщение без `id`) получает 202 без тела, как требует
спецификация. `DELETE` закрывает сессию.

`GET` транспорт не берёт: поток событий нужен серверу, который сам
инициирует сообщения, а таких сообщений в объёме нет. Запрос уходит дальше
по цепочке обработчиков и получает `404` от сервера. Спецификация протокола
предпочла бы `405`, и клиент SDK его распознаёт особо; `404` он сообщает
своему `onerror` и продолжает работать, потому что поток необязателен.
Кодов вне перечня категорий отказа у ядра нет, и заводить их ради одного
ответа этот change не будет.

**Почему не `StreamableHTTPServerTransport` из SDK.** Он принимает
`IncomingMessage` и `ServerResponse`, а собственный обработчик сервера их
как раз и получает. Вместе с ним в дерево установки попали бы `express` и
`hono` из зависимостей SDK.

### 9. Сессия — состояние транспорта

Карта «идентификатор сессии — согласованная версия протокола» живёт в
экземпляре транспорта и очищается в `close()`. Отдельного ресурса не нужно:
у транспорта уже есть жизненный цикл, и `close()` вызывается на SHUTDOWN.

`initialize` заводит сессию и возвращает её идентификатор заголовком
`Mcp-Session-Id`. Запросы `tools/list` и `tools/call` этот заголовок несут;
неизвестный идентификатор — отказ категории `not_found`. Заголовок
`MCP-Protocol-Version` сверяется со списком поддерживаемых версий;
расхождение — отказ категории `bad_request`.

Ограничения на сессии — предельное число и срок бездействия — объявляются
опциями транспорта. Предел по умолчанию 100, срок бездействия пять минут:
столько же держат сессию большинство реализаций Streamable HTTP, а агент
между вызовами инструментов думает секунды.

### 10. `Ok` и `Fail` — два исхода вызова инструмента

Успех отдаётся `content` со значением в виде JSON-текста и, если у
инструмента объявлена `outputSchema`, ещё и `structuredContent`: второе поле
нужно клиентам, которые структурированный ответ читают.

Отказ отдаётся `isError: true` и текстом, в котором названы `code`,
`message` и `details` отказа. В `structuredContent` детали отказа не уходят:
клиент проверяет это поле объявленной схемой выхода, и отказ под неё не
подходит. Исключением протокола отказ не становится: отказ — часть
объявленного контракта операции, и агент должен его прочитать и учесть.

Неожиданная ошибка превращается ядром в `internal_error` ещё в пайплайне, и
до транспорта доходит обычным отказом без текста исключения и стека.

### 11. Границы пакета

Тест границы перечисляет разрешённые импорты, как в других пакетах.
`@nestlingjs/mcp` импортирует `@nestlingjs/app`, `@nestlingjs/container`,
`@nestlingjs/operations`, `@nestlingjs/transport.http` и модули Node.
Валидаторов, SDK и HTTP-фреймворков среди импортов рантайма нет.

## Risks / Trade-offs

- **Версия протокола уйдёт вперёд, своя реализация отстанет.** → Список
  поддерживаемых версий — константа пакета; интеграционный прогон клиентом
  SDK ломается на несовместимости, а обновление SDK в `devDependencies`
  становится сигналом.
- **Агент получит доступ к инструменту, которого не должен видеть.** →
  Состав задан декларациями и виден в диффе; `annotations` сообщают агенту
  характер инструмента. Аутентификацию закрывает `auth-layer` (строка 78
  roadmap).
- **Схема не переводится в JSON Schema.** → Падение в `serve` с указанием
  инструмента и слота, до открытия сокета. Обходного пути нет: агенту
  нельзя показать инструмент, вход которого не описан.
- **Сессии накопятся.** → Предельное число и срок бездействия опциями;
  превышение предела — отказ на `initialize`.
- **Своя реализация JSON-RPC содержит дефект, которого нет у SDK.** →
  Интеграционный прогон настоящим клиентом плюс тесты на конверт: неизвестный
  метод, сообщение без `id`, дефектный JSON, неизвестная версия протокола.
- **`GET` отвечает `404` вместо `405`.** → Клиент SDK продолжает работать;
  расхождение названо в README пакета, чтобы его не искали в коде.
- **Две поверхности одной операции не проверены ядром явно.** → Свойство
  держится спекой; если ядро когда-нибудь запретит две реализации, спека
  упадёт первой.

## Migration Plan

Миграции нет: пакет новый, публичных экспортов не меняет. Порядок работ —
в [tasks.md](./tasks.md).

## Open Questions

1. **Пайплайн инструмента и слой приложения.** Политика корня может
   требовать слой на каждом endpoint'е транспорта. У HTTP это решает опция
   `pipeline` у декларации, и у `mcpTool` она тоже есть. Открыт вопрос,
   нужна ли транспорту опция «пайплайн по умолчанию для всех инструментов»
   или хватает пайплайна в каждой декларации. Решить при реализации по тому,
   как это выглядит в примере.
2. **Имя экземпляра транспорта.** `mcp({ name })` даёт второй экземпляр по
   аналогии с `http({ name })`. Открыт вопрос, нужен ли он в V1 или
   экземпляр всегда один.
