# multi-injection — design

## Context

Источник истины — `docs/decisions/ideas.md`, секция «[2026-07-10]
Multi-injection через token families: `Family.all`». Мотивация — в
`proposal.md`. Текущее состояние кода (сверено 2026-07-29, после change
`token-families`):

- **Токены — брендированные строки** (`TokenString<T> = string & { __type }`),
  вся машинерия билдера ключуется `stringifyToken()` (`common.ts`).
- **Семейство** (`providers/token-family.ts`) — функция-значение с внутренним
  `Map<param, token>` и глобальными индексами модуля: `memberIndex`
  (`tokenId → { familyName, param }`), `sentinelIndex` (`.auto`-сентинел →
  семейство), `familyNames`. Параметр `{auto}` зарезервирован и бросает при
  попытке создать им члена.
- **Билдер** (`builder/container.builder.ts`): `build()` = `appendFactoryProviders()`
  → `materializeFamilyMembers()` (фикспоинт с лимитом `MAX_MATERIALIZATION_ROUNDS`)
  → `instantiateAll()` → `buildDependencyGraph()` → `ensureAcyclic()` →
  опционально `checkStrictExports()`. `#providers` — `Map<tokenId, definition>`,
  то есть **порядок вставки провайдеров сохраняется**.
- **Материализация — deps-only**: `collectPendingMembers()` смотрит deps всех
  зарегистрированных провайдеров и берёт только тех членов, у которых **ещё нет
  провайдера**. Следствие, на котором стоит этот change: явно
  зарегистрированный `classProvider(IHealthCheck('db'), DbHealthCheck)` —
  легальный член, рецепт его не перетирает.
- **`strictExports`** проверяет рёбра готового графа: ребро на зависимость,
  принадлежащую модулю M, из потребителя не из M (в том числе **из потребителя
  без модуля**) требует токен в `exports` модуля M.

Ограничения: TS 5.7 strict, ES-декораторы без reflect-metadata, zero magic,
изменения аддитивные для `@nestling/container`.

## Goals / Non-Goals

**Goals:**

- `Family.all` — сентинел-токен семейства, типизированный как
  `TokenString<readonly T[]>`.
- Синтетический узел-агрегат, создаваемый на `build()`: deps = все
  зарегистрированные члены семейства, значение — массив их инстансов.
- Полное равноправие агрегата с прочими узлами: проверка циклов,
  топологические `init()`/`destroy()`, `toJSON()`/`traverse()`, визуализация,
  `strictExports`, атрибуция.
- Закрытие трёх открытых вопросов записи ideas.md: пустое семейство, порядок
  элементов, форма инжекта.
- Демонстрация в `examples.simple-app` и раздел в гайде.

**Non-Goals:** `multi: true`; рантайм-резолюция состава; гарантии порядка
сверх документированного (явные веса — позже, аддитивно); scoped/ленивые
агрегаты и агрегаты-подмножества; формы `[param, T][]`/`Map<param, T>`;
форсирование материализации членов без потребителя (seed/pin — открытый вопрос
`token-families`); `familyOverride` для подмены состава в тестах (change
`testing-package`).

## Decisions

**D1. `Family.all` — сентинел `"<Name>:{all}"`, симметричный `.auto`.**
Свойство `all` семейства — брендированная строка `` `${name}:{all}` ``,
типизированная как `TokenString<readonly T[]>` и зарегистрированная в
отдельном индексе `allSentinelIndex` (`tokenId → family`). Параметр `{all}`
резервируется: `Family('{all}')` бросает так же, как `Family('{auto}')`.

- *Почему не объект-токен и не метод `Family.all()`*: токены в контейнере —
  строки; сентинел-строка не трогает ни `stringifyToken`, ни ключевание графа,
  ни `UnwrapInjectionTokens`. Метод породил бы вопрос «а что, если вызвать
  дважды» и не был бы пригоден в `deps` как значение.
- *Почему отдельный индекс, а не `memberIndex`*: агрегат — не член семейства;
  попадание `{all}` в `memberIndex` заставило бы `collectPendingMembers()`
  считать его материализуемым членом и вызвать на нём рецепт.

**D2. Форма инжекта — `readonly T[]`, массив замораживается.**
`.all: TokenString<readonly T[]>`; инстанс агрегата — `Object.freeze(members)`.
Открытый вопрос ideas.md «`T[]` vs `[param, T][]`/`Map`» решён в пользу `T[]`:
имя/идентичность вклада — забота самого вклада (`check.name`), а пары/`Map`
дублируют то, что уже есть в id узла графа.

- Массив — снапшот сборки, разделяемый всеми потребителями; мутация одним
  потребителем была бы видна остальным. `readonly` + `freeze` превращают это
  из конвенции («не мутируйте») в гарантию, ловимую и компилятором, и
  рантаймом.
- *Отличие от эскиза в ideas.md* (`private checks: HealthCheck[]`): эскиз
  иллюстративный; `docs/design/container.md` («агрегирующий токен
  `TokenString<T[]>`») уточняется этим change'ем до `readonly T[]`.

**D3. Агрегат создаётся deps-driven — только если `.all` упомянут в deps.**
Новая фаза `materializeFamilyAggregates()` сканирует deps всех
зарегистрированных провайдеров, собирает упомянутые `.all`-сентинелы и на
каждый регистрирует обычный провайдер.

- *Почему не создавать агрегаты для всех известных семейств*: значения
  семейств глобальны для процесса (модульные индексы), состав «известных
  семейств» зависел бы от того, какие модули импортированы, — недетерминизм
  ровно того сорта, который change `endpoint-discovery` из графа выкорчёвывает.
  Плюс граф засорялся бы узлами, которых никто не просил.
- Симметрично deps-only материализации членов (`token-families` D4).
  Следствие, фиксируемое спекой: неупомянутый `.all` узла не создаёт,
  `container.get(Family.all)` → `null`.

**D4. Фаза — после фикспоинта материализации членов, до `instantiateAll()`.**
Порядок в `build()`: `appendFactoryProviders()` → `materializeFamilyMembers()`
→ **`materializeFamilyAggregates()`** → `instantiateAll()` → граф → циклы →
`strictExports`.

- Состав известен только после фикспоинта: рецепт может породить провайдер,
  чьи deps втягивают новых членов.
- Второй фикспоинт не нужен: deps агрегата — исключительно токены уже
  зарегистрированных провайдеров, новых материализаций они не порождают.
- Провайдер, зависящий от `.all` **своего** семейства и при этом являющийся
  членом этого семейства, даёт цикл `агрегат → член → агрегат`. Отдельной
  проверки не вводим: цикл ловится существующей детекцией в `instantiateAll()`
  и `ensureAcyclic()` — это и есть «агрегат участвует в проверке циклов
  наравне с прочими узлами».

**D5. Реализация агрегата — обычный `factoryProvider`.**
`{ provide: Family.all, useFactory: (...members) => Object.freeze(members),
deps: [...memberTokens] }`. Никаких новых видов провайдеров, узлов графа и
полей метаданных: `DIGraph`/`DINode`, lifecycle-обход, `toJSON()`, `@nestling/viz`
не меняются.

- *Почему не новый вид узла с флагом `synthetic`*: цель change'а — «агрегат
  неотличим от прочих узлов»; флаг немедленно потребовал бы ветвлений во всех
  потребителях графа. Отличимость и так есть — по id `"<Name>:{all}"`.
- Инстанс-массив хуков жизненного цикла не имеет (`getLifecycleHooks` на
  массиве вернёт пусто), а `@OnInit`/`@OnDestroy` самих вкладов отрабатывают на
  их собственных узлах в топологическом порядке — вклады инициализируются
  раньше агрегата и уничтожаются позже.

**D6. Состав — все члены семейства, у которых есть провайдер на момент фазы.**
Это объединение явных вкладов (`classProvider(IHealthCheck('db'), …)`),
членов, материализованных рецептом из deps, и членов, полученных из
`.auto`. Членство определяется реестром семейства (`memberIndex`), а не
парсингом id, — правило `token-families` D3 действует и здесь.

- Рецепт семейству **не обязателен**: семейство без `familyProvider`, но с
  явными вкладами, агрегируется штатно. Ошибка «нет рецепта» остаётся ровно
  там, где была: член упомянут в deps и провайдера у него нет.
- `.all` **не форсит** материализацию: член, созданный вызовом `Family('x')`,
  но не упомянутый в deps и не имеющий явного провайдера, в массив не попадает.
  Иначе агрегат материализовал бы открытое пространство параметров — то есть
  всё, что кто-либо где-либо вызвал при импорте.

**D7. Порядок элементов — порядок регистрации провайдеров-вкладов.**
Массив собирается обходом `#providers` (insertion-ordered `Map`) с фильтром
«член семейства F». Практически это: провайдеры в порядке регистрации модулей
(`imports` обходятся первыми, вглубь) и внутри модуля — в порядке массива
`providers`; следом — члены, материализованные фикспоинтом, в порядке раундов.
Порядок детерминирован для одного и того же кода и пиннится тестом.

- *Почему не сортировка по параметру*: провоцирует управлять порядком через
  имена (`01-foo`, `02-bar`) — конвенция вместо гарантии; и «алфавитный»
  порядок так же произволен, как любой другой, но при этом ещё и скрывает
  фактическую топологию сборки.
- *Почему не «порядок не определён»*: недетерминированный порядок делает
  нестабильными снапшот-тесты и вывод `explain()`/визуализации.
- Контракт узкий: гарантируется детерминизм и то, что порядок — регистрационный;
  сборка, где порядок вкладов семантически значим (цепочка middleware),
  должна дождаться явных весов, а не полагаться на порядок `imports`.

**D8. Пустое семейство → пустой массив.**
`.all` без единого члена даёт узел с нулём deps и значением `[]` (открытый
вопрос ideas.md решён).

- «Не выбрал фичу → её вкладов нет» — штатное состояние модульного монолита и
  будущей матрицы select-топологий; ошибка на пустоте ломала бы ровно тот
  сценарий, ради которого агрегат и делается.
- *Риск «опечатался в семействе / забыл импортировать модуль → тихий `[]`»*
  принимается: пустота диагностируется на графе (узел виден, deps пусты).
  Opt-in строгость (минимальная мощность семейства) добавляется аддитивно,
  когда появится кейс.

**D9. Токен `.all` и параметр `{all}` зарезервированы.**
Регистрация собственного провайдера с `provide: Family.all` (напрямую, через
модуль или как результат рецепта) SHALL падать при регистрации с внятной
ошибкой; `Family('{all}')` бросает как зарезервированный параметр.

- *Почему не «пользовательский провайдер побеждает»*: два источника истины для
  одного узла — состав то из графа, то из руки; guarantee over convention.
- Легальный сценарий подмены состава в тестах закрывает `familyOverride`
  тестового корня (change `testing-package`), а не молчаливый перехват токена.

**D10. `.all` допустим в deps любого определения.**
В отличие от `.auto`, агрегату не нужен «потребитель»: `.all` легален в deps
классового `@Injectable`, `factoryProvider`, `classProvider` и провайдеров,
порождённых рецептом. Существующая проверка `assertNoAutoSentinels` остаётся
относящейся только к `.auto`.

**D11. Атрибуция агрегата — `metadata.module === undefined`.**
Синтетический узел не принадлежит ни одному модулю: потребителей `.all` может
быть несколько в разных модулях, а узел один.

- Следствие для `strictExports` (без единой правки в самой проверке): агрегат —
  безмодульный потребитель, поэтому его ребро на вклад модуля M требует
  `exports: [Family]` (или членский токен) у M. Это и есть «явный контракт
  „модуль контрибьютит в семейство"» из ideas.md. Ребро
  `потребитель → агрегат` свободно (у зависимости нет модуля).
- *Почему не приписывать агрегат модулю потребителя*: неоднозначно при
  нескольких потребителях и превратило бы `strictExports` в функцию от того,
  кто первым запросил `.all`.

## Risks / Trade-offs

- [Пустой массив маскирует опечатку в семействе или незарегистрированный
  модуль-вкладчик] → узел агрегата присутствует в графе и виден в
  визуализации/`toJSON()` с пустыми deps; правило документируется в гайде;
  opt-in строгость откладывается до реального кейса (D8).
- [Порядок зависит от порядка `imports` — рефакторинг импортов молча меняет
  порядок массива] → контракт документирован как «порядок регистрации» и
  запиннен тестом; для семантически значимого порядка явно предписаны
  будущие веса, а не `.all` (D7).
- [Разделяемый массив: мутация одним потребителем видна всем] →
  `readonly T[]` + `Object.freeze` (D2); тип ловит мутацию на компиляции,
  freeze — в рантайме.
- [Цикл `агрегат → член → агрегат` даёт сообщение об ошибке в терминах
  синтетического токена `"HealthCheck:{all}"`, который пользователь не писал]
  → id читаем и однозначно указывает на семейство; тест на цикл фиксирует
  наличие семейства в тексте ошибки.
- [`strictExports` начинает требовать `exports` у всех модулей-вкладчиков —
  для кого-то это новые нарушения после включения `.all`] → флаг opt-in,
  требование осмысленное («контрибьютить в чужой агрегат — публичный акт») и
  документируется в разделе гайда про `.all`.
- [Реестры семейств и сентинелов — глобальное для процесса состояние] →
  как и в `token-families`: индексы только отображают id → семейство, состав
  сборки определяется зарегистрированными провайдерами (D3, D6).
- [Провайдер, порождённый рецептом уже после фазы агрегатов, не попал бы в
  массив] → такого не бывает: агрегаты создаются строго после фикспоинта
  материализации, а deps агрегата новых членов не порождают (D4); инвариант
  проверяется тестом «рецепт-порождённый член входит в `.all`».

## Migration Plan

Изменение аддитивное, breaking-изменений нет: новое свойство `TokenFamily.all`,
новая фаза `build()`, новые ошибки на ранее невозможных формах записи
(`provide: Family.all`, `Family('{all}')`). Существующие контейнеры собираются
и ведут себя как раньше. Шаги:

1. `.all`-сентинел и индекс в `providers/token-family.ts` + юнит-тесты
   (тип, id, резервирование параметра).
2. Фаза `materializeFamilyAggregates()` в билдере + запрет регистрации на
   `.all`-токен; рантайм-тесты состава, порядка, пустоты, дедупликации,
   циклов, lifecycle, `strictExports`.
3. Демонстрация в `examples.simple-app` (вклады из разных модулей + агрегатор).
4. Документация: README пакета (ru/en), раздел гайда `di-token-families.md`
   с пересверкой даты, уточнение `docs/design/container.md`, пометки «РЕШЕНО»
   на трёх открытых вопросах записи ideas.md.
5. Откат — revert коммитов; пользовательских миграций нет.

## Open Questions

- **Явные веса/приоритеты вкладов** (`order`, `before`/`after`): отложено до
  кейса, где порядок семантически значим; добавляется аддитивно поверх D7, не
  меняя формы `.all`.
- **Opt-in строгость на пустое семейство** (минимальная мощность): отложено
  (D8); форма — опция семейства или policy-check на графе (change
  `policy-check`), решается там, где появится потребность.
- **Подмена состава агрегата в тестах**: `familyOverride` — change
  `testing-package` (roadmap #18); здесь сознательно запрещаем перехват токена
  (D9), чтобы у подмены был ровно один легальный путь.
