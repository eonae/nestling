## Context

Change #77 `observability` дал ядру две половины наблюдаемости и остановился
ровно на границе экспорта.

Метрики. Интерфейс `Metrics` с двумя пишущими методами, корень `RootMetrics$`
опцией `makeApp({ metrics })`, семейство `Metrics$(scope)`, четыре метрики
ядра на endpoint и на вызов порта. Инструментовка включается сравнением корня
с `noopMetrics` по ссылке. Формата экспорта ядро не знает: числа уходят через
стороннюю реализацию корня.

Трассы. Well-known переменная `Trace` с полями `traceId`, `spanId`,
`parentSpanId` и `sampled`, pre-шаг `withTracing()`, формат W3C по HTTP и полем
конверта по шине, поле `traceId` в каждой записи логгера. Читалка
`traceparent()` для кода вне пакета.

Что осталось незакрытым:

1. Сторонняя реализация корня написана в примерах. Файлы
   `examples/microservice/src/metrics.ts` и
   `examples/modular-app/src/metrics.ts` совпадают до символа: сто двадцать
   строк формата экспозиции Prometheus. Комментарий в шапке объясняет, что так
   проверяется публичная граница ядра. Граница проверена, файл остался.
2. Трасса никуда не экспортируется. Идентификаторы едут между процессами,
   но интервал участка не записывает никто.

Ограничения, в которых делается change:

- Ядро не трогается. Строка 85 roadmap говорит: «ядро даёт интерфейс и
  переменную, формата экспорта не знает».
- Приложение, которое ставит сателлит, не обязано ставить его целиком:
  метрики без трасс и трассы без метрик — рабочие сочетания.
- Приложение без сателлита продолжает собираться: узел `RootMetrics$` есть в
  графе всегда.

## Goals / Non-Goals

**Goals:**

- Один пакет закрывает и метрики, и трассы: `@nestlingjs/otel`.
- Экспортёра телеметрии в коде примера не остаётся.
- Участок трассы уходит экспортёру с теми же идентификаторами, которые ядро
  везёт по сети, — иначе дерево не сходится.
- Отсутствие экспорта на endpoint'е ловится на сборке, а не в проде.
- Сервис может дописать атрибут на текущем участке, не зная про OTel SDK.

**Non-Goals:**

- Новый шов в ядре. Разобран ниже, решение D1.
- Участок на вызов порта. Решение D5.
- Экспорт логов по OTLP: логгер пишет в `stderr`, сбор строк — дело
  развёртывания.
- Автоматическая инструментовка `pg`, `fetch` и прочих библиотек. Пакеты
  `@opentelemetry/instrumentation-*` приложение подключает само.
- Свой HTTP-сервер под экспозицию. Endpoint живёт на сокете приложения.

## Decisions

### D1. Участок пишет слой сателлита, гарантию даёт политика

Участок — интервал: у него есть начало и конец. Метрика — одно значение в один
момент, и потому корня метрик под неё хватило. Под интервал шва в ядре нет.

**Решение.** Сателлит отдаёт слой пайплайна. Pre-шаг открывает участок,
`.finally`-шаг закрывает его исходом. Что слой есть у каждого endpoint'а,
утверждает политика сборки — `everyEndpoint(…).hasVar(Span)`.

```typescript
// пакет
export const Span = contextVar<OtelSpan>()('span');

// сателлит: слой требует trace в контексте и добавляет span
const spans = makePipeline<{ trace: TraceContext }>()
  .pre(Span.provide((ctx) => open(ctx.input.trace)))
  .finally((outcome, res, ctx) => close(ctx.input.span, outcome, res, ctx));
```

```typescript
// приложение
export const observabilityLayer = compose(
  makePipeline().pre(withRequestId()).pre(withTracing()).finally(AuditOutcome),
  telemetry.spans,
);

makeApp({
  policies: [everyEndpoint().hasVar(Span, 'span')],
});
```

**Почему не шов ядра `makeApp({ spans })`.** Вариант рассматривался всерьёз:
рантайм пайплайна в `settle` уже знает шаблон маршрута, исход, длительность и
значение `Trace`, и второй вызов рядом с записью метрики покрыл бы все
endpoint'ы разом. Отвергнут по двум причинам. Первая: гарантию даёт политика,
и она сильнее умолчания — забытый слой падает на фазе BUILD с именем модуля и
паттерном, а не молча не экспортируется. Вторая: третий интерфейс
наблюдаемости в ядре стоит дороже, чем строка в `policies:`, и формат участка
пришлось бы фиксировать в спеке ядра — то самое знание об экспорте, от
которого ядро отгорожено.

**Почему довод #77 против `.finally`-шага здесь не работает.** В #77
отказались писать метрику шагом, и три довода были такие: слой в каждом
пайплайне, незамеченный endpoint, отложенная фаза потока. Первые два снимает
политика. Третий снимает сам рантайм: `.finally`-шаг у потокового ответа
вызывается после закрытия итератора (`runFinals` откладывается вместе с
`settle`), так что длительность участка покрывает доставку целиком — ровно как
у метрики. Воспроизводить фазу заново не приходится.

### D2. Идентификаторы участка принадлежат ядру

`Tracer.startSpan` из OTel SDK минтит `spanId` своим `IdGenerator`. Ядро уже
сминтило свой в `withTracing()` и увезло его соседу заголовком `traceparent`.
Два разных идентификатора на один участок — разорванное дерево: участок соседа
ссылается на родителя, которого в экспорте нет.

**Решение.** Сателлит не зовёт `startSpan`. Он собирает значение формы
`ReadableSpan` из `TraceContext` и отдаёт его напрямую `SpanExporter`:

| Поле участка | Откуда |
| --- | --- |
| `spanContext().traceId`, `spanId` | `Trace` |
| `parentSpanContext.spanId` | `Trace.parentSpanId` |
| `spanContext().traceFlags` | `Trace.sampled` |
| `name` | `ctx.endpoint.pattern` |
| `startTime`, `endTime` | часы pre-шага и `.finally`-шага |
| `status` | исход шага |
| `attributes` | транспорт, паттерн, исход и то, что дописал сервис |

`ReadableSpan` — интерфейс, а не класс: значение собирается объектным
литералом. Это та же форма, которую `SpanExporter` получает от SDK, поэтому
любой готовый экспортёр (OTLP, консольный, свой) работает без переходника.

**Альтернатива:** свой `IdGenerator` в `BasicTracerProvider`. Отвергнута:
генератор вызывается без контекста запроса и не знает, какой идентификатор
нужно вернуть.

### D3. Исход шага в статус участка

`.finally`-шаг получает исход одного из четырёх значений. Отображение:

| Исход | Статус участка | Почему |
| --- | --- | --- |
| `completed` | `OK` | запрос обработан |
| `failed` | `ERROR` | отказ объявленный или нет — для наблюдателя провал |
| `aborted` | `ERROR` | работу прервали, результата нет |
| `disconnected` | `UNSET` | клиент ушёл; сервис ни при чём |

`disconnected` не красится в `ERROR` намеренно: иначе процент ошибок в дашборде
растёт от поведения клиентов, и сигнал теряется. Исход остаётся атрибутом
участка, поэтому отфильтровать его можно.

### D4. Переменная `Span` — и обогащение, и политика

Участок кладётся в контекст переменной `Span`, а не в замыкание слоя. Это даёт
две вещи одним значением.

Сервис дописывает атрибут, не зная про SDK:

```typescript
@Component([Ctx(Span)])
export class UsersService {
  constructor(private readonly span: CtxReader<OtelSpan>) {}

  find(id: string) {
    this.span.get()?.setAttribute('user.id', id);
  }
}
```

Политика проверяет присутствие по переменной: `hasVar` засчитывает объявление
через `Var.provide`, и переживает перекомпозицию слоя — в отличие от
`hasLayer`, который сравнивает значение по ссылке.

Поверхность значения — два метода, `setAttribute` и `addEvent`. `end` наружу
не выходит: закрывает участок слой, и второй закрыватель означал бы два
участка с одним идентификатором.

### D5. Вызов порта своего участка не получает

Слой живёт в пайплайне, а у вызова порта пайплайна нет. Дерево от этого не
рвётся: вызыватель везёт `Trace` в конверте, получатель продолжает трассу
своим `withTracing()`, и участок его endpoint'а встаёт ребёнком участка
вызывателя. Пропадает только промежуточное звено — время, проведённое в сети
и в очереди брокера. Его показывает пара метрик `nestling.port.duration` и
`nestling.request.duration`: разность и есть накладные расходы доставки.

Условие возврата: когда разность метрик перестанет отвечать на вопрос «где
запрос провёл время» — например, понадобится разложить задержку по конкретным
вызовам внутри одного обработчика.

### D6. Один вход, три части

`otel(options)` возвращает значение с тремя полями.

```typescript
export interface Otel {
  /** Корень метрик: значение опции `makeApp({ metrics })` */
  readonly metrics: Metrics;

  /** Слой участков: композируется в слой наблюдаемости приложения */
  readonly spans: Pipeline<{ trace: TraceContext }, { span: OtelSpan }>;

  /** Плагин: endpoint экспозиции и ресурс сброса на остановке */
  readonly plugin: Plugin;
}
```

Три отдельные фабрики отвергнуты: корень метрик, endpoint экспозиции и ресурс
сброса обязаны смотреть в один `MeterProvider`. Отдельные фабрики заставили бы
приложение сшивать их руками — ровно то, что делает сейчас пример, передавая
`exporter` и в `metrics:`, и в `metricsPlugin(exporter)`.

Опции:

```typescript
export interface OtelOptions {
  /** Имя сервиса: атрибут ресурса `service.name` */
  readonly service: string;

  /** Версия сервиса: атрибут ресурса `service.version` */
  readonly version?: string;

  /** Адрес экспозиции; умолчание — `/metrics` */
  readonly path?: string;

  /** Куда уходят участки; без него слой не экспортирует ничего */
  readonly traces?: SpanExporter;

  /** Читалки метрик сверх экспозиции — например, OTLP-пуш */
  readonly readers?: readonly MetricReader[];
}
```

Без `traces` слой работает и политику удовлетворяет, но участки никуда не
уходят — как пустой корень метрик у ядра. Так приложение включает экспорт
конфигурацией развёртывания, не трогая композицию.

Своих обёрток над экспортёрами пакет не заводит: `OTLPTraceExporter`
импортируется приложением напрямую. Обёртка добавила бы третье имя к двум
существующим и устаревала бы вместе с опциями SDK.

### D7. Экспозиция без своего сервера

`PrometheusExporter` из `@opentelemetry/exporter-prometheus` по умолчанию
поднимает собственный HTTP-сервер. Второй сокет в приложении не нужен:
`detached`-endpoint на сокете приложения уже описан в примере и в главе 22.

**Решение.** `new PrometheusExporter({ preventServerStart: true })` как
`MetricReader`, `collect()` на запрос, `PrometheusSerializer` в текст. Endpoint
объявлен `output: 'text'` и `detached: 'metrics scrape: not part of the
application API'` — метрики снимает сборщик, а не клиент API, и в документ
OpenAPI строка не идёт.

### D8. Сброс на остановке — ресурс плагина

`PeriodicExportingMetricReader` и пакетная отправка участков копят записи в
памяти. Процесс, который выключили между отправками, теряет последний
интервал.

**Решение.** Плагин объявляет `@Resource`, чей `release` вызывает
`forceFlush()` и `shutdown()` у провайдера метрик и у экспортёра участков.
Ресурс — не отдельная забота приложения: он приходит вместе с плагином, и
порядок остановки держит ядро.

### D9. Зависимости — настоящий OTel SDK

Решение пользователя на propose. Пакет зависит от `@opentelemetry/api`,
`sdk-metrics`, `exporter-prometheus`, `sdk-trace-base`, `resources` и
`semantic-conventions`.

Прецедент логгера (запись [2026-09-13], пункты 24–27: pino отменён ценой
двух мегабайт против трёхсот строк своего) на сателлит не переносится. Там
спор шёл про умолчание ядра, которое платят все. Здесь пакет ставит тот, кому
нужен OpenTelemetry, и имя пакета обещает именно SDK: корзины гистограмм,
модель ресурса и совместимость с чужими коллекторами не воспроизводятся своими
тремястами строками.

Peer-зависимости отвергнуты: корень метрик создаётся синхронно на фазе 0, и
необязательная зависимость там не работает — тот же довод, что закрыл
опциональный peer на pino.

### D10. Главы гайда: 22 переписывается, 23 заводится

Глава 22 «Считать запросы и вызовы между процессами» остаётся про метрики;
раздел «Адаптер и endpoint `/metrics`» превращается из «адаптер пишет
приложение» в «адаптер ставится пакетом». Глава 23 «Увидеть, где запрос провёл
время» — новая: слой, политика, `Ctx(Span)`, просмотр дерева в Jaeger.

Одна глава — одна задача. Смешивать счёт и трассу в главе 22 значило бы
удвоить её объём и сломать это правило.

## Risks / Trade-offs

- **Форма `ReadableSpan` — внутренний контракт SDK, а не публичный протокол**
  → пакет строит её в одном месте, и это место закрыто тестом против
  настоящего `SpanExporter`: он получает участок и проверяет поля. Смена формы
  в мажоре SDK падает тестом, а не в проде.
- **Слой на каждом endpoint'е забывается** → политика `hasVar(Span)` в обоих
  примерах и в главе 23. Осознанный отказ — `detached`, как у остальных
  политик.
- **Шесть пакетов `@opentelemetry/*` в зависимостях** → тест границы пакета
  перечисляет фактические импорты, и лишняя зависимость в манифесте падает
  инвариантом `deps-sync`. Приложение без сателлита не платит ничего.
- **`Ctx(Span)` возвращает `undefined` вне запроса и на endpoint'е без слоя**
  → тип читалки это называет, вызов пишется через `?.`. Сделать значение
  обязательным нельзя: пайплайна у `@OnStart` нет.
- **Два процесса пишут одно имя метрики с разным набором атрибутов** → имена
  и атрибуты ядра фиксированы спекой `kernel-metrics`, а свои записи
  приложение делает через токен семейства, который добавляет `scope`.

## Migration Plan

Обратной совместимости в проекте нет, миграция — это правка двух примеров в
том же change'е.

1. Пакет заводится и проходит `yarn verify` со своими спеками.
2. `examples/microservice`: `src/metrics.ts` удаляется целиком, `exporter`
   в `src/app.ts` заменяется на `otel({ service: 'microservice' })`, слой
   `observability` композируется с `telemetry.spans`, в `policies:`
   добавляется `hasVar(Span)`.
3. `examples/modular-app`: то же плюс `src/metrics.spec.ts` переписывается —
   проверяет текст экспозиции и участок, полученный подставным
   `SpanExporter`.
4. Главы 22 и 23 и их английские пары, README пакета парой, таблица пакетов
   в `docs/README.md`, справочник `docs/compatibility.md` парой.

Откат — снятие ветки: в `main` change попадает одним merge-коммитом.

## Open Questions

1. **Чем доказывать совместимость экспорта.** Кандидаты: подставной
   `SpanExporter` в спеке пакета (быстро, но проверяет нашу же форму) или
   контейнер с коллектором OTel в интеграционном прогоне (доказывает, но
   стоит времени сборки). Решить на apply; по умолчанию — первое, второе
   строкой в `ideas.md`, если первого окажется мало.
2. **OTLP-пуш метрик в этом change или позже.** Поле `readers` его допускает,
   но ни один пример им не пользуется, и умолчанием остаётся экспозиция.
   Оставлять ли поле без потребителя — решить на apply.
3. **Имя `service` против `serviceName`.** Короткое привычное слово против
   точного имени атрибута `service.name`. Склоняюсь к `service`: пара
   `service` и `version` читается вместе.
4. **Метрическая половина под пересмотром.** Сессия
   `change/rewrite-metrics` ведёт разбор декларативных метрик: каталог
   метрик известен на сборке, ядро держит `MetricsStore$`, опция
   `makeApp({ metrics })` исчезает, формат Prometheus переезжает в отдельный
   пакет. Если направление подтвердится, решения D6, D7 и D9
   переписываются: сателлит подписывается на store через `tap(sink)`, а
   экспозиция перестаёт быть его частью. Решения D1–D5 и спека
   `otel-span-export` от этого не зависят.
