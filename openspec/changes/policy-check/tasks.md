# tasks — policy-check: инварианты на собранном графе

Порядок работ идёт снизу вверх (провенанс пайплайна → `detached` → словарь
политик в ядре → врезка в `@nestling/app` → транспортные словари → тестовый
корень → ESLint-плагин → витрина → доки): каждая группа оставляет репозиторий
собираемым, откат — отбрасыванием верхних ступеней.

## 1. Провенанс композиции в `@nestling/pipeline`

- [x] 1.1 Поле `sources: readonly PipelineImpl[]` в `PipelineImpl`
      (`packages/nestling.pipeline/src/core/pipeline.ts`) с JSDoc «ссылки на
      значения, из которых произошёл пайплайн; единственный источник истины
      для идентичности слоя»
- [x] 1.2 Запись провенанса: `emptyLayer()` → `[]`, `withOwnLayer` → `[this]`,
      `compose(...)` → сами аргументы без разворачивания, `bind(resolve)` →
      `[this]`
- [x] 1.3 Внутренний предикат «пайплайн произошёл от значения» — обход DAG
      провенанса в ширину со ссылочным равенством и защитой от повторного
      посещения (значение легально встречается в нескольких ветках)
- [x] 1.4 Рантайм-тесты провенанса: `compose(base, authed)` содержит оба;
      вложенная композиция транзитивна; `authed.pre(x)` содержит `authed`, а
      `authed` при этом не изменился; результат `bind()` содержит несвязанный
      оригинал; чужой слой с тем же составом юнитов **не** содержится
- [x] 1.5 Рантайм-тест неизменности исполнения: порядок pre-трактов, ответных
      фаз и `finally` на композиции из трёх слоёв совпадает с эталоном до
      введения провенанса

## 3. Словарь политик в ядре

- [x] 3.1 Новый модуль `packages/nestling.pipeline/src/metadata/policy.ts`:
      типы `PolicySubject`, `PolicyViolation`, `Policy`
      (`describe()` + `check(subjects)`), реэкспорт из `metadata/index.ts`
- [x] 3.2 `everyEndpoint({ transport?, pattern? })` — билдер политик: фильтр
      по токену транспорта (ссылочное равенство) и по `RegExp` на
      `endpoint.pattern`; пустой фильтр = все ручки; конъюнкция при обоих
      полях
- [x] 3.3 `.hasLayer(layer, label?)` — предикат поверх обхода провенанса
      (1.3): ручка без `pipeline` нарушает; `describe()` и `detail`
      нарушения используют `label`, а без него — «the required layer»
- [x] 3.4 Исключение detached-ручек: билдер отсеивает субъекты с непустым
      `detached` **до** применения предиката (opt-out тотален)
- [x] 3.5 Рантайм-тесты словаря: фильтр по транспорту не трогает чужой
      транспорт; фильтр по паттерну; нарушение называет паттерн, транспорт и
      модуль; ручка без пайплайна нарушает; detached-ручка исключена;
      приложение без ручек проходит любую политику

## 4. Прогон политик в `@nestling/app`

- [x] 4.1 `policies?: readonly Policy[]` в `AssemblySpec` и `AssemblyPlan`
      (`packages/nestling.app/src/plan.ts`), нормализация в `makePlan`
- [x] 4.2 `#assertPolicies(discovery)` в `App`, вызываемый в `#assemble()`
      **после** `#assertFormsSupported`: субъекты собираются из
      `discovery.endpoints` (`{ endpoint, moduleName }` уже структурно
      совпадает с `PolicySubject`)
- [x] 4.3 Агрегированная диагностика: прогоняются все политики, нарушения
      группируются по политике, сообщение называет число нарушений, описание
      политики, паттерн/транспорт/модуль каждой ручки и обе починки
      (композировать слой либо `detached: '<причина>'`)
- [x] 4.4 `detached?: string` в `CheckedEndpoint`, заполнение в `check()`
- [x] 4.5 Печать списка detached-ручек в `#announce()` — по строке на ручку с
      паттерном, транспортом и причиной; при пустом списке не печатается
      ничего
- [x] 4.6 Рантайм-тесты `run()`/`check()`: нарушение падает до `@OnInit`
      (счётчик хука равен нулю) и до открытия сокета; ошибка перечисляет все
      нарушения обеих политик; структурная ошибка (незарегистрированный
      транспорт) называется раньше нарушения политики; ручка невыбранной
      фичи не проверяется; отчёт `check()` несёт `detached`; при пустом
      `policies` поведение прежнее
