# Модель ошибок: `Fail` — значение, закрытый контракт

> «Модель ошибок: Fail — значение, code-идентичность, `defineFail`, ошибки
> в контракте» [2026-07-10], «Типизированные клиенты из контрактов»
> [2026-07-13] (ре-материализация). Статус реализации —
> [roadmap](../decisions/roadmap.md).

## 1. `Fail` — значение; `throw` — механизм, не семантика

Rust-рамка (`Result` + `panic!`) на JS: ожидаемый отказ домена (`Fail`)
ходит **как значение** — хоть возвратом, хоть броском; брошенный не-`Fail` —
«паника» (`INTERNAL_ERROR`, детали скрыты). `throw` — транспортировка
значения (в JS нет `?`-оператора), а не семантика.

- `Output<T, E> = Promise<Ok<T> | E | T>` (+ `OutputSync`); голое значение
  оборачивается в `Ok`. `E` по умолчанию **пусто** (`never`): ручка без
  `errors:` вернуть отказ не может — иначе типы разрешали бы то, что
  граница гарантированно превратит в `UnknownError`.
- Дискриминант `isFail: true as const` / `false` — сериализуемый,
  в отличие от `instanceof`. Оборачивание отказа в успех закрыто типом:
  `new Ok(fail)` — ошибка компиляции.
- Рантайм: возвращённый `Fail` попадает на error-track **до** `.ok`-юнитов —
  инвариант «`.ok` видит только успех» держится для обоих путей.
- `Fail extends Error`: стек для throw-пути бесплатно, return-пути не мешает.
- Правило для человека: **свой отказ — `throw` (ранний выход из глубины),
  чужой — `return` (проброс отказа порта)**.

## 2. Словарь статусов, `code`, `cause`

- `ErrorStatus` — семантический, транспортно-нейтральный: `BAD_REQUEST`,
  `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `TIMEOUT`,
  `TOO_MANY_REQUESTS`, `INTERNAL_ERROR`, …; маппинг на провод (HTTP-статус,
  код шины) — забота транспорта.
- `code?: string` — стабильный машинный код («что именно случилось»);
  статус отвечает «как отвечать транспорту» — разные оси.
- `cause?: unknown` — обёртывание исходной ошибки (ES2022).
- На проводе (`ErrorDetails`): `status`, `code`, `message`, `details`,
  `requestId` (кладётся `.catch`/`.finally`-юнитами из контекста —
  корреляция с логами без кода пользователя).

## 3. Доменные ошибки: `defineFail`, идентичность по `code`

```typescript
export const OrderNotFound = defineFail('ORDER_NOT_FOUND', {
  status: 'NOT_FOUND',
  details: z.object({ orderId: z.string() }),   // schema-first — и для details
  message: (d) => `Order ${d.orderId} not found`,
});

throw OrderNotFound({ orderId: '42' });
throw OrderNotFound({ orderId: '42' }, { cause: dbError });
// в .catch-юните:
if (OrderNotFound.is(res)) { /* ... */ }        // матчинг по code
```

**Единственный источник данных отказа — `details`.** Конструктор принимает
их (тип выведен из схемы, без аннотаций) и валидирует схемой на месте;
`message` — либо строка, либо функция **от этих деталей**. Произвольной
арности у сообщения нет: связать её со схемой типами нечем, и данные
пришлось бы дублировать в вызове. Без схемы конструктор вызывается без
аргументов — `EmailTaken()`. Второй аргумент — опции (`cause`).

Определение — значение со свойствами `code`, `status`, `schema` и
предикатом `is`; само оно вызываемо. Регистрации нет: на приложение
определение влияет только через `errors:` декларации.

Идентичность — по `code`, не по `instanceof`: `Fail`, прилетевший от
remote-порта или в клиент, — десериализованные данные; класс на них мёртв,
`code` выживает на проводе. Поэтому `is` распознаёт код у обоих носителей:
у значения-отказа (в том числе разобранного из JSON) и у контекста
ответа-ошибки, который видит `.catch`-юнит. Порт-клиент и `makeClient`
**ре-гидрируют** remote-отказ в настоящий `Fail` на своей стороне
([contracts.md](./contracts.md)).

## 4. Ошибки — часть контракта: `E ∪ UnknownError`

`errors: [EmailTaken, OrderLimitReached]` в декларации endpoint'а/контракта —
типизированный канал отказов. Гарантия двухуровневая:

- **Компилятор** — всё, что течёт значениями. `defineFail` брендирует тип
  (`Fail<'EMAIL_TAKEN'>`); `Output<T, E>` сверяет `return` с декларацией —
  в том числе проброс отказа порта: чужой `Fail` не пролезает в ответ, пока
  не задекларирован. Ранний выход — типизированный бросатель
  **`meta.fail(e): never`** (второй зарезервированный ключ meta после
  `signal`): принимает только задекларированные отказы, тип рождается из
  декларации.
- **Рантайм на границе пайплайна** — остальное (прямой `throw`, отказы из
  глубины, обходы типов): всё, что доехало до границы незадекларированным,
  **нормализуется в `UnknownError`** (встроенный `defineFail('UNKNOWN')`,
  статус `INTERNAL_ERROR`). Ответ **без кода** — в том числе порождённый
  анонимным `Fail.notFound(...)` — незадекларирован по определению.
  Оригинал целиком уходит диагностическому хуку `onUnknownFail` (дефолт —
  `console.error`; логгера в ядре нет по принципу минимума зависимостей),
  клиенту — generic-тело. Никакого warn-and-pass.

Множество отказов доезжает до рантайма **значением декларации**: `errors:`
→ `EndpointMeta` → контекст запроса. Глобального реестра нет, поэтому
пайплайн, исполненный без декларации, видит пустое множество.

Итог: ответ endpoint'а — **закрытое множество** `E ∪ UnknownError`;
`UnknownError` неявно входит в контракт каждого endpoint'а (default-ответ
в OpenAPI). Встроенные коды фреймворка входят в множество тем же способом:
сегодня это `VALIDATION_FAILED` у `validate()`-юнита (иначе страж
превращал бы штатный 400 валидации в 500), позже — `DeadlineExceededError`
у портов. Набор закрыт и растёт только вместе с ядром: публичного способа
пометить свой код встроенным нет.

Страж стоит **после всех `.catch`-юнитов**: `.catch` — легальное место,
где недекларированный отказ превращается в контрактный. Осознанный
трейд-офф: забытая декларация = `UnknownError` (500) вместо «случайно
работавшего» 404 — громко и сразу, зато клиент не успевает опереться на
implicit contract.

Почему бросатель живёт на meta, а не свободной функцией поверх ALS: типы
лексичны и статичны, ALS динамичен и стёрт в рантайме — тип не может
зависеть от того, «в каком запросе меня вызвали». Глубокие сервисы бросают
свои `defineFail`-ошибки, не зная контракта вызвавшего endpoint'а; сверка
с контрактом — забота границы.
