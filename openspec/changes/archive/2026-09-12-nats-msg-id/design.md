# Дизайн: `Nats-Msg-Id` и окно дедупликации потока

## Context

Долговечная публикация идёт через JetStream:

```typescript
if (options.durable) {
  await this.#ensureStream(connection, address);
  await connection.jetstream().publish(address, data, { headers });

  return;
}
```

`#ensureStream` создаёт поток `{ name, subjects }`, если его нет, и
принимает существующий как есть. Конверт кладёт в заголовки `encodeEnvelope`:
`Nl-Subject`, `Nl-Timeout-Ms`, `Nl-Idempotency-Key`, `Nl-Ctx`.

Relay outbox'а публикует запись с ключом, равным её идентификатору:

```typescript
await this.#options.bus.publish(record.subject, record.payload, {
  idempotencyKey: record.id,
  durable: record.durable,
  ...
});
```

Повтор возникает, когда брокер сохранил сообщение, а подтверждение не
дошло. `publish` бросает, relay отмечает запись `retry` с backoff и через
паузу публикует её снова — с тем же ключом. Сегодня в потоке оказываются
две копии.

Полный цикл повторов relay считается по секции `outbox`: `backoffMs` 500,
удвоение, потолок `backoffMaxMs` 30 000, `maxAttempts` 10. Сумма пауз —
около 122 секунд.

Ограничения, в которых работает решение:

- Транспорт не переписывает чужие потоки — правило спеки `durable-delivery`
  и текст ошибки о конфликте состава subject'ов.
- Клиент брокера изолирован коннектором: всё, что транспорт просит у
  брокера, перечислено в `NatsLike` и его частях.
- Тесты пакета и приложений идут против двойника без сети.

## Goals / Non-Goals

**Goals:**

- Повтор публикации relay в пределах окна не доходит до подписчика.
- Величина окна видна и настраивается; умолчание перекрывает цикл повторов
  relay.
- Поток, созданный не транспортом, остаётся за эксплуатацией, но расхождение
  видно в логе.
- Двойник ведёт себя как брокер: дедупликация проверяется тестами без сети.

**Non-Goals:**

- Замена `@nestlingjs/inbox`. Окно брокера сужает поток повторов, гарантию
  «ровно один раз» даёт отметка приёма в транзакции приложения.
- Дедупликация core-публикаций и req-reply.
- Возврат осиротевших записей outbox'а из состояния `claimed`.

## Decisions

### 1. Заголовок ставится только у долговечной публикации

`Nats-Msg-Id` попадает в конверт, когда публикация идёт через JetStream и в
конверте есть ключ идемпотентности. Core NATS заголовок игнорирует.

Альтернатива — ставить заголовок всегда, рядом с `Nl-Idempotency-Key`,
одной строкой в `encodeEnvelope`. Отвергнута: заголовок с именем брокера в
core-сообщении читается как обещание дедупликации, которого core NATS не
выполняет. Ложное обещание дороже одной ветки в коде.

Следствие для формы: `encodeEnvelope` получает признак долговечности, а не
вторую функцию. Признак уже есть в опциях публикации, и конверт остаётся
одним местом, где заголовки называются по именам.

### 2. Окно — опция фабрики `dedupeWindowMs`, а не поле конфиг-секции

Секция `nats` держит то, что меняется между окружениями: адреса, потолок
ожидания, префикс subject'ов. Окно дедупликации — параметр определения,
которое транспорт создаёт, как и `maxDeliver` — параметр durable-потребителя.
`maxDeliver` живёт опцией фабрики, и окно встаёт рядом с ним.

Альтернатива — `NATS_DEDUPE_WINDOW` в секции. Отвергнута по двум причинам.
Первая: значение попадает в определение потока только при его создании, а
создаёт поток тот процесс, который опубликовал первым; читать такое из
окружения каждой реплики — приглашение к расхождению. Вторая: величина
выводится из секции `outbox` того же приложения, то есть принадлежит
сборке, а не окружению.

### 3. Умолчание — 5 минут

Окно обязано перекрывать цикл повторов relay: пока запись не отмечена
опубликованной, relay возвращается к ней снова. Цикл занимает около
122 секунд, умолчание JetStream — 2 минуты, то есть впритык. Пять минут
дают запас в два с половиной раза и остаются дешёвыми: брокер держит в
памяти идентификаторы сообщений за окно.

Значение `0` выключает дедупликацию: поле в определении потока не задаётся,
сверка существующего потока не выполняется. Заголовок при этом ставится —
он безвреден и полезен в `nats sub`.

### 4. Существующий поток: предупреждение, не отказ

Поток, покрывающий subject, принимается как есть — это действующее правило.
К нему добавляется сверка: окно уже поднято, и если у потока оно меньше
настроенного, транспорт пишет `warn` с именем потока и обоими числами.

Альтернатива — ронять сборку, как на конфликте состава subject'ов.
Отвергнута: конфликт subject'ов означает, что доставка не работает вовсе, а
узкое окно означает, что часть повторов дойдёт до подписчика — то есть
ровно сегодняшнее поведение. Слой приёма его и закрывает. Останавливать
приложение из-за отсутствия оптимизации не за что.

Альтернатива «переписать поток» отвергнута правилом: retention, storage и
лимиты — зона эксплуатации.

Предупреждение печатается один раз на поток: `#ensureStream` вызывается на
каждой долговечной публикации, и без памяти предупреждение шло бы на каждое
сообщение. Транспорт держит множество имён потоков, о которых уже сказал.

### 5. Границу коннектора переходит `duplicate_window` в наносекундах

`NatsStreamConfigLike` получает необязательное поле `duplicate_window`,
`NatsPubAckLike` — поле `duplicate`. Оба названы так, как их называет API
брокера: рядом уже лежат `durable_name`, `ack_policy`, `max_deliver`.
Коннектор — перечень глаголов и полей брокера, и переименование прятало бы
то, что подстановщик своего клиента обязан узнать.

Перевод миллисекунд в наносекунды делает транспорт при создании потока:
наружу, в опцию фабрики, единица брокера не выходит.

`duplicate` в подтверждении нужен, чтобы дубль отличался от первой
публикации. Транспорт пишет о нём `debug` с subject'ом: событие редкое и
означает, что окно сработало.

### 6. Двойник дедуплицирует так же

Состояние потока в двойнике получает карту «идентификатор сообщения →
момент, после которого запись протухла». Публикация с известным
идентификатором внутри окна не попадает ни в поток, ни в core-доставку и
возвращает подтверждение с `duplicate: true` и последовательным номером
первой публикации.

Без этого поведение проверялось бы только интеграционным прогоном против
живого брокера, а он идёт отдельно и не на каждом коммите.

Момент двойник берёт тем же способом, что и остальные его таймеры, — чтобы
тест не зависел от настоящих часов там, где окно нужно перешагнуть.

## Risks / Trade-offs

- **Окно шире цикла повторов не спасает от повтора после долгого простоя** →
  записан в границе: relay, вернувшийся к записи через час, опубликует её
  заново, и повтор снимет слой приёма. Окно брокера закрывает быстрые
  повторы, а не все.
- **Первый процесс задаёт окно на всё время жизни потока** → предупреждение
  называет расхождение, а команда правки потока приведена в README: окно
  меняется без пересоздания.
- **Дедупликация по ключу, назначенному приложением** → приложение может
  публиковать с любым ключом, и два разных сообщения с одним ключом в одном
  потоке схлопнутся в одно. Это семантика ключа идемпотентности, а не новое
  поведение: тот же ключ уже определяет повтор на приёме.
- **Память брокера под окно** → идентификаторы за 5 минут потока с высоким
  темпом стоят памяти на сервере. Величина открыта опцией, и её снижение не
  требует правок кода.

## Migration Plan

Изменение аддитивное: приложение без опции получает поток с окном 5 минут и
заголовок в долговечных публикациях.

Поток, созданный до этого change'а, окна не получит — транспорт его не
переписывает. Запись `warn` назовёт такой поток при первой публикации;
эксплуатация правит его командой `nats stream edit <имя> --dupe-window=5m`.
Откат — снять опцию и вернуть окно потока прежней командой.
