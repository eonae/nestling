Nestling / Основы

Основы

Как приложение собирается и живёт: контейнер, фазы жизненного цикла, конфигурация без process.env в коде, стриминг и тестирование без магии моков.

Контейнер

@nestling/container — основа фреймворка: типобезопасный DI без сторонних зависимостей на стандартных декораторах ECMAScript. Его можно использовать отдельно: во фронтенде, в CLI, рядом с любым фреймворком.

Жадный, а не ленивый

Контейнер жадный: на build() он создаёт весь граф сразу. Из этого следует большинство гарантий Nestling:

  • Циклы обнаруживаются при вычислении топологического порядка: приложение падает на старте, а не в проде.
  • Недостающая зависимость — ошибка build() с именем токена.
  • Полный граф означает, что визуализация, топологический порядок init/destroy и explain() работают всегда.
  • Невыбранная фича не строится: её провайдеры не попадают в граф (см. монолит).

Хуки жизненного цикла в топологическом порядке

Провайдер может объявить @OnInit (захват ресурса: пул БД, соединение) и @OnDestroy (освобождение). Они выполняются в строгом топологическом порядке: init — от зависимостей к зависимым, destroy — в обратном порядке. Вопроса «что раньше: хук модуля или сервиса» не возникает, потому что хуков у модулей нет.

@Injectable([DbConfig])
export class Database {
  #pool!: Pool;
  constructor(private cfg: Config<typeof DbConfig>) {}

  @OnInit() async connect() { this.#pool = await createPool(this.cfg.url); }
  @OnDestroy() async close() { await this.#pool.end(); }
}
Стандартные декораторы

Nestling использует декораторы из спецификации ECMAScript, а не экспериментальные декораторы TypeScript с reflect-metadata. Декораторов параметров в стандарте пока нет, поэтому зависимости объявляются массивом в @Injectable([...]). Это цена стандарта, и она же делает граф явным.

Multi-injection

Частая задача: разные модули независимо добавляют реализации одного операции (health-checks, миграции, валидаторы, обработчики событий), а один потребитель хочет получить весь набор массивом, не зная состава. В Angular это multi: true, в Nest такой набор собирают вручную.

В Nestling это ещё одно применение семейств токенов, и правило «один токен — один узел» сохраняется. Каждый вклад — обычный провайдер с членским токеном семейства. Агрегат — специальный токен Family.all, который на build() превращается в массив всех зарегистрированных членов:

export const IHealthCheck = makeTokenFamily<HealthCheck, [name: string]>('HealthCheck');
// каждый модуль регистрирует свой вклад как ОБЫЧНЫЙ провайдер
export const DbModule = makeFeature({
  name: 'module:db',
  providers: [classProvider(IHealthCheck('db'), DbHealthCheck)],
});
@Injectable([IHealthCheck.all])   // Token<readonly HealthCheck[]>
export class HealthEndpoint {
  constructor(private checks: HealthCheck[]) {}

  async handle() {
    const results = await Promise.all(this.checks.map(c => c.probe()));
    return new Ok({ ok: results.every(r => r.ok), results });
  }
}

Без реестра и без рантайм-резолюции

Состав массива определяет регистрация в контейнере, а не побочные эффекты импортов. На build() контейнер спрашивает у семейства, какие из зарегистрированных провайдеров являются его членами, и создаёт узел-агрегат с рёбрами к каждому из них. Дальше это обычный узел графа: циклы обнаруживаются, init и destroy идут топологически (все вклады инициализированы до агрегатора), визуализация видит всё.

Согласованность с фичами

Состав массива равен тому, что зарегистрировано. Поэтому выбор фич фильтрует его автоматически: если фича не выбрана, её health-checks в массив не попадают. Реестры на побочных эффектах (глобальный Set, который наполняется при импорте) так работать не могут, и Nestling их не использует.

Почему не multi: true

У каждого вклада свой токен (IHealthCheck('db')), поэтому он остаётся адресуемым по отдельности: его можно инжектировать точечно, увидеть в графе, отнести к модулю. multi: true складывает всех в один токен и теряет это. Агрегат — производное ребро графа, а не особый вид провайдера.

Жизненный цикл

App проводит приложение через семь фаз. Порядок фаз — не оформление: именно он делает ряд ошибок невозможными структурно.

0  BOOTSTRAP   чтение и проверка конфига · select        → падение на старте
1  ASSEMBLE    построение графа · discovery · привязка портов → падение на старте
2  INIT        @OnInit: захват ресурсов · connect       (dispatch НЕ существует)
3  WIRE        регистрация endpoint'ов                   (dispatch СОЗДАЁТСЯ здесь)
4  START       @OnStart: serve(dispatch, signal)         — не listen()
5  RUN         обработка запросов · reloadable-конфиг
6  SHUTDOWN    обратный порядок START · отмена запросов · @OnDestroy

Гарантия, а не конвенция

Классическая ошибка: транспорт начинает слушать сокет в @OnInit, когда маршрутизация ещё не готова, и первые запросы уходят в никуда. Nest полагается на договорённость «не делайте так». Nestling делает это невозможным:

  • у транспорта нет метода listen() без аргументов;
  • принимать запросы можно только с готовой таблицей маршрутов: serve(dispatch, signal);
  • dispatch создаётся на фазе WIRE, между INIT и START.

Транспорту, который попытался бы принимать запросы раньше, нечего было бы маршрутизировать: dispatch ещё не существует. Порядок 2→3→4 обязателен: если объединить WIRE с ASSEMBLE, dispatch станет доступен слишком рано, и гарантия перестанет действовать.

Хук Смысл
@OnInit Захватить ресурс: подключиться к БД или NATS. Транспорт подключён, но запросы не принимает.
@OnStart Начать обслуживать запросы (serve). Только здесь и только с готовым dispatch.
@OnDestroy Освободить ресурс. Выполняется в обратном топологическом порядке.

При SIGTERM и SIGINT остановка идёт в обратном порядке: остановить приём запросов, отменить текущие через meta.signal, закрыть ресурсы. Корректная остановка встроена в жизненный цикл.

Конфигурация

Конфиг в Nestling — не отдельная подсистема и не «стадия конфигурации», а частный случай зависимости. Секция объявляется схемой, инжектируется как типизированный объект и проверяется на старте: невалидный конфиг роняет приложение до захвата ресурсов.

export const OrdersConfig = makeConfig('orders', {
  maxItems:    z.coerce.number().default(100),   // ключ ORDERS_MAX_ITEMS
  databaseUrl: from('DATABASE_URL', z.url()),    // точное имя ключа, без префикса
});

// наружу из пакета — только описание ключей; сам токен не экспортируется
export const ordersKeys = OrdersConfig.keys;
@Injectable([OrdersConfig])
export class OrdersService {
  constructor(private cfg: Config<typeof OrdersConfig>) {}

  create(dto: NewOrder): Order {
    if (dto.items.length > this.cfg.maxItems) throw TooManyItems({ max: this.cfg.maxItems });
    /* ... */
  }
}

Секция не знает, откуда пришло значение

Секция называет ключ (maxItems превращается в ORDERS_MAX_ITEMS), но не источник. Откуда взялось значение — из env, файла или Vault — решает ядро, а не пользовательский код.

process.env читает только ядро. Привязка источников добавляется постепенно: если приложению хватает env, в composition root про конфиг не написано ничего. Второй источник привязывается плоским списком:

// только env — писать ничего не нужно
await assemble({ modules: [OrdersModule], transports: [http()] }).run();

// добавили Vault и файл — привязка в корне, порядок задаёт приоритет
await assemble({
  modules: [OrdersModule],
  transports: [http()],
  config: [
    [vault(), [ordersKeys]],               // привязка по ключам, не по токенам
    [file('config.yaml'), ['*_URL']],
  ],
}).run();

Приватность секции

У секции два права, и это два разных объекта. Токен даёт право инжекта; он не экспортируется из пакета, поэтому чужой инжект нельзя даже написать. Это та же видимость ES-модулей, которая охраняет токены ядра; регистрировать секцию в модуле не нужно, контейнер видит её как обычную зависимость. .keys даёт право привязки; инжектировать его нечем, поэтому экспортировать его безопасно. Корень получает ровно то право, которое ему нужно.

Reloadable-секции

Источник с наблюдением (reloadableFile, vault({ watch: true })) при изменении обновляет reloadable-секцию: экземпляр остаётся тем же, поля обновляются на месте. Два отличия от старта:

  • на старте невалидный конфиг роняет приложение; при перезагрузке невалидное значение отбрасывается с предупреждением, и остаётся последнее рабочее;
  • вступит ли изменение в силу, решает потребитель. Поэтому reloadable — явный выбор при объявлении секции.
export const Runtime = makeConfig.reloadable('runtime', {
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  rps:      z.coerce.number().default(100),
});

@Injectable([Runtime])
class RateLimiter {
  #bucket = new TokenBucket(100);
  constructor(private cfg: Config<typeof Runtime>) {}
  @OnStart() start(signal: AbortSignal) {
    this.#bucket.refill(this.cfg.rps);
    this.cfg.onChange(signal, (next) => this.#bucket.refill(next.rps)); // отписка по signal
  }
}
Ядро и пользовательский код

Граница между вашим кодом и кодом фреймворка устроена как в операционной системе. Токены ядра (источники конфига, транспорты, шина, механизм графа) не экспортируются, поэтому из пользовательского кода их нечем инжектировать. Пересечь границу можно только через публичные операции: инжект Config<X>, вызов Port или Emitter, возврат из endpoint'а. Границу держит видимость ES-модулей, а не проверка прав в рантайме.

Асинхронный контекст

Накопленный контекст пайплайна доступен хендлеру явно, через meta. Но requestId нужен и логгеру в репозитории тремя уровнями ниже, а передавать его параметрами через все сигнатуры неудобно. Решение Nestling: значение передаётся через AsyncLocalStorage, зависимость объявляется явно, доступ только на чтение.

export const RequestId = contextVar<string>()('requestId');   // брендированный ключ, как makeToken<T>()

// запись — только из pre-юнитов:
// .pre(RequestId.provide(...))  →  + { requestId } в контекст и в проекцию

// глубокий сервис читает через ИНЖЕКТИРУЕМЫЙ ридер:
@Injectable([Ctx(RequestId)])
export class AuditLog {
  constructor(private requestId: CtxReader<string>) {}
  write(e: AuditEvent) {
    this.log.info({ requestId: this.requestId.get() }, e.name);
  }
}

Как это устроено:

  • Записывают только .pre-юниты. Проекция в AsyncLocalStorage — копия накопленного контекста только для чтения; единственный писатель — рантайм пайплайна. Context.set() из произвольного места нет.
  • Зависимость видна в графе. Ctx(RequestId) — член семейства токенов: кто читает контекст, видно в графе, в визуализации и в explain(). В тестах ридер подменяется обычным valueProvider, AsyncLocalStorage не нужен. Поскольку контейнер видит всех запрошенных членов семейства на сборке, полный список чтений контекста известен на build().
  • get() и peek() повторяют асимметрию пайплайна. На пути успеха контекст полный, и get(): T всегда возвращает значение. В .catch, .finally, @OnStart и фоновых задачах значения может не быть, и для них есть peek(): T | undefined. get() без значения бросает ошибку с указанием текущей фазы.
  • В проекции только накопленный input и signal: отмена нужна и глубоко в сервисах. raw и endpoint в проекцию не попадают, чтобы транспорт не проникал в домен.
  • Через порты. Внутри процесса контекст проходит через port.call() сам. Для удалённых портов переменные с propagate: true передаются в заголовках сообщения (NATS), и транспорт на другой стороне открывает контекст заново.
Почему не статический AsyncContext.get()

Статический доступ поверх AsyncLocalStorage со строковыми ключами — глобальное состояние: зависимость не видна в графе, тесты требуют настоящего AsyncLocalStorage, наличие ключа не типизировано, а запись разрешена откуда угодно. Инжектируемый ридер только для чтения закрывает все четыре пункта ценой одной строки в deps. Строгая проверка, что каждый читатель достижим только из endpoint'ов, чей пайплайн записывает ключ, — политика hasVar на собранном графе.

Стриминг

Стриминг построен на стандартном AsyncIterable, а не на библиотечном типе. Pull-модель даёт backpressure без дополнительного кода: медленный клиент просто не запрашивает следующий элемент. Поэтому RxJS нет на границах фреймворка, но внутри хендлера он доступен полностью.

Верхний уровень input и output — это форма, а листья — схемы: значение (схема как есть), stream(T), events(T), multipart({ fields, files }). Форма определяет способ валидации (значение целиком или каждый элемент потока), media type и способ передачи ответа. Файловое поле объявляется через upload({ maxSize, mime, multiple }); лимиты применяются во время разбора, поэтому файл сверх лимита не буферизуется целиком.

stream(T) и events(T)

Две разные формы с разной семантикой:

stream(T) events(T)
Природа конечные данные (экспорт, большой результат) открытая подписка
Конец естественный: данные закончились нет; нормальное завершение — отключение клиента
HTTP NDJSON, chunked SSE: heartbeat, id:, переподключение
Документация OpenAPI AsyncAPI 
export const streamLogs = httpEndpoint({
  method: 'POST',
  path: '/logs/stream',
  input: stream(LogChunk),                  // NDJSON: объект на строку, каждый проверяется схемой
  output: z.object({ processed: z.number() }),
  pipeline: makePipeline(),
  handle: async (chunks: AsyncIterableIterator<LogChunk>) => {
    let processed = 0;
    for await (const chunk of chunks) processed++;
    return { processed };
  },
});
Исход потока известен только после доставки

Для потоковой формы .finally вызывается после того, как поток дочитан, оборвался ошибкой или закрыт потребителем, а не сразу после ответной фазы, когда не отправлен ещё ни один байт. Пайплайн отдаёт транспорту итератор-обёртку; её закрытие ровно один раз вычисляет исход и вызывает .finally. Отсюда обязанность транспорта: потребить итератор или закрыть его. Счётчики ctx.summary (itemsIn, itemsOut и байты там, где транспорт их знает) к этому моменту посчитаны.

Отказ посреди потока уже не может сменить статус ответа: NDJSON обрывается (клиент видит незавершённый chunked-ответ), SSE получает кадр event: error с телом отказа и закрывается. В обоих случаях исход — failed, а .catch не вызывается: заменять ответ уже нечем.

AbortSignal — основной механизм отмены

В meta каждого запроса есть signal: AbortSignal. Его взводит транспорт (клиент отключился), приложение (остановка) или администратор (принудительное закрытие подписки). Это единый механизм отмены: без него бесконечные подписки не завершаются, а close() ждёт живые соединения.

Источники событий — обычные провайдеры

Источник живёт в контейнере как синглтон и работает независимо от подписчиков. Хендлер вызывается один раз на соединение и подписывается на источник:

@Injectable([])
export class LogHub {
  #topic = new Topic<LogEvent>({ buffer: 1000, onSlowConsumer: 'disconnect' });
  publish(e: LogEvent) { this.#topic.push(e); }
  subscribe(signal: AbortSignal) { return this.#topic.subscribe(signal); }
}

// endpoint: подписка на каждое соединение
handle: async function* (_, meta) {
  yield* hub.subscribe(meta.signal);       // отписка привязана к отмене
}

Два уровня обработки

У потоков две цепочки: действия на весь запрос (фазы .pre, .ok, .catch, .finally) и действия на каждый элемент. Второе объявляется прямо на форме stream() или events() линейной цепочкой комбинаторов; фаз здесь нет, элемент проходит через преобразования по порядку:

input: stream(LogChunk)
  .tap(c => log.debug(c.message))    // наблюдение
  .filter(c => c.level !== 'debug')  // T → T
  .limit(50_000)                     // Fail при превышении
  .gapTimeout(30_000)                // разрыв при молчании
  .batch(100),                       // меняет тип: хендлер получит LogChunk[]
Граница с RxJS

Набор комбинаторов закрытый и инфраструктурный: наблюдение, отсечение, лимиты, время, группировка. Всё, что связано с перестановкой во времени и слиянием потоков (merge, switchMap, combineLatest), относится к логике хендлера, где можно взять RxJS. Переход простой: from(asyncIterable) и обратно, а отмена связывается через meta.signal.

Схемы и OpenAPI

Всё, что пересекает границу приложения, объявлено схемой: вход и выход endpoint'а, секция конфига, payload операции. Nestling не привязан к конкретному валидатору: ядро принимает Standard Schema — общий интерфейс, который вместе спроектировали авторы Zod, Valibot и ArkType. Любая схема со свойством ~standard работает сразу: Zod (v4, включая zod/mini), Valibot, ArkType, Effect Schema.

// Zod — привычный вариант…
export const NewOrder = z.object({ items: z.array(OrderItem).min(1) });

// …но операция тот же на Valibot или ArkType — валидатор выбираете вы:
export const NewOrder = v.object({ items: v.pipe(v.array(OrderItem), v.minLength(1)) });
export const NewOrder = type({ items: OrderItem.array().atLeastLength(1) });

Рантайму от схемы нужны два свойства: validate (невалидный payload даёт 400 со стандартным списком issues: { message, path }[]; формат задаёт спецификация, а не вендор) и вывод типов для хендлера. Zod при этом не является зависимостью ядра: валидатор приносит приложение. Лёгкий бандл (zod/mini, Valibot) или богатый синтаксис (ArkType) — выбор приложения.

OpenAPI: конвертер объявляется явно

Standard Schema стандартизует только валидацию. Интроспекции в спецификации нет: в рантайме схема — чёрный ящик с функцией validate, и получить из неё JSON Schema через общий интерфейс нельзя. Для этого нужен конвертер конкретного валидатора (z.toJSONSchema(), @valibot/to-json-schema и подобные). Поэтому модуль документации не угадывает валидатор: конвертер объявляется в composition root.

import { openapi } from '@nestling/openapi';
import { zodConverter } from '@nestling/openapi.zod';

await assemble({
  modules: [
    OrdersModule,
    openapi({
      info: { title: 'Orders API', version: '1.0.0' },
      converters: [zodConverter()],   // схемы каких вендоров документируем
    }),
  ],
  transports: [http()],
}).run();

Дальше работает механика жадного старта. Все endpoint'ы известны на build(), у каждой схемы есть поле ~standard.vendor, и на сборке модуль сверяет вендоров со списком конвертеров. Схема, которую нечем конвертировать, — ошибка запуска, а не пустой раздел в документации через месяц. Если документация включена, недокументированных endpoint'ов не бывает.

  • Несколько валидаторов в одном приложении допустимы: сторонний модуль может быть написан на Valibot, а ваш код — на Zod. Схема сама сообщает вендора, converters — список.
  • Обход конвертера: аннотация jsonSchema(schema, json) задаёт JSON Schema вручную — для экзотического валидатора или доводки.
  • Ошибки — тоже операция: errors: [EmailTaken] из декларации превращается в responses, а неявный UnknownError — в ответ default.
  • Стриминг: для stream и events тот же механизм строит AsyncAPI.
Почему не универсальный генератор

Поле vendor есть в спецификации именно как признак для безопасного приведения к конкретному валидатору: авторы Standard Schema прямо признали, что потребителям иногда нужно спускаться под общий интерфейс. Конвертер — это оформленное приведение: @nestling/openapi.zod зависит от zod как от peer-зависимости и следует его мажорным версиям. Если сообщество стандартизует и выход в JSON Schema, конвертеры сведутся к одному универсальному, а сигнатура openapi() не изменится.

Тестирование

Правило одно: уровень теста равен границе видимости. Внутри пакета видно всё: юнит-тесты и тесты модуля живут рядом с кодом, и приватность токенов им не мешает. Приложению видны только публичные права, поэтому app-тесты подменяют зависимости на границах между модулями, а не внутри чужого кода. Тестовая поверхность совпадает с экспортной.

Уровень 0: без фреймворка

Провайдеры — обычные классы и фабрики с явными зависимостями, секция конфига — объектный литерал, порт — объект с методом call. У юнит-теста нет импортов из @nestling/*:

const svc = new OrdersService({ maxItems: 2, databaseUrl: 'postgres://test' });
expect(() => svc.create({ items: [a, b, c] })).toThrow();

App-тест: тестовый composition root

Подмена в Nestling — не патчинг и не перехват модулей, а замена узла графа до создания экземпляров. Тест — это другой composition root:

await using app = await assembleTest({
  features: [OrdersFeature],
  config: [[vars({ ORDERS_MAX_ITEMS: '5' }), '*']],           // источник в памяти
  overrides: [[OrdersRepo, inMemoryOrdersRepo()]],            // токен → фейк
  stubs: [stub(ChargeCard, async () => new Ok({ chargeId: 'test' }))],
});

const res = await app.call(CreateOrder, { items });           // полный пайплайн, без сокетов
expect(res.isFail).toBe(false);
  • Прунинг. Поддерево заменённого узла, на которое больше никто не ссылается, выпадает из графа: если репозиторий подменён, пул PostgreSQL не создаётся и не подключается. Тест получает минимальный граф без дополнительного кода.
  • Без сокетов. Тестовое приложение проходит фазы 0–3: dispatch уже создан (WIRE), START не выполняется, транспорты не принимают запросы. app.call и app.emit типизированы схемами и проводят запрос через весь пайплайн; этим app-тест отличается от юнит-теста.
  • await using. Symbol.asyncDispose выполняет SHUTDOWN в обратном порядке; ресурсы между тестами не остаются.
  • overrides есть только у assembleTest. В боевом assemble подмены графа нет.

Границы подмены вместо чужих токенов

Всё, что app-тест хочет подменить, имеет свою точку входа; чужие внутренности не нужны:

Что подменяется Инструмент
Конфиг (и перезагрузка) vars({...}) — объектный источник с watch и set(): проверяется и горячая перезагрузка (последнее рабочее значение, onChange). process.env не трогается, поэтому тесты выполняются параллельно.
Чужая фича stub(Contract, impl) — фейковый порт, ответы которого проверяются схемой операции при каждом вызове.
Сквозная инфраструктура familyOverride(ILogger, () => noop) — подмена рецепта всего семейства.
Контекст запроса valueProvider(Ctx(RequestId), 'test-id') — AsyncLocalStorage в тесте не нужен.
Транспорт не подменяется: вместо HTTP-клиента используется app.call внутри процесса.
Стаб не может разойтись с реальностью

stub(Contract, ...) проверяется схемой операции на каждом вызове. Фейк, который перестал соответствовать реальному сервису, падает сразу, а не даёт зелёный тест при красном проде. Класс ошибок, который порождают jest-моки, исчезает по построению.

.check(): вся топология одним тестом

Жадный контейнер делает build() универсальной проверкой: циклы, недостающие зависимости, привязка портов, полнота env. .check() проходит фазы 0–1: конструкторы выполняются, @OnInit — нет, то есть ни одного соединения не открывается:

for (const select of ['all', 'orders', 'billing'] as const) {
  test(`топология ${select} собирается`, () =>
    assemble({ features, select, transports: [http()] }).check());
}

Все split-топологии L4 проверяются в CI без развёртывания.

Модуль в изоляции и тестовая поверхность модуля

testModule(OrdersModule, { stubs }) — мини-приложение вокруг одного модуля: неудовлетворённые импорты нужно застабать явно, ошибка перечисляет недостающие токены. testModule живёт внутри пакета модуля, поэтому токены видны без экспорта. Если модуль хочет разрешить приложению подменять свою инфраструктуру, он экспортирует подготовленную поверхность (токены и готовые фейки вроде inMemoryOrdersRepo()) через subpath ./testing — условный экспорт, который в проде не резолвится.

Почему не jest.mock

Перехват системы модулей — рантайм-магия: мок живёт вне графа, контейнер о нём не знает, прунинг невозможен, проверить фейк схемой некому. Подмена на фазе ASSEMBLE даёт то же самое, но в графе, с проверками и типами. Чужое неэкспортированное не подменяется вообще: иначе граница видимости была бы формальностью. В крайнем случае модуль подменяется целиком — он ведь значение.
