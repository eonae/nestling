## Context

`withIdentity`, `withPermissions`, `withRequestLogging` были написаны до
модели отказов слоя (`layer-fails`, roadmap #34) и до канонического
интерфейса логгера (`kernel-logger`, roadmap #57). С тех пор ни один
пример, пакет или гайд их не использует — grep по `src` всех пакетов и
`examples/*/src` находит только: собственные спеки трёх юнитов, три
type-test фикстуры `@nestlingjs/app` (`compose-wrong-order.ts`,
`compose-arity3-inner.ts`, `pre-requires-missing.ts`) и текстовые примеры
в `docs/design/pipeline.md`, `docs/design/testing.md`,
`packages/nestling.app/src/pipeline/core/TYPE-TESTS.md`. `readme.md`
пакета перечисляет их в списке публичных экспортов. Три спеки openspec
(`kernel-logger`, `pipeline-phase-model`, `packages-layout`) называют эти
юниты в тексте требований и сценариев.

## Goals / Non-Goals

**Goals:**

- Убрать три юнита и их спеки из кода без следа в публичном API.
- Заменить их как иллюстративный пример в type-тестах и доках равноценным
  примером на уже существующих, живых юнитах — не потерять типовое
  покрытие (двухшаговая зависимость pre-юнитов, арность 3).
- Снять/поправить три спека openspec, которые называют удаляемые имена
  в тексте требований.

**Non-Goals:**

- Не проектировать замену аутентификации — это `auth-layer` (roadmap
  #78), отдельный change без готового дизайна.
- Не трогать `httpAccessLog` (`nestling.transport.http/src/units.ts`) —
  он не импортирует `withRequestLogging`, только упоминает его в
  комментарии как сравнение; комментарий переживёт change без изменений,
  поскольку описывает собственное поведение `httpAccessLog`, а не чужого
  юнита.

## Decisions

**Удалить, а не переписать под `.pre(unit, { errors })`.** Причина —
инвентаризация импортов: ни одного вызывающего кода вне тестов/доков нет,
значит переписывать нечего ради обратной совместимости (которой в V1 не
существует). Второй довод — `withIdentity`/`withPermissions` кодируют
плоскую модель аутентификации (произвольная функция → identity →
permissions), которую `auth-layer` заменит типизированной переменной
`Caller`; сохранение текущих сигнатур под новым каналом ошибок создало
бы API, которое `auth-layer` тут же уберёт повторно.

**Type-test фикстуры получают локальные инлайн pre-юниты вместо
публичного API.** Фикстуры проверяют механику типов билдера (порядок
слоёв, накопление `TNeeds`, арность composе), а не поведение конкретной
аутентификации — им нужен любой pre-юнит с нужной формой входа/выхода.
Инлайн-функция `(ctx) => ({ identity: ... })` даёт тот же типовой эффект
без публичного экспорта, который выгоднее не создавать заново для теста.

**Спеки openspec правятся точечно, без общего аудита текста.** Три
найденных места (`kernel-logger`, `pipeline-phase-model`,
`packages-layout`) — единственные, где текст называет удаляемые имена
(проверено grep по `openspec/specs/`). `kernel-logger` теряет требование
целиком (описанного поведения больше нет); `pipeline-phase-model` и
`packages-layout` меняют только идентификатор в примере сценария — сам
нормативный текст требования не меняется, поэтому это `MODIFIED
Requirements` с минимальной правкой, а не редизайн спека.

**Замена примера в `pipeline-phase-model`**: `withIdentity(auth)` →
`withTracing()` — оба юнита имеют форму `PreUnitFn<EmptyInput, {…}>` и
остаются в публичном экспорте, сценарий продолжает иллюстрировать
накопление входа двумя `.pre()` подряд.

**Замена примера в `packages-layout`**: `withRequestLogging` →
`readSectionSnapshot` — то же внутреннее (не экспортированное из
`src/index.ts`) имя, что уже используется соседним сценарием «Внутреннее
имя не выходит наружу» в том же требовании; переиспользование одного
имени в обоих сценариях этого требования читается связнее, чем два
разных примера.

## Risks / Trade-offs

[Три type-test фикстуры перестают демонстрировать работу конкретно
`withIdentity`/`withPermissions`] → это и есть цель: фикстуры проверяют
билдер, а не эти два юнита; инлайн-юнит с тем же типовым контрактом даёт
идентичное покрытие диагностики компилятора.

[Кто-то мог полагаться на `withIdentity`/`withPermissions` как готовый
пример аутентификации, скопировав его в свой код] → инвентаризация не
нашла такого кода в репозитории; вне репозитория пользователей нет
(стадия проекта — активное проектирование, `CLAUDE.md`).

## Migration Plan

Обратной совместимости нет: миграции для потребителей не требуется.
Внутри репозитория — правки одним change'ем, без промежуточного
состояния (алиасов или deprecated-обёрток не заводим).
