# Семейства токенов в DI

> Гайд по **текущему API**; сверено с кодом `examples.simple-app` (2026-09-01).

Семейство токенов — один рецепт для многих зависимостей, которые
различаются параметром: логгер на каждый скоуп, HTTP-клиент на каждый
upstream, очередь на каждое имя. Член семейства запрашивается как обычная
зависимость (`ILogger('users')`), а контейнер создаёт его при сборке. В
рантайме ничего не резолвится: `build()` видит все запрошенные члены и
создаёт для каждого обычный узел графа.

## Объявление семейства

```typescript
// packages/examples.simple-app/src/logging/registry.ts
import { makeTokenFamily } from '@nestling/container';

export interface ILogger {
  log(...args: unknown[]): void;
}

export const ILogger = makeTokenFamily<ILogger, [scope: string]>('Logger');
```

`ILogger('users')` возвращает токен с id `Logger:users`. Повторный вызов с
тем же параметром возвращает тот же токен. Член семейства — полноценный
`InjectionToken`: его можно указывать в `deps` класса с `@Injectable`, в
`deps` фабричного провайдера и передавать в `container.get()` и
`getOrThrow()`.

`const` и `interface` под одним именем — обычный приём TypeScript:
`ILogger` как значение — семейство, `ILogger` как тип — интерфейс сервиса.

## Рецепт семейства

Провайдер регистрируется не для каждого члена, а для семейства целиком:

```typescript
// packages/examples.simple-app/src/logging/logging.module.ts
import { factoryProvider, familyProvider, makeModule } from '@nestling/container';

import { AppConfig } from '../config/app.config';
import { ILogger } from './registry';

export const LoggingModule = makeModule({
  name: 'module:logging',
  providers: [
    familyProvider(ILogger, (scope) =>
      factoryProvider(
        ILogger(scope),
        (config: Config<typeof AppConfig>) => ({
          log: (...args: unknown[]) =>
            console.log(`[${config.logLevel}] Logger:${scope}`, ...args),
        }),
        [AppConfig] as const,
      ),
    ),
  ],
});
```

Рецепт — функция `(param) => ProviderDefinition<T>`. Она возвращает
обычное определение провайдера (`valueProvider`, `factoryProvider` или
`classProvider`), поэтому у члена есть свои `deps`: здесь он зависит от
секции конфига (см. [config.md](./config.md)). В тестах член подменяется
так же, как любой другой провайдер.

Контейнер проверяет, что `provide` результата совпадает с токеном члена.
Если рецепт вернул провайдер для другого токена, сборка падает с указанием
семейства, параметра и фактического токена.

`familyProvider(...)` принимается в `providers` модуля (массивом или
фабрикой) и напрямую в `builder.register(...)`. Второй рецепт для того же
семейства — ошибка регистрации.

## Что делает `build()`

1. Собирает все члены зарегистрированных семейств, упомянутые в `deps`
   зарегистрированных провайдеров.
2. Вызывает рецепт один раз на каждый уникальный параметр.
3. Регистрирует результат как обычный провайдер, с именем модуля, в
   котором зарегистрирован рецепт.
4. Повторяет, пока появляются новые члены: провайдер из рецепта сам может
   зависеть от членов того же или другого семейства.

Дальше член ничем не отличается от провайдера, зарегистрированного
вручную. Он создаётся при сборке; два потребителя `ILogger('users')`
получают один инстанс; он участвует в проверке циклов, получает `@OnInit`
и `@OnDestroy` в топологическом порядке, относится к своему модулю,
попадает в `toJSON()` и визуализацию.

Член, которого никто не запросил, не создаётся: `container.get()` вернёт
для него `null`. Набор членов определяют `deps`, а не порядок импортов,
поэтому сборка детерминирована.

**Член создаётся только вызовом семейства.** `makeToken('Logger:users')`
даёт похожую строку, но не члена. Контейнер сообщит об отсутствующем
провайдере и подскажет, что токен похож на член семейства `Logger`, а
членов создают вызовом `Logger('<param>')`.

## `.auto`: член, названный по потребителю

```typescript
// packages/examples.simple-app/src/users/users.repository.ts
@Injectable([IDatabase, ILogger.auto])
export class UserRepository {
  constructor(database: IDatabase, logger: ILogger) { /* ... */ }
}
```

`ILogger.auto` — маркер, который `@Injectable` заменяет на
`ILogger('UserRepository')` в момент декорирования класса. Потребитель
известен статически, в рантайме ничего не резолвится. В выводе примера это
строка `[debug] Logger:UserRepository Loading all users`.

Ограничения:

- `.auto` допустим только в `deps` класса с `@Injectable`. В `deps`
  фабричного провайдера класса-потребителя нет, поэтому это ошибка
  регистрации с подсказкой написать явный `ILogger('<имя>')`.
- Класс без имени (анонимный) — ошибка при декорировании.
- Id члена берётся из `constructor.name`. Минификация, которая
  переименовывает классы, переименует и членов. Целевая среда — серверный
  Node, где классы не минифицируют.

`.auto`-член и явный `ILogger('UserRepository')` — один и тот же узел
графа.

## `.all`: массив всех членов (multi-injection)

Обратная задача: вкладов много, регистрируют их независимо разные модули,
а потребитель один и состава заранее не знает. Так устроены
health-check'и, миграции, валидаторы. Каждый вклад — обычный провайдер с
членским токеном; центрального списка нет:

```typescript
// packages/examples.simple-app/src/health/registry.ts
export interface IHealthCheck {
  readonly name: string;
  check(): Promise<string>;
}

export const IHealthCheck = makeTokenFamily<IHealthCheck, [name: string]>(
  'HealthCheck',
);
```

```typescript
// packages/examples.simple-app/src/database/database.module.ts
export const DatabaseModule = makeModule({
  name: 'module:database',
  providers: [
    classProvider(IDatabase, Database),
    classProvider(IHealthCheck('database'), DatabaseHealthCheck),
  ],
});
```

Второй вклад живёт в `ApiModule`:
`classProvider(IHealthCheck('api'), ApiHealthCheck)`. Чтобы его добавить,
первый модуль править не пришлось.

Агрегатор зависит от `IHealthCheck.all` — токена с типом
`TokenString<readonly IHealthCheck[]>`:

```typescript
// packages/examples.simple-app/src/health/health.service.ts
@Injectable([IHealthCheck.all, HealthConfig, ILogger.auto])
export class HealthService {
  constructor(
    checks: readonly IHealthCheck[],
    config: Config<typeof HealthConfig>,
    logger: ILogger,
  ) { /* ... */ }
}
```

`IHealthCheck.all` стоит в `deps` рядом с обычными токенами: секцией
конфига и членом семейства логгеров. Агрегат ничем не привилегирован.

Вывод примера показывает оба вклада:
`Running 2 health checks against localhost:5432` и
`Health: [ 'database: ok', 'api: ok' ]`.

### Как `build()` собирает агрегат

После того как рецепты перестали создавать новых членов, контейнер
регистрирует для `.all` синтетический узел: его `deps` — токены всех
зарегистрированных членов семейства, а инстанс — массив их инстансов.
Дальше это обычный узел графа: он участвует в проверке циклов (в том
числе `агрегат → член → агрегат`), в `init()` и `destroy()` по
топологическому порядку, в `toJSON()` и визуализации.

- Состав агрегата — все члены, у которых на этот момент есть провайдер:
  явные вклады, члены из рецепта и члены из `.auto`. Рецепт семейству не
  обязателен: семейство из одних явных вкладов агрегируется так же.
- `.all` не создаёт членов. Член, созданный вызовом
  `IHealthCheck('orphan')`, но никем не запрошенный и без провайдера, в
  массив не попадёт и узла не получит. Иначе агрегат включал бы всё, что
  кто-либо вызвал при импорте.
- Неупомянутый `.all` не создаёт узла: `container.get(IHealthCheck.all)`
  вернёт `null`.
- Пустое семейство даёт пустой массив, а не ошибку: «фичу не выбрали, её
  вкладов нет» — нормальное состояние. Опечатка в имени семейства выглядит
  так же, поэтому узел агрегата с пустыми `deps` виден в `toJSON()` и
  визуализации.
- Порядок элементов — порядок регистрации: сначала модули и провайдеры в
  порядке регистрации, затем члены, добавленные рецептами. Порядок
  детерминирован, но больше ничего не обещано. Если порядок важен
  (цепочка обработчиков), не опирайтесь на порядок `imports`.
- Массив `readonly` и заморожен: это снимок сборки, общий для всех
  потребителей `.all`. Мутация одним потребителем была бы видна остальным.
- Агрегат не принадлежит модулю (`metadata.module === undefined`). Его
  рёбра к вкладам ничем не ограничены: вклад чужого модуля попадает в
  массив без дополнительных объявлений.
- Токен зарезервирован: провайдер с `provide: IHealthCheck.all` — ошибка
  регистрации, как и параметр члена `'{all}'`.

## Видимость: чем ограничен доступ к членам

Границу держат ES-модули и границы пакетов, а не модуль контейнера. Токен,
который не должен покидать свою папку, не экспортируют из её `index.ts` —
тогда зависимость на него не написать. Поля `exports` у модуля нет, и
проверки рёбер графа на сборке тоже нет: она видела бы только граф и
пропускала типы в `.d.ts`, создание класса через `new`, подстановки
`overrides` и чтение чужого ключа через `Config(key)`.

Из этого следует правило для семейств: вклад — это провайдер члена в
`providers` модуля, и другой записи он не требует.

## Чего нет в V1

- Семейств с несколькими параметрами (`IQueue('orders', 'dlq')`): параметр
  ровно один.
- Валидации параметра (например, enum допустимых скоупов). Оберните
  семейство своей функцией, если это нужно.
- Создания члена без потребителя (seed-список): единственный источник
  членов — `deps`, и `.all` этого не меняет.
- Весов и приоритетов вкладов в `.all`: порядок только регистрационный.
- Агрегатов-подмножеств (`.all` с фильтром), форм `[param, T][]` и `Map`,
  подмены состава агрегата в тестах — см.
  [roadmap](../decisions/roadmap.md).
