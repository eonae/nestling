# design — streaming-v2

## Context

Целевое состояние: [`docs/design/streaming.md`](../../../docs/design/streaming.md)
(формы, два скоупа, `Topic`, граница с RxJS) и
[`docs/design/endpoints.md`](../../../docs/design/endpoints.md) §5 (дерево
форм io). Логика — `docs/decisions/ideas.md`: «[2026-07-06] Стриминг:
`stream(T)` ≠ `events(T)`, AbortSignal, источники событий», «[2026-07-06]
Два скоупа обработки: request-pipeline и item-цепочки», «[2026-07-13]
Контракт первичен» (п. 4–5). Мотивация и границы — [proposal.md](./proposal.md).

Текущее состояние кода:

- `packages/nestling.pipeline/src/core/io/io.ts` — плоский набор
  модификаторов: `stream(schema|primitive)`, `withFiles(schema, {buffer})`,
  `files({buffer})`, примитивы `'binary'|'text'`; `InferInput`/`InferOutput`
  разбирают их условными типами; `analyzePayload` даёт `PayloadConfig`,
  который читают оба транспорта и `binding.ts`;
- `src/core/pipeline.ts:569` — `normalizeResponse` (после #15 знает `Ok`,
  `Fail` и «голое значение»), `:611` — страж контракта, `:625` —
  `computeOutcome` и вызов `.finally`-юнитов **до фактической отправки**
  байтов; ограничение помечено в `src/core/types/unit.ts:29-32` прямой
  ссылкой на этот change;
- `src/core/types/context.ts` — `ExtendableContext` (`endpoint`, `raw`,
  `signal`, `input`), `FilePart { field, filename, mime, stream, size? }`,
  `makeEmptyContext(raw, endpoint, signal, startInput)`;
- `src/middlewares/validate.ts` — валидирует только `type === 'schema'`,
  прочие формы «подготавливает транспорт»;
- `transport.http/src/parser.ts` — `parseStream` (NDJSON + валидация
  элемента прямо в парсере), `parseWithFiles`/`parseFilesOnly` (busboy,
  лимит из общего `maxBodySize`); `adapter.ts:66-93` — любой
  `AsyncIterable` в ответе сериализуется одним и тем же NDJSON;
  `transport.ts:329` — switch по `inputConfig.type`;
- `transport.cli/src/index.ts` — `stream` = stdin, `withFiles` частично;
- `@nestling/transport` — `ITransport { endpoint, listen, close? }` без
  каких-либо сведений о способностях.

Ограничения, которые нельзя нарушить:

- **границы — стандартный `AsyncIterable`**, ни RxJS, ни своего типа
  потока в публичном API; словарь комбинаторов закрытый и
  инфраструктурный (лакмус из журнала: никакого `merge`/`switchMap`);
- **schema-first**: схема описывает провод в обе стороны, поэтому
  тип-меняющие трансформации видимы в декларации, а тип-сохраняющие — нет;
- **no runtime magic**: цепочка — значение на декларации, а не
  ambient-middleware; контейнера в момент создания io-декларации нет;
- **ядро без валидатора и без HTTP-специфики**: SSE, NDJSON, heartbeat,
  multipart — забота транспорта; форма io транспорт-нейтральна;
- **типовой бюджет pipeline** (change #23): новые тип-параметры не должны
  ронять снапшоты диагностик и порог инстанциаций;
- модель ошибок из #15: множество ответов ручки закрыто, всё
  незадекларированное страж превращает в `UnknownError`.

## Goals / Non-Goals

**Goals**

1. `stream` и `events` различимы в декларации, и различие доезжает до
   framing'а, семантики завершения и документации.
2. io-декларация — дерево форм с листьями Standard Schema; валидация
   поэлементна и симметрична (вход и выход).
3. Item-скоуп выражается на декларации закрытым словарём комбинаторов;
   тип-меняющие шаги видимы в контракте.
4. Исход (`Outcome`) честен для потоков: `.finally` знает, дотёк ли поток.
5. `Topic` — примитив, достаточный для источников событий и
   переиспользуемый config'ом и шиной, без зависимости от pipeline.
6. Богатые формы объявляются в контракте и проверяются против
   способностей транспорта на сборке, а не в рантайме первого запроса.

**Non-Goals** — см. «Non-goals» в [proposal.md](./proposal.md) (реестр
подписок, стриминг по шине, RxJS на границах, DI в комбинаторах,
AsyncAPI, streaming-клиент, `serve(dispatch)`, gate).

## Decisions

### D1. Форма io — брендированное значение-дескриптор, а не схема

Верхний уровень `input`/`output` — **форма**; листья — Standard Schema или
примитив (`'binary'`/`'text'`). Форма — неизменяемое значение с
неперечислимым брендом (как декларация endpoint'а и bind-карта):

```typescript
type FormKind = 'value' | 'stream' | 'events' | 'multipart';

interface FormDescriptor {
  readonly kind: FormKind;
  readonly leaf?: Schema | 'binary' | 'text';   // stream/events/value
  readonly chain?: readonly ChainStep[];        // stream/events
  readonly items?: { validate: boolean; onInvalid: 'fail' | 'skip' };
  readonly fields?: Schema;                     // multipart
  readonly files?: Readonly<Record<string, UploadSpec>>;
}
```

`analyzePayload`/`PayloadConfig` заменяются на `describeForm(io):
FormDescriptor`: старый описатель не различает `events` и знает два
разных multipart-модификатора. Схема без обёртки (и `undefined`)
описывается как `kind: 'value'` — «схема как есть» остаётся канонической
записью, никаких `value(...)` вводить не нужно.

**Почему не «стрим как схема»** (упаковать поток в Standard Schema):
отвергнуто в журнале — стрим не значение, спека для значений остаётся
нетронутой, а форма живёт над схемами. **Почему бренд, а не структурная
утиная типизация** (`__type: 'stream'` как сейчас): случайный объект с
полем `kind` не должен приниматься за форму — это тот же аргумент, что
для бренда декларации.

### D2. `stream(T)` и `events(T)` — один механизм, разная семантика

Обе формы дают `AsyncIterableIterator<TItem>` на границе и несут одну и ту
же item-цепочку. Различаются три вещи, и все три — наблюдаемые:

| | `stream(T)` | `events(T)` |
|---|---|---|
| нормальное завершение | источник закончился → `completed` | завершение = дисконнект → `disconnected` |
| HTTP-framing | NDJSON, `application/x-ndjson`, chunked | SSE, `text/event-stream` |
| место в контракте | вход и выход | выход (вход — при наличии capability у транспорта) |

Реализация формы одна (`kind` — поле дескриптора), поэтому item-цепочки,
валидация и счётчики пишутся один раз. Различие живёт в двух точках:
`computeOutcome` (какой исход нормален) и transport framing.

**Почему не один `stream` с флагом** (`stream(T, { sse: true })`): флаг —
транспортная деталь в транспорт-нейтральном слое; различие семантическое
(«конечные данные» vs «открытая подписка»), и оно нужно документации
(OpenAPI vs AsyncAPI) и исходам, а не только HTTP.

### D3. Item-цепочка — иммутабельный билдер на форме; асимметрия задаётся слотом

```typescript
interface StreamForm<TWire, TItem = TWire> extends FormDescriptor {
  tap(fn: (item: TItem) => void): StreamForm<TWire, TItem>;
  filter(pred: (item: TItem) => boolean): StreamForm<TWire, TItem>;
  limit(max: number): StreamForm<TWire, TItem>;
  gapTimeout(ms: number): StreamForm<TWire, TItem>;
  throttle(perSecond: number): StreamForm<TWire, TItem>;
  batch(size: number): StreamForm<TWire, TItem[]>;                    // тип-меняющий
  through<TNext>(fn: (src: AsyncIterable<TItem>) => AsyncIterable<TNext>): StreamForm<TWire, TNext>;
}
```

Каждый комбинатор возвращает **новую** форму (значение неизменно) —
только так работает переиспользование хелперами:
`const guarded = (s) => stream(s).limit(50_000).gapTimeout(30_000)`.

**Асимметрия входа и выхода обеспечивается типом слота, а не двумя
разными билдерами**: слот `output` принимает `StreamForm<T, T>`
(тип-параметры совпадают), слот `input` — `StreamForm<T, any>`. Поэтому
`.batch(100)` на выходе — ошибка компиляции в точке декларации
(`StreamForm<T, T[]>` не присваивается `StreamForm<T, T>`), а `.through`
разрешён на выходе ровно в `T → T`-варианте. Отдельного «выходного»
типа цепочки не появляется, и правило журнала («оба конца выхода
зафиксированы схемой») выражено одной сигнатурой.

**Словарь закрыт.** Комбинаторы с реордерингом времени, слиянием потоков
и higher-order streams не входят — это dataflow, ему место в хендлере
(RxJS как обычная зависимость). `.through` — единственный escape hatch, и
он честно объявлен в декларации.

### D4. Где применяется цепочка: вход — при сборке payload, выход — при нормализации ответа

- **Вход.** Транспорт декодирует провод в поток значений (NDJSON-строки →
  объекты) и передаёт его kernel-функции `bindInputStream(form, source,
  ctx)`, которая навешивает: поэлементную валидацию (по схеме-листу),
  счётчик `itemsIn`, затем шаги цепочки в порядке объявления. Хендлер
  получает результат. Ошибка комбинатора возникает лениво, при
  `for await` внутри хендлера → бросок → обычный error-track
  (`.catch`/`.finally`) — ровно то, что описано в журнале.
- **Выход.** `normalizeResponse` в пайплайне видит, что `endpoint.output` —
  потоковая форма, и оборачивает возвращённый хендлером `AsyncIterable`:
  шаги цепочки → поэлементная валидация → счётчик `itemsOut` → обёртка
  завершения (D6). Транспорт получает готовый итератор и занимается
  только framing'ом.

**Почему выходная цепочка в пайплайне, а не в транспорте**: форма io —
kernel-понятие, и цепочка обязана работать одинаково у любого транспорта;
транспорт остаётся переводчиком байтов. **Почему входная — в транспорте
(через kernel-функцию), а не в `validate()`-юните**: юнит валидации
работает после того, как payload собран, а поток к этому моменту уже
должен быть обёрнут — иначе первый элемент утечёт мимо счётчиков.
`validate()` для потоковых форм остаётся no-op (как сейчас).

### D5. Поэлементная валидация: синхронно, по схеме-листу, с opt-out на форме

`stream(T)`/`events(T)` принимают вторым аргументом опции:
`{ validate?: boolean; onInvalid?: 'fail' | 'skip' }` (дефолт
`{ validate: true, onInvalid: 'fail' }`). Валидация — та же синхронная
реализация, что у значений (`validateSync`, правила change #19), никакой
второй кодовой ветки.

- **вход**: элемент валидируется **до** цепочки (схема описывает провод);
  `onInvalid: 'fail'` → `ValidationFailed` (kernel-код, 400),
  `onInvalid: 'skip'` → элемент отбрасывается, счётчик `itemsIn` его не
  учитывает;
- **выход**: элемент валидируется **после** цепочки (цепочка `T → T`, так
  что оба конца — провод); невалидный элемент — всегда отказ (mid-stream
  политика D9), `onInvalid` на выходе игнорируется как бессмысленный:
  тихо ронять данные из ответа фреймворк не будет.

Это закрывает открытый вопрос журнала «поэлементная валидация горячих
стримов: дефолт и форма opt-out»: дефолт — валидировать (schema-first не
делает исключений для горячего пути), opt-out — явный
`{ validate: false }` на форме, видимый в декларации.

### D6. Исход потокового ответа — после доставки; `.finally` откладывается обёрткой

Сейчас `.finally` вызывается сразу после ответного тракта, и для стрима
это ложь: «completed» печатается до того, как ушёл первый байт.

Решение: для потоковых форм пайплайн отдаёт транспорту итератор-обёртку,
в `finally`-блоке которой (срабатывает и на нормальном конце, и на
`throw`, и на `return()` от потребителя) он один раз выполняет:
вычисление исхода → `.finally`-юниты. Не-потоковые ответы работают как
сейчас — момент вызова не меняется.

```
handler → [цепочка] → [валидация] → [счётчики] → [finish-обёртка] → транспорт
                                                        └─ finally-юниты, once
```

Исход: `signal.aborted` → `disconnected` (`ClientDisconnectedError`) или
`aborted`; иначе ошибка в потоке → `failed`; иначе — `completed` для
`stream` и `disconnected` для `events`, завершившихся отвалом клиента
(источник, закончившийся сам, даёт `completed` и для `events`).

**Контракт с транспортом**: получив потоковый ответ, транспорт обязан
либо потребить итератор до конца, либо закрыть его `return()` (в т.ч.
при ошибке отправки и при дисконнекте). Иначе `finally` не выполнится —
это проверяется тестом на каждом транспорте.

**Отвергнуто**: колбэк `onDelivered` в `ResponseContext` (транспорт
обязан не забыть его позвать — та же дисциплина, но без структурной
гарантии, что закрытие итератора и финализация — одно событие); и
«вычислять исход в транспорте» (транспорт не знает про фазы пайплайна —
прямое нарушение разделения из `docs/design/transports.md`).

### D7. `summary` — живой объект в контексте

```typescript
interface StreamSummary {
  itemsIn: number; itemsOut: number;
  bytesIn?: number; bytesOut?: number;
}
```

Создаётся вместе с контекстом (`makeEmptyContext`), доступен как
`ctx.summary` — read-only ссылка на мутируемый рантаймом объект.
`itemsIn`/`itemsOut` считают обёртки D4; байты заполняет транспорт там,
где знает их (HTTP — прочитанное тело и записанные байты ответа). Для
не-потоковых ручек `itemsIn/itemsOut` остаются нулями — поле есть всегда,
чтобы наблюдатель не ветвился.

**Почему не четвёртый аргумент `.finally`**: `summary` нужен не только
`finally` (например, `.ok`-юниту, логирующему размер экспорта), а ctx —
уже канал per-request данных. **Почему не в `input`**: `input` — это то,
что накопили pre-юниты и увидит хендлер в meta; счётчики туда не
относятся и портили бы вывод типов слоёв.

### D8. `multipart({ fields, files })` + `upload(...)` вместо `withFiles`/`files`

```typescript
input: multipart({
  fields: z.object({ title: z.string() }),                 // необязателен
  files: { avatar: upload({ maxSize: 5 * MiB, mime: ['image/png', 'image/jpeg'] }) },
})
// payload: { fields: { title: string }, files: { avatar: FilePart } }
```

- `upload({ maxSize, mime, multiple })` — спецификация файлового поля;
  `multiple: true` даёт `FilePart[]`, иначе один `FilePart` (второй файл
  с тем же именем — отказ);
- лимиты применяются **во время** парсинга: превышение `maxSize`
  прерывает разбор конкретного файла, не буферизуя его целиком;
  несовпадение `mime` — отказ до чтения тела файла;
- поля формы валидируются схемой `fields` целиком (после сборки
  bind-карты: path-параметры и query по-прежнему кладутся в `fields`);
- ключи `files` типизируют payload — имена файловых полей известны
  статически, в отличие от нынешнего плоского `FilePart[]`.

**Почему BREAKING, а не алиасы**: целевой дизайн не знает `withFiles`
и `files`, две формы для одного концерна — источник дрейфа (у одной есть
схема, у другой нет; лимит у обеих общий и берётся из чужой настройки).
Пакет не опубликован; миграция механическая и покрыта примером
`upload-avatar.endpoint.ts`.

### D9. Mid-stream отказ: политика транспорта + `failed`

Заголовки ушли — статус сменить нельзя. Ответ обязан быть честным по
framing'у:

- **NDJSON (`stream`)**: поток обрывается (`res.destroy()`), клиент видит
  незавершённый chunked-ответ — это и есть сигнал «данные неполны»;
- **SSE (`events`)**: отправляется именованное событие `event: error` с
  телом отказа (`{ error, code? }`) и соединение закрывается — SSE
  позволяет это, и клиентская сторона стандартно умеет читать именованные
  события;
- в обоих случаях `.finally` получает `failed`, а незадекларированный
  отказ проходит ту же нормализацию `UnknownError`, что и на обычном
  пути; оригинал уходит в `onUnknownFail`.

`.catch`-юниты mid-stream **не** вызываются: ответный тракт уже завершён,
и «замена ответа» физически невозможна. Это ограничение фиксируется
спекой явно, чтобы не выглядело недоделкой.

### D10. Kernel-отказы цепочек и статус `PAYLOAD_TOO_LARGE`

`.limit(n)` → `StreamLimitExceeded` (`STREAM_LIMIT_EXCEEDED`,
`PAYLOAD_TOO_LARGE` → HTTP 413); `.gapTimeout(ms)` → `StreamGapTimeout`
(`STREAM_GAP_TIMEOUT`, `TIMEOUT` → HTTP 504). Оба входят в kernel-набор
кодов: иначе страж границы (#15) превращал бы штатный отказ лимита в
`500 UNKNOWN` — прямое противоречие модели входных ошибок, ровно как с
`VALIDATION_FAILED`.

Словарь статусов пополняется `PAYLOAD_TOO_LARGE`: семантика «вход больше
допустимого» в ядре уже существует де-факто (HTTP-транспорт отвечает 413
на `PayloadTooLargeError`), но выразить её из пайплайна было нечем.

### D11. SSE-специфика живёт в HTTP-словаре декларации, не в форме

Форма `events(T)` транспорт-нейтральна. Всё SSE-специфичное объявляется
там, где легальна транспортная специфика, — в словаре `httpEndpoint`:

```typescript
httpEndpoint({
  method: 'GET', path: '/activity/live',
  output: events(ActivityEvent),
  sse: { id: (e) => e.id, event: (e) => e.kind, heartbeat: 15_000 },
  ...
})
```

Дефолт heartbeat — опция транспорта (`sseHeartbeat`, 15s); `id`/`event`
не заданы — соответствующие поля кадра не пишутся. Приём реконнекта:
транспорт кладёт заголовок `Last-Event-ID` в **типизированный стартовый
контекст** (`{ lastEventId?: string }`) для деклараций с `events`-выходом
— тем же механизмом, что `rawBody: true` (change #21), без изобретения
нового канала. Хендлер получает его через meta и сам решает, откуда
продолжить.

### D12. `Topic` — в новом пакете `@nestling/streams`

Пакет без внешних зависимостей: `Topic<T>`, реализация комбинаторов
item-цепочек и утилиты итерации под `AbortSignal`. `@nestling/pipeline`
зависит от него и строит поверх формы io.

```typescript
class Topic<T> {
  constructor(options?: { buffer?: number; onSlowConsumer?: 'drop-oldest' | 'disconnect' });
  push(value: T): void;                       // не ждёт подписчиков
  subscribe(signal?: AbortSignal): AsyncIterableIterator<T>;
  close(): void;                              // завершает все подписки
  get subscribers(): number;
}
```

Политика медленного подписчика (открытый вопрос журнала) закрывается
опцией с дефолтом `drop-oldest`: горячий источник не блокируется никогда,
а `disconnect` доступен там, где потеря событий недопустима и лучше
оборвать подписку. Ключевое: **push никогда не ждёт**, буфер per-подписчик.

**Почему отдельный пакет, а не `@nestling/pipeline`**: `Topic` нужен
config-модулю (`reloadable`, #9) и `InProcessBus` (#11) — тянуть ради
broadcast-примитива весь пайплайн неправильно. **Почему не `@common/misc`**:
это внутренняя утилитарная свалка репозитория, а `Topic` — публичный
примитив, на который опирается satellite (#7).

### D13. Capability транспорта: объявление + проверка на сборке

```typescript
interface TransportCapabilities {
  readonly input: ReadonlySet<FormKind>;
  readonly output: ReadonlySet<FormKind>;
}
interface ITransport { readonly capabilities: TransportCapabilities; /* … */ }
```

HTTP: `input {value, stream, multipart}`, `output {value, stream, events}`.
CLI: `input {value, stream}`, `output {value, stream}`. Проверка — одна
kernel-функция `assertFormsSupported(definition, capabilities, where)`:
её зовёт `App` при регистрации (текст называет ручку, модуль, транспорт и
форму) и сам транспорт в `endpoint()`/`route()` — чтобы standalone-путь
не оставался без гарантии. Обе точки — до приёма запросов, что и есть
fail-fast на ASSEMBLE в терминах текущего жизненного цикла (фазовый
lifecycle приезжает с #10; тогда вызов переедет в фазу, текст останется).

**Почему не типами**: транспорт выбирается на сборке, декларация — при
объявлении; связать их типами можно было бы только протащив тип
транспорта в декларацию, что противоречит «pipeline и handler
транспорт-слепые». Это ровно тот случай, где журнал предписывает
проверку на графе, а не церемонию в типах.

### D14. Отмена доводится до итератора

`meta.signal` (change #3) остаётся единственным механизмом отмены, но
добавляется симметричное действие: транспорт, обнаруживший дисконнект,
**закрывает** итератор ответа (`return()`), а `bindInputStream` реагирует
на `signal.abort` завершением входного потока. Это делает
детерминированными `try/finally` в хендлере-генераторе и отписку от
`Topic` (`subscribe(signal)` завершается сам). Без этого «бесконечная
подписка» удерживала бы ресурсы до GC.

## Risks / Trade-offs

- **Отложенный `.finally` меняет наблюдаемый момент вызова** → для
  не-потоковых ручек поведение не меняется вовсе; для потоковых прежний
  момент был неверным (исход печатался до отправки). Разница фиксируется
  спекой и отдельным тестом «finally после последнего байта».
- **Транспорт может не закрыть итератор** → `finally` не выполнится.
  Митигация: контракт зафиксирован в спеке `transport-form-capabilities`,
  оба транспорта покрыты тестом (успех, дисконнект, ошибка отправки).
- **Поэлементная валидация горячего потока стоит CPU** → opt-out явный
  (`{ validate: false }`) и виден в декларации; бенчмарка в CI не
  заводим — сначала нужен реальный профиль нагрузки.
- **SSE mid-stream `event: error` может быть принят клиентом за
  доменное событие** → имя `error` зарезервировано и документируется;
  прикладным событиям имя задаёт `sse.event`, и совпадение с `error`
  отвергается при создании декларации.
- **`drop-oldest` по умолчанию теряет события молча** → `Topic`
  инкрементит счётчик отброшенных и отдаёт его в `subscribers`-статистике;
  выбор политики — одно поле в конструкторе, оба варианта равнодоступны.
- **Новый пакет — новая единица сборки/публикации** → `@nestling/streams`
  без внешних зависимостей и с узким API; альтернатива (положить `Topic`
  в pipeline) обошлась бы дороже при #9/#11.
- **Рост тип-параметров формы (`StreamForm<TWire, TItem>`)** → риск для
  бюджета типов #23; митигация — прогон `type-budget` и снапшотов
  диагностик в DoD, формы не участвуют в рекурсии слоёв.

## Migration Plan

1. **`@nestling/streams`**: `Topic`, комбинаторы, утилиты итерации под
   сигналом. Пакет самодостаточен и тестируется первым.
2. **Формы io в ядре**: дерево форм, `describeForm`, вывод типов,
   `multipart`/`upload`, удаление `withFiles`/`files`; проверки формы при
   создании декларации.
3. **Рантайм пайплайна**: выходная цепочка и валидация в
   `normalizeResponse`, finish-обёртка и отложенный `.finally`,
   `summary` в контексте, kernel-отказы и `PAYLOAD_TOO_LARGE`.
4. **Capability**: `ITransport.capabilities`, `assertFormsSupported`,
   вызовы в `App` и транспортах.
5. **HTTP-транспорт**: NDJSON и SSE на выходе, приём `stream` через
   kernel-обёртку, multipart с `upload()`-лимитами, mid-stream политика,
   `Last-Event-ID` в стартовый контекст, закрытие итератора.
6. **CLI-транспорт**: способности, stdin как `stream`, NDJSON-выход.
7. **Примеры и доки**: миграция `examples.*`, SSE-пример поверх `Topic`,
   пересверка гайдов, правка `design/`, README, roadmap.

Откат — по группам: до шага 3 изменения аддитивны (кроме удаления
`withFiles`/`files`); шаги 5–6 независимы между транспортами.

## Open Questions

- **Гранулярность `bytesIn/bytesOut`**: считать ли байты после сжатия
  (сжатия в V1 нет) — решаем при появлении compression-сантехники.
- **`throttle` — семантика при переполнении**: буферизовать или ронять?
  V1: буферизует (pull-модель сама создаёт backpressure), ронять
  элементы — только `Topic` и только по своей политике.
- **`events` во входе HTTP** (клиент льёт SSE) — capability отсутствует;
  вернуться, если появится реальный кейс (кандидат — WebSocket-транспорт,
  вне V1).
- **Совместное использование одной формы двумя декларациями** — формы
  иммутабельны, так что технически безопасно; нужна ли явная гарантия в
  спеке, решим по результатам реализации.
