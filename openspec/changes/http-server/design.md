## Context

Сокетом сейчас владеет транспорт. `HttpTransport.serve` создаёт
`http.Server`, вешает обработчик, зовёт `listen` и запоминает адрес;
`close()` дренажит соединения. Порт берётся из `options.port ?? 3000`,
причём опция фабрики сильнее конфига: провайдер читает секцию
`HttpConfig` и передаёт значения конструктору, а спред
`...transportOptions` идёт последним.

Секция объявлена литералом: `makeConfig('http', { port, host })`.
Префикс один на пакет, поэтому два экземпляра транспорта читают один
`HTTP_PORT`.

Дубликат паттерна обнаруживается в `HttpRouter.route`, который вызывается
из `serve`. К этому моменту фазы 0–3 пройдены, `@OnInit` и `@OnStart`
отработали, ресурсы захвачены.

Целевое состояние описано в
[transports.md §4.2](../../../docs/design/transports.md) и записью
[ideas.md [2026-09-06] «HTTP-сервер как ресурс»](../../../docs/decisions/ideas.md).

Что уже есть и на что этот change опирается:

- Фаза 0 BOOTSTRAP и синхронная сборка (change `sync-assemble`): секции
  считаются из снимка до `build()`.
- `@Resource` с `static acquire(...deps, signal)` и `release()` (change
  `resources-and-roles`): захват асинхронен, провал захвата останавливает
  старт, потребитель создаётся после успешного захвата.
- Семейства токенов (`makeTokenFamily`): `HttpTransport$(name)` уже
  параметризован именем экземпляра.
- `App` уже держит список запущенных транспортов (`#serving`) и закрывает
  их реверсом.

## Goals / Non-Goals

**Goals:**

- Сокетом владеет отдельный узел графа, а не транспорт.
- Порт и хост приходят только из конфига; у `http()` опции порта нет.
- Два экземпляра читают разные ключи: `HTTP_PORT` и `HTTP_ADMIN_PORT`.
- Несколько транспортов работают на одном сокете.
- Сокет открывается после того, как все транспорты присоединили
  обработчики.
- Дубликат паттерна останавливает сборку до захвата ресурсов.

**Non-Goals:**

- TLS, HTTP/2, WebSocket, unix-сокет.
- Встраивание в `http.Server`, созданный вне приложения.
- Пробы `httpProbes()` — change `health`.
- Вычисляемые поля конфига и `env({ prefix })` — change `config-derived`.
- Переключатели состава — change `switches`.

## Decisions

### 1. Ядро знает роль «слушатель», а не HTTP

`@nestling/app` получает интерфейс `IListener`: `listen(): Promise<void>`
и `drain(): Promise<void>`. Ни `http.Server`, ни `node:http` в ядро не
попадают. `HttpServer` — реализация в `@nestling/transport.http`.

Почему так: порядок фаз — обязанность корня, а корень не должен знать про
HTTP. Альтернатива «`App` перечисляет серверы отдельным полем корня
(`servers:`)» отвергнута: состав корня и без того длинный, а сервер
объявляется рядом с транспортом, который на нём работает.

### 2. Сервер объявляется в `transports:`, транспорт ссылается на объявление

`httpServer({ name? })` возвращает `ServerDeclaration` — имя, токен и
провайдер, по форме такой же, как `TransportDeclaration`. Поле
`transports:` принимает union объявлений; различает их дискриминатор
`kind: 'transport' | 'server'`.

`http({ server })` принимает объявление сервера и берёт с него токен: он
входит в `deps` провайдера транспорта. Без `server` фабрика объявляет
сервер сама, с тем же именем, что у транспорта, и кладёт его в поле
`server` своего объявления. Корень регистрирует такие вложенные
объявления вместе с транспортом.

Один и тот же сервер может встретиться дважды — явным элементом
`transports:` и внутри `http({ server: api })`. Дедупликация идёт по
токену: второй провайдер не регистрируется. Два **разных** объявления с
одним именем — ошибка ASSEMBLE.

```typescript
const api = httpServer({ name: 'api' });

await makeApp({
  features: [Users],
  transports: [api, http({ server: api }), graphql({ server: api })],
}).assemble().run();
```

Почему объявление, а не токен: токен пришлось бы экспортировать из
пакета, и тогда сервер можно было бы инжектировать в прикладной код.
Объявление даёт ссылку без такого права.

### 3. Обработчики выстраиваются в цепочку, 404 отдаёт сервер

`HttpServer.attach(handler)` добавляет обработчик в конец цепочки.
Обработчик возвращает `true`, если ответ отправлен, и `false`, если
маршрут не его. Сервер зовёт их по порядку присоединения и отвечает
`404`, когда никто не взял запрос.

Сейчас `404` отдаёт транспорт из `handle`: `router.find` не нашёл
маршрут. После изменения транспорт на том же месте возвращает `false`.

Почему цепочка: без неё два транспорта на одном сокете невозможны —
первый же отвечал бы `404` на чужие маршруты.

### 4. Секция сервера — семейство по имени экземпляра

`makeConfig` вызывается на экземпляр, результат кэшируется по имени.
Префикс строится из имени: `default` даёт `HTTP`, `admin` — `HTTP_ADMIN`.
Ключи выходят `HTTP_PORT`, `HTTP_HOST`, `HTTP_ADMIN_PORT`,
`HTTP_ADMIN_HOST`.

Наружу уходит `httpServerKeys(name?)` — дескриптор ключей одного
экземпляра; токен секции остаётся приватным. Экспорт `httpConfigKeys`
удаляется.

Имя превращается в префикс тем же правилом, что имя поля в ключ:
верхний регистр, `-` и пробелы в `_`. Имя, дающее пустой или
конфликтующий префикс, — ошибка сборки.

Альтернатива «одна секция с полем-картой (`HTTP_PORTS=api:3000,admin:3001`)»
отвергнута: значение перестаёт быть числом, валидация выпадает из схемы, а
`vault` не умеет отдавать половину такой строки.

### 5. Что остаётся транспорту, что переходит серверу

| | транспорт | сервер |
| --- | --- | --- |
| `serve(dispatch, signal)` | ✓ | |
| `capabilities`, разбор, ответ | ✓ | |
| `maxBodySize`, таймауты запроса, `sseHeartbeat` | ✓ | |
| `http.Server`, `listen`, `address()` | | ✓ |
| таймауты `node:http` (`requestTimeout`, `headersTimeout`, `keepAliveTimeout`) | | ✓ |
| дренаж и `closeTimeout` | | ✓ |

Таймауты `node:http` — свойства сервера, а не транспорта; они переезжают
опциями `httpServer({ requestTimeout, … })`. Реестр контроллеров запроса
остаётся у транспорта: он про отмену обработки, а не про сокет.

`HttpTransport.close()` остаётся: он отменяет запросы в обработке. Сокет
он больше не закрывает.

### 6. Порядок фаз

START:

1. `container.start()` — хуки `@OnStart`.
2. `serve(dispatch, signal)` у транспортов в порядке объявления —
   присоединение обработчиков.
3. `listen()` у серверов в порядке объявления.

SHUTDOWN — строгий реверс:

1. Взвод сигнала остановки.
2. `drain()` у серверов в обратном порядке — новые соединения не
   принимаются, открытые дочитываются.
3. `close()` у транспортов в обратном порядке.
4. `container.destroy()`, затем закрытие источников конфига.

Гарантия «трафик не раньше `dispatch`» остаётся структурной: сокета до
шага 3 нет вовсе.

### 7. Уникальность паттерна проверяется в discovery

Проверка идёт при построении карты транспортов: ключ — пара «токен
экземпляра, паттерн». Совпадение даёт ошибку ASSEMBLE с паттерном,
именами обеих единиц и путями обоих файлов.

Паттерн HTTP включает метод (`GET /users`), поэтому `GET /users` и
`POST /users` не конфликтуют.

Проверка живёт в ядре и потому работает для всех транспортов. Правило
шины «два владельца операции» (`collectImplementations`) остаётся своим:
оно про операции, а не про паттерны, и текст ошибки у него другой.

Почему в discovery, а не в `makeDispatch`: `makeDispatch` работает на
WIRE, после INIT. Ресурсы к этому моменту захвачены.

## Risks / Trade-offs

- **Цепочка обработчиков добавляет вызов на каждый запрос.** Горячий путь
  был предметом отдельного change (`hot-path-trim`). Смягчение: при
  единственном обработчике цепочка вырождается в прямой вызов, ветка
  выбирается один раз на `listen`, а не на запрос.
- **`ServerDeclaration` расширяет форму `transports:`.** Поле перестаёт
  быть однородным. Смягчение: дискриминатор `kind` проверяет компилятор,
  а объявление сервера необязательно — приложение с одним HTTP пишет
  `transports: [http()]`, как раньше.
- **Дедупликация по токену прячет опечатку в имени.** Два объявления
  `httpServer({ name: 'api' })` в разных местах дадут два токена одного
  члена семейства и совпадут. Смягчение: совпадение по токену
  допускается, а несовпадение объявлений при равном имени — ошибка.
- **`HTTP_PORT=0` в тестах меняет способ узнать адрес.** Хелперы читают
  адрес у сервера. Смягчение: `app.servers` даёт доступ к объявленным
  серверам так же, как `app.transports` — к транспортам.

## Migration Plan

Ломающие правки идут одной волной, обратной совместимости нет:

1. `http({ port, host })` → `HTTP_PORT`, `HTTP_HOST` в `vars` или env.
2. `transport.address()` → `server.address()`.
3. `httpConfigKeys` → `httpServerKeys(name?)`.
4. Таймауты `node:http` и `closeTimeout` — из `http({ … })` в
   `httpServer({ … })`.

Затрагиваются `examples/app-with-http` (хелпер тестового приложения),
`examples/users-service`, `examples/simple-http-server`, README пакетов
`@nestling/transport.http`, `@nestling/app`, `@nestling/testing`,
`@nestling/openapi` и главы гайда 6 и 24.

## Open Questions

- Нужен ли `httpServer()` без единого транспорта на нём. Сейчас такой
  сервер откроет сокет и будет отвечать `404`. Вариант — предупреждение
  на ASSEMBLE по образцу «интерком без операций».
- Порядок цепочки при равных префиксах путей задаётся порядком
  объявления в `transports:`. Достаточно ли этого, покажет первый
  satellite-транспорт на общем сокете.
