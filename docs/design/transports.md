## 1. Место транспорта

Транспорт — **переводчик провода в значения и обратно**, обычный провайдер
с lifecycle ([composition.md](./composition.md)). Разделение ответственности
жёсткое:

- pipeline и хендлер оперируют **значениями** ([pipeline.md](./pipeline.md));
- всё байтовое — парсинг, framing, сжатие, CORS, content negotiation,
  multipart — **транспорт**;
- `IncomingMessage`/`ServerResponse` и прочие нативные объекты за пределы
  транспорта не выходят.

Контракт транспорта:

- **способности** — `capabilities`: множества форм io, которые транспорт
  умеет принимать и отдавать (см. §1.1);
- **go-live** — `serve(dispatch, signal)`: единственный вход в эфир. Ни
  nullary `listen()`, ни метода регистрации отдельной ручки в контракте
  нет — всё, чем транспорт обслуживает запросы, приезжает `dispatch`'ем;
- **shutdown** — `close()`: дренаж активных соединений, отмена in-flight.

`Dispatch` строится ядром в фазе WIRE (`makeDispatch`) — по одному на
транспорт, только из его ручек — и передаётся аргументом `serve` в START.
Он несёт **две части**:

- `routes` — проекции деклараций: паттерн, формы io, bind-карта,
  транспортный словарь и объявленные отказы. Исполнимых полей (`handle`,
  `pipeline`, `deps`, `resolve`) в проекции нет;
- `call(pattern, ctx, options?)` — исполнение ручки: выбор ветки «с
  pipeline / без pipeline» и её выполнение. Ветка одна на все транспорты,
  дублировать её транспорт не должен.

Разделение проходит **по составу, а не по времени передачи**: провод —
транспорту, исполнение — ядру. Поэтому «уйти в эфир пораньше» бесполезно, а
не просто не рекомендовано. Опции границы (`exposeErrorDetails`,
`onUnknownFail`) едут аргументом `call`: это политика конкретного провода,
а не свойство таблицы маршрутов.

Проверка форм io против способностей — в двух точках одной реализацией и с
одним текстом: на фазе ASSEMBLE (`App` знает и декларации, и инстансы
транспортов из графа) и в `serve` до открытия сокета (standalone-путь).

Standalone-путь пользуется теми же примитивами:

```typescript
const controller = new AbortController();
await transport.serve(makeDispatch([Ping]), controller.signal);
```

`makeDispatch` принимает только исполнимые декларации (`TNeeds = never`):
декларацию с непогашенными зависимостями отсекают типы.

Транспорт строит контекст запроса из провода и отдаёт его пайплайну; о фазах
пайплайна он не знает. Отмена: транспорт взводит `meta.signal` при
дисконнекте клиента; per-request и transport-level сигналы объединяются
через `AbortSignal.any`.

**Потоковый ответ — контракт с двумя обязанностями.** Получив от пайплайна
потоковый итератор, транспорт обязан либо потребить его до конца, либо
закрыть (`return()`) — в том числе при ошибке отправки и при дисконнекте:
именно закрытие итератора выполняет отложенные `.finally`-юниты
([pipeline.md](./pipeline.md)). Симметрично, обнаружив дисконнект,
транспорт закрывает итератор ответа, а не только взводит сигнал — иначе
«бесконечная подписка» удерживала бы ресурсы до GC.

### 1.1 Способности по формам io

```typescript
interface TransportCapabilities {
  readonly input: ReadonlySet<FormKind>;    // 'value' | 'stream' | 'events' | 'multipart'
  readonly output: ReadonlySet<FormKind>;
}
```

Способности — **данные транспорта**, а не конвенция и не рантайм-проверка
в момент первого запроса. Поле обязательное: сторонний транспорт обязан
объявить его явно.

| Транспорт | Вход | Выход |
|---|---|---|
| HTTP | `value`, `stream`, `multipart` | `value`, `stream`, `events` |
| CLI | `value`, `stream` | `value`, `stream` |
| Шина/порты (V1) | `value` | `value` |

Богатство объявляется в **контракте**, а согласуется проверкой биндинга на
сборке: декларация, чья форма не входит в способности её транспорта, падает
**до приёма запросов** — и на фазе ASSEMBLE под `App`, и в `serve` на
standalone-пути. Проверка одна на оба пути, и текст ошибки называет ручку,
транспорт, слот и форму со списком поддерживаемых.
Связать декларацию и транспорт типами было бы можно только протащив тип
транспорта в декларацию — это прямо противоречит «pipeline и хендлер
транспорт-слепые», поэтому здесь проверка на графе, а не церемония в типах.

## 2. Приём input: bind-карта и strict-приём

Как единая `input`-схема раскладывается по частям запроса, определяет
**bind-карта** декларации ([endpoints.md](./endpoints.md)): транспорт
карту только читает — считает её конструктор декларации. Payload
собирается **только из канонических мест** с фиксированным приоритетом
`path > пометка > остальное`: поле не в том месте не попадает в payload и
проваливает обычную валидацию. Merge «отовсюду» не существует, как и
ошибок конфликта источников. Query-массивы: повтор ключа → массив;
`query({ multiple: true })` — массив и при одном вхождении.

Тело запроса читается **только когда его требует карта** (источник
«остальное» — body, есть `body()`-пометка или взведён `rawBody`): у `GET`
без пометок тело не буферизуется вовсе. Парсинг тела управляется формой
io-декларации (значение / `stream` / `events` / `multipart`), а не
отдельным route-конфигом.

## 3. Этаж сантехники

Статика, catch-all, CORS, сжатие, редиректы, wildcard-подписки шины — **не
endpoint'ы**: это конфиг/плагины транспорта, без схем и контрактов. Escape
hatch для сырых случаев живёт на этом этаже — параллельной модели деклараций
нет ([endpoints.md](./endpoints.md), онтология).

## 4. HTTP (`@nestling/transport.http`)

- **Роутинг** — find-my-way, паттерны из деклараций (`method` + `path`
  с параметрами).
- **Парсинг по io-декларации**: JSON-тело; NDJSON — входной стрим;
  multipart — busboy, файлы отдаются хендлеру стримами
  (`FilePart { field, filename, mime, stream }`), лимиты (`upload({...})`)
  применяются **во время** парсинга, без буферизации; `rawBody: true` —
  байты в типизированный стартовый контекст одним чтением (значение
  парсится из тех же байтов), несовместим с потоковыми и multipart-формами.
- **Стриминг ответа**: `stream` → NDJSON (`application/x-ndjson`, chunked);
  `events` → SSE (`text/event-stream`, `no-cache`, heartbeat-комментарии,
  `id:`/`event:` из секции `sse` декларации, приём `Last-Event-ID`).
  Mid-stream ошибка: NDJSON — обрыв соединения, SSE — кадр `event: error`
  с телом отказа и закрытие; в обоих случаях исход `failed` в `finally`
  ([streaming.md](./streaming.md)).
- **Hardening**: лимит тела `maxBodySize` (раннее прерывание → `413`);
  типизированные ошибки входа → `400` (не `500`); настраиваемые таймауты
  `node:http`; graceful `close()` с дренажом; детали необработанных
  500-ошибок скрыты по умолчанию (`exposeErrorDetails`). Ответ на ошибку
  валидации — стандартные `issues` ([schemas.md](./schemas.md)).
- Порт и адрес — из конфиг-секции транспорта (`HTTP_PORT`, `HTTP_HOST`), не
  из литералов в корне; приоритет: явные опции фабрики > конфиг > дефолт.
  Фактический адрес после go-live — `address()` (`null` до `serve` и после
  `close()`); аргументов у `serve`, кроме `dispatch` и `signal`, нет.

## 5. CLI (`@nestling/transport.cli`)

Команды вместо маршрутов: `pattern` — имя команды. Что значит «эфир» для
командной строки, решает режим `serve`: `'argv'` — single-shot по аргументам
процесса, `'repl'` — чтение команд из stdin до `exit`. Обе ветки исполняют
ручку через `dispatch.call`; `execute({ command, args, options })` остаётся
публичной точкой single-shot для корня и тестов. Сбор недостающего input по
схеме — политика биндинга `missing: 'prompt'`
([endpoints.md](./endpoints.md), §6). Stdin — входной стрим: `stream(T)`
читает NDJSON-строки, `stream('binary')` — чанки как есть; потоковый выход
пишется в stdout тем же NDJSON. `events` и `multipart` CLI не умеет: у
команды нет открытого соединения, дисконнект которого был бы нормальным
завершением, а файлы приходят путями в аргументах.

## 6. Шина (`@nestling/ports`)

`InProcessBus` — транспорт с двумя способностями: входящей (`ITransport`,
маршруты реализаций контрактов) и исходящей (`IMessageBus`, вызыватели).
Дихотомия «messaging vs transports» ложная, поэтому отдельной сущности
«транспорт шины» рядом с шиной не существует.

Отличий от прочих транспортов ровно два. Первое: маршруты подписываются
**на фазе WIRE**, а не в `serve` — `@OnStart` уже вправе звать порт, а
go-live транспортов идёт после `@OnStart`; `serve` остаётся точкой, где
сигнал приложения связывается с каналом остановки шины. Второе: в корне
in-proc шина не перечисляется — её регистрирует kernel-модуль портов, и в
графе она появляется только там, где есть хоть одна реализация контракта
**или** где корень поставил транспорт шины сам (§7).

Способности по формам io — только `value` в обе стороны: контракт со
`stream`/`events` отвергается на ASSEMBLE существующей проверкой форм.
Подробности — [contracts.md](./contracts.md).

Шина объявляет **значением** две свои способности: `remote` (доставляет ли
за пределы процесса) и `durable` (умеет ли долговечную доставку). Первая —
вход биндинга вызывателей ([contracts.md](./contracts.md) §3), вторая —
основание видимой деградации: приложение с `durable`-контрактами на шине,
которая долговечность не умеет, стартует, но печатает на go-live строку с
перечнем контрактов, обслуживаемых недолговечно. У `InProcessBus` обе
способности ложны.

## 7. NATS (`@nestling/transport.nats`)

`NatsBus` — то же одно значение с двумя способностями, что и in-proc шина,
и **под тем же токеном**: `nats()` это обычный транспорт-провайдер в
`transports:` корня. Когда корень его поставил, kernel-модуль портов свою
реализацию не регистрирует — шина в приложении ровно одна, и брокер не
«добавляется» к in-proc шине, а является ею. Ни одна декларация
`implement(...)`, ни один контракт и ни один call-site при подключении не
меняются: это и есть L4 из [composition.md](./composition.md).

**Адресация.** Subject — имя контракта (при заданном `NATS_SUBJECT_PREFIX`
с префиксом); группа доставки — та же карта, что считает in-proc шина:
`owner:<subject>` у `request`/`command`, имя подписчика у `event`.
Добавление реплики не требует правки конфигурации.

**Фазы** у брокера разъезжаются точнее, чем у темы в куче: соединение
захватывается на INIT (это ресурс), `attach(dispatch)` на WIRE запоминает
маршруты и проверяет формы io, подписки заводятся в `serve` — **после**
`@OnStart`, поэтому входящее сообщение не застаёт незавершённый `@OnStart`;
SHUTDOWN дренажит, возвращая неподтверждённые durable-сообщения в поток.

**Провод.** Тело кодируется кодеком (JSON по умолчанию, заменяем опцией
фабрики), конверт едет headers'ами: относительный `timeoutMs`,
`idempotencyKey`, провозимый контекст (`Nl-Ctx`, JSON-объект целиком — имена
заголовков канонизируются брокером, и ключ переменной в имени их не
переживает). Ответ req-reply — `ResponseContext` тем же кодеком, поэтому
ре-гидрация задекларированного `Fail` по коду работает по проводу той же
процедурой, что локально.

**Потолок ожидания.** Брокерский запрос не бывает бесконечным: вызов без
`meta.deadline` ограничен `NATS_REQUEST_TIMEOUT` (30 с по умолчанию), с
бюджетом — `min(остаток, потолок)`. Это не дефолтный **бюджет**: бюджет
свойство вызова и наследуется вглубь, потолок — свойство провода, как
таймаут сокета у HTTP-сервера. Разница видна в тексте отказа.

**Долговечность.** `durable: true` объявляется контрактом (только
`command`/`event`), и NATS обслуживает такие subject'ы через JetStream:
поток, выведенный из subject'а, durable-потребитель, выведенный из группы,
`ack` по факту решения (успех и задекларированный `Fail` одинаково),
повторная доставка там, где решения не получилось. Существующий поток,
покрывающий subject, принимается как есть; поток с тем же именем и
конфликтующим составом subject'ов — fail-fast.

Вендорская специфика (wildcard, ack, KV, ordered consumers) не протекает ни
в `IMessageBus`, ни в контрактный API — ядро знает только интерфейс
([contracts.md](./contracts.md)). Сантехника выражается тем же глаголом
подписки: wildcard-аудитор пишется инжектом `MessageBus$` и вызовом
`subscribe('orders.>', …)` в `@OnStart`, третьего понятия деклараций для
этого не вводится. Wildcard при этом — брокерская способность: in-proc шина
трактует subject буквально.

Клиент брокера изолирован узким коннектором (`connect` — опция фабрики), а
in-memory двойник брокера экспортируется по конвенции `./testing`: тесты
приложения и пакета зелены без сети, а совместимость с настоящим брокером
проверяет отдельный интеграционный прогон.
