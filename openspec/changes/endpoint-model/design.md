## Context

Сегодня декларация endpoint'а существует в двух формах, сходящихся к одному
рантайм-представлению:

- **Классовая** — `@Injectable([deps]) @HttpEndpoint(method, path, opts)
  class X implements IEndpoint`. Декоратор пишет метаданные в
  `Symbol.for('nestling:handler')` на конструкторе; `App` резолвит инстанс из
  контейнера и передаёт транспорту `{ ...metadata, pipeline, handle:
  instance.handle.bind(instance) }`. `makeAppModule` подмешивает
  endpoint-классы в `providers`, чтобы контейнер их инстанцировал.
- **Функциональная** — `makeEndpoint({ transport, pattern, input, output,
  pipeline, handle })` (identity-функция), принимается только напрямую
  транспортом (`HttpTransport.route`, `CliTransport.endpoint`); под `App`
  не работает, потому что `AppModule.endpoints` типизирован как
  `Constructor<IEndpoint<any, any, any>>[]`.

Обе формы дают `EndpointDefinition<I, O, P>` — ровно то, что исполняет
транспорт. Разница целиком в способе доставки метаданных и в том, откуда
берётся `handle`.

Change #8 (`endpoint-discovery`, заархивирован) уже убрал глобальный реестр:
дискавери идёт обходом дерева модулей (`discoverEndpoints(modules)` — чистая
функция), декоратор остался чистым носителем метаданных. Это оставило
классовый путь без единственного, что его держало, и сделало замену
конструктора на значение локальной правкой дискавери.

Целевое состояние уже описано в `docs/design/endpoints.md` (три этажа,
per-transport конструкторы, `deps` + три формы `handle`,
standalone-гарантия). Этот change приводит к нему код.

Ограничения площадки: TS 5.7 strict, ESM, **стандартные ES-декораторы**
(параметр-декораторов нет — инъекция всегда явным массивом токенов),
Standard Schema без интроспекции ключей, zod — peer/dev.

## Goals / Non-Goals

**Goals:**

- Одна форма декларации — значение, созданное конструктором своего
  транспорта (`httpEndpoint`, `cliEndpoint`); `endpoints:` модуля принимает
  значения.
- `deps` + три формы `handle` (функция / каррированная фабрика /
  класс-хендлер), резолвимые контейнером на старте `App`.
- Standalone-гарантия в типах: транспорт напрямую принимает только deps-free
  декларацию.
- Удаление `@Endpoint`/`@HttpEndpoint`/`IEndpoint`/`EndpointMetadata` и
  остатков реестра; ноль метаданных на классах.
- Типизированный транспортный словарь: `path` — литерал, path-параметры
  извлекаются на уровне типов; конструктор — единственная точка, куда
  `input-bind` внесёт bind-карту.
- Примеры и гайды переведены; `yarn verify` и `yarn docs:audit` зелёные.

**Non-Goals:**

- `makeContract`/`implement` и порты (change `ports`); онтология «контракт
  первичен» здесь только фиксируется в доках.
- Bind-карта, strict-приём, `query()`, `rawBody` (change `input-bind`).
  `mergePayload`/`PayloadConflictError` не трогаются.
- Транспорт токеном и endpoint как узел графа с синтетическим id (change
  `features`): транспорт по-прежнему адресуется строкой, `deps` резолвятся
  контейнером в той же точке старта, где раньше резолвились endpoint-классы.
- `errors:` в словаре (change `error-model`), формы io (change
  `streaming-v2`), CLI-политика `missing: 'prompt'`.
- Изменение `@Injectable`, провайдеров и классов-юнитов пайплайна
  (`pipeline-unit-forms` не меняется).

## Decisions

### D1. `EndpointDefinition` получает четвёртый параметр — неразрешённые зависимости

```typescript
interface EndpointDefinition<I, O, P, TNeeds = never> { … }
```

Симметрично `Pipeline<TReq, TAcc, TNeeds>`: `TNeeds = never` ⇔ декларация
исполнима. Транспорты сужают приём до `EndpointDefinition<I, O, P, never>` —
той же техникой, которой уже пользуется `pipeline?: Pipeline<AnyInput, P,
never>` в текущем `EndpointDefinition`. Standalone-гарантия получается
бесплатно и одинаково выглядит для пайплайна и для хендлера.

**Уточнено на реализации:** `TNeeds` накапливает не только зависимости
хендлера, но и **классы-юниты пайплайна**. Причина: раньше «пайплайн с
классами-юнитами» и «исполнимый пайплайн» различались двумя типами
(`EndpointMetadata.pipeline: Pipeline<…, unknown>` под `App` против
`EndpointDefinition.pipeline: Pipeline<…, never>` для транспорта). После
слияния метаданных и декларации в одно значение это различие негде хранить,
кроме `TNeeds`. Без него `server.route(декларация с .pre(SomeClass))`
компилировался бы и падал в рантайме — регресс существующей
compile-time-гарантии.

*Альтернатива — отдельный тип `UnresolvedEndpoint`:* два имени вместо
одного параметра, каждое место приёма пришлось бы описывать дважды;
асимметрия с пайплайном.

### D2. Три упорядоченные перегрузки конструктора вместо условного типа

```typescript
// 1) без зависимостей
httpEndpoint({ method, path, …, handle: (input, meta) => … })
  → EndpointDefinition<I, O, P, never>

// 2) каррированная фабрика
httpEndpoint({ …, deps: [A, IToken], handle: (a, t) => (input, meta) => … })
  → EndpointDefinition<I, O, P, A | IToken>

// 3) класс-хендлер
httpEndpoint({ …, handle: CreateOrderHandler })
  → EndpointDefinition<I, O, P, typeof CreateOrderHandler>
```

Формы различимы по типу `handle` без чтения `deps`: голая функция
возвращает `Output`, каррированная — функцию, класс — конструктор.
Порядок перегрузок (функция → каррированная → класс) фиксирован: TS берёт
первую подходящую, а самый частый случай должен диагностироваться первым.
Типы зависимостей разворачиваются существующим
`UnwrapInjectionTokens<D>` из `@nestling/container` — тем же, что уже
обслуживает `@Injectable`.

*Альтернатива — одна сигнатура с условным типом по наличию `deps`:*
при несовпадении схемы и хендлера TS печатает трассировку по всей условной
цепочке. Перегрузки дают привязку ошибки к ближайшей сигнатуре. Бюджет
на читаемость диагностик (литерал `__error`, снапшот-тесты) — отдельный
change `pipeline-type-dx` (#23), закрывающий это breaking-окно; здесь
фиксируется только порядок перегрузок и позитивные type-тесты.

### D3. Гашение зависимостей — метод `resolve` на значении декларации

```typescript
declaration.resolve(resolver)              // (token) => unknown — форма App
declaration.resolve([svc, logger])         // позиционные инстансы — форма ideas
  → EndpointDefinition<I, O, P, never>
```

Две перегрузки одного метода, различимые в рантайме (`Array.isArray`).
Резолвер — единственная форма, работающая для класс-хендлера (класс надо
достать из контейнера); позиционный массив — для каррированной формы вне
контейнера, как записано в ideas «[2026-07-13] Endpoint-декларации», п. 7.
`resolve` возвращает **новое значение**, исходная декларация неизменна —
одну и ту же декларацию можно резолвить разными наборами (тесты).

**Уточнено на реализации:** шаг один, а не два. Раз `TNeeds` накрывает и
классы-юниты пайплайна (D1), `resolve(resolver)` обязан гасить и их —
иначе он возвращал бы `TNeeds = never` при несвязанном пайплайне, то есть
врал бы. Внутри `resolve` по-прежнему вызывается тот же `pipeline.bind` —
механизм не меняется, меняется точка вызова. `App` на старте делает для
каждой обнаруженной декларации ровно один шаг —
`endpoint.resolve(resolver)` — и передаёт транспорту deps-free значение.
Резолвер `App` один на все три источника (токен `deps`, класс-хендлер,
класс-юнит): для автора это одна и та же незарегистрированная зависимость,
и текст ошибки одинаково называет её, паттерн ручки и модуль-объявитель.

Позиционная форма `resolve([...])` классы-юниты материализовать не может
(инстансы позиционно соответствуют `deps`, а не юнитам) — такая попытка
даёт ошибку с именем юнита и подсказкой перейти на резолвер-форму. То же
для класс-хендлера.

*Альтернатива — резолв внутри транспорта:* транспорт получил бы знание о
контейнере, а standalone-путь — обязательный контейнер; ровно та связка,
которую снимает standalone-гарантия.

### D4. Класс-хендлер регистрируется в `providers:` явно

`makeAppModule` перестаёт что-либо подмешивать в `providers`. Класс,
переданный в `handle`, — обычный `@Injectable`-класс и регистрируется как
любой другой провайдер. Если он не резолвится — ошибка старта, называющая
класс, паттерн ручки и модуль-объявитель.

Обоснование: токены в `deps` пользователь регистрирует сам — авторегистрация
класс-формы дала бы асимметрию «класс волшебный, токен нет»; и это ровно та
неявность (`endpoints` → `providers`), которую снимает этот change.

*Альтернатива — `makeAppModule` обходит `endpoints:` и добавляет
класс-хендлеры в `providers`:* короче на строку в модуле, но воскрешает
неявную регистрацию и расходится с обработкой `deps`.

### D5. Идентичность декларации — symbol-бренд, проверяемый дискавери

`makeEndpoint` ставит на возвращаемое значение неперечислимый
`Symbol.for('nestling:endpoint')`. Дискавери проверяет бренд у каждого
элемента `endpoints:` и падает с указанием модуля и позиции в массиве.
Это замена ушедшей проверки «класс без метаданных эндпоинта»: без бренда
опечатка (положили сервис вместо декларации) всплыла бы как `undefined`
в рантайме транспорта.

Проверка «класс с метаданными эндпоинта объявлен провайдером, но не в
`endpoints:`» (`assertEndpointsDeclared`) удаляется: метаданных на классах
больше нет, отличить «забытый endpoint-класс» от обычного провайдера нечем.

### D6. Идентичность ручки в диагностике — `pattern`, не имя класса

Из метаданных уходит `className`. Все тексты ошибок старта переходят на
`pattern` (`POST /api/users`) плюс имя модуля-объявителя. Паттерн уникален
в пределах транспорта и говорит читателю больше, чем имя класса; для
класс-хендлера имя класса добавляется как уточнение.

### D7. Транспортный словарь: `path` — литерал, path-параметры на уровне типов

`httpEndpoint` генерик по `Path extends string`; экспортируется
`PathParams<Path>` — union имён `:param`-сегментов шаблона. В этом change
он фиксируется type-тестами и становится точкой, из которой `input-bind`
построит правило «имя поля совпало с path-параметром → путь».

Рантайм-проверки конструктора ограничены тем, что проверяемо без
интроспекции схемы (Standard Schema ключей не отдаёт): непустой `path`,
`path` начинается с `/`, нет повторяющихся имён path-параметров, непустое
имя команды для `cliEndpoint`. Проверка «path-параметр без поля в схеме»
требует bind-карты и приезжает с `input-bind`.

Сборка payload (`mergePayload`) не меняется — иначе этот change съел бы
предмет следующего.

### D8. `makeEndpoint` остаётся kernel-примитивом

Вся машинерия (`deps`, нормализация трёх форм `handle`, `resolve`, бренд)
живёт в `@nestling/pipeline` у `makeEndpoint`; `httpEndpoint` и
`cliEndpoint` — тонкие обёртки, добавляющие транспортный словарь и
`transport`/`pattern`. Один рантайм на все транспорты, включая будущие.
`makeEndpoint` остаётся в экспортах, но из пользовательского канона доков
уходит — так же, как он описан в `docs/design/endpoints.md` §2.

## Risks / Trade-offs

- **Диагностика перегрузок `handle` при опечатке в схеме** → порядок
  перегрузок фиксирован (частый случай первым), добавляются позитивные
  type-тесты на все три формы; читаемость сообщений — предмет
  `pipeline-type-dx` (#23) в этом же breaking-окне.
- **Новое трение: класс-хендлер надо руками положить в `providers`** →
  ошибка старта называет класс, паттерн и модуль и предлагает починку;
  переход показан в README `@nestling/app` и в переведённом гайде
  `http-app-di.md`.
- **Массовая правка примеров (9 ручек в `examples.app-with-http` плюс два
  standalone-примера)** → примеры переводятся целиком, регресс ловят
  существующие интеграционные тесты транспортов и `yarn verify`.
- **Значение вместо класса ослабляет статическую защиту содержимого
  `endpoints:`** → symbol-бренд (D5) + ошибка старта с позицией в массиве.
- **Часть удаляемого API (`@HttpEndpoint`) — самая узнаваемая для
  приходящих с NestJS** → сознательная цена, зафиксированная в ideas
  «Один канонический стиль деклараций»; смягчение — класс-хендлер
  сохраняет привычную структуру «конструктор + метод `handle`».
- **`assertEndpointsDeclared` уходит — «объявил ручку, забыл добавить в
  `endpoints:`» перестаёт ловиться** → в новой модели такая декларация
  просто неиспользуемое значение, и это ловит `noUnusedLocals`/линт на
  неэкспортированном значении; для экспортированных — предмет policy-check
  (#28).

## Migration Plan

Порядок работ внутри change'а (каждый шаг оставляет репозиторий
собираемым):

1. `@nestling/pipeline` — `EndpointDefinition<I, O, P, TNeeds>`, `deps`,
   нормализация форм `handle`, `resolve`, бренд; удаление `Endpoint`,
   `getEndpointMetadata`, `EndpointMetadata`, `IEndpoint`.
2. `@nestling/transport` — `ITransport.endpoint()` сужается до deps-free.
3. `@nestling/transport.http` — `httpEndpoint` + `PathParams`; удаление
   `HttpEndpoint`, `HttpEndpointOptions`, `HttpEndpointMetadata`,
   `getHttpEndpointMetadata`, `makeHttpEndpoint`; `route` сужается.
4. `@nestling/transport.cli` — `cliEndpoint`.
5. `@nestling/app` — `AppModule.endpoints` как список деклараций,
   `makeAppModule` без подмешивания в `providers`, дискавери на значениях,
   `#registerEndpoints` через `resolve`; удаление `assertEndpointsDeclared`.
6. Примеры: `examples.app-with-http`, `examples.simple-http-server`,
   `examples.simple-cli`.
7. Доки: сверка `design/endpoints.md` с реализацией, правки
   `design/transports.md` и `design/composition.md`, запись в
   `decisions/ideas.md` о расхождениях (если появятся), перевод трёх
   гайдов с новой датой в плашке, README пакетов, статус в `roadmap.md`.

Откат — ветка `change/endpoint-model` целиком; промежуточного режима
совместимости (оба стиля одновременно) нет намеренно: он и есть та цена,
которую change убирает.

## Open Questions

- **Имена конструкторов** — `httpEndpoint`/`cliEndpoint` (как в
  `docs/design/endpoints.md`) против `makeHttpEndpoint`/`makeCliEndpoint`
  (конвенция `make*` из записи «Один канонический стиль»). Принято
  `httpEndpoint` — за design-доком; конвенция `make*` остаётся за
  kernel-примитивами и транспорт-нейтральными конструкторами.
- **Позиционная форма `resolve([...])` для класс-хендлера** — типами не
  выражается осмысленно (у класса свои `@Injectable`-deps). В V1 доступна
  только резолвер-форма; если кейс всплывёт — аддитивно.
- **`name:`/operationId в словаре** — не заводится до `contracts`/`openapi`,
  чтобы не плодить второй источник идентичности рядом с `pattern`.
