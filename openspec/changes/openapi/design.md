## Context

Всё, из чего состоит операция, уже лежит на значении-декларации:

| Что | Где лежит сейчас | Кто это положил |
|---|---|---|
| метод, шаблон пути, размещение полей | `endpoint.binding` — плоская `HttpBinding` (`fields` + `rest`) | #21 `input-bind`, #22 `contract-clients` |
| формы io и их media types | `input`/`output` + `describeForm`/`mediaTypeOf` | #6 `streaming-v2` |
| объявленные отказы и их статусы | `errors: [defineFail(...)]`, у каждого `code`/`status`/`schema` | #15 `error-model` |
| состав приложения | `discoverEndpoints(modules)` по дереву **выбранных** фич | #8 `endpoint-discovery` |
| перевод листовой схемы в JSON Schema | `SchemaDocConverter` + `pickConverter` в схемном слое | #19, #26 |
| перевод статуса в код провода | `STATUS_MAP` в `@nestling/transport.http` | #15 |

Не хватает трёх вещей, и ровно они составляют этот change: (1) кода, который
всё перечисленное складывает в документ; (2) способа satellite-модулю
увидеть дискавери; (3) слота для того, чего в схемах нет в принципе —
`summary`, `tags`, успешного статуса.

Ограничения, которые нельзя обойти:

- **Интроспекции у Standard Schema нет.** Единственный способ узнать
  структуру — конвертер вендора. Значит, генератор разбирает **JSON Schema
  на выходе конвертера**, а не вендорскую схему, и «нет конвертера» —
  ситуация, которую надо диагностировать, а не обходить.
- **Список конвертеров — данные вызывающего.** Глобального реестра нет
  (`standard-schema-validation`), поэтому конвертеры приезжают опцией.
- **Строгость к отсутствию конвертера у потребителей разная** и уже
  зафиксирована таблицей в `design/schemas.md`: снапшот помечает лист
  непрозрачным, документация роняет boot.

## Goals / Non-Goals

**Goals:**

- Документ OpenAPI 3.1, выводимый **только** из значений-деклараций, без
  единого декоратора и без второго описания API рядом с кодом.
- Boot-time-гарантия: если документация включена, недокументируемых
  HTTP-ручек в приложении не существует — сборка падает раньше сокета.
- Ни одной зависимости от валидатора в генераторе; конвертер — явная
  зависимость, поставляемая отдельным пакетом.
- Escape hatch, работающий в **любой** схемной позиции, а не только в
  `input`/`output` верхнего уровня.
- Генератор пригоден и вне приложения: чистая функция, которую CI зовёт,
  чтобы положить `openapi.json` в артефакты.

**Non-Goals:**

- AsyncAPI, кодогенерация клиентов, Swagger UI в поставке, OpenAPI 3.0,
  интроспекция вендорских схем — см. Non-goals предложения.
- Полнота покрытия OpenAPI-спеки: `security`, `servers`, `externalDocs`
  принимаются опциями как есть и никак не выводятся; `callbacks`,
  `webhooks`, `links` не поддерживаются.

## Decisions

### 1. Три поверхности: чистая функция, модуль, конвертер

```typescript
// @nestling/openapi
buildOpenApiDocument(
  endpoints: readonly DocumentedEndpoint[],   // { endpoint, moduleName }
  options: OpenApiOptions,
): OpenApiDocument;                            // JSON-значение

openapi(options: OpenApiOptions & ServeOptions): Module;

// @nestling/openapi.zod
zodConverter(): SchemaDocConverter;
```

`DocumentedEndpoint` структурно совпадает с `DiscoveredEndpoint` дискавери и
с `PolicySubject` политик — тем же приёмом, которым `PolicySubject` уже
избегает конвертации между пакетами. Поэтому CI-сценарий пишется в три
строки и не поднимает приложение:

```typescript
const { endpoints } = discoverEndpoints(modulesOf(features));
writeFileSync('openapi.json', JSON.stringify(
  buildOpenApiDocument(endpoints, { info, converters: [zodConverter()] }),
));
```

**Почему функция, а не только модуль.** Документ нужен в двух режимах —
отдаваться ручкой и лежать файлом в артефактах сборки; общий у них
только первый.

**Отвергнуто:** метод `App.openapi()` — генератор попал бы в `@nestling/app`
вместе с зависимостью от HTTP-специфики; `check()`-подобный отчёт как
источник — отчёт уже потерял ссылки на декларации (он сериализуем), а
генератору нужны сами схемы.

### 2. Модуль-издатель строит документ на ASSEMBLE

`openapi(...)` — обычный параметризованный модуль (конвенция #13
`plugins`; `logging({ service })` в примере — тот же приём):

```typescript
makeAppModule({
  name: 'module:openapi',
  providers: [factoryProvider(OpenApiDocument$,
    (discovery) => buildOpenApiDocument(discovery.endpoints, options),
    [Discovery$])],
  endpoints: [httpEndpoint({
    method: 'GET', path: options.path ?? '/openapi.json',
    pipeline: options.pipeline, detached: options.detached,
    doc: { hidden: 'служебная ручка: сам документ' },
    deps: [OpenApiDocument$],
    handle: (document) => async () => Ok.of(document),
  })],
})
```

Boot-time-гарантия **не пишется отдельным кодом** — она следствие жадного
контейнера: `builder.build()` вызывает фабрику на фазе 1 ASSEMBLE, и любая
диагностика генератора роняет сборку там же, где падают все прочие
структурные сверки, до `@OnInit` и до `serve`. Ровно этот аргумент —
«жадный контейнер знает все endpoints на старте» — записан в
[ideas.md [2026-07-13]](../../../docs/decisions/ideas.md).

`pipeline`/`detached` в опциях обязательны как возможность: приложение
вправе требовать политикой слой на каждой HTTP-ручке
(`everyEndpoint(...).hasLayer(observability)`), а satellite-модуль про этот
слой ничего не знает. Без обеих опций подключение модуля роняло бы
`policies` — и это была бы наша проблема, а не пользователя.

**Отвергнуто:**

- **`Policy`-значение как носитель проверки** (`assemble({ policies: [documentable(...)] })`).
  Интерфейс `Policy` открыт, и проверка легла бы в него идеально, но
  документ нужен ещё и **как значение** ручке; политика, копящая результат
  в замыкание, — побочный эффект в предикате, и забытая политика давала бы
  пустой документ вместо ошибки.
- **Проверка на `@OnInit`** — фаза 2, после захвата ресурсов
  конструкторами; fail-fast на ASSEMBLE строго лучше и достаётся даром.

### 3. `Discovery$` — инжектируемая дискавери

`assemble` регистрирует результат `discoverEndpoints` провайдером-значением
под токеном `Discovery$` (`@nestling/app`). Значение то же самое, которое
`App` уже вычисляет до построения графа; регистрация value-провайдера ничего
не стоит.

**Почему без него нельзя.** Модуль обязан видеть **выбранную** топологию: с
`select: 'users'` документ не должен описывать ручки невыбранных фич.
Единственное место, где эта топология известна, — `assemble`.

**Отвергнуто:**

- **Передавать модули/фичи аргументом** `openapi({ from: features, select })` —
  дублирование `select` в корне; разъезд двух списков даёт документ, не
  совпадающий с приложением, и заметить это нечем.
- **Перечислять документируемые декларации руками** — второе описание API,
  ровно то, от чего уходим.
- **Глобальный реестр деклараций** — это тот самый протекающий `Set`,
  который убрал change #8.

Значение отдаётся read-only (замороженные списки): инжектируемая дискавери —
поверхность интроспекции, а не точка расширения; править состав приложения
из графа нельзя.

### 4. Слот `doc:` — единственный источник неcхемных метаданных

```typescript
interface DeclarationDoc {
  summary?: string;
  description?: string;
  tags?: readonly string[];
  deprecated?: boolean;
  /** Статус успешного ответа; по умолчанию OK (NO_CONTENT без `output`) */
  status?: SuccessStatus;
  /** Ручка не попадает в документ — только с причиной */
  hidden?: string;
}
```

Слот живёт **на транспорт-нейтральном уровне** (`EndpointOptions` ядра и
`ContractSpec`), ядро его переносит и не интерпретирует — как `binding`.
Формат-нейтральность обязательна: AsyncAPI будет читать тот же слот, и
`operationId`/`externalDocs` в нём поэтому нет.

- **`operationId` не объявляется, а выводится**: имя контракта, если
  декларация служит контракту, иначе детерминированный слаг от метода и
  пути (`get_api_users_id`). Правило документируется; ручное имя не нужно,
  пока имя контракта уникально по построению.

  **Уточнено реализацией.** Первоначально здесь было написано
  `busBindingOf(endpoint)?.subject` — и это неверно для той единственной
  формы, ради которой правило заводилось: у HTTP-декларации,
  построенной контракт-формой, биндинг это **bind-карта**, а не bus-биндинг,
  и bus-биндинга у неё не бывает вовсе. Имя контракта поэтому едет на самой
  карте (`HttpBinding.contract`, заполняет только `makeContract`): карта —
  то же значение на контракте и на реализации, поэтому другого честного
  канала нет, а второе поле на декларации дублировало бы то, что уже есть в
  её адресе. Чтение bus-биндинга остаётся первым по порядку — оно ничего не
  стоит и покроет декларацию, которая однажды будет нести оба.
- **`tags` не выводятся из имени модуля.** Соблазн есть (атрибуция уже в
  дискавери), но это конвенция, притворяющаяся гарантией: имя модуля —
  `module:users`, и подрезать префикс значило бы угадывать. Нет `doc.tags` —
  нет тегов.
- **`hidden: '<причина>'`, а не `hidden: true`** — прямая калька с
  `detached` (#28): тотальный opt-out обязан быть читаем в diff'е. Скрытые
  ручки перечисляются в `x-nestling-hidden`-расширении документа? Нет —
  документ отдаётся наружу; список печатает модуль на старте, рядом со
  списком detached-ручек.
- **В контракт-форме `doc` принадлежит контракту** — добавляется в
  `CONTRACT_OWNED` наравне с `input`/`output`/`errors`. Документация
  операции — часть интерфейса операции, а не её реализации, и внешний
  потребитель контракта видит её из того же импорта.

### 5. `jsonSchema(schema, json)` — аннотация схемного слоя, не поле декларации

```typescript
input: z.object({ payload: jsonSchema(ExoticSchema, { type: 'object' }) })
```

Значение-аннотация: `~standard` наследуется, поэтому валидируется
аннотированная схема ровно как исходная и годится в любую схемную позицию.
Диспетчер (`pickConverter` и общий описатель листа) читает аннотацию
**раньше** конвертера.

**Почему не поле `doc.jsonSchema` на декларации** (как буквально сказано в
записи журнала): override нужен не только верхнему уровню `input`/`output`,
но и `details` конкретного отказа, и полям `multipart` — поле на декларации
пришлось бы превращать в путь внутрь дерева форм. Аннотация рядом со схемой
попадает точно туда, где проблема, и заодно снимает непрозрачность листа
для снапшота контрактов (#26) — второго потребителя того же диспетчера.

**Отвергнуто:** `WeakMap`-реестр аннотаций (скрытое состояние вместо
значения; две копии пакета — два реестра) и мутация переданной схемы
(`defineProperty` на чужом значении).

### 6. Правила маппинга

Одна операция на пару `(метод, путь)` из bind-карты; `:param` → `{param}`.

**Параметры и тело — из одной конвертации.** `input` конвертируется в
JSON Schema **один раз**, затем раскладывается по bind-карте:

| Источник | Куда | Как считается `required` |
|---|---|---|
| `fields[name].in === 'path'` | `parameters[in: path]` | всегда `true` |
| `fields[name].in === 'query'` | `parameters[in: query]`, `style: form`, `explode: true` | из `required[]` конвертированной схемы |
| остальные поля, `rest === 'query'` | `parameters[in: query]` | оттуда же |
| остальные поля, `rest === 'body'` | `requestBody` — та же схема минус вынесенные поля (из `properties` и из `required`) | схема как есть |

Схема параметра — `properties[name]` конвертированной схемы. Отсюда две
диагностики, которых раньше не было нигде:

- **path-параметр, которого нет в схеме** — ошибка сборки. Change #21 явным
  образом отложил эту проверку «до `@nestling/openapi`, где вендор-конвертер
  структуру схемы уже знает»; здесь она и появляется;
- **`bind`-пометка на несуществующем поле** — та же ошибка (типы её ловят,
  но не в JS-потребителе и не при непрозрачном `input`).

Если конвертированный `input` — не объект с `properties`, а карта требует
разложить поля, это ошибка сборки с тем же текстом, что и рантайм-правило
`assertBindable` («в payload нечего класть»).

**Media types — из формы**, штатным `mediaTypeOf` (одно правило на
транспорт, клиента и документацию):

| Форма | Запрос | Ответ |
|---|---|---|
| значение | `application/json` | `application/json` |
| `stream(T)` | `application/x-ndjson` | `application/x-ndjson`, схема — **элемент** |
| `events(T)` | — | `text/event-stream`, схема элемента в `description` |
| `multipart({fields, files})` | `multipart/form-data`: поля из `fields`, файлы — `type: string, format: binary` (массив при `multiple`), `contentMediaType` из `upload({ mime })` | — |
| примитив `binary`/`text` | `application/octet-stream` / `text/plain` | то же |
| `rawBody: true` | не меняет media type: тело парсится как обычно, сырые байты — деталь стартового контекста | — |

**Ответы:**

- успех: код из `doc.status` (по умолчанию `200`; `204` без `output`),
  переведённый тем же `STATUS_MAP`, что и в бою;
- каждый `errors[i]` → код своего `status`; тело — **то, что реально пишет
  транспорт**: `{ error: string, code: const '<CODE>', details?: <схема> }`;
  несколько отказов на одном коде → `oneOf`;
- `400` добавляется автоматически, если у ручки есть схема входа: граница
  отвечает `VALIDATION_FAILED` с `issues` независимо от `errors:`;
- `default` → `UnknownError`: контракт границы это `E ∪ UnknownError`
  (#15), и документ обязан его отражать.

**Отвергнуто:** RFC 9457 `application/problem+json` — отложен
(`deferred.md`), документ описывает текущий формат провода, а не желаемый.

### 6a. Направление конвертации — добавлено реализацией

`SchemaDocConverter.toJsonSchema` получил необязательный второй параметр
`{ io?: 'input' | 'output' }`, и генератор его передаёт: `input` для тела
запроса, `output` для тела ответа и `details` отказов.

Найдено на первом же живом примере. `z.string().transform(Number)` (поиск
пользователей в `examples.app-with-http`) описывает **две** формы: строку на
проводе и число у хендлера. Штатный `z.toJSONSchema` без подсказки на такой
схеме просто бросает, а угадать за пользователя нельзя: тело запроса обязано
описываться первой формой, тело ответа — второй, и направление-слепой
конвертер всегда неправ про одно из них.

Параметр опционален с обеих сторон — конвертер одного аргумента остаётся
валидным конвертером, а снапшот контрактов, сравнивающий форму с самой
собой, подсказку не передаёт, — поэтому добавление аддитивно.

Заодно бросок конвертера перехватывается и превращается в обычную
диагностику с именем ручки и слота: без этого ошибка уезжала бы наружу без
координат, что для тотальной проверки неприемлемо.

### 7. Границы пакетов

`@nestling/openapi` зависит от `@nestling/contracts` (bind-карта, формы,
статусы), `@nestling/pipeline` (декларация, конвертеры), `@nestling/app`
(токен дискавери, `makeAppModule`) и `@nestling/transport.http`
(`httpEndpoint` для своей ручки и перевод статуса в код). Последняя
зависимость честная: генератор описывает **HTTP**-провод, и переписывать
`STATUS_MAP` копией значило бы завести второй источник истины. Поэтому из
транспорта наружу выносится `httpCodeOf(status)`, а карта остаётся там же,
где была.

Валидатора среди зависимостей нет ни одного — это проверяется тестом
границы импортов по образцу `contracts-package-boundary`.

**Уточнено реализацией:** обход **не спускается** в зависимости, и `node:*`
нарушением не считается. Причина в том, что транзитивная формулировка была
бы ложной: `@nestling/transport.http` читает zod в своей конфиг-секции, то
есть в транзитивном замыкании генератора валидатор есть — и будет. Обещание,
которое можно держать честно, ровно одно: **сам генератор** валидатора не
импортирует и не объявляет. Оно и проверяется — двумя утверждениями: по
графу импортов собственных модулей `dist/` и по манифесту пакета
(`dependencies` + `peerDependencies`). Механизм обхода получил под это два
опциональных флага (`descend`, `allowNodeBuiltins`); поведение существующих
двух тестов не изменилось.

Аннотация `jsonSchema` при этом живёт не здесь, а в `@nestling/contracts`
(см. §5): ею объявлены схемы самого ядра, и автор контракта, импортируемого
во фронт, обязан иметь к ней доступ без серверных пакетов. Диспетчер,
читающий аннотацию, остался рядом с `SchemaDocConverter`.

## Risks / Trade-offs

- **Различия конвертеров вендоров** (`z.record`, discriminated unions,
  `default`) дают разный JSON Schema на «одинаковых» схемах → цена принята
  записью журнала; поставляем свой конвертер только для zod, остальные — по
  спросу, интерфейс публичный.
- **`doc.status` не проверяем**: хендлер, вернувший `Ok.created`, при
  `doc.status: 'OK'` даст документ, расходящийся с проводом → фиксируется
  открытым вопросом ниже; ослабление — дефолт совпадает с самым частым
  случаем, и расхождение видно в первом же вызове.
- **Аннотация `jsonSchema` наследует схему через прототип** — экзотический
  валидатор, чей `validate` завязан на `Object.getOwnPropertyNames(this)`,
  может повести себя иначе → тест на аннотированной zod- и valibot-схеме;
  при отказе запасной вариант — обёртка, копирующая `~standard` явно.
- **Документ строится на каждом старте** — стоимость конвертации всех схем
  на boot. Для сотен ручек это единицы миллисекунд, но при `openapi()` в
  корне цена платится всегда → опция «строить лениво» намеренно не
  заводится: ленивое построение убило бы boot-time-гарантию, ради которой
  всё и затевалось.
- **`Discovery$` расширяет публичную поверхность V1** после фиксации API
  волной 2 → аддитивно и мотивированно (satellite обязан видеть топологию);
  значение read-only, точкой расширения не является.

## Migration Plan

Ломать нечего: все поля опциональны, приложение без `openapi()` в корне
собирается ровно как прежде. Порядок работ — снизу вверх: аннотация и слот
`doc` (ядро) → `Discovery$` → генератор → конвертер → модуль → пример и
гайд.
