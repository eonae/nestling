# Дизайн: адаптер к клиенту `nats`

## Context

Пакет `@nestlingjs/transport.nats` держит всё знание о клиенте брокера в
`connector.ts`. Там же объявлен `NatsLike` — перечень того, что транспорт
просит у брокера, и `defaultConnector`, который должен отдать реализацию
этого перечня:

```typescript
export const defaultConnector: NatsConnector = async ({ servers }) => {
  const { connect } = await import('nats');

  return (await connect({ servers: [...servers] })) as unknown as NatsLike;
};
```

Приведение через `unknown` компилятор не проверяет. Прогон против `nats:2`
уронил шесть тестов из семи. Расхождения перечислены в
[ideas.md [2026-09-12]](../../../docs/decisions/ideas.md) «Коннектор к
живому клиенту `nats`»; ниже они сверены с типами `nats@2.29.3`:

| Что просит `NatsLike` | Что даёт `nats@2.29.3` |
| --- | --- |
| `connection.headers()` | `headers()` — функция модуля; у `NatsConnection` такого метода нет |
| `jetstream().subscribe(subject, { stream, durable })` | `subscribe(subject, ConsumerOptsBuilder \| Partial<ConsumerOpts>)`, помечен `@deprecated` |
| `jsm.streams.add(cfg) → StreamConfig` | `add(cfg: Partial<StreamConfig>) → Promise<StreamInfo>` |
| `jsm.consumers.add(…) → ConsumerConfig` | `add(stream, cfg: Partial<ConsumerConfig>) → Promise<ConsumerInfo>` |
| `JsMsg.redeliveryCount`, `JsMsg.respond()` | `info.redeliveryCount`; `respond()` у `JsMsg` нет |

Шестое расхождение таблица не называет, а компилятор поймает:
`NatsConsumerConfigLike.ack_policy` объявлен строкой `'explicit'`, а
`ConsumerConfig.ack_policy` — значение перечисления `AckPolicy`.

Совпадают `publish`, `request`, `subscribe`, `jetstream()`,
`jetstreamManager()`, `drain()` и `closed()`, а также форма заголовков:
`MsgHdrs` несёт `get`, `set`, `has` и `keys`.

## Goals / Non-Goals

**Goals:**

- Расхождение между `NatsLike` и клиентом ловит компилятор, а не живой
  прогон.
- Живой прогон запускается одной командой и стоит на пути выпуска.
- `NatsLike` остаётся перечнем того, что транспорт просит у брокера.

**Non-Goals:**

- Переход на линию `@nats-io/*` (v3).
- Живой прогон в CI на каждом коммите.
- Изменение способностей транспорта: формы io, конверт вызова, окно
  дедупликации, отображение операции на subject.

## Decisions

### 1. Адаптер — функция `adapt` внутри `connector.ts`

`defaultConnector` соединяется с брокером и передаёт соединение в
`adapt(connection, headers)`, которая собирает `NatsLike` полем за полем.
Функция не экспортируется из пакета: она деталь умолчательного коннектора,
а не часть публичного API.

Каждое поле результата присваивается явно, поэтому расхождение в любой
сигнатуре становится ошибкой тайпчека. Приведений через `unknown` и `any`
в файле не остаётся.

**Альтернатива — оставить приведение, но сузить до `as NatsLike`.**
Компилятор проверил бы структурную совместимость, и часть расхождений
всплыла бы. Но `headers()` и `subscribe` требуют не проверки, а работы:
метода `headers` у соединения нет, и приведение любой формы его не создаст.

### 2. Заголовки — функцией модуля

`NatsLike.headers()` возвращает результат вызова `headers()`, который
берётся из того же динамического импорта, что и `connect`:

```typescript
const { connect, headers } = await import('nats');
```

`MsgHdrs` подходит под `NatsHeadersLike` структурно: `get(k, match?)`,
`set(k, v, match?)`, `has(k, match?)` и `keys(): string[]`. Обёртка
заголовкам не нужна — нужен только источник пустого набора.

### 3. Долговечная подписка — упрощённым API потребителей

`NatsJetStreamLike.subscribe(subject, { stream, durable })` исполняется
через `js.consumers.get(stream, durable)` и `consumer.consume()`.
Результат — `ConsumerMessages`, то есть `AsyncIterable<JsMsg>`; адаптер
оборачивает его генератором, который отдаёт `NatsJsMsgLike`.

Запись в `ideas.md` называла другой путь — `consumerOpts()`. Он не годится
по двум причинам. `js.subscribe` и `js.pullSubscribe` в `nats@2.29`
помечены `@deprecated` с указанием на `Consumer#consume()`. Кроме того,
`js.subscribe` — push-подписка, а она требует у потребителя
`deliver_subject`; транспорт создаёт потребителя из `durable_name`,
`ack_policy` и `filter_subject`, то есть pull-потребителя, и push-подписка
к нему не привяжется. Добавить `deliver_subject` значило бы протащить
механику доставки в `NatsConsumerConfigLike`.

Выбор дешевле и для будущего перехода: в линии `@nats-io/*` упрощённый API
потребителей — единственный.

**Альтернатива — `js.pullSubscribe` с ручным `pull`.** Тот же pull под
рукой, но с собственным циклом запросов и таймеров. `consume()` этот цикл
уже содержит.

### 4. `NatsJsMsgLike` перестаёт наследовать `NatsMsgLike`

Сейчас сообщение потока объявлено как `NatsMsgLike` плюс подтверждения,
поэтому граница требует от него `respond()`. Клиент такого метода не даёт,
а транспорт его на долговечном пути не зовёт: `respond` используется
только в доставке core-сообщений.

`NatsJsMsgLike` объявляет свой набор: `subject`, `data`, `headers`,
`redeliveryCount`, `ack`, `nak`, `term`. Это не подгонка границы под
клиента, а удаление глагола, которого у сообщения потока нет: адреса
ответа у него тоже нет.

`redeliveryCount` обёртка берёт из `msg.info.redeliveryCount`.

**Альтернатива — вернуть `respond()`, который всегда отвечает `false`.**
Граница обещала бы ответ там, где ответить некому.

### 5. Конфигурации разворачиваются из `*Info`

`streams.add` и `streams.info` возвращают `StreamInfo`, `consumers.add` —
`ConsumerInfo`. Адаптер возвращает `info.config`: он шире, чем
`NatsStreamConfigLike` и `NatsConsumerConfigLike`, и присваивается им
структурно.

`ack_policy` переводится в `AckPolicy.Explicit` на входе — перечисление
клиента за границу не выходит.

### 6. `nats` — peer-зависимость

Клиент переезжает из `dependencies` в `peerDependencies` плюс
`devDependencies`: тесты пакета его импортируют, а потребитель ставит
версию под свой брокер. Так уже сделано в `@nestlingjs/logging.pino` с
`pino`, и ровно это README пакета обещает читателю сегодня, расходясь с
манифестом.

### 7. Живой прогон — `compose.yaml` и `yarn test:live`

В корне репозитория появляется `compose.yaml` со службой `nats`: образ
`nats:2`, команда `-js`, порт 4222. Корневой скрипт `test:live` запускает
`node scripts/test-live.mjs`, который поднимает службу, ждёт порт, гоняет
тесты пакета с заданным `NATS_TEST_SERVERS`, останавливает службу и
возвращает код прогона.

Готовность ждёт скрипт, а не `healthcheck` службы: официальный образ
`nats:2` собран без оболочки, и команде проверки внутри контейнера
взяться неоткуда. Скрипт открывает TCP-соединение на 4222 в цикле с
потолком ожидания.

**Альтернатива — служба брокера в CI на каждом коммите.** Ловит
расхождение раньше и не требует ничего от человека, но удорожает каждую
сборку ветки. Выбор в пользу локального прогона сделан пользователем на
propose; воротами его делает шаг `RELEASING.md` перед подъёмом версии.

## Risks / Trade-offs

- **Ручной прогон можно пропустить** → шаг стоит в `RELEASING.md` первым в
  разделе «Выпуск», до подъёма версии, и назван в спеке `package-publication`
  требованием. Автоматической защиты у него нет — это цена выбранного
  варианта.
- **`consume()` не останавливается при закрытии транспорта** → `close()`
  дренирует соединение, и итератор потребителя обязан завершиться вместе с
  ним. Если живой прогон покажет зависший процесс, граница `subscribe`
  получит возвращаемый тип с `close()`, а транспорт — вызов в фазе
  остановки. Решается фактом прогона на apply.
- **Двойник и живой брокер разойдутся в деталях** → сценарии живого
  прогона повторяют сценарии двойника, и расхождение видно на том же
  наборе тестов.
- **Peer-зависимость ломает `pack:check`** → проверка ставит тарболы в
  проект вне репозитория; если импорт клиента там перестанет
  разрешаться, `nats` добавляется в зависимости проверочного проекта.

## Migration Plan

Публичное API пакета не меняется: адаптер живёт под `defaultConnector`, а
подстановка своего коннектора опцией `connect` работает как раньше.
Видимое изменение одно — клиент `nats` ставит потребитель, и README уже
описывает установку именно так.

Порядок работ: адаптер и граница сообщения потока, затем двойник под
суженную границу, затем прогон против живого брокера, затем `compose.yaml`
со скриптом и шаг выпуска.
