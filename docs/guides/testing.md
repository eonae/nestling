# Тестирование приложения: `assembleTest`, `.check()`, `./testing`

> Гайд по **текущему API**; сверено с кодом `examples.app-with-http` (2026-08-27).
> Раздел 4 сверен с тестом изоляции фичи в `examples.split-nats`.

Между юнитом и e2e была дыра: прогнать запрос через полный пайплайн, но без
сокета, было не через что. Её закрывает `@nestling/testing` — тестовый
composition root, который ведёт **то же самое** приложение по фазам 0–3 и
останавливается.

```typescript
import { assembleTest, unwrap, vars } from '@nestling/testing';

await using app = await assembleTest({
  features: [UsersFeature, OpsFeature, QuotasFeature],
  transports: [http({ port: 0 })],
  overrides: [[UsersRepository, inMemoryUsersRepo()]],
  config: vars({ HTTP_PORT: '0' }),
});

expect(unwrap(await app.call(GetUser, { id: '1' }))).toEqual({
  id: '1',
  name: 'Alice',
  email: 'alice@example.com',
});
```

## 1. Три уровня и граница между ними

| Уровень | Чем поднимается | Что проверяет | Чего не проверяет |
|---|---|---|---|
| **юнит** | `new UserService(logger, repo)` | доменную логику | ничего из фреймворка — у юнита нет импортов из `@nestling/*` |
| **app-тест** | `assembleTest({ … })` + `app.call` | сборку графа, **все слои пайплайна**, валидацию схем, страж границы, отказы с их `status`/`code` | провод: раскладку path/query/body, заголовки, сокет |
| **e2e** | `assemble({ … }).run()` + HTTP-клиент | всё вместе, включая провод | быстроту и изоляцию |

App-тест берёт готовый payload — транспортный биндинг он не выполняет
намеренно: сборка запроса из path/query/body проверяется e2e и юнит-тестами
bind-карты. Кадр запроса при этом честный, но пустой: слой видит
`raw.transport` и `raw.pattern` своей декларации, а `raw.attributes` — `{}`,
если тест не задал их через `options`.

## 2. Что происходит и чего не происходит

`assembleTest` проходит `0 BOOTSTRAP → 1 ASSEMBLE → 2 INIT → 3 WIRE`:

- **происходит**: резолв `select`, регистрация, дискавери, построение графа,
  все fail-fast'ы ASSEMBLE (транспорт под ручку, формы io, циклы),
  `@OnInit`, рождение `dispatch`;
- **не происходит**: `@OnStart`, `serve` (сокет не открывается), обработчики
  `SIGTERM`/`SIGINT`, печать состава сборки в stdout.

Отсюда следствие, которое стоит знать заранее: **ресурс, захваченный в
`@OnStart`, в app-тесте не захватывается**. Это цена фазовой модели, а не
дефект: `@OnStart` — хук go-live, а тестовый прогон в эфир не выходит. Всё,
что нужно тесту, захватывается в `@OnInit` — что фазовая модель и предписывает.

`assembleTest` асинхронна, поэтому канон записи — `await using app = await
assembleTest(…)`: `await using` ждёт dispose, а не инициализатор. Форма без
`using` тоже работает:

```typescript
let app: TestApp;
beforeEach(async () => { app = await assembleTest({ … }); });
afterEach(async () => { await app.close(); });   // повторный close() безопасен
```

## 3. `overrides` + прунинг

Подстановка — это замена узла графа **до инстанциации**, а не патчинг
модулей и не перехват `import`:

```typescript
overrides: [
  [UsersRepository, inMemoryUsersRepo()],       // пара «токен → фейк»
  familyOverride(ILogger, () => noopLogger),    // рецепт семейства целиком
  contextValue(RequestId, 'req-1'),             // ambient-переменная запроса
]
```

- пара типизирована: фейк, не совместимый с типом токена, — ошибка
  компиляции;
- override токена, которого нет в графе, — ошибка сборки. Переименовали
  провайдер — тест падает, а не мокает молча пустоту;
- два override'а одного токена — ошибка;
- строковой формы (`overrideByName('…')`) нет: мокаешь то, на что у теста
  есть ссылка;
- `contextValue(Var, value)` — тот же список: ридер ambient-переменной
  ([http-app-di.md](./http-app-di.md), «Ambient-контекст») — обычный узел
  графа, и подменяется он как обычный узел. Подставленное значение читается
  **без запроса**: сервис можно позвать напрямую, ALS для этого не нужен, а
  на `app.call` подмена сильнее того, что положил пайплайн. Не подменил —
  видишь боевую проекцию: внутри вызова значение слоя, вне вызова `peek()`
  даёт `undefined`.

Заменили узел — его осиротевшее поддерево выпадает из графа. В примере
`UsersRepository` был единственным потребителем `UsersStore`, поэтому
соединение не открывается вовсе:

```typescript
expect(app.pruned).toContain('UsersStore');
expect(app.get(UsersStore)).toBeNull();
```

Без `overrides` прунинг **тождественен**: `app.pruned` пуст, граф ровно тот
же, что в бою.

## 4. Фича без соседей: `stub(Contract, impl)` и `app.emit`

Фича, инжектящая `ChargeCard.port`, без соседа не собиралась бы вовсе:
рецепт вызывателя падает проверкой достижимости — «контракт заинжекчен, но
никто в этой сборке его не реализует и шина наружу не доставляет». Затаскивать
в тест соседнюю фичу целиком значило бы отменять модульный монолит, поэтому
шов другой — **фейк-вызыватель как значение**:

```typescript
// packages/examples.split-nats/src/isolated.spec.ts
await using app = await assembleTest({
  features: [OrdersFeature, QuotasFeature],
  select: 'orders',
  stubs: [
    stub(ClaimQuota, async (input) => ({ granted: input.amount })),
    stub(OrderPlaced, (input) => void placed.push(input)),
  ],
  overrides: [contextValue(TenantId, 'acme')],
});
```

`stub(C, impl)` возвращает пару «токен вызывателя → фейк»: `[C.port, …]` у
`request`-контракта и `[C.emitter, …]` у `command`/`event` — сторону выбирает
вид контракта, а не вызывающий. Пара едет полем `stubs:` наравне с обычными
парами «токен → значение»: отдельного поля под контрактные стабы нет.

Работает это на свойстве контейнера, а не на исключении для тестов: явный
провайдер члена семейства **опережает** рецепт, поэтому боевой
`buildPort`/`buildEmitter` для застабанного контракта не вызывается ни разу —
а значит и проверка достижимости не выполняется.

**Фейк валидируется схемами своего контракта при каждом вызове** — в этом вся
его ценность:

- вход разбирается `input`-формой: невалидный payload — `VALIDATION_FAILED`,
  и `impl` не вызывается;
- успешный результат разбирается `output`-формой: фейк, вернувший
  `{ grantedAmount: 1 }` вместо `{ granted: 1 }`, роняет тест на себе, а не
  на потребителе. Здесь стаб **строже** боевого co-located порта, и это
  осознанно: у боевого ответа позади pipeline реализации, у стаба его нет;
- отказ обязан входить в `errors:` контракта (∪ kernel-коды
  `VALIDATION_FAILED`, `UNKNOWN`, `DEADLINE_EXCEEDED`). Незадекларированный
  код — дефект теста, и стаб **бросает**, называя контракт, полученный код и
  список допустимых, вместо того чтобы тихо превратить его в `UnknownError`;
- не-`Fail` исключение из `impl` пробрасывается как есть: «фейк упал» не
  должно читаться как «сосед вернул `UNKNOWN`».

Эксплуатационный профиль тоже воспроизводится: исчерпанный `meta.deadline`
даёт `DEADLINE_EXCEEDED` **до** вызова фейка, а `emit` команды всегда несёт
`idempotencyKey` — переданный или отчеканенный стабом. Иначе тест на дедлайны
или на идемпотентность проходил бы со стабом и разъезжался с продом.

Call-site при этом тождествен боевому: значение стаба — `Port<C>` /
`Emitter<C>`, результат — `PortResult<C>`, а несовместимый фейк — ошибка
компиляции в точке `stub(...)`. Форма `impl` — обычный хендлер: голое
значение, `new Ok(value)` или объявленный отказ. Своего spy у стаба нет и не
будет — `jest.fn()` в позиции `impl` работает без единой строки поддержки.

### `app.emit` — драйвер снаружи внутрь

Стаб заменяет то, что приложение зовёт **наружу**. Обратное направление —
`app.emit(Contract, payload, meta?)`: он доставляет факт или команду **всем**
co-located подписчикам, каждому через его собственный полный пайплайн, ровно
как это сделал бы издатель.

```typescript
const [{ subscriber, response }] = await app.emit(PlaceOrder, {
  orderId: 'o-1',
  amount: 10,
});
```

- возвращаются ответы подписчиков с именем каждого
  (`{ subscriber, response }[]`), а не `Promise<void>` боевого эмиттера:
  издатель за обработку не отвечает, а тест отвечает ровно за неё, и
  «доставлено, а обработалось ли — неизвестно» превращает проверку в гонку.
  Ждать здесь безопасно — сокета нет, подписчики co-located;
- транспортные атрибуты кадра несут профиль вызова, включая `idempotencyKey`
  у вида `command`, — обработчик видит то же, что увидел бы в бою;
- ноль подписчиков у `event` — легальный broadcast и пустой список; у
  `command` — ошибка адресации с перечнем доступных subject'ов;
- `request`-контракт здесь — ошибка компиляции: у него не подписчики, а один
  владелец, отвечающий вызывающему;
- стаб эмиттера доставке не мешает: одно направление не отменяет другого.

## 5. Правило: мокаешь — проверь топологию

Прунинг делает граф теста уже боевого, а стаб — ещё и не тем по контрактам:
это их смысл и их цена. Цену компенсирует `.check()`: структурная проверка
на **честном** графе, без подстановок.

```typescript
import { checkTopologies } from '@nestling/testing';

await checkTopologies(
  { features: [UsersFeature, OpsFeature, QuotasFeature], transports: [http({ port: 0 })] },
  ['all', 'users', 'ops'],
);
```

`check()` гоняет фазы 0–1: конструкторы выполняются, `@OnInit` — нет, значит
ресурсы не захватываются, а каждая топология деплоя проверяется в CI без
деплоя. `checkTopologies` собирает **все** отказы и падает одним сообщением,
называя топологию для каждого; отчёты по успешным — обычное значение
(`features`, `endpoints`, `transports`), которое можно проверить ассертом.

Инварианты сборки едут сюда же: `spec` с полем `policies:` проверяется в
**каждой** топологии матрицы, поэтому нарушение, возникающее только на
подмножестве фич, ловится до деплоя (`policies:` принимает и `assembleTest`
— тестовый корень инварианты не ослабляет, см.
[гайд по композиции](./composition.md)). Причины `detached` приезжают в
отчёте значением, поэтому состав выведенных из-под политик ручек
сравнивается ассертом, а не парсингом вывода:

```typescript
// packages/examples.app-with-http/src/app.spec.ts
const [{ report }] = await checkTopologies(spec, ['all']);

expect(
  report.endpoints
    .filter(({ detached }) => detached !== undefined)
    .map(({ pattern }) => pattern),
).toEqual(['GET /health']);
```

Ограничение: конструктор с побочкой ломает `.check()`. Это и так нарушение
фазовой модели — ресурсы захватываются в `@OnInit`.

### Стабы сверяются с матрицей тем же приёмом

`app.stubbed` — имена застабанных контрактов значением (симметрично
`app.pruned`), а `report.contracts` каждой топологии — дескрипторы
контрактов, которые она **публикует**. Пересечение этих двух значений и есть
машинная форма правила: стаб, прикрывший контракт, которого не реализует ни
одна честная топология, становится виден в CI.

```typescript
// packages/examples.split-nats/src/isolated.spec.ts
const topologies = await checkTopologies(honestSpec, ['all', 'orders', 'quotas']);

const published = new Set(
  topologies.flatMap(({ report }) => report.contracts.map(({ name }) => name)),
);

expect(app.stubbed.filter((name) => !published.has(name))).toEqual([]);
```

Отдельного хелпера под эту сверку в пакете нет: обе стороны — уже значения, а
лишняя функция сузила бы её до одного варианта.

### Отчёт совместимости контрактов — из той же матрицы

Отчёт каждой топологии несёт поле `contracts` — дескрипторы контрактов,
которые эта топология **публикует**. Значит, проверка «не сломал ли я
контракт соседней фичи» пишется одним импортом и без пересборки приложения:

```typescript
// packages/examples.app-with-http/src/contracts.compat.spec.ts
import {
  checkTopologies,
  diffContracts,
  formatCompatibility,
  snapshotContracts,
} from '@nestling/testing';

const reports = await checkTopologies(spec, ['all', 'users', 'ops'], {
  converters: [zodConverter()],
});

const report = diffContracts(readBaseline(), snapshotContracts(reports));

console.log(formatCompatibility(report));
expect(report.breaking).toEqual([]);
```

`checkTopologies` прокидывает `options` в `check()` каждой топологии;
вызов из двух аргументов работает как раньше. Без конвертеров дескрипторы
всё равно строятся — структурная часть (вид контракта, формы io, коды и
статусы отказов) точна и без них, а листовые схемы честно помечаются
непрозрачными и дают вердикт `unknown`.

Сведение матрицы идёт **объединением**: контракт, публикуемый только
топологией `all`, в снапшоте есть и знает, кто его опубликовал, — иначе
«фича не выбрана в топологии `ops`» читалось бы как «контракт удалён».

Падает здесь ровно `expect` теста: `diffContracts` — чистая функция двух
значений, в сборке она не участвует и по результату сравнения не бросает.
Правила вердиктов и обновление baseline — в
[гайде по портам](./ports.md).

## 6. Конфиг тестом, а не окружением

`vars({ … })` — объектный `ConfigSource`; `process.env` не трогается, поэтому
тесты изолированы и параллелимы бесплатно.

```typescript
const src = vars({ RUNTIME_LOG_LEVEL: 'info' });

await using app = await assembleTest({ …, config: src });

src.set('RUNTIME_LOG_LEVEL', 'debug');   // reloadable-секция перепроецируется
```

Поле `config:` тестового корня принимает три формы: источник (сахар для
`[[source, '*']]`), одну привязку и список привязок. В боевом `assemble`
сахара нет — там привязка есть акт с приоритетами.

## 7. `./testing`-subpath: курируемая тестовая поверхность

Токены, разрешённые к подмене, и готовые фейки экспортируются отдельным
subpath'ом под условием `"testing"`:

```jsonc
// package.json модуля
"exports": {
  ".":         "./dist/index.js",
  "./testing": { "testing": "./dist/testing/index.js" }
}
```

Условие включено только в тест-раннере, поэтому прод-импорт не резолвится
**на уровне Node** — граница структурная, а не конвенция. Внутри subpath'а
живёт то, что автор держит в контракте с реализацией: в примере это токен
`UsersRepository` и фейк `inMemoryUsersRepo()`, которым пользуются и
app-тесты, и юнит-тест `UserService`. Ядро следует той же конвенции: шов,
которым `@nestling/testing` заводит фазы 0–3, живёт в `@nestling/app/testing`.

**jest** — условие включается в конфигурации тестов:

```javascript
testEnvironmentOptions: {
  customExportConditions: ['testing', 'node', 'node-addons'],
},
```

**vitest** — то же самое пишется как `resolve.conditions`:

```javascript
export default defineConfig({
  resolve: { conditions: ['testing', 'node'] },
});
```

Пакету, который импортирует такой subpath при сборке (а не только в тестах),
нужен `customConditions: ['testing']` в `tsconfig.json` — иначе typecheck
не найдёт модуль. Для `await using` там же понадобится
`lib: ['es2022', 'dom', 'dom.iterable', 'esnext.disposable']`.

## 8. Модуль в изоляции

```typescript
await using app = await testModule(ReportsModule, {
  stubs: [
    [ILogger, noopLogger],
    [IClock, { now: () => 42 }],
    stub(ChargeCard, async () => ({ chargeId: 'c1' })),
  ],
  transports: [http({ port: 0 })],
});
```

`testModule` поднимает мини-приложение вокруг одного модуля (с его
`imports`) и kernel-модуля конфига. Поле `stubs` то же самое, что у
`assembleTest`, поэтому меж-фичевый вызов, объявленный модулем, поставляется
им наравне с недостающим провайдером. Каждый неудовлетворённый импорт обязан
быть застабан явно; забыли — ошибка перечисляет **все** недостающие токены
с потребителем каждого:

```
Unsatisfied dependencies (2):
  - 'IsolatedClock' required by 'ReportService'
  - 'IsolatedUsers' required by 'ReportService'
```

Та же диагностика работает и на боевой сборке: `assemble`, который разъехался
по зависимостям, теперь называет все дыры сразу.

## 9. Чего в пакете нет

Ни своего `describe`, ни матчеров, ни snapshot-механики — jest остаётся
jest'ом. Нет и собственного spy у стаба: `impl` — обычная функция, поэтому
`jest.fn()` в этой позиции работает без единой строки поддержки в пакете.
Нет `app.port(Contract)` — типизированного порта для теста потребителя:
консументская сторона закрывается стабом, а вопрос остаётся открытым в
[журнале решений](../decisions/ideas.md). Подстановок не принимает и
`.check()` — он обязан гонять честный граф, которым и компенсируются
прунинг со стабами.
