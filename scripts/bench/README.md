# Бенчмарки

## `http.ts`

Сравнивает `@nestling/transport.http` с Fastify, Express и Hono на
одинаковой паре endpoint'ов: `GET /users/:id` с JSON-ответом и
`POST /users` с телом, проверенным одной и той же zod-схемой у всех
серверов.

```bash
yarn nx run-many -t build      # серверы берут пакеты Nestling из dist
yarn bench:http                # все четыре сервера, вывод таблицами
yarn bench:http --markdown     # сводная таблица в Markdown для ideas.md
```

Файлы:

- `servers.ts` — серверы и их endpoint'ы, по одной фабрике на фреймворк;
- `server.ts` — точка входа дочернего процесса: поднимает один сервер и
  печатает порт;
- `http.ts` — раннер: поднимает серверы по очереди в отдельных процессах,
  прогоняет autocannon, печатает таблицу на сценарий и сводку с
  отношением к Fastify.

Каждый сервер работает в отдельном процессе, а клиент autocannon — в
процессе раннера. Так сервер не делит цикл событий с клиентом, и числа
близки к тому, что даёт сервер под внешней нагрузкой.

Переменные окружения:

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `BENCH_DURATION` | секунды на один замер | `10` |
| `BENCH_CONNECTIONS` | одновременных соединений | `50` |
| `BENCH_SERVERS` | серверы через запятую: `nestling,fastify,express,hono` | все |
| `BENCH_NODE` | путь к бинарю Node для серверов | текущий `node` |

`BENCH_NODE` позволяет снять тот же замер на другой версии Node без
пересборки: `BENCH_NODE=$HOME/.nvm/versions/node/v24.10.0/bin/node yarn bench:http`.
Клиент при этом остаётся на текущей версии.

Колонки вывода: среднее req/s, разброс req/s между секундами (σ), средняя
латентность, p99, максимум, число ошибок и отношение req/s к Fastify.
Разброс и максимум нужны, чтобы видеть паузы: среднее req/s их скрывает.

Числа — точка отсчёта, а не порог. Они зависят от машины замера, поэтому
бенчмарк не входит в `yarn verify`, не проверяется тестом и ничего не
блокирует. Результат последнего замера и его условия записаны в
[`docs/decisions/ideas.md`](../../docs/decisions/ideas.md), запись
[2026-09-05] «Сигнал отмены запроса: реестр контроллеров вместо
`AbortSignal.any`».

На `GET` стороны неравны: Nestling проверяет path-параметр схемой, а
остальные читают его без проверки. Декларация с path-параметром без
`input` в Nestling запрещена, поэтому убрать эту работу нельзя. На `POST`
все четыре сервера разбирают JSON и проверяют тело одной схемой.

## Почему Nestling медленнее Fastify

Замер 2026-09-05 на Node 24 после change'а `abort-signal-registry`:
`GET /users/:id` 0.77 от Fastify, `POST /users` 0.97. На `POST` обе стороны
разбирают JSON и проверяют тело одной схемой, и разница уходит в шум. На
`GET` у Fastify нет ни проверки входа, ни контекста запроса, поэтому
сценарий показывает цену того, что Nestling делает на каждый запрос.

CPU-профиль сервера Nestling под этой нагрузкой (Node 24, `--cpu-prof`,
доли self-time от всех сэмплов; простой цикла событий 41%, запись в сокет
`writev` 25%):

| Доля | Что | У Fastify |
|---|---|---|
| 4.4% | `@nestling/transport.http`: `handle`, `sendResponse`, `readQuery`, `new URL`, `assemblePayload` | 2.4% собственного кода на те же обязанности |
| 2.2% | `@nestling/pipeline`: `execute`, `runFinals`, `normalizeResponse`, проверка `errors:` | нет: маршрут вызывает хендлер напрямую |
| 1.1% | `_storeHeader` из `node:http`: заголовки ставятся `setHeader`, затем `end` | 0.4%: `writeHead` с готовым объектом |
| 0.7% | `find-my-way` | 0.5%: тот же маршрутизатор |
| 0.5% | `AsyncContextFrame`: область контекста запроса на каждый вызов | нет |
| 0.4% | слушатель `'close'` на ответ и `AbortController` запроса | нет |
| 0.4% | `dispatch.call` из `@nestling/transport` | нет |
| 0.1% | zod: проверка path-параметра схемой | нет: параметр читается как есть |

В пересчёте на запрос Nestling тратит около 20 µs процессорного времени,
Fastify около 16 µs. Разница складывается из трёх частей.

1. **Гарантии, которых у Fastify в этом сценарии нет.** Проверка входа
   схемой, область `AsyncLocalStorage` для `Ctx`, проверка ответа по
   `errors:`, `.finally` с исходом запроса, сигнал отмены на каждый
   запрос и счётчик байтов в `summary`. Это около 1.5 µs, и они остаются:
   без них нет ни закрытого множества отказов, ни контекста из глубины
   графа, ни отмены по дисконнекту.
2. **Работа, которую можно вынести из горячего пути.** `new URL()` и
   `URLSearchParams` на запрос без query (0.46 µs против 0.17 µs у разбора
   по `indexOf`), `httpBindingOf` и `describeForm` на каждый запрос вместо
   таблицы маршрута, проверка нерезолвленных юнитов и копии массивов слоёв
   в `execute`, двойной spread контекста на pre-юнит, несколько
   `setHeader` вместо одного `writeHead`. Это около 1.5–2 µs; пункты
   перечислены в d/10 §5.5 и идут отдельным change'ем после замера.
3. **Микротаски.** Запрос проходит пять `await` (`handle`,
   `dispatch.call`, `executeWithHandler`, `execute`, `sendResponse`) против
   двух у Fastify: `runMicrotasks` и `processTicksAndRejections` дают 2%
   сэмплов.

Чего в разнице нет: сериализация ответа (`JSON.stringify` у обоих, на
объекте из двух полей рукописный сериализатор не быстрее), маршрутизатор
(общий), парсер HTTP (общий `node:http`). На Node 22 добавляется цена
хуков промисов `AsyncLocalStorage`: около 14% пропускной способности,
флаг `--experimental-async-context-frame` её снимает.
