## [2026-07-13] `header()`: параметры операции в HTTP-заголовках

**Откуда:** обсуждение канонизации HTTP-input — конвенция размещения + bind-карта
([d/06, продолжение](../history/discussions/06-critical-design-review.md)).

**Граница, зафиксированная в обсуждении** (meta vs input для заголовков):

- **ambient / cross-cutting** заголовки (`Authorization`, `traceparent`,
  `X-Request-Id`) — это *контекст* запроса, одинаковый для всех ручек: живут в
  meta/ctx через pre-юниты (`withIdentity` и т. п.), как сейчас. На клиенте
  симметрично: конфигурируются один раз при создании клиента, не аргумент вызова.
- `Accept` / `Content-Type` / `Last-Event-ID` — концерн транспорта
  (content negotiation, SSE-реконнект), до пользователя не доходят вообще.
- **заголовок-«параметр операции»** — клиент обязан передать его осознанно
  per-call, без него вызов не имеет смысла (`If-Match`/expectedVersion для
  оптимистичной блокировки; данные в заголовках внешних контрактов, которые мы
  не контролируем) — кандидат в **input** через пометку
  `header('If-Match', schema)` в bind-карте. Тогда контракт остаётся
  transport-agnostic: на NATS то же поле едет просто в payload, заголовок —
  деталь HTTP-биндинга.

**Почему параметр операции нельзя оставить в meta:** декларация endpoint'а
интроспектируема, pre-юнит — непрозрачная функция. Заголовок, поднятый в meta
pre-юнитом, выпадает из статически выводимого контракта: OpenAPI не узнает об
обязательном заголовке, типизированный клиент не потребует аргумент. Всё, что
клиент передаёт per-call, должно жить в декларации (input + bind).

**Почему отложено:** реальных кейсов мало — правило «бизнес-данные в body/query,
не в кастомных заголовках» в силе; v1 HTTP-канона обходится path/query/body.
Bind-карта аддитивна: добавить `header()` позже — обратно-совместимо
(асимметрия рисков — тот же аргумент, что при отказе от `.after`).

**Триггеры возврата:**

- первый реальный кейс оптимистичной блокировки (`If-Match`) или интеграции с
  внешним API, возящим данные операции в заголовках;
- дизайн типизированного клиента / OpenAPI-генерации, если им понадобится полная
  модель заголовков;
- смежная отложенная под-тема, вернуть вместе: **типизация ответных заголовков**
  в output-декларации (`Location`, `ETag`) — сейчас `Ok.created(value, headers)`
  остаётся нетипизированным обогащением.

## [2026-07-13] Outbox / saga: точка интеграции с портами

**Откуда:** критическое ревью
([d/06 §5](../history/discussions/06-critical-design-review.md)). Дисциплина
портов ([ideas.md, 2026-07-08](./ideas.md)) уже фиксирует: кросс-фичевая
согласованность = события + outbox/saga, не общая транзакция — но точка
интеграции не определена.

**Что уже придумано:**

- **Outbox** — транзакционный emit: событие пишется в БД в одной транзакции с
  бизнес-изменением, отдельный relay доставляет его в шину. Вероятная точка
  интеграции — **не ядро, а satellite-пакет**: обёртка emitter'а поверх
  хранилища + relay-процесс, встроенный в lifecycle (стартует в RUN-фазе,
  корректно гасится на SHUTDOWN). Контрактный API потребителя (`.emit()`)
  не меняется — меняется биндинг на сборке, в духе dispatch-политик.
- **Saga** — уровень приложения поверх `command`/`event`; от фреймворка ей
  нужны идемпотентность (принята, см. [ideas.md, 2026-07-13](./ideas.md)) и
  correlation в meta — отдельного механизма в ядре не предполагается.

**Почему отложено:** нет реального кейса; черта «kernel 1.0» — ядро не тянет
хранилище; дизайн зависит от принятых, но ещё не реализованных вещей (порты,
NATS-транспорт, идемпотентность).

**Триггеры возврата:**

- первый реальный кейс кросс-фичевой согласованности с БД (событие обязано
  выжить при падении после коммита);
- реализация L4/NATS в roadmap — спроектировать relay вместе с транспортом;
- запрос transactional emit от пользователей портов.
