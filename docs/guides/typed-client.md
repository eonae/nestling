# Типизированный клиент из контрактов

> Гайд по **текущему API**; сверено с кодом `examples.app-with-http` (2026-08-01).

Контракт уже порождает двух потребителей: реализацию (`implement` или
контракт-форму `httpEndpoint`) и внутреннего вызывателя (`.port`/`.emitter`).
Третий — **внешний**: фронт, сервис на другом стеке, скрипт. Ему недоступен
DI, и до этого change'а недоступен был и адрес: `name` контракта это subject
шины, а HTTP-паттерн жил только в декларации endpoint'а.

Теперь адрес живёт на контракте, а клиент строится из него одной функцией.

## Два пакета и почему их два

```typescript
import { CreateUser, GetUser } from './api.contracts';   // ваши контракты
import { makeClient } from '@nestling/client';
```

`@nestling/contracts` — дом направление-нейтральных деклараций:
`makeContract`, `defineFail`, `Ok`/`Fail`, словарь статусов, формы io,
пометки размещения и bind-карта. У пакета **нет runtime-зависимостей**:
транзитивно в его графе импортов только типы Standard Schema. Ни контейнера,
ни pipeline, ни транспорта, ни `node:*` там нет — и это не обещание, а
инвариант: тест обходит замыкание собранного `dist/` и падает, называя
модуль и запрещённый импорт.

`@nestling/client` зависит только от контрактов и говорит с сетью через
`fetch`. Оба пакета собираются в браузерный бандл без полифиллов.

> Канонический импорт `makeContract` — `@nestling/contracts`.
> `@nestling/ports` его **не** реэкспортирует: этот реэкспорт вернул бы
> объявление контракта в пакет с серверными зависимостями и снова сделал бы
> «контракт импортируется во фронт» вопросом дисциплины импортов.

## Адрес на HTTP-проводе: секция `http:`

```typescript
import { makeContract, query } from '@nestling/contracts';

export const CreateUser = makeContract({
  name: 'api.users.create',
  kind: 'request',
  http: { method: 'POST', path: '/api/users', bind: { dryRun: query() } },
  input: CreateUserInput,
  output: User,
  errors: [EmailTaken, QuotaExceeded],
});

export const GetUser = makeContract({
  name: 'api.users.get',
  kind: 'request',
  http: 'GET /api/users/:id',            // сахар для случая без пометок
  input: z.object({ id: z.string() }),
  output: User,
  errors: [UserNotFound],
});
```

Секция принимается в двух формах: строкой `'<METHOD> <path>'` (строгий
разбор — ровно один пробел, непустые метод и путь) и записью
`{ method, path, bind?, rawBody?, sse? }`. Строка — сахар ровно для случая
без пометок: `bind`, `rawBody` и `sse` ею не выразить.

**Карта разворачивается в момент `makeContract`**, тем же кодом, что
обслуживает HTTP-декларацию. Значит:

- все проверки размещения (пометка на path-параметре, `body()` у метода без
  тела, path-параметр при неструктурном `input`, `rawBody` с потоковой
  формой, `sse` при не-`events`-выходе) срабатывают **на импорте модуля с
  контрактами** — у владельца декларации, а не при сборке приложения и не
  при первом вызове клиента;
- карта доступна с самого значения: `CreateUser.http` — уже развёрнутый
  `{ method, path, fields, rest, rawBody }`.

Секция `http:` ничего не меняет в контракте шины: вид, `.port`/`.emitter`,
`implement` и вызов по шине работают как прежде. Одно значение — два провода.

## Серверная сторона: контракт-форма `httpEndpoint`

```typescript
export const GetUser = httpEndpoint({
  contract: GetUserContract,
  pipeline: basePipeline,
  deps: [UserService, ILogger],
  handle: getUserHandler,
});
```

`method`, `path`, `bind`, `rawBody`, `sse`, `input`, `output` и `errors`
принадлежат контракту: переобъявить их здесь — **ошибка компиляции**, ровно
как в `implement`. Bind-карта берётся с контракта тем же значением и
повторно не считается — «одна карта на оба конца провода» держится на
тождестве, а не на совпадении двух вычислений.

Контракт без `http:` отвергается в момент создания декларации: текст
называет контракт и предлагает либо объявить `http:`, либо реализовать
контракт через `implement` (шина).

Три формы `handle`, `deps`, `pipeline`, `detached`, дискавери, `policies` и
визуализация работают как у любой HTTP-декларации: контракт-форма — форма
записи, а не новый примитив.

## Клиент

```typescript
const api = makeClient(
  { createUser: CreateUser, getUser: GetUser },
  {
    baseUrl: 'https://api.example.com',
    headers: () => ({ authorization: `Bearer ${token()}` }),
  },
);
```

Методы именует **потребитель** — ключами записи. Вывода имён из `name`
контракта (парсинга `'users.create'` во вложенные объекты) нет: имя
контракта это адрес на шине, и превращать адрес в форму чужого API значило
бы навязывать её.

Клиент — значение: он ничего не регистрирует, не требует DI и работает в
скрипте, импортировавшем ровно два пакета.

### Call-site эквивалентен вызывателю

| Вид контракта | Вызыватель | Метод клиента |
|---|---|---|
| `request` | `port.call(payload, meta?)` | `Promise<Ok<Output> \| Fail<E ∪ UnknownError>>` |
| `command` | `emitter.emit(payload, meta?)` | `Promise<void>`, отказ бросается |
| `event` | `emitter.emit(...)` | отвергается в `makeClient` |

```typescript
const created = await api.createUser({ name: 'Alice', email: 'a@b.c' });

if (EmailTaken.is(created)) {
  console.log(`email taken: ${created.details.email}`);   // details типизированы
} else if (created.isFail) {
  console.log(`unexpected: ${created.message}`);          // UNKNOWN ∪ DEADLINE_EXCEEDED
} else {
  console.log(created.value.id);
}
```

Та же ветвящаяся логика, что написана для `.port`, работает без правок:
множество результата закрыто как `E ∪ UnknownError`, идентичность отказа —
код, а не `instanceof` (по проводу класс мёртв).

`event` отвергается потому, что событие это broadcast-факт с 0..N
подписчиками, а HTTP-вызов адресует ровно одного получателя. Текст ошибки
предлагает `command`.

### Сборка запроса — обратная операция к приёму

Клиент раскладывает payload по той же bind-карте, по которой транспорт
собирает его обратно:

```
path   ← поля с placement.in === 'path'   → подстановка в шаблон, encodeURIComponent
query  ← поля с placement.in === 'query'  + (rest === 'query' ? остальные : ∅)
body   ← поля с placement.in === 'body'   + (rest === 'body'  ? остальные : ∅)
```

Инвариант «разбор собранного клиентом запроса даёт исходный payload»
проверяется round-trip-тестом на наборе карт, а не выводится из совпадения
реализаций.

Тело — JSON; `Content-Type: application/json` ставится **только когда тело
есть**. `baseUrl` и путь склеиваются буквально (база без хвостового слэша
плюс путь) — без «умного» разрешения относительных URL.

### Коерсия query определена и не догадывается

| Значение | Что уходит на провод |
|---|---|
| `undefined`, `null` | ключ не пишется вовсе |
| скаляр (`string`/`number`/`boolean`) | `String(value)` |
| массив скаляров | повторяющиеся вхождения ключа в порядке следования |
| объект, вложенный массив | `TypeError` в момент вызова, с именем поля |

Отсутствие остаётся отсутствием — `.optional()` и дефолты схемы продолжают
работать. Молчаливого `[object Object]` на проводе не будет: это ошибка
программиста, и она бросается, а не возвращается `Fail`'ом.

> **Схема query-поля обязана принимать проводную форму.** Query несёт
> строки, и клиент пишет туда `String(value)`. `z.boolean()` отверг бы
> законный `?dryRun=true`; в примере поле объявлено `z.stringbool()` —
> оно понимает `'true'`/`'false'`/`'1'`/`'0'`. Это свойство провода, а не
> дефект клиента, и знать о нём должна схема.

### Ответ: успех, валидация, отказ

- **2xx** → HTTP-код отображается обратно в `SuccessStatus`; `204` даёт
  `Ok('NO_CONTENT', null)`.
- **Валидация ответа — по умолчанию.** Обещание клиента это типизированный
  результат; отдать невалидированный JSON под типом `Output` значит соврать
  в типе. Отключается явно: `makeClient(record, { validateOutput: false })`.
  Валидация синхронная — `Promise` из `~standard.validate` трактуется как
  ошибка, как в ядре.
- **Не-2xx** → тело `{ error, code?, details? }`. Если `code` объявлен в
  `errors:` контракта, отказ рематериализуется этим определением: `status`
  берётся из определения (сервер мог ответить любым), `message` — с провода,
  `details` — с провода, но проверенные схемой определения.
- **Всё остальное** — сеть недоступна, тело не JSON, ответ не прошёл
  `output`-схему, код не объявлен, детали не сошлись — даёт `UnknownError` с
  оригиналом в `cause`. Третьего кода не вводится.

Клиент **не бросает** на транспортных и контрактных сбоях у `request`: он
возвращает `Fail`. Бросает он только на дефектах использования
(`TypeError` на непредставимом query-поле).

### `meta`: отмена и бюджет

```typescript
await api.getUser({ id }, { signal, deadline: new Date(Date.now() + 2_000) });
```

`signal` уезжает в `fetch`. `deadline` — **абсолютный момент**, как у
портов: истёкший бюджет даёт `DeadlineExceeded` **до** отправки, без похода
в сеть; неистёкший композируется в `AbortSignal` вместе с пользовательским.

`idempotencyKey` в v1 у клиента нет: согласованного HTTP-слота для него не
существует, а провезти его «каким-нибудь заголовком» значит договориться с
самим собой.

### Конфигурация клиента

```typescript
makeClient(record, {
  baseUrl: string,
  headers?: Record<string, string> | (() => Record<string, string> | Promise<…>),
  fetch?: typeof globalThis.fetch,
  validateOutput?: boolean,   // default: true
});
```

`headers` допускает функцию: auth-токен ротируется, а статическая запись
защёлкнула бы его на момент создания клиента. `fetch` инжектируется —
тестируемость без сети и работа в средах со своим `fetch`.

Per-call заголовков в V1 нет: всё, что клиент передаёт на каждый вызов,
живёт в декларации (`input` плюс bind-карта).

## Fail-fast создания клиента

`makeClient` отвергает **в момент создания**, называя ключ метода:

- контракт без секции `http:` — HTTP-адреса у него нет;
- контракт вида `event`;
- потоковая (`stream`/`events`) или `multipart`-форма io — streaming-клиент
  проектируется отдельно;
- не-JSON тело (`'binary'`/`'text'`) — v1 говорит только JSON;
- `baseUrl`, не являющийся абсолютным URL.

Отложенной диагностики («упадёт при первом вызове») нет: запись контрактов
известна целиком, и всё проверимое проверяется сразу.

## Чего клиент не делает

- **Стриминга** — `stream` → NDJSON, `events` → SSE с реконнектом по
  `Last-Event-ID` — отдельно и позже, вместе с AsyncAPI.
- **Кодогенерации**: типы выводятся из контракта. Путь для не-TS-потребителей
  — через [`@nestling/openapi`](../design/schemas.md).
- **Вызовов по шине**: `makeClient` это HTTP. У шины есть
  `@nestling/transport.nats`.
