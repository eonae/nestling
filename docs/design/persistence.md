> [2026-09-11], «Транзакционный приём: отметка в базе, слой подписчика,

Ядро драйвера базы не тянет. Соединение, транзакция запроса и адаптеры
`OutboxStore` и `InboxStore` живут сателлитом
[`@nestlingjs/drizzle.pg`](../../packages/nestling.drizzle.pg/): адаптер и
транзакция обязаны быть на одном соединении, поэтому пакет, который везёт
слой транзакции, везёт и драйвер. `drizzle-orm` и `pg` — peer-зависимости.

Диалект стоит в имени пакета, потому что диалект стоит в коде: пакет
открывает транзакцию командой на соединении, выданном пулом `pg`, а выдача
сессии у каждого драйвера своя. Имя следует правилу транспортов
(`transport.http`, `transport.nats`), где вторая часть называет
реализацию.

## 1. Соединение объявляется значением

```typescript
export const db = drizzlePg({ schema });
export const analytics = drizzlePg({ name: 'analytics', schema: reports });

export const app = makeApp({
  features: [UsersFeature],
  plugins: [db, analytics],
  transports: [http()],
});
```

Вызов создаёт DI-токен соединения, переменную контекста транзакции,
конструктор слоя, политику предпосылки и дескриптор ключей конфига. Все
пять несут тип схемы этого соединения, поэтому обращение к таблице другой
схемы — ошибка компиляции.

Несколько соединений — несколько вызовов. Глобального семейства
`Db$('analytics')` нет: член семейства несёт один тип значения на всё
семейство, и тип схемы был бы потерян. Два вызова с одним именем
останавливают объявление: имя задаёт и ключи конфига, и идентификатор
DI-токена, и поле контекста с сессией.

## 2. Секция конфига — семейство по имени соединения

Поля секции: адрес базы, размер пула, таймаут подключения, таймаут
простоя, потолок времени запроса и признак TLS. Соединение по умолчанию
читает `DATABASE_URL`, именованное — `DATABASE_ANALYTICS_URL`; правило
вставки имени задаёт ядро ([config.md](./config.md)).

Наружу уходит только дескриптор ключей: DI-токен секции остаётся
приватным, как у транспортов и у outbox'а. Адрес помечен секретом, и
вычисляемое поле с хостом наследует секретность — лог подключения пишет
хост, а не адрес с паролем.

## 3. Пул — ресурс с пробой

Пул открывается на фазе INIT и закрывается на SHUTDOWN: ввода-вывода на
фазе сборки нет. Захват проверяет пул первым запросом, поэтому недоступная
база останавливает старт сообщением, которое называет имя соединения и
ключ конфига с адресом.

Ресурс объявляет проверку состояния, и контейнер делает из неё вклад в
пробы ([composition.md](./composition.md)). Имя проверки равно
идентификатору DI-токена, поэтому в `/readyz` соединения видны как
`database` и `database:analytics`.

Значение DI-токена несёт два члена: экземпляр drizzle на пуле — для
запросов вне транзакции — и выдачу сессии с открытой транзакцией.

## 4. Транзакция запроса — переменная контекста

Форма `db.transaction(cb)` не подходит: значение живёт только внутри
колбэка, а репозиторий и эмиттер читают его из контекста запроса.
Транзакция объявляется переменной, а кладёт её слой пайплайна:

```typescript
export const transactional = compose(authed, db.transaction());
```

Внутри слоя четыре части. Класс-мост берёт соединение из контейнера и
открывает транзакцию командой `BEGIN` на соединении из пула; писатель
переменной кладёт экземпляр drizzle, привязанный к этой транзакции; `.ok`
коммитит; `.catch` откатывает, а `.finally` возвращает соединение в пул на
любом исходе, включая обрыв связи с клиентом и остановку приложения.

Мост кладёт в контекст сессию, а не значение переменной: сессию читают
`.ok`, `.catch` и `.finally`, а выдаёт её соединение из контейнера. Ключи
выводятся из имени экземпляра детерминированно: `tx` и
`txSession` у соединения по умолчанию, `analyticsTx` и `analyticsTxSession`
у именованного. Поэтому два соединения не спорят за поле контекста, а
конфликт ключей проверяет компилятор в точке композиции.

Уровень изоляции задаётся аргументом конструктора слоя и входит в команду
открытия. Потолок времени запроса ставится на время транзакции.

## 5. Значение переменной — экземпляр drizzle

```typescript
@Component([db.connection, Ctx(db.tx)])
export class DbUsersRepository {
  async list(limit: number): Promise<User[]> {
    return this.connection.db.select().from(users).limit(limit);
  }

  async insert(data: NewUser): Promise<User> {
    const [row] = await this.tx.get().insert(users).values(data).returning();

    return row;
  }
}
```

Читающий метод берёт соединение из пула, изменяющий — транзакцию запроса.
Обёртки с методами `commit` и `rollback` у репозитория нет: решение о
коммите принадлежит слою.

Политика `db.requiresTransaction(filter?, label?)` требует, чтобы каждый
endpoint под фильтром объявлял переменную транзакции. Нарушение
останавливает сборку на фазе ASSEMBLE — до фазы INIT и до открытия сокета.

## 6. Адаптер хранилища outbox'а

Адаптер живёт в подпуте `@nestlingjs/drizzle.pg/outbox`, а
`@nestlingjs/outbox` объявлен необязательной peer-зависимостью:

```typescript
export const outboxStore = pgOutboxStore(db);

export const appOutbox = outbox({
  transaction: db.tx,
  store: outboxStore.token,
  operations: [UserCreated],
});
```

Запись идёт транзакцией вызывающего, поэтому строка события и строка
бизнес-изменения коммитятся вместе. Значение не той формы даёт ошибку с
обеими починками: объявить слой транзакции этого соединения или передать
плагину outbox'а переменную того же соединения. Выдача и отметка исходов
идут на пуле: relay живёт вне запроса и транзакции не имеет
([operations.md](./operations.md), §2.6).

Таблица записей отдаётся объявлением drizzle и строкой DDL. Объявление
приложение включает в свою схему drizzle-kit, и миграция генерируется
вместе с остальными; строка DDL нужна тем, кто ведёт миграции руками.
Порядок создания задаёт отдельная возрастающая колонка: идентификатор
служит ключом идемпотентности, а два момента создания в пределах
миллисекунды неразличимы.

Выдача партии — один запрос с пропуском заблокированных строк: две реплики
relay, читающие одну таблицу, не получат одну запись. Запись с разделом не
выдаётся, пока предыдущая запись того же раздела не отмечена
опубликованной или застрявшей. Отметка исходов идемпотентна: исход
применяется только к записи, взятой в работу.

## 7. Адаптер хранилища отметок приёма

Адаптер живёт в подпуте `@nestlingjs/drizzle.pg/inbox`, а
`@nestlingjs/inbox` — второй необязательный peer рядом с outbox'ом:

```typescript
export const inboxStore = pgInboxStore(db);

export const appInbox = inbox({ transaction: db.tx, store: inboxStore.token });
```

Отметка ставится транзакцией вызывающего, поэтому она и записи хендлера
коммитятся вместе. Значение не той формы даёт ошибку с обеими починками —
теми же, что у адаптера outbox'а.

Таблица отдаётся объявлением drizzle и строкой DDL, как таблица записей.
Первичный ключ составной: потребитель и ключ идемпотентности. Индекс по
моменту постановки нужен проходу уборщика.

Конкурентный повтор разрешает первичный ключ, а не приложение: вставка
идёт с `ON CONFLICT DO NOTHING RETURNING`, и вторая транзакция получает
ноль строк, то есть повтор. Голая вставка не годится — нарушение
уникальности в PostgreSQL рвёт транзакцию целиком, и слой не смог бы
завершить endpoint успехом.

Проход уборщика идёт на пуле и удаляет партию отметок старше срока
хранения: уборщик живёт вне запроса и транзакции не имеет
([operations.md](./operations.md), §2.6).

## 8. Границы

Другие диалекты в V1 не поддерживаются: каждый следующий драйвер — своя
реализация выдачи сессии. Миграции идут вне процесса приложения.
Собственного query builder'а и репозитория пакет не даёт — запросы пишутся
drizzle. Двухфазного коммита нет: согласованность между базами держится
событиями и outbox'ом.

Слой транзакции не применяется к формам вывода `stream` и `events`: юнит
`.ok` выполняется в начале ответной фазы, поэтому коммит прошёл бы раньше,
чем хендлер дочитал курсор ([streaming.md](./streaming.md)).
