## Context

Скилл Claude Code это каталог с файлом `SKILL.md`. У файла есть
frontmatter с полями `name` и `description`; по `description` агент решает,
загружать ли скилл. Тело `SKILL.md` попадает в контекст целиком, поэтому его
держат коротким, а подробности выносят в соседние файлы, которые агент
читает по потребности. Репозиторий уже ведёт три таких скилла в
`.claude/skills/` (`docs-style`, `docs-audit`, `openspec-*`), но все они про
работу над самим Nestling.

Материал для скилла есть весь: 27 глав гайда, 13 design-доков,
`conventions.md`, `glossary.md`, 18 README пакетов и шесть приложений в
`examples/`. Задача не написать новое, а отобрать то, что нужно агенту в
чужом проекте, и записать по-английски в размер, который не вытесняет из
контекста код пользователя.

Ограничения:

- Пакеты собираются одинаково (`CLAUDE.md`, раздел «Конфигурация пакетов»).
  Новый пакет копирует набор конфигов целиком.
- `yarn verify` гоняет `build`, `typecheck`, `lint`, `test` и `type-budget`
  по всем пакетам через nx. Проверка сниппетов должна попасть в эти таргеты,
  а не в отдельную команду, иначе её будут забывать.
- `scripts/pack-check.mjs` требует от публикуемого пакета собранный `dist`
  и импортирует его настоящим Node'ом из установленного тарбола.
- Публикация идёт тегом из `.github/workflows/release.yml`, список пакетов
  читается из `scripts/packages.mjs` по каталогам `packages/*`.

## Goals / Non-Goals

**Goals**

- Агент в проекте пользователя пишет код на Nestling с первого раза: без
  цикла «написал по привычке из Nest — получил ошибку компиляции».
- Скилл устаревает шумно: расхождение с API роняет `yarn verify`.
- Установка одной командой и без вопросов о том, куда класть файлы.

**Non-Goals**

- Перевод гайда и design-доков на английский.
- Второй формат для других агентов.
- Изменения публичного API пакетов.

## Decisions

### Решение 1. Формат — скилл Claude Code, один

Скилл загружается по `description`, то есть тогда, когда агент собирается
писать код на Nestling, и не занимает контекст в остальное время. Тело
делится на `SKILL.md` и `references/`, и агент дочитывает подробности сам.

Альтернативы:

- **Раздел в README пакета.** README читают и человек, и агент, но README
  отвечает на вопрос «что в пакете сегодня», и правила написания кода в него
  не помещаются: потолок 120 строк и фиксированный состав разделов заданы
  инвариантами `docs:audit`.
- **`AGENTS.md` в корне проекта пользователя.** Формат читают несколько
  агентов, но файл загружается всегда и целиком; правила Nestling заняли бы
  контекст в каждой сессии, включая те, где пишут фронтенд.
- **MCP-сервер с поиском по документации.** Требует запущенного процесса и
  сети, отвечает на вопрос только если его задали. Агент, который пишет
  `@Injectable()` по привычке, вопроса не задаёт.

### Решение 2. Доставка — публикуемый пакет с командой установки

Пакет `@nestlingjs/agent-skill` несёт файлы скилла и команду
`npx @nestlingjs/agent-skill`, которая копирует их в
`.claude/skills/nestling/` текущего проекта. Версия скилла совпадает с
версией пакетов ядра: обе выпускаются одним тегом из одного репозитория.

Альтернативы:

- **Папка в репозитории, копировать руками.** Пользователю нужно найти
  репозиторий, выбрать ветку под свою версию и скопировать каталог. Обновление
  после `npm update` не происходит вовсе.
- **Файлы внутри `@nestlingjs/app`.** Ставится вместе с ядром, но агент
  Claude Code не ищет скиллы в `node_modules`: их читают из `.claude/skills/`.
  Пришлось бы всё равно копировать, только из чужого каталога.
- **Постинсталл-хук, который копирует сам.** Ставит файлы в проект без
  спроса, а `npm install` в CI выполняется на каждой сборке.

### Решение 3. Текст скилла на английском

Скилл читает модель, а не разработчик. Корневой `README.md` и манифесты
пакетов уже английские; русский остаётся у документации, у которой читатель
русский. Скилл — единственный английский текст в `docs`-жанрах, и правила
`/docs-style` к нему не применяются: они описывают русский синтаксис и
русские замены. Линтер `docs-style` каталог скилла не проверяет.

Русским остаётся `README.md` пакета: у него тот же читатель, что у остальных
README репозитория, и те же инварианты `docs:audit`.

### Решение 4. Состав скилла

```
.claude/skills/nestling/
├── SKILL.md
└── references/
    ├── endpoints.md    — декларация endpoint'а: операция, схемы, формы io, привязка входа
    ├── container.md    — DI-токены, провайдеры, роли классов, модули, фазы
    ├── pipeline.md     — слои, `.pre`/`.ok`/`.catch`/`.finally`, `compose`, контекст, политики
    ├── errors.md       — `makeFail`, категории кодов, `Ok`/`Fail`, `Output`
    ├── config.md       — секции, ключи, источники, `derived`
    ├── features.md     — фичи, операции, вызыватели и эмиттеры, события, split
    ├── testing.md      — `assembleTest`, `overrides`, стабы, `checkTopologies`
    └── from-nest.md    — таблица «в Nest писали так — в Nestling пишется так»
```

`SKILL.md` содержит пять частей: чем Nestling отличается от того, что модель
знает по Nest; скелет сервиса файлами; минимальное работающее приложение
одним блоком кода; список правил, нарушение которых ловится компилятором или
фазой ASSEMBLE; таблица «нужно X — читай `references/Y.md`».

Правило отбора: в скилл попадает то, что модель напишет неправильно, если не
прочитает. Всё остальное остаётся в гайде. Поэтому в скилле есть явный список
зависимостей у декоратора, отказ значением вместо `throw`, обращение к соседней
фиче через операцию и синхронная сборка без I/O в фабриках, но нет ни истории
решений, ни сравнения с альтернативами, ни объяснений «почему так».

Потолок: 250 строк на `SKILL.md`, 200 на файл `references/`. Потолок держит
скилл в размере, при котором его загрузка не вытесняет из контекста код
пользователя.

### Решение 5. Сниппеты — компилируемые файлы, блоки кода сверяются с ними

Каждый TypeScript-сниппет скилла лежит отдельным файлом в
`packages/nestling.agent-skill/snippets/` и входит в проект пакета. Файл
импортирует настоящие `@nestlingjs/*`, поэтому `yarn typecheck` компилирует
его против того API, которое собрано из `src` соседей.

Markdown называет файл HTML-комментарием перед блоком кода:

```markdown
<!-- snippet: get-user.endpoint.ts -->
```typescript
…содержимое snippets/get-user.endpoint.ts…
```
```

Скрипт `scripts/snippets.mjs` работает в двух режимах: сверяет блоки с
файлами и переписывает блоки из файлов. Сверку вызывает спека
`src/snippets.spec.ts`, поэтому расхождение роняет `yarn verify` на таргете
`test`. Спека проверяет и обратное направление: файл сниппета, на который не
ссылается ни один markdown, — ошибка.

Альтернативы:

- **Компилировать блоки прямо из markdown.** Пришлось бы собирать временный
  проект и повторять `tsconfig` пакета; редактор при этом внутри блока не
  подсказывает ничего.
- **Держать сниппеты только в файлах, а в markdown ставить ссылку.** Агент
  читает скилл из своего проекта, где файлов сниппетов нет. Блок кода должен
  быть в тексте целиком.
- **Ничего не проверять.** Так живут блоки кода в главах гайда, и там это
  ловит сверка человеком по плашке «сверено с кодом». Скилл читает не человек,
  и повода откладывать проверку на человека нет.

### Решение 6. Раскладка пакета

```
packages/nestling.agent-skill/
├── src/
│   ├── index.ts         — `installSkill()`: копирование каталога в проект
│   ├── cli.ts           — команда с shebang; разбор аргументов, вывод отчёта
│   └── snippets.spec.ts — сверка блоков кода со сниппетами
├── skill/               — файлы скилла; едут в тарбол как есть
├── snippets/            — компилируемые сниппеты; в тарбол не едут
├── scripts/snippets.mjs — сверка и перезапись блоков
└── README.md
```

- `files: ["dist", "skill"]`. Каталог `snippets/` нужен только проверке.
- `bin` один: `npx @nestlingjs/agent-skill` запускает его без имени.
  `tsc` сохраняет строку `#!/usr/bin/env node` в начале файла при эмите.
- Пакеты, которые импортируют сниппеты, объявлены в `devDependencies` через
  `workspace:*`. У `dist` зависимостей нет вовсе: `index.ts` и `cli.ts`
  импортируют только `node:*`.
- `installSkill()` экспортируется из бареля: `pack-check` импортирует
  установленный пакет, и точка входа должна что-то экспортировать.
- Каталог скилла находится относительно собранного файла
  (`new URL('../skill/', import.meta.url)`), а не относительно `process.cwd()`.

Скилл не устанавливается в сам репозиторий. Копия в `.claude/skills/` разошлась
бы с источником, а проверка сравнивала бы копию с копией. Агенту, который
работает над Nestling, доступны сам гайд и `examples/`.

### Решение 7. Поведение команды установки

- Пишет в `.claude/skills/nestling/` относительно текущего каталога. Другой
  каталог задаётся флагом `--dir`.
- Файл, которого нет, создаётся. Файл, совпадающий с источником, не трогается.
- Файл, отличающийся от источника, не перезаписывается: команда печатает его
  имя и завершается кодом 1. `--force` перезаписывает.
- В конце печатает, что создано, что совпало и что расходится.

Поведение выбрано так, потому что пользователь мог дописать скилл под свой
проект. Молчаливая перезапись потеряла бы его правки при первом
`npx` после обновления.

### Решение 8. Проверки репозитория

- `nx.json`: именованный вход `sources` получает `{projectRoot}/snippets/**/*`
  и `{projectRoot}/skill/**/*`. Без этого nx отдаёт закэшированный результат
  `typecheck` и `test` после правки скилла.
- `scripts/pack-check.mjs`: у пакета с полем `bin` файл команды обязан быть в
  тарболе и запускаться из установленного пакета. Проверка общая для
  репозитория, а не для одного пакета: следующий пакет с командой получит её
  без правок.
- `docs:audit` новых инвариантов не получает: его правила описывают `docs/` и
  `packages/*/README.md`, и README нового пакета попадает под них сам.

## Risks / Trade-offs

- **Проза скилла расходится с кодом, а компилятор этого не видит.** Сниппеты
  ловят изменение сигнатур, но не изменение смысла. → Проза короткая по
  потолку строк, а каждый файл `references/` называет README пакета, откуда
  читать актуальный перечень имён.
- **Скилл разрастается.** Каждый следующий change будет хотеть добавить в него
  свой раздел. → Потолки строк заданы требованием и проверяются; правило отбора
  записано в спеке, а не в устной договорённости.
- **Английский текст расходится с русским гайдом.** Два текста об одном. →
  Скилл не пересказывает гайд: он даёт форму кода и правила, а объяснения
  оставляет документации, на которую ссылается.
- **Команда перезаписывает чужие файлы.** → Отличающийся файл не трогается без
  `--force`, и команда завершается ошибкой.
- **Проверка сниппетов удлиняет `typecheck` пакета.** Сниппеты импортируют
  пять пакетов, и таргет ждёт их сборки. → Это один пакет из девятнадцати, и nx
  кэширует результат по входам.

## Migration Plan

Миграции нет: пакет новый, публичный API не меняется. Порядок выпуска —
обычный, из `RELEASING.md`: пакет входит в тег вместе с остальными.
