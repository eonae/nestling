## Context

Поле `Module.exports` появилось вместе с семействами токенов (change
`token-families`, 28.07.2026) и получило вторую роль в change
`multi-injection` (29.07.2026): узел-агрегат `Family.all` не принадлежит
модулю, поэтому под `strictExports` вклад чужого модуля требовал
объявления.

Сегодня в коде это выглядит так. `ContainerBuilderOptions.strictExports`
по умолчанию `false` (`container.builder.ts:143`). Проверка выполняется
единственным шагом 11 в `build()` (`container.builder.ts:252`) на уже
построенном графе. Метод `isExportedFrom` вызывается ровно из двух мест:
из `checkStrictExports` и из `computeExported`, который заполняет
`metadata.exported` для визуализации. В `get()` и при инжекте проверок
нет.

Опция недоступна там, где приложение собирают: `assemble()` создаёт билдер
с `overrides` и `familyOverrides` (`app.ts:385`), а `AssemblySpec`
(`plan.ts:39`) поля для неё не имеет. Поэтому все пять модулей
`examples.simple-app` объявляют `exports`, и ни одна сборка их не
проверяет.

## Goals / Non-Goals

**Goals:**

- Удалить `Module.exports`, `ContainerBuilderOptions.strictExports` и
  проверку из `build()`.
- Удалить `metadata.exported` из узла графа, его сериализации и
  визуализатора.
- Оставить вклад в семейство работающим ровно так же, как сейчас работает
  вклад без включённой проверки.
- Сохранить `metadata.module`: атрибуция, разрешение коллизий имён и
  discovery не меняются.

**Non-Goals:**

- Модель прав конфига. `Config(key)` читает любой ключ, включая
  секретный — отдельная тема.
- ESLint-правило на импорты между папками модулей. Остаётся выбором
  пользователя.
- Поле `imports`. Остаётся списком модулей для рекурсивной регистрации.

## Decisions

### Удалять, а не делать обязательным

Альтернатива — сделать `exports` обязательным полем и проверять всегда.
Отвергнута: граница вышла бы дырявой. Проверка видит только рёбра готового
графа, поэтому мимо неё проходят типы в `.d.ts` потребителя, создание
класса через `new` в обход контейнера, подстановка `overrides` в чужих
тестах и чтение чужого ключа через `Config(key)`. Обещание «модули
изолированы» стало бы ложным, а ложное обещание об изоляции хуже
честного её отсутствия: на него начинают полагаться.

### Проблема семейств исчезает вместе с проверкой

Требование «вклад чужого модуля объявляется в `exports`» порождено самой
проверкой, а не существует отдельно от неё. Вклад уже записан явно:
`classProvider(IHealthCheck('db'), DbHealthCheck)` в `providers` модуля
называет токен семейства прямо и виден на графе. Строка
`exports: [IHealthCheck]` добавляла к этому только проверяемость ребра,
которого без проверки нет.

Альтернатива — обёртка `contribute(IHealthCheck('db'), DbHealthCheck)`
как синоним `classProvider` с говорящим именем. Отвергнута: косметика без
гарантии, а словарь провайдеров растёт.

### `metadata.exported` уходит целиком

Флаг вычисляется из `Module.exports` и без него неопределён. Оставить его
как «всегда `undefined`» значило бы держать в графе поле, которое ничего
не сообщает. Визуализатор (`nestling.viz`) показывает публичность узла
цветом и в подсказке — эта отрисовка убирается вместе с полем.

### Порядок работ: контейнер, затем потребители

`Module.exports` — необязательное поле, поэтому после его удаления из
типа компилятор сам покажет каждое место, где оно ещё объявлено: пять
модулей фреймворка и шесть модулей примеров. Это и есть список работ,
проверяемый `yarn build`.

## Risks / Trade-offs

- **Публичная поверхность модуля перестаёт быть видимой одним списком** →
  Для модулей внутри пакета такого места больше нет. Смягчения внутри
  фреймворка не предусмотрено; граница пакета по-прежнему описана его
  `index.ts`, и именно она остаётся рекомендуемой единицей публикации.
- **Визуализация теряет деление на публичное и внутреннее** → Узлы
  остаются сгруппированы по `metadata.module`, поэтому принадлежность
  видна, а публичность больше не показывается.
- **Тестовые данные визуализатора содержат `exported`** →
  `packages/nestling.viz/src/static/data/graph-data.json` обновляется
  вместе с типами, иначе фикстура разойдётся с формой графа.
- **Спека `strict-exports` удаляется целиком** → При архивации change'а
  её каталог уходит из `openspec/specs/`. Историю решения сохраняют
  `docs/decisions/ideas.md` и `archlog.md`.

## Migration Plan

Обратной совместимости не предусмотрено: стадия активного проектирования,
пользователей нет. Удаление одношаговое.

1. Убрать поле из типа `Module` и опцию из `ContainerBuilderOptions`.
2. Прогнать `yarn build` и убрать `exports` во всех местах, которые
   покажет компилятор.
3. Обновить документацию и записать решение в `docs/decisions/ideas.md`.

Отката не предполагается. Вернуть проверку означало бы вернуть и поле, и
опцию — то есть новый change с собственным обоснованием.
