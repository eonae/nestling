## Context

Скилл `@nestlingjs/agent-skill` 0.1.3 держится двумя проверками. `skill.spec.ts`
сверяет состав файлов, части `SKILL.md`, потолки строк и отсутствие кириллицы.
`snippets.spec.ts` сверяет блоки кода с файлами `snippets/`, а сами файлы
тайпчекаются проектом пакета против настоящих пакетов `@nestlingjs/*`.

Первый внешний прогон
([d/14](../../../docs/history/discussions/14-first-external-run.md)) показал
границу этих проверок. Сниппеты компилируются по одному, приложением их никто
не собирает, и два endpoint'а не проходят политику, которую объявляет
`snippets/app.ts`. Открытый вопрос записи
[ideas.md [2026-09-11]](../../../docs/decisions/ideas.md) — «проза расходится с
кодом, а компилятор этого не видит» — проявился не в прозе: разошлись сами
сниппеты.

Ограничения, в которых идёт работа:

- **Потолки строк.** `SKILL.md` — 250 строк, файл `references/` — 200.
  `endpoints.md` занимает 194, поэтому раздел об HTTP-форме ответа в него не
  влезает.
- **Каждый TypeScript-блок скилла — файл `snippets/`.** Новый блок кода требует
  нового сниппета; блок без пометки `<!-- snippet: … -->` роняет `yarn verify`.
- **Текст скилла английский, кириллица запрещена** — и в прозе, и в
  комментариях сниппетов.
- **Сниппеты компилируются проектом пакета** (`tsconfig.json` с
  `customConditions: ["testing"]`), а исполняются jest'ом через
  `moduleNameMapper` на исходники соседей.

## Goals / Non-Goals

**Goals:**

- Приложение из сниппетов проходит ASSEMBLE в `yarn verify`, а не только
  компилируется.
- Агент, прочитавший скилл, знает, из чего состоит проект и чем его запускают.
- HTTP-форма ответа описана там, где её ищут, вместе с правилом о `redirect:`.
- Каждый публикуемый пакет фреймворка назван в скилле хотя бы строкой.

**Non-Goals:**

- Справочник диагностик (`references/diagnostics.md`) — change 68.
- Шаблон проекта и генератор — отложены.
- Правки самого фреймворка — change'и 67–70.
- Проверка того, что рекомендованный `tsconfig.json` компилирует чужой проект,
  постоянным тестом: см. решение 5.

## Decisions

### 1. Сборку проверяет `snippets.spec.ts`, импортируя `app.ts` напрямую

Спека получает второй блок: `assembleTest(app, { config: vars({ API_TOKEN }) })`
для `app` из `../snippets/app.js`. Assembly доходит до WIRE, то есть проходит
BOOTSTRAP, ASSEMBLE, INIT и WIRE: политики проверены, контейнер построен,
`Database.acquire` выполнен, таблица диспетчеризации собрана.

Подмен нет, кроме конфигурации и логгера: смысл проверки в том, чтобы
собрался настоящий граф сниппетов. `overrides: [[RootLogger$, spyLogger().logger]]`
убирает вывод в консоль теста, не трогая граф. `config: vars({ … })` обязателен —
`apiToken` объявлен без умолчания.

Импортируется именно `app.ts`, а не сниппет `assemble-test.ts`: последний сам
объявляет `describe`/`it` и при импорте из спеки зарегистрировал бы свои тесты
вторым набором.

_Альтернатива — `checkTopologies` вместо `assembleTest`._ Отвергнуто: проверка
структурная, экземпляры не создаются, и провайдер юнита слоя из неё не виден.
Сборка дороже на миллисекунды и проверяет больше.

_Альтернатива — отдельный файл `snippets-assemble.spec.ts`._ Отвергнуто: обе
проверки об одном — о сниппетах как о наборе, — и разделение заставляет читателя
искать вторую.

### 2. Границу приложения задаёт достижимость от `app.ts`

Требование называет не список файлов, а правило: сниппет входит в приложение,
если `app.ts` достаёт его импортами. Сегодня это двенадцать файлов из
шестнадцати. Вне остаются четыре, каждый по своей причине:

| Сниппет | Почему вне |
| --- | --- |
| `minimal-app.ts` | запускает приложение верхнеуровневым `await … .run()` при импорте |
| `assemble-test.ts` | сам объявляет тесты |
| `handler-unit.ts` | сам объявляет тесты |
| `call-neighbour.ts` | показывает класс, который ни одна фича не объявляет |

Список в спеке был бы копией, которую надо править при каждом новом сниппете;
правило переживает правки.

### 3. `GetUser` и `ListUsers` берут `observability` целиком, без композиции

`GetUser` идёт без `pipeline:` — получает `pipeline: observability`.
`ListUsers` объявляет свой `makePipeline().pre(withRequestId())` — получает то
же `observability`.

Демонстрация `.pre(withRequestId())` при этом не теряется: `pipeline.md` собирает
`observability` ровно этим вызовом, а `compose` показывает там же на `authed`.
Дублировать её в `endpoints.md` было нужно, пока сниппеты не собирались; теперь
это расхождение, которое стоит `yarn verify`.

_Альтернатива — `compose(observability, makePipeline().pre(withRequestId()))`
в `ListUsers`._ Отвергнуто: политика проходит, но `withRequestId` встал бы
дважды, и читатель `endpoints.md` унёс бы это как образец.

### 4. Редирект входит в приложение сниппетов

`references/http.md` получает сниппет `redirect.endpoint.ts` — `GET`-декларация
с полем `redirect: 302` и хендлером, возвращающим `HttpResponse.redirect(url)`.
Endpoint объявлен в `UsersFeature` и собирается вместе со всеми: так обязательное
поле `redirect:` проверено сборкой, а не только компиляцией.

Метод `GET` выбран намеренно: политика `authed` в `app.ts` требует слой у
`POST`, `PATCH` и `DELETE`, и редирект после входа потянул бы за собой
аутентификацию там, где её по смыслу нет.

_Альтернатива — сниппет вне приложения._ Отвергнуто: правило про `redirect:`
ловится именно на сборке, и проверять его стоит тем же способом, каким его
встретит пользователь.

### 5. `setup.md` проверяется разово, кроме имён правил ESLint

Блоки `setup.md` — JSON, JavaScript и команды оболочки. Сниппетами они не
становятся: проверка сниппетов работает по TypeScript-блокам, а `tsconfig.json`
компилировать нечем.

Одно место всё же получает гарантию. Имена правил `@nestlingjs/<rule>` в блоке
`eslint.config.js` спека сверяет с ключами экспорта `@nestlingjs/eslint-plugin`:
переименование правила роняет `yarn verify`, а не всплывает у пользователя.
Плагин добавляется в `devDependencies` пакета через `workspace:*`.

Остальное (`target`, `lib`, скрипты) проверяется один раз при реализации —
сборкой отдельного проекта по написанному конфигу, — и результат записывается в
`tasks.md`. Постоянный тест здесь стоил бы запуска `tsc` над фикстурой в каждом
прогоне и ловил бы то, что меняется раз в год.

### 6. Таблица пакетов живёт внутри «Where to look next»

Шесть пакетов получают вторую таблицу в разделе «Where to look next», после
таблицы `references/`. Новой части второго уровня не появляется: `skill.spec.ts`
требует ровно пять заголовков `##`, и это требование остаётся.

### 7. `node:test` показан отдельным сниппетом, jest остаётся первым

`testing.md` получает сниппет `node-test.ts`: один тест на `node:test` и
`node:assert/strict`, собирающий то же `app`. Блок стоит после jest'а, а строка
про запуск называет `node --test --conditions=testing`.

Сниппет, а не текстовый блок: смысл `snippets/` в том, что форма кода
компилируется против настоящего API, и вариант раннера от этого не освобождает.

## Risks / Trade-offs

- **Сборка в спеке делает проверку сниппетов медленнее и ярче падает.** Ошибка
  в любом из двенадцати файлов теперь роняет тест сборки, а не только
  тайпчек → это и есть цель; сообщение ASSEMBLE называет фичу, класс и причину,
  поэтому диагностика остаётся читаемой.
- **`Database.acquire` исполняется в тесте.** Ресурс держит массив в памяти и
  I/O не делает → `await using` закрывает сборку, `spyLogger` глушит вывод.
- **Рекомендованный `tsconfig.json` может разойтись с тем, что работает.**
  Репозиторий собирает пакеты с `moduleResolution: "bundler"` из-за `.d.cts`
  zod v4 (TS1542), и для чужого проекта это надо проверить отдельно →
  открытый вопрос 1, проверка входит в задачи.
- **Скилл растёт: десять файлов вместо восьми.** Тело `SKILL.md` попадает в
  контекст целиком, `references/` — по требованию → `SKILL.md` прибавляет около
  пятнадцати строк из восьмидесяти восьми свободных, потолки не двигаются.
- **`endpoints.md` остаётся у потолка.** После переноса раздела об
  `HttpResponse` там освобождается несколько строк → следующая тема HTTP пойдёт
  в `http.md`, а не обратно.

## Open Questions

1. **`module: "nodenext"` или `"esnext"` + `moduleResolution: "bundler"` в
   `setup.md`.** `nodenext` проверяет специфаеры `.js` компилятором, но zod v4
   отдаёт `.d.cts`, который в репозитории даёт TS1542. Решается при реализации:
   собрать проект по обоим конфигам на актуальных zod и TypeScript, записать
   результат; при чистой сборке рекомендуется `nodenext`, иначе `bundler` с
   одной фразой о причине.
2. **Нужны ли `references/outbox.md` и `references/client.md`** или достаточно
   строки в таблице пакетов. Решать по второму внешнему прогону
   ([ideas.md [2026-09-12]](../../../docs/decisions/ideas.md), открытый вопрос 1).
3. **Станет ли `node:test` основным вариантом `testing.md`.** Для проекта на
   Node 24 без бандлера он проще jest; в этом change'е jest остаётся первым
   (там же, открытый вопрос 2).
