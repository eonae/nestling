## Context

Standard Schema разводит две роли, которые до сих пор играл один интерфейс.
Первая роль — **граница**: ядро принимает схему от приложения и вызывает
`~standard.validate`, не зная вендора. Вторая роль — **авторство**: сам
фреймворк пишет схемы для своих секций конфига и своих фактов. Правило было
одно на обе роли, и авторство платило по счёту границы.

Счёт видно в коде. Четыре файла `src/schema.ts` — в `inbox`, `outbox`,
`drizzle.pg` и `subscriptions` — содержат почти дословно совпадающие
литералы `StandardSchemaV1` с вендором `nestling`. В `@nestlingjs/app` тот
же приём повторяют три хелпера секций ядра: `enumeration` в логгере,
`milliseconds` в пробах, `dispatchSchema` в портах. Ни одна из этих схем не
конвертируется в JSON Schema, поэтому снимок конфига описывает их исходом
`unconvertible`, а чейнинга у них нет: граница передаётся позиционным
аргументом (`int(500, 1)`).

Ограничения, в которые вписывается решение:

- **Публичный API вендора не называет** — это граница, и она остаётся.
  Приложение на valibot собирается и работает.
- **Циклов между пакетами нет.** `@nestlingjs/schema.zod` зависит от
  `@nestlingjs/app` (тип `SchemaDocConverter`), поэтому обратная
  зависимость невозможна.
- **Совместимости не существует** — проект в стадии проектирования,
  старое API удаляется целиком.

## Goals / Non-Goals

**Goals**

- Один дом для всего, что фреймворк делает с zod.
- Схемы, которые пишет фреймворк, конвертируются штатным конвертером.
- Конвертер zod не называется в опциях там, где он и так подразумевается.
- `info` документа OpenAPI записан в одном месте.

**Non-Goals**

- Команда фреймворка для генерации документа (`nestling openapi`).
- Конвертер-умолчание у `describeConfig` и `check`.
- Переименования из change 86 (`build`, «шаг»).
- Обратная совместимость в любом виде.

## Decisions

### 1. Граница проходит по публичному API, а не по списку зависимостей

Правило: ни один экспортируемый тип, параметр или возвращаемое значение не
называет zod. Зависимость пакета от zod — выбор реализации; приложению она
видна только строкой в `node_modules`.

Исключение ровно одно и оно названо именем пакета: `@nestlingjs/schema.zod`
называет zod в `ZodConverterOptions`, потому что это и есть пакет вендора.

Проверка механическая, но идёт по **экспортам барреля**, а не по всем
файлам объявлений: `scripts/boundary/public-api-validator.mjs` перечисляет
имена `dist/index.d.ts` каждого публикуемого пакета и ищет вендора в их
типах. Формулировка «в `dist/*.d.ts` слова `zod` нет ни в одной строке»
неверна и была неверна до этого change'а: секция конфигурации выводит свой
тип из схемы, поэтому `zod` стоит в `config.d.ts` у `transport.http` и
`transport.nats`. Секции при этом остаются внутренними именами — из
барреля выходит только `.keys`.

Одна настоящая утечка этим уточнением не закрывается, и её приходится
чинить: `makeEvent` держит схему параметром публичного типа
(`EventOperation<I, …>`), а факты `outbox` и `subscriptions` — публичные
экспорты. Поэтому их рекорды объявляются нейтральным типом:

```typescript
const publishedSchema: StandardSchemaV1<unknown, OutboxPublishedFact> =
  z.object({ … });
```

Значение остаётся zod-схемой — вендор `zod`, штатный конвертер её
переводит, — а тип вендора не называет. Проверку компилятор делает сам:
это обычное присваивание, а не приведение.

*Альтернатива — peer-зависимость zod у всех пакетов.* Отвергнута: она
превращает выбор реализации в требование к приложению, то есть ровно в то,
от чего граница и защищает.

### 2. Пустую строку считает отсутствующим значением ядро, а не схема

Сегодня каждый рукописный хелпер начинается с `isBlank(value)`: `KEY=` в
окружении означает «ключ не задан», и вместо пустой строки поле получает
умолчание. Открытый билдер zod так не умеет: `.default()` срабатывает
только на `undefined`, а `z.coerce.number()` превратит `''` в ноль.

Поэтому правило переезжает в ядро, в одну точку — туда, где сырое значение
ключа отдаётся схеме поля (`config/project.ts` и `config/load.ts` фазы 0).
Пустая строка становится `undefined` до вызова `validateSync`.

Семантика поиска не меняется: значение по-прежнему берётся у первой
привязки, которая ключ покрывает. Пустая строка не «пропускает ход» и не
уводит читалку к следующему источнику — иначе `KEY=` в локальном файле
молча открывало бы дорогу значению с машины.

*Альтернатива — `z.preprocess(blankToUndefined, …)` внутри билдера.*
Отвергнута: `preprocess` отдаёт `ZodPipe`, у которого нет ни `.min()`, ни
`.default()`, и чейнинг — то единственное, ради чего билдеры и заводятся.

### 3. Билдеров два, и оба — открытые значения zod

```typescript
export const int = () => z.coerce.number().int();
export const flag = () => z.union([z.boolean(), z.stringbool()]);
```

Границу и умолчание дописывает вызывающий: `int().min(1).default(500)`.
Умолчание идёт последним, потому что оно и есть последнее звено цепочки.

`str()` из `drizzle.pg` не переезжает: обязательная непустая строка это
`z.string().min(1)`, и заводить для неё имя значило бы изобретать
заменитель ровно там, где решение велит его не изобретать. По той же
причине рекорды фактов `outbox` и `subscriptions` пишутся `z.object({ … })`
на месте объявления, а конструктора `record()` не остаётся.

Аннотация `jsonSchema()` вокруг рекордов исчезает вместе с ними: она стояла
там потому, что вендора `nestling` не понимает ни один конвертер.

### 4. Секции ядра — на zod, конвертер в ядро не приходит

`@nestlingjs/app` объявляет `zod` зависимостью и пишет свои три секции на
нём: `z.enum(['debug', 'info', 'warn', 'error']).default('info')` вместо
рукописного `enumeration`, `int().min(0).default(2000)` вместо
`milliseconds`. Текст отказа приходит от валидатора.

Билдеры ядро берёт не из `schema.zod`, а пишет цепочку zod напрямую:
`schema.zod` зависит от `@nestlingjs/app`, и обратная стрелка замкнула бы
цикл. Двух строк ради этого не жалко — секций три, полей пять.

Конвертер в ядро не приходит по той же причине и ещё по одной:
[config.md §8](../../../docs/design/config.md) оставляет список конвертеров
данными вызывающего, и без `converters` снимок конфига остаётся прежним.
Меняется не сигнатура `describeConfig`, а конвертируемость её входа.

*Альтернатива — оставить секции ядра рукописными и приписать им
`jsonSchema()`.* Отвергнута: JSON Schema и проверка писались бы руками
порознь и разъезжались бы молча.

### 5. Умолчание конвертера — «добавить или заменить», одной функцией

`@nestlingjs/schema.zod` отдаёт функцию разрешения списка:

```typescript
withZodDefault(converters?: readonly SchemaDocConverter[]): readonly SchemaDocConverter[]
```

Она дописывает `zodConverter()` к списку вызывающего и пропускает этот шаг,
если в списке уже есть конвертер вендора `zod`. Отсюда обе половины
обещания: приложение на valibot передаёт свой конвертер и получает **оба**,
а приложение, которому нужен `z.toJSONSchema` со своими опциями, передаёт
`zodConverter({ … })` и заменяет умолчание.

Зовут её три потребителя JSON Schema — `@nestlingjs/openapi`,
`@nestlingjs/mcp` и `@nestlingjs/transport.cli` — каждый в той же точке,
где сегодня зовёт `assertConverters`. Проверка на дубли вендора внутри
списка вызывающего остаётся: `withZodDefault` её не отменяет, а идёт после.

Следствие для диагностики: `converters: []` больше не оставляет потребителя
без конвертера, поэтому текст «конвертер не передан» перестаёт быть верным.
Отказ на схеме чужого вендора называет вендор и предлагает передать его
конвертер списком.

*Альтернатива — `converters` заменяет список целиком.* Отвергнута:
приложение, дописавшее конвертер valibot, теряло бы zod, хотя половина его
схем на zod.

### 6. Документ строит объявленный плагин

`openapi(options)` возвращает значение с методом:

```typescript
export interface OpenApiPlugin extends Plugin {
  document(discovery: EndpointDiscovery): OpenApiDocument;
}
```

Скрипт CI становится строкой: `appOpenapi.document(app.discover(args))`.
Опции у плагина уже есть, поэтому `info` записан в одном месте, а общий
экспорт `openapiOptions` примера исчезает вместе с полем `converters` у
`mcp({ … })`.

Метод и фабрика провайдера зовут одну внутреннюю функцию, поэтому документ
из артефактов CI и документ по `GET /openapi.json` совпадают по построению.
Публичное имя `buildOpenApiDocument` уходит из барреля: поверхностей пакета
становится две — `openapi(options)` и `OpenApiDocument$`.

Метод работает и тогда, когда плагин не попал в состав: значение живёт в
модуле приложения, а `Docs.when(appOpenapi)` решает только судьбу
endpoint'а. Документ для контура с выключенной документацией строится тем
же вызовом.

*Альтернатива — `buildOpenApiDocument(discovery)`, ищущая плагин среди
единиц состава.* Отвергнута: `EndpointDiscovery` пришлось бы пополнить
значениями единиц (`ResolvedBundle` ссылку на исходный плагин сегодня
теряет), а поиск по своему символу — это поиск, то есть ровно та магия, от
которой фреймворк отказывается. И документ переставал бы строиться при
`docs=off`.

### 7. `@nestlingjs/models` удаляется целиком

Каталог `packages/nestling.models` удаляется. Три имени — `fromType`,
`fromScratch`, `makeModel` — переезжают в `@nestlingjs/schema.zod` вместе
со своими тестами и разделами README. Импортёров у них нет ни одного, кроме
таблицы пакетов в `docs/README.md` и перечня в скилле агента.

Имя `@nestlingjs/models` в реестр больше не выходит: ни tombstone-версии,
ни редиректа.

### 8. zod — обычная зависимость у авторов схем, peer — только у `schema.zod`

Пакет, который **пишет** схемы (`app`, `inbox`, `outbox`, `drizzle.pg`,
`subscriptions`), объявляет `zod` в `dependencies` — тем же способом, каким
это уже делает `@nestlingjs/transport.http`. Пакет, который **конвертирует
чужие** схемы (`schema.zod`), держит `zod` в `peerDependencies`: он обязан
работать той же копией, что и приложение.

Расхождение манифеста с импортами ловит правило `dependency-list` из
`@nestlingjs/eslint-plugin`.

### 9. Что остаётся рукописным

`details` отказов ядра (`operations/kernel-fails.ts`), схема отчёта проб
(`transport.http/probes.ts`) и переключатели `@nestlingjs/container`
остаются литералами `StandardSchemaV1`. Причины разные и обе не про
нейтральность: схема отчёта проб не проверяет ничего (отчёт строит тот же
процесс), а `z.custom<T>()` непредставим в JSON Schema; контейнеру
зависимостей не добавляется, у него их две и обе свои.

Отказы `@nestlingjs/mcp` (`errors.ts`, хелпер `singleField`) на zod
переезжают: пакет и так получает `schema.zod`, а `singleField` — заменитель
`z.object({ code: z.number() })` и ничего кроме.

## Risks / Trade-offs

- **Две копии zod в дереве зависимостей** → конвертер приложения получит
  схему секции, созданную другой копией. Проверяется тестом: конвертер
  переводит секцию пакета в JSON Schema, и результат сверяется с ожидаемым.
  `^4.0.0` у всех пакетов даёт одну копию при обычной установке.
- **Приложение на другом валидаторе тянет zod через ядро** → это цена
  решения, принятая явно: граница обещает, что приложение **пишет** схемы
  на чём хочет, а не что zod не окажется в `node_modules`.
- **Правило пустой строки живёт в одном месте и невидимо на месте
  объявления** → покрывается тестом на секцию с `KEY=` и строкой в
  `design/config.md`.
- **Умолчание конвертера прячет ошибку конфигурации** → раньше пустой
  список означал «я забыл конвертер» и давал понятный отказ; теперь такой
  отказ приходит только на схеме чужого вендора. Диагностика переписывается
  так, чтобы называть вендор и путь к схеме.

## Migration Plan

Порядок работ, каждый шаг оставляет репозиторий зелёным:

1. `@nestlingjs/schema.zod`: билдеры `int`/`flag`, `withZodDefault`, модели
   из `models`, переписанная шапка. Удаление `packages/nestling.models`.
2. Правило пустой строки в ядре плюс тест.
3. Секции ядра на zod; удаление `enumeration`, `milliseconds`,
   `dispatchSchema`.
4. Секции и факты сателлитов на zod; удаление четырёх `src/schema.ts` и
   `singleField` в `mcp`.
5. Умолчание конвертера у `openapi`, `mcp`, `transport.cli` и новые тексты
   диагностики.
6. `OpenApiPlugin.document()`, уход `buildOpenApiDocument` из барреля.
7. Примеры: `app-with-http` (`app.ts`, `openapi.ts`, `mcp`), `simple-cli`.
8. Документация: `design/schemas.md`, `design/config.md`, `docs/README.md`,
   главы гайда, рецепт MCP, README семи пакетов на обоих языках, скилл
   агента.

Отката не предусмотрено: change ломающий, ветка сливается целиком.

## Open Questions

Открытых вопросов не осталось. Два решены при подготовке этого документа:

1. **Форма документа из discovery** (открытый вопрос записи ideas.md) —
   метод у плагина, решение 6.
2. **Секции ядра** — переезжают на zod, решение 4; `@nestlingjs/app`
   получает зависимость, конвертер не получает.
