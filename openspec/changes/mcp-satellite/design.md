## Context

Декларация операции уже содержит всё, из чего состоит определение
MCP-инструмента. `makeRequest` требует `name`, принимает `input`, `output`,
`errors` и секцию `doc`; определение инструмента в протоколе требует `name`,
`inputSchema` и принимает `description`, `outputSchema` и `annotations`.
Соответствие полное, и переводить приходится только схемы — из Standard
Schema в JSON Schema.

Механизм не новый. `@nestlingjs/openapi` читает декларации и отдаёт документ,
`@nestlingjs/client` читает те же декларации и отдаёт типизированный клиент.
Сателлит MCP — третий потребитель того же значения.

Две особенности ядра определяют форму решения:

- **Вызыватель — член семейства DI-токенов.** `Operation.caller` создаёт узел
  графа только тогда, когда кто-то объявил его в списке зависимостей
  (`packages/nestling.operations/src/families.ts`). Операция, которую никто не
  вызывает, узлов не создаёт. Поэтому «взять все операции из discovery и
  позвать любую» невыполнимо: чтобы звать, надо объявить зависимость.
- **`Dispatch` плагину недоступен.** Таблица маршрутов строится на фазе WIRE
  на каждый транспорт и передаётся транспорту; DI-токена у неё нет
  (`packages/nestling.app/src/transport/dispatch.ts`). Плагин не может
  исполнить чужой endpoint по паттерну.

Плагин `openapi(...)` — образец формы: параметризованное значение, провайдер
на фазе ASSEMBLE, собственный служебный endpoint с `doc.hidden`, опция
`pipeline` на случай политики корня.

## Goals / Non-Goals

**Goals:**

- Определение инструмента выводится из декларации операции; второго описания
  для агента не пишется.
- Состав инструментов объявлен списком и виден в диффе.
- Отказ операции попадает к агенту отказом, а не исключением протокола.
- Ошибка объявления обнаруживается на фазе ASSEMBLE, до `serve`.
- Зависимостей рантайма у пакета нет.

**Non-Goals:**

Перечислены в [proposal.md](./proposal.md), раздел «Non-goals». Коротко:
только `tools`, только вид `request`, только ответ на запрос клиента, без
аутентификации, без stdio, без полей MCP в секции `doc`.

## Decisions

### 1. Инструмент — производное от `request`-операции, выбранное списком

```typescript
mcp({
  server: { name: 'users-service', version: '1.0.0' },
  converters: [zodConverter()],
  tools: [
    tool(CreateUser, {
      description: 'Создать пользователя. Адрес почты должен быть свободен.',
      annotations: { destructiveHint: false, idempotentHint: false },
    }),
    tool(FindUsers, { annotations: { readOnlyHint: true } }),
  ],
})
```

`tool(Operation, options?)` — чистая функция от операции к значению-объявлению.
Имя инструмента по умолчанию — `Operation.name` с точками, заменёнными на
подчёркивания (`users.create` → `users_create`): протокол требует имени из
`[a-zA-Z0-9_-]`. Описание по умолчанию — `doc.description ?? doc.summary`.
`options.name` и `options.description` перекрывают умолчание.

**Почему список, а не discovery.** Вызыватель создаётся объявленной
зависимостью, поэтому список инструментов — это и есть список зависимостей
плагина. Форма «все операции, помеченные флагом в `doc`» потребовала бы
разрешать DI-токены, которых нет в графе, и завела бы в секцию `doc` поле,
осмысленное только для MCP.

Второй довод содержательный. Открыть агенту весь внутренний интерком по
умолчанию — не то поведение, которое хочется получить по невнимательности.
Выбор объявляется.

**Почему только `request`.** У `command` и `event` вызыватель — эмиттер:
`emit` возвращает `Promise<void>` по факту доставки, а не обработки, и
отказа у него нет. Инструменту нужен результат. Операция, которую агент
должен звать, объявляется через `makeRequest`.

**Отвергнуто: инструмент вне операции (`makeTool`).** Он получился бы вторым
механизмом объявления с теми же полями и без пайплайна, политик и проверки
отказов на выходе. Инструмент, которого нет в HTTP API, выражается уже
имеющимися средствами: операция без секции `http:`, реализованная
`implement`. `tool(...)` выставляет её агенту, и она проходит те же
проверки, что остальные endpoint'ы.

### 2. Вызов — через `Operation.caller`, как у соседней фичи

Плагин собирает список зависимостей из `tools` и объявляет провайдер:

```typescript
factoryProvider(
  McpTools$,
  (...ports: Port<AnyRequestOperation>[]) => bindTools(tools, ports, options),
  tools.map((declared) => declared.operation.caller),
)
```

Вызов инструмента — это `port.call(input, meta)` с тем же `meta`, который
endpoint `/mcp` получил от транспорта. Отмена и срок доставки идут сквозь:
клиент разорвал соединение — `AbortSignal` дошёл до операции.

Для агента это означает, что инструмент проходит ровно тот путь, что и
обычный вызов соседней фичи: пайплайн реализации, её слои, её политики.
Отдельного пути исполнения в пакете нет.

### 3. Протокол своей реализацией, SDK в `devDependencies`

`@modelcontextprotocol/sdk@1.30.0` объявляет семнадцать зависимостей, среди
них `express`, `hono`, `@hono/node-server`, `cors`, `express-rate-limit`,
`jose`, `ajv` и `zod`. Они ставятся все, даже если импортируется один
`server/index.js`. У `@nestlingjs/transport.http` зависимостей две, у ядра
ноль; сателлит с двумя HTTP-фреймворками в дереве выпадает из этого ряда.
Транзитивная зависимость от zod вдобавок сняла бы у пакета то свойство,
которое `@nestlingjs/openapi` держит тестом.

Поэтому протокол реализуется в пакете, а SDK стоит в `devDependencies` и
работает доказательством:

- **Сверка типов.** `mcp.type-test.ts` присваивает наши `McpToolDefinition` и
  `McpCallToolResult` типам `Tool` и `CallToolResult` из
  `@modelcontextprotocol/sdk/types.js`. Расхождение — ошибка компиляции.
- **Интеграционный прогон.** Тест поднимает приложение, соединяет с ним
  `Client` из SDK по HTTP и вызывает `listTools()` и `callTool()`. Ответ
  сервера проверяет настоящая реализация клиента, а не наши ожидания.

Объём собственной реализации — конверт JSON-RPC 2.0 и пять методов:
`initialize`, `notifications/initialized`, `ping`, `tools/list`,
`tools/call`.

**Отвергнуто: SDK в `dependencies`.** Дешевле в коде и дороже в установке;
цена платится каждым, кто ставит пакет.

**Отвергнуто: отказаться от SDK вовсе.** Тогда соответствие протоколу
подтверждали бы только наши тесты, написанные по нашему же прочтению
спецификации. Клиент SDK в тесте — независимая проверка, и стоит она одной
строки в `devDependencies`.

### 4. Транспорт — один endpoint `POST /mcp`, без потока событий

Плагин объявляет один endpoint. Тело запроса — сообщение JSON-RPC, ответ —
сообщение JSON-RPC со статусом `ok`. Нотификация (сообщение без `id`)
отвечает статусом `accepted` без тела, как требует спецификация.

`GET /mcp` не объявляется: поток событий нужен серверу, который сам
инициирует сообщения, а таких сообщений в объёме нет. Клиент получит `405`
от маршрутизатора — это законный ответ для сервера без потока.

**Почему не `StreamableHTTPServerTransport` из SDK.** Он принимает
`IncomingMessage` и `ServerResponse`, а `ctx.raw` таких полей не несёт
(`packages/nestling.app/src/pipeline/core/types/raw.ts`) и нести не должен:
привязка к `node:http` в контексте закрыла бы сателлиту путь к другим
транспортам. Форма «endpoint принимает сообщение, endpoint возвращает
сообщение» от рантайма не зависит.

Идентификатор сессии возвращается заголовком через `HttpResponse`, читается
из `ctx.raw.attributes`. Заголовок `MCP-Protocol-Version` сверяется со
списком поддерживаемых версий; расхождение — отказ категории `bad_request`.

### 5. Сессия — ресурс, карта закрывается на SHUTDOWN

```typescript
@Resource([McpTools$, McpOptions$])
class McpSessions {
  static async acquire(tools: BoundTool[], options: McpOptions) { /* ... */ }
  async release() { /* ... */ }
}
```

Сессия хранит согласованную версию протокола и сведения о клиенте из
`initialize`. Роль `@Resource` выбрана потому, что у карты есть время жизни
приложения и её нужно закрыть: `release` вызывается на SHUTDOWN, и висящих
сессий после остановки не остаётся.

Ограничения на сессии — предельное число и срок бездействия — объявляются
опциями плагина со значениями по умолчанию. Без них карта росла бы от
каждого нового клиента.

### 6. Схемы — те же конвертеры, что у OpenAPI

`inputSchema` и `outputSchema` инструмента получаются вызовом
`leafJsonSchema(converters, leaf, { io })` — публичного помощника ядра,
которым пользуется `@nestlingjs/openapi`. Пакет не зависит ни от одного
валидатора: конвертер приходит данными в `converters:`.

Протокол требует, чтобы `inputSchema` был объектной схемой. Операция со
входом-примитивом или потоком инструментом быть не может; это проверяется
при сборке.

### 7. `Ok` и `Fail` — два исхода вызова инструмента

Успех отдаётся `structuredContent` со значением `Ok` плюс `content` с тем же
значением в виде JSON-текста: второе поле нужно клиентам, которые
структурированный ответ не читают.

Отказ отдаётся `isError: true` и текстом, в котором названы `code` и
`message` отказа; `details` уходит в `structuredContent`. Исключением
протокола отказ не становится: отказ — часть объявленного контракта
операции, и агент должен его прочитать и учесть, а не получить обрыв.

Неожиданная ошибка (не `Fail`) превращается ядром в `internal_error` ещё в
пайплайне, и до сателлита доходит обычным отказом.

### 8. Диагностика — на фазе ASSEMBLE

Определения инструментов строятся провайдером, а провайдер зовётся жадным
контейнером на фазе ASSEMBLE. Поэтому валит старт, а не первый запрос
агента:

- имя инструмента не уникально в списке;
- имя не соответствует `[a-zA-Z0-9_-]{1,128}` после подстановки;
- схема входа не переводится в JSON Schema (конвертера нет или схема
  непредставима);
- схема входа не объектная;
- у инструмента нет ни описания, ни `doc.summary` — агент выбирает
  инструмент по описанию, и пустое описание делает его бесполезным.

Форма та же, что у `@nestlingjs/openapi`: нарушения копятся и сообщаются
одним списком, а не первым попавшимся.

### 9. Границы пакета

Тест границы перечисляет разрешённые импорты, как в других пакетах.
`@nestlingjs/mcp` импортирует `@nestlingjs/app`, `@nestlingjs/operations`,
`@nestlingjs/transport.http` и модули Node. Валидаторов, SDK и HTTP-серверов
среди импортов рантайма нет.

## Risks / Trade-offs

- **Версия протокола уйдёт вперёд, своя реализация отстанет.** → Список
  поддерживаемых версий — константа пакета; интеграционный прогон клиентом
  SDK ломается на несовместимости, а обновление SDK в `devDependencies`
  становится сигналом. Пакет объявляет ту версию, которую реализует, и
  согласует её в `initialize`.
- **Агент получит доступ к операции, которую звать не должен.** → Состав
  задан списком и виден в диффе; `annotations` сообщают агенту характер
  инструмента. Аутентификацию закрывает `auth-layer` (строка 78 roadmap).
- **Схема не переводится в JSON Schema.** → Падение на ASSEMBLE с указанием
  инструмента и слота, как у генератора OpenAPI. Обходного пути нет: агенту
  нельзя показать инструмент, вход которого не описан.
- **Сессии накопятся.** → Предельное число и срок бездействия опциями со
  значениями по умолчанию; превышение предела — отказ на `initialize`.
- **Своя реализация JSON-RPC содержит дефект, которого нет у SDK.** →
  Интеграционный прогон настоящим клиентом плюс тесты на конверт: неизвестный
  метод, сообщение без `id`, дефектный JSON, неизвестная версия протокола.
- **Первая внешняя проверка ляжет на пример.** → `examples/app-with-http`
  подключает плагин, и снимок его определений инструментов сверяется тестом.

## Migration Plan

Миграции нет: пакет новый, публичных экспортов не меняет. Порядок работ —
в [tasks.md](./tasks.md).

## Open Questions

1. **`outputSchema` в определении инструмента.** Протокол его принимает, и у
   операции схема выхода есть. Открыт вопрос, объявлять ли её всегда: клиент,
   объявивший `outputSchema`, обязан отдавать `structuredContent`, и операция
   с выходом-потоком под это не подходит. Решить при реализации по составу
   форм io.
2. **Имя инструмента по умолчанию.** `users.create` → `users_create`
   читается, но теряет различение, если в списке окажутся `users.create` и
   `users_create`. Проверка уникальности это поймает; вопрос — сообщать ли
   при этом, что причина в подстановке.
3. **Срок бездействия сессии.** Значение по умолчанию выбирается при
   реализации; кандидат — пять минут, как у большинства реализаций
   Streamable HTTP.
