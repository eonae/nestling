## Провайдеры и токены

Зависимости объявляются **явным массивом токенов** — никакого
`reflect-metadata` и инжекта «по типу»:

```typescript
@Injectable([UserRepository, ILogger('users')])
export class UserService {
  constructor(
    private repo: UserRepository,
    private logger: ILoggerService,
  ) {}
}
```

- **Класс — сам себе токен**; `@Injectable([deps])` — стандартный
  ES-декоратор (не `experimentalDecorators`), несущий только список deps.
- **Интерфейсы и значения** — через явные токены (`token<T>(id)`) и
  примитивы `classProvider(token, Class)` / `factoryProvider(token, fn, deps)` /
  `valueProvider(token, value)`. Это низкоуровневые кирпичи контейнера
  (интерфейс-токены, конфиг, тесты), а не отдельный «стиль».
- Цена дублирования списка (декоратор + конструктор) — осознанный trade-off
  за отсутствие магии компилятора.

## Жадная сборка

`build()` инстанцирует **весь граф сразу**: топологическая сортировка,
проверка циклов, недостающих узлов и (opt-in) видимости — всё падает на
старте, не в рантайме. `forwardRef` не существует как понятие. Граф полный
и интроспектируемый: визуализация, атрибуция узлов модулям, топологический
init/destroy.

**Недостающие зависимости перечисляются разом.** Проверка идёт до
инстанциации: обход `deps` всех провайдеров, сбор токенов без провайдера с
потребителем каждого, одна ошибка со списком — так же, как это давно делает
`strictExports`. Строгая сборка обязана рассказать всю историю, а не первую
её строку.

Lifecycle-хуки провайдеров: `@OnInit` (захват ресурсов), `@OnStart`
(go-live), `@OnDestroy` (освобождение, в реверсе топосорта) — семантика фаз
в [composition.md](./composition.md). Lifecycle — свойство классов-провайдеров;
у factory-провайдеров его нет.

## Шов тестового корня: подстановка и прунинг

`ContainerBuilder` принимает две опции, помеченные как шов тестового корня:
`overrides` (пары «токен → значение») и `familyOverrides` (подмена рецепта
семейства). Публичный `assemble` их не пробрасывает и никогда не будет —
подстановка есть свойство тестового прогона ([testing.md](./testing.md)).

Порядок в `build()` — единственное, где всё это имеет значение:

1. раскрытие фабрик провайдеров модулей;
2. **подмена рецептов семейств** — до материализации, иначе члены родились
   бы по боевому рецепту;
3. материализация членов семейств (fixpoint);
4. **подстановка**: провайдер токена заменяется на `{ provide, useValue }` с
   сохранением атрибуции к модулю — иначе `strictExports`, визуализация и
   диагностика начали бы врать про владельца;
5. **прунинг** осиротевших поддеревьев;
6. материализация агрегатов `Family.all` — **после** прунинга, по оставшимся
   членам;
7. перечень недостающих зависимостей, инстанциация, граф, циклы,
   `strictExports`.

Fail-fast подстановки: override токена, для которого провайдера нет
(переименовали провайдер → тест не мокает молча пустоту; для членского
токена — отдельная подсказка, что член становится узлом графа только по
факту инжекта) и два override'а одного токена («последний выигрывает» здесь
ничем не лучше явного отказа).

**Алгоритм прунинга.** Пусть `deps` — отношение зависимостей до подстановки,
`deps′` — после (у заменённых токенов исходные `deps` запоминаются). Ребро на
`Family.all` при обходе разворачивается в рёбра ко всем текущим членам —
иначе потребитель агрегата терял бы своих членов.

- `R` = токены с нулевой входящей степенью в объединении `deps ∪ deps′`,
  плюс токены, недостижимые из них по объединению (участники циклов — они
  обязаны дойти до детектора циклов, а не исчезнуть);
- `Keep` = достижимые из `R` по `deps′`;
- прунятся `All \ Keep`: провайдер не инстанцируется, узла в графе нет,
  `@OnInit`/`@OnDestroy` не выполняются. Заменённый узел не прунится.

Корней как понятия в жадном контейнере нет — зарегистрирован, значит нужен;
объединение `deps ∪ deps′` даёт ровно нужную асимметрию: пул **не** корень
(на него смотрел репозиторий *до* подстановки), а после подстановки на него
не смотрит никто. Отсюда же несущий инвариант: **без `overrides`
`deps = deps′`, из узлов нулевой входящей степени достижим каждый узел
⇒ `Keep = All`, прунинг тождественен** — боевая сборка не меняется ни на
один узел. Список id выпавших узлов отдаётся наружу (`app.pruned`): «почему
мой `@OnInit` не выполнился» должно отвечаться данными, а не чтением
исходников.

## Модули — plain objects

Модуль — значение: метка принадлежности, единица упаковки, метаданные для
графа. Рантайм-инкапсуляции (нестовские `exports`) нет — **видимость решают
ES-модули**: не экспортировал токен из пакета — снаружи его физически нечем
запросить.

```typescript
export const OrdersModule = makeModule({
  name: 'module:orders',
  providers: [OrdersService, OrdersRepository],
  endpoints: [CreateOrder],          // декларации — значения (endpoints.md)
});
```

- **Идентичность модуля — его значение.** То же значение, встреченное
  повторно (по `imports`, в корне и в фиче, двумя фичами), регистрируется
  один раз. Имя же — **ключ атрибуции** провайдеров, экспортов и эндпоинтов,
  поэтому два **разных** значения под одним именем есть ошибка сборки с
  указанием имени и починок: разделить одно значение импортом, назвать
  конфигурации по-разному, проверить дубли пакета в зависимостях. Тихая
  победа первого невозможна — вместе со вторым значением исчезли бы его
  провайдеры и ручки. Сравнение ссылочное: структурного сравнения опций и
  мемоизации по аргументам нет — это была бы рантайм-магия.
- **Параметризованный модуль — просто функция**, возвращающая модуль:
  `logging({ service: 'orders-api' })`. Понятия `DynamicModule` /
  `forRoot` / `forRootAsync` не нужны. Канон: результат создаётся
  **значением один раз** и разделяется импортом — повторный вызов той же
  фабрики (даже с теми же опциями) даёт другое значение под тем же именем и
  роняет сборку. Что параметр, а что конфиг-секция модуля —
  [composition.md §5](./composition.md).
- **`strictExports`** (opt-in) — build-time проверка рёбер готового графа
  против деклараций exports: lint на сборке, не рантайм-ACL.
- Дискавери провайдеров, endpoints и транспортов — **обходом дерева
  зарегистрированных модулей**; глобальных реестров-при-импорте нет. Обход
  дискавери применяет то же правило идентичности, что и билдер, — «что
  обнаружено» не расходится с «что собрано».

## Token families

Семейство токенов — один рецепт, много инстансов по ключу. Покрывает
параметризованные провайдеры, consumer-aware инжект и multi-injection —
статически, на сборке:

```typescript
const ILogger = makeTokenFamily<ILoggerService, [scope: string]>('Logger');

// инфраструктурный модуль регистрирует ОДИН рецепт на семейство:
familyProvider(ILogger, (scope) =>
  factoryProvider(ILogger(scope), (cfg) => new Logger(scope, cfg), [IConfig]));

// бизнес-код запрашивает члена как обычную зависимость:
@Injectable([UserService, ILogger('users')])
class CreateUserEndpoint { /* ... */ }
```

- `ILogger('users')` — мемоизированный токен-член (`Logger:users`); билдер
  собирает все члены, упомянутые в deps, и материализует их рецептом —
  обычные узлы графа, жадно.
- **`.auto`** — consumer-aware сахар: `ILogger.auto` резолвится в
  `ILogger('CreateUserEndpoint')` в момент регистрации (потребитель известен
  статически). Кейс Nest `transient + INQUIRER` без transient-скоупа.
- **`.all`** — multi-injection: агрегирующий токен `TokenString<readonly T[]>`.
  Вклады — обычные провайдеры с членскими токенами
  (`classProvider(IHealthCheck('db'), DbHealthCheck)`), регистрируются
  независимо разными модулями; билдер на `build()` создаёт синтетический
  узел-агрегат с массивом инстансов — заморожен, порядок = порядок регистрации
  вкладов (явные, затем материализованные фикспоинтом), пустое семейство даёт
  `[]`. Узел безмодульный, поэтому под `strictExports` вклад требует
  `exports` у своего модуля. Не выбрал фичу → её вкладов нет в массиве — тем же
  механизмом, что и всё остальное. Никакого `multi: true` на общем токене:
  каждый вклад индивидуально адресуем.
- Конфиг — частный случай семейств ([config.md](./config.md)); on-demand
  клиенты (`GrpcClient(server)` + unbound-ключи) — тоже.

## Kernel space / user space

Граница как в ОС: **kernel** (токены не экспортируются) — источники конфига,
транспорты, шина и port-клиенты, машинерия графа и lifecycle; **user space** —
сервисы, endpoints, контракты, конфиг-как-данные. Пересечение границы — только
через публичные «syscalls»: инжект `Config<X>`, `Port`/`Emitter`, возврат
значения из хендлера. Enforcement — та же ES-видимость, без рантайм-ACL.
User-space код провенанс-слеп и транспорт-слеп: один и тот же бизнес-код
работает локально и в split, с конфигом из env или vault.

## Асинхронный контекст

Для глубоких сервисов (логгер в репозитории тремя слоями ниже хендлера) —
read-only ALS-проекция pipeline-контекста. Формула: **значение едет
ambient'ом, зависимость — явная; запись — монополия pre-юнитов**.

**Переменная — типизированный ключ накопленного `input`**, а не ячейка
отдельного хранилища: второго состояния, способного разойтись с первым, не
существует. Объявление — двойным вызовом (`contextVar<T>()` фиксирует тип,
второй вызов — ключ литералом):

```typescript
export const RequestId = contextVar<string>()('requestId');
// ключ 'requestId' — то же поле, что видит юнит в ctx.input.requestId
```

- **Писатель — сама переменная**: `Var.provide(compute)` возвращает обычный
  `PreUnitFn<TReq, { key: T }>`, поэтому «объявлено» и «положено» — одно
  действие, разойтись им нечем. Юнит, кладущий то же поле «вручную», для
  ридеров работает, но объявителем не считается — политика его не засчитает.
- **Ридер — член token family**: `Ctx(RequestId)` в deps → `CtxReader<string>`
  (`Ctx` типизирован значением переменной: `Ctx('requestId')` строкой не
  компилируется). Зависимость от request-контекста — видимое ребро DI-графа;
  полный список ambient-чтений известен на `build()`; в тестах подменяется
  `valueProvider` (сахар — `contextValue`, [testing.md](./testing.md)), ALS не
  нужен. Рецепт семейства даёт kernel-модуль, который корень регистрирует
  всегда — как для конфига, полей в словаре сборки нет.
- `get(): T` — бросает с диагностикой фазы; `peek(): T | undefined` — для
  ответного тракта, `@OnStart` и фоновых путей (зеркало асимметрии
  пайплайна — [pipeline.md](./pipeline.md)).
- **В ячейке** — накопленный `input`, `signal` и фаза; `raw`, `endpoint` и
  `summary` в ambient не отдаются — транспорт не протекает в домен. Сигнал
  живёт вне `input` и потому read-only: `Ctx(Signal)` читается, ключ
  `'signal'` зарезервирован, `provide` у переменной нет ни в типе, ни в
  рантайме. **Единственный писатель ячейки — рантайм пайплайна**; публичного
  сеттера не существует, ALS вторым каналом записи не является.
- **Присутствие проверяется на сборке**, opt-in: `everyEndpoint(…).hasVar(Var)`
  ([pipeline.md §7](./pipeline.md)) — типы закрывают чтение из юнита, политика
  закрывает чтение из глубины графа, где типов входа нет.
- **Провоз через границу порта — opt-in переменной**:
  `contextVar<T>()('tenantId', { propagate: true })`. Флаг есть свойство
  **объявления**, а не точки подключения: провозится именно переменная, и
  решение об этом видно там же, где она объявлена. Общей протечки контекста
  вызывающего не существует ни на одном пути биндинга — вызов порта
  открывает собственный request-scope, — а `propagate` есть именованное,
  объявленное исключение из этого правила.
  - **Сбор** — на вызывателе, из ячейки текущего запроса; значения едут
    полем конверта шины, а не подмешиваются в payload. Вне запроса
    (`@OnStart`, фоновая задача) провозить нечего, и это легально.
  - **Приём** — двумя каналами, как у профиля вызова
    ([contracts.md §4](./contracts.md)): безусловный `ctx.raw.attributes` и
    ambient-проекция штатным писателем `Var.propagated()`. Он несёт ту же
    рантайм-пометку, что `Var.provide`, поэтому
    `everyEndpoint(…).hasVar(Var)` засчитывает его, и присутствие
    провозимого контекста проверяемо на сборке.
  - **Значение не валидируется**: схемы у ambient-переменной нет, и рантайм
    её не изобретает. Провоз пересекает границу доверия — что провозится и
    что на основании провезённого решается, остаётся ответственностью
    приложения.
  - Read-only переменные (`Signal`) провозимыми не бывают: их значение
    поставляет рантайм запроса получателя, и привезённое ему не замена.
  - Граница провоза — **шина**: провоза через HTTP и CLI нет.
- Отдельного пакета `@nestling/context` нет: писатель типизируется
  `ExtendableContext` пайплайна, ячейку обновляет его рантайм, предикат живёт
  в его словаре политик.

## Что в контейнер не кладётся

- **Request-состояние** — никогда не в DI: типизированный request-контекст —
  это накопленный `input` пайплайна; для глубоких сервисов — асинхронный
  контекст (выше). Request-scope-провайдеров и их bubbling не существует
  by design.
- **Ленивая инициализация** и **рантайм-подграфы** (child-контейнеры) —
  осознанно вне V1 (см. записи журнала).
