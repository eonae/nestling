## Why

Операция уже несёт всё, из чего состоит определение MCP-инструмента: имя,
схему входа, схему выхода, список отказов и секцию `doc`. Второго описания
для агента писать не нужно — нужен пакет, который отдаёт объявленное по
протоколу.

MCP — входящий протокол. Агент присылает `tools/call`, сервер выбирает
маршрут, исполняет его пайплайном и отвечает. Это устройство транспорта, а
не плагина, и `transports.md` §4.2 такой случай уже описывает: «Несколько
транспортов на одном сокете получают один сервер: `http({ server: api })` и
`graphql({ server: api })`».

Решение зафиксировано записью
[ideas.md [2026-09-12]](../../../docs/decisions/ideas.md) «Разбор обзоров
d/10 и d/13», пункт 7, по
[d/13 §6.5](../../../docs/history/discussions/13-framework-review-3.md).
Строка 82 [roadmap](../../../docs/decisions/roadmap.md).

Это тот же механизм, что уже дали `@nestlingjs/openapi` и
`@nestlingjs/client`: одна декларация — три потребителя. Для фреймворка на
Node такого предложения сейчас нет ни у кого.

## What Changes

- Новый пакет `@nestlingjs/mcp` — транспорт-сателлит на публичных
  примитивах ядра, как `@nestlingjs/outbox` и `@nestlingjs/subscriptions`.
- `mcp({ info, converters, server?, path?, name? })` объявляется в
  `transports:` корня и присоединяется к уже объявленному HTTP-серверу.
  Второго сокета не появляется: обработчик встаёт в цепочку сервера рядом с
  обработчиком `http()`.
- Инструмент — endpoint этого транспорта. Форм две, как у всех транспортов:
  `mcpTool('users_create', { … })` объявляет инструмент вместе со схемами, а
  `mcpTool.implement(CreateUser, { handler })` обслуживает уже объявленную
  операцию.
- Состав инструментов — это endpoint'ы, объявленные на транспорте MCP.
  Отдельного списка `tools:` нет: состав виден там же, где состав любого
  другого транспорта.
- `tools/list` строится в `serve` из `dispatch.routes` — до того, как сервер
  откроет сокет. Схемы переводятся в JSON Schema теми же конвертерами, что у
  OpenAPI (`converters: [zodConverter()]`). Пакет не зависит ни от одного
  валидатора.
- `tools/call` исполняется `dispatch.call(pattern, ctx)`. Инструмент проходит
  пайплайн своей декларации, её слои и её политики — тот же путь, что
  обычный HTTP-запрос.
- Сессии клиентов — состояние транспорта: карта «идентификатор сессии —
  согласованная версия протокола», очищается в `close()`.
- Протокол реализуется в пакете; `@modelcontextprotocol/sdk` стоит в
  `devDependencies` и работает доказательством — сверкой типов и
  интеграционным прогоном настоящим клиентом.
- `Fail` операции попадает к агенту отдельным исходом (`isError` в
  результате вызова инструмента) с кодом и деталями отказа, а не
  исключением протокола.
- Новый рецепт `docs/recipes/mcp.md` на примере `app-with-http`.

Ломающих изменений нет: пакет новый, чужих экспортов не трогает.

### Non-goals

- **Ресурсы и промпты MCP.** Только `tools` этим change'ем. У ресурсов и
  промптов нет соответствия в декларациях, и им нужна своя форма
  объявления — отдельным решением, не попутно.
- **Server-initiated сообщения.** `GET` по пути транспорта с потоком событий
  не открывается: сервер отвечает на запросы клиента и сам ничего не
  инициирует. Выборка (sampling), нотификации об изменении списка
  инструментов и логирование через протокол — вне объёма.
- **Аутентификация.** Пакет её не делает. Заголовки запроса доходят до
  пайплайна декларации обычным путём, и кто вызывает — задача слоя
  приложения (строка 78 roadmap, `auth-layer`).
- **Отдельный процесс со stdio.** Сателлит живёт в приложении, которое
  обслуживает те же операции.
- **Каталог инструментов в `doc:`.** Полей, осмысленных только для MCP, в
  секции `doc` не появляется: она не зависит от формата документации, и
  это её собственное правило. Имя, описание и подсказки агенту объявляет
  словарь декларации.
- **Транспорт поверх чужого сокета.** `mcp({ server })` принимает
  объявление HTTP-сервера. Своего слушателя пакет не заводит.

## Capabilities

### New Capabilities

- `mcp-transport`: объявление `mcp(...)`, присоединение к HTTP-серверу,
  конверт JSON-RPC 2.0, пять методов протокола, сессии клиентов и
  диагностика на `serve`.
- `mcp-tool-declarations`: инструмент как endpoint — `mcpTool(name, …)` и
  `mcpTool.implement(Operation, …)`, вывод имени и описания, перевод схем в
  JSON Schema, отображение `Ok` и `Fail` на результат вызова инструмента.

### Modified Capabilities

Нет. Секция `doc` не меняется, `endpoint-discovery` и
`transport-form-capabilities` не меняются, `openapi-document` и
`typed-http-client` не трогаются.

## Impact

- **Новый пакет** `packages/nestling.mcp` по общему набору конфигов:
  `tsconfig.json`, `tsconfig.build.json`, `eslint.config.js`,
  `jest.config.js`, README с плашкой статуса.
- **Зависимости**: `@modelcontextprotocol/sdk` — только `devDependencies`;
  `@nestlingjs/app`, `@nestlingjs/container`, `@nestlingjs/operations`,
  `@nestlingjs/transport.http` — обычные зависимости пакета.
- **Публичные экспорты ядра**: ожидается, что хватает имеющихся —
  `makeTransportDeclaration`, `makeEndpoint`, `Dispatch`, `ITransport`,
  `leafJsonSchema`. Из `@nestlingjs/transport.http` берутся `HttpServer`,
  `HttpServer$`, `httpServer` и `parseJson`. Если сателлиту чего-то не
  хватает, экспорт добавляется в пакет ядра — так же, как это решено для
  стороннего транспорта в `satellite.integration.spec.ts`.
- **Документация**: рецепт `docs/recipes/mcp.md` и строка в
  `docs/recipes/README.md`; строка пакета в таблице `docs/README.md`;
  раздел в `docs/design/transports.md` о втором протоколе на одном сокете;
  раздел в `docs/design/operations.md` о третьем потребителе деклараций.
- **Пример**: `examples/app-with-http` объявляет транспорт и два-три
  инструмента.
- **Roadmap**: строка 82 переходит в `done`, запись
  `ideas.md [2026-09-12]` получает пометку «РЕАЛИЗОВАНО» по пункту 7.
