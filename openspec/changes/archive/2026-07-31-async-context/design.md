# design — async-context: read-only ALS-проекция pipeline-контекста

## Context

Накопленный `input` пайплайна видят только юниты и хендлер: сигнатура
`handler(payload, meta)` — граница, дальше которой контекст запроса не едет.
Всё, что глубже (репозиторий, клиент upstream, логгер внутри сервиса),
остаётся без `requestId` — и команда заводит собственный ALS-мешок с записью
из любого места и нетипизированным `get<V>(key)`.

Что уже есть в репозитории и на что этот change опирается:

- **Накопительный `input`** (`ExtendableContext<TAcc>`): pre-юниты монотонно
  добавляют поля, конфликты и недостачи ловятся типами в точке композиции
  (`packages/nestling.pipeline/src/core/pipeline.ts`).
- **Провенанс композиции** и предикат `derivesFrom` — идентичность слоя по
  ссылке; на нём стоит `everyEndpoint(…).hasLayer(…)`
  (`src/metadata/policy.ts`). Интерфейс `Policy` объявлен точкой расширения
  именно под этот change.
- **Token families**: члены материализуются на `build()` фикспоинтом по
  `deps`, рецепт регистрируется `familyProvider`, kernel-модуль конфига
  (`configKernel`) — образец «семейство + приватная машинерия, регистрируется
  корнем всегда».
- **Две точки исполнения ручки**: `PipelineImpl.executeWithHandler` и
  `callDirectly` в `makeDispatch` (ручка без пайплайна).

Ограничения: no runtime magic, explicit over implicit, guarantee over
convention; request-scope-провайдеров в контейнере нет и не будет; жадный
контейнер обязан видеть все зависимости статически.

## Goals / Non-Goals

**Goals:**

- Глубокий сервис читает `requestId` (и любую объявленную переменную), не
  получая его параметром и не завися от транспорта.
- Зависимость от request-контекста — **видимое ребро DI-графа**, а не
  невидимый статический вызов: `explain()`, визуализация и подмена в тестах
  работают штатными средствами.
- Запись — монополия pre-юнитов; ALS остаётся проекцией, а не вторым каналом.
- Присутствие переменной проверяемо **на сборке**, opt-in, той же машинерией
  policy-check, что и присутствие слоя.
- Аддитивность: существующий код собирается и работает без правок.

**Non-Goals:**

- `propagate` в заголовках remote-портов — приезжает с #12 (`transport.nats`).
- Публичная запись в ALS из пользовательского кода.
- Автоматический вывод требования из графа («провайдер с `Ctx(X)` достижим
  только из ручек, кладущих X») — см. «Open Questions».
- `raw`/`endpoint`/`summary` в ambient; request-scope-провайдеры DI.

## Decisions

### 1. Ambient-переменная — типизированный ключ накопленного `input`

`contextVar<T>('requestId')` объявляет **имя поля в накопленном `input`**, а
не ячейку отдельного хранилища. Проекция read-only, потому что читает то, что
пайплайн и так накопил: второго состояния, способного разойтись с первым,
не существует.

```typescript
export const RequestId = contextVar<string>('requestId');
// ключ 'requestId' — то же поле, что видит юнит в ctx.input.requestId
```

Значение несёт `key`, рантайм-идентичность и фантомный тип — тот же паттерн,
что `makeToken<T>()`.

_Отвергнуто:_ **отдельная ambient-карта** (`Map<varId, value>`) рядом с
`input` — два состояния и вопрос «что видит юнит, а что сервис»; запись в
карту пришлось бы разрешать отдельным API, то есть завести второй канал.

### 2. Писатель — `Var.provide(compute)`, конструктор pre-юнита

Открытый вопрос ideas.md — «рантайм-декларация добавок» для policy-check.
Требований два: (а) декларация не должна расходиться с фактом, (б) она должна
быть видна **на сборке**, до первого запроса.

```typescript
export const withRequestId = () =>
  RequestId.provide((ctx) => headerOr(ctx, crypto.randomUUID()));

const observability = makePipeline().pre(withRequestId()).finally(AuditOutcome);
```

`provide` возвращает обычный `PreUnitFn<TReq, { requestId: string }>`:
накопительная типизация, конфликты и требования — прежняя машинерия. Добавку
строит сама переменная (`{ [key]: value }`), поэтому «объявлено» и
«положено» — одно и то же действие. На значении юнита стоит неперечислимый
symbol-маркер с переменной; `PipelineImpl.pre()` читает его и кладёт
переменную в множество объявленных — рядом с `sources` и по тем же правилам
(`compose` объединяет, деривация билдера и `bind()` сохраняют).

Компилятор при этом гарантирует ещё одно: pre-юнит, читающий переменную из
`ctx.input`, требует её типом (`makePipeline<{ requestId: string }>()`), и
композиция без слоя-писателя не соберётся. Policy-check закрывает то, что
типами не выражается: чтение **из глубины графа**, где типов входа нет.

_Отвергнуто:_

- **`RequestId.of(uuid)` — брендированная добавка** (рабочая гипотеза
  ideas.md): даёт тождество декларации и факта, но видна только в рантайме,
  на первом запросе — а проверка нужна на `build()`.
- **`expose`/`provides` в точке подключения** (`pre(unit, { provides: [X] })`)
  — декларация, живущая отдельно от факта: юнит перестал класть переменную,
  а список остался; проверка становится проверкой комментария.
- **Вывод из типов** (`TAdd` пайплайна) — type erasure: к фазе ASSEMBLE
  типов нет вовсе.

Цена решения: юнит, кладущий ambient-переменную «вручную» (`return {
requestId }`), для readers работает, а для `hasVar` невидим — политика его
не засчитает. Направление ошибки безопасное (ложное падение сборки, а не
ложное разрешение), а починка — одна строка. Мульти-переменный писатель
(`provides([A, B], unit)`) не вводится по причине из отвергнутых вариантов:
несколько `pre`-юнитов дешевле, чем расходящаяся декларация.

### 3. Ридер — член token family `Ctx(Var)`

```typescript
@Injectable([Ctx(RequestId), ILogger])
export class UsersRepository {
  constructor(
    private readonly requestId: CtxReader<string>,
    private readonly logger: ILoggerService,
  ) {}

  async byId(id: string) {
    this.logger.debug(`[${this.requestId.peek() ?? 'n/a'}] select ${id}`);
  }
}
```

Токен члена — `'Ctx:requestId'`, обычный узел графа. Отсюда: зависимость
видна в визуализации и `explain()`, билдер знает полный список ambient-чтений
приложения на `build()`, а тест подменяет ридер `valueProvider` — ALS не
нужен.

Публичный `Ctx` — типизированный аксессор над **приватным** семейством:

```typescript
const CtxFamily = makeTokenFamily<AnyCtxReader, [key: string]>('Ctx'); // @internal
export const Ctx = <T>(v: AnyContextVar<T>): TokenString<CtxReader<T>> =>
  CtxFamily(v.key) as TokenString<CtxReader<T>>;
```

Так `Ctx('requestId')` со строкой не компилируется (тип члена зависит от
переменной, а не от семейства), а рецепт остаётся обычным `familyProvider` в
kernel-модуле.

_Отвергнуто:_ **статический `AsyncContext.get(key)`** (ориентир-антипример
rsdk) — глобал: невидим в графе, нетестируем без ALS, присутствие не
типизировано. **Экспорт семейства как есть** — потерянная типизация члена и
легальный `Ctx('опечатка')`.

### 4. Kernel-модуль ридеров регистрируется корнем всегда

`contextKernel()` — модуль с одним `familyProvider(CtxFamily, …)`; `assemble`
регистрирует его рядом с `configKernel`. Без единого `Ctx(...)` в `deps` он не
материализует ничего (фикспоинт идёт по `deps`), поэтому «всегда» ничего не
стоит, зато в корне про ambient-контекст не пишется ни строки — как и про
конфиг.

### 5. Ячейка: накопленный `input` + `signal` + фаза; писатель один

```typescript
interface RequestCell {
  input: AnyInput;                                   // ссылка на накопленное
  signal: AbortSignal;
  phase: 'pre' | 'handler' | 'response' | 'finally' | 'stream';
}
```

`raw`, `endpoint` и `summary` в ячейку не кладутся: транспорт в домен не
протекает. `signal` — well-known переменная `Signal` (`Ctx(Signal)`), ключ
`'signal'` зарезервирован: `contextVar('signal')` из пользовательского кода
падает с указанием импортировать `Signal`. `Signal` имеет тип
`ReadonlyContextVar<AbortSignal>` — `provide` у неё отсутствует и в типах, и
в рантайме: писать `signal` в `input` нечему.

Обновляет ячейку **только** рантайм пайплайна: после каждого pre-юнита
`cell.input = currentCtx.input`, на переходах — `cell.phase`. Публичного
сеттера нет; `CtxReader` несёт ровно `get`/`peek`.

### 6. Scope открывают обе точки исполнения ручки, включая поток

- `PipelineImpl.executeWithHandler` — оборачивает **всё** тело: pre-тракт,
  хендлер, ответный тракт, стража границы и `finally`.
- `callDirectly` (`makeDispatch`, ручка без пайплайна) — открывает scope с
  пустым `input` и `signal` запроса: `peek()` даёт `undefined`, а не «нет
  контекста», и глубокий сервис ведёт себя одинаково на обоих путях.
- **Потоковый ответ**: обёртка выходного итератора (`withFinish` рядом с
  `bindOutputStream`) прокатывает каждый `next()` и финализацию в той же
  ячейке с `phase: 'stream'`. Иначе шаги item-цепочки и ленивые генераторы —
  ровно те места, где ambient-логирование нужнее всего, — оказывались бы вне
  scope'а: `executeWithHandler` возвращает итератор до того, как транспорт
  начнёт его тянуть.

Вложенный запуск (in-proc вызов ручки внутри хендлера, `app.call` в тесте)
даёт вложенный scope — внутренний перекрывает внешний на своё время жизни;
это штатная семантика `AsyncLocalStorage.run`.

Вне запроса (`@OnStart`, cron, фоновая задача) scope'а нет: `peek()` даёт
`undefined`, `get()` бросает с текстом про фоновый путь. Отложенный код,
запущенный **внутри** запроса и переживший его (таймер, fire-and-forget),
продолжает видеть ячейку с финальным `input` — документированное поведение;
`capture()` в V1 не вводится.

### 7. `get()` / `peek()` — зеркало асимметрии, диагностика по фазе

`peek(): T | undefined` — присутствие определяется `key in cell.input` (для
`Signal` — наличием scope'а). `get(): T` бросает `ContextVarUnavailableError`
с текстом, зависящим от того, что рантайм знает:

| Ситуация | Текст |
| --- | --- |
| scope'а нет | «no request context here (`@OnStart`, cron, background) — use `peek()`» |
| фаза `response`/`finally`/`stream`, ключа нет | «pre-тракт не дошёл до юнита, кладущего `<key>`; на ответном тракте контекст `Partial` — use `peek()`» |
| фаза `pre`/`handler`, ключа нет | «`<key>` не в накопленном input: композируйте слой с `<Var>.provide(…)` или объявьте политику `hasVar`» |

Ошибка — обычный `Error` (программная, не доменная): страж границы
нормализует её в `UnknownError`, как любую необработанную. Отдельного
kernel-`Fail` она не заводит — отказ не контрактный и клиенту про него знать
нечего.

_Отвергнуто:_ **безусловная гарантия присутствия** (`get()` не бросает
никогда) — несостоятельна: ответный тракт `Partial`, пути вне запроса
существуют. Отсюда пара `get`/`peek` плюс opt-in-проверка на сборке.

### 8. Policy-check — предикат `hasVar` того же словаря

```typescript
policies: [
  everyEndpoint({ transport: HttpTransport$ }).hasVar(RequestId, 'requestId'),
];
```

Проверка — «пайплайн ручки объявил переменную» по множеству из решения 2;
ручка без пайплайна нарушает (как и в `hasLayer`: «нет пайплайна» и «нет
переменной» неразличимы), `detached: '<причина>'` выводит из-под предиката,
диагностика агрегируется общим прогоном `@nestling/app`. Ни второго поля в
корне, ни второго обхода дискавери — интерфейс `Policy` для того и объявлен
открытым.

_Отвергнуто (в V1):_ **вывод требования из графа** — «каждый провайдер с
`Ctx(X)` достижим только из ручек, чей пайплайн кладёт X». Красивее (не надо
называть переменную в корне), но требует двух новых публичных поверхностей:
токены, требуемые декларацией (`deps` + класс-хендлер + классы-юниты — сейчас
приватное состояние), и запрос транзитивного замыкания у `BuiltContainer`.
Это отдельный change, аддитивный: он приезжает значением того же типа
`Policy`.

### 9. Всё живёт в `@nestling/pipeline`; `@nestling/context` не заводится

Имя `@nestling/context` было зарезервировано записью [2026-07-06], но:
писатель типизируется `ExtendableContext` пайплайна, ячейку обновляет рантайм
пайплайна, предикат живёт в словаре политик пайплайна. Отдельный пакет дал бы
цикл зависимостей либо дубль типов. Резервирование снимается записью в
`decisions/`.

ALS-инстанс — модульное состояние `@nestling/pipeline` (тот же приём, что
реестры семейств в `@nestling/container`).

### 10. Совместимость: `withRequestId()` переписывается через переменную

Штатный `withRequestId()` становится `RequestId.provide(…)` с прежней
сигнатурой `PreUnitFn<EmptyInput, { requestId: string }>`. Приложения, уже
композирующие его, бесплатно получают `Ctx(RequestId)` и проходят
`hasVar(RequestId)`. `RequestId` экспортируется как well-known переменная
рядом с `Signal`.

## Risks / Trade-offs

- **Ambient — имплицитность, а принцип обратный.** → Смягчение конструкцией:
  зависимость явная (ребро графа), запись явная (pre-юнит), присутствие
  проверяемо (политика). Неявен только транспорт значения — то, что
  пользователь всё равно сделает сам, но без гарантий.
- **Юнит-«ручной писатель» невидим для `hasVar`** → направление ошибки
  безопасное (ложное падение сборки); диагностика прямо называет
  `<Var>.provide(…)` как починку; в доках правило одной строкой.
- **Две копии `@nestling/pipeline` в графе зависимостей** дадут два ALS, и
  чтение тихо вернёт `undefined` → монорепо-workspace и единая версия;
  риск отмечается в README, как и для реестров семейств.
- **Стоимость ALS на каждый запрос** (одна ячейка + `als.run`) платится даже
  приложением без единого ридера → цена порядка микросекунд против
  безусловной простоты правила «scope есть всегда»; условное открытие по
  наличию `Ctx`-членов в графе завело бы связь рантайма пайплайна со сборкой.
- **`peek()` неотличим от значения `undefined`**, если `T` включает
  `undefined` → документируется; такие переменные объявлять не рекомендуется
  (для «может не быть» есть сам `peek`).
- **Долгоживущий отложенный код видит ячейку после ответа** → документируется
  как поведение; `capture()`/сброс ячейки — открытый вопрос.

## Migration Plan

Change аддитивный: ломающих правок нет, публичные сигнатуры не меняются.

1. Переменные, ридеры, ALS-store и открытие scope в `@nestling/pipeline` —
   поведение существующих пайплайнов не меняется (scope открыт, читателей
   нет).
2. `contextKernel()` в `@nestling/app` и scope на прямом пути в
   `@nestling/transport`.
3. Предикат `hasVar` — только объявленный в корне работает.
4. `contextValue` в `@nestling/testing`, витрина в
   `packages/examples.app-with-http`, доки.

Откат — отбрасывание верхних ступеней: без объявленных политик и без ридеров
поведение тождественно текущему.

## Open Questions

- **Графовый вывод требования** (решение 8) — отдельный change; предпосылки:
  публикация токенов, требуемых декларацией, и запрос транзитивного замыкания
  у `BuiltContainer`.
- **`capture()` для отложенного кода** — нужен ли явный перенос/сброс scope'а
  для таймеров и фоновых задач, переживающих запрос (ideas.md, открытый
  вопрос).
- **Сервис, нужный и в request-пути, и в `@OnStart`**: хватает ли `peek()`
  или нужен второй ридер с иной строгостью (ideas.md, открытый вопрос).
- **`identity` в ambient** — дублировать ли её в оба канала (meta хендлера и
  ambient) или оставить только явной (ideas.md, открытый вопрос).
- **Где объявляется `propagate`** — на переменной или на биндинге порта;
  решается вместе с #12 (`transport.nats`), когда появится вторая сторона
  провода.
