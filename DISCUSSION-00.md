Мысли по поводу связки pipeline, transports и endpoints.

Одна из главный идей - разделение инфраструктурной и бизнес логики.

Инфраструктурная логика - это middleware, которые обрабатывают данные перед приходов
в handler и после выхода из handler.

[Терминология]

1. Handler - это функция (метод класса), реализующая бизнес логику.
2. Pipeline - вся последовательность обработки запроса, включая инфраструктурную логику (middleware), но
не включающая транспорто-специфичные преобразования. Handler - логически неотъемлемая часть
последовательности обработки запроса. Однако чисто технически.
3. Transport - это компонент отвечающий за приём и нормализацию запроса, роутинг (нахождение нужного пайплайна) и возврат ответа.
3. Endpoint - вот тут вопрос... Может нам назвать интерфейс IHandler, а декоратор @Route()?

[Абстракция обработчика]
Очень интересный момент - обработчик получает на вход нормализованные данные. И отдаёт тоже.
Получается, что он не зависит от транспорта. Но это же значит, что повесив
на него несколько декораторов @Endpoint() (или Route()), я могу подключить его к двум
разным транспортам эндпоинтам в одном транспорте.

Но тут вопрос. Допустим у меня есть процедура создания пользователя и я хочу сделать
ещё доступной с двух HTTP-ручек. Для фронтенда - там сессионная авторизация, и через внешнее API - там API-ключ.

Получается, что пайплайны-то разные. Ну и ок, если пайплайн не получает разные
варианты Identity. Хотя с другой стороны, identity: User | App - вполне себе
ок и уже в обработчике это разруливать.

А ещё описания могут быть разные...

Вообще получается знаешь как - обработчики транспорто-независимые, но ПАЙПЛАЙНО-зависимые.

[Типизация пайплайна]

``` typescript
type Fn<T = any, R = any> = (arg: T) => R;

type PipedFn<Fns extends Fn[]> = 
  Fns extends [Fn<infer A, infer B>]
    ? Fn<A, B>
    : Fns extends [Fn<infer A, infer B>, ...infer Rest]
    ? Rest extends [Fn<infer C, any>, ...Fn[]]
      ? B extends C
        ? PipedFn<[Fn<A, C>, ...Rest extends [Fn<any, any>, ...infer R] ? R : []]>
        : never
      : Fn<A, B>
    : never;

function pipe<Fns extends Fn[]>(
  ...fns: Fns
): PipedFn<Fns> {
  return ((arg: any) => 
    fns.reduce((acc, fn) => fn(acc), arg)) as any;
}
```

Можно ли это как-то использовать для типизации пайплайна?

Грубо говоря идея такая:
- сейчас у нас через middleware не идут изменяемые данные. Добавляем возможность
добавлять какие-то данные в контекст.
- объявляем пайплайн. const pipeline = new Pipeline(middlewares) На уровне типов
контролируем, что предыдущая middleware уже положила в контекст то, что нужно следующей
- при этом важно, чтобы декларация типов была немногословная
- дальше этот пайплайн навешиваем на хэндлер при помощи декоратора @Pipeline().
- Вот тут я не знаю - было бы очень круто, чтобы была ещё гарантия совпадения типов
метаданных между пайплайном в декораторе и метаданными класса.

Вряд ли можно проконтролировать совпадение, если оно будет в функции handle.. или можно?

Ну вот. Собственно пайплайны используются только в этом декораторе. Нужен ещё пайплайн (другие middleware, другая авторизация и т. д.) - сделаем другой.
Можно ещё сделать дефолт. Зарегистрировать пайплайн в App { defaultPipeline: ... } и тогда декоратор
@Pipeline() нужен только там, где нужен кастом какой-то... Но если так, тогда как типы проверить?

[Изменяемый контекст]
По идее, это должен быть типизированный KeyValue. Вопрос ещё а должен ли
этот контекст быть доступен в обработчике? Да, Identity конечно, а что ещё? 

[Валидация и авторизация]
Middleware или нет? Если идём по пути явного конструирования пайплайна, то скорее да.
Можно поменять местами..

Но с другой стороны без валидации типизация может оказаться ложной - может это неразделимые вещи?

Идентификация и Аутентификация - тоже может быть фиксированная функция, а не middleware. И Identity
- не просто какой-то KV, а, что называется First class citizen.

Спорный вопрос, является ли авторизация бизнес-логикой? Если проверка разрешений/ролей - то есть права входа в да. Если нет - тогда,
к сожалению надо будет уже делать в обработчике.
