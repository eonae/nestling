Транспорт принимает запросы извне — по HTTP, из командной строки, от
брокера, — переводит байты в значения, передаёт их в `dispatch` и
отправляет ответ обратно. Это обычный провайдер с жизненным циклом
([composition.md](./composition.md)).

## 1. Место транспорта

Границы ответственности:

- пайплайн и хендлер работают со значениями ([pipeline.md](./pipeline.md));
- всё байтовое — парсинг, framing, сжатие, CORS, content negotiation,
  multipart — делает транспорт;
- нативные объекты (`IncomingMessage`, `ServerResponse` и подобные) за
  пределы транспорта не выходят.

Интерфейс транспорта:

- `capabilities` — множества форм io, которые транспорт принимает и отдаёт
  (§1.1);
- `serve(dispatch, signal)` — единственный способ начать приём запросов.
  Метода `listen()` без аргументов и метода регистрации отдельного
  endpoint'а нет: всё, что транспорт обслуживает, приходит в `dispatch`;
- `close()` — остановка: дренаж активных соединений, отмена запросов в
  обработке.

`Dispatch` строит ядро на фазе WIRE (`makeDispatch`): по одному на транспорт,
только из endpoint'ов этого транспорта. Транспорт получает его аргументом
`serve` на фазе START. `Dispatch` состоит из двух частей:

- `routes` — проекции деклараций: паттерн, формы io, bind-карта,
  транспортные поля и объявленные отказы. Исполняемых полей (`handle`,
  `pipeline`, `deps`, `resolve`) в проекции нет;
- `call(pattern, ctx, options?)` — исполнение endpoint'а: выбор ветки «с
  пайплайном» или «без пайплайна» и её выполнение. Ветка одна для всех
  транспортов; транспорт её не дублирует.

Транспорт получает только маршруты и функцию вызова, поэтому начать приём
запросов раньше START невозможно: до WIRE маршрутизировать нечего. Опции
границы (`exposeErrorDetails`, `onUnknownFail`) передаются аргументом
`call`: это настройки конкретного транспорта, а не свойство таблицы
маршрутов.

Формы io проверяются против способностей транспорта в двух точках одной
реализацией и с одним текстом ошибки: на фазе ASSEMBLE (`App` знает и
декларации, и инстансы транспортов из графа) и в `serve` до открытия сокета
(standalone-путь).

Standalone-путь использует те же примитивы:

```typescript
const controller = new AbortController();
await transport.serve(makeDispatch([Ping]), controller.signal);
```

`makeDispatch` принимает только исполнимые декларации (`TNeeds = never`):
декларацию с неразрешёнными зависимостями отсекают типы.

Транспорт строит контекст запроса из данных запроса и отдаёт его пайплайну;
о фазах пайплайна он не знает. При отключении клиента транспорт взводит
`meta.signal`; сигнал запроса и сигнал транспорта объединяются через
`AbortSignal.any`.

Потоковый ответ накладывает на транспорт две обязанности. Получив от
пайплайна итератор, транспорт обязан либо прочитать его до конца, либо
закрыть (`return()`) — в том числе при ошибке отправки и при отключении
клиента: закрытие итератора выполняет отложенные `.finally`-юниты
([pipeline.md](./pipeline.md)). Обнаружив отключение, транспорт закрывает
итератор ответа, а не только взводит сигнал: иначе бесконечная подписка
удерживала бы ресурсы до сборки мусора.

### 1.1 Способности по формам io

```typescript
interface TransportCapabilities {
  readonly input: ReadonlySet<FormKind>;    // 'value' | 'stream' | 'events' | 'multipart'
  readonly output: ReadonlySet<FormKind>;
}
```

Способности — данные транспорта, а не соглашение и не проверка при первом
запросе. Поле обязательное: сторонний транспорт объявляет его явно.

| Транспорт | Вход | Выход |
|---|---|---|
| HTTP | `value`, `stream`, `multipart` | `value`, `stream`, `events` |
| CLI | `value`, `stream` | `value`, `stream` |
| Шина/порты (V1) | `value` | `value` |

Формы объявляются в контракте, а проверка биндинга на сборке сверяет их со
способностями транспорта. Декларация с формой, которую транспорт не
поддерживает, падает до приёма запросов: на фазе ASSEMBLE под `App` и в
`serve` на standalone-пути. Проверка одна на оба пути; текст ошибки называет
endpoint, транспорт, слот и форму и перечисляет поддерживаемые формы.
Проверка выполняется на графе, а не в типах деклараций: декларация не знает
тип своего транспорта, и это свойство сохраняется намеренно.

## 2. Приём input: bind-карта и строгий приём

Как единая `input`-схема раскладывается по частям запроса, определяет
bind-карта декларации ([endpoints.md](./endpoints.md)). Карту вычисляет
конструктор декларации; транспорт её только читает. Payload собирается
только из канонических мест с приоритетом «path, затем пометка, затем
остальное». Поле, присланное не в том месте, в payload не попадает и не
проходит обычную валидацию. Слияния «отовсюду» нет, как и ошибок конфликта
источников. Повтор ключа в query даёт массив; `query({ multiple: true })`
даёт массив и при одном вхождении.

Тело запроса читается, только когда его требует карта: источник «остальное»
указывает на body, есть пометка `body()` или включён `rawBody`. У `GET` без
пометок тело не буферизуется. Способ разбора тела задаёт форма
io-декларации (значение, `stream`, `events`, `multipart`), а не отдельный
конфиг маршрута.

## 3. Байтовый уровень

Статика, catch-all, CORS, сжатие, редиректы, wildcard-подписки шины — не
endpoint'ы. Это конфигурация и плагины транспорта, без схем и контрактов.
Сюда же относится обработка сырых случаев, для которых декларация не
подходит; параллельной модели деклараций для них нет
([endpoints.md](./endpoints.md)).

## 4. HTTP (`@nestling/transport.http`)

- Роутинг — find-my-way; паттерны берутся из деклараций (`method` и `path`
  с параметрами).
- Разбор по io-декларации: JSON-тело; NDJSON — входной поток; multipart —
  busboy, файлы отдаются хендлеру потоками
  (`FilePart { field, filename, mime, stream }`), лимиты (`upload({...})`)
  применяются во время разбора, без буферизации. `rawBody: true` кладёт
  байты в типизированный стартовый контекст одним чтением (значение
  разбирается из тех же байтов); с потоковыми и multipart-формами
  несовместим.
- Потоковый ответ: `stream` отдаётся как NDJSON (`application/x-ndjson`,
  chunked); `events` — как SSE (`text/event-stream`, `no-cache`,
  heartbeat-комментарии, `id:` и `event:` из секции `sse` декларации,
  приём `Last-Event-ID`). Ошибка посреди потока: для NDJSON — обрыв
  соединения, для SSE — кадр `event: error` с телом отказа и закрытие; в
  обоих случаях `.finally` видит исход `failed`
  ([streaming.md](./streaming.md)).
- Защита: лимит тела `maxBodySize` (раннее прерывание, ответ `413`);
  типизированные ошибки входа дают `400`, а не `500`; настраиваемые
  таймауты `node:http`; `close()` с дренажом; детали необработанных
  500-ошибок скрыты по умолчанию (`exposeErrorDetails`). Ответ на ошибку
  валидации — стандартные `issues` ([schemas.md](./schemas.md)).
- Порт и адрес берутся из конфиг-секции транспорта (`HTTP_PORT`,
  `HTTP_HOST`), а не из литералов в корне. Приоритет: явные опции фабрики,
  затем конфиг, затем значение по умолчанию. Фактический адрес после
  старта — `address()` (`null` до `serve` и после `close()`). Аргументов у
  `serve`, кроме `dispatch` и `signal`, нет.

## 5. CLI (`@nestling/transport.cli`)

У CLI вместо маршрутов команды: `pattern` задаёт имя команды. Что значит «принимать
запросы» для командной строки, решает режим `serve`: `'argv'` — один вызов
по аргументам процесса, `'repl'` — чтение команд из stdin до `exit`. Обе
ветки исполняют endpoint через `dispatch.call`; `execute({ command, args,
options })` остаётся публичной точкой одиночного вызова для корня и тестов.
Сбор недостающего input по схеме — политика биндинга `missing: 'prompt'`
([endpoints.md](./endpoints.md), §6). Stdin — входной поток: `stream(T)`
читает строки NDJSON, `stream('binary')` — чанки как есть; потоковый выход
пишется в stdout тем же NDJSON. `events` и `multipart` CLI не поддерживает:
у команды нет открытого соединения, отключение которого было бы нормальным
завершением, а файлы приходят путями в аргументах.

## 6. Шина (`@nestling/ports`)

`InProcessBus` — транспорт с двумя интерфейсами: входящим (`ITransport`,
маршруты реализаций контрактов) и исходящим (`IMessageBus`, вызыватели).
Отдельной сущности «транспорт шины» рядом с шиной нет.

От остальных транспортов шина отличается двумя вещами. Первое: маршруты
подписываются на фазе WIRE, а не в `serve`. `@OnStart` уже может вызывать
порт, а транспорты начинают приём после `@OnStart`; `serve` остаётся
точкой, где сигнал приложения связывается с каналом остановки шины.
Второе: в корне in-process шина не перечисляется — её регистрирует
kernel-модуль портов. В графе она появляется, только если есть хотя бы одна
реализация контракта или корень поставил транспорт шины сам (§7).

Формы io — только `value` в обе стороны: контракт со `stream` или `events`
отвергается на ASSEMBLE той же проверкой форм. Подробности —
[contracts.md](./contracts.md).

Шина объявляет значениями две способности: `remote` (доставляет ли за
пределы процесса) и `durable` (умеет ли долговечную доставку). Первая —
вход биндинга вызывателей ([contracts.md](./contracts.md) §3). Вторая
определяет видимую деградацию: приложение с `durable`-контрактами на шине
без долговечности стартует, но при запуске печатает строку с перечнем
контрактов, обслуживаемых без долговечности. У `InProcessBus` обе
способности ложны.

## 7. NATS (`@nestling/transport.nats`)

`NatsBus` — такое же значение с двумя интерфейсами, что и in-process шина,
и под тем же токеном: `nats()` — обычный провайдер транспорта в
`transports:` корня. Когда корень его поставил, kernel-модуль портов свою
реализацию не регистрирует: шина в приложении ровно одна, и брокер не
добавляется к in-process шине, а заменяет её. Ни одна декларация
`implement(...)`, ни один контракт и ни один вызов при подключении не
меняются — это уровень L4 из [composition.md](./composition.md).

### 7.1 Адресация

Subject — имя контракта (с префиксом, если задан `NATS_SUBJECT_PREFIX`).
Группа доставки вычисляется той же картой, что и у in-process шины:
`owner:<subject>` у `request`/`command`, имя подписчика у `event`.
Добавление реплики не требует правки конфигурации.

### 7.2 Фазы

У брокера фазы различимы точнее, чем у in-process шины. Соединение
открывается на INIT (это ресурс). `attach(dispatch)` на WIRE запоминает
маршруты и проверяет формы io. Подписки создаются в `serve` — после
`@OnStart`, поэтому входящее сообщение не застаёт незавершённый `@OnStart`.
На SHUTDOWN транспорт дренажит обработку и возвращает неподтверждённые
durable-сообщения в поток.

### 7.3 Формат сообщений

Тело кодируется кодеком (JSON по умолчанию; кодек заменяется опцией
фабрики). Конверт передаётся заголовками: относительный `timeoutMs`,
`idempotencyKey`, передаваемый контекст. Контекст едет одним заголовком
`Nl-Ctx` с JSON-объектом целиком: брокер канонизирует имена заголовков, и
ключ переменной в имени заголовка не сохранился бы. Ответ req-reply —
`ResponseContext` тем же кодеком, поэтому объявленный `Fail`
восстанавливается по коду той же процедурой, что и локально.

### 7.4 Потолок ожидания

Запрос через брокер не бывает бесконечным. Вызов без `meta.deadline`
ограничен `NATS_REQUEST_TIMEOUT` (30 с по умолчанию); вызов с бюджетом —
`min(остаток, потолок)`. Потолок не является бюджетом по умолчанию. Бюджет
принадлежит вызову и передаётся вглубь; потолок принадлежит транспорту, как
таймаут сокета у HTTP-сервера. Разница видна в тексте отказа.

### 7.5 Долговечность

`durable: true` объявляется контрактом (только `command` и `event`), и NATS
обслуживает такие subject'ы через JetStream: поток выводится из subject'а,
durable-потребитель — из группы; `ack` отправляется по факту решения (успех
и объявленный `Fail` одинаково); там, где решения не получилось, сообщение
доставляется повторно. Существующий поток, покрывающий subject, принимается
как есть; поток с тем же именем и конфликтующим составом subject'ов роняет
сборку.

### 7.6 Граница с брокером

Специфика брокера (wildcard, ack, KV, ordered consumers) не попадает ни в
`IMessageBus`, ни в контрактный API: ядро знает только интерфейс
([contracts.md](./contracts.md)). Задачи байтового уровня решаются тем же
методом подписки: wildcard-аудитор инжектит `MessageBus$` и вызывает
`subscribe('orders.>', …)` в `@OnStart`; третьего вида деклараций для этого
нет. Wildcard — способность брокера: in-process шина трактует subject
буквально.

Клиент брокера изолирован узким коннектором (`connect` — опция фабрики).
In-memory двойник брокера экспортируется по соглашению `./testing`: тесты
приложения и пакета проходят без сети, а совместимость с настоящим брокером
проверяет отдельный интеграционный прогон.
