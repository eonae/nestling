## Провайдеры и токены

Зависимости объявляются явным массивом токенов. Ни `reflect-metadata`, ни
инжекта «по типу» нет.

```typescript
@Injectable([UserRepository, ILogger('users')])
export class UserService {
  constructor(
    private repo: UserRepository,
    private logger: ILoggerService,
  ) {}
}
```

- Класс служит токеном сам себе. `@Injectable([deps])` — стандартный
  ES-декоратор (не `experimentalDecorators`); он несёт только список
  зависимостей. У класса без зависимостей форма короче: `@Injectable()`.
- Интерфейсы и значения регистрируются через явные токены
  (`makeToken<T>(id)`) и примитивы `classProvider(token, Class)`,
  `factoryProvider(token, fn, deps)`, `valueProvider(token, value)`. Это
  низкоуровневые примитивы контейнера для интерфейс-токенов, конфига и
  тестов, а не отдельный стиль деклараций.
- **Токен — объект, идентичность у него ссылочная.** Строковый `id` служит
  отображению: текстам ошибок, отчётам и `toJSON()` графа. Совпадение `id`
  подмены не вызывает — токены остаются разными, — но делает отчёты
  неоднозначными, и сборка об этом предупреждает. Каждый вызов `makeToken`
  даёт новый токен, поэтому токен объявляют один раз и импортируют
  значением. Класс тоже опознаётся по ссылке: два одноимённых класса из
  разных пакетов — два разных узла графа, а не молчаливая подмена.
- Список зависимостей дублируется в декораторе и в конструкторе. Это цена
  отказа от магии компилятора.

## Жадная сборка

`build()` создаёт весь граф сразу. Сборка выполняет топологическую
сортировку, проверяет циклы и отсутствующие узлы. Любая из этих ошибок
останавливает старт
приложения; в рантайме они не возникают. Понятия `forwardRef` нет. Готовый
граф полон и доступен для интроспекции: визуализация, атрибуция узлов
модулям, инициализация и остановка в топологическом порядке.

Отсутствующие зависимости перечисляются одной ошибкой. Проверка идёт до
создания экземпляров: сборка обходит `deps` всех провайдеров, собирает
токены без провайдера вместе с их потребителями и выдаёт один список.

Хуки жизненного цикла провайдеров: `@OnInit` (захват ресурсов), `@OnStart`
(начало приёма запросов), `@OnDestroy` (освобождение ресурсов, в обратном
топологическом порядке). Семантика фаз описана в
[composition.md](./composition.md). Хуки есть только у классов-провайдеров;
у фабричных провайдеров их нет.

## Подстановка и прунинг в тестовой сборке

`ContainerBuilder` принимает две опции для тестовой сборки: `overrides`
(пары «токен и значение») и `familyOverrides` (замена рецепта семейства).
Публичный `makeApp` эти опции не принимает: подстановка узлов — свойство
тестового прогона ([testing.md](./testing.md)).

`build()` выполняет шаги в таком порядке:

1. раскрывает фабрики провайдеров модулей;
2. заменяет рецепты семейств (`familyOverrides`) — до создания членов,
   чтобы члены создавались уже по тестовому рецепту;
3. создаёт членов семейств (до неподвижной точки);
4. подставляет `overrides`: провайдер токена заменяется на
   `{ provide, useValue }`, атрибуция к модулю сохраняется, поэтому
   визуализация и диагностика по-прежнему показывают владельца;
5. удаляет осиротевшие поддеревья (прунинг);
6. создаёт агрегаты `Family.all` — после прунинга, из оставшихся членов;
7. перечисляет отсутствующие зависимости, создаёт экземпляры, строит граф,
   проверяет циклы.

Подстановка падает на сборке в двух случаях. Первый — override для токена
без провайдера: например, провайдер переименовали, и тест заменил бы
пустоту; для члена семейства ошибка отдельно объясняет, что член становится
узлом графа только после того, как кто-то его инжектирует. Второй — два
override'а для одного токена.

**Алгоритм прунинга.** Пусть `deps` — отношение зависимостей до
подстановки, `deps′` — после неё (для заменённых токенов исходные `deps`
запоминаются). Ребро на `Family.all` при обходе разворачивается в рёбра ко
всем текущим членам семейства, чтобы потребитель агрегата не потерял их.

- `R` — токены с нулевой входящей степенью в объединении `deps ∪ deps′`,
  плюс токены, недостижимые из них по объединению. Так участники циклов
  остаются в графе и попадают в проверку циклов, а не исчезают.
- `Keep` — токены, достижимые из `R` по `deps′`.
- Удаляются `All \ Keep`: их провайдеры не создаются, узла в графе нет,
  `@OnInit` и `@OnDestroy` не вызываются. Заменённый узел не удаляется
  никогда.

Объединение `deps ∪ deps′` при выборе `R` нужно для случаев вроде
«репозиторий заменён на in-memory, а пул БД зависел только от него». До
подстановки на пул ссылался репозиторий, после подстановки — никто, поэтому
пул выпадает из графа как осиротевший, а не остаётся в нём как корень.

Инвариант: без `overrides` `deps = deps′`, каждый узел достижим из узлов с
нулевой входящей степенью, поэтому `Keep = All`, и прунинг ничего не
меняет. Боевая сборка совпадает с тестовой сборкой без подстановок до
единого узла. Список идентификаторов удалённых узлов доступен как
`app.pruned`: на вопрос «почему мой `@OnInit` не выполнился» отвечают
данные, а не чтение исходников.

## Модули

Модуль — значение: метка принадлежности провайдеров и единица упаковки.
Границей он не является, поэтому поля `exports` у него нет; endpoint'ов у
него тоже нет — их объявляет единица слоя приложения
([composition.md](./composition.md)). Модуль описывают `name`, `providers`
и `dependsOn`. Видимость держат ES-модули и границы пакетов: если токен не
экспортирован из пакета, снаружи его невозможно запросить.

```typescript
export const OrdersModule = makeModule({
  name: 'module:orders',
  providers: [OrdersService, OrdersRepository],
  dependsOn: [StorageModule],        // без чего этот модуль не работает
});
```

- `dependsOn` означает принадлежность, а не доступ: провайдеры видны
  всем, кто может импортировать токен. Модули из `dependsOn`
  регистрируются вместе с этим модулем.
- Идентичность модуля — его значение. Одно и то же значение, встреченное
  повторно (через `dependsOn`, в двух фичах, в фиче и в плагине),
  регистрируется один раз. Имя модуля — ключ атрибуции его провайдеров,
  поэтому два разных значения под одним именем — ошибка сборки. Ошибка
  называет имя и способы починки: разделить одно значение импортом, дать
  конфигурациям разные имена, проверить дубли пакета в зависимостях.
  Сравнение значений ссылочное: структурного сравнения опций и мемоизации
  по аргументам нет.
- Параметризованный модуль — функция, которая возвращает модуль. Понятий
  `DynamicModule`, `forRoot` и `forRootAsync` нет. Результат такой функции
  создаётся один раз и разделяется импортом: повторный вызов фабрики, даже
  с теми же опциями, даёт другое значение под тем же именем и роняет
  сборку.
- Контейнер используется и автономно, без `App`: группировка провайдеров с
  меткой нужна там сама по себе.

## Семейства токенов

Семейство токенов — один рецепт и много экземпляров, различающихся
параметром. Семейства покрывают параметризованные провайдеры, зависимость
экземпляра от потребителя и multi-injection. Всё это решается при сборке.

```typescript
const ILogger = makeTokenFamily<ILoggerService, [scope: string]>('Logger');

// инфраструктурный модуль регистрирует ОДИН рецепт на семейство:
familyProvider(ILogger, (scope) =>
  factoryProvider(ILogger(scope), (cfg) => new Logger(scope, cfg), [IConfig]));

// бизнес-код запрашивает члена как обычную зависимость:
@Injectable([UserService, ILogger('users')])
class CreateUserEndpoint { /* ... */ }
```

- `ILogger('users')` — мемоизированный токен-член с идентификатором
  `Logger:users`. Мемоизация — часть обещания семейства: без неё каждое
  обращение заводило бы новый узел под тем же именем. Семейство и параметр
  член хранит **полями**, поэтому вопрос «чей это токен» не зависит от
  того, как выглядит его `id`: токен, собранный вручную через
  `makeToken('Logger:users')`, членом семейства не является. Сборка находит
  все члены, упомянутые в `deps`, и создаёт для каждого узел графа по
  рецепту. Это обычные узлы, и создаются они жадно.
- `.auto` — член, параметр которого равен имени потребителя. `ILogger.auto`
  в `deps` класса `CreateUserEndpoint` становится
  `ILogger('CreateUserEndpoint')` в момент регистрации, потому что
  потребитель известен статически. Так решается случай
  `transient + INQUIRER` из Nest без transient-скоупа.
- `.all` — multi-injection: агрегирующий токен типа
  `Token<readonly T[]>`. Это выделенное значение, а не член с
  зарезервированным параметром: `IHealthCheck('all')` — обычный член и с
  агрегатом не сталкивается. Вклады — обычные провайдеры с членскими
  токенами (`classProvider(IHealthCheck('db'), DbHealthCheck)`); их
  регистрируют независимо разные модули. На `build()` сборка создаёт
  синтетический узел-агрегат со списком экземпляров. Список заморожен;
  порядок — порядок регистрации вкладов: сначала явные, затем созданные по
  рецепту. Пустое семейство даёт `[]`. Узел-агрегат не принадлежит модулю;
  вклад не требует объявлений сверх провайдера члена. Если
  фича не выбрана, её вкладов в списке нет — тем же механизмом, который
  убирает из графа её провайдеры. Каждый вклад адресуем и по отдельности:
  `IHealthCheck('db')` — обычный токен.
- Конфиг ([config.md](./config.md)) и клиенты инфраструктуры по требованию
  (`GrpcClient(server)` плюс unbound-ключи) — тоже семейства.

## Ядро и пользовательский код

Граница проведена как в операционной системе. К ядру относятся источники
конфига, транспорты, шина и клиенты портов, механизм графа и жизненного
цикла; их токены не экспортируются. К пользовательскому коду — сервисы,
endpoint'ы, операции и конфиг как данные. Пересечь границу можно только
через публичные точки: инжект `Config<X>`, `Port` и `Emitter`, возврат
значения из хендлера. Границу держит видимость ES-модулей, а не проверка
прав в рантайме. Пользовательский код не знает ни источника конфига, ни
транспорта: один и тот же бизнес-код работает в одном процессе и в
split-развёртывании, с конфигом из env или из Vault.

## Асинхронный контекст

Сервисам в глубине графа (логгер в репозитории тремя слоями ниже хендлера)
нужны значения из контекста запроса, например `requestId`. Для них есть
проекция контекста пайплайна через AsyncLocalStorage, доступная только для
чтения. Правило: значение приходит из окружения, но зависимость от него
объявлена явно; записывать значения могут только `.pre`-юниты.

Переменная контекста — типизированный ключ накопленного `input` пайплайна,
а не ячейка отдельного хранилища. Отдельного состояния, которое могло бы
разойтись с `input`, нет. Объявление — двойной вызов: `contextVar<T>()`
фиксирует тип, второй вызов задаёт ключ литералом.

```typescript
export const RequestId = contextVar<string>()('requestId');
// ключ 'requestId' — то же поле, что видит юнит в ctx.input.requestId
```

- Запись делает сама переменная: `Var.provide(compute)` возвращает обычный
  `PreUnitFn<TReq, { key: T }>`. Объявление переменной и запись значения —
  одно действие. Юнит, который кладёт то же поле в `input` вручную, для
  читателей работает, но объявителем переменной не считается, и политика
  `hasVar` его не засчитывает.
- Чтение — член семейства токенов: `Ctx(RequestId)` в `deps` даёт
  `CtxReader<string>`. `Ctx` типизирован значением переменной:
  `Ctx('requestId')` со строкой не компилируется. Зависимость от контекста
  запроса — обычное ребро графа, и полный список чтений контекста известен
  на `build()`. В тестах читатель заменяется через `valueProvider`
  (сокращённая запись — `contextValue`, см. [testing.md](./testing.md));
  AsyncLocalStorage для этого не нужен. Рецепт семейства даёт модуль ядра,
  который composition root регистрирует всегда; поля для него в `makeApp`
  нет, как и для конфига.
- `get(): T` бросает ошибку с указанием текущей фазы, если значения нет.
  `peek(): T | undefined` предназначен для ответной фазы пайплайна,
  `@OnStart` и фоновых задач. Эта пара повторяет асимметрию контекста в
  пайплайне ([pipeline.md](./pipeline.md)).
- В проекции доступны накопленный `input`, `signal` и текущая фаза. `raw`,
  `endpoint` и `summary` в проекцию не попадают: транспорт не должен
  проникать в домен. Сигнал живёт вне `input`, поэтому доступен только для
  чтения: `Ctx(Signal)` читается, ключ `'signal'` зарезервирован, метода
  `provide` у этой переменной нет ни в типе, ни в рантайме. Проекцию
  обновляет только рантайм пайплайна; публичного сеттера нет.
- Присутствие переменной проверяется на сборке, opt-in:
  `everyEndpoint(…).hasVar(Var)` ([pipeline.md §7](./pipeline.md)). Типы
  закрывают чтение из юнита, политика — чтение из глубины графа, где типов
  входа нет.
- Передача переменной через порт — opt-in в объявлении:
  `contextVar<T>()('tenantId', { propagate: true })`. Флаг стоит на
  объявлении, а не в точке подключения: передаётся именно переменная, и
  решение об этом видно там же, где она объявлена. Контекст вызывающего в
  реализацию порта не попадает ни при одном способе привязки: вызов порта
  открывает собственный контекст запроса. `propagate` — именованное
  исключение из этого правила.
  - Сбор значений происходит на стороне вызывающего, из контекста текущего
    запроса. Значения отправляются полем конверта шины, а не подмешиваются
    в payload. Вне запроса (`@OnStart`, фоновая задача) передавать нечего,
    и это допустимо.
  - Приём идёт двумя каналами, как у профиля вызова
    ([operations.md §4](./operations.md)): безусловно в `ctx.raw.attributes`
    и в проекцию контекста через `Var.propagated()`. Этот писатель несёт ту
    же рантайм-пометку, что и `Var.provide`, поэтому
    `everyEndpoint(…).hasVar(Var)` засчитывает его, и присутствие
    переданного контекста проверяется на сборке.
  - Значение не валидируется: схемы у переменной контекста нет. Передача
    пересекает границу доверия; что передавать и что решать на основании
    переданного, остаётся ответственностью приложения.
  - Переменные только для чтения (`Signal`) передаваться не могут: их
    значение поставляет рантайм запроса на стороне получателя.
  - Передача работает только через шину. Через HTTP и CLI контекст не
    передаётся.
- Отдельного пакета `@nestling/context` нет: писатель типизируется
  `ExtendableContext` пайплайна, проекцию обновляет его рантайм, предикат
  `hasVar` живёт в его наборе политик.

## Что в контейнер не попадает

- Состояние запроса. Типизированный контекст запроса — накопленный `input`
  пайплайна; для сервисов в глубине графа — асинхронный контекст (раздел
  выше). Провайдеров со скоупом запроса нет.
- Ленивая инициализация и рантайм-подграфы (дочерние контейнеры) в V1 не
  входят (см. записи журнала).
