## Context

CLI-транспорт собирает вход команды из аргументов процесса: позиционные
аргументы становятся полем `args`, `--key value` — полем `key`, `--flag` —
значением `true`. Собранный объект проверяет схема `input`, и отсутствие
обязательного поля даёт отказ `bad_request` с путём поля. Единственный
способ подсказать пользователю недостающее — текст сообщения схемы.

Целевой дизайн описывает вторую стратегию: политика биндинга
`missing: 'prompt'` достраивает вход вопросами в терминале
([design/endpoints.md](../../../docs/design/endpoints.md) §6). Вопрос
выводится из схемы: `enum` — выбор из списка, `boolean` — подтверждение,
`.describe()` — подсказка, `default` — значение по «Enter».

Ограничение, определяющее всю конструкцию: **Standard Schema не даёт
интроспекции**. Спецификация описывает только проверку значения —
`~standard.validate` и вендора. Перечень полей, их типы, `enum` и описания
из неё не читаются ни у одного валидатора.

В репозитории уже есть механизм, который переводит схему в форму, пригодную
для чтения: `SchemaDocConverter` из `@nestlingjs/operations`. Конвертер
объявляет вендора и отдаёт JSON Schema; генератор OpenAPI строит на нём весь
документ. Конвертер zod — десять строк поверх `z.toJSONSchema()` — лежит в
пакете `@nestlingjs/openapi.zod`.

## Goals / Non-Goals

**Goals:**

- Команда с `missing: 'prompt'` спрашивает недостающие обязательные поля и
  выполняется с достроенным входом.
- Форма вопроса выводится из схемы, а не объявляется второй раз рядом с ней.
- Вне терминала поведение прежнее: отказ валидации, а не зависший процесс.
- Ядро не меняется: политика живёт в пакете транспорта.
- Вопросы проверяются тестом без терминала.

**Non-Goals:**

- Справка, подкоманды, индикатор выполнения — граница пакета прежняя.
- Диалог посреди выполнения: он выражается парой операций plan/apply.
- Скрытый ввод пароля.
- Вопросы по массивам и вложенным объектам.
- Конвертер для валидатора, отличного от zod.
- Сбор недостающего входа в других транспортах.

## Decisions

### 1. Политика едет в декларации и переносится полем `binding`

`cliEndpoint` принимает `missing: 'error' | 'prompt'` и кладёт значение в
`binding` декларации: `binding: { missing: 'prompt' }`. Ядро поле `binding`
переносит и не читает — так же через него едет bind-карта HTTP. Транспорт
читает политику с проекции маршрута (`route.binding`) на `serve`.

Почему в декларации, а не в опциях транспорта: политика описывает **биндинг
операции**, и соседние команды одного приложения различаются. Команда
`deploy` спрашивает окружение, команда `status` в диалоге не нуждается.

Почему через `binding`, а не новым полем `RouteDeclaration`: проекция
маршрута перечисляет поля поимённо (`transport`, `pattern`, `input`,
`output`, `binding`, `errors`), и новое транспортное поле в ядре означало бы,
что ядро знает про CLI. `binding` для того и непрозрачен.

Умолчание `'error'` названо значением, а не отсутствием поля: политик две, и
вторая читается в декларации как выбор, а не как умолчание, о котором надо
помнить.

*Отвергнуто:* `cli({ missing: 'prompt' })` как режим транспорта — политика
стала бы свойством процесса, и команда, которой диалог противопоказан
(вызов из скрипта), потребовала бы второго экземпляра транспорта.

### 2. Конвертер обязателен и передаётся опцией транспорта

`cli({ converters: [zodConverter()] })`. На `serve` транспорт берёт схему
`input` каждой команды с `missing: 'prompt'` и ищет конвертер по
`~standard.vendor`. Конвертера нет — `serve` падает с именем команды,
вендором и подсказкой, какой пакет поставить.

Почему обязателен: без JSON Schema вопрос знает только имя поля. Получилось
бы две разные степени полноты у одной политики — та самая «деградация по
умолчанию», от которой отказывается принцип **guarantee over convention**.
Приложение, которому вопросы не нужны, конвертер не передаёт и ничего не
теряет: проверка касается только команд с политикой.

Почему опцией транспорта, а не из графа: конвертеры приложение не носит —
их принимают `check()` и плагин `openapi()`, каждый своим списком. Транспорт
объявляется значением (`cli({ … })`), и список рядом с объявлением читается
там же, где имя экземпляра и режим.

*Отвергнуто:* вывод вопросов из ошибок валидации. Standard Schema даёт
`message` и `path`, но не код: отличить «поля нет» от «поле не того типа»
нельзя, а форма поля неизвестна вовсе.

*Отвергнуто:* вопросы, объявленные в декларации рядом с политикой
(`missing: { prompt: { env: 'Окружение?' } }`). Схема и вопросы разъезжаются
при первом же изменении схемы.

### 3. План вопросов строится на `serve` и кэшируется по команде

Транспорт при регистрации маршрутов строит для каждой команды с политикой
`PromptPlan` — перечень полей с формой вопроса. Конвертация схемы выполняется
один раз, а не на каждый вызов команды.

Побочный результат: непригодная схема обнаруживается при старте, а не на
первом вызове. Это то же правило, по которому `serve` уже проверяет формы io
против способностей транспорта.

### 4. JSON Schema берётся в направлении `io: 'input'`

Конвертер принимает `{ io: 'input' | 'output' }`. Для CLI верно `'input'`:
это форма, в которой значение приходит извне, а извне у команды приходит
argv. Схема с преобразованием (`z.stringbool()`) описывается как строка, и
ответ строкой проходит валидацию так же, как прошёл бы флаг.

### 5. Форма вопроса читается с узла схемы, непонятный узел пропускается

План читает у корневого узла `properties` и `required`. Спрашиваются только
поля из `required`, которых нет в собранном payload. Форма вопроса:

| Узел | Вопрос | Ответ |
|---|---|---|
| `enum: [...]` | нумерованный список | элемент списка как есть |
| `type: 'boolean'` | `[y/n]` | `true` или `false` |
| `type: 'string' \| 'number' \| 'integer'` | строка | введённая строка |
| прочее | не задаётся | — |

`description` печатается подсказкой, `default` показывается в скобках и
подставляется по пустому вводу.

Непонятный узел (`array`, `object`, `anyOf`, `$ref`) пропускается молча, и
поле остаётся незаданным: дальше его забирает валидация и отвечает отказом,
как сегодня. Молча — потому что поле могло быть задано флагом, и ошибка при
старте запретила бы рабочую команду.

*Отвергнуто:* вопрос по массиву («значение или Enter для завершения»).
Позиционные аргументы CLI приходят массивом `args`, и соблазн велик, но ввод
списка по одному элементу — отдельная форма диалога со своими правилами
отмены и редактирования. V1 ограничивается скалярами; рецепт показывает
команду с именованными полями.

### 6. Ответ подставляется в форме флага

Правило: **промпт кладёт то же, что положил бы флаг командной строки**.
Строка для скаляра, `true`/`false` для `boolean`, элемент списка для `enum`.
Схема, написанная под argv (`z.coerce.number()` там, где нужно число),
работает с вопросами без единой правки.

*Отвергнуто:* приведение ответа к типу JSON Schema (строка «3» → число 3).
Тогда у одной схемы появились бы два входа с разными правилами, и
`z.coerce.number()` пришлось бы снимать ради вопросов и возвращать ради
флагов.

### 7. Интерактивность определяется средой, опция перекрывает

Вопросы задаются, когда поток ввода — терминал (`isTTY`) и переменная `CI` не
задана. Опция `cli({ interactive: true | false })` решает явно и проверку
среды не выполняет.

Без вопросов поведение прежнее: команда доходит до валидации и отвечает
отказом. Процесс в конвейере не зависает на вопросе, которого никто не
увидит.

Опция нужна тестам: подставленный поток ввода терминалом не является, и без
явного `interactive: true` вопросы не задавались бы никогда.

### 8. Один readline на транспорт

В режиме `'repl'` интерфейс уже открыт — вопросы задаются им же
(`rl.question`), иначе два читателя поделили бы строки `stdin` между собой.
В режиме `'argv'` интерфейс открывается перед вопросами и закрывается сразу
после: команде без недостающих полей терминал не нужен.

Конец ввода (`EOF`) на вопросе оставляет поле незаданным. Дальше работает
валидация — отдельного отказа «диалог прерван» нет.

### 9. Потоки ввода и вывода становятся опциями транспорта

`cli({ input, output, errorOutput })`, умолчания — `process.stdin`,
`process.stdout`, `process.stderr`. Транспорт перестаёт писать через
`console` и читать `process.stdin` напрямую.

Два повода. Первый: вопросы и ответы иначе не проверить тестом — понадобился
бы настоящий терминал. Второй: README пакета уже описывает
`CliTransportOptions` как «имя программы, режим REPL, потоки ввода и
вывода», а в коде есть только `mode` и `argv`. Расхождение чинится тем же
change'ем, который его обнаружил.

Поток входных данных команды (`stream`-форма `input`) читается из того же
`input`: подстановка потока в тест работает и для команд с `stdin`.

### 10. Поток на входе и вопросы несовместимы

Команда с формой `input: stream(...)` и политикой `missing: 'prompt'` роняет
`serve`. Вопросы и поток читают один `stdin`, и что бы транспорт ни выбрал,
вторая половина работать не будет. Ошибка называет команду и обе причины.

### 11. `@nestlingjs/openapi.zod` → `@nestlingjs/schema.zod`

Конвертер переводит схему в JSON Schema и об OpenAPI ничего не знает: его
читают генератор документа, структурная проверка `check()`, снапшот
совместимости контрактов, а теперь и вопросы CLI. Имя пакета называло
первого потребителя, и CLI-утилита ставила бы пакет с чужим именем.

Экспорты не меняются: `zodConverter`, `ZodConverterOptions`. Меняются имя
пакета, каталог (`packages/nestling.schema.zod`), описание и ключевые слова
манифеста.

## Risks / Trade-offs

**`rl.question` внутри обработчика `line` в REPL.** Интерфейс readline
перехватывает следующую строку вопросом, и обычная выдача строк на это
время прекращается. Поведение проверяется тестом на REPL с вопросом: ответ
уходит в вопрос, а не в разбор команды.

**Переименование опубликованного пакета.** `@nestlingjs/openapi.zod` 0.1.3
остаётся в реестре как есть: прав на удаление у нас нет и удалять нечего —
установленные копии продолжат работать. Новое имя выходит следующим релизом
с общей версией монорепы.

**Вопрос по полю, которое пользователь задал бы флагом.** План спрашивает
только отсутствующие поля, но команда, вызванная с опечаткой в имени флага
(`--evn prod`), спросит поле, которое пользователь считал заданным. Это то
же поведение, что у отказа валидации сегодня, только в форме вопроса.

**Тексты вопросов на английском.** Строки рантайма в репозитории английские
(запись [ideas.md [2026-09-12]](../../../docs/decisions/ideas.md)), и вопросы
не исключение: `description` схемы печатается как написан автором.

## Migration Plan

1. Переименование пакета отдельным коммитом: `git mv`, правки манифеста,
   `yarn install` для `yarn.lock`, замена имени в `@nestlingjs/openapi`,
   примерах, документации и спеке `openapi-document`.
2. Политика и вопросы в транспорте.
3. Потоки транспорта и перевод печати с `console`.
4. Пример `simple-cli`: команда с `missing: 'prompt'`.
5. Документация: `design/transports.md` §5, `design/endpoints.md` §6,
   `recipes/cli.md`, README пакетов.

Откат — обратные коммиты: политика аддитивна, а переименование затрагивает
только имя пакета.

## Open Questions

- Скрытый ввод (`format: 'password'` в JSON Schema) — отдельная работа, если
  понадобится секрет в аргументе команды.
- Позиционные аргументы (`args`) вопросами не собираются. Понадобится —
  решать вместе с формой диалога для списка.
