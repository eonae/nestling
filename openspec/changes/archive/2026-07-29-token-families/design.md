# token-families — design

## Context

Источник истины — `docs/decisions/ideas.md`, секция «[2026-07-06] Token
families + модули без рантайм-инкапсуляции» (Решения 1–3; Решение 4 задаёт
Non-Goals). Текущее состояние (сверено с кодом 2026-07-07):

- **Токены — брендированные строки.** `TokenString<T> = string & { __type }`,
  `makeToken(id)` — каст строки; `InjectionToken = TokenString | Constructor`
  (`common.ts`). Вся машинерия билдера ключуется `stringifyToken()`.
- **Провайдеры** — три вида определений (`useClass`/`useValue`/`useFactory`)
  плюс голый класс с `@Injectable`; deps — явный массив токенов
  (`providers/variants.ts`). `@Injectable` кладёт `{ injectionToken,
  dependencies }` в `injectableMetaStorage` (WeakMap) в момент декорирования —
  конструктор уже доступен (`injectable.decorator.ts`).
- **Билдер** (`builder/container.builder.ts`): `register()` различает Module
  (по `isModule` — эвристика «есть строковый `name`») и Provider;
  `build()` = `appendFactoryProviders()` → `instantiateAll()` (жадно,
  с детекцией циклов) → `buildDependencyGraph()` → `ensureAcyclic()`.
  Модульная атрибуция: `#providerToModule`, `#moduleExports`
  (уже собирается, но нигде не проверяется) → `DINodeMetadata.module` /
  `.exported` (см. спеку `container-module-attribution`).
- **Ручной прообраз фичи** — `examples.simple-app/src/logging/registry.ts`:
  `Set<InjectionToken<ILogger>>` + фабрика `ILogger(scope)` c id
  `Logger:${scope}`, и `logging.module.ts` с `ProvidersFactory`, штампующим
  провайдер на каждый токен из Set. Работает через import-side-effects
  (модуль обязан импортироваться после всех вызовов `ILogger(...)`), контейнер
  паттерн не видит и не проверяет.

Ограничения: TS 5.7 strict, стандартные ES-декораторы без reflect-metadata,
zero magic, минимум зависимостей. Изменения должны быть аддитивными для
`@nestling/container`.

## Goals / Non-Goals

**Goals:**

- `makeTokenFamily<T, Params>('Name')` — фабрика мемоизированных членских
  токенов `"Name:param"`; член — обычный `TokenString`.
- `familyProvider(family, recipe)` — один рецепт на семейство; на `build()`
  материализация всех членов, упомянутых в deps зарегистрированных провайдеров
  (включая порождённые рецептами), в обычные узлы графа: дедупликация, жадная
  инстанциация, циклы, lifecycle, module-атрибуция.
- `Family.auto` — резолюция в `Family('<ИмяКлассаПотребителя>')` в момент
  декорирования `@Injectable`.
- Опция `new ContainerBuilder({ strictExports: true })` — build-time lint
  рёбер графа против `exports` модулей; `exports` принимает семейство.
- Миграция `examples.simple-app/logging` на новое API как демонстрация.

**Non-Goals:** request-состояние в DI; `lazy()`; `createScope`/подграфы;
DynamicModule/forRoot-аналоги; рантайм-инкапсуляция модулей; токен-форма
юнитов pipeline (`RateLimit('strict')` в `TNeeds` — change pipeline-v2, здесь
только совместимость: члены семейства — обычные `InjectionToken`); валидация
параметров семейства; многопараметрические семейства (см. D2 и Open
Questions); `Family.all` — multi-injection-агрегат (массив всех
зарегистрированных членов) — отдельный change `multi-injection` (roadmap #14,
ideas.md [2026-07-10]); здесь важна только предпосылка: явная регистрация
провайдеров с членскими токенами легальна (D4 материализует лишь членов без
провайдера).

## Decisions

**D1. API `familyProvider`: рецепт возвращает готовое определение провайдера**
(открытый вопрос (а) из ideas.md — решён).

```typescript
familyProvider(ILogger, (scope) =>
  factoryProvider(ILogger(scope), (config) => new Logger(scope, config), [IConfig]),
);
```

Рецепт `(param) => ProviderDefinition<T>` возвращает обычное определение
(`factoryProvider`/`valueProvider`/`classProvider`). Билдер при материализации
валидирует, что `stringifyToken(def.provide)` совпадает с id члена
(`family(param)`), иначе — ошибка сборки с именем семейства и параметром.

- *Почему не `{ deps, factory }`* (вторая альтернатива из ideas.md): это
  параллельный мини-словарь определений, который покрывает только
  factory-форму (нельзя вернуть `valueProvider` для заглушки в тестах или
  `classProvider`), и его пришлось бы отдельно типизировать и документировать.
  Переиспользование существующего словаря — ноль новых концепций; единственный
  риск формы 1 (рецепт вернул провайдер с чужим `provide`) закрывается дешёвой
  build-time проверкой с внятной ошибкой.
- *Почему не «билдер сам подставляет `provide`»* (гибрид): скрытая магия —
  определение в руках пользователя выглядит полным, но его `provide`
  игнорировался бы; противоречит explicit over implicit.

**D2. Параметры семейства: в v1 — ровно один строковый параметр.**
`makeTokenFamily<T, Params extends [param: string]>` — генерик оставлен
тьюплом (как в эскизе ideas.md) ради именованной подписи в IDE и будущего
расширения, но v1 ограничивает его одним `string`. Id члена — `"Name:param"`
(двоеточие в параметре допустимо: имя семейства не содержит `:`, разбор — по
первому разделителю; фактически разбор не нужен — см. D3). Мемоизация: повторный
вызов с тем же параметром возвращает тот же токен (для строк — тривиально по
значению) и не плодит записей в реестре членов.

- *Почему не тьюпл примитивов с `join(':')`*: вопросы экранирования
  разделителя и канонизации (число vs строка) без реальной потребности — все
  кейсы ideas.md (`ILogger(scope)`, `IQueue(name)`, `IHttpClient(upstream)`,
  `RateLimit('strict')`) однопараметрические; расширение аддитивно.
- *Почему не объект-параметр*: нет детерминированной сериализации в id.

**D3. Обнаружение членов: реестр на значении семейства, не парсинг id.**
Семейство хранит внутренний `Map<param, token>` созданных членов
(формализация `loggersRegistry` из примера). Билдер, получив
`familyProvider(family, recipe)`, спрашивает у семейства соответствие
`tokenId → param` при сканировании deps. Токены остаются голыми
брендированными строками — `InjectionToken`, `stringifyToken`, графовая
машинерия и совместимость с pipeline-v2 не затрагиваются.

- *Почему не брендированные объекты-токены*: ломают простоту `token = string`
  и всю существующую машинерию ключевания.
- *Почему не парсинг `"Name:param"` по префиксу*: ложные срабатывания на
  токенах, созданных `makeToken('Name:x')` мимо семейства; префикс-матчинг —
  implicit-магия. Следствие реестра: членом считается только токен, созданный
  вызовом семейства. Токен-двойник через `makeToken` даст обычную ошибку
  «Provider for token not found» — документируем правило «члены создаются
  только через семейство».
- Побочный эффект вызова `Family(param)` — запись в реестр семейства — на
  сборку не влияет: материализуются только члены, упомянутые в deps
  зарегистрированных провайдеров (D4). Сборка детерминирована относительно
  зарегистрированного, а не относительно порядка импортов — в отличие от
  ручного паттерна.

**D4. Материализация — отдельная фаза `build()` до `instantiateAll()`,
итерация до фикспоинта.** После `appendFactoryProviders()`: собрать по deps
всех зарегистрированных провайдеров упоминания членов зарегистрированных
семейств; для каждого уникального члена без провайдера — вызвать рецепт (ровно
один раз на параметр), проверить `provide` (D1), зарегистрировать результат
как обычный провайдер с moduleName модуля, в котором зарегистрирован
`familyProvider`. Повторять, пока появляются новые члены (провайдер, созданный
рецептом, может зависеть от членов того же или другого семейства). Дальше —
обычные `instantiateAll` (детекция циклов покрывает и циклы через членов) и
`buildDependencyGraph`.

- Ошибки: член в deps, семейство известно (токен есть в реестре какого-то
  зарегистрированного семейства), но `familyProvider` не зарегистрирован →
  ошибка сборки, называющая семейство и параметр; повторный
  `familyProvider` для того же семейства → ошибка регистрации (симметрично
  «already registered» для токена); рецепт бросил → ошибка сборки с семейством
  и параметром.
- *Почему deps-only, без seed-списка* («материализовать member без
  потребителя»): единственный источник — явные deps; член без потребителей не
  создаётся (и `get()`/`getOrThrow()` его не увидят — контракт
  `container-accessor-contract` не меняется). Seed-опция
  (`familyProvider(f, r, { include: [...] })`) отвергнута в v1 — реальный кейс
  примера покрыт (в `main.ts` `getOrThrow(ILogger('app'))` работает, т.к.
  `AppService` deps'ит `ILogger('app')`); добавить seed можно аддитивно.
- *Почему не рантайм-резолюция по требованию*: разрушает полный граф,
  топологический init/destroy и проверку циклов — прямо противоречит
  ideas.md («„динамика" происходит на этапе сборки»).

**D5. `familyProvider` — новый вид регистрируемого определения.**
`FamilyProviderDefinition = { family, recipe }` с type guard
`isFamilyDefinition` (по наличию `family`+`recipe`); принимается `register()`
и массивом/фабрикой `providers` модуля. Порядок распознавания в `register()`:
family-определение → модуль → провайдер (у family-определения нет поля
`name`, но проверка до `isModule` страхует от эвристики «есть строковый
`name`»). В `Map#providers` family-провайдер не попадает (у него нет
собственного токена) — хранится в отдельной структуре «семейство → рецепт +
moduleName».

- *Почему не метод `builder.registerFamily(...)`*: второй путь регистрации
  мимо модулей; family-провайдер должен жить в `providers` модуля, чтобы
  атрибуция и `strictExports` работали единообразно.

**D6. `.auto` — сентинел, резолвящийся в `@Injectable` при декорировании**
(открытый вопрос (б) из ideas.md — решён: в v1 только классы).
`Family.auto` — специальный токен-сентинел (брендированная строка вида
`"Name:{auto}"`, зарегистрированная во внутреннем реестре сентинелов
семейства), типизированный как `TokenString<T>`, чтобы deps-массив
типочекался как обычно. `Injectable(...)` при декорировании заменяет каждый
сентинел в deps на `family(constructor.name)` (конструктор в этот момент уже
доступен) и кладёт в метаданные уже резолвленный токен. Потребитель —
декорируемый класс; два класса с `ILogger.auto` получают двух разных членов.

- В deps `factoryProvider`/`classProvider`/`familyProvider`-рецептов
  «потребителя» нет — сентинел, доживший до регистрации/сборки, даёт ошибку
  с подсказкой «используйте `Family('<имя>')` явно». Escape hatch и есть
  явный вызов.
- *Почему не «потребитель = id `provide` фабричного провайдера»*: семантика
  расходится с классовой (имя класса vs произвольный id токена), выглядит
  как магия; отвергнуто для v1.
- *Почему не INQUIRER-подобная рантайм-резолюция*: рантайм-магия и transient,
  от которых фича и уходит.
- Анонимный класс / пустое `constructor.name` → ошибка при декорировании.

**D7. `strictExports` — opt-in lint рёбер готового графа.**
`new ContainerBuilder(options?: { strictExports?: boolean })` (первый параметр
конструктора — аддитивно). После `buildDependencyGraph()`: для каждого ребра
`consumer → dep`, где `dep.metadata.module = M` и потребитель не из `M`
(другой модуль или без модуля), токен `dep` обязан быть в `exports` модуля
`M`. Узлы без модуля потребляются свободно. Все нарушения собираются и
бросаются одной ошибкой со списком «consumer → dep (module)».

- **Отсутствующий/пустой `exports` = ничего не экспортировано.** Флаг —
  opt-in: включил строгий режим — объявляй exports честно. *Альтернатива
  «нет exports = всё экспортировано» отвергнута*: lint становится беззубым
  именно там, где модули exports не объявляли.
- **`exports` принимает семейство**: `exports: [ILogger]` означает «все
  материализованные члены экспортированы». Семейства в `exports`
  обрабатываются отдельной веткой (семейство — функция; пропускать её через
  `stringifyToken` нельзя — тот взял бы `.name` функции и экспортировал бы
  токен `"Logger"` вместо членов); `#moduleExports`-матчинг и
  `metadata.exported` члена учитывают членство через реестр семейства (D3).
- *Почему не рантайм-инкапсуляция / не проверка при `get()`*: ideas.md,
  Решение 3 — ES-модули уже система видимости; это lint по готовому графу,
  дешёвый и детерминированный.
- Тип `Module.exports` расширяется до `(InjectionToken | TokenFamily)[]` —
  аддитивно.

**D8. Валидация параметров семейства — отложена осознанно**
(открытый вопрос (в) из ideas.md — решён как «не в v1»).
В v1 `makeTokenFamily` принимает любой строковый параметр. Обоснование:
потребность гипотетическая (enum скоупов); пользователь может обернуть
семейство своей функцией с валидацией; будущая опция
`makeTokenFamily(name, { validate })` добавляется аддитивно, не меняя ни
токенов, ни рецептов.

## Risks / Trade-offs

- [`.auto` зависит от `constructor.name`; минификация/бандлинг переименуют
  классы → нестабильные id членов] → целевая среда — серверный Node без
  минификации; правило документируется рядом с `.auto`; анонимный класс —
  явная ошибка при декорировании (D6).
- [Токен-двойник `makeToken('Logger:users')` мимо семейства не считается
  членом → «Provider not found» озадачивает] → правило «члены — только через
  вызов семейства» в доке и JSDoc; текст ошибки материализации подсказывает
  ближайшее зарегистрированное семейство по префиксу id.
- [Рецепт, порождающий новых членов на каждом витке фикспоинта (например,
  `ILogger(scope)` deps'ит `ILogger(scope + ':x')`), даёт бесконечную
  материализацию] → жёсткий лимит итераций фикспоинта с внятной ошибкой,
  называющей семейство и последние параметры (диагностика вместо зависания).
- [Реестр членов на значении семейства — глобальное для процесса состояние] →
  реестр только отображает `param → token` (строки), на состав сборки не
  влияет (deps-only, D4); в тестах семейства пересоздаются вместе с модулем —
  изоляция jest покрывает.
- [`strictExports` на существующем проекте даст лавину нарушений (никто не
  объявлял exports)] → флаг выключен по умолчанию; включение — осознанный
  шаг после объявления exports; ошибка перечисляет все нарушения разом, а не
  по одному.
- [Эвристика `isModule` («есть строковый `name`») могла бы съесть
  family-определение] → `isFamilyDefinition` проверяется первым в
  `register()` (D5); форма `{ family, recipe }` не имеет `name`.
- [Валидация `provide` в D1 не может проверить тип `T` рецепта] → типовая
  совместимость обеспечивается сигнатурой `familyProvider<T>` (рецепт обязан
  вернуть `ProviderDefinition<T>`); рантайм-проверка ловит только id, это
  осознанная граница (как и везде в контейнере).

## Migration Plan

Изменение аддитивное, breaking-изменений для контейнера нет: новые экспорты
(`makeTokenFamily`, `familyProvider`, тип `TokenFamily`), новый необязательный
параметр конструктора `ContainerBuilder`, расширение типа `Module.exports`.
Существующий код (включая ручной паттерн реестра) продолжает работать без
изменений. Шаги:

1. Реализация в `@nestling/container` + рантайм-тесты.
2. Миграция `examples.simple-app/src/logging/` (registry.ts + logging.module.ts)
   на `makeTokenFamily`/`familyProvider` — демонстрация и dogfooding; ручной
   паттерн остаётся в git-истории как прообраз.
3. Документация (README пакета, docs/guides).
4. Откат — revert коммитов; пользовательских миграций нет.

## Open Questions

- **Явная материализация члена без потребителя** (seed-опция
  `familyProvider(f, r, { include })` или `family.pin('app')`): отложено до
  реальной потребности — текущие кейсы покрыты deps-упоминаниями; расширение
  аддитивно (D4).
- **Многопараметрические семейства** (`IQueue('orders', 'dlq')`): отложено —
  требует решения о канонизации id (экранирование разделителя); v1 сознательно
  однопараметрический (D2).
- **Типизированная валидация/сужение параметра** (литеральные union-скоупы
  вместо `string`): частично достижимо уже сейчас генериком
  `Params extends [param: string]` с литеральным типом; выделять ли это в
  документированный паттерн — решим при написании гайда (связан с D8).
