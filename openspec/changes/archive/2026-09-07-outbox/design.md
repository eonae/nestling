## Context

`emit` доставляет сообщение в шину сразу. Бизнес-изменение коммитится
отдельно. Между коммитом и отправкой есть окно, в котором падение процесса
теряет событие. Общая транзакция между фичами запрещена правилом портов
([operations.md §2.4](../../../docs/design/operations.md)), поэтому
согласованность между фичами держится событиями — и без транзакционного
emit'а не держится вовсе.

Ограничения, в которых решается задача:

- ядро не тянет хранилище, поэтому решение живёт в сателлите;
- kernel-пакеты в этом change'е не изменяются — это условие замера границы;
- пакет не зависит ни от одного драйвера базы данных;
- у приложения уже есть своя дисциплина транзакций, и второго владельца
  транзакции у него быть не должно.

Базовая линия API — `main` после change'ей 45, 46 и 49. Роли классов —
`@Component`, `@Resource` и `@Handler`; хуков `@OnInit` и `@OnDestroy`
больше нет, захват и освобождение выражает ресурс, начало фоновой работы —
`@OnStart(signal)`.

Разбор вариантов — ревью
[d/13](../../../docs/history/discussions/13-framework-review-3.md) и
последующее обсуждение с автором.

## Goals / Non-Goals

**Goals:**

- Событие, отправленное из транзакции, переживает падение процесса после
  коммита.
- Транзакционность emit'а видна в коде вызывающего, а не назначается
  невидимо на сборке.
- Отсутствие транзакции обнаруживается на фазе ASSEMBLE, а не на первом
  запросе в проде.
- Пакет собирается из публичных примитивов; ядро не получает диффа.

**Non-Goals:**

- Саги, корреляция, состояние процесса.
- Драйверы баз данных и миграции схемы таблицы.
- Управление транзакцией: пакет её не открывает, не коммитит и не
  откатывает.
- Дедупликация на приёме.

## Decisions

### 1. Точка врезки — явный DI-токен `outboxed(Op)`

Транзакционный эмиттер даётся вторым токеном рядом с `Op.emitter`, а не
подменяет его.

```typescript
@Handler([outboxed(UserCreated), UsersRepository$])
export class CreateUserHandler {
  constructor(
    private readonly userCreated: Emitter<typeof UserCreated>,
    private readonly users: UsersRepository,
  ) {}
}
```

Тип значения — тот же `Emitter<C>`, поэтому тело хендлера не меняется;
меняется одна строка в списке зависимостей.

Отвергнуто:

- **Обёртка шины под `MessageBus$`.** При политике `local-first` команда с
  co-located реализацией идёт через `dispatch` мимо шины
  (`kernel.ts`, `bindsRemote`), поэтому корректность потребовала бы
  `always-remote` для всего приложения. Гранулярности по операциям нет.
- **Подмена члена `EmitterFamily`.** Ближе всего к записи
  [deferred [2026-07-13]](../../../docs/decisions/deferred.md), но
  повторная регистрация рецепта семейства — ошибка контейнера
  (`container.builder.ts`), а публичной точки декорирования провайдера нет.
  Кроме того, невидимая транзакционность спорит с принципом «explicit over
  implicit».
- **Метод плагина `appOutbox.emitter(Op)`.** Список операций вошёл бы в тип
  плагина, и операция вне списка не компилировалась бы — проверка строже,
  чем ошибка сборки. Отвергнуто из-за направления импорта: файл endpoint'а
  импортировал бы значение, параметризованное составом приложения. Endpoint
  импортирует декларации — слои, секции конфига, операции; значения
  композиционного корня в файл фичи не попадают. Разделение экспортов
  барелем (`plugin` в корень, `emitter` в endpoint'ы) проблему не снимает:
  значение остаётся тем же.

Следствие выбора: оба эмиттера сосуществуют. Нетранзакционный emit из
`@OnStart` или фоновой задачи выражается штатным `Op.emitter`, поэтому
конфигурации вида «отправить напрямую, если транзакции нет» не нужно.

### 2. Список операций передаётся плагину явно

`outboxed(Op)` возвращает член семейства DI-токенов, ключ — имя операции.
Рецепту семейства нужна сама операция: схема входа для проверки payload и
имя subject'а. Операции перечисляются при объявлении плагина.

```typescript
export const appOutbox = outbox({
  transaction: Tx,
  store: OutboxStore$,
  operations: [UserCreated, OrderPlaced],
});
```

Запрошенный член семейства, которого нет в списке, роняет сборку с
указанием добавить операцию.

Отвергнут реестр уровня модуля, который наполнялся бы вызовами
`outboxed(Op)` при импорте. Глобальный реестр деклараций уже удалялся из
ядра вместе с `@Endpoint` (change 8); повторять его в сателлите нельзя.

Отсюда ограничение: экземпляр плагина в приложении один. Рецепт семейства
регистрируется однажды, и второй вызов `outbox(...)` контейнер отклонит как
повторную регистрацию. Ограничение записывается в README пакета.

### 3. Транзакция — предпосылка приложения

Пакет получает транзакцию, но не управляет ею. Переменную контекста
объявляет приложение своим типом и передаёт плагину параметром:

```typescript
export const Tx = contextVar<DbTransaction>()('tx');
```

Пакет читает её через `Ctx(options.transaction)` и передаёт значение в
`OutboxStore.append(tx, records)` непрозрачно, ни одного метода на нём не
вызывая.

Адаптер хранилища приложение поставляет любой формой ресурса: классом с
`@Resource` или функциональным `resourceProvider(OutboxStore$, { deps,
acquire, release })`. Своего класса писать не обязательно.

Решающий довод — драйвер. Адаптер хранилища и транзакция обязаны быть на
одном соединении. Пакет, который везёт слой транзакции, обязан везти и
драйвер, и перестаёт быть драйвер-независимым. Поэтому граница проходит
здесь.

### 4. Предпосылка проверяется политикой, а не соглашением

`Ctx(Tx).peek() === undefined` на первом запросе в проде — недопустимый
режим отказа для фреймворка с правилом «guarantee over convention».
Пакет отдаёт политику значением, корень подключает её в `policies:`:

```typescript
policies: [appOutbox.requiresTransaction({ pattern: /^(POST|PATCH|DELETE) / })],
```

Предикат — `hasVar` по переданной переменной. Фильтр endpoint'ов задаёт
корень: какие endpoint'ы обязаны быть в транзакции, знает приложение.
Приложению доступен и более строгий вариант — `hasLayer` по собственному
слою транзакции: он покрывает и коммит с откатом, а не только открытие.

### 5. Переменную транзакции объявляет юнит-мост

`Var.provide(compute)` принимает функцию от контекста и зависимостей из
контейнера не получает (`variable.ts`). Соединение приходит из контейнера,
поэтому слой приложения выглядит так:

```typescript
export const transactional = makePipeline()
  .pre(ProvideDb)                                              // @Handler-юнит
  .pre(Tx.provide<{ db: Db }>((ctx) => ctx.input.db.begin()))  // объявляет переменную
  .ok(CommitTransaction)
  .catch(RollbackTransaction);
```

Требование второго юнита к контексту проверяется компилятором в точке
композиции. Цена — один юнит-мост; она фиксируется как находка замера, а
не закрывается правкой ядра.

### 6. Запись проверяется схемой в момент `emit`

Обёртка валидирует payload схемой `input` операции до записи в хранилище.
Ошибка схемы обязана падать в транзакции вызывающего: в relay откатывать
уже нечего.

### 7. Relay публикует напрямую в шину

Relay — фоновая задача на `@OnStart`, а не эмиттер: публикация через
`outboxed(Op)` дала бы рекурсию.

```typescript
await this.bus.publish(record.subject, record.payload, {
  idempotencyKey: record.id,
  durable: record.durable,
});
```

`PublishOptions.idempotencyKey` есть у шины независимо от вида операции,
на приёме он приходит как `BusMessageMeta.idempotencyKey`. Поэтому
at-least-once доставка события закрывается идентификатором записи, хотя
типизированный `meta.idempotencyKey` ядро даёт только командам.

### 8. Relay — ресурс, а не компонент

Relay обязан дописать партию до того, как хранилище закроется. Фаза
SHUTDOWN взводит сигнал `@OnStart`, а затем освобождает ресурсы в обратном
топологическом порядке ([composition.md](../../../docs/design/composition.md)),
и завершения фоновой задачи компонента при этом никто не ждёт.

Поэтому relay объявлен ресурсом: `static acquire` конструирует его,
`@OnStart(signal)` запускает цикл, а `release()` дожидается конца текущей
партии. Relay зависит от хранилища, поэтому обратный порядок освобождает
его раньше адаптера — ровно та очерёдность, которая нужна.

Компонент с `@OnStart` отвергнут: сигнал он получил бы, но процесс мог бы
выйти на середине партии, и записи остались бы отмеченными как взятые в
работу.

Цикл разложен на два уровня: публичный метод `drain()` выполняет один
проход по партии, `@OnStart` повторяет его до сигнала. Так тесты
детерминированы: `assembleTest` останавливается после WIRE и `@OnStart` не
выполняет ([test-composition-root](../../specs/test-composition-root/spec.md)),
поэтому тест вызывает `drain()` сам и не ждёт таймера.

### 9. Порядок внутри раздела

Порядок внутри агрегата — необязательное поле
`partitionKey`: следующая запись раздела не отправляется, пока не отправлена
предыдущая. Между разделами порядка нет.

### 10. Отсутствие шины в графе роняет сборку

`MessageBus$` попадает в граф, только когда корень поставил шину или есть
реализации операций (`kernel.ts`, `busInGraph`). Событие без подписчиков
реализаций не создаёт, поэтому приложение с outbox'ом и без подписчиков
дало бы relay, которому некуда публиковать.

Плагин зависит от `MessageBus$` и роняет сборку с текстом, называющим обе
починки: подключить транспорт шины или убрать плагин. Молчаливый простой
отвергнут: запись копится, никто не замечает.

### 11. Признак «relay в этом процессе» — поле секции конфига

В split-развёртывании relay нужен не в каждом процессе. Признак читается
из секции конфига пакета. Переключатели состава (change 47) выразили бы
это лучше, но change не закрыт, и зависеть от него здесь незачем.

## Risks / Trade-offs

- **Идиома `db.transaction(cb)` исключена** → транзакция обязана
  открываться пайплайном, а не колбэком внутри репозитория: снаружи
  колбэка транзакции нет, и атомарность недостижима в принципе. Смягчение:
  правило стоит первой строкой README пакета, глава гайда показывает
  репозиторий, читающий транзакцию из контекста.
- **Семантика `emit` меняется** → `Promise<void>` завершается по факту
  записи, а не доставки. Смягчение: сказано в README и в JSDoc токена;
  прямой эмиттер с прежней семантикой остаётся доступен.
- **Задержка доставки** → между коммитом и публикацией проходит до
  интервала опроса. Смягчение: интервал настраивается; событие
  `outbox.published` даёт измеримую задержку.
- **Дубли при падении между публикацией и отметкой** → доставка
  at-least-once. Смягчение: ключ идемпотентности равен идентификатору
  записи, дедупликация — обязанность обработчика.
- **Реплики разбирают одну таблицу** → конкурентный `claim`. Смягчение:
  вся сложность спрятана за одним методом интерфейса, адаптер SQL
  реализует его пропуском заблокированных строк.
- **Замер границы может упереться в ядро** → тогда change фиксирует
  находку записью журнала и не правит kernel-пакет. Риск для сроков, не
  для дизайна.

## Migration Plan

Обратной совместимости нет: пакет новый, публичное API ядра не меняется.
Приложение подключает пакет тремя шагами — объявить переменную транзакции,
поставить адаптер `OutboxStore`, перечислить операции в `outbox({ … })`.
Откат — удалить плагин и вернуть `Op.emitter` в списки зависимостей.

## Findings

Правило «файл endpoint'а импортирует декларации, но не значения,
параметризованные составом приложения» в документации не записано и
линтером не проверяется. В примерах оно соблюдается: барели
`plugins/auth` и `plugins/observability` делят экспорты на значение для
корня и слой для endpoint'ов, а `appAuth` и `appObservability`
встречаются только в `app.ts`. Правил у `@nestling/eslint-plugin` два —
`endpoint-has-layer` и `import-through-barrel`, — и это не покрыто ни
одним.

Место правила — `conventions.md`, проверка — третье правило линтера. В
скоуп этого change'а не входит.

## Open Questions

- Нужна ли константа DDL таблицы на диалект строкой в пакете. Драйвера она
  не требует, но фиксирует форму таблицы, которую пакет читает только через
  адаптер.
- Стоит ли пакету публиковать факт `outbox.lag` рядом с `published` и
  `stuck`, или задержка выводится потребителем из `published`.
