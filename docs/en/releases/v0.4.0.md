# 0.4.0

> All `@nestlingjs/*` packages ship as one version. The release carries
> the commits from the `v0.3.0` tag to the `v0.4.0` tag, 14 September
> 2026. An old name is removed together with its replacement: there are
> no aliases or wrappers in the packages.

## Upgrading

```bash
yarn up '@nestlingjs/*'
```

The version is one for all packages: a package of the previous version
does not work next to a new one. The Node requirement is the same, 24
and above.

The NATS client moved to the peer dependencies, so an application with a
bus installs it itself:

```bash
yarn add nats@^2.29.3
```

The configuration source on top of Vault is installed separately, as
needed:

```bash
yarn add @nestlingjs/config.vault
```

The full reference of the environment is
[compatibility.md](../compatibility.md).

## Breaks silently

The compiler will not show these changes: the code builds and behaves
differently.

- The order in which configuration sources start no longer follows the
  order of the list: it is derived from `needs`. A source that stood
  first in the list starts after the one whose keys it needs —
  [section](#a-source-takes-its-coordinates-from-another-source).
- A failure under the `argv()` marker does not reach a `catch`: the
  boundary prints the message and ends the process. A `try`/`catch`
  around `build(argv(process.argv)).run()` stops firing —
  [section](#a-failure-under-the-argv-marker-is-a-message-and-exit-code-1).
- `check()` fails where it used to print a report with the
  `implemented: false, called: true` line. A topology without an owner
  of the operation stops passing the smoke check —
  [section](#an-unreachable-operation-is-a-build-phase-failure).
- The `nats` client does not arrive as a dependency of the transport.
  The installation passes, and the build fails on the import —
  [section](#nats-is-a-peer-dependency).

## Configuration

### A source takes its coordinates from another source

`ConfigSource` got the `needs` field, a DI token of the section whose
values the source needs to start. The validated values arrive as an
argument of `init()`.

```typescript
// src/sources/vault.ts — 0.3.0
export const vaultSource: ConfigSource = {
  name: 'vault',
  // There was nowhere to take the address and the token from: the reader
  // had not projected a single section yet, and the source read
  // process.env itself
  async init(): Promise<void> {
    this.secrets = await read(process.env.VAULT_ADDR, process.env.VAULT_TOKEN);
  },
  get: (key) => this.secrets[key],
};
```

```typescript
// src/sources/vault.ts — 0.4.0
export const vaultSource: ConfigSource<VaultCoordinates> = {
  name: 'vault',
  needs: VaultConfig,
  async init(values): Promise<void> {
    this.secrets = await read(values.addr, values.token);
  },
  get: (key) => this.secrets[key],
};
```

The type of a source became parameterized: `ConfigSource<Needs>` declares
`needs` and accepts the values of the section. A source without `needs`
gets `undefined` and declares `init()` without parameters, as before.

The order in which sources start is derived from the declaration. The
order of the list of bindings stays the priority of key resolution and
only that: Vault, standing above `.env` in the list, starts after it,
because it takes its address from there.

```typescript
// src/main.ts — 0.4.0
await app.build(argv(process.argv)).run({
  config: [
    bind(vault(VaultConfig, { retries: 2 }), { timeout: 3000 }),
    ...defaultSources,
  ],
});
```

The section of coordinates is projected from the sources that started
earlier, and its values are fixed in the snapshot. Vault itself is not
asked about `VAULT_ADDR`, even when it is bound without `keys`:
otherwise the coordinates of Vault would be looked up in Vault itself.

Phase 0 fails before any input and output in three cases: the bindings
reference each other through `needs`, the `needs` section is not covered
by the sources that started, the section is declared
`makeConfig.reloadable`. The message names the source and the missing
keys. Read more in [chapter 7](../guide/07-config.md) and in the recipe
["Configuration from a file and without a restart"](../recipes/config-sources.md).

> Upgrade: mechanical — the `init()` of an own source gets a parameter,
> and the reading of `process.env` inside it is replaced by the `needs`
> field.
> Why: [ideas.md, `[2026-09-13] Конфигурация: привязки на run(), env() и dotenv() умолчанием, bind(), needs у источника`](../../decisions/ideas.md#2026-09-13-%D0%BA%D0%BE%D0%BD%D1%84%D0%B8%D0%B3%D1%83%D1%80%D0%B0%D1%86%D0%B8%D1%8F-%D0%BF%D1%80%D0%B8%D0%B2%D1%8F%D0%B7%D0%BA%D0%B8-%D0%BD%D0%B0-run-env-%D0%B8-dotenv-%D1%83%D0%BC%D0%BE%D0%BB%D1%87%D0%B0%D0%BD%D0%B8%D0%B5%D0%BC-bind-needs-%D1%83-%D0%B8%D1%81%D1%82%D0%BE%D1%87%D0%BD%D0%B8%D0%BA%D0%B0), points 6–8.

### `@nestlingjs/config.vault`

A package with one source: `vault(section, options?)` reads a KV v2
secret in one request on phase 0.

```typescript
// src/main.ts
import { bind, defaultSources } from '@nestlingjs/app';
import { vault, VaultConfig } from '@nestlingjs/config.vault';

await app.build(argv(process.argv)).run({
  config: [
    bind(vault(VaultConfig, { retries: 2 }), { timeout: 3000 }),
    ...defaultSources,
  ],
});
```

The `VaultConfig` section declares `VAULT_ADDR`, `VAULT_TOKEN` under
`secret()`, `VAULT_MOUNT` with the `secret` default and `VAULT_PATH`. An
application with two stores declares its own section of any shape that
fits `VaultCoordinates` and passes it as the same argument.

The package does not take a Vault client: the request goes through the
standard `fetch`, and the source presents itself with the
`X-Vault-Token` header. `retries` is the number of additional attempts
on a network failure and on a `5xx` response; the pause starts at 250 ms
and doubles. The `401`, `403` and `404` responses cause no retry.

The package has three boundaries: one authentication method, no watching
of a secret, one engine — KV v2 at the `{mount}/data/{path}` path. Read
more in the README of the package and in the recipe
["Configuration from a file and without a restart"](../recipes/config-sources.md).

## The build

### An unreachable operation is a BUILD phase failure

A call to an operation that nobody can serve is rejected on the BUILD
phase. The check moved from the factory of the invoker into the recipe
of the family, so both entries that do not reach INIT see it:
`App.check()` and `checkTopologies`.

```typescript
// scripts/check.ts — 0.3.0
const report = await app.check(argv(process.argv));
// a topology without an owner of the operation passed the smoke check
// and printed { operation: 'billing.charge', implemented: false, called: true }
```

```typescript
// scripts/check.ts — 0.4.0
const report = await app.check(argv(process.argv));
// Operation 'billing.charge' (kind 'request') is injected as '.caller',
// but no selected feature implements it and this build has no intercom,
// so the call has nowhere to go…
```

The failure is counted by two conditions at once: there is no co-located
implementation, and the bus does not deliver outside the process. With a
remote bus the absence of a local owner is legitimate — the owner may
live in another process, and its unavailability stays an ordinary
delivery failure. An event does not stop being an exception: a broadcast
without subscribers is legitimate.

The line "every called operation has an owner or a bus" of
[guarantees.md](../guarantees.md) promised the BUILD phase before too —
the code came to the promise. Read more in
[chapter 20](../guide/20-split.md).

> Upgrade: needs a decision — a topology that used to reach INIT is now
> rejected at build time: either the owning feature is added to the
> argument, or the selection is closed over calls with `includeDeps`.
> Why: [ideas.md, `[2026-09-14] Разбор отчёта об обновлении до 0.3.0`](../../decisions/ideas.md#2026-09-14-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D1%82%D1%87%D1%91%D1%82%D0%B0-%D0%BE%D0%B1-%D0%BE%D0%B1%D0%BD%D0%BE%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8-%D0%B4%D0%BE-030-%D0%B7%D0%B0%D0%BC%D0%B5%D1%82%D0%BA%D0%B0-020-%D0%B2%D0%B5%D1%80%D1%81%D0%B8%D1%8F-%D1%83-%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%D0%B0-%D0%B4%D0%BE%D1%81%D1%82%D0%B8%D0%B6%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C-%D0%BD%D0%B0-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B5), point 5.

### The nature of a bus is a field of the declaration

`BusDeclaration` got the required `remote` field. The `remote` property
of `IMessageBus` is removed: the nature of a bus stopped being a
capability of an instance, because on the BUILD phase there are no
instances yet.

```typescript
// src/bus/my-bus.ts — 0.3.0
export class MyBus implements IMessageBus {
  readonly remote = true;
  readonly durable = false;
  // …
}
```

```typescript
// src/bus/my-bus.ts — 0.4.0
export class MyBus implements IMessageBus {
  readonly durable = false;
  // …
}

export const myBus = (): BusDeclaration =>
  transportValue(MyBus$, new MyBus(), {
    capabilities,
    bus: true,
    remote: true,
  });
```

The instance keeps `durable`. This is the same split as with the
`capabilities` of a transport: what the build check needs lies in the
declaration. The built-in `nats()` declares `remote: true` itself, and
an application that uses it needs no edits.

> Upgrade: mechanical — an own bus implementation moves `remote` from the
> class into the transport declaration.
> Why: [ideas.md, `[2026-09-14] Разбор отчёта об обновлении до 0.3.0`](../../decisions/ideas.md#2026-09-14-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D1%82%D1%87%D1%91%D1%82%D0%B0-%D0%BE%D0%B1-%D0%BE%D0%B1%D0%BD%D0%BE%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8-%D0%B4%D0%BE-030-%D0%B7%D0%B0%D0%BC%D0%B5%D1%82%D0%BA%D0%B0-020-%D0%B2%D0%B5%D1%80%D1%81%D0%B8%D1%8F-%D1%83-%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%D0%B0-%D0%B4%D0%BE%D1%81%D1%82%D0%B8%D0%B6%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C-%D0%BD%D0%B0-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B5), point 5.

## The entry point

### A failure under the `argv()` marker is a message and exit code 1

An entry that got `argv(process.argv)` ends the process itself not only
on `--help`, but on a failure too. The message goes to `stderr` without
a stack, and the exit code is `1`. The rule holds at three entries:
`build(…).run()`, `discover(…)` and `check(…)`.

```bash
# 0.3.0
node dist/main.js --features orders
# node:internal/process/promises:394
#             triggerUncaughtException(err, true /* fromPromise */);
#             ^
# Error: Config section 'vault' is not covered by any bound source
#     at project (/app/node_modules/@nestlingjs/app/dist/config/reader.js:214:11)
#     … twelve more frames of the internals of the package
```

```bash
# 0.4.0
node dist/main.js --features orders
# Error: Config section 'vault' is not covered by any bound source
#   caused by: Error: VAULT_ADDR, VAULT_TOKEN
echo $?  # 1
```

The `cause` chain is unfolded into the text: every level takes its own
line with an indent. A configuration failure and a constructor failure
carry the reason in `cause`, and without it the message of the top level
does not name the culprit. There is no stack in the text — the frames
are addressed to the author of the framework, and the text is read by
the author of the application.

The object form of the argument does not change its behaviour: an
embedded application and a test catch the promise themselves, and the
process does not belong to them. Read more in
[chapter 19](../guide/19-select.md).

> Upgrade: needs a decision — an application that caught the failure
> around `run()` moves to the object form of the argument; an entry point
> under the marker leaves printing and exiting to the boundary.
> Why: [ideas.md, `[2026-09-14] Разбор отчёта об обновлении до 0.3.0`](../../decisions/ideas.md#2026-09-14-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D1%82%D1%87%D1%91%D1%82%D0%B0-%D0%BE%D0%B1-%D0%BE%D0%B1%D0%BD%D0%BE%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8-%D0%B4%D0%BE-030-%D0%B7%D0%B0%D0%BC%D0%B5%D1%82%D0%BA%D0%B0-020-%D0%B2%D0%B5%D1%80%D1%81%D0%B8%D1%8F-%D1%83-%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%D0%B0-%D0%B4%D0%BE%D1%81%D1%82%D0%B8%D0%B6%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C-%D0%BD%D0%B0-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B5), point 7.

## The NATS transport

### `nats` is a peer dependency

The consumer installs the client of the broker, with the version that
fits its broker. The manifest of `@nestlingjs/transport.nats` is brought
to what the README of the package promises the reader.

```bash
# 0.3.0 — the client arrived as a dependency of the transport
yarn add @nestlingjs/transport.nats
```

```bash
# 0.4.0
yarn add @nestlingjs/transport.nats nats@^2.29.3
```

> Upgrade: mechanical — `nats` is added to the dependencies of the
> application; the range is `^2.29.3`.

### The connector is assembled by an adapter

`defaultConnector` assembles the `NatsLike` boundary from
`NatsConnection` explicitly: `headers()` is taken by a module import,
`StreamInfo` and `ConsumerInfo` are unfolded down to the configuration,
and `ack_policy` is translated into a value of the enumeration of the
client. The cast through `unknown` is gone — the compiler must catch a
divergence from the client.

A durable subscription goes through the simplified consumers API:
`js.consumers.get(stream, durable)` and `consume()` instead of
`js.subscribe(subject, opts)`. The `NatsJetStreamLike.subscribe`
boundary stayed the same; what the adapter fulfils it with changed.

This does not concern an application: the io shapes, the call envelope,
the deduplication window and the mapping onto a subject did not change.

> Why: [ideas.md, `[2026-09-12] Коннектор к живому клиенту nats: адаптер вместо каста`](../../decisions/ideas.md#2026-09-12-%D0%BA%D0%BE%D0%BD%D0%BD%D0%B5%D0%BA%D1%82%D0%BE%D1%80-%D0%BA-%D0%B6%D0%B8%D0%B2%D0%BE%D0%BC%D1%83-%D0%BA%D0%BB%D0%B8%D0%B5%D0%BD%D1%82%D1%83-nats-%D0%B0%D0%B4%D0%B0%D0%BF%D1%82%D0%B5%D1%80-%D0%B2%D0%BC%D0%B5%D1%81%D1%82%D0%BE-%D0%BA%D0%B0%D1%81%D1%82%D0%B0).

## The linter

`@nestlingjs/eslint-plugin` got two rules, both at the `error` level.

`conditional-spread` catches a conditional spread in an object literal.
A ternary with an empty literal is rewritten by the autofix, but only
when the test is boolean by its shape; a spread through `&&` with a
non-boolean test reports the trap of zero and of an empty string.

```typescript
// src/http/options.ts — before
const options = { ...(verbose ? { level: 'debug' } : {}), ...(port && { port }) };
```

```typescript
// src/http/options.ts — after
const options = {
  ...(verbose && { level: 'debug' }),
  ...(port !== undefined && { port }),
};
```

`no-process-globals` forbids `process.env` and `process.argv` in
sources. The environment reaches the application through the `env()`
source, and the command line through the `argv()` marker. One form is
allowed: `process.argv` as the immediate argument of `argv()`. A
legitimate reading — the seam of an adapter, a script, a client outside
the container — is silenced by an `eslint-disable` directive with the
reason in the file itself.

The plugin has no preset: a config lists the rules by name. Read more in
[conventions.md](../conventions.md) and in the README of the package.

> Upgrade: mechanical — spreads are rewritten as an `&&` with an explicit
> comparison, and a reading of a process global is replaced by the `env()`
> source or silenced by a directive with a reason.
> Why: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), point 11,
> and [ideas.md, `[2026-09-13] Аргумент сборки: argv() по схеме декларации`](../../decisions/ideas.md), point 6.

## The agent skill

`npx @nestlingjs/agent-skill` writes a `.manifest.json` manifest next to
the files of the skill — the version of the package and the hash of
every file it put there. By it a repeated installation tells an edited
file from a merely old one:

- the manifest recognises the hash of a file — the file is replaced by
  the new version silently;
- the hash is not recognised — the command names the file, leaves it as
  it is and exits with code 1; `--force` overwrites.

A copy installed by a previous version of the command has no manifest.
There is nothing to compare with, so one `--force` is the price of the
first update.

The text of the skill names the version of Nestling it describes, and
the agent compares it with the version of `@nestlingjs/app` in the
`package.json` of the project. They diverged — the agent says so and
offers a reinstallation.

The composition grew to fourteen files: the catalogue of packages moved
into `references/packages.md`, and the references of observability and
of storage appeared. Eleven places are rewritten to the forms of 0.3.0 —
the configuration reference in full, `doc: { status }`, the string form
`build('users')` and the bindings in the topology matrix.

> Upgrade: mechanical — the first update of the skill goes with
> `--force`, and after that the manifest is there and updates go
> silently.
> Why: [ideas.md, `[2026-09-14] Разбор отчёта об обновлении до 0.3.0`](../../decisions/ideas.md#2026-09-14-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D1%82%D1%87%D1%91%D1%82%D0%B0-%D0%BE%D0%B1-%D0%BE%D0%B1%D0%BD%D0%BE%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8-%D0%B4%D0%BE-030-%D0%B7%D0%B0%D0%BC%D0%B5%D1%82%D0%BA%D0%B0-020-%D0%B2%D0%B5%D1%80%D1%81%D0%B8%D1%8F-%D1%83-%D1%81%D0%BA%D0%B8%D0%BB%D0%BB%D0%B0-%D0%B4%D0%BE%D1%81%D1%82%D0%B8%D0%B6%D0%B8%D0%BC%D0%BE%D1%81%D1%82%D1%8C-%D0%BD%D0%B0-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B5), point 4.

## Removed

- The `remote` property of `IMessageBus`. The nature of a bus is
  declared by the `remote` field of the transport declaration.
- `MessageBus$` from the dependencies of the invoker recipes: there is
  nothing left to read on the instance.
- `nats` from the dependencies of `@nestlingjs/transport.nats`. The
  client moved to the peer dependencies and needs no replacement.
- The requirement of `port-binding` for the failure text to name the
  consuming module: the recipe of a family knows the name of the
  operation, but not who injects it.

## Testing

- The `checkTopologies` matrix sees an unreachable operation: a topology
  that will not come up fails at build time instead of printing a
  report.
- `yarn test:live` runs the packages against real services. `compose.yaml`
  brings up `nats:2` with JetStream, and the `docker-compose.yml` of the
  `config.vault` package brings up Vault in dev mode. Without the
  `TEST_VAULT_ADDR` and `TEST_VAULT_TOKEN` variables the run is skipped.
- The live run became a step of the release: `RELEASING.md` requires it
  before the version is raised.

## For those who build the repository

The verification of the repository became a graph of tasks instead of a
schedule. `typecheck`, `lint` and `test` declared
`dependsOn: ["^build", "build"]`, the default parallelism is six tasks,
and the nx cache directory is moved out of the working tree: a session
in a new worktree no longer starts with 170 seconds.

The build stopped checking types. swc emits the JavaScript, a per-file
emitter of TypeScript emits the declarations, and `typecheck` stayed the
only type check per run. Hence `isolatedDeclarations: true` in the base
and the explicit annotations on the public exports: 33 places in `app`,
8 in `operations`, 7 in `transport.http`, 1 in `container`. There is one
exception — `drizzle.pg` is built by `tsc`.

`skipLibCheck: true` moved into `tsconfig.base.json`, and the strict
pass got its own name: `verify:strict` runs `typecheck` without that
flag over the built `dist`. It lives on the release path, not in every
run.

Two methods of `BuiltApp` with computed names are declared by
declaration merging: next to `declare class BuiltApp` in the `.d.ts`
there is now `export interface BuiltApp`. The set of methods and their
signatures are the same.

`yarn docs:audit` got two invariants. `deleted-names` catches a removed
public name in the live texts: the list is the difference of the barrels
across all release tags and `HEAD`, 135 names. `landing-lead` requires
exactly one paragraph of prose in `docs/index.md` before the first `##`:
the landing template takes the first paragraph as the lead and silently
drops the second.
