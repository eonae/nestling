# 16. Обновление демо-приложения до 0.3.0: отчёт внешнего агента (2026-09-14)

> Замороженная запись. Решения — запись

> обновлении до 0.3.0»; change'и 104–109 —

## 1. Источник

Агент вне репозитория обновил демо-приложение «сервис коротких ссылок» с
0.1.3 сразу до 0.3.0, минуя 0.2.0. Приложение — то же, что в первом
внешнем прогоне ([d/14](./14-first-external-run.md)): две фичи, пять
endpoint'ов, восемь тестов. Обновление заняло один проход по пяти файлам;
тесты, typecheck и endpoint'ы после него живые.

По итогам агент оставил отчёт с девятью найденными проблемами и сводкой
приоритетов. Документ хранится в артефактории
(`nestling-0.3.0-upgrade-report.md`, 2026-09-14) и приведён ниже без
правок: опущен только его заголовок, остальные заголовки понижены на
один уровень.

Ценность отчёта в том, что он написан с позиции, которой в репозитории
нет ни у кого: читатель видел только опубликованные пакеты и
`docs/en/releases/`, а историю решений — нет.

## 2. Исходный документ

**Проект:** `nestling-test` (демо-сервис коротких ссылок, две фичи)
**Переход:** `0.1.3` → `0.3.0`
**Дата:** 14 сентября 2026
**Статус:** обновление завершено — 8/8 тестов зелёные, typecheck чистый, приложение
поднимается, все пять ручек отвечают как раньше.

Источник правок — [`docs/en/releases/v0.3.0.md`](https://github.com/eonae/nestling/blob/main/docs/en/releases/v0.3.0.md).
Всё, что ниже помечено «проверено», воспроизведено в этом репозитории.

### 2. Впечатления

**Легло хорошо.** Один проход, пять файлов, без тупиков.

**`status` наверх из `doc` — правильный шаг, и типы это ловят.** `Ok.created` перестал
компилироваться под `Output<Link, typeof AliasTaken>`, пока не дописал третий
параметр `'created'`. Это та жёсткость, ради которой всё и затевается.

**RFC 9457 приехал консистентно в оба места** — и в рантайм, и в документ, без
единой строки в декларации:

```
$ curl -i localhost:3111/links/nope
HTTP/1.1 404 Not Found
content-type: application/problem+json

{"type":"urn:error:not_found:link","title":"Not Found","status":404,
 "detail":"Short link nope does not exist","details":{"code":"nope"}}
```

```
POST /links      → 201 application/json | 400, 401, 409, default → problem+json
GET  /links      → 200 application/json | 400, default
GET  /links/{code} → 200 application/json | 400, 404, default
GET  /r/{code}   → 302 (без тела)        | 400, 404, default
```

`201` у `POST /links` встал из `status:` автоматически.

**`--help` из декларации** — писать нечего, схема выводится сама:

```
Usage: node dist/main.js [options]

Features: links, stats

Options:
  --features <all|name,…>  Features to build. Default: all
  --include-deps           Add features whose operations the selection calls
  --help                   Print this schema and exit
```

**Конфиг-привязки на `run()`** сделали `makeApp` честным «что за приложение»
вместо «чем его кормить».

**Тексты ошибок — сильная сторона.** Вот такое читается и чинится без исходников:

> `Operation 'stats.visits' (kind 'request') is injected as '.caller', but no selected
> feature implements it and this build has no intercom, so the call has nowhere to go.
> Either add the feature that implements it to the build argument (or close the selection
> over calls with 'build({ features, includeDeps: true })'), or assign the intercom role
> to a bus transport…`

**Ресурсы при падении INIT корректно разматываются** — проверено отдельно:
`release()` вызывается, утечки нет.

### 3. Реальные проблемы

#### 3.1. Нет release notes для 0.2.0 — корень половины боли

`docs/en/releases/` содержит только `README.md` и `v0.3.0.md`, и `v0.3.0.md`
написан как дифф **от 0.2.0**. На npm опубликованы `0.1.1`, `0.1.3`, `0.2.0`, `0.3.0`.
Все, кто ставил пакет до 13 сентября, сидят на `0.1.x` — и для прыжка
`0.1.3 → 0.2.0` документации нет вообще.

#### 3.2. `httpEndpoint` сменил форму в 0.2.0, и об этом не написано нигде

Был вызываемой функцией, стал объектом конструкторов (`.get` / `.post` / … /
`.implement`).

Проверено — дифф публичных имён барелей `0.1.3 → 0.2.0`:

```
app             удалённых имён: 0
transport.http  удалённых имён: 0
testing         удалённых имён: 0
openapi         удалённых имён: 0
operations      удалённых имён: 1  (CommandMeta)
```

Имя `httpEndpoint` на месте — сломался только его тип. То есть breaking change,
который **не ищется ни по таблице переименований, ни по разделу «Removed»**:
импорт резолвится, падает вызов. В этом проекте — 4 файла из 5 сломавшихся.

#### 3.3. `check()` не ловит недостижимый порт, хотя JSDoc обещает

JSDoc `discover()` прямым текстом: «Ошибки собранного графа он не бросает:
**неудовлетворённая зависимость**, нарушенная политика, форма io вне способностей
транспорта и отсутствие требуемого транспорта — исходы `check()`».

Проверено:

```
app.check({ features: 'links' })   → PASSED, features=['links']
                                      operations: [
                                        { name:'links.visited', implemented:false, called:true },
                                        { name:'stats.visits',  implemented:false, called:true },
                                      ]

app.build({ features: 'links' }).run()  → падает на фазе INIT
```

Данные в отчёте есть, но матрица `checkTopologies` не падает. Правило
«мокаешь — проверь топологию» на этом ломается: топология, которая заведомо не
поднимется, проходит проверку.

#### 3.4. `objectSource` убран, а прод-замены нет

В разделе «Removed» это подано как переезд в testing под именем `vars` — но `vars`
живёт в devDependency. Публичных источников в ядре осталось два: `env()` и
`dotenv(path)`.

Приложению, которое возило свои умолчания источником, деть их некуда. Здесь было
одно поле (`objectSource({ APP_PAGE_SIZE: '10' }, 'defaults')`) — перенёс в
`.default()` схемы. Для «слоя умолчаний стенда» так не выйдет.

#### 3.5. `argv()` не даёт задать умолчание `--include-deps`

Схема флагов выводится из декларации, а `includeDeps` лежит в
`RESERVED_SWITCH_NAMES` — переключателем его не объявишь, умолчание жёстко
`false`. Хочешь другое — отказывайся от `argv()` целиком, а вместе с ним от
`--help` и от выведенной схемы.

Тихая смена поведения: в этом проекте `RUN_INCLUDE_DEPS` был `true`, и
`--features links` теперь падает там, где `RUN_FEATURES=links` работал.

#### 3.6. Забытый `@nestlingjs/openapi.zod` тянет второй экземпляр ядра

Он pinned на `@nestlingjs/app: 0.1.3` **точной** версией. Проверено на чистом
проекте с `app@^0.3.0` + `openapi.zod@^0.1.3`:

```
node_modules/@nestlingjs/app                                    0.3.0
node_modules/@nestlingjs/openapi.zod/node_modules/@nestlingjs/app  0.1.3
```

Два ядра в одном процессе — бренды, DI-токены и `instanceof` перестают совпадать.
Deprecation-варнинг есть, но в выводе `npm install` теряется, а в `v0.3.0.md`
`openapi.zod` не назван ни разу (там только `@nestlingjs/models` → `schema.zod`).

**Предложение:** опубликовать `openapi.zod@0.3.0`, который просто реэкспортирует
`schema.zod`.

#### 3.7. Опечатка в deprecation-сообщении `@nestlingjs/models`

```
$ npm view @nestlingjs/models@0.2.0 deprecated
переехал в @nestling/schema.zod
```

Такого скоупа нет — правильный `@nestlingjs/schema.zod`. У `openapi.zod`
сообщение корректное («переименован в @nestlingjs/schema.zod»).

#### 3.8. Скилл `.claude/skills/nestling` устарел целиком

Это ровно тот артефакт, которым фреймворк учит агентов писать код, — и сейчас он
учит **удалённому** API по каждому пункту релиза: `assembleTest`, `app.assemble()`,
`load(RootConfig)`, `objectSource`, `config: [[source, keys]]` в корне, `openapi()`,
`doc: { status }`, `httpEndpoint({ method, path })`, `testUnit`.

Конкретные места:

| Файл | Строки |
|---|---|
| `SKILL.md` | 47, 100, 113, 116, 141 |
| `references/testing.md` | 3, 31, 49, 59, 147 |
| `references/config.md` | 84, 92–93 |
| `references/endpoints.md` | 37, 114, 170 |
| `references/errors.md` | 104 |
| `references/from-nest.md` | 16, 22, 52, 69, 70 |
| `references/features.md` | 189 |
| `references/container.md` | 3 |

Самый дешёвый и самый окупаемый фикс из всего списка.

#### 3.9. Мелочь: ошибка фазы INIT улетает сырым стеком

Текст самой ошибки отличный (см. § 2), но приходит он необработанным rejection'ом
со стеком внутренностей:

```
at assertReachable (…/@nestlingjs/app/dist/ports/kernel.js:64:11)
at buildPort      (…/@nestlingjs/app/dist/ports/kernel.js:108:5)
…
```

Рамка вокруг него — как у `--help` — читалась бы лучше.

## 3. Сверка с кодом

Проверены все девять пунктов. Подтвердились все, но два из них названы не
тем, чем оказались.

**3.1 — подтверждено.** В `docs/releases/` лежат только `README.md` и
`v0.3.0.md`. Между тегами `v0.1.3` и `v0.2.0` — 172 коммита и
15 заархивированных change'ей. Правило папки `releases/` требует заметку
на каждую версию, и 0.2.0 её не получила.

**3.2 — подтверждено, и шире, чем в отчёте.** Change `http-method-constructors`
(строка 72 roadmap) вошёл в `v0.2.0`; заметка 0.3.0 его не описывает,
потому что описывает диапазон от 0.2.0. Отдельно верен тезис о методе
поиска: таблица переименований ищет по имени, а здесь имя осталось, и
сменилась форма вызова. Тем же способом из виду ушло переименование
`@nestlingjs/openapi.zod` → `@nestlingjs/schema.zod` — оно легло в 0.2.0
коммитом `b6c25f6f` и не названо ни в одной заметке.

**3.3 — подтверждено.** Проверка достижимости живёт в `assertReachable`
(`packages/nestling.app/src/ports/kernel.ts`) и срабатывает при создании
порта, то есть на фазе 2 INIT. `check()` идёт по фазам 0–1 и до неё не
доходит. Данные для отказа в отчёте уже есть: запись карты операций несёт
`called: true`, `implemented: false` и пустой `via`. Спека
`structural-check` такого сценария не содержит — пропуск не нарушает
записанного требования, а показывает его дыру.

**3.4 — подтверждено как факт, но названо неверно.** Прод-замены у
`objectSource` нет намеренно: решение [2026-09-13] «Конфигурация: привязки
на `run()`…», пункт 9, оставляет `ConfigSource` публичным интерфейсом на
три строки. Проблема не в отсутствии замены, а в том, что документация
ведёт читателя не туда. Константа приложения — это `.default()` в схеме
секции, а не источник конфигурации: источник добывает значения извне, а
хардкод в источнике остаётся приёмом теста. Рецепт
[config-sources.md](../../recipes/config-sources.md) при этом открывается
примером, где самодельный источник раздаёт константы, и читатель копирует
именно его.

**3.5 — подтверждено.** В разборе командной строки `includeDeps`
инициализируется `false`, а имена `includeDeps` и `include-deps` лежат в
`RESERVED_SWITCH_NAMES`: переключателем их не объявить. Отказ от `argv()`
ради другого умолчания стоит `--help` и выведенной схемы флагов — размен
неравный.

**3.6 — подтверждено реестром.** У `@nestlingjs/openapi.zod` опубликованы
`0.1.1` и `0.1.3`, зависимость `@nestlingjs/app` записана точной версией
`0.1.3`. Установка рядом с `app@^0.3.0` даёт два экземпляра ядра.

**3.7 — подтверждено.** `npm view @nestlingjs/models@0.2.0 deprecated`
печатает `переехал в @nestling/schema.zod`: скоупа `@nestling` не
существует. Рядом второй дефект, которого в отчёте нет: строка русская, а
её читатель — терминал пользователя, где по правилу 12 `docs/README.md`
язык английский. Шаблон в `RELEASING.md`, по которому она написана, тоже
русский.

**3.8 — подтверждено, но причина другая.** Перечисленные в отчёте строки
принадлежат копии скилла от 0.1.3, лежащей в проекте пользователя.
Установщик сравнивает файл проекта с упакованным источником и, не найдя
совпадения, считает файл правленым вручную: нетронутая старая копия
попадает в `diverged` и без `--force` не обновляется. Заметка о выпуске
про переустановку скилла не говорит вовсе. Состояние самого скилла в
репозитории разобрано отдельно — см. раздел 4, пункт 2.

**3.9 — подтверждено.** `run()` отклоняет промис, и точка входа из
заметки о выпуске (`await app.build(argv(process.argv)).run()`) его не
ловит. Рядом с этим `--help` печатает схему в `stdout` и завершает
процесс сам, и комментарий в `args.ts` объясняет почему: «выход процесса
— поведение командной строки, а не библиотеки». Одна и та же точка входа
ведёт себя как команда при разборе флагов и как библиотека при отказе
подъёма.

## 4. Указания пользователя

Разбор принят целиком, с четырьмя уточнениями; пятое пришло следом,
отдельным вопросом. Нумерация — пользователя.

1. **Константы передаются схемами, а не источниками.** Правило
   формулируется явно и попадает в заметки о выпусках и в документацию:
   значение-константа живёт в `.default()` схемы секции, источник
   конфигурации добывает значения извне. Хардкод в источнике — приём
   теста, и только.

2. **Скилл проверить целиком, а не по трём строкам.** Механическая сверка
   имён показывает мало; нужно понять, что в скилле неактуально и чего в
   нём не хватает после 0.2.0 и 0.3.0. Отдельный вопрос: как сделать
   необходимость переустановки скилла очевидной для пользователя, не
   заводя post-install. Предложенное направление — сверку версий делает
   сам агент по правилу из скилла.

3. **Недостижимая операция на сборке — принято, реализация обсуждается
   отдельно** в сессии change'а.

4. **Умолчание `--include-deps` — принято, форма обсуждается отдельно.**

5. **Отдельный вопрос: как не забывать обновлять скилл.** Речь уже не о
   пользователе, который не переустановил копию, а об авторах
   фреймворка, которые меняют API и не трогают скилл. Проверка показала
   две причины. Скилла нет ни в Definition of Done `CLAUDE.md`, ни в
   правиле `rules.tasks` файла `openspec/config.yaml`: change
   закрывается, ни разу на него не взглянув. А механизм свежести,
   который спасает главы гайда, здесь не работает — он сравнивает дату
   плашки с коммитами в коде, и часы сбрасываются любым касанием файла.
   Последний коммит, тронувший скилл, правил в нём импорты под новый
   тест-раннер, поэтому по датам скилл выглядит свежим. Решение —
   механический инвариант на удалённые имена, пункты 9 и 10 записи
   журнала и строка 109 roadmap.
