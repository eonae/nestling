# Операции, вызыватели и клиенты

> **Целевое состояние V1.** Логика решений: [ideas.md](../decisions/ideas.md) —
> «Порты: межфичевое общение через операции» [2026-07-08], «Типизированные
> клиенты из операций» [2026-07-13], «Порты: deadline, идемпотентность,
> версионирование операций» [2026-07-13], «Операция первичен» [2026-07-13];
> уточнения реализации — записи от 2026-07-31 (порты, версионирование, NATS)
> и 2026-08-01 («Клиенты из операций: реализация»).
> Отложенное (outbox/saga) — [deferred](../decisions/deferred.md).
> Статус реализации — [roadmap](../decisions/roadmap.md).

Операция — единица общения между фичами: имя, вид, схемы входа и выхода,
список отказов. Одно и то же значение используют три стороны: реализация
(`implement`), вызывающий (`.caller` или `.emitter`) и внешний клиент
(`makeClient`). Этот документ описывает саму операцию (§1), вызывателей и
биндинг вызовов (§2), интерком и политику диспатча (§3), профиль вызова
(§4) и внешний клиент (§5).

## 1. Операция

Конструкторов три, по одному на вид. Вид следует из точки объявления, а не
из поля: правила видов расходятся, и расхождение проверяет тип.

```typescript
export const ChargeCard = makeRequest({
  name: 'billing.charge',            // адрес: subject интеркома, ключ discovery
  http: 'POST /billing/charges',     // HTTP-адрес (опционально); bind-карта
  input:  z.object({ orderId: z.string(), amount: z.number() }),
  output: z.object({ chargeId: z.string() }),
  errors: [CardDeclined],            // типизированный список отказов (errors.md)
  doc: { summary: 'Charge a card', tags: ['billing'] },  // schemas.md §2.2
});

export const SendReceipt = makeCommand({
  name: 'billing.send-receipt',
  input: z.object({ orderId: z.string() }),
  durable: true,                     // указание переживает недоступность
});

export const OrderPlaced = makeEvent({
  name: 'orders.placed',
  input: z.object({ orderId: z.string() }),
});
```

| Конструктор | Вызыватель | `output` / `errors` | `durable` | `subscriber` у реализации |
|---|---|---|---|---|
| `makeRequest` | `.caller` | есть | невыразим | запрещён |
| `makeCommand` | `.emitter` | есть | есть | запрещён |
| `makeEvent` | `.emitter` | невыразимы | есть | обязателен |

Правила читаются как типы, а не как проверки при создании значения:
`makeEvent({ output })` не компилируется, потому что ответа у события нет;
`makeRequest({ durable })` не компилируется, потому что вызывающий ждёт
ответа и переживать нечего.

### 1.1. Адреса

`name` — адрес операции на шине (subject NATS) и ключ discovery. `http:` —
адрес того же операции для HTTP; поле необязательное. Операция нейтрален к
направлению: одно значение служит и реализации, и вызову. К транспорту он не
нейтрален: адреса всех транспортов объявляются в нём. Bind-карта HTTP-адреса
вычисляется при объявлении, поэтому ошибка в ней обнаруживается у
владельца операции, а транспорт, OpenAPI и клиент читают готовую карту из
одного импорта.

### 1.2. Секция `doc:`

Секция документации принадлежит операции наравне с `input`, `output` и
`errors`: документация операции — часть её интерфейса. Внешний потребитель
получает её тем же импортом, что и схемы. В форме с операцией декларации
переобъявить `doc:` нельзя ни в типах, ни в рантайме, поэтому две реализации
одного операции описывают его одинаково. Состав полей и правила проверки —
[schemas.md §2.2](./schemas.md).

### 1.3. Три вида

| Вид | Семантика | Владельцев |
|---|---|---|
| `request` | запрос и ответ `Ok` или `Fail` | ровно один |
| `command` | без ответа; обрабатывает один получатель (queue-group) | ровно один |
| `event` | факт; получает каждый подписчик | 0..N подписчиков |

Различие между `command` и `event` нужно горизонтальному масштабированию:
реплики владельца команды образуют одну группу и делят нагрузку, а событие
получает каждый подписчик. Для общения между фичами по умолчанию подходит
`event`: `request` заставляет вызывающего ждать соседа, `event` — нет.

### 1.4. Долговечность

Поле `durable: true` допустимо у `command` и `event`; у `request`
`makeRequest` / `makeCommand` / `makeEvent` отвергает его в момент объявления. Признак объявляется в
операции, потому что его должны знать обе стороны: издатель ждёт
подтверждения записи, подписчик читает долговечно, а живут они в разных
процессах. Других мест объявления нет — ни в `implement`, ни в конфигурации
транспорта. Как обслужить признак, решает транспорт (§3); названия
брокерских механизмов (JetStream) в операции, биндинге и конверте не
появляются.

### 1.5. Пакеты

`makeRequest` / `makeCommand` / `makeEvent`, `defineFail`, `Ok`/`Fail`, перечень статусов, формы io и
bind-карта живут в `@nestling/operations`. У пакета нет runtime-зависимостей
(транзитивно — только типы Standard Schema), поэтому операцию можно
импортировать во фронтенд и в скрипты. Этот инвариант проверяет тест,
который обходит граф импортов собранного пакета. Примитив токена инжекции
пакет получает из subpath `@nestling/container/tokens` — листовых модулей
без runtime-импортов; благодаря этому `.caller` и `.emitter` — настоящие члены
семейств токенов.

Рантайм (вызыватели, шина, биндинг) живёт в `@nestling/ports`. Он
реэкспортирует типы вызывателей (`Port`, `Emitter`, `PortMeta`), но не
`makeRequest` / `makeCommand` / `makeEvent`: объявление операции импортируется только из
`@nestling/operations`.

### 1.6. Версия

Версия входит в имя: `user.create.v2`. Отдельного поля версии нет.
`makeRequest` / `makeCommand` / `makeEvent` суффикс `.vN` не требует и не разбирает; операция без
суффикса допустим.

### 1.7. Схемный дифф

Сравнение схем со снапшотом опубликованных операций показывает
несовместимые изменения, но не блокирует ни сборку, ни CI. Устройство:

- `describeContract(operation, { converters? })` возвращает
  `ContractDescriptor` — JSON-значение: имя, вид, дерево форм io, коды и
  статусы отказов. Листовые схемы переводит вендорский конвертер
  ([schemas.md](./schemas.md) §2); без конвертера лист помечается
  непрозрачным. «Схемы нет» и «схема есть, но не сконвертирована» — разные
  состояния.
- `.check()` кладёт дескрипторы опубликованных операций в поле
  `operations` отчёта. Источник — discovery (декларации с bus-биндингом), а
  не приватный реестр `makeRequest` / `makeCommand` / `makeEvent`. `snapshotOperations(reports)` сводит
  матрицу `select`-топологий ([testing.md](./testing.md)) в
  `OperationSnapshot` объединением: операция, отсутствующая в одной
  топологии из трёх, — невыбранная фича, а не удалённая операция.
  Сериализация детерминирована: один и тот же граф даёт побайтово один и
  тот же файл.
- `diffOperations(baseline, current)` даёт каждому расхождению ровно один
  вердикт: `breaking`, `additive` или `unknown`. Направление определяет
  слот. `input` приходит в реализацию, поэтому сужение принимаемого —
  `breaking`; `output` уходит из неё, поэтому ослабление гарантии —
  `breaking`. Правило одно для всех трёх видов. Всё, что правила не
  покрывают (незнакомые ключевые слова JSON Schema, смена вендора,
  непрозрачный лист), получает `unknown`, а не «совместимо».
- Отчёт — значение; `formatCompatibility` печатает его для человека.
  Операция с вердиктом `breaking` получает подсказку нового имени: для
  `billing.charge` это `billing.charge.v2`. Подсказка — единственное место,
  где суффикс `.vN` распознаётся; переименования не происходит.
- `diffOperations` не участвует в сборке, не вызывается из `run()` и
  `check()` и не бросает по результату сравнения; флага «падать на
  breaking» нет. Исключение одно: нечитаемый baseline (чужая
  `snapshotVersion`) — ошибка автора проверки, и она бросается.

## 2. Порты

### 2.1. Реализация

`implement(Contract, { deps?, pipeline?, handle, subscriber?, detached? })`
([endpoints.md](./endpoints.md)) создаёт декларацию endpoint'а поверх того
же примитива ядра, что `httpEndpoint` и `cliEndpoint`. Реализация кладётся
в `endpoints:` модуля и получает всё, что есть у любого endpoint'а:
discovery, `dispatch`, пайплайн, проверку отказов на выходе, `policies` и
`detached`, отчёт `check()` и вызов по значению в тестах. `input`, `output`
и `errors` берутся из операции; их переобъявление в реализации — ошибка
компиляции.

Операция с секцией `http:` реализуется формой с операцией
`httpEndpoint({ operation, deps?, pipeline?, handle, detached? })`. Поля
`method`, `path`, `bind`, `rawBody`, `sse`, `input`, `output` и `errors` в
этой форме объявлены как `never`: адрес и схемы берутся из операции,
bind-карта — тем же значением, без повторного вычисления. Операция без
`http:` эта форма отвергает при создании декларации; текст ошибки
предлагает объявить секцию или реализовать операцию на интеркоме через
`implement`.

### 2.2. Адреса реализаций

Паттерн endpoint'а в процессе и subject на шине различаются. Паттерн —
`<name>` у `request`/`command` и `<name>@<subscriber>` у `event`; subject
всегда `<name>`. Поле `subscriber:` обязательно для `event` (подписчиков
0..N) и запрещено для `request`/`command` (владелец ровно один). Имя
подписчика автор задаёт явно: с брокером оно становится именем queue-group
и durable-подписки.

### 2.3. Вызов

Потребитель инжектит `Operation.caller` или `Contract.emitter`:

```typescript
deps: [ChargeCard.caller],
handle: (billing) => async (input, meta) => {
  const charge = await billing.call({ orderId: input.id, amount: input.total }, meta);
  if (charge.isFail) return charge;          // отказ — данные, не исключение
  /* ... */
}
```

Порт связывается с local-клиентом (реализация в этом же процессе) или
remote-клиентом (через шину) в composition root; на запросе вызывается уже
выбранная константа. Входов у биндинга три: топология (какие фичи выбраны в
этот процесс), природа шины (доставляет ли она за пределы процесса) и
политика диспатча (§3). Вызыватель — член семейства токенов, поэтому узел
графа появляется только у операций, которые кто-то инжектит.

Природа шины влияет на биндинг так. При remote-шине `request`/`command` без
реализации в этом процессе биндится remote, и сборка не падает. Проверки
состава кластера нет: недоступный владелец в рантайме — обычный отказ
доставки. `event` при remote-шине всегда уходит через шину: множество
подписчиков открыто, и часть их живёт в других процессах. Подписчик в том же
процессе получает ровно одну копию — через собственную подписку у брокера.

Тип вызова одинаков в одном процессе и при split-развёртывании: всегда
async, всегда `Ok | Fail`. Remote-отказ восстанавливается в настоящий
`Fail` по `code` ([errors.md](./errors.md)). Множество ответов закрыто:
объявленные отказы плюс коды ядра (`UNKNOWN`, `VALIDATION_FAILED`) — так
же, как у endpoint'а.

`emit` возвращает `Promise<void>` по факту доставки, а не обработки. Отказ
подписчика попадает в диагностический хук, а не вызывающему.

Вызыватели получают исполнитель на фазе WIRE, где создаётся `dispatch`. Там
же шина подписывается на subject'ы своих маршрутов, поэтому `@OnStart` уже
может вызывать порт. Вызов раньше WIRE завершается ошибкой, а не ожиданием.

### 2.4. Правила

Порт никогда не транзакционен, даже в одном процессе: вызов выполняется в
собственном request-scope, и асинхронный контекст вызывающего внутрь не
попадает. Локальный порт может вернуть `Fail`. Вход валидируется на обоих
путях. Согласованность между фичами обеспечивают события плюс outbox или
saga ([deferred](../decisions/deferred.md)), а не общая транзакция.

### 2.5. Ошибки сборки

Сборка падает, если: у `request`/`command` нет реализации в процессе и нет
remote-биндинга; у операции два владельца; у события два подписчика с
одним именем; в операции порта объявлена форма `stream` или `events`.
Событие без подписчиков допустимо.

## 3. Шина и политика диспатча

Ядро зависит только от интерфейса `IMessageBus` с операциями `request`,
`publish` и `subscribe` — минимальным набором, который есть у любого
брокера. Реализации: `InProcessBus` без зависимостей и
`@nestling/transport.nats` (queue-group для реплик, JetStream для
`durable`). Специфика NATS в контрактный API не попадает.

`InProcessBus` — одно значение с двумя интерфейсами: `IMessageBus`
(исходящая сторона) и `ITransport` (входящая, `serve(dispatch, signal)`).
Broadcast построен на `Topic` ([streaming.md](./streaming.md)), поэтому
публикация не ждёт медленного подписчика. Формы io — только `value`. В корне
in-process шина не упоминается: её регистрирует kernel-модуль портов, и она
начинает принимать вызовы, только когда её требует хотя бы одна
обнаруженная реализация.

Корень может поставить шину сам: `nats()` — обычный провайдер транспорта под
тем же токеном. Когда он есть в `transports:`, kernel-модуль портов свою
реализацию не регистрирует, и оба токена (`MessageBus$` и токен транспорта
шины) дают один инстанс. Шина в приложении ровно одна; брокер не добавляется
к in-process шине, а заменяет её.

Шина объявляет значениями две способности: `remote` — доставляет ли она за
пределы процесса (вход биндинга, §2), и `durable` — умеет ли долговечную
доставку (§1). У `InProcessBus` обе ложны. Приложение с
`durable`-операциями на такой шине стартует, но при запуске печатает строку
с перечнем операций, которые обслуживаются без долговечности, — так же,
как список `detached`-endpoint'ов.

Политика диспатча выбирается на сборке:

- `local-first` — реализация из этого же процесса вызывается напрямую,
  остальные через шину;
- `always-remote` — каждый вызов идёт как сообщение. На in-process шине это
  означает асинхронный барьер, структурную копию payload и ответа и
  валидацию ответа по `output`-схеме; на брокере — отправку по сети.

Политика — поле `dispatch` kernel-секции конфига `nestlingPorts`
(`NESTLING_PORTS_DISPATCH`, по умолчанию `local-first`). Она читается
обычным механизмом конфигурации; поля `dispatch:` в `assemble` нет. Смена
политики — смена конфига; код вызова не меняется.

## 4. Профиль вызова

Вызов в одном процессе и вызов через сеть различаются эксплуатационным
профилем: бюджетом времени, идемпотентностью, передачей контекста. Профиль
встроен в API операции.

### 4.1. Бюджет времени

`meta.deadline` рядом с `meta.signal` — абсолютный момент типа `Date`; для
удобства есть `deadlineIn(ms)`. Число не принимается: `500` одинаково
читается и как epoch, и как «через 500 мс». Модель — как в gRPC: внутри
процесса передаётся момент, по сети — относительный timeout (рассинхрон
часов не влияет), на приёме он снова становится моментом по часам
получателя. Бюджета по умолчанию нет: вызов без `deadline` не ограничен по
времени.

Точек контроля три: проверка до вызова (`dispatch` и шина не тронуты),
проверка до обработки на приёме и отмена во время обработки. Сигнал
обработчика — композиция бюджета и `meta.signal`, поэтому реализация видит
исчерпание через свой `ctx.signal`. Отказ — `DeadlineExceeded`. Отмена
вызывающим по-прежнему даёт `UnknownError`; два случая различаются по тому,
чей таймер сработал, а не по `signal.reason`. Код `DEADLINE_EXCEEDED` —
встроенный, как `UNKNOWN`: в `errors:` он не объявляется, но входит в
закрытое множество ответов любого порта.

### 4.2. Идемпотентность

`idempotencyKey` в `meta` есть только у `command`-операций: тип `meta`
выбирается по виду операции (`MetaOf<C>`), и обращение к полю у `request`
или `event` — ошибка компиляции. `emit` команды всегда отправляется с
ключом: либо переданным вызывающим, либо сгенерированным вызывателем. Ключ
стабилен относительно повторных доставок одного `emit`; два разных `emit`
получают разные ключи. Ключ передаётся конвертом шины (в NATS —
заголовком). Дедупликацию делает satellite-пакет на стороне обработчика;
ядро гарантирует только доставку ключа хендлеру и юнитам.

### 4.3. Два канала доставки профиля

Первый канал, безусловный, — `ctx.raw.attributes` (рядом с `subject`).
Второй — переменные асинхронного контекста `Deadline` и `IdempotencyKey` со
штатными писателями `withDeadline()` и `withIdempotencyKey()`. Переменные
экспортируются значениями, поэтому наличие профиля проверяется на сборке:
`everyEndpoint(…).hasVar(IdempotencyKey)`. Вложенный вызов бюджет не
наследует — так же, как не наследует `meta.signal`; обработчик, отдающий
остаток дальше, передаёт его явно.

### 4.4. Передача контекста

Переменная, объявленная с `{ propagate: true }`, передаётся через границу
порта конвертом шины (в NATS — одним заголовком `Nl-Ctx`). Значения
собирает вызыватель из ячейки текущего запроса. «Весь контекст» не
передаётся никогда: `propagate` — именованное исключение из правила
«контекст вызывающего внутрь реализации не попадает». На приёме значения
кладутся в `ctx.raw.attributes`, а в асинхронный контекст их включает
штатный писатель `Var.propagated()` — тот же двухканальный приём, что у
профиля. Поведение одинаково для обоих путей биндинга. Подробности —
[container.md](./container.md), «Асинхронный контекст».

## 5. Внешний клиент: `makeClient`

Потребитель вне процесса Nestling — фронтенд, сервис на другом стеке,
скрипт — не имеет доступа к DI. Клиент для него строится из операции:

```typescript
import { CreateUser, GetUser } from '@acme/billing-contracts'; // пакет без runtime-зависимостей
import { makeClient } from '@nestling/client';

const api = makeClient(
  { createUser: CreateUser, getUser: GetUser },  // методы именует потребитель
  { baseUrl, fetch?, headers? },                 // общие заголовки: auth, tracing
);

const result = await api.createUser({ ... });
// Promise<Ok<Output> | Fail<EmailTaken | UnknownError>>
```

- Тип вызова тот же, что у порта: `Ok | Fail`, закрытое множество
  `E ∪ UnknownError`.
- Запрос собирается по bind-карте операции (path, query, body). Ответ
  валидируется по `output`-схеме через `~standard.validate`; валидатор
  приносит потребитель.
- Отказы восстанавливаются по `code` из `errors:`; незнакомый код
  становится `UnknownError`.
- Заголовки, общие для всех вызовов (auth, tracing), задаются при создании
  клиента. Имена методов задаёт потребитель через record; имя операции
  (`'users.create'`) в структуру объекта не разбирается.
- Валидация ответа включена по умолчанию. Отключается явно:
  `makeClient(record, { validateOutput: false })`.
- Сериализация query закрыта: `undefined` и `null` не пишутся, скаляр —
  `String(value)`, массив скаляров — повторяющиеся вхождения ключа, всё
  остальное — `TypeError` в момент вызова с именем поля. Обратная сторона:
  схема query-поля обязана принимать строку (`z.stringbool()`,
  `z.coerce.*`), потому что query несёт строки.
- `meta` клиента — `{ signal?, deadline? }`. `deadline` (абсолютный момент,
  как у портов) проверяется до отправки: истёкший бюджет даёт
  `DeadlineExceeded` без запроса в сеть. `idempotencyKey` у клиента нет:
  согласованного HTTP-слота для него не существует.
- На транспортных и контрактных сбоях `request` клиент не бросает
  исключений, а возвращает `Fail`. Исключения — только при неверном
  использовании.
- `makeClient` отвергает в момент создания, называя ключ метода в record:
  операцию без `http:`, вид `event`, потоковую или `multipart`-форму io,
  не-JSON тело, неабсолютный `baseUrl`.
- `makeClient` живёт в `@nestling/client`: построен на `fetch`, без
  Node-специфики; граница пакета проверяется тем же обходом графа
  импортов.
- Для потребителей не на TypeScript остаётся путь через OpenAPI
  ([transports.md](./transports.md) / запись «Standard Schema…OpenAPI»).
