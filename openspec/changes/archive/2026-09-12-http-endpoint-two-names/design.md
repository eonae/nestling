## Context

`httpEndpoint` несёт четыре перегрузки: две формы хендлера у анонимной
формы и те же две у формы с операцией. TypeScript печатает подробности
каждой перегрузки, пока их не больше трёх, и **только последнюю**, когда
их больше. Последняя перегрузка — анонимная форма с класс-хендлером.
Её тип-параметры для формы с операцией бессмысленны: `PF` равно `never`,
`I` неизвестен. Отсюда обе жалобы пункта B1
([d/14](../../../docs/history/discussions/14-first-external-run.md)):
ошибка не называет отказ и садится на строку, которую чинить не нужно.

### Замер «до»

Фикстура на реальных типах (`type-tests` транспорта, tsc 5.7.3):
операция с `errors: [EmailTaken]`, пайплайн объявляет `EmailTaken`
(то есть верен), класс-хендлер возвращает `CardDeclined`.

```
_b1-repro.ts(25,3): error TS2769: No overload matches this call.   ← operation:
  The last overload gave the following error.
    Type 'PipelineBuilder<…, Fail<"conflict:email_taken">>' is not assignable
      to type 'Pipeline<EmptyInput, AnyInput, never, never>'.
      …
            Type 'Fail<"conflict:email_taken", undefined>' is not assignable to type 'never'.
              …
                        Type 'unknown' is not assignable to type '{ email: string; }'.

_b1-repro.ts(26,3): error TS2769: No overload matches this call.   ← pipeline:
  (тот же текст, тринадцать строк)
```

Две диагностики по тринадцать строк. Ни одной на строке `handler:`. Код
`payment_required:card_declined` в тексте не назван ни разу.

### Замер «после разведения имён»

Прототип: те же две перегрузки формы с операцией, вынесенные под
отдельное имя с операцией первым аргументом. Та же фикстура:

```
_b1-split.ts(24,3): error TS2769: No overload matches this call.   ← handler:
  Overload 1 of 2, …
    Type 'typeof CreateUserHandler' is not assignable to type 'HandlerFn<…>'.
  Overload 2 of 2, …
    …
                      Type '"payment_required:card_declined"' is not assignable to type '"internal_error"'.
```

Одна диагностика, на строке `handler:`, и последняя строка называет код.
Печатаются **обе** перегрузки, потому что их стало две.

Это же объясняет, почему разведение чинит и анонимную форму. Сегодня её
диагностика — тоже «последняя перегрузка», и снапшот
`function-undeclared-fail` фиксирует бесполезный текст: «функция не
подходит под `new (...args: any[])`». После разведения у `httpEndpoint`
останутся две перегрузки, и первой напечатается та, что про функцию.

## Goals / Non-Goals

**Goals:**

- Ошибка незаявленного отказа садится на строку `handler:` и называет код.
- Ложная диагностика на строке `pipeline:` исчезает.
- Поля, принадлежащие операции, нельзя передать в реализацию — потому что
  их нет в словаре, а не потому что они запрещены типом `never`.
- Тексты диагностик закреплены снапшотами до того, как их процитирует
  справочник скилла.

**Non-Goals:**

- Статические конструкторы по HTTP-методу (`httpEndpoint.get`) — change 71.
- Брендирование диагностик `bind`, `output` и стартового контекста.
- Изменение модели декларации, правил размещения полей и границы отказов
  в рантайме.

## Decisions

### D1. Имя формы с операцией — `httpEndpoint.implement(Operation, { … })`

Статический метод на конструкторе, а не отдельная функция верхнего
уровня. Операция идёт первым аргументом — как у `implement(Operation,
{ … })` в `@nestlingjs/app`.

Почему статик, а не `httpImplement`. Имена транспорта — существительные,
называющие значение: `httpEndpoint`, `httpServer`, `http()`. `httpImplement`
— глагол, и в этом ряду читается как действие в рантайме. Статик решает и
вопрос будущего: если change 71 добавит `httpEndpoint.get`, `httpEndpoint`
станет пространством имён с `.get`, `.post`, …, `.implement`, и форма
останется связной. Если 71 не состоится, остаётся вызываемая функция со
статиком — тоже связно. Отдельная функция `httpImplement` во втором мире
осталась бы сиротой.

Отвергнутые варианты:

- **`serve({ operation, … })`** — имя занято методом транспорта
  `serve(dispatch, signal)`.
- **`httpEndpoint.of(Operation, …)`** — `of` обещает сокращённую запись
  того же значения. Это другая декларация: у неё другой владелец адреса и
  схем.
- **Оставить одно имя, поменяв порядок перегрузок** — отвергнуто записью
  [ideas.md [2026-09-04]](../../../docs/decisions/ideas.md) «Отказы слоя»:
  форма с функцией обязана стоять раньше класс-формы, иначе параметр
  хендлера теряет контекстный тип.

### D2. Словарь реализации теряет поля операции, а не запрещает их

`HttpOperationDictionary` переименовывается в `HttpImplementDictionary` и
теряет ключ `operation` вместе с девятью полями `never` (`method`, `path`,
`bind`, `rawBody`, `sse`, `input`, `output`, `errors`, `doc`): лишний ключ в
объектном литерале TypeScript отвергает и без них.

Рантайм-проверки остаются все три, потому что каждая ловит то, чего типы
у JS-потребителя не видят: `assertOperation` (первый аргумент создан
`makeRequest`), `assertOperationOwned` (поле операции переобъявлено
реализацией) и ошибка «у операции нет секции `http:`». Удаление
`assertOperationOwned` вместе с полями `never` поменяло бы ошибку на
молчаливое игнорирование поля.

Тексты ошибок получают новый префикс: `httpEndpoint.implement(CreateUser,
{ … })` вместо `httpEndpoint({ operation: CreateUser, … })`.

### D3. Незаявленный отказ называется литералом, а не именованным типом

Брендированный тип печатается **инлайновым литералом**, как диагностики
пайплайна (`ValidateStart`, `ValidateOperationFails`), а не именованным
алиасом, как `DependencyLengthError` в контейнере. Замер обеих печатей на
одной фикстуре:

```
# именованный алиас
Type 'typeof CreateUserHandler' is not assignable to type
  'typeof CreateUserHandler & UndeclaredFailError<"payment_required:card_declined", "conflict:email_taken">'.

# инлайновый литерал
Type 'typeof CreateUserHandler' is not assignable to type
  'typeof CreateUserHandler & { __error: "Handler returns a failure that is not
   declared in 'errors:'"; returned: "payment_required:card_declined";
   declared: "conflict:email_taken"; }'.
```

Алиас печатает имя, литерал — предложение. Читатель ошибки чинит её без
справочника; справочник остаётся для случаев, где текст короче причины.
Состав полей — как у остальных диагностик слотов: `__error` называет
правило, `returned` и `declared` дают данные, `hint` называет починку.

### D4. Позиция брендирования у форм хендлера разная

У класс-хендлера бренд стоит **в слоте**: `handler: H & ValidateFails<H, E>`,
приём `ValidConstructorLength` из контейнера. У хендлера-функции бренд
стоит **в возвращаемом типе**: `(payload, meta) => R & ValidateFails<R, E>`.

Причина — фиксация тип-параметра. Слот `handler: F & ValidateFails<F, E>`
с `F extends HandlerFn<…>` не работает: `F` нужен, чтобы контекстно
типизировать стрелку, поэтому TypeScript фиксирует его на **ограничении**,
и валидатор всегда видит `AnyFail`. Замер на мини-модели: ошибка
появляется на каждом хендлере, включая правильный, и в поле `returned`
стоит `string`. Параметр `R` в возвращаемой позиции этой проблемой не
страдает: `payload` и `meta` типизируются конкретными типами из операции,
а `R` выводится из тела.

Ошибка при этом всё равно садится на строку `handler:`: не подходит
функция целиком, а не только её результат. Замер:

```
_b1-brand-fn.ts(11,3): error TS2769: No overload matches this call.   ← handler:
  Overload 1 of 2, …
      Type 'Promise<Fail<"payment_required:card_declined"> | Ok<…>>' is not
        assignable to type 'Promise<…> & { __error: …; returned:
        "payment_required:card_declined"; declared: "conflict:email_taken"; }'.
```

### D5. Проверку множества отказов держит бренд, а не ограничение

Чтобы бренд вообще увидел отказ, ограничение обязано его пропустить:
`R extends OutputSync<InferOutput<O>, AnyFail> | Output<…, AnyFail>`, то
есть «любой отказ». Проверку значения `Ok` ограничение держит по-прежнему,
а множество отказов проверяет только бренд.

Цена: если бренд не сработает, незаявленный отказ скомпилируется. Граница
пайплайна в рантайме такой отказ всё равно заменит на `internal_error`
(capability `endpoint-error-contract`), то есть это потеря ранней ошибки,
а не дыра в гарантии. Случай закрепляется фикстурой: хендлер, объявленный
переменной типа `HandlerFn`, где вывод `R` невозможен.

### D6. Отсечка от протечки текста в чужую диагностику

`ValidateFails` возвращает `unknown`, если коды возвращённых отказов —
`FailCode`, то есть весь возможный набор. Это признак того, что `R`
откатился на ограничение и брендировать нечего.

Без отсечки текст бренда попадал в ошибку про **неверное значение**:
замер показал `& UndeclaredFailError<FailCode, "conflict:email_taken">` в
диагностике, где отказов не было вовсе. Это ровно тот дефект, который
change 67 чинил у `RoleShapeError` (пункт B2 прогона), и лечится он так
же — условием, которое срабатывает только на конкретном случае.

Первая версия отсечки сравнивала с `string` и не сработала: откат даёт
`FailCode` — шаблонный литерал, а не `string`. Проверено замером: после
правки бренд из диагностики про значение исчез.

### D7. Отказы ядра вычитаются из множества

`UndeclaredFails` вычитает из возвращённых отказов и объявленные, и
`FailOf<KernelFail>`: граница пропускает отказы ядра у любой декларации,
и правило типов повторяет правило границы. Замер: хендлер, возвращающий
`InternalError()` без объявления, компилируется.

### D8. Бренд применяется ко всем четырём конструкторам

Тип живёт в `@nestlingjs/operations` рядом с `ValidateOperationFails` и
используется в слотах `handler` у `httpEndpoint`,
`httpEndpoint.implement`, `implement` и `cliEndpoint`. Оставить его только
в HTTP значило бы, что диагностика зависит от транспорта: следующий
внешний прогон нашёл бы это первым же хендлером на шине.

## Risks / Trade-offs

- **Рост бюджета типов.** Условный тип в слоте `handler` считается на
  каждую декларацию. → Бенч-граф `@nestlingjs/app/type-tests/bench`
  прогоняется до и после; строка с замером добавляется в `BUDGET.md`.
  Пороги двигать не планируется: запас к `instantiationsDelta` сейчас ×2.3.
- **Брендирование функции зависит от порядка вывода в TypeScript.**
  Мажорное обновление компилятора может его изменить. → Снапшоты
  `endpoint-type-diagnostics` ловят это дифом, а не жалобой пользователя;
  фикстура «правильный хендлер компилируется» ловит обратный случай —
  ложную ошибку на верном коде.
- **Миграция 39 мест в четырёх пакетах и двух примерах.** → Правка
  механическая: `httpEndpoint({ operation: Op, …rest })` →
  `httpEndpoint.implement(Op, { …rest })`. Компилятор ловит пропущенное
  место: ключа `operation` в словаре больше нет.
- **Справочник диагностик цитирует тексты, которые меняются.** →
  `references/diagnostics.md` пишется последней задачей, после того как
  снапшоты сняты, и цитирует их, а не память.
- **Две позиции брендирования — две формы одного правила.** Читателю кода
  это надо объяснить. → JSDoc у `ValidateFails` называет причину
  (фиксация тип-параметра) и ссылается на фикстуру, которая её
  закрепляет.

## Migration Plan

1. Конструктор и тип — `@nestlingjs/transport.http`, `@nestlingjs/operations`.
2. Фикстуры и снапшоты `type-tests`: обе формы обоих конструкторов,
   правильный хендлер, отказ ядра, случай без вывода `R`.
3. Тесты пакетов: `operation-endpoint.spec.ts`, `handler-form.type-test.ts`,
   интеграционные спеки транспорта, `document.spec.ts` OpenAPI.
4. Примеры и сниппеты скилла.
5. Документация: главы гайда, `design/`, глоссарий, README пакетов.
6. `references/diagnostics.md` — последним.

Отката не предусмотрено: в проде фреймворка нет, обратной совместимости
не существует. Внешние пользователи получают ломающее изменение одним
релизом вместе с change 71, если тот успеет в то же окно.
