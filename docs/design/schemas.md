## 1. Ядро принимает Standard Schema

На всех схемных границах ядро принимает **`StandardSchemaV1`**
(standardschema.dev) — общий интерфейс zod / valibot / arktype /
Effect Schema / TypeBox: одно проперти `~standard` с
`validate(value) → {value} | {issues}` и фантомными типами для инференса.

- Валидация — через `~standard.validate`; вывод типов — `InferOutput`.
- **Валидатор приносит пользователь** — zod, `zod/mini`, valibot, arktype —
  на его вкус и бюджет бандла; зависимостью ядра валидатор не является.
  В примерах документации — zod как один из вариантов.
- **Единая точка валидации** — `validateSync(schema, value, message)`:
  через неё проходят и `parsePayload`/`parseMetadata`, и pipeline-юнит
  `validate()`, и поэлементная валидация элементов потока, и fallback-ветки
  транспортов. Прямых `schema.parse(...)` и дак-тайпов вида
  `{ parse(data): T }` в ядре нет — форма отказа одна на всех путях.
- `SchemaValidationError` несёт стандартизованные `issues`
  (`{message, path?}[]`) — формат отказа валидации гарантирован спекой,
  а не вендором; вендорские типы ошибок в публичный API не текут.
  Путь нормализуется при конструировании ошибки: сегмент-объект `{key}`
  разворачивается в `key`, символ приводится к строке, числовой индекс
  остаётся числом — `issues` уезжают в тело ответа, форма провода
  JSON-сериализуема и от вендора не зависит.
- `validate`, вернувший Promise (async refinements), в синхронном
  пайплайне — ошибка, не тихая деградация.
- **Внешний клиент валидирует ответ той же схемой.** `makeClient` проверяет
  тело успешного ответа по форме `output` контракта через
  `~standard.validate` — по умолчанию, с явным opt-out
  `validateOutput: false`: обещание клиента это типизированный результат, и
  отдать невалидированный JSON под типом `Output` значит соврать в типе.
  Синхронность обязательна и здесь. Отличается **исход**: на клиенте отказ
  валидации не бросается, а становится `UnknownError` с issue'ами в
  `cause` — клиент не бросает на контрактных сбоях
  ([contracts.md](./contracts.md)). Валидатор по-прежнему приносит
  потребитель: `@nestling/contracts` знает о схеме только её `~standard`.
- **Ошибка конфигурации ≠ ошибка входа.** Async-схема
  (`AsyncSchemaNotSupportedError`) и объект, не реализующий спеку
  (`NotAStandardSchemaError`, типичная причина — валидатор старее
  zod 3.24 / valibot 1.0), — отдельные классы, намеренно **не** наследники
  `SchemaValidationError`: их бросает не пользователь запроса, а автор
  приложения, и транспорт отдаёт на них 500, а не 400.

Критичное свойство спеки: она покрывает **только валидацию + инференс,
интроспекции нет** — схема в рантайме непрозрачна. Поэтому всё, что требует
знания структуры, устроено явно, без заглядывания в вендорские схемы:
размещение поля объявляется пометкой рядом со схемой, а не внутри неё
(`bind: { expand: query() }`, [endpoints.md](./endpoints.md)), секция
конфига — рекорд полей
([config.md](./config.md)), генерация JSON Schema — через вендор-конвертеры
(ниже).

Непрозрачность — свойство **рантайма**: на уровне типов ключи известны
(`InferInput<I>`). Этой асимметрией пользуются там, где можно: ключи
`bind` типизированы полями схемы, поэтому опечатка ловится компилятором,
хотя рантайм тех же ключей не знает. Проверки, которым нужен перечень
ключей в рантайме, не заводятся вовсе — они были бы конвенцией, а не
гарантией.

## 2. Вендор-конвертеры — нейтральный контракт схемного слоя

Валидация и всё, что требует знания структуры схемы, разведены: рантайм
ядра знает только `~standard.validate`; JSON Schema нужна тем, кто
описывает схему наружу.

Конвертер — публичный контракт **схемного слоя**
`SchemaDocConverter { vendor; toJsonSchema(schema, options?) }` с
диспетчеризацией по `~standard.vendor`. Он нейтрален к потребителю: ядро по
вендору не ветвится и вендорские схемы не интроспектирует, а список
конвертеров — данные вызывающего (глобального реестра нет; два конвертера с
одним `vendor` в списке — ошибка в точке передачи).

`options` несёт одну подсказку — `io: 'input' | 'output'`. Схема с
преобразованием описывает **две** формы: то, что приходит по проводу, и то,
что получает хендлер; тело запроса обязано описываться первой, тело ответа —
второй. Подсказка необязательна с обеих сторон: конвертер вправе её
игнорировать, а потребитель, которому направление безразлично (снапшот
сравнивает форму с самой собой), — не передавать.

**Escape hatch — аннотация `jsonSchema(schema, json)`**, а не поле
декларации. Она возвращает значение, наследующее `~standard` исходной схемы:
валидирует ровно как исходная и годится в **любую** схемную позицию —
`input`, `output`, лист потоковой формы, `fields` формы `multipart`,
`details` определения отказа. Поле на декларации пришлось бы превращать в
путь внутрь дерева форм; аннотация попадает точно туда, где проблема.
Диспетчер читает её **раньше** конвертера, поэтому аннотированный лист
конвертируем независимо от списка. Тем же механизмом объявлены схемы самого
ядра (`details` kernel-отказов написаны руками, и вендора `nestling` ни один
конвертер не понимает). Мутации переданной схемы и глобального реестра
аннотаций не существует.

Потребителей два, и **строгость при отсутствии конвертера у них разная** —
поэтому диспетчер её не зашивает: он возвращает «конвертера нет»
отдельным исходом, а решение принимает потребитель.

| Потребитель | Нет конвертера для вендора |
|---|---|
| генерация документации (§2.1) | fail-fast на boot: недокументируемых ручек не бывает |
| снапшот контрактов ([contracts.md](./contracts.md) §1) | лист непрозрачен → вердикт `unknown` |

Общий для обоих: конвертер — единственное место, знающее устройство
конкретного валидатора, и он пишется в десять строк поверх штатного
конвертера валидатора (`z.toJSONSchema()` и аналоги).

### 2.1. OpenAPI — opt-in модуль

```typescript
openapi({ info: { title: 'My API', version: '1.0.0' },
          converters: [zodConverter()], pipeline: observability })
```

Поверхностей три, потому что документ нужен в двух режимах — отдаваться
ручкой и лежать файлом в артефактах сборки, — и общий у них только первый:

| Поверхность | Что делает |
|---|---|
| `buildOpenApiDocument(endpoints, options)` | чистая функция: вход — то же значение, что отдаёт дискавери; ни контейнера, ни транспортов |
| `openapi(options)` | параметризованный модуль: строит документ на фазе 1 ASSEMBLE и отдаёт ручкой (`GET /openapi.json`) |
| `OpenApiDocument$` | токен готового документа — ручка это способ его отдать, а не место, где он появляется |

- **`@nestling/openapi` не знает ни про один валидатор** — он принимает
  тот же `SchemaDocConverter`, что и снапшот контрактов, а не заводит
  свой тип. Это проверяется тестом границы импортов, а не обещанием.
- **Конвертеры — отдельные пакеты** (`@nestling/openapi.zod` peer-зависит
  от zod, и т. п.): пользователь ставит ровно то, чем пользуется; мажоры
  конвертера следуют за мажорами валидатора.
- **Boot-time-гарантия** отдельным кодом не пишется — она следствие жадного
  контейнера: фабрика документа зовётся на ASSEMBLE, и любая диагностика
  роняет сборку до `@OnInit` и до открытия сокета. Ленивого построения не
  существует: оно уничтожило бы эту гарантию. Проверка тотальна —
  нарушения всех ручек уезжают одним сообщением.
- **Модуль обычный.** Примитива «плагин» в ядре нет: `openapi(...)`
  возвращает то же, что любой параметризованный инфра-модуль. Опции `path`,
  `pipeline` и `detached` обязательны как возможность: корень вправе
  требовать политикой слой на каждой HTTP-ручке, а satellite-модуль про
  этот слой знать не может.
- **Состав приложения — значение.** Модуль читает `Discovery$`
  ([composition.md](./composition.md)): это единственный способ увидеть
  **выбранную** топологию, не дублируя `select` в корне.
- Источники сверх JSON Schema — из деклараций: слот `doc:` (§2.2);
  `errors:` → `responses` (`UnknownError` — default-ответ,
  [errors.md](./errors.md)); формы io → media types
  ([endpoints.md](./endpoints.md)); размещение полей — bind-карта
  (`parameter` vs `requestBody`); перевод статуса в код провода — та же
  таблица, что у транспорта.
- Генератор — первый потребитель, которому нужна **структура** схемы, и
  потому дом двух диагностик, отложенных до него: path-параметр, которому
  нет свойства в схеме, и `bind`-пометка на несуществующем поле.

**AsyncAPI** для `command`/`event` и потоковых форм — тем же механизмом и
тем же слотом `doc`, отдельным change'ем.

### 2.2. Слот `doc:` — то, чего в схемах нет

```typescript
interface DeclarationDoc {
  summary?: string;
  description?: string;
  tags?: readonly string[];
  deprecated?: boolean;
  status?: SuccessStatus;   // успешный ответ; дефолт OK, без output — NO_CONTENT
  hidden?: string;          // не документировать — только с причиной
}
```

Слот живёт на транспорт-нейтральном уровне (`EndpointOptions` ядра и
`ContractSpec`); ядро его **переносит и не интерпретирует**, как `binding`.
Формат-нейтральность обязательна: тот же слот читает будущая генерация
AsyncAPI, поэтому `operationId`/`externalDocs`/`servers` в нём нет.

- **`operationId` выводится**: имя контракта, если декларация служит
  контракту, иначе детерминированный слаг от метода и пути
  (`get_api_users_id`). Объявить его вручную нельзя — неизвестное поле
  секции отвергается в точке создания.
- **`tags` не выводятся из имени модуля**: это была бы конвенция,
  притворяющаяся гарантией.
- **`hidden: '<причина>'`, а не `hidden: true`** — прямая калька с
  `detached`: тотальный opt-out обязан быть читаем в diff'е. Скрытая ручка
  выпадает и из документа, и из проверки схем; список скрытого печатает
  модуль на старте, в документ он не попадает.
- **В контракт-форме `doc` принадлежит контракту** наравне с
  `input`/`output`/`errors`: документация операции — часть интерфейса, а не
  реализации, и две реализации одного контракта не могут описывать его
  по-разному.

Словарь проверяется в момент создания значения — не-строка, `tags` не
массивом строк, статус вне словаря успешных, `hidden: true` и неизвестное
поле валят объявление, а не сборку.
