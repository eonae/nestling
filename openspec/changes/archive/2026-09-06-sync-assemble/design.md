## Context

Жизненный цикл приложения описан в
[composition.md §1](../../../docs/design/composition.md): фаза 0 BOOTSTRAP
читает источники конфига в снимок, фаза 1 ASSEMBLE синхронна и без
ввода-вывода. Код фазы 0 не имеет.

Как устроено сейчас:

- `configKernel()` регистрирует читалку узлом графа с асинхронной фабрикой
  (`useFactory: async () => { … await reader.init() }`). Порядок
  инстанцирования гарантирует, что `init()` источников отработал раньше
  проекции любой секции. Фаза подменена топологией.
- `ContainerBuilder.build()` асинхронный: `await` стоит на фабрике
  `providers` модуля (`appendFactoryProviders`) и на каждом `useFactory`
  (`createInstance`). Тип `FactoryProviderDefinition.useFactory` при этом
  возвращает `T`, а не `Promise<T>`.
- `App.check()` поднимает источники, потому что проходит через тот же граф.
- `ConfigReader.read(key)` опрашивает источники на каждом чтении; снимка нет.

Ограничения. `ConfigSource.get(key)` синхронный по контракту: ввод-вывод
источник делает в `init()` и `close()`. Значит после фазы 0 чтение значений
уже не требует асинхронности — мешает только место, где `init()` вызывается.
Хуки `@OnInit`, `@OnStart` и `@OnDestroy` остаются асинхронными; синхронной
становится только сборка.

## Goals / Non-Goals

**Goals:**

- Фаза 0 существует в коде отдельным шагом с наблюдаемой границей.
- `build()` синхронный; фаза 1 не делает ввода-вывода.
- Асинхронная фабрика — ошибка сборки, а не работающий обход фазовой модели.
- `check()` умеет проверять состав без единого источника.
- Снимок значений доступен до регистрации провайдеров — предпосылка
  переключателей состава (change `switches`).

**Non-Goals:**

- Перенос создания экземпляров на INIT, `@Resource`, `acquire`/`release` —
  change `resources-and-roles`.
- Переключатели, `makeSwitch`, типизированный аргумент сборки — change
  `switches`.
- Новые источники (`file`, `vault`) и `env({ prefix })`.

## Decisions

### 1. Читалка создаётся вне контейнера и входит в граф значением

`AssembledApp` получает приватный шаг `#bootstrap()`: создаёт `ConfigReader`
по привязкам плана, вызывает `await reader.init()`, снимает снимок и
возвращает читалку. `configKernel(reader)` регистрирует её `valueProvider`'ом
под тем же приватным kernel-токеном; рецепты семейств `ConfigSection` и
`Config` не меняются.

Почему так: граница фазы становится видимой в коде — до `#assemble()`
ввод-вывод есть, после его нет. Альтернатива «оставить узел с асинхронной
фабрикой» сохраняет фазу выведенной из топологии, а вместе с ней и
асинхронный `build()`. Альтернатива «снимок вместо читалки» не подходит:
`reloadable` нужен объект, который наблюдает источники после сборки.

### 2. Снимок — карта значений внутри читалки, дозаполняемая по промаху

`init()` читает в снимок все ключи из реестра объявленных секций
(`declaredKeys()`). `read(key)` отдаёт значение из снимка. Ключ, которого в
реестре нет — член семейства `Config(key)` под unbound-глобом, — читается
через `get()` уже инициализированных источников и попадает в снимок.
`#refreshAll()` перечитывает ключи reloadable-секций в снимок перед
перепроекцией.

Почему так: состав членов семейства `Config(key)` известен только внутри
`build()`, то есть после фазы 0; заранее их ключи не перечислить. Чтение по
промаху ввода-вывода не делает — `get()` синхронный по контракту источника.
Альтернатива «источник перечисляет свои ключи» расширяет `ConfigSource`
методом ради одного сценария.

### 3. Повторы — на стороне источника

Ядро зовёт `init()` каждого источника один раз, по порядку привязок. Отказ
превращается в ошибку фазы 0, называющую источник и несущую исходную ошибку
в `cause`.

Почему так: сколько раз и с какой паузой повторять, знает источник — файл и
Vault отличаются и природой отказа, и ценой повтора. Ядру нечем отличить
временный отказ от постоянного. Альтернативы — повторы читалки по опции или
с умолчанием — кладут политику в ядро и добавляют неявные тайминги.
Формулировка composition.md «делается ограниченное число повторов»
переписывается: повторы объявляет источник.

### 4. `build()` синхронный, `Promise` из фабрики — ошибка сборки

`appendFactoryProviders()` и `instantiateAll()` теряют `await`; `build()`
возвращает `BuiltContainer`. `createInstance()` проверяет результат
`useFactory` на thenable и бросает ошибку с DI-токеном провайдера.
Возвращаемый тип хелпера `factoryProvider()` запрещает `Promise`
условным типом; тот же запрет получает фабрика `providers` модуля
(`ProvidersFactory`).

Типом одного запрета мало: `Module.providers` типизирован как
`ModuleProvider<unknown>[]`, и `Promise<T>` присваивается `unknown` — литерал
провайдера внутри модуля компилятор пропустит. Поэтому рантайм-проверка
обязательна, а тип закрывает путь через хелперы.

Текст ошибки называет провайдера и говорит, где место захвата внешнего мира:
до change `resources-and-roles` это хук `@OnInit`, после — `resourceProvider`.
Подсказку правит тот change, а не этот.

### 5. Фаза 1 синхронна целиком, включая проверки на графе

`#assemble()` перестаёт быть асинхронным. Единственная асинхронная проверка
на собранном графе — `assertFeatureBoundary`, и она такая только из-за
`container.traverse()`, чей колбэк может вернуть `Promise`. Контейнер
получает синхронный перебор узлов (`forEachNode`), `traverse` остаётся для
хуков жизненного цикла.

### 6. Читалка закрывается явно, а не хуком графа

`@OnDestroy` с `ConfigReader.close()` снимается. `AssembledApp.close()`
закрывает источники после `container.destroy()`, шов проверки — сразу после
формирования отчёта.

Почему так: узел графа `useValue` живёт временем контейнера, а `check()`
контейнер не разрушает — источники остались бы открытыми. Явное закрытие
делает время жизни читалки временем `run()`, как предписывает запись
ideas.md.

### 7. `check()` остаётся асинхронным и принимает конфиг

`CheckOptions` получает поле `config` в трёх формах: источник, одна привязка,
список привязок. Нормализация форм (`toBindings`) и тип `ConfigInput`
переезжают из `@nestling/testing` в `@nestling/app`, где живут привязки;
тестовый пакет их использует, `TestConfig` удаляется. `checkTopologies`
прокидывает опцию в каждую топологию.

Сигнатура остаётся `Promise<CheckReport>`: фаза 0 поднимает источники, а
значит асинхронна. С `config: vars({ … })` ввода-вывода нет, но форма вызова
одна — двух сигнатур на один метод не будет.

## Risks / Trade-offs

- **Провайдер с асинхронной фабрикой в чужом коде перестаёт собираться** →
  осознанно: фабрика, захватывающая соединение, и была дырой в фазовой
  модели. Ошибка называет провайдера и место захвата.
- **Снимок расходится с источником между фазой 0 и сборкой** → значения
  не-reloadable секций фиксируются на старте; это и есть заявленная
  семантика фазы 0. Reloadable-секции обновляются наблюдением, как раньше.
- **Read-through по промаху снимка оставляет чтение вне фазы 0** → чтение
  синхронно и без ввода-вывода по контракту `ConfigSource.get`; источник,
  нарушающий контракт, нарушал его и до change'а.
- **`forEachNode` — второй способ обхода графа рядом с `traverse`** →
  разница названа в JSDoc: `traverse` ждёт хуки, `forEachNode` не ждёт
  ничего. Синхронной проверке нечего ждать.

## Migration Plan

Пользователей нет, обратная совместимость не поддерживается. Внутри репозитория:

1. `@nestling/container` — синхронный `build()`, проверка на `Promise`,
   `forEachNode`.
2. `@nestling/app` — фаза 0 в `AssembledApp`, `configKernel(reader)`, снимок
   в `ConfigReader`, `CheckOptions.config`, синхронный `#assemble()`.
3. `@nestling/testing` — `toBindings` из `@nestling/app`, `checkTopologies`
   с конфигом.
4. `examples/container` — `builder.build()` без `await`.
5. Документация: `composition.md` (фаза 0, повторы источника), `config.md`,
   `container.md`, README трёх пакетов, главы гайда 06 и 07.
