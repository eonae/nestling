# Заметка о выпуске

Заметку читает тот, кто обновляет приложение с прошлой версии. Он держит
в руках работающий код и хочет знать три вещи: чем обновиться, что
сломается и что с этим делать. Всё остальное в заметке — следствия.

Правила ведения папки — раздел «releases/»
[`docs/README.md`](../../../docs/README.md), требования — спека
[`openspec/specs/release-notes/spec.md`](../../../openspec/specs/release-notes/spec.md).
Стиль текста общий для репозитория — скилл
[`docs-style`](../docs-style/SKILL.md); здесь записано только то, чем
заметка отличается от главы гайда.

## Порядок разделов

Один выпуск — один файл `docs/releases/vX.Y.Z.md` и его пара
`docs/en/releases/vX.Y.Z.md`. Разделы идут в этом порядке, раздел без
содержания опускается:

| Раздел | Что несёт |
| --- | --- |
| `# X.Y.Z` | номер версии, больше ничего |
| плашка | диапазон коммитов и даты |
| `## Обновление` | команда обновления и требования к окружению |
| `## Коротко` | список изменений выпуска, строка на изменение |
| `## <Предмет>: было и стало` | один-два файла, показывающие большую часть изменений разом |
| `## Ломается молча` | изменения, которых компилятор не покажет |
| разделы по подсистемам | изменение за изменением |
| `## Удалено` | имена и формы, которых больше нет |
| `## Тестирование` | что меняется в тестах приложения |
| `## Примеры и документация` | новые тексты, переехавшие главы, состав `examples/` |
| `## Что дальше` | чего в выпуске нет и где смотреть сроки |
| `## Для тех, кто собирает репозиторий` | изменения, видимые только в этом репозитории |
| `## Таблица переименований {#renames}` | строка на каждое переименование и на смену формы вызова |

Три раздела обязательны всегда: «Обновление», «Коротко» и таблица
переименований. «Ломается молча» обязателен, когда такое изменение в
выпуске есть.

## Плашка

Плашка идёт сразу за заголовком и называет диапазон одной формой:

```markdown
> Все пакеты `@nestlingjs/*` выходят одной версией. В выпуск вошли
> коммиты от тега `v0.3.0` до тега `v0.4.0`, 14 сентября 2026. Старое
> имя удалено вместе с появлением замены: алиасов и обёрток в пакетах
> нет.
```

Обе границы диапазона называются тегами. Заметка пишется до подъёма
версии, поэтому своего тега в момент письма ещё нет: пишется он всё
равно, а сверяется на шаге 2 [`RELEASING.md`](../../../RELEASING.md).
SHA в плашке не стоит — читатель заметки тегами пользуется, а SHA
сверяет автор.

## Обновление

Первое, что делает читатель, — ставит новую версию. Раздел даёт команду
и всё, что нужно знать до неё:

```markdown
## Обновление

```bash
yarn up '@nestlingjs/*'
```

Версия одна на все пакеты: пакет прошлой версии рядом с новым не
работает. Node — не ниже 24. Новый пакет ставится отдельно:
`yarn add @nestlingjs/config.vault`. Клиент брокера переехал в
peer-зависимости: `yarn add nats@^2.29.3`.
```

Раздел называет только то, что изменил выпуск: требование к Node — если
оно поднялось, peer-зависимости — если появились или сменили диапазон,
новые пакеты — списком. Полный справочник окружения лежит в
[`compatibility.md`](../../../docs/compatibility.md), и раздел ведёт
туда ссылкой, а не пересказом.

## Коротко

«Коротко» — список, а не абзац. Строка называет одно изменение и ведёт
в свой раздел заметки:

```markdown
## Коротко

- Источник конфигурации берёт свои координаты из другого источника:
  поле `needs` и `init(values)` — [раздел](#конфигурация).
- Отказ под маркером `argv()` уходит в `stderr` кодом выхода `1` —
  [раздел](#точка-входа).
```

Пять-семь строк. Список служит и оглавлением: у заметки на восемьсот
строк другого нет.

## Ломается молча

Переименование ловит компилятор, и читателю с ним просто: таблица
переименований в конце перечисляет их все. Дорого стоит другое —
изменение, которое компилируется и ведёт себя иначе. Такие изменения
собраны в один список сразу после «Коротко», строкой на изменение со
ссылкой на раздел:

```markdown
## Ломается молча

Эти изменения компилятор не покажет: код собирается и ведёт себя иначе.

- Список в `config` заменяет `defaultSources` целиком, и прежнее чтение
  `process.env` пропадает — [раздел](#привязки-конфигурации).
- `DB_POOL_MAX=` даёт умолчание, а не ноль — [раздел](#схемы).
```

Что сюда попадает: смена значения по умолчанию, смена формата на сети,
смена кода выхода, смена очерёдности, новый отказ там, где раньше был
запуск. Что не попадает: переименование, удаление имени и смена формы
вызова — их держит компилятор.

## Раздел об изменении

Раздел показывает код прошлой версии и код этой парой блоков, потом
ведёт в главу, где новое описано целиком. Подпись блока называет путь в
проекте читателя и версию:

````markdown
### Привязки конфигурации — опция `run()`

Поле `config:` у `makeApp` удалено. Привязки источников принимает метод,
который запускает приложение: `run({ config })`.

```typescript
// src/main.ts — 0.2.0
const app = makeApp({ features: [AppFeature], config: [[defaults, keys]] });
```

```typescript
// src/main.ts — 0.3.0
const app = makeApp({ features: [AppFeature] }).build();

await app.run({ config: [bind(defaults, { keys })] });
```

Подробнее — [глава 7](../guide/07-config.md).

> Обновление: механическое — привязки переезжают из `makeApp` в `run()`,
> кортеж заменяется вызовом `bind()`.
> Почему: [ideas.md, `[2026-09-13] Конфигурация: привязки на run()`](../decisions/ideas.md#2026-09-13-%D0%BA%D0%BE%D0%BD%D1%84%D0%B8%D0%B3%D1%83%D1%80%D0%B0%D1%86%D0%B8%D1%8F-...).
````

Ломающее изменение называется раньше добавления. Журнал решений заметка
не пересказывает: «почему» — одна строка со ссылкой.

### Пометка «Обновление»

Каждый раздел про ломающее изменение заканчивается строкой, по которой
читатель оценивает работу, не читая раздел целиком:

- `> Обновление: механическое — <что переставить>.` Правка по образцу,
  решения не требует.
- `> Обновление: требует решения — <что выбрать>.` Читатель выбирает
  форму, значение или место.

Раздел про добавление такой строки не несёт: добавление никого не
ломает.

### Пометка «Почему»

Форма одна на оба языка, различаются слово и глубина пути:

```markdown
> Почему: [ideas.md, `[2026-09-14] Метрика — декларация`](../decisions/ideas.md#2026-09-14-%D0%BC%D0%B5%D1%82%D1%80%D0%B8%D0%BA%D0%B0--...).
> Why: [ideas.md, `[2026-09-14] Метрика — декларация`](../../decisions/ideas.md#2026-09-14-%D0%BC%D0%B5%D1%82%D1%80%D0%B8%D0%BA%D0%B0--...).
```

Три правила держат эту форму:

- **Ссылка ведёт на запись, а не на файл.** `ideas.md` — десять тысяч
  строк; без якоря читатель ищет запись сам. Якорь строится по
  заголовку `## [дата] Заголовок`, как его строит GitHub: нижний
  регистр, знаки препинания удалены, пробелы заменены дефисами.
- **Заголовок записи стоит инлайн-кодом.** Журнал русский и переводу не
  подлежит, а кириллица в английском тексте вне кода — ERROR
  `lang-cyrillic`.
- **Якорь процентно закодирован на обоих языках.** Он лежит вне
  обратных кавычек, и там кириллицу ловят два инварианта: `lang-cyrillic`
  в английском файле и запрещённые слова `docs-style` в русском.

Якоря проставляет и сверяет скрипт скилла, руками они не пишутся:

```bash
node .claude/skills/release-notes/scripts/check.mjs --fix docs/releases/v0.4.0.md
```

## Заголовки

Заголовок раздела заметки называет изменение, а не предмет:
«`build` вместо `assemble`», «Метрика — декларация», «Сервер объявляется
`server()`». Это исключение из правила
[`docs-style`](../docs-style/SKILL.md) «заголовок называет предмет»:
читатель заметки просматривает оглавление в поисках того, что сломается
у него, и предмет («Сборка приложения») ему об этом не говорит.

Остальные правила стиля действуют без изменений: одна мысль на
предложение, глагол в каждом предложении, не больше одного жирного на
раздел, термины из глоссария.

## Таблица переименований

Таблица идёт последней и несёт строку на каждое переименованное имя.
Колонки: было, стало, пакет. Строки сгруппированы по пакету в том
порядке, в каком пакеты идут в таблице `docs/README.md`.

Колонка «было» показывает вызов, а не идентификатор, когда имя осталось
прежним, а форма сменилась: `makeApp({ config })` → `run({ config })`.
По одному идентификатору такое изменение в таблице не находится.

## Дописывание вышедшей заметки

Заметка описывает свой диапазон и после тега не переписывается. Разрешена
одна правка: строка в конце раздела о том, что с этим изменением стало
дальше.

```markdown
В 0.3.0 `spyMetrics()` удалён вместе с остальной подсистемой метрик:
[заметка 0.3.0](./v0.3.0.md).
```

Строка ставится в конце раздела, называет версию и ведёт в её заметку.
Текст самого раздела остаётся прежним: он верен для своей версии.

## Откуда берётся материал

Источников два, и они сходятся:

```bash
git log --oneline v0.3.0..HEAD
git diff --name-only v0.3.0..HEAD -- openspec/changes/archive/ | cut -d/ -f4 | sort -u
```

Первый даёт коммиты, второй — changes, заархивированные в диапазоне. У
каждого change'а раздел «What Changes» файла `proposal.md` называет, что
вошло, и помечает ломающее словом **BREAKING**. Раздел «Non-goals»
называет, чего в выпуске нет, — из него растёт «Что дальше».

Факты сверяются с кодом, а не с предложением: change мог уточниться при
реализации. Сигнатуры берутся из README пакета, поведение — из спек.

## Чек-лист перед завершением

1. `node .claude/skills/release-notes/scripts/check.mjs docs/releases/vX.Y.Z.md docs/en/releases/vX.Y.Z.md` — 0 ERROR.
2. `node .claude/skills/docs-style/scripts/lint.mjs <оба файла>` — 0 запрещённых слов.
3. Строка выпуска стоит в обоих оглавлениях — `docs/releases/README.md` и
   `docs/en/releases/README.md`, новая версия первой строкой.
4. Каждое имя из колонки «было» таблицы переименований встречается в
   тексте заметки: строка таблицы без раздела оставляет читателя без
   замены.
5. Каждый **BREAKING** из архивных `proposal.md` диапазона назван либо
   разделом, либо строкой «Ломается молча», либо строкой «Удалено».
6. `yarn docs:audit quick` — 0 ERROR.
