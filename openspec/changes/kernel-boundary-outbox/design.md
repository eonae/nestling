## Context

`@nestling/outbox` написан целиком поверх публичных примитивов: `git diff`
по kernel-пакетам за тот change пуст. Замер границы, ради которого пакет
писался, нашёл четыре места, где примитивов не хватило, и пакет обошёл
каждое своими силами. Обходы работают, но стоят приложению лишнего кода:

| Находка | Обход сегодня | Цена |
|---|---|---|
| №1 `Var.provide` не видит контейнера | класс-мост `@Handler([Database])` кладёт соединение в `input`, писатель читает его оттуда | лишний класс, лишняя строка в `providers:`, лишний юнит в слое |
| №2 у события нет `meta.idempotencyKey` | relay публикует ключ через `IMessageBus` мимо `Emitter` | приложение так не может: `emit` события ключа не принимает |
| №3 текст ошибки задаёт контейнер | починка вписана в идентификатор DI-токена-алиаса | идентификатор DI-токена перестал быть именем |
| №4 словарь `meta` закрыт ядром | раздел записи назначает функция плагина | место вызова не решает, чем упорядочена его запись |

Все четыре зафиксированы тестами
`packages/nestling.outbox/src/core-limits.spec.ts`. Тест проверяет
**поведение ядра**: правка ядра его уронит, и это задумано — падение
означает, что находку пора закрывать и в журнале.

Change правит ядро и снимает обходы. Ограничение прошлого change'а
(«ядро не трогаем») было условием замера, а не выводом из него: замер
состоялся и записан, поэтому ограничение снимается.

## Goals / Non-Goals

**Goals:**

- Слой транзакции пишется одним юнитом: писатель переменной получает
  зависимости из контейнера.
- Издатель события может передать ключ идемпотентности так же, как
  издатель команды.
- Сателлит дополняет текст ошибки о недостающей зависимости, не трогая
  идентификаторы DI-токенов.
- Сателлит расширяет словарь `meta` вызова своим полем, оставаясь
  совместимым с `Port`/`Emitter` ядра.
- `core-limits.spec.ts` удаляется: ни одной незакрытой находки не
  остаётся.

**Non-Goals:**

- Публичный конструктор юнита с зависимостями для произвольной фазы.
- Чеканка ключа идемпотентности событию.
- Дедупликация, упорядоченная доставка и понятие раздела в ядре.
- Подсказки на семействах DI-токенов и на классах.

## Decisions

### 1. Писатель переменной получает зависимости второй формой `provide`

`ContextVar.provide` получает перегрузку с зависимостями:

```typescript
Tx.provide([Database], (ctx, db) => db.begin());
```

Зависимости — обычные DI-токены. Пайплайн резолвит их на `bind()` тем же
резолвером, которым создаёт классы-юниты: `endpoint.resolve(resolver)`
уже принимает `(token: InjectionToken) => unknown`, а под `App` этим
резолвером служит `#requireDependency`. Поэтому отсутствие провайдера
даёт ту же ошибку фазы ASSEMBLE, что и у класса-юнита: с паттерном
endpoint'а, модулем-объявителем и способом починки.

Значение, возвращаемое `provide`, остаётся pre-юнитом: добавка,
накопительная типизация и рантайм-пометка переменной те же. Меняется
одно — юнит несёт список DI-токенов и попадает в `TNeeds` пайплайна,
как класс-форма. `TNeeds ≠ never` означает «пайплайн не готов к
исполнению»; для писателя с зависимостями это верно ровно так же.

*Отвергнуто:*

- **Синтез класса внутри `provide`.** Пришлось бы записать метаданные
  роли, а писать их умеет только декоратор: хранилище `roleMetaStorage`
  не экспортируется намеренно — запись мимо декоратора обошла бы сверку
  списка зависимостей с параметрами. Синтезированный класс к тому же
  анонимен, а класс-юнит перечисляется в `providers:` — приложению
  пришлось бы регистрировать значение, которое оно не может назвать.
- **Публичный `withDeps([...], fn)` для любой фазы.** Механизм тот же,
  но запроса замер не дал: у `.ok`, `.catch` и `.finally` класс-форма
  читается не хуже функции. Писатель переменной — единственное место,
  где класс существует только ради переезда значения через `ctx.input`.
  Механизм внутри пайплайна пишется общим; наружу в V1 торчит одна
  дверь.
- **Ридер вместо зависимости.** `Ctx(Database)` не подходит: контекстные
  ридеры читают переменные запроса, а соединение — значение из
  контейнера.

### 2. Требования писателя к контексту выводятся из аннотации `ctx`

Одноаргументная форма объявляет требования тип-аргументом:
`TenantId.provide<{ identity: Identity }>((ctx) => …)`. У формы с
зависимостями тип-аргументов два (список DI-токенов и требования), а
частичного вывода тип-аргументов в TypeScript нет: указав одно, автор
обязан указать и второе.

Поэтому у второй формы требования объявляются аннотацией параметра:

```typescript
Tx.provide([Database], (ctx: ExtendableContext<{ identity: Identity }>, db) =>
  db.begin(ctx.input.identity.tenant),
);
```

Список DI-токенов выводится из первого аргумента, `db` получает тип
контекстно, требования — из аннотации. Обе формы дают один и тот же
pre-юнит; расходятся только способы назвать требования.

Проверка вывода — тип-тест до реализации: если вывод `db` ломается,
запасной вариант — оба тип-аргумента явно, а аннотация остаётся
сокращённой записью.

*Отвергнуто:* отдельное имя метода (`provideWith`). Второе имя для того
же действия спорит с правилом «писатель у переменной один»: их стало бы
два в типе и два в документации, а различие между ними — деталь вывода
типов.

### 3. Ключ идемпотентности переезжает из `CommandMeta` в `EmitMeta`

`CommandMeta` переименовывается в `EmitMeta`, а `MetaOf<C>` выбирает
словарь по виду `request`, а не по виду `command`:

```typescript
export interface EmitMeta extends PortMeta {
  idempotencyKey?: string;
}

export type MetaOf<C extends AnyOperation> = C extends { kind: 'request' }
  ? PortMeta
  : EmitMeta;
```

Дискриминант остаётся полем `kind`: структурная проверка операции
целиком уходит в бесконечную рекурсию и роняет `tsc`.

Чеканка ключа не расширяется: `idempotencyKeyOf` по-прежнему возвращает
ключ только для вида `command`. Событие едет с ключом тогда, и только
тогда, когда его передал издатель. Разница честная: ключ команды —
идентичность намерения, и вызыватель может её выдумать; у факта такой
идентичности нет, а сгенерированный ключ выглядел бы основанием для
дедупликации, не будучи им.

Конверт не меняется вовсе: `PublishOptions.idempotencyKey` и
`BusMessageMeta.idempotencyKey` кладутся при любой публикации уже
сегодня — правятся их JSDoc, где написано «команды», и спека
`port-idempotency`. Приёмная сторона тоже не меняется: ключ приходит в
`ctx.raw.attributes`, а `withIdempotencyKey()` кладёт его в переменную —
одинаково для команды и события.

*Отвергнуто:*

- **Оставить как есть, переписав дизайн-док.** Тогда relay остаётся
  единственным издателем события с ключом, а приложение — нет: ядро
  умеет то, чего не даёт пользователю. Это не гарантия, а асимметрия.
- **Ключ у `request`.** У запроса живой вызывающий ждёт ответа, ретрай
  которого — забота вызывателя. Поле в `meta` обещало бы дедупликацию,
  которой на этом пути нет.

### 4. Подсказка живёт на объявлении DI-токена

`makeToken` принимает второй аргумент:

```typescript
export const MessageBus$ = makeToken<IMessageBus>('MessageBus', {
  hint: "add a bus transport to 'transports:'",
});
```

Ошибка о недостающих зависимостях печатает подсказки строками под
перечнем — подсказку недостающего DI-токена и подсказку каждого
потребителя, у которого она объявлена:

```
Unsatisfied dependencies (1):
  - 'MessageBus' required by '@nestling/outbox relay'
    MessageBus: add a bus transport to 'transports:'
    @nestling/outbox relay: or remove the outbox plugin
Register a provider for each of them (in 'providers:' of a module, or via register()).
```

Правило одно: подсказка печатается там, где напечатан её DI-токен.
Потребитель без подсказки печатается как сегодня, одним именем.

Пакет-сателлит перестаёт вписывать текст починки в идентификатор:
`OutboxBus$` остаётся алиасом ради имени потребителя, но идентификатор
становится именем (`'@nestling/outbox relay'`), а починка — подсказкой.

*Отвергнуто:*

- **Хук `assemble({ onUnsatisfied })` или обёртка `build()`.** Точка
  расширения на процедуре сборки даёт пакету право переписать чужой
  текст целиком, а нужно ему — дополнить свой абзац. Формат ошибки
  сборки остаётся за ядром.
- **Подсказка только у недостающего DI-токена.** `MessageBus$`
  принадлежит ядру, и «убрать плагин outbox'а» ядро о себе написать не
  может. Половина починки осталась бы невыразимой.
- **Обёртка зависимости (`hinted(MessageBus$, '…')`) в списке deps.**
  Значение, похожее на DI-токен и не являющееся им, пришлось бы
  разворачивать в каждом месте, где список зависимостей читается.

### 5. Словарь `meta` — тип-параметр вызывающей стороны

`Port` и `Emitter` получают второй тип-параметр со значением по
умолчанию:

```typescript
export type InvokeArgs<
  C extends AnyOperation,
  M extends MetaOf<C> = MetaOf<C>,
> = undefined extends InputOf<C>
  ? [payload?: InputOf<C>, meta?: M]
  : [payload: InputOf<C>, meta?: M];

export interface Emitter<C extends EmittingOperation<any, any, any, any>, M extends MetaOf<C> = MetaOf<C>> {
  emit(...args: InvokeArgs<C, M>): Promise<void>;
}
```

Рантайма правка не касается: ядро кладёт в конверт свои поля и не
смотрит на чужие. Сателлит объявляет словарь пересечением и остаётся
совместимым — параметр метода в TypeScript бивариантен, поэтому
значение `Emitter<C, MetaOf<C> & { partitionKey?: string }>`
присваивается переменной типа `Emitter<C>`. Хендлер, которому раздел не
нужен, объявляет зависимость прежним `Emitter<typeof Op>`; хендлер,
которому нужен, — типом сателлита.

*Отвергнуто:*

- **Поле `partitionKey` в `meta` ядра.** Шина V1 порядка доставки не
  обещает. Поле в ядре было бы обещанием без гарантии — ровно то, что
  запрещает «guarantee over convention».
- **Собственный интерфейс эмиттера в сателлите.** Совместимость с
  `Emitter<C>` пришлось бы воспроизводить руками, включая условный
  кортеж `InvokeArgs` для операции без входа. Копия чужого типа
  разъезжается с оригиналом при первой же его правке.
- **Тип-параметр только у `Emitter`.** `InvokeArgs` общий, и обёртка
  порта упрётся в ту же стену. Цена симметрии — ноль строк рантайма.

### 6. Раздел записи задаётся местом вызова

В `@nestling/outbox` опция `partitionKey` у `outbox({ … })` удаляется, а
раздел передаётся аргументом:

```typescript
await this.userCreated.emit(user, { partitionKey: user.id });
```

Функция плагина знала о записи меньше, чем место вызова: ей приходилось
угадывать поле ключа по payload'у, приводя его типом. Правило «раздел
называет тот, кто знает порядок» ставит решение туда, где оно
принимается.

Тип эмиттера сателлита — `OutboxEmitter<C> = Emitter<C, OutboxEmitMeta<C>>`,
где `OutboxEmitMeta<C> = MetaOf<C> & { partitionKey?: string }`.
`outboxed(Op)` отдаёт DI-токен этого типа.

*Отвергнуто:* оставить обе двери — функцию плагина как умолчание и
аргумент как переопределение. Два источника одного значения требуют
правила старшинства, а само правило не записано ни в одном из них.

### 7. Тест границы удаляется целиком, а не переписывается

`core-limits.spec.ts` фиксировал поведение ядра, которое change меняет:
три его сценария падают по построению. Место проверок — спеки ядра:
писатель с зависимостями проверяется спекой переменных, ключ события —
спекой порта, подсказка — спекой контейнера. Пакет проверяет своё:
раздел из места вызова и текст ошибки без шины.

Так же закрывалась находка №4 записи о реестре подписок: change
`stream-finish` удалил `packages/nestling.subscriptions/src/core-limits.spec.ts`
вместе с находкой.

## Risks / Trade-offs

- **Вывод типов у формы с зависимостями** → тип-тест пишется до
  реализации: вывод `db` из списка DI-токенов при аннотированном `ctx`.
  Не сработает — оба тип-аргумента указываются явно, а поведение
  рантайма не меняется.
- **Бюджет типов от второго тип-параметра `Port`/`Emitter`** →
  `yarn type-budget` замеряется до и после правки `families.ts`. Порог
  превышен — параметр остаётся только у `Emitter`, где он доказан
  сателлитом.
- **`idempotencyKey` у события читается как обещание дедупликации** →
  спека и JSDoc называют гарантию ядра ровно: ключ провозится и
  доступен обработчику, дедупликация — забота сателлита. Чеканки у
  события нет, поэтому «ключ есть всегда» про событие не говорится.
- **Подсказки удлиняют текст ошибки сборки** → печатаются только
  объявленные, по строке на DI-токен. Приложение без подсказок видит
  прежний текст.
- **`EmitMeta` вместо `CommandMeta` — переименование в публичном
  API** → правится каждое место импорта; репозиторий не несёт
  совместимости, и алиаса не остаётся.

## Migration Plan

1. Контейнер: опции `makeToken`, печать подсказок, подсказка ядра у
   `MessageBus$`.
2. Операции: `EmitMeta`, `MetaOf` по виду `request`, тип-параметр
   словаря у `Port` и `Emitter`; замер бюджета типов.
3. Приложение: вторая форма `provide`, резолв зависимостей юнита на
   `bind`, ключ идемпотентности события на обоих путях биндинга.
4. `@nestling/outbox`: раздел аргументом `emit`, удаление опции
   плагина и алиаса шины, удаление `core-limits.spec.ts`.
5. `examples/users-service`: `ProvideDb` уходит из кода и из
   `providers:`, раздел переезжает в вызов `emit`.
6. Документация: дизайн-доки, главы 14 и 27, README четырёх пакетов,
   пометки «РЕАЛИЗОВАНО» у каждой из четырёх находок записи
   [ideas.md [2026-09-07]](../../../docs/decisions/ideas.md).

Откат — обратный порядок; промежуточных состояний, в которых
приложение собирается, но ведёт себя иначе, план не создаёт.

## Open Questions

- Нужна ли подсказка семейству DI-токенов. Сателлиты семейств
  (`outboxed`, `Logger$`) до сих пор упирались в имя потребителя, а не
  в имя члена, но пример появится раньше или позже.
- Останется ли `OutboxBus$` алиасом после того, как подсказки станут
  печататься у потребителей. Прямая зависимость relay от `MessageBus$`
  назвала бы потребителем класс, и подсказку пришлось бы вешать на
  ядро.
