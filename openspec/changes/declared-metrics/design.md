## Context

Метрики ядра появились change'ем `observability`
([архив](../archive/2026-09-13-observability/)). Схема повторила схему
логгера: интерфейс `Metrics` с двумя пишущими методами, корень
`RootMetrics$` из опции `makeApp({ metrics })`, семейство `Metrics$(scope)`
поверх корня, четыре метрики ядра на endpoint и на вызов порта. Пустая
реализация под корнем служит выключателем: рантайм сравнивает корень с ней
по ссылке и без настоящей реализации не снимает время.

Схема работает, но метрика в ней называется строкой в точке записи.
Отсюда состав метрик неизвестен никому, пока запись не случится, а набор
рядов — пока не случится запись с конкретными атрибутами. Экспозиция
Prometheus без заранее заведённых рядов не показывает нули; `HELP`, `TYPE`
и единицу измерения взять неоткуда; опечатка в имени заводит второй ряд.

Направление записи выбрано так, что ядро ничего не хранит: значения
копит чужая реализация корня. Поэтому адаптер приходится сшивать руками —
один объект уходит и в опцию `metrics`, и в провайдер плагина, который
читает его `render()`.

Прецеденты «состав известен на сборке» в репозитории уже есть, и все три
устроены одинаково: объявление — значение, сборка собирает перечень.
Операция объявляется `makeRequest`/`makeCommand`/`makeEvent`, и реестр
имён пакета ловит два объявления одного адреса. Endpoint объявляется
значением, discovery собирает перечень, документ OpenAPI строится из
деклараций. Вклад в пробы приходит провайдером токена семейства
`HealthCheck$`, а `ContainerBuilder.familyMembers` даёт перечень вкладов
до создания экземпляров — вклады невыбранных фич выпадают тем же
механизмом, который убирает их провайдеры.

Ограничения, в которых работает этот change:

- Обратной совместимости нет: старое API удаляется целиком.
- Ядро формата экспорта не знает и знать не должно.
- Цена наблюдаемости на горячем пути обязана оставаться измеримо малой.
- Изменение затрагивает ветку `change/otel-satellite`, чьё предложение
  написано против опции корня. Её метрическая часть перевыпускается после
  этого change'а; трассовая половина не зависит.

## Goals / Non-Goals

**Goals**

- Состав метрик известен на фазе BUILD, вместе с выбором фич и ветками
  переключателей.
- Набор рядов объявленных атрибутов известен там же, поэтому экспозиция
  отдаёт нули до первой записи.
- Незадекларированная запись невыразима в типах.
- Накопленное держит ядро; экспорт читает его узлом графа, а не
  договаривается об одном объекте на два места.
- Запись объявленного ряда не собирает строковый ключ.

**Non-Goals**

- Вид `gauge`.
- Метрическая часть сателлита `@nestlingjs/otel`.
- Политика сборки на каталог (`everyMetric(…)`).
- Множество значений атрибута из конфига.
- Exemplars и связь записи с трассой.

## Decisions

### D1. Метрика объявляется значением, а не называется строкой

Группа метрик — значение, созданное `makeMetrics`:

```typescript
export const OrdersMetrics = makeMetrics('orders', {
  created: counter({
    help: 'Созданные заказы',
    attributes: { tier: ['free', 'paid'], source: open },
  }),
  'checkout.duration': histogram({
    help: 'Время оформления',
    unit: 'ms',
    buckets: [5, 10, 25, 50, 100, 250, 500, 1000],
    attributes: { step: ['validate', 'charge', 'persist'] },
  }),
});
```

Конструкторов два, по одному на вид, а не один с полем `kind`. Причина та
же, что у трёх конструкторов операции: правила видов расходятся — у
счётчика нет корзин, у гистограммы нет прибавки по умолчанию, — и
расхождение проверяется типом в точке объявления, а не условием при
создании значения.

**Альтернатива: каталог отдельно от записи.** Объявить список метрик, а
писать по-прежнему строкой. Отвергнуто: список и вызовы расходятся молча,
и гарантии не возникает — это convention, а не guarantee.

**Альтернатива: статический анализ.** Правило в `@nestlingjs/eslint-plugin`
собирает вызовы `counter('…')` в каталог. Отвергнуто: каталог существует
только в линтере, рантайм и экспортёр о нём не знают.

### D2. Имя складывается из префикса и ключа, без преобразований

Имя метрики — `${prefix}.${key}`. Ключ записывается так, как должен
выглядеть в имени: `'checkout.duration'` — обычный ключ объекта в
кавычках. Преобразования `camelCase` → точки нет.

Причина — «no runtime magic»: правило «имя равно тому, что написано»
читается без знания фреймворка, а правило «`requestDuration` становится
`request.duration`» требует помнить преобразование и ломается на
аббревиатурах.

Префикс попадает в имя, а не в атрибут. Сегодня область живёт атрибутом
`scope`, который добавляет рецепт семейства. Перенос в имя убирает ряд
атрибутов у каждой метрики и делает имя самодостаточным. Ядро при этом
сохраняет свои имена: префикс `nestling`, ключи `requests`,
`request.duration`, `port.calls`, `port.duration`.

### D3. Атрибут объявлен перечнем значений или пометкой `open`

```typescript
attributes: { tier: ['free', 'paid'], source: open }
```

Перечень даёт два следствия: значение вне перечня не компилируется, и
ряды этой метрики известны как произведение перечней. `open` объявляет
атрибут, значения которого известны только в рантайме: ряд заводится по
факту первой записи, нулей у него нет.

Пометка обязательна и не имеет умолчания. Автор метрики отвечает за
количество рядов; `open` — место, где он это подтверждает. Атрибут без
объявления не принимается: запись с лишним ключом не компилируется.

**Альтернатива: только ключи, без значений.** Ловит опечатки в ключах, но
не даёт нулевых рядов — то есть не решает главного.

### D4. Декларация — DI-токен, писатель приходит из графа

```typescript
@Component([OrdersMetrics])
export class OrdersService {
  constructor(private readonly metrics: MetricsOf<typeof OrdersMetrics>) {}

  create(): void {
    this.metrics.created.add(1, { tier: 'paid', source: 'web' });
  }
}
```

Декларация служит и объявлением, и адресом зависимости — как операция
служит и реализации, и вызывающей стороне. Писателя раздаёт граф, потому
что запись идёт в store конкретного приложения: в одном процессе
приложений может быть несколько, и ambient-корень их бы смешал.

У счётчика метод `add(value?, attributes?)`, у гистограммы —
`record(value, attributes?)`. Методы синхронны и возвращают `void`, как
сейчас: запись не имеет права задерживать запрос.

Следствие, которое принимается осознанно: код вне графа метрику написать
не может. Свободная функция получает писателя параметром от того, кто
объявил зависимость.

### D5. Группы подключаются вкладом, а не саморегистрацией

Поле `metrics:` появляется у фичи, модуля и плагина — рядом с
`endpoints:` и `providers:`:

```typescript
makeFeature({
  name: 'orders',
  metrics: [OrdersMetrics],
  endpoints: [...],
  providers: [OrdersService],
});
```

Саморегистрация при создании значения (как у реестра операций) отвергнута:
реестр операций глобален на пакет, и его единственная задача — запретить
два объявления одного адреса. Каталог метрик принадлежит сборке, а не
пакету: у двух приложений одного репозитория каталоги разные, и состав
зависит от выбора фич.

Декларация, которую запросили в `deps`, но не подключили вкладом, даёт
отказ сборки с текстом, называющим поле `metrics:` её фичи.

### D6. Накопленное держит ядро

`MetricsStore$` — узел графа, который есть всегда. Он хранит значения
рядов и каталог, по которому они заведены.

```typescript
interface MetricsStore {
  readonly catalog: MetricsCatalog;
  snapshot(): MetricsSnapshot;
  tap(sink: MetricSink): () => void;
}
```

Опция `makeApp({ metrics })` удаляется. Вместе с ней уходят `RootMetrics$`,
семейство `Metrics$`, пустая реализация как выключатель, функция
`configuredMetrics` и ошибка дубля под корнем — она существовала ровно
потому, что корень задавался двумя способами.

Интерфейс `Metrics` остаётся в поверхности пакета под именем `MetricSink`
и меняет сторону: был входом, который реализует приложение, стал выходом
store, на который подписываются. Границу ядра это не двигает — формата
экспорта ядро по-прежнему не знает.

**Альтернатива: оставить корень, добавить каталог.** Экспортёр получал бы
каталог вызовом `describe(catalog)`. Отвергнуто по требованию
пользователя и по существу: тогда каждый экспортёр заново пишет
накопление, а сшивание «один объект в опцию и в провайдер» остаётся.

### D7. У store два выхода: снимок и поток

`snapshot()` отдаёт состояние всех рядов на момент вызова. `tap(sink)`
подписывает получателя на записи и отдаёт ему стартовым состоянием
текущий снимок; возвращает функцию отписки.

Двух выходов требует OpenTelemetry: асинхронной гистограммы в его спеке
нет (есть `ObservableCounter`, `ObservableUpDownCounter` и
`ObservableGauge`), поэтому кормить SDK периодическим чтением снимка
нельзя. Push-сателлит берёт `tap`, pull-экспозиция — `snapshot`: снимок на
запрос сборщика дешевле, чем вызов на каждой записи.

Стартовое состояние в `tap` закрывает записи, сделанные до подписки —
фазы INIT и START пишут раньше, чем сателлит успевает подписаться.

Исключение подписчика изолируется и не доходит до запроса, как
изолируются исключения `.finally`-шагов: сбойный экспортёр не роняет
обработку. Изоляция логируется в логгер ядра.

### D8. Ряд адресуется индексом, вычисленным на сборке

Ряды объявленных атрибутов — произведение их перечней. Каждому
присваивается индекс на фазе BUILD, значения лежат в плоском массиве.
Запись становится прибавкой по индексу.

```
сейчас:  keyOf(name, attributes) — конкатенация + сортировка ключей,
         строковый ключ Map на каждой записи
станет:  values[index] += value
```

Ряды открытых атрибутов остаются в словаре: их индекс заранее неизвестен.
Это второй довод объявлять перечни там, где они есть.

Гистограмма хранит корзины, сумму и счётчик наблюдений. Границы корзин
приходят из декларации, поэтому store агрегирует без догадок, а
push-сателлит получает готовую гистограмму, а не пару `_count`/`_sum`.

### D9. Инструментовка включена всегда

Выключателя нет. Он существовал потому, что запись уходила в чужую
реализацию и стоила строкового ключа; теперь запись объявленного ряда —
прибавка по индексу, а память — восемь байт на ряд счётчика.

Требование «приложение без метрик не платит» из спеки `kernel-metrics`
снимается: платить стало не за что.

### D10. Ресурс сброса принадлежит владельцу получателя

Store ресурсом не владеет: у него нет получателя, и сбрасывать ему некуда.
Ресурс объявляет тот, кто отправляет наружу, — push-сателлит.

Порядок закрытия даёт обе нужные гарантии без новых механизмов.
`App.close()` — строгий реверс START: сигнал, дренаж серверов, закрытие
транспортов, `container.destroy()`. К моменту `destroy` записи прекращены,
а ресурсы освобождаются реверсом топологического порядка — значит
сателлит, зависящий от `MetricsStore$`, закрывается раньше него и
последний снимок ему доступен.

Pull-экспозиции сбрасывать нечего: сборщик просто не придёт снова.

### D11. Формат экспозиции — отдельный пакет

`@nestlingjs/prometheus` читает `MetricsStore$` и отдаёт текст экспозиции
endpoint'ом с пометкой `detached`. Зависимостей от OpenTelemetry у него
нет.

Формат не кладётся в `@nestlingjs/app`, потому что ядро форматов не знает.
Он не кладётся и в `@nestlingjs/otel`: тащить SDK ради текстовой
экспозиции незачем, а сателлиту остаётся push по OTLP и трассы.

### D12. Каталог ядра достраивается из деклараций сборки

Ядро объявляет свою группу с префиксом `nestling`. Атрибуты `outcome`,
`kind` и `binding` — постоянные перечни. Атрибуты `transport` и `pattern`
вычисляются из деклараций endpoint'ов этой сборки, а `operation` — из
топологии операций.

Поэтому ряды ядра известны целиком до первого запроса, и экспозиция
свежеподнятого приложения показывает нули по каждому endpoint'у и каждому
исходу.

Следствие: каталоги двух сборок одного приложения различаются, если
различается выбор фич. Это правильно и означает, что дифф каталога в CI
снимается по конкретной сборке.

### D13. Тест читает снимок

`spyMetrics()` удаляется из `@nestlingjs/testing`: перехватывать нечего,
записи и так лежат в store. Тестовое приложение отдаёт снимок, а
утверждение адресует ряд декларацией и атрибутами, а не строкой:

```typescript
await using testApp = await buildTest(app);

await testApp.call(CreateOrder, { sku: 'x' });

expect(testApp.metrics.of(OrdersMetrics.created, { tier: 'paid' })).toBe(1);
```

## Risks / Trade-offs

- **Комбинаторный рост рядов.** Три атрибута по десять значений дают
  тысячу рядов на метрику ещё до трафика → произведение перечней считается
  на BUILD; превышение порога становится отказом сборки, называющим
  метрику и её атрибуты. Порог — предмет открытого вопроса 2.
- **Двойное хранение при push.** Значения лежат и в store, и в SDK
  сателлита → цена — килобайты; альтернатива (store только для pull)
  оставила бы push-сторону без стартового состояния.
- **Объём миграции.** Затронуты ядро, тестовый пакет, два примера, глава
  гайда и три design-документа → примеры мигрируются вместе с кодом, а
  главы пересверяются в том же change'е; «сверено с кодом» обновляется.
- **Код вне графа не пишет метрики** → писатель передаётся параметром;
  случай редкий, и явная передача читается лучше ambient-корня.
- **Ветка `otel-satellite` ждёт.** Её метрическая часть перевыпускается →
  трассовая половина от этого change'а не зависит и идёт параллельно;
  предупреждение врезано в её `tasks.md` коммитом `784ccf30`.
- **Store в ядре берёт на себя агрегацию.** Корзины гистограмм — работа,
  которой у ядра не было → границы приходят из декларации, ядро не
  выбирает их само и формата не знает.

## Migration Plan

1. Объявления и каталог в `@nestlingjs/app`: `makeMetrics`, конструкторы
   видов, `open`, вклад `metrics:`, сборка каталога на BUILD.
2. Store: ряды по индексам, словарь открытых рядов, `snapshot`, `tap`.
3. Ядро переводится на свою группу: рантайм пайплайна и узел порта пишут
   по декларации; `RootMetrics$`, `Metrics$`, опция корня и
   `configuredMetrics` удаляются.
4. `@nestlingjs/testing`: `spyMetrics()` удаляется, появляется чтение
   снимка.
5. Пакет `@nestlingjs/prometheus`.
6. Примеры `microservice` и `modular-app`: свои группы метрик, экспозиция
   пакетом, `src/metrics.ts` удаляется.
7. Документация: глава 22 и пара, `design/container.md`, `design/pipeline.md`
   §2, `design/operations.md` §2.3 и пары, таблица пакетов, README.

Отката нет и не предусматривается: в проде фреймворка нет, старое API
удаляется целиком.

## Open Questions

1. Имя пакета формата. `@nestlingjs/prometheus` называет формат, а не
   роль; альтернатива — `@nestlingjs/metrics.prometheus` по образцу
   `logging.pino`. Склоняюсь к первому: пакет не сателлит библиотеки, а
   один формат экспозиции.
2. Порог предвычисленных рядов. Нужен ли он в первой версии, и считается
   ли он на метрику или на каталог.
3. Форма адресации ряда в тесте: `testApp.metrics.of(Decl.member, attrs)`
   или снимок списком записей с поиском.
4. Нужен ли `tap` в этом change'е, если его единственный потребитель —
   метрическая часть сателлита, выходящая позже. Аргумент за: без него
   спека store неполна, и push-сторона не проверяется. Аргумент против:
   выход без потребителя рискует не совпасть с тем, что понадобится.
