## 1. Три уровня деклараций

Всё, что приложение обслуживает, описывается на одном из трёх уровней.

1. **Байтовый уровень транспорта** — статика, CORS, сжатие,
   wildcard-подписки. Это настройки и плагины транспорта; схем и операций
   здесь нет ([transports.md](./transports.md)). Случаи, которые не
   укладываются в схемы, обрабатываются на этом уровне; отдельной модели
   деклараций для них не существует.
2. **Операции** — все операции со схемами: интерфейс (`input`, `output`,
   `errors`) и адреса (`name`, `http:`, `cli:`, …)
   ([operations.md](./operations.md)).
3. **Реализации** — `implement(Operation, { pipeline?, handler,
   subscriber? })`. Поле `subscriber` задаёт адрес подписки: оно обязательно
   у операции-события и запрещено у остальных видов
   ([operations.md](./operations.md)).

Операция первичен. Конструкторы транспортов (`httpEndpoint`, `cliEndpoint`,
…) — сокращённая запись для «анонимная операция плюс `implement` одним
вызовом». На уровне ядра любая декларация компилируется в один и тот же узел
графа.

Endpoint отличается от операции только видимостью. Экспортированная
именованная операция вызываема: через `.caller`, клиенты, интерком, с учётом
версий. Анонимная декларация — только транспортная поверхность. Чтобы
endpoint стал вызываемым, достаточно дать ему имя операции и экспортировать.

Декораторных деклараций (`@Endpoint`, `@HttpEndpoint`), интерфейса
`IEndpoint` и глобального реестра endpoint'ов нет. Канонический стиль
деклараций — функциональный (`make*`). Классы используются там, где нужен
DI: провайдеры, юниты, хендлеры.

## 2. Декларация: значение, созданное конструктором транспорта

```typescript
export const CreateOrder = httpEndpoint({
  method: 'POST',
  path: '/orders',
  input: NewOrder,
  output: Order,
  errors: [OrderLimitReached],       // типизированный канал E (errors.md)
  pipeline: basePipeline,
  handler: {
    deps: [OrdersService],
    handle: (orders) => async (input, meta) => new Ok(orders.create(input)),
  },
});
```

**Поля транспорта.** `method`, `path` и другие поля конкретного транспорта
разрешены только в декларации и типизированы: path-параметры выводятся из
шаблона, правило размещения полей и bind-карта (§4) вычисляются в
конструкторе. Пайплайн и хендлер о транспорте не знают; операция от
транспорта не зависит.

**`makeEndpoint`.** Это примитив ядра, из которого собраны конструкторы
транспортов; в пользовательский код он не входит. В нём живёт весь общий
код: нормализация форм `handler`, получение зависимостей из
контейнера, бренд, `errors:`, `doc:`, `detached`. Конструктор транспорта
добавляет только свои поля.

**Проверка при создании.** Поля проверяются в момент создания декларации, а
не при сборке приложения. Ошибку сразу дают: пустой `path`, `path` без
ведущего `/`, повторяющийся path-параметр, пустое имя команды. Список
`errors:` проверяется там же: элемент, не созданный `makeFail`, и
повторяющийся `code` дают ошибку с именем endpoint'а и проблемным значением.
Секция `doc:` отвергает неизвестное поле, `hidden: true` и статус вне
перечня успешных; пометка `detached` отвергает не-строку и пустую причину.
Проверки, которым нужно сопоставить шаблон пути со схемой, живут на уровне
bind-карты (§4): Standard Schema не отдаёт перечень ключей.

**`errors:`.** Это поле ядро интерпретирует, в отличие от непрозрачного
биндинга. Из него выводится тип отказов хендлера, и оно же передаётся через
`EndpointMeta` в проверку операции отказов на выходе из пайплайна.
Конструкторы транспортов поле только пробрасывают.

**`detached: '<причина>'`.** Пометка выводит endpoint из-под всех
инвариантов сборки ([pipeline.md §7](./pipeline.md)). Поле не зависит от
транспорта и живёт в ядре. Его тип — `string`: `detached: true` не
компилируется, а не-строку и пустую строку рантайм отвергает при создании
декларации. Ядро переносит причину на значение и сохраняет её при `resolve`,
как `binding` и `errors:`.

**`doc:`.** Секция документации: `summary`, `description`, `tags`,
`deprecated`, успешный `status`, `hidden: '<причина>'`. Она не зависит ни
от транспорта, ни от формата документации. Ядро её не интерпретирует: ни
один путь исполнения запроса от неё не зависит; ядро переносит секцию на
значение и сохраняет при `resolve`, как `binding`. Читают её генераторы
описаний ([schemas.md §2.2](./schemas.md)). Полей, осмысленных только для
одного формата, в секции нет; например, `operationId` выводится, а не
объявляется. В форме с операцией секция принадлежит операции наравне с
`input`, `output` и `errors`.

**Бренд.** Декларация помечена symbol-брендом. Значение остаётся обычным
объектом: спред, `Object.keys` и сериализация бренда не видят. Элемент
`endpoints:` без бренда роняет старт с именем объявившей единицы и
позицией в массиве; молча он не пропускается.

**Ссылка на транспорт** — токен **экземпляра**. Декларация выбирает свой
экземпляр полем `on:` (`on: 'admin'`); без него это `'default'`. Endpoint,
чьего экземпляра нет в графе, роняет сборку на фазе ASSEMBLE.

**Несколько транспортов.** Канон — именованная операция с несколькими
биндингами и один `implement`. Несколько тонких деклараций с общим
хендлером — вариант для анонимных поверхностей с разными наборами полей.
Каждая декларация знает свой транспорт.

**Узел графа.** Endpoint — обычный узел графа с синтетическим id
(`endpoint:POST /orders`). Рёбра зависимостей хендлера видны в визуализации и `explain()`;
циклы проверяются как для любого узла. Узел создаётся
жадно на фазе ASSEMBLE, паттерн регистрируется на фазе WIRE.

## 3. Поле `handler`: три формы

Всё, что относится к исполнению, лежит в поле `handler`. Декларация
описывает адрес, схемы, отказы и пайплайн; зависимости принадлежат
хендлеру, а не декларации.

| Форма | Когда |
|---|---|
| `handler: (input, meta) => …` | без зависимостей. Единственная форма, которую принимают standalone-транспорты (`server.route`): endpoint с зависимостями туда не проходит по типам |
| `handler: { deps: […], handle: (…deps) => (input, meta) => … }` | каррированная фабрика. Внешний вызов происходит один раз при сборке (как конструктор), замыкание становится инстансом. Порядок аргументов `handle` совпадает с порядком `deps` |
| `handler: Class` | класс с `@Injectable` и методом `handle`. Endpoint создаёт экземпляр сам: он становится провайдером этого класса, и регистрировать класс в `providers:` не нужно; повторная регистрация — ошибка сборки |

Во всех трёх формах `meta` содержит зарезервированный ключ
`signal: AbortSignal` (отмена запроса) и поля контекста, накопленные
`.pre`-юнитами. Если pre-юнит добавил поле `signal`, инъекция его
перекрывает. Возвращаемый тип сверяется и со схемой `output`, и со списком
`errors:` — в точке декларации ([errors.md](./errors.md)). Отказ
возвращается значением; `throw` — доставка из глубины вызовов
([errors.md §1](./errors.md)).

Классовая форма — канон для кода приложения: она сохраняет привычную после
NestJS структуру «конструктор плюс метод», но без декораторной декларации:

```typescript
@Injectable([OrdersService, ChargeCard.caller])
export class CreateOrderHandler {
  constructor(
    private orders: OrdersService,
    private billing: Port<typeof ChargeCard>,
  ) {}
  async handle(
    input: NewOrder,
    meta: { signal: AbortSignal },
  ): Output<Order, typeof OrderLimitReached> { /* ... */ }
}

export const CreateOrder = httpEndpoint({
  method: 'POST',
  path: '/orders',
  input: NewOrder,
  output: Order,
  errors: [OrderLimitReached],
  pipeline: basePipeline,
  handler: CreateOrderHandler,   // класс — поле типизированного вызова:
});                              // сверка со схемами в точке декларации, implements не нужен
```

Unit-тест хендлера не требует фреймворка: каррированная фабрика вызывается
с фейками, класс создаётся через `new CreateOrderHandler(fakes…)`. Импортов
из `@nestling/*` в таком тесте нет.

**Неразрешённые зависимости в типе.** Тип endpoint'а содержит всё, что ещё
не получено из контейнера: токены `handler.deps`, класс хендлера и классы
юнитов пайплайна. `server.route()` принимает только endpoint без них, так
же как `Pipeline<any, never>`. Зависимости получаются одним шагом
`endpoint.resolve(resolver)`; тот же вызов связывает юниты пайплайна тем же
резолвером. App делает это на фазе WIRE для каждой обнаруженной декларации.
Позиционная форма `endpoint.resolve([...])` предназначена для каррированной
фабрики вне контейнера (тесты). Класс-хендлер и пайплайн с классами-юнитами
требуют формы с резолвером: создать их инстансы иначе нечем.

## 4. HTTP: размещение полей `input` и bind-карта

Схема `input` одна для всех транспортов. Куда каждое её поле кладётся в
HTTP-запросе, определяет детерминированное правило от шаблона пути, метода
и пометок:

1. имя поля совпало с path-параметром шаблона — поле берётся из пути;
2. поле помечено `query(...)` или `body()` — из указанного места;
3. остальные поля берутся из query для методов без тела (`GET`, `HEAD`,
   `DELETE`, `OPTIONS`, `TRACE`) и из тела для остальных методов;
4. заголовки читаются только по пометке, никогда по умолчанию. В V1
   пометки `header()` нет ([deferred](../decisions/deferred.md)).

```typescript
export const CreateUser = httpEndpoint({
  method: 'POST',
  path: '/users/:orgId/members',
  input: z.object({
    orgId: z.string(),                     // совпало с :orgId → путь
    name: z.string(),                      // POST → тело
    dryRun: z.stringbool().optional(),     // пометка ниже → query
    tags: z.array(z.string()).optional(),  // ?tags=a&tags=b
  }),
  bind: { dryRun: query(), tags: query({ multiple: true }) },
  output: User,
  pipeline: basePipeline,
  handler: {
    deps: [UserService],
    handle: (users) => async (input) => Ok.of(await users.add(input)),
  },
});
```

**Пометка — значение.** `query(options?)` и `body()` — экспортируемые
конструкторы пометок. Строковая форма вида `{ expand: 'query' }` не
принимается. Ключи `bind` типизированы полями схемы за вычетом
path-параметров: опечатка в ключе и пометка на path-параметре — ошибки
компиляции.

**Bind-карта.** Правило размещения и пометки разворачиваются в плоскую
карту «явные размещения плюс правило для остальных полей». Это происходит
при создании декларации или операции, а не при регистрации в App. Карту
читают транспорт, генератор OpenAPI и типизированный клиент; клиент
получает её из одного импорта операции, без серверного кода. Перечислить
все поля карта не может (интроспекции схем нет), но у каждого поля есть
ровно одно место.

**Строгий приём.** Payload собирается только из канонических мест. Поле,
присланное не туда, в payload не попадает и не проходит обычную валидацию.
Слияния «поле принимается отовсюду» нет, ошибок конфликта источников тоже.
Тело запроса читается только тогда, когда его требует карта.

**Ошибки при создании декларации.** Пометка на поле-path-параметре;
`body()` у метода без тела; `bind` или path-параметр при неструктурном
`input` (потоковая форма, примитив); path-параметр при отсутствии `input`;
`rawBody` вместе с потоковой или multipart-формой. У `multipart` роль
структурного `input` играют поля формы: path-параметры и помеченные
query-поля добавляются к `fields`. Случай «path-параметр объявлен, а поля с
таким именем в схеме нет» в общем виде не диагностируется, потому что
Standard Schema не отдаёт перечень ключей ([schemas.md](./schemas.md)).
Диагностика есть там, где есть конвертер вендора ([schemas.md
§2.1](./schemas.md)).

**Массивы в query.** Повтор ключа даёт массив в порядке следования;
последнее значение не затирает предыдущие. `query({ multiple: true })` даёт
массив и при одном вхождении. Ноль вхождений означает отсутствие поля;
обязательность решает схема. Преобразование строк query в числа и булевы
значения (`?page=2`) делает схема (`z.coerce`), а не транспорт.

**Заголовки контекста.** `Authorization`, `traceparent` и подобные
заголовки — контекст запроса; они попадают в `meta` через pre-юниты.
`Accept` и `Content-Type` обрабатывает транспорт; до хендлера они не
доходят.

## 5. Формы io: дерево форм над схемами

`input` и `output` — не всегда одна схема. Верхний уровень декларации —
форма; листья — Standard Schema. Спецификация схем для значений при этом
не затрагивается.

| Форма | Семантика | HTTP media type |
|---|---|---|
| значение (схема как есть) | обычный запрос/ответ | JSON |
| `stream(T)` | конечный поток | NDJSON / chunked |
| `events(T)` | открытая подписка | `text/event-stream` (SSE) |
| `multipart({ fields, files })` | поля + файлы | `multipart/form-data` |

Форма — неизменяемое брендированное значение: произвольный объект с полем
`kind` за форму не принимается. Схема без обёртки и отсутствие `input` —
это форма значения; отдельного конструктора `value(...)` нет.

Проверку выполняет рантайм перед хендлером ([pipeline.md](./pipeline.md)),
и зависит она от формы: значение проверяется целиком, элементы `stream` и
`events` — по одному во время чтения. У `multipart` поля проверяются
схемой `fields` там же, в рантайме, а файлы (`upload({ maxSize, mime })`)
ограничивает транспорт во время разбора, не буферизуя их. Семантика потоков и item-цепочек описана в
[streaming.md](./streaming.md).

Соответствие форм и media types детерминировано; оно служит входом для
генерации OpenAPI.

При создании декларации отвергаются: `multipart` в `output`; `upload()` вне
`multipart`; потоковая форма без листа; шаг item-цепочки, меняющий тип
(`.batch`), в `output`. Текст ошибки называет endpoint, слот и форму.

### `multipart({ fields, files })` и `upload(...)`

```typescript
input: multipart({
  fields: z.object({ id: z.string(), title: z.string() }),  // необязателен
  files: { avatar: upload({ maxSize: 5 * MiB, mime: ['image/png', 'image/jpeg'] }) },
})
// payload: { fields: { id: string; title: string }, files: { avatar: FilePart } }
```

- `upload({ maxSize, mime, multiple })` описывает файловое поле.
  `multiple: true` даёт `FilePart[]`, иначе один `FilePart`, и второй файл с
  тем же именем отвергается. Незаявленное файловое поле тоже отвергается.
- Лимиты действуют во время разбора: превышение `maxSize` прерывает чтение
  этого файла (`PAYLOAD_TOO_LARGE`, 413); несовпадение `mime` даёт отказ до
  чтения тела (400).
- Ключи `files` типизируют payload: имена файловых полей известны
  статически. Совпадение имени файлового поля с полем `fields` — ошибка
  компиляции.
- Форма разрешена только во входе: значения у неё нет.

### Особенности SSE: поле `sse` HTTP-декларации

Форма `events(T)` не зависит от транспорта, поэтому всё, что относится к
передаче событий по HTTP, объявляется в полях HTTP-декларации:

```typescript
export const ActivityStream = httpEndpoint({
  method: 'GET',
  path: '/activity/live',
  output: events(ActivityEvent),
  sse: { id: (e) => e.id, event: (e) => e.kind, heartbeat: 15_000 },
  pipeline: basePipeline,
  handler: {
    deps: [ActivityHub],
    handle: (hub) => async (_payload, meta: { signal: AbortSignal; lastEventId?: string }) =>
      Ok.of(hub.subscribe(meta.signal)),
  },
});
```

- Если `id` или `event` не заданы, соответствующие поля кадра не пишутся.
  Если не задан `heartbeat`, берётся опция транспорта. Имя события `error`
  зарезервировано за отказом посреди потока и отвергается при создании
  декларации. `sse` без `events`-выхода — тоже ошибка.
- Переподключение: заголовок `Last-Event-ID` попадает в типизированный
  стартовый контекст (`lastEventId?: string`) деклараций с
  `events`-выходом. Это тот же механизм, что у `rawBody: true`; отдельного
  канала нет. Откуда продолжить поток, решает хендлер.

### Сырые байты: `rawBody`

Пометка `rawBody: true` в HTTP-декларации включает доступ к байтам тела
(подписи webhook'ов, HMAC). Транспорт кладёт байты в типизированный
стартовый контекст; слой проверки объявляет
`makePipeline<{ rawBody: Uint8Array }>()`. Забытую пометку находит
компилятор в точке декларации, на слоте `pipeline`. Тело читается один раз:
значение парсится из тех же байтов, лимит `maxBodySize` действует как
обычно. Память расходуется только у деклараций с этой пометкой.

### Проверка формы против транспорта

Операция может объявлять любые формы. На фазе ASSEMBLE биндинг проверяется
против возможностей транспорта, и несовпадение роняет сборку с ошибкой,
называющей операция, транспорт и форму. HTTP поддерживает потоки и
multipart; шина и порты V1 — только формы-значения.

## 6. CLI-биндинг

Декларация `cliEndpoint` состоит из имени команды и той же io-декларации.
Как собрать недостающий `input`, решает политика биндинга, а не операция.
`missing: 'prompt'` выводит вопросы из схемы: enum становится выбором из
списка, boolean — подтверждением, `.describe()` — подсказкой, default —
значением по «Enter». В режиме CI вопросы отключены: отсутствие флага —
ошибка. Диалог посреди выполнения выражается парой операций plan/apply; этот
приём подтверждаемой операции не зависит от транспорта. Операция всегда
остаётся функцией `input → output`.
