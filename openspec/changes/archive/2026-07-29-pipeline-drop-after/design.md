## Context

Фазовая модель пайплайна (change `pipeline-v2`, архив 2026-07-13) дала
билдер `makePipeline()` со словарём `.pre` / `.ok` / `.catch` / `.after` /
`.finally`. Ответный тракт при этом — не набор фаз, а **один список
юнитов** в порядке объявления: юнит применяется по применимости к
*текущему* ответу. `.after` — единственный юнит, применимый всегда, и
именно он ломает объяснимость правила: любой честный ответ на вопрос
«в каком порядке идут `after` и `ok`?» требует абзаца оговорок.

Текущее состояние кода (`packages/nestling.pipeline/src/core/pipeline.ts`):

- `PhasedPipeline.after<M>(unit)` — метод интерфейса билдера (строка ~204);
- `type ResponsePhase = 'ok' | 'catch' | 'after'` (строка ~277);
- `PipelineImpl.after()` — пуш в `layer.responses` с `phase: 'after'`;
- проверка применимости: `entry.phase === 'after' || (entry.phase === 'ok') === response.isSuccess`;
- `AfterUnitFn` в `core/types/unit.ts`, публичный через цепочку `export *`.

Потребителей внутри репозитория нет: `.after` вызывается только в двух
spec-файлах самого пакета (`pipeline.spec.ts`, `pipeline.runtime.spec.ts`).
Ни `middlewares/*`, ни `examples.*`, ни транспорты его не используют.

Целевые доки уже описывают тройку: `docs/design/pipeline.md` и
`docs/preview/` перечисляют только `.ok`/`.catch`/`.finally`. Расходятся с
целевым состоянием дельта-спеки `openspec/specs/pipeline-phase-model` и
`pipeline-composition`, README и `TYPE-TESTS.md` пакета, а также гайд
`docs/guides/http-functional.md` (таблица фаз + оговорка в плашке).

Логика решения — [ideas.md](../../../docs/decisions/ideas.md), секция
«[2026-07-10] Pipeline: отказ от `.after`». Change #17 из roadmap, входит
в breaking-окно волны 2, размер S.

## Goals / Non-Goals

**Goals:**

- Удалить `.after` из публичного API (билдер, тип `AfterUnitFn`) и из
  рантайма (`ResponsePhase`, ветка применимости).
- Свести словарь ответного тракта к Promise-тройке `ok`/`catch`/`finally`
  и переформулировать правило порядка в одно предложение.
- Привести дельта-спеки, README, `TYPE-TESTS.md` и гайд в соответствие;
  зафиксировать миграцию `.after(u)` → `.ok(u).catch(u)` вместе с её
  единственным расхождением по семантике.
- Сохранить поведение остальных фаз бит-в-бит: удаление не должно менять
  ни один сценарий, где `.after` не участвовал.

**Non-Goals:**

- Любая другая правка фазовой модели: типизация ctx (полный у `.ok`,
  `Partial` собственного слоя у `.catch`/`.finally`), запрет
  `Fail → Ok`, семантика `finally` и `Outcome` — не трогаются.
- `compose` и модель слоёв: порядок «pre снаружи внутрь / ответный тракт
  и finally изнутри наружу» остаётся как есть.
- DX-типы точки композиции — отдельный change `pipeline-type-dx` (#23).
- Замена `.after` любым другим примитивом.

## Decisions

### 1. Чистое удаление, без deprecation-периода

`.after` удаляется одним шагом: метод, тип, ветка рантайма. Deprecated-
заглушка (`/** @deprecated */ after()` с делегированием в `ok`+`catch`)
отвергнута — пакет доrelease'ный, потребителей ноль, а заглушка сохранила
бы ровно ту сущность в словаре, ради устранения которой затевается change.
Переходный период обошёлся бы дороже самой миграции.

**Альтернатива (отвергнута):** оставить и «просто лучше задокументировать» —
лечение симптома; сущность без использований и без незаменимых кейсов не
оправдывает третий вид юнита в правиле порядка (ideas.md, отвергнутые
варианты).

### 2. Применимость сводится к одному сравнению

После удаления ветки `entry.phase === 'after'` проверка применимости
становится тотальной по булеву признаку:

```ts
const applicable = (entry.phase === 'ok') === response.isSuccess;
```

`ResponsePhase` сужается до `'ok' | 'catch'`. Это не оптимизация, а
следствие: с двумя фазами применимость — ровно «совпал ли вид юнита с
видом текущего ответа». Введение отдельного прохода по `after`-юнитам
после `ok`/`catch` отвергнуто в журнале: это вторая модель исполнения и
разрыв правила «декларация читается сверху вниз = порядок исполнения».

### 3. Порядок и «текущий ответ» остаются несущими

Удаление `.after` **не превращает** ответный тракт в две фазы. Юниты
по-прежнему лежат в одном списке `layer.responses` в порядке объявления,
и применимость считается по ответу *на момент подхода к юниту*. Ключевой
наблюдаемый сценарий сохраняется и должен остаться в тестах: если
`.ok`-юнит бросил, ответ становится ошибкой, и объявленный **после** него
`.catch`-юнит применим и исполняется. Именно этот сценарий отличает «один
список» от «сначала все ok, потом все catch», поэтому он выносится в
явное требование дельта-спека, а не остаётся деталью реализации.

### 4. Миграция — `.ok(u).catch(u)` с явно зафиксированным нюансом

Сигнатура `AfterUnitFn` — объединение сигнатур `OkUnitFn` и `CatchUnitFn`
по ответу (`ResponseContext` против `SuccessResponseContext` /
`ErrorResponseContext`) при том же ctx (`Partial` собственного слоя), так
что любой after-юнит записывается двумя явными строками. Расхождение
ровно одно и подлежит документированию:

| | `.after(u)` | `.ok(u).catch(u)` |
|---|---|---|
| `u` не бросает | 1 вызов | 1 вызов (по применимости) |
| `u` бросает в роли ok-юнита | 1 вызов, ответ → ошибка | **2 вызова**: ok бросил → ответ стал ошибкой → `u` применим как catch |

Вывод для доки миграции: функцию, которая может бросать, не регистрируют
в обе фазы одним значением. Это не дефект замены, а прямое следствие
правила «применимость по текущему ответу» — того самого, которое `.after`
маскировал.

### 5. Типы: `AfterUnitFn` удаляется, а не сужается

`AfterUnitFn` уходит из `core/types/unit.ts` целиком. Оставить его как
alias (`type AfterUnitFn = OkUnitFn | CatchUnitFn`) отвергнуто: тип без
метода, который его принимает, — мёртвый публичный символ, а `export *`
делает любой оставленный символ частью API V1. Пользовательский код,
типизировавший переменную как `AfterUnitFn`, переписывается на две
переменные либо на `OkUnitFn`/`CatchUnitFn` по месту.

### 6. Рантайм-guard: текст ошибки обновляется вместе с API

Сообщение `'pre() is not available after a response-phase method
(.ok/.catch/.after/.finally)'` перечисляет фазы буквально — список
приводится к `(.ok/.catch/.finally)`. Мелочь, но это единственное место,
где словарь фаз просачивается в рантайм-строку; расхождение здесь
всплывёт у пользователя раньше, чем в доках.

### 7. Доки: правим только то, что разошлось

`docs/design/pipeline.md` и `docs/preview/` уже описывают целевую тройку —
они писались после принятия решения. Работа по ним сводится к проверке
на остаточные упоминания и к снятию оговорки «⚠️ В целевом V1 фаза
`.after` уходит (roadmap 17)» из плашки `docs/guides/http-functional.md`
(вместе со строкой `.after` в таблице фаз и обновлением даты «сверено с
кодом»). Запись в `decisions/ideas.md` уже существует — новая не
добавляется; в `roadmap.md` обновляется статус change #17.

## Risks / Trade-offs

- **[Регресс порядка ответного тракта]** Удаление ветки применимости
  трогает единственное место, где решается, исполнять юнит или нет →
  Митигация: рантайм-тест «ok бросил → последующий catch применим» и тест
  порядка при композиции (`ok(authed)` → `ok(base)` → `finally(authed)` →
  `finally(base)`) остаются и переписываются без `.after`, а не удаляются
  вместе с ним.

- **[Потеря покрытия при переписывании тестов]** Три рантайм-теста и два
  типовых теста построены вокруг `.after`; наивная замена «удалить строку»
  снизила бы покрытие ответного тракта → Митигация: каждый `.after`-тест
  переписывается на эквивалент `.ok`/`.catch`, дополнительно добавляется
  тест на нюанс двойного вызова из решения 4 (он фиксирует поведение,
  на которое ссылается дока миграции).

- **[Breaking для внешних потребителей]** `.after` и `AfterUnitFn`
  исчезают из публичного API → Митигация: change идёт в breaking-окне
  волны 2 до фиксации публичного API V1; миграция — механическая, описана
  в проposal и в записи журнала. Асимметрия рисков в пользу удаления:
  вернуть `.after` позже — аддитивное изменение, убрать после релиза —
  breaking.

- **[Оставшиеся упоминания в доках]** `.after` упоминается в
  `history/` (immutable) и в архивных change'ах → Митигация: они не
  правятся по правилу «history immutable, архив — снимок на момент
  архивации»; проверка ограничивается живыми доками (`design/`, `guides/`,
  `preview/`, README пакетов) и `openspec/specs/`.

## Migration Plan

1. Рантайм и типы (`pipeline.ts`, `unit.ts`) — удаление метода, фазы,
   ветки применимости, типа; правка текста рантайм-ошибки.
2. Тесты пакета — переписывание `.after`-сценариев на `.ok`/`.catch`
   плюс новый тест на двойной вызов при броске.
3. Дельта-спеки `pipeline-phase-model` и `pipeline-composition`.
4. Доки: README и `TYPE-TESTS.md` пакета, гайд `http-functional.md`
   (таблица + плашка + дата), `roadmap.md` (статус #17); проверка
   `design/` и `preview/` на остаточные упоминания.
5. `yarn verify` + `yarn docs:audit` (0 ERROR).

Откат: change — чистое удаление в отдельной ветке `change/pipeline-drop-after`;
откат = revert коммитов ветки, поскольку никакие данные и никакие
внешние контракты не мигрируют.
