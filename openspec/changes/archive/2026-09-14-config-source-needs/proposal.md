## Why

Источник конфигурации не может взять свои координаты из другого источника.
`init()` вызывается без аргументов и по порядку списка привязок, а значит
источник, чей адрес и учётные данные лежат в `.env`, поднять нечем: к
моменту его `init()` читалка ещё не проецировала ни одной секции. Сценарий
«локально `.env`, на стендах Vault» из-за этого не пишется вовсе —
сетевого источника в репозитории нет ни одного.

Решение записано в
[ideas.md [2026-09-13]](../../../docs/decisions/ideas.md) «Конфигурация:
привязки на `run()`, `env()` и `dotenv()` умолчанием, `bind()`, `needs` у
источника», пункты 6–8. Change `config-run-bind` закрыл пункты 1–5 и 9–10;
пункты 6–8 остались строкой 92 roadmap. Целевое состояние уже описано в
[design/config.md §3](../../../docs/design/config.md) — код отстаёт от него
ровно на этот change.

## What Changes

- **`ConfigSource` получает поле `needs`** — DI-токен секции, значения
  которой источнику нужны для подъёма. Тип источника становится
  параметризованным: `ConfigSource<Needs>` объявляет `needs` и принимает
  проверенные значения секции аргументом `init(values)`.
- **BREAKING: `init()` принимает аргумент.** Источник без `needs`
  получает `undefined` и объявляет `init()` без параметров, как и раньше;
  сигнатура интерфейса меняется у всех реализаций.
- **Очерёдность подъёма выводится из `needs`, а не из порядка списка.**
  Порядок привязок остаётся приоритетом разрешения ключа и только им:
  Vault, стоящий в списке выше `.env`, поднимается после него, потому что
  берёт оттуда адрес.
- **Цикл в `needs` — отказ фазы 0 до всякого ввода-вывода**, с перечнем
  источников цикла в сообщении.
- **Секция `needs` проецируется из источников, поднятых раньше.**
  Зависимый источник свои `needs`-ключи не обслуживает, и после его
  подъёма секция не перепроецируется: значения этих ключей фиксируются в
  снимке в момент проекции.
- **Секция `needs`, не покрытая поднятыми источниками, — отказ фазы 0**
  с перечнем недостающих ключей. Отказ считается до `init()`, а не после
  неудачной валидации.
- **Новый пакет `@nestlingjs/config.vault`** с одним экспортируемым
  источником `vault(section, options?)` и секцией координат `VaultConfig`.
  Источник читает секрет KV v2 через `fetch`, представляется заголовком
  `X-Vault-Token` и повторяет запрос по опции `retries` — повтор остаётся заботой источника,
  как требует спека `config-bootstrap-snapshot`.
- **Прогон против живого Vault**: `docker-compose.yml` пакета поднимает
  Vault в dev-режиме, каталог `e2e` проверяет чтение, отсутствие секрета и
  отказ аутентификации. Без переменной `TEST_VAULT_ADDR` прогон
  пропускается, CI поднимает Vault сервисом.
- **Документация**: README пары нового пакета, строка в таблице пакетов
  `docs/README.md`, раздел рецепта `config-sources.md` про источник за
  координатами, уточнение примера опций `vault(...)` в `design/config.md`.

### Non-goals

- **Наблюдение за Vault.** `watch` у сетевого источника — опрос с
  перепроекцией reloadable-секций; в этот change он не входит и уходит
  записью в `deferred.md`.
- **Аутентификация AppRole, Kubernetes и AWS.** Минимальный источник
  ходит с заголовком `X-Vault-Token`; остальные способы добавляются опцией
  позже.
- **Динамические секреты и продление аренды.** Значение читается один раз
  на фазе 0 и живёт в снимке, как у любого источника.
- **`retries` в ядре.** Повторы принадлежат источнику: ядру нечем
  отличить временный отказ от постоянного, и спека уже это фиксирует.
- **`needs` у reloadable-секции.** Перепроекции секции координат нет, а
  reloadable обещает обратное — такое объявление отказывает.
- **Второй Vault в одном процессе.** Форма `vault(section)` его не
  запрещает, но сценарий не проверяется и в рецепт не идёт.

## Capabilities

### New Capabilities

- `config-source-needs`: зависимость источника от секции — поле `needs`,
  `init(values)`, топологическая очерёдность подъёма, отказ по циклу,
  отказ по непокрытой секции, правило «зависимый источник свои
  `needs`-ключи не обслуживает».
- `config-vault-package`: пакет `@nestlingjs/config.vault` — состав,
  `vault(section, options?)`, секция `VaultConfig`, чтение KV v2,
  аутентификация заголовком `X-Vault-Token`, повторы опцией `retries`.

### Modified Capabilities

- `config-sources-binding`: интерфейс `ConfigSource` дополняется полем
  `needs`, `init` принимает значения секции; порядок списка привязок
  объявляется приоритетом разрешения ключа, а не очерёдностью подъёма.
- `config-bootstrap-snapshot`: фаза 0 поднимает источники в порядке
  зависимостей; ключи секции `needs` попадают в снимок в момент её
  проекции и позже не перечитываются.

## Impact

- **Код**: `packages/nestling.app/src/config/` — `source.ts` (тип
  источника и `bind`), `reader.ts` (порядок подъёма, проекция секции
  `needs`, исключение зависимого источника из разрешения его ключей),
  `errors.ts` (отказы по циклу и по непокрытой секции), `project.ts`
  (проекция мимо графа для фазы 0); новый каталог
  `packages/nestling.config.vault`.
- **Зависимости**: у нового пакета — только `@nestlingjs/app` и схемы;
  клиент Vault не берётся, запросы идут штатным `fetch`.
- **CI**: сервис Vault и переменные `TEST_VAULT_ADDR`, `TEST_VAULT_TOKEN`
  в `.github/workflows/ci.yml`.
- **Документация**: `docs/design/config.md`, `docs/recipes/config-sources.md`,
  `docs/README.md`, README пара нового пакета, английские пары
  изменённых глав, `roadmap.md` и `ideas.md`.
- **Публикация**: первая публикация имени `@nestlingjs/config.vault`
  требует доверенного издателя на странице пакета в реестре. Это действие
  владельца, оно вне change'а.
