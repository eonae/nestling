## Context

Аудит документации уже умеет две вещи, на которых стоит этот change. Модуль
`scripts/package-exports.mjs` читает публичные имена пакета по барелям из
поля `exports`, разбирая исходники TypeScript compiler API, — ему не нужен
собранный `dist`. Инвариант `lang-parity` берёт состав публикуемого из
`scripts/site/sections.mjs`, а не из списка в скрипте. Обоим здесь находится
вторая работа.

Чего в аудите нет — сравнения текста с кодом по существу. Плашка «сверено с
кодом» сравнивает дату, а не содержание, и часы ей сбрасывает любое касание
файла. Сверка со сниппетами проверяет блоки, помеченные
`<!-- snippet: -->`, — проза и таблицы остаются вне.

Прототип проверки написан до этого документа, и числа ниже измерены, а не
предположены.

## Goals / Non-Goals

**Goals:**

- Инвариант ловит удалённое публичное имя в живом тексте и не даёт ложных
  находок на сегодняшнем состоянии репозитория.
- Список удалённых имён строится сам и не обнуляется выпуском.
- Состав проверяемых текстов растёт вместе с документацией без правки кода
  проверки.
- Прогон укладывается в время, за которое аудит уже работает.

**Non-Goals:**

- Ловить удалённые поля деклараций и сменившиеся формы вызова: `doc: { status }`
  и `build('users')` именем не экспортируются.
- Чинить скилл целиком: это change `agent-skill-upgrade` (строка 105).
- Вводить плашку свежести скиллу.

## Decisions

### 1. База сравнения — объединение по всем тегам, а не прошлый тег

Запись `ideas.md` говорит «разностью имён барелей между прошлым тегом и
`HEAD`». Так написано 14 сентября, когда прошлым тегом был `v0.2.0`. В тот же
день вышел `v0.3.0` — тот самый выпуск, чьи удаления и должна ловить проверка.
Измерено:

| База | Имён в базе | Удалённых | Находок |
|---|---|---|---|
| `v0.3.0` | 785 | **0** | 0 |
| `v0.2.0` | 676 | 39 | 4 |
| объединение `v0.1.1`…`v0.3.0` | 920 | 135 | 4 |

Прошлый тег обнуляет проверку ровно в момент, ради которого она заводится:
выпуск переносит тег вперёд, и устаревший текст перестаёт быть находкой, не
изменившись ни на строку. Объединение по всем тегам этого не делает. Цена —
имена постарше в списке; находок они не добавили ни одной.

Отвергнуто: «предпоследний тег». Сдвигает проблему на один выпуск, а не
убирает.

### 2. Дерево тега читается `git archive` во временный каталог

`collectPackageExports` читает с диска, и дереву тега нужен диск.
`git archive <tag> packages | tar -x` кладёт `packages/` во временный каталог
за 0.9 с на пять тегов (27 МБ). Рабочий каталог не переключается, рабочее
дерево не трогается.

Отвергнуто: `git worktree add`. Список worktree общий на репозиторий, и в нём
параллельно живут сессии других change'ей — аудит не должен туда писать.

Отвергнуто: чтение блобов через `git cat-file`. Пришлось бы повторить
резолвинг `exports` → `src` внутри дерева git, то есть второй экземпляр
логики, которая уже есть.

### 3. Имена тега кэшируются по SHA тега

Разбор пяти деревьев — 2.4 с, аудит сегодня идёт 3.1 с. Удвоение времени за
инвариант, который по большей части ничего не находит, — плохая сделка.

Тег неизменяем, поэтому список имён тега кэшируется файлом, имя которого
содержит SHA коммита тега. Кэш лежит в `node_modules/.cache/docs-audit/`:
каталог уже игнорируется git'ом и чистится вместе с зависимостями. Промах
кэша стоит полного прогона, попадание — чтения JSON.

### 4. Состав живых текстов — публикуемое минус `releases/`, плюс скилл и README репозитория

`SECTIONS` из `scripts/site/sections.mjs` перечисляет всё, что выходит на
сайт: главы, рецепты, design-доки, README пакетов, отдельные страницы корня
`docs/` и папку `docs/releases/`. Живой текст — это тот же список без
`releases/`: заметка о выпуске называет старое имя по своему назначению.

Скилл и README репозитория на сайт не выходят и добавляются двумя строками.

Выигрыш: новая глава, новый рецепт и новый пакет попадают под проверку сами.
Ровно так устроен `lang-parity`, и второго перечня файлов в аудите не
появляется.

### 5. Форма засчитывания: три шага сужения, измеренные на репозитории

Правило «имя в обратных кавычках или в блоке кода» из записи даёт 334
находки — почти все ложные. Сужение шло замерами:

| Правило | Находок | Что убрало |
|---|---|---|
| имя где угодно в инлайн-коде и в блоке кода | 334 | — |
| только форма использования | 20 | пути, адреса, локальные переменные, куски длинных имён |
| плюс три исключения | **4** | цитаты плашек, левая колонка таблицы перехода, имена секций |

Итоговое правило:

- в блоке кода — вызов `имя(`, дженерик `имя<`, спецификатор импорта из
  `@nestlingjs/*`;
- в прозе — только внутри фрагмента инлайн-кода: фрагмент целиком равен
  имени либо содержит имя вызовом или дженериком.

Одиночную форму в прозе пришлось оставить: две находки из четырёх — это
`` `load` `` без скобок в `design/config.md` и в английской паре. Она же даёт
почти весь шум, и его снимает исключение из решения 6.

Импорт засчитывается только из `@nestlingjs/*`. Без этого условия
`import { app, openapi } from './app.js'` в главе 13 — находка на локальную
переменную примера.

### 6. Исключение по хвосту имени сегодняшнего пакета

`openapi`, `inbox`, `outbox`, `subscriptions` — удалённые фабрики плагинов
(`makeOpenapi` и дальше по списку) и одновременно живые слова: имена секций
конфигурации и хвосты имён пакетов. Восемь ложных находок из двадцати дала
одна строка `docs/conventions.md`, перечисляющая имена секций.

Исключается одиночная форма у имени, которое совпадает с сегментом имени
сегодняшнего пакета. Форма вызова у таких имён засчитывается по-прежнему:
`` `outbox({ … })` `` — находка, `` `outbox` `` — нет.

Отвергнуто: список-исключение руками. Держать его пришлось бы синхронно с
пакетами.

Отвергнуто: «имя встречается в исходниках строковым литералом». Проверено на
девяти именах: `outbox` даёт 13 совпадений, `subscriptions` — ноль, а `load`
и `objectSource` дают ложные. Признак не разделяет.

### 7. Цитата и таблица перехода — два оставшихся исключения

Строка блоковой цитаты (`>`) пропускается целиком. Десять находок из
двадцати — плашки design-доков, цитирующие запись журнала: «HTTP-сервер как
ресурс: `httpServer({ name })`» [2026-09-06]. Плашка называет решение
прошлого, и это её работа.

В трёх файлах перехода с NestJS — `docs/from-nestjs.md`, английская пара и
`references/from-nest.md` скилла — у строки таблицы отбрасывается первая
ячейка. Там стоят имена чужого фреймворка: `ConfigModule` с опцией `load`
совпал с нашим удалённым `load` случайно. Отбрасывание ограничено этими
файлами: в остальных таблицах первая колонка несёт наши имена.

### 8. Находка — ERROR

Проверка встаёт инвариантом `deleted-names` в `check.mjs` и даёт ERROR:
`yarn docs:audit` завершается кодом 1, job документации в CI падает. Job уже
берёт историю целиком (`fetch-depth: 0`), и теги ему доступны.

Множество удалённых имён печатается отдельным вызовом скрипта — тем же
способом, каким `package-exports.mjs` печатает имена пакета. Без этого
разбираться с находкой пришлось бы вслепую.

### 9. Четыре находки чинятся здесь, а не откладываются

Инвариант не вводят красным. Две правки в `design/config.md` и его паре —
`load` больше не имя чтения фазы 0. Две в справочнике конфигурации
скилла — `load(RootConfig)` в прозе и `objectSource(…)` в блоке без языка.

Раздел «Sources» скилла целиком перепишет change 105, и обе правки он
перепишет вместе с ним. Здесь они делаются минимально — ровно чтобы имя
ушло.

## Risks / Trade-offs

**Change, удаляющий публичное имя, теперь обязан починить тексты в том же
change'е** → это и есть намерение: строка Definition of Done называет работу,
инвариант ловит пропуск. Цена реальна — удаление имени становится дороже на
проход по текстам.

**Ложная находка на будущем имени, совпавшем с английским словом** →
одиночная форма в прозе. Сегодня таких нет; рычаг сужения известен — снять
одиночную форму и оставить только вызов, потеряв две находки из четырёх.

**Время прогона растёт с числом тегов** → кэш по SHA тега. Тег неизменяем,
промах бывает один раз на тег.

**Клон без тегов** → WARN и пропуск. ERROR там был бы ложным: сравнивать не с
чем.

**Имя, удалённое и не встречавшееся в документации** → в множестве лежит
мёртвым весом. 135 имён — плоское множество строк, стоимости у него нет.

**Пересечение с change'ами 104 и 105** → оба правят те же файлы. Порядок
роадмапа ставит 109 после 105; при обратном порядке правки решения 9
конфликтуют со сплошной переписью раздела «Sources», и разрешается конфликт
в пользу 105.

## Migration Plan

Отката не требуется: change добавляет проверку и правит четыре строки
текста. Порядок работы — инвариант, затем починка находок, чтобы прогон до и
после был виден.
