## Context

`planInput` в `packages/nestling.openapi/src/input.ts` конвертирует схему
`input` один раз, с подсказкой `io: 'input'`, и раскладывает результат по
bind-карте. Одна и та же конвертированная схема служит трём целям: даёт
схемы параметров, даёт их обязательность и становится схемой
`requestBody` за вычетом вынесенных полей.

Для схемы без преобразований одного прогона достаточно: обе формы
совпадают. Для `z.stringbool()` они расходятся. На zod 4.2.1 прогоны дают
вот что:

| Схема поля | `io: 'input'` | `io: 'output'` |
|---|---|---|
| `z.stringbool()` | `type: 'string'` | `type: 'boolean'` |
| `z.coerce.number()` | `type: 'number'` | `type: 'number'` |
| `z.string().pipe(z.coerce.number().int())` | `type: 'string'` | `type: 'integer'` с `minimum` и `maximum` |
| `z.string().transform(Number)` | `type: 'string'` | ошибка «Transforms cannot be represented in JSON Schema» |
| `z.enum(['asc', 'desc'])` | `type: 'string'` с `enum` | `type: 'string'` с `enum` |

Ограничения, в которых нужно уместиться:

- Интроспекции схемы нет ([design/schemas.md](../../../docs/design/schemas.md)
  §1). Генератор видит только JSON Schema на выходе конвертера, поэтому
  конвертировать одно поле отдельно от остальных он не может.
- Конвертер вызывается с подсказкой на схему целиком. Одно поле с
  преобразованием роняет весь прогон `io: 'output'`.
- Диагностики построения тотальны и роняют сборку до открытия сокета
  ([openapi-document](../../../openspec/specs/openapi-document/spec.md)).
  Endpoint, который документируется сегодня, обязан документироваться и
  после change'а.
- Тело запроса описывается формой `io: 'input'`: в JSON `stringbool` и
  есть строка.

## Goals / Non-Goals

**Goals:**

- Параметр `in: 'query'` со схемой `z.stringbool()` несёт в документе
  `type: 'boolean'`.
- Правило не зависит от валидатора: оно сравнивает две JSON Schema.
- Endpoint, который документировался до change'а, документируется и
  после, с тем же набором диагностик.

**Non-Goals:**

- Схема `requestBody` и поля формы `multipart`. Они описываются входной
  формой.
- Массивы и объекты, полученные преобразованием из строки. Сериализация
  query им не соответствует.
- Строковые форматы разобранной формы (`format: 'date-time'`). Открытый
  вопрос 1 записи
  [ideas.md [2026-09-12]](../../../docs/decisions/ideas.md).

## Decisions

**Второй прогон живёт в `planInput`, выбор формы — в `planParameters`.**
Лист схемы и имя слота для диагностики есть только у `planInput`, и
второй прогон конвертера ставится рядом с первым. `planParameters`
получает третий аргумент — разобранный объект, `undefined` или объект со
свойствами, — и на каждое свойство решает, какую форму взять.

Альтернатива — конвертировать внутри `planParameters`, как сказано в
записи решения. Отвергнута: функции пришлось бы передать лист и слот,
то есть весь вход `planInput`, ради одного вызова.

**Второй прогон идёт только там, где есть что описывать.** Условие
считается до конвертации: разобрать вход удалось (`object` есть), и
bind-карта выносит хотя бы одно поле в путь или в query. Второе проверяет
предикат `takesParameters(binding)`: правило `rest === 'query'` либо
пометка с `in !== 'body'`. У endpoint'а с `rest: 'body'` и без пометок
второго прогона не будет.

Альтернатива — ленивое вычисление функцией-замыканием на случай, когда ни
одно свойство правилу не подошло. Отвергнута: предикат читается на месте,
а замыкание пришлось бы ещё и запоминать.

**Второй прогон пишет диагностики в отдельную копилку.** `convertLeaf`
при отказе конвертера добавляет диагностику и возвращает `undefined`.
Второму прогону такое поведение не нужно: отказ в направлении `output` —
штатная ситуация, а вход уже описан первым прогоном. Поэтому второй
прогон получает `{ ...context, diagnostics: new Diagnostics() }`, и всё,
что он скажет, остаётся в выброшенном экземпляре.

Альтернативы: флаг `quiet` в `ConvertContext` — поле, которое читает
ровно один вызывающий; свой `try`/`catch` вокруг `leafJsonSchema` — второе
место, знающее про отказы конвертера.

**Правило выбора сравнивает `type` двух свойств.** Схема параметра
берётся из разобранной формы, когда выполнено всё:

- свойство входной формы — объект JSON Schema с `type: 'string'`;
- свойство разобранной формы — объект JSON Schema с `type` из набора
  `'boolean'`, `'number'`, `'integer'`.

Условие на входную форму отсекает случаи, где расхождения нет
(`z.coerce.number()` строкой не описан) и где разобранная форма означала
бы другую сериализацию (массив или объект из преобразования). Условие на
разобранную форму отсекает `format` и `pattern`: они не меняют тип.

**Свойство переносится целиком.** Вместе с `type` приходят `description`,
`default` и ограничения разобранной формы. `z.string().pipe(z.coerce.number().int())`
даёт `type: 'integer'` с границами `minimum` и `maximum`.

Альтернатива — подставить во входное свойство один ключ `type`.
Отвергнута: у входного свойства могут быть строковые ограничения
(`minLength`, `pattern`), и с числовым `type` они образуют схему, которой
не соответствует ни одно значение.

**Обязательность и тело остаются от входной формы.** `required`
параметра говорит, обязан ли клиент прислать поле, а это свойство
запроса. Поле `taken` и вычитание из `requestBody` тоже считаются по
входной форме: набор свойств у двух форм может не совпадать, а тело
описывается только входной.

**Правило применяется ко всем трём путям `planParameters`** — пометке
`path`, пометке `query` и правилу `rest: 'query'`. У `query({ multiple: true })`
выбранное свойство становится `items` схемы-массива: схема элемента и есть
то, что правило уточняет.

## Risks / Trade-offs

- **Одно поле с преобразованием отменяет правило для всех параметров
  endpoint'а.** Прогон `io: 'output'` конвертирует схему целиком, и
  `z.string().transform(Number)` в теле запроса лишает разобранной формы
  и query-параметры. Смягчения в этом change'е нет: разбить прогон по
  полям нельзя без интроспекции схемы. Поведение при отказе — сегодняшнее,
  и сборка остаётся зелёной.
- **Второй вызов конвертера на endpoint.** Платят почти все endpoint'ы:
  path-параметр или `rest: 'query'` есть у большинства. Цена — один
  `z.toJSONSchema` на endpoint на фазе ASSEMBLE, до открытия сокета;
  в обработке запроса конвертер не участвует.
- **Документ существующих приложений меняется.** У поля со строковым
  входом и скалярным выходом параметр получает новый `type`. Публичное
  API не меняется, но потребитель, сверяющий документ снапшотом, увидит
  разницу.
- **`z.enum` остаётся строкой.** Обе формы дают `type: 'string'` с
  `enum`, и правило молчит. Это верно: по сети приходит одна из
  перечисленных строк.

## Migration Plan

Миграции для пользователя нет: код приложения не меняется. Внутри
репозитория меняются два места, которые читают документ:
`packages/nestling.openapi/src/document.spec.ts` и
`examples/app-with-http/src/app.spec.ts` — там появляются проверки типа
параметра.

## Open Questions

   без преобразования одинаков в обеих формах. Возвращаться к вопросу,
   если генераторы клиентов начнут терять `Date` — открытый вопрос 1
   записи решения.
