## Context

Приложение на Nestling сегодня подключает базу само. Соединение объявляется
ресурсом приложения, транзакция запроса собирается из двух юнитов пайплайна
руками, а адаптер `OutboxStore` пишется под свою базу. Это показывает
пример `users-service` и глава 27 гайда: код там разбирается как образец, но
переносится в новый сервис копированием.

Ядро драйвер не тянет по решению: запись
[ideas.md [2026-09-07]](../../../docs/decisions/ideas.md) «Транзакционный
outbox» назвала слой транзакции и адаптер хранилища работой сателлита,
потому что оба обязаны жить на одном соединении. Этот change пишет такой
сателлит.

Ограничения, в которых он пишется:

- **Транзакция — переменная контекста.** Форма `db.transaction(cb)` не
  подходит: значение живёт только внутри колбэка, а репозиторий и эмиттер
  читают его из контекста запроса.
- **Запись переменной делает `Var.provide(compute)`**, и зависимостей из
  контейнера эта функция не получает. Соединение приходит именно из
  контейнера, поэтому слой состоит минимум из двух юнитов.
- **Контейнер собирается синхронно**, ввода-вывода на фазе сборки нет.
  Открыть пул может только ресурс на фазе INIT.
- **Плагин не зависит от DI-токенов фичи.** Инфраструктура хранения — плагин,
  и проверка границы фич не даёт ей знать о бизнес-логике.
- **Тип схемы drizzle параметризует всё**, что пакет отдаёт наружу: значение
  соединения, значение транзакции, адаптер хранилища.

## Goals / Non-Goals

**Goals:**

- Несколько именованных соединений с PostgreSQL в одном процессе, каждое со
  своей конфиг-секцией, своим DI-токеном и своей пробой.
- Транзакция запроса одной строкой в композиции endpoint'а, с гарантией
  возврата соединения в пул на любом исходе.
- Типизация схемы drizzle от объявления соединения до вызова в репозитории.
- Готовый адаптер `OutboxStore`: приложение, которое ставит оба пакета, не
  пишет SQL outbox'а.
- Пакет собирается из публичных примитивов ядра; правок ядра change не несёт.

**Non-Goals:**

- MySQL, SQLite и драйверы без сессионных транзакций.
- Миграции из процесса приложения.
- Собственный query builder, репозиторий или маппер.
- Транзакция, охватывающая два соединения.
- Транзакция вокруг потокового ответа.

## Decisions

### 1. Отдельный пакет, диалект в имени

Пакет — `@nestlingjs/drizzle.pg`, каталог `packages/nestling.drizzle.pg`.
Диалект стоит в имени, потому что диалект стоит в коде: пакет открывает
транзакцию командой на соединении, выданном пулом `pg`, а выдача сессии у
каждого драйвера своя. Имя следует правилу транспортов
(`transport.http`, `transport.nats`), где вторая часть называет реализацию.

`drizzle-orm` и `pg` объявлены peer-зависимостями: версию драйвера выбирает
приложение, и двух копий `pg` в процессе быть не должно.

**Альтернативы:** имя `@nestlingjs/drizzle` с диалектом внутри — отложено до
второго диалекта, иначе имя обещает больше, чем пакет умеет. Общий интерфейс
драйвера с одной реализацией — абстракция без второго потребителя, проверить
её нечем.

### 2. Соединение объявляется значением

`drizzlePg(options)` возвращает плагин, который несёт собственные DI-токены:

```typescript
export const db = drizzlePg({ schema });
export const analytics = drizzlePg({ name: 'analytics', schema: analyticsSchema });

export const app = makeApp({
  features: [UsersFeature],
  plugins: [db, analytics],
  config: [[dotenv('.env'), db.keys], [dotenv('.env'), analytics.keys]],
  transports: [http()],
});
```

Несколько соединений — несколько вызовов. DI-токен, переменная транзакции и
слой создаются внутри вызова, поэтому тип схемы у каждого соединения свой и
доходит до места использования.

**Альтернативы:** глобальное семейство `Db$('analytics')` — член семейства
несёт один тип значения на всё семейство, и тип схемы был бы потерян.
Один плагин со списком `connections: [...]` — список пришлось бы разбирать
по индексу, а типы соединений сложились бы в объединение.

### 3. Конфиг-секция — член семейства по имени соединения

```typescript
const DatabaseConfig = makeConfig.family('database', {
  url: secret(str()),
  poolMax: int(10, 1),
  connectTimeoutMs: int(5000, 0),
  idleTimeoutMs: int(10_000, 0),
  statementTimeoutMs: int(0, 0),
  ssl: flag(false),
});
```

Соединение по умолчанию читает `DATABASE_URL`, `DATABASE_POOL_MAX` и так
далее; `name: 'analytics'` читает `DATABASE_ANALYTICS_URL`. Правило вставки
имени — то же, что у HTTP-сервера, и задаёт его ядро.

Наружу уходит только `db.keys`: DI-токен секции остаётся приватным, как у
транспортов и у outbox'а. Схемы объявлены минимальными
Standard-Schema-значениями пакета, поэтому зависимости от zod у пакета нет.

Адрес помечен `secret()`; вычисляемое поле `host` наследует секретность и
служит логу подключения.

### 4. Пул — ресурс с пробой

Соединение объявляется `resourceProvider`-определением внутри фабрики:
`acquire` создаёт `Pool`, проверяет его первым запросом и возвращает
значение `PgConnection<S>`; `release` закрывает пул; `health` выполняет
`SELECT 1` с сигналом.

Проба заводится автоматически: контейнер перечисляет ресурсы с `health`, а
сборка приложения делает из них членов `HealthCheck$`. Имя проверки равно
идентификатору DI-токена, поэтому в `/readyz` соединения видны как
`database` и `database:analytics`.

`PgConnection<S>` несёт два члена: `db` — экземпляр drizzle на пуле, для
чтения вне транзакции, и `begin(options)` — выдача сессии с открытой
транзакцией.

### 5. Транзакция открывается командой на соединении из пула

```typescript
async begin(options: BeginOptions = {}): Promise<PgSession<S>> {
  const client = await this.pool.connect();

  try {
    await client.query(beginCommand(options));
  } catch (error) {
    client.release();
    throw error;
  }

  return new PgSession(drizzle(client, { schema: this.schema }), client);
}
```

`PgSession` держит клиента и состояние. `commit()` шлёт `COMMIT`,
`rollback()` — `ROLLBACK`, `release()` откатывает незавершённую транзакцию и
возвращает клиента в пул. Все три идемпотентны: повтор на завершённой сессии
ничего не делает. Уровень изоляции задаёт аргумент слоя и превращается в
`BEGIN ISOLATION LEVEL …`.

**Альтернатива — мост поверх `db.transaction(cb)`.** Колбэк drizzle пришлось
бы держать незавершённым весь запрос и завершать его отложенным промисом.
Цена: соединение остаётся занятым, пока кто-то не взведёт сигнал, потерянный
сигнал исчерпывает пул, а стек ошибки идёт через внутренности drizzle.
Выигрыш — независимость от драйвера — при охвате «только pg» сводится к
одному вызову `pool.connect()`.

### 6. Слой транзакции — юнит-мост, писатель переменной и ответная фаза

```typescript
export const transactional = compose(authed, db.transaction());
```

Внутри `db.transaction(options?)` собирается пайплайн из четырёх частей:

1. `.pre` класса-моста: он получает соединение из контейнера, зовёт
   `begin(options)` и кладёт сессию в контекст под своим ключом.
2. `.pre` писателя переменной: `Tx.provide((ctx) => ctx.input[sessionKey].db)`.
3. `.ok`: `commit()`. Провал коммита бросает, и ответ становится внутренней
   ошибкой.
4. `.catch`: `rollback()`. `.finally`: `release()` — возврат клиента в пул на
   любом исходе, включая обрыв соединения с клиентом и остановку приложения.

Мост нужен потому, что `Var.provide(compute)` не получает зависимостей из
контейнера. Класс объявляется в теле фабрики, рядом с DI-токеном соединения,
и виден только ей.

Сессия попадает в контекст под ключом `tx` + `Session` с приставкой имени:
`txSession` у соединения по умолчанию, `analyticsTxSession` у именованного.
Ключ переменной выводится так же: `tx` и `analyticsTx`. Правило
детерминированное и записано в документации, поэтому два соединения не
спорят за одно поле контекста, а конфликт ключей проверяет компилятор в
точке композиции.

### 7. Значение переменной — экземпляр drizzle

`db.tx` несёт не обёртку, а сам экземпляр drizzle, привязанный к
транзакции. Репозиторий пишет обычный запрос:

```typescript
@Component([db.connection, Ctx(db.tx)])
export class DbUsersRepository implements UsersRepository {
  constructor(
    private readonly connection: PgConnection<typeof schema>,
    private readonly tx: CtxReader<PgTx<typeof schema>>,
  ) {}

  async list(limit: number): Promise<User[]> {
    return this.connection.db.select().from(users).limit(limit);
  }

  async insert(data: Omit<User, 'id'>): Promise<User> {
    const [row] = await this.tx.get().insert(users).values(data).returning();

    return row;
  }
}
```

Читающий метод берёт соединение из пула, изменяющий — транзакцию запроса.
`get()` не допускает отсутствия значения: запись вне транзакции падает.

**Альтернатива:** класс-обёртка с полем `db` и методами `commit`/`rollback`.
Она дала бы репозиторию доступ к коммиту, а решение о коммите принадлежит
слою, а не репозиторию.

### 8. Политика предпосылки

`db.requiresTransaction(filter?, label?)` возвращает `everyEndpoint(filter)
.hasVar(db.tx)`. Endpoint под фильтром, не композированный от слоя,
останавливает сборку на фазе ASSEMBLE. Та же форма, что у
`appOutbox.requiresTransaction`, и та же причина: какие endpoint'ы обязаны
быть в транзакции, знает приложение.

### 9. Адаптер хранилища outbox'а — подпуть и необязательная peer-зависимость

Адаптер живёт в подпуте `@nestlingjs/drizzle.pg/outbox`; `@nestlingjs/outbox`
объявлен необязательной peer-зависимостью. Приложение без outbox'а ставит
пакет и о хранилище не знает; приложение с outbox'ом получает готовый
адаптер.

```typescript
export const outboxStore = pgOutboxStore(db);

export const appOutbox = outbox({
  transaction: db.tx,
  store: outboxStore.token,
  operations: [UserCreated],
  partitionKey: (payload) => (payload as { id: string }).id,
});
```

`append(transaction, records)` приводит непрозрачное значение к экземпляру
drizzle и вставляет записи им, поэтому строка события и строка пользователя
коммитятся вместе. Значение не той формы даёт ошибку с текстом, называющим
обе починки. `claim` и `settle` работают на пуле: relay живёт вне запроса и
транзакции не имеет.

**Альтернатива:** отдельный пакет `@nestlingjs/drizzle.pg.outbox` по образцу
`openapi.zod`. Для одного файла адаптера это лишний манифест, лишний
README и лишняя строка релиза.

### 10. Таблица записей: объявление drizzle и константа DDL

Пакет отдаёт таблицу объявлением drizzle (`outboxTable(name?)`) и её DDL
строкой (`outboxDdl(name?)`). Обе формы живут в отдельном листовом подпуте
`@nestlingjs/drizzle.pg/outbox/table` с условием экспорта `default`:
схему читает drizzle-kit, а он резолвит её по-cjs'ному, и подпуть, который
тянет за собой ядро, ему не годится. Подпуть `./outbox` те же имена
реэкспортирует. Объявление приложение включает в свою схему
drizzle-kit, и миграция генерируется вместе с остальными; константа нужна
тем, кто ведёт миграции руками. Это закрывает открытый вопрос записи об
outbox'е про DDL таблицы: форму таблицы задаёт тот, кто её читает.

Колонки: `id` (text, первичный ключ, он же ключ идемпотентности), `seq`
(bigserial, порядок создания), `subject`, `payload` (jsonb), `durable`,
`partition_key`, `context` (jsonb), `state`, `attempts`, `available_at`,
`created_at`, `claimed_at`, `published_at`. Индексы: по `state` и
`available_at` для выдачи, по `partition_key` и `seq` для порядка раздела.

### 11. Выдача партии держит порядок раздела

`claim` выполняет один `UPDATE … FROM (SELECT … FOR UPDATE SKIP LOCKED)
RETURNING *`. Кандидат берётся, если он ожидает публикации, его
`available_at` не в будущем и в его разделе нет ни более ранней ожидающей
записи, ни записи, уже взятой в работу. `SKIP LOCKED` не даёт двум репликам
взять одну строку, а условие раздела не даёт обгона внутри раздела —
семантика совпадает с `InMemoryOutboxStore`, на котором написаны тесты
пакета outbox'а.

`settle` применяет исходы одним `UPDATE … WHERE id = ANY(...)` по каждому
статусу и идемпотентен: исход применяется только к записи, взятой в работу.

### 12. Тесты: юниты на фейковом пуле, e2e на настоящей базе

Юнит-тесты подставляют объект с методами `connect`, `query`, `release` и
`end` и проверяют порядок команд: `BEGIN` до хендлера, `COMMIT` на успехе,
`ROLLBACK` на отказе, возврат клиента в пул на любом исходе, идемпотентность
повторного завершения.

Тесты, которым нужен настоящий PostgreSQL, живут в `e2e/` пакета и
пропускаются без `DATABASE_URL`: `yarn verify` остаётся зелёным на машине
без базы. Они проверяют то, что фейком не проверяется, — конкурентную выдачу
двумя репликами, `SKIP LOCKED`, изоляцию и видимость записи внутри
транзакции. CI поднимает PostgreSQL сервисом и задаёт `DATABASE_URL`.

### 13. Пример переезжает на настоящую базу

`users-service` переходит с таблицы в памяти на PostgreSQL: схема drizzle,
миграции drizzle-kit, `docker-compose.yml`, скрипты `db:up` и `db:migrate`.
Спеки примера, которым нужна база, получают тот же пропуск без
`DATABASE_URL`. Глава 27 гайда переписывается на этот код; часть «Что
осталось за кадром» про адаптер уходит.

## Замер границы ядра

Пакет собирается из публичных примитивов, и `git diff` по kernel-пакетам у
change'а пуст. Места, в которые он упёрся, фиксируются тестами
`core-limits.spec.ts` пакета и не чинятся здесь:

1. **`Var.provide(compute)` не получает зависимостей из контейнера.**
   Второй потребитель той же находки после outbox'а. Цена та же — один
   юнит-мост, — но теперь мост объявляется внутри фабрики, потому что
   DI-токен соединения создаётся там же. Функциональной формы юнита со
   списком зависимостей у пайплайна нет. Находка №1 change'а 57
   `kernel-boundary-outbox` получает второй пример.
2. **`.ok`-юнит не превращает успех в объявленный отказ.** Провалившийся
   `COMMIT` — ровно этот случай: изменение не сохранено, а ответ уже
   успешен. Юнит бросает, и ответ становится внутренней ошибкой, хотя
   честнее был бы `CONFLICT` с деталями сериализации.
3. **Ресурс не публикует фактов жизненного цикла.** Открытие и закрытие
   пула видны только в логе; операции вроде `outbox.published` у ресурсов
   нет, поэтому подписаться на разрыв соединения нечем.
4. **`.pre` не принимает юнит, ключ добавки которого — параметр типа.**
   Находка реализации. Проверка юнита сводит добавку через `Awaited` и
   `Exclude`, а шаблонный ключ от параметра типа (`${N}Tx`) не сводится, и
   верный юнит не проходит по типу. Поэтому слой собирается на литеральных
   ключах, а имя экземпляра подставляет объявленный тип слоя; место
   зафиксировано в `plugin.type-test.ts`.

## Risks / Trade-offs

- **Транзакция вокруг потокового ответа.** `.ok` выполняется до отдачи
  потока, поэтому `COMMIT` уйдёт раньше, чем хендлер дочитает курсор →
  слой не применяется к `stream` и `events`; ограничение записано в
  документации, а политика `requiresTransaction` касается изменяющих
  endpoint'ов.
- **Долгая транзакция держит соединение пула.** Соединений столько, сколько
  задано `poolMax`, и медленный хендлер блокирует остальные →
  `statementTimeoutMs` выставляется на сессии, а слой возвращает клиента в
  `.finally` при любом исходе, включая отмену запроса.
- **Два соединения в одном запросе не дают общей транзакции.** Приложение
  может открыть слои обоих соединений и получить два независимых коммита →
  документация называет это прямо, а согласованность между базами остаётся
  за событиями и outbox'ом.
- **`yarn verify` не проверяет SQL без базы.** Юнит-тесты на фейке не ловят
  ошибку в тексте запроса → SQL проверяется e2e-тестами в CI, и они
  обязательны для ветки change'а.
- **Peer-зависимости расходятся по версиям.** `drizzle-orm` меняет типы
  между минорными версиями → диапазон peer-зависимости узкий, а
  type-тесты пакета проверяют типизацию схемы.
- **Утечка секрета в лог.** Адрес базы содержит пароль → поле помечено
  `secret()`, а лог подключения пишет вычисляемый `host`.

## Migration Plan

1. Пакет добавляется как новый: существующие приложения не затрагиваются.
2. Пример `users-service` переводится целиком в одном change'е — параллельно
   две реализации хранения в нём не живут.
3. Откат — снятие пакета из `plugins:` и возврат прежнего `persistence.ts`;
   ветка change'а до архивации остаётся отдельной.

## Open Questions

- Нужен ли слой только для чтения (`access: 'read only'`) отдельным
  аргументом: он полезен на реплике, но без второго соединения в примере
  проверить его нечем.
- Ставить ли `application_name` соединения из имени приложения: имя корня
  пакету не видно, и его пришлось бы принимать опцией.
- Стоит ли пакету отдавать готовый вклад `HealthCheck$` с запросом
  приложения вместо `SELECT 1`: проба ресурса проверяет живость пула, а не
  доступность схемы.
