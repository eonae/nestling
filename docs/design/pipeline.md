## 1. Модель: плоские фазы

Пайплайн — последовательность юнитов вокруг хендлера. Юниты делятся на
четыре вида по моменту выполнения, и декларация читается сверху вниз как
план исполнения. Вложенных обёрток и `next()` нет: у каждого юнита ровно
одна точка выполнения, и она видна из имени метода.

Пайплайн объявляется билдером `makePipeline()`. Билдер иммутабелен: каждый
метод возвращает новый пайплайн.

| Метод | Роль | Когда | ctx |
|---|---|---|---|
| `.pre(u)` | препроцессор | до хендлера, по порядку объявления | накопленный, полный |
| `.ok(u)` | постпроцессор | ответ = `Ok` | **полный** (свой слой + внешние) |
| `.catch(u)` | обработчик ошибок | ответ = `Fail` | свой слой `Partial`, внешние полные |
| `.finally(u)` | наблюдатель исхода | всегда, последним | как `.catch` + `outcome` |

Имена методов совпадают с методами Promise: `ok`, `catch`, `finally`.
Метода `.then` у пайплайна нет: объект с методом `then` становится
thenable, и `await pipeline` попытался бы его разрешить.

Отдельных понятий «middleware», «обёртка» и «exception filter» в
пайплайне нет. Транзакция записывается тремя явными юнитами: `.pre`
открывает её, `.ok` подтверждает, `.catch` откатывает. Централизованное
преобразование ошибок — обычный `.catch`-юнит.

## 2. Исполнение одного слоя

`.pre`-юниты выполняются по порядку объявления. Каждый из них дополняет
контекст типизированными полями; контекст только растёт, поля не
удаляются и не меняют тип. Юнит завершается одним из двух способов: он
возвращает добавку к контексту или возвращает отказ из списка `errors`,
объявленного при его подключении (§3). Возвращённый отказ рантайм узнаёт
по `isFail` до того, как положить результат в контекст: хендлер не
вызывается, и пайплайн сразу переходит к ответной фазе с этим `Fail`.
Отказ, брошенный из юнита, обрабатывается так же.

Хендлер выполняется, когда все `.pre`-юниты прошли. Отказ, который
хендлер вернул, обрабатывается так же, как отказ, который он бросил:
`throw` — только способ доставить значение `Fail`, а не другая семантика
([errors.md](./errors.md)).

После хендлера выполняются юниты `.ok` и `.catch`. Они образуют один
список в порядке объявления. Перед каждым юнитом рантайм смотрит на
текущий ответ: для успеха выполняются `.ok`-юниты, для ошибки —
`.catch`-юниты, остальные пропускаются. Юнит может изменить ответ. Если
`.ok`-юнит бросил исключение, ответ становится ошибкой, и дальше по списку
срабатывают уже `.catch`-юниты. `.catch`-юнит может вернуть просто `Fail`,
не собирая `ErrorResponseContext` вручную: рантайм обработает его так же,
как `Fail`, возвращённый хендлером.

Когда список пройден, рантайм сверяет ответ с эффективным множеством
отказов endpoint'а: `errors:` декларации, отказы, объявленные слоями его
пайплайна (§3), и отказы ядра ([errors.md §4](./errors.md)). Ошибка с
кодом, которого там нет, заменяется на `InternalError`. Проверка
стоит после `.catch`, потому что именно в `.catch` незадекларированную
ошибку можно превратить в задекларированную, и до `.finally`, чтобы
`.finally` видел тот ответ, который действительно уйдёт клиенту.

`.finally`-юниты выполняются последними и получают исход запроса:
`completed`, `disconnected`, `aborted` или `failed`.

**Момент `.finally` зависит от формы `output`.** У endpoint'а с обычным,
не потоковым выходом `.finally` вызывается сразу после ответной фазы. У
потокового (`stream`, `events`) исход известен только после доставки,
поэтому `.finally` откладывается до завершения потока: поток дочитан до
конца, оборвался ошибкой или закрыт потребителем. Пайплайн отдаёт
транспорту итератор-обёртку, и закрытие этой обёртки выполняет `.finally`
ровно один раз. Отсюда обязанность транспорта: потребить итератор или
закрыть его ([transports.md](./transports.md)). Выходная item-цепочка и
поэлементная валидация выхода применяются в том же месте, при
нормализации ответа ([streaming.md](./streaming.md)).

Билдер следит за порядком методов: после первого `.ok`, `.catch` или
`.finally` метод `.pre` недоступен в типах. Поэтому порядок чтения
декларации всегда совпадает с порядком исполнения.

### `ctx.summary`

`ctx.summary` — итог запроса для наблюдателей: `itemsIn` и `itemsOut`
(считает рантайм item-цепочек), `bytesIn` и `bytesOut` (заполняет
транспорт, если знает их). Ссылка read-only; значения актуальны на момент
чтения. Поле есть у любого endpoint'а: у не потокового счётчики остаются
нулями, так что наблюдателю не нужно проверять форму выхода. `summary`
лежит в контексте, а не передаётся отдельным аргументом `.finally`,
потому что нужен и `.ok`-юнитам.

## 3. Слои и `compose`

Один вызов `makePipeline()` с цепочкой методов определяет один слой.
Пайплайн endpoint'а — стек слоёв, который собирает функция `compose` из
констант:

```typescript
export const base = makePipeline().pre(withRequestId()).finally(audit);
export const authed = compose(
  base,
  makePipeline().pre(withIdentity()),
);
// у endpoint'а: pipeline: compose(authed, makePipeline<{ identity: User }>().pre(...))
```

- `compose(outer, ..., inner)` принимает список слоёв. Он читается сверху
  вниз как «снаружи внутрь»; в том же порядке слои показывает `explain()`.
- `.pre`-юниты выполняются снаружи внутрь, ответные юниты и `.finally` —
  изнутри наружу.
- Слой выполняется, только если `.pre`-юниты всех внешних слоёв прошли.
  Поэтому ответные юниты слоя видят контекст внешних слоёв полным;
  `Partial` остаётся только для `.pre` собственного слоя.
- Требования слоя к внешнему контексту объявляются явно, тип-параметром:
  `makePipeline<{ identity: User }>()`. Компилятор проверяет их в точке
  композиции.
- Пайплайн подключается только в декларации endpoint'а; уровней App или
  модуля нет. Переиспользуются экспортируемые константы и фабрики
  (`authedWith(verifyFn)`). Модуль с endpoint'ами принимает пайплайн
  параметром фабрики, и тип параметра описывает требуемый контекст.

### Отказы слоя

Отказ, которым может завершиться pre-юнит, объявляется при подключении
юнита:

```typescript
export const authed = compose(
  observability,
  makePipeline().pre(Authenticate, { errors: [Unauthorized] }),
);
```

- Второй аргумент `.pre` — список определений `makeFail`. Юнит возвращает
  отказ из этого списка значением, как хендлер возвращает отказ из
  `errors:`. Возвращённый отказ вне списка — ошибка компиляции в точке
  `.pre`. Отказы ядра допустимы без объявления.
- Пайплайн несёт объявленные отказы в типе, параметром `TFails`, и в
  значении, рядом с множеством объявленных переменных. Правила те же:
  `compose` объединяет, `bind` и деривация билдера сохраняют.
- Декларация endpoint'а складывает эффективное множество отказов из
  своего `errors:` и отказов пайплайна. Оно входит в тип хендлера, в
  `EndpointMeta` для проверки на границе и в документ OpenAPI. Хендлер
  может вернуть отказ, объявленный слоем.
- В форме с операцией (`httpEndpoint({ operation, pipeline })`,
  `implement(Operation, { pipeline })`) отказы пайплайна обязаны входить в
  `errors:` операции: операция описывает всё, что получит клиент.
  Нарушение — ошибка компиляции в точке декларации в формате §4 с
  подсказкой добавить определение в операцию. Та же проверка выполняется
  на фазе ASSEMBLE.
- Отказ, брошенный из юнита или из глубины вызовов, компилятор не видит.
  Он обязан быть объявлен слоем или endpoint'ом, иначе граница заменяет
  его на `InternalError`.

## 4. Типизация

Тип контекста в ответной фазе учитывает, что `.pre`-юниты могли не
выполниться: у `.catch` и `.finally` собственный слой контекста — `Partial`.
У `.ok`-юнитов гарантия сильнее. Успех приходит только из хендлера, а
хендлер выполняется только после всех `.pre`, поэтому контекст у `.ok`
полный.

На этой гарантии держатся два ограничения V1: нет раннего успешного выхода
из `.pre` (gate для кэша или идемпотентности) и нет восстановления `Fail`
в `Ok` внутри `.catch`. Оба сделали бы успех возможным без прохода всех
`.pre`, и полный контекст у `.ok` перестал бы быть гарантией.

### Диагностика типов

Диагностика типов — часть API. При нарушении требований слоя тип параметра
`compose` схлопывается в читаемый литерал:
`{ __error: '…'; missing: { identity: User } }`. Первая строка ошибки
компилятора называет проблему, а не трассировку дженериков. `missing` —
рекорд из имён полей и их типов. В него попадают и поля, которых внешние
слои не дают, и поля, которые они дают с несовместимым типом. Форма литерала одна во всех точках проверки: в
`compose`, в цепочке `.pre` (там второй случай описывает рекорд
`conflicting`, где значение — пара «было, стало») и в слоте `pipeline`
транспортной декларации (там литерал дополнен полем `hint` с конкретным
действием). В неуспешной ветке параметр — только
литерал ошибки, без пересечения с типом слоя.

Тексты диагностик фиксируются snapshot-тестами по каталогу фикстур с
заведомо неправильными композициями. Стоимость типов ограничена бюджетом,
который проверяется вместе с остальным репозиторием: детерминированные
счётчики компилятора (`Instantiations`, `Types` — дельтой к пустой базе)
с жёстким порогом и латентность реального tsserver с широким потолком.
Граф из ~50 вложенных слоёв компилируется без `TS2589`.

## 5. Формы юнитов и `TNeeds`

| Форма | TNeeds | Использование |
|---|---|---|
| функция | — | базовый случай |
| инстанс (`new WithTracing(...)`) | — | мост: класс без DI |
| класс (`WithTracing`) | +Constructor | App резолвит из контейнера на старте |
| токен (`RateLimit('strict')`) | +Token | конфигурируемые юниты через token families |

`TNeeds` — второй тип-параметр пайплайна. В нём накапливаются
зависимости, которые пайплайн получит позже: классы и токены юнитов. У
пайплайна без таких юнитов `TNeeds` равен `never` (`Pipeline<…, never>`).
Standalone-транспорты принимают только такой пайплайн; `run()` резолвит
`TNeeds` контейнером при старте. Без контейнера зависимости подставляются
вручную: `pipeline.resolve([[Class, instance]])`. Отказы, объявленные при
подключении юнитов, накапливаются в отдельном тип-параметре `TFails` (§3).

Юнит — синглтон. Состояние одного запроса живёт только в контексте.

## 6. Границы пайплайна

- **Пайплайн работает со значениями, транспорт — с байтами**
  ([transports.md](./transports.md)). Сжатие, CORS и content negotiation
  — не юниты.
- Ответная фаза не меняет тип значения ответа: output-схема описывает то,
  что уходит по сети. Общий конверт вида `{data, meta}` — часть схемы или
  опция сериализации транспорта, а не юнит.
- Retry и timeout — декларативные опции endpoint'а, которые исполняет
  оркестратор, а не юниты-обёртки. Опция видна в метаданных, документации
  и визуализации.
- Логика на уровне элемента потока (валидация элементов, лимиты,
  таймауты) — item-цепочки на io-декларации, а не юниты запроса. У потоков
  два разных скоупа обработки: соединение и элемент
  ([streaming.md](./streaming.md)).

## 7. Интроспекция и policy-check

`pipeline.explain()` печатает план исполнения: дерево фаз и слоёв с
аннотациями накопления контекста (`→ {identity: User}`). Он служит для
отладки, документации и визуализации графа.

Policy-check проверяет сквозные инварианты на собранном графе. Инвариант
вида «каждый HTTP-endpoint защищён» не выражается типами хендлера, поэтому
объявляется в composition root и проверяется на фазе ASSEMBLE, когда все
значения уже созданы:

```typescript
makeApp({
  policies: [
    everyEndpoint({ transport: HttpTransport$ }).hasLayer(authedBase, 'authedBase'),
  ],
  /* ... */
})
```

- **Фильтр** — два необязательных поля, которые сужают множество
  endpoint'ов совместно. `transport` — токен транспорта (`HttpTransport$`,
  а не провайдер `http()`); сравнение по ссылке. `pattern` — `RegExp` по
  строке `endpoint.pattern` (`'POST /api/users'`); строка вместо `RegExp`
  не принимается. Пустой фильтр означает все endpoint'ы приложения.
- Предикатов в V1 два. `hasLayer(layer, label?)` — пайплайн endpoint'а
  композирован от этого слоя. `hasVar(variable, label?)` — пайплайн
  объявил эту ambient-переменную ([container.md](./container.md)).
  Объявителем переменной считается `.pre`-юнит формы `<Var>.provide(…)`;
  множество объявленных переменных хранится на пайплайне рядом с
  провенансом и ведёт себя так же: `compose` объединяет, деривация билдера
  и `bind` сохраняют. Юнит, который кладёт то же поле в контекст вручную,
  предикат не удовлетворяет: сборка упадёт, а починка занимает одну
  строку.
- Слой идентифицируется по ссылке на значение, а не по имени. Для этого
  пайплайн хранит провенанс композиции — ссылки на значения, из которых он
  получен (`compose` хранит свои аргументы, деривация билдера и `bind` —
  предшественника). `hasLayer` обходит этот DAG и сравнивает ссылки.
  Поэтому `compose(base, authed)` содержит оба слоя, вложенная композиция
  транзитивна, а `authed.pre(x)` по-прежнему содержит `authed`.
- Метка слоя — второй, необязательный аргумент `hasLayer(layer, label)`.
  Она используется только в тексте нарушения. Автоматически имя не
  выводится: ни из переменной, ни из `Function.name`, ни из стека.
- Endpoint без `pipeline` нарушает любую политику, под которую попал: для
  инварианта «endpoint защищён» отсутствие пайплайна и отсутствие слоя
  неразличимы.
- Диагностика агрегированная. Выполняются все политики, нарушения
  группируются по политике. Сообщение называет число нарушений, описание
  политики, паттерн, транспорт и модуль каждого endpoint'а и обе починки:
  композировать слой или пометить `detached`.
- Исключение из проверок — `detached: '<причина>'` в декларации
  endpoint'а. Строка обязательна и непуста (`detached: true` не
  компилируется). Исключение полное: endpoint выпадает из всех политик.
  `run()` печатает список таких endpoint'ов с причинами при старте, а
  `check()` возвращает их в отчёте.
- Политики выполняются в `run()`, в `check()` и в
  тестовом корне `assembleTest`. Это последняя проверка фазы: после сверки
  транспортов и форм io и до `@OnInit`. В CI политики прогоняются
  `.check()`-матрицей топологий ([testing.md](./testing.md)).
- ESLint-правило `endpoint-has-layer` из `@nestling/eslint-plugin`
  (уровень `warn`) подсказывает в редакторе простые случаи. Гарантию даёт
  policy-check: пайплайны — значения, они проходят через фабрики и
  параметры, и в точке объявления статически не проверяются.
- Предикат — значение типа `Policy` с методами `describe()` и
  `check(subjects)`. Тот же механизм проверяет присутствие
  ambient-переменных (`hasVar`, [container.md](./container.md),
  «Асинхронный контекст») и инварианты инфра-модулей вроде «каждый endpoint
  композирован от слоя наблюдаемости» ([composition.md §5](./composition.md)).
  Новый предикат не требует ни второго прохода по discovery, ни нового поля
  в корне. И `hasVar`, и `hasLayer` опираются на состояние, накопленное
  пайплайном при композиции, а не на интроспекцию графа. Вывод требования
  из достижимости `Ctx(X)` в V1 не входит (см. запись журнала).
