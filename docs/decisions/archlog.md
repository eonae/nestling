[01.09.2026] Модуль без exports: поле и опция strictExports удалены (remove-module-exports).

Первый change после закрытия волны 6 — не новая способность, а снятие
механизма. `Module.exports` и `ContainerBuilder({ strictExports })` удалены из
`@nestling/container` целиком: шагов сборки в `build()` стало десять вместо
одиннадцати, а узел графа потерял `metadata.exported` — вычислять флаг больше
не из чего. `metadata.module` остался: атрибуция провайдера к модулю не
менялась.

Причина — роль модуля. Модуль в Nestling метит принадлежность провайдеров и
пакует их в единицу; границу держат ES-модули и границы пакетов. Проверка
`strictExports` смотрела только рёбра готового графа: мимо неё проходили типы
в `.d.ts`, создание класса через `new` в обход контейнера, подстановки
`overrides` в тестах и чтение чужого ключа через `Config(key)`. Включить её
там, где собирают приложение, было нельзя — `assemble()` опцию не принимал.
Примеры объявляли `exports` в каждом модуле, а проверяла их ноль сборок:
конвенция вместо гарантии, ровно то, что запрещает принцип guarantee over
convention.

Вклад в семейство теперь объявляется одним провайдером:
`classProvider(IHealthCheck('db'), DbHealthCheck)` в `providers` модуля — полная
форма записи, а узел-агрегат `Family.all` собирает всех зарегистрированных
членов независимо от модулей. BREAKING: `exports` в модуле и `strictExports` в
опциях билдера стали неизвестными полями, замены им нет. Дельта-спеки влиты:
спека `strict-exports` удалена целиком, из `container-module-attribution`
и `multi-injection` сняты требования про экспортированность. См. change
`remove-module-exports` и запись [2026-09-01] в ideas.md.

[01.08.2026] Реестр подписок: замер удался, ядро пусто в диффе, четыре находки — не дыры в примитивах (subscriptions-registry).

Change #7 — последний в roadmap и единственный, чей продукт не столько код,
сколько **измерение** тезиса [«Kernel 1.0», п. 1](./ideas.md): satellite
пишется поверх публичных примитивов, не трогая ядро. Результат: пакет
[`@nestling/subscriptions`](../../packages/nestling.subscriptions/) собран
целиком на `.pre`/`.finally`, класс-форме юнита, `AbortSignal`, DI, `Topic` и
контрактах; `git diff` по kernel-пакетам за весь change пуст; внешних
зависимостей нет, `@nestling/app` в зависимостях тоже нет. Полный отчёт —
[ideas.md, секция «[2026-08-01] Реестр подписок: результат dogfooding-замера»](./ideas.md).

**Половина ценности замера — то, что не потребовало исключений.** Момент
`.finally` у потоковых форм снял запись ровно тогда, когда поток дотёк,
оборвался или был закрыт, — ни своего хука, ни таймера; `Topic` дал ленту с
буфером и `drop-oldest` как есть; `event`-контракт с нулём подписчиков
легален, поэтому публикация фактов не требует от приложения ни подписчика, ни
шины; параметризованный инфра-модуль (#13) и `assembleTest` подошли без
оговорок; `jsonSchema(...)` сделал документируемыми схемы, написанные руками,
так что независимость satellite'а от вендора схем не стоила ни OpenAPI, ни
схемного диффа.

**Четыре находки, и ни одна не закрыта правкой ядра.** (1) Ключ `signal` в
`meta` зарезервирован пайплайном, поэтому админский kill — обязательно второе
поле `meta.subscription.signal` = `AbortSignal.any(запрос, админский)`:
слой, подменивший сигнал запроса, сломал бы `computeOutcome` для всех
наблюдателей; правится не ядро, а обещание `design/streaming.md` §1. (2)
`Outcome` не выражает административное завершение — и не должен: знания о
реестре у него нет, satellite вводит свой `CloseReason = Outcome | 'killed'`.
(3) Кластерное управление невыразимо шиной V1 (ни scatter-gather, ни
широковещания без queue-group) — реестр node-local, наблюдение кластерное
фактами с именем узла; имитация `request`-контрактом отвергнута, потому что
молчаливо неверный ответ хуже отсутствующей возможности; триггер возврата — в
[deferred.md](./deferred.md). (4) Найдено по ходу: `.finally` не исполняется
у **непрочитанного** потокового ответа — `return()` на неначатом генераторе
тела не запускает. Это дефект рантайма потоков, а не дыра в примитивах
(контракт «потребить итератор либо закрыть его» из `design/transports.md`
сегодня работает наполовину); зафиксирован живым тестом
`packages/nestling.subscriptions/src/core-limits.spec.ts` и чинится отдельным
change'ем — правка ядра ради satellite'а обесценила бы замер. Дельта-спек
влит: `subscription-registry` (новая capability). **Волной 6 закрыт план до
целевого состояния V1.**

[01.08.2026] Стаб — не подмена рецепта, а опережение его; строгость стаба выше боевого порта намеренно (testing-stub-contract).

Остаток change'а #18, ждавший портов (#11): `stub(Contract, impl)`, `app.emit`
и `app.stubbed`. Ядра портов, контрактов, контейнера и `App` не тронуты ни
строкой — второй после #7 догфудинг тезиса «satellite пишется, не трогая
ядро», и заготовленное ядром пакета поле `stubs:` приняло контрактные стабы
без единой правки. Подробности решения — [ideas.md, секция «[2026-07-10]
Пакет тестирования»](./ideas.md), отметка «РЕАЛИЗОВАНО 2026-08-01 (остаток)».

**Механизм — свойство контейнера, а не новая машинерия.** Стаб есть обычный
провайдер на токен-член семейства вызывателей, зарегистрированный корневым, то
есть до материализации членов; `collectPendingMembers` пропускает токены, у
которых провайдер уже есть, поэтому боевой `buildPort`/`buildEmitter` для
застабанного контракта не вызывается ни разу — и `assertReachable` не
срабатывает. Именно это делает возможным «фича собирается без соседа». Отсюда
же и канон: `familyOverride(PortFamily, …)` подменил бы рецепт **всех**
контрактов разом и потребовал бы вынести `@internal`-семейство наружу, а
`overrides:` работает только когда член уже стал узлом графа. Проверяется
тестом на инвариант «боевой рецепт не вызван», а не только на «вызов вернул
ответ»: регресс в контейнере упадёт здесь.

**Стаб строже боевого co-located порта — осознанно.** Он валидирует выход,
которого боевой порт не валидирует (у боевого ответа позади pipeline
реализации, у стаба pipeline'а нет), а незадекларированный отказ фейка
**бросает** вместо превращения в `UnknownError`: боевой порт защищает
потребителя от чужой реализации, которую не контролирует, автор же стаба
контролирует обе стороны. По той же логике не-`Fail` исключение из `impl`
пробрасывается как есть — «фейк упал» не должно читаться как «сосед вернул
UNKNOWN». Профиль вызова при этом воспроизводится полностью, включая чеканку
`idempotencyKey` у команды, иначе тест на неё расходился бы с продом ровно в
том месте, ради которого ключ чеканится в вызывателе.

**`app.emit` — драйвер, а не издатель**, поэтому возвращает ответы
подписчиков с именем каждого, а не `Promise<void>` боевого эмиттера: издатель
за обработку не отвечает, тест отвечает ровно за неё, а ожидание безопасно —
сокета нет, подписчики co-located. Доставка идёт через `dispatch` по
bus-биндингам ручек, а не через эмиттер из графа: тест-драйвер внешний, и
`container.get(C.emitter)` дал бы вызыватель, только если его кто-то инжектит.
Стаб эмиттера и `app.emit` ортогональны — первый заменяет то, что приложение
зовёт наружу, второй драйвит его снаружи внутрь.

**Сверх записи приехал `app.stubbed`** — состав подстановок значением,
симметрично `app.pruned`. Связь с матрицей `.check()` сделана данными:
`.check()` подстановок не принимает и не примет, а сверка «каждый застабанный
контракт опубликован хотя бы одной топологией» пишется обычным `expect` над
`app.stubbed` и полем `contracts` отчётов. Отдельный хелпер отвергнут: обе
стороны уже значения, а функция сузила бы сверку до одного её варианта.
Дельта-спеки влиты: `contract-stubs` (новая), `test-composition-root` и
`module-isolation-testing` (изменённые).

[01.08.2026] Секретность — свойство ключа, а не объявления; редактирование ошибается в безопасную сторону, запрет — в опасную (config-secrets).

Change #25 доводит до кода запись [2026-07-13] «Конфиг: `secret()` и общие
ключи», аддитивно поверх #9 — ядро не тронуто нигде, кроме `@nestling/config`.
Реализация уточнила шесть вещей, и две из них меняют формулировку исходной
записи.

**Композиция обёрток канонизирована в одну сторону: `secret(from(...))`.**
Запись говорила «`secret(schema)`», не отвечая, как секретность сочетается с
точным именем ключа. Ответ выведен из онтологии: секретность — свойство
**поля**, `from()` называет его **ключ**, поэтому модификатор снаружи, имя
внутри, схема в листе. Обратный порядок отвергается типами (`SecretField` не
реализует `~standard`), а рантайм-ветка в разборе листа ловит JS-потребителя и
`as any`, называя починку. Симметричная композиция отвергнута прямо: два
способа написать одно нарушают «один канонический стиль деклараций».

**Редактируется объект ошибки, а не только её текст.** «Логи фреймворка
редактируют значение» оказалось недостаточной гарантией: `error.failures` —
публичное поле, и логгер, дампнувший его, обязан быть безопасен по
построению. Вендорский текст поэтому не покидает вызов валидации вовсе — в
отказ складываются уже редактированные issue'ы (`message: '<redacted>'`, пути
сохранены), а `ConfigFieldFailure` несёт признак `redacted`. Эвристика
«содержит ли сообщение значение» отвергнута как ровно тот умный рантайм,
который запрещают принципы, и как ложноотрицательная на любом преобразовании.
Смягчение: **незаданный ключ не редактируется** — утечки в его сообщении нет
по определению, а «expected string, received undefined» это самая частая
ошибка с секретами.

**Третья поверхность — display-хуки проекции**, найденная реализацией:
реальная утечка в жизни не в тексте ошибки, а в `console.log(cfg)`. Проекция
секции с секретами получает неперечислимые `toJSON()` и
`[Symbol.for('nodejs.util.inspect.custom')]()`, отдающие копию с `'***'`;
чтение поля не меняется ничем, а секция без секретных полей остаётся тем же
объектом, что и до change'а. Геттеры, возвращающие `***`, сломали бы саму цель
конфига; прокси над проекцией — рантайм-магия и цена на каждом чтении. Граница
гарантии (`{ ...cfg }`, `Object.values`, своя интерполяция) названа в спеке
прямо как свойство v1.

**Асимметрия областей у общего ключа**: секретность считается по
**объявленным** секциям, конфликт `reloadable` — по **материализованным**.
Лишний `***` не стоит ничего; лишняя ошибка сборки убивает приложение, в
котором конфликтующая секция даже не выбрана топологией. Отсюда место
проверки: не реестр (объявление происходит при импорте) и не модульный флаг
`consumed` (две `assembleTest` в одном файле давали бы ложный конфликт), а
**сама читалка** — единственный объект, чья жизнь совпадает с жизнью одной
сборки. Наконец, обещанные записью «читатели ключа в `explain()`» приземлились
в `describeConfig()`: графового `explain()` в коде нет, а форму снимка из
спеки #9 ломать нельзя — key-центричный индекс `keys: [{ key, secret, readers }]`
встал **рядом** с section-центричным перечнем. Дельта-спеки влиты:
`config-secrets`, `config-shared-keys` (новые), `config-sections`,
`config-registry` (изменённые).

[01.08.2026] Контракт — двустороннее значение: имя адресует шину, `http:` адресует провод (contract-clients). Закрывает волну 5.

Change #22 доводит до кода запись [2026-07-13] «Типизированные клиенты из
контрактов». Обещание «импортируем контракт во фронт» проверялось буквально,
и именно эта проверка определила цену change'а: оценка M не сошлась, потому
что работа оказалась не в новой логике, а в физическом переезде
декларативного слоя между пакетами.

**`@nestling/contracts` — переезд, а не фасад.** `Ok`/`Fail` со словарём
статусов, `defineFail` с kernel-отказами, формы io вместе с `FilePart`,
декларативная половина bind-карты, `SseConfig` и сам `makeContract` с
реестром имён и семействами вызывателей уезжают в пакет целиком. Фасад не
менял бы граф импортов: `import { makeContract } from '@nestling/contracts'`
всё равно втянул бы контейнер и транспорт, и гарантия осталась бы
конвенцией — а tree-shaking есть свойство инструмента потребителя, не наше.
Поэтому инвариант проверяется **тестом**, обходящим замыкание собранного
`dist/` с белым списком и запретом `node:*`; он же покрывает
`@nestling/client`. Прежняя поверхность сохранена ES-реэкспортом (тот же
модуль — идентичность значений не двоится), но **`@nestling/ports`
`makeContract` не реэкспортирует**, вопреки собственной формулировке
`design/contracts.md` до этого change'а: реэкспорт вернул бы объявление
контракта в пакет с серверными зависимостями, и упаковочная гарантия стала
бы вопросом дисциплины импортов. Цена — миграция импортов в примерах и
тестах, которую компилятор находит целиком. Ограничение названо прямо:
диагностика TypeScript на старый импорт — обычное «has no exported member» и
на новый дом не указывает; «указатель»-заглушкой поставить нельзя, потому
что это снова экспорт запрещённого имени, и путь оставлен документации.

**Примитив токена въезжает subpath'ом `@nestling/container/tokens`.**
`makeContract` ставит на контракт `.port`/`.emitter` — членов семейств, а
членство обязано регистрироваться в самом семействе (токен, лишь похожий на
члена, членом не является, и билдер это диагностирует). Листовые модули у
контейнера уже были, барель втянул бы билдер графа. **Отвергнут отдельный
пакет `@nestling/tokens`** — инвертирует онтологию (токен инжекции это
понятие контейнера) и разносит по пакетам общее модульное состояние реестра;
**отвергнута «поздняя инициализация» вызывателей из `@nestling/ports`** —
прямое нарушение **no runtime magic**: поведение значения зависело бы от
того, импортирован ли другой пакет. `FilePart.stream` объявлен
`AsyncIterable<Uint8Array>` вместо `Readable` по причине не рантайма
(типовой импорт компилятор стирает), а `.d.ts`: пакет обязан типизироваться
в проекте без Node-типов, и Node'овский `Readable` этому типу удовлетворяет.

**Секция `http:` — данные адресации, разворачиваемые в ту же bind-карту и
тем же кодом, что у декларации.** Два места вызова, одна реализация канона —
расхождению правил между контрактом и декларацией негде взяться, а карта
читается из одного импорта контракта, без серверного кода и без запуска
приложения. Вторая сторона того же значения — **контракт-форма
`httpEndpoint({ contract, … })`**: без неё `http:` описывал бы адрес,
который никто не обязан обслуживать. **Отвергнут отдельный конструктор
`implementHttp`** — дублировал бы перегрузки трёх форм хендлера ради
синонима. Цена нашлась реализацией и оказалась в диагностике типов:
перегрузок стало шесть, а TypeScript при числе больше трёх перестаёт их
перечислять и печатает ошибку только последней; последней обязана стоять
класс-форма, поэтому к настоящей причине примешивается шум про
`HandlerClass` — снапшоты диагностик обновлены, факт зафиксирован. Слот
`pipeline` контракт-формы типизирован без сторожа стартового контекста:
контекст зависит от `rawBody`, который контракт несёт данными, а не типом, и
сторож отвергал бы законную webhook-реализацию — тот же компромисс уже
принят на шине.

**Два открытых вопроса записи [2026-07-13] закрыты.** Валидация ответа —
**по умолчанию**: обещание клиента есть типизированный результат, и отдать
невалидированный JSON под типом `Output` значит соврать в типе; отключение
однострочное и явное (`validateOutput: false`), а отказ валидации не
бросается, а становится `UnknownError` с issue'ами в `cause` — клиент не
бросает на контрактных сбоях. Коерсия query закрыта таблицей:
`undefined`/`null` — ключ не пишется (отсутствие остаётся отсутствием, и
`.optional()` продолжает работать), скаляр — `String(value)`, массив
скаляров — повторяющиеся вхождения (симметрия с `readQuery`), всё остальное
— `TypeError` в момент вызова с именем поля, потому что молчаливый
`[object Object]` на проводе хуже падения. Обратная сторона найдена
интеграционным тестом и названа свойством провода, а не дефектом клиента:
**схема query-поля обязана принимать проводную форму** (`z.boolean()`
отвергает законный `?dryRun=true`; канон — `z.stringbool()`/`z.coerce.*`).
Автоматической коерсии на стороне транспорта не вводится: угадывать тип по
строке значит ровно то, чего избегает schema-first.

**Call-site клиента эквивалентен вызывателю порта** — `request` даёт
`Ok | Fail`, `command` даёт `Promise<void>`, — а множество результата
закрыто как `E ∪ UnknownError` симметрично серверной границе: ре-гидрация по
коду работает ровно потому, что страж границы отдаёт код отказа в теле.
Непригодность контракта (нет `http:`, вид `event`, потоковая форма,
относительный `baseUrl`) диагностируется в момент `makeClient`, а не при
первом вызове. **Отвергнут вывод имён методов из `name` контракта** — имя
контракта это адрес на шине, и превращать адрес в форму чужого API значит
навязывать её; методы именует потребитель ключами record'а. Также отвергнуты
**`http:` списком адресов** (несколько адресов у одной операции это
несколько контрактов), **ленивое вычисление карты при первом обращении**
(fail-fast обязан срабатывать у владельца декларации, в момент загрузки
модуля) и **мульти-транспортная декларация** (сломала бы однозначность
`dispatch`, политик и визуализации). Дельта-спеки влиты: новые capability
`contract-http-binding`, `contracts-package-boundary`, `typed-http-client`;
расширены `contract-declarations`, `endpoint-declarations`,
`http-input-binding`. См. change `contract-clients`,
[гайд](../guides/typed-client.md), ideas.md «[2026-08-01] Клиенты из
контрактов: реализация», дискуссия
[d/07](../history/discussions/07-typed-clients.md),
[архив change'а](../../openspec/changes/archive/2026-08-01-contract-clients/).

[31.07.2026] NATS: брокер **является** шиной приложения, а не встаёт рядом с ней (transport-nats). ~~Закрывает волну 5.~~ — УТОЧНЕНО: последним change'ем волны 5 идёт #22 `contract-clients`, см. запись [01.08.2026].

Change #12 — проверка тезиса L4 («location transparency»): split-развёртывание
обязано получаться правкой корня и конфига, не трогая ни контракты, ни
декларации, ни call-site. Пример `examples.split-nats` держит один код фич и
два корня и служит доказательством.

**`nats()` — обычный транспорт-провайдер под тем же токеном `BusTransport$`,
которым пользуется `InProcessBus`.** Kernel-модуль портов регистрирует
in-proc шину только если корень не поставил транспорт шины сам; `MessageBus$`
становится алиасом инстанса `BusTransport$` (направление алиаса развёрнуто
один раз и одинаково для обеих реализаций). Довод — дихотомия «messaging vs
transports» уже признана ложной в [d/05 §4](../history/discussions/05-modular-monolith-features-ports.md),
и две шины воскресили бы её как «локальная» и «сетевая». К тому же
`local-first` и так не ходит на шину для co-located вызовов — роль «локальной
шины» в модели исполняет диспетчер, а не шина. **Отвергнут собственный токен
`NatsTransport$`**: на него не ссылается ни одна декларация, значит у
транспорта не было бы ни маршрутов, ни `dispatch`, и inbound-сторона
потребовала бы машинерии подписки мимо `serve`. **Отвергнуто поле корня
`bus:`** — перечень полей `assemble` закрыт, а шина есть транспорт.

**Третий вход биндинга — природа шины, объявленная значением
(`IMessageBus.remote`).** «Владелец не выбран здесь» перестаёт означать
«владельца нет»: `request`/`command` без co-located реализации биндится
remote вместо падения ASSEMBLE, а fail-fast остаётся ровно для in-proc шины.
Проверки, требующей знания о составе кластера, намеренно не заведено —
недоступность владельца в рантайме есть обычный отказ доставки. Единственное
изменение поведения работающего кода: **`event` при remote-шине уходит через
шину всегда**, потому что множество подписчиков события открыто и локальный
dispatch молча потерял бы тех, кто в других процессах; co-located подписчик
получает ровно одну копию — loopback'ом со своего же subject'а. **Отвергнуто
«доставить локально И опубликовать»** (две копии co-located подписчику) и
**отвергнуто гашение loopback-подписки** (потребовало бы service discovery на
сборке).

**Фазы разъезжаются там, где у in-proc шины они совпадали:** соединение — в
INIT (ресурс захватывается как ресурс, поэтому вызов порта из `@OnStart`
работоспособен), маршруты и проверка форм — в WIRE, подписки — в `serve`
после `@OnStart` (входящее сообщение не застаёт незавершённый `@OnStart` —
это гарантия dispatch в изначальном смысле), дренаж — в SHUTDOWN. Названо
честно: гарантия «dispatch существует с WIRE» была и остаётся
**внутрипроцессной**, за её пределами ответ на гонку старта — `deadline` и
ретрай вызывающего, а не подписка раньше `@OnStart`.

**Конверт — в headers, тело — кодеком, ответ — `ResponseContext`.**
Ре-гидрация задекларированного `Fail` по коду заработала по проводу без
единой правки — ровно то, ради чего страж границы отдаёт код отказа в теле.
Реализация внесла поправку в дизайн: `Nl-Ctx` **один заголовок**, а не
`Nl-Ctx-<key>` на переменную, потому что клиент брокера канонизирует имена
заголовков по MIME (`Nl-Ctx-tenantId` → `Nl-Ctx-Tenantid`), а ключ
ambient-переменной — имя поля накопленного `input`, и потеря регистра сделала
бы `TenantId.propagated()` неработоспособным; значение канонизации не
подвергается, поэтому ключи переехали внутрь значения. Кодек — JSON по
умолчанию (**отвергнут msgpack/бинарный формат по умолчанию**: дебажимость в
`nats sub` дороже процентов размера), и его ограничение названо прямо: JSON
строже, чем `structuredClone`, которым репетирует провод `always-remote`, —
но потеря типа даёт громкий отказ валидации входа по схеме на приёме, а не
тихо приезжает не тем типом. Потолок `NATS_REQUEST_TIMEOUT` — свойство
**провода**, а не воскресший дефолтный бюджет, от которого отказался #27:
бюджет наследуется вглубь вызовов, потолок — нет.

**`durable` объявляется контрактом**, потому что долговечность — свойство
операции, а издатель (обязан дождаться подтверждения записи) и подписчик
(обязан читать durable-потребителем) живут в разных процессах, и единственное
доступное обоим значение — контракт. У `request` флаг отвергается в точке
создания: ответа ждёт живой вызывающий. **Отвергнут `durable` на
`implement`-декларации** (издатель в другом процессе о ней не знает и
опубликовал бы мимо потока) и **отвергнут список durable-subject'ов в
конфигурации транспорта** (молча разъезжается с кодом). Шина без способности
не роняет сборку, а печатает на go-live строку с перечнем контрактов,
обслуживаемых недолговечно, — тем же приёмом, что список `detached`-ручек:
иначе локальный запуск без брокера стал бы невозможен, а тихая деградация
недопустима. Ack — по факту **решения**: успех и задекларированный `Fail`
одинаково означают «обработано», повтор — только там, где решения не
получилось (`UNKNOWN`, остановка процесса). Слово «JetStream» не появляется
ни в контракте, ни в биндинге, ни в конверте.

**`propagate` повторяет механику, которую #27 уже построил для `deadline` и
`idempotencyKey`** — и это главный довод за неё: второй машинерии для той же
задачи не заводится. Провозится только объявленное `{ propagate: true }`;
общей протечки ambient-контекста вызывающего в реализацию не появляется —
требование `port-invocation` остаётся в силе, а `propagate` есть именованное
исключение, видимое в объявлении переменной. Приём двухслойный: атрибуты
безусловны, ambient-проекцию включает штатный писатель `Var.propagated()` с
той же меткой, что `Var.provide`, поэтому `hasVar` его засчитывает и
присутствие провозимого контекста проверяемо на сборке. Провезённое **не
валидируется** (схемы у ambient-переменной нет, и рантайм её не изобретает) —
граница доверия пересекается явно и названа в документации.

**Открытый вопрос ideas.md про третье понятие деклараций закрыт
отрицательно:** wildcard-аудитор пишется инжектом `MessageBus$` и
`subscribe('orders.>', …)` в `@OnStart` — это первый этаж онтологии
(сантехника транспорта), схем, контракта и policy-check он не заслуживает;
`natsEndpoint` не введён. Клиент брокера изолирован узким коннектором,
двойник брокера экспортируется по конвенции `./testing`, поэтому `yarn verify`
зелёный без сети; ограничение названо в README прямо — двойник проверяет наш
код, а совместимость с брокером проверяет интеграционный прогон по
`NATS_TEST_SERVERS`. Дельта-спеки влиты: новые capability `nats-transport`,
`durable-delivery`, `context-propagation`; расширены `message-bus`,
`port-binding`, `contract-declarations`, `async-context-vars`. См. change
`transport-nats`, [гайд](../guides/ports.md) (разделы про split-развёртывание
и провоз контекста), ideas.md «[2026-07-31] NATS: шина приложения»,
[архив change'а](../../openspec/changes/archive/2026-07-31-transport-nats/).

[31.07.2026] Совместимость контрактов: снапшот из дискавери, вердикт по слоту, третий вердикт `unknown` (contract-versioning).

Change #26 закрыл вторую половину записи [2026-07-13] («версия — в имени,
дифф подсвечивает и не блокирует»): как именно устроены снапшот, дифф и отчёт.
Дизайн зажат тремя ограничениями — Standard Schema непрозрачна в рантайме,
отчёт во фреймворке всегда значение, а «не блокирует» обязано быть свойством
конструкции, а не обещанием в доке.

**Источник снапшота — дискавери, а не приватный реестр `makeContract`.**
Снапшот отвечает на вопрос «что я обещал наружу», поэтому строится по
декларациям с bus-биндингом — по тому, что приложение **реализует**. В реестр
попадает всё импортированное, включая контракты соседних фич; спека
`contract-declarations` прямо запрещает делать его источником истины о составе.
Матрица топологий сводится **объединением**, и дескриптор несёт перечень
опубликовавших топологий — иначе «контракт удалён» и «фича не выбрана в этой
топологии» слились бы в один красный отчёт.

**Направление берётся из слота, а не из роли смотрящего.** `input` приходит
в реализацию (сужение принимаемого — `breaking`), `output` уходит из неё
(ослабление гарантии — `breaking`). Правило одинаково для всех трёх видов,
включая `event`, где реализация — подписчик: «подписчик стал требовать больше»
и есть breaking для издателя. Классификация по роли владельца/потребителя
отвергнута: она требовала бы знать, кто смотрит, и давала бы разные вердикты
на одном снапшоте.

**Третий вердикт `unknown` вместо «раз не знаю — значит совместимо».**
Разбираемое подмножество JSON Schema закрыто (`type`, `properties`,
`required`, `items`, `enum`, `nullable`); `$ref`/`allOf`/`oneOf`/`anyOf`,
непрозрачный лист и смена вендора дают `unknown` с JSON-путём. Приравнять
`unknown` к `breaking` было отвергнуто намеренно: смена патч-версии конвертера
перекрасила бы весь отчёт в красный, и им перестали бы пользоваться.

**Отсутствие флага блокировки — конструкция, а не умолчание.** `diffContracts`
не участвует в сборке, не вызывается из `run()`/`check()` и не бросает по
результату сравнения; уронить CI можно ровно одним способом — написать
`expect(report.breaking).toEqual([])` в своём тесте. `failOnBreaking` отвергнут:
наличие флага делает блокировку штатным режимом фреймворка. Единственное
исключение — нечитаемый baseline (чужая `snapshotVersion`): это ошибка автора
проверки, а не breaking change, и она бросает.

**`SchemaDocConverter` заведён на схемном слое, а не в пакете документации** —
потребителей два, и снапшот приезжает раньше `@nestling/openapi` (#20).
Диспетчер возвращает «конвертера нет» наблюдаемым исходом, строгость выбирает
потребитель. Подсказка bump'а (`billing.charge` → `.v2`) — единственное место,
где суффикс `.vN` распознаётся: `makeContract` его не требует, не разбирает и
поля версии не заводит. Дельта-спеки влиты: новая capability
`contract-compatibility`, расширены `standard-schema-validation` и
`structural-check`.

[31.07.2026] Эксплуатационный профиль вызова: бюджет — момент, ключ — только у команд (port-deadline-idempotency).

Change #27 закрыл ровно то, на чём, по [d/06 §5](../history/discussions/06-critical-design-review.md),
сломалась Service Weaver: location transparency, отданная без
**эксплуатационного профиля**. После #11 call-site co-located и remote вызова
совпадал до последнего дженерика, но ограничить hop бюджетом было нечем, а
ретрай брокера был неотличим от нового намерения.

**Бюджет — абсолютный момент внутри процесса, относительный timeout по
проводу.** Это gRPC-модель, и выбрана она не по авторитету, а потому что
единственная делает clock skew между подами семантически безразличным:
отправитель считает остаток по своим часам, получатель превращает его обратно
в момент по своим — транзит съедает бюджет, рассинхрон не съедает. Ни одна
сторона не сравнивает свои часы с чужими. `deadline: number` не принимается
вовсе: «500» одинаково правдоподобно читается как epoch и как «через 500 мс»,
а разница между прочтениями — разница между мгновенным отказом и полусекундным
бюджетом. Сахар `deadlineIn(ms)` даёт момент из относительного бюджета, и
именно он стоит в примерах.

**Fail-fast — до вызова и до обработки.** Исчерпанный бюджет даёт
`DeadlineExceeded`, не тронув ни `dispatch`, ни шину; исчерпанный к моменту
приёма — не тронув обработчика. Истечение **в полёте** взводит `ctx.signal` и
завершает вызов тем же кодом, а не `UnknownError`, которым до сих пор кончалась
всякая отмена. Различение опирается на владение таймером бюджета, а не на
`signal.reason`: `reason` приходит из кода вызывающего и доверенным источником
не является.

**`DeadlineExceeded` — kernel-код, и определён он там, где живёт набор.**
`DEADLINE_EXCEEDED` (статус `TIMEOUT` → 504) в `errors:` не декларируется, но
входит в закрытое множество ответов любой ручки и любого порта. Определение
живёт в `@nestling/pipeline` — там же, где закрытый набор и его читатель, —
и **реэкспортируется** из `@nestling/ports`: регистрация из другого пакета
означала бы рантайм-мутацию закрытого множества. Набор вырос ровно так, как
обещал `error-model` (#15): вместе с механизмом, который отказ порождает.

**`idempotencyKey` — только у `command`, и это типовое решение, а не
соглашение.** У `request` и `event` поля нет даже в типе: `MetaOf<C>`
выбирается по виду контракта, поэтому передача ключа туда — ошибка компиляции.
Молчаливо проигнорированное поле было бы худшим исходом из возможных — код,
выглядящий идемпотентным и таковым не являющийся. Ключ чеканит **вызыватель**,
если вызывающий его не дал: транспорт не знает, где кончается один `emit`, и
гарантии «ретрай доставки несёт тот же ключ, два `emit` — разные» дать не может.
Дедупликации в ядре нет и не будет: хранилище — satellite-концерн, ядро
гарантирует ровно провоз и доступность.

**Профиль читается двумя каналами.** Безусловно — `raw.attributes` рядом с
`subject`; из произвольной глубины — ambient-переменные `Deadline` и
`IdempotencyKey` со штатными pre-юнитами, кладущими их из тех же атрибутов.
Переменные экспортированы **значениями**, поэтому `everyEndpoint(…).hasVar(…)`
адресует именно их, и присутствие ключа проверяется на сборке, а не на запросе.
Наследование бюджета вложенным вызовом оставлено **явным** — как сегодня не
наследуется `meta.signal`.

`InProcessBus` реализовал конверт целиком — как репетицию провода: пересчёт
`timeoutMs` в момент на приёме, отказ по исчерпанию в транзите без вызова
`dispatch.call`, ключ в атрибутах. Wire-часть для NATS едет с change #12, но
форма LCD уже зафиксирована и интерфейс под неё расширять не придётся.
См. change `port-deadline-idempotency`, [гайд](../guides/ports.md),
ideas.md «[2026-07-31] Порты: бюджет вызова моментом, ключ идемпотентности
у команд».

[31.07.2026] Порты: индиректность резолвится на сборке, а inbound-сторона — буквально endpoint (ports).

Change #11 открыл волну 5 и снял противоречие «location transparency vs no
runtime magic» единственным способом, совместимым с принципами: **выбор пути
делается на ASSEMBLE, а не на запросе**. Контракт (`makeContract`) —
направление-нейтральное значение с тремя видами (`request`, `command`,
`event`), чьё имя одновременно subject шины и ключ дискавери; повтор имени —
ошибка в точке создания. Потребитель инжектит `Contract.port`/`.emitter` —
члены token-семейств, материализуемые **только для запрошенных** контрактов,
— и зовёт константу, замкнутую на выбранный путь.

**Половина change'а оказалась не написана, а переиспользована.** Реализация
контракта — не новая ось регистрации, а обычная декларация: `implement`
строится тем же `makeEndpoint`, кладётся в `endpoints:` модуля и наследует
дискавери из дерева выбранных модулей, `makeDispatch`, pipeline, страж
границы, `policies`/`detached`, `check()` и вызов по значению в тестовом
корне. Тем самым онтология «per-transport конструктор = сахар над анонимным
контрактом плюс `implement`» перестала быть словами в дизайне и стала кодом:
`httpEndpoint(...)` и `implement(C, ...)` компилируются в узел одного вида,
различаясь только биндингом. Адрес в процессе и адрес на шине разведены:
`pattern` события несёт `<name>@<subscriber>` (имя подписчика задаётся явно —
это будущая queue-group), subject остаётся именем контракта.

**Политика диспатча — конфигурация, а не поле корня.** Перечень полей
`assemble` не пополнился: ни `dispatch:`, ни `bus:`, ни `contracts:`. Политика
живёт в kernel-секции `nestlingPorts` (`NESTLING_PORTS_DISPATCH`,
по умолчанию `local-first`) и потому переключается привязанным источником и
`vars()` в тестовом корне — то есть `.check()`-матрица гоняет обе топологии
без правки call-site. `always-remote` в V1 — не поднятый брокер, а честная
симуляция провода поверх in-proc шины: async-барьер, структурная копия payload
и ответа, валидация ответа по `output`-схеме. Несериализуемое значение падает
здесь, в dev, а не в день разъезда фич по процессам.

**Позднее связывание оставлено ровно одно и оно явное.** `dispatch` рождается
в WIRE, поэтому local-клиент получает исполнитель шагом той же фазы, а вызов
порта раньше WIRE — внятная ошибка с именем контракта и фазы, а не молчаливое
ожидание или `undefined`. Резолва «кто обслуживает контракт» на вызове не
существует: связывание происходит один раз. `InProcessBus` сделан одним
значением с двумя способностями (`ITransport` + `IMessageBus`) — отдельных
сущностей «шина» и «транспорт шины» нет, broadcast построен на `Topic` из
`@nestling/streams`, способности по формам io — только `value` (контракт со
`stream`/`events` отвергается существующей capability-проверкой на ASSEMBLE).

**Дисциплина выражена ошибками сборки, а не разделом гайда.** `call` всегда
async и Fail-able даже co-located; отказ ре-гидрируется по `code` одним
нормализатором для обоих путей (объявленный — в настоящий `Fail`,
незадекларированный — в `UnknownError`, `stack` границу не пересекает), из-за
чего тип call-site совпадает у co-located и split до последнего дженерика;
вызов уходит в собственный request-scope — общей транзакции и ambient-контекста
вызывающего у обработчика нет; `request`/`command` без реализации и без
remote-шины — падение ASSEMBLE с указанием контракта и потребителя.
Не-goals оставлены следующим change'ам: NATS и wire-`propagate` (#12),
`deadline`/`idempotencyKey` (#27), схемный дифф (#26), `stub(Contract)` (#18),
`http:`-биндинг и `makeClient` (#22). См. change `ports`.

[31.07.2026] Ambient-контекст: переменная — типизированный ключ накопленного input, писатель — конструктор pre-юнита (async-context).

Вопрос change'а был поставлен не как «магия или без магии», а как **чья магия
— фреймворка с гарантиями или пользователя без**: логгер тремя слоями ниже
хендлера всё равно получит `requestId`, и без ответа фреймворка команда заводит
собственный `AsyncLocalStorage`-мешок — глобал, невидимый в графе,
нетипизированный, с записью откуда угодно. Формула ответа: **значение едет
ambient'ом, зависимость явная, запись — монополия pre-юнитов**.

**Главное решение — ambient-переменная не заводит второго состояния.**
`contextVar<string>('requestId')` объявляет **имя поля в накопленном `input`
пайплайна**, а не ячейку отдельного хранилища; ALS-проекция read-only именно
потому, что читает то, что пайплайн и так накопил, — расходиться не с чем.
Отвергнута отдельная ambient-карта (`Map<varId, value>`) рядом с `input`: два
состояния и немедленный вопрос «что видит юнит, а что сервис», плюс запись в
карту потребовала бы второго канала API.

**Закрыт открытый вопрос ideas.md «рантайм-декларация добавок».** Требований к
декларации было два — не расходиться с фактом и быть видимой **на сборке**, до
первого запроса. Победила форма `Var.provide(compute)`: конструктор,
возвращающий обычный `PreUnitFn<TReq, { key: T }>`, где добавку строит сама
переменная, — «объявлено» и «положено» становятся одним действием, а
неперечислимый symbol-маркер на значении юнита даёт пайплайну множество
объявленных переменных рядом с провенансом композиции (те же правила:
`compose` объединяет, деривация и `bind()` сохраняют). Отвергнуты: рабочая
гипотеза `RequestId.of(uuid)` — тождество есть, но видно только в рантайме, на
первом запросе; `pre(unit, { provides: [X] })` — декларация живёт отдельно от
факта, и проверка вырождается в проверку комментария; вывод из типов пайплайна
— к фазе ASSEMBLE типов нет вовсе (type erasure). Цена: юнит, кладущий поле
«вручную», для читателей работает, а для `hasVar` невидим — направление ошибки
безопасное (ложное падение сборки, не ложное разрешение), починка в одну
строку, диагностика прямо называет `<Var>.provide(…)`.

**Чтение — инжектируемый член token family, а не статический аксессор.**
`Ctx(RequestId)` даёт токен `'Ctx:requestId'` — обычный узел графа, поэтому
зависимость от request-контекста видна в визуализации и `explain()`, полный
список ambient-чтений известен на `build()`, а тест подменяет ридер
`valueProvider`/`contextValue` — ALS в тестах не нужен. Публичный `Ctx` —
типизированный аксессор над приватным семейством: так `Ctx('requestId')` со
строкой не компилируется, а рецепт остаётся обычным `familyProvider` в
kernel-модуле, который корень регистрирует **всегда** (как `configKernel`) и
который без единого читателя не материализует ничего. Отвергнут статический
`AsyncContext.get(key)` — глобал: невидим в графе, нетестируем без ALS,
присутствие не типизировано.

**`get()`/`peek()` — зеркало асимметрии пайплайна, а не удобство.**
Безусловная гарантия присутствия несостоятельна by design: ответный тракт
видит собственный pre-контекст как `Partial`, а пути вне запроса (`@OnStart`,
cron) существуют. Отсюда пара методов плюс диагностика `get()`, зависящая от
того, что рантайм знает о месте вызова: нет scope'а — «фоновый путь, используй
`peek()`»; ответный тракт/`finally`/поток — «pre не дошёл до юнита-писателя»;
pre/handler — «композируй слой с `<Var>.provide(…)` или объяви `hasVar`».
Ошибка — обычный `Error`: недоступность переменной программная, страж границы
нормализует её в `UnknownError`, kernel-`Fail` для неё не заводится.

**Scope открывают обе точки исполнения ручки, включая потоковый ответ.**
Прямой путь (`callDirectly`, ручка без пайплайна) открывает scope с пустым
`input`, чтобы `peek()` возвращал `undefined`, а не падал «контекста нет»:
поведение глубокого сервиса не должно зависеть от того, есть у ручки пайплайн
или нет. Отдельно покрыт выходной поток — `executeWithHandler` возвращает
итератор **до** того, как транспорт начнёт его тянуть, поэтому без обёртки
каждого `next()` и финализации ambient-чтение ломалось бы ровно у ленивых
генераторов и item-цепочек, где логирование нужнее всего.

**Присутствие проверяется предикатом того же словаря** — `hasVar(Var, label?)`
поверх машинерии #28: opt-in, объявляется значением в `policies:`, ручка без
пайплайна нарушает, `detached: '<причина>'` выводит из-под проверки. Графовый
вывод требования («каждый провайдер с `Ctx(X)` достижим только из ручек,
кладущих X») отвергнут для V1 не по красоте, а по цене: он требует двух новых
публичных поверхностей — публикации токенов, требуемых декларацией, и запроса
транзитивного замыкания у `BuiltContainer`; приедет отдельным change'ом
значением того же типа `Policy`.

**Зарезервированное имя `@nestling/context` снято** (запись [2026-07-06]): всё
живёт в `@nestling/pipeline`, потому что писатель типизируется контекстом
пайплайна, ячейку обновляет рантайм пайплайна, а предикат — из словаря политик
пайплайна; отдельный пакет дал бы цикл зависимостей либо дубль типов. Штатный
`withRequestId()` переписан через `RequestId.provide(…)` с прежней сигнатурой —
приложения, уже композирующие его, бесплатно получают `Ctx(RequestId)` и
проходят `hasVar`. Change аддитивный: без объявленных политик и без ридеров
поведение тождественно прежнему. Дельта-спеки влиты: новые
`async-context-vars`, `context-readers`, `request-context-scope`; дополнены
`pipeline-composition`, `policy-predicates`, `test-composition-root`.

[31.07.2026] Cross-cutting без нового примитива: инфра — параметризованный модуль, идентичность модуля — значение (plugins).

Вопрос change'а был не «как сделать плагины», а «куда девается каждая часть
чужого примитива». Ответ — таблица соответствий: `modules()` плагина → те же
`modules:`/`providers:` (корня — для процесс-глобального, фичи — для
feature-scoped), параметризация → функция, возвращающая модуль (`logging({ … })`),
конфиг плагина → секция `makeConfig`, объявленная самим инфра-модулем (наружу —
только `.keys`), `forTransports()` → обычная зависимость от токена транспорта с
fail-fast на ASSEMBLE, `configureMiddleware` → экспортируемый pipeline-слой плюс
`everyEndpoint(…).hasLayer(ref)` из #28. У каждой части есть адрес, и ни одна не
требует нового понятия — поэтому `Plugin` не появился даже как тонкая обёртка
над модулем: обёртка ничего не добавляет к значению, но заводит второй способ
сказать «модуль» и вместе с ним вопросы «плагин в фиче — это плагин?» и «каков
порядок плагинов».

**Обещанное поле `plugins:` снято из целевого словаря `assemble`.** Root-bag
тождественен `modules:` корня — те же значения, та же фаза, та же дедупликация,
— а два поля с одной семантикой заставляли бы выбирать между ними на каждом
инфра-модуле. Взамен сформулировано правило: **перечень полей `assemble`
закрыт**. `providers:` рядом с `modules:` остаётся по другой причине — он
выражает другую *форму* (провайдер, а не модуль). Заодно закрыт открытый вопрос
ideas.md [2026-07-08]: ambient policy-check — машинерия #28, а не хук
`OnConfiguration` (хук — барьер «весь конфиг → весь init», зависимость даёт
точную топологию).

**Главное изменение кода — идентичность модуля.** `#modules: Set<string>` в
`ContainerBuilder` стал `Map<string, Module>`: то же значение под занятым именем
— no-op (модуль, разделяемый корнем и фичей или двумя фичами, — главный сценарий
инфраструктуры), **другое** значение под занятым именем — бросок. Раньше
срабатывало «первый выиграл», и вместе со вторым значением молча терялись его
провайдеры, экспорты и эндпоинты — тихая потеря части приложения там, где автор
писал `logging({ level: 'debug' })` в одной фиче и `logging({ level: 'warn' })` в
другой. Сравнение ссылочное: структурное («опции совпали — считаем одним») — та
самая runtime magic, которую фреймворк себе запрещает, оно требует обхода
произвольных значений (функции, инстансы клиентов) и меняет тихую потерю на
тихое слияние. Диагностика называет три починки — разделить одно значение
импортом, дать конфигурациям разные имена, проверить дубли пакета в
зависимостях. Формально это ужесточение публичного контракта, практически —
перевод «тихо теряем» в «падаем на сборке»: правильно работавшее приложение
коллизии не имеет по построению. Отсюда и канон параметризованного модуля:
**значение создаётся один раз и импортируется**, а не вызывается фабрикой у
каждого потребителя.

То же правило зеркалится в `discoverEndpoints` (свой `Map`, свой бросок того же
смысла): в App-пути коллизия всегда падает раньше — регистрация модулей
предшествует дискавери, — но `discoverEndpoints` экспортируется отдельно и по
своей capability обязана зеркалить обход контейнера; молчащая там проверка
делала бы зеркало кривым ровно там, где оно важно. Общий обходчик из
`@nestling/container` отвергнут для change'а размера S: публичная поверхность
растёт ради пяти строк, а дискавери всё равно нужен свой visit.

**Линия «параметр модуля vs конфиг-секция»** проговорена как канон: параметр
функции-модуля — решение composition root (форма графа, выбор реализации, набор
провайдеров; живёт в коде и в diff'е ревью), конфиг-секция — решение среды
(адреса, порты, уровни, таймауты; валидируется на `build()`, может быть
reloadable). Критерий для автора инфра-модуля: меняется без пересборки образа —
секция; меняет то, какие провайдеры существуют, — параметр. Feature-scoped
инфраструктура кода не потребовала — свойство следует из жадного контейнера и
`select`, — и зафиксирована тестом: невыбранная фича не тянет свою инфру в граф,
две co-located фичи с одним значением делят инстанс. Витрина канона —
`examples.app-with-http`: `LoggerModule` стал `logging({ … })` со своей секцией и
экспортируемым слоем наблюдаемости, который требует политика из #28. См. change
`plugins`.

[31.07.2026] Инварианты на собранном графе: `policies:`, провенанс композиции, `detached` (policy-check).

Endpoint-only pipeline купил compile-time проверки ценой сквозных инвариантов.
Пайплайн объявляется на каждой ручке своим значением, и **ничто не замечало
ручку, композированную не от той базы**: забытый auth-слой на одном endpoint'е —
каноническая уязвимость, а типы её не ловят («должен быть защищён» — не свойство
типов хендлера: хендлер, не читающий `identity`, типобезопасен и с auth, и без).
Критическое ревью назвало это самым сильным внутренним противоречием дизайна.
Композиция константами решает переиспользование, но не гарантию.

**Гарантия живёт на фазе 1 ASSEMBLE, где все значения деклараций
материализованы.** `assemble({ policies })` принимает инварианты значениями и
прогоняет их последними из fail-fast'ов сборки: сперва «граф вообще собирается»
(транспорты, формы io), затем инварианты на нём. До `@OnInit` не доходит ни одно
нарушение — ресурсы не захватываются, сокеты не открываются. Множество
проверяемых ручек — результат дискавери по дереву модулей, то есть ручки
**выбранной топологии**: политика проверяет то, что действительно поедет, а не
весь репозиторий. Прогон идёт на каждом входе, строящем граф — `run()`,
`check()` (значит, и `checkTopologies` по матрице `select`-топологий в CI) и
тестовый корень `assembleTest`; тест не ослабляет инварианты.

**Идентичность слоя — ссылочная, и ради этого пайплайн начал нести провенанс
композиции.** `compose(a, b)` запоминает ссылки на **сами аргументы** (не
разворачивая их провенанс), деривация билдера — ссылку на предшественника,
`bind()` — на несвязанный оригинал; `hasLayer(ref)` обходит этот граф по
ссылочному равенству. Транзитивность отсюда бесплатна: `compose(compose(base,
authed), extra)` удовлетворяет всем трём, а `authed.pre(x)` — политике на
`authed`, потому что pre-тракт монотонен и деривация умеет только добавлять.
Сравнений по имени слоя, по `Function.name`, по идентичности юнитов и по
структуре нет: одноимённая копия слоя из другого файла политику не проходит, и
это ровно то поведение, которое нужно. Провенанс не влияет на исполнение и не
ломает иммутабельность. Автоматический вывод имени слоя для диагностики
отвергнут как runtime magic — человекочитаемая метка передаётся вторым
аргументом `hasLayer(ref, 'authedBase')`.

**Словарь предикатов v1 намеренно минимален** — `everyEndpoint({ transport?,
pattern? }).hasLayer(...)`. Фильтр по транспорту берёт **токен**, а не строку;
`pattern` — `RegExp`, а не строка-префикс: «строка как префикс» было бы неявным
правилом. Ручка **без** пайплайна считается нарушающей: для инварианта «ручка
защищена» отсутствие пайплайна и отсутствие слоя неразличимы, и трактовка «нечего
проверять» открывала бы дыру именно там, где её ищут. `Policy` — открытый
интерфейс (`describe()` + `check(subjects)`), поэтому `hasVar` для ambient-vars
(#16) и инварианты плагинов (#13) лягут в тот же список `policies:` без второй
машинерии и без второго прохода по дискавери. Пользовательские предикаты над
интроспекцией `explain()` отложены: форма плана исполнения как публичного
значения — открытый вопрос.

**Opt-out — только `detached: '<причина>'`.** `detached: true` невыразим по типам
(поле — `string`), а рантайм дублирует правило для JS-потребителей, отвергая
пустую строку в момент создания декларации. Per-policy адресация
(`detached: { policyName: reason }`) отвергнута: политик у приложения единицы, а
адресация по имени завела бы в системе вторую идентичность рядом со ссылочной.
Главное — opt-out не тихая дыра: `App` печатает список detached-ручек с
причинами на старте, а `CheckReport` несёт причину **значением**, поэтому тест
матрицы топологий сравнивает состав исключений, не парся stdout. Нарушения при
этом перечисляются разом — один бросок со всеми провинившимися ручками, их
модулями-объявителями и способом починки: чинить инварианты по одной ручке за
прогон не режим работы.

**ESLint-правило — фидбек, а не гарантия, и это зафиксировано явно.** Новый
пакет `@nestling/eslint-plugin` с правилом `endpoint-has-layer` разбирает только
буквальные случаи (`pipeline:` — идентификатор или `compose(...)` из
идентификаторов) и **молчит** там, где значение синтаксически непрозрачно:
параметр модуля-фабрики, вызов неизвестной функции, spread. Ложное срабатывание
на легальном коде хуже пропуска, потому что пропуск ловит policy-check.
Рекомендуемый уровень — `warn`: падающий CI создавал бы ложное представление о
гарантии, которой синтаксическое правило дать не может; type-aware вариант
отвергнут — типовая информация не отменяет фабрик, стоит дорого и гарантии всё
равно не даёт. Практическая находка, вписанная в спеку: опция имени конструктора
называется `constructorName`, а не `constructor` — свойство с таким именем в

be string»).

[31.07.2026] Ядро `@nestling/testing`: тестовый корень, подстановка с прунингом, `.check()` (testing-package).

Тестировать приложение целиком было нечем. Единственный composition root вёл
приложение сразу до RUN — сокеты, обработчики `SIGTERM`/`SIGINT`, — поэтому тесту
оставались либо юнит на голых классах, либо e2e с портом и HTTP-клиентом.
Середины не было: прогнать запрос через полный пайплайн без сокета — не через
что, подменить репозиторий фейком — нечем. Хуже того, жадный контейнер без
прунинга **анти-тестовый**: даже будь подстановка, замена репозитория фейком не
помешала бы pg-пулу проинстанцироваться и открыть соединение.

**Пакет тонкий по построению** — тестируемость здесь следствие архитектуры, а не
машинерии пакета. `assembleTest(spec)` принимает тот же словарь сборки, что
`assemble`, и останавливается после фазы `3 WIRE`: `@OnInit` выполнены,
`dispatch` рождён, START не наступает. `app.call(Endpoint, input)` исполняет
ручку через **полный пайплайн** in-proc — этим app-тест и отличается от юнита, —
типизируясь схемами декларации: `input` по `input`-форме, ветка отказа несёт
`status` и `code` из закрытого контракта `errors:`. Декларация ищется по
идентичности значения, поэтому «ручка не выбрана `select`» — внятная ошибка с
перечнем доступных, а не тихий промах.

**`overrides` — ключ только тестового корня, и это структурная граница.**
Подстановка происходит в графе на ASSEMBLE, до инстанциации: не патчинг и не
перехват module system. Право override позиционное — подменяется только тот
токен, ссылка на который есть у теста; строковой формы (`overrideByName('…')`)
не существует, поэтому чужой неэкспортированный провайдер не мокается никак, и
это фича. Override токена, которого нет в графе, — ошибка сборки: молчаливо
проигнорированный override означал бы тест, который «мокает» пустоту и гоняет
боевой код, переживая переименование провайдера.

**Прунинг осиротевших поддеревьев** — то, что делает подстановку осмысленной:
замокал репозиторий → пул не коннектится, узла в графе нет, его хуки не
выполняются. Несущий инвариант, делающий прунинг безопасным для боевой сборки:
**без `overrides` прунинг тождественен** — множество узлов не меняется ни на
один, включая узлы, на которые никто не ссылается, и участников циклов
(диагностика цикла продолжает падать, а не тихо выбрасывать оба узла). Отсюда
форма алгоритма: отношение зависимостей берётся дважды — до и после подстановки,
корни считаются по объединению, достижимость — по отношению после;
`Family.all` разворачивается в членов, агрегаты материализуются после прунинга.

**`.check()` — метод корня, а не тестового приложения.** Ровно потому, что
прунинг убирает узлы из тестового графа, нужна компенсация: структурный смок
гоняет фазы 0–1 на **честном** графе, без подстановок, — конструкторы без
`@OnInit`, значит без захвата ресурсов, зато со всеми fail-fast'ами сборки.
`checkTopologies(spec, selections)` проверяет матрицу `select`-топологий одним
тестом и перечисляет **все** отказы, а не первый. По той же логике «перечислять
разом» поправлена и обычная сборка: неудовлетворённые зависимости теперь
диагностируются одним списком до инстанциации, а не первой попавшейся ошибкой в
её процессе.

**Конвенция `./testing`-subpath** — тестовая capability пакета через conditional
export по условию `"testing"`, включённому только в тест-раннере: прод-импорт не
резолвится на уровне Node module resolution, то есть граница структурная, а не
конвенция. Догфудится на самом ядре — внутренний шов, которым `@nestling/testing`
заводит фазы 0–3, живёт в `@nestling/app/testing`, поэтому в публичной
поверхности `@nestling/app` нет ни `overrides`, ни способа остановиться на WIRE.
`vars({ … })` даёт конфиг теста объектом вместо `process.env` — параллельные
тесты бесплатно и программно проверяемый reload.

Change поставлен **раньше, чем требует граф зависимостей**: `assembleTest` /
`vars()` / `.check()` удешевляют каждый следующий change волн 4–6, чьи тесты
теперь пишутся против собранного приложения, а не против ручной обвязки
контейнера. Перенесён ровно один пункт исходного скоупа — `app.emit`: понятия
`Event` (контракт вида `event`, `Emitter`, шина) в ядре ещё нет, эмитить нечего;
вместе с `stub(Contract, impl)` он уезжает в волну 6, после портов. Форма
`app.call` и поле `stubs:` («токен → значение») выбраны так, чтобы оба легли
аддитивно. Дельта-спеки влиты: `test-composition-root`, `graph-overrides-pruning`,
`structural-check`, `module-isolation-testing`, `testing-subpath-convention`,
`container-accessor-contract`. См. change `testing-package`.

[31.07.2026] Фичи, `assemble` и фазовый lifecycle: гарантия `dispatch` вместо конвенции (features).

Корень приложения был конструктором `new App({ transports: Record<string,
ITransport>, modules, config })`, а транспорт уходил в эфир нульарным
`transport.listen()`. Обе поверхности противоречили `design/composition.md` §2,§4
и `design/transports.md` §1 и делали модульный монолит невыразимым: транспорты —
мешок в конструкторе (зависимости им не инжектнуть, lifecycle App гонял руками
`Promise.all`, «какие транспорты существуют» — независимая ось конфига), `listen()`
— footgun (ничто не мешало повесить go-live на `@OnInit` и уйти в эфир до
регистрации ручек), а выбора подмножества фич не существовало вовсе. Предпосылки
были готовы: дискавери из дерева модулей (#8) и конфиг (#9, точка привязки
временно жила в `AppConfig.config`).

Ключевое наблюдение change'а: ~80% модели уже было бесплатно. Модули — значения,
значит фича — значение, а выбор подмножества — фильтрация массива; контейнер
жадный, значит «не выбрал фичу → её провайдеры не построились» получается само.
Новой машинерии контейнера не добавилось, кроме одного хука `@OnStart`.

**Гарантия go-live держится составом данных, а не проверкой.** `Dispatch`
рождается в фазе WIRE и разделён по составу, а не по времени передачи: `routes` —
проекции деклараций без `handle`/`pipeline`/`deps` (провод: роутинг и парсинг по
io-декларации и bind-карте), `call(pattern, ctx, options?)` — исполнение (ядро).
Транспорт получает объект только аргументом `serve(dispatch, signal)`, то есть в
START; до этого исполнимых ручек у него нет физически. Вариант «два канала»
(`ITransport.endpoint(def)` в WIRE + `dispatch` в START), как буквально читался
`transports.md` §1, отвергнут: второй канал отдавал бы транспорту **полную**
декларацию с хендлером, и гарантия снова висела бы на честном слове транспорта.
Отвергнут и «dispatch как непрозрачный пропуск, который нужно предъявить» —
гарантия должна быть следствием состава данных, а не проверки. Побочный выигрыш:
ветка «декларация без pipeline», продублированная в HTTP и CLI, уехала в ядро;
`DispatchOptions` (`exposeErrorDetails`, `onUnknownFail`) — свойства границы,
поэтому едут аргументом транспорта, а не хранятся в `dispatch`. Формулировка §1
`transports.md` уточнена по факту: WIRE строит таблицу `pattern→handler` — она и
**есть** `dispatch`, в START она только передаётся.

**Транспорт — обычный провайдер.** `http()`/`cli()` возвращают провайдер, а не
инстанс: зависимости (секция `HTTP_PORT`/`HTTP_HOST`) инжектятся контейнером,
lifecycle гоняется по графу. Множество транспортов **выводится**: токены,
упомянутые декларациями после `select`, ∪ токены провайдеров из `transports:`;
отдельной оси конфигурации нет. Семейство `Transports(name)` + `Family.all`
отвергнуто: семейство — один рецепт на всех членов, а транспорты приезжают
разными классами из разных пакетов, и собирать их пришлось бы рецептом-
диспетчером по имени — ровно та рантайм-магия, которой в ядре нет. Поле
`transport` декларации стало нести токен; чтобы `@nestling/pipeline` не зависел
от `@nestling/transport`, ядро типизирует его как токен неуточнённого типа, а
транспортный пакет уточняет до `TokenString<ITransport>`; строковое имя выводится
из id токена и продолжает ехать в `Raw.transport`/`EndpointMeta.transport` —
пользовательские слои не сломались. Capability negotiation как отдельная механика
исчезла: HTTP-ручка без HTTP-транспорта в графе — тот же fail-fast на ASSEMBLE,
что и любая незарегистрированная зависимость.

**Фазы стали адресуемыми.** `0 BOOTSTRAP → 1 ASSEMBLE → 2 INIT → 3 WIRE →
4 START → 5 RUN → 6 SHUTDOWN`, фазы 0–1 fail-fast (ошибка сборки предшествует
захвату ресурсов), SHUTDOWN — строгий реверс: `signal` → `close()` транспортов в
обратном порядке → `container.destroy()`. `@OnStart` — третий хук контейнера,
по топосорту, после того как все `@OnInit` завершились: «wiring между init и
start» стал свойством графа. Фаза 0 осталась вне `assemble` — `select`
вычисляется до сборки, и чтобы это не требовало ручного `process.env`,
`@nestling/config` получил примордиальное `load(section)`: синхронное чтение
ключей секции из env с валидацией и fail-fast, без контейнера и без привязанных
источников. Это единственное пред-сборочное чтение конфига.

**`select` — замыкание без магии.** `dependsOn` принимает значения-фичи, а не
имена: строковая ссылка потребовала бы глобального реестра фич — того самого,
которого нет и для эндпоинтов (#8). Транзитивно достижимые фичи участвуют в
выборе, даже если не перечислены в `features:`. Цикл в `dependsOn` легален —
это «без чего фича не работает», а не порядок построения. Fail-fast на
неизвестном имени (с перечнем доступных), одноимённых фичах, пустом выборе
(`''`/`[]`: «ничего» пишется отсутствием `features`, а не пустой строкой) и
`select` без `features`.

Публичный корень зафиксирован: `assemble({ modules?, providers?, features?,
select?, transports?, config? })` — единственная точка, каждое поле опционально,
L0-приложение не упоминает ни фич, ни конфига. `new App(...)` перестал быть
поверхностью не проверкой, а типами: конструктор принимает внутренний
`AssemblyPlan`, тип которого не экспортируется. Поля `plugins`/`policies`/
`dispatch` аддитивны и приедут своими change'ами (#13, #28, #11).

BREAKING — три поверхности сразу, все предписаны целевым design'ом и поставлены
одним change'ом, чтобы после #10 корень был зафиксирован: исчезает конструктор
`new App({ transports: Record })`, исчезает нульарный `listen()` вместе с
точками регистрации ручки на транспорте, поле `transport` декларации несёт токен
вместо строки. Проверка форм io против способностей транспорта переехала на
ASSEMBLE (для `App`) и в `serve` до открытия сокета (standalone) — одна
реализация, один текст ошибки; прежняя точка (`endpoint()`/`route()`) ушла
вместе с методом. Дельта-спеки влиты: новые `composition-root`,
`feature-bundles`, `lifecycle-phases`, `transport-providers`,
`dispatch-guarantee`; изменены `endpoint-discovery`, `endpoint-declarations`,
`transport-form-capabilities`, `lifecycle-metadata-idempotency`,
`app-shutdown-abort`, `config-sources-binding`. Все четыре примера переведены на
`assemble` (`app-with-http` — витрина L2 с фичами и `select`), добавлен гайд
`docs/guides/composition.md`. См. change `features`.

[31.07.2026] Конфигурация как token families: секции, keys-capability, `ConfigSource` (config-module). Открывает волну 4.

Конфигурации во фреймворке не было вообще: единственной её материализацией был
ручной `valueProvider(IConfig, { … })` с захардкоженными строками в
`examples.simple-app`. `process.env` не читал ни один пакет ядра, схемной
валидации на старте не существовало, и оба инварианта фазы 0 из
`design/composition.md` — «`process.env` трогается только в config» и
«невалидный конфиг на старте = FAIL-FAST» — держать было нечем. Все примитивы
к этому моменту уже стояли: token families (#5), `Topic` в `@nestling/streams`
(#6 — пакет заводился **именно** под reloadable конфига и шину портов),
Standard Schema как схемная граница (#19).

Поставлен пакет `@nestling/config`. `makeConfig('orders', record)` объявляет
секцию **рекордом полей** с произвольными Standard-Schema-листьями:
перечислимость берётся с уровня JS-объекта, поэтому интроспекция вендорских
схем не нужна нигде (вендор-конвертеры для конфига отвергнуты записью
[2026-07-14] ровно этим аргументом). Имя ключа выводится детерминированно
(`maxItems` → `ORDERS_MAX_ITEMS`, `httpURL` → `ORDERS_HTTP_URL`),
`from('DATABASE_URL', schema)` отменяет префикс целиком — так объявляются общие
ключи. Секция — член token family: инжект `@Injectable([OrdersConfig])`
материализует узел фреймворковым рецептом, отдельной регистрации в модуле нет,
ключа `configs:` у модуля не появилось.

Четыре решения — ключевые. **Приватность — keys-capability, а не проверка на
`build()`**: право инжекта — сам токен секции (пакет его не экспортирует, чужой
инжект нечем написать — граница держится видимостью ES-модулей), право
привязки — branded-хэндл `.keys`, которым ничего не инжектишь. Понятия «владелец
секции» в модели нет: нарушение нечем выразить, значит нечего и проверять.
**Токен секции — не-инстанцируемый класс-токен** со статикой `.keys`: `design/config.md`
требует одновременно `@Injectable([OrdersConfig])` и `OrdersConfig.keys`, а
строковый токен свойств не несёт; расширение `InjectionToken` объектными токенами
отвергнуто как правка ядра контейнера в 22 местах вне закрытого breaking-окна.
**Ключи не становятся узлами графа** — перечень ключей это данные реестра, а не
рёбра: узлы-на-ключ дали бы красивый `explain()`, но сломали бы reloadable
(значение узла фиксируется на `build()`) и умножили граф на число полей.
**Читалка — обычный узел с асинхронной фабрикой**, а не фаза BOOTSTRAP: порядок
инстанцирования сам гарантирует, что `init()` источников отработал до проекции
секций — тот же аргумент, которым в журнале отвергнут хук `OnConfiguration`
(конфиг — зависимость, а не фаза).

Источники — объекты `ConfigSource { get; init?; watch?; close? }`, читаемые одной
приватной kernel-читалкой; свои координаты источник берёт из примордиального
`process.env` в `init()`, и это его единственный контакт с окружением. Привязка в
корне — плоский список `config: [[src, keys | glob]]`, порядок = приоритет, env —
неявный пол (только env → в корне про конфиг не пишешь ничего; kernel-модуль App
регистрирует всегда). До появления `assemble()` (#10) список живёт в `AppConfig` —
перенос будет одной строкой. Опечатка в глобе не молчит: читалка сверяет таргеты
с реестром и warn'ит о привязке, не покрывшей ни одного объявленного ключа —
поверхность для аудита без превращения глоба в ошибку. Канал warn'ов подменяем
(`onWarn`), чтобы предупреждения проверялись тестом.

Валидация — независимая по полям, агрегированная по секции: отказ одного поля не
прерывает проверку остальных, все проваленные поля собираются в один
`ConfigValidationError` с ключами, issues и перечнем опрошенных источников
(это же свойство потом обслужит общие ключи в #25). Отсутствие значения не
отдельный вид отказа — читалка отдаёт `undefined`, решает схема. Старт и рантайм
асимметричны намеренно: невалидное значение на старте убивает процесс, невалидное
горячее обновление — нет (секция целиком остаётся last-good, полуприменённого
состояния не возникает, уходит warn). `reloadable` — снапшот с read-latest
геттерами плюс `onChange(signal, cb)` поверх `Topic` и `AbortSignal`; инстанс
стабилен, обновление меняет поля на месте.

`validateSync` и её окружение переехали из `@nestling/pipeline` в `@common/misc`
(реэкспорт из прежнего места сохранён — публичный API не изменился): конфиг фазы 0
не должен зависеть от request-пайплайна фаз 3–5, иначе зависимость
`@nestling/config → @nestling/pipeline` инвертировала бы порядок фаз. Дельта-спеки
влиты: новые `config-sections`, `config-keys-capability`, `config-sources-binding`,
`config-reloadable`, `config-registry`; модифицирована `standard-schema-validation`.
Вне скоупа осознанно: `secret()` и семантика общих ключей (#25), кросс-полевые
инварианты секции (открытый вопрос записи [2026-07-14]), готовые источники
(`file()`, `vault()`) — пакетами поверх `ConfigSource`. См. change `config-module`.

[31.07.2026] Стриминг: `stream` ≠ `events`, io-декларация — дерево форм (streaming-v2). Закрывает волну 3.

набором `stream`/`withFiles`/`files`, где multipart описан двумя разными
модификаторами, лимит файла брался из общего `maxBodySize`, а поэлементная
валидация жила только на входе и только в HTTP-парсере — выход не
валидировался вовсе, хотя схема описывает провод в обе стороны.

Поставлены четыре вещи. (1) **`stream` ≠ `events`** — различие объявляется
в декларации и определяет и framing (NDJSON против SSE с heartbeat, `id:`
и приёмом `Last-Event-ID` в типизированный стартовый контекст), и семантику
завершения: нормальный исход `stream` — `completed`, `events` —
`disconnected`. (2) **io-декларация — дерево форм**
`value | stream | events | multipart({ fields, files })` с листьями
Standard Schema; валидация по форме, поэлементно и **в обе стороны**;
маппинг форм на media types детерминирован и отдаётся как данные — вход
для OpenAPI (#20) и клиента (#22). (3) **Item-цепочки на io-декларации** —
закрытый инфраструктурный словарь (`tap`/`filter`/`limit`/`gapTimeout`/
`throttle`/`batch`/`through`) без фаз: у элемента нет «хендлера
посередине». (4) **`Topic`** в новом пакете `@nestling/streams` без внешних
зависимостей — bounded buffer + `AbortSignal`, публикация не ждёт медленного
подписчика; источник событий остаётся обычным singleton-провайдером, особого
вида endpoint'а для него не заводится.

Три решения — ключевые. **Асимметрия цепочек по schema-first**: входная
вправе менять тип (её результат и есть форма хендлера), выходная — только
`T → T`, потому что оба её конца зафиксированы схемой; ограничение
обеспечивается типами в точке декларации, а не рантайм-проверкой. **Исход
потокового ответа честен**: `.finally` для потоковых форм откладывается до
момента, когда поток дотёк, оборвался или был закрыт потребителем, — а
значит, обязанность транспорта потребить итератор или закрыть его
`return()` стала частью контракта, и вместе с ней детерминированными стали
`try/finally` в хендлере-генераторе и отписка от `Topic`. **Capability
биндинга — данные, а не конвенция**: транспорт объявляет поддерживаемые
формы раздельно для входа и выхода, несовместимая декларация падает при
регистрации, до приёма запросов; богатство объявляется в контракте, а не
сужается до пересечения способностей всех транспортов — из этого же
правила стриминг по шине портов в V1 даёт внятную ошибку сборки вместо
тихой деградации. Отвергнуто: RxJS на публичных границах (границы остаются
`AsyncIterable`, а `merge`/`switchMap`/`combineLatest` — dataflow, его
место в хендлере) и поэлементная логика через фазы request-pipeline.
Kernel-набор кодов пополнен `STREAM_LIMIT_EXCEEDED` и `STREAM_GAP_TIMEOUT`:
иначе страж границы из #15 превращал бы штатный отказ лимита в
`500 UNKNOWN`.

BREAKING по четырём пунктам: `withFiles()`/`files()` удалены в пользу
`multipart()`/`upload({ maxSize, mime, multiple })`, и payload multipart-ручки
сменил форму (`{ data, files }` → `{ fields, files }` с файлами по именам
полей); `analyzePayload`/`PayloadConfig` заменены описателем формы, знающим
`events` и `multipart`; `.finally` у потоковых ручек вызывается позже;
`ITransport` получил обязательное `capabilities`. Non-goals: реестр подписок
(#7 — намеренно satellite поверх этих примитивов), стриминг по шине (после
#11, вместе с AsyncAPI), DI в комбинаторах цепочки, streaming-клиент (#22).
Дельта-спеки влиты: новые `io-forms`, `stream-item-chains`,
`event-sources-topic`, `http-streaming-framing`,
`transport-form-capabilities`; изменены `pipeline-phase-model`,
`endpoint-declarations`, `http-input-binding`, `http-transport-limits`,
`http-request-cancellation`, `error-values`, `domain-fail-definitions`.
Открытые вопросы, оставшиеся после реализации (гранулярность байтов в
`summary`, `events` во входе, семантика `throttle` при переполнении), —
в [deferred.md](./deferred.md). Запись в `ideas.md`, закрывающая вопросы
журнала (политика `Topic` для медленного подписчика; дефолт и форма opt-out
поэлементной валидации; политика невалидного элемента), подготовлена, но
**не внесена**: по правилу CLAUDE.md она ждёт явного «запиши» — до тех пор
эти решения зафиксированы артефактами change'а и этой записью. См. change
`streaming-v2`.

[31.07.2026] Модель ошибок: `Fail` — значение, контракт отказов закрыт (error-model). Первый change волны 3.

Модель ошибок расходилась на трёх уровнях: превью обещало Result-семантику
(`return charge`, `charge.isFail`), типы её не знали (`Output<T>` не включал
`Fail`, поля `isFail` не существовало), а `normalizeResponse` знал только
`instanceof Ok` — из-за чего **возвращённый `Fail` уезжал клиенту как
`200 OK` с сериализованным телом ошибки**. Это был баг, а не недоделка, и
он же задавал приоритет: change поставлен первым в волне 3.

Поставлено четыре связанных вещи. (1) **Возврат ≡ бросок**: возвращённый
отказ уходит на error-track до `.ok`-юнитов, так что инвариант «`.ok` видит
только успех» держится на обоих путях. Дискриминант `isFail` — обычное
свойство, а не `instanceof`: на проводе класс мёртв, поле выживает.
(2) **Две оси у отказа**: `status` («как отвечать транспорту», словарь
пополнен `CONFLICT`/`TIMEOUT`/`TOO_MANY_REQUESTS` → 409/504/429) и `code`
(«что именно случилось»), плюс `cause` для обёртывания исходной ошибки.
(3) **`defineFail`** даёт доменный отказ как значение — конструктор,
схема `details`, предикат `.is()`, брендированный тип `Fail<'CODE',
Details>`; идентичность по коду, поэтому распознавание переживает границу
процесса. Определение создаётся без побочных эффектов и влияет на
приложение только через `errors:`. (4) **`errors:` в декларации** —
типизированный канал: из списка выводится `E` в `Output<T, E>` и второй
зарезервированный ключ `meta.fail(e: E): never` (ранний выход, сохраняющий
анализ control flow).

Ключевое решение — **страж на границе**, а не церемония на каждом
провайдере: всё, что доехало до границы незадекларированным (прямой
`throw`, отказ из глубины сервисов, JS-обход типов), нормализуется в
`UnknownError`; оригинал целиком уходит в диагностический хук
`onUnknownFail`, клиенту — generic-тело. Warn-and-pass отвергнут: смысл
в том, что множество ответов ручки **закрыто** — `E ∪ UnknownError ∪
kernel-коды`, и клиент может на это опираться. Страж стоит после всех
`.catch`-юнитов и до `.finally`: `.catch` — легальное место, где
недекларированный отказ становится контрактным. Kernel-коды (`UNKNOWN`,
`VALIDATION_FAILED`) входят в множество неявно — иначе страж превратил бы
штатный 400 валидации в 500; набор закрыт и растёт только вместе с ядром.
Отвергнуты (в журнале идей): `throws:`-декларации провайдеров с графовой
проверкой и иерархия классов исключений с `@Exception`/`@Throws` — обе
чужеродны values-идиоме, `instanceof` не переживает провод.

BREAKING по трём пунктам: возвращённый `Fail` больше не `200 OK`;
незадекларированный отказ на границе отвечает 500 `UNKNOWN` вместо
собственного статуса (ручки с ad-hoc `Fail.*` обязаны либо объявить отказ,
либо оформить его в `.catch`); `Output`/`OutputSync` получили второй
тип-параметр. Раскрытие `message`/`details` без `exposeErrorDetails`
осталось привилегией **задекларированного** отказа. Non-goals: ре-гидрация
remote-`Fail` (едет с #11 `ports`), wire-формат RFC 9457 (отложен),
раскладка `errors:` в OpenAPI-responses (#20). Дельта-спеки влиты:
новые `error-values`, `domain-fail-definitions`, `endpoint-error-contract`;
изменены `error-response-safety`, `pipeline-phase-model`,
`endpoint-declarations`, `endpoint-handler-di`,
`http-request-validation-errors`. См. change `error-model`.

[31.07.2026] Бюджет на DX типов pipeline (pipeline-type-dx). Закрывает breaking-окно волны 2.

Шестой и последний change окна: снапшоты диагностик и порог tsserver имеют
смысл только поверх уже зафиксированных типов, поэтому он шёл после
#19/#17/#8/#24/#21. Замеры показали, что риск, названный внешним ревью
([d/06 §6](../history/discussions/06-critical-design-review.md)), не
гипотетический, а уже реализовавшийся: 50 слоёв вложенной композиции —
476 561 514 инстанциаций, 41.55 s проверки, `34× TS2589` и hover ~40 s. То
есть заявленный потолок вложенности не «медленный», а **не компилируется**.
Pre-тракт при этом бесплатен (цепочка из 50 `.pre` — +64 K к базе): взрывалась
именно вложенность.

Корень оказался не в сложности накопления input, а в **форме сигнатуры**:
`compose` был объявлен через `A extends AnyPipeline` и доставал тип-параметры
условными типами (`ReqOf`/`AccOf`/`NeedsOf` над фантомным `$types`), поэтому
каждый уровень вложенности переразворачивал всю цепочку заново. Переход на
прямой вывод — параметры объявлены как `Pipeline<RA, AA, NA>`, тип-параметры
выводятся из аргумента — дал на том же графе 64 286 инстанциаций / 0.80 s /
hover 83 ms: ×7 400 по инстанциациям и ×470 по латентности редактора. Call-site,
арности (2–4 слоя), рантайм и результирующие типы не изменились; сломались
только тесты типов внутри репозитория, ссылавшиеся на старые поля литерала.

Второй симптом того же корня — текст диагностики. Четырёхполевой литерал
(`ERROR`/`MISSING_FIELDS`/`OUTER_PROVIDES`/`INNER_REQUIRES`) плюс хвост
`& PipelineBuilder<...>` называл проблему, но топил её в шуме: `MISSING_FIELDS`
был юнионом ключей **без типов** (а при несовместимом типе существующего поля
вырождался в `never` — случай просто не диагностировался), два поля дублировали
то, что видно наведением на аргументы. Форма схлопнута до двух полей:
`__error` — текст, `missing` — **рекорд «поле → его тип»**; для перезаписи поля
pre-юнитом — `conflicting`. Литерал разворачивается принудительно (`Simplify`
как часть контракта: именованный алиас TypeScript печатает именем, пряча
текст), из позиции параметра ушло пересечение `& B` — при этом вывод
тип-параметров внутреннего слоя сохраняется, TypeScript берёт кандидатов из
ветвей условного типа. Та же форма — в pre-тракте и в `ValidateStart` слота
`pipeline` HTTP-транспорта: одна форма во всех точках отказа.

Гарантией читаемости сделан **снапшот текста**, а не assert-тесты типов
(`expectTypeOf`/`tsd` проверяют факт ошибки, а не то, как она читается):
каталог фикстур заведомо неправильных композиций компилируется одной
программой компилятора, нормализованный текст диагностик сравнивается со
снапшотами, усечение длинных типов не отключается — фиксируется ровно то, что
видит пользователь. Стоимость типов стала числом с порогом
([BUDGET.md](../../packages/nestling.pipeline/type-tests/BUDGET.md)): два
измерения разной строгости — детерминированные счётчики компилятора как
**дельта к пустому файлу** (жёсткий порог ×4 к замеру; абсолюты зависят от
версии TS и `lib.d.ts`) и латентность реального tsserver (щедрый потолок ×24,
ловит регрессию на порядок, а не дрожание машины). Пороги читаются раннером из
самого BUDGET.md — подвинуть порог, не оставив записи замера с датой и версией
TS, нельзя. Прогон — отдельный nx-таргет в составе `yarn verify`, каталог
`type-tests/` исключён из `build` и `lint` (намеренные ошибки компиляции их не
валят). Дельта-спеки влиты: новые `pipeline-type-diagnostics` и
`pipeline-type-budget`, усилено требование о проверке требований слоя в
`pipeline-composition`. Вариадический `compose(...layers)` не вводился — замер
показал, что дорога именно вложенность, а не потолок арности.

[30.07.2026] Канон размещения HTTP-input и плоская bind-карта (input-bind). BREAKING.

Пятый change breaking-окна волны 2 и конец приёма «поле берётся отовсюду». До
него payload собирала `mergePayload(body, query, params)`: одноимённый ключ в
двух источниках давал `PayloadConflictError` → 400, а сам merge был
**необратим** — по декларации нельзя было сказать, где живёт поле. Это не
только implicit contract (контракт ручки шире, чем задумывал автор, и сузить
его нечем), но и прямая блокировка двух даунстримов: генератору OpenAPI (#20)
неоткуда взять `parameter` vs `requestBody`, типизированному клиенту (#22) —
куда класть поле при сборке запроса. Внешнее ревью назвало HTTP-модель
слабейшим местом дизайна ([d/06 П.4](../history/discussions/06-critical-design-review.md)).

Канон — детерминированная функция `(шаблон пути, метод, пометки) → место` с
приоритетом: совпадение имени поля с path-параметром шаблона → путь; явная
пометка → её место; всё остальное → query для методов без тела
(`GET`/`HEAD`/`DELETE`/`OPTIONS`/`TRACE`) и body для остальных. Заголовки —
только по пометке и никогда конвенцией (`header()` отложен, см.
[deferred.md](./deferred.md)). Пометки — значения-марки `query()`/`body()` в
поле `bind` словаря, а не обёртки схемы и не строки: марку внутрь вендорского
shape не положить (zod принимает только `ZodType`, а прочитать чужой shape
нечем ни у одного вендора — граница, зафиксированная `standard-schema`, #19),
а марка-значение переживает добавление `header('If-Match')` с аргументом без
смены носителя. Ключи `bind` при этом типизированы схемой через
`InferInput<I>`: опечатка в имени поля и пометка на path-параметре — ошибки
компиляции; рантайм-дубли тех же правил оставлены для JS-потребителей и
непрозрачного `input`.

Носитель — плоская `HttpBinding` `{ method, path, fields, rest, rawBody }`:
явные размещения плюс правило для остального. Перечислить все поля карта не
может (ключей схемы в рантайме нет), но **тотальна как правило** — у каждого
поля есть место. Разворачивается она **при создании декларации**, а не при
регистрации в `App`: клиент импортирует контракт без серверного кода и обязан
получить карту из одного импорта. Ядро остаётся HTTP-слепым —
`EndpointOptions`/`EndpointDefinition` получили непрозрачное `binding`,
которое `makeEndpoint` переносит, не интерпретируя; типизирует и читает его
транспорт (`httpBindingOf`). Отвергнуты: пятый generic-параметр декларации
(тип-шум в каждой сигнатуре) и складывание карты в `EndpointMeta` (это
pipeline-facing структура, а карта нужна клиенту, пайплайна не импортирующему).

Приём стал strict: `payload = { ...restSource, ...markedFields, ...pathParams }`
с фиксированным приоритетом, который в конфликт не превращается — поле не в
своём месте просто не попадает в payload и падает обычной валидацией схемы.
`mergePayload` и `PayloadConflictError` удалены как класс задач, вместе с
`merge.ts`/`merge.spec.ts`; требование «конфликт ключей → 400» вычеркнуто из
`http-request-validation-errors`. Побочный эффект: тело читается только когда
его требует карта — у `GET` без `body()`-пометок не буферизуется вовсе. Для
`withFiles` правило то же: path-параметры и query-пометки подмешиваются к
полям формы до валидации. Заодно починен тихий баг — повтор query-ключа
(`?tag=a&tag=b`) больше не теряется в last-wins: `getAll` даёт массив, ноль
вхождений остаётся отсутствием (чтобы работали `.optional()` и дефолты), а
`query({ multiple: true })` даёт массив и при одном вхождении.

`rawBody: true` — opt-in, меняющий **тип** стартового контекста:
`Start = rawBody extends true ? { rawBody: Uint8Array } : EmptyInput`, и слой
проверки подписи объявляется как `makePipeline<{ rawBody: Uint8Array }>()`.
Простой типизации слота не хватило: `TReq` у `Pipeline` ковариантен через
фантомное `$types`, поэтому забытая пометка прошла бы молча — слот сторожит
условный тип `ValidateStart` в позиции параметра (техника `ValidateCompose`).
Байты читаются один раз под тем же `maxBodySize` и значение парсится из них
же; со `stream`/`files`/`withFiles` — fail-fast. Альтернатива «всегда класть
байты в raw» отвергнута: память платили бы все ручки, а гарантия стала бы
конвенцией «не забудь pre-юнит». Точка входа байтов в контекст —
четвёртый параметр `makeEmptyContext` (стартовый input, дефолт пустой).

Fail-fast при создании декларации доведён до предела, достижимого без
интроспекции: пометка на path-поле, `body()` у метода без тела, `bind` или
path-параметр при неструктурном `input` (`stream`/`files`/примитивы),
path-параметр при отсутствии `input`, `rawBody` со стримом и multipart.
Правило «path-параметр без поля в схеме — ошибка сразу» в полном виде
недостижимо (перечня ключей у схемы нет) — реализована его решаемая часть,
остаток задокументирован как известное ограничение и передан кандидатом в
`openapi` (#20), где вендор-конвертер структуру уже знает. Дельта-спеки влиты:
новый `http-input-binding`, модифицированы `endpoint-declarations` и
`http-request-validation-errors`. Примеры пополнены показательными кейсами —
`search-users` (GET → query) и webhook-ручка с `rawBody` и проверкой
HMAC-подписи; гайды `http-app-di.md` и `http-functional.md` пересверены. Вне scope осознанно: `header()` (deferred), генерация OpenAPI
(#20) и сборка запроса клиентом (#22) — оба читают произведённую здесь карту,
`http:`-биндинг контракта (`ports`, #11 — та же функция разворачивания,
но поле не заводится), коерсия провод-строк (`?page=2` → `number`) как
ответственность автора схемы, формы io (`streaming-v2`, #6) и CLI-биндинг.
См. [архив change'а](../../openspec/changes/archive/2026-07-30-input-bind/).

[30.07.2026] Декларации endpoint'ов — значения (endpoint-model). BREAKING.

Четвёртый change breaking-окна волны 2 и конец двух параллельных стилей
деклараций. До него классовый путь (`@Endpoint`/`@HttpEndpoint` +
`implements IEndpoint`) принимал только `App`, функциональный (`makeEndpoint`)
— только standalone-транспорты: `AppModule.endpoints` был типизирован
`Constructor<IEndpoint>[]` и значений не брал. Обе поверхности сводились к
одному и тому же `EndpointDefinition{handle}`, но классовая надстройка стоила
~600 строк (декораторы, WeakMap-метаданные, `IEndpoint`, резолв инстансов) и
×2 к докам, примерам и тестам. Решающий довод — не размер, а перманентное
свойство TS: **декоратор не влияет на типы**, поэтому всё продающее в дизайне
(schema-first вход/выход, типизированная `meta`, `Output<T, E>`, контракты)
классовой декларации доставалось бы вечной `implements`-церемонией.

Канон — per-transport конструкторы: `httpEndpoint({ method, path, input,
output, pipeline, deps, handle })` и `cliEndpoint({ command, … })`.
Транспортный словарь легален и типизирован только здесь — пайплайн и хендлер
остаются транспорт-слепыми. `path` берётся литеральным типом, имена
path-параметров извлекаются из шаблона на уровне типов; в конструкторе
оставлена явная точка расширения, куда `input-bind` (#21) внесёт
разворачивание bind-карты. Ошибки словаря (пустой `path`, путь без ведущего
слэша, дублирующийся `:param`, пустая команда) бросаются **в момент создания
значения**, а не на старте приложения. Общая машинерия не размазана по
транспортам: `makeEndpoint` остаётся kernel-примитивом (нормализация форм
`handle`, `deps`, гашение, бренд), конструкторы — надстройки над ним. Из
пользовательского канона `makeEndpoint` ушёл, из экспортов — нет.

Удалены `@Endpoint`, `@HttpEndpoint`, `IEndpoint`, `EndpointMetadata`,
`getEndpointMetadata`, `getHttpEndpointMetadata`, `HttpEndpointOptions`,
`HttpEndpointMetadata`, `makeHttpEndpoint` и symbol-ключ `nestling:handler`.
Метаданных на классах больше нет — вместе с ними ушёл остаток
endpoint-registry, начатый в `endpoint-discovery` (#8). `endpoints:` модуля
принимает значения, `makeAppModule` перестал подмешивать эндпоинты в
`providers`: инстанцировать нечего. Отличить декларацию от постороннего
значения позволяет неперечислимый symbol-бренд — элемент `endpoints:` без
бренда даёт ошибку старта с именем модуля и индексом в массиве; молчаливого
пропуска нет.

DI хендлера — поле `deps` и три формы `handle`: голая функция
`(input, meta) => …`; каррированная фабрика `deps: […]` +
`(…deps) => (input, meta) => …`, где внешний вызов происходит **один раз на
сборке** и замыкание играет роль инстанса; класс под `@Injectable` с методом
`handle`, резолвимый контейнером. Класс — форма подключения DI, а не второй
стиль деклараций: декларация во всех трёх случаях одно и то же значение, а
`implements` не нужен, потому что сверка сигнатуры со схемами идёт в точке
декларации. Хендлер тестируется без фреймворка — фабрику зовут с фейками
напрямую, класс создают через `new`.

Standalone-гарантия переехала в типы. `EndpointDefinition` получил параметр
неразрешённых зависимостей (дефолт `never`, симметрия с `TNeeds` у
`Pipeline`), и `server.route()` / `ITransport.endpoint()` принимают только
deps-free декларацию. Параметр накапливает не только токены `deps` и
класс-хендлер, но и **классы-юниты пайплайна**: после слияния метаданных и
декларации в одно значение это единственное место, где различимы «пайплайн,
требующий `bind`» и «исполнимый пайплайн», — без этого standalone-приём терял
бы compile-time-гарантию. Гашение — `endpoint.resolve(resolver | [instances])`,
возвращающий **новую** декларацию; исходная не мутируется, поэтому одну
декларацию можно погасить дважды разными наборами. Класс-форма и юниты
требуют резолвер-формы (позиционному массиву нечем их инстанцировать) и
говорят об этом текстом ошибки. `App` гасит зависимости контейнером на старте
одним шагом — `pipeline.bind` вызывается изнутри `resolve` тем же резолвером,
— и падает до приёма запросов, называя паттерн ручки, модуль-объявитель,
недостающую зависимость и способ починки.

Дискавери переехала со значений-конструкторов на декларации: транспорт и
паттерн читаются с самой декларации, `DiscoveredEndpoint` несёт её вместо
конструктора и метаданных. Проверка «класс с метаданными эндпоинта вне
`endpoints:`» удалена как беспредметная — метаданных нет, отличить забытую
ручку от обычного провайдера нечем; неиспользуемая декларация ловится
`noUnusedLocals`, а «каждая объявленная ручка обслуживается» — предмет
`policy-check` (#28) на собранном графе. Требование «объявленный эндпоинт
обязан резолвиться контейнером» не исчезло, а переехало в
`endpoint-handler-di` и расширилось на `deps` и класс-хендлер.

Онтология «контракт первичен» зафиксирована в доках, а не в коде:
per-transport конструкторы описаны как сахар «анонимный контракт +
`implement`»; сам `makeContract`/`implement` приезжает с `ports` (#11).
Дельта-спеки влиты: новые `endpoint-declarations` и `endpoint-handler-di`,
модифицирован `endpoint-discovery`. Примеры переведены: `examples.app-with-http`
(9 эндпоинтов) — с декораторов на `httpEndpoint` с сохранением
классов-хендлеров как демонстрации DI-формы, `examples.simple-http-server` и
`examples.simple-cli` — с `makeEndpoint` на транспортные конструкторы; гайды
`http-app-di.md`, `http-functional.md`, `cli.md` пересверены. Вне scope
осознанно оставлены: bind-карта и strict-приём (`input-bind`, #21 — рантайм
`mergePayload`/`PayloadConflictError` здесь не тронут), «транспорт токеном»
(`features`, #10 — транспорт по-прежнему адресуется строкой), формы io
(`streaming-v2`, #6), `errors:` в контракте (`error-model`, #15),
CLI-политика `missing: 'prompt'`. См. change `endpoint-model`.

[29.07.2026] Дискавери эндпоинтов из дерева модулей (endpoint-discovery). BREAKING.

Третий change breaking-окна волны 2. Множество обслуживаемых эндпоинтов задаёт
состав контейнера, а не граф импортов. Глобальный `Set`
(`metadata/endpoint-registry.ts`) удалён вместе с `registerEndpoint`,
`getAllEndpoints` и `clearEndpointRegistry`; `@Endpoint`/`@HttpEndpoint`
перестали само-регистрироваться — декоратор только пишет метаданные класса.
Эндпоинт обслуживается, только если перечислен в `endpoints:` модуля,
достижимого из `modules` приложения.

Протечка была структурной, а не косметической: реестр наполнялся при любом
транзитивном импорте (barrel, тест, соседний модуль), `App.#registerEndpoints`
итерировал его и падал на `container.get()` для класса, чей модуль в контейнер
не регистрировали. Дискавери был ортогонален составу собранного приложения —
ровно то, что ломает выбор подмножества модулей, ради которого затевается
ветка модульного монолита.

`@nestling/app` получил чистую функцию `discoverEndpoints(modules)`:
depth-first обход `modules` + `imports`, `imports` раньше собственных
эндпоинтов, дедупликация модулей по имени (зеркало
`ContainerBuilder.registerModule` — «обнаружено» не расходится с «собрано»),
пометка на входе гасит цикл `A → B → A`, дедуп конструктора внутри модуля,
детерминированный порядок. Результат — значение, а не побочный эффект: список
`{ endpoint, metadata, moduleName }` плюс карта «требуемый транспорт → его
ручки». Считается без контейнера и транспортов, поэтому обход тестируется
напрямую и годится как шов для `features` (#10) и policy-check на полном
графе (#28). `makeAppModule` перестал терять `endpoints` — возвращаемое
значение теперь `AppModule extends Module` с сохранённым полем (классы
по-прежнему дублируются в `providers`, чтобы контейнер их инстанцировал).

Три молчаливых режима стали ошибками старта, и каждая называет
модуль-объявитель: класс в `endpoints:` без метаданных эндпоинта (был
`console.warn` + skip), класс **с** метаданными, попавший в `providers` мимо
любого `endpoints:` (иначе миграция даёт молча необслуженную ручку; провайдеры
из `ProvidersFactory` не линтуются — до `build()` их состав неизвестен, и
ограничение задокументировано), недостающий требуемый транспорт (текст
называет транспорт, паттерн ручки и модуль). Сконфигурированный транспорт, на
который дискавери не дала ни одной ручки, остаётся легальным и поднимается: у
него есть маршруты и помимо дискавери (`HttpTransport.route()`). Изоляция
тестов стала структурной — `clearEndpointRegistry()` из `beforeEach` ушёл
вместе с реестром.

Форма деклараций не менялась: `@Endpoint`, `@HttpEndpoint`, `IEndpoint` и
`makeEndpoint` остались, `endpoints:` по-прежнему принимает конструкторы —
уход на per-transport конструкторы-значения это следующий change
`endpoint-model` (#24), с которым декораторы и умрут. Новая capability
`endpoint-discovery` влита в основные спеки целиком (8 требований: источник
дискавери, модуль-значение, правила обхода, форма результата, три fail-fast'а
и обязанность резолвиться контейнером). Целевое состояние —
[design/container.md](../design/container.md) («глобальных реестров-при-импорте
нет») и [design/composition.md](../design/composition.md) §1; логика —
ideas.md «[2026-07-08] Модульный монолит: фичи, `select`, дискавери из дерева
модулей», разбор — [discussions/05 §1](../history/discussions/05-modular-monolith-features-ports.md).
См. [архив change'а](../../openspec/changes/archive/2026-07-29-endpoint-discovery/).

[29.07.2026] Pipeline: отказ от фазы `.after` (pipeline-drop-after). BREAKING.

Второй change breaking-окна волны 2. Словарь ответного тракта сведён к
Promise-тройке `.ok`/`.catch`/`.finally`: постпроцессор, обработчик ошибок,
наблюдатель исхода. `.after` — единственный член словаря без аналога у
`Promise` — удалён вместе с типом `AfterUnitFn` из публичного экспорта
`@nestling/pipeline`; в рантайме `ResponsePhase` сужен до `'ok' | 'catch'`,
а проверка применимости схлопнулась до одного сравнения
`(entry.phase === 'ok') === response.isSuccess`.

Ниша фазы оказалась пуста после двух более ранних решений: границы
«pipeline = значения, transport = байты» и правила «ответный тракт не меняет
тип value». Наблюдение на любом исходе — это `.finally`, маппинг ошибок —
`.catch`, обогащение успеха — `.ok`; работы, которую делал бы только `.after`,
не осталось. Зато цена была: `ok`/`catch`/`after` — не три фазы, а один
список с применимостью по текущему ответу, и `.after` был единственной
причиной, по которой это правило не формулировалось одним предложением.
Использований не было ни в middleware пакета, ни в примерах — только в спеках.

Миграция: `.after(u)` → `.ok(u).catch(u)`. Сигнатура совпадает (свой слой
`Partial`, возможность заменить ответ), поэтому замена механическая.
Единственное расхождение задокументировано: если `u` бросит в роли ok-юнита,
ответ станет ошибкой и `u` исполнится второй раз уже как catch-юнит, тогда
как `.after` исполнялся ровно один раз — потенциально бросающую функцию
не регистрируют в обе фазы одним значением.

Семантика оставшихся фаз не менялась. Тесты `.after`-сценариев переписаны
на `.ok`/`.catch` без потери покрытия, добавлены рантайм-проверки порядка
при ответе-ошибке в композиции, применимости по текущему ответу и двойного
вызова `.ok(u).catch(u)`. Текст рантайм-guard'а `pre()` теперь перечисляет
актуальный словарь. Дельта-спеки влиты: `pipeline-phase-model` (словарь,
type-state, правило исполнения), `pipeline-composition` (порядок при
композиции, добавлен сценарий ответа-ошибки), `request-abort-signal`
(редакционно — перечень фаз, которым доступен `ctx.signal`). Целевое
состояние — [design/pipeline.md](../design/pipeline.md); логика и отвергнутые
варианты — ideas.md «[2026-07-10] Pipeline: отказ от `.after`».
См. [архив change'а](../../openspec/changes/archive/2026-07-29-pipeline-drop-after/).

[29.07.2026] Схемы: Standard Schema вместо привязки к zod (standard-schema). BREAKING.

Первый change breaking-окна волны 2. Ядро больше не знает про валидатор:
`Schema` в `@common/misc` — это `StandardSchemaV1`, `Infer`/`DomainType` идут
через `InferOutput`, а валидация — вызов `schema['~standard'].validate(value)`.
Вендорские типы (`z.ZodType`, `z.infer`, `ZodError`) из публичных сигнатур
ушли; `zod` убран из `peerDependencies` пяти пакетов ядра и из единственного
рантайм-импорта (`middlewares/meta.ts`), оставшись devDependency там, где его
импортируют тесты. Единственная схемная зависимость — types-only
`@standard-schema/spec`, а сам тип реэкспортирован из `@common/misc`, чтобы
потребителю не требовалось ставить пакет спеки.

Ключевое свойство спеки, определившее дизайн: Standard Schema даёт валидацию
и инференс, но **не интроспекцию**. Схема в рантайме — чёрный ящик, поэтому
всё, что требует знания структуры, в ядро не попало (конвертеры в JSON Schema
поедут отдельными пакетами с change `openapi`). Следствие: `InferSchemaType`
схлопнут до `~standard` (yup, у которого спеки нет, выпал из поддержки), а
дак-тайп `interface Schema<T> { parse(data): T }` из `EndpointMeta` удалён —
он лгал (в `input` клали и модификаторы, и примитивы).

Вся валидация сведена в одну функцию `validateSync` (`@nestling/pipeline`):
через неё идут `parsePayload`/`parseMetadata`, юнит `validate()`, поэлементная
валидация NDJSON-потока и fallback-ветки транспортов без pipeline — прямых
`schema.parse(...)` в ядре и транспортах не осталось, так что одна и та же
невалидная запись даёт одинаковую ошибку на любом пути. `SchemaValidationError`
несёт `issues: readonly { message, path? }[]` вместо поля `zodError`; путь
нормализуется при конструировании (сегмент-объект `{ key }` → `key`, символ →
строка, индекс остаётся числом), поэтому `issues` JSON-сериализуемы и уезжают
в `details` 400-ответа без вендорских `code`/`expected`/`received`.

Граница «ошибка входа vs ошибка конфигурации» проведена явно. Синхронность
валидации — гарантия: thenable из `validate` даёт `AsyncSchemaNotSupportedError`
вместо Promise, уехавшего handler'у вместо значения. Объект без `~standard`
(или с чужой версией) даёт `NotAStandardSchemaError` с внятной причиной, а не
`TypeError` о чтении свойства у `undefined`. Оба класса намеренно **вне**
иерархии `SchemaValidationError` — транспорт отдаёт на них 500 с маскировкой
деталей по политике `error-response-safety`, а не 400.

BREAKING по трём точкам: `SchemaValidationError.zodError` больше не существует
(есть `issues`), схемы обязаны реализовывать Standard Schema v1 (zod ≥ 3.24 /
4.x — да, yup — нет), async-схемы перестали молча работать. Дельта-спеки влиты:
новая capability `standard-schema-validation`, уточнено требование «Schema
validation failures keep 400» в `http-request-validation-errors`. Целевое
состояние — [design/schemas.md](../design/schemas.md) §1; логика и отвергнутые
варианты — ideas.md «[2026-07-13] Схемы: Standard Schema вместо привязки к
zod». См. [архив change'а](../../openspec/changes/archive/2026-07-29-standard-schema/).

[29.07.2026] Multi-injection: `Family.all` — узел-агрегат семейства (multi-injection).

Инжект массива независимо зарегистрированных вкладов закрыт без флага
`multi: true` и без side-effect-реестра. `Family.all` — сентинел-токен семейства
(`"HealthCheck:{all}"`, тип `TokenString<readonly T[]>`); вклад остаётся обычным
провайдером с членским токеном (`classProvider(IHealthCheck('db'), DbHealthCheck)`),
который любой модуль регистрирует сам, не правя центральное место.

Механика: на `build()`, строго после фикспоинта материализации членов и до
инстанциации, билдер регистрирует на каждый упомянутый в deps сентинел обычный
factory-провайдер с deps = токены всех зарегистрированных членов семейства и
значением — замороженным массивом их инстансов. Дальше агрегат неотличим от
прочих узлов: проверка циклов (цикл через агрегат печатает путь, а не только
входной токен), топологические `init()`/`destroy()`, `toJSON()`/`traverse()`,
визуализация, `strictExports`. Узел безмодульный, поэтому вклад чужого модуля
требует `exports` — «модуль контрибьютит в семейство» стало явным контрактом.

Границы. Агрегат deps-driven: неупомянутый `.all` узла не порождает (`get()` →
`null`) и материализацию членов не форсит — в массив попадают только члены, у
которых есть узел. Три открытых вопроса записи ideas.md закрыты: пустое
семейство → `[]` (узел без deps, сборка успешна); порядок — порядок регистрации
(явные вклады, затем материализованные фикспоинтом); форма инжекта —
`readonly T[]`, имя вклада — забота самого вклада. Токен `.all` и параметр
`{all}` зарезервированы: собственный провайдер на агрегатный токен и
`Family('{all}')` — ошибки.

Не BREAKING: аддитивное свойство семейства, новая фаза `build()` и новые ошибки
на ранее невозможных формах записи; поведение собранных контейнеров не менялось.
Демонстрация — семейство health-check'ов в `examples.simple-app` с вкладами из
`module:database` и `module:api`; гайд —
[guides/di-token-families.md](../guides/di-token-families.md). См. change
`multi-injection`.

[28.07.2026] Token families, `.auto` и strictExports в контейнере (token-families).

Параметризованные провайдеры перестали быть ручным паттерном. `makeTokenFamily`
даёт семейство токенов (`ILogger('users')` → мемоизированный `Logger:users`),
`familyProvider(family, recipe)` регистрирует ОДИН рецепт на всё семейство, а
`build()` получил фазу материализации: собирает членов, упомянутых в deps
зарегистрированных провайдеров, вызывает рецепт ровно раз на уникальный параметр
и регистрирует результат обычным узлом графа. Дальше член неотличим от обычного
провайдера — дедупликация, циклы, lifecycle, атрибуция к модулю, визуализация.
Сбор итеративный (провайдер из рецепта сам может зависеть от членов) с жёстким
лимитом в 100 раундов: самоподпитывающийся рецепт даёт диагностику, а не зависание.

Ключевые границы. Рецепт возвращает готовое определение провайдера, а не
`{ deps, factory }`: переиспользуется существующий словарь (`valueProvider` для
заглушки в тестах, `classProvider` с lifecycle), а единственный риск формы —
чужой `provide` — закрыт build-time проверкой с внятной ошибкой. Членство
определяется реестром семейства, а не парсингом id: `makeToken('Logger:users')`
членом не является (ошибка «provider not found» с подсказкой про семейство).
Материализация только от deps: член без потребителей не создаётся, `get()` для
него возвращает `null` — контракт аксессоров не менялся.

`Family.auto` — consumer-aware сахар: `@Injectable([ILogger.auto])` резолвится в
`ILogger('<ИмяКласса>')` в момент декорирования, закрывая нестовский
`transient + INQUIRER` без transient-скоупа. Вне классового `@Injectable`
сентинел запрещён (ошибка регистрации с подсказкой на явный вызов), анонимный
класс — ошибка при декорировании.

`new ContainerBuilder({ strictExports: true })` — opt-in lint рёбер готового
графа против `exports` модулей: кросс-модульное ребро на неэкспортированный
токен собирает нарушение, все нарушения приходят одной ошибкой. Отсутствующий
`exports` = ничего не экспортировано (иначе lint беззуб именно там, где нужен);
`exports: [Family]` экспортирует всех материализованных членов. Это проверка на
сборке, а не рантайм-инкапсуляция: в `get()` и при инжекте проверок нет.

Не BREAKING: всё аддитивно (новые экспорты, необязательный параметр конструктора,
расширение типов `Module.exports`/`providers`); поведение по умолчанию не
изменилось. `examples.simple-app` мигрирован с ручного `Set` + `ProvidersFactory`
на семейство, `UserRepository` демонстрирует `.auto`. Гайд —
[guides/di-token-families.md](../guides/di-token-families.md). См.
[архив change'а](../../openspec/changes/archive/2026-07-29-token-families/).

[07.07.2026] Pipeline v2: плоские фазы, слои, compose (pipeline-v2). BREAKING.

`definePipeline().use(middleware)` заменён на `makePipeline()` со словарём
фаз `.pre/.ok/.catch/.after/.finally` (вид юнита виден в декларации, она
читается сверху вниз как план исполнения). Ответный тракт появился в
рантайме впервые: ответные юниты применяются к текущему ответу и могут
его заменить (`.ok` — успех успехом, `.catch` — ошибку ошибкой; gate и
восстановление Fail→Ok — осознанные ограничения v1). `.finally` наблюдает
исход `completed | disconnected | aborted | failed` (v1: вычисляется после
ответной фазы, до фактической отправки; точный момент «всё дотекло» —
в streaming-v2). Честная опциональность: `.ok` видит полный ctx,
`.catch`/`.after`/`.finally` — свой слой Partial, внешние слои — полными.

Слои: один `makePipeline()` = один слой; `compose(outer, ..., inner)` —
pre снаружи внутрь, ответные и finally изнутри наружу; требования слоя
(`makePipeline<{identity: User}>()`) проверяются компилятором в точке
композиции. `TNeeds` (третий тип-параметр): классы-юниты резолвятся
контейнером на старте App (`bind`), standalone-транспорты принимают
только исполнимый пайплайн — двухуровневость фреймворка видна в типах.

`executeWithHandler` сохранил сигнатуру (миграция транспортов — типы);
`meta.signal` и `exposeErrorDetails` перенесены без изменений; причины
аборта типизированы (`ClientDisconnectedError`/`TransportClosingError`).
Удалена мёртвая ветка `@Middleware`/middleware-registry/
`AppModule.middleware` (DI-резолв не был реализован; роль занял `TNeeds`).
Мигрированы транспорты, App, все examples и гайды. См. change `pipeline-v2`.

[07.07.2026] meta.signal — сигнал отмены запроса насквозь (abort-signal).

В `meta` каждого хендлера появился гарантированный `signal: AbortSignal`
(ключ зарезервирован; без транспортного сигнала подставляется never-aborted).
Его взводят: HTTP-транспорт при дисконнекте клиента (`'close'` на response
при недописанном ответе) и `close()` транспорта при graceful shutdown —
per-request и transport-level источники объединяются через `AbortSignal.any`,
реестр in-flight контроллеров не нужен. `App.close()` не менялся: отмена
in-flight — обязанность транспорта внутри его `close()`; `CliTransport`
взводит свой сигнал при `close()`. Отмена кооперативная: force-close по
`closeTimeout` остаётся fallback'ом.

Поведенческое изменение `close()`: сигналы in-flight запросов взводятся
до дренажа, кооперативное завершение — основной механизм. Попутно закрыта
дыра дренажа: keep-alive соединение, освободившееся после начала `close()`,
Node сам не закрывает — добавлена периодическая зачистка
`closeIdleConnections()` в окно дренажа. Это предпосылка streaming-v2
(item-цепочки и `events(T)` описаны в терминах `meta.signal`).
См. change `abort-signal`.

[07.07.2026] Internal 500 error details hidden by default (transport-hardening).

Раньше `Pipeline.errorToResponse` под захардкоженным `isDevelopment = true`
всегда клал `error.message` и `error.stack` в тело 500-ответа, а верхний catch
HTTP-транспорта отдавал `error.message` для любых ошибок. Это утечка внутренних
деталей на любом публичном окружении.

Теперь необработанные (не `Fail`) ошибки по умолчанию дают
`{ "error": "Internal server error" }` без message/stack. Раскрытие включается
явной опцией `exposeErrorDetails` (свойство окружения: опция транспорта →
`executeWithHandler`, а не поле переиспользуемого Pipeline). `CliTransport`
передаёт `true` (локальный инструмент). `Fail` не затронут — его message/details
автор раскрыл осознанно.

Поведенческое изменение (не BREAKING по API): клиенты/тесты, полагавшиеся на
текст 500-ответа, его больше не увидят. Заодно ошибки входа классифицированы
корректно: битый JSON и конфликт ключей payload → `400`, превышение
`maxBodySize` → `413` (вместо прежних `500`). См. change `transport-hardening`.

[07.07.2026] Container: атрибуция провайдеров, идемпотентность lifecycle, контракт get() (container-fixes).

Три точечных дефекта `@nestling/container` из аудита 2026-07-06, не зависящих от
целевого дизайна (token families — отдельный change). (1) **Функциональные
провайдеры модуля теряли принадлежность**: `appendFactoryProviders()` регистрировал
их без имени модуля (`module: undefined` в графе → «ничьи» узлы, `strictExports` их
не увидел бы). Теперь имя модуля прокидывается — метка и признак `exported` те же,
что у провайдеров-массивом. (2) **Lifecycle-метаданные накапливались per-instance**:
`@OnInit`/`@OnDestroy` писали имя метода в `addInitializer`, который по стандарту ES
выполняется на каждый инстанс → N инстансов давали N дублей хука → `init()`/`destroy()`
вызывался N раз (проявлялось при нескольких сборках/семействах). Запись сделана
идемпотентной (раз на метод класса). (3) **Контракт аксессоров**: `get()` возвращает
`T | null` (JSDoc ошибочно заявлял `@throws` — контракт `getOrThrow()`); `getOrThrow()`
теперь проверяет наличие УЗЛА графа, а не truthiness — легитимные `0`/`''`/`false`
больше не дают ложный not-found. Не BREAKING (публичный API не изменился; поправлено
ошибочное поведение). Дельта-спеки влиты: `container-module-attribution`,
`lifecycle-metadata-idempotency`, `container-accessor-contract`. См. change
`container-fixes`.

[07.01.2026] Endpoint classes instead of Controllers.

Switched from @Controller with @Endpoint methods to @Endpoint on classes. Main reasons:
1. TypeScript method decorators cannot check parameter types against schemas due to type system limitations
2. @Endpoint on class constructors allows checking the entire class shape through constructor constraint
3. One class = one endpoint (Single Responsibility) - better isolation and testability
4. Both functional style (app.endpoint) and class style (@Endpoint) provide full type checking

Controller approach (multiple endpoints in one class) violates SRP and lacks compile-time type safety. Endpoint approach is more explicit and type-safe.

[27.09.2025] Modules as plain objects.

Modules make dependency tree much more complex if they are class with dependencies. My take is that modules are just blueprints, that shouldn't work in application runtime. No lifecycle hooks, no injection, etc.

There are some doubts though:
1. Maybe we'll need hooks that should work when all module providers are initialized or destroyed. We always have option to extend configuration object and `makeModule` function
2. Maybe we'll need something like `configure` function which can be used by plugins to extends app functionality. But this doesn't seem to be ID-container's business.

Module metadata will be preserved. We will always know what module is source of any provider.

One thing that i had in my mind - remove modules from container and make them next layer of abstraction. But in this case we won't be able to protect module scopes (everything will be global!)
