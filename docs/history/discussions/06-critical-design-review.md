# 06 · Критическое ревью целевого дизайна (внешний взгляд)

**Дата:** 2026-07-13.
**Формат:** ревью документации (`design/` + `decisions/` + `guides/` на момент
коммита `2c158e2`), выполнено Claude по запросу. Сравнение с NestJS, Fastify
и соседями по экосистеме. Реализация на момент ревью отстаёт от дизайна —
ревью оценивает именно **намерение**, не код.

---

## Общий вердикт

Дизайн — один из самых дисциплинированных в open source: журнал решений с
отвергнутыми вариантами, статусные плашки, «папка = статус». Ядро идей (жадный
контейнер, видимость через ES-модули вместо рантайм-инкапсуляции, pipeline без
`next()`, Fail-как-значение, `dispatch` рождается в WIRE) — цельное и внутренне
консистентное.

Главные риски системные, а не точечные:

1. заявка «меньше NestJS» уже не соответствует фактическому скоупу — kernel
   разросся (порты, шина, select-топологии, reloadable-конфиг, async-context);
2. самая базовая часть — HTTP-модель endpoint'а — недоспроектирована по
   сравнению с амбициозной надстройкой: нет path-параметров, типизации
   query/headers, дизайна OpenAPI, версионирования контрактов.

---

## Что сделано сильно (лучше конкурентов)

- **Явный массив зависимостей вместо `reflect-metadata`** — убирает класс
  нестовских проблем (инжект по интерфейсу, `emitDecoratorMetadata`, магия
  компилятора). Цена (дублирование списка) — осознанный trade-off.
- **Видимость через ES-модули** — элегантнее нестовских `exports`: нарушение
  нельзя даже написать. Keys-capability для конфига — красивое развитие
  (разделить объект с двумя правами на две capability).
- **Pipeline v2** — отказ от onion/`next()` с сохранением типизированного
  накопления контекста решает реальные боли (скрытый control flow, «headers
  already sent», три разных «after»). Запись про отказ от `.after` — образец
  инженерного мышления.
- **Стриминг на `AsyncIterable`** с pull-backpressure и границей «Rx — в
  хендлере, не в ядре» — прямой ответ на нестовские Rx-интерцепторы.
- **Модель ошибок** (Fail-значение, code-идентичность, ре-гидрация на проводе,
  нормализация в `UnknownError`) — закрытое множество `E ∪ UnknownError`
  сильнее, чем у кого-либо в экосистеме, кроме Effect.
- **Testing-пакет**: `stub(Contract)` с валидацией по схеме контракта и прунинг
  осиротевших поддеревьев в `assembleTest` — обе идеи выдающиеся.

## Критика

### 1. «Меньше NestJS» — уже неправда

Суммарная поверхность целевого дизайна (контейнер + families + `.all`,
pipeline v2, стриминг + `Topic`, конфиг с reloadable/vault/глобами, features +
select, контракты + порты + три dispatch-политики + NATS, async-context,
error-model, testing) — **больше** концептуальной поверхности ядра Nest.
Fastify выиграл нишу противоположной стратегией: крошечное ядро + плагины.
18 changes в roadmap при отстающей реализации — профиль проекта, который
рискует умереть недостроенным. Прогрессивное раскрытие L0–L4 отвечает на это
по оси *пользователя*, но не по оси *мейнтейнера*. Предложение: жёсткая черта
«kernel 1.0» (L0–L1 + pipeline + error-model + streaming), L3–L4 — спутник со
своим темпом.

### 2. Endpoint-only pipeline противоречит «guarantee over convention»

«Нет уровней App/module» куплено ради compile-time проверок, но следствие
записано в ideas.md честно: сквозные инварианты становятся **конвенцией**.
Для requestId терпимо, для **аутентификации** — нет: забытый `authed`-слой на
одном endpoint'е — каноническая уязвимость, и дизайн защищает от неё хуже
нестовского глобального guard. Startup policy-check везде помечен «отложено» —
по собственной логике фреймворка он обязан быть в v1, вместе с `detached:` как
явным opt-out. Самое сильное внутреннее противоречие дизайна.
*(Обсуждение и предложения — см. продолжение этой дискуссии.)*

### 3. HTTP-модель — самое слабое место

`RequestContext` содержит `headers`, `query`, `body` — и **ни слова о
path-параметрах**; ни один пример не показывает `GET /users/:id`. Единственная
`input`-схема — и как она распределяется по частям HTTP-запроса, не определено
нигде (Fastify разделяет `body`/`querystring`/`params`/`headers`). Смежное:

- типизация **ответных заголовков** (`Ok.created(user, {Location})` есть, но в
  контракте endpoint'а заголовков нет — они вне schema-first);
- `transports.md` §1 всё ещё описывает `.ok/.after` после решения drop-after;
- **OpenAPI трижды упомянут как «бесплатно» — а дизайна генерации нет.** Это
  главный кэш-аут schema-first; «бесплатно» не бывает (anyOf для
  `E ∪ UnknownError`, стримы, multipart — всё требует решений).

### 4. Жёсткая привязка к zod — упущение по DX и производительности

Экосистема сошлась на **Standard Schema** (zod/valibot/arktype): фреймворк
может принимать любую совместимую библиотеку. Хардкод zod — анахронизм на
старте. Отдельно перф: идентичность Fastify построена на компилируемой
валидации (ajv) и сериализации (fast-json-stringify); zod в горячем цикле
медленнее. Output-схема уже есть — компилируемая сериализация напрашивается.
Если перф не входит в позиционирование — записать как осознанный не-goal.

### 5. Порты и L4: history is not on your side

Дизайн портов — лучший виденный вариант location transparency (всегда async,
всегда Fail-able, без транзакций, биндинг на сборке). Но: **Service Weaver**
(Google, та же идея) заархивирован в конце 2024; Moleculer остался нишевым.
Проблема не в error-path (закрыт), а в том, что co-located и split различаются
*профилем*. В дизайне отсутствуют:

- **deadline propagation** — бюджет времени через `meta`, уменьшающийся на hop
  (есть `signal`, нет дедлайнов);
- **retry/idempotency на контракте** — `command` без ключа идемпотентности при
  redelivery — дыра;
- **версионирование контрактов** — при split поды с разными версиями схем;
  без правил эволюции L4 в эксплуатации не живёт;
- **outbox/saga** — упомянуты, но точка интеграции не определена.

### 6. Типовая машинерия pipeline — недооценённый DX-риск

Монотонное накопление + `Partial` на ответном тракте + требования слоёв в
`compose` + `TNeeds` — уровень сложности tRPC-middleware и Effect Layer вместе.
Известные последствия: нечитаемые ошибки в точке композиции, деградация
tsserver, хрупкость при обновлениях TS. Нет бюджета на диагностику
(snapshot-тесты сообщений об ошибках, замеры tsserver). Плюс два параллельных
стиля (классы и `make*`) удваивают поверхность доков/примеров/тестов навсегда.

### 7. Конфиг: два незакрытых угла

(а) `from('DATABASE_URL')` позволяет двум секциям читать один ключ с разными
схемами — семантика коллизии не определена; (б) **секреты** — нет `secret()`
для редактирования значений в логах/`explain()`/доках.

### 8. Мелкие несостыковки доков

- `guides/http-functional.md` документирует `.after` — формально честно (гайд
  следует коду), но стоит пометить «уходит, см. pipeline-drop-after»;
- пока жив баг «возвращённый `Fail` → `200 OK`» (roadmap #15), гайды учат
  `throw Fail`, а design-доки L3 показывают `return charge` — читатель двух
  документов получает противоречивые привычки.

## Сравнение с соседями

**NestJS.** Чинятся реальные боли: module-церемония и `forRoot`/`DynamicModule`
(модуль — значение, параметризация — функция), request-scope bubbling (запрещён
by design), Rx-интерцепторы (AsyncIterable), зоопарк
guards/pipes/interceptors/filters (один pipeline + `.catch`), `forwardRef`
(жадный граф). Честное «архитектурно лучше». Чего Nest даёт, а nestling нет:
глобальные инварианты (см. §2 критики), экосистема готовых модулей, низкий
порог входа (CLI-генераторы, однозначное «как принято»).

**Fastify.** Пересечение — транспортный слой (оба на find-my-way). Fastify —
это перф (компилируемые схемы), инкапсуляция деревом плагинов, хуки уровня
приложения. Ответ nestling на инкапсуляцию (ES-модули) элегантнее; по перфу и
app-хукам — позади без явного решения.

**tRPC / ts-rest / oRPC / Elysia+Eden / Hono RPC.** Ближайшая родня по духу:
pipeline с накоплением ctx ≈ tRPC-middleware; `makeContract` ≈ ts-rest
contract. У всех есть **типизированный клиент из контракта** — главный драйвер
adoption; у nestling его нет (см. предложение 1).

**Encore.ts / Service Weaver / Moleculer.** Родня по L2–L4. Encore.ts
показывает, что «декларативная инфраструктура + типизированные API + локальный
дашборд» продаётся как целостный DX; Service Weaver — предупреждение, что
location transparency сама по себе не удерживает пользователей.

**Effect.** Модель ошибок nestling — «Effect по духу без Effect по цене»:
закрытое множество ошибок без монадического рантайма. Правильная середина.

## Предложения (по убыванию ценности)

1. **Типизированный клиент из endpoint'ов/контрактов** (`@nestling/client`).
   Всё уже есть: схемы input/output, `errors:` в контракте, `Ok|Fail`. Клиент
   с типами `E ∪ UnknownError` на вызов — то, чего нет ни у Nest, ни у
   Fastify; это же закрывает «порт наружу» (фронтенд — ещё один потребитель
   контракта). Дешевле остальных больших фич, максимальный эффект.
2. **Standard Schema вместо жёсткого zod** на всех границах
   (`input`/`output`/`defineFail.details`/`makeConfig`). До реализации —
   почти бесплатно; после — breaking.
3. **Policy-check и `detached:` — в v1** + рецепт auth в гайдах (первый вопрос
   любого пользователя).
4. **Дизайн-док HTTP-модели**: params/query/headers в input, типизированные
   ответные заголовки, content negotiation, cookies.
5. **Дизайн-док OpenAPI/AsyncAPI-генерации** поверх `explain()`/реестра:
   default-ответ из `UnknownError`, `errors:` → responses, `stream/events` →
   media types.
6. **Версия + правила эволюции схем контрактов** для L4 (additive-only,
   проверка совместимости в `.check()`-матрице CI).
7. **Deadline propagation + идемпотентность**: `meta.deadline` рядом с
   `meta.signal`; `idempotencyKey` для `command`.
8. **Health/readiness из фаз lifecycle**: readiness = «дошли до RUN»,
   liveness = «SHUTDOWN не начался» — почти бесплатно, продаёт в k8s.
9. **`secret()` в makeConfig** + семантика коллизий общих ключей.
10. **Wire-формат ошибок — RFC 9457 (problem+json)**: `code`/`status`/
    `details`/`requestId` ложатся почти один в один.
11. **Бюджет на DX типов**: snapshot-тесты ошибок компилятора в точке
    `compose`, замер tsserver на графе ~50 слоёв/эндпоинтов — до фиксации
    публичного API.

## Продолжение (2026-07-13): пункты 3 и 4

### П.3 — почему «база + compose» и линтер не дают гарантию

- Глобальный base-пайплайн + `compose` решает **переиспользование**, не
  **гарантию**: ничто не обнаруживает endpoint, который не композировался от
  базы (или композировался не от той — `base` vs `authedBase`). «Этот endpoint
  должен быть защищён» — не свойство типов хендлера: хендлер, не использующий
  `identity`, типобезопасен и с auth, и без ⇒ нужна политика, а не типы.
- **Линтер (ESLint)** — хорош как editor-фидбек, плох как основа: пайплайны —
  значения, текущие через фабрики и параметры; документированный паттерн
  «модуль-фабрика с параметром `pipeline`» статически непроверяем в точке
  объявления (значение известно только в call-site). Плюс `eslint-disable`,
  «работает если настроен».
- Гарантия должна жить на **собранном графе** (фаза ASSEMBLE), где все значения
  материализованы: проверка точна по построению. Прецедент жанра в самом
  дизайне — `strictExports` («build-time lint на готовом графе»). `.check()`
  (testing-пакет, фазы 0–1) даёт тот же прогон в CI на матрице select-топологий.
- Эскиз: `assemble({ policies: [everyEndpoint({transport:'http'}).hasLayer(authedBase)] })`;
  идентичность слоя — по ссылке на значение (слои экспортируются константами);
  opt-out — `detached: '<причина>'` (строка обязательна; App печатает список
  detached-ручек на старте — поверхность для аудита). Двухслойно: ESLint-правило
  для буквальных случаев — подсказка, policy-check — гарантия.
- Статус: подход согласован концептуально; в ideas.md не записан.

### П.4 — merge уже реализован; принят подход «канон + bind-карта»

- **Находка в коде:** `mergePayload(body, query, params)` в
  `transport.http/src/merge.ts` уже сливает всё в единый payload (конфликт
  ключей → 400). Критика ревью уточнена: проблема не «нет params», а
  **необратимость** merge: «поле принимается отовсюду» — implicit contract
  (та же категория, что отвергнутый warn-and-pass в error-model), а OpenAPI и
  типизированному клиенту нужно каноническое место каждого поля.
- **Принято в обсуждении:**
  - канон — детерминированная функция `(pattern, метод, пометки) → размещение`:
    совпадение с path-параметром → путь; пометка → указанное место; остальное —
    query для GET/HEAD/DELETE, body для POST/PUT/PATCH; заголовки — только по
    пометке, никогда конвенцией;
  - сахар-пометки (`query(...)`, `header(...)` в схеме — ход `from()` из
    makeConfig) разворачиваются при регистрации в плоскую **bind-карту** —
    несущий уровень, который потребляют транспорт/OpenAPI/клиент и который
    переживает переход на Standard Schema (при непрозрачной схеме bind-карта
    пишется руками);
  - **strict-приём**: payload собирается только из канонических мест —
    enforcement бесплатен (поле не в том месте = обычная ошибка валидации),
    `PayloadConflictError` исчезает как класс;
  - fail-fast при регистрации (path-параметр без поля в схеме, пометка на
    path-поле, body-пометка у GET);
  - query-массивы: повтор ключа → массив, поле-массив оборачивает одиночное
    значение (чинит тихий last-wins повторных query-ключей в
    `transport.ts:323`).
- **Заголовки**: граница meta vs input — ambient-контекст (`Authorization`,
  tracing) остаётся в meta через pre-юниты; per-call параметр операции
  (`If-Match`) — кандидат в input через `header()` в bind. `header()` из v1
  канона исключён — отложен, логика и триггеры возврата:
  [decisions/deferred.md](../../decisions/deferred.md).
- Статус: подход согласован; запись в ideas.md — отдельным «запиши».

## Продолжение (2026-07-13): пункты 5, 6, 7

### П.5 — порты: deadline, идемпотентность, версионирование

Приняты (запись в ideas.md «Порты: deadline, идемпотентность, версионирование
контрактов»):

- **deadline** — gRPC-модель: `meta.deadline` рядом с `meta.signal`,
  абсолютный момент внутри процесса, относительный timeout по проводу
  (clock skew); fail-fast `DeadlineExceededError` до вызова; код встроенный,
  уровень фреймворка;
- **идемпотентность** — `idempotencyKey` в meta для `command`, ключ едет
  через транспорт; дедупликация — satellite, не ядро;
- **версионирование** — версия явно в имени контракта (`user.create.v2`);
  проверка совместимости в `.check()`-матрице **подсвечивает** breaking
  changes, но не блокирует. Отвергнут additive-only как жёсткий gate:
  breaking должен быть видимым, а не невозможным.
- **outbox/saga** — отложены с эскизом точки интеграции (satellite-обёртка
  emitter'а + relay в lifecycle):
  [decisions/deferred.md](../../decisions/deferred.md).

### П.6 — типовая машинерия

- **Два стиля**: уходим от двойного стиля — канонический стиль деклараций
  функциональный (`make*`); классы остаются DI-формой (провайдеры,
  юниты-классы), не стилем деклараций. Запись в ideas.md «Один канонический
  стиль деклараций». Попутно снят открытый вопрос модели ошибок о привязке
  `E` к классовому endpoint'у.
- **Бюджет на DX типов** (snapshot-тесты ошибок компилятора в точке
  `compose`, замер tsserver, типы-ошибки в стиле tRPC/Elysia) — сначала
  отложено («из текста предложения ценность неочевидна»), затем **принято**
  после демонстрации на примерах (до/после для ошибки в `compose`). Запись в
  ideas.md «Бюджет на DX типов pipeline».

### П.7 — конфиг

Принято (запись в ideas.md «Конфиг: `secret()` и общие ключи»):

- **`secret(schema)`** — редактирование в `explain()`/логах/доках; без
  брендирования типа в v1 (бренд — возможное аддитивное ужесточение);
- **общие ключи** — разделяемый read-only ресурс: независимая валидация
  каждой секцией, fail-fast на старте, `explain()` показывает читателей;
  единственный конфликт сборки — несогласованный `reloadable`; секретность
  общего ключа — по объединению.
