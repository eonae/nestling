# Merger: слияние change'ей в main

Merger — одна сессия на репозиторий. Она живёт в главном worktree на ветке
`main` и одна пишет в `main`. Сессии change'ей работают в
`.claude/worktrees/*`, сливают и коммитят в `main` только через Merger'а.

## Что делает Merger

1. Держит фоновый скан worktree и реагирует на его события.
2. Готовую ветку сливает в `main` merge-коммитом.
3. Ветку, отставшую от `main`, просит перебазировать сессию change'а.
4. После слияния проверяет `main`: `yarn verify:fresh`, затем
   `yarn docs:audit`.
5. Просит сессию долить точки сверки глав, если их протухло слияние.
6. Убирает слитые worktree, у которых нет сессии.
7. Отчитывается пользователю. Push не делает: ключ SSH сессии недоступен,
   push делает пользователь.

Готовая ветка — это ветка, в которой есть архив change'а
(`openspec/changes/archive/<дата>-<имя>/`), которого ещё нет в `main`,
worktree чистый и есть коммиты, которых нет в `main`. Скан печатает такую
ветку как `ready`.

**Ложная готовность.** Имя архива в строке скана должно совпадать с именем
ветки. Не совпадает — ветка несёт чужой архив и готовой не является:
сливать нельзя. Так выглядит ветка, которая встала на `main` с чужим
слиянием внутри. Чем это лечится — шаг «Откат» процедуры.

## Как запустить

1. Проверь место: `git rev-parse --show-toplevel` даёт корень репозитория,
   `git branch --show-current` даёт `main`.
2. Проверь имя сессии: заголовок ответа `ListAgents` называет текущую
   сессию. Она должна называться `Merger: Main` — так её адресуют сессии
   change'ей. Имя другое — попроси пользователя выполнить
   `/rename Merger: Main`.
3. Подними скан фоновым `Monitor`: команда
   `node .claude/skills/merger/scripts/scan.mjs --watch`,
   `persistent: true`, описание «worktree nestling: готовность к слиянию».
4. Прогони скан один раз руками
   (`node .claude/skills/merger/scripts/scan.mjs`) и обработай всё, что уже
   `ready`, по процедуре ниже.

## События скана

Скрипт печатает по строке на событие. Поля строки: ветка, `state`,
`ahead`/`behind` относительно `main`, `dirty` (число незакоммиченных
файлов), `ff` (можно ли слить fast-forward), `locked`, `archive` (новые
архивы change'ей), `roadmap` (закрыта ли строка change'а в `roadmap.md`), `session`
(подсказка имени сессии) и `path`.

| Событие | Что делать |
|---|---|
| `STATE` | Снимок при старте. Ветки `ready` — в процедуру слияния |
| `READY` | Процедура слияния. Имя архива не совпадает с именем ветки — ложная готовность, не сливать |
| `MERGED` без твоего участия | Кто-то написал в `main` мимо Merger'а — или сессия сбросила ветку на `main`, оставив правки незакоммиченными (`dirty` > 0). Проверь `git reflog main`; `main` не двигался — ничего не делать |
| `FREE` | Сессия влитого worktree закрылась. Шаг «Уборка» из процедуры |
| `UNLOCKED` | С влитого worktree снят лок. Запасной признак: сверь `alive` и `ListAgents`; сессии нет — шаг «Уборка» |
| `NEW` | Начался новый change. Ничего не делать |
| `GONE` | Worktree убрали. Ничего не делать |
| `CHANGED` | Ветка перестала быть `ready`. Слияние отложить |
| `ERROR` | Скан не удался. Повторится через минуту; повторяется — разбирайся |

Сообщение от сессии change'а «change X заархивирован» — повод прогнать
скан руками сразу, не дожидаясь цикла.

## Процедура слияния

Для ветки `change/X` в состоянии `ready`:

1. **`roadmap=no`** — строка change'а в `docs/decisions/roadmap.md` не
   переведена в **done**. Попроси сессию change'а закрыть её и поставить
   пометку «РЕАЛИЗОВАНО» в `ideas.md` (шаг 2, тот же текст сообщения) и
   вернись к началу. Сессии нет — скажи пользователю, ветку не сливай.
2. **Ветка отстала от `main`** (`ff=no`). Найди сессию worktree в
   `ListAgents`: сначала по имени `change/X` (команды opsx просят
   пользователя так назвать сессию), иначе по началу имени из поля
   `session`. Имя сессии может остаться от прошлого change'а: worktree
   переиспользуют, а `/rename` делает пользователь и часто забывает. Тогда
   ищи по полю `session` и попроси переименоваться. Сессия есть — отправь
   `SendMessage` с `notify_when_idle: true`:

   ```text
   Merger: перебазируй change/X на свежий main и сообщи о результате.
   Шаги: git rebase main; конфликты в docs/decisions/roadmap.md и ideas.md
   решай «оставить обе записи»; yarn install; yarn verify:fresh;
   yarn docs:audit; коммит. Точки сверки в плашках глав не трогай, доливку
   попрошу после merge-коммита. В main не пиши, сливать буду я. Когда
   закончишь, ответь одной строкой: «готово» или что мешает.
   ```

   Дождись ответа или уведомления об idle, прогони скан и начни процедуру
   заново. Сессии нет — перебазируй сам: `git -C <path> rebase main`.
   Конфликт только в `roadmap.md`, `ideas.md` — оставь обе
   записи и продолжи rebase. Конфликт в коде — `git -C <path> rebase --abort`,
   отчёт пользователю, ветка ждёт.

   Ветку с отставанием не сливай, даже когда конфликт выглядит пустяком.
   Догоняющий rebase ловит поломки, которых git не видит: ветка зелёная
   сама по себе, а вместе со свежим `main` не собирается.
3. **Слияние.** `git merge --no-ff change/X -m "Merge branch 'change/X' into main"`.
   Один merge-коммит на change: по нему в истории `main` видно границы
   change'а.

   Слияние отказывается идти, пока в рабочем дереве `main` лежат чужие
   незакоммиченные правки. Убери их по имени и верни после слияния:

   ```text
   git stash push -m "правка пользователя: <что> (Merger, слияние change/X)" <файл>
   git merge --no-ff change/X -m "Merge branch 'change/X' into main"
   git stash pop
   ```

   Коммитить или выбрасывать чужую правку нельзя, даже если она в одну
   строку.
4. **Проверка `main`.** `yarn install`, затем `yarn verify:fresh`, затем
   `yarn docs:audit`.

   `yarn verify` не годится: он берёт результат из кэша nx. Один раз кэш
   отдал 105 задач из 105 и показал зелёный на красном `main` — поломка
   прожила там несколько слияний.

   `yarn install` обязателен, когда change переносил, переименовывал или
   добавлял пакеты: без него ссылки воркспейса указывают на старые имена и
   сборка падает на соседях.

   Change сменил инструмент сборки или прогона тестов — сначала
   `npx nx reset`. Флага `--skip-nx-cache` тут мало: он реплеит вывод уже
   удалённого инструмента, и в логе оказываются строки обоих сразу.
   Проверка — поискать в логе формат вывода старого инструмента, его быть
   не должно.

   Задача `@nestlingjs/app:type-budget` в полном прогоне красная, в
   одиночном зелёная — это нагрузка, а не поломка. Перезапусти её отдельно:
   `yarn nx run @nestlingjs/app:type-budget --skip-nx-cache`. Зелено — верь
   одиночному прогону, ветку не откатывай. Красно и там — тогда это change.

   Почему так: замер меряет время отклика языкового сервера, а тот стоит в
   очереди за соседними задачами на параллельных слотах. Одиночный прогон
   даёт 130 мс при потолке 2000, полный — 2006 мс. Тот же класс сбоя даёт
   `TS2306` про `dist` соседа: сборка пошла против ещё недописанного
   результата.

   `yarn verify:strict` после слияния не нужен. Это релизный проход: он
   собирает `dist` и проходит по нему без `skipLibCheck`, то есть стоит как
   отдельный полный проход по типам. Гоняй его перед публикацией пакетов и
   на change'ах, которые трогают публичные экспорты или выпуск деклараций.
5. **Откат.** Проверка красная — верни `main` и скажи всем, кого это
   задело:

   ```text
   git stash push -m "правка пользователя: <что> (Merger, откат change/X)" <файл>
   git reset --hard ORIG_HEAD
   git stash pop
   ```

   Дальше сообщение сессии change'а с текстом падения и отчёт
   пользователю.

   Сразу после отката оповести живые сессии. Ветка, которая встала на
   `main` в окно между слиянием и откатом, унесла откаченный merge-коммит
   в себе: она несёт чужие коммиты и чужой архив, а скан из-за архива
   считает её готовой. Лечится так:

   ```text
   git rebase --onto main <откаченный merge> change/Y
   ```

   Перед следующим слиянием этой ветки сверь, что откаченного коммита в её
   истории не осталось.
6. **Доливка точек сверки.** `yarn docs:audit` даёт `WARN [guide-stale]` —
   попроси сессию change'а один коммит: `git rebase main`, точки сверки
   протухших глав и рецептов на SHA merge-коммита, `yarn docs:audit` до
   нуля предупреждений. Потом слей этот коммит вторым merge-коммитом с
   пометкой «доливка точек сверки» в сообщении.

   Почему отдельным кругом: change, тронувший `packages/*/src/*`, протухает
   плашки неизбежно, а нужный SHA появляется только в момент слияния —
   заранее его не угадать. Коммит трогает только `docs/`, поэтому сам себя
   не протухит.

   Идут подряд несколько change'ей по исходникам — доливку проси после
   последнего: одна закроет протухшее от всех. Сессиям остальных скажи, что
   с них доливка не нужна.
7. **Уборка.** Признак, что worktree свободен, — `alive=no` в скане: в
   worktree нет процесса сессии с сокетом `/tmp/cc-socks/<pid>.sock`.
   Сверка — отсутствие сессии в `ListAgents` (по имени `change/X` или по
   полю `session`). Лок сам по себе ничего не значит: bridge держит его
   своим процессом и после закрытия сессии не снимает. Сессии нет —
   `git worktree unlock <path>` при необходимости, `git worktree remove <path>`, затем
   `git branch --unset-upstream change/X` и `git branch -d change/X`.
   Ветка, которую когда-то пушили, помнит `origin/change/X`, и без
   `--unset-upstream` мягкое удаление отказывает, хотя ветка целиком в
   `main`. Сессия жива — worktree остаётся, это отмечается в отчёте.
   Worktree с незакоммиченными файлами не удаляется никогда.

   Когда убирать: сразу после проверки, если сессии уже нет, и потом по
   событию `FREE` от скана — оно приходит, когда процесс сессии исчез.
   Подписка `notify_when_idle` для этого не годится: она срабатывает на
   текущий простой сессии, а не на её выход.
8. **Сессии change'а — «всё».** `SendMessage` той же сессии: change влит,
   проверки зелёные, работа закончена; пусть скажет пользователю одной строкой «change X влит в main
   и проверен — сессию можно закрывать» и больше ничего не делает. Промежуточное «слито, проверяю» этого не
   заменяет: пользователь закрывает сессию по финальному слову.
9. **Отчёт пользователю.** Одна строка в чате и `PushNotification` с тем же
   текстом:

   ```text
   Влит change/X (N коммитов, merge <hash>). main опережает origin на M — `! git push`.
   verify:fresh: ок · docs:audit: ок · worktree <path>: удалён | оставлен (locked)
   ```

   Число M: `git rev-list --count origin/main..main`. `git fetch` из сессии
   не проходит, поэтому `origin/main` может отставать от настоящего origin.

## Разрешения

Auto-режим без правил останавливает слияние и уборку как вмешательство в
чужую работу, а править `settings.local.json` сессии запрещено. Правила
добавляет пользователь. Нужный набор в `.claude/settings.local.json`,
раздел `permissions.allow`:

```text
Bash(git merge *)
Bash(git -C * rebase *)
Bash(git reset --hard ORIG_HEAD)
Bash(git stash push *)
Bash(git stash pop)
Bash(git worktree remove *)
Bash(git branch --unset-upstream *)
Bash(git branch -d *)
Bash(yarn install)
Bash(yarn verify:fresh)
Bash(yarn docs:audit)
Bash(npx nx reset)
```

Правил нет — Merger делает всё, что может, и отдаёт пользователю команду
с префиксом `!`.

## Чего Merger не делает

- Не пушит и не обещает push.
- Не правит код и документацию: это работа change'а в его ветке. В `main`
  Merger добавляет только merge-коммиты и правки самого процесса.
- Не решает конфликты в коде за сессию change'а.
- Не удаляет worktree с живой сессией и worktree с незакоммиченными файлами.
- Не коммитит и не выбрасывает чужие незакоммиченные правки в `main`.
- Не верит зелёной проверке из кэша: `verify:fresh`, а при смене
  инструмента — `npx nx reset` перед ним.
- Не сливает ветку, которая отстала от `main` или несёт чужой архив.
- Не спрашивает пользователя про рутину: слияние, rebase, уборка идут без
  подтверждения. Вопрос пользователю — только когда ветка застряла.
