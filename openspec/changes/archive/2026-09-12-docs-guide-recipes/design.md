# design — docs-guide-recipes

## Context

`docs/guide/` держит 27 глав, два приложения и оглавление. Главы 1–19
читаются подряд и опираются на код общего примера; главы 20–27
самостоятельны. Разделение признано оглавлением словами «часть 5
читается по потребности», но не файлами: все лежат в одной нумерации.

Замер связей показывает, что нумерация уже сдерживает содержание.

| Что измерено | Значение |
|---|---|
| Ссылок между главами внутри `docs/guide/` | 250 |
| Из них в главах 20–27 и приложениях | 96 |
| Ссылок на главы из README пакетов | 18 файлов |
| Ссылок на главы из `docs/design/` | 2 |
| Глав, ссылающихся вперёд на главу 27 | 6 |

Глава 27 «База данных и транзакция» — прямое следствие: её дописали в
конец, потому что вставить главу в середину дороже, чем добавить к
списку. Пример у неё `users-service`, то есть пример части 1, а лежит она
в части «Редкие задачи».

Целевая структура записана в
[ideas.md [2026-09-05]](../../../docs/decisions/ideas.md) «Структура
документации» и разобрана в
[d/11](../../../docs/history/discussions/11-docs-structure-and-site.md).
Это третья волна уборки из пяти; волны 1 и 2 закрыты.

Три ограничения определяют решения ниже.

1. **Генератор сайта читает одну папку.** `scripts/site/build.mjs` берёт
   `docs/guide/` константой и падает, если состав README и файлов папки
   разошёлся. Разделы и URL-пути — работа волны 4.
2. **`docs:audit` тоже знает одну папку.** Плашка «сверено с кодом»,
   полнота оглавления и ссылка плашки README пакета записаны про
   `docs/guide/`.
3. **Текст глав не переписывается.** Этот change двигает файлы и правит
   ссылки; содержание правится только там, где его делят.

## Goals / Non-Goals

**Goals:**

- Читатель видит путь из 21 главы и отдельный список из восьми рецептов.
- Глава о базе стоит там, где её читают, а не в конце.
- Вход для читателя с опытом Nest и справочник гарантий лежат в корне
  `docs/`, где их видно без оглавления гайда.
- Сборка сайта и `docs:audit` покрывают обе папки жанра.

**Non-Goals:**

- Разделы сайта, URL-пути, поиск, метаданные, бейджи разделов — волна 4.
- Публикация в GitHub Pages — волна 5.
- Переписывание текста глав по существу.
- Деление глав 10 (462 строки) и 13 (454).
- Правка README пакетов по существу.

## Decisions

### 1. Два списка: путь нумерован, рецепт назван

`docs/guide/` — путь со сквозной нумерацией в именах файлов.
`docs/recipes/` — рецепты без номеров, имя файла называет задачу
(`webhook.md`, `cli.md`). У каждой папки своё оглавление в `README.md`.

Номер решает одну задачу: он задаёт порядок чтения. У рецепта порядка нет,
поэтому номер ему только мешает — он устаревает при вставке соседа и тянет
за собой правку чужих ссылок.

Отвергнуто: **оставить общий список и пометить часть 5 в оглавлении.**
Так сегодня и сделано; пометка не мешает ни ссылке на номер, ни
дописыванию главы в конец.

Отвергнуто: **убрать номера и из глав пути.** Порядок чтения — то, ради
чего путь существует, и в имени файла он виден без оглавления.

### 2. Порядок пути и целевая нумерация

Части становятся двумя: «Сервис» на `users-service` и «Приложение» на
`app-with-http` и `split-nats`. Главы 1–10 сохраняют номер и имя файла,
остальные сдвигаются.

| Было | Стало | Часть |
|---|---|---|
| `01-first-service` … `10-auth` | без изменений | 1. Сервис |
| `27-database-and-transaction`, первая половина | `11-database` | 1 |
| `11-files-and-streams` | `12-files-and-streams` | 1 |
| `12-openapi-and-client` | `13-openapi-and-client` | 1 |
| `13-features` | `14-features` | 2. Приложение |
| `14-events` | `15-events` | 2 |
| `27-database-and-transaction`, вторая половина | `16-durable-events` | 2 |
| `15-live-feed` | `17-live-feed` | 2 |
| `16-testing-features` | `18-testing-features` | 2 |
| `17-select` | `19-select` | 2 |
| `18-split` | `20-split` | 2 |
| `19-compatibility` | `21-compatibility` | 2 |
| `20-webhook` … `26-extending` | `recipes/webhook.md` … `recipes/extending.md` | рецепты |
| `appendix-a-alternatives` | `recipes/alternatives.md` | рецепты |
| `appendix-b-from-nestjs` | `docs/from-nestjs.md` | корень `docs/` |
| `guide/README.md`, раздел «Что проверяется до первого запроса» | `docs/guarantees.md` | корень `docs/` |

Глава о базе встаёт одиннадцатой, а не сразу за конфигом, потому что её
код требует уже введённых понятий: слой `transactional` записан как
`compose(authed, db.transaction())`, транзакция читается ридером `Ctx`,
а предпосылка проверяется политикой с предикатом `hasVar`. Слой и
`compose` вводит глава 9, `authed` и политики — глава 10.

Расстановка меняет направление ссылок на главу о базе.

| Откуда и о чём | Было | Стало |
|---|---|---|
| 12 «Файлы и большие выгрузки», слой транзакции | вперёд на 16 глав | назад на 1 |
| 13 «Отдать фронтенду документацию и клиент», слой транзакции | вперёд на 15 | назад на 2 |
| 15 «Оповещать соседей», ключ идемпотентности | вперёд на 13 | вперёд на 1 |
| 6 «Откуда хендлер берёт репозиторий», транзакция запроса | вперёд на 21 | вперёд на 5 |
| 10 «Пускать только своих», приём и политика outbox'а | вперёд на 17 | вперёд на 6 |
| 8 «Убедиться, что работает», база и хранилище outbox'а | вперёд на 19 | вперёд на 3 и на 8 |

Три последние остаются ссылками вперёд. Глава 6 показывает репозиторий,
который уже читает транзакцию из контекста. Глава 8 объясняет, почему в
тестовом наборе настоящая база. Глава 10 называет слой приёма первым
применением досрочного успеха. Все шесть ссылок становятся короче:
самая дальняя ведёт на восемь глав вперёд вместо девятнадцати.

### 3. Глава 27 делится по месту в пути, а не по размеру

Граница деления проходит по предпосылкам, а не посередине файла.

| Раздел главы 27 | Куда |
|---|---|
| Соединение объявляется значением | 11 |
| Транзакция открывается пайплайном | 11 |
| Репозиторий читает транзакцию из контекста | 11 |
| Предпосылка проверяется на сборке | 11, без абзаца про плагин outbox'а |
| Схема накатывается вне процесса | 11 |
| Событие в ту же транзакцию | 16 |
| Кто отправляет запись | 16 |
| Повтор не доходит до хендлера | 16 |
| Тест не ждёт таймера | 16 |
| Что настраивается | делится: секция `database` в 11, секции `outbox` и `inbox` в 16 |
| Что осталось за кадром | делится по теме абзаца |

Первая половина не знает ни об операциях, ни о фичах и читается в части 1.
Вторая опирается на `event` и `subscriber` из главы 15 и читается сразу
за ней. Каждая половина получает своё вступление и свой раздел
«Проверка»; остальной текст переносится дословно.

Отвергнуто: **перенести главу целиком.** Тогда outbox вводится до того,
как читатель увидел события и фичи, а взаимная ссылка с главой о
событиях остаётся.

### 4. Глава 12 не делится

План волны 3 требовал разделить её надвое. Повод, записанный в d/11, —
«471 строка и девять разделов»; сегодня в ней 360 строк и шесть
разделов, а раздел про клиент занимает 75 строк. Самые большие главы
теперь другие: 27 (474), 10 (462), 13 (454).

Деление дало бы главу на 260 строк и главу на 100, причём обе отвечают
на один вопрос читателя — что отдать фронтенду. Размер сам по себе
поводом не считается: глава делится тогда, когда решает две задачи с
разным местом в пути. Это и есть случай главы 27, а не главы 12.

### 5. Два документа переезжают в корень `docs/`

`docs/from-nestjs.md` и `docs/guarantees.md` не входят ни в путь, ни в
рецепты. Первый читают до гайда, второй — как справочник по гарантиям
фреймворка. Оба уже сегодня не имеют примера-источника: приложение Б
сверено с `design/` и README пакетов, а таблица гарантий — с кодом ядра.

Из переезда следует, что `docs/README.md` называет их в карте папок, а
README гайда ссылается на оба вместо того, чтобы включать их в себя.
«Карта понятий» остаётся в README гайда: она называет главу, в которой
понятие вводится, то есть описывает путь.

### 6. Источники сборки перечисляет `scripts/site/sections.mjs`

Константа `GUIDE` в `build.mjs` становится списком источников в отдельном
файле. Источник двух видов: папка с оглавлением (`guide/`, `recipes/`) и
отдельная страница (`guarantees.md`, `from-nestjs.md`). Порядок в списке
задаёт порядок разделов собранного файла.

Вывод остаётся одним файлом `docs/.site/index.html`. Инвариант «состав
README равен файлам папки» применяется к каждой папке-источнику
отдельно и остаётся ошибкой сборки.

Имя `sections.mjs` взято из d/11 §5.3: волна 4 добавляет в те же записи
URL-путь и заголовок раздела, но не заводит файл заново.

Отвергнуто: **оставить генератор нетронутым.** Тогда между волнами 3 и 4
восемь рецептов и два документа корня не попадают в собранный файл, и
единственный способ их прочитать — репозиторий.

Отвергнуто: **сделать разделы и URL-пути сразу.** Это волна 4 целиком:
отдельные файлы, навигация между ними, пейджер поверх разделов, ссылки
на GitHub. Смешивать её с переездом файлов — значит ревьюить две работы
одним диффом.

### 7. Ссылка пересчитывается от каталога вывода

Сегодня ссылка в соседнюю папку `docs/` переносится в собранный файл
дословно: `docs/guide/` и `docs/.site/` лежат на одной глубине, и
`../design/errors.md` попадает куда нужно. У страницы из корня `docs/`
глубина другая, и дословный перенос дал бы битую ссылку.

Генератор разрешает ссылку относительно каталога исходного файла, а потом
записывает её относительно `docs/.site/`. Для глав результат тот же, что
и сегодня, — правило обобщается, а не меняет поведение.

### 8. Якорь раздела — имя файла без папки

Слаг главы начинается с цифры (`11-database`), слаг рецепта — с буквы
(`cli`). Столкнуться они не могут, поэтому папка в якорь не входит и
ссылки внутри собранного файла остаются прежнего вида. Правило
«идентификатор заголовка получает приставку из слага и двух дефисов»
действует без изменений.

### 9. `docs:audit` проверяет обе папки

| Проверка | Было | Стало |
|---|---|---|
| Плашка «сверено с кодом» | главы `docs/guide/*.md`, кроме `appendix-*` | главы `docs/guide/*.md` и рецепты `docs/recipes/*.md` |
| Полнота оглавления в обе стороны | `docs/guide/README.md` | плюс `docs/recipes/README.md` |
| Ссылка плашки README пакета | требуется в `docs/guide/` | требуется в `docs/guide/` **или** `docs/recipes/` |
| Цели линтера стиля | `docs/guide` | плюс `docs/recipes`, `docs/guarantees.md`, `docs/from-nestjs.md` |

Исключение `appendix-*` исчезает вместе с приложениями. Рецепт
`alternatives.md` получает обычную плашку «сверено с кодом
`app-with-http`» вместо сегодняшней вольной формулировки, поэтому проверка
покрывает все файлы обеих папок без списка исключений.

### 10. Файлы двигаются через `git mv`

История файла нужна проверке свежести: `docs:audit` сравнивает дату
плашки с датой последнего коммита примера, а не главы, но история главы
остаётся единственным способом понять, когда текст менялся.
Переименования делаются `git mv` по одному, в порядке убывания номера,
чтобы `12-files-and-streams` не занял имя, которое ещё принадлежит
другому файлу.

## Risks / Trade-offs

- **250 внутренних ссылок и номера глав в прозе правятся вручную** →
  правка механическая и проверяемая: `yarn docs:build` падает на ссылке
  в несуществующую главу, `docs:audit` — на расхождении оглавления и
  файлов. Порядок работ: сначала переименования и оглавления, потом
  ссылки, потом сборка как проверка.
- **Номер главы в прозе («приём из главы 14») скриптом не находится** →
  после правки ссылок вычитывается каждое вхождение слова «глав» рядом с
  числом; таких мест порядка сотни, и все они стоят рядом со ссылкой,
  номер которой уже исправлен.
- **Деление главы 27 — единственное место, где текст пишется заново** →
  обе половины сверяются с `users-service` заново, и плашки получают
  свежую дату. Разделы переносятся целиком: перенос абзацами дал бы два
  текста, ни один из которых не сверен.
- **Внешние ссылки на файлы гайда ломаются** → документация нигде не
  опубликована (волна 5 только предстоит), поэтому единственные
  потребители — файлы репозитория, и все они правятся тем же change'ем.
- **Рецепт вышел из нумерации и может выпасть из внимания** → на него
  ссылаются README пакетов (`transport.cli`, `subscriptions`, `viz`),
  оглавление рецептов и главы пути; полноту обеих сторон проверяет
  `docs:audit`.

## Migration Plan

1. `git mv` всех файлов: сначала главы пути в порядке убывания номера,
   потом рецепты в `docs/recipes/`, потом приложение Б в корень `docs/`.
2. Деление главы 27 на `11-database.md` и `16-durable-events.md`.
3. Вынос раздела «Что проверяется до первого запроса» в
   `docs/guarantees.md`.
4. Два оглавления: `docs/guide/README.md` переписывается на две части,
   `docs/recipes/README.md` пишется заново.
5. Ссылки: внутри обеих папок, из README пакетов, из `docs/design/`, из
   `docs/README.md` и из скиллов.
6. Генератор: `sections.mjs`, список источников, пересчёт ссылок.
7. `docs:audit`: обе папки, ссылка плашки README, цели линтера стиля.
8. Проверка: `yarn docs:build`, `yarn docs:audit`, линтер стиля.

Откат — `git revert` одного change'а: кода он не касается, состояние
между шагами нигде не сохраняется.

## Open Questions

- Нужен ли рецептам порядок в оглавлении или они перечисляются по
  алфавиту. Предложено: по частоте обращения, как сегодня устроена
  часть 5, — от webhook к расширению ядра.
- Останется ли `docs/guarantees.md` отдельным документом после волны 4
  или станет разделом сайта, собираемым из плашек. Решать в волне 4.
