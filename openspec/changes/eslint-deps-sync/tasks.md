## 2. Правило `dependency-list`

- [x] 2.1 `src/dependency-list.ts`: обход `ClassDeclaration` и
  `ClassExpression` с декоратором `Component`, `Handler` или `Resource`,
  вызванным по идентификатору; аргумент декоратора читается как список:
  отсутствие аргумента — пустой список, литерал массива без spread —
  элементы, всё остальное — молчание (D4, D6 design)
- [x] 2.2 Эталон параметров: собственный `constructor` у `@Component` и
  `@Handler`, `static acquire` без последнего параметра у `@Resource`;
  `TSParameterProperty` разворачивается до параметра; без эталона правило
  молчит
- [x] 2.3 Вывод ожидаемого элемента по таблице D2: `Logger`,
  `Config<typeof X>`, `Port<typeof Op>`, `Emitter<typeof Op>`, `X` при
  видимом `X$`, массив `X[]`/`readonly X[]`/`ReadonlyArray<X>` при видимом
  `X$`, класс `X`; остальное — непрозрачная позиция
- [x] 2.4 Классификация `X` по привязке через `sourceCode.getScope` (D3):
  `ClassName` и импорт значением — класс; `Type`, `import type` и
  `import { type X }` — непрозрачно; без привязки — непрозрачно; видимый
  `X$` сильнее классификации
- [x] 2.5 Совпадение по голове выражения: идентификатор `X`, член
  `Op.caller`/`Op.emitter`, выражение с крайним левым идентификатором `X$`
  (`X$`, `X$(…)`, `X$.auto`, `X$.all`)
- [x] 2.6 Проверка длины: диапазон от числа обязательных параметров до
  общего числа, rest-параметр снимает верхнюю границу; сообщение `length`
  на аргументе декоратора с числом DI-токенов и параметров; автофикс
  дописывает недостающие позиции каноническими элементами, написанные не
  трогает, лишние убирает и доступен только при известных недостающих
  позициях; для `@Component()` без аргумента автофикс вставляет массив
- [x] 2.7 Проверка позиций при допустимой длине: сообщение `mismatch` на
  элементе с именем параметра, текстом типа и ожидаемым DI-токеном;
  `meta.hasSuggestions`, suggestion заменяет элемент каноническим текстом;
  автофикса у `mismatch` нет
- [x] 2.8 Тексты сообщений на английском, каждое называет статус подсказки
  и компилятор как гарантию; JSDoc файла — что правило ловит, где молчит и
  почему замена не автофикс
- [x] 2.9 `src/index.ts`: экспорт `dependencyList`, регистрация
  `'dependency-list'` в объекте плагина, JSDoc и пример конфига с тремя
  правилами

## 3. Тесты правила

- [x] 3.1 `src/dependency-list.spec.ts` на `RuleTester` с
  `tseslint.parser`; пролог фикстур с импортами значением, `import type`

- [x] 3.2 Валидные случаи — по строке таблицы: класс из импорта значением,
  класс из объявления в файле, `Config<typeof X>`, `Port`/`Emitter`,
  `Logger` при `Logger$.auto` и при `Logger$('db')`, интерфейс при `X$`,
  член семейства `Counter$('users')`, `readonly HealthCheck[]` при
  `HealthCheck$.all`, класс при видимом `X$`
- [x] 3.3 Валидные случаи молчания: `CtxReader<T>` при `Ctx(Var)`,
  `Set<string>`, `import type` без DI-токена рядом, глобальный тип, список
  идентификатором, spread, класс без собственного конструктора,
  `@Resource` без `acquire`, декоратор через член, необязательный параметр
  при обеих длинах, rest-параметр, `@Resource` с `acquire` и сигналом
- [x] 3.4 Невалидные случаи: `@Component()` при непустом конструкторе с
  `output` автофикса; недостающий последний DI-токен с автофиксом; лишний
  DI-токен с автофиксом; расхождение длины при непрозрачной позиции без
  автофикса (`output` равен `code`); `mismatch` с `suggestions` и без
  изменения `output`; необязательный параметр при трёх элементах
- [x] 3.5 `yarn workspace @nestlingjs/eslint-plugin test`, `lint`,
  `typecheck`, `build` зелёные
