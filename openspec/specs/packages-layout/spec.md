# packages-layout

## Purpose

Что попадает в опубликованный пакет и что нет. Сборка выносит в `dist`
только исходники: файлы проверки типов и каталоги фикстур остаются в
репозитории, поэтому `dist` не импортирует пакеты, объявленные только в
`devDependencies` — у установившего их нет. Объявленные зависимости
совпадают с импортируемыми: лишнее объявление заставляет ставить пакет,
который не нужен, а недостающее работает лишь пока пакет оказался в
дереве по другой причине. Тем же правилом живёт список разрешённых
импортов в тесте границы: он описывает фактическую границу пакета.
Публичный API пакета перечисляет корневой барель поимённо: имя
выходит наружу по решению автора, а не потому что попало под
`export *`.

## Requirements

### Requirement: Сборка пакета не выносит наружу тестовый код

`dist` пакета SHALL содержать только его исходники. Файлы проверки типов
(`*.type-test.ts`) и каталоги фикстур (`__fixtures__`) SHALL быть
исключены в `tsconfig.build.json` наравне с `*.spec.ts` и `*.test.ts`.
Исключение SHALL быть записано в шаблоне, который копирует новый пакет, а
не в отдельных пакетах: иначе следующий пакет с фикстурами повторит
дефект.

Ни один файл в `dist` SHALL NOT импортировать пакет, объявленный только в
`devDependencies`: у установившего такой зависимости нет, и импорт не
разрешится.

#### Scenario: Проверка типов не попадает в dist

- **WHEN** пакет собран и в `src` есть `overrides.type-test.ts`
- **THEN** в `dist` нет ни `overrides.type-test.js`, ни его `.d.ts`

#### Scenario: Фикстуры не попадают в dist

- **WHEN** пакет собран и в `src` есть каталог `__fixtures__`
- **THEN** в `dist` этого каталога нет

#### Scenario: Импорт devDependency из dist

- **WHEN** файл в `dist` импортирует пакет, объявленный только в
  `devDependencies`
- **THEN** это расхождение с требованием

#### Scenario: Новый пакет наследует исключение

- **WHEN** заведён пакет по образцу конфигов и в нём появился
  `__fixtures__`
- **THEN** сборка исключает каталог без правки конфига этого пакета

### Requirement: Объявленные зависимости совпадают с импортируемыми

Для каждого пакета множество внутренних зависимостей, объявленных в
`package.json` (`dependencies` и `peerDependencies` скоупа `@nestlingjs`),
SHALL совпадать с множеством пакетов, которые импортирует
его `src/` вне тестовых файлов.

Тестовыми SHALL считаться `*.spec.ts`, `*.test.ts`, `*.type-test.ts` и
содержимое `__fixtures__`. Пакет, который импортируется только из них,
SHALL быть объявлен в `devDependencies`.

Зависимость, объявленная и не импортируемая, SHALL быть удалена.
Зависимость, импортируемая и не объявленная, SHALL быть добавлена.

#### Scenario: Лишнее объявление

- **WHEN** `package.json` пакета объявляет `@nestlingjs/operations`, а ни один
  модуль `src/` вне тестовых файлов его не импортирует
- **THEN** это расхождение с требованием

#### Scenario: Недостающее объявление

- **WHEN** модуль `src/` импортирует `@nestlingjs/app`, а `package.json`
  пакета его не объявляет
- **THEN** это расхождение с требованием

#### Scenario: Импорт только из проверки типов

- **WHEN** пакет импортирует `@nestlingjs/transport.http` только в
  `*.type-test.ts`
- **THEN** зависимость остаётся в `devDependencies` и в `dependencies`
  не переносится

### Requirement: Список разрешённых импортов не шире фактических

Тест границы пакета SHALL перечислять в списке разрешённых импортов
только то, что пакет действительно импортирует. Имя, которого нет в
импортах, SHALL быть убрано: список описывает границу, а не пожелания к
ней.

#### Scenario: Лишнее имя в списке

- **WHEN** список разрешённых импортов `@nestlingjs/operations` называет
  `@nestlingjs/app`, а пакет его не импортирует
- **THEN** имя убирается, и тест границы остаётся зелёным

### Requirement: Корневой барель пакета перечисляет публичные имена поимённо

Файл `src/index.ts` пакета SHALL перечислять экспортируемые имена явными
операторами `export { … }` и `export type { … }`. Оператор `export *` из
собственного модуля в корневом бареле SHALL NOT использоваться: он делает
публичной каждую строку внутреннего модуля, и граница пакета перестаёт быть
решением автора.

Имена, реэкспортируемые из соседнего пакета, SHALL идти отдельным оператором
с именем этого пакета в специфаере. Так видно, что пришло от соседа, а что
объявлено здесь.

Публичным SHALL считаться имя, у которого есть читатель: импорт вне `src`
пакета либо упоминание в `docs/design/` или `docs/guide/`. Имя без читателя
SHALL оставаться экспортом своего модуля и SHALL NOT реэкспортироваться
корневым барелем.

#### Scenario: Внутреннее имя не выходит наружу

- **WHEN** функция `readSectionSnapshot` экспортируется модулем
  `src/config/registry.ts`, но не названа в `src/index.ts`
- **THEN** `import { readSectionSnapshot } from '@nestlingjs/app'` не
  компилируется, а внутри пакета имя работает как раньше

#### Scenario: Имя соседа видно в бареле

- **WHEN** `@nestlingjs/app` отдаёт `Ok` и `Fail` из `@nestlingjs/operations`
- **THEN** в `src/index.ts` они перечислены оператором
  `export { … } from '@nestlingjs/operations'`, а не приходят через `export *`
  собственного модуля

#### Scenario: У имени появился читатель

- **WHEN** новый пакет импортирует `withRequestLogging` из `@nestlingjs/app`
- **THEN** имя возвращается в `src/index.ts` одной строкой, и это не ломающее
  изменение

### Requirement: Пакеты репозитория живут в одном скоупе

Имя пакета SHALL начинаться со скоупа `@nestlingjs`. Внутренний пакет —
тот, который приходит зависимостью и своего API не обещает, — SHALL
называться с префиксом `common.` после скоупа.

Внутренний пакет SHALL публиковаться наравне с остальными: сборка не
бандлит зависимости, поэтому импорт внутреннего пакета остаётся в `dist`
его потребителя, и без публикации установка потребителя ломается.

#### Scenario: Имя внутреннего пакета

- **WHEN** пакет служит зависимостью ядра и собственного API не обещает
- **THEN** он называется `@nestlingjs/common.<имя>`

#### Scenario: Внутренний пакет в реестре

- **WHEN** публикуется пакет, который импортирует `@nestlingjs/common.misc`
- **THEN** `@nestlingjs/common.misc` публикуется той же версией

### Requirement: Каталог пакета из его имени не выводится

Инструмент, которому нужен каталог пакета по имени, SHALL читать имена из
манифестов `packages/*/package.json` либо SHALL нести явное правило для
каждой формы имени. Вывод каталога подстановкой скоупа в шаблон SHALL NOT
применяться: скоуп у всех пакетов общий, а каталоги называются по-разному.

#### Scenario: Резолв каталога внутреннего пакета

- **WHEN** инструменту нужен каталог пакета `@nestlingjs/common.misc`
- **THEN** он находит `packages/common.misc`, а не
  `packages/nestlingjs.common.misc`

#### Scenario: Резолв каталога без каталога `packages`

- **WHEN** инструмент запущен на корне, где каталога `packages` нет
- **THEN** он сообщает, что пакет не найден, а не падает
