# design — features: фичи, `select` и composition root

## Context

Текущий корень — `new App({ transports: Record<string, ITransport>, modules,
providers, config })`. `App.#init()` строит контейнер, гоняет `container.init()`,
затем `#registerEndpoints()` отдаёт разрешённые декларации транспортам
(`transport.endpoint(def)`), а `#listen()` вызывает `transport.listen()` через
`Promise.all`. Транспорты живут вне графа: `new HttpTransport({ port: 3000 })`
конструируется в корне руками. Декларация ссылается на транспорт **строкой**
(`endpoint.transport === 'http'`), дискавери группирует по этой строке, App
сверяет её с ключами `Record`.

Что уже готово и на что опираемся:

- дискавери из дерева модулей — `discoverEndpoints(modules)`, чистая функция
  (change #8);
- декларации-значения с `resolve(resolver)` и symbol-брендом (change #24),
  bind-карта (#21), закрытый контракт отказов (#15), формы io и
  `assertFormsSupported` (#6);
- конфиг: `makeConfig`, `configKernel(bindings)`, `ConfigSource`, `Topic`
  (change #9);
- контейнер: `@OnInit`/`@OnDestroy` c топосортом и реверсом, token families,
  `Family.all` (changes #5, #14).

Ограничения: транспорт исполняет пайплайн сам
(`pipeline.executeWithHandler(handler, ctx, …)` внутри `HttpTransport.handle`),
у HTTP есть fallback-ветка «декларация без pipeline», а интеграционные тесты
транспортов поднимают сокет через `transport.listen(0, '127.0.0.1')`. Всё это —
поверхность миграции.

## Goals / Non-Goals

**Goals:**

- фича и выбор подмножества как значения, без новой машинерии контейнера;
- один composition root `assemble(...)`, где машинерия фич опциональна;
- фазы жизненного цикла адресуемы, а `dispatch` — фазовый ресурс, дающий
  **структурную** гарантию «ранний go-live невозможен»;
- транспорт — обычный узел графа: с зависимостями, lifecycle и токеном;
- вся неудовлетворённая потребность (нет транспорта, форма вне способностей,
  незарегистрированная зависимость) падает **на сборке**, до приёма запросов.

**Non-Goals:** порты и шина (#11), NATS (#12), policy-check (#28), тестовый
корень (#18), инверсия акцептора, полная конфигурация транспортов секциями.
См. Non-goals в [proposal.md](./proposal.md).

## Decisions

### D1. `dispatch` — единственный канал, по которому транспорт получает ручки

`Dispatch` создаётся ядром в фазе WIRE и несёт **две части**:

```typescript
/** Проекция декларации: всё, кроме исполнимых полей */
export type RouteDeclaration = Omit<AnyEndpointDefinition, 'handle' | 'pipeline' | 'deps' | 'resolve'>;

export interface Dispatch {
  /** Маршруты этого транспорта: роутинг + io-декларация для парсинга */
  readonly routes: readonly RouteDeclaration[];

  /** Исполнение ручки: pipeline + handler. Транспорт строит ctx и зовёт это */
  call(pattern: string, ctx: RequestContext, options?: DispatchOptions): Promise<ResponseContext>;
}

export const makeDispatch = (endpoints: readonly ExecutableDeclaration[]) => Dispatch;
```

Транспорт получает `dispatch` только аргументом `serve(dispatch, signal)`, то
есть в фазе START. До этого момента у него **нет ни одной исполнимой ручки**:
проекция `routes` не содержит `handle`/`pipeline`, а `call` живёт в `dispatch`.
«Ранний listen» из [ideas.md [2026-07-08]](../../../docs/decisions/ideas.md)
запрещён не конвенцией, а тем, что маршрутизировать нечего.

**Почему один объект, а не два канала** (регистрация деклараций в WIRE +
`dispatch` в START, как буквально читается [`transports.md`](../../../docs/design/transports.md) §1):
второй канал (`ITransport.endpoint(def)`) отдавал бы транспорту **полную**
декларацию с `handle`, и гарантия снова держалась бы на честном слове
транспорта — «мы дали тебе хендлер, но исполнять начни позже». Разделение
проходит не по времени передачи, а по составу: провод (`routes`) — транспорту,
исполнение (`call`) — ядру. Таблица `pattern→handler` по-прежнему строится в
WIRE — она и есть `dispatch`; в START она только передаётся. Формулировку §1
`transports.md` («принимает kernel-декларации в фазе WIRE») уточняем по факту
реализации: WIRE строит таблицу, транспорт получает её вместе с `dispatch`.

**Почему `call(pattern, ctx)`, а не «транспорт исполняет сам»:** исполнение
пайплайна одинаково для всех транспортов, а его перенос в ядро убирает из
транспортов и fallback-ветку «декларация без pipeline» (сейчас продублирована
в HTTP и CLI). Транспорт остаётся переводчиком провода: роутит, парсит по
io-декларации и bind-карте, строит `ctx`, отдаёт результат в провод.
`DispatchOptions` (`exposeErrorDetails`, `onUnknownFail`) — свойства границы,
поэтому едут аргументом от транспорта, а не зашиты в `dispatch`.

**Альтернатива «dispatch как непрозрачный токен-заглушка»** (передать
что-нибудь, что нужно предъявить) отвергнута: гарантия должна быть
следствием состава данных, а не проверки «предъяви пропуск».

`Dispatch`, `RouteDeclaration` и `makeDispatch` живут в `@nestling/transport`
(зависит от `@nestling/pipeline`, не зависит от `@nestling/app`) — так
standalone-путь и `App` пользуются одной реализацией.

### D2. Транспорт — провайдер с токеном; множество транспортов выводится, а не конфигурируется

`http(options?)` / `cli(options?)` возвращают **провайдер**, а не инстанс:

```typescript
export const HttpTransport$ = makeToken<ITransport>('transport:http');   // токен
export const http = (options?: HttpTransportOptions): Provider<ITransport> =>
  factoryProvider(HttpTransport$, (cfg) => new HttpTransport({ ...cfg, ...options }), [HttpConfig]);
```

Множество транспортов приложения = **токены, упомянутые декларациями** (после
`select`) ∪ **токены провайдеров из `transports:`**. Транспорт, приехавший
infra-модулем фичи, попадает в множество через ссылку своих ручек; транспорт
без единой ручки легален, если перечислен в `transports:` (существующее
поведение сохраняется). Ручка ссылается на токен, которого нет в графе →
fail-fast на ASSEMBLE с именем ручки, модуля-объявителя и подсказкой.

**Почему не token family `Transports(name)` + `Family.all`:** семейство — это
**один рецепт** на всех членов (`familyProvider(family, recipe)`), а транспорты
приезжают разными классами из разных пакетов. Собирать их семейством пришлось
бы через рецепт-диспетчер по имени — ровно та рантайм-магия, которой в ядре
нет. Явное объединение двух множеств токенов проще и полностью статично.

**Токен вместо строки в декларации.** Поле `transport` декларации несёт токен;
чтобы `@nestling/pipeline` не зависел от `@nestling/transport` (цикл), ядро
типизирует его как `TokenString<any>` (`TransportRef`), а `@nestling/transport`
уточняет `TransportToken = TokenString<ITransport>`. Строковое имя (`'http'`)
выводится из id токена и продолжает ехать в `Raw.transport` и
`EndpointMeta.transport` — пользовательские слои не ломаются.

### D3. `@OnStart` в контейнере; `serve` драйвит App

Контейнер получает третий хук: декоратор `@OnStart` и `BuiltContainer.start()`,
обходящий узлы **топологически** (та же машинерия, что `init()`), с той же
идемпотентностью метаданных, что у `@OnInit`/`@OnDestroy`.

Фаза START состоит из двух шагов в фиксированном порядке:

1. `container.start()` — `@OnStart`-хуки по топосорту;
2. `App` вызывает `serve(dispatch, signal)` на каждом транспорте в
   детерминированном порядке (порядок токенов: `transports:` корня, затем
   порядок дискавери).

**Почему go-live не хук транспорта:** `@OnStart`-хук нульарный, а `dispatch` —
аргумент; «инжектнуть dispatch» нельзя — он не существует на build. Значит
go-live драйвится App'ом (как и записано в
[d/05 §7](../../../docs/history/discussions/05-modular-monolith-features-ports.md)),
а `@OnStart` остаётся для пользовательских провайдеров, которым нужен старт
после WIRE (планировщики, консьюмеры).

SHUTDOWN — строгий реверс: `abort(signal)` → `close()` транспортов в обратном
порядке (дренаж) → `container.destroy()` (реверс топосорта). Оба канала
остаются: `signal` — «новое не принимаем, in-flight отменяем», `close()` —
дренаж соединений с таймаутом.

### D4. `select` — замыкание `dependsOn` с fail-fast, без магии

```typescript
makeFeature({ name: 'orders', modules: [OrdersModule], dependsOn: [SharedFeature] })
```

`dependsOn` — **ссылки на значения-фичи**, а не имена: строковая ссылка
требовала бы глобального реестра фич, а его нет по тем же причинам, по которым
нет реестра эндпоинтов. Транзитивно достижимые фичи участвуют в выборе, даже
если не перечислены в `features:`.

Форма `select`: `'all'` | `'orders,billing'` | `['orders','billing']`;
отсутствует при заданных `features` → все. Fail-fast: неизвестное имя (с
перечнем доступных), одноимённые разные фичи, пустой выбор (`''`/`[]` —
«ничего» пишется явным отсутствием фич, а не пустой строкой), `select` без
`features`. Цикл в `dependsOn` **легален**: `dependsOn` описывает «без чего
фича не работает», а не порядок построения; замыкание идёт с множеством
посещённых. Дедупликация фич — по имени, как у модулей в контейнере.

### D5. `assemble` — единственный публичный корень

```typescript
assemble({ modules?, providers?, features?, select?, transports?, config? }): App
```

`modules` и `features` совмещаются: итоговое дерево = `modules` корня +
модули выбранных фич (дедупликация модулей — существующая, по имени).
`new App(...)` перестаёт быть публичной поверхностью: конструктор принимает
внутренний нормализованный `AssemblyPlan`, тип которого не экспортируется —
значит `new App({...})` невыразим по типам, без рантайм-проверок. Класс `App`
остаётся экспортированным как тип результата с методами `run()` / `close()`.

Поля `plugins`, `policies`, `dispatch` из [`composition.md`](../../../docs/design/composition.md) §2
в этом change не появляются — они аддитивны и приезжают своими change'ами
(#13, #28, #11).

Фаза 0 (BOOTSTRAP) остаётся вне `assemble`: `select` вычисляется в корне до
сборки. Чтобы это не требовало ручного `process.env`, `@nestling/config`
получает **примордиальное чтение секции** `load(section)` — синхронное чтение
её ключей из `process.env` с валидацией и fail-fast, без контейнера и без
привязанных источников. Это единственное пред-сборочное чтение конфига, ровно
как записано в ideas.md.

### D6. Проверка форм io — на ASSEMBLE и в `serve`, одна реализация

`assertFormsSupported` вызывается:

- в фазе ASSEMBLE — `App` знает и декларации, и инстансы транспортов из графа
  (это соответствует инварианту «валидация биндингов» фазы 1 в
  `composition.md`);
- в `serve(dispatch, …)` — для standalone-пути, до открытия сокета.

Прежняя точка (`transport.route()` / `transport.endpoint()`) исчезает вместе
с методом. Текст ошибки не меняется — реализация одна.

### D7. Конфиг транспорта: секция + приоритет явных опций

`@nestling/transport.http` объявляет секцию `makeConfig('http', { port, host })`
(наружу — только `HttpConfig.keys`) и читает её в провайдере. Приоритет:
явные опции `http({ port })` > конфиг (`HTTP_PORT`) > дефолт. Это минимальный
объём, доказывающий тезис §7 дискуссии («транспорту нужны инжектируемые
зависимости»); остальные опции (`maxBodySize`, таймауты, `sseHeartbeat`)
остаются аргументом фабрики. `new HttpTransport(options)` продолжает работать
без контейнера — провайдер лишь надстройка.

Побочно: `HttpTransport` теряет аргументы `listen(port, host)`, поэтому
фактический адрес после `serve` отдаётся методом `address()` — он же нужен
интеграционным тестам, поднимающимся на порту `0`.

## Risks / Trade-offs

- **[Перенос исполнения ручки в `dispatch` ломает тонкости HTTP]** —
  `drainFileStreams`, `exposeErrorDetails`, `onUnknownFail`, mid-stream
  ошибки. → Сантехника ответа (`sendResponse`, дренаж multipart) остаётся в
  транспорте; в `dispatch` уезжает только выбор ветки «pipeline / без
  pipeline» и её исполнение. Регрессионный щит — существующие интеграционные
  тесты `transport.integration.spec.ts` и `streaming.integration.spec.ts`,
  которые переписываются на `serve`, но не меняют ожиданий по проводу.
- **[Три BREAKING-поверхности сразу]** (`new App`, `listen()`, `transport` как
  токен) в волне, объявленной аддитивной. → Все три предписаны целевым
  design'ом и приезжают одним change'ом, а не размазываются: после #10
  публичный корень фиксируется. В roadmap отмечаем оговорку явно.
- **[Объём L: шесть модифицируемых capability + миграция четырёх примеров]**
  → Порядок работ в `tasks.md` идёт снизу вверх (контейнер → контракт
  транспорта → app → транспорты → примеры → доки), каждый шаг оставляет
  репозиторий собираемым.
- **[Зависимость `@nestling/transport.http` → `@nestling/config`]** —
  транспортный пакет тянет конфиг. → Зависимость односторонняя и уже
  «разрешена» дизайном (`transports.md` §4: «порт и опции — из конфиг-секции»);
  standalone-конструктор транспорта конфига не требует.
- **[`select` как строка из env — стрингли-типизированный вход]** → Это
  граница процесса (аргумент бинарника), она строковая по природе; ошибки
  ловятся fail-fast'ом с перечнем доступных имён на ASSEMBLE.
- **[Цикл в `dependsOn` разрешён]** — можно построить взаимно зависимые фичи и
  не заметить, что «выбрал одну — приехали обе». → Документируем в спеке и
  гайде; `explain()`-поверхность (что реально выбрано) печатается на старте.

## Migration Plan

1. `@nestling/container`: `@OnStart` + `BuiltContainer.start()` — аддитивно,
   ничего не ломает.
2. `@nestling/transport`: `Dispatch`/`RouteDeclaration`/`makeDispatch`,
   `ITransport.serve` вместо `listen`/`endpoint`.
3. `@nestling/transport.http` и `.cli`: `serve`, токены, фабрики-провайдеры,
   исполнение через `dispatch`; тесты транспортов переезжают на `serve`.
4. `@nestling/app`: `makeFeature`, `select`, `assemble`, фазовый рантайм,
   fail-fast'ы ASSEMBLE.
5. `packages/examples.*`: четыре примера на `assemble`; `app-with-http`
   дополнительно показывает L2 (две фичи + `select` из env).
6. Документация: `design/composition.md` и `design/transports.md` — уточнения
   по факту; новый `guides/composition.md`; пересверка гайдов; README пакетов;
   roadmap + archlog.

Откат — обычный revert ветки change'а: промежуточных состояний в
опубликованном API не остаётся, все шаги едут одной веткой.

## Open Questions

- **`explain()` на старте** — что именно печатать (выбранные фичи, транспорты,
  ручки) и под каким флагом. В этом change — минимум: одна строка со списком
  выбранных фич и транспортов; полноценный `explain` — тема policy-check (#28)
  и отдельной записи.
- **Порядок `serve` между транспортами** зафиксирован как детерминированный,
  но не топологический. Если появится транспорт, зависящий от другого
  транспорта, порядок придётся выводить из графа — вопрос вернётся вместе с
  NATS (#12).
