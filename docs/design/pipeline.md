## 1. Модель: фазы вместо луковицы

Никакого `next()` и onion-модели: скрытый control flow, потеря
типизированного накопления контекста и анализируемости цепочки — причины,
по которым Koa-модель отвергнута. Пайплайн — **плоские фазы**, декларация
читается сверху вниз как план исполнения. Слова «middleware» в словаре нет;
отдельной подсистемы «exception filters» нет — маппинг ошибок это
обычный `.catch`-юнит.

**Словарь билдера** (`makePipeline()`, иммутабельный — каждый метод
возвращает новый пайплайн):

| Метод | Роль | Когда | ctx |
|---|---|---|---|
| `.pre(u)` | препроцессор | до хендлера, по порядку объявления | накопленный, полный |
| `.ok(u)` | постпроцессор | ответ = `Ok` | **полный** (свой слой + внешние) |
| `.catch(u)` | обработчик ошибок | ответ = `Fail` | свой слой `Partial`, внешние полные |
| `.finally(u)` | наблюдатель исхода | всегда, последним | как `.catch` + `outcome` |

Словарь Promise-чист (`ok`/`catch`/`finally`); `.then` запрещён навсегда
(thenable-ловушка). Понятия «обёртка/wrapper» нет: транзакция =
`pre + ok + catch` — три явные строчки.

## 2. Исполнение одного слоя

Pre-юниты — по порядку объявления, каждый **монотонно накапливает
типизированный input**; падение любого pre ⇒ сразу ответная фаза с `Fail`.
Хендлер — если все pre прошли. Ответный тракт — **один список юнитов в
порядке объявления**: юнит применяется по применимости к *текущему* ответу
(`ok` — к успеху, `catch` — к ошибке) и может ответ заменить (ok-юнит
бросил → ответ стал ошибкой → последующие `catch` применимы). `.finally` —
после того как всё дотекло, с исходом
`completed | disconnected | aborted | failed`.

Type-state билдера: `.pre` недоступен после первого ответного метода —
чтение сверху вниз всегда совпадает с порядком исполнения.

## 3. Слои и `compose`

Пайплайн — стек слоёв; один вызов `makePipeline()` с цепочкой методов
определяет **один слой**. Композиция — жадная, константами:

```typescript
export const base = makePipeline().pre(withRequestId()).finally(audit);
export const authed = compose(
  base,
  makePipeline().pre(withIdentity()),
);
// у endpoint'а: pipeline: compose(authed, makePipeline<{ identity: User }>().pre(...))
```

- `compose(outer, ..., inner)` — список слоёв, читается сверху вниз как
  «снаружи внутрь» (= порядок в `explain()`).
- Pre-тракты исполняются снаружи внутрь, ответные и `finally` — изнутри
  наружу. Слой исполняется, только если pre всех внешних слоёв прошли ⇒
  **ответные юниты слоя видят контекст внешних слоёв полным и
  гарантированным**; `Partial` — только для pre собственного слоя.
- **Требования слоя к внешнему контексту** объявляются явно —
  `makePipeline<{ identity: User }>()` — и проверяются **компилятором в
  точке композиции**.
- Уровней привязки App/модуля нет: пайплайн подключается только в декларации
  endpoint'а. Переиспользование — экспортируемые константы и фабрики
  (`authedWith(verifyFn)`); модуль с endpoints принимает пайплайн параметром
  фабрики — зависимость видна, тип параметра документирует требуемый контекст.

## 4. Типизация: честная опциональность

Ключевой ход, заменивший луковицу: на ответном тракте обогащение могло не
случиться ⇒ ctx там `Partial` (правда в типах). Юниты только-на-успех имеют
железную гарантию: успех ⇒ весь pre-тракт прошёл ⇒ ctx полный.

**Ограничения V1 (осознанные):** нет раннего успешного выхода (gate: кэш,
идемпотентность) и нет восстановления `Fail → Ok` в `.catch` — оба ломают
гарантию «успех приходит только из хендлера», на которой держится полный
ctx у `.ok`. Сильная типизация важнее; условия возврата к gate — в записи
журнала.

**Диагностика типов — часть API.** При нарушении требований слоя тип
параметра `compose` схлопывается в читаемый литерал
(`{ __error: '…'; missing: { identity: User } }`) — первая строка диагностики
называет проблему, а не трассировку дженериков. `missing` — **рекорд «имя
поля → его тип»**: туда попадают и поля, которых внешние слои не дают, и
поля, которые дают, но несовместимого типа. Форма едина во всех точках
проверки pipeline: точка композиции, pre-тракт (там второй случай —
`conflicting` рекордом «имя → [было, стало]») и слот `pipeline`
транспортной декларации (там литерал дополнен `hint` с конкретным
действием). В неуспешной ветке параметр — **только** литерал ошибки, без
пересечения с типом слоя.

Тексты диагностик фиксируются snapshot-тестами по каталогу фикстур
заведомо неправильных композиций. На стоимость типовой машинерии есть
**бюджет**: детерминированные счётчики компилятора
(`Instantiations`/`Types`, дельтой к пустой базе) с жёстким порогом и
латентность реального tsserver со щедрым потолком; граф ~50 слоёв
вложенной композицией компилируется без `TS2589`. Бюджет — часть проверки
репозитория, а не отчёт.

## 5. Формы юнитов и `TNeeds`

| Форма | TNeeds | Использование |
|---|---|---|
| функция | — | базовый случай |
| инстанс (`new WithTracing(...)`) | — | мост: класс без DI |
| класс (`WithTracing`) | +Constructor | App резолвит из контейнера на старте |
| токен (`RateLimit('strict')`) | +Token | конфигурируемые юниты через token families |

`TNeeds` — второй тип-параметр пайплайна, накопитель отложенных зависимостей.
Чистый пайплайн — `Pipeline<…, never>`; **standalone-транспорты принимают
только его** — граница «полностью функциональный сценарий» держится типами,
а не конвенцией. App гасит `TNeeds` контейнером на старте; вручную —
`pipeline.resolve([[Class, instance]])`. Юнит — синглтон; per-request
состояние живёт только в ctx.

## 6. Границы пайплайна

- **Pipeline оперирует значениями, транспорт — байтами**
  ([transports.md](./transports.md)): сжатие, CORS, content negotiation —
  не юниты.
- **Ответный тракт не меняет тип value** — иначе output-схема перестаёт
  описывать провод (schema-first). Глобальный конверт `{data, meta}` — часть
  схемы или опция сериализации транспорта, не юнит.
- **Retry/timeout — не обёртки** (onion умер), а декларативные опции
  endpoint'а, исполняемые оркестратором: видны в метаданных, доках,
  визуализации.
- **Per-item логика** (валидация элементов, лимиты, таймауты потока) — не
  request-юниты, а item-цепочки на io-декларации: у стримов два разных скоупа
  обработки — соединение и элемент ([streaming.md](./streaming.md)).

## 7. Интроспекция и policy-check

`pipeline.explain()` — заявленная часть API: печатает план исполнения
(дерево фаз и слоёв с аннотациями накопления — `→ {identity: User}`).
Назначение тройное: отладка, документация, узел визуализации графа.

На этой же интроспекции держится **policy-check** — гарантия сквозных
инвариантов уровня сборки. Композиция константами решает переиспользование,
но не гарантию («каждая HTTP-ручка защищена» — не свойство типов хендлера),
поэтому инварианты декларируются в composition root и проверяются на
собранном графе (ASSEMBLE), где все значения материализованы:

```typescript
assemble({
  policies: [everyEndpoint({ transport: http }).hasLayer(authedBase)],
  /* ... */
})
```

- Идентичность слоя — **по ссылке на значение** (слои экспортируются
  константами), не по имени.
- Opt-out — `detached: '<причина>'` в декларации endpoint'а: строка
  обязательна, App печатает список detached-ручек на старте — поверхность
  для аудита.
- Двухслойность: ESLint-правило подсказывает в редакторе буквальные случаи;
  policy-check — гарантия (значения текут через фабрики и параметры и
  статически в точке объявления непроверяемы).
- Та же машинерия обслуживает проверку присутствия ambient-vars
  ([container.md](./container.md), «Асинхронный контекст») и инварианты
  плагинов; в CI политики гоняются `.check()`-матрицей топологий
  ([testing.md](./testing.md)).
