## Context

Контракт — центральное значение дизайна: из него растут реализация
(`implement`), внутренний вызыватель (`.port`/`.emitter`) и документация.
Внешнего потребителя нет, и мешают этому ровно две вещи:

1. **Адреса нет.** `name` контракта это subject шины. HTTP-паттерн сегодня
   живёт только в декларации endpoint'а, а декларация неотделима от `handle`
   и его серверных зависимостей.
2. **Пакет тяжёлый.** `makeContract` живёт в `@nestling/ports`, который тянет
   `@nestling/pipeline`, `@nestling/container`, `@nestling/transport`,
   `@nestling/config`. Импортировать это во фронт нельзя.

Что уже есть и на что опираемся:

- плоская bind-карта (`computeHttpBinding` в `@nestling/transport.http`) —
  разворачивается **при создании декларации**, несёт `method`, `path`,
  `fields`, `rest`, `rawBody`, `sse`;
- strict-приём на сервере (`assemblePayload`) — у каждого поля ровно одно
  место, слияния источников нет;
- `defineFail` с code-идентичностью и `errors:` в декларации; страж границы,
  нормализующий незадекларированное в `UnknownError`;
- проводной формат отказа: статус HTTP + тело `{ error, code?, details? }`;
- `~standard.validate` в ядре, синхронная валидация обязательна.

Ограничения, заданные записями журнала: bind-карта обязана быть выводима из
значения, которое импортирует клиент; методы клиента именует потребитель;
call-site эквивалентен вызывателю; ambient-заголовки — конфиг создания
клиента.

## Goals / Non-Goals

**Goals:**

- Из одного импортированного значения контракта клиент знает **всё**, что
  нужно для вызова: адрес, размещение полей, схему ответа, множество отказов.
- Пакет с контрактами импортируется во фронт: в графе импортов нет ни
  серверного кода, ни контейнера, ни Node-специфики, ни внешних
  runtime-зависимостей (транзитивно — только типы `@standard-schema/spec`).
- Один и тот же `http:` обслуживает обе стороны: клиент собирает запрос по
  карте, сервер разбирает запрос по той же карте, взятой с того же значения.
- Контракт результата закрыт: `Ok<Output> | Fail<E ∪ UnknownError>` — то же
  множество, что у порта.

**Non-Goals:**

- Streaming-клиент, кодогенерация, per-call заголовки, клиент по шине —
  см. Non-goals предложения.
- Изменение семантики портов, форм хендлера, фазовой модели pipeline.
- Универсальный HTTP-клиент: `makeClient` умеет ровно то, что описывает
  контракт, и отказывается делать что-либо ещё.

## Decisions

### 1. `@nestling/operations` — физический переезд, а не фасад

**Решение.** Заводится пакет `@nestling/operations`, в который **переезжает**
замыкание декларативного слоя:

| Откуда | Что | Почему обязано переехать |
|---|---|---|
| `@nestling/pipeline` | `core/result.ts` (`Ok`, `Fail`, `isFail`, `FailData`), `core/status.ts` | клиент конструирует `Fail` и читает статусы |
| `@nestling/pipeline` | `core/define-fail.ts`, `core/kernel-fails.ts` | рематериализация по `code`, `UnknownError` |
| `@nestling/pipeline` | `core/io/{forms,io,summary,assert,capabilities}.ts` | `input:`/`output:` контракта — формы io; `ValidateOutputForm` закрывает слот в `ContractSpec` |
| `@nestling/ports` | `contract.ts`, `registry.ts`, семейства вызывателей | сам `makeContract` |
| `@nestling/transport.http` | пометки `query()`/`body()`, тип `HttpBinding`, `computeHttpBinding` | карта считается в `makeContract` |

Остаются на месте: рантайм пайплайна и страж границы, `bind-stream.ts`
(нужен `@nestling/streams`), `implement`, шина, kernel портов, потребляющая
половина bind-карты (`assemblePayload`, `readQuery`, `bindingNeedsBody`,
`httpBindingOf`).

**Почему не фасад-пакет, реэкспортирующий из `@nestling/ports`.** Фасад не
меняет граф импортов: `import { makeContract } from '@nestling/operations'`
всё равно втянул бы контейнер и транспорт. Обещание «импортируем во фронт»
осталось бы конвенцией, а не гарантией.

**Почему не «оставить как есть, бандлер вытрясет».** Tree-shaking — свойство
инструмента потребителя, а не наше. Принцип **guarantee over convention**
требует, чтобы граф импортов физически не доходил до серверного кода. Это
проверяемо тестом (см. решение 3), tree-shaking — нет.

**Альтернатива, отвергнутая:** оставить `makeContract` в `@nestling/ports`, а
клиенту отдать отдельное «описание контракта» (`describeContract` уже есть).
Отвергнута: два артефакта разъезжаются, потребителю нужны оба — ровно
контраргумент, которым в d/07 был отвергнут `httpBind()`.

### 2. Примитив токена — subpath `@nestling/container/tokens`

`makeContract` ставит на контракт `.port`/`.emitter` — члены семейств
токенов, а членство обязано регистрироваться **в самом семействе**: токен,
который лишь выглядит как член (`makeToken('Port:foo')`), членом не является,
и билдер это специально диагностирует.

Модули `container/src/common.ts` и `container/src/providers/token-family.ts`
уже являются листьями: ни один из них не имеет runtime-импортов (только
`import type`). Поэтому `@nestling/container` получает subpath-экспорт
`./tokens`, отдающий ровно эту пару, а `@nestling/operations` импортирует
`@nestling/container/tokens`. Граф импортов пакета контрактов до билдера
графа и `@common/graphs` не доходит.

**Альтернатива 1:** вынести токены в отдельный пакет `@nestling/tokens`.
Честнее по `package.json` (не осталось бы даже install-веса `@common/graphs`),
но инвертирует онтологию — токен инжекции это понятие контейнера — и
разносит по пакетам общее модульное состояние реестра членов. Отвергнута как
цена, не оправданная выигрышем.

**Альтернатива 2:** не класть `.port`/`.emitter` на контракт, а выдавать их
функцией `portOf(Contract)` из `@nestling/ports`. Отвергнута: ломает уже
зафиксированный публичный API портов ради упаковки.

**Альтернатива 3:** ставить вызыватели «поздней инициализацией» из
`@nestling/ports` при импорте. Отвергнута прямо — **no runtime magic**:
поведение значения зависело бы от того, импортирован ли другой пакет.

### 3. Граница пакета проверяется тестом, а не обещанием

В `@nestling/operations` добавляется тест, обходящий граф импортов собранного
`dist/` и падающий, если в замыкании встретился пакет вне белого списка
(`@common/misc`, `@nestling/streams`, `@nestling/container/tokens`,
`@standard-schema/spec`) или импорт `node:*`. Так «zero runtime deps»
перестаёт быть строчкой в README и становится инвариантом, который ломается
громко и сразу.

### 4. Реэкспорт: сохраняем поверхность, но не воспроизводим ошибку упаковки

- `@nestling/pipeline` реэкспортирует всё переехавшее, что уже было в его
  публичной поверхности (`Ok`, `Fail`, `isFail`, статусы, `defineFail`,
  kernel-отказы, формы io). Это рабочий словарь любого хендлера; заставлять
  автора ручки добавлять импорт из другого пакета — налог без выигрыша.
- `@nestling/transport.http` реэкспортирует `query()`/`body()` и тип карты:
  автор HTTP-декларации берёт их оттуда же, откуда `httpEndpoint`.
- `@nestling/ports` **не** реэкспортирует `makeContract` и типы контракта.
  Именно этот реэкспорт вернул бы контракт в тяжёлый пакет и сделал бы
  «`makeContract` не живёт там, где сервер» вопросом дисциплины импортов.
  Примеры и гайды переводятся на `@nestling/operations`.

Реэкспорт — ES-модульный, то есть тот же модуль: идентичность значений и
одно модульное состояние реестров сохраняются.

### 5. Секция `http:` — данные контракта, карта считается в `makeContract`

Форма записи:

```typescript
http: 'POST /users/:id'
http: { method: 'POST', path: '/users/:id', bind?, rawBody?, sse? }
```

Строковая форма — сахар над развёрнутой: разбор `'<METHOD> <path>'` строгий,
без второго пробела и без пустого пути. Правила размещения, словарь пометок и
все fail-fast — **те же самые**, что у HTTP-декларации: код правила один
(`computeHttpBinding`), места вызова два.

Точка разворачивания — создание контракта. Это уточнение уже записано в d/07:
клиенту карта нужна без сервера, из одного импорта, поэтому привязывать
разворачивание к регистрации endpoint'а нельзя.

**Отвергнуто:** `http:` только строкой (не выразить `bind`/`rawBody`);
`http:` списком (несколько адресов у одной операции — это несколько
контрактов); ленивое вычисление карты при первом обращении (fail-fast
обязан срабатывать у владельца декларации, в момент загрузки модуля).

### 6. `httpEndpoint({ contract, … })` — вторая сторона того же значения

Без серверной формы `http:` описывал бы адрес, который никто не обязан
обслуживать: автор писал бы `httpEndpoint({ method, path, input, … })`
руками и рано или поздно разъехался бы с контрактом. Поэтому `httpEndpoint`
получает контракт-форму:

```typescript
httpEndpoint({ contract: CreateUser, deps: [UserService], handle: (svc) => (input) => … });
```

- `method`, `path`, `bind`, `rawBody`, `input`, `output`, `errors` объявлены
  в словаре как `never` — переобъявление интерфейса операции ошибка
  компиляции, ровно как в `ImplementDictionary`;
- карта берётся с контракта как есть, повторно не считается;
- контракт без `http:` отвергается в момент создания декларации с текстом,
  называющим контракт;
- три формы `handle`, `pipeline`, `detached` работают как у любой
  HTTP-декларации: это обычная декларация, а не новый примитив.

**Отвергнуто:** отдельный конструктор `implementHttp(Contract, …)` —
дублировал бы перегрузки трёх форм хендлера ради синонима;
мульти-транспортная декларация (одно значение и на шине, и в HTTP) — ломает
модель «декларация принадлежит одному транспорту», и `dispatch`, политики и
визуализация перестали бы быть однозначными.

### 7. Сборка запроса — обратная операция к strict-приёму

Клиент читает bind-карту и раскладывает payload:

```
path   ← поля с placement.in === 'path'   → подстановка в шаблон, encodeURIComponent
query  ← поля с placement.in === 'query'  + (rest === 'query' ? остальные : ∅)
body   ← поля с placement.in === 'body'   + (rest === 'body'  ? остальные : ∅)
```

Инвариант, который обязан держаться и проверяется round-trip-тестом:
`assemblePayload(binding, split(binding, payload)) ≡ payload` для любого
payload, представимого на проводе.

Коерсия (закрывает открытый вопрос записи):

- `undefined` и `null` — ключ в query не пишется вовсе: сервер отсутствие
  трактует как отсутствие, и `.optional()`/дефолты схемы продолжают работать;
- скаляр (`string`/`number`/`boolean`) → `String(value)`;
- массив скаляров → повторяющиеся ключи в порядке следования (симметрия с
  `readQuery`, который сохраняет все вхождения);
- всё остальное в query (объект, вложенный массив) → `TypeError` в момент
  вызова, с именем поля: молчаливого `[object Object]` не будет.

Тело — JSON; `Content-Type: application/json` ставится только когда тело
есть. `baseUrl` и `path` склеиваются буквально (`baseUrl` без хвостового
слэша + `path`) — без «умного» разрешения относительных URL.

### 8. Ответ: успех, валидация, отказ

- **2xx** → HTTP-код отображается обратно в `SuccessStatus`; `204` даёт
  `Ok('NO_CONTENT', null)`. Тело разбирается как JSON.
- **Валидация ответа — по умолчанию** (закрывает второй открытый вопрос).
  Обещание клиента — типизированный результат; отдать невалидированный JSON
  под типом `Output` значит соврать в типе. Отключается явно:
  `makeClient(record, { validateOutput: false })`. Валидация синхронная —
  `Promise` из `~standard.validate` трактуется как ошибка, как в ядре.
- **Не-2xx** → тело `{ error, code?, details? }`. Если `code` объявлен в
  `errors:` контракта — отказ рематериализуется этим определением: статус
  берётся из определения (сервер мог ответить любым), `details` валидируются
  схемой определения, `message` берётся с провода. Иначе — `UnknownError`.
- **Любой сбой, не описанный контрактом** — сеть недоступна, тело не JSON,
  ответ не прошёл `output`-схему, `code` не объявлен — даёт `UnknownError` с
  оригиналом в `cause`. Третьего кода не вводится: множество `E ∪ UnknownError`
  закрыто, и call-site порта, где `default`-ветка ловит `UnknownError`,
  переносится на клиента без правок.

Клиент **не бросает** на транспортных и контрактных сбоях — он возвращает
`Fail`. Бросает он только на дефектах использования (`TypeError` на
непредставимом query-поле): это ошибка программиста, а не ответ сервиса.

### 9. Call-site зеркалит вызыватель вида контракта

| Вид | Вызыватель | Метод клиента |
|---|---|---|
| `request` | `port.call(payload, meta?)` | `Promise<Ok<Output> \| Fail<E ∪ UnknownError>>` |
| `command` | `emitter.emit(payload, meta?)` | `Promise<void>`, отказ бросается |
| `event` | `emitter.emit(...)` | отвергается в `makeClient` |

`event` отвергается потому, что событие это broadcast-факт с 0..N
подписчиками, а HTTP-вызов адресует ровно одного получателя. Текст ошибки
предлагает `command` — намерение, адресованное одному владельцу.

`meta` клиента — `{ signal?, deadline? }`. `signal` уезжает в `fetch`;
`deadline` (абсолютный момент, как у портов) проверяется до вызова
(`DeadlineExceeded` без похода в сеть) и композируется в `AbortSignal`.
`idempotencyKey` в v1 у клиента нет: согласованного HTTP-слота для него не
существует, а провезти его «каким-нибудь заголовком» значит договориться с
самим собой — вынесено в открытые вопросы.

### 10. Конфиг клиента

```typescript
makeClient(record, {
  baseUrl: string,
  headers?: Record<string, string> | (() => Record<string, string> | Promise<Record<string, string>>),
  fetch?: typeof globalThis.fetch,
  validateOutput?: boolean,   // default: true
});
```

`headers` допускает функцию: auth-токен ротируется, а статический рекорд
защёлкнул бы его на момент создания клиента. `fetch` инжектируется —
тестируемость без сети и работа в средах со своим `fetch`.

Fail-fast в момент `makeClient` (не при первом вызове): контракт без `http:`;
контракт вида `event`; потоковая форма io (`stream`/`events`/`multipart`/
`upload`) в `input` или `output`; `baseUrl` не абсолютный URL. Все тексты
называют ключ метода в record'е.

## Risks / Trade-offs

- **Переезд задевает почти все пакеты.** → Двигаем модуль-в-модуль с
  реэкспортом из прежнего дома, `yarn verify` после каждого шага; ни один
  публичный символ не пропадает, поэтому дифф механический и проверяемый
  компилятором.
- **`defineFail(...).is(ResponseContext)` тянет тип контекста ответа из
  pipeline.** → В `@nestling/operations` перегрузка объявляется над
  минимальным структурным типом (`{ isSuccess: false; value?: { code?: string } }`),
  который `ResponseContext` удовлетворяет. Рантайм уже проверяет только
  `isSuccess === false` — сужение не теряется.
- **Subpath `./tokens` — новая точка резолва.** → Объявляется в `exports` и в
  `tsconfig` путях один раз; тест графа импортов (решение 3) поймает
  случайный откат на барель `@nestling/container`.
- **Две копии `@nestling/operations` в одном приложении разведут реестр имён и
  идентичность токенов.** Риск общий для любого пакета с модульным
  состоянием. → Фиксируем в README пакета; в монорепо снимается workspace-ом.
- **Валидация ответа по умолчанию стоит времени на больших ответах.** →
  Осознанная цена за неложный тип; opt-out явный и однострочный.
- **`http:` расширяет контракт транспортной секцией.** Контраргумент «контракт
  станет свалкой биндингов» ослаблен тем, что секция — **данные** для карты, а
  не поведение; но правило нужно держать: в контракте могут появляться только
  секции, из которых выводится адресация и размещение, и ничего про
  исполнение.
- **Round-trip-инвариант проверяется на представимом множестве.** Payload с
  непредставимым в query значением у метода без тела не собирается вовсе —
  это `TypeError` на клиенте, а не тихое расхождение.

## Migration Plan

1. `@nestling/container`: subpath `./tokens`; поверхность бареля не меняется.
2. Новый пакет `@nestling/operations`; переезд листьев в порядке зависимостей:
   `status` → `result` → `define-fail` → `kernel-fails` → `io/*` → декларативная
   половина bind-карты → `contract`/`registry`/семейства. После каждого шага —
   реэкспорт из прежнего дома и `yarn verify`.
3. `http:` в `ContractSpec` + fail-fast + материализация карты.
4. Контракт-форма `httpEndpoint`.
5. Новый пакет `@nestling/client`.
6. Примеры (`examples.app-with-http` — контракты с `http:` и
   клиент-потребитель; `examples.split-nats` — импорт `makeContract`), гайды,
   design/decisions, README пакетов.

Откат: шаги 3–6 независимы и снимаются по отдельности; шаг 2 — единый
коммит-переезд, откатывается целиком.

## Open Questions

- **`idempotencyKey` по HTTP** — нужен согласованный слот (заголовок
  `Idempotency-Key`?) и его чтение серверной границей. Вне этого change'а;
  триггер возврата — первый внешний потребитель `command`-контракта.
- **Провоз `deadline` по проводу** — у портов через NATS относительный timeout
  уже есть; для HTTP слота нет. Пока deadline только локальный.
- **Streaming-клиент** — `stream` → NDJSON, `events` → SSE с реконнектом по
  `Last-Event-ID`; проектируется вместе с AsyncAPI.
- **Content-negotiation** — v1 говорит только JSON. Контракт с не-JSON телом
  (`'binary'`, `'text'`) сейчас отвергается вместе с прочими непотоковыми
  примитивами; отдельный вопрос, стоит ли открывать их раньше стриминга.
