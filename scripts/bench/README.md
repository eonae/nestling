# Бенчмарки

## `http.ts`

Сравнивает `@nestling/transport.http` с Fastify, Hono и Express на
одинаковой паре endpoint'ов: `GET /users/:id` с JSON-ответом и
`POST /users` с телом, проверенным одной и той же zod-схемой у всех
серверов.

```bash
yarn nx run-many -t build      # серверы берут пакеты Nestling из dist
yarn bench:http                # все серверы, вывод таблицами
BENCH_ROUNDS=3 yarn bench:http --markdown   # медиана из трёх, сводка в Markdown
```

Файлы:

- `servers.ts` — серверы и их endpoint'ы, по одной фабрике на вариант;
- `server.ts` — точка входа дочернего процесса: поднимает один сервер и
  печатает порт;
- `http.ts` — раннер: поднимает серверы по очереди в отдельных процессах,
  прогоняет autocannon, печатает таблицу на сценарий и сводку с
  отношением к серверу-эталону.

Серверы идут двумя ярусами. Nestling один: проверку входа схемой и
область контекста запроса у его endpoint'а отключить нельзя. У каждого
чужого фреймворка два варианта.

| Сервер | Что делает на запрос |
|---|---|
| `nestling` | маршрут, `AbortController`, область `AsyncLocalStorage`, проверка path-параметра схемой, хендлер, проверка ответа по `errors:`, `.finally` |
| `fastify`, `hono`, `express` | маршрут, область `AsyncLocalStorage` через хук или middleware, проверка path-параметра той же zod-схемой, хендлер |
| `fastify-bare`, `hono-bare`, `express-bare` | маршрут и хендлер; параметр читается как есть |
| `nestling-layers`, `fastify-layers` | поверх первого яруса: идентификатор запроса из заголовка или `randomUUID`, арендатор из `x-tenant`, счётчик исходов после ответа; у Nestling слой из двух pre-юнитов и `.finally`, у Fastify хуки `onRequest` и `onResponse` |

Первый ярус отвечает на вопрос «сколько стоит фреймворк при равных
обязанностях», второй — «какова нижняя граница цены самого фреймворка»,
третий — «сколько стоят слои вокруг хендлера».
На `POST` все серверы разбирают JSON и проверяют тело одной схемой.

Каждый сервер работает в отдельном процессе, а клиент autocannon — в
процессе раннера. Так сервер не делит цикл событий с клиентом, и числа
близки к тому, что даёт сервер под внешней нагрузкой.

Переменные окружения:

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `BENCH_DURATION` | секунды на один замер | `10` |
| `BENCH_CONNECTIONS` | одновременных соединений | `50` |
| `BENCH_ROUNDS` | прогонов по всем серверам; в отчёт идёт прогон с медианным req/s | `1` |
| `BENCH_SERVERS` | серверы через запятую, например `nestling,fastify,nestling-layers` | все |
| `BENCH_REFERENCE` | сервер для колонки «отношение» | `fastify` |
| `BENCH_NODE` | путь к бинарю Node для серверов | текущий `node` |

Колонки вывода: среднее req/s, разброс req/s между секундами (σ), средняя
латентность, p99, максимум, число ошибок и отношение req/s к эталону.
Разброс и максимум нужны, чтобы видеть паузы: среднее req/s их скрывает.

Числа — точка отсчёта, а не порог. Они зависят от машины замера, поэтому
бенчмарк не входит в `yarn verify`, не проверяется тестом и ничего не
блокирует. Результат последнего замера и его условия записаны в
[`docs/decisions/ideas.md`](../../docs/decisions/ideas.md), запись
[2026-09-05] «Сигнал отмены запроса: реестр контроллеров вместо
`AbortSignal.any`».

## Почему Nestling медленнее Fastify

Замер 2026-09-05 на Node 24, медиана из трёх прогонов, после change'ей
`abort-signal-registry` и `hot-path-trim`:

| Сервер | `GET /users/:id` | к `fastify` | `POST /users` | к `fastify` |
|---|---:|---:|---:|---:|
| `nestling` | 54 955 | 0.92 | 45 776 | 1.14 |
| `fastify` | 59 675 | 1.00 | 40 101 | 1.00 |
| `fastify-bare` | 62 405 | 1.05 | 41 141 | 1.03 |
| `hono` | 55 440 | 0.93 | 45 184 | 1.13 |
| `express` | 37 125 | 0.62 | 30 464 | 0.76 |
| `nestling-layers` | 50 741 | 0.85 | 42 645 | 1.06 |
| `fastify-layers` | 57 872 | 0.97 | 38 037 | 0.95 |

На `POST` все серверы разбирают JSON и проверяют тело одной схемой, и
Nestling обгоняет Fastify. На `GET` разрыв 8% при равных обязанностях,
столько же у Hono. До `hot-path-trim` разрыв был 20%: его давала обвязка
запроса, а не гарантии (запись ideas.md [2026-09-05] «Горячий путь»).

CPU-профиль сервера Nestling под этой нагрузкой (Node 24, `--cpu-prof`,
доли self-time от всех сэмплов; простой цикла событий 44%, запись в сокет
и парсер `node:http` в остатке):

| Доля | Что | У Fastify |
|---|---|---|
| 3.6% | `@nestling/transport.http`: `sendResponse`, `handle`, `assemblePayload` | 2.4% собственного кода на те же обязанности |
| 1.7% | `@nestling/pipeline`: `execute`, проверка `errors:`, `normalizeResponse` | нет: маршрут вызывает хендлер напрямую |
| 2.4% | микротаски: четыре `await` на запрос против двух | около 1% |
| 0.7% | `find-my-way` | 0.5%: тот же маршрутизатор |
| 0.5% | `_storeHeader` и `writeHead` из `node:http` | 0.4% |
| 0.5% | `AsyncContextFrame`: область контекста запроса | столько же у варианта с теми же обязанностями |
| 0.3% | слушатель `'close'` на ответ и `AbortController` запроса | нет |
| 0.1% | zod: проверка path-параметра схемой | столько же у варианта с теми же обязанностями |

Оставшаяся разница складывается из двух частей.

1. **Гарантии, которых у Fastify нет и в варианте с теми же
   обязанностями.** Проверка ответа по `errors:`, `.finally` с исходом
   запроса, сигнал отмены и слушатель `'close'` на каждый запрос, счётчик
   байтов в `summary`, объекты контекста для юнитов. Около 1 µs, и они
   остаются: без них нет ни закрытого множества отказов, ни исхода запроса
   для наблюдателей, ни отмены по дисконнекту.
2. **Микротаски.** Запрос проходит `handle`, `dispatch.call`, `execute` и
   `sendResponse`; у Fastify два `await`. Убрать их можно только расщепив
   путь на синхронный для формы `value` и асинхронный для потоков.

Слои стоят Nestling больше, чем Fastify: `nestling-layers` теряет против
`nestling` 8%, `fastify-layers` против `fastify` 3%. Каждый pre-юнит
ждётся через `await`, а хук Fastify вызывает `done()` синхронно.
Проверка `then` на значении вместо `await` — кандидат на следующий замер.

Чего в разнице нет: сериализация ответа (`JSON.stringify` у обоих, на
объекте из двух полей рукописный сериализатор не быстрее), маршрутизатор
(общий), парсер HTTP (общий `node:http`), проверка входа и контекст
запроса (столько же платит Fastify с теми же обязанностями).
