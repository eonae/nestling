## [2026-07-06] Token families + модули без рантайм-инкапсуляции

### Контекст

«Динамические инжекты» (on-demand провайдеры) — это не одна фича. За словом
скрываются пять разных потребностей:

1. **Параметризованные провайдеры** — один рецепт, много инстансов по ключу:
   `ILogger(scope)`, `IQueue(name)`, `IHttpClient(upstream)`.
2. **Consumer-aware провайдеры** — инстанс зависит от того, кто его инжектит
   (логгер, названный по классу-потребителю; в Nest — transient + INQUIRER).
3. **Request-состояние** — identity, requestId, транзакция.
4. **Ленивая инициализация** — тяжёлый ресурс, создаваемый при первом обращении.
5. **Рантайм-подграфы** — плагины, per-tenant контейнеры.

Ключевое наблюдение: потребности **1 и 2 — статические**. Они выглядят
«динамикой» только в Nest, где их нельзя выразить иначе как рантайм-резолюцией.
В nestling зависимости объявляются явным массивом — билдер на `build()` видит
все запрошенные члены семейства и может инстанцировать их жадно. Граф остаётся
полным: визуализация, топологический init/destroy и проверка циклов работают
как раньше.

### Решение 1: makeTokenFamily

Формализация паттерна из `examples.simple-app/src/logging/registry.ts`
(ручной Set + фабрика токенов) в фичу контейнера.

```typescript
// Семейство токенов: рецепт один, инстансов много
const ILogger = makeTokenFamily<ILoggerService, [scope: string]>('Logger');

// ILogger('users') → TokenString<ILoggerService>
// - id = "Logger:users"
// - мемоизировано: повторный вызов с тем же параметром → тот же токен

// Инфраструктурный модуль регистрирует ОДИН рецепт на всё семейство:
familyProvider(ILogger, (scope) =>
  factoryProvider(ILogger(scope), (config) => new Logger(scope, config), [IConfig]),
);

// Бизнес-код запрашивает члена семейства как обычную зависимость:
@Injectable([UserService, ILogger('users')])
class CreateUserEndpoint { /* ... */ }
```

Семантика `build()`:

- билдер собирает все члены семейств, упомянутые в deps зарегистрированных
  провайдеров;
- для каждого уникального параметра вызывает рецепт и создаёт обычный узел графа;
- дальше всё как всегда: жадная инстанциация, проверка циклов, lifecycle-хуки.

Никакой рантайм-резолюции. «Динамика» происходит на этапе сборки.

### Решение 2: consumer-aware сахар

```typescript
@Injectable([UserService, ILogger.auto])
class CreateUserEndpoint { /* ... */ }
// ILogger.auto резолвится в ILogger('CreateUserEndpoint')
// в момент регистрации — потребитель известен статически.
```

Покрывает кейс Nest `transient + INQUIRER`, но без transient-скоупа и без
рантайм-магии.

### Решение 3: модули остаются plain objects, видимость — через ES-модули

Наблюдение, недоступное Nest: в nestling инжектят по **токену-значению, который
нужно импортировать**. Не экспортировал токен из `index.ts` модуля — снаружи его
физически невозможно запросить. ES-модули уже являются системой видимости;
рантайм-инкапсуляция (как в Nest) не нужна.

Следствия:

- **Модуль** = plain object: метка принадлежности + единица упаковки
  (providers, endpoints, middleware) + метаданные для графа/визуализации.
- **`exports` как рантайм-механизм — не делаем.** Вместо этого:
  - видимость по умолчанию — ES-экспорты (+ ESLint boundaries между пакетами
    при желании);
  - опциональная строгость: `new ContainerBuilder({ strictExports: true })` —
    на `build()` проверить рёбра готового графа против деклараций exports.
    Это build-time lint, не рантайм. Граф уже есть — проверка дешёвая.
- **Параметризованные модули бесплатны**: модуль — значение, значит
  `LoggingModule({ level: 'debug' })` — просто функция, возвращающая Module.
  Концепция DynamicModule / forRoot / forRootAsync не нужна вообще.

### Решение 4: что НЕ кладём в контейнер

- **Request-состояние (потребность 3)** — никогда не в DI. Типизированный
  request-контекст уже есть: это input пайплайна (`withIdentity` кладёт
  identity — это и есть request scope, причём типизированный). Для глубоких
  сервисов — отдельный пакет `@nestling/context` на AsyncLocalStorage
  (в планах). Это защищает от нестовского bubbling request-scope, заражающего
  граф.
- **Lazy (потребность 4)** — если понадобится: явная обёртка
  `deps: [lazy(HeavyClient)]` → инжектится `Lazy<T>` с `.get(): Promise<T>`.
  Явность вместо прокси. Отложено.
- **Подграфы (потребность 5)** — child-контейнер
  `container.createScope(providers)`: видит синглтоны родителя, свой подграф
  валидирует в момент своего `build()`. Отложено.

### Итоговая рамка

**Инфраструктура = семейства (рецепты) + pipeline-шаги. Бизнес = обычные
провайдеры (экземпляры) + endpoints.** Бизнес-код запрашивает членов семейств;
инфраструктурные модули поставляют рецепты. Разделение бизнес/инфраструктура
становится видимой структурой, а не конвенцией.

### Открытые вопросы

- API `familyProvider`: рецепт возвращает готовый provider-объект или
  `{ deps, factory }`?
- `ILogger.auto` внутри фабричных провайдеров (не классов) — чем считать
  «потребителя»?
- Нужна ли валидация параметров семейства (например, enum допустимых скоупов)?

## [2026-07-06] Стриминг: `stream(T)` ≠ `events(T)`, AbortSignal, источники событий

### AbortSignal — first-class примитив контекста

В `meta` каждого запроса есть `signal: AbortSignal`. Его взводят:

- транспорт — при отвале клиента (закрытие соединения);
- приложение — при graceful shutdown (`App.close()` абортит все in-flight
  запросы и подписки);
- (в будущем) кто угодно ещё — например, админский kill подписки.

Единый механизм отмены для всего: без него бесконечные подписки не завершаются
в принципе, а `close()` виснет на живых соединениях. Хендлер обязан уважать
signal (для `for await` по подписке это происходит естественно, если источник
принимает signal).

### `stream(T)` и `events(T)` — разные модификаторы

Семантика разная, объявляется декларативно в endpoint'е:

| | `stream(T)` | `events(T)` |
|---|---|---|
| Природа | конечные данные (экспорт, большой результат) | открытая подписка |
| Конец | естественный (данные закончились) | нет; «нормальное завершение» = дисконнект |
| HTTP-framing | NDJSON / chunked | SSE: heartbeat, `id:`, реконнект по `Last-Event-ID` |
| Доки | OpenAPI | AsyncAPI |

Словарь исходов завершения (для finish-фазы/наблюдателей):
`completed | disconnected | aborted | failed`. Для `stream` нормален
`completed`, для `events` — `disconnected`.

### Источники событий — это DI, а не особый вид endpoint'ов

Хендлер вызывается один раз **на соединение** и подписывается на источник,
который живёт в контейнере как обычный singleton-сервис (и работает независимо
от наличия подписчиков):

```typescript
// инфраструктура: источник — обычный провайдер
class LogHub {
  #topic = new Topic<LogEvent>();      // broadcast-примитив (пакет utils)
  publish(e: LogEvent) { this.#topic.push(e); }
  subscribe(signal: AbortSignal) { return this.#topic.subscribe(signal); }
}

// endpoint: подписка per-connection
makeEndpoint({
  pattern: 'GET /logs/live',
  output: events(LogEvent),
  handle: async function* (_, meta) {
    yield* hub.subscribe(meta.signal);
  },
});
```

Endpoint-модель остаётся единообразной; никакого нового вида endpoint'ов.

Открытый вопрос: политика `Topic` для медленного подписчика — ограниченный
буфер + drop-oldest или принудительный дисконнект. Pull-модель AsyncIterable
даёт backpressure на соединении бесплатно, но горячий источник не может ждать
медленного клиента — один тормозной подписчик не должен останавливать всех.

### Правило: тип-сохраняющее vs тип-меняющее

- **Тип-сохраняющие** трансформации потока (`T → T`: наблюдение, лимиты,
  таймауты, фильтрация) — инфраструктура, допустимы вне контракта endpoint'а.
- **Тип-меняющие** (`T → T[]` батчинг, `T → T & {id}` обогащение) — часть
  контракта endpoint'а: только там, где они видимы в его декларации.
  Иначе схемы перестают описывать реальные типы и рушится schema-first.

### Реестр подписок — отдельный пакет

Типовая задача: посмотреть активные подписки из другого хендлера, завершить
конкретную и т. д. Делается поверх публичных примитивов (DI + signal +
finish-хук), в ядро не входит:

```typescript
// идея: @nestling/subscriptions
interface SubscriptionInfo { id; endpoint; identity?; startedAt }
class SubscriptionRegistry {
  list(filter?): SubscriptionInfo[];
  abort(id: string): boolean;   // взводит signal конкретной подписки
}
```

Подписка регистрируется при старте events-запроса и снимается в finish;
её signal — комбинация (AbortSignal.any) транспортного и админского.
«Убить подписку» = тот же AbortSignal, что и дисконнект/shutdown.

Ценность как dogfooding-тест: если такой пакет пишется, не трогая ядро, —
значит, публичных примитивов (pipeline-хуки, signal, DI) достаточно.

## [2026-07-06] Pipeline v2: плоские фазы, слои, композиция константами

### Логика принятия решений (как мы сюда пришли)

**1. «After» — это не одна точка, а три.** Стримы делают это видимым:
(a) хендлер вернул результат, первый байт не ушёл — envelope ещё можно менять;
(b) стрим течёт — можно только оборачивать итератор;
(c) всё дотекло / соединение закрылось — можно только наблюдать.
Фреймворки, у которых «after» один (Express, Koa, Nest-интерцепторы),
получают «headers already sent» и костыли вокруг стримов.

**2. Отказ от onion / `next()`.** Классическая Koa-модель отвергнута:
теряется типизированное монотонное накопление input (главная фишка),
появляется скрытый control flow (можно не вызвать next, вызвать дважды,
проглотить ошибку), исчезает статическая анализируемость цепочки
(нужна для explain/визуализации/OpenAPI).

**3. Луковица без next (вариант A) — работает, но плохо читается.**
Парные юниты `{pre, post}`, post-фазы в LIFO. Корректна на error-path
(post запускается только если pre активировался), но: post, объявленный
первым, срабатывает последним; маппер ошибок надо объявлять в начале
цепочки. Непрозрачно.

**4. Требование: вид юнита должен быть виден в декларации.**
Универсальный `.use()` не говорит, что перед тобой — pre, post или обёртка.
Отсюда именованные методы билдера.

**5. Плоские фазы (вариант E) + честная опциональность.** Ключевое озарение:
луковица была нужна только чтобы согласовать типы с рантаймом на пути ошибок.
Есть второй способ — сказать правду в типах: на ответном тракте обогащение
могло не случиться ⇒ ctx там `Partial`. А юниты только-на-успех имеют
железную гарантию: успех ⇒ весь pre-тракт прошёл ⇒ ctx полный.
Понятие «обёртка/wrapper» умирает: транзакция = `pre + ok + catch`,
три явные строчки. Автоматическое LIFO-разматывание ресурсов меняем на
явный порядок — в духе «explicit over implicit».

**6. Слова.** `makePipeline` (конвенция `make*` во всей кодовой базе);
`.catch` — знакомо по Promise, семантика совпадает; `.ok` — рифмуется с
классом `Ok`. Отказы: `after + successOnly: true` — булева опция, меняющая
ТИП ctx колбэка, хуже двух коротких методов; `.then` — запрещён навсегда:
объект с методом then становится thenable, `await pipeline` попытается его
резолвить (ловушка, известная по Knex).

**7. Хендлер — явно в середине (идея: слот/дырка → слои).** Декларация
читается сверху вниз как план исполнения целиком. Композиция пайплайнов
становится структурной: родитель видимо оборачивает потомка, правило
«ответные юниты родителя — последними» следует из формы. Возвращаются
градуированные гарантии типов (см. спецификацию). Точный синтаксис
композиции — открытый вопрос (см. ниже).

**8. Жадная композиция константами, привязка только к endpoint'у.**
Уровни App/module (глобальный пайплайн, модульный) отвергнуты:
отложенная сборка через реестр проверяется только на старте, а жадная
сборка константами — компилятором. Ответ на «переиспользование в модулях»:
модуль-фабрика с параметром `pipeline` — зависимость видна, тип параметра
документирует требуемый контекст, проверка compile-time. Цена: сквозные
инварианты («у всех ручек есть requestId») становятся конвенцией;
смягчение возможно позже — пайплайн интроспектируем, App может на старте
проверять политику («каждый пайплайн содержит withRequestId»).

**9. Классы-юниты и граница миров в типах.** Юниты-классы нужны для DI
(зависимости, lifecycle). Чтобы «полностью функциональный» сценарий остался
гарантией, а не конвенцией, — второй тип-параметр `TNeeds`: накопитель
отложенных зависимостей. Чистый пайплайн — `TNeeds = never` (дефолт,
функциональный API не меняется). Standalone-транспорты принимают только
`Pipeline<any, never>`; App резолвит TNeeds контейнером на старте.
Двухуровневость фреймворка становится видимой в системе типов.

### Спецификация

**Словарь билдера:**

| Метод | Когда | ctx |
|---|---|---|
| `.pre(u)` | до хендлера, по порядку объявления | накопленный, полный |
| `.ok(u)` | ответ = `Ok` | **полный** (свой слой + внешние) |
| `.catch(u)` | ответ = `Fail` | свой слой `Partial`, внешние полные |
| `.after(u)` | всегда на ответном тракте | свой слой `Partial`, внешние полные |
| `.finally(u)` | момент (c), с исходом | как catch + `outcome` |

**Исполнение (один слой):** pre по порядку; падение ⇒ сразу ответная фаза
с `Fail`. Хендлер — если все pre прошли. Ответная фаза — строго в порядке
объявления, юнит применяется по применимости к ТЕКУЩЕМУ ответу и может
его заменить. `finally` — после того как всё дотекло
(`completed | disconnected | aborted | failed`).

**Слои (композиция).** Пайплайн — стек слоёв. Один вызов `makePipeline()`
с цепочкой методов определяет ОДИН слой. Композиция — `compose(outer, ..., inner)`:
список слоёв, читается сверху вниз как «снаружи внутрь» (= порядок в `explain()`).
Понятий «дырка»/«слот»/пустых маркеров нет: плоский однослойный пайплайн —
частный случай. Вложение (`base` оборачивает `authed` оборачивает `mutating`):

- pre-тракты исполняются снаружи внутрь, ответные — изнутри наружу,
  `finally` — изнутри наружу;
- слой исполняется, только если pre всех внешних слоёв прошли ⇒
  **ответные юниты слоя видят контекст внешних слоёв полным
  и гарантированным**; Partial — только для pre собственного слоя;
- требования слоя к внешнему контексту объявляются явно:
  `makePipeline<{ identity: User }>()` — и проверяются компилятором
  в точке композиции.

**Type-state билдера:** `.pre` недоступен после первого ответного метода
(чтение сверху вниз = порядок исполнения, всегда).

**Ограничения v1 (осознанные):**

- **Нет раннего успешного выхода** (gate: кэш, идемпотентность) и
  **нет восстановления в catch** (`Fail → Ok`). Причина: оба ломают
  гарантию полного ctx у `.ok` («успех приходит только из хендлера»).
  Сильная типизация важнее; gate — кандидат в v2 с правилом
  «`.ok` до первого `.catch` — полный ctx, после — Partial».

**Юниты — четыре формы:**

| Форма | TNeeds | Использование |
|---|---|---|
| функция | — | базовый случай |
| инстанс (`new WithTracing(...)`) | — | мост: класс без DI |
| класс (`WithTracing`) | +Constructor | App резолвит из контейнера на старте |
| токен (`RateLimit('strict')`) | +Token | конфигурируемые юниты через token families |

Классы — обычные провайдеры: `@Injectable([deps])`, lifecycle-хуки,
регистрация в модуле, ошибка на старте если не зарегистрирован.
Контракт: юнит — синглтон, per-request состояние только в ctx.

**Переиспользование:** пайплайн — иммутабельное значение. Инфраструктурные
модули экспортируют готовые пайплайны-константы и фабрики
(`authedWith(verifyFn)`). Подключение — только явное, в `makeEndpoint`.
Модули с endpoint'ами принимают пайплайн параметром фабрики:

```typescript
export const makeHealthcheckModule = (opts: { pipeline?: Pipeline<EmptyInput> }) =>
  makeAppModule({
    name: 'module:healthcheck',
    endpoints: [makeHealthEndpoint(opts.pipeline ?? makePipeline())],
  });
```

### Отвергнутые варианты (чтобы не возвращаться)

- **Koa-style `(ctx, next)`** — скрытый control flow, потеря типизации
  и анализируемости.
- **Луковица с LIFO без next (A)** — корректна, но post читается задом
  наперёд, error-маппер объявляется первым.
- **Два списка «тракт запроса / тракт ответа» (B)** — парные вещи
  (транзакция) разваливаются на половинки; гейтинг по активации требует
  value-парности; сложнее плоских фаз.
- **Буквальная вложенность `compose(a, compose(b, h))` (C)** — пирамида,
  боль вывода типов.
- **Именованные страты `.onRequest/.around/.onResponse` (D)** — фиксируют
  структуру, теряется контроль глубины.
- **Уровни привязки App/module/endpoint** — отложенная сборка = потеря
  compile-time проверок; неявность «что навешано на ручку».
- **`after(fn, { successOnly: true })`** — опция, меняющая тип ctx.
- **`.then`** — thenable-ловушка.

## [2026-07-06] Два скоупа обработки: request-pipeline и item-цепочки

### Логика решения

Первый подход к per-chunk логике — обёртки итераторов внутри request-юнитов
(same-type re-add `payload` в pre; type-preserving обёртка `res.value` в after).
Технически работает и даже разрешён текущей типовой машинерией
(`ConflictingKeys` допускает повтор ключа с тем же типом), но: смешивает два
скоупа в одной конструкции, требует хака «состояние счётчиков в мутируемом
ctx-объекте», вынуждает generic-гимнастику (`makePipeline<{payload:
Chunks<unknown>}>()`).

Осознание: у стримов/ивентов **два разных «пайплайна»** — действия на весь
поток (соединение) и действия на каждый элемент. Это разные конструкции
с разной формой, и им нужны разные механизмы.

### Спецификация

| | Request-scope | Item-scope (chunk/event) |
|---|---|---|
| Запускается | раз на запрос/соединение | на каждый элемент потока |
| Форма | фазы `.pre/.ok/.catch/.after/.finally` | линейная цепочка комбинаторов, **фаз нет** |
| Где объявлен | `pipeline: compose(...)` | на io-декларации `stream()`/`events()` |
| Состояние | ctx | внутри цепочки; стандартные счётчики → `summary` |

У элемента нет «хендлера посередине» и нет запроса-ответа — он просто течёт
через последовательность трансформаций. Поэтому никакого словаря фаз:

```typescript
input: stream(LogChunk)
  .tap(c => log.debug(c.message))     // наблюдение
  .filter(c => c.level !== 'debug')   // T → T
  .limit(50_000)                      // Fail при превышении
  .gapTimeout(30_000)                 // разрыв при молчании
  .batch(100),                        // тип-меняющий: хендлер получит Chunks<LogChunk[]>

output: events(OrderEvent)
  .tap(e => metrics.inc('events_out'))
  .throttle(10),                      // только T → T
```

**Асимметрия входа и выхода** (следствие schema-first, а не запрет):

- входная цепочка МОЖЕТ менять тип — она видимая часть контракта endpoint'а:
  схема описывает провод (NDJSON-строка = `LogChunk`), результат цепочки —
  форму хендлера;
- выходная цепочка — только `T → T`: оба её конца зафиксированы
  (хендлер yield'ит по output-схеме, схема описывает провод).

**Правила:**

- Ошибки item-цепочки эскалируют в request-pipeline: комбинатор бросил `Fail`
  → итерация в хендлере кинула → обычные `catch`/`finally`. Если выход уже
  тёк — mid-stream политика транспорта + `finally(failed)`.
- Состояние — внутри цепочки; фреймворк кладёт стандартные метрики
  (`itemsIn/itemsOut/bytes`) в `summary` для `finally`. Хак «счётчики
  в мутируемом ctx» умер вместе с первым подходом.
- Переиспользование — функции-хелперы:
  `const guardedStream = (s) => stream(s).limit(50_000).gapTimeout(30_000)`.
- Escape hatch: `.through(src => wrapped)` — на входе можно с изменением
  типа, на выходе `T → T`.
- **Per-connection vs per-published-event:** item-цепочка работает на копии
  потока ОДНОГО клиента (100 подписчиков → `.tap` сработает 100 раз на одно
  опубликованное событие). Логика «один раз на публикацию» живёт у источника —
  в `Topic`/хабе (DI-сервис), до всяких подписчиков.

### Не переизобретаем ли мы RxJS? (принцип-ограничитель)

Поверхностно похоже (цепочки операторов над потоками), по сути — нет,
и вот дисциплина, которая удерживает границу:

1. **Протокол на границах — стандартный `AsyncIterable`**, не библиотечный
   тип. Pull-модель со встроенным backpressure (медленный клиент просто
   не тянет) — естественная для сервера, в отличие от push-модели Observable,
   где backpressure надо докручивать. Ноль зависимостей; sync iterator
   helpers уже в языке, async-версия идёт через TC39 — мы движемся туда же,
   куда стандартная библиотека.
2. **Набор комбинаторов закрытый и инфраструктурный**: наблюдение, отсечение,
   лимиты, время, группировка. Лакмус: комбинаторы с реордерингом времени,
   слиянием потоков и higher-order streams (`merge`, `switchMap`,
   `combineLatest`) в фреймворк НЕ входят. Это dataflow-программирование —
   место ему в хендлере, где пользователь волен взять хоть RxJS
   (интероп тривиален: `from(asyncIterable)` и обратно).
3. **`Topic` ≈ Subject-lite осознанно**: маленький примитив (bounded buffer
   + AbortSignal), а не парадигма. Антипример перед глазами — Nest, намертво
   прикованный к RxJS через интерцепторы: RxJS навязан всем, а со стримами
   всё равно неловко.

Документация с полными примерами (мостики, отмена, backpressure,
функциональный и классовый стили): [design/rxjs.md](../design/rxjs.md).

### Открытые вопросы (сводно по pipeline v2 и item-цепочкам)

- DI в комбинаторах item-цепочки: io-декларация создаётся вне контейнера.
  v1: комбинаторы — функции/замыкания; логике с DI — request-юнит
  (advanced-путь через обёртку) или хендлер.
- Политика невалидного элемента: `onInvalid: 'skip' | 'fail'` (v1: fail).
- ~~Синтаксис композиции~~ — РЕШЕНО: `compose(outer, ..., inner)`.
  Пустой маркер `.slot()` отвергнут: позиция «дырки» выводима (между
  последним `.pre` и первым ответным методом), маркер без семантики — шум.
- Gate / ранний успешный выход — v2.
- Политика `Topic` для медленного подписчика.
- Policy-check на старте («каждый пайплайн содержит X») — дверь открыта,
  не закладываем.
- Per-transport дефолтные пайплайны — место есть, решение отложено.
