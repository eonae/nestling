## Context

Реестр подписок хранит `identity` — строку, по которой администратор
фильтрует список и убивает подписки конкретного клиента. Значение
вычисляет опция плагина:

```typescript
// packages/nestling.subscriptions/src/registry.ts:32
export type SubscriptionContext = ExtendableContext<AnyInput>;
export type IdentityExtractor = (ctx: SubscriptionContext) => string | undefined;
```

`AnyInput` — это `Record<string, unknown>`, поэтому чтение любого поля
накопленного `input` требует приведения. Приведение стоит в примере
`examples/microservice`, в JSDoc `module.ts` и в двух спеках реестра: это
рекомендованный способ, и он отключает проверку типов ровно там, где
приложение знает форму лучше пакета.

При этом накопленный `input` уже описан значениями — контекстными
переменными (`RequestId`, прикладные `contextVar<T>()('userId')`).
Переменная несёт ключ поля и тип значения, сравнивается по ссылке, а
политика `everyEndpoint(…).hasVar(RequestId)` умеет требовать её объявления
на каждом endpoint'е. В примере такая политика уже стоит. Реестру
достаточно назвать переменную — форму `input` он по-прежнему не знает и
знать не должен.

Constraint пакета: `@nestlingjs/subscriptions` — сателлит. Он строится на
публичных примитивах, из `@nestlingjs/app` берёт пайплайн и `makePlugin`,
и его граница закреплена тестом `boundary.spec.ts`.

## Goals / Non-Goals

**Goals:**

- `identity: RequestId` — первая и рекомендованная форма.
- Вычисляемый ключ из нескольких переменных без приведения.
- Реестр не знает формы `input`: он хранит строку, а не входные данные.
- Ни одного `as` в примере, JSDoc, README и спеках пакета.

**Non-Goals:**

- Параметр типа у реестра (`subscriptions<TInput>({…})`).
- Форма переменной у `labels`.
- Своя политика сборки «переменная `identity` объявлена пайплайном».
- Изменение типа `SubscriptionInfo.identity` и фильтра `list({ identity })`.

## Decisions

### 1. `identity` принимает переменную или функцию

```typescript
/** Переменная, годная в `identity`: её значение — строка */
export type IdentityVar = ReadonlyContextVar<string | undefined>;

/**
 * Вторая форма — вычисление по контексту. Накопленный `input` здесь пуст:
 * значения переменных приходят аргументами из `computed`.
 */
export type IdentityFn = (ctx: ExtendableContext<EmptyInput>) => string | undefined;

export type IdentitySource = IdentityVar | IdentityFn;
```

`ReadonlyContextVar<string | undefined>` принимает и `ContextVar<string, 'requestId'>`
(свойство `$type` ковариантно, лишние свойства структурная типизация
разрешает), и переменную, объявленную как `contextVar<string | undefined>()`.
Тип `ReadonlyContextVar`, а не `ContextVar`: реестру нужно читать
переменную, а не писать её.

**Альтернатива — параметр типа у реестра** (`subscriptions<TInput>({…})`):
отвергнута записью ideas.md. Она убирает `as`, но приложение объявляет
форму `input` вторым экземпляром — руками, рядом с переменными, которые эту
форму уже описали.

**Альтернатива — дженерик на опциях** (`RegistryOptions<TReq>` с выводом
`TReq` из аннотации `ctx`): приложение пишет
`(ctx: ExtendableContext<{ userId: string }>) => ctx.input.userId`.
Приведения нет, но связь с переменной остаётся по имени поля: переименуют
ключ переменной — аннотация продолжит компилироваться и молча промахнётся.
Отвергнута: это та же болезнь без `as`.

### 2. Вычисляемый ключ — хелпер `computed(vars, compute)`

```typescript
export function computed<const V extends readonly AnyContextVar[], T>(
  vars: V,
  compute: (ctx: ExtendableContext<EmptyInput>, ...values: VarValues<V>) => T,
): (ctx: ExtendableContext<EmptyInput>) => T;
```

Форма повторяет `Var.provide(deps, compute)` ядра: список первым
аргументом, контекст первым параметром вычисления, значения следом.
Приложение называет **значения**, а не пересказывает форму `input`:

```typescript
identity: computed([TenantId, UserId], (_ctx, tenant, user) => `${tenant}:${user}`),
```

`VarValues<V>` — кортежный mapped type: `{ [I in keyof V]: V[I] extends
ReadonlyContextVar<infer T> ? T : never }`. Сложных конструкций вроде
`UnionToIntersection` здесь нет намеренно: тип попадает в бюджет пакета.

Хелпер читает значения из `ctx.input` по ключам переменных и зовёт
`compute`. Результат — обычная функция от контекста, поэтому форм в типе
`IdentitySource` остаётся две, а не три.

**Альтернатива — контекст, типизированный переменными**
(`(ctx: ExtendableContext<{ tenantId: string; userId: string }>) => …` с
выводом типа из списка): читается привычнее, но требует
`UnionToIntersection` над кортежем и раздувает бюджет типов у каждого
потребителя. Значения аргументами дают тот же результат дешевле.

### 3. Функция без переменных типизируется `EmptyInput`, а не `AnyInput`

Функция, которой переменные не нужны, остаётся обычной функцией:

```typescript
labels: (ctx) => ({ transport: ctx.endpoint.transport }),
```

Её `ctx.input` теперь `EmptyInput`, то есть пуст. Чтение поля из него —
ошибка компиляции, а не приглашение написать `as`: у автора нет способа
«почти правильно» прочитать накопленный вход мимо переменных. Кому вход
нужен — берёт `computed`.

`labels` получает ту же типизацию (`LabelsFn`, `computed` применим и к
нему), но формы переменной не получает: метки — словарь, переменной
такого типа в коде не встречается. Это зафиксировано в Non-goals.

### 4. Нормализация — один раз, в конструкторе реестра

Конструктор приводит обе опции к внутренней форме
`(ctx: SubscriptionContext) => …`:

```typescript
const readIdentity = isContextVar(options.identity)
  ? (ctx: SubscriptionContext) => asString(ctx.input[options.identity.key])
  : options.identity;
```

Приведение контекста живёт ровно в одном месте пакета — там же, где оно
живёт в ядре у `provide(deps, compute)`. `open()` зовёт готовую функцию и
про формы опции не знает.

Различает формы предикат `isContextVar` из `@nestlingjs/app`: сегодня он
есть в коде ядра (`context/variable.ts`), но из barrel не экспортируется.
Экспорт добавляется — знанием о форме переменной владеет тот, кто
переменную объявляет, а сателлит не должен проверять её `typeof value.key`
собственной копией предиката. Граница пакета этим не нарушается:
`boundary.spec.ts` запрещает сборку приложения и объявление фичи, а не
примитивы пайплайна.

### 5. Значение не строка — подписка без `identity`

Переменная объявлена типом, но в рантайме `input` заполняет пайплайн, и
значение может отсутствовать (юнит `provide` не попал в пайплайн этого
endpoint'а). Тогда запись появляется без `identity` — ровно тот же исход,
что у экстрактора, вернувшего `undefined`. Нестроковое значение трактуется
так же.

Броска здесь нет намеренно: `open()` стоит на горячем пути, до вызова
хендлера, и отказ реестра уронил бы запрос, который к наблюдаемости
отношения не имеет. Гарантию «переменная объявлена» даёт политика сборки
`everyEndpoint(…).hasVar(…)` — то есть она проверяется до первого запроса,
а не на каждом.

## Risks / Trade-offs

- **`labels` без формы переменной выглядит несимметрично** → симметрия тут
  ложная: значение меток — словарь, и переменная `Record<string, string>`
  не встречается ни в одном примере. Хелпер `computed` работает с обеими
  опциями, поэтому вычисление меток из переменных доступно.
- **`EmptyInput` в голой функции ломает код, который читал `ctx.input`
  приведением** → это и есть цель change'а; других потребителей, кроме
  примера и документации, нет.
- **Переменная объявлена, но пайплайн её не кладёт — `identity` пуст молча**
  → политика `hasVar` ловит это на сборке; в примере она уже стоит, в
  рецепте `ops.md` появится строка об этом.
- **Бюджет типов пакета** → `VarValues` — кортежный mapped type без
  распределения по объединениям; `yarn type-budget` входит в `yarn verify`
  и поймает регрессию.
- **Экспорт `isContextVar` расширяет публичную поверхность ядра** →
  предикат уже публичен по смыслу (`AnyContextVar` и `ReadonlyContextVar`
  экспортируются), а альтернатива — копия предиката в сателлите.

## Migration Plan

Обратной совместимости не существует: старая форма экстрактора с
приведением удаляется вместе с примерами. Порядок правок — пакет, затем
пример, затем документация обоих языков.
