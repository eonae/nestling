# multi-injection — tasks

## 1. Сентинел `Family.all` (nestling.container)

- [x] 1.1 Свойство `all` в `TokenFamily<T>`: брендированная строка `"<name>:{all}"`, тип `TokenString<readonly T[]>`; отдельный индекс `.all`-сентинелов (`tokenId → family`), НЕ `memberIndex` — иначе фикспоинт материализации примет агрегат за члена (design D1)
- [x] 1.2 Резервирование параметра `{all}`: `Family('{all}')` бросает с именем семейства и указанием на `Family.all` (симметрично `{auto}`)
- [x] 1.3 Внутренние хелперы билдера: «токен — это `.all` семейства F?» и «токены зарегистрированных членов семейства F в порядке регистрации» (обход insertion-ordered `#providers`, членство — через реестр семейства, не парсингом id; design D6, D7)
- [x] 1.4 Юнит-тесты сентинела: id `"HealthCheck:{all}"`; типовой тест на `readonly T[]` в конструкторе потребителя; ошибка на `Family('{all}')`

## 2. Фаза агрегатов в `build()` (nestling.container)

- [x] 2.1 `materializeFamilyAggregates()` — новая фаза строго после `materializeFamilyMembers()` и до `instantiateAll()`: сбор `.all`-сентинелов, упомянутых в deps зарегистрированных провайдеров, и регистрация на каждый обычного `factoryProvider(Family.all, (...members) => Object.freeze(members), [...memberTokens])` (design D3, D4, D5)
- [x] 2.2 Deps-driven: агрегаты создаются только для упомянутых `.all`; неупомянутый `.all` узла не порождает; `.all` не форсит материализацию членов (design D3, D6)
- [x] 2.3 Запрет регистрации собственного провайдера на `.all`-токен (прямая регистрация, `providers` модуля, результат рецепта) — ошибка при регистрации, называющая токен и причину «зарезервирован за узлом-агрегатом» (design D9)
- [x] 2.4 `.all` разрешён в deps любого определения; проверка `assertNoAutoSentinels` остаётся относящейся только к `.auto` (design D10)
- [x] 2.5 Атрибуция агрегата: `metadata.module === undefined`; в `strictExports` и `computeExported` никаких спец-веток не добавляется (design D11)

## 3. Рантайм-тесты агрегата (nestling.container)

- [x] 3.1 Состав: вклады из разных модулей (`classProvider(IHealthCheck('db'), …)`) собираются в массив; те же инстансы, что в узлах-членах; семейство без `familyProvider` агрегируется штатно
- [x] 3.2 Состав + материализация: член, порождённый рецептом из deps, и член из `.auto` входят в массив; член, созданный вызовом `Family('orphan')` без потребителя и без явного провайдера, — не входит и узла не имеет
- [x] 3.3 Дедупликация: два потребителя `.all` → один узел и один и тот же массив; вклад, дополнительно инжектимый напрямую по членскому токену, в массиве один раз тем же инстансом
- [x] 3.4 Пустое семейство: узел без deps, значение `[]`, сборка успешна (design D8)
- [x] 3.5 Порядок: вклады модулей `a`, `b`, `c` → порядок `a`, `b`, `c`; явные вклады предшествуют материализованным фикспоинтом (design D7)
- [x] 3.6 Заморозка: массив заморожен, `push` состава не меняет
- [x] 3.7 Агрегат — обычный узел: цикл `агрегат → член → агрегат` (провайдер члена deps'ит `.all`) даёт ошибку сборки с токеном `"HealthCheck:{all}"`; порядок lifecycle (init вкладов до init потребителя, destroy вкладов после destroy потребителя, по одному разу); узел присутствует в `toJSON()`/`traverse()` с рёбрами на членов
- [x] 3.8 `.all` в deps `factoryProvider` — сборка успешна, фабрика получает массив
- [x] 3.9 Неупомянутый `.all`: узла нет, `container.get(Family.all)` → `null`
- [x] 3.10 `strictExports`: неэкспортированный вклад → ошибка с ребром `"HealthCheck:{all}" → "HealthCheck:db"` и модулем-владельцем; `exports: [IHealthCheck]` у модуля-вкладчика → сборка успешна; ребро `потребитель → агрегат` свободно
- [x] 3.11 Ошибка на попытке зарегистрировать провайдер с `provide: Family.all`
