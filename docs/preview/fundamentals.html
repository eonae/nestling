Nestling / Основы

Основы

Как всё собирается и живёт: контейнер, фазы жизненного цикла, конфигурация без process.env в коде, стриминг и тестирование без моков-магии.

Контейнер

@nestling/container — фундамент фреймворка: типобезопасный DI без единой сторонней зависимости, на стандартных декораторах ECMAScript. Его можно использовать и отдельно — во фронтенде, в CLI, рядом с любым фреймворком.

Жадный, а не ленивый

Контейнер жадный: на build() он инстанцирует весь граф разом. Это не деталь реализации, а источник почти всех гарантий Nestling:

  • Циклы обнаруживаются при топосортировке — падение на старте, не в проде.
  • Недостающая зависимость = ошибка build() с именем токена.
  • Полный граф ⇒ визуализация, топологический init/destroy и explain работают всегда.
  • «Не выбрал фичу → её код не построился» получается само собой (см. монолит).

Lifecycle-хуки в топологическом порядке

Провайдер может реализовать @OnInit (захват ресурса: пул БД, connect) и @OnDestroy (освобождение). В отличие от Nest, они исполняются в строгом топологическом порядке: init — от листьев к корню, destroy — строго в реверсе. Никакой неопределённости «что раньше — хук модуля или сервиса». 

@Injectable([DbConfig])
export class Database {
  #pool!: Pool;
  constructor(private cfg: Config<typeof DbConfig>) {}

  @OnInit() async connect() { this.#pool = await createPool(this.cfg.url); }
  @OnDestroy() async close() { await this.#pool.end(); }
}
Стандартные декораторы

Nestling использует декораторы из спецификации ECMAScript, а не экспериментальные декораторы TypeScript с reflect-metadata. Параметр-декораторов в стандарте пока нет — поэтому зависимости объявляются массивом в @Injectable([...]), а не через параметры. Это цена, которая заодно делает граф явным.

Multi-injection

Частый паттерн: разные модули независимо контрибьютят реализации одного контракта — health checks, миграции, валидаторы, обработчики событий — а один потребитель хочет получить весь набор массивом, не зная состава. В Angular это multi: true (несколько провайдеров делят токен), в Nest — вообще ручная сборка.

В Nestling это ещё одно применение token families — и без потери «один токен — один узел». Каждый вклад — обычный провайдер с членским токеном семейства; агрегат — сентинел Family.all, который на build() резолвится в массив всех зарегистрированных членов: 

export const IHealthCheck = makeTokenFamily<HealthCheck, [name: string]>('HealthCheck');
// каждый модуль регистрирует свой вклад как ОБЫЧНЫЙ провайдер
export const DbModule = makeAppModule({
  name: 'module:db',
  providers: [classProvider(IHealthCheck('db'), DbHealthCheck)],
  exports: [IHealthCheck],   // явный контракт: «я контрибьючу в семейство»
});
@Injectable([IHealthCheck.all])   // TokenString<HealthCheck[]>
export class HealthEndpoint {
  constructor(private checks: HealthCheck[]) {}

  async handle() {
    const results = await Promise.all(this.checks.map(c => c.probe()));
    return new Ok({ ok: results.every(r => r.ok), results });
  }
}

Никакого registry, никакой рантайм-резолюции

Состав массива определяет регистрация в контейнере, а не побочные эффекты импортов. На build() билдер спрашивает у реестра семейства, какие из зарегистрированных провайдеров — его члены, и создаёт синтетический узел-агрегат с рёбрами на каждого. Дальше это обычный узел полного графа: циклы обнаруживаются, init/destroy идут топологически (все вклады инициализированы до агрегатора), визуализация видит всё.

Бесплатная синергия с фичами

Раз состав массива = что зарегистрировано, то выбор фич фильтрует его автоматически: не выбрал фичу → её health-check'ов нет в массиве. Тем же механизмом, что «не выбрал фичу → её провайдеры не построились». Side-effect-реестры (глобальный Set, наполняемый при импорте) именно на этом и ломаются — Nestling их не использует нигде.

Почему не multi: true

У каждого вклада — свой токен (IHealthCheck('db')), поэтому он остаётся индивидуально адресуемым: его можно заинжектить точечно, увидеть в графе, атрибутировать модулю. multi: true сваливает всех в один токен и всё это теряет. Агрегат — производное ребро графа, а не особый вид провайдера.

Жизненный цикл

App проводит приложение через семь фаз. Порядок этих фаз — не оформление, а несущая конструкция: именно он делает ряд ошибок структурно невозможными. 

0  BOOTSTRAP   load + validate config · select        → FAIL-FAST
1  ASSEMBLE    build граф · discover · bind ports      → FAIL-FAST
2  INIT        @OnInit: захват ресурсов · connect       (dispatch НЕ существует)
3  WIRE        регистрация эндпоинтов                    (dispatch РОЖДАЕТСЯ здесь)
4  START       @OnStart: serve(dispatch, signal)         — НЕ listen()
5  RUN         обработка запросов · live config-refs
6  SHUTDOWN    реверс START · abort in-flight · @OnDestroy

Гарантия, а не конвенция

Классическая ошибка: транспорт начинает слушать сокет в @OnInit, когда роутинг ещё не готов — и первые запросы летят в пустоту. Nest полагается на конвенцию «не делайте так». Nestling делает это невозможным:

  • у транспорта нет nullary-метода listen();
  • уйти в эфир можно только приняв готовый dispatch: serve(dispatch, signal);
  • а dispatch — фазовый ресурс, он рождается в WIRE, между INIT и START.

Раннему listen просто нечего маршрутизировать — dispatch'а ещё не существует. Порядок 2→3→4 несущий: слить WIRE в ASSEMBLE нельзя, иначе dispatch станет доступен слишком рано и гарантия сломается. Это и есть «guarantee over convention» в чистом виде.

ХукСмысл
@OnInitЗахватить ресурс: подключиться к БД/NATS. Транспорт подключён, но не в эфире.
@OnStartGo-live: начать обслуживать (serve). Только здесь, только с готовым dispatch.
@OnDestroyОсвободить ресурс. Исполняется строго в реверсе топосорта.

При SIGTERM/SIGINT shutdown идёт в обратном порядке: остановить приём → прервать in-flight через meta.signal → закрыть ресурсы. Graceful shutdown встроен, не прикручен сбоку.

Конфигурация

Конфиг в Nestling — не отдельная подсистема и не «стадия конфигурации». Это частный случай зависимости. Секция объявляется схемой, инжектится как типизированный срез, и валидируется жадно на старте: невалидный конфиг = FAIL-FAST. 

export const OrdersConfig = makeConfig('orders', z.object({
  maxItems:    z.coerce.number().default(100),   // ← ключ ORDERS_MAX_ITEMS
  databaseUrl: from('DATABASE_URL', z.url()),    // точное имя ключа, без префикса
}));

// наружу из пакета — только хэндл ключей; сам токен не реэкспортируется
export const ordersKeys = OrdersConfig.keys;
@Injectable([OrdersConfig])
export class OrdersService {
  constructor(private cfg: Config<typeof OrdersConfig>) {}

  create(dto: NewOrder): Order {
    if (dto.items.length > this.cfg.maxItems) throw TooManyItems({ max: this.cfg.maxItems });
    /* ... */
  }
}

Секция не знает, откуда пришло значение

Ключевая идея — source-agnostic. Секция называет ключ (maxItems → ORDERS_MAX_ITEMS), но не источник. Откуда взялось значение — из env, файла или Vault — это концерн ядра (kernel), а не пользовательского кода. Секция читает ключ так же слепо, как процесс читает файловый дескриптор.

Единственный контакт с process.env — внутри ядра. Пользовательский код его не трогает вообще. Привязка источников — прогрессивная: если у тебя только .env, в composition root про конфиг не написано ничего. Появился второй источник — привязываешь его плоским списком: 

// только env → ничего писать не нужно
await assemble({ modules: [OrdersModule], transports: [http()] }).run();

// добавили Vault и файл → привязка в корне, порядок = приоритет
await assemble({
  modules: [OrdersModule],
  transports: [http()],
  config: [
    [vault(), [ordersKeys]],               // привязка по ключам, не по токенам
    [file('config.yaml'), ['*_URL']],
  ],
}).run();

Приватность секции

У секции две capability — и это два разных объекта. Токен (право инжекта) не экспортируется из пакета: чужой инжект невозможен даже синтаксически — нарушение нечем написать. Это та же ES-видимость, что охраняет kernel-токены, и никакой отдельной регистрации секции в модуле не нужно — билдер видит её как обычную зависимость. .keys (право привязки) — branded-хэндл набора ключей; инжектировать его нечем, поэтому экспортировать безопасно. Корень получает ровно ту capability, которая ему нужна, — и не получает ту, которая не нужна никому.

Reloadable-конфиги

Источник с наблюдением (reloadableFile, vault({ watch: true })) на изменение пере-проецирует reloadable-секцию: инстанс стабилен, поля обновляются на месте. Две асимметрии со стартом:

  • старт: невалидный конфиг → die. reload: невалидный → keep last-good + warn. Живой процесс не падает из-за плохого горячего значения.
  • вступит ли изменение в силу — ответственность потребителя. Поэтому reloadable — opt-in.
export const Runtime = makeConfig.reloadable('runtime', z.object({
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  rps:      z.coerce.number().default(100),
}));

@Injectable([Runtime])
class RateLimiter {
  #bucket = new TokenBucket(100);
  constructor(private cfg: Config<typeof Runtime>) {}
  @OnStart() start(signal: AbortSignal) {
    this.#bucket.refill(this.cfg.rps);
    this.cfg.onChange(signal, (next) => this.#bucket.refill(next.rps)); // отписка по signal
  }
}
Kernel space / user space

Граница между тем, что пишешь ты, и тем, чем владеет фреймворк, устроена как в ОС. Kernel (источники конфига, транспорты, шина, машинерия графа) — токены не экспортируются, поэтому из user-space их физически нечем инжектить. Пересечь границу можно только через «системные вызовы»: инжект Config<X>, вызов Port/Emitter, возврат из endpoint. Enforcement — не рантайм-ACL, а видимость ES-модулей.

Асинхронный контекст

Накопленный контекст пайплайна доступен хендлеру явно — через meta. Но requestId нужен и логгеру в репозитории тремя слоями ниже, а протаскивать его параметрами через все сигнатуры никто не станет. Ответ Nestling: значение едет ambient'ом (AsyncLocalStorage), зависимость — явная, доступ — только чтение. 

export const RequestId = contextVar<string>('requestId');   // branded-ключ, как token<T>()

// обогащение — как и раньше, монополия pre-юнитов:
// .pre(withRequestId())  →  + { requestId } в контекст и в ALS-проекцию

// глубокий сервис читает через ИНЖЕКТИРУЕМЫЙ ридер:
@Injectable([Ctx(RequestId)])
export class AuditLog {
  constructor(private requestId: CtxReader<string>) {}
  write(e: AuditEvent) {
    this.log.info({ requestId: this.requestId.get() }, e.name);
  }
}

Как это устроено и почему именно так:

  • Запись — только pre-юниты. ALS — не второй канал обогащения, а read-only проекция накопленного контекста; единственный писатель — рантайм пайплайна. Никакого Context.set() из произвольного места.
  • Зависимость видна в графе. Ctx(RequestId) — член token family: кто читает ambient — видно в DI-графе, в визуализации и в explain(); в тестах ридер подменяется обычным valueProvider — ALS не нужен. И поскольку билдер видит всех запрошенных членов семейства статически, полный список ambient-чтений приложения известен уже на build().
  • get() / peek() — зеркало асимметрии пайплайна. На успешном тракте контекст полный — get(): T гарантирован. В .catch/.finally pre-тракт мог не дойти до нужного юнита, а в @OnStart/cron scope вообще не открыт — там честный peek(): T | undefined. Провальный get() бросает с диагностикой: рантайм знает, в какой фазе вы находитесь.
  • В проекции — только накопленный input (+ signal как well-known var: отмена нужна и глубоко в сервисах). raw и endpoint в ambient не отдаются — это была бы протечка транспорта в домен.
  • Сквозь порты. In-proc контекст течёт через port.call() сам; для remote-портов vars с propagate: true едут в заголовках (NATS), и транспорт на той стороне открывает scope заново.
Почему не статический AsyncContext.get()

Классическое решение (статик поверх ALS-Map со строковыми ключами) — глобал: зависимость не видна в графе, тесты требуют настоящего ALS, присутствие ключа не типизировано, а запись разрешена откуда угодно. Инжектируемый read-only ридер закрывает все четыре пункта — ценой одной строчки в deps. Строгая проверка присутствия (каждый читатель достижим только из endpoint'ов, чей пайплайн кладёт ключ) — opt-in policy-check на build(), в духе strictExports.

Стриминг

Стриминг — на стандартном AsyncIterable, а не на библиотечном типе. Pull-модель даёт backpressure бесплатно: медленный клиент просто не запрашивает следующий элемент. Именно поэтому RxJS нет на границах фреймворка (он push, backpressure надо докручивать) — но он полностью доступен внутри хендлера.

Верхний уровень input/output — это форма, а листья — схемы: значение (схема как есть), stream(T), events(T), multipart({ fields, files }). Форма определяет и способ валидации (значение — целиком, поток — поэлементно в обе стороны), и media type, и framing ответа. Файловое поле объявляется upload({ maxSize, mime, multiple }), и лимиты применяются во время разбора — файл сверх лимита не буферизуется целиком ради того, чтобы потом быть отвергнутым.

stream(T) ≠ events(T)

Две разные формы io-декларации с разной семантикой:

stream(T)events(T)
Природаконечные данные (экспорт, большой результат)открытая подписка
Конецестественный — данные закончилисьнет; «нормально» = дисконнект
HTTP-framingNDJSON / chunkedSSE: heartbeat, id:, реконнект
ДокиOpenAPIAsyncAPI
 
export const streamLogs = httpEndpoint({
  method: 'POST',
  path: '/logs/stream',
  input: stream(LogChunk),                  // NDJSON: объект на строку, каждый валидируется
  output: z.object({ processed: z.number() }),
  pipeline: makePipeline(),
  handle: async (chunks: AsyncIterableIterator<LogChunk>) => {
    let processed = 0;
    for await (const chunk of chunks) processed++;
    return { processed };
  },
});
Исход потока честен только по факту доставки

Для потоковой формы .finally вызывается после того, как поток дотёк, оборвался ошибкой или был закрыт потребителем, — а не после ответной фазы, когда не ушёл ещё ни один байт. Пайплайн отдаёт транспорту итератор-обёртку, и её закрытие ровно один раз считает исход и выполняет наблюдателей; отсюда обязанность транспорта потребить итератор либо закрыть его. Счётчики ctx.summary (itemsIn/itemsOut, плюс байты там, где транспорт их знает) к этому моменту досчитаны.

Отказ посреди потока статус сменить уже не может: NDJSON-ответ обрывается (клиент видит незавершённый chunked), SSE получает кадр event: error с телом отказа и закрывается. В обоих случаях исход — failed, а .catch не вызывается: заменять ответ физически не на что.

AbortSignal — first-class примитив

В meta каждого запроса есть signal: AbortSignal. Его взводят: транспорт (клиент отвалился), приложение (graceful shutdown), администратор (kill подписки). Это единый механизм отмены для всего — без него бесконечные подписки не завершаются, а close() виснет на живых соединениях.

Источники событий — это DI

Источник живёт в контейнере как обычный singleton и работает независимо от подписчиков. Хендлер вызывается один раз на соединение и подписывается на него: 

@Injectable([])
export class LogHub {
  #topic = new Topic<LogEvent>({ buffer: 1000, onSlowConsumer: 'disconnect' });
  publish(e: LogEvent) { this.#topic.push(e); }
  subscribe(signal: AbortSignal) { return this.#topic.subscribe(signal); }
}

// endpoint: подписка per-connection
handle: async function* (_, meta) {
  yield* hub.subscribe(meta.signal);       // отписка сшита с отменой
}

Два скоупа обработки

У потоков две разные «цепочки»: действия на весь поток (request-scope: фазы .pre/.ok/...) и действия на каждый элемент (item-scope). Второе объявляется прямо на io-декларации линейной цепочкой комбинаторов — фаз тут нет, элемент просто течёт сквозь трансформации: 

input: stream(LogChunk)
  .tap(c => log.debug(c.message))    // наблюдение
  .filter(c => c.level !== 'debug')  // T → T
  .limit(50_000)                     // Fail при превышении
  .gapTimeout(30_000)                // разрыв при молчании
  .batch(100),                       // тип-меняющий: хендлер получит батчи
Не переизобретаем ли мы RxJS?

Нет — и граница держится дисциплиной. Набор комбинаторов закрытый и инфраструктурный: наблюдение, отсечение, лимиты, время, группировка. Всё, что про реордеринг времени и слияние потоков (merge, switchMap, combineLatest) — это dataflow-программирование, ему место в хендлере, где ты волен взять хоть RxJS. Интероп тривиален: from(asyncIterable) и обратно, а отмена сшивается через meta.signal автоматически.

Схемы и OpenAPI

Всё, что пересекает границу приложения, объявлено схемой: вход и выход endpoint'а, секция конфига, payload контракта. При этом Nestling не привязан к конкретному валидатору: ядро принимает Standard Schema — общий интерфейс, спроектированный совместно авторами Zod, Valibot и ArkType. Любая схема, реализующая проперти ~standard, работает из коробки: Zod (v4, включая zod/mini), Valibot, ArkType, Effect Schema. 

// Zod — привычный дефолт…
export const NewOrder = z.object({ items: z.array(OrderItem).min(1) });

// …но контракт тот же на Valibot или ArkType — выбор валидатора за тобой:
export const NewOrder = v.object({ items: v.pipe(v.array(OrderItem), v.minLength(1)) });
export const NewOrder = type({ items: OrderItem.array().atLeastLength(1) });

Рантайму от схемы нужны ровно два свойства: validate (невалидный payload → 400 со стандартным списком issues: { message, path }[] — формат гарантирован спекой, а не вендором) и инференс типов для хендлера. Сам zod при этом — не зависимость ядра: валидатор приносит приложение. Лёгкий бандл (zod/mini, Valibot) или богатый синтаксис (ArkType) — твой трейд-офф, не наш.

OpenAPI: конвертер — явная зависимость

Standard Schema стандартизует только валидацию. Интроспекции в спеке нет: в рантайме схема — чёрный ящик с непрозрачной функцией validate, и сгенерировать из неё JSON Schema через общий интерфейс невозможно — нужно нырять во внутренности конкретного валидатора (z.toJSONSchema(), @valibot/to-json-schema, …). Поэтому модуль документации не «угадывает» валидатор — конвертер объявляется явно, в composition root: 

import { openapi } from '@nestling/openapi';
import { zodConverter } from '@nestling/openapi.zod';

await assemble({
  modules: [OrdersModule],
  transports: [http()],
  docs: openapi({
    info: { title: 'Orders API', version: '1.0.0' },
    converters: [zodConverter()],   // схемы какого вендора умеем документировать
  }),
}).run();

Дальше работает знакомая механика жадного старта. Все endpoints известны на build(), у каждой схемы есть поле ~standard.vendor — на инициализации модуль сверяет вендоров со списком конвертеров. Схема, которую нечем конвертировать, — это ошибка запуска, а не пустая секция в /docs через месяц. Если документация включена, недокументируемых endpoint'ов не бывает.

  • Несколько валидаторов в одном приложении — законно: сторонний модуль может быть написан на Valibot, пока твой код на Zod. Схема сама сообщает вендора, converters — список.
  • Escape hatch: явный jsonSchema: в декларации endpoint'а перекрывает конвертер — для экзотического валидатора или ручной доводки.
  • Ошибки — тоже контракт: errors: [EmailTaken] из декларации превращается в responses, а неявный UnknownError — в default-ответ.
  • Стриминг: для stream/events та же машинерия генерирует AsyncAPI.
Почему не универсальный генератор

Поле vendor существует в спеке именно как дискриминант для безопасного даункаста: авторы Standard Schema прямо признали, что потребителям иногда нужно спускаться под общий интерфейс. Конвертер — это и есть оформленный даункаст: @nestling/openapi.zod peer-зависит от zod и живёт в его мажорах. Если сообщество стандартизует ещё и JSON Schema-выход, конвертеры выродятся в один универсальный — сигнатура openapi() не изменится.

Тестирование

Правило одно: уровень теста = граница видимости. Внутри пакета видно всё — юнит- и модульные тесты живут рядом с кодом, и приватность токенов им не мешает по построению. Приложению видны только публичные capability — app-тесты мокают на архитектурных швах, а не в чужих внутренностях. Тестовая поверхность — это экспортная поверхность.

Уровень 0: без фреймворка

Провайдеры — обычные классы и фабрики с явными зависимостями, конфиг-срез — объектный литерал, порт — объект с call. У юнит-теста нет импортов из @nestling/*: 

const svc = new OrdersService({ maxItems: 2, databaseUrl: 'postgres://test' });
expect(() => svc.create({ items: [a, b, c] })).toThrow();

App-тест: тестовый composition root

Мок в Nestling — не патчинг и не перехват module system, а подстановка в графе до инстанциации. Тест — это просто другой composition root: 

await using app = await assembleTest({
  features: [OrdersFeature],
  config: [[vars({ ORDERS_MAX_ITEMS: '5' }), '*']],           // in-memory источник
  overrides: [[OrdersRepo, inMemoryOrdersRepo()]],            // токен → фейк
  stubs: [stub(ChargeCard, async () => new Ok({ chargeId: 'test' }))],
});

const res = await app.call(CreateOrder, { items });           // полный пайплайн, без сокетов
expect(res.isFail).toBe(false);
  • Прунинг. Осиротевшее поддерево заменённого узла выпадает из графа: замокал репозиторий → pg-пул не инстанцируется и не коннектится. Тест получает минимальный граф бесплатно.
  • Без сокетов. Тестовый app проходит фазы 0–3: dispatch уже рождён (WIRE), START не выполняется — транспорты не в эфире. app.call/app.emit типизированы схемами и гонят запрос через весь пайплайн — это и отличает app-тест от юнита.
  • await using. Symbol.asyncDispose даёт честный SHUTDOWN в реверсе — никаких повисших ресурсов между тестами.
  • overrides есть только у assembleTest. В боевом assemble подмены графа не существует — даже как соблазна.

Швы вместо чужих токенов

Всё, что app-тест хочет подменить, уже имеет свою дверь — чужие внутренности не нужны:

ШовИнструмент
Конфиг (+ reload)vars({...}) — объектный источник с watch/set(): тестируется и горячая перезагрузка (keep-last-good, onChange). process.env не трогается → тесты параллелятся.
Чужая фичаstub(Contract, impl) — фейк-порт, валидируемый схемой контракта при каждом вызове.
Cross-cuttingfamilyOverride(ILogger, () => noop) — подмена рецепта всего семейства.
Request-контекстvalueProvider(Ctx(RequestId), 'test-id') — ALS в тесте не нужен.
Транспортне мокается: in-proc app.call вместо HTTP-клиента.
Мок не может врать

stub(Contract, ...) валидируется схемой контракта на каждом вызове — фейк, разъехавшийся с реальным сервисом, падает сразу, а не «зелёный тест, красный прод». Класс багов, который плодят jest-моки, исчезает by design: guarantee over convention, продолженный в тесты.

.check(): вся топология одним тестом

Жадный контейнер делает build() универсальным ассертом: циклы, недостающие зависимости, port-биндинг, полнота env. .check() гоняет фазы 0–1 — конструкторы без @OnInit, то есть без единого коннекта: 

for (const select of ['all', 'orders', 'billing']) {
  test(`топология ${select} собирается`, () =>
    assembleTest({ features, select }).check());
}

Все split-топологии L4 валидируются в CI без деплоя.

Модуль в изоляции и тестовая capability

testModule(OrdersModule, { stubs }) — мини-app вокруг одного модуля: неудовлетворённые импорты обязаны быть застабаны явно, ошибка перечисляет недостающие токены. Живёт внутри пакета модуля — токены видны без экспорта. А если модуль хочет разрешить приложению мокать свою инфраструктуру, он экспортирует курируемую поверхность (токены + готовые фейки вроде inMemoryOrdersRepo()) через subpath ./testing — conditional export, который в проде просто не резолвится.

Почему не jest.mock

Перехват module system — runtime magic: мок живёт вне графа, контейнер о нём не знает, прунинг невозможен, валидировать фейк схемой некому. Подстановка на ASSEMBLE даёт то же самое — но в графе, с проверками и типами. А чужое неэкспортированное не мокается вообще — иначе граница видимости была бы декорацией; для крайних случаев модуль подменяется целиком: он ведь значение.
