# design — plugins: cross-cutting без нового примитива

## Context

Что уже есть и на что опираемся:

- **Модуль — plain value.** `makeModule` (`packages/nestling.container/src/modules/modules.ts:59`)
  — identity-функция; `Module` несёт `name`, `providers` (массив или фабрика),
  `imports`, `exports`. Параметризованный модуль уже выразим и назван каноном
  в [`design/container.md`](../../../docs/design/container.md): «просто
  функция, возвращающая модуль; `DynamicModule`/`forRoot` не нужны».
- **`ContainerBuilder.registerModule`** (`container.builder.ts:279`) —
  рекурсивный обход `imports`; загруженные модули помнятся в
  `#modules: Set<string>`, при повторе имени метод делает `return`. Имя модуля
  служит **ключом атрибуции**: `#moduleExports.set(m.name, …)`,
  `#providersFactories.set(m.name, …)`, `metadata.module` у узлов графа.
- **`discoverEndpoints`** (`packages/nestling.app/src/discovery.ts:41`) —
  зеркальный обход того же дерева со своим `visited: Set<string>` по имени;
  порядок и правила дедупликации специально выровнены с билдером
  (capability `endpoint-discovery`), включая текущее «одноимённые считаются
  одним».
- **Порядок фазы 1** (`app.ts:307`): `builder.register(kernel)` →
  `register(modules)` → `register(providers)` → `register(transports)` →
  `discoverEndpoints(plan.modules)` → `builder.build()` → проверки транспортов,
  форм io и политик. Регистрация модулей идёт **до** дискавери.
- **Фичи** (`feature.ts:129`) уже запрещают одноимённые разные значения:
  «Two different features are named 'X'. Feature names are the selection
  vocabulary, so they must be unique.» — готовая формулировка правила и тон
  диагностики.
- **Политики** (#28) дают `everyEndpoint({ transport?, pattern? }).hasLayer(ref)`
  с идентичностью слоя по ссылке — механизм, которым выражается вездесущность
  инфраструктурного слоя.
- **Конфиг** (#9) даёт `makeConfig('prefix', { … })` с keys-capability: секцию
  объявляет тот, кто её читает, токен секции не экспортируется, наружу уезжает
  `.keys` — то есть «конфиг плагина едет с плагином» уже выразимо.

Ограничения, формирующие дизайн:

1. **Имя модуля — ключ, а не подпись.** По нему атрибутируются провайдеры,
   экспорты и фабрики; в диагностике политик модуль-объявитель тоже назван
   именем. Два разных значения под одним именем ломают эту адресацию — какое
   бы из них ни выиграло.
2. **Одноимённая коллизия сегодня молчит дважды** — в контейнере теряются
   провайдеры второго значения, в дискавери — его эндпоинты. Причём
   зафиксировано это не случайно, а требованием
   (`endpoint-discovery`: «дедуплицируются по имени, не по ссылке») и тестом
   `discovery.spec.ts:107`.
3. **Ссылочное равенство модулей стабильно только внутри одного экземпляра
   пакета.** Две копии библиотеки в `node_modules` (dual package hazard) дают
   два значения с одним именем — и это именно тот случай, который сегодня
   схлопывается молча, а завтра должен называть себя вслух.
4. **`plugins?` живёт только в design-доке.** В `AssemblySpec`
   (`plan.ts:39`) поля нет и никогда не было — снятие ничего не ломает в коде,
   но требует правки целевого дока и пометки в журнале решений.
5. **Change размера S не должен превращаться в новую подсистему.** Всё, что
   решается конвенцией и тестом, решается конвенцией и тестом; в ядро уходит
   ровно одна проверка.

## Goals / Non-Goals

**Goals:**

- зафиксировать «плагина как примитива нет» **требованием**, а не устной
  договорённостью: ни типа, ни поля корня, ни хука конфигурации;
- сделать конвенцию «инфраструктура = параметризованный модуль» безопасной:
  разделение значения импортом работает, коллизия имён падает;
- дать канону проверяемые свойства — feature-scoped инфра едет с фичей,
  требование окружения падает на ASSEMBLE, вездесущность слоя гарантируется
  политикой;
- провести различительную линию «что параметр модуля, а что конфиг-секция»,
  чтобы канон не расплывался при первом же применении;
- показать всё это в примере целиком, не добавив в ядро ни одного примитива.

**Non-Goals:** новый примитив, ambient middleware, per-transport дефолтный
пайплайн, новые предикаты политик, мемоизация модулей по опциям,
автогенерация имени. См. Non-goals в [proposal.md](./proposal.md).

## Decisions

### D1. Плагин раскладывается на существующие примитивы — таблица соответствий

Целевой док получает не «главу про плагины», а раздел про инфраструктуру, где
каждая часть чужого примитива названа своим механизмом:

| Часть `PlatformAppPlugin` | Механизм nestling |
|---|---|
| `modules()` в root | `modules:`/`providers:` корня — для процесс-глобальной инфраструктуры; `modules:` фичи — для feature-scoped |
| параметризация плагина | функция, возвращающая модуль: `logging({ … })`; значение создаётся один раз и импортируется |
| конфиг плагина | секция `makeConfig`, объявленная самим инфра-модулем; наружу — только `.keys` |
| `forTransports()` | обычная зависимость от токена транспорта → fail-fast на ASSEMBLE |
| `configureMiddleware` | экспортируемый pipeline-слой + `everyEndpoint(…).hasLayer(ref)` |
| error-formatting/sending | `.catch`/`.finally`-юниты того же слоя (модель ошибок #15) |
| `contextEnrichers` | `pre`-юнит слоя; глубокое чтение — `Ctx(Var)` из #16 |

Ценность таблицы — не в полноте, а в том, что она **закрывает вопрос**: у
каждой части есть адрес, и ни одна не требует нового понятия.

**Альтернативы.** (а) Ввести `Plugin` как тонкую обёртку над модулем ради
узнаваемости имени — отвергнуто: обёртка ничего не добавляет к значению,
но заводит второй способ сказать «модуль», а вместе с ним вопросы «плагин в
фиче — это плагин?» и «порядок плагинов». (б) Оставить всё как есть, без
раздела в доке — отвергнуто: «плагинов нет» без объяснения, куда девать
`forTransports` и `configureMiddleware`, читается как пробел, а не как решение.

### D2. Поля `plugins:` в корне не будет; из целевого словаря оно снимается

`design/composition.md` §2 обещает `plugins?` как «тонкий root-bag для ambient
cross-cutting». Обещание снимается: root-bag тождественен `modules:` корня —
те же значения, та же фаза, та же дедупликация, — а два поля с одинаковой
семантикой заставляют выбирать между ними на каждом инфра-модуле («это уже
плагин или ещё модуль?»). `providers:` рядом с `modules:` существует по другой
причине: он выражает *другую* форму (провайдер, а не модуль), когда заводить
модуль незачем.

Правило корня формулируется явно: **перечень полей `assemble` закрыт**;
cross-cutting-инфраструктура попадает в граф теми же двумя полями, что и
всякая другая.

**Альтернативы.** (а) Оставить `plugins:` как алиас `modules:` с более
говорящим именем — отвергнуто: имя, не меняющее поведения, — чистая
когнитивная нагрузка. (б) Сделать `plugins:` bag'ом с собственной фазой
конфигурации — отвергнуто ещё в ideas.md [2026-07-08] (`OnConfiguration`
строго хуже зависимости: хук — барьер «весь конфиг → весь init», зависимость
даёт точную топологию).

### D3. Идентичность модуля — значение; одноимённые разные значения — ошибка

`#modules: Set<string>` становится `Map<string, Module>`:

- имя не занято → регистрируем, запоминаем значение;
- имя занято **тем же** значением (`===`) → no-op, как сегодня (модуль,
  импортированный двумя фичами или корнем и фичей, — норма и главный сценарий
  разделения инфраструктуры);
- имя занято **другим** значением → бросок с текстом в тоне фич: два разных
  модуля названы одинаково; имя модуля — ключ атрибуции провайдеров и
  экспортов, поэтому оно уникально; чинится либо разделением одного значения
  (`export const cacheRedis = redis({ … })` и импорт его обеими фичами), либо
  разными именами, если конфигурации действительно две. Упоминание про две
  копии пакета в диагностике — там же, потому что это второй по частоте
  источник коллизии.

Сравнение — ссылочное. Структурное («опции совпадают → считаем одним») — та
самая рантайм-магия, которую фреймворк себе запрещает: оно требует обхода
произвольных значений (функции, инстансы клиентов), даёт разный ответ на
семантически одинаковых конфигурациях и превращает тихую потерю в тихое
слияние.

**Почему ошибка, а не регистрация обоих.** Одно имя — один ключ в
`#moduleExports`, `#providersFactories`, `metadata.module` и в диагностике
политик («модуль-объявитель»). Разрешив два значения под одним ключом, мы
получаем неоднозначную атрибуцию и отчёты, в которых нельзя понять, чей это
провайдер; общий токен всё равно упал бы дальше — но уже сообщением
«Provider for token 'X' is already registered», уводящим от настоящей причины.

**Почему это не BREAKING в практическом смысле.** Изменение переводит
поведение из «тихо теряем часть приложения» в «падаем на сборке», ловится
любым тестом и `check()`, и приложение, которое работало правильно, коллизии
не имеет по построению. Формально это ужесточение публичного контракта
контейнера — фиксируется дельтой `endpoint-discovery` и `composition-root`.

**Альтернативы.** (а) Оставить «первый выиграл» и описать в доке — отвергнуто
(это и есть разрыв конвенции и гарантии, из-за которого change существует).
(б) Warning вместо ошибки — отвергнуто: warning в сборке никто не читает, а
пропажа провайдеров проявится в проде. (в) Мемоизировать параметризованные
модули по опциям внутри `makeModule` — см. Non-goals.

### D4. Правило действует в обоих обходах, но врезка — в контейнере

`builder.register(...modules)` исполняется раньше `discoverEndpoints`, поэтому
в App-пути коллизия падает в контейнере — до дискавери дело не доходит. Но
`discoverEndpoints` экспортируется из `@nestling/app` как самостоятельная
функция и по своей capability обязана «зеркалить обход контейнера»; молчащая
там проверка сделала бы зеркало кривым ровно в том месте, где оно важно.
Поэтому:

- **гарантия** — в `ContainerBuilder.registerModule`;
- **зеркало** — в `discoverEndpoints`: тот же `Map<string, Module>` и тот же по
  смыслу бросок (пять строк дублирования вместо межпакетного хелпера);
- тест в `@nestling/app` фиксирует, что при сборке через `assemble` сообщение
  приходит от контейнера — то есть порядок проверок не изменился.

**Альтернатива** — экспортировать из `@nestling/container` общий обходчик
(`walkModules`) и переиспользовать его в дискавери. Отвергнуто для change'а
размера S: публичная поверхность контейнера растёт ради пяти строк, а
дискавери всё равно нужен свой visit (эндпоинты, атрибуция, порядок).

### D5. Что параметр модуля, а что конфиг-секция

Канон инфра-модуля живёт ровно на этой линии, поэтому она проговаривается в
доке и показывается в примере:

- **параметр функции-модуля** — решение **composition root**: форма графа,
  выбор реализации, имя инстанса, набор провайдеров. Оно известно в момент
  сборки, живёт в коде и в diff'е ревью;
- **конфиг-секция, которую модуль везёт** — решение **среды**: адреса, порты,
  уровни, таймауты. Оно приезжает из источников, валидируется на `build()` и
  может быть reloadable.

Это та же ось, по которой в ideas.md [2026-07-08] отвергнуты «connection
strings как структурный конфиг»: URL узла не меняет форму графа, а «нужен
рестарт» — свойство держателя ресурса, не конфига. Практический критерий для
автора инфра-модуля: *если значение меняется без пересборки образа — это
секция; если его изменение меняет то, какие провайдеры существуют, — это
параметр.*

### D6. Feature-scoped инфраструктура: кода не требует, гарантия — тест

Свойство «инфра едет с фичей» уже следует из жадного контейнера и `select`:
модуль приезжает в граф только через дерево выбранных фич. Change не добавляет
механики, но закрепляет свойство тестом на трёх утверждениях: (1) при выбранной
фиче провайдер инфра-модуля построен; (2) при невыбранной — его нет в графе,
даже если файл импортирован процессом; (3) две co-located фичи, импортирующие
**одно значение** инфра-модуля, получают один инстанс.

Третий пункт — прямая проверка того, что D3 не сломал главный сценарий
разделения, и одновременно проверка обещания «co-located фичи делят синглтон,
split даёт клиент на процесс».

### D7. Витрина в `examples.app-with-http` — минимальная, но полная

`LoggerModule` превращается в `logging({ … })`: функция, возвращающая модуль,
значение создаётся один раз (в модуле-инфраструктуре примера) и импортируется
фичами. Модуль везёт свою конфиг-секцию (уровень — из среды), принимает
параметром то, что решает корень (D5), и экспортирует слой наблюдаемости,
который уже требуется политикой в `main.ts`. Ни одной новой строки в ядре
пример при этом не использует — в этом и смысл витрины.

Витрину держим в габаритах S: параметризация, секция, слой, тест на
feature-scoped. Второй инфра-модуль (условный `redis`) не заводим — он
повторил бы те же свойства без нового смысла.

## Risks / Trade-offs

- **Ужесточение ломает код, где одноимённые модули создавались фабрикой на
  каждый вызов** (`imports: [logging({ level })]` в двух местах) → это ровно
  тот код, который сегодня теряет часть конфигурации молча; диагностика
  называет обе починки, а `yarn verify` по монорепо показывает масштаб внутри
  проекта (ожидание — ноль случаев, проверяется в первой же задаче).
- **Dual package hazard даёт ложноположительную ошибку**: две копии пакета —
  два значения с одним именем, приложение «внезапно перестало собираться» →
  причина упоминается в тексте ошибки третьим пунктом, рядом с двумя
  штатными починками; альтернатива (тихое схлопывание) хуже — она даёт две
  копии синглтона в проде.
- **Конвенция шире, чем гарантия**: «инфра оформляется модулем» не
  принудительно — никто не мешает написать ambient-обходной путь через
  побочный эффект импорта → pipeline-часть закрыта политиками, остальное
  честно остаётся конвенцией; ESLint-правило под это не заводим (см.
  Non-goals #28: правило — подсказка, гарантия — граф).
- **Раздел доки про «то, чего нет»** рискует устареть тише, чем код → раздел
  привязывается к примеру (гайд сверяется с `examples.app-with-http`) и к
  требованию `infrastructure-modules`, которое проверяется тестами.

## Migration Plan

1. `@nestling/container`: `Map` вместо `Set`, бросок на коллизию, тесты (тот
   же модуль дважды — no-op; разные значения с одним именем — ошибка).
2. `@nestling/app`: то же правило в `discoverEndpoints`; инвертировать тест
   `discovery.spec.ts:107` («одноимённые считаются одним» → «одноимённые
   разные — ошибка»); тест порядка (в `assemble` сообщение приходит от
   контейнера).
3. `yarn verify` по монорепо — убедиться, что коллизий в примерах и пакетах
   нет; починить, если есть.
4. Пример: `logging({ … })`, секция, слой, тест feature-scoped.
5. Доки: `design/composition.md` (снятие `plugins?`, раздел про
   инфраструктуру), `design/container.md` (идентичность модуля),
   `design/pipeline.md` §7 (терминология), `decisions/ideas.md` (запись +
   СУПЕРСИД строки о root-bag'е), `guides/composition.md`, README пакетов,
   статус в roadmap.

Откат тривиален: правило — одна проверка в двух обходах, снятие возвращает
прежнее поведение; документационная часть откатывается отдельно и независимо.

## Open Questions

- **Конвенция именования параметризованных модулей** (`module:redis` против
  `module:redis:cache`, когда конфигураций две) — оставляем автору: правило
  требует уникальности, но не диктует схему. Если практика покажет
  повторяющийся паттерн, он опишется в гайде, а не в ядре.
- **Проверка непустого имени в `makeModule`** (симметрия с `makeFeature`) —
  напрашивается, но это отдельное ужесточение поверхности контейнера; в
  scope change'а не берётся, чтобы не смешивать с правилом идентичности.
