## 1. `Fail` — значение; `throw` — способ доставки

Ожидаемая ошибка домена — это значение `Fail`. Хендлер может вернуть его
или бросить; для пайплайна оба пути равнозначны. Брошенное исключение,
которое не является `Fail`, считается внутренней ошибкой: клиент получает
`INTERNAL_ERROR` без деталей. Модель повторяет пару `Result` и `panic!`
из Rust. `throw` здесь заменяет отсутствующий в JS оператор `?`. Это
способ доставить значение из глубины вызовов, а не отдельная семантика.

- `Output<T, E> = Promise<Ok<T> | E | T>` (есть и `OutputSync`). Голое
  значение `T` оборачивается в `Ok`. По умолчанию `E` равен `never`:
  endpoint без `errors:` не может вернуть отказ.
- Дискриминант — поле `isFail`: `true as const` у `Fail`, `false` у `Ok`.
  Оно сериализуется, в отличие от проверки `instanceof`. Завернуть отказ в
  успех нельзя: `new Ok(fail)` — ошибка компиляции.
- Возвращённый `Fail` попадает в ветку ошибки до `.ok`-юнитов. Инвариант
  «`.ok` видит только успех» держится для обоих путей.
- `Fail extends Error`, поэтому у брошенного отказа есть стек вызовов.
- Правило для автора кода: свой отказ бросают (`throw` — ранний выход из
  глубины), чужой возвращают (`return` — проброс отказа порта).

## 2. Статусы, `code`, `cause`

- `ErrorStatus` — категория ошибки, не зависящая от транспорта:
  `BAD_REQUEST`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`,
  `TIMEOUT`, `TOO_MANY_REQUESTS`, `INTERNAL_ERROR` и другие. В HTTP-статус
  или код шины её переводит транспорт.
- `code?: string` — стабильный машинный код: что именно случилось. Статус
  отвечает на другой вопрос — как транспорту ответить клиенту.
- `cause?: unknown` — исходная ошибка, как у `Error` в ES2022.
- В сериализованном виде (`ErrorDetails`) уходят `status`, `code`,
  `message`, `details` и `requestId`. `requestId` кладут `.catch`- и
  `.finally`-юниты из контекста, так что ответ связывается с логами без
  кода пользователя.

## 3. Доменные ошибки: `defineFail` и идентичность по `code`

```typescript
export const OrderNotFound = defineFail('ORDER_NOT_FOUND', {
  status: 'NOT_FOUND',
  details: z.object({ orderId: z.string() }),   // schema-first — и для details
  message: (d) => `Order ${d.orderId} not found`,
});

throw OrderNotFound({ orderId: '42' });
throw OrderNotFound({ orderId: '42' }, { cause: dbError });
// в .catch-юните:
if (OrderNotFound.is(res)) { /* ... */ }        // матчинг по code
```

Данные отказа берутся только из `details`. Конструктор принимает их с
типом, выведенным из схемы, и проверяет схемой на месте. `message` — строка
или функция от этих деталей. Если схемы нет, конструктор вызывается без
аргументов: `EmailTaken()`. Второй аргумент — опции, например `cause`.

Определение — значение со свойствами `code`, `status`, `schema` и
предикатом `is`; его можно вызывать как функцию. Регистрировать
определение не нужно: на приложение оно влияет только через `errors:`
декларации.

Отказ распознаётся по `code`, а не по `instanceof`. `Fail`, пришедший от
удалённого порта или в клиент, — это десериализованные данные: класса у
них нет, а `code` сохраняется. Поэтому `is` проверяет код у двух
носителей: у значения-отказа (в том числе разобранного из JSON) и у
контекста ответа-ошибки, который видит `.catch`-юнит. Второй носитель
описан минимальным структурным типом
`{ isSuccess: false; value?: { code?: string } }`, а не типом контекста
пайплайна; сужение типа в `.catch` от этого не меняется.

Порт и `makeClient` восстанавливают удалённый отказ в настоящий `Fail` на
своей стороне по одному правилу. `status` берётся из определения: контракт
знает его точнее, чем ответ сервера. `message` берётся из ответа, потому
что описывает конкретный случай. `details` берутся из ответа и
проверяются схемой определения. Если детали не прошли схему, код не
объявлен в контракте, тело не JSON, сеть недоступна или ответ не прошёл
`output`-схему, клиент получает `UnknownError` с оригиналом в `cause`.
Множество ответов у внешнего потребителя — `E ∪ UnknownError`, то же, что
у порта. Ветка `default`, написанная для `.port`, переносится на клиента
без правок ([contracts.md](./contracts.md)).

## 4. Ошибки — часть контракта: `E ∪ UnknownError`

Поле `errors: [EmailTaken, OrderLimitReached]` в декларации endpoint'а или
контракта объявляет, какие отказы возможны. Гарантия держится на двух
уровнях.

- Компилятор проверяет всё, что передаётся значениями. `defineFail`
  брендирует тип (`Fail<'EMAIL_TAKEN'>`); `Output<T, E>` сверяет `return`
  с декларацией, в том числе проброс отказа порта: чужой `Fail` не попадёт
  в ответ, пока не задекларирован. Для раннего выхода есть типизированная
  функция `meta.fail(e): never` — второй зарезервированный ключ `meta`
  после `signal`. Она принимает только задекларированные отказы; её тип
  выводится из декларации.
- Рантайм проверяет остальное на выходе из пайплайна: прямой `throw`,
  отказы из глубины сервисов, обходы типов. Всё, что дошло до выхода
  незадекларированным, **заменяется на `UnknownError`** — встроенное
  определение `defineFail('UNKNOWN')` со статусом `INTERNAL_ERROR`. Ответ
  без кода, в том числе созданный анонимным `Fail.notFound(...)`,
  незадекларирован по определению. Оригинал целиком передаётся
  диагностическому хуку `onUnknownFail` (по умолчанию — `console.error`),
  клиенту уходит общее тело ошибки.

Множество отказов доходит до рантайма как значение декларации: из
`errors:` в `EndpointMeta`, оттуда в контекст запроса. Глобального реестра
нет, поэтому пайплайн, выполненный без декларации, видит пустое множество.

Вызов порта закрыт тем же множеством и той же процедурой: на границе отказ
восстанавливается по `code` из `errors:` контракта, незадекларированный
становится `UnknownError`, а коды ядра (`VALIDATION_FAILED`,
`DEADLINE_EXCEEDED`) входят в контракт и там
([contracts.md](./contracts.md)).

Итог: ответ endpoint'а — закрытое множество `E ∪ UnknownError`.
`UnknownError` входит в контракт каждого endpoint'а неявно (ответ
`default` в OpenAPI). Встроенные коды фреймворка входят в множество тем же
способом: `VALIDATION_FAILED` у проверки входа, `PAYLOAD_TOO_LARGE` у
лимита размера входа, `STREAM_LIMIT_EXCEEDED` и `STREAM_GAP_TIMEOUT` у
item-цепочек, `DEADLINE_EXCEEDED` у бюджета вызова портов. Их определения называются без суффикса `Error`
(`DeadlineExceeded`, `ValidationFailed`); `UnknownError` — единственное
исключение. Набор встроенных кодов закрыт и растёт только вместе с ядром;
публичного способа объявить свой код встроенным нет.

Проверка на выходе стоит после всех `.catch`-юнитов: `.catch` — то место,
где незадекларированный отказ превращается в задекларированный. Забытая
декларация проявляется сразу: клиент получает `UnknownError` (500), а не
случайно работающий 404.
