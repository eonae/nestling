## [Ассистент]

**Короткий ответ:** nestling необычно хорошо подходит — лучше, чем Nest, — из-за
двух уже принятых решений:

1. **Модули — plain values** (`makeModule`/`makeAppModule` — identity-функции) ⇒
   «фича» — тоже значение, выбор подмножества = фильтрация массива в композиционном
   корне.
2. **Контейнер жадный** ⇒ «не выбрал фичу → её провайдеры не построились» само
   собой.

~80% бесплатно. Но есть одна вещь, которая мешает: **глобальный registry
эндпоинтов** (`endpoint-registry.ts:10` — модульный `Set`; `@Endpoint`

выбором подмножества. **Фикс:** обнаруживать эндпоинты обходом дерева модулей, а не
из глобального registry.

Дальше слои: **фича** = бандл модулей (`makeFeature`); **манифест + селектор**
(`--features`); **capability negotiation** (поднимать только нужные транспорты);
**порты** (типизированные контракты для межфичевого общения, local/remote-биндинг —
самый большой research); **конфиг**.

Таблица «что бесплатно / что чинить / что исследовать»: фича=фильтр — бесплатно;
не выбрал→не построилось — бесплатно; дискавери из дерева модулей — S, обязательно;
`makeFeature`+select — S; capability negotiation — M; порты — L, research.

## [Пользователь]

Давай подумаем о портах более целенаправленно. Понятно, что должен быть какой-то
механизм. Но: 1) Как это будет выглядеть в коде? 2) Как работать инфраструктурно?
3) Как настраиваться? У меня была мысль о том, чтобы всё общение организовать через
nats.. и request-reply и fire-and-forget. Единственное, не хочется фреймворк
прибиваться гвоздями к nats.

## [Ассистент]

**Половина портов уже есть.** Inbound («я обрабатываю контракт») = буквально
endpoint (`App` роутит по `metadata.transport`; contract-endpoint с `transport:
'nats'` ляжет на NATS-транспорт — ноль изменений в ядре). Outbound («мне нужно
позвать») = единственное, чего нет.

**Контракт — общее направление-нейтральное значение** (`makeContract({ name, kind,
input, output })`). Три вида: `request` (req-reply, Fail-able), `command`
(fire-and-forget, один обработчик, queue-group), `event` (broadcast, 0..N).
Различать command/event важно для масштабирования: queue-group делит нагрузку между
репликами.

**Q1 код:** владелец реализует как endpoint; потребитель инжектит `ChargeCard.port`,
зовёт `.call(input, meta): Promise<Ok|Fail>`; эмиттер/консьюмер для событий.
`.call/.emit` всегда async + Fail-able, даже co-located.

**Q2 инфра:** ядро зависит от `IMessageTransport` (`request/publish/subscribe`);
`InProcessBus` (Map) и `NatsTransport`; `meta.signal` → таймаут; inbound
переиспользует существующую машинерию эндпоинтов.

**Q3 конфиг:** биндинг в композиционном корне — владелец co-located → local,
иначе → remote поверх шины, иначе fail-fast. NATS адресует subject'ом → не нужен
per-feature реестр адресов.

**Не прибиваемся к NATS:** ядро знает только `IMessageTransport`; NATS —
отдельный пакет; интерфейс на LCD; NATS-specific не протекает.

**Напряжения:** порты никогда не транзакционны (даже co-located); локальный порт
обязан уметь падать; outbox-проблема. Открытые: версионирование контрактов, где
лежат контракты.

Самый острый вопрос: `request` vs `event` как дефолт — синхронный request-reply
порождает distributed monolith.

## [Ассистент]

**1. Дихотомия ложная** — NATS транспорт: и inbound (`ITransport`), и outbound.
Один мешок с capability (`InboundTransport`/`OutboundTransport`).

**2. NATS_URL — тернарник враньё.** Конфиг транспортов статичен и одинаков для всех
процессов развёртывания; между процессами меняется только `select`. Процесс не
знает локально, кто позовёт его снаружи → inbound подписывается на шину всегда,
когда она есть. Разница «локально/прод» — в конфиге, не в коде.

**3. Диспатч — политика, а не зашивка.** Порт говорит с *шиной*, какая — политика
на сборке: `local-first`/`always-remote`/`balanced`. Реализации: in-proc-direct,
NATS, in-proc-simulated (message-семантика без NATS). NATS queue-groups = server-side
LB бесплатно. Смена политики = смена конфига, call-site не меняется.

**4. Конфиг.** `process.env` — в одном пакете, остальное инжектит типизированные
срезы. Три тира: bootstrap (структурный) / static operational / live operational
(opt-in). Конфиг — фаза 0, до контейнера. Невалидный структурный → fail-fast, не
стартуем (retry на моргающий источник — ок). Watch/reload — opt-in на значение
(`ConfigRef<T>`), только для operational.

## [Ассистент]

Ты прав, и это лучше. **Транспорт — обычный синглтон с зависимостями и lifecycle**,
ровно то, чем контейнер управляет. Мешок `transports: Record` дублирует контейнер

— отдельная фаза (`@OnInit` = connect; регистрация — между; `listen`/`@OnStart` =
эфир, драйвится App). Неснимаемо-внешним осталось `select` + сырая загрузка
конфига.

## [Пользователь]

А что запретит разработчику транспорта повесить OnInit на listen?

## [Ассистент]

Справедливо. **Ничего** — «дисциплина» из прошлого хода это конвенция, footgun. По
стандарту nestling недостаточно. Убрать возможность: убрать nullary `listen()`,
уйти в эфир можно только приняв **готовый диспетчер** (`serve(dispatch, signal)`),
а `dispatch` не существует до фазы регистрации. Транспорт — переводчик провода, не
владелец роутинга; раннему listen нечего маршрутизировать. `dispatch` — фазовый
ресурс (на `@OnInit` нет, на `@OnStart` да). Лестница: конвенция < dispatch-как-
аргумент < инверсия акцептора. Дефолт — средний; `listen()` из контракта убираем.

## [Ассистент]

`[исследование: rsdk core/config — config.module.ts, config.context.ts,
config-metadata.extractor.ts]`

**rsdk:** секции-классы (`@Property`); мерж на уровне источников
(`.env→process.env→динамические` в `Vars`); инжект через factory-провайдеры;

feature-scoped бесплатно; **eager-валидация бесплатно**.

построение провайдера / зависимость / `@OnInit` потребителя / reload-событие. Хук
**грубее зависимости** (барьер «весь конфиг → весь init»); зависимость даёт точную
топологию. Конфиг — не фаза, а зависимость.

**Глобальный конфиг — почти ничего:** только `select` + source-bootstrap (как/откуда
грузить). DB URL/NATS servers/HTTP port/policy — provider-config в секциях. Ты прав.

`[исследование: rsdk grpc.clients — module.generator.ts, token.factories.ts,
grpc.clients.config.ts, config-section autodoc fragment]`

Твои два вопроса — одно и то же. **rsdk grpc:** выводит env-ключ из имени сервера,
регистрирует **standalone-свойство на лету** («unbound property», вне секции),
`forProperty` даёт провайдер, channel/client инжектят адрес. Инжектнул клиент →
env-адрес сам. **Это token families** (roadmap item 5): `GrpcClient(server)` тянет
`Config(addressKey(server))`; жадный билдер видит запрошенные члены → build-time,
без рантайм-резолюции (vs ленивый rsdk). Build-time param = семейство; runtime
param = фабрика (репозиторий+кэш). **Отказ от sources падает отсюда:** нет
`ConfigSource`/`Vars`-мержа; readers-провайдеры (Env примордиальный, Vault/File
опциональные); override — в recipe семейства («нет волта → env»). Провенанс-слепота
и выгрузка доки целы (реестр свойств, даже полнее). Секция, unbound-свойство,
on-demand-клиент, `ILogger(scope)` — один механизм.

Ещё момент. В rsdk есть концепция плагинов — подключаются глобально (с глобальной
настройкой), влияют на всё приложение. Инфраструктура: RedisPlugin → глобальный

бизнес, в плагинах инфраструктура, cross-cutting concerns. Как ложится на nestling,
особенно с учётом фич?

## [Ассистент]

`[исследование: rsdk plugins — types/plugins.ts (PlatformAppPlugin), plugin.module.ts,
grpc/db.knex plugins, platform.module.ts]`

Три части плагина ложатся по-разному. **(1) Инфра-часть растворяется в модулях:**
плагин = параметризованный инфра-модуль (`redis()` → модуль, `RedisClient`
синглтон). «Глобальность» ≠ ambient-инжект — провайдер в корне, но инжект требует
импорта токена (ES-видимость цела). **(2) Cross-cutting pipeline НЕ ложится:**
pipeline-v2 отверг App/module-уровни → плагин экспортирует pipeline-слой, endpoint
композирует явно + policy-check, вместо ambient middleware. **(3) С фичами:**
плагины процесс-глобальны; feature-scoped инфра едет с фичей (падает из `select`,
co-located делят синглтон, split — отдельные per-process); ambient cross-cutting —
тонкий root-bag. Общий бэкенд у разнесённых фич — дата-архитектурный концерн, не
механика плагинов.
