## 1. Секция

Секция конфига — объект, в котором каждому полю сопоставлена схема. Из пакета наружу экспортируется
только описание ключей; сам DI-токен секции остаётся приватным.

```typescript
// orders.config.ts — из пакета наружу идёт только дескриптор ключей
export const OrdersConfig = makeConfig('orders', {
  maxItems:    z.coerce.number().default(100),          // ← ключ ORDERS_MAX_ITEMS
  databaseUrl: secret(from('DATABASE_URL', z.url())),   // точное имя + секрет
  apiToken:    secret(z.string()),                      // скрывается в выводе
});
export const ordersKeys = OrdersConfig.keys;        // экспортируемое право привязки

@Component([OrdersConfig])
export class OrdersService {
  constructor(private cfg: Config<typeof OrdersConfig>) {}
}
```

- Секция — рекорд полей. Перечень полей известен на уровне JS-объекта;
  листья — любые Standard Schema ([schemas.md](./schemas.md)); `from()` и
  `secret()` — обёртки листьев. Вывод имён ключей, реестр для документации
  и привязка источников работают с полями рекорда и не заглядывают внутрь
  схем. Поля валидируются независимо друг от друга.
- **Пустое значение ключа означает отсутствие значения.** `KEY=` в
  окружении или в файле читается как «ключ не задан»: ядро сводит пустую
  строку к `undefined` до вызова схемы поля, и дальше решает схема —
  `default` даёт умолчание, обязательное поле даёт отказ. Правило живёт в
  одном месте ядра и действует одинаково на обоих путях чтения: проекции
  секции из графа и первичном чтении фазы 0 (`bootstrapConfig`). Схемам полей знать о
  нём не нужно — ни своим, ни пользовательским. Порядок поиска значения
  правило не меняет: значение берётся у первой привязки, которая ключ
  покрывает, и пустая строка не уводит читалку к следующему источнику —
  иначе `KEY=` в локальном файле молча открывало бы дорогу значению с
  машины.
- Обёртки сочетаются в единственном порядке: `secret()` снаружи, `from()`
  внутри. Обратный порядок не проходит по типам и даёт ошибку в точке
  объявления с указанием правильного порядка. Обёртки в валидации не
  участвуют: проверяет только схема листа.
- **Вычисляемое поле** объявляется третьим аргументом `makeConfig`.
  Аргумент — функция, которая получает конструктор `derived` и
  возвращает рекорд вычисляемых полей. `derived(deps, fn)` называет
  зависимости именами полей первого рекорда, а `fn` получает их значения
  по порядку.

  ```typescript
  export const PgConfig = makeConfig('pg', {
    host:     z.string().default('localhost'),
    port:     z.coerce.number().int().default(5432),
    user:     z.string(),
    password: secret(z.string()),
  }, (derived) => ({
    url: derived(['host', 'port', 'user', 'password'],
      (host, port, user, password) =>
        `postgresql://${user}:${password}@${host}:${port}/app`),
  }));
  ```

  Значение считается при валидации секции на BUILD и заново при
  перезагрузке, если изменилась хотя бы одна зависимость. Поле секретно,
  если секретна хотя бы одна зависимость. Ключа у поля нет, в `.keys` оно
  не входит. Ошибка `fn` на сборке — ошибка конфига с именем секции, поля
  и списком зависимостей.

  Три правила держатся типами, а не проверками в момент объявления. Имя
  зависимости берётся из имён первого рекорда, поэтому опечатка не
  компилируется. Типы аргументов `fn` выводятся из схем зависимостей,
  поэтому ложная аннотация не компилируется тоже. Зависеть от другого
  вычисляемого поля нечем: в первом рекорде их нет. Цена формы названа
  прямо — секция перестала быть одним рекордом, схемы объявляются первым
  аргументом, вычисляемые поля вторым.
- Имя ключа строится из префикса секции и имени поля: `maxItems` даёт
  `ORDERS_MAX_ITEMS`. `from('KEY', schema)` задаёт точное имя. Источник
  значения в секции не указывается: секция читает ключ и не знает, откуда
  пришло значение.
- `makeConfig.family(prefix, record)` объявляет **секцию-семейство**: по
  одной секции на каждый экземпляр пакета. Имя экземпляра входит в
  префикс: `'default'` даёт ключи пакета как есть (`HTTP_PORT`),
  `'admin'` — с добавкой (`HTTP_ADMIN_PORT`). Имя приводится к
  `SCREAMING_SNAKE_CASE` тем же правилом, что имя поля. Повторный вызов с
  тем же именем отдаёт тот же DI-токен, а `.keys` у каждого экземпляра свои:
  привязка адресует ключи одного экземпляра. Нужна такая секция там, где
  экземпляров несколько, а значения у них разные, — два HTTP-сервера не
  могут слушать один порт ([transports.md §4.2](./transports.md)).

  ```typescript
  const HttpServerConfig = makeConfig.family('http', {
    port: z.coerce.number().int().default(3000),
    host: z.string().default('0.0.0.0'),
  });

  HttpServerConfig('default').keys;   // HTTP_PORT, HTTP_HOST
  HttpServerConfig('admin').keys;     // HTTP_ADMIN_PORT, HTTP_ADMIN_HOST
  ```
- Секция — частный случай семейства DI-токенов
  ([container.md](./container.md)): узел графа создаётся, когда кто-то
  инжектирует секцию. Регистрировать её в модуле не нужно.

## 2. Два права: инжект и привязка

Приватность секции не проверяется на `build()`: чужой инжект невозможно
написать.

- DI-токен секции даёт право инжекта. Он не экспортируется из пакета, поэтому
  снаружи секцию нельзя запросить: нет импорта — нет DI-токена.
- `.keys` даёт право привязки. Это экспортируемый брендированный дескриптор
  набора ключей; инжектировать его нельзя, поэтому экспорт безопасен.

Понятия «владелец секции» и ключа `configs:` у модуля нет. Вспомогательное
ESLint-правило напоминает: экспортируйте `.keys`, а не результат
`makeConfig`.

Форма DI-токена: `makeConfig` возвращает **сам токен семейства**
`ConfigSection` с дописанным `.keys`. Инжект секции и упоминание токена семейства —
одно и то же ребро графа, потому что это одно и то же значение. DI-токен
объектный, поэтому нести `.keys` он может сам, без класса-обёртки. `.keys`
— экземпляр `ConfigKeys<Prefix>`: у него нет ни `id`, ни конструктора,
поэтому в `deps` он не проходит по типам.

## 3. Источники и привязки при запуске

Источник — объект `ConfigSource { get; init?; close?; watch?; needs? }`,
не провайдер. Все источники читает одна приватная читалка в ядре. Она
поднимает источники на фазе 0 BOOTSTRAP и складывает значения в снимок;
секции считаются из снимка на BUILD, синхронно
([composition.md §1](./composition.md)).

Список привязок принимает `run()`: откуда берутся значения — свойство
процесса, а не приложения. Тот же список принимают `check(args, { config })`
и тестовый корень `buildTest(app, { config })`; `discover()` конфига не
читает. Декларация `makeApp` поля для источников не имеет: состав
приложения определяет только аргумент сборки, конфигурация на состав не
влияет.

```typescript
// умолчание: про конфиг ничего не пишешь
await app.build(argv(process.argv)).run();

// то же самое, записанное явно: окружение выше локального файла
await app.build(argv(process.argv)).run({
  config: [
    bind(env()),
    bind(dotenv('.env'), { optional: true }),
  ],
});

// стенд: Vault поверх умолчания
await app.build(argv(process.argv)).run({
  config: [bind(vault(VaultConfig), { timeout: 3000 }), ...defaultSources],
});
```

Переданный список заменяет умолчание целиком. Умолчание экспортируется
значением `defaultSources`. Тестовый корень умолчания не имеет: ключ,
которого нет в переданных источниках, отсутствует, и тест не зависит от
окружения машины.

Привязка — `bind(source, options?)`: источник и ключи, за которые он
отвечает. Порядок списка задаёт приоритет: первый источник, вернувший
значение, выигрывает.

| Опция | Что делает |
|---|---|
| `keys` | дескрипторы `.keys` секций и глобы ключей; по умолчанию `'*'` |
| `optional` | источник не поднялся — читалка пропускает его вместо отказа; так объявляется `dotenv('.env')`, которого в контейнере нет |
| `timeout` | граница ожидания `init()`, по умолчанию 10 секунд; отказ называет источник |

Привязка адресует ключи, а не DI-токены. Сборка создаёт на BUILD все
секции, инжектированные в выбранных фичах, и там же их валидирует.
Невалидный конфиг останавливает старт (fail-fast).

Источники ядра — два. `env({ prefix? })` читает переменные окружения; с
префиксом читает `<prefix><KEY>` и отдаёт значение под `KEY`, так один
`.env` обслуживает несколько сервисов. `dotenv(path)` читает файл формата
`.env` через `util.parseEnv`, зависимостей у него нет. Ядро само
`process.env` не читает: окружение попадает в снимок только через
объявленный `env()`. Источники с сетью живут пакетами: `vault(...)` в
`@nestlingjs/config.vault`. Тестовый источник `vars({...})` лежит в
`@nestlingjs/testing` ([testing.md §4](./testing.md)).

Координаты источника приходят аргументами конструктора или из секции,
объявленной полем `needs`, и никогда из ключей, которые сам источник
наполняет. `dotenv(path)` получает путь строкой. `vault(VaultConfig)`
объявляет `needs: VaultConfig` и получает проверенные значения секции в
`init(values)`: адрес и учётные данные читаются из источников, поднятых
раньше. Читалка поднимает источники в порядке зависимостей, а не в порядке
списка: Vault с приоритетом выше `.env` читается после него, потому что
берёт оттуда координаты. Цикл в `needs` — отказ до всякого ввода-вывода.
Секцию из `needs` читалка берёт из уже поднятых источников; зависимый
источник свои `needs`-ключи не обслуживает, и после его подъёма секция не
перепроецируется. Секция, не покрытая поднятыми источниками, — отказ на
фазе 0 с перечнем недостающих ключей; привязка с `optional` вместо отказа
пропускает источник. Секция `needs`, объявленная `makeConfig.reloadable`
или не объявленная вовсе, — отказ безусловный: перепроекции у координат
нет, а несуществующая секция означает неимпортированный модуль.

Поведение самого источника задаётся его опциями, а не привязкой:
`vault(VaultConfig, { retries: 3 })`. Наблюдения у сетевого источника
нет: значение читается один раз на фазе 0 и живёт в снимке. Отказ
`init()` останавливает старт ошибкой, называющей источник, если привязка
не `optional`. На фазе 0
происходит ровно тот ввод-вывод, который перечислен в `config`. Читалка
живёт время `run()`: `close()` источников вызывается явным шагом SHUTDOWN,
после разрушения контейнера, а структурная проверка закрывает их сразу
после отчёта.

Снимок фазы 0 содержит все объявленные ключи. Ключ, которого не называет ни
одна секция — токен семейства `Config(key)` под unbound-глобом, — читается
первым обращением и запоминается в снимке: состав таких токенов семейства известен
только внутри `build()`, а `get()` источника синхронен и ввода-вывода не
делает.

Свою секцию транспорт объявляет сам и наружу отдаёт один дескриптор:
`serverKeys(name?)` у `@nestlingjs/transport.http`, `natsConfigKeys` у
`@nestlingjs/transport.nats`. Оба — то же право привязать источник, что и
`.keys` у секции приложения; DI-токен секции транспорт держит приватным,
поэтому инжектировать её может только он сам.

Модуль ядра, отвечающий за конфиг, регистрируется всегда: поля для него в
`makeApp` нет.

Глоб, который не совпал ни с одним объявленным ключом, даёт на старте
предупреждение, а не ошибку: предупреждение ловит опечатку вроде `'*_UR'`,
а глоб при этом может быть рассчитан на unbound-ключи семейств.
Предупреждения уходят в логгер ядра `Logger$('nestling:config')` уровнем
`warn`, порядок подъёма источников — туда же уровнем `debug`: он выведен
из `needs` и глазами по списку больше не читается. Читалка создаётся раньше логгера и зависеть от него не может:
реализация логгера читает секцию конфига. Поэтому до `build()`
предупреждения копятся, сразу после него сборка подключает логгер к
читалке и отдаёт накопленное, а дальше записи идут напрямую. В тесте их
перехватывает `spyLogger()` через подмену `RootLogger$`
([testing.md](./testing.md)).

## 4. Reloadable

```typescript
export const Runtime = makeConfig.reloadable('runtime', {
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  rps:      z.coerce.number().default(100),
});

// (а) read-latest — читаем при каждом использовании, подписка не нужна
@Component([Runtime])
class Logger {
  constructor(private cfg: Config<typeof Runtime>) {}
  debug(m: string) { if (gte(this.cfg.logLevel, 'debug')) this.write(m); }
}

// (б) react — перестроить ресурс при изменении
@Component([Runtime])
class RateLimiter {
  #bucket = new TokenBucket(100);
  constructor(private cfg: Config<typeof Runtime>) {}
  @OnStart() start(signal: AbortSignal) {
    this.#bucket.refill(this.cfg.rps);
    this.cfg.onChange(signal, (next) => this.#bucket.refill(next.rps)); // отписка по signal
  }
}

// корень: reloadable-источник — то, что включает reload
await app.build(args).run({
  config: [bind(reloadableFile('runtime.yaml'), { keys: Runtime.keys })],
});
```

Источник с наблюдением (`watch`) сообщает читалке о новом значении, и та
обновляет reloadable-секции: экземпляр секции остаётся тем же, поля
обновляются на месте. Два отличия от старта:

- на старте невалидное значение останавливает приложение; при перезагрузке
  невалидное значение отбрасывается, остаётся последнее валидное, и
  выдаётся предупреждение;
- вступит ли изменение в силу, зависит от потребителя. Чтение поля при
  каждом использовании и `onChange` видят новое значение; значение,
  скопированное в конструкторе, не обновится. Поэтому reloadable —
  opt-in.

## 5. Секреты

`secret(leaf)` помечает поле секретным; реестр конфига знает секретные
ключи. Для потребителя значение остаётся обычным: тип не брендируется.

Фреймворк скрывает секреты во всём выводе, который производит сам. Таких
поверхностей три:

- `ConfigValidationError`. Сообщения проблем секретного поля заменяются на
  `'<redacted>'` и в тексте ошибки, и в объекте `failures[].issues`. Имя
  ключа, имя поля и число отказов остаются. Исключение: если значение не
  было задано (`undefined`), скрывать нечего, и сообщение показывается
  целиком — «ключ не задан» и есть главный сценарий отладки секрета.
- Проекция секции. `toJSON()` и `nodejs.util.inspect.custom` возвращают
  копию с `'***'` вместо секретных полей, поэтому `console.log(cfg)` и
  `JSON.stringify(cfg)` безопасны. Оба токена семейства неперечислимы, форма объекта
  не меняется, чтение поля возвращает настоящее значение. Секция без
  секретных полей этих токенов семейства не получает.
- Снимок `describeConfig()`. Ключ несёт флаг `secret`; значений в снимке
  нет.

**Граница гарантии.** `{ ...cfg }`, `Object.values(cfg)`, чтение поля и
передача его в свой логгер возвращают настоящее значение. Фреймворк
отвечает только за то, что печатает сам.

## 6. Общие ключи

Один ключ (`DATABASE_URL`) могут читать несколько секций. Ключ —
разделяемый ресурс только для чтения: право читать не означает владения.
Вторая секция объявляет чтение без ведома первой; ошибки «ключ уже занят»
нет.

- Каждая секция валидирует сырое значение своей схемой независимо: две
  секции могут видеть ключ по-разному (`z.string()` и
  `z.coerce.number()`). Любая упавшая валидация останавливает старт.
- Единственный конфликт сборки — несогласованный `reloadable`: одна секция
  объявила ключ reloadable, другая нет. Это ошибка сборки: все читатели
  ключа должны одинаково понимать, может ли значение измениться на ходу.
  Ошибка называет ключ, обе секции, оба поля и обе починки; её текст не
  зависит от порядка создания секций.
- Проверка охватывает одну сборку и только созданные секции. Объявление,
  не попавшее в выбранную топологию, конфликта не создаёт; состояние одной
  сборки не влияет на следующую в том же процессе.
- Секретность общего ключа определяется по всем объявленным секциям, а не
  только по созданным: если хотя бы одна секция объявила `secret()`, ключ
  скрывается везде. Асимметрия с предыдущим пунктом намеренная: лишнее
  скрытие безопасно, лишняя ошибка сборки — нет.
- `describeConfig()` показывает всех читателей ключа. Индекс по ключам
  `keys: [{ key, secret, readers: [{ section, field, exact, reloadable,
  secret }] }]` строится по объявленным секциям, поэтому в него попадают и
  читатели вне выбранной топологии.

## 7. Инфраструктура по требованию и unbound-ключи

`GrpcClient(server)` — токен семейства, который транзитивно зависит от
`Config(addressKey(server))`. Кто инжектирует клиент, тот получает адрес
из env без дополнительного кода; жадная сборка создаёт всё на `build()`.
Unbound-паттерны экспортируют свои глобы так же, как секции экспортируют
`.keys` (`'*_GRPC_ADDRESS'`). Параметр, известный только в рантайме (адрес
из БД), семейством не выражается: для него нужна фабрика вне жадного
графа.

## 8. Интроспекция и документация

Реестр свойств конфига — источник генерируемой документации: ключи, схемы,
значения по умолчанию, принадлежность фиче (выводится из графа), читатели
общих ключей, пометки секретов. Значений и обращений к сети в нём нет.

`describeConfig()` возвращает две проекции одних и тех же данных: перечень
по секциям (`sections`) отвечает на вопрос «что читает эта секция», индекс
по ключам (`keys`) — на вопрос «кто читает этот ключ». Графовый `explain()`
контейнера читает тот же индекс реестра.

`describeConfig({ converters })` переводит листья в JSON Schema тем же
`SchemaDocConverter`, что и OpenAPI ([schemas.md §2](./schemas.md)).
Описание ключа несёт саму схему и исход конвертации: схема объявлена
аннотацией, схема получена конвертером или конвертера для вендора нет.
Описание, умолчание и перечисление читаются из схемы полями `description`,
`default` и `enum`; отдельных полей снимка для них нет. Диспетчер зовётся с
направлением `input`: таблица описывает то, что человек пишет в окружение.
Из снимка строится таблица переменных для документации по развёртыванию.
Без `converters` снимок остаётся прежним — полей JSON Schema в нём нет.

Секции самого фреймворка переводятся штатным конвертером: они написаны на
том же валидаторе, что и схемы приложения ([schemas.md §1](./schemas.md)).
Умолчания у `describeConfig` при этом нет — список конвертеров остаётся
данными вызывающего.

Вычисляемые поля секции стоят в снимке отдельным перечнем: имя поля, список
зависимостей и признак секретности. В перечень ключей и в key-центричный
индекс они не входят, потому что ключа у них нет и привязать к ним источник
нельзя.
