# mcp-tool-declarations

## Purpose

Инструмент MCP — обычный endpoint, объявленный конструктором `mcpTool`. Форм
две, как у каждого транспорта: `mcpTool(name, { … })` объявляет инструмент
вместе со схемами, `mcpTool.implement(operation, { handler })` обслуживает
уже объявленную операцию. Имя выводится из имени операции заменой точек на
подчёркивания, описание берётся из словаря реализации или из секции `doc`
операции. Описание обязательно: агент выбирает инструмент по нему, и
инструмент без описания он выбрать не может. Схемы входа и выхода
переводятся в JSON Schema конвертерами из `converters:` транспорта, поэтому
сам пакет не зависит ни от одного валидатора. Успех операции отдаётся
результатом вызова инструмента, объявленный отказ — результатом с
`isError: true`, а не ошибкой протокола: отказ входит в контракт операции, и
агент должен его прочитать. Одну операцию допустимо обслуживать двумя
поверхностями сразу — `httpEndpoint.implement` и `mcpTool.implement` с одним
классом-хендлером.

## Requirements

### Requirement: Инструмент объявляется конструктором транспорта

`@nestlingjs/mcp` SHALL экспортировать `mcpTool` — конструктор деклараций с
двумя формами, как у каждого транспорта.

`mcpTool(name, { description, input?, output?, errors?, annotations?,
pipeline?, handler })` SHALL объявлять инструмент вместе со схемами. Первый
аргумент — имя инструмента; оно же `pattern` декларации.

`mcpTool.implement(operation, { name?, description?, annotations?, pipeline?,
handler })` SHALL объявлять инструмент из операции. `input`, `output`,
`errors` и адрес SHALL браться с операции; их переобъявление в словаре
реализации SHALL отвергаться.

`mcpTool.implement` SHALL принимать операцию вида `request`. Операции видов
`command` и `event` SHALL отвергаться ошибкой типа при компиляции и ошибкой
рантайма при вызове из JavaScript: результата, который агент мог бы
прочитать, у них нет.

Обе формы SHALL возвращать обычную декларацию endpoint'а: она кладётся в
`endpoints:` фичи и получает discovery, пайплайн, проверку отказов на выходе
и `policies`.

#### Scenario: Инструмент из операции

- **WHEN** объявлен `mcpTool.implement(CreateUser, { handler })`, где
  `CreateUser` создана `makeRequest`
- **THEN** получена декларация endpoint'а на транспорте MCP со схемами и
  отказами операции

#### Scenario: Анонимный инструмент

- **WHEN** объявлен `mcpTool('search_users', { description, input, output, handler })`
- **THEN** получена декларация endpoint'а с паттерном `search_users`

#### Scenario: Операция вида command отвергается

- **WHEN** из JavaScript вызван `mcpTool.implement(SendEmail, { handler })`,
  где `SendEmail` создана `makeCommand`
- **THEN** брошена ошибка, называющая вид операции и то, что инструмент
  требует вида `request`

#### Scenario: Поле операции в словаре реализации отвергается

- **WHEN** вызван `mcpTool.implement(CreateUser, { input: OtherSchema, handler })`
- **THEN** брошена ошибка, называющая `input` полем операции

### Requirement: Имя инструмента выводится из имени операции

Имя инструмента в форме `implement` SHALL быть равно `options.name`, если оно
задано, и выводиться из `operation.name` иначе. При выводе точки SHALL
заменяться на подчёркивания: `users.create` даёт `users_create`.

Итоговое имя SHALL соответствовать `^[a-zA-Z0-9_-]{1,128}$` в обеих формах.
Имя, не прошедшее проверку, SHALL отвергаться при создании декларации.

#### Scenario: Точки заменяются подчёркиваниями

- **WHEN** объявлен `mcpTool.implement(CreateUser, { handler })` для операции
  с `name: 'users.create'`
- **THEN** инструмент называется `users_create`

#### Scenario: Явное имя перекрывает выведенное

- **WHEN** объявлен `mcpTool.implement(FindUsers, { name: 'search_users', handler })`
- **THEN** инструмент называется `search_users`

#### Scenario: Имя не по шаблону протокола

- **WHEN** объявлен `mcpTool('users/create', { … })`
- **THEN** брошена ошибка, называющая шаблон, которого требует протокол

### Requirement: Описание инструмента обязательно

У инструмента SHALL быть непустое описание. В форме `implement` оно берётся
из `options.description`, иначе из `operation.doc.description`, иначе из
`operation.doc.summary`. Описание SHALL вычисляться при создании декларации
и ехать в её биндинге: проекция маршрута секцию `doc` не несёт.

Инструмент, у которого не нашлось ни одного из трёх, SHALL сообщаться как
нарушение при старте транспорта.

Требование строже, чем у документа OpenAPI, намеренно: агент выбирает
инструмент по описанию, и инструмент без описания он выбрать не может.

#### Scenario: Описание берётся с операции

- **WHEN** объявлен `mcpTool.implement(CreateUser, { handler })`, у операции
  есть `doc: { summary: 'Создать пользователя' }`
- **THEN** описание инструмента — `Создать пользователя`

#### Scenario: Операция без описания

- **WHEN** объявлен инструмент для операции без `doc.description` и без
  `doc.summary`, и `options.description` не задано
- **THEN** старт падает с текстом, называющим инструмент и три места, где
  описание может быть объявлено

### Requirement: Схемы переводятся конвертерами вызывающего

`inputSchema` и `outputSchema` определения инструмента SHALL получаться
переводом форм io декларации в JSON Schema помощником ядра `leafJsonSchema` с
конвертерами из `converters:` транспорта.

Пакет SHALL NOT зависеть ни от одного валидатора: ни его модули SHALL NOT
импортировать zod, valibot, arktype и прочие, ни его манифест SHALL NOT
объявлять их в `dependencies`/`peerDependencies`. Утверждение SHALL
относиться к самому пакету, а не к транзитивному замыканию, и SHALL
проверяться тестом границы.

`inputSchema` SHALL быть объектной JSON Schema — этого требует протокол.
Инструмент, вход которого не объектный, SHALL сообщаться как нарушение при
старте. Инструмент без `input` SHALL получать пустую объектную схему.

`outputSchema` SHALL объявляться тогда и только тогда, когда форма выхода
переводится в объектную JSON Schema. Клиент проверяет по ней
`structuredContent`, и необъектный выход под это требование не подходит.

Схема, которую ни один конвертер не перевёл, SHALL сообщаться как нарушение с
указанием инструмента и слота.

#### Scenario: Схема входа переведена в JSON Schema

- **WHEN** транспорт объявлен с `converters: [zodConverter()]`, а вход
  инструмента — `z.object({ email: z.string() })`
- **THEN** определение инструмента несёт `inputSchema` с `type: 'object'` и
  свойством `email`

#### Scenario: Конвертера нет

- **WHEN** транспорт объявлен с пустым `converters: []`, а схемы инструментов
  написаны на zod
- **THEN** старт падает с текстом, называющим инструмент, слот и отсутствие
  конвертера

#### Scenario: Выход не объектный

- **WHEN** у инструмента `output: z.number()`
- **THEN** определение инструмента `outputSchema` не несёт

#### Scenario: Валидатор не объявлен пакетом

- **WHEN** прочитан манифест `@nestlingjs/mcp`
- **THEN** среди `dependencies` и `peerDependencies` нет ни одного валидатора

### Requirement: Успех операции отдаётся результатом вызова инструмента

Успешный результат `Ok` SHALL отдаваться в `content` значением выхода в виде
текста JSON. При объявленной `outputSchema` то же значение SHALL уходить и в
`structuredContent`.

Поле `isError` у успеха SHALL отсутствовать или быть `false`.

#### Scenario: Успешный вызов инструмента

- **WHEN** агент вызвал инструмент с объявленной `outputSchema`, хендлер
  вернул `Ok({ id: 'u-1' })`
- **THEN** результат несёт `content` с текстом `{"id":"u-1"}` и
  `structuredContent` со значением `{ id: 'u-1' }`, а `isError` не выставлен

#### Scenario: Успех без объявленной схемы выхода

- **WHEN** агент вызвал инструмент без `outputSchema`, хендлер вернул `Ok(42)`
- **THEN** результат несёт только `content` с текстом `42`

### Requirement: Отказ операции отдаётся отказом инструмента, а не ошибкой протокола

Отказ `Fail` SHALL отдаваться результатом вызова инструмента с
`isError: true`. `content` SHALL содержать текст, называющий `code`,
`message` и `details` отказа.

Детали отказа SHALL NOT уходить в `structuredContent`: клиент проверяет это
поле объявленной схемой выхода, и отказ под неё не подходит.

Отказ SHALL NOT превращаться в ошибку JSON-RPC: объявленный отказ — часть
контракта операции, и агент должен его прочитать, а не получить обрыв вызова.

Ошибка, которую хендлер не объявил, приходит из пайплайна отказом категории
`internal_error` и SHALL отдаваться тем же путём. Деталей необъявленной ошибки
в ответе SHALL NOT быть.

#### Scenario: Объявленный отказ доходит до агента

- **WHEN** агент вызвал инструмент, хендлер вернул
  `EmailTaken.fail({ email: 'a@b.c' })`
- **THEN** результат несёт `isError: true` и текст с кодом
  `conflict:email_taken` и деталями, `structuredContent` отсутствует, а ответ
  JSON-RPC остаётся успешным

#### Scenario: Необъявленная ошибка не раскрывает деталей

- **WHEN** хендлер инструмента бросил исключение
- **THEN** результат несёт `isError: true` и код `internal_error`, а текста
  исключения и стека в ответе нет

### Requirement: Определения инструментов совпадают с типами протокола

Пакет SHALL объявлять собственные типы определения инструмента и результата
его вызова, не импортируя их из SDK в рантайме.

Совпадение с протоколом SHALL проверяться файлом проверки типов: объявленные
пакетом типы присваиваются `Tool` и `CallToolResult` из
`@modelcontextprotocol/sdk/types.js`. SDK SHALL стоять в `devDependencies` и
SHALL NOT попадать ни в `dependencies`, ни в `peerDependencies`.

#### Scenario: Типы пакета присваиваются типам SDK

- **WHEN** прогнан `typecheck` пакета
- **THEN** присваивание `McpToolDefinition` типу `Tool` и `McpCallToolResult`
  типу `CallToolResult` проходит без ошибок

#### Scenario: SDK не попадает в зависимости рантайма

- **WHEN** прочитан манифест `@nestlingjs/mcp`
- **THEN** `@modelcontextprotocol/sdk` объявлен только в `devDependencies`

### Requirement: Одна операция обслуживается и по HTTP, и инструментом

Операция SHALL допускать две входящие поверхности сразу: `httpEndpoint.implement`
и `mcpTool.implement` в одном приложении. Класс-хендлер у них SHALL быть один.

Свойство SHALL проверяться спекой: запрет двух владельцев работает на
биндингах шины, и то, что транспортные биндинги под него не попадают, нужно
удерживать тестом.

#### Scenario: Две поверхности одной операции

- **WHEN** собрано приложение, где `CreateUser` реализована и
  `httpEndpoint.implement`, и `mcpTool.implement` с тем же классом-хендлером
- **THEN** сборка проходит, `POST /users` отвечает, и `tools/call` для
  `users_create` отвечает тем же значением
