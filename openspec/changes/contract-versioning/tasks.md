# Tasks: contract-versioning

Порядок — от схемного слоя наружу (см. `design.md` → D8 «Размещение кода»).
Каждый раздел самодостаточен: закончив его, `yarn verify` должен быть
зелёным. Разделы 1–4 — чистые функции над значениями, поэтому тестируются
без сборки приложения; раздел 5 подключает их к `.check()`.

## 1. Контракт вендор-конвертера (`@nestling/pipeline`)

- [x] 1.1 Тип `SchemaDocConverter { vendor: string; toJsonSchema(schema): unknown }`
  в схемном слое; доккоммент называет обоих потребителей — снапшот
  контрактов (сейчас) и `@nestling/openapi` (#20), — чтобы второй не завёл
  свой
- [x] 1.2 Диспетчер `pickConverter(converters, schema)`: выбор по
  `schema['~standard'].vendor`, отсутствие конвертера — наблюдаемый исход
  (`undefined`), а не бросок; строгость выбирает вызывающий (D2)
- [x] 1.3 Fail-fast на список с двумя конвертерами одного `vendor` — в точке
  передачи списка, с именем вендора-дубликата
- [x] 1.4 Экспорт из публичной поверхности `@nestling/pipeline`
- [x] 1.5 Рантайм-тесты: выбор по вендору; пустой список даёт «конвертера
  нет» без броска; дубль вендора бросает; `validateSync` и схемные границы
  не затронуты (регрессия — конвертеры к валидации отношения не имеют)

## 2. Дескриптор контракта (`@nestling/ports`)

- [x] 2.1 Типы `ContractDescriptor`, `FormDescriptorValue`,
  `SchemaDescriptor` (примитив | JSON Schema | непрозрачный лист с `vendor`
  | отсутствие листа) — все JSON-сериализуемые, без функций и символов
- [x] 2.2 `describeContract(contract | декларация, { converters? })`: имя,
  вид, формы `input`/`output` через `describeForm`, файловые поля
  `multipart` с ограничениями, отказы (`code`, `status`) отсортированные по
  коду
- [x] 2.3 Различить «схемы нет» и «схема есть, но не сконвертирована»
  явными пометками в значении (D2)
- [x] 2.4 Рантайм-тесты: value-формы с конвертером и без; `stream`-выход;
  `multipart` с `upload()`; `JSON.parse(JSON.stringify(d))` равен исходному
  дескриптору

## 3. Снапшот и детерминированная сериализация (`@nestling/ports`)

- [x] 3.1 Тип `ContractSnapshot { snapshotVersion: 1; contracts }`;
  дескриптор несёт перечень опубликовавших топологий (D1)
- [x] 3.2 `snapshotContracts(reports)` на **структурном** типе
  `readonly { contracts }[]` — без импорта `CheckReport` из
  `@nestling/app`, иначе граф пакетов станет циклическим (D8)
- [x] 3.3 Сведение объединением топологий; расхождение дескрипторов одного
  имени между топологиями — ошибка сведения с именем и списком
  расходящихся топологий
- [x] 3.4 Детерминированная сериализация: контракты по имени, отказы по
  коду, ключи JSON Schema в стабильном порядке
- [x] 3.5 Рантайм-тесты: объединение (контракт из одной топологии в
  снапшоте есть, топология названа); побайтовое совпадение двух прогонов;
  перестановка модулей в `spec` не меняет сериализованный снапшот;
  конфликт дескрипторов бросает

## 4. Дифф и отчёт (`@nestling/ports`)

- [x] 4.1 Разбор подмножества JSON Schema (`type`, `properties`,
  `required`, `items`, `enum`, `nullable`) с рекурсией по `properties` и
  `items`; узел вне подмножества — `unknown` с JSON-путём, никогда не
  молчаливая совместимость (D4)
- [x] 4.2 `diffContracts(baseline, current)`: закрытый словарь вердиктов
  `breaking` | `additive` | `unknown`, направление берётся из слота
  (`input` — приходит, `output` — уходит), таблица правил из `design.md` D4
- [x] 4.3 Структурные правила: исчезновение/появление контракта, `kind`,
  вид формы io, примитивный лист, коды и `status` отказов
- [x] 4.4 `CompatibilityReport` — значение с расхождениями,
  сгруппированными по вердикту; каждое несёт имя контракта, путь и описание
- [x] 4.5 Подсказка bump'а: `suggestedName` только у контрактов с
  `breaking`; `<name>` → `<name>.v2`, `<name>.vN` → `.v{N+1}`; распознавание
  суффикса живёт **только** здесь (D7)
- [x] 4.6 `formatCompatibility(report)`: секции по вердиктам со счётчиками,
  в непустой секции `unknown` — строка про подключение конвертера
- [x] 4.7 Бросок **только** на нечитаемом baseline (неизвестная
  `snapshotVersion`, значение не того вида) с ожидаемой и полученной
  версией; по результату сравнения — никогда (D5)
- [x] 4.8 Экспорт всего перечисленного из `index.ts` `@nestling/ports`
- [x] 4.9 Рантайм-тесты по таблице вердиктов: удалённое поле `output`;
  новое required- и новое optional-поле `input`; симметрия слотов на одном
  и том же свойстве; `required` ↔ `optional` в обоих слотах; enum в обоих
  слотах; сужение `type`; удалённый и добавленный код отказа; смена
  `status`; смена `kind`; смена вида формы io
- [x] 4.10 Рантайм-тесты `unknown`: `type` → `oneOf`; смена `vendor`;
  непрозрачные листья с обеих сторон при неизменной структурной части
- [x] 4.11 Рантайм-тесты отчёта: пустой baseline даёт сплошной `additive`;
  три breaking не бросают и не трогают сборку; `report.breaking` сравним
  как значение; baseline «из будущего» бросает
- [x] 4.12 Тест отсутствия флага блокировки: публичная поверхность не несёт
  ни `failOnBreaking`, ни его синонимов (D5 — «не блокирует» структурно)

## 5. Сбор контрактов в `.check()` (`@nestling/app`)

- [x] 5.1 `check(options?)` — необязательный словарь с `converters`; вызов
  без аргумента ведёт себя ровно как прежде
- [x] 5.2 Поле `contracts` в `CheckReport`: дескрипторы деклараций с
  bus-биндингом (`busBindingOf`) из дискавери — **не** из приватного
  реестра `makeContract` (D1)
- [x] 5.3 Отсутствие конвертера для вендора листа не роняет `check()`:
  лист помечается непрозрачным
- [x] 5.4 Рантайм-тесты: контракт в отчёте с конвертером и без;
  импортированный, но не реализованный контракт не попадает в отчёт;
  `contracts` пуст у приложения без контрактов; `check()` по-прежнему не
  выполняет `@OnInit` и не влияет на `run()`

## 6. Матрица топологий (`@nestling/testing`)

- [x] 6.1 `checkTopologies(spec, selections, options?)` — прокидывание
  опций в `check()` каждой топологии; вызов из двух аргументов не меняется
- [x] 6.2 Зависимость на `@nestling/ports` в `package.json` и реэкспорт
  `snapshotContracts`/`diffContracts`/`formatCompatibility` — CI-тест
  пишется одним импортом
- [x] 6.3 Рантайм-тесты: конвертеры доезжают до каждой топологии; снапшот
  собирается из отчётов матрицы без повторной сборки приложения; контракт,
  публикуемый одной топологией из трёх, попадает в снапшот с названной
  топологией
