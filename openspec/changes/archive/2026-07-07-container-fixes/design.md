# container-fixes — design

## Context

Текущее состояние (сверено с кодом 2026-07-07):

- **Атрибуция модуля.** `registerModule` при `providers`-массиве вызывает
  `registerProvider(provider, m.name)` — метка модуля проставляется. При
  `providers`-функции модуль складывает фабрику в
  `#providersFactories: Map<string, ProvidersFactory>` (ключ — имя модуля).
  Позже `appendFactoryProviders()` итерирует `.values()` и вызывает
  `registerProvider(provider)` **без** имени модуля
  (`container.builder.ts:246-253`). Итог: `#providerToModule` для этих токенов
  пуст, и в `buildDependencyGraph` узел получает `metadata.module = undefined`,
  `metadata.exported = undefined`. Метка и признак экспорта теряются, хотя ключ
  с именем модуля уже под рукой.
- **Накопление lifecycle-метаданных.** `@OnInit`/`@OnDestroy`
  (`lifecycle.ts:54-110`) внутри `context.addInitializer` делают
  `metadata.<hook>.push(context.name)` в per-constructor `lifecycleMetadata`.
  По спецификации стандартных ES-декораторов инициализатор метода выполняется
  **на каждый инстанс**, поэтому имя метода дописывается при каждом `new`.
  После N инстансов `onInit`/`onDestroy` содержат имя N раз →
  `getLifecycleHooks` вернёт N одинаковых хуков → `init()`/`destroy()`
  вызовется N раз. Существующие тесты (`lifecycle.spec.ts`) создают один
  инстанс на свежеопределённый класс, поэтому дефект невидим.
- **Контракт accessor'ов.** `BuiltContainer.get()`
  (`container.built.ts:89-95`) возвращает `(node?.instance as T) ?? null` — не
  бросает. JSDoc над ним обещает `@throws` и «returns The service instance» —
  это контракт `getOrThrow()`. `getOrThrow()` (`:97-103`) без JSDoc и проверяет
  `if (!instance)`: на легитимных falsy-значениях (`0`, `''`, `false`) бросает
  ложное «not found».

Ограничение: не менять публичные сигнатуры и типы; token families и
`strictExports` (ideas.md) сюда не тащить.

## Goals / Non-Goals

**Goals:**

- Провайдеры из функциональной фабрики модуля получают ту же метку модуля и
  признак экспорта, что и провайдеры-массивом.
- `@OnInit`/`@OnDestroy`-метаданные не зависят от числа инстансов; каждый хук
  собирается и вызывается ровно один раз.
- JSDoc `get()`/`getOrThrow()` соответствует поведению; `getOrThrow` отличает
  отсутствие токена от falsy-значения.
- Рантайм-тесты на каждый из трёх дефектов.

**Non-Goals:** token families, `strictExports`, рантайм-инкапсуляция модулей,
scoped-контейнеры, различение `get()` для значения `null`/`undefined`.

## Decisions

**D1. Прокидывать имя модуля из `#providersFactories` в `registerProvider`.**
`appendFactoryProviders()` итерирует не `.values()`, а `.entries()`:
```
for (const [moduleName, factory] of this.#providersFactories) {
  for (const provider of await factory()) {
    this.registerProvider(provider, moduleName);
  }
}
```
Имя модуля уже есть в ключе Map — дополнительного состояния не требуется.
После этого `#providerToModule` заполняется одинаково для обеих форм
`providers`, и `buildDependencyGraph` проставляет `module`/`exported` из уже
существующих `#providerToModule` и `#moduleExports` без изменений (ключи
там — `stringifyToken`, что совпадает с текущей схемой).
*Почему не отдельная Map провайдер→модуль для фабрик*: лишнее состояние;
имя уже в ключе. *Почему не проставлять метку в самой фабрике*: фабрика —
пользовательский код, не должна знать про метаданные графа.

**D2. Идемпотентная запись lifecycle-метаданных (dedup по имени метода).**
В `@OnInit`/`@OnDestroy` перед `push` проверяем наличие имени:
```
if (!metadata.onInit.includes(name)) metadata.onInit.push(name);
```
Имена методов внутри класса уникальны, поэтому dedup по имени безопасен и
делает сбор метаданных идемпотентным относительно числа инстансов.
*Почему не убрать `addInitializer` и не регистрировать один раз*: у method-
декоратора нет доступа к классу вне инициализатора (класс ещё не существует на
момент декорирования) — `addInitializer` остаётся единственной точкой, где
доступен `this.constructor`. Дедупликация — минимальное корректное
вмешательство. *Почему не Set*: порядок хуков значим (объявление →
исполнение); массив с проверкой сохраняет порядок, `LifecycleMetadata`
и `LifecycleHooks` остаются массивами (тип не меняется).
Замечание о наследовании: при декорированном методе базового класса
инициализатор исполняется с `this.constructor` = фактический (под)класс —
поведение атрибуции хуков к подклассу не меняется, dedup на него не влияет.

**D3. Выправить контракт `get()`/`getOrThrow()` под фактическое поведение.**
- `get()`: JSDoc переписать — возвращает `T | null`, `null` когда токен не
  зарегистрирован; **без** `@throws`. Поведение не меняется.
- `getOrThrow()`: добавить JSDoc и заменить `if (!instance)` на проверку
  наличия узла в графе, чтобы `0`/`''`/`false` не считались отсутствием.
  Реализация опирается на присутствие токена, а не на truthiness инстанса
  (например, `get`, отличающий «нет узла» от «есть узел с falsy-значением», —
  через отдельный внутренний признак наличия либо прямой запрос узла графа).
*Почему трогаем поведение `getOrThrow`, а roadmap называет только «JSDoc get()»*:
корректно задокументировать `get()` невозможно, не зафиксировав рядом контракт
парного `getOrThrow()`; truthiness-баг — тот же метод-семейство и та же строка
внимания. Изменение узкое и низкориск. Различение `null`/`undefined`-значения
для `get()` остаётся вне scope (Non-Goals).

## Risks / Trade-offs

- [Проставление метки модуля меняет снапшоты `toJSON()`/viz, если где-то
  зафиксировано `module: undefined` для функциональных провайдеров] → это и
  есть исправление; поправить ожидания в тестах, отметить как фикс.
- [Dedup по имени скроет легитимный повторный `@OnInit` на одноимённых
  сущностях] → имена методов класса уникальны; сценария «два разных хука с
  одним именем» не существует.
- [Изменение `getOrThrow` на проверку наличия узла требует различать «нет
  узла» и «falsy-значение»] → делаем через явный запрос узла графа, не через
  truthiness; покрываем тестом с `useValue: 0`.

## Migration Plan

Публичный API и сигнатуры неизменны — миграция пользовательского кода не
нужна. Наблюдаемые изменения: (1) функциональные провайдеры теперь помечены
модулем в графе; (2) lifecycle-хуки перестают дублироваться при нескольких
сборках; (3) `getOrThrow` перестаёт ложно бросать на falsy-значениях. Все три —
приведение к корректному поведению. Откат — revert коммита.

## Open Questions

- Нужно ли `get()` различать «токен не зарегистрирован» и «зарегистрировано
  значение `null`/`undefined`»? Сейчас неотличимо (оба → `null`). Отложено:
  реальных провайдеров со значением `null` в кодовой базе нет; пересмотреть,
  если появится потребность (кандидат — `has(token)` в публичном API).
