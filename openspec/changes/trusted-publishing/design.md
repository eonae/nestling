## Context

Релиз `v0.1.1` упал на первом же пакете: реестр ответил `403` с текстом
`Two-factor authentication or granular access token with bypass 2fa
enabled is required to publish packages`. OIDC-обмен к тому моменту уже
отработал, подпись provenance ушла в журнал прозрачности, и упал именно
`PUT` в реестр.

Ограничения, в которых нужно уместиться:

- Публикация требует двухфакторной аутентификации у аккаунта мейнтейнера.
  Это политика реестра для новых пакетов, а не настройка аккаунта.
- Granular-ключ доступа с обходом 2FA публиковать пока может, но с
  января 2027 теряет это право. Заводить процесс вокруг него значит
  переделывать через несколько месяцев.
- Доверенного издателя заводят на странице пакета. Пакета, которого в
  реестре нет, страницы не имеет.
- Застейджить новое имя реестр тоже не даёт.

Отсюда следует, что первая публикация каждого нового имени обязана быть
интерактивной, а всё остальное может идти без секретов вовсе.

## Goals / Non-Goals

**Goals:**

- Публикация из CI без долгоживущего ключа доступа.
- Provenance у всех версий, кроме первой версии нового имени.
- Повторяемость: упавший релиз доводится тем же тегом.

**Non-Goals:**

- Staged publishing.
- Публикация `@nestlingjs/viz`: пакет помечен `private: true`, вопрос его
  упаковки открыт записью [2026-09-10].
- Автоматическое заведение доверенных издателей. Их восемнадцать штук
  один раз, и API для этого нет.

## Decisions

**Доверенный издатель вместо ключа доступа.** Workflow релиза
авторизуется OIDC-обменом: реестр проверяет владельца, репозиторий и имя
файла workflow. Украсть такую идентичность нельзя, поэтому секрет
`NPM_TOKEN` удаляется, а не заменяется другим.

Альтернатива — granular-ключ доступа с обходом 2FA. Отвергнута: в январе
2027 такие ключи лишаются права публиковать, и процесс пришлось бы
переделывать.

**Первая версия имени уходит с рабочей машины.** `scripts/publish.mjs`
получает режим `--interactive`: проверяет вход через `npm whoami`,
предупреждает об отсутствии provenance и спрашивает код 2FA перед
отправкой тарбола.

Код переиспользуется, пока реестр его принимает. Код живёт полминуты, а
публикация восемнадцати пакетов занимает дольше, поэтому одного ввода не
хватит; спрашивать же код на каждый пакет значило бы восемнадцать вводов
там, где хватает нескольких. Отказ по коду отличается от прочих ошибок
реестра по `EOTP` в выводе.

Альтернатива — опубликовать с машины версию-заглушку `0.0.0`, завести
доверенных издателей и выпустить `0.1.1` из CI с provenance. Отвергнута:
в реестре навсегда осталось бы восемнадцать мусорных версий ради значка
у первой версии, которой ещё никто не пользуется.

**npm на runner'е обновляется явно.** Доверенного издателя npm понимает с
версии 11.5.1, а с Node 24 на runner попадает та версия, что вошла в
образ. Шаг `npm install -g npm@latest` снимает зависимость от образа.

**Манифест не считается изменением примера.** Проверка свежести глав
гайда сравнивала дату последнего коммита в каталог пакета с датой плашки.
`lerna version` меняет в каждом манифесте одно поле `version`, поэтому
каждый релиз помечал бы устаревшими все главы сразу. Путь
`:(exclude)<pkg>/package.json` убирает манифест из расчёта.

## Risks / Trade-offs

**Первая версия имени без provenance** → цена разовая и касается только
`0.1.1`, у которой пользователей нет. Все следующие версии подписываются.

**Доверенный издатель не заведён, а тег поставлен** → релиз падает с
`403`. Разбор отказа записан в `RELEASING.md`, публикация повторяема тем
же тегом после настройки.

**Имя файла workflow входит в идентичность издателя** → переименование
`release.yml` ломает публикацию молча, до следующего тега. Файл
переименовывать нельзя, пока издатели не перенастроены.

**`npm@latest` на runner'е** → версия не закреплена, и ломающее
изменение npm придёт само. Взамен не приходится следить за версией npm в
образе runner'а; при первом же отказе версия закрепляется.

## Migration Plan

1. Опубликовать `0.1.1` с рабочей машины: `npm login`,
   `yarn build && yarn pack:check`, `node scripts/publish.mjs --interactive`.
2. Завести доверенного издателя на каждом опубликованном пакете:
   владелец `eonae`, репозиторий `nestling`, файл `release.yml`.
3. Удалить секрет `NPM_TOKEN` из настроек репозитория.
4. Следующий релиз выпустить тегом и убедиться, что у версии стоит значок
   provenance.

Отката не требуется: упавший релиз ничего не публикует, а уже
опубликованные версии пропускаются проверкой в `scripts/publish.mjs`.

## Open Questions

1. Переживает ли один код 2FA несколько публикаций подряд. Скрипт
   рассчитан на оба исхода, но сколько кодов потребует прогон из
   восемнадцати пакетов, покажет первая публикация.
2. Что делать с новым именем пакета после того, как процесс устоялся:
   каждый такой пакет снова требует ручной первой публикации, и это стоит
   записать в чек-лист создания пакета.
