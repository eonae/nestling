# Выпуск версии

Версию поднимает человек, публикует CI по тегу. Ключа доступа к реестру в
репозитории нет: право публиковать даёт OIDC-обмен с доверенным издателем,
заведённым на странице пакета. Он же выдаёт provenance, поэтому у версии,
отправленной с рабочей машины, значка provenance не будет.

Версия одна на все публикуемые пакеты — они выпускаются вместе и совместимы
между собой только одной версии. `@nestlingjs/viz` помечен `private: true`,
в реестр не уходит и в подъёме версии не участвует.

## Что нужно один раз

1. Организация `nestlingjs` в реестре, аккаунт с правом публиковать в неё.
2. Двухфакторная аутентификация на этом аккаунте — passkey или код
   приложения. Реестр требует её от любой публикации: аккаунт без 2FA
   получает `403` с текстом
   `Two-factor authentication ... is required to publish packages`.
3. Публичный репозиторий. На приватном provenance не выдаётся, и шаг
   публикации падает.
4. Доверенный издатель на странице каждого публикуемого пакета: владелец
   `eonae`, репозиторий `nestling`, файл workflow `release.yml`. Заводится
   после того, как пакет появился в реестре — см. следующий раздел.
5. Право `publish` у каждого издателя. Реестр выдаёт новому издателю
   только `stage publish` — право положить версию в staging, откуда её
   выпускает человек. Прямая публикация добавляется отдельно: кнопкой
   Edit на карточке издателя или командой `npm trust`. Без неё релиз
   падает с `403 OIDC permission denied for this action`.

## Первая публикация имени

Доверенного издателя нельзя привязать к пакету, которого в реестре ещё
нет, а застейджить новое имя реестр не даёт. Поэтому первую версию каждого
нового имени отправляет человек со своей машины:

```bash
npm login
yarn nx run-many -t build && yarn pack:check
node scripts/publish.mjs --interactive
```

Скрипт идёт по публикуемым пакетам и пропускает уже опубликованные версии.
Второй фактор спрашивает сам `npm publish`, на каждый пакет: passkey он
подтверждает адресом, который печатает в терминал и открывает в браузере,
код приложения — запросом в том же терминале. Прервать прогон можно на
любом пакете: повторный запуск продолжит с того, что ещё не в реестре.

После этого заведите доверенного издателя на странице каждого нового
пакета и дайте ему право `publish`. Список имён для такой разовой
операции выдаёт `publishablePackages()` из `scripts/packages.mjs`, а
заводит издателя команда:

```bash
npm trust github <пакет> --repo eonae/nestling --file release.yml \
  --allow-publish --allow-stage-publish -y
```

Дальше имя выпускается только через CI, и этот раздел к нему больше не
относится.

## Выпуск

### 1. Ветка влита в `main`, CI зелёный

Тег ставится на коммит в `main`. Workflow проверки прогоняет `yarn verify`
на каждый push и pull request — его результат виден в списке проверок.

### 2. Поднять версию

```bash
git switch main && git pull
yarn lerna version <patch|minor|major> --force-publish
```

`--force-publish` берёт все пакеты, не сверяясь с тем, что менялось после
прошлого тега. Версия одна на всех, поэтому «этот пакет не изменился»
смысла не имеет, а без флага релиз без правок в `packages/` заканчивается
строкой «No changed packages found».

Команда правит `version` в восемнадцати манифестах и в `lerna.json`, делает
коммит и ставит тег `vX.Y.Z`. Пуш выключен настройкой (`push: false`), так
что до следующего шага всё остаётся локальным и откатывается через
`git reset --hard origin/main`.

Внутренние зависимости остаются записанными протоколом `workspace:*` — это
верно: подставит версии `yarn pack` в момент упаковки.

### 3. Отправить коммит и тег

```bash
git push --follow-tags
```

Одна команда отправляет два ref'а, и каждый запускает свой workflow: ветка
`main` — проверку, тег `v*` — релиз. Оба прогона названы заголовком
коммита, который сделала `lerna version`, поэтому в списке выглядят
одинаково.

Проверка на таком коммите ничего не прогоняет: она видит тег версии и
пропускает `yarn verify`, потому что тот же коммит проверяет релиз.

### 4. Дождаться workflow

Порядок шагов: `yarn install --immutable` → `yarn verify` →
`yarn pack:check` → `node scripts/publish.mjs`. Публикация выполняется
последней и только после того, как тарболы установились в проект вне
репозитория и оттуда импортировались. Красный шаг до неё не доводит.

`publish.mjs` сверяет тег с манифестами: если тег обещает версию, которой
в манифестах нет, релиз останавливается до публикации.

### 5. Проверить результат

```bash
npm view @nestlingjs/app version
```

На странице пакета должен стоять значок provenance со ссылкой на прогон
workflow.

## Когда что-то пошло не так

**Workflow упал до публикации.** Ничего не опубликовано. Исправьте
причину, влейте в `main`, удалите тег локально и на сервере
(`git tag -d vX.Y.Z && git push origin :vX.Y.Z`), повторите с шага 2.

**Workflow упал в середине публикации.** Часть пакетов уже в реестре.
Публикация повторяема: `publish.mjs` спрашивает реестр о каждой версии и
пропускает опубликованные, поэтому достаточно перезапустить упавший
прогон тем же тегом.

**Реестр ответил `403 OIDC permission denied for this action`.** Обмен
состоялся, но издателю не разрешено то, что делает workflow. Проверьте на
карточке издателя право `publish`: новому издателю реестр выдаёт только
`stage publish`.

**Реестр ответил `403` про двухфакторную аутентификацию.** Публикация
выполняется не тем способом, который реестр ожидает. Проверьте, что на
странице пакета заведён доверенный издатель с этим репозиторием и файлом
`release.yml`, а у job'а есть право `id-token: write`. У нового имени такой
страницы ещё нет, поэтому первую версию публикуйте по разделу «Первая
публикация имени».

**Опубликовано не то.** Отката нет. `npm unpublish` работает 72 часа и
только пока версией никто не пользуется; после этого пара имя-версия
занята навсегда. Правильный ход — выпустить следующую версию, а сломанную
пометить как deprecated:

```bash
npm deprecate @nestlingjs/app@X.Y.Z "сломанная сборка, используйте X.Y.Z+1"
```

## Проверить упаковку до релиза

```bash
yarn nx run-many -t build && yarn pack:check
```

Упаковывает публикуемые пакеты, ставит тарболы в проект вне репозитория и
импортирует каждый оттуда. Ловит то, чего не видит `yarn verify`: пакет без
сборки в тарболе, оставшийся протокол `workspace:` и зависимость,
объявленную в `devDependencies`, но импортируемую из `src`. В `yarn verify`
проверка не входит — ставит пакеты из сети и занимает минуты.
