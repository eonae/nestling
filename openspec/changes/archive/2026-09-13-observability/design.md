## Context

Ядро уже держит два соседних механизма, на которые наблюдаемость ложится
без новых понятий.

- **Логгер.** `RootLogger$` создаётся вне графа, семейство `Logger$(scope)`
  строит члена как `root.child({ scope })`, умолчание задаётся ядром, а
  настоящая реализация приходит опцией `makeApp({ logger })`. Провайдер под
  корневым DI-токеном — ошибка дубля. Метрики повторяют эту схему целиком.
- **Ambient-переменные.** `well-known.ts` держит `Signal` и `RequestId`;
  `ambientRequestId()` читает идентификатор мимо графа, чтобы им
  пользовался корневой логгер. `contextVar(…, { propagate: true })` уже
  везёт значение конвертом шины и кладёт его в `ctx.raw.attributes` на
  приёме. Трассировка встаёт третьей well-known переменной.

Швов для записи метрики ровно два.

- `PipelineImpl.executeWithHandler` в `pipeline/core/pipeline.ts` считает
  `outcome` функцией `computeOutcome` и вызывает `.finally`-юниты. Опции
  выполнения `ExecuteOptions` уже возят `logger`.
- `ports/kernel.ts` собирает узел порта: строки 203 и 230 выбирают между
  local- и remote-реализацией из `ports/invoker.ts`. Обёртка в этих двух
  местах покрывает все четыре формы вызывателя.

Ограничение — горячий путь. Change `hot-path-trim` снял с запроса всё, что
можно было снять, и бюджет зафиксирован бенчем под Node 24. Наблюдаемость
не имеет права его сдвинуть у приложения, которое её не включало.

## Goals / Non-Goals

**Goals:**

- Запрос, прошедший три процесса, связывается одним `traceId` в записях
  логгера.
- Счётчик и длительность на endpoint и на вызов порта считает ядро, а не
  прикладной код.
- Публичной границы ядра хватает стороннему экспортёру: доказывается
  адаптером внутри `examples/split-nats`, без нового пакета.
- Приложение без настроенных метрик не платит за них ничего.

**Non-Goals:**

- Пакет `@nestlingjs/otel`, экспорт спанов и endpoint `/metrics`.
- Формат Prometheus и любой другой формат экспорта в ядре.
- Автоматическая подстановка `withTracing()` в каждый endpoint.
- Сэмплирование: ядро переносит флаг, но не решает, что записывать.
- Провоз trace-context через CLI-транспорт.

## Decisions

### Метрику пишет рантайм пайплайна, а не `.finally`-юнит

Запись стоит в `executeWithHandler` рядом с вызовом `.finally`-юнитов, в
том же месте, где вычислен `outcome`.

Юнит потребовал бы от приложения добавить его в каждый пайплайн, и endpoint
без слоя остался бы неучтённым. Рантайм видит все четыре исхода
(`completed`, `disconnected`, `aborted`, `failed`) и уже умеет откладывать
ответную фазу потокового ответа до закрытия итератора — обе особенности
пришлось бы воспроизводить в юните.

`ExecuteOptions` получает поле `metrics?: Metrics` рядом с `logger`.
`makeDispatch` передаёт его тем же способом, что логгер.

### Инструментовка включается вместе с настоящей реализацией

`RootMetrics$` есть в графе всегда, и умолчание под ним ничего не делает:
фича с метрикой собирается без плагина — это требование записи
[ideas.md [2026-09-12]](../../../docs/decisions/ideas.md).

Инструментовку ядра включает опция `makeApp({ metrics })`. Без неё поле
`metrics` в `ExecuteOptions` не заполняется, и рантайм не снимает время и
не вызывает счётчик: проверка `metrics === undefined` — та же форма, что у
`logger` сегодня.

Отвергнут флаг `enabled` в интерфейсе `Metrics`: он обязал бы каждого
адаптера отвечать на вопрос рантайма, а ответ всегда один.

### Интерфейс `Metrics` — два пишущих метода

```typescript
type MetricAttributes = Record<string, string | number | boolean>;

interface Metrics {
  counter(name: string, value?: number, attributes?: MetricAttributes): void;
  histogram(name: string, value: number, attributes?: MetricAttributes): void;
}
```

Методы пишут значение, а не отдают объект-инструмент. Инструмент пришлось
бы создавать, кэшировать и как-то закрывать, а пустая реализация перестала
бы быть пустой функцией. Адаптер, которому инструменты нужны, создаёт их у
себя по имени.

`gauge` в V1 нет: ядру нечего им измерять.

### Корень и семейство — по образцу логгера

- `RootMetrics$` — корневой DI-токен типа `Metrics`. Значение задаётся
  опцией `makeApp({ metrics })`, провайдер под ним — ошибка дубля с тем же
  текстом, что у логгера.
- `Metrics$(scope)` — семейство. Член добавляет к каждой записи атрибут
  `scope`. `Metrics$.auto` даёт члена по имени класса-потребителя.
- У `Metrics` нет метода `child`: рецепт семейства оборачивает корень сам.

### Имена метрик и атрибуты

| Метрика | Вид | Атрибуты |
| --- | --- | --- |
| `nestling.requests` | счётчик | `transport`, `pattern`, `outcome` |
| `nestling.request.duration` | гистограмма, мс | `transport`, `pattern`, `outcome` |
| `nestling.port.calls` | счётчик | `operation`, `kind`, `binding`, `outcome` |
| `nestling.port.duration` | гистограмма, мс | `operation`, `kind`, `binding`, `outcome` |

Все атрибуты берутся из деклараций, а не из запроса: `pattern` — шаблон
маршрута endpoint'а, `operation` — имя операции. Значений конечное число, и
количество рядов не растёт от трафика.

Единица длительности — миллисекунды, как у `timeoutMs` и `deadline`.

`binding` принимает `local` и `remote`. Вызов порта с co-located
реализацией идёт через `dispatch` и поэтому даёт обе метрики: свою и
метрику endpoint'а реализации. Атрибут `binding` разделяет их при подсчёте.

### Переменная `Trace` — объект, формат передачи по сети — W3C

```typescript
interface TraceContext {
  readonly traceId: string;
  readonly spanId: string;
  readonly parentSpanId?: string;
  readonly sampled: boolean;
}

export const Trace: ContextVar<TraceContext, 'trace'>;
```

Ключ `'trace'` резервируется за ядром, как `'signal'` и `'requestId'`.
Переменная объявлена `{ propagate: true }`, поэтому вызыватель порта кладёт
её в конверт шины, а получатель — в `ctx.raw.attributes`.

Значение — объект, а не строка `traceparent`: прикладной код читает
`traceId` через `Ctx(Trace)` без разбора формата. Строка W3C остаётся
формой передачи по HTTP.

### `withTracing()` — pre-юнит, кладущий переменную

Юнит читает родительский контекст из `ctx.raw.attributes` в таком порядке:

1. поле `trace` — значение, привезённое шиной;
2. заголовок `traceparent` — HTTP;
3. ничего — начинается новая трасса.

Дальше юнит создаёт идентификатор участка из восьми случайных байт, кладёт
прежний участок в `parentSpanId` и пишет переменную. Непонятный
`traceparent` не отказ: он игнорируется, и трасса начинается заново.
Значение приходит из-за границы доверия и схемы не имеет — так же, как
любое провозимое значение.

Композиция остаётся явной: юнит объявляется в пайплайне, как
`withRequestId()`. Автоматической подстановки нет — это правило
`explicit over implicit`, и оно же делает присутствие трассировки
проверяемым политикой `everyEndpoint(…).hasVar(Trace)`.

Отвергнут вариант «ядро кладёт трассу само, мимо пайплайна»: значение
попало бы в накопленный `input` мимо pre-юнита, что запрещено capability
`context-propagation`.

### `traceId` в записи логгера

`ConsoleLogger` добавляет поле `traceId` тем же приёмом, что `requestId`:
функцией `ambientTraceId()`, читающей ячейку текущего запроса мимо графа.
Поле добавляется, если трасса в контексте есть и вызов его не задал.

Это главная отдача change'а для `split-nats`: записи двух процессов
сходятся по одному значению.

### Транспортные пакеты не меняются

Родительский контекст читается из `ctx.raw.attributes` в обоих случаях.
HTTP-транспорт кладёт туда все заголовки запроса, а `profileAttributes`
кладёт провозимые значения под их собственными ключами рядом с `subject`.
Ни `transport.http`, ни `transport.nats` для приёма трассы править не
требуется.

### Клиент отправляет `traceparent` — читалкой из опции

`makeClient` принимает опцию `trace: () => string | undefined` и ставит её
значение заголовком `traceparent`. Заголовок, заданный полем `headers`,
сильнее. Вне запроса читалка возвращает `undefined`, и заголовка не
появляется.

Отвергнут вариант «клиент читает `Trace` сам»: `@nestlingjs/client`
зависит только от `@nestlingjs/operations` и собирается для браузера — это
свойство пакета, закреплённое тестом границы. Чтение ambient-контекста
потребовало бы зависимости от `@nestlingjs/app` и `node:async_hooks`, то
есть всего фреймворка в браузерном бандле.

Готовую читалку экспортирует `@nestlingjs/app`, и включение остаётся
однострочным:

```typescript
import { traceparent } from '@nestlingjs/app';

const api = makeClient({ getUser: GetUser }, { baseUrl, trace: traceparent });
```

### `spyMetrics()` — записи значениями

`@nestlingjs/testing` экспортирует `spyMetrics()`, возвращающий
`{ metrics, records }`, где запись — `{ kind, name, value, attributes }`.
Подмена `[RootMetrics$, spy.metrics]` в `overrides` перехватывает записи
всех членов `Metrics$`, как `[RootLogger$, spy.logger]` перехватывает
записи логгера.

## Risks / Trade-offs

- **Горячий путь дорожает у всех.** → Инструментовка включается вместе с
  опцией `makeApp({ metrics })`; без неё рантайм не делает ни одного
  лишнего вызова. Бенч под Node 24 прогоняется до и после, результат
  сравнивается с бюджетом `hot-path-trim`.
- **Длительность потокового ответа измеряет доставку, а не хендлер.** →
  Ответная фаза потока откладывается до закрытия итератора, и метрика
  следует за ней. Поведение называется в главе гайда и в JSDoc.
- **Локальный вызов порта учитывается дважды.** → Атрибут `binding`
  разделяет вызов порта и обработку endpoint'а реализации. Пример в главе
  показывает, как считать одно и другое.
- **`traceparent` приходит из-за границы доверия.** → Значение не
  валидируется схемой, непонятное игнорируется. Ограничение названо в
  документации рядом с тем же ограничением провоза контекста.
- **Атрибуты раздувают количество рядов у экспортёра.** → Ядро берёт
  атрибуты только из деклараций. Значения из запроса в метрики не
  попадают, и это фиксируется требованием capability.

## Migration Plan

Ломающих изменений нет. Приложение получает новые экспорты и опцию;
существующий код собирается без правок.

Включение — два шага: добавить `withTracing()` в базовый слой и передать
`makeApp({ metrics })`. Оба шага показывает пример `split-nats`.
