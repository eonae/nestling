## Короткий ответ

nestling **необычно хорошо** подходит под эту идею — лучше, чем Nest, — и не случайно, а из-за двух уже принятых решений:

1. **Модули — plain values** (`makeModule`/`makeAppModule` — identity-функции). Значит «фича» — это тоже просто значение, а выбор подмножества фич — это **фильтрация массива в композиционном корне**, а не рантайм-механизм внутри контейнера.
2. **Контейнер жадный** (`build()` инстанцирует весь граф, топологический init/destroy, проверка циклов). Значит «не выбрал фичу → её провайдеры физически не построились» получается **само собой**, без единой строчки feature-flag-логики в ядре.

То есть 80% того, что ты описываешь, фреймворк уже поддерживает бесплатно. Есть **ровно одна вещь, которая сегодня активно этому мешает**, и есть один по-настоящему трудный слой (межфичевое взаимодействие). Разберу по порядку.

## Что мешает сегодня: глобальный registry эндпоинтов

Смотри цепочку:

- `packages/nestling.pipeline/src/metadata/endpoint-registry.ts:10` — модульный глобальный `const endpointRegistry = new Set()`.
- `endpoint.ts:97` — декоратор `@Endpoint` при импорте класса **сам себя** регистрирует в этот Set (side-effect импорта).
- `App.#registerEndpoints()` (`app.ts:200`) итерирует `getAllEndpoints()` и делает `container.get(EndpointClass)` — **и бросает**, если класс есть в registry, но его модуль не зарегистрирован в контейнере (`app.ts:215`).

Это прямо конфликтует с «запусти подмножество фич». Как только файл фичи оказался импортирован (транзитивно, через barrel, ради теста — неважно), её эндпоинты попадают в глобальный Set, и App попытается их инстанцировать и упадёт, потому что модуля в контейнере нет. Дискавери эндпоинтов сейчас **ортогонален** тому, какие модули ты выбрал.

**Фикс** (он же — латентный баг-фикс, полезный сам по себе): эндпоинты должны обнаруживаться **обходом дерева зарегистрированных модулей** (`AppModule.endpoints` + `imports`), а не из глобального registry. Тогда «не выбрал фичу → её эндпоинтов просто нет» работает честно и без зависимости от «не импортируй файл». Это полностью в духе ideas.md: модуль — единица упаковки, сборка жадная, магии нет. Глобальный Set после этого можно оставить только для standalone-транспортов или выкинуть.

Это **предпосылка №1** для всей затеи, и она маленькая.

## Слой «фича» поверх модулей

Фича — на уровень выше `AppModule`: именованный бандл модулей + декларация того, **что фиче нужно от рантайма**. Раз модули — значения, фича тоже значение:

```typescript
const OrdersFeature = makeFeature({
  name: 'orders',
  modules: [OrdersModule, OrdersHttpModule],
  needs: ['http'],            // какие транспорты/рантаймы требует
  dependsOn: ['catalog'],     // от каких фич зависит (для резолва подмножества)
  config: OrdersConfigSchema, // zod-схема env этой фичи
});
```

И манифест + селектор:

```typescript
const app = assemble({
  features: [OrdersFeature, BillingFeature, CatalogFeature, WorkerFeature],
  transports: { http: new HttpTransport({ port: 3000 }) },
  select: parseFeaturesFlag(process.argv), // 'all' | ['orders','billing']
});
```

`select` замыкает `dependsOn` (выбрал `orders` → тянется `catalog`), собирает модули выбранных фич и отдаёт их в существующий `App`. Здесь **ноль новой машинерии контейнера** — только фильтрация массива значений. `--features=all` для локалки, `--features=orders` для горизонтального масштабирования одной функции — это разные аргументы одного и того же бинарника.

## Capability negotiation (какие транспорты поднимать)

Прямое следствие горизонтального масштабирования: разные подмножества фич = разные топологии одного кода.

- `--features=api` — HTTP-facing, поднимает порт.
- `--features=workers` — консьюмеры очереди, **HTTP не открывает вообще**.
- `--features=all` — всё, локальная разработка.

Значит App должен поднимать **только те транспорты/рантаймы, что реально нужны выбранным фичам** (`needs`), и **падать на старте** (fail-fast), если фича требует `http`, а транспорт не сконфигурирован. Сейчас `App.#listen()` тупо поднимает все транспорты из конфига — это надо связать с `needs` выбранного подмножества. Средний по размеру кусок.

## Трудный слой: как фичи общаются (суть модульного монолита)

Вот где решается, получится ли **splittable-монолит**, а не distributed monolith. Два режима одного и того же call-site A→B:

- **co-located** (A и B в одном процессе) — это просто вызов через DI, синхронно, транзакционно, типизированно;
- **split** (A и B в разных процессах, отмасштабированы врозь) — это сеть (HTTP/очередь), асинхронно, может упасть.

Требование «масштабировать функции независимо» означает, что **один и тот же вызов A→B должен работать в обоих режимах без переписывания A**. Это location transparency, и она в лоб противоречит принципу ideas.md «no runtime magic / explicit over implicit».

Разрешение противоречия — в духе nestling: **индиректность резолвится на этапе сборки, а не на запросе.**

- Фичи общаются **только через типизированные порты-контракты** (schema-first, как эндпоинты), а не импортируя конкретные сервисы друг друга. B *предоставляет* порт, A *потребляет* токен порта — конкретную реализацию B не видит.
- **Биндинг порта выбирает селектор в композиционном корне**, зная выбранное подмножество + карту топологии (кто где крутится):
  - B в выбранном наборе → порт биндится на локальную реализацию (провайдер), вызов в процессе;
  - B не выбран → порт биндится на remote-client (HTTP/очередь) на адрес, где B живёт.

На запросе A вызывает **конкретный** клиент, зафиксированный на старте — никакого динамического dispatch, никакого service discovery в контейнере. Граф остаётся полным и проверяется на `build()`. Это ровно «жадная композиция константами, проверка компилятором».

Дисциплина, которая делает монолит реально splittable (и которую фреймворк должен сделать **синтаксически видимой**): **межфичевый вызов по контракту всегда async + failure-aware** (`Ok`/`Fail`), даже когда фичи co-located — потому что завтра между ними сеть. Вызовы **внутри** фичи — обычные функции через DI. То, что граница (порт) выглядит в коде иначе, чем «внутри» (plain DI), — и есть то, что отличает модульный монолит от распределённого монолита, который на самом деле не разбирается.

Честно: это единственный по-настоящему большой и исследовательский кусок. В v1 его можно **отложить**, введя ограничение «фичи, которые синхронно зовут друг друга, нельзя разносить по процессам» — и разрешать split только там, где связь уже через очередь/HTTP. Порты добавляются потом, не ломая композиционную модель.

| | Стоимость | Что это |
|---|---|---|
| Фича = бандл значений, выбор = фильтр массива | **бесплатно** | следствие «модули — plain values» |
| Не выбрал → не построилось | **бесплатно** | следствие жадного контейнера |
| Per-feature конфиг `Feature(config)` | **бесплатно** | следствие «параметризованные модули — это функции» |
| Дискавери эндпоинтов из дерева модулей | **S, обязательно** | иначе глобальный registry ломает всё; ещё и баг-фикс |
| `makeFeature` + манифест + `--features` селектор | **S** | тонкий слой над модулями |
| Capability negotiation (поднимать нужные транспорты, fail-fast) | **M** | «разные подмножества = разные топологии» |
| Порты + local/remote-биндинг (location transparency) | **L, research** | суть splittable-монолита; можно отложить |

Вывод: **архитектурно фреймворк уже почти готов** — потому что ключевые решения (модули-значения, жадная сборка, отказ от рантайм-инкапсуляции) случайно оказались ровно теми, на которых строится модульный монолит с выбираемыми фичами. Требуется один обязательный фикс (дискавери эндпоинтов) и один тонкий слой (`makeFeature` + селектор), чтобы получить рабочий `--features=all|subset`. А масштабирование отдельных функций врозь упирается в порты — и здесь надо думать отдельно.

## Половина портов у тебя уже есть

Порт распадается на два направления:

- **Inbound** — «я обрабатываю этот контракт» (сторона-владелец). Это **буквально endpoint**. `App.#registerEndpoints` уже роутит эндпоинты по `metadata.transport` (`app.ts:223`): endpoint объявляет, на каком транспорте он живёт, App находит транспорт и регистрирует. Contract-endpoint с `transport: 'nats'` попадёт на NATS-транспорт, чей `endpoint()` вместо HTTP-роутинга сделает `nc.subscribe(subject, handler)`. **Ноль изменений в ядре** (кроме фикса дискавери из прошлого разговора).
- **Outbound** — «мне нужно позвать этот контракт» (сторона-потребитель). Вот это **единственное, чего реально нет**: типизированный клиент + решение local-vs-remote.

То есть NATS как транспорт для inbound — это ещё один пакет `@nestling/transport.nats`, реализующий существующий `ITransport`, ровно как `transport.http` сегодня. Новая абстракция нужна только для исходящей стороны. Дальше — по твоим трём вопросам.

## Контракт как общее значение (основа всего)

Порт и endpoint должны рождаться из **одного** schema-first значения — иначе они разъедутся. Контракт направление-нейтрален:

```typescript
// features/billing/contracts.ts — владеет billing, импортируют потребители
export const ChargeCard = defineContract({
  name: 'billing.charge',        // → NATS subject
  kind: 'request',               // request-reply
  input:  z.object({ orderId: z.string(), amount: z.number() }),
  output: z.object({ chargeId: z.string() }),
});

export const OrderPlaced = defineContract({
  name: 'orders.placed',
  kind: 'event',                 // fire-and-forget, 0..N потребителей
  payload: z.object({ orderId: z.string(), total: z.number() }),
});
```

Три вида (это ровно то, что ты назвал «request-reply и fire-and-forget», но fire-and-forget честнее разбить надвое):

| `kind` | Семантика | Потребителей | NATS-маппинг |
|---|---|---|---|
| `request` | request-reply, синхронно-ish, **Fail-able**, таймаут | ровно 1 владелец | `nc.request/reply` |
| `command` | fire-and-forget, но обработать должен ровно один | 1 владелец (реплики делят) | queue-group / JetStream work-queue |
| `event` | fire-and-forget, broadcast-факт | 0..N | fan-out / JetStream stream |

Различать `command` и `event` важно из-за **горизонтального масштабирования**: N реплик фичи подписываются одной **queue group** → нагрузка делится, а не дублируется. Для NATS это буквально параметр подписки, и в этом весь кайф subject-адресации — добавил реплику, конфиг не трогал.

## 1. Как выглядит в коде

**Владелец реализует** — это обычный endpoint, привязанный к контракту:

```typescript
@Injectable([PaymentGateway])
class ChargeCardEndpoint implements Handler<typeof ChargeCard> {
  constructor(private gw: PaymentGateway) {}
  async handle(input, meta) {                      // input типизирован из контракта
    const chargeId = await this.gw.charge(input, meta.signal);  // signal уже есть
    return Ok({ chargeId });
  }
}
export const chargeCard = implement(ChargeCard, ChargeCardEndpoint);
```

**Потребитель инжектит порт** — токен, выведенный из контракта:

```typescript
@Injectable([ChargeCard.port])
class PlaceOrderEndpoint {
  constructor(private billing: Port<typeof ChargeCard>) {}
  async handle(input, meta) {
    const res = await this.billing.call({ orderId, amount }, meta);  // Promise<Ok|Fail>
    if (res.isFail) return res;      // отказ сети — это НОРМАЛЬНЫЙ Fail, не исключение
    // ...
  }
}
```

**Событие — эмиттер и консьюмер:**

```typescript
// publisher (в orders)
@Injectable([OrderPlaced.emitter])
class PlaceOrderEndpoint {
  constructor(private events: Emitter<typeof OrderPlaced>) {}
  async handle(...) { await this.events.emit({ orderId, total }); }
}

// consumer (в search) — тот же endpoint, только вид event
@Injectable([SearchIndex])
class OnOrderPlaced implements Consumer<typeof OrderPlaced> {
  async handle(evt) { await this.index.add(evt.orderId); }
}
export const onOrderPlaced = consume(OrderPlaced, OnOrderPlaced);
```

**Ключевое:** `.call()` и `.emit()` **всегда** `async` + `Ok/Fail`, даже когда billing co-located. Потому что завтра между ними NATS. Тип call-site у co-located и split **идентичен** — в этом вся суть. Именно то, что граница-порт синтаксически отличается от «внутри фичи» (обычный DI, обычные функции), и отделяет модульный монолит от распределённого монолита, который на самом деле не разбирается.

## 2. Как работает инфраструктурно

Ядро зависит только от одного интерфейса:

```typescript
interface IMessageTransport {
  request(subject, payload, opts): Promise<Encoded>;   // бэкает Port.call
  publish(subject, payload, opts): Promise<void>;      // бэкает Emitter.emit
  subscribe(subject, handler, opts): Subscription;     // бэкает inbound-endpoint
}
```

- `Port.call` → `bus.request(subject, input, { timeout, signal })` → декод ответа → **валидация против output-схемы** контракта. Schema-first end-to-end, включая провод.
- `Emitter.emit` → `bus.publish`.
- Inbound → `bus.subscribe(subject, { queue: consumerFeatureName }, handler)` — регистрируется через **существующую** машинерию эндпоинтов.
- `meta.signal` (уже приземлён в abort-signal change) прокидывается в `request` как таймаут/отмена. Приятный reuse.
- `Ok`/`Fail` — те же типы из pipeline. `Topic` (из streaming-идей) — это и есть in-proc шина для локального `emit`.

**Два бэкенда одного интерфейса:**
- `InProcessBus` — `Map<subject, handler>`, прямой вызов (zero-dep, дефолт, аналог `MockTransport` из `helpers.ts`). Локальный порт всё равно async и Fail-able, всё равно уважает `signal`.
- `NatsTransport` — `request`/`publish`/`subscribe` ложатся на core-глаголы NATS один-в-один. Durability (`event` с `durable: true`) → JetStream; core → at-most-once.

## 3. Как настраивается

Только в композиционном корне. Селектор (тот же, что выбирает фичи) получает `(выбранные фичи, messaging-транспорт)` и для **каждого контракта** решает:

- владелец **выбран** (co-located) → порт-токен биндится на `LocalPort` (прямой диспатч), inbound-endpoint регистрируется на in-proc шине;
- владелец **не выбран** → порт-токен биндится на `RemotePort` поверх messaging-транспорта; inbound здесь **не** регистрируется (он в другом процессе);
- владелец не выбран **и** messaging нет → **fail-fast на старте** с точным сообщением. Это capability negotiation из прошлого разговора, расширенная на порты.

Биндинг решается один раз на старте (там, где живёт конфиг) → на запросе потребитель зовёт **конкретный** клиент-константу, никакого routing-lookup в рантайме. Это ровно «жадная композиция константами», просто конфиг-driven вместо compile-time.

```typescript
assemble({
  features: [OrdersFeature, BillingFeature, SearchFeature],
  select:   process.env.FEATURES,                 // 'all' | 'orders,search'
  messaging: process.env.NATS_URL
    ? new NatsTransport({ servers: [process.env.NATS_URL] })
    : undefined,                                   // нет → всё должно быть co-located
  transports: { http: new HttpTransport({ port }) },
});
```

**Операционный выигрыш NATS именно здесь:** subject-адресация → тебе не нужен per-feature реестр адресов. Один `NATS_URL`, а маршрут (subject = имя контракта) выводится сам. С HTTP пришлось бы конфигурировать service discovery / базовые URL каждой фичи. Поэтому для «всё общение через шину» NATS — сильный выбор.

## Честные напряжения (это самое важное для «think about it»)

Порты легко спроектировать так, что получится distributed monolith. Три правила, которые, по-моему, надо принять жёстко (nestling же «even more opinionated»):

1. **Порты никогда не транзакционны — даже co-located.** Если разрешить локальному A→B делить транзакцию БД с B, код сломается при разнесении по процессам. Кросс-фичевая согласованность = только события + outbox/saga, никогда общая транзакция. Это и есть граница «splittable».

2. **Локальный порт обязан уметь падать.** Иначе команды напишут потребителей, которые не обрабатывают `Fail` (локально же всегда `Ok`), и split их убьёт. Тип возврата `Ok|Fail` спасает статически; можно ещё dev-флаг «хаос»: локальный порт иногда возвращает `Fail`, чтобы дисциплина не протухала.

3. **Outbox-проблема.** `emit` + запись в БД должны быть атомарны (событие уходит, только если транзакция закоммитилась). Даёт ли это фреймворк или оставляет приложению — открытый вопрос, но `kind: 'event'` + `durable` — то место, где он всплывёт.

И два вопроса поменьше, которые стоит решить до кода:

- **Где физически лежат контракты.** Если billing владеет `ChargeCard`, а orders его импортирует — orders цепляется за пакет billing. Вариант (a): контракт в публичном API фичи-владельца (`billing/contracts`), импортируется потребителями — сцепка с **контрактом**, не с реализацией, это ок. Вариант (b): общий пакет `contracts`. По вашей философии «ES-модули = система видимости» вариант (a) честнее: токен контракта надо экспортировать, чтобы импортировать, — видимость не соврёт.
- **Версионирование контрактов.** Split = продюсер и консьюмер деплоятся в разных версиях. `orders.placed.v1` в subject или schema-registry — отложить, но заложить.

## 1. `messaging` vs `transports` — да, ложная дихотомия

Ты прав, я развалил на два ведра то, что одно ведро. NATS — транспорт: он и **экспонирует** inbound-контракты (`ITransport`, как HTTP сегодня), и **зовёт** outbound (новый интерфейс). Правильная модель — не «транспорты и мессаджинг», а **один мешок транспортов с разными способностями**:

```typescript
interface InboundTransport  { endpoint(def): void; listen(); close(); }   // HTTP, CLI, NATS
interface OutboundTransport { request(subj, p, opts); publish(subj, p, opts); }  // NATS
// конкретный транспорт реализует то подмножество, что умеет
class NatsTransport implements InboundTransport, OutboundTransport { ... }
class HttpTransport implements InboundTransport { ... }
```

Конфиг становится один:

```typescript
assemble({
  features: [...],
  select,
  transports: { http: new HttpTransport({ port }), nats: new NatsTransport({ servers }) },
});
```

А биндинг портов при сборке спрашивает у транспортов их capability: «кто здесь `OutboundTransport`?» — на него и вешаются remote-порты. Это та же capability negotiation, просто теперь она про направление, а не про «http/нет».

## 2. NATS_URL — ты прав, тернарник был враньём

Я сам себе противоречил. Локальность определяется `select`, но сам транспорт — это инфраструктура, и он **не должен** быть условным от `select`. Правильная формулировка:

> **Конфиг транспортов статичен и одинаков для всех процессов одного развёртывания; между процессами меняется только `select`.**

Тонкость, которую я в прошлый раз замолчал, а ты нащупал: **процесс не может локально знать, кто позовёт его контракты снаружи.** Если я `--features=billing`, а orders крутится в другом поде — billing обязан экспонировать `billing.charge` на NATS, хотя его собственный `select` про orders ничего не знает. Значит правило:

- **inbound:** фича подписывает свои контракты на каждый сконфигурированный `OutboundTransport` — **всегда**, когда шина есть (дёшево, идемпотентно);
- **outbound:** порт к контракту, чей владелец не co-located, биндится на шину.

Отсюда следствия, которые снимают твой вопрос:
- **Распределённое развёртывание** → NATS сконфигурирован везде, одинаково. Никакого тернарника.
- **Локальная разработка** (`select=all`, NATS нет) работает, потому что ни один порт не remote → шина не нужна.
- **Fail-fast** срабатывает ровно в одном случае: выбрал подмножество **и** потребляешь контракт невыбранной фичи **и** шины нет.

А разница между «локально» и «прод» — это **разница в конфиге, не в коде**. Один и тот же бинарник: dev-конфиг даёт `{select: all, nats: none}`, prod-конфиг billing-пода даёт `{select: billing, nats: ...}`. Что напрямую выводит на пункт 4.

## 3. Диспатчинг — да, и это делает картину лучше

Согласен целиком, и «всегда через NATS» не тупо — это модель «everything is a message» (OTP/акторы). Ошибка была в моей жёсткой зашивке «local owner → всегда in-proc». Правильно: **порт всегда говорит с *шиной*, а не с фиксированным клиентом**, а какая шина — это **политика, выбранная при сборке**:

```typescript
type DispatchPolicy =
  | 'local-first'    // co-located → in-proc; иначе → сеть   (дефолт)
  | 'always-remote'  // всегда через шину, даже co-located    (uniform, «всё — сообщение»)
  | 'balanced';      // размазать local + remote-реплики      (client-side spill)
```

Три реализации `IMessageBus` под одним интерфейсом:
- **in-proc-direct** — прямой вызов (быстро, zero-dep, дефолт для co-located);
- **NATS** — сеть;
- **in-proc-simulated** — async + сериализация + инъекция отказов, **без реального NATS**. Вот это ключевое: даёт message-семантику (всё async, всё Fail-able) в тестах и dev, не поднимая NATS. То есть «всегда через шину» безопасно, потому что «шина» ≠ «NATS».

Про совмещение с принципом «жадная композиция константами»: `local-first`/`always-remote` резолвятся в **одну** константу-клиент на старте — рантайм-lookup ноль. Только `balanced` добавляет рантайм-диспатч — и ты в него **явно** оптишься. Принцип цел: политика видна в композиции, дефолт статичен.

Про балансировку отдельно: **NATS queue-groups дают server-side LB бесплатно** — публикуешь в subject, шина раздаёт репликам в очереди. Client-side балансировка нужна только для одного кейса — «предпочитай локальный хендлер, перелив на кластер» — это и есть `balanced`. Не строй клиентский LB как отдельную махину: в NATS-модели это на 90% server-side. Главное — **смена политики = смена конфига, call-site `port.call()` не меняется вообще.**

## 4. Конфигурация — тут надо разложить аккуратно

Полностью на твоей стороне: `process.env` по коду — это шум без валидации. Принцип:

> **`process.env` (и файлы, и Vault) трогает ровно один пакет — config. Везде остальное инжектит типизированные срезы конфига (zod-схема). Остальному коду — `eslint no-process-env`.**

Дальше три вещи, которые надо разделить, потому что ты их пока валишь в кучу (и правильно чувствуешь, что куча).

### 4a. Три тира конфига по изменяемости

| Тир | Что | Когда читается | Меняется |
|---|---|---|---|
| **bootstrap** (структурный) | `select`, транспорты, connection-строки | фаза 0, до контейнера | только рестарт |
| **static operational** | бизнес-тюнинг (retry, лимиты) | при build, инжектится провайдером | только рестарт (безопасный дефолт) |
| **live operational** (opt-in) | явно перезагружаемые значения | инжектится `ConfigRef<T>` | watch/reload |

Смысл разделения: **структурный конфиг нельзя горячо подменить** — нельзя на лету поменять, какие фичи в процессе, или DB-URL, на котором уже висит пул. Watch/reload физически применим только к operational-тюнингу. Это отвечает на твой вопрос «делаем watch на Vault?» — да, но **только для явно помеченных значений тира 3**, а не глобально.

### 4b. Конфиг — это фаза 0 жизненного цикла, до контейнера

Твой вопрос «старт → сборка контейнера → чтение конфига, что дальше?» содержит инверсию: **конфиг читается ДО сборки**, потому что от него зависит сама форма контейнера (`select`, набор транспортов). Порядок:

```
0. bootstrap:  загрузить источники (env/file/vault) → валидировать структурный конфиг
               → FAIL-FAST если невалиден
               ↓ (даёт: select, transports, connection-конфиг)
1. assemble:   build контейнера (срезы конфига зарегистрированы как провайдеры)
   ↓
2. init:       @OnInit — пулы, соединения
   ↓
3. listen:     транспорты подписываются/слушают
   ↓
4. run
```

Фаза 0 — self-contained, без DI (сырой HTTP к Vault / чтение файла — можно, контейнера ещё нет). Прочитанный конфиг потом **регистрируется провайдером** в контейнер (фаза 1), чтобы сервисы инжектили типизированные срезы. Читается один раз, переиспользуется.

### 4c. Ответы на «не стартуем / ждём / watch»

- **Невалидный структурный конфиг → fail-fast, не стартуем.** Никогда не поднимаемся полу-сконфигурированными. Перезапуск — задача оркестратора (k8s), не in-process ожидания. Исключение: если *источник* моргает на старте (Vault недоступен 2 секунды) — bounded retry-with-timeout в фазе 0, потом либо старт, либо смерть. Это «ждём источник, потом стартуем-или-умираем», а НЕ «стартуем и ждём».
- **«Стартуем и ждём конфиг»** — нет. Сервис, который поднялся без конфига, в неопределённом состоянии (он healthy? он принимает трафик?). Здоровее не подниматься.
- **Watch/reload** — opt-in на значение, тир 3. Значение инжектится не как `T`, а как `ConfigRef<T>` (`.current` + сигнал изменения — переиспользуем `Topic`/`AbortSignal`). Кто хочет живые обновления — подписывается; кто прочитал `.current` — получил снапшот. И честное ограничение: reload значения, требующего пере-wiring подграфа (новый лимит → пересоздать limiter), — это уже **re-init подграфа**, а это отложенный `createScope` из ideas.md. Так что v1 live-config = только значения, применяемые без пере-wiring; всё остальное = рестарт.

### 4d. Бонус — конфиг завязан на `select`

Каждая фича объявляет свою config-схему (`makeConfigSchema`). `assemble` собирает схемы **только выбранных** фич + core, валидирует источники против их объединения. `--features=billing` → отсутствие `ORDERS_*` не ошибка. Ergonomics-выигрыш и естественная связка конфига с выбором фич.

## Про строки подключения — ты прав, я был неправ

Хороший вопрос, он вскрыл, что я **склеил две ортогональные оси** и назвал результат «структурным»:

- **Ось A — определяет ли конфиг *форму графа* контейнера** (какие узлы/транспорты вообще существуют).
- **Ось B — насколько дорого подменить значение на живую** (re-init стоимость).

Строку подключения я запихнул в «структурный», потому что она попадает под ось B (пул на неё завязан → менять больно). Но по оси A она **не структурная вообще**: узел-провайдер БД существует в графе независимо от *значения* URL. Форма графа при `DB_URL=X` и `DB_URL=Y` идентична. URL — это просто **параметр узла, который и так есть**, а не то, что порождает или убирает узлы.

То есть «нужен рестарт, чтобы поменять DB_URL» — это следствие того, что **держатель значения (пул) дорого пере-инициализировать**, а не того, что значение «структурное». Если бы пул умел менять URL на живую — строка была бы спокойно reloadable. Свойство перезагружаемости живёт **на потребляющем узле, а не на конфиге**.

Исправленная модель — две категории вместо трёх тиров:

| | Что | Кто параметризуется | Смена значения |
|---|---|---|---|
| **assembly-config** (真 структурный) | `select`, набор транспортов, dispatch-policy | **билдер** (форма графа) | ре-assemble = рестарт |
| **provider-config** (всё остальное) | строки подключения, креды, таймауты, лимиты, флаги | **узлы графа** | зависит от re-init стоимости *узла* |

Assembly-config — маленькое закрытое множество: только то, что нужно знать, **чтобы вообще собрать граф**. Всё прочее, включая connection strings, — обычные provider-значения: грузятся в фазе 0, валидируются против схем выбранных фич, регистрируются типизированными провайдерами. А «рестарт / snapshot / live-ref» — это уже вопрос к потребляющему узлу, не к тиру конфига:

- узел захватил значение в конструкторе (пул, соединение) → смена = re-init узла (в пределе — процесса);
- узел читает `.current` при каждом использовании (таймаут, флаг) → смена бесплатна.

И усиливающее следствие, которое как раз в духе nestling: **если строка подключения начинает влиять на форму графа — это запах.** Условие вида «есть `REDIS_URL` → регистрируем RedisCache, иначе InMemoryCache» — это решение, которое должно подниматься на уровень `select`/фич (явно), а не выводиться из наличия env-строки. В правильной модели connection string формы графа не касается никогда — и поэтому она не структурная по определению.

Так что спасибо — таксономию правлю: **структурно только то, что меняет, какие узлы существуют (`select` + транспорты + policy). Connection strings — рядовой provider-config.**

## Почему «набор транспортов» не должен быть отдельным конфигом

Потому что **транспорт — это обычный синглтон с зависимостями и жизненным циклом**, ровно то, чем контейнер и управляет. Отдельный мешок `transports: Record<string, ITransport>` — это спецслучай, дублирующий то, что контейнер уже умеет:

- **зависимости** — NATS-транспорту нужен его connection-конфиг (тот самый provider-config из прошлого разговора!), HTTP — логгер, TLS-сертификаты, метрики. Если транспорт инстанцируется руками снаружи, ты не можешь их инжектить — тянешь вручную. Если провайдер — `@Injectable([NatsConfig, ILogger])` и всё;
- **lifecycle** — `listen`/`close` это и есть `@OnInit`/`@OnDestroy`-фаза, топологически упорядоченная. Сейчас `App` руками гоняет `Promise.all(transports.listen())` — переизобретает то, что контейнер делает по графу.

И главное следствие для твоего первого вопроса: **если транспорты — провайдеры в модулях, то «какие транспорты существуют» выводится из `select`**, а не задаётся отдельной ручкой. Фича, которой нужен HTTP, импортирует infra-модуль с HTTP-транспортом; не выбрал фичу — транспорта нет. То есть я в прошлый раз **пересчитал** assembly-config: «набор транспортов» — не независимая ось, он падает из `select`. После этой правки структурным остаётся по сути только `select`.

Бонусом чинится ещё пара вещей:
- endpoint ссылается на транспорт **токеном, а не строкой** (`@Endpoint({ transport: NatsTransport })` вместо `'nats'`) — типобезопасно, в духе «инжект по значению-токену»;
- **capability negotiation исчезает как отдельная механика**: HTTP-endpoint, которому нужен `HttpTransport`, а того нет в графе → падение на регистрации, ровно тем же fail-fast, что уже есть в `#registerEndpoints`. Не надо `needs: ['http']` — это просто разрешение зависимости.

## Единственная тонкость — которую твой `App` уже почти держит

Есть один порядок, который нельзя нарушить: транспорт не должен начать слушать **до** того, как на него навесили endpoints. И тут приятно — `App` уже разведён на нужные фазы: `#init` (build → `container.init()` → `#registerEndpoints`) → `#listen`. То есть регистрация уже сидит между init и listen. Меняется только источник транспортов: **не из мешка в конструкторе, а из контейнера** (дискаверятся из дерева модулей — симметрично фиксу дискавери эндпоинтов).

Дисциплина, которую это выявляет и которую надо зафиксировать явно:

- **`@OnInit` = захватить ресурс** (открыть соединение с NATS, поднять сокет);
- **регистрация эндпоинтов** — между;
- **`listen` = уйти в эфир** (начать принимать), драйвится `App`, а НЕ `@OnInit`.

Если склеить «connect» и «listen» в один `@OnInit` — транспорт начнёт слушать с непривязанными роутами. Поэтому `listen`/`close` остаются App-driven поверх контейнера, а не прячутся в lifecycle-хук провайдера.

## Что в итоге остаётся снаружи контейнера

Схлопывается почти всё:

| Было внешним | Стало |
|---|---|
| набор транспортов | провайдеры, выводятся из `select` |
| port-биндинг (local/remote) | вычисляется из графа: есть локальный хендлер контракта? → local; нет → remote-клиент поверх outbound-транспорта-провайдера |

Неснимаемо-внешним остаётся ровно два: **`select`** (он решает, что кладём в билдер — нельзя решить это внутри контейнера, который ещё не собран) и **сырая загрузка конфига в фазе 0** (прочитать env/файл/Vault, чтобы накормить config-провайдеры и узнать `select`). Значения — провайдеры; внешний только загрузчик.

Так что да — транспорты классами в контейнер. Это убирает спецслучай, а не добавляет.

## Транспорт не владеет `listen()`

Убираем nullary-метод. Уйти в эфир можно только приняв **готовый диспетчер** (таблицу `pattern → handler`), а он не существует до фазы регистрации эндпоинтов:

```typescript
interface InboundTransport {
  // никакого listen() без аргументов.
  // единственный вход в эфир — принять диспетчер, которого на @OnInit ещё нет.
  serve(dispatch: Dispatch, signal: AbortSignal): Promise<void>;
}
type Dispatch = (raw: RawRequest) => Promise<RawResponse>;
```

Теперь автор **не может** уйти в эфир на `@OnInit`, потому что уходить некуда: `dispatch` ему никто ещё не дал, а фреймворк отдаёт его только после wiring. Ключевой сдвиг ответственности: **транспорт — это переводчик провода (`wire ↔ message`), а не владелец роутинга.** Даже если автор в обход построит свой `http.Server` и вызовет `.listen()` в `@OnInit` — ему **нечего туда маршрутизировать**: таблица роутов принадлежит фреймворку, выразить «обслужи endpoint X» без `dispatch` невозможно. Ранний listen не просто неудобен — он бесполезен. Ты сделал неправильное трудным, а правильное — единственным поддержанным путём.

## Это и есть ответ на прошлый открытый вопрос про `@OnStart`

`dispatch` — это **фазовый ресурс**: на `@OnInit` он не резолвится (эндпоинтов ещё нет), на `@OnStart` — резолвится. Поэтому смысл заводить `@OnStart` в контейнере ровно один: сделать «wiring происходит между `@OnInit` и `@OnStart`» **гарантией графа**, а не порядком в `App.run`. Захват ресурсов (connect NATS, DNS) — `@OnInit`; уход в эфир — `@OnStart`, где `dispatch` уже есть; между ними — регистрация. Смешать нельзя, потому что на `@OnInit` нужного входа просто не существует.

## Если хочешь совсем «невозможно» (level-3)

Инвертировать владение акцептором: сокет держит **фреймворк**, а HTTP-транспорт — это чистая функция `(RawRequest) => Promise<RawResponse>`, без всякого `listen` вообще. Тогда абузить нечего физически. Цена — не универсально: для pub/sub-транспортов (NATS) «акцептор» это подписка, которой владеет сам транспорт, туда инверсия ложится хуже.

Поэтому лестница enforcement такая:

| Уровень | Механизм | Абузится? |
|---|---|---|
| конвенция | «положи listen в start-фазу» | да (то, что я сказал в прошлый раз) |
| **dispatch как обязательный аргумент** | go-live требует ресурс, доступный только на `@OnStart` | нет разумного пути |
| инверсия акцептора | фреймворк владеет сокетом, транспорт = `(req)=>res` | нет вообще |

Я бы взял **средний как дефолт** — он структурный и одинаково ложится на HTTP и NATS, — а инверсию оставил как опцию для тех транспортов, где акцептор естественно отдаётся фреймворку. То есть `listen()` из публичного контракта транспорта **убираем совсем**; остаётся `serve(dispatch, signal)`.

## Что rsdk делает (чтобы говорить об одном)

- **Секции конфига — классы** (`Config` + `@ConfigSection`/`@Property`). Каждый модуль объявляет свою секцию со своими ключами.
- **Мерж — на уровне источников, не объектов.** `ConfigContext` грузит `.env → process.env → динамические source'ы` в порядке приоритета в один плоский слой `Vars`. Каждая секция **проецирует** свой срез из этого общего слоя. «Мерж» — это общий пул источников + per-section-проекция, а не слияние конфиг-объектов.
- **Инжектятся через DI.** `createConfigProvider(ctor)` — **factory-provider**, резолвящий секцию из `ConfigContext`. Сервис инжектит класс секции, получает заполненный инстанс.
- **Автодискавери.** `ConfigMetadataExtractor` смотрит deps конструкторов, находит секции (`Config.isConfigSection`), сам регистрирует провайдер. `forFeature` задепрекейчен: «configs are loaded automatically».
- **Reload — события, не хук.** `ReloadEvents` + `section.tryUpdate(vars)` на `'merge'`: инстанс секции стабилен, поля обновляются на месте.
- **Глобальный `forRoot` = только `appName` (префикс), `sources`, `appNameStrategy`.** Бутстрап + нейминг. **Никаких бизнес-значений там нет.**

## Как это ложится на nestling (и почему проще, чем в rsdk)

Прямой перенос, но nestling делает это **чище**, потому что контейнер **жадный**:

- **Секция конфига = обычный провайдер.** Инжектится по токену. Никакого factory-provider-танца «инстансов ещё нет, резолвим лениво» — это **костыль под ленивость Nest**. В жадном контейнере секция инстанцируется на `build()` как любой узел.
- **Мерж** = слияние источников в фазе 0 (defaults < file < env < динамические), каждая секция проецирует+валидирует свой срез. Неймспейс на фичу (`ORDERS_`, `BILLING_`) — как `appName`-префикс rsdk, только per-feature.
- **Feature-scoped бесплатно.** `select` → в графе только секции выбранных фич → валидируются только они. `--features=billing` не требует `ORDERS_*`. Конфиг связан с фичами через тот же `select`.
- **Жадная валидация бесплатно.** Контейнер строит всё → все секции инстанцируются на `build()` → все провалидированы разом → fail-fast. rsdk ради этого форсит eager-extraction standalone-свойств в конструкторе `ConfigContext` — потому что Nest ленив. Тебе это не нужно.

## `OnConfiguration` — не нужен, и это строго, а не «бред по ощущению»

Твоё «чем от OnInit отличается» — правильный нюх. Разложим, что бы хук вообще делал, и куда каждый смысл девается:

| Что мог бы значить «OnConfiguration» | Куда это на самом деле уходит |
|---|---|
| загрузить источники | **фаза 0**, до контейнера — это вообще не хук |
| спроецировать источники → секцию | **обычное построение провайдера** на `build()` |
| «конфиг готов, отреагируй» | ты просто **зависишь** от секции → контейнер строит тебя после неё |
| захватить ресурс по конфигу (пул по URL) | **`@OnInit` потребителя** (пул инжектит `DbConfig`) |
| конфиг перезагрузился | **событие reload**, не стартовый хук |

Ни одного смысла, который не покрыт связкой «фаза 0 + порядок зависимостей + `@OnInit` потребителя + reload-события».

И самый острый аргумент: **хук был бы грубее, чем зависимость.** Хук — это барьер «весь конфиг → весь init». А зависимость даёт точную топологию: `DbConfig` готов ровно перед `DbPool`, который его просит, и ни секундой раньше/позже. Объявить конфиг зависимостью — **строго лучше**, чем хук, потому что граф секвенирует его точнее. Отличие от `@OnInit` фундаментальное: `@OnInit` — это **сайд-эффектная выдача ресурса** (async, может упасть на I/O, топологически упорядочена). Чтение конфига — **чистая проекция** из уже загруженного слоя, происходит в конструкции, без сайд-эффектов. Конфиг — это не *фаза*, которую хукаешь, а *зависимость*, которую объявляешь. Так что да — `OnConfiguration` избыточен.

(Единственный реальный дизайн-вопрос вокруг этого: **async-источники (Vault)**. Либо грузим все источники в фазе 0 до `build()` — тогда секции остаются синхронными провайдерами и валидация eager (моя рекомендация); либо разрешаем async-factory-секции на `build()` — как rsdk. Я за первое: eager-валидация и fail-fast важнее.)

## Что легитимно в глобальном конфиге кроме features — ты прав, почти ничего

Ты дожал мою «assembly-config» до правды. Критерий «что обязано быть до контейнера»: **только то, что нельзя выразить провайдером без циклической зависимости** — то есть то, что решает, какие провайдеры вообще существуют.

Это ровно два:

1. **`select`** — какие фичи/модули идут в билдер. Провайдером быть не может: билдер не может собрать себя на основе провайдера, которого ещё нет.
2. **Source-bootstrap** — как/откуда грузить *остальной* конфиг (адрес Vault, префикс, strategy). Это «конфиг для загрузки конфига», берётся из примордиальных env/file. Ровно `appName`/`sources`/`appNameStrategy` из `forRoot` rsdk.

**Всё остальное — provider-config в секциях модулей.** DB URL, NATS servers, HTTP port — да, ты прав в третий раз: это обычные параметры, они инжектятся в свои узлы:

- HTTP-порт → секция `HttpConfig`, инжектится в HTTP-транспорт-провайдер (то есть в корне даже `http({ port: 3000 })` с литералом уходит — порт приходит из конфига);
- NATS servers → секция `NatsConfig`, инжектится в NATS-транспорт;
- **dispatch-policy** → тоже provider-config, инжектится в port-client, который на `build()` фиксирует стратегию (local/remote — константа на процесс; per-call только `balanced`). Не assemble-time.

Присутствие самого NATS-транспорта, если помнишь, выводится из `select` (нужен ли выбранным фичам remote-порт), а не задаётся флагом. Так что **`select` — единственный неснимаемый вход**, плюс примордиальный указатель «откуда грузить конфиг». Глобальный конфиг — не помойка для URL'ов; rsdk это прямо подтверждает своим `forRoot`.

## Неявные провайдеры и видимость

Да: `app`/infra-модули «подсовывают» в граф провайдеры, которых пользователь не писал. Полный список:

| Провайдер | Видимость | Как юзер до него дотягивается |
|---|---|---|
| `ConfigSource` (слитый слой источников) | **приватный** | никак — только через секции конфига |
| транспорты (`http`/`nats`) | **приватный** | никак напрямую — через `Port`/`Emitter` |
| bus / port-client (на контракт) | внутренности приватные, `Port<C>`/`Emitter<C>` — **публичные** | инжектит `Port<C>`/`Emitter<C>` |
| logger | **публичный** (контрпример) | инжектит напрямую — так и задумано |

Механизм видимости — **нативный nestling: не экспортируем токен** (ideas.md, решение 3: «не экспортировал токен — снаружи запросить физически невозможно»). Никакого рантайм-ACL «только в конфиги». `ConfigSource` — токен внутри `@nestling/app`, наружу не реэкспортится → пользовательский сервис не может его инжектить, потому что не может импортировать. Транспорты — так же: `http()`/`nats()` возвращают модуль, но токен транспорта приватный; до провода добираешься только через `Port`/`Emitter`, а те внутри держат приватный транспорт.

И вот ключевой поворот, который **работает в твою пользу против классовых конфигов**: если конфиг — это `makeConfig(schema)` (данные), то провайдер конфига **генерирует фреймворк**. Значит `ConfigSource` инжектит фреймворк в свой сгенерированный провайдер, а **пользователь не пишет проводку и потому вообще не нуждается в токене источника** — источник не протекает в user-space ни на грамм. В rsdk-стиле конфиг-класс пишет пользователь, и туда приходится прокидывать `ConfigContext` — концепт источника подтекает. Декларативный `makeConfig` **улучшает инкапсуляцию**, а не только сокращает код. Твоё «только в конфиги» становится сильнее: «только во фреймворк-сгенерированные провайдеры, в user-code — никогда».

## Стилистические варианты `makeConfig`

**Вариант 1 — zod + префикс-конвенция (компактно, детерминированная «магия»)**

```typescript
export const OrdersConfig = makeConfig('orders', z.object({
  maxItems:    z.coerce.number().default(100),   // ← ORDERS_MAX_ITEMS
  databaseUrl: fromEnv('DATABASE_URL', z.url()), // escape: не префиксованный общий ключ

```
Поле → `PREFIX_SCREAMING_SNAKE` по конвенции; `fromEnv` — люк для общих ключей. Плюс: минимум букв, фича владеет своим неймспейсом. Минус: неявный маппинг (хоть и детерминированный).

**Вариант 2 — zod + явная карта ключей (никакой магии)**

```typescript
export const OrdersConfig = makeConfig({
  schema: z.object({ maxItems: z.coerce.number().default(100), databaseUrl: z.url() }),
  env:    { maxItems: 'ORDERS_MAX_ITEMS', databaseUrl: 'DATABASE_URL' },
});
```
Полный zod + явное соответствие. Плюс: всё видно, переиспользует zod целиком. Минус: дублирование имён полей, многословнее.

**Вариант 3 — field-хелперы `env('KEY')` (явно, самодостаточно) — мой фаворит**

```typescript
export const OrdersConfig = makeConfig({
  maxItems:    env('ORDERS_MAX_ITEMS').number().default(100),
  databaseUrl: env('DATABASE_URL').url(),
  // сложное поле — люк в zod:
  cors:        env('ORDERS_CORS').as(z.array(z.string())),
});
```
`env(key)` — билдер поля, `.number()/.url()/.default()` дают типизированный спек, `makeConfig` выводит выходной тип. Плюс: компактно **и** явно про ключ, «читается как схема», `.as(z…)` подключает zod там, где он нужен. Минус: маленький параллельный API к zod для базовых коэрсеров (но легко ложится на zod внутри).

**Вариант 4 — source-accessor функция (максимально явно, source-scoping буквальный)**

```typescript
export const OrdersConfig = makeConfig((cfg) => ({
  maxItems:    cfg.number('ORDERS_MAX_ITEMS', { default: 100 }),
  databaseUrl: cfg.url('DATABASE_URL'),
}));
```
Фреймворк зовёт функцию с типизированным `cfg` (read-only срез источника, валидация на чтении). Плюс: «источник только в конфигах» становится буквальным — `cfg` вручается лишь билдерам конфига; максимум явности. Минус: нет отдельного объекта-схемы → нечего интроспектировать (дамп конфига в доки, `--print-config`).

**Инжект и тип — одинаково для всех:**

```typescript
// класс-стиль
@Injectable([OrdersConfig])
class OrdersService { constructor(private cfg: Config<typeof OrdersConfig>) {} }

// функциональный
factoryProvider(OrdersService, makeOrdersService, [OrdersConfig]);
```

**Reload** — не отдельный стиль, а флаг: `makeConfig.reloadable(...)` → сгенерированный провайдер подписывается на `'merge'` источника, инстанс стабилен, поля живые; `cfg.onChange(signal, cb)` для реактивных. Снапшот-потребитель просто читает поля один раз.

## Kernel / user space — и почему это решает вопрос об источниках

Формализую (и добавлю в доку): kernel space — привилегированное, чем владеет фреймворк, токены не экспортируются (`ConfigSource`, транспорты, bus/port-client, машинерия графа). User space — то, что пишешь ты (сервисы, endpoints, контракты, конфиг-как-данные). Границу пересекаешь только через публичные абстракции — «системные вызовы»: инжект `Config<X>`, `Port.call`/`Emitter.emit`, возврат из endpoint. Enforcement — не рантайм-ACL, а видимость ES-модулей.

Теперь суть: **«откуда берётся значение» — это про environment, а environment — kernel-space забота.** Значит вариант, где конфиг знает `env('KEY')`, **протаскивает kernel-концерн в user space**. Твой дискомфорт точный. Провенанс-слепой конфиг (читает ключ из результата мержа, не зная источника) — это как программа читает `fd`, не зная физического устройства за ним. Аналогия не украшение — она диктует ответ: **мержим в общий `Vars`, конфиги потребляют результат (подход B, как rsdk).**

## A (source-per-field) vs B (merge → Vars → project)

| | **B: merge → Vars** (rsdk) | **A: `env()`/`vault()` в поле** |
|---|---|---|
| Конфиг знает источник | нет — только ключ + тип | да — верб источника в поле |
| Перенести env → vault | правка источников, конфиг не трогаем | правка **конфига** |
| Precedence | единый порядок для всех ключей | per-field, семантика мутная |
| Reload | единый: одно `'merge'` → пере-проекция | per-source, сложнее |
| Per-field «только из vault» | через source-policy (kernel) | прямо в поле |
| Namespace ключей | общий → нужны префиксы | давления меньше |
| Kernel/user граница | **чистая** (провенанс в kernel) | **протекает** в user-space |

**Чего не можешь в B:** сказать в самом поле «это значение только из vault, никогда из файла» — провенанс сплющен. Но это **не потеря**: такое ограничение — это *политика источника*, и её место в kernel (source может быть scoped на набор ключей / ключ помечен secret). Ты восстанавливаешь единственное реальное преимущество A там, где ему и место, — в kernel, а не в конфиге.

**Чего не можешь в A:** переносить значения между источниками, не редактируя конфиги; дать вменяемую единую precedence; сделать простой единый reload.

**Вывод — B.** И тут приятно: **вариант 1 уже и есть B** (префикс → *ключ*, не источник; какой source его накормит — решает мерж). Вариант 3 становится B заменой `env('KEY')` → `from('KEY')` (agnostic-ссылка на ключ). Вербы `env`/`file`/`vault` живут только в root-объявлении источников. Так что тебе не нужно выбирать между «1 или 3» и «A или B» — берёшь B, а 1 vs 3 остаётся чистой синтаксикой (префикс-конвенция против явного `from('KEY')`).

## Reloadable — как реально используется

Источник с наблюдением (`reloadableFile`, `vault({ watch: true })`) на изменение пере-сливает `Vars` и пере-проецирует reloadable-секции; инстанс стабилен, поля обновляются на месте. Два способа потребления:

```typescript
export const Runtime = makeConfig.reloadable('runtime', z.object({
  logLevel: z.enum(['debug', 'info', 'warn', 'error']).default('info'),
  rps:      z.coerce.number().default(100),
}));

// (а) read-latest — читаем при каждом использовании, подписка не нужна
@Injectable([Runtime])
class Logger {
  constructor(private cfg: Config<typeof Runtime>) {}
  debug(m: string) { if (gte(this.cfg.logLevel, 'debug')) this.write(m); }  // всегда актуальный уровень
}

// (б) react — надо перестроить ресурс при изменении
@Injectable([Runtime])
class RateLimiter {
  #bucket = new TokenBucket(100);
  constructor(private cfg: Config<typeof Runtime>) {}
  @OnStart() start(signal: AbortSignal) {
    this.#bucket.refill(this.cfg.rps);
    this.cfg.onChange(signal, (next) => this.#bucket.refill(next.rps));  // отписка по signal сервиса
  }
}

// корень: reloadable-источник — то, что вообще включает reload
await assemble({ sources: [env(), reloadableFile('runtime.yaml')], /* ... */ }).run();
```

Реальные кейсы: **уровень логирования** (покрутить verbosity в проде без рестарта), **rate-limit/таймауты** (подстроить под нагрузкой во время инцидента), **операционные флаги** («включить новый алгоритм ценообразования» — не путать со структурным `select`, тот требует рестарта).

Две асимметрии со стартом, важные на практике:
- **старт: невалидный конфиг → die (fail-fast); reload: невалидный → keep last-good + warn.** Живой процесс не падает из-за плохого горячего значения.
- **вступит ли изменение в силу — ответственность потребителя.** read-latest и `onChange` — да; значение, захваченное один раз в конструкторе (URL пула) — нет. Поэтому reloadable — opt-in и только для значений, которые кто-то честно перечитывает или на которые реагирует.

## Почему это ложится чисто, а не создаёт вторую систему

Ключевое наблюдение: зависимости конфиг-источников образуют **DAG, укоренённый в примордиальном env**. А значит это не отдельная фаза бутстрапа — это просто **самый ранний топологический слой того же контейнера**:

```
EnvSource (примордиальный, без deps: process.env + .env по фикс-пути)
   ↓
FileSource   (dep: FileConfig  ← CONFIG_FILE из env)     производные источники,
VaultSource  (dep: VaultConfig ← VAULT_ADDR/TOKEN из env)  сконфигурированные из env
   ↓
ConfigSource (merged Vars: агрегирует все источники по precedence)
   ↓
OrdersConfig … (user-секции проецируют по ключу)
   ↓
всё остальное
```

Жадный контейнер с топосортом **уже секвенирует это правильно** — тот же аргумент, что был против `OnConfiguration`-хука: конфиг — это зависимость, не фаза. Источники-как-провайдеры просто протягивают ту же логику до самого низа. И бонус: **запрет циклов в nestling защищает бутстрап конфига** — «vault-токен из файла, а путь файла из vault» упадёт cycle-ошибкой на build, а не молча зациклится.

Что это даёт:
- **путь файла / адрес vault — из `.env`**, а не литералы в composition root (твоя исходная боль);
- **lifecycle бесплатно** — `VaultSource.@OnInit` (fetch + token-renew loop), `@OnDestroy` (стоп), watching-file `@OnDestroy` (закрыть watcher);
- **не нужен = не импортирован** — `@nestling/config.vault` это модуль; нет в композиции → источника нет;
- `sources: [...]` bag исчезает — источники это просто модули, которые ты импортируешь. `EnvSource` присутствует всегда (примордиальный).

Единственное пред-сборочное чтение остаётся `select` (из примордиального env — нужно до контейнера, чтобы знать форму графа). Async-источники (vault) = async-factory-провайдеры, awaited в build, fail-fast сохраняется.

Набросок:

```typescript
// @nestling/config.file — производный источник как провайдер
export const FileConfig = makeConfig('config', z.object({
  path: from('CONFIG_FILE').default('config.yaml'),   // путь — из env/.env
}));
@Injectable([FileConfig])
class FileSource implements ConfigSourceProvider {
  constructor(private cfg: Config<typeof FileConfig>) {}
  @OnInit() load() { this.data = parseYaml(readFile(this.cfg.path)); }
  get(key: string) { return this.data[key]; }
  readonly priority = 10;                               // precedence — явная
}

// composition root — bag sources больше нет, источники это модули
await assemble({
  modules: [FileSourceModule, VaultSourceModule, OrdersModule],
  select: bootEnv('FEATURES'),   // единственное пред-сборочное чтение
  transports: [http()],
}).run();
```

Источники встают в kernel-space рядом с транспортами: pluggable-kernel-провайдеры, композируются модулями, юзер их не инжектит (юзер инжектит *секции*, не источники).

## Твоё сомнение про документацию — снимается, и docs даже становятся полнее

Разведём два разных «что нужно конфигурировать»:

1. **Что приложение потребляет** — это declarative *секции* (`makeConfig(schema)`). Схема — это **данные**, регистрируется в метадата-реестре на import (ровно как rsdk-шный `ConfigMetadataProvider`). Выгрузка доки читает эти схемы — **без значений, без live-vault, без запуска логики**. Источники-как-провайдеры на это никак не влияют: они меняют *откуда берётся значение*, а не *какие ключи объявлены*.

2. **Что нужно самим источникам** (`VAULT_ADDR`, `CONFIG_FILE`) — а это теперь **тоже declarative секция** (`FileConfig`, `VaultConfig`), которую источник-провайдер инжектит. Значит она попадает в тот же реестр и в ту же выгрузку.

Итог — доки становятся **полнее**, а не беднее:

```
$ nestling config:doc --features=all       # грузит модули, читает СХЕМЫ, не значения
OrdersConfig  ORDERS_MAX_ITEMS : number = 100
              DATABASE_URL     : url (required)
FileConfig    CONFIG_FILE      : string = "config.yaml"
VaultConfig   VAULT_ADDR       : url (required)
              VAULT_TOKEN       : string (required)
```

Раньше `sources: [vault({ addr: '...' })]` прятал конфиг источника литералом в корне — теперь он декларирован и виден. То, что **теряется** — чисто-статический (AST, без import) обход. Но он никому не нужен: import-time-реестр схем робастнее и это то, что делают и rsdk, и Nest.

Единственное условие, которое это накладывает (и оно lint-able): **источник обязан объявлять свой конфиг секцией, а не читать ключи ad-hoc.** Та же дисциплина `no-process-env`, что и для user-кода — если `VaultSource` дёрнет `env.get('VAULT_NS')` в обход `VaultConfig`, этот ключ выпадет из доки. Правило линтера закрывает.

## Что это поднимает решить

- **precedence должна стать явной** — раньше её задавал порядок в `sources: [...]`, теперь источники дискаверятся из модулей, значит нужен `priority` на источнике (или ранжирующий агрегатор). Мелочь, но решить надо.
- **`select` — по-прежнему единственное пред-сборочное чтение** из примордиального env; всё остальное уходит в граф.
- **два уровня «нужен конфиг»**: schema-level (статично, из секций, для доки и линта) vs value-level (рантайм, из источников, для fail-fast). Полезно держать их раздельно в реализации.

## Что делает rsdk с grpc-клиентами

Когда объявляешь клиент к серверу (`UsersService`), `ModuleGenerator.createClientModuleDefinition`:

1. выводит env-ключ из имени: `getPropertyKey('UsersService')` → `USERS_SERVICE_GRPC_ADDRESS`;
2. **регистрирует standalone-свойство на лету**: `ConfigMetadataRegistry.registerProperty(target, key, { parser: GrpcAddressParser, expectedInEnv: false })` — это и есть «unbound property»: конфиг-свойство, **не привязанное ни к какой `@ConfigSection`**, выведенное из объявления клиента;
3. `PlatformConfigModule.forProperty(alias)` создаёт провайдер `STANDALONE_CONFIG_PROPERTY_<alias>`, резолвящий это одно свойство из `ConfigContext`;
4. channel-провайдер инжектит `propertyToken` (адрес) → канал; client-провайдер инжектит канал → клиент.

Итог: **инжектнул клиент — env-адрес пришёл сам**, ты не писал секцию. И on-demand: провайдеры генерятся ровно для тех серверов, которые ты реально инжектишь. Плюс второй режим (`createClientFactoryModuleDefinition`): `factory.create(runtimeAddress)` — адрес известен только в рантайме.

## Это token families — и оно уже в роадмапе (item 5)

«Unbound property» = **параметризованный конфиг-токен, член семейства**. grpc-клиент = член семейства `GrpcClient(server)`, чей провайдер транзитивно тянет член конфиг-семейства `Config(addressKey(server))`. Ровно `makeTokenFamily`/`familyProvider` из [ideas.md](../decisions/ideas.md) (решения 1–2). И тут **важное преимущество nestling над rsdk**: rsdk резолвит standalone-свойства лениво (factory-провайдеры, `resolveProperty`), потому что Nest ленив. Жадный билдер nestling **видит все запрошенные члены семейств в deps** и инстанцирует их на `build()` — без рантайм-резолюции. «Динамика» происходит на сборке.

```typescript
// config-property как семейство (kernel). readers — провайдеры: env примордиальный, vault опциональный
const Cfg = makeTokenFamily<unknown, [key: string]>('Config');
familyProvider(Cfg, (key) =>
  factoryProvider(Cfg(key),
    (vault, env) => vault?.get(key) ?? env.get(key),   // «нет волта → env» — здесь
    [VaultReader.optional, EnvReader]));

// секция makeConfig — сахар: объявляет свойства (в реестр → доки) и проецирует в типизированный объект
export const OrdersConfig = makeConfig('orders', z.object({ maxItems: z.coerce.number().default(100) }));
//   ≈ Cfg('ORDERS_MAX_ITEMS'), спроецированный в { maxItems }

// unbound: grpc-клиент как семейство, тянет адрес транзитивно
const GrpcClient = makeTokenFamily<Client, [srv: ServerDef]>('GrpcClient');
familyProvider(GrpcClient, (srv) =>
  factoryProvider(GrpcClient(srv), (addr) => channelTo(addr), [Cfg(addressKey(srv))]));
//   addressKey(UsersService) = 'USERS_SERVICE_GRPC_ADDRESS'  ← auto-declared unbound property

@Injectable([GrpcClient(UsersService)])   // инжектишь клиент — адрес из env приходит сам
class Foo { constructor(private users: Client) {} }
```

Билдер видит `GrpcClient(UsersService)` → recipe → `Cfg('USERS_SERVICE_GRPC_ADDRESS')` → `EnvReader`. Всё жадно, в графе (визуализируется, валидируется), в реестре свойств (→ автодок). **Секция, unbound-свойство, on-demand-клиент, `ILogger(scope)` — один механизм.**

### Build-time параметр vs runtime параметр

Тут важная граница, и rsdk её проводит двумя генераторами:

| Параметр известен | Механизм | Пример |
|---|---|---|
| **на сборке** (какие серверы зовёшь — статично из deps) | **token family** — жадно, в графе, документируется | `GrpcClient(UsersService)`, `Cfg(key)`, unbound-адрес |
| **в рантайме** (адрес из БД, per-tenant) | **фабрика** — репозиторий+кэш, вне жадного графа | `GrpcClientFactory.create(addr)` |

```typescript
// runtime-адрес → не семейство, а фабрика (ideas.md решение 5: рантайм-подграфы)
@Injectable([GrpcClientFactory])
class PerTenant {
  constructor(private clients: GrpcClientFactory) {}
  call(addr: string) { return this.clients.get(UsersService, addr); }  // кэш каналов внутри
}
```

Семейство — когда билдер может перечислить членов статически; фабрика — когда нет. Не смешивать.

## Отказ от `sources` — падает из этого же

Ты прав, и это следствие token-families, а не отдельное решение. В прошлый ход была цепочка `sources → ConfigSource(merge Vars) → секции`. Теперь:

- **нет `ConfigSource`, нет `Vars`-мержа, нет bag `sources: [...]`;**
- **readers — провайдеры**: `EnvReader` (примордиальный, всегда есть), `VaultReader`/`FileReader` (опциональные, из своих модулей);
- **override живёт в recipe конфиг-семейства** (kernel-space, «на уровне провайдера», как ты сказал): цепочка `vault?.get(key) ?? env.get(key)` — а не централизованный мерж-в-данные. «Нет волта → env» — это `VaultReader.optional` в recipe.

Что теряем vs централизованный мерж — единый **precedence-как-данные**. Но он не исчезает, а переезжает в recipe семейства (по-прежнему одно место). Что **не** теряем:

- **провенанс-слепоту** — бизнес-конфиг (`makeConfig`, `Cfg(key)`) называет ключ, а не источник; какие readers и в каком порядке — решает recipe (kernel). Твоё требование из прошлого хода цело;
- **выгрузку доки** — реестр свойств (rsdk-шный `ConfigMetadataRegistry`) записывает каждое объявленное свойство, включая unbound grpc-адреса; жадный граф содержит каждый *запрошенный* член. `config:doc` дампит ровно то, что приложение потребляет, — даже полнее, чем дамп источников.

То есть «переопределить конфигурацию» ты не теряешь — оно просто становится `VaultReader.optional` в одном recipe вместо `sources`-мержа. А `sources` как сущность уходит.

## 1. «Вносит глобальную инфраструктуру» — растворяется в модулях

Эта часть — 80% плагина — в nestling **не нуждается в новом примитиве**. Мы уже это проходили с транспортами и источниками: раз модуль — значение, а `redis(opts)` — функция, возвращающая модуль, то «плагин» это **параметризованный инфра-модуль, композируемый в корне**:

```typescript
export const redis = () => makeModule({          // redis(opts) — модуль-значение, параметризован бесплатно
  name: 'infra:redis',
  providers: [RedisConfig, factoryProvider(RedisClient, makeRedis, [RedisConfig])],
});                                               // RedisClient — экспортируемый токен, синглтон в процессе

@Injectable([RedisClient])
class CacheService { constructor(private redis: Redis) {} }
```

Два важных следствия, снимающих кажущиеся возражения:

- **«Глобальность» ≠ ambient-инжект.** Провайдер живёт в корне процесса один раз (синглтон), но **инжектнуть его можно только импортнув токен** `RedisClient` — ES-видимость цела. То есть глобальная регистрация провайдера и «называешь токен, чтобы инжектить» сосуществуют. Это ровно kernel/user из §3: плагин — **композируемая kernel-инфраструктура**, юзер дотягивается через импорт токена.
- **Конфиг плагина — секция, которую он же и везёт** (`RedisConfig`), а не литерал в `redis({ url })`. Как `VaultConfig` у источника. Консистентно с конфиг-моделью: `redis()` без аргументов, url приходит из `RedisConfig` через env/reader.

`forTransports()` тоже растворяется: плагин, которому нужен HTTP, — его провайдеры зависят от токена транспорта → fail-fast, если его нет. Явный `requires` нужен только для слабого случая `'any'` («хоть какой-то ingress должен быть»).

## 2. «Хуки в сквозной тракт» — вот это НЕ ложится напрямую

Плагин rsdk через `configureMiddleware` навешивает middleware на **все** роуты глобально. А nestling в pipeline-v2 **осознанно отверг** уровни привязки App/module — «жадная сборка константами, привязка только к endpoint'у» ([ideas.md](../decisions/ideas.md)). Прямого «ambient middleware от плагина» в nestling нет и по дизайну быть не должно.

Значит сквозной концерн плагина ложится иначе: **плагин экспортирует слой пайплайна-константу, endpoint композирует его явно**, а «вездесущность» — конвенция + опциональный policy-check на старте:

```typescript
// плагин экспортирует СЛОЙ, а не навешивает ambient middleware
export const tracing = makePipeline().pre(withTrace()).finally(reportSpan());

// endpoint композирует явно
makeEndpoint({ /* ... */ pipeline: compose(tracing, validation) });

// «в каждом пайплайне есть tracing» — startup policy-check (ideas.md pipeline-v2, п.8),
// либо per-transport дефолтный пайплайн (там же — «место есть, решение отложено»)
```

Это честная развилка с rsdk, и она принципиальная: nestling меняет «невидимо навесили на всех» на «видимо скомпозировал, а инвариант проверил на старте». Часть плагина, которая про error-formatting/tracing/context, — это либо pipeline-слои (композируются), либо `@nestling/context` на AsyncLocalStorage (ideas.md решение 4), но **не** ambient-инъекция в тракт.

## 3. Плагины + разделение на фичи (главное)

Вот тут интересно, и тут плагины перестают быть просто «глобальными». Ключевой вопрос: **глобальные — относительно чего?** Относительно процесса (выбранного подмножества фич) или относительно логического приложения (всех фич)?

Инфраструктура **процесс-глобальна**: один Redis-клиент на процесс, его делят все фичи, что крутятся в этом процессе. Разнёс фичи по процессам — у каждого свой Redis-клиент. Значит «какие плагины» должно **падать из выбранного подмножества фич** — тот же паттерн, что с транспортами и источниками (четвёртый раз). Спектр:

| Тип | Где объявляется | При split |
|---|---|---|
| **feature-scoped инфра** (Redis для кэш-фичи, Kafka для events) | фича импортирует инфра-модуль / зависит от его токенов | **едет с фичей** — процесс без этой фичи её инфру не поднимает |
| **ambient cross-cutting** (логирование, трейсинг, error-handling) | в корне, `assemble({ plugins: [...] })` | в каждом процессе, независимо от фич |

```typescript
// (а) feature-scoped — инфра внутри фичи, возит её с собой
export const CacheFeature = makeFeature({
  name: 'cache',

  features: [CacheFeature, OrdersFeature],
  select,
});
```

Три вещи, которые это даёт и которые стоит проговорить:

- **Фича возит свою cross-cutting инфру.** Это и делает фичу независимо-развёртываемой: `--features=cache` в отдельном поде поднимает Redis, потому что фича его импортирует; под с `--features=orders` — нет. Не надо руками синхронить «плагины ↔ выбранные фичи».
- **Шаринг бесплатен от жадного контейнера.** Две фичи импортят `redis()` → co-located: **один** общий `RedisClient` (дедуп синглтона); split: два процесса, два клиента. «Модульный монолит → микросервисы» получается без правок кода — только за счёт singleton-семантики per-process.
- **Граница честности.** Если две разнесённые фичи делят один *бэкенд* (один Redis-сервер / одни таблицы) — это уже **дата-архитектурный** концерн (общие таблицы = distributed monolith smell), не механика плагинов. Плагин даёт клиент; кто чем владеет в сторадже — отдельный разговор.

То есть `plugins: [...]` как root-bag остаётся, но **тонкий** — только вездесущее. Специфичная инфра — это импорты внутри фич, по тому же greedy-паттерну «из дерева модулей».

## Итог

- **Инфраструктурная часть плагина** = параметризованный инфра-модуль (значение) + его конфиг-секция + экспортируемые токены. Новый примитив не нужен — это kernel-инфраструктура, композируемая как модуль.
- **Сквозная-пайплайновая часть** = экспортируемые pipeline-слои + policy-check, **не** ambient middleware (принципиальное расхождение с rsdk).
- **С фичами:** плагины процесс-глобальны; feature-scoped инфра едет с фичей (падает из `select`), ambient cross-cutting — тонкий root-bag. Шаринг/изоляция — бесплатно от контейнера per-process.

## Чем «откуда читать конфиг» отличается от обычного сервиса

Обычный провайдер (сервис): их **много**, каждый модуль-библиотека приносит свои, ты просишь по имени. `RedisClient`, `UserService` — таких десятки, и они разбросаны по модулям.

А «откуда берётся конфиг» — не такое:

- он **один** на всё приложение;
- решается в **одном** месте — в composition root (у автора приложения);
- библиотеки его **не приносят и не трогают** — иначе библиотека решала бы, откуда её настройки, а это ровно то, что запрещено;
- из него **читают все**.

То есть это не «ещё один сервис из кучи», а **единый центральный свод правил**: «вот места, откуда берём настройки, вот в каком порядке». Поэтому он и не лезет в модель «обычный провайдер, который модули регистрируют». Твоя интуиция верная.

## Как это выглядит

Одно центральное место — в корне приложения — говорит, откуда читать. Библиотека только называет настройку.

```
// БИБЛИОТЕКА (например redis-модуль) — просто называет ключ, откуда — не знает
redisUrl = настройка('REDIS_URL')     // по умолчанию возьмётся из env

// COMPOSITION ROOT (приложение) — ОДНО место решает, откуда и в каком порядке
приложение({
  конфиг: {
    читать: [ волт(адрес: изEnv('VAULT_ADDR')), env() ],   // сначала волт, потом env
    особо:  { REDIS_URL: 'только из волта' },               // переопределение по ключу
  },
  features: [...],
})
```

Правила:

- **По умолчанию — env.** Ничего не написал в корне → всё читается из переменных окружения. Библиотеки работают, композиция минимальна.
- **Хочешь иначе — говоришь в корне.** Порядок мест + отдельные переопределения по ключу. Библиотеки при этом **не меняются** — они как называли `REDIS_URL`, так и называют.

Прошлый мой вариант (каждый источник — отдельный провайдер, читаем через цепочку) как раз спотыкался о твои две вещи. А тут:

- **бутстрап** (адрес волта из env) — естественно: центральная штука при своей настройке сама читает env для своих координат;
- **жизненный цикл** (подключиться к волту, обновлять токен, закрыть) — один сервис, один цикл. Вместо кучи источников-провайдеров, каждый со своим циклом, — одна вещь.

## Что это меняет, а что нет

Не меняется ничего из того, что решили:

- **Группа = пачка отдельных настроек, и всё** — принято, так и оставляем.
- Каждая настройка — это ключ + значение по умолчанию. Одиночная (адрес gRPC-клиента) и та, что в группе, — одинаковые.

Меняется только одно: настройка читает своё значение **из этого единого центрального места**, а не из «цепочки сервисов-читателей». Проще.

## Read the request first

Calibrate treatment, not whether to design. A doc deserves the same craft as a landing page — what changes is the treatment that craft is delivered in.

Many requests call for a more utilitarian treatment: a plan, a memo, a demo. Make it polished: include real typographic hierarchy, considered spacing, and a proper palette, but avoid over-designing. Most pages do not need a flashy, gigantic hero. Keep flourishes tasteful and limited.

Some requests call for an editorial treatment: a landing page, a game, an app or tool they'll keep or share.

When unsure: a well-composed page is never the wrong answer; an over-designed visual identity sometimes is.

Fundamentals below apply to everything. The editorial process after that runs only when the read above says so.

## Fundamentals for every artifact

**Honor what's already there** Look for an existing design system first — CLAUDE.md, a tokens or theme file, existing component styles. When one exists, apply it; everything below fills gaps and never overrides. Precedence is always: the user's own words, then the project's existing system, then your choices.

**Ground it in the subject.** If the subject isn't already clear, pin it: one concrete subject, its audience, and the page's single job. The subject's own world — its materials, instruments, vernacular — is where distinctive choices come from. Build with real content throughout, never lorem.

**Pair typefaces** Typography carries the page even when the page isn't about typography. The Artifact CSP blocks font CDNs, so don't link a webfont URL and risk a silent fallback. Instead inline the face as a @font-face data URI. Keep running text near 65 characters wide; set a type scale and stay on it; give headings `text-wrap: balance`, body text room to breathe, and uppercase labels a touch of letter-spacing.

**Choose neutrals, don't default to them.** A pure mid-grey reads as unconsidered; a grey with a slight hue bias toward the page's accent reads as chosen. Pure white and near-black are fine grounds when they suit the subject — the point is that the neutral was picked, not inherited.

**Design both themes.** The page renders in the viewer's theme: `prefers-color-scheme` carries the OS preference, and the viewer's toggle stamps `data-theme="dark"` / `data-theme="light"` on the root element, which must override the media query in both directions. The robust pattern is token-level: define the palette as custom properties on `:root`, redefine only the tokens under `@media (prefers-color-scheme: dark)` — style components through the tokens, never directly inside the media query — then redefine them again under `:root[data-theme="dark"]` and `:root[data-theme="light"]`. Give the second theme the same care as the first — don't naively invert; keep contrast legible and the accent working on both grounds. A design that deliberately commits to one visual world (a neon arcade screen, a letterpress invitation) may stay single-theme — make it a choice, not an omission.

**Let layout do the spacing.** Lay out sibling groups with flex or grid and `gap`, not per-element margins that silently collapse or double. Wide content — tables, code, diagrams — gets `overflow-x: auto` on its own container so the page body never scrolls sideways. Reach for `font-variant-numeric: tabular-nums` wherever digits line up in columns.

**Avoid AI-generated design** AI-generated design currently clusters around a few looks: warm cream (#F4F1EA) with a serif display and terracotta accent; near-black with a lone acid-green or vermilion pop; broadsheet hairline rules with dense columns; a purple-to-blue gradient hero on white; Inter or Space Grotesk as the "safe" face; emoji as section markers; everything centered; `rounded-lg` everywhere; accent bar/rail on rounded cards. Where the user pins down a visual direction, follow it exactly — their words always win, including when they ask for one of these looks. Where nothing is specified, don't spend that freedom on one of these defaults.

**Build cleanly** Be cognizant of overlapping elements, cascade collisions, silent font fallbacks; visual bugs hide in the gap between source and output. Close every non-void element, double-quote attributes, give keyboard focus a visible state, respect `prefers-reduced-motion`. For generative or decorative graphics, reach for Canvas or WebGL rather than hand-authoring long SVG path data.

**CSS rules** When writing the CSS, watch your selector specificities. It is easy to generate classes that cancel each other out — a type-based selector like `.section` fighting an element-based one like `.cta` over padding and margins between sections. Structure the cascade so it doesn't silently undo your spacing.

**Writing the copy** Words are design material, not decoration. Write from the user's side of the screen — name things by what people recognize, not how the system is built (a person manages *notifications*, not *webhook config*). Active voice; a control says exactly what happens ("Publish", then a toast that says "Published"). Errors explain what went wrong and how to fix it — no apologies, no vagueness. Specific beats clever.

**Structure is information** Structural devices, numbering, eyebrows, dividers, labels, should encode something true about the content, not decorate it. Many generic designs use numbered markers (01 / 02 / 03), but that's only appropriate if the content actually is a sequence - like a real process or a typed timeline where order carries information the reader needs. Question if choices like numbered markers actually make sense before incorporating them.

**When it's a UI, not a document** A dashboard or tool is scanned and operated, not read top-to-bottom, so the craft shifts from typography to information design. Surface the summary before the detail; encode state in form as well as number — a pill, a chip, a severity stripe — so what needs attention reads at a glance. Semantic color (good / warning / critical) is separate from the accent hue and doesn't count as your accent. Give sparklines and charts the same care as type: an area fill, a faint grid, an emphasized endpoint. What's interactive should look interactive.

Before writing code, sketch a short design plan — a compact token system with color, type, and layout:
- **Color**: describe the palette as 4–6 named hex values.
- **Type**: typefaces for 2+ roles — a characterful display face used with restraint, a complementary body face, and a utility face for captions or data if needed.

## Да, токены конфигов экспортируются — и это несёт смысл

Чтобы вариант 3 работал, composition root должен **назвать** `RedisConfig`, `DbConfig` — значит пакет их экспортирует:

```typescript
// пакет @acme/redis — экспортирует токен конфига (просто декларация ключей, без источника)
export const RedisConfig = makeConfig('redis', z.object({ url: from('REDIS_URL') }));

await assemble({
  config: { default: env(), bind: [[vault(), [RedisConfig]]] },
  features,
});
```

Важно: пакет экспортит **декларацию** (какие ключи), но **не знание об источнике**. Привязка к волту живёт в корне. То есть «библиотека не знает, откуда конфиг» — цело: экспорт токена ≠ знание про волт.

## Экспортить или нет — это выбор со смыслом

Ровно как с любым токеном в nestling (не экспортировал → снаружи не достать), экспорт конфига решает, что можно с ним делать снаружи:

- **Экспортировал** `RedisConfig` → автор приложения может привязать его к источнику, посмотреть в доке, переопределить. Это **публичная конфиг-поверхность** пакета.
- **Не экспортировал** → конфиг **приватный**: его нельзя назвать в `bind`, значит нельзя привязать индивидуально.

При этом «приватный» **не значит «только env»**. `default` применяется ко **всем** конфигам — и публичным, и приватным. Приватный просто **следует за default** и не роутится отдельно:

```typescript
config: {
  default: vault(),                  // ← ВСЁ читается из волта, включая приватные конфиги
  bind: [[env(), [RedisConfig]]],    // ← а вот RedisConfig — исключение, из env
}
```

Так что модель ровная: `default` — для всего, `bind` — только для того, что смог назвать (а назвать можешь только экспортированное).

## Что можно класть в `bind` — не только токены

У нас есть и одиночные настройки без группы (адрес gRPC-клиента, `*_GRPC_ADDRESS`). Их токена-группы нет, поэтому `bind` принимает **два вида цели**:

```typescript
bind: [
  [vault(), [RedisConfig, DbConfig]],   // по токену группы — типобезопасно, требует export
  [vault(), ['*_GRPC_ADDRESS']],        // по шаблону ключа — для одиночных/сквозных
]
```

Токен группы под капотом — это просто «набор ключей, которые он объявил» (через префикс/схему), так что привязка по токену = «эти объявленные ключи → сюда». Без строковой хрупкости для случая групп.

## Почему это не создаёт проблем

- **Связности нет:** корень и так зависит от библиотек (он их композирует); импортнуть их конфиг-токены — обычная зависимость, не цикл.
- **Утечки нет:** токен — это декларация ключей и схемы, а не внутренности. Экспортишь ровно ту поверхность, которую и так надо документировать.
- **Механизма нового нет:** это обычный `export const`. Хочет пакет — экспортит, не хочет — держит приватным. Язык уже даёт нужное.

## Конфиг приватен для инжекта

Твоя мысль: конфиг — это **приватная деталь модуля**. Другой модуль должен зависеть от его *сервиса* (`RedisClient`), а не лезть в его *настройки* (`RedisConfig`). Значит:

- **инжектить `RedisConfig` может только его модуль-владелец** (его собственные провайдеры, которые из этого конфига строят сервисы);
- инжект конфига провайдером из чужого модуля → **ошибка на сборке** («config X приватен для модуля Y; зависите от сервисов Y, не от его конфига»).

Это не ES-видимость (импортнул — инжектишь), а **правило контейнера поверх неё** — через привязку провайдеров к модулям (`container-module-attribution` уже есть). Проверка на build, в духе `strictExports`.

## Как это уживается с вариантом 3 (привязка по токену)

Ключ: **«назвать для привязки» и «инжектить» — разные права.** Токен конфига несёт два, и они расщепляются:

- **referenceable** — назвать в `bind`, показать в доке. Это делает корень (импортит токен, чтобы указать в `bind`). Инжект-права не даёт.
- **injectable** — только владелец, проверяется на сборке.

То есть экспорт конфиг-токена = «можно назвать/привязать», а **не** «можно инжектить». Экспортил — корень роутит его в волт; но чужой модуль всё равно не заинжектит (build-правило не пустит).

Если хочешь строже — второй вариант: инжектируемый токен вообще не покидает модуль, а для привязки/доки экспортится отдельная лёгкая ссылка (`RedisConfig.ref`). Чище разделение, но две сущности на конфиг. Я бы взял первый (один токен + build-правило) — меньше поверхности.

## Документация + «под фиче-флагом или нет»

Тут важное твоё требование. Генератор доки идёт по собранным + выбранным модулям и на каждый конфиг вешает:

- какому **модулю → фиче** принадлежит;
- **всегда-он (core)** или **под флагом** (`--features`, опционально).

```
CONFIG (--features=all)

  core (всегда)
    LoggingConfig    LOG_LEVEL          info
  feature: cache  [под флагом]
    RedisConfig      REDIS_URL          (обязательно)
  feature: billing [под флагом]
    DbConfig         DATABASE_URL       (обязательно)
```

Так для конкретного развёртывания (подмножества фич) видно, что настраивать; а полная выгрузка (`--features=all`) помечает, что нужно только при включённой фиче. Это ровно «понимать, под фиче-флагом оно или нет».

## Что именно различает «назвать» и «заинжектить»

Позиция токена:

| Где стоит `RedisConfig` | Это | Кто может |
|---|---|---|
| в `config.bind` у `assemble` | *назвать* (роутинг к источнику) | любой (это делает корень) |
| в списке зависимостей провайдера | *заинжектить* (прочитать значения) | только модуль-владелец |

`config.bind` обрабатывает конфиг-подсистема как «маршрут», а не как DI-зависимость. ## Как это работает под капотом

Проверка — на сборке, дёшево, потому что вся инфа уже есть:

- каждый конфиг знает владельца (из `configs: [...]`);


## 2. Как реализуется источник

Источник — **не DI-провайдер**, а маленький объект, который центральная читалка держит и опрашивает. Контракт минимальный:

```typescript
interface ConfigSource {
  get(key: string): string | undefined;      // дай значение ключа или ничего
  init?(): Promise<void>;                     // подготовка (прочитать файл, коннект к волту)
  close?(): Promise<void>;                    // остановка (закрыть коннект)
  watch?(onChange: () => void): () => void;   // для reloadable; вернуть отписку
}
```

Конкретные источники — фабрики, возвращающие такой объект:

```typescript
// env — примордиальный, без состояния
const env = (): ConfigSource => ({
  get: (key) => process.env[key],
});

// файл — читает при старте, умеет следить
const file = (path: string): ConfigSource => {
  let data: Record<string, string> = {};
  return {
    async init() { data = parseYaml(await readFile(path)); },
    get: (key) => data[key],
    watch(onChange) {
      const w = fsWatch(path, async () => { data = parseYaml(await readFile(path)); onChange(); });
      return () => w.close();
    },
  };
};

// волт — состояние + жизненный цикл (коннект, обновление токена)
const vault = (opts: VaultOpts): ConfigSource => {
  let client: VaultClient, cache: Record<string, string> = {};
  return {
    async init()  { client = connect(opts); cache = await client.readAll(); },
    get: (key)    => cache[key],
    async close() { await client.stop(); },
  };
};
```

Читалка (kernel) на старте: `init()` все источники (в т.ч. `await` для волта → fail-fast, если обязательного нет), на `get(key)` идёт по правилам из `config` (сначала переопределение, потом env), на shutdown — `close()`. Координаты волта (`VAULT_ADDR`) — это единственное место, где фабрика читает `process.env` напрямую при своём создании; всё остальное — через читалку.

Вот почему источники «не обычные провайдеры»: их создаёт и оркестрирует одна читалка, а не контейнер; в графе их нет.

## 3. Реактивность без тяжёлой зависимости (офтоп)

Сначала важное: **для конфига реактивность почти не нужна.** Основной режим — *read-latest*: `cfg.logLevel` читается в момент использования и всегда актуален. Ноль машинерии. «Реагировать» (пересобрать пул) надо редко — только там и нужен push.

- **Свой крошечный нотификатор** (рекомендую) — набор колбэков + вызов на reload, ~10 строк. У вас уже есть `Topic` (из streaming-идей) и `AbortSignal` для отписки — `onChange(signal, cb)` ложится на них без новых зависимостей.
- **Нативный `EventTarget`** — стандартный, глобальный в Node, ноль зависимостей. `target.addEventListener('change', …)`. Если не хочется писать даже нотификатор.
- **TC39 Signals** (`signal-polyfill`) — это и есть «стандартная реактивность» на подходе (авто-трекинг зависимостей, как в SolidJS), которую тянут в язык. ## 2. Нотификатор — да, вызов работает. Вот весь механизм

Ключевой момент: для reloadable инжектится **не замороженный снапшот, а маленький живой объект** — геттеры полей (всегда актуальные) + метод `onChange`. Поэтому вызывать на нём `onChange` есть на чём.

`Topic` (у вас уже есть по streaming-идеям) + `AbortSignal` для отписки:

```typescript
class Topic<T> {
  #subs = new Set<(v: T) => void>();
  subscribe(signal: AbortSignal, cb: (v: T) => void) {
    this.#subs.add(cb);
    signal.addEventListener('abort', () => this.#subs.delete(cb), { once: true });
  }
  push(v: T) { for (const cb of this.#subs) cb(v); }
}
```

Живой хэндл, который фреймворк генерирует для reloadable-конфига:

```typescript
function reloadableHandle(reader, schema, keys) {
  const topic = new Topic();
  let current = validate(schema, project(reader, keys));
  reader.onChanged(keys, () => {                     // источник дёрнул watch → перечитали
    current = validate(schema, project(reader, keys)) ?? current;   // невалидное → keep-last
    topic.push(current);
  });
  return {
    get logLevel() { return current.logLevel; },     // read-latest — всегда актуально
    onChange: (signal, cb) => topic.subscribe(signal, cb),
  };
}
```

Потребитель:

```typescript
@Injectable([RuntimeConfig])
class Logger {
  constructor(private cfg: Config<typeof RuntimeConfig>) {}

  debug(m: string) { if (gte(this.cfg.logLevel, 'debug')) this.write(m); }   // ← работает: геттер живой

  @OnStart() start(signal: AbortSignal) {
    this.cfg.onChange(signal, next => this.applyLevel(next.logLevel));       // ← работает
  }
}
```

Что происходит по шагам, чтобы было видно, что «вызов работает»:

1. `onChange(signal, cb)` → `cb` кладётся в `#subs` Topic'а;
2. файл поменялся → watch источника → читалка перечитала → `topic.push(next)` → все `cb` вызвались;
3. сервис умирает (shutdown/destroy взвёл `signal`) → `abort` → `cb` сам удалился из `#subs`.

~15 строк, ноль зависимостей, на нативных `Set` + `AbortSignal`. Read-latest (`cfg.logLevel`) вообще без подписки — просто геттер.
