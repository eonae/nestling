## [2026-07-06] Token families + модули без рантайм-инкапсуляции

### Контекст

«Динамические инжекты» (on-demand провайдеры) — это не одна фича. За словом
скрываются пять разных потребностей:

1. **Параметризованные провайдеры** — один рецепт, много инстансов по ключу:
   `ILogger(scope)`, `IQueue(name)`, `IHttpClient(upstream)`.
2. **Consumer-aware провайдеры** — инстанс зависит от того, кто его инжектит
   (логгер, названный по классу-потребителю; в Nest — transient + INQUIRER).
3. **Request-состояние** — identity, requestId, транзакция.
4. **Ленивая инициализация** — тяжёлый ресурс, создаваемый при первом обращении.
5. **Рантайм-подграфы** — плагины, per-tenant контейнеры.

Ключевое наблюдение: потребности **1 и 2 — статические**. Они выглядят
«динамикой» только в Nest, где их нельзя выразить иначе как рантайм-резолюцией.
В nestling зависимости объявляются явным массивом — билдер на `build()` видит
все запрошенные члены семейства и может инстанцировать их жадно. Граф остаётся
полным: визуализация, топологический init/destroy и проверка циклов работают
как раньше.

### Решение 1: makeTokenFamily

Формализация паттерна из `examples.simple-app/src/logging/registry.ts`
(ручной Set + фабрика токенов) в фичу контейнера.

```typescript
// Семейство токенов: рецепт один, инстансов много
const ILogger = makeTokenFamily<ILoggerService, [scope: string]>('Logger');

// ILogger('users') → TokenString<ILoggerService>
// - id = "Logger:users"
// - мемоизировано: повторный вызов с тем же параметром → тот же токен

// Инфраструктурный модуль регистрирует ОДИН рецепт на всё семейство:
familyProvider(ILogger, (scope) =>
  factoryProvider(ILogger(scope), (config) => new Logger(scope, config), [IConfig]),
);

// Бизнес-код запрашивает члена семейства как обычную зависимость:
@Injectable([UserService, ILogger('users')])
class CreateUserEndpoint { /* ... */ }
```

Семантика `build()`:

- билдер собирает все члены семейств, упомянутые в deps зарегистрированных
  провайдеров;
- для каждого уникального параметра вызывает рецепт и создаёт обычный узел графа;
- дальше всё как всегда: жадная инстанциация, проверка циклов, lifecycle-хуки.

Никакой рантайм-резолюции. «Динамика» происходит на этапе сборки.

### Решение 2: consumer-aware сахар

```typescript
@Injectable([UserService, ILogger.auto])
class CreateUserEndpoint { /* ... */ }
// ILogger.auto резолвится в ILogger('CreateUserEndpoint')
// в момент регистрации — потребитель известен статически.
```

Покрывает кейс Nest `transient + INQUIRER`, но без transient-скоупа и без
рантайм-магии.

### Решение 3: модули остаются plain objects, видимость — через ES-модули

Наблюдение, недоступное Nest: в nestling инжектят по **токену-значению, который
нужно импортировать**. Не экспортировал токен из `index.ts` модуля — снаружи его
физически невозможно запросить. ES-модули уже являются системой видимости;
рантайм-инкапсуляция (как в Nest) не нужна.

Следствия:

- **Модуль** = plain object: метка принадлежности + единица упаковки
  (providers, endpoints, middleware) + метаданные для графа/визуализации.
- **`exports` как рантайм-механизм — не делаем.** Вместо этого:
  - видимость по умолчанию — ES-экспорты (+ ESLint boundaries между пакетами
    при желании);
  - опциональная строгость: `new ContainerBuilder({ strictExports: true })` —
    на `build()` проверить рёбра готового графа против деклараций exports.
    Это build-time lint, не рантайм. Граф уже есть — проверка дешёвая.
- **Параметризованные модули бесплатны**: модуль — значение, значит
  `LoggingModule({ level: 'debug' })` — просто функция, возвращающая Module.
  Концепция DynamicModule / forRoot / forRootAsync не нужна вообще.

### Решение 4: что НЕ кладём в контейнер

- **Request-состояние (потребность 3)** — никогда не в DI. Типизированный
  request-контекст уже есть: это input пайплайна (`withIdentity` кладёт
  identity — это и есть request scope, причём типизированный). Для глубоких
  сервисов — ~~отдельный пакет `@nestling/context` на AsyncLocalStorage
  (в планах)~~ — **СУПЕРСИД 2026-07-31** (change `async-context`):
  резервирование имени снято, всё живёт в `@nestling/pipeline`. Писатель
  типизируется его `ExtendableContext`, ячейку обновляет его рантайм,
  предикат `hasVar` живёт в его словаре политик — отдельный пакет дал бы
  цикл зависимостей либо дубль типов. Это защищает от нестовского bubbling
  request-scope, заражающего граф.
- **Lazy (потребность 4)** — если понадобится: явная обёртка
  `deps: [lazy(HeavyClient)]` → инжектится `Lazy<T>` с `.get(): Promise<T>`.
  Явность вместо прокси. Отложено.
- **Подграфы (потребность 5)** — child-контейнер
  `container.createScope(providers)`: видит синглтоны родителя, свой подграф
  валидирует в момент своего `build()`. Отложено.

### Итоговая рамка

**Инфраструктура = семейства (рецепты) + pipeline-шаги. Бизнес = обычные
провайдеры (экземпляры) + endpoints.** Бизнес-код запрашивает членов семейств;
инфраструктурные модули поставляют рецепты. Разделение бизнес/инфраструктура
становится видимой структурой, а не конвенцией.

### Открытые вопросы

- API `familyProvider`: рецепт возвращает готовый provider-объект или
  `{ deps, factory }`?
- `ILogger.auto` внутри фабричных провайдеров (не классов) — чем считать
  «потребителя»?
- Нужна ли валидация параметров семейства (например, enum допустимых скоупов)?

## [2026-07-06] Стриминг: `stream(T)` ≠ `events(T)`, AbortSignal, источники событий

### AbortSignal — first-class примитив контекста

В `meta` каждого запроса есть `signal: AbortSignal`. Его взводят:

- транспорт — при отвале клиента (закрытие соединения);
- приложение — при graceful shutdown (`App.close()` абортит все in-flight
  запросы и подписки);
- (в будущем) кто угодно ещё — например, админский kill подписки.

Единый механизм отмены для всего: без него бесконечные подписки не завершаются
в принципе, а `close()` виснет на живых соединениях. Хендлер обязан уважать
signal (для `for await` по подписке это происходит естественно, если источник
принимает signal).

### `stream(T)` и `events(T)` — разные модификаторы

Семантика разная, объявляется декларативно в endpoint'е:

| | `stream(T)` | `events(T)` |
|---|---|---|
| Природа | конечные данные (экспорт, большой результат) | открытая подписка |
| Конец | естественный (данные закончились) | нет; «нормальное завершение» = дисконнект |
| HTTP-framing | NDJSON / chunked | SSE: heartbeat, `id:`, реконнект по `Last-Event-ID` |
| Доки | OpenAPI | AsyncAPI |

Словарь исходов завершения (для finish-фазы/наблюдателей):
`completed | disconnected | aborted | failed`. Для `stream` нормален
`completed`, для `events` — `disconnected`.

### Источники событий — это DI, а не особый вид endpoint'ов

Хендлер вызывается один раз **на соединение** и подписывается на источник,
который живёт в контейнере как обычный singleton-сервис (и работает независимо
от наличия подписчиков):

```typescript
// инфраструктура: источник — обычный провайдер
class LogHub {
  #topic = new Topic<LogEvent>();      // broadcast-примитив (пакет utils)
  publish(e: LogEvent) { this.#topic.push(e); }
  subscribe(signal: AbortSignal) { return this.#topic.subscribe(signal); }
}

// endpoint: подписка per-connection
makeEndpoint({
  pattern: 'GET /logs/live',
  output: events(LogEvent),
  handle: async function* (_, meta) {
    yield* hub.subscribe(meta.signal);
  },
});
```

Endpoint-модель остаётся единообразной; никакого нового вида endpoint'ов.

Открытый вопрос: политика `Topic` для медленного подписчика — ограниченный
буфер + drop-oldest или принудительный дисконнект. Pull-модель AsyncIterable
даёт backpressure на соединении бесплатно, но горячий источник не может ждать
медленного клиента — один тормозной подписчик не должен останавливать всех.

### Правило: тип-сохраняющее vs тип-меняющее

- **Тип-сохраняющие** трансформации потока (`T → T`: наблюдение, лимиты,
  таймауты, фильтрация) — инфраструктура, допустимы вне контракта endpoint'а.
- **Тип-меняющие** (`T → T[]` батчинг, `T → T & {id}` обогащение) — часть
  контракта endpoint'а: только там, где они видимы в его декларации.
  Иначе схемы перестают описывать реальные типы и рушится schema-first.

### Реестр подписок — отдельный пакет

Типовая задача: посмотреть активные подписки из другого хендлера, завершить
конкретную и т. д. Делается поверх публичных примитивов (DI + signal +
finish-хук), в ядро не входит:

```typescript
// идея: @nestling/subscriptions
interface SubscriptionInfo { id; endpoint; identity?; startedAt }
class SubscriptionRegistry {
  list(filter?): SubscriptionInfo[];
  abort(id: string): boolean;   // взводит signal конкретной подписки
}
```

Подписка регистрируется при старте events-запроса и снимается в finish;
её signal — комбинация (AbortSignal.any) транспортного и админского.
«Убить подписку» = тот же AbortSignal, что и дисконнект/shutdown.

Ценность как dogfooding-тест: если такой пакет пишется, не трогая ядро, —
значит, публичных примитивов (pipeline-хуки, signal, DI) достаточно.

## [2026-07-06] Pipeline v2: плоские фазы, слои, композиция константами

### Логика принятия решений (как мы сюда пришли)

**1. «After» — это не одна точка, а три.** Стримы делают это видимым:
(a) хендлер вернул результат, первый байт не ушёл — envelope ещё можно менять;
(b) стрим течёт — можно только оборачивать итератор;
(c) всё дотекло / соединение закрылось — можно только наблюдать.
Фреймворки, у которых «after» один (Express, Koa, Nest-интерцепторы),
получают «headers already sent» и костыли вокруг стримов.

**2. Отказ от onion / `next()`.** Классическая Koa-модель отвергнута:
теряется типизированное монотонное накопление input (главная фишка),
появляется скрытый control flow (можно не вызвать next, вызвать дважды,
проглотить ошибку), исчезает статическая анализируемость цепочки
(нужна для explain/визуализации/OpenAPI).

**3. Луковица без next (вариант A) — работает, но плохо читается.**
Парные юниты `{pre, post}`, post-фазы в LIFO. Корректна на error-path
(post запускается только если pre активировался), но: post, объявленный
первым, срабатывает последним; маппер ошибок надо объявлять в начале
цепочки. Непрозрачно.

**4. Требование: вид юнита должен быть виден в декларации.**
Универсальный `.use()` не говорит, что перед тобой — pre, post или обёртка.
Отсюда именованные методы билдера.

**5. Плоские фазы (вариант E) + честная опциональность.** Ключевое озарение:
луковица была нужна только чтобы согласовать типы с рантаймом на пути ошибок.
Есть второй способ — сказать правду в типах: на ответном тракте обогащение
могло не случиться ⇒ ctx там `Partial`. А юниты только-на-успех имеют
железную гарантию: успех ⇒ весь pre-тракт прошёл ⇒ ctx полный.
Понятие «обёртка/wrapper» умирает: транзакция = `pre + ok + catch`,
три явные строчки. Автоматическое LIFO-разматывание ресурсов меняем на
явный порядок — в духе «explicit over implicit».

**6. Слова.** `makePipeline` (конвенция `make*` во всей кодовой базе);
`.catch` — знакомо по Promise, семантика совпадает; `.ok` — рифмуется с
классом `Ok`. Отказы: `after + successOnly: true` — булева опция, меняющая
ТИП ctx колбэка, хуже двух коротких методов; `.then` — запрещён навсегда:
объект с методом then становится thenable, `await pipeline` попытается его
резолвить (ловушка, известная по Knex).

**7. Хендлер — явно в середине (идея: слот/дырка → слои).** Декларация
читается сверху вниз как план исполнения целиком. Композиция пайплайнов
становится структурной: родитель видимо оборачивает потомка, правило
«ответные юниты родителя — последними» следует из формы. Возвращаются
градуированные гарантии типов (см. спецификацию). Точный синтаксис
композиции — открытый вопрос (см. ниже).

**8. Жадная композиция константами, привязка только к endpoint'у.**
Уровни App/module (глобальный пайплайн, модульный) отвергнуты:
отложенная сборка через реестр проверяется только на старте, а жадная
сборка константами — компилятором. Ответ на «переиспользование в модулях»:
модуль-фабрика с параметром `pipeline` — зависимость видна, тип параметра
документирует требуемый контекст, проверка compile-time. Цена: сквозные
инварианты («у всех ручек есть requestId») становятся конвенцией;
смягчение возможно позже — пайплайн интроспектируем, App может на старте
проверять политику («каждый пайплайн содержит withRequestId»).

**9. Классы-юниты и граница миров в типах.** Юниты-классы нужны для DI
(зависимости, lifecycle). Чтобы «полностью функциональный» сценарий остался
гарантией, а не конвенцией, — второй тип-параметр `TNeeds`: накопитель
отложенных зависимостей. Чистый пайплайн — `TNeeds = never` (дефолт,
функциональный API не меняется). Standalone-транспорты принимают только
`Pipeline<any, never>`; App резолвит TNeeds контейнером на старте.
Двухуровневость фреймворка становится видимой в системе типов.

### Спецификация

**Словарь билдера:**

| Метод | Когда | ctx |
|---|---|---|
| `.pre(u)` | до хендлера, по порядку объявления | накопленный, полный |
| `.ok(u)` | ответ = `Ok` | **полный** (свой слой + внешние) |
| `.catch(u)` | ответ = `Fail` | свой слой `Partial`, внешние полные |
| ~~`.after(u)`~~ | ~~всегда на ответном тракте~~ | ~~свой слой `Partial`, внешние полные~~ — СУПЕРСИД: убран, см. [2026-07-10] «отказ от `.after`» |
| `.finally(u)` | момент (c), с исходом | как catch + `outcome` |

**Исполнение (один слой):** pre по порядку; падение ⇒ сразу ответная фаза
с `Fail`. Хендлер — если все pre прошли. Ответная фаза — строго в порядке
объявления, юнит применяется по применимости к ТЕКУЩЕМУ ответу и может
его заменить. `finally` — после того как всё дотекло
(`completed | disconnected | aborted | failed`).

**Слои (композиция).** Пайплайн — стек слоёв. Один вызов `makePipeline()`
с цепочкой методов определяет ОДИН слой. Композиция — `compose(outer, ..., inner)`:
список слоёв, читается сверху вниз как «снаружи внутрь» (= порядок в `explain()`).
Понятий «дырка»/«слот»/пустых маркеров нет: плоский однослойный пайплайн —
частный случай. Вложение (`base` оборачивает `authed` оборачивает `mutating`):

- pre-тракты исполняются снаружи внутрь, ответные — изнутри наружу,
  `finally` — изнутри наружу;
- слой исполняется, только если pre всех внешних слоёв прошли ⇒
  **ответные юниты слоя видят контекст внешних слоёв полным
  и гарантированным**; Partial — только для pre собственного слоя;
- требования слоя к внешнему контексту объявляются явно:
  `makePipeline<{ identity: User }>()` — и проверяются компилятором
  в точке композиции.

**Type-state билдера:** `.pre` недоступен после первого ответного метода
(чтение сверху вниз = порядок исполнения, всегда).

**Ограничения v1 (осознанные):**

- **Нет раннего успешного выхода** (gate: кэш, идемпотентность) и
  **нет восстановления в catch** (`Fail → Ok`). Причина: оба ломают
  гарантию полного ctx у `.ok` («успех приходит только из хендлера»).
  Сильная типизация важнее; gate — кандидат в v2 с правилом
  «`.ok` до первого `.catch` — полный ctx, после — Partial».

**Юниты — четыре формы:**

| Форма | TNeeds | Использование |
|---|---|---|
| функция | — | базовый случай |
| инстанс (`new WithTracing(...)`) | — | мост: класс без DI |
| класс (`WithTracing`) | +Constructor | App резолвит из контейнера на старте |
| токен (`RateLimit('strict')`) | +Token | конфигурируемые юниты через token families |

Классы — обычные провайдеры: `@Injectable([deps])`, lifecycle-хуки,
регистрация в модуле, ошибка на старте если не зарегистрирован.
Контракт: юнит — синглтон, per-request состояние только в ctx.

**Переиспользование:** пайплайн — иммутабельное значение. Инфраструктурные
модули экспортируют готовые пайплайны-константы и фабрики
(`authedWith(verifyFn)`). Подключение — только явное, в `makeEndpoint`.
Модули с endpoint'ами принимают пайплайн параметром фабрики:

```typescript
export const makeHealthcheckModule = (opts: { pipeline?: Pipeline<EmptyInput> }) =>
  makeAppModule({
    name: 'module:healthcheck',
    endpoints: [makeHealthEndpoint(opts.pipeline ?? makePipeline())],
  });
```

### Отвергнутые варианты (чтобы не возвращаться)

- **Koa-style `(ctx, next)`** — скрытый control flow, потеря типизации
  и анализируемости.
- **Луковица с LIFO без next (A)** — корректна, но post читается задом
  наперёд, error-маппер объявляется первым.
- **Два списка «тракт запроса / тракт ответа» (B)** — парные вещи
  (транзакция) разваливаются на половинки; гейтинг по активации требует
  value-парности; сложнее плоских фаз.
- **Буквальная вложенность `compose(a, compose(b, h))` (C)** — пирамида,
  боль вывода типов.
- **Именованные страты `.onRequest/.around/.onResponse` (D)** — фиксируют
  структуру, теряется контроль глубины.
- **Уровни привязки App/module/endpoint** — отложенная сборка = потеря
  compile-time проверок; неявность «что навешано на ручку».
- **`after(fn, { successOnly: true })`** — опция, меняющая тип ctx.
- **`.then`** — thenable-ловушка.

### Уточнения (сессия 2026-07-08/09): границы, вычитания, explain

**Граница «pipeline = значения, transport = байты».** Сжатие, CORS,
content-negotiation — **не** pipeline, а транспорт (он про байты); pipeline
оперирует только абстрактными значениями. Эта линия сама отвечает на половину
вопросов «куда положить X». Следствие для ответного тракта: `.ok/.after/.catch`
**не меняют тип value** — иначе output-схема перестаёт описывать провод (рушится
schema-first). Глобальный конверт `{data, meta}` — часть схемы или опция
сериализации транспорта, **не** юнит пайплайна.

**Отвергнуто: retry/timeout как обёртка вокруг хендлера.** Осознанная цена отказа
от onion: `middleware-retry`/`middleware-timeout` написать нельзя. И не нужно — это
**декларативные опции endpoint'а** (`timeout: 5000`, `retry: {...}`), которые
исполняет оркестратор. Декларативно = видно в метаданных = попадает в доки и
визуализацию.

**Словарь и вычитания против Nest.** Слово «middleware» из фреймворка убрано: оно
врёт дважды (подразумевает wrapping и `next()`, а нет ни того, ни другого). Честный
словарь — препроцессоры (`.pre`), постпроцессоры (`.ok`/`.after`), обработчики
ошибок (`.catch`). Отдельного механизма «exception filters» (как в Nest) **нет** —
централизованный маппинг ошибок это обычный `.catch`-юнит. Тонкость: сам `.catch`
принимает функцию/класс с определённой сигнатурой, и эта сигнатура/интерфейс **и
есть** по сути exception filter — просто под другим именем. Отвергнута не
концепция, а отдельная подсистема и нестовское имя. Рабочее имя типа/декоратора —
`Catch` или `CatchHandler` (открыто).

**`pipeline.explain()` — заявленная часть API** (не мелочь). Печатает план
исполнения: дерево фаз и слоёв с аннотациями (напр. `→ {identity: User}` в точке
композиции). Назначение тройное — отладка, документация, узел визуализации
(endpoint со своим пайплайном = разворачиваемый узел). На этом же интроспективном
значении держится ~~опциональный~~ startup policy-check («каждый пайплайн содержит
withRequestId») — *с 2026-07-14 часть V1, см. запись «Policy-check на собранном
графе»*.

**Отложенные мелочи.** `pipeline.resolve([[Class, instance]])` — сахар вручную
погасить `TNeeds` (классы-юниты → инстансы) для standalone-использования
библиотечного пайплайна без App. ~~`detached: true` на endpoint'е — opt-out
потенциального «дефолтного» пайплайна (напр. healthcheck без общих юнитов): уровни
App/модуля отвергнуты, но точечный opt-out — открытая дверь на потом~~ —
РЕШЕНО 2026-07-14: `detached: '<причина>'` входит в V1 (строка-причина
обязательна), см. запись «Policy-check на собранном графе».

## [2026-07-06] Два скоупа обработки: request-pipeline и item-цепочки

### Логика решения

Первый подход к per-chunk логике — обёртки итераторов внутри request-юнитов
(same-type re-add `payload` в pre; type-preserving обёртка `res.value` в after).
Технически работает и даже разрешён текущей типовой машинерией
(`ConflictingKeys` допускает повтор ключа с тем же типом), но: смешивает два
скоупа в одной конструкции, требует хака «состояние счётчиков в мутируемом
ctx-объекте», вынуждает generic-гимнастику (`makePipeline<{payload:
Chunks<unknown>}>()`).

Осознание: у стримов/ивентов **два разных «пайплайна»** — действия на весь
поток (соединение) и действия на каждый элемент. Это разные конструкции
с разной формой, и им нужны разные механизмы.

### Спецификация

| | Request-scope | Item-scope (chunk/event) |
|---|---|---|
| Запускается | раз на запрос/соединение | на каждый элемент потока |
| Форма | фазы `.pre/.ok/.catch/.after/.finally` | линейная цепочка комбинаторов, **фаз нет** |
| Где объявлен | `pipeline: compose(...)` | на io-декларации `stream()`/`events()` |
| Состояние | ctx | внутри цепочки; стандартные счётчики → `summary` |

У элемента нет «хендлера посередине» и нет запроса-ответа — он просто течёт
через последовательность трансформаций. Поэтому никакого словаря фаз:

```typescript
input: stream(LogChunk)
  .tap(c => log.debug(c.message))     // наблюдение
  .filter(c => c.level !== 'debug')   // T → T
  .limit(50_000)                      // Fail при превышении
  .gapTimeout(30_000)                 // разрыв при молчании
  .batch(100),                        // тип-меняющий: хендлер получит Chunks<LogChunk[]>

output: events(OrderEvent)
  .tap(e => metrics.inc('events_out'))
  .throttle(10),                      // только T → T
```

**Асимметрия входа и выхода** (следствие schema-first, а не запрет):

- входная цепочка МОЖЕТ менять тип — она видимая часть контракта endpoint'а:
  схема описывает провод (NDJSON-строка = `LogChunk`), результат цепочки —
  форму хендлера;
- выходная цепочка — только `T → T`: оба её конца зафиксированы
  (хендлер yield'ит по output-схеме, схема описывает провод).

**Правила:**

- Ошибки item-цепочки эскалируют в request-pipeline: комбинатор бросил `Fail`
  → итерация в хендлере кинула → обычные `catch`/`finally`. Если выход уже
  тёк — mid-stream политика транспорта + `finally(failed)`.
- Состояние — внутри цепочки; фреймворк кладёт стандартные метрики
  (`itemsIn/itemsOut/bytes`) в `summary` для `finally`. Хак «счётчики
  в мутируемом ctx» умер вместе с первым подходом.
- Переиспользование — функции-хелперы:
  `const guardedStream = (s) => stream(s).limit(50_000).gapTimeout(30_000)`.
- Escape hatch: `.through(src => wrapped)` — на входе можно с изменением
  типа, на выходе `T → T`.
- **Per-connection vs per-published-event:** item-цепочка работает на копии
  потока ОДНОГО клиента (100 подписчиков → `.tap` сработает 100 раз на одно
  опубликованное событие). Логика «один раз на публикацию» живёт у источника —
  в `Topic`/хабе (DI-сервис), до всяких подписчиков.

### Не переизобретаем ли мы RxJS? (принцип-ограничитель)

Поверхностно похоже (цепочки операторов над потоками), по сути — нет,
и вот дисциплина, которая удерживает границу:

1. **Протокол на границах — стандартный `AsyncIterable`**, не библиотечный
   тип. Pull-модель со встроенным backpressure (медленный клиент просто
   не тянет) — естественная для сервера, в отличие от push-модели Observable,
   где backpressure надо докручивать. Ноль зависимостей; sync iterator
   helpers уже в языке, async-версия идёт через TC39 — мы движемся туда же,
   куда стандартная библиотека.
2. **Набор комбинаторов закрытый и инфраструктурный**: наблюдение, отсечение,
   лимиты, время, группировка. Лакмус: комбинаторы с реордерингом времени,
   слиянием потоков и higher-order streams (`merge`, `switchMap`,
   `combineLatest`) в фреймворк НЕ входят. Это dataflow-программирование —
   место ему в хендлере, где пользователь волен взять хоть RxJS
   (интероп тривиален: `from(asyncIterable)` и обратно).
3. **`Topic` ≈ Subject-lite осознанно**: маленький примитив (bounded buffer
   + AbortSignal), а не парадигма. Антипример перед глазами — Nest, намертво
   прикованный к RxJS через интерцепторы: RxJS навязан всем, а со стримами
   всё равно неловко.

Документация с полными примерами (мостики, отмена, backpressure,
функциональный и классовый стили): [design/rxjs.md](../history/superseded/rxjs-design-page.md).

### Открытые вопросы (сводно по pipeline v2 и item-цепочкам)

- DI в комбинаторах item-цепочки: io-декларация создаётся вне контейнера.
  v1: комбинаторы — функции/замыкания; логике с DI — request-юнит
  (advanced-путь через обёртку) или хендлер.
- Политика невалидного элемента: `onInvalid: 'skip' | 'fail'` (v1: fail).
- ~~Синтаксис композиции~~ — РЕШЕНО: `compose(outer, ..., inner)`.
  Пустой маркер `.slot()` отвергнут: позиция «дырки» выводима (между
  последним `.pre` и первым ответным методом), маркер без семантики — шум.
- Gate / ранний успешный выход — v2.
- Политика `Topic` для медленного подписчика.
- ~~Policy-check на старте («каждый пайплайн содержит X») — дверь открыта,
  не закладываем~~ — РЕШЕНО 2026-07-14: часть V1, см. «Policy-check на
  собранном графе».
- Per-transport дефолтные пайплайны — место есть, решение отложено.

## [2026-07-08] Модульный монолит: фичи, `select`, дискавери из дерева модулей

Полная логика сессии: [discussions/05](../history/discussions/05-modular-monolith-features-ports.md).
Целевые примеры и схема жизненного цикла: [design/composition-and-lifecycle](../history/superseded/composition-and-lifecycle.md).

### Контекст

Гипотеза: перспективный способ структурировать проекты до ~1M строк — модульный
монолит с запуском выбранного подмножества фич (`--features=all` локально,
отдельные фичи по процессам в проде). nestling подходит из-за двух уже принятых
свойств: **модули — plain values** (⇒ фича = значение, выбор подмножества =
фильтрация массива в композиционном корне) и **жадный контейнер** (⇒ «не выбрал
фичу → её провайдеры не построились» само собой). ~80% модели бесплатны.

### Решение

- **Фича** = `makeFeature({ name, modules, dependsOn })` — бандл модулей, тоже
  значение. Селектор замыкает `dependsOn`, отдаёт модули выбранных фич в контейнер.
  Ноль новой машинерии контейнера.
- **`assemble(...)`** — надстройка над `new App({ modules, transports })` с
  опциональными полями. Приложение из одной фичи **выглядит так, будто фич нет**
  (L0 не упоминает `feature`/`select`/`port`). Слои аддитивны (L0 модули → L1
  конфиг → L2 фичи+select → L3 порты co-located → L3→L4 split; между L3 и L4 код
  фич не меняется).
- **Дискавери эндпоинтов/транспортов — обходом дерева зарегистрированных модулей**,
  НЕ из глобального registry. Предпосылка №1 и одновременно баг-фикс.

### Отвергнутые варианты

- **Глобальный registry эндпоинтов как источник дискавери**
  (`endpoint-registry.ts` — модульный `Set`, `@Endpoint` сам-регистрируется при
  импорте). Протекает при любом транзитивном импорте, ломает выбор подмножества:
  импортнул файл фичи → её эндпоинты в Set → `App.#registerEndpoints` пытается их
  инстанцировать и падает. Дискавери ортогонален выбору. → обход дерева модулей.
- **«Набор транспортов» как отдельная ось конфига** — отвергнута: транспорты стали
  провайдерами, «какие транспорты существуют» выводится из `select`
  (см. запись про жизненный цикл ниже). Capability negotiation растворяется в
  DI + fail-fast.

## [2026-07-08] Порты: межфичевое общение через контракты

### Контекст

Как фичи общаются, определяет, будет ли монолит **splittable** или превратится в
distributed monolith. Два регистра одного call-site A→B: co-located (через DI,
синхронно, транзакционно) и split (сеть, async, может упасть). «Масштабировать
функции независимо» ⇒ один call-site должен работать в обоих режимах без
переписывания A (location transparency), а она в лоб противоречит принципу «no
runtime magic».

### Решение

- **Разрешение противоречия:** индиректность резолвится **на сборке, а не на
  запросе**. Порт биндится на local-клиент или remote-клиент в композиционном
  корне (по выбору фич + топологии); на запросе A зовёт конкретную константу.
  «Жадная композиция константами».
- **Половина портов уже есть.** Inbound («обрабатываю контракт») = **буквально
  endpoint** (`App` роутит по `metadata.transport`). Outbound («зову контракт») =
  единственное новое: типизированный клиент.
- **Контракт** — общее направление-нейтральное значение
  `makeContract({ name, kind, input, output })`. Три вида: `request` (req-reply,
  Fail-able, 1 владелец), `command` (fire-and-forget, 1 обработчик, queue-group),
  `event` (broadcast, 0..N). Различие command/event нужно для горизонтального
  масштабирования: N реплик = одна queue-group = нагрузка делится.
- **API:** владелец реализует контракт как endpoint; потребитель инжектит
  `Contract.port` / `Contract.emitter`, зовёт `.call(input, meta): Promise<Ok|Fail>`
  / `.emit(payload)`. Всегда async + Fail-able, **даже co-located** (завтра —
  сеть). Тип call-site у co-located и split идентичен.
- **Инфра:** ядро зависит от `IMessageTransport` (`request`/`publish`/`subscribe` —
  LCD). Реализации: `InProcessBus` (Map, zero-dep) и `@nestling/transport.nats`.
- **Диспатч — политика на сборке**, не зашивка: `local-first` / `always-remote`
  («всё — сообщение») / `balanced` (client-side spill). `local-first`/
  `always-remote` → одна константа-клиент на старте; только `balanced` — рантайм.
  Смена политики = смена конфига, call-site не меняется. `always-remote` в dev =
  in-proc-simulated шина (async + сериализация), не поднятый NATS.

### Дисциплина (жёсткая)

- **Порты никогда не транзакционны, даже co-located** — иначе общая транзакция
  ломается при split.
- **Локальный порт обязан уметь падать** (`Ok|Fail`) — иначе потребители не
  обработают `Fail`, и split их убьёт.
- Кросс-фичевая согласованность = события + outbox/saga, не общая транзакция.

### Отвергнутые варианты

- **Синхронный `request` как дефолт кросс-фичевого общения** — временна́я
  связанность, каскадные отказы (distributed monolith). Здоровее — событийный
  дефолт; `request` — для честных запросов.
- **Прибивание к NATS** — ядро знает только `IMessageTransport`; NATS —
  отдельный пакет как `transport.http`; NATS-specific (JetStream KV, wildcard,
  ack) не протекает в контрактный API (дисциплина границы, как с RxJS).
- **Дихотомия `messaging` / `transports`** — ложная: NATS это транспорт с двумя
  способностями (`InboundTransport` + `OutboundTransport`), один мешок.
- **`messaging: NATS_URL ? nats() : undefined`** — тернарник враньё: конфиг
  транспортов статичен и одинаков для всех процессов развёртывания, меняется
  только `select`; разница «локально/прод» — в конфиге, не в коде.

## [2026-07-08] Жизненный цикл: фазы, `@OnStart`/go-live, гарантия `dispatch`

### Контекст

Транспорты, будучи синглтонами с зависимостями и lifecycle, должны быть
**провайдерами** (как всё остальное), а не мешком `transports: Record` в
конструкторе `App`. Тогда «какие транспорты существуют» выводится из `select`,
endpoint ссылается на транспорт токеном (не строкой), capability negotiation =
DI + fail-fast. Но это вскрывает: **go-live — отдельная фаза** от init.

### Решение

Фазы жизненного цикла:

```
0 BOOTSTRAP  load+validate config · select     → FAIL-FAST
1 ASSEMBLE   build граф · discover · bind ports → FAIL-FAST
2 INIT       @OnInit: захват ресурсов · connect · dispatch НЕ существует
3 WIRE       регистрация эндпоинтов · dispatch РОЖДАЕТСЯ здесь
4 START      @OnStart: serve(dispatch, signal) — НЕ listen()
5 RUN        port.call/emit → local | bus · live config-refs
6 SHUTDOWN   реверс START · abort in-flight (meta.signal) · @OnDestroy
```

- **`@OnStart`** добавляется к `@OnInit`, чтобы «wiring между init и start» стал
  **гарантией графа**: `@OnInit` = захватить ресурс (connect); регистрация
  эндпоинтов — между; `serve`/go-live — на `@OnStart`.
- **Гарантия «`listen` на `@OnInit` невозможен»** держится структурно: у транспорта
  **нет nullary `listen()`**; уйти в эфир можно только приняв **готовый
  `dispatch`** (`serve(dispatch, signal)`), а `dispatch` — фазовый ресурс,
  рождается в WIRE. Транспорт — переводчик провода, не владелец роутинга; раннему
  listen нечего маршрутизировать. START по топосорту, SHUTDOWN строго в реверсе.

### Отвергнутые варианты

- **Транспорты мешком в конструкторе** (`transports: Record<string, ITransport>`) —
  дублирует контейнер (зависимости не инжектнуть, lifecycle гоняется руками).
- **`listen()` как nullary-метод транспорта** — footgun: разработчик повесит его
  на `@OnInit`, конвенция не спасёт. По стандарту «guarantee over convention» —
  убрать возможность (dispatch-как-обязательный-аргумент). Инверсия акцептора
  (фреймворк владеет сокетом, транспорт = `(req)=>res`) — level-3, опция для
  транспортов, где акцептор естественно отдаётся фреймворку (HTTP), хуже для
  pub/sub.
- **Слить WIRE в ASSEMBLE** (собрать `dispatch` на build) — сломает гарантию:
  `dispatch` станет доступен слишком рано. Порядок 2→3→4 несущий.

## [2026-07-08] Kernel/user space; конфиг как token-families; плагины

### Контекст

Конфиг rsdk-стиля (`Config`-классы + `@Property`) многословен → идём в
`makeConfig(schema)`. Но это тянет за собой вопросы: как конфиги мержатся, куда
инжектятся, нужна ли отдельная стадия конфигурации, что живёт в «глобальном»
конфиге, и как всё это соотносится с on-demand-инфраструктурой (клиенты, плагины).

### Решение 1: kernel / user space

Граница как в ОС. **Kernel space** (токены **не** экспортируются): `ConfigSource`/
readers, транспорты, bus/port-client, машинерия графа. **User space**: сервисы,
endpoints, контракты, конфиг-как-данные. Граница пересекается только через
публичные «syscalls»: инжект `Config<X>`, `Port/Emitter`, возврат из endpoint.
**Enforcement — видимость ES-модулей, не рантайм-ACL** (не экспортировал токен →
нечем инжектить). Декларативный `makeConfig(schema)` делает провайдер конфига
фреймворк-генерируемым ⇒ источник **не протекает в user-space вообще** —
декларативность улучшает инкапсуляцию.

### Решение 2: конфиг — частный случай token-families (sources убраны)

- Конфиг-свойство = член семейства `Config(key)`, читает значение из **одной
  центральной читалки**, настраиваемой только в composition root. Это **не
  обычный провайдер** (их много, приносят модули) — она одна на приложение,
  библиотеки её не трогают и не знают, откуда конфиг. Дефолт — env.
  **Прогрессивно:** только `.env` → в корне про конфиг ничего не пишешь; появился
  второй источник (волт/файл) → в корне привязываешь конфиги/ключи к нему
  (порядок + переопределения). Библиотеки не меняются. Точный синтаксис привязки —
  открыт (варианты обкатываются).
- `makeConfig('prefix', schema)` — сахар: объявляет свойства (в реестр → доки) и
  проецирует в типизированный объект. **Source-agnostic**: называет ключ, не
  источник (провенанс — kernel-концерн; конфиг слеп, как чтение `fd`).
- **On-demand клиенты и «unbound properties»** (grpc-адрес из env) — тот же
  механизм: `GrpcClient(server)` — член семейства, транзитивно тянет
  `Config(addressKey(server))`. Инжектнул клиент → env-адрес пришёл сам. Жадный
  билдер видит запрошенные члены статически → инстанцирует на build (без
  рантайм-резолюции, в отличие от ленивого rsdk). Runtime-параметр (адрес из БД) —
  не семейство, а фабрика (`GrpcClientFactory.create(addr)`, вне жадного графа).
- **Стадия конфигурации не нужна как хук.** Конфиг — зависимость, не фаза: readers
  → `Config(key)` → секции → потребители — топологический слой того же графа
  (запрет циклов защищает бутстрап). Жадный контейнер даёт eager-валидацию и
  fail-fast бесплатно. `select` — единственное пред-сборочное чтение
  (примордиальный env).
- **Reloadable** — свойство узла (`onChange(signal, cb)` / read-latest). Асимметрия:
  старт-невалидный → die; reload-невалидный → keep last-good + warn; вступит ли в
  силу — ответственность потребителя (opt-in).

### Решение 3: плагины = композируемая kernel-инфраструктура

Плагин (cross-cutting инфра: Redis, HTTP-клиенты, валидация) в nestling **не новый
примитив**, а параметризованный инфра-модуль (`redis()` — функция → модуль,
провайдер `RedisClient` синглтон в процессе). «Глобальность» ≠ ambient-инжект:
провайдер в корне, но инжект требует импорта токена (ES-видимость цела). Конфиг
плагина — секция, которую он везёт. С фичами:

- **feature-scoped инфра** (Redis для кэш-фичи) — фича импортирует инфра-модуль →
  **едет с фичей** при split; co-located фичи делят один синглтон, split —
  отдельные клиенты per-process (бесплатно от контейнера);
- ~~**ambient cross-cutting** (логирование, трейсинг) — тонкий root-bag
  `assemble({ plugins: [...] })`, в каждом процессе.~~ — **СУПЕРСИД 2026-07-31**
  (change `plugins`, #13): поля `plugins:` не будет — root-bag тождественен
  `modules:` корня, а два поля с одной семантикой заставляли бы выбирать между
  ними на каждом инфра-модуле. Ambient-инфраструктура объявляется теми же
  `modules:`/`providers:` корня; перечень полей `assemble` закрыт. Там же
  идентичность модуля стала **значением**: то же значение схлопывается,
  два разных под одним именем — ошибка сборки, а не тихая победа первого
  ([design/composition.md §5](../design/composition.md),
  [design/container.md](../design/container.md)).

### Отвергнутые варианты

- **Class-конфиги rsdk** — многословно; и хуже инкапсулируют (источник подтекает в
  пользовательский класс).
- **`OnConfiguration`-хук** — избыточен и строго хуже зависимости (хук — барьер
  «весь конфиг → весь init»; зависимость даёт точную топологию). Каждый его смысл
  уходит в фазу-0 / построение провайдера / `@OnInit` потребителя / reload-событие.
- **Connection strings как «структурный» конфиг** — ошибка склейки двух осей
  (форма графа vs re-init стоимость). URL узла БД не меняет форму графа; «нужен
  рестарт» — свойство держателя (пул), не конфига. Всё, кроме `select` +
  source-bootstrap, — обычный provider-config.
- **Source-per-field (`env('KEY')` в поле)** — протаскивает kernel-концерн
  (провенанс) в user-space; ломает единый precedence и reload. → source-agnostic
  ключи + readers в recipe.
- **`sources: [...]` bag / merged `Vars` как отдельная подсистема** — источники
  кроме env производны (путь/адрес из env) и нужны не всегда ⇒ readers-провайдеры +
  config-family; bag убран. (Промежуточный вариант «sources как провайдеры →
  merged Vars» тоже отвергнут в пользу per-property family.)
- **Ambient middleware от плагина** (`configureMiddleware` на все роуты) —
  противоречит pipeline-v2 (уровни App/module отвергнуты). Взамен: плагин
  **экспортирует pipeline-слой**, endpoint композирует явно; вездесущность —
  конвенция + опциональный startup policy-check. *(С 2026-07-14 вездесущность
  — не конвенция, а гарантия: `policies:` на собранном графе, см. запись
  «Policy-check на собранном графе».)*

## [2026-07-10] Multi-injection через token families: `Family.all`

### Контекст

Multi-injection — инжект массива вкладов, которые независимо регистрируются
разными модулями (health checks, миграции, валидаторы, обработчики событий).
Это обратная задача к `familyProvider`: там **один рецепт → много членов**,
и потребитель знает параметр (`ILogger('users')`); тут **много явных
провайдеров → один потребитель-агрегатор**, который состава не знает.

Сегодня задача решается либо центральным списком deps в агрегирующей фабрике
(каждый вклад — правка центрального места), либо side-effect-реестром
(`Set` при импорте) — паттерном, уже отвергнутым при дискавери эндпоинтов
([discussions/05 §1](../history/discussions/05-modular-monolith-features-ports.md)).

Наблюдение: дизайн `token-families` (change 5) уже покрывает бо́льшую часть
задачи, ничего не меняя:

- **члены с явными провайдерами легальны** — материализация deps-only
  срабатывает только для членов *без* провайдера; вклад = обычный провайдер
  с членским токеном: `classProvider(IHealthCheck('db'), DbHealthCheck)`;
- **реестр семейства** (design D3) даёт билдеру ответ «какие зарегистрированные
  провайдеры — члены семейства F» без парсинга id;
- **уникальные членские токены сохраняют инвариант «один токен — один узел»** —
  в отличие от Angular-стиля `multi: true`, где несколько провайдеров делят
  токен и теряют индивидуальную адресуемость.

Не хватает одного примитива — агрегирующего токена.

### Решение: `Family.all`

```typescript
export const IHealthCheck = makeTokenFamily<HealthCheck, [name: string]>('HealthCheck');

// вклады — ОБЫЧНЫЕ провайдеры, каждый в своём модуле:
// db.module:    classProvider(IHealthCheck('db'), DbHealthCheck)
// redis.module: classProvider(IHealthCheck('redis'), RedisHealthCheck)

// агрегатор инжектит массив, не зная состава:
@Injectable([IHealthCheck.all])
class HealthEndpoint {
  constructor(private checks: HealthCheck[]) {}
}
```

- `Family.all` — сентинел, типизированный как `TokenString<T[]>`; симметричен
  `.auto` (design D6), но резолвится **на `build()`** (состав известен только
  после всех регистраций и фикспоинта материализации), а не при декорировании.
- Билдер создаёт **синтетический узел-агрегат**: deps = все зарегистрированные
  + материализованные члены семейства, значение — массив их инстансов. Узел
  обычный: циклы, топологический init/destroy, визуализация — как у всех.
  Никакой рантайм-резолюции.
- `.all` **не форсит материализацию** открытого пространства параметров:
  агрегат считается после фикспоинта из явно зарегистрированных членов +
  членов, материализованных из deps. Рецепт семейству не обязателен.
- **Синергия с модульным монолитом**: состав массива = что зарегистрировано в
  контейнере ⇒ «не выбрал фичу → её вкладов нет в массиве» — само собой, тем
  же механизмом, что «не выбрал фичу → её провайдеры не построились».
- **`strictExports`**: рёбра агрегата к членам чужих модулей требуют
  `exports: [IHealthCheck]` — явный контракт «модуль контрибьютит в семейство».
- Реализация — **отдельный аддитивный change поверх `token-families`**
  (roadmap #14); v1 семейств не трогаем — там уже всё совместимо.

### Отвергнутые варианты

- **`multi: true` на одном токене** (Angular-стиль) — ломает «один токен —
  один узел», теряет индивидуальную адресуемость вкладов (нельзя запросить
  конкретный `IHealthCheck('db')`) и module-атрибуцию.
- **Центральный список deps в агрегирующей фабрике** — работает уже сейчас,
  но каждый вклад требует правки центрального места; убивает смысл
  multi-injection.
- **Side-effect-реестр** (`Set` при импорте) — протекает при транзитивном
  импорте, ломает выбор подмножества фич; уже отвергнут в d/05 §1.
- **Рантайм-резолюция «отдай всех, кого найдёшь»** — разрушает полный граф,
  топологический init/destroy и проверку циклов.

### Открытые вопросы

  позже, аддитивно.~~ — **РЕШЕНО 2026-07-29** (change `multi-injection`, D7):

## [2026-07-10] Модель ошибок: Fail — значение, code-идентичность, `defineFail`, ошибки в контракте

### Контекст

Чтение превью документации показало, что модель ошибок недожата. Ориентиром
смотрели rsdk (`packages/core/src/exceptions`): иерархия классов
`PlatformException` (code, severity, cause, details) → `PipelineException`
(+ `kind` — транспортно-нейтральная семантика: INPUT/CONFLICT/NOT_FOUND/…) →
конкретные исключения; per-transport форматтеры мапят kind → HTTP-статус /
gRPC-код; метаданные — декораторы `@Exception` (доки) и `@Throws`
(реестр-конвенция, без гарантии).

Состояние nestling: `Fail extends Error` с плоским `ErrorStatus`. Дыры:

1. **Словарь статусов дырявый и HTTP-скошенный**: нет `CONFLICT`, `TIMEOUT`,
   `TOO_MANY_REQUESTS`. Показательно: пример в превью писал
   `Fail.badRequest('Email already taken')` — семантически это конфликт;
   автор вынужден врать, потому что словаря не хватает.
2. **Нет `cause`** — обёртывания исходной ошибки (ES2022 `Error` уже умеет).
3. **Нет `code`** — стабильного машинного кода для клиента. Статус отвечает
   «как отвечать транспорту», code — «что именно случилось»; разные оси.
4. **Нет доменного слоя** — все бросают анонимные `Fail.notFound('...')`.
5. **Трёхслойное расхождение Ok|Fail**: превью обещает Result-семантику
   (`return charge`, `charge.isFail`), типы её не знают
   (`Output<T> = Promise<Ok<T> | T>` — `Fail` в возврате не участвует,
   поля `isFail` не существует), а рантайм (`normalizeResponse` в
   `pipeline.ts`) знает только `instanceof Ok` → возвращённый `Fail`
   уедет клиенту как `200 OK` с сериализованным Fail в теле.

### Решение 1: Fail — значение; throw — легальный ранний выход

Rust-рамка (`Result` + `panic!`), спроецированная на JS: ожидаемый отказ
домена (`Fail`) ходит как значение — хоть возвратом, хоть броском; брошенный
не-`Fail` — «паника» (`INTERNAL_ERROR`, детали скрыты — уже так). `throw` —
механизм транспортировки значения (в JS нет `?`-оператора), а не семантика.

- `Output<T> = Promise<Ok<T> | Fail | T>` (и `OutputSync` симметрично);
- дискриминант `isFail: true as const` на `Fail` / `false` на `Ok` —
  сериализуемый, в отличие от `instanceof`;
- рантайм: в `normalizeResponse` ветка `instanceof Fail` → error-track
  **до** `.ok`-юнитов — инвариант «`.ok` видит только успех» сохраняется;
- правило для человека: **свой отказ — `throw` (ранний выход из глубины),
  чужой — `return` (проброс отказа порта)**;
- `Fail extends Error` остаётся: стек для throw-пути бесплатно, return-пути
  не мешает.

### Решение 2: словарь + `code` + `cause`

- дополнить `ErrorStatus` семантикой: `CONFLICT`, `TIMEOUT`,
  `TOO_MANY_REQUESTS`; маппинг на провод — забота транспорта (как сейчас);
- `Fail` получает `code?: string` (стабильный машинный код,
  `'ORDER_NOT_FOUND'`) и `cause?: unknown`;
- формат на проводе (`ErrorDetails`): + `code` (+ `requestId` — см. запись
  про асинхронный контекст ниже).

### Решение 3: доменные ошибки — `defineFail`, идентичность по code

Не иерархия классов + декораторы (идиома rsdk), а значения + schema-first:

```typescript
export const OrderNotFound = defineFail('ORDER_NOT_FOUND', {
  status: 'NOT_FOUND',
  message: (id: string) => `Order ${id} not found`,
  details: z.object({ orderId: z.string() }), // schema-first — и для details
});

throw OrderNotFound('42');
// в .catch-юните:
if (OrderNotFound.is(res)) { /* ... */ }     // матчинг по code
```

Идентичность — по `code`, не по `instanceof`: `Fail`, прилетевший от
remote-порта, — десериализованные данные, класс на них мёртв, `code`
выживает на проводе. Правило для порт-клиента: remote-отказ
**ре-гидрируется** в настоящий `Fail` на клиентской стороне.

### Решение 4: ошибки — часть контракта endpoint'а

`errors: [EmailTaken, OrderLimitReached]` в декларации endpoint'а/контракта:
OpenAPI-доки бесплатно; потребители порта знают, какие отказы ждать.
rsdk-идея `@Throws`, но как контракт, а не конвенция.

Гарантия двухуровневая — честное следствие «throw — легальный путь»
(уточнено 2026-07-10, после вопроса «как затипизируем throw»):

- **компилятор** — всё, что течёт значениями. `defineFail` брендирует тип
  отказа (`Fail<'EMAIL_TAKEN'>`); `Output<T, E>` сверяет `return` с
  декларацией — в т.ч. проброс отказа порта: чужой `Fail` не пролезет в
  ответ, пока не задекларирован (контрактная честность цепочек). Ранний
  выход — типизированный бросатель **`meta.fail(e: E): never`**: принимает
  только задекларированные отказы, бросает внутри, `never` сохраняет control
  flow. Это второй зарезервированный ключ meta (как `signal`) — тип рождается
  из декларации endpoint'а;
- **рантайм на границе пайплайна** — остальное (прямой `throw`, отказы из
  глубины сервисов, JS-обходы типов): всё, что доехало до границы
  незадекларированным, **нормализуется в `UnknownError`** — встроенный
  `defineFail('UNKNOWN')` со статусом `INTERNAL_ERROR`. Оригинал целиком
  уходит в лог (с requestId), клиенту — generic-тело. Никакого
  «warn и пропустить»: это снова была бы конвенция. Итог: ответ endpoint'а —
  **закрытое множество** `E ∪ UnknownError`; `UnknownError` неявно входит в
  контракт каждого endpoint'а (default-ответ в OpenAPI).

Страж стоит **после всех `.catch`-юнитов**: `.catch` — легальное место, где
недекларированный (например, доменный из глубины) отказ превращается в
контрактный; нормализуется только то, что доехало до границы. Осознанный
трейд-офф: забытая декларация = `UnknownError` (500) вместо «случайно
работавшего» 404 — громко и сразу (в dev — первым же тестом), зато клиент
не успевает опереться на implicit contract, который сломается позже.

Почему бросатель живёт на meta, а не свободной функцией поверх ALS: система
типов лексична и статична, ALS — динамичен и стёрт в рантайме; тип не может
зависеть от того, «в каком запросе меня вызвали». Типизация течёт только
значениями (аргументы, генерики, замыкания) — и meta (накопленный контекст)
как раз и есть лексический канал от декларации endpoint'а к хендлеру.
Для глубоких сервисов ALS-fail был бы ещё и протечкой слоёв: домен не должен
знать контракт вызвавшего его endpoint'а — он бросает свои
`defineFail`-ошибки, а сверка с контрактом — забота границы.

### Отвергнутые варианты

- **Иерархия классов + декораторы (`@Exception`/`@Throws`, rsdk)** — чужеродна
  values-идиоме nestling; instanceof-идентичность ломается на проводе;
  реестр — конвенция без гарантии.
- **`severity` в ошибке** — концерн логгера, не ошибки.
- **Fail только throw** (NestJS-путь) — try/catch вокруг каждого вызова
  порта, нетипизированно, легко забыть; рушит L3/L4-историю «отказ порта —
  данные, не исключение».
- **Fail только return** (fp-ts/neverthrow) — без `?`-оператора каждый
  приватный хелпер тащит `| Fail` в сигнатуре, ранний выход умирает; запретить
  throw в JS всё равно нельзя — «только значение» тоже была бы конвенцией.
- **Двухслойность enum `kind` + статус** (rsdk) — не нужна: плоский
  семантический статус + per-transport маппинг достаточны.
- **Fail-хелпер поверх ALS** («типизировать throw через асинхронный
  контекст») — статически невозможно: тип не достаётся из динамики, ALS
  невидим для компилятора, сигнатура выродилась бы в `fail(e: Fail)` без
  сужения до декларации. Для глубоких сервисов — ещё и протечка контракта
  endpoint'а в домен. Рантайм-валидация в точке броска (чуть более точный
  стек) не окупает второй глобальный API.
- **Warn-and-pass на границе** (пропускать незадекларированный отказ с
  предупреждением) — контракт остаётся конвенцией: клиент опирается на
  случайно работающие незадекларированные ответы, и эта опора ломается
  непредсказуемо. Нормализация в `UnknownError` делает множество ответов
  закрытым.
- **`throws:`-декларации провайдеров + графовая проверка на `build()`**
  (rsdk `@Throws` с гарантией) — не нужны: гарантию контракта герметично
  даёт нормализация на границе. Проверка добавляла бы только раннее
  обнаружение забытых деклараций — ценой церемонии на каждом провайдере,
  ложных срабатываний (достижимость ≠ фактический вызов) и дыры в листьях
  (декларация всё равно может врать). Цена не окупается.

### Открытые вопросы

- `new Ok(fail)` типами не запрещён и уедет как успех — закрыть типом
  (`TValue extends Fail ? never : …`) или зафиксировать как «не делайте так».
- `Fail` посреди стрима — к streaming-v2, сейчас не обещаем.
- Точный API `defineFail`: форма message-фабрики, связь details-схемы с
  типом аргументов.
- ~~Форма привязки `E` к классовому endpoint'у~~ — СНЯТО: классовый стиль
  деклараций уходит, см. [2026-07-13] «Один канонический стиль деклараций».

## [2026-07-10] Асинхронный контекст: read-only ALS-проекция pipeline-контекста

> **РЕАЛИЗОВАНО 2026-07-31** — change `async-context` (#16 roadmap).
> Реализованы решения 1–6; решение 7 (`propagate` через remote-порты) уехало
> в #12 `transport.nats` — объявлять сериализацию в заголовки, пока нет
> второй стороны провода, нечем. Реализация **закрыла открытый вопрос
> «рантайм-декларация добавок»** и уточнила четыре вещи, не менявшие сути
> решения: (1) писатель — **`Var.provide(compute)`**, конструктор pre-юнита
> от самой переменной: добавку `{ [key]: T }` строит переменная, поэтому
> «объявлено» и «положено» — одно действие; рабочая гипотеза записи
> `RequestId.of(uuid)` **отвергнута** — брендированная добавка видна только
> в рантайме, на первом запросе, а проверка нужна на `build()`; отвергнуты
> и `expose`/`provides` в точке подключения — декларация, живущая отдельно
> от факта, вырождается в проверку комментария; (2) присутствие проверяет
> **предикат `hasVar(Var)`** того же словаря политик — по множеству
> объявленных переменных, накопленному пайплайном рядом с провенансом, а не
> выводом из достижимости `Ctx(X)` в графе (решение 5 в исходной формулировке
> требовало двух новых публичных поверхностей — публикации токенов
> декларации и транзитивного замыкания у `BuiltContainer` — и осталось
> отдельным аддитивным change'ом); (3) объявление — **двойным вызовом**
> `contextVar<T>()('key')`: ключ обязан остаться литералом, иначе `provide`
> не типизирует добавку, а частичного вывода тип-аргументов в TypeScript нет;
> (4) scope открывают **обе** точки исполнения ручки и отдельно потоковый
> путь — обёртка выходного итератора прокатывает каждый `next()` в той же
> ячейке, иначе ленивые генераторы и шаги item-цепочек оказывались бы вне
> проекции. Цена решения (1) документирована: юнит, кладущий поле «вручную»,
> для ридеров работает, а для `hasVar` невидим — ложное падение сборки,
> починка в одну строку. Отдельный пакет `@nestling/context` **не заведён**
> — см. пометку СУПЕРСИД в записи [2026-07-06].

### Контекст

Глубоким сервисам (логгер в репозитории тремя слоями ниже хендлера) нужны
requestId/traceId без протаскивания параметрами через все сигнатуры.
`@nestling/context` на AsyncLocalStorage уже был зарезервирован
([2026-07-06], решение 4 в записи про token families).

Ориентир-антипример — rsdk `actx`: статический `AsyncContext.get/set(key:
string)` поверх ALS-Map — глобал (зависимость не видна в DI-графе, боль в
тестах), нетипизированное присутствие (`get<V>` — каст), запись из любого
места (rewrite-guard в рантайме). Полезные идеи там же: `ContextEnricher` +
`IngressContext.run(carrier, fn)` — транспортно-нейтральное открытие scope,
`capture()` для отложенного кода.

Конфликт с принципом: ambient — имплицитность, у нас «explicit over
implicit». Но реальный выбор — не «магия vs без магии», а **«чья магия —
фреймворка с гарантиями или пользователя без»**: кривой ALS-Map команды
заводят сами. Плюс три вещи пользователь чисто сделать не может: открытие
scope вокруг запроса (место оркестратора), пропагация через remote-порты
(заголовки — концерн транспорта), интеграция с логированием.

### Решение

Формула: **значение едет ambient'ом, зависимость — явная; запись — монополия
pre-юнитов, ALS — read-only проекция**.

1. **`contextVar<T>('key')`** — branded-ключ, тот же паттерн, что
   `token<T>()`: compile-time тип + runtime-идентичность + флаг `propagate`
   (сериализация в заголовки для remote-портов).
2. **Обогащение — только pre-юниты** (как сейчас); накопительная типизация
   остаётся в пайплайне. ALS — не второй канал записи: оркестратор открывает
   scope на запрос, рантайм пайплайна (единственный писатель) обновляет
   cell — ссылку на текущий накопленный `input`.
3. **Доступ — инжектируемый ридер, член token family**: `Ctx(RequestId)` в
   deps → `CtxReader<string>`. Зависимость от request-контекста — видимое
   ребро DI-графа (визуализация, `explain()`, подмена в тестах через
   `valueProvider` — ALS не нужен). Свойство families «билдер видит все
   запрошенные члены статически» ⇒ полный список ambient-чтений приложения
   известен на `build()`.
4. **`get()` / `peek()`** — зеркало асимметрии пайплайна (полный контекст на
   успешном тракте, `Partial` на ответном): `get(): T` бросает с
   диагностикой — рантайм знает текущую фазу (она в том же ALS) и может
   сказать «вы в `.catch`-тракте, pre упал до `withRequestId` — используйте
   `peek()`»; `peek(): T | undefined` — для ответного тракта, `@OnStart`,
   cron и фоновых путей.
5. **Графовая проверка присутствия — opt-in policy-check** (как
   `strictExports`): каждый провайдер с `Ctx(X)` достижим только из
   endpoint'ов, чей пайплайн кладёт X. Упирается в type erasure: «что
   пайплайн предоставляет» существует только в типах ⇒ нужна
   рантайм-декларация добавок (форма — открытый вопрос).
6. **В cell — только `input`** (накопленный мешок) + `signal` как well-known
   var (`Ctx(Signal)`): отмена глубоко в сервисах — легитимная нужда. `raw`
   и `endpoint` в ambient не отдаём — протечка транспорта в домен.
7. **Порты**: in-proc ALS течёт сквозь `port.call()` сам (co-located фичи
   получают контекст без кода); remote — vars с `propagate: true` едут в
   заголовках (NATS), транспорт на той стороне вскрывает scope.

Связка с моделью ошибок: `.catch`/`.finally`/форматтер кладут `requestId` в
тело ошибки — корреляция ответа с логами без кода пользователя.

### Отвергнутые варианты

- **Статический `AsyncContext.get/set`** (rsdk) — глобал: невидим в
  DI-графе, нетестируем без ALS, присутствие не типизировано.
- **ALS как канал записи** (`set` + rewrite-guard) — второй механизм
  обогащения; запись остаётся монополией pre-юнитов, rewrite-guard не нужен
  by design.
- **Протаскивание requestId параметрами** — та боль, ради которой всё;
  на практике не делается.
- **Весь `ctx` в ambient** (включая `raw`/`endpoint`) — транспорт протекает
  в домен, ломает линию «pipeline ≠ транспорт».
- **Безусловная гарантия присутствия** — несостоятельна: ответный тракт
  (`Partial`), пути вне запроса (`@OnStart`, cron). Отсюда `get()/peek()` +
  opt-in policy-check вместо абсолютной статики.

### Открытые вопросы

- ~~**Рантайм-декларация добавок** для policy-check: `expose` в точке

## [2026-07-10] Pipeline: отказ от `.after`

### Логика решения

Повод — вопрос при написании документации: «в каком порядке исполняются
`after`/`ok`, `after`/`catch` и `finally`?» Честный ответ (`ok`/`catch`/`after` —
не три фазы, а ОДИН список в порядке объявления; юнит применяется по
применимости к ТЕКУЩЕМУ ответу; `finally` — отдельно и всегда последним)
не помещается в текст без абзаца оговорок. Это симптом лишней сущности,
а не недоработка формулировки.

1. **Ниша пустует.** После границы «pipeline = значения, transport = байты»
   и правила «ответный тракт не меняет тип value» у `.after` не осталось
   легитимной работы: наблюдение на любом исходе — `finally`, маппинг
   ошибок — `.catch`, обогащение успеха — `.ok`. Факт на момент решения:
   ни один middleware `nestling.pipeline`, ни один пример `.after`
   не используют — только спеки самого пакета.
2. **Выразительность не теряется.** Сигнатура `.after` совпадает с `.catch`
   (свой слой `Partial`), поэтому любой after-юнит записывается как
   `.ok(u).catch(u)` — две явные строчки. Тот же ход, которым умер
   «wrapper» (транзакция = `pre + ok + catch`): explicit over implicit.
3. **Словарь становится Promise-чистым.** `ok`/`catch`/`finally` — знакомая
   тройка (`then`/`catch`/`finally`); `.after` — единственный член без
   аналога, и именно вокруг него возникала путаница с порядком. Правило
   ответного тракта сжимается до одного предложения: «юниты исполняются
   в порядке объявления; `ok` применим к успеху, `catch` — к ошибке,
   ответ могут заменить; `finally` — всегда, последним».
4. **Асимметрия рисков.** Вернуть `.after` позже — обратно-совместимое
   добавление (если реальный кейс появится); убрать после релиза —
   breaking. Сейчас, при нуле использований, удаление почти бесплатно.

**Нюанс замены** (в док миграции): `.ok(u).catch(u)` ≠ `.after(u)` в одном
углу — если `u` в роли ok-юнита бросит, ответ станет ошибкой и `u`
исполнится второй раз уже как catch-юнит. С `.after` юнит исполнялся ровно
один раз. Вывод: функцию, которая может бросать, не регистрируют в обе
фазы одним значением.

### Спецификация (дельта к [2026-07-06] Pipeline v2)

- `.after(u)` удаляется из билдера, типов (`AfterUnitFn`) и рантайма
  (`ResponsePhase` = `'ok' | 'catch'`).
- Семантика ответного тракта не меняется: один список юнитов в порядке
  объявления, применимость по текущему ответу (ok-юнит бросил → ответ стал
  ошибкой → последующие `catch` применимы) — просто теперь она
  формулируется без третьего вида юнитов.
- Словарь: препроцессоры (`.pre`), постпроцессоры (`.ok`), обработчики
  ошибок (`.catch`), наблюдатель исхода (`.finally`).
- Упоминания `.after` в записях [2026-07-06] («словарь билдера»,
  «постпроцессоры (`.ok`/`.after`)», форма request-scope в сравнении
  с item-цепочками) — суперсид этой записью.

### Отвергнутые варианты

- **Оставить и «просто лучше задокументировать»** — документация была бы
  лечением симптома; сущность без использований и без незаменимых кейсов
  не оправдывает третий вид юнита в правиле порядка.
- **`after` как отдельная фаза после `ok`/`catch`** — делает порядок
  «предсказуемым», но ломает принцип «декларация читается сверху вниз =
  порядок исполнения» и добавляет вторую модель исполнения.

## [2026-07-10] Конфиг: keys-capability вместо `configs:`-владения

### Контекст

Разбор «а зачем вообще отдельный ключ `configs:`» показал: генерация провайдера,
eager-валидация и reload держатся на token family (билдер видит
`@Injectable([OrdersConfig])` статически, рецепт — фреймворковый), привязка — на
упоминании токена в корне. Единственное, что ключ добавляет графу, — **метку
владельца** для проверки приватности на `build()`. Сама проверка существует
из-за двойственности «токен referenceable в привязке, но не injectable чужим» —
один объект с двумя позиционными правами. А корню токен нужен только потому,
что привязка адресует секции токенами, — из-за этого токен экспортируется, и
неэкспортируемость (канонический kernel/user-механизм) перестаёт защищать.

### Решение

Разделить токен на две capability — у каждой ровно одно право:

- **инжект** — сам токен секции; он **не экспортируется из пакета** (приватность =
  видимость ES-модулей; чужой инжект невозможен синтаксически — нарушение нельзя
  даже написать);
- **привязка** — `OrdersConfig.keys`: экспортируемый хэндл набора ключей;
  инжектировать его нечем (не токен), поэтому экспорт безопасен.

Следствия:

- **ключ `configs:` у модуля удаляется**; владение как понятие уходит;
  проверка приватности на `build()` не нужна (нечего нарушать);
- **привязка в корне — по key-set-хэндлам и глобам**:
  `config: [[vault(), [ordersKeys]]]`. Слоистость чище: центральная читалка
  живёт в домене ключей, привязка по токену секции была лёгким нарушением слоёв.
  Плоский список / порядок = приоритет / env — неявный пол / прогрессивность —
  без изменений;
- **типизация ключей двухуровневая**: уровень 1 (несущий, фиксируем) — opaque
  branded `ConfigKeys<'orders'>` с рантайм-набором строк; уровень 2 (опция,
  не фиксируем) — литеральный юнион имён через template literal types
  (camelCase→SNAKE на типах) вплоть до проверки глобов; нагрузка на tsserver —
  против;
- **глоб — тот же тип**: `'*_GRPC_ADDRESS'` = `` `${string}_GRPC_ADDRESS` ``;
  unbound-свойства семейств могут экспортировать свои паттерны симметрично
  секциям;
- **атрибуция для доков** (тег фичи) — выводится из графа: инжекторы
  неэкспортированного токена гарантированно в одном пакете;
- ESLint-правило: «экспортируй `.keys`, не результат `makeConfig`»
  (вспомогательное).

### Цена

- Гарантия приватности меняет вид: была ошибка на `build()` при любом раскладе,
  стала невозможность-по-построению, охраняемая дисциплиной экспорта + линтом.
  Экспортировал токен — билдер уже не скажет (владельца он не знает).
- Объявленная-но-не-потреблённая секция (за флагом) выпадает из графа: нет
  eager-валидации её ключей и её нет в доках, пока никто не инжектит.
- Две сущности в API модуля (приватный токен + экспортный хэндл).

### Отвергнутые варианты

- **Статус-кво (`configs:` + build()-проверка)** — работает, но строка на модуль
  покупает только метку владельца, а правило «право зависит от позиции» — патч
  поверх одного токена с двумя правами; capability-модель делает патч ненужным
  и честнее ложится на принцип «enforcement — видимость ES-модулей».
- **Привязка только строками/глобами** (токены не нужны в корне) — теряет
  типизированную привязку по группе; опечатка в глобе молча не привязывает ничего.
- **Вывод владельца из графа** (владелец = единственный инжектор) — implicit
  ownership против «explicit over implicit», action-at-distance (легальность
  инжекта в A зависит от инжекта в B), нельзя объявить секцию до первого
  потребителя.
- **Литеральные типы ключей как несущий уровень** — type-механика ради
  type-механики: рантайму хватает строк в хэндле, корню — branded-типа.

Суперсид: пункт «приватность конфига» и цель привязки «токен группы» из финала
§15 (запись [2026-07-08], «Kernel/user space; конфиг как token-families» →
«Открытые вопросы»); соответствующие фрагменты
[composition-and-lifecycle.md](../history/superseded/composition-and-lifecycle.md) и
roadmap item 9 обновлены этим же изменением.

## [2026-07-10] Пакет тестирования (`@nestling/testing`)

> **РЕАЛИЗОВАНО 2026-07-31 (ядро)** — change `testing-package` (#18 roadmap).
> Реализованы решения 1–7 кроме `stub(Contract, impl)` и `app.emit`: понятия
> контракта в V1 ещё нет, поэтому они уехали в остаток change'а (волна 6,
> после #11 `ports`); поле `stubs:` введено уже сейчас — в форме «токен →
> значение», чтобы контрактные стабы легли в него аддитивно. Реализация
> закрыла один из открытых вопросов и уточнила три вещи, не менявшие сути:
> (1) **форма `overrides` для членов семейств** — точечно поверх
> материализованного члена да, рецепт целиком — `familyOverride`; член,
> которого никто не инжектит, узлом графа не является, и override по нему
> падает с отдельной подсказкой; (2) `assembleTest` асинхронна, поэтому
> канон — `await using app = await assembleTest(…)`; (3) `.check()` — метод
> корня `assemble`, а не тестового приложения (он обязан гонять честный
> граф), а перечисление всех отказов матрицы живёт в хелпере
> `checkTopologies` пакета: ядро фейлится быстро; (4) наружу отдан
> `app.pruned` — список выпавших прунингом узлов, чтобы «почему мой
> `@OnInit` не выполнился» отвечалось данными.

### Контекст

Тесты живут внутри пакета. Вопрос-триггер: как app-тестам мокать провайдеры,
если токены приватные (keys-capability, kernel-токены)? Ответ вырос в дизайн
пакета тестирования целиком.

### Принцип: уровень теста = граница видимости

**Тестовая поверхность — это экспортная поверхность.** Внутри пакета видно всё
(unit- и модульные тесты, приватность не мешает по построению); приложению видны
только публичные capability (app-тесты мокают на архитектурных швах). «Как
замокать чужой приватный провайдер» — никак, и это фича: либо модуль экспортирует
тестовую capability, либо мок на шве, либо тест написан не на том уровне.

### Решения

1. **Уровень 0 — без фреймворка.** Провайдеры — классы/фабрики с явными deps,
   конфиг-срез — объектный литерал, порт — объект с `call`. Принцип: *у
   юнит-теста нет импортов из `@nestling/*`*.
2. **`assembleTest` — тестовый composition root.** Мок = подстановка в графе на
   ASSEMBLE, до инстанциации (не патчинг, не перехват module system). Ключ
   `overrides: [[Token, fake]]` существует **только** у тестового корня.
   **Прунинг**: осиротевшее поддерево зависимостей заменённого узла выпадает из
   графа (замокал репозиторий → pg-пул не инстанцируется и не коннектится) —
   без этого жадный контейнер был бы анти-тестовым. Право override —
   позиционное: мокаешь то, на что есть ссылка.
3. **Швы app-теста** (чужие токены не нужны):
   - конфиг — `vars({...})`: объектный `ConfigSource` с `watch` + программным
     `set()` → тестируется и reload-механика (пере-проекция, keep-last-good,
     `onChange`); `process.env` в тестах не трогается → параллелизм бесплатно;
   - меж-фичевые вызовы — `stub(Contract, impl)`: фейк-порт, **валидируемый
     схемой контракта при каждом вызове** — мок не может разъехаться с
     реальностью (guarantee over convention в тестах);
   - request-контекст — `valueProvider(Ctx(X), value)` (уже решено 2026-07-10);
   - cross-cutting — override рецепта семейства:
     `familyOverride(ILogger, () => noop)`;
   - транспорт — не мокается: in-proc dispatch.
4. **Тестовая capability модуля — subpath `./testing`** с conditional export
   (условие `"testing"` включено только в тест-раннере → прод-импорт не
   резолвится на уровне Node resolution, граница структурная). Экспортирует
   курируемую поверхность: токены, разрешённые к подмене, и готовые фейки
   (`inMemoryOrdersRepo()`), которые автор держит в контракте с реализацией.
5. **Прогон без сокетов.** Тестовый app = фазы 0–3 (BOOTSTRAP..WIRE): `dispatch`
   уже рождён, START не выполняется → транспорты не в эфире. `app.call(Endpoint,
   input)` / `app.emit(Event, payload)` — типизированы схемами, гонят запрос
   через **полный пайплайн** (это и отличает app-тест от юнита). `await using`
   (`Symbol.asyncDispose`) → честный SHUTDOWN в реверсе. Настоящий e2e — обычный
   `run()` на случайном порту, вне пакета.
6. **`.check()` — структурный смок**: фазы 0–1 (конструкторы без `@OnInit` →
   без захвата ресурсов). Один тест на вариант деплоя: матрица `select`-топологий
   (`'all' | 'orders' | 'billing'`) валидируется в CI без деплоя — циклы,
   port-биндинг, полнота env.
7. **`testModule(M, { stubs })` — модуль в изоляции**: мини-app вокруг одного
   модуля; неудовлетворённые импорты обязаны быть застабаны явно, ошибка
   перечисляет недостающие токены. Живёт внутри пакета модуля → токены видны
   без экспорта.

Состав пакета: `assembleTest` (overrides + прунинг, стоп до START, `await
using`), `vars()`, `stub()`, `familyOverride()`, `.check()`, `testModule()`.
Пропорция намеренная: тестируемость — следствие архитектуры, пакет — тонкий.

### Цена

- Чужое неэкспортированное не мокается — точка (иначе модель видимости —
  декорация). Жёсткий выход для легаси: фейк-модуль целиком (модуль — значение,
  подменяется в `modules`/`features`).
- Прунинг ⇒ граф теста ≠ прод-граф; компенсация — `.check()` на честном графе.
- Конструкторы с побочками ломают `.check()` — они и так нарушают lifecycle;
  усиливает кандидатуру policy-check «ресурсы только в `@OnInit`».

### Отвергнутые варианты

- **`jest.mock` / перехват module system** — runtime magic в чистом виде; мок
  живёт вне графа, контейнер о нём не знает, прунинг невозможен.
- **`overrideByName('...')` / строковый доступ к приватным токенам** — дыра в
  ES-видимости, обесценивает kernel/user-границу.
- **`overrides` в боевом `assemble`** — подмена графа не должна существовать в
  проде даже как соблазн.

### Открытые вопросы

- ~~Форма `overrides` для членов семейств (`Cfg('KEY')` точечно vs только
  рецепт).~~ — РЕШЕНО change'ом `testing-package`: точечно поверх
  материализованного члена **и** `familyOverride` для рецепта целиком.
- `app.port(Contract)` — типизированный порт для теста потребителя.
- Включение `"testing"`-condition в vitest/jest из коробки. Частично снят:
  рецепт для обоих раннеров есть в [гайде](../guides/testing.md), репо
  включает условие в `jest.config.base.js`; автоматизации не делаем.

## [2026-07-13] Схемы: Standard Schema вместо привязки к zod; OpenAPI через явные конвертеры

### Контекст

Ядро (`nestling.pipeline/src/schema/*`) жёстко завязано на zod: `z.ZodType` в
сигнатурах `parsePayload`/`parseMetadata`, `z.infer` в `DomainType`, `ZodError`
торчит из публичного `SchemaValidationError`. zod `^4.0.0` — рантайм-зависимость
всего стека.

Тем временем экосистема стандартизовалась: **Standard Schema v1**
(standardschema.dev, январь 2025) — общий интерфейс, спроектированный совместно
авторами Zod, Valibot и ArkType. Вся спека — одно проперти `~standard` на схеме:
`{ version: 1, vendor: string, validate(value) → {value} | {issues}, types }`
(`types` — фантом для инференса; `validate` может вернуть Promise). Реализуют
Zod ≥ 3.24 (в 4 — нативно, включая `zod/mini`), Valibot ≥ 1.0, ArkType ≥ 2.0,
Effect Schema, TypeBox и др.; принимают tRPC v11, Hono, TanStack, AI SDK.

Критичное для нас свойство: **спека покрывает только валидацию + инференс
типов; интроспекции нет.** `StandardSchemaV1` в рантайме — чёрный ящик:
`validate` — непрозрачная функция, структуру схемы («объект с полями
`email: string`») через стандартный интерфейс перечислить нельзя, а генерация
JSON Schema — это ровно обход структуры. Поле `vendor` существует в спеке
именно как дискриминант для безопасного downcast в вендорские потроха.

### Решение 1: ядро принимает `StandardSchemaV1`

> **РЕАЛИЗОВАНО 2026-07-29** — change `standard-schema` (#19 roadmap).
> Реализация уточнила две вещи, не менявшие сути решения: (1) валидация
> собрана в единственную функцию `validateSync(schema, value, message)`,
> через которую идут `parsePayload`/`parseMetadata`, юнит `validate()`,
> поэлементная валидация потока и fallback-ветки транспортов — иначе форма
> отказа расходилась бы по четырём `catch`-ам; (2) `path` нормализуется при
> конструировании ошибки (`{key}` → `key`, символ → строка, индекс — число),
> потому что `issues` уезжают в тело HTTP-ответа и форма провода не должна
> зависеть от упаковки пути вендором.

- `parsePayload`/`parseMetadata`/`DomainType` переходят с `z.ZodType`/`z.infer`
  на `StandardSchemaV1`/`InferOutput`; валидация — через
  `schema['~standard'].validate(...)`.
- `SchemaValidationError` несёт стандартизованные `issues`
  (`{message, path?}[]`) вместо `ZodError` — zod перестаёт течь в публичный
  API; формат отказа валидации гарантирован спекой, а не вендором
  (guarantee over convention).
- zod уходит из dependencies ядра в devDependencies (тесты, примеры);
  валидатор приносит пользователь: zod, `zod/mini`, valibot, arktype —
  на его вкус и бюджет бандла.
- ~~`validate`, вернувший Promise (async refinements), в синхронном пайплайне —
  ошибка (`TypeError: async schemas are not supported`), не тихая
  деградация.~~ — **УТОЧНЕНО 2026-07-29**: тезис в силе, но класс ошибки
  выбран иначе. Async-схема даёт `AsyncSchemaNotSupportedError`, объект без
  `~standard` — `NotAStandardSchemaError`; оба намеренно **не** наследуют
  `SchemaValidationError`, поскольку это ошибки конфигурации приложения, а не
  входа: транспорт отдаёт на них 500, и общий `TypeError` замаскировал бы их
  под 400 в `catch`-ветках.

### Решение 2: OpenAPI-модуль с явными конвертерами

Раз стандартной интроспекции нет, путь «схема → JSON Schema»
вендор-специфичен: zod 4 — нативный `z.toJSONSchema()`, valibot —
`@valibot/to-json-schema`, arktype — встроенный `.toJsonSchema()`, TypeBox —
уже JSON Schema. Отсюда архитектура документирования:

- **валидация и документация разведены**: рантайм ядра знает только
  `~standard.validate`; JSON Schema нужна лишь opt-in модулю документации;
- **`@nestling/openapi` не знает ни про один валидатор.** Конвертер — его
  явная зависимость, публичный контракт:

  ```typescript
  interface SchemaDocConverter {
    /** совпадает с `~standard.vendor` схем, которые он умеет */
    readonly vendor: string;
    toJsonSchema(schema: StandardSchemaV1): JsonSchema;
  }

  openapi({ converters: [zodConverter()], info: { title: 'My API' } })
  ```

- **конвертеров — список** (внутри — map по `~standard.vendor`, заполняемый
  пользователем, а не фреймворком): модульный монолит допускает сторонний
  модуль на другом валидаторе, схема сама сообщает вендора;
- **конвертеры — отдельные пакеты** (`@nestling/openapi.zod` peer-зависит от
  zod, и т.п.): пользователь ставит ровно то, чем пользуется; мажоры
  конвертера следуют за мажорами валидатора (zod 3 vs zod 4);
- **boot-time-гарантия**: жадный контейнер знает все endpoints на старте —
  модуль на инициализации сверяет вендоров всех схем с переданными
  конвертерами; нет конвертера → приложение не поднимается (недокументируемых
  endpoints не бывает, если документация включена);
- **escape hatch**: явный `jsonSchema` в декларации endpoint'а перекрывает
  конвертацию (экзотический вендор, ручная доводка);
- **метаданные сверх JSON Schema** (`summary`, `tags`, examples) — из
  декларации endpoint'а; `errors:` → `responses` (`UnknownError` — default)
  приезжает из модели ошибок ([2026-07-10], roadmap 15); stream/events →
  AsyncAPI тем же механизмом (roadmap 6);
- **готовность к будущему**: в сообществе Standard Schema обсуждается
  стандартизация JSON Schema-выхода; если приземлится — «конвертеры по
  вендору» вырождаются в один универсальный, публичный интерфейс `openapi()`
  не меняется.

Прецеденты паттерна: type providers у Fastify (`@fastify/type-provider-zod`),
per-validator resolvers у hono-openapi, конвертеры oRPC.

### Цена

- Матрица «вендор × конвертер» на поддержке: различия в деталях маппинга
  (`z.record`, discriminated unions, `default`) — наша забота в конвертерах,
  которые поставляем сами (стартово: zod; valibot/arktype — по спросу).
- Пользователь обязан явно назвать конвертер — одна строка в composition root
  даже в 100%-zod-приложении (честная плата за explicit over implicit).

### Отвергнутые варианты

- **Остаться zod-only** — простейший путь (нативный `z.toJSONSchema()`, один
  формат ошибок), но lock-in валидатора в ядре и `ZodError` в публичном API;
  фреймворк, продающий «no lock-in» в остальном, привязывает к вендору схем.
- **Вшитый в `@nestling/openapi` реестр конвертеров по `vendor`** («фреймворк
  сам понял, что у меня valibot») — implicit magic, optional peer-deps на все
  валидаторы разом, версионная матрица внутри одного пакета.
- **Универсальный конвертер поверх Standard Schema** — невозможен по
  построению: интерфейс не даёт интроспекции, `validate` непрозрачен.
- **JSON Schema как источник истины** (путь TypeBox) — теряется DX
  zod/valibot, ради которого валидаторы и выбирают.

### Открытые вопросы

- ~~**Разложение merged payload.** `InputSources.payload` — это body + query +
  params, слитые в один объект; OpenAPI требует обратного: какое поле —
  `parameter (in: query/path)`, какое — `requestBody`. Одна merged-схема этой
  информации не несёт. Нужен либо маппинг от транспорта (path-параметры
  выводимы из роута, остальное — конвенция «GET → query, иначе body»), либо
  раздельная декларация источников. **Блокер генерации, не зависит от выбора
  валидатора** — решить до реализации roadmap 20.~~ —
  **РЕШЕНО 2026-07-13**: канон размещения + bind-карта, см.
  [2026-07-13] «Канонизация HTTP-input» ниже.
- `$ref`/components: именованные схемы вместо инлайн-копий → конвертеру нужен
  контекст (`toJsonSchema(schema, ctx)` с реестром имён; у zod 4 — registries).
- async-схемы: запрет навсегда или async-ветка пайплайна валидации.
- точка монтирования `openapi()` в composition root: ключ `docs:` в `assemble`
  (так показано в preview) vs обычный модуль/фича.
- AsyncAPI: форма io-декларации stream/events для доков (после roadmap 6).

## [2026-07-13] Канонизация HTTP-input: канон размещения + bind-карта

### Контекст

Внешнее ревью ([d/06 §3](../history/discussions/06-critical-design-review.md))
назвало HTTP-модель слабейшим местом: как единая `input`-схема распределяется
по частям HTTP-запроса, не определено нигде; path-параметры не показаны ни в
одном примере. Находка в коде: `mergePayload(body, query, params)`
(`transport.http/src/merge.ts`) уже сливает всё в один payload (конфликт
ключей → 400), но merge **необратим**: «поле принимается отовсюду» — implicit
contract (та же категория, что отвергнутый warn-and-pass в error-model).
OpenAPI (roadmap 20) и типизированному клиенту (запись ниже) нужно
каноническое место каждого поля. Подход согласован в продолжении d/06 (П.4);
здесь — фиксация.

### Решение

- **Канон** — детерминированная функция `(pattern, метод, пометки) →
  размещение`: совпадение имени поля с path-параметром → path; явная
  пометка → указанное место; остальное — query для `GET/HEAD/DELETE`,
  body для `POST/PUT/PATCH`; заголовки — **только по пометке, никогда
  конвенцией**.
- **Сахар-пометки** (`query(...)`, `header(...)` в схеме — ход `from()` из
  makeConfig) разворачиваются в плоскую **bind-карту** — несущий уровень,
  который потребляют транспорт, OpenAPI и типизированный клиент. Карта
  переживает переход на Standard Schema: при непрозрачной для интроспекции
  схеме bind-карта пишется руками.
- **Точка разворачивания — создание декларации** (`makeContract` /
  `makeEndpoint`), **не регистрация в App**: клиент потребляет bind-карту
  без сервера, из одного импорта контракта; fail-fast срабатывает у владельца
  (уточнение из дизайна клиентов, [d/07](../history/discussions/07-typed-clients.md);
  для инлайн-`makeEndpoint` создание и регистрация — одно место).
- **Strict-приём**: payload собирается только из канонических мест;
  enforcement бесплатен — поле не в том месте не попадает в payload и
  проваливает обычную валидацию; `PayloadConflictError` исчезает как класс.
- **Fail-fast при создании**: path-параметр без поля в схеме, пометка на
  path-поле, body-пометка у GET — ошибка сразу (guarantee over convention).
- **Query-массивы**: повтор ключа → массив; поле-массив оборачивает
  одиночное значение (чинит тихий last-wins повторных query-ключей в
  `transport.ts`).
- `header()` в v1 канона **не входит** — отложен; граница meta vs input
  (ambient-контекст против per-call параметра операции) и триггеры возврата —
  в [deferred.md](./deferred.md).

### Отвергнутые варианты

- **Оставить merge-отовсюду** — необратимый implicit contract; OpenAPI и
  клиент не могут вывести, куда класть поле.
- **Раздельная декларация источников** (Fastify-стиль:
  `body`/`querystring`/`params`/`headers` отдельными схемами) — дробит
  контракт на HTTP-куски: тот же контракт на NATS/CLI не имеет query/params;
  единый `input` переносим между транспортами, размещение — деталь
  HTTP-биндинга, а не формы данных.
- **Warn на неканоническом размещении с приёмом** — warn-and-pass уже
  отвергнут в error-model; конвенция вместо гарантии.

### Открытые вопросы

- **Коерсия провод-строк**: path/query несут строки; `number`/`boolean` в
  схеме — ответственность автора схемы (`z.coerce`) или канонное правило
  коерсии по bind-месту? Влияет и на клиент (сериализация в обратную сторону).
- ~~Форма пометок для не-zod вендоров (интроспекция вендор-специфична;
  гарантированный минимум — ручная bind-карта в декларации).~~ — **РЕШЕНО**
  change'ом `input-bind`: пометка — значение (`query()`/`body()`) в поле
  `bind` словаря декларации, рядом со схемой, а не внутри неё; вендор при
  этом не важен вовсе, а ключи `bind` типизированы через `InferInput<I>`
  (рантайм ключей не знает, типы знают). Носитель — плоская bind-карта —
  от формы сахара не зависит. Обоснование и отвергнутые варианты —
  `openspec/changes/archive/*-input-bind/design.md`, решение D2.

## [2026-07-13] Типизированные клиенты из контрактов

### Контекст

Контракт (`makeContract`, [d/05 §3](../history/discussions/05-modular-monolith-features-ports.md),
roadmap 11) уже порождает *внутренний* типизированный клиент — `Port` с
биндингом local/remote на сборке. Для потребителя **вне nestling-процесса**
(фронт, сервис на другом стеке, скрипт) дыра: DI недоступен, HTTP-адреса в
контракте нет (`name` — адрес шины). Сегодняшний `makeEndpoint` сращивает
контракт с реализацией (`handle` — обязательное поле `EndpointDefinition`) —
«только контракт» неимпортируем без серверного кода. Дискуссия —
[d/07](../history/discussions/07-typed-clients.md).

### Решение 1: HTTP-биндинг — секция контракта

`http: 'POST /users/:id'` (или развёрнуто `{ method, path, bind? }` — ручная
bind-карта для непрозрачных схем). Логика: `name` — уже адресация (NATS
subject), `http:` — та же адресация для другого провода; нейтральность
контракта — про **направление** (реализуешь или зовёшь), не про транспорт.
Несущий аргумент: bind-карта обязана выводиться из значения, которое
импортирует клиент. Канон-валидация (см. запись выше) — fail-fast при
`makeContract`.

### Решение 2: внешний клиент — `makeClient`

```typescript
const api = makeClient(
  { createUser: CreateUser, getUser: GetUser },   // потребитель сам именует методы
  { baseUrl, fetch?, headers? },                  // ambient: auth, tracing — здесь
);
const result = await api.createUser({ ... });
// Promise<Ok<Output> | Fail<EmailTaken | UnknownError>>
```

- Тип call-site **идентичен порту**: всегда async, `Ok|Fail` — дисциплина
  портов распространяется на внешних потребителей без изменений.
- Методы именует потребитель через record (explicit over implicit) — никакого
  парсинга `'users.create'` в nested-объекты.
- Ambient-заголовки — конфиг создания клиента (симметрия с границей meta vs
  input в [deferred.md](./deferred.md)); per-call заголовки — после возврата
  `header()`.

### Решение 3: ошибки через провод

Рематериализация `Fail` по `code` из `errors:` контракта — code-идентичность
`defineFail` ([2026-07-10]) выбрана ровно потому, что instanceof не переживает
сериализацию, а `code` переживает. Незадекларированный код → `UnknownError`.
Закрытый контракт `E ∪ UnknownError` симметричен серверной границе.

### Решение 4: пакетирование

- **`@nestling/contracts`** — `makeContract`, `defineFail`; зависимости —
  только Standard Schema (types-only) ⇒ **zero runtime deps**, импортируем во
  фронт. Следствие для roadmap 11: `makeContract` не живёт в
  `@nestling/pipeline`.
- **`@nestling/client`** — `makeClient`; fetch-based, без Node-специфики и
  серверных зависимостей.
- Валидация ответа по `output`-схеме — через `~standard.validate`,
  вендор-нейтрально; валидатор приносит потребитель.

### Решение 5: `makeEndpoint` остаётся инлайн-формой

«Анонимный контракт + реализация на месте» — честный L0 прогрессивного
раскрытия. Клиента из него не сделать — **осознанное ограничение**: хочешь
клиента — вынеси контракт в отдельное значение.

### Отвергнутые варианты

- **Клиент из `typeof endpoint`** — импорт тянет `handle` и все серверные
  зависимости; контракт должен быть отделён физически.
- **`httpBind(Contract, 'POST /users')` отдельным значением** — два артефакта
  разъезжаются; клиенту нужны оба; биндинг — данные контракта, не поведение.
- **Pattern только в реализации** (как сейчас) — клиент не видит адреса.
- **Парсинг `name` → `client.users.create`** — имплицитная магия строковых
  имён.
- **Кодогенерация TS-клиента по OpenAPI** — лишний цикл для TS-потребителей
  (TS-first вывод из схем без generation step); для не-TS-потребителей путь
  остаётся — roadmap 20.

### Открытые вопросы

- **Streaming-клиент**: `stream` → NDJSON `AsyncIterable<T>`, `events` → SSE
  с реконнектом по `Last-Event-ID` — v2, проектировать вместе с AsyncAPI
  (после roadmap 6).
- Валидация ответа: по умолчанию или opt-in.
- ~~Версионирование контрактов (эволюция схем, совместимость клиентов)~~ —
  РЕШЕНО: см. [2026-07-13] «Порты: deadline, идемпотентность, версионирование».
- Коерсия — общий вопрос с канонизацией (запись выше).

## [2026-07-13] Порты: deadline, идемпотентность, версионирование контрактов

### Контекст

Критическое ревью ([d/06 §5](../history/discussions/06-critical-design-review.md)):
co-located и split вызовы различаются *профилем*, и в дизайне портов
([2026-07-08]) отсутствовали deadline propagation, идемпотентность и
версионирование контрактов. Прецедент жанра — Service Weaver (заархивирован):
location transparency без эксплуатационного профиля не живёт.

### Решение

- **Deadline** — `meta.deadline` рядом с существующим `meta.signal`. Модель
  gRPC: внутри процесса — абсолютный момент, по проводу едет **относительный
  timeout** (clock skew между подами не влияет на семантику). На каждом hop
  dispatch пересчитывает остаток; бюджет исчерпан → fail-fast
  `DeadlineExceededError` **до** вызова. Код — встроенный, уровень фреймворка
  (как `UnknownError`): в `errors:` контракта не декларируется, но входит в
  закрытое множество ответов любого порта.
- **Идемпотентность** — `idempotencyKey` в meta для `command`-контрактов:
  dispatch генерирует/принимает ключ и провозит через транспорт (NATS
  headers). Дедупликация — **не в ядре**: хранилище ключей — satellite-концерн
  (обёртка/юнит на стороне обработчика); ядро гарантирует только, что ключ
  доедет и будет доступен хендлеру и юнитам.
- **Версионирование** — версия живёт **явно в имени контракта**
  (`user.create.v2`): имя и так адресация (NATS subject), версия — часть
  адреса. Проверка совместимости схем — прогон в `.check()`-матрице CI против
  снапшота опубликованных схем — **подсвечивает breaking changes, но не
  блокирует**: отчёт «breaking: удалено поле X» — сигнал для bump имени,
  решение остаётся за человеком.

### Отвергнутые варианты

- **Абсолютный deadline по проводу** — clock skew между подами делает бюджет
  недостоверным; относительный timeout на hop — стандартное решение (gRPC).
- **Дедупликация в ядре** — тянет хранилище ключей в kernel; против черты
  «kernel 1.0».
- **Additive-only как жёсткое правило** (блокирующий gate в CI) — breaking
  changes бывают осознанными; задача системы — сделать их видимыми, а не
  невозможными.
- **Версия в поле метаданных контракта** — неявно: два контракта с одним
  именем и разными версиями сталкиваются в адресации; explicit over implicit.

### Открытые вопросы

- Дефолтный deadline: отсутствует (бюджет только явный) или framework default.
- Где живёт снапшот схем для сравнения: файл в репо или внешний registry.
- `idempotencyKey` для `request`-контрактов (retry POST-подобных запросов) —
  пока только `command`.

## [2026-07-13] Один канонический стиль деклараций: функциональный (`make*`)

### Контекст

Критическое ревью ([d/06 §6](../history/discussions/06-critical-design-review.md)):
два параллельных публичных стиля (классовый и функциональный) навсегда
удваивают поверхность доков, примеров и тестов — при и без того высокой
сложности типовой машинерии pipeline.

### Решение

Уходим от двойного стиля. **Канонический стиль деклараций — функциональный**
(конвенция `make*`: `makeEndpoint`, `makeContract`, `makeConfig`,
`makePipeline`). Классовый стиль как равноправный параллельный путь деклараций
из доков и примеров уходит; поверхность гайдов/примеров/тестов ведётся для
одного стиля.

Классы **остаются** там, где несут DI-нагрузку, — это форма подключения к
контейнеру, а не стиль деклараций: провайдеры (`@Injectable([deps])`),
юниты-классы (форма «класс» в таблице форм юнитов Pipeline v2 §9 — без
изменений).

Следствие: открытый вопрос модели ошибок «форма привязки `E` к классовому
endpoint'у» снимается вместе с классовым стилем деклараций.

### Отвергнутые варианты

- **Двойная поверхность как позиционирование** («класс-стиль для мигрирующих
  с Nest») — цена постоянная (каждый пример, гайд и тест ×2), выгода —
  разовая при миграции; миграционный гайд дешевле параллельного стиля.

## [2026-07-13] Конфиг: `secret()` и общие ключи

### Контекст

Критическое ревью ([d/06 §7](../history/discussions/06-critical-design-review.md)):
(а) `from('DATABASE_URL')` позволяет двум секциям читать один ключ с разными
схемами — семантика не определена; (б) нет механизма секретов для
редактирования значений в логах/`explain()`/генерируемых доках.

### Решение

- **`secret(schema)`** в `makeConfig` — помечает ключ секретным. Реестр
  конфига знает пути секретов; `explain()`, логи фреймворка и генерируемые
  доки редактируют значение (`***`). Для потребителя значение остаётся
  обычным (без брендирования типа) — v1.
- **Общие ключи: ключ — разделяемый read-only ресурс.** Каждая секция
  валидирует сырое значение **независимо** своей схемой; любая упавшая
  валидация — fail-fast на старте; `explain()` показывает всех читателей
  ключа. Прямое продолжение keys-capability ([2026-07-10]): право читать
  ключ ≠ владение ключом.
- **Единственный настоящий конфликт — несогласованный `reloadable`**: одна
  секция объявила ключ reloadable, другая нет → ошибка на сборке. Семантика
  «значение может измениться под ногами» должна быть согласована всеми
  читателями.
- **Секретность общего ключа — по объединению**: хоть одна секция объявила
  `secret()` → ключ редактируется везде.

### Отвергнутые варианты

- **Запрет чтения одного ключа несколькими секциями** — легитимный кейс и
  прямое следствие capability-модели; запрет вернул бы понятие владельца,
  от которого keys-capability ушла.
- **Брендированный `Secret<T>` с явным `.reveal()`** — сильнее защита от
  логирования самим пользователем, но дороже по DX; редактирование на стороне
  фреймворка закрывает основной риск. Бренд — возможное аддитивное ужесточение
  позже (v1 не блокирует).

## [2026-07-13] Endpoint-декларации: per-transport конструкторы, `deps`-инжект, формы хендлера

### Контекст

Детализация записи «Один канонический стиль деклараций: функциональный» (выше):
она фиксирует, *что* канон один; эта — *как выглядит канон для endpoints* и что
именно происходит с классами. Триггер — вопрос «нужен ли функциональный формат
вообще», разобранный на аудите кода и сравнении с конкурентами (полная логика —
[d/08](../history/discussions/08-endpoint-declarations-and-styles.md)).

Факты аудита (2026-07-13):

- оба стиля уже сводятся к одному представлению: `EndpointDefinition{handle}`
  (`makeEndpoint` — identity-функция ~7 строк), `ProviderDefinition`
  (class/factory — одна ветка if/else в билдере);
- классовый путь endpoint'а — обёртка ~600–650 строк (декораторы,
  WeakMap-метаданные, `IEndpoint`, глобальный реестр, резолв инстансов) и
  держится на саморегистрации в глобальном `Set` при импорте — паттерне,
  отвергнутом в d/05 §1;
- симметрия сломана в обе стороны: `App` принимает только классовые endpoints
  (`AppModule.endpoints: Constructor<IEndpoint>[]`), `makeEndpoint` живёт
  только standalone и не покрыт тестами; lifecycle — только у классов.

Из сравнения: два симметричных стиля не продал никто (Vue Options/Composition
и React classes/hooks — расколотая экосистема, в итоге один «рекомендуемый»);
Angular мигрировал guards/interceptors на функции, оставив классы сервисам;
вся типизированная родня (tRPC/ts-rest/oRPC/Hono/Elysia) — декларации-значения,
потому что **декоратор не влияет на типы** (перманентное свойство TS — и
legacy, и стандартных ES-декораторов). Ниша «декларации-значения + настоящий
DI/lifecycle/модульный монолит» — пуста.

### Решение

1. **Endpoint-декларация — значение, создаётся конструктором своего
   транспорта**: `httpEndpoint({ method, path, input, output, errors?,
   pipeline?, deps?, handle })`, `cliEndpoint(...)`; реализация контракта —
   `implement(Contract, ...)`. Словарь транспорта в декларации легален и
   типизирован: path-параметры из шаблона, канон размещения + bind-карта
   (запись «Канонизация HTTP-input») разворачиваются здесь. Generic
   `makeEndpoint` — kernel-примитив, из которого транспортные конструкторы
   собирают свои; из пользовательского канона уходит. «Инлайн-форма» из
   записи «Типизированные клиенты» (решение 5) — это и есть `httpEndpoint`.
2. **Декораторы-носители метаданных удаляются из целевой поверхности**:
   `@Endpoint`/`@HttpEndpoint`, интерфейс `IEndpoint`, endpoint-registry.
   `endpoints:` модуля принимает значения; дискавери — из дерева модулей
   (roadmap 8).
3. **DI хендлера — поле `deps`** (явный массив, как везде) и **три формы
   `handle`** (симметрия «четырём формам юнитов» pipeline v2):

   | Форма | Когда |
   |---|---|
   | `(input, meta) => …` | без зависимостей; единственная форма, которую принимают standalone-транспорты |
   | `deps: […]` + `(…deps) => (input, meta) => …` | каррированная фабрика: внешний вызов — один раз на сборке (аналог конструктора), замыкание = инстанс |
   | класс с `@Injectable` и методом `handle` | резолвится контейнером (механизм классов-юнитов); проверка типов — в точке декларации (класс — поле generic-вызова, `implements` не нужен) |

   Класс-хендлер — **форма подключения DI, а не второй стиль деклараций**
   (граница из записи «Один канонический стиль»); привычная после Nest
   структура (конструктор + метод) сохраняется без декораторной декларации.
4. **Сервисы — канонично классы** (`@Injectable([deps])`, lifecycle-хуки,
   класс — сам себе токен). `factoryProvider`/`valueProvider` — примитивы
   контейнера (интерфейс-токены, конфиг, тесты), не «стиль». Lifecycle для
   фабрик не делаем — кейса нет.
5. **Endpoint — обычный узел графа** с синтетическим id
   (`endpoint:POST /orders`): рёбра `deps` видны в визуализации/`explain`,
   циклы и `strictExports` — штатно; инстанцирование жадно на ASSEMBLE,
   регистрация паттернов — WIRE.
6. **Этажность транспорта.** Декларация владеет **словарём вида** транспорта
   (но не инстансом/конфигом — порт и адреса живут в composition root);
   pipeline и handler — транспорт-слепые («значения, не байты»); контракты —
   транспорт-нейтральный этаж (нейтральность там, где она функциональна:
   co-located ↔ split). Ссылка декларации на транспорт — **токеном** (принято
   [2026-07-08]) → endpoint без транспорта в графе = FAIL-FAST на ASSEMBLE.
   Один handler на несколько транспортов = несколько тонких деклараций с
   общим значением/классом — явно (без ExecutionContext-маскарада Nest).
   *Уточнено для именованных контрактов: один контракт с несколькими
   биндингами + один `implement` — см. [2026-07-13] «Контракт первичен», п. 8.*
7. **Standalone-гарантия в типах**: тип endpoint'а несёт неразрешённые deps;
   `server.route()` принимает только endpoint без deps (симметрично
   `Pipeline<any, never>`); ручное гашение — `endpoint.resolve([...])`
   (аналог `pipeline.resolve`).

### Цена

- Роутинг и схемы уезжают из декоратора в значение — при миграции с Nest
  переписывается слой контроллеров (сервисы переносятся почти дословно;
  класс-хендлер сохраняет привычную форму).
- Перегрузка `handle` по наличию `deps` — типовая машинерия; нужен бюджет DX
  (снапшот-тесты ошибок компилятора — тот же пункт, что для `compose`).

### Отвергнутые варианты

- **Полная симметрия двух стилей** — см. запись «Один канонический стиль»
  (удвоение поверхности навсегда).
- **Классы канонично везде** (декораторные декларации) — декоратор не влияет
  на типы: каждая типовая фича (канал `E`, meta из пайплайна, контракты)
  требовала бы `implements`-церемонии вместо инференса — классовая декларация
  вечно отстаёт; реестр-при-импорте уже отвергнут (d/05 §1).
- **Убрать классы целиком** (Effect-путь) — теряется класс-как-токен и
  lifecycle-методы сервисов; отчуждает мигрирующих с Nest; функциональный
  lifecycle потребовал бы отдельного дизайна без реального кейса.
- **deps третьим аргументом per-call** (`handle(input, meta, deps)`) —
  смешивает singleton-сборку с per-request сигнатурой; в тестах deps
  передавались бы в каждый вызов.
- **Service locator** (`meta.get(Token)` / `inject()` внутри хендлера / ALS) —
  рантайм-резолюция, зависимость невидима в DI-графе; «no runtime magic».
- **Endpoint как токен + `factoryProvider`** (прежний §5
  composition-and-lifecycle) — три артефакта на ручку и токен, который никто
  не инжектит; остаётся низкоуровневой возможностью, не каноном.
- **Generic `transport: 'http'`-строка в декларации** — притворяется
  нейтральной, а `pattern` втайне HTTP-шный; строка вместо токена теряет
  fail-fast и типизацию словаря.

### Открытые вопросы

- Перегрузка типов `handle` по наличию `deps` (инференс между соседними
  полями объекта) — прототип до фиксации API.
- Имена конструкторов: `httpEndpoint` vs `makeHttpEndpoint` (конвенция
  `make*`).
- `.auto` в `deps` endpoint'а: потребитель = синтетический id ручки
  (для произвольных фабрик вопрос из [2026-07-06] остаётся открыт).
- Мульти-инстанс одного транспорта (public + admin HTTP) — эскиз через token
  family (`Http('admin')`); решать в 10 (`features`).
- `name:`/operationId в декларации (OpenAPI, имя узла графа).
- Форма `implement` с deps: `implement(C, { deps, handle })` vs общий объект.

Суперсид: двухстилевая прогрессия
[composition-and-lifecycle](../history/superseded/composition-and-lifecycle.md) §4/§5
переработана этим же изменением (одна прогрессия + «Формы хендлера»);
примеры [rxjs.md](../history/superseded/rxjs-design-page.md) приведены к канону.

## [2026-07-13] Бюджет на DX типов pipeline

### Контекст

Критическое ревью ([d/06 §6](../history/discussions/06-critical-design-review.md)):
типовая машинерия pipeline (монотонное накопление, `Partial` на ответном
тракте, `TNeeds`) — сложность уровня tRPC-middleware и Effect Layer вместе.
Известные последствия жанра: нечитаемые ошибки в точке композиции, деградация
tsserver, хрупкость при обновлениях TS. Без специальной работы пользователь в
точке `compose` видит трассировку внутренних дженериков
(`MergeCtx`/`AccumulateCtx`, десятки строк), а не свою ошибку. Принято после
демонстрации на примерах (d/06, продолжение пп. 5–7).

### Решение

Три инструмента, все — **до фиксации публичного API pipeline v2**:

1. **Типы-ошибки в сигнатуре `compose`** (приём tRPC/Elysia): при нарушении
   требований слоя тип параметра схлопывается в читаемый литерал
   `{ __error: 'Слой требует контекст, которого нет во внешних слоях';
   missing: { identity: User } }` — первая строка диагностики называет
   проблему и недостающие поля вместо трассировки инстанцирования.
2. **Snapshot-тесты текстов диагностик**: каталог фикстур заведомо
   неправильных композиций (нет `identity` во внешних слоях, неверный порядок
   слоёв, `.pre` после ответного метода); CI прогоняет `tsc` и сравнивает
   тексты ошибок со снапшотами. Диф снапшота ловит деградацию сообщений при
   обновлении TypeScript или рефакторинге типов — до пользователей.
3. **Бенчмарк tsserver**: синтетический граф ~50 слоёв/эндпоинтов, порог в CI
   на время hover/автокомплита (и/или check time из
   `tsc --extendedDiagnostics`).

### Отвергнутые варианты

- **«Чинить по жалобам»** — деградация DX типов тихая: обнаруживается после
  релиза, когда публичный API уже зафиксирован и упрощать типы поздно.
- **Assert-тесты типов (`expectTypeOf`/`tsd`) как замена** — проверяют *факт*
  ошибки, не *читаемость текста*; снапшот текста — единственный способ
  зафиксировать само сообщение.

## [2026-07-13] Контракт первичен: онтология деклараций, три этажа, формы io

### Контекст

Вопрос «нужны ли endpoints как понятие — или в принципе только контракты?»
([d/08, продолжение](../history/discussions/08-endpoint-declarations-and-styles.md)).
Стресс-тест на неудобных кейсах (webhook, SSE-лента, multipart, CLI,
статика/catch-all, NATS wildcard) показал: ни один не требует endpoint как
*отдельного первичного понятия* — каждый раскладывается либо в контракт
(иногда анонимный), либо этажом ниже, в сантехнику транспорта. Развитие
записей «Endpoint-декларации» и «Типизированные клиенты» (решение 5 —
«инлайн = анонимный контракт» — становится общим принципом иерархии).

### Решение

1. **Иерархия деклараций — контракт первичен.** Контракт (интерфейс + адреса:
   `name`, `http:`, `cli:`, …) → `implement(Contract, { pipeline?, deps?,
   handle })` → per-transport конструкторы (`httpEndpoint`, `cliEndpoint`, …) =
   сахар «анонимный контракт + implement одним жестом». На kernel-уровне всё
   по-прежнему компилируется в один узел графа — меняется объяснение и
   иерархия понятий, не API.
2. **Различие endpoint/контракт = видимость.** Экспортированный именованный
   контракт — capability «меня можно позвать» (порты, клиенты, версии, шина);
   анонимный/неэкспортированный — чисто транспортная поверхность. Enforcement —
   ES-модули, как везде. Деградация плавная: «дай ручке имя и экспортируй —
   станет портируемой».
3. **Три этажа.** (1) *Сантехника транспорта* — статика, CORS, сжатие,
   wildcard-подписки NATS: конфиг/плагины транспорта, без схем и контрактов;
   escape hatch для сырых случаев живёт здесь, а не как параллельная модель
   деклараций. (2) *Контракты* — все schema-first операции. (3) *Реализации*.
4. **Валидация биндинга против способностей транспорта** (ASSEMBLE,
   fail-fast). Контракту можно богатые формы (стримы, multipart) — биндинг
   проверяет: HTTP умеет, шина/порт v1 — только value-формы → внятная ошибка
   «транспорт не умеет streaming (v2)». Снимает конфликт «контракт =
   пересечение возможностей транспортов vs endpoint = объединение»: богатство
   объявляется в контракте, проверяется при сборке.
5. **io-декларация — дерево форм, не схема.** Верхний уровень —
   `value | stream(T) | events(T) | multipart({ fields, files })`; листья —
   Standard Schema (спека для значений не затрагивается). Валидация по форме:
   value — целиком; stream/events — поэлементно (opt-out для горячих потоков);
   multipart — поля схемой, файлы (`upload({ maxSize, mime })`) лимитирует
   транспорт **во время** парсинга, не буферизуя. Маппинг форм на media types
   детерминирован (events → `text/event-stream`, stream → NDJSON,
   multipart → `multipart/form-data`) — вход для OpenAPI (roadmap 20).
6. **Сырые байты — opt-in пометка `rawBody: true`** в HTTP-словаре декларации
   (webhook-подписи, HMAC): транспорт сохраняет байты и кладёт их в
   **типизированный стартовый контекст**; слой проверки объявляет требование
   `makePipeline<{ rawBody: Uint8Array }>()` → забытая пометка = ошибка
   компилятора в точке композиции, а не undefined в рантайме. Память платится
   только там, где запрошена.
7. **Интерактив CLI — стратегия сбора input у биндинга, не свойство
   операции.** Политика `missing: 'prompt'`: промпты выводятся из схемы
   (enum → select, boolean → confirm, `.describe()` → подсказка, default →
   «Enter»); CI-режим отключает (нет флага = ошибка). Диалог посреди
   выполнения — декомпозиция в пару операций plan/apply: паттерн
   подтверждаемой операции, транспортно-нейтрален (тот же plan → confirm →
   apply доступен HTTP-фронту и шине). Операция остаётся `input → output`.
8. **Мультитранспорт именованного контракта** — уточнение п. 6 записи
   «Endpoint-декларации»: канон — один контракт с несколькими биндингами +
   один `implement`; «несколько тонких деклараций с общим хендлером» остаётся
   для анонимных поверхностей с разными словарями.

### Отвергнутые варианты

- **Endpoint как отдельное первичное понятие** — все кейсы разложились в
  контракт или сантехнику; двойная онтология оставляла бы OpenAPI, клиентам и
  policy-check два параллельных реестра.
- **«Всё — сообщение» сейчас** (HTTP-транспорт просто доставляет в dispatch
  контракта) — связало бы HTTP-ядро с несуществующим дизайном стриминга по
  шине; capability-валидация биндинга даёт ту же честность без связывания.
- **`meta.rawBody` всегда** — память на каждый запрос ради 1% ручек; мешок
  meta вместо типовой гарантии.
- **Стрим как схема** (упихнуть в Standard Schema) — стрим не значение;
  «форма над схемами» сохраняет спеку нетронутой.
- **Интерактивность как свойство операции** — ломает `input → output`;
  операция перестаёт быть вызываемой другими транспортами.

### Открытые вопросы

- Форма API: `implement(Contract, …)` vs `Contract.implement(…)`; синтаксис
  multipart/`upload()` в io-декларации.
- Поэлементная валидация горячих стримов: дефолт и форма opt-out.
- NATS (к change 12): гипотеза — вся inbound-поверхность = контракты
  (queue-group-воркеры) + сантехника (wildcard-аудиторы), `natsEndpoint` как
  третье понятие не нужен. Проверить при реализации.
- Streaming через шину — v2 (после 6, проектировать вместе с AsyncAPI).

## [2026-07-13] Документация: `design/` — полное целевое состояние V1

### Контекст

Полный аудит и внешняя критика доков (продолжение
[d/06](../history/discussions/06-critical-design-review.md)) показали
системный дрейф: после решения «дистилляции не будет — без двойной
бухгалтерии» (фиксировалось в docs/README) целевой дизайн большинства
подсистем (pipeline, контейнер, конфиг, ошибки, порты, стриминг) жил только
в журнале решений; три design-дока покрывали лишь часть поверхности и
отставали от свежих записей (Standard Schema, `secret()`, deadline,
bind-карта — ни один не был отражён; path-параметры не показаны ни в одном
примере). Одновременно в доках смешивались целевое состояние и порядок
работ («до релиза pipeline v2», roadmap-номера в design-тексте) — при том,
что разрабатывается V1 и никакого «v2» как имени API не существует.

### Решение

1. **`design/` = полное целевое состояние V1**, по одному доку на подсистему
   (карта — `design/README.md`): principles, container, composition,
   pipeline, endpoints, contracts, config, errors, schemas, streaming,
   transports, testing. Доки пишутся в настоящем времени, «как будто
   реализовано».
2. **В design-доках нет порядка работ и статусов реализации** — только
   плашка «Целевое состояние V1» со ссылками: записи ideas.md (логика,
   отвергнутые варианты) и roadmap (статус). Дизайн без записи в журнале
   в design/ не попадает.
3. **Слова «v2» в целевых доках не существует**: осознанно исключённое из
   V1 живёт в deferred.md и открытых вопросах записей. Имена changes
   (`pipeline-v2`, `streaming-v2`) остаются идентификаторами изменений,
   не версиями продукта; формулировки «до релиза pipeline v2» в roadmap
   заменены на «до фиксации публичного API V1».
4. Прежние design-доки распределены и перенесены в `history/superseded/`
   с плашками (composition-and-lifecycle, transport-centric-http,
   rxjs-страница).

### Отвергнутые варианты

- **Сохранить «журнал + спеки как единственное описание»** (решение
  «без двойной бухгалтерии») — цена двойной бухгалтерии оказалась меньше
  цены отсутствия целостного описания: журнал append-only и хронологичен,
  читать целевую картину по 15 записям с суперсидами невозможно, дрейф
  дизайна никем не замечается. Двойная бухгалтерия управляема правилом
  «поменял решение → правь док тем же изменением» + `/docs-audit`.
- **Статусные плашки «частично реализовано» в design/** — смешивают ось
  «что хотим» с осью «что сделано»; вторая ось целиком уехала в roadmap.

## [2026-07-14] «Kernel 1.0» — граница ядра и фиксация breaking-окна V1

### Контекст

Термин «kernel 1.0» пришёл из критического ревью
([d/06 §1](../history/discussions/06-critical-design-review.md)):
предложение провести жёсткую черту скоупа. Черта де-факто уже применялась в
двух принятых решениях («дедупликация — satellite, не ядро» в записи про
deadline; «ядро не тянет хранилище» в deferred по outbox), но самого решения
в журнале не было — аудит 2026-07-13 пометил ссылки как висящие на фантоме.

### Решение

1. **«Kernel 1.0» — это граница ядра, а не отсечение уровней.** Ядро
   (kernel-пакеты `@nestling/*`) не тянет хранилище и внешнюю инфраструктуру.
   Всё, что требует стораджа или внешних систем, — satellite-пакеты поверх
   публичных примитивов: дедупликация идемпотентности, outbox/relay, реестр
   подписок, дашборды. Лакмус — dogfooding: satellite пишется, не трогая ядро.
2. **Прогрессия L0–L4 целиком входит в целевой V1.** Отсечение L3–L4 в
   «спутник со своим темпом» (буквальное предложение d/06) отвергнуто:
   location transparency и модульный монолит — стержень позиционирования,
   а аддитивность уровней уже гарантирует, что L0 за них не платит.
   Фазируемость реализации обеспечивает roadmap, а не обрезание дизайна.
3. **Breaking-окно фиксации публичного API V1 закрыто по составу**:
   changes 17 (`pipeline-drop-after`), 19 (`standard-schema`),
   21 (`input-bind`), 23 (`pipeline-type-dx`), 24 (`endpoint-model`).
   Новые breaking-идеи в окно не добавляются — они проектируются поверх
   зафиксированного API (asymmetry of risk: аддитивное расширение дёшево,
   расфиксация — нет).

### Отвергнутые варианты

- **«Kernel 1.0 = L0–L1 + pipeline + error-model + streaming, L3–L4 —
  спутник»** (d/06 §1 буквально) — режет ценностное предложение; страх
  «умереть недостроенным» лечится фиксацией окна (п. 3), а не ампутацией.
- **Не фиксировать черту** — на неё уже опираются принятые решения;
  нефиксированная граница — конвенция, а не гарантия.

### Открытые вопросы

- Формальный признак kernel/satellite в упаковке (namespace-конвенция
  `@nestling/x` vs `@nestling-satellite/x`) — решить при первом satellite.

## [2026-07-14] Policy-check на собранном графе; `detached` — только с причиной

> **РЕАЛИЗОВАНО 2026-07-31** — change `policy-check` (#28 roadmap).
> Реализация уточнила три вещи, не менявшие сути решения: (1) фильтр
> `everyEndpoint({ transport })` принимает **токен** транспорта
> (`HttpTransport$`), а не его провайдер `http()`, как было в наброске
> формы, — множество транспортов выводится из графа, и декларация ссылается
> на транспорт тем же токеном; (2) идентичность слоя держится не на
> `explain()`, а на заведённом для этого **провенансе композиции** — `compose`
> запоминает ссылки на аргументы, деривация билдера и `bind` — на
> предшественника (после `compose` в слоях не остаётся ни одной ссылки на
> исходное значение: `cloneLayer` создаёт новые объекты); (3) опция
> ESLint-правила названа `constructorName`, а не `constructor`: свойство с
> таким именем в JSON-схеме правила ломает валидацию конфига в ESLint 9.
> Ручка без `pipeline` трактуется как нарушение (отсутствие пайплайна и
> отсутствие слоя для инварианта неразличимы), диагностика агрегирована по
> политикам, а `detached` виден двумя каналами — строкой на старте и полем
> `CheckedEndpoint.detached` в отчёте `check()`.

### Контекст

Endpoint-only pipeline купил compile-time проверки ценой сквозных
инвариантов: «у каждой HTTP-ручки есть auth-слой» держалось конвенцией.
Для requestId это терпимо, для аутентификации — нет: забытый `authed`-слой
на одном endpoint'е — каноническая уязвимость. Критическое ревью назвало это
самым сильным внутренним противоречием дизайна
([d/06 §2 + П.3](../history/discussions/06-critical-design-review.md) —
подход там согласован концептуально); прежние записи держали policy-check
«опциональной дверью», а `detached: true` — «отложенной мелочью».

### Решение

Policy-check — **часть V1**, гарантия уровня сборки:

- **Живёт на собранном графе (ASSEMBLE)**, где все значения
  материализованы, — проверка точна по построению. Прецеденты жанра в самом
  дизайне: `strictExports`, boot-time проверка конвертеров OpenAPI.
- **Форма**: `assemble({ policies: [everyEndpoint({ transport: http })
  .hasLayer(authedBase)] })`; словарь предикатов v1 минимальный
  (фильтр по транспорту/паттерну, `hasLayer`).
- **Идентичность слоя — по ссылке на значение**: слои и так экспортируются
  константами; никакого сравнения по имени.
- **Opt-out — `detached: '<причина>'`**: строка обязательна; App печатает
  список detached-ручек на старте — поверхность для аудита.
  `detached: true` без причины не существует.
- **Двухслойность**: ESLint-правило — editor-фидбек для буквальных случаев;
  policy-check — гарантия (пайплайны — значения, текущие через фабрики и
  параметры; статически в точке объявления они непроверяемы).
- **Та же машинерия** обслуживает policy-check присутствия ambient-vars
  (async-context) и инварианты плагинов («каждый пайплайн содержит
  tracing»); `.check()` (testing) гоняет policies в CI на матрице
  `select`-топологий.

Суперсид: «опциональный startup policy-check» и «`detached: true` —
отложенные мелочи» в записи [2026-07-06] (Pipeline, уточнения); пункт
«Policy-check на старте — дверь открыта, не закладываем» в открытых
вопросах там же.

### Отвергнутые варианты

- **ESLint как основа гарантии** — документированный паттерн
  «модуль-фабрика с параметром `pipeline`» статически непроверяем в точке
  объявления (значение известно только в call-site); плюс `eslint-disable`
  и «работает, если настроен».
- **Оставить конвенцией** («глобальный base + дисциплина compose») — compose
  решает переиспользование, не гарантию: ничто не обнаруживает endpoint,
  композированный не от той базы. «Должен быть защищён» — не свойство типов
  хендлера: хендлер, не использующий `identity`, типобезопасен и с auth,
  и без.
- **Проверка на регистрации per-endpoint** — нет полного графа; policy
  вида «каждый endpoint транспорта X» проверяема только на множестве.

### Открытые вопросы

- Расширяемость словаря предикатов (пользовательские предикаты над
  интроспекцией `explain()`).
- Политики вне pipeline («ресурсы только в `@OnInit`») — тот же механизм,
  отдельное решение.

## [2026-07-14] Конфиг: форма секции — рекорд полей (совместимость со Standard Schema)

### Контекст

Standard Schema не даёт интроспекции ([2026-07-13] «Схемы»), а `makeConfig`
строил имена ключей из полей **объектной схемы** (`maxItems` →
`ORDERS_MAX_ITEMS`) — перечисление полей объекта работало только с zod.
d/06 №2 прямо называл makeConfig схемной границей; аудит 2026-07-13 пометил
противоречие как незакрытое.

### Решение

Форма секции — **рекорд полей**, а не объектная схема:

```typescript
export const OrdersConfig = makeConfig('orders', {
  maxItems:    z.coerce.number().default(100),   // ← ключ ORDERS_MAX_ITEMS
  databaseUrl: from('DATABASE_URL', z.url()),     // точное имя ключа
  apiToken:    secret(z.string()),                // редактируется в выводе
});
```

- Перечислимость полей — на уровне JS-объекта nestling-API; **листья —
  произвольные Standard Schema**; `from()`/`secret()` — обёртки листьев.
  Интроспекция схем не нужна нигде: деривация ключей, реестр для доков,
  секреты и привязка работают с ключами рекорда.
- Тот же ход, что bind-карта в канонизации HTTP-input: структурная
  информация, нужная фреймворку, живёт в его собственных декларациях,
  а не вытаскивается из вендорских схем.
- Асимметрия с HTTP-input осознанна: `input` — единая переносимая схема
  (одно значение на проводе) с ручной bind-картой для непрозрачных схем;
  секция конфига — по построению набор независимых ключей, у неё нет
  «единого значения», поэтому рекорд — честная форма, а не fallback.
- Валидация: поля независимы (согласуется с семантикой общих ключей —
  независимая валидация каждым читателем); eager на `build()`, fail-fast.

### Отвергнутые варианты

- **Объектная схема (`z.object`) как форма секции** — перечисление полей
  вендор-специфично; ядро получает lock-in ровно в самом массовом API.
- **Вендор-конвертеры для конфига** (как у OpenAPI) — тяжёлая машинерия
  (пакет на вендора) ради перечисления ключей; для opt-in доков оправдана,
  для базового конфига — нет.
- **Оставить конфиг zod-only как осознанное исключение** — конфиг пишет
  каждое приложение; исключение в этом месте обесценивает «валидатор
  приносит пользователь».

### Открытые вопросы

- Кросс-полевые инварианты секции («если A задан, то B обязателен») —
  опциональный валидатор секции поверх независимых полей.
- Сахар «объектная zod-схема → авторазворот в рекорд» как вендор-расширение
  (не в ядре).

## [2026-07-31] Порты: адрес подписки, политика конфигом, sim-режим провода

### Контекст

Реализация change `ports` (#11) вскрыла четыре вопроса, которых запись
[2026-07-08] «Порты: межфичевое общение через контракты» не решала: как
адресуются несколько подписчиков одного события; откуда берётся политика
диспатча, если перечень полей `assemble` закрыт; что именно значит
`always-remote` без брокера; и что возвращает `emit`.

### Решение

- **Адрес подписки — явное имя, а не автогенерация.** `implement` требует
  `subscriber:` у контракта-события и запрещает его у `request`/`command`.
  Паттерн ручки — `<name>@<subscriber>` (уникальность внутри транспорта),
  subject шины — `<name>` (общий у всех подписчиков). Автогенерация
  суффикса отвергнута дважды: счётчик зависит от порядка импортов (адрес
  подписки перестал бы воспроизводиться между процессами), имя модуля
  привязало бы сетевой адрес к внутренней структуре кода. В мире с брокером
  это имя становится queue-group и durable-подпиской, поэтому оно вводится
  сразу.
- **Политика диспатча — kernel-секция конфига `nestlingPorts`**
  (`NESTLING_PORTS_DISPATCH`, умолчание `local-first`), а не поле корня и
  не примордиальный `load`. Поле корня невозможно (перечень закрыт, #13);
  примордиальное чтение отвергнуто, потому что `load` знает единственный
  источник — `process.env`, и политику нельзя было бы переключить ни
  привязанным источником, ни `vars()` в тесте, — а «репетиция split в
  тестах» и есть главный сценарий `always-remote`.
- **`always-remote` в V1 — симуляция провода**: async-барьер, структурная
  копия payload и ответа (`structuredClone`), валидация ответа по
  `output`-схеме. Несериализуемое значение даёт отказ с именем поля. Смысл
  режима — поймать в dev и в тестах то, что сломалось бы при разъезде фич
  по процессам; local-путь ответ не валидирует (типы уже гарантируют
  форму), и эта разница документируется как свойство, а не деталь.
- **`emit` возвращает `Promise<void>`** по факту доставки, не обработки.
  Симметрия с `call` (`Ok | Fail`) ложная: подтверждать нечего, а
  обязанность разбирать результат fire-and-forget-вызова — шум на каждом
  call-site. Единственный осмысленный отказ («некому обработать») поднят на
  сборку, где строго полезнее.
- **Подписка шины — шаг фазы WIRE, а не `serve`.** Гарантия фазовой модели
  говорит, что `@OnStart` уже вправе звать порт, а go-live транспортов идёт
  **после** `@OnStart` — значит при `always-remote` вызов из `@OnStart`
  оказался бы недоставленным. Поэтому `InProcessBus` подписывает маршруты
  в `bindPorts` (WIRE), а `serve` остаётся точкой связывания сигнала
  приложения с каналом остановки. Побочный выигрыш: тестовый корень,
  который до START не доходит вовсе, гоняет обе политики.
- **Множество ответов порта закрыто `E ∪ UnknownError ∪ kernel-коды.**
  Ре-гидрация по `code` одинакова на обоих путях; kernel-коды (сегодня
  `VALIDATION_FAILED`, завтра `DEADLINE_EXCEEDED`) контрактны для порта по
  той же причине, по которой они контрактны для ручки, — иначе штатный
  отказ валидации входа приезжал бы потребителю `UnknownError`'ом.
- **Вызыватель, запрошенный декларацией, материализуется якорем.** Члены
  token-семейств собираются по `deps` **провайдеров**, а декларация
  провайдером не является (её зависимости гасит WIRE). Kernel-модуль портов
  получает список `deps` обнаруженных деклараций и регистрирует по ним один
  служебный узел-якорь — без него `deps: [C.port]` у ручки давало бы «no
  provider» в WIRE. Альтернатива «расширить сбор членов в контейнере» не
  выбрана: это правка ядра контейнера ради одного потребителя.

### Отвергнутые варианты

- **Отдельная ось регистрации контрактов** (`contracts:` в модуле, свой
  реестр реализаций, свой рантайм исполнения) — второй способ объявить
  обработчик запроса и вторая машинерия исполнения; ровно то, от чего ушёл
  #24.
- **Шина, регистрируемая всегда** — приложение без контрактов платило бы
  узлом графа; вместо этого kernel-модуль заводит шину только при непустой
  топологии реализаций, а вызыватели и держатель исполнителей — члены
  семейств, то есть материализуются по требованию.
- **Ленивый резолв «кто обслуживает контракт» на каждом вызове** — тот
  самый runtime-lookup, ради отсутствия которого биндинг вынесен на сборку.

### Открытые вопросы

- Диагностика необработанного отказа `emit`: сейчас печать тем же путём,
  что у стража границы; при появлении структурного логгера пересматривается.
- Имя пакета: рантайм живёт в `@nestling/ports`; zero-runtime-deps
  `@nestling/contracts` появится вместе с `makeClient` (#22), и туда
  переедет объявление контракта с реэкспортом.

## [2026-07-31] Порты: бюджет вызова моментом, ключ идемпотентности у команд

### Контекст

Реализация change `port-deadline-idempotency` (#27) забирает обещание,
записанное над `PortMeta` change'ем #11: «`deadline` и `idempotencyKey`
приезжают отдельным change'ем и встают сюда, не меняя ни одного call-site».
Запись [2026-07-13] «Порты: deadline, идемпотентность, версионирование
контрактов» назвала модель (gRPC), но оставила открытыми форму значения,
владельца пересчёта, поведение бюджета в полёте, наследование вглубь и
место определения отказа. Плюс два вопроса, которых там не было вовсе:
кто чеканит ключ идемпотентности и как профиль доезжает до кода
произвольной глубины.

### Решение

- **`deadline` — абсолютный момент `Date`, а не число и не длительность.**
  Длительность «протухает» на каждом await'е между её вычислением и
  вызовом; момент — нет, и он же переживает передачу дальше по цепочке.
  `deadline: number` не принимается: `500` одинаково правдоподобно читается
  и как epoch-миллисекунды, и как «через 500 мс», а разница между этими
  прочтениями — разница между мгновенным fail-fast и полусекундным
  бюджетом. Сахар — `deadlineIn(ms)`.
- **По проводу — относительный `timeoutMs`, внутри процесса — момент.**
  Отправитель считает остаток по своим часам, получатель превращает его
  обратно в момент по своим. Ни одна сторона не сравнивает свои часы с
  чужими, поэтому skew между подами на семантику не влияет — бюджет съедает
  только транзит. Пересчёт делает шина: конверт принадлежит ей, и
  NATS-транспорт сделает ровно то же, читая header.
- **Три точки контроля, и все три — существующая машинерия.** Fail-fast до
  вызова (`dispatch`/шина не тронуты), fail-fast до обработки на приёме
  (`dispatch.call` не зовётся) и отмена **в полёте**: `AbortSignal.timeout`
  в композиции с `meta.signal`. Третья точка не факультативна — бюджет,
  который не прерывает работу, это не бюджет, а комментарий: вызов с
  `deadlineIn(50)` мог бы честно ждать минуту.
- **Различение отмены — по владению таймером, а не по `signal.reason`.**
  Оборвал собственный таймер бюджета → `DeadlineExceeded`; оборвал
  `meta.signal` вызывающего → `UnknownError`, как было. `reason` приходит
  из кода вызывающего и доверенным источником не является.
- **Бюджет вглубь не наследуется — ровно как `signal`.** Обработчик,
  отдающий остаток дальше, передаёт его явно. Автонаследование через ALS
  (модель gRPC context) отвергнуто на три голоса: прецедент `signal`
  (`meta?.signal ?? NEVER_ABORTED`); требование `port-invocation`, что
  ambient-контекст вызывающего не протекает внутрь реализации, — а подхват
  бюджета из ALS это ровно протекание; и `no runtime magic`. Отсюда же
  следует, что переменная `Deadline` — не удобство, а **условие
  выполнимости** явной передачи.
- **Дефолтного бюджета нет** — открытый вопрос записи [2026-07-13]
  закрывается в пользу «бюджет только явный». Framework default — это
  неявный таймаут, который однажды обрежет легальную длинную операцию, и
  владелец ручки о нём не узнает. Побочно: вызов без `deadline` не заводит
  ни одного объекта на горячем пути.
- **`idempotencyKey` — только у `command`, и это ошибка компиляции.**
  Словарь meta выбирается по виду контракта (`MetaOf<C>`), поэтому
  `OrderPlaced.emitter.emit(p, { idempotencyKey })` на событии не
  компилируется. Молчаливо игнорируемое поле — худший вариант: код
  выглядит идемпотентным и не является им. Это тот же приём, которым #11
  закрыл `.port` у `event`.
- **`MetaOf<C>` дискриминирует по полю `kind`, а не по `C extends
  CommandContract`.** Контракт несёт токен вызывателя, вызыватель —
  `InvokeArgs`, а тот снова `MetaOf`: структурная проверка контракта
  целиком уходит в бесконечную рекурсию и роняет `tsc` на первом же
  `Port<typeof C>` — то есть на форме, которую сами доки и показывают.
  Дискриминант этой петли не имеет. Вскрыто тип-тестом, а не пользователем.
- **Ключ чеканит вызыватель, если его не дали.** `emit` команды всегда
  едет с ключом. Причина — ключ должен быть стабилен относительно
  **ретраев доставки**, а не относительно вызовов: ретрай одного и того же
  `emit` обязан нести тот же ключ, два разных `emit` — разные. Ключ,
  рождённый в транспорте, такой гарантии не даёт: транспорт не знает, где
  кончается один `emit`.
- **Профиль доезжает двумя каналами.** Безусловный — `raw.attributes`
  (провод, рядом с `subject`, кладут оба вызывателя и шина). Второй —
  ambient-переменные `Deadline`/`IdempotencyKey` со штатными писателями
  `withDeadline()`/`withIdempotencyKey()`, точная копия схемы `RequestId` +
  `withRequestId()`. Переменные экспортируются **значениями**, потому что
  политика `everyEndpoint(…).hasVar(IdempotencyKey)` адресует значение, а
  не имя. Это не дублирование: атрибуты — провод, переменная — проекция,
  проверяемая на сборке.
- **Определение отказа живёт в `@nestling/pipeline`, а не в
  `@nestling/ports`.** Там же, где `KERNEL_FAIL_CODES` и `isKernelFailCode`:
  регистрация кода из чужого пакета означала бы рантайм-мутацию множества,
  обещанного закрытым. `@nestling/ports` определение реэкспортирует.
- **Имя — `DeadlineExceeded`, без суффикса `Error`.** Соседи по набору —
  `ValidationFailed`, `StreamLimitExceeded`, `StreamGapTimeout`;
  `UnknownError` в этом ряду исключение, а не правило. Дизайн-доки писались
  до появления набора и называли определение `DeadlineExceededError` — их
  правит этот change.

### Отвергнутые варианты

- **`timeout: number` как длительность в meta** — проще на call-site, но не
  переживает цепочку вызовов: каждый hop начинал бы бюджет заново, то есть
  суммарное время не ограничивалось бы ничем. Ровно та ошибка, из-за
  которой gRPC перешёл на deadline.
- **Абсолютный момент по проводу** — при рассинхроне часов бюджет
  становится недостоверным в обе стороны: либо мгновенный fail-fast на
  здоровом вызове, либо бесконечный бюджет.
- **Только fail-fast до вызова, без отмены в полёте** — букве записи
  [2026-07-13] удовлетворяет, но даёт бюджет, который ничего не
  ограничивает.
- **Одно общее поле `idempotencyKey` в `PortMeta` с рантайм-проверкой
  вида** — рантайм-ошибка вместо ошибки компиляции там, где вид контракта
  известен статически.
- **Не чеканить ключ, оставляя поле пустым** — тогда «ядро гарантирует, что
  ключ доедет» превращается в «доедет, если вы его задали», и
  сателлит-дедупликатор обязан уметь работать без ключа.
- **Well-known read-only переменные по образцу `Signal`** (значение из
  `RequestCell`, а не из накопленного `input`) — потребовало бы расширить
  `RequestCell` и правило «второго хранилища нет» двумя полями ради
  удобства, которое штатный pre-юнит даёт бесплатно. `Signal` живёт там
  **по необходимости**: сигнал существует и у ручки без пайплайна.
- **Дедупликация в ядре** — хранилище ключей, окно, ответ-повтор. Ядро
  хранилище не тянет (запись [2026-07-14] «Kernel 1.0»); если сателлиту не
  хватит ключа и юнита, это фиксируется отдельной записью, а не точечным
  хаком.

### Открытые вопросы

- **`idempotencyKey` для `request`** (ретрай POST-подобных вызовов)
  остаётся открытым: форма `MetaOf<C>` выбрана так, что расширение вида не
  ломает call-site.
- **Собственный статус бюджета на проводе, отличный от 504** («мой бюджет
  истёк» против «апстрим не ответил») — вопрос к #12, когда появится
  настоящий remote hop.
- **`Ctx(...)` в `deps:` декларации не материализуется**: члены
  token-семейств собираются фикспоинтом по `deps` **провайдеров**, а
  kernel-модуль контекста, в отличие от портового, списка деклараций не
  получает. Канон — читать переменную из провайдера (`@Injectable`), и
  витрина написана так; но асимметрия с `C.port` в `deps:` ручки реальна и
  ждёт решения.

## [2026-07-31] Версионирование контрактов: снапшот из дискавери, вердикт по слоту, третий вердикт `unknown`

### Контекст

Запись [2026-07-13] («Порты: deadline, идемпотентность, версионирование
контрактов», п. 3) зафиксировала половину решения: версия живёт явно в имени,
а схемный дифф против снапшота **подсвечивает** breaking changes и **не
блокирует**. Вторая половина — как именно устроены снапшот, дифф и отчёт —
решалась при реализации change #26, поверх готовых `implement`, дискавери и
`.check()`-матрицы.

Дизайн формируют три ограничения: Standard Schema непрозрачна в рантайме
(интроспекции нет — см. [2026-07-13] «Схемы»), отчёт во фреймворке всегда
значение, а не лог, и «не блокирует» обязано быть свойством конструкции, а
не обещанием в доке.

### Решение

- **Источник снапшота — дискавери, а не приватный реестр `makeContract`.**
  Снапшот отвечает на вопрос «что я обещал наружу», поэтому строится из
  деклараций с bus-биндингом (`busBindingOf`) — из того, что приложение
  **реализует**. Спека `contract-declarations` прямо запрещает делать
  реестр источником истины о составе: в него попадает всё импортированное,
  включая контракты соседних фич.
- **Матрица сводится объединением топологий.** Контракт публикуется
  топологией, а не приложением; дескриптор несёт перечень опубликовавших
  топологий, поэтому «контракт удалён» и «фича не выбрана в этой
  топологии» различимы, а не сливаются в красный отчёт.
- **Направление берётся из слота, а не из роли смотрящего.** `input`
  приходит в реализацию (сужение принимаемого — `breaking`), `output`
  уходит из неё (ослабление гарантии — `breaking`). Правило одинаково для
  `request`, `command` и `event` — включая `event`, где реализация является
  подписчиком: «подписчик стал требовать больше» и есть breaking для
  издателя.
- **Третий вердикт `unknown` вместо «раз не знаю — значит совместимо».**
  Разбираемое подмножество JSON Schema закрыто (`type`, `properties`,
  `required`, `items`, `enum`, `nullable`; рекурсия — по `properties` и
  `items`); композиционные ключевые слова (`$ref`, `allOf`, `oneOf`,
  `anyOf`) и любое изменение незнакомого ключевого слова дают `unknown` с
  JSON-путём. Непрозрачный лист и смена вендора — тоже `unknown`.
  `unknown` **не** приравнен к `breaking` намеренно: смена патч-версии
  конвертера перекрасила бы весь отчёт в красный, и им перестали бы
  пользоваться. Совпадение незнакомого ключевого слова расхождением не
  является — иначе `$schema` от конвертера красил бы каждую строку.
- **Отсутствие флага блокировки — конструкция, а не умолчание.**
  `diffContracts` не участвует в сборке, не вызывается из `run()`/`check()`
  и не бросает по результату сравнения. Уронить CI можно ровно одним
  способом — написать `expect(report.breaking).toEqual([])` в своём тесте.
  Единственное исключение — нечитаемый baseline (чужая `snapshotVersion`,
  значение не того вида): это ошибка автора проверки, а не breaking change,
  и она бросает — по той же линии, по которой
  `AsyncSchemaNotSupportedError` отделён от `SchemaValidationError`.
- **Конвертер живёт на схемном слое, а не в пакете документации.**
  `SchemaDocConverter { vendor; toJsonSchema(schema) }` заводится в
  `@nestling/pipeline`, потому что потребителей два и второй (снапшот)
  приезжает раньше первого (`@nestling/openapi`, #20). Строгость при
  отсутствии конвертера в диспетчер не зашита: он возвращает «конвертера
  нет» наблюдаемым исходом, а решение принимает потребитель — документации
  fail-fast на boot, снапшоту вердикт `unknown`.
- **Подсказка bump'а — подсказка.** Контракт с хотя бы одним `breaking`
  получает в отчёте `suggestedName` (`billing.charge` → `billing.charge.v2`,
  `user.create.v2` → `.v3`). Это **единственное** место, где суффикс `.vN`
  распознаётся: `makeContract` его не требует и не разбирает, поля версии
  не существует, переименования не происходит.

### Отвергнутые варианты

- **Хеш схемы вместо JSON Schema** — отвечает «изменилось», но не «что и в
  какую сторону», а весь смысл отчёта в строке «breaking: удалено поле X».
- **Своя мини-интроспекция zod** — запрещена принципом
  ([2026-07-13] «Схемы»: интроспекция вендорских схем не заводится нигде) и
  ломается на каждом мажоре валидатора.
- **Второй пакет-конвертер ради снапшота** — `@nestling/openapi.zod` часть
  #20; заводить свой значило бы обещать пользователю два. Гайд показывает
  конвертер в десять строк поверх `z.toJSONSchema()`, тесты и пример
  используют его же фикстурой.
- **Общий fail-fast при отсутствии конвертера** — сделал бы снапшот
  бесполезным без конвертера, хотя его структурная часть (вид, формы,
  коды отказов) точна и так.
- **Классификация по роли (владелец/потребитель)** вместо слота —
  потребовала бы знать, кто смотрит отчёт, и давала бы разные вердикты на
  одном и том же снапшоте.
- **Флаг `failOnBreaking`** — наличие флага делает блокировку штатным
  режимом фреймворка и провоцирует «включим на всякий случай». Тест на
  равенство отчёта — та же строка кода, но без нашей санкции. Это
  продолжение отвергнутого в [2026-07-13] «additive-only как жёсткое
  правило».
- **Снапшот из потребляемых контрактов (`.port` в `deps:`)** — симметричная
  и отдельная задача: снапшот описывает публикуемую сторону, ожидания
  потребителя живут на клиенте (#22).
- **Приравнять `unknown` к `breaking`** — см. выше: отчёт стал бы
  нечитаемым от шума конвертера.
- **`snapshotContracts(reports: CheckReport[])` с импортом типа из
  `@nestling/app`** — замкнуло бы граф пакетов (`app` уже зависит от
  `ports`). Функция принимает структурный тип `readonly { contracts }[]`.

### Открытые вопросы

- **Где живёт снапшот** — файл в репозитории или внешний registry. Перенесено
  из [2026-07-13] без изменений: форма API выбрана так, чтобы ответ не менял
  ни одну сигнатуру — baseline приходит **значением**, читает его
  пользователь.
- **Стоит ли расширять разбираемое подмножество JSON Schema** (`oneOf` как
  сумма, `allOf` как пересечение) — решать после #20, когда станет видно,
  что конвертеры реально порождают.
- **HTTP-поверхность в снапшоте** — механически возможна (дескриптор
  строится по декларации), но перекрывается OpenAPI-диффом из #20.
- **Файловые поля `multipart`** правила пока не покрывают (лимиты и MIME —
  свойства транспорта, а не схемы): их изменение даёт `unknown`.
