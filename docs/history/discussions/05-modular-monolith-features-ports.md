# Модульный монолит, фичи, порты, конфиг: логика решений

Сессия проектирования (2026-07-07/08). Документ фиксирует **весь ход
рассуждений**, а не только итоговые решения: какие варианты рассматривались,
почему отвергнуты, на каких развилках как повернули. Итоговая целевая картина
(схема + примеры) — в [`docs/design/composition-and-lifecycle.md`](../../design/composition-and-lifecycle.md).
Полный транскрипт — рядом: [`05-modular-monolith-transcript.md`](./05-modular-monolith-transcript.md).

---

## 0. Постановка

Гипотеза: перспективный способ структурировать относительно небольшие проекты
(до ~1M строк) — **модульный монолит с запуском выбранного подмножества фич**.
Один бинарник: локально `--features=all`, в проде отдельные фичи
масштабируются горизонтально по разным процессам. Вопрос: насколько nestling это
поддерживает и как реализовать.

---

## 1. Почему nestling уже почти готов

Два уже принятых решения оказались ровно теми, на которых строится эта модель:

1. **Модули — plain values** (`makeModule`/`makeAppModule` — identity-функции).
   ⇒ «фича» — тоже значение, а выбор подмножества фич — **фильтрация массива в
   композиционном корне**, а не рантайм-механизм в контейнере.
2. **Контейнер жадный** (`build()` инстанцирует весь граф, топосорт init/destroy,
   проверка циклов). ⇒ «не выбрал фичу → её провайдеры не построились»
   получается **само собой**.

Вывод: ~80% модели бесплатны. Но есть **одна вещь, которая активно мешает**.

### Что мешает: глобальный registry эндпоинтов

`packages/nestling.pipeline/src/metadata/endpoint-registry.ts:10` — модульный
глобальный `Set`. Декоратор `@Endpoint` (`endpoint.ts:97`) при импорте класса
**сам себя** туда регистрирует. `App.#registerEndpoints` (`app.ts:200`)
итерирует `getAllEndpoints()` и делает `container.get(EndpointClass)` — и
**бросает**, если класс в registry, но его модуль не в контейнере.

Это прямо конфликтует с выбором подмножества: импортировал файл фичи (транзитивно,
barrel, тест) → её эндпоинты в глобальном Set → App пытается их инстанцировать и
падает. Дискавери эндпоинтов **ортогонален** тому, какие модули выбраны.

**Решение:** эндпоинты обнаруживать **обходом дерева зарегистрированных модулей**
(`AppModule.endpoints` + `imports`), не из глобального registry. Это и баг-фикс
сам по себе (глобальный Set протекает при любом импорте). Предпосылка №1.

## 2. Слой «фича» над модулями

Фича — уровнем выше `AppModule`: именованный бандл модулей + декларация того, что
фиче нужно от рантайма. Раз модули — значения, фича тоже значение
(`makeFeature({ name, modules, dependsOn })`). Селектор замыкает `dependsOn`,
собирает модули выбранных фич, отдаёт в существующий `App`. **Ноль новой
машинерии контейнера** — фильтрация значений.

`--features=all` (локалка) и `--features=orders` (масштабирование одной функции) —
разные аргументы одного бинарника.

**Capability negotiation (первая формулировка, позже упрощённая — см. §7):**
разные подмножества фич = разные топологии одного кода (`api` поднимает HTTP;
`workers` — консьюмеры очереди, HTTP не открывает). App поднимает только нужные
транспорты, fail-fast при неудовлетворённой потребности.

## 3. Порты — межфичевое взаимодействие (интеллектуальное ядро)

### Наблюдение, сократившее объём вдвое

Порт распадается на два направления:

- **Inbound** («я обрабатываю контракт») = **буквально endpoint**. `App` уже
  роутит эндпоинты по `metadata.transport`; contract-endpoint с `transport:'nats'`
  ляжет на NATS-транспорт. **Ноль изменений в ядре** (кроме фикса дискавери).
- **Outbound** («мне нужно позвать контракт») = **единственное, чего нет**:
  типизированный клиент + решение local-vs-remote.

Значит новая абстракция нужна только для исходящей стороны.

### Контракт как общее направление-нейтральное значение

Порт и endpoint должны рождаться из одного schema-first значения, иначе разъедутся:
`makeContract({ name, kind, input?, output?, payload? })`. Три вида:

| `kind` | Семантика | Потребителей | NATS |
|---|---|---|---|
| `request` | request-reply, Fail-able, таймаут | ровно 1 владелец | req/reply |
| `command` | fire-and-forget, обработать должен один | 1 владелец (реплики делят) | queue-group / JetStream |
| `event` | fire-and-forget, broadcast-факт | 0..N | fan-out / JetStream |

Различать `command`/`event` важно для **горизонтального масштабирования**: N реплик
подписываются одной **queue group** → нагрузка делится. Subject-адресация NATS →
добавил реплику, конфиг не трогал.

### Две регистра одного call-site и location transparency

`co-located` (в одном процессе) A→B = вызов через DI, синхронно, транзакционно.
`split` (разные процессы) = сеть, async, может упасть. «Масштабировать функции
независимо» ⇒ **один call-site должен работать в обоих режимах без переписывания
A**. Это location transparency, и она в лоб противоречит принципу «no runtime
magic».

**Разрешение противоречия:** индиректность резолвится **на сборке, а не на
запросе**. Фичи общаются только через типизированные порты; биндинг порта (local
vs remote) выбирает селектор в композиционном корне, зная выбор фич + топологию.
На запросе A зовёт конкретный клиент-константу — никакого service discovery в
контейнере. Это «жадная композиция константами».

### Дисциплина (жёсткие правила — nestling «even more opinionated»)

- **`.call()`/`.emit()` всегда async + `Ok/Fail`, даже co-located** — потому что
  завтра между фичами сеть. Тип call-site у co-located и split **идентичен**. То,
  что граница-порт синтаксически отличается от «внутри фичи» (обычный DI), и
  отделяет модульный монолит от распределённого монолита.
- **Порты никогда не транзакционны, даже co-located.** Иначе общая транзакция
  ломается при split. Кросс-фичевая согласованность = события + outbox/saga.
- **Локальный порт обязан уметь падать** (тип `Ok|Fail`), иначе напишут
  потребителей, не обрабатывающих `Fail`, и split их убьёт.
- **Outbox-проблема** (`emit` + запись в БД атомарно) — отложенный вопрос, всплывёт
  на `event`+`durable`.

### Как выглядит в коде

Владелец реализует контракт как endpoint; потребитель инжектит `ChargeCard.port`
(токен из контракта) и зовёт `.call(input, meta): Promise<Ok|Fail>`; эмиттер —
`OrderPlaced.emitter`, консьюмер — contract-endpoint вида `event`. Полные листинги
в целевом доке (L3).

### Инфраструктура

Ядро зависит от одного интерфейса `IMessageTransport` (`request`/`publish`/
`subscribe`) — LCD NATS-глаголов. Две реализации: `InProcessBus` (Map, прямой
вызов, zero-dep) и `NatsTransport`. `meta.signal` (уже есть) → таймаут/отмена.
`Topic` (из streaming-идей) → in-proc шина для локального `emit`.

### Не прибиваемся к NATS

Ядро знает только `IMessageTransport`; `@nestling/transport.nats` — отдельный
пакет, как `transport.http`. Интерфейс держим на LCD (`request/publish/subscribe`
+ queue-group + флаг `durable`); NATS-specific (JetStream KV, wildcard-subjects,
ack-семантика) **не протекает** в контрактный API — та же дисциплина, что с
границей RxJS. Лакмус: `transport.amqp`/in-memory пишутся, не трогая ядро.

## 4. Дихотомия `messaging` / `transports` — ложная

Первый набросок конфига разделил `transports: {http}` и `messaging: nats`. Это
неверно: **NATS — транспорт**, он и экспонирует inbound (`ITransport`), и зовёт
outbound. Правильно — **один мешок транспортов с разными способностями**:

```
InboundTransport  { endpoint; listen; close }   // HTTP, CLI, NATS
OutboundTransport { request; publish }           // NATS
```

Конкретный транспорт реализует то подмножество, что умеет. Биндинг портов
спрашивает capability: «кто здесь `OutboundTransport`?».

---

## 5. `NATS_URL`-флаг — тернарник был враньём

Набросок содержал `messaging: NATS_URL ? nats() : undefined`. Ошибка: локальность
определяется `select`, но сам транспорт — инфраструктура, он **не условный от
select**.

> Конфиг транспортов статичен и одинаков для всех процессов одного развёртывания;
> между процессами меняется только `select`.

Тонкость, замеченная в обсуждении: **процесс не знает локально, кто позовёт его
контракты снаружи.** Если `--features=billing`, а orders в другом поде — billing
обязан экспонировать `billing.charge` на NATS, хотя его `select` про orders не
знает. Правило:

- **inbound:** фича подписывает свои контракты на каждый сконфигурированный
  `OutboundTransport` — всегда, когда шина есть;
- **outbound:** порт к невыбранному владельцу биндится на шину.

Следствия: распределённое развёртывание → NATS везде одинаково; локалка
(`all`+нет NATS) работает (нет remote-портов); fail-fast только при
`подмножество + потребляешь чужой контракт + шины нет`. Разница «локально/прод» —
**в конфиге, не в коде**.

## 6. Диспатч — политика, а не зашивка

Идея «всегда через NATS, даже co-located» не тупа — это модель «everything is a
message» (OTP). Ошибка первого наброска — жёсткая зашивка «local owner → всегда
in-proc». Правильно: **порт всегда говорит с *шиной*, а не с фиксированным
клиентом**, а какая шина — политика, выбранная на сборке:

- `local-first` (дефолт-кандидат): co-located → in-proc, иначе сеть;
- `always-remote`: всегда через шину (uniform, «всё — сообщение»);
- `balanced`: размазать local + remote-реплики (client-side spill).

Реализации `IMessageBus`: **in-proc-direct**, **NATS**, **in-proc-simulated**
(async + сериализация без реального NATS — message-семантика в тестах/dev).
`local-first`/`always-remote` резолвятся в одну константу на старте (рантайм-lookup
ноль); `balanced` — единственный с рантайм-диспатчем, и в него оптишься явно.
Балансировка: NATS queue-groups дают server-side LB бесплатно; client-side нужен
только для local/remote spill = `balanced`. **Смена политики = смена конфига,
call-site не меняется.**

(Инъекцию отказов в in-proc-simulated рассматривали и **убрали** — остаётся только
async + serialization-граница.)

Открытая развилка: дефолтная политика. `local-first` быстрее/zero-dep, но два пути
исполнения (риск «локально работает, split падает»). `always-remote` (через
in-proc-simulated в dev) убирает этот класс багов ценой сериализации даже в одном
процессе. Склонение — к `always-remote`, но «remote» в dev = симулированная шина,
не поднятый NATS.

## 7. Транспорты — провайдеры, а не мешок в конструкторе

Вопрос: зачем вообще конфигурировать «набор транспортов»? И мысль: транспорты
передавать классами, инициализировать в контейнере.

Разбор: **транспорт — обычный синглтон с зависимостями и lifecycle**, ровно то,
чем контейнер управляет. Мешок `transports: Record<string, ITransport>`
дублирует то, что контейнер уже умеет:

- **зависимости** — NATS-транспорту нужен connection-конфиг, HTTP — логгер, TLS;
  инстанцируешь руками снаружи → не инжектнуть;
- **lifecycle** — `listen`/`close` = фаза; `App` руками гоняет `Promise.all` —
  переизобретает то, что контейнер делает по графу.

Главное следствие: **если транспорты — провайдеры, «какие транспорты существуют»
выводится из `select`**, а не отдельная ручка. Фича, которой нужен HTTP,
импортирует infra-модуль с транспортом. То есть в §2 я пересчитал assembly-config:
«набор транспортов» — не независимая ось.

Бонусы: endpoint ссылается на транспорт **токеном, а не строкой**; **capability
negotiation исчезает** как отдельная механика (HTTP-endpoint без `HttpTransport` в
графе → тот же fail-fast, что уже есть).

### Выявленная тонкость: go-live — отдельная фаза

Транспорт не должен слушать до навешивания эндпоинтов. `App` уже разведён на фазы
(`#init` → `#registerEndpoints` → `#listen`); меняется только источник транспортов
(из контейнера, дискаверятся из дерева модулей). Дисциплина:

- `@OnInit` = захватить ресурс (connect);
- регистрация эндпоинтов — между;
- **`listen`/go-live** = `@OnStart`, драйвится App, не `@OnInit`.

Это ответ на «нужен ли `@OnStart` в дополнение к `@OnInit`»: да, чтобы «wiring
между init и start» стал гарантией графа.

### Что осталось внешним (пересмотр)

Схлопнулось почти всё: набор транспортов → из `select`; port-биндинг → из графа;
capability negotiation → DI + fail-fast. Неснимаемо-внешним осталось: **`select`**
(решает, что в билдере) + **сырая загрузка конфига** (фаза 0).

## 8. Гарантия `dispatch`: почему `listen` на `@OnInit` невозможен

Вопрос: что запретит разработчику транспорта повесить `listen` на `@OnInit`?
Честный ответ: **ничего** — «дисциплина» из §7 это конвенция, footgun. По стандарту
nestling («guarantee, not convention») недостаточно.

Лестница enforcement:

| Уровень | Механизм | Абузится? |
|---|---|---|
| конвенция | «положи listen в start-фазу» | да |
| **dispatch как обязательный аргумент** | go-live требует ресурс, доступный только на `@OnStart` | нет разумного пути |
| инверсия акцептора | фреймворк владеет сокетом, транспорт = `(req)=>res` | нет вообще |

**Средний уровень (дефолт):** убрать nullary `listen()`; уйти в эфир можно только
приняв **готовый диспетчер** (`serve(dispatch, signal)`), а `dispatch` не
существует до фазы регистрации. Транспорт — переводчик провода, не владелец
роутинга; ранний listen не просто неудобен — ему **нечего маршрутизировать**.
`dispatch` — фазовый ресурс: на `@OnInit` не резолвится, на `@OnStart` да. Инверсия
акцептора (level-3) — опция для транспортов, где акцептор естественно отдаётся
фреймворку (HTTP), но хуже для pub/sub (NATS-подписка = акцептор). Итог: `listen()`
из публичного контракта транспорта **убираем**, остаётся `serve(dispatch, signal)`.

## 9. Жизненный цикл (итог фаз)

```
0 BOOTSTRAP  load+validate config · select     → FAIL-FAST
1 ASSEMBLE   build граф · discover · bind ports → FAIL-FAST
2 INIT       @OnInit: захват ресурсов · connect · dispatch НЕ существует
3 WIRE       регистрация эндпоинтов · dispatch РОЖДАЕТСЯ здесь
4 START      @OnStart: serve(dispatch, signal) — не listen()
5 RUN        port.call/emit → local | bus · live config-refs
6 SHUTDOWN   реверс START · abort in-flight (meta.signal) · @OnDestroy
```

Несущая ось: `dispatch` рождается строго между INIT и START. Слить WIRE в ASSEMBLE
нельзя — `dispatch` станет доступен слишком рано и гарантия §8 сломается. START по
топосорту, SHUTDOWN строго в реверсе.

## 10. Опциональность машинерии (прогрессивное раскрытие)

Принцип: **приложение из одной фичи выглядит так, будто фич нет вообще.** Слои
аддитивны:

- **L0** модули + транспорт (ни features, ни select, ни портов);
- **L1** + config;
- **L2** + `makeFeature` + `select` (монолит с выбором);
- **L3** + контракт + порт (co-located, in-proc);
- **L4** + NATS + policy (split).

Между L3 и L4 **код фич не меняется** — разнесение живёт в композиционном корне и
конфиге. `assemble(...)` — одна функция с опциональными полями; простой случай
игнорирует всю машинерию. Приведены два стиля (класс + функциональный), корень
почти идентичен — различаются строительные блоки.

## 11. Конфигурация (самый длинный разбор)

### 11.1. Отказ от class-стиля rsdk

rsdk-стиль (`Config`-классы + `@Property`) многословен. Идём в `makeConfig(schema)`
с хелперами. Рассмотрели 4 стилистических варианта:

1. zod + префикс-конвенция (компактно, детерминированная «магия»);
2. zod + явная карта ключей (никакой магии, многословно);
3. field-хелперы `env('KEY').number().default()` (явно, самодостаточно);
4. source-accessor функция (максимум явности, source-scoping буквальный, но нет
   объекта-схемы для интроспекции).

Выбор сузился до 1 и 3.

### 11.2. Неявные провайдеры и kernel/user space

Модель: `app`/infra-модули «подсовывают» в граф провайдеры, которых пользователь
не писал. Аналогия с ОС:

- **kernel space** (токены **не** экспортируются): `ConfigSource`, транспорты,
  bus/port-client, машинерия графа;
- **user space**: сервисы, endpoints, контракты, конфиг-как-данные;
- граница пересекается только через публичные «syscalls»: инжект `Config<X>`,
  `Port/Emitter`, возврат из endpoint.

**Enforcement — не рантайм-ACL, а видимость ES-модулей** (ideas.md решение 3): не
экспортировал токен → нечем инжектить. Транспорты не инжектятся в произвольные
сервисы; до провода добираешься только через `Port`/`Emitter`.

Ключевой поворот: **декларативный `makeConfig(schema)` делает провайдер конфига
фреймворк-генерируемым** → `ConfigSource` инжектит фреймворк, пользователь не пишет
проводку и не нуждается в токене источника. Источник не протекает в user-space
вообще. В rsdk-стиле конфиг-класс пишет пользователь и туда прокидывается
`ConfigContext` — концепт подтекает. **Декларативный конфиг улучшает инкапсуляцию.**

### 11.3. `OnConfiguration`-хук — не нужен (и строго)

Рассмотрели идею отдельного lifecycle-хука для стадии конфигурации. Разложили, что
он мог бы значить, и куда каждый смысл девается:

| «OnConfiguration» мог бы значить | Куда уходит |
|---|---|
| загрузить источники | фаза 0, до контейнера — не хук |
| спроецировать источник → секцию | обычное построение провайдера |
| «конфиг готов, отреагируй» | ты зависишь от секции → контейнер строит тебя после |
| захватить ресурс по конфигу | `@OnInit` потребителя |
| конфиг перезагрузился | событие reload, не стартовый хук |

Самый острый аргумент: **хук грубее зависимости.** Хук — барьер «весь конфиг →
весь init». Зависимость даёт точную топологию: `DbConfig` готов ровно перед
`DbPool`. Отличие от `@OnInit`: тот — сайд-эффектная выдача ресурса; чтение конфига
— чистая проекция. Конфиг — не фаза, а зависимость. Хук избыточен и **строго
хуже**.

Жадный контейнер даёт **eager-валидацию бесплатно**: все секции инстанцируются на
build → провалидированы → fail-fast. rsdk форсит это вручную, потому что Nest
ленив.

### 11.4. Что легитимно в глобальном конфиге — почти ничего

Критерий: **что нельзя выразить провайдером без цикла** — то, что решает, какие
провайдеры существуют. Это:

1. **`select`** — какие фичи в билдере (провайдером быть не может: цикл);
2. **source-bootstrap** — как/откуда грузить остальной конфиг (адрес Vault,
   префикс) — из примордиального env. Ровно `appName`/`sources`/`strategy` из
   `forRoot` rsdk.

**Всё остальное — provider-config в секциях.** DB URL, NATS servers, HTTP port,
dispatch-policy — обычные параметры, инжектятся в свои узлы. (Ранее я по ошибке
относил connection strings к «структурному» — развилка §11.5.) rsdk подтверждает:
`forRoot` держит только appName/sources/strategy, не бизнес-значения.

### 11.5. Ошибка «connection strings — структурный конфиг»

Поймана в обсуждении. Я склеил две ортогональные оси:

- **A — определяет ли форму графа** (какие узлы существуют);
- **B — дорого ли подменить на живую** (re-init стоимость).

Connection string по оси A **не структурная**: узел БД существует независимо от
значения URL. «Нужен рестарт» — следствие того, что *держатель* (пул) дорого
пере-инициализировать (ось B), а не структурности. Свойство перезагружаемости живёт
**на потребляющем узле, а не на конфиге**. Исправленная модель: **assembly-config**
(билдер: select, транспорты, policy) vs **provider-config** (всё остальное).

### 11.6. Source-agnostic: merge → Vars → project (подход B), а не source-per-field

Развилка: конфиг знает про источник (`env('KEY')`) — или мержим источники в общий
`Vars` (как rsdk) и конфиги потребляют результат?

Дискомфорт от `env('KEY')`: **«откуда берётся значение» — это environment, а
environment — kernel-space забота.** Конфиг (user space) должен быть
провенанс-слеп (читает ключ из мержа, как программа читает `fd`). Аналогия §11.2
диктует ответ.

| | **B: merge → Vars** | **A: `env()` в поле** |
|---|---|---|
| знает источник | нет | да |
| перенести env→vault | правка источников | правка конфига |
| precedence | единый | per-field, мутный |
| reload | единый (`'merge'`) | per-source |
| «только из vault» | source-policy (kernel) | в поле |
| kernel/user граница | чистая | протекает |

Чего не может B — сказать в поле «только из vault»; но это *политика источника*
(kernel), восстанавливается там, где ей место. Вывод — **B**. Вариант 1 уже B
(префикс → ключ, не источник); вариант 3 становится B заменой `env('KEY')` →
`from('KEY')`. Вербы `env/file/vault` живут только в root-объявлении источников.

### 11.7. Reloadable-конфиги

Источник с наблюдением (`reloadableFile`, `vault({watch})`) на изменение
пере-сливает `Vars`, пере-проецирует reloadable-секции (инстанс стабилен, поля
обновляются на месте). Потребление: **read-latest** (читаем при использовании,
подписка не нужна) или **react** (`onChange(signal, cb)` — перестроить ресурс).
Две асимметрии со стартом:

- **старт: невалидный → die; reload: невалидный → keep last-good + warn.**
- **вступит ли в силу — ответственность потребителя** (read-latest/onChange — да;
  захваченное в конструкторе — нет). reloadable — opt-in.

### 11.8. Источники — тоже провайдеры (производные от env)

> **Супёрсид (см. §15):** этот шаг (sources-как-провайдеры → merged `Vars`) был
> промежуточным. Финал — конфиг как token-families, `sources`/`Vars` как отдельная
> подсистема убраны совсем. §11.6/§11.8 читать через §15.

Наблюдение: чтобы сходить в файл, путь хочется указать в `.env`. Значит источники
кроме env — **производные** (сконфигурированы из env), и нужны не всегда. ⇒ сделать
их **провайдерами** (`@nestling/config.file`, `@nestling/config.vault`).

Это тот же приём, что с транспортами (§7): **убить bag** `sources: [...]`.
Зависимости источников образуют DAG, укоренённый в примордиальном env:

```
EnvSource → FileSource/VaultSource (конфиг из env) → ConfigSource (merge) → секции
```

Жадный топосорт секвенирует это как самый ранний слой того же контейнера — не
отдельная фаза (тот же аргумент, что против `OnConfiguration`). **Запрет циклов
защищает бутстрап** (vault-токен из файла, а путь файла из vault → cycle-ошибка).
Async-источники = async-factory, fail-fast сохраняется. Не нужен = не импортирован.
`select` остаётся единственным пред-сборочным чтением. Источники встают в kernel
рядом с транспортами.

**Сомнение — статическая выгрузка доки конфига** — снимается и даже улучшается:

1. что приложение *потребляет* — declarative *секции*; схема — данные,
   регистрируется на import (как rsdk `ConfigMetadataProvider`); выгрузка читает
   схемы **без значений/без live-vault** — источники-как-провайдеры на это не
   влияют;
2. что нужно *самим источникам* (`VAULT_ADDR`) — тоже declarative секция →
   попадает в ту же выгрузку.

Раньше `sources:[vault({addr:'...'})]` прятал конфиг источника литералом — теперь
он декларирован и виден. Доки **полнее**. Условие (lint-able): источник обязан
объявлять конфиг секцией, не читать ad-hoc (та же дисциплина `no-process-env`).
Теряется чисто-статический AST-обход — но он не нужен, import-time-реестр робастнее.

Поднятые к решению вопросы: **precedence должна стать явной** (`priority` на
источнике вместо порядка в bag); два уровня «нужен конфиг» — schema-level
(статично, доки/линт) vs value-level (рантайм, fail-fast).

## 12. Сквозные принципы (что выкристаллизовалось)

- **Неснимаемо-внешнее** = `select` + примордиальное чтение env (для select и
  координат источников). Всё остальное — провайдеры.
- **Видимость через ES-модули**, не рантайм-инкапсуляцию (kernel/user).
- **Жадная композиция константами**; индиректность (location transparency,
  dispatch-policy) резолвится на сборке/старте, не на запросе.
- **Конфиг — зависимость, не фаза**; провенанс-слепой; источники, транспорты,
  секции — всё провайдеры одного графа.
- **Explicit over implicit; guarantee over convention** (dispatch-as-arg,
  fail-fast, тип `Ok|Fail` на портах).
- Повторяющийся приём: **`X: [...]` bag → провайдеры из дерева модулей** (эндпоинты,
  транспорты, источники — трижды).

## 15. Финал конфига: token-families, `sources` убраны (супёрсид §11.6/§11.8)

### Наблюдение из rsdk grpc-клиентов

`ModuleGenerator.createClientModuleDefinition` для сервера: выводит env-ключ из
имени (`USERS_SERVICE_GRPC_ADDRESS`), **регистрирует standalone-свойство на лету**
(`ConfigMetadataRegistry.registerProperty`, `expectedInEnv:false`) — это «unbound
property», конфиг-свойство вне всякой секции; `forProperty(alias)` даёт провайдер,
резолвящий его; channel/client-провайдеры инжектят адрес. Инжектнул клиент →
env-адрес пришёл сам. On-demand: провайдеры генерятся ровно для инжектнутых
серверов. Второй режим (`createClientFactoryModuleDefinition`) — `factory.create(
runtimeAddress)` для рантайм-адреса.

### Это token families (roadmap item 5)

«Unbound property» = параметризованный конфиг-токен, член семейства.
grpc-клиент = `GrpcClient(server)`, транзитивно тянет `Config(addressKey(server))`.
**Жадный билдер видит запрошенные члены статически → инстанцирует на build без
рантайм-резолюции** (в отличие от ленивого rsdk — там factory-провайдеры под
ленивость Nest). Секция, unbound-свойство, on-demand-клиент, `ILogger(scope)` —
**один механизм**.

```
Cfg = makeTokenFamily<unknown,[key:string]>('Config')
familyProvider(Cfg, key => factoryProvider(Cfg(key),
  (reader) => reader.get(key), [ConfigReader]))   // ConfigReader — приватный kernel-токен: ОДНА центральная читалка (env — пол, vault/файл — override внутри неё), а не набор readers-провайдеров
GrpcClient(srv) → recipe → Cfg(addressKey(srv)) → ConfigReader   # всё в графе
```

Граница: **build-time параметр = семейство** (жадно, документируется);
**runtime параметр = фабрика** (репозиторий+кэш, вне жадного графа) — не смешивать.

### Отказ от `sources`

Чтобы сходить в файл, путь хочется в `.env` ⇒ источники кроме env производны и
нужны не всегда. Финал:

- нет `ConfigSource`/`Vars`-мержа/bag `sources: [...]`;
- **источники — не обычные провайдеры, а части одной центральной читалки**,
  настраиваемой только в composition root (уточнение после обсуждения: библиотека
  называет ключ и знать не должна, откуда он; «откуда читать» — одно на приложение,
  модули его не приносят);
- **override — в этой центральной читалке** («нет волта → env»), настраивается в
  корне.

**Прогрессивность конфига** (принцип): только `.env` → в корне про конфиг **ничего**
не пишешь (дефолт — env); появился второй источник → в корне привязываешь
конфиги/ключи к источнику (порядок + переопределения), библиотеки не меняются.
Точный синтаксис привязки — открытая развилка (варианты в цвете отдельной
страницей).

Теряем единый precedence-как-данные (переезжает в recipe — по-прежнему одно место).
Не теряем: провенанс-слепоту (бизнес называет ключ, recipe решает readers) и
выгрузку доки (реестр свойств содержит каждое объявленное, включая unbound → доки
**полнее**; условие lint-able: источник объявляет конфиг секцией, не читает ad-hoc).

Это пересматривает config-раздел `composition-and-lifecycle.md` в третий раз
(class-секции → merged-Vars → readers+family) и, по-видимому, финально: конфиг
перестаёт быть отдельной подсистемой.

### Финальный синтаксис и решения (конфиг) — зафиксировано 2026-07-08

```typescript
// A. Объявление (библиотека/модуль): группа = пачка настроек; источник не называется
export const RedisConfig = makeConfig('redis', z.object({
  url:      from('REDIS_URL'),               // точное имя
  poolSize: z.coerce.number().default(10),   // → REDIS_POOL_SIZE (из префикса)
}));

// B. Чтение — только модуль-владелец (configs: [RedisConfig])
@Injectable([RedisConfig])
class RedisClient { constructor(private cfg: Config<typeof RedisConfig>) {} }
// @Injectable([RedisConfig]) в чужом модуле → ошибка на build()

// C. Привязка источников в корне — плоский список, env неявный пол
await assemble({
  config: [
    [vault(), [RedisConfig, DbConfig]],   // по токену группы
    [vault(), ['*_GRPC_ADDRESS']],        // или по шаблону ключа
  ],
  features,
});
// только .env → assemble({ features })

// D. Источник — не провайдер, а объект; свои координаты из примордиального env
const file = (opts = {}) => ({
  async init() { this.data = parseYaml(await readFile(process.env[opts.pathKey ?? 'CONFIG_FILE'] ?? 'config.yaml')); },
  get: (k) => this.data[k],
  watch(onChange) { /* fsWatch → onChange() */ },
});
```

Решения (все — из разбора выше):

- **Объявление:** `makeConfig('prefix', zodSchema)`; префикс строит имя, `from('KEY')` —
  точное; источник не называется; группа = пачка настроек (подтверждено).
- **Приватность:** `configs: [X]` = владение; инжект только владельцем; чужой →
  **ошибка на `build()`** (структурная — рёбра графа + метка владельца, независима от
  значений, ловится в любом тесте/CI, как cycle-check). Токен *referenceable* в
  привязке, но не *injectable* чужим: право зависит от позиции (привязка vs deps).
- **Источники — не провайдеры**, а объекты `ConfigSource { get; init?; close?; watch? }`
  в одной приватной читалке (kernel). env — база. Координаты источника (`path`, `addr`) —
  из примордиального `process.env` в `init()` (единственный контакт с `process.env`);
  бизнес-ключи — через читалку. Цикла нет (env — floor).
- **Создание значения:** фреймворк генерирует фабрику конфига, инжектит в неё **читалку**
  (приватный kernel-токен), фабрика читает ключи и валидирует схемой. Пользователь env
  и читалку не видит.
- **Привязка в корне (прогрессивно):** `.env` → ничего; иначе плоский список
  `config: [[src, targets]]`, env неявный пол, `default` не пишем; цель — токен группы
  или шаблон ключа; порядок = приоритет.
- **Reloadable:** `makeConfig.reloadable`; read-latest (геттер, без подписки);
  `onChange(signal, cb)` на `Topic`+`AbortSignal` (живой хэндл вместо снапшота, ноль
  зависимостей); невалидный reload → keep-last + warn; opt-in. Реактивную библиотеку не
  тянем (read-latest покрывает основное; стандартная ставка на будущее — TC39 Signals).
- **Документация:** автоматически для собранных+выбранных модулей, тег фичи + флаг
  (core / под-флагом); из реестра свойств, без значений/сети.
- **Reloadable поверх non-watching источника:** секция помечена `reloadable`, но
  источник не умеет `watch` (обычный env) → **warn при старте, не падаем** (значение
  просто не будет обновляться; capability-mismatch, а не ошибка).
- **Форма «всё из источника»:** цель привязки — не только токен группы / шаблон
  `'*_KEY'`, но и `'*'` (весь источник): `config: [[vault(), '*']]`.
- **Ранняя проверка приватности (опционально):** помимо ошибки на `build()` —
  ESLint-правило «`@Injectable` с чужим `Config`» ловит нарушение ещё до сборки
  (вспомогательное, не замена build-check).

### Отвергнутые варианты синтаксиса привязки (чтобы не возвращаться)

Синтаксис *объявления* секции разобран в §11.1 (4 стиля, сузили до 1 и 3). Здесь —
синтаксис *привязки* источников в корне; рассмотрели 4, выбрали 3:

| # | Форма | Почему нет / да |
|---|---|---|
| 1 | просто порядок `config: [vault(), env()]` | проще некуда, но vault дёргается для **всех** ключей, не только секретов. Остался как **вырожденный случай** варианта 3 |
| 2 | источник знает свои ключи `vault({ only: [...] })` | vault ограничен секретами, но **шаблоны ключей уезжают в объявление источника** — источник начинает знать про чужие ключи (протечка ответственности) |
| 3 ✓ | привязка групп `config: { default: env(), bind: [[vault(), [DbConfig]]] }` | ровно «привязать конфиг к источнику»; позже **упрощён до плоского** `config: [[src, targets]]` — env неявный пол, обёртка `{default, bind}` убрана |
| 4 | fluent `config().base(env()).from(vault(), [...])` | читается как фраза, но это **ещё один стиль API** (лишняя поверхность) |

Прогрессивность встроена в синтаксис: `.env` → ничего → плоский список привязок.
Токен группы = «набор объявленных ею ключей», поэтому привязка по токену не хрупкая
(в отличие от строковых шаблонов). Пакет экспортит **декларацию** (какие ключи), но
не знание об источнике — «библиотека не знает, откуда конфиг» цело.

### Обзор реактивности для reloadable (почему свой нотификатор)

Для `onChange` рассмотрели, чем уведомлять:

- **нативный `EventTarget`** — есть везде, но многословный API;
- **TC39 Signals** (`signal-polyfill`) — будущий стандарт; **стратегическая ставка**
  на него как на стандартную траекторию (как с AsyncIterable для стримов);
- **мелкие сторы** (nanostores ~300 б, `@preact/signals-core`) — лёгкие, но это
  зависимость и своя парадигма ради малого;
- **RxJS** — **сознательно нет** (та же дисциплина границы, что в streaming-идеях).

Вывод v1: свой минимальный `onChange(signal, cb)` на `Topic` + `AbortSignal` — ноль
зависимостей, живой хэндл вместо снапшота; read-latest покрывает основное. Полноценную
реактивную библиотеку не тянем.

(глобально); `forTransports()` — нужные транспорты (bootstrap-проверка);
cross-cutting хуки (`configureMiddleware`, error-formatting/sending/transforming,
tracing, `contextEnrichers`). Философия (в комментарии): «инициализация не торчит
наружу из библиотеки, но иногда её надо расширить извне». Бизнес — в app-модулях,
инфра — в плагинах.

### Раскладка на nestling — три части ложатся по-разному

1. **Инфра-часть (~80%) растворяется в модулях.** Плагин = параметризованный
   инфра-модуль (`redis()` — функция → модуль, `RedisClient` синглтон в процессе).
   **«Глобальность» ≠ ambient-инжект:** провайдер в корне, но инжектнуть можно
   только импортнув токен (ES-видимость цела). Kernel-инфраструктура (§11.2).
   Конфиг плагина — секция, которую он везёт. `forTransports` → DI + fail-fast.
2. **Cross-cutting pipeline-часть НЕ ложится напрямую.** pipeline-v2 отверг уровни
   App/module — ambient middleware в nestling нет по дизайну. Взамен: плагин
   **экспортирует pipeline-слой-константу**, endpoint композирует явно;
   вездесущность — конвенция + опциональный startup policy-check («каждый pipeline
   содержит tracing») / per-transport дефолтный пайплайн (отложено в pipeline-v2).
   Принципиальное расхождение: «видимо скомпозировал + проверил» вместо «невидимо
   навесил на всех».

### С фичами (главный акцент)

Плагины **процесс-глобальны**; «какие плагины» падает из выбранного подмножества —
тот же паттерн, что транспорты/источники (4-й раз):

- **feature-scoped инфра** (Redis для кэш-фичи) — фича импортирует инфра-модуль →
  **едет с фичей** при split; co-located фичи делят один синглтон, split —
  отдельные клиенты per-process (бесплатно от контейнера). Это и делает фичу
  независимо-развёртываемой;
- **ambient cross-cutting** (логирование, трейсинг) — тонкий root-bag
  `assemble({ plugins: [...] })`, в каждом процессе.

Граница честности: общий *бэкенд* (один Redis-сервер / одни таблицы) у разнесённых
фич — дата-архитектурный концерн (distributed monolith smell), не механика
плагинов.

### Повторяющийся приём

`X: [...]` bag → провайдеры из дерева модулей — применён к эндпоинтам, транспортам,
источникам и теперь feature-scoped плагинам. Как root-bag остаётся только ambient
cross-cutting.
