## 1. Ядро принимает Standard Schema

На всех границах, где нужна схема, ядро принимает `StandardSchemaV1`
([standardschema.dev](https://standardschema.dev)). Это общий интерфейс
zod, valibot, arktype, Effect Schema и TypeBox: одно свойство `~standard`
с функцией `validate(value)`, которая возвращает `{ value }` или
`{ issues }`, и фантомные типы для вывода типов.

Валидация идёт через `~standard.validate`, типы выводятся через
`InferOutput`. Валидатор выбирает и устанавливает пользователь: zod,
`zod/mini`, valibot, arktype. Публичные типы ядра валидатор не называют.

Внутри фреймворка валидатор один — zod. Схемы, которые пишет сам
фреймворк (секции конфигурации пакетов, рекорды фактов, хелперы полей),
написаны на нём, а пакеты, которым нужна JSON Schema, берут конвертер zod
по умолчанию (§2). Для приложения это выбор реализации, а не требование:
приложение на другом валидаторе собирается и работает, а там, где нужен
документ, передаёт свой конвертер.

**Граница проходит по публичному API.** Ни один экспортируемый тип,
параметр или возвращаемое значение пакетов фреймворка не называет
валидатора; исключение ровно одно и названо именем пакета —
`@nestlingjs/schema.zod`. Зависимость пакета от zod приложению видна
только строкой в `node_modules`, а вендор в **типе** отнял бы у него выбор
собственного валидатора. Поэтому схема, которую пишет фреймворк и которая
уходит в публичный тип (рекорд факта), объявляется нейтральным типом
`StandardSchemaV1<unknown, T>`: значение остаётся zod-схемой и переводится
штатным конвертером, а тип вендора не называет. Проверка механическая:
`yarn verify` перечисляет экспорты барреля каждого публикуемого пакета и
ищет в их типах имя валидатора.

**Единая точка валидации.** Вся валидация в ядре проходит через одну
функцию `validateSync(schema, value, message)`: `parsePayload`,
`parseMetadata`, проверка входа endpoint'а рантаймом пайплайна,
поэлементная проверка элементов потока и проверка полей секций конфига.
Прямых вызовов `schema.parse(...)` и duck-typing вида `{ parse(data): T }`
в ядре нет, поэтому форма отказа на всех путях одна. Своей ветки проверки
у транспортов нет: транспорт собирает значение, рантайм его проверяет.

`SchemaValidationError` несёт `issues` в стандартном формате
`{ message, path? }[]`. Формат гарантирован спецификацией, а не вендором;
типы ошибок валидатора в публичный API не попадают. Путь нормализуется при
создании ошибки: сегмент-объект `{ key }` превращается в `key`, символ — в
строку, числовой индекс остаётся числом. `issues` уходят в тело ответа, и
их JSON-форма от вендора не зависит.

Если `validate` вернул Promise (асинхронные refinements), синхронный
пайплайн даёт ошибку, а не пропускает значение.

**Клиент валидирует ответ той же схемой.** `makeClient` проверяет тело
успешного ответа по форме `output` операции через `~standard.validate`.
Проверка включена по умолчанию и отключается явно: `validateOutput: false`.
Синхронность обязательна и здесь. Исход другой, чем на сервере: отказ
валидации не бросается, а становится `InternalError` с `issues` в `cause`,
потому что клиент не бросает исключений на сбоях операции
([operations.md](./operations.md)). Валидатор и здесь приносит потребитель:
`@nestlingjs/operations` знает о схеме только её `~standard`.

**Ошибка конфигурации и ошибка входа — разные классы.** Асинхронная схема
даёт `AsyncSchemaNotSupportedError`; объект, не реализующий спецификацию
(обычно валидатор старее zod 3.24 или valibot 1.0), —
`NotAStandardSchemaError`. Оба класса не наследуют
`SchemaValidationError`: это ошибки автора приложения, а не пользователя
запроса, и транспорт отвечает на них 500, а не 400.

**Интроспекции нет.** Спецификация покрывает только валидацию и вывод
типов; в рантайме схема непрозрачна. Поэтому всё, что требует знания
структуры схемы, объявляется явно, без заглядывания внутрь вендорских
объектов: размещение поля — пометкой рядом со схемой
(`bind: { expand: query() }`, [endpoints.md](./endpoints.md)), секция
конфига — записью полей ([config.md](./config.md)), JSON Schema — через
конвертеры вендоров (§2).

Непрозрачность — свойство рантайма; на уровне типов ключи схемы известны
(`InferInput<I>`). Этим пользуются везде, где можно: ключи `bind`
типизированы полями схемы, и опечатку находит компилятор, хотя рантайм тех
же ключей не знает. Проверок, которым нужен перечень ключей в рантайме, в
ядре нет.

## 2. Конвертеры схем

Валидация и описание схемы наружу разделены. Рантайм ядра знает только
`~standard.validate`; JSON Schema нужна тем, кто публикует описание API.

Конвертер — публичный интерфейс схемного слоя:
`SchemaDocConverter { vendor; toJsonSchema(schema, options?) }`.
Диспетчеризация идёт по `~standard.vendor` схемы. Ядро по вендору не
ветвится и схемы не интроспектирует. Потребитель JSON Schema
держит конвертер zod по умолчанию и принимает список `converters`, который
добавляет конвертеры других вендоров или заменяет конвертер zod.
Глобального реестра нет. Два конвертера с одним `vendor` в списке —
ошибка в точке передачи.

`options` содержит одну подсказку: `io: 'input' | 'output'`. Схема с
преобразованием описывает две формы: что приходит по сети и что получает
хендлер. Тело запроса описывается первой формой, тело ответа — второй.
Подсказка необязательна с обеих сторон: конвертер может её игнорировать, а
потребитель, которому направление безразлично (снапшот сравнивает форму с
самой собой), может её не передавать.

**Аннотация `jsonSchema(schema, json)`.** Это способ задать JSON Schema
вручную для одного листа. Аннотация возвращает значение, наследующее
`~standard` исходной схемы: оно валидирует точно так же и подходит в
любую схемную позицию — `input`, `output`, лист потоковой формы, `fields`
формы `multipart`, `details` определения отказа. Диспетчер читает
аннотацию раньше конвертера, поэтому аннотированный лист конвертируется
независимо от списка конвертеров. Тем же механизмом объявлены схемы самого
ядра: `details` kernel-отказов написаны вручную, и вендора `nestling` ни
один конвертер не знает. Переданная схема не мутируется; глобального
реестра аннотаций нет.

Диспетчер живёт в `@nestlingjs/operations`, рядом с аннотацией
`jsonSchema`, которую читает первым источником. Пакет запроса ему не
подходит: снимок конфига строится до существования запроса, а слой
конфига в слой пайплайна не смотрит. `@nestlingjs/app` реэкспортирует его
имена, поэтому потребитель импортирует их оттуда же, откуда и раньше.

**Три потребителя.** Диспетчер возвращает «конвертера нет» отдельным
исходом, а что с этим делать, решает потребитель:

| Потребитель | Нет конвертера для вендора |
|---|---|
| генерация документации (§2.1) | ошибка на старте: недокументируемых endpoint'ов не бывает |
| снапшот операций ([operations.md](./operations.md) §1) | лист непрозрачен, вердикт `unknown` |
| `describeConfig({ converters })` ([config.md §8](./config.md)) | исход `unconvertible` в описании ключа: JSON Schema нет, и это отличается от «описания у поля нет» |

Конвертер — единственное место, которое знает устройство конкретного
валидатора. Он пишется в десять строк поверх штатного конвертера
валидатора (`z.toJSONSchema()` и аналоги).

Всё, что фреймворк делает с zod, живёт в одном пакете
`@nestlingjs/schema.zod`: конвертер `zodConverter()`, разрешение списка
конвертеров `withZodDefault()`, хелперы полей секций `int()` и `flag()` —
открытые билдеры, к которым вызывающий дописывает границы и умолчание
(`int().min(1).default(500)`), — и модели `makeModel`, `fromScratch` и
`fromType`, сверяющие схему с уже существующим TypeScript-типом.

Умолчание подставляет сам потребитель — `withZodDefault(converters)` в той
точке, где он читает список вызывающего. Функция дописывает `zodConverter()`
к списку и пропускает этот шаг, если конвертер вендора `zod` в списке уже
есть. Отсюда обе половины обещания: список **добавляет** конвертер другого
вендора, не теряя zod, и **заменяет** конвертер zod своим. Пустой список и
отсутствие списка дают один результат.

### 2.1. OpenAPI: модуль по выбору

```typescript
openapi({ info: { title: 'My API', version: '1.0.0' }, pipeline: observability })
```

Документ нужен в двух режимах — отдаваться endpoint'ом и лежать файлом в
артефактах сборки. Обслуживает оба одно значение, поэтому поверхностей у
пакета две. Третья строка таблицы принадлежит `@nestlingjs/app`: это вход,
которым режим сборки получает состав приложения.

| Поверхность | Что делает |
|---|---|
| `openapi(options)` | плагин-издатель: строит документ на фазе 1 BUILD и отдаёт его endpoint'ом (`GET /openapi.json`). Его же метод `document(discovery)` строит документ от результата `app.discover(args)` — без контейнера, транспортов и поднятого приложения |
| `OpenApiDocument$` | DI-токен готового документа; endpoint — способ его отдать, а не место, где он появляется |
| `app.discover(args?)` | вход генератора: фаза 0 декларации отдаёт состав значением, без графа и источников. Документ для артефактов собирается тем же аргументом сборки, которым поднимается процесс ([composition.md](./composition.md)) |

- `@nestlingjs/openapi` принимает тот же `SchemaDocConverter`, что и
  снапшот операций, и своего типа не заводит. Конвертер zod он берёт из
  `@nestlingjs/schema.zod` по умолчанию; в публичных типах zod не
  упоминается.
- Конвертер другого валидатора — отдельный пакет по образцу `schema.zod`;
  мажорные версии конвертера следуют за мажорными версиями валидатора.
- Документ строится фабрикой провайдера на фазе BUILD. Любая
  диагностика роняет сборку до INIT и до открытия сокета. Ленивого
  построения нет. Проверка полная: нарушения всех endpoint'ов собираются
  в одно сообщение.
- `openapi(...)` возвращает обычный плагин-значение с параметрами; новых
  примитивов роль плагина не приносит. Опции `path`, `pipeline` и
  `detached` позволяют применить к endpoint'у документа те же политики
  корня, что и к остальным HTTP-endpoint'ам.
- Метод и фабрика провайдера зовут одну внутреннюю функцию: документ из
  артефактов сборки и документ по `GET /openapi.json` совпадают по
  построению. Метод работает и тогда, когда плагин не попал в состав:
  значение живёт в декларации, а ветка переключателя (`Docs.when(…)`)
  решает только судьбу endpoint'а. Документ для контура с выключенной
  документацией строится тем же вызовом.
- Состав приложения модуль читает из `Discovery$`
  ([composition.md](./composition.md)): так он видит выбранную топологию
  без дублирования `select`. Скрипт CI берёт тот же состав из
  `app.discover(args)`, а опции документа — у плагина из декларации:
  `info` записан один раз.
- Кроме JSON Schema документ собирается из деклараций: слот `doc:` (§2.2);
  `errors:` становятся `responses`, `InternalError` — ответом по умолчанию
  ([errors.md](./errors.md)); формы io определяют media types
  ([endpoints.md](./endpoints.md)); bind-карта разделяет `parameter` и
  `requestBody`; статус переводится в HTTP-код той же таблицей, что у
  транспорта.
- Параметр описывается разобранной формой поля, если она скалярная.
  Схема `input` конвертируется дважды: прогон `io: 'input'` даёт тело и
  обязательность параметров, прогон `io: 'output'` — схемы параметров.
  Свойство берётся из второй формы, когда в первой оно несёт
  `type: 'string'`, а во второй — `boolean`, `number` или `integer`;
  переносится оно целиком, вместе с `description`, `default` и
  ограничениями. Так `dryRun: z.stringbool()` в query попадает в документ
  булевым параметром, оставаясь строкой в схеме тела. Второй прогон идёт
  только у endpoint'ов, которые выносят хотя бы одно поле в путь или в
  query. Отказ второго прогона диагностики не даёт: схема с `transform` в
  направлении `output` непредставима, и параметры такого endpoint'а
  описываются входной формой.
- Две диагностики живут в генераторе: path-параметр, которому нет свойства
  в схеме, и пометка `bind` на несуществующем поле. Обеим нужна структура
  схемы, которую даёт только конвертер.

AsyncAPI для `command`, `event` и потоковых форм строится тем же механизмом
и читает тот же слот `doc`.

### 2.2. Слот `doc:` — то, чего в схемах нет

```typescript
interface DeclarationDoc {
  summary?: string;
  description?: string;
  tags?: readonly string[];
  deprecated?: boolean;
  status?: SuccessStatus;   // успешный ответ; дефолт ok, без output — no_content
  hidden?: string;          // не документировать — только с причиной
}
```

Слот живёт на уровне ядра, в `EndpointOptions` и `OperationSpec`, и не
зависит от транспорта. Ядро его переносит и не интерпретирует, как
`binding`. Слот не зависит и от формата документа: тот же слот читает
генерация AsyncAPI, поэтому полей `operationId`, `externalDocs` и
`servers` в нём нет.

- `operationId` выводится: имя операции, если декларация служит
  операции, иначе детерминированный слаг от метода и пути
  (`get_api_users_id`). Объявить его вручную нельзя: неизвестное поле
  секции отвергается при создании декларации.
- `tags` из имени модуля не выводятся. Нет `doc.tags` — нет тегов.
- `hidden` принимает только строку с причиной, как `detached`. Скрытый
  endpoint выпадает и из документа, и из проверки схем. Список скрытых
  endpoint'ов модуль печатает на старте; в документ он не попадает.
- В реализации операции `doc` принадлежит операции наравне с `input`,
  `output` и `errors`: две реализации одной операции описывают его
  одинаково.

Секция проверяется при создании значения. Не-строка, `tags` не массивом
строк, статус вне перечня успешных, `hidden: true` и неизвестное поле дают
ошибку при объявлении, а не при сборке приложения.
