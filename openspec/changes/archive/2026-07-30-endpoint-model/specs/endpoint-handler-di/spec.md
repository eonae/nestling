# endpoint-handler-di

## ADDED Requirements

### Requirement: Хендлер принимается в трёх формах

Конструктор декларации SHALL принимать `handle` в трёх формах:

1. **функция** `(input, meta) => …` — без зависимостей;
2. **каррированная фабрика** — поле `deps: […]` явным массивом токенов плюс
   `(…deps) => (input, meta) => …`;
3. **класс** с методом `handle`, резолвимый контейнером.

Формы SHALL различаться по типу переданного `handle` без чтения `deps`.
Класс-форма SHALL быть формой подключения DI, а не вторым стилем
деклараций: сама декларация во всех трёх случаях SHALL оставаться одним и
тем же значением.

#### Scenario: Функция без зависимостей

- **WHEN** объявлено `httpEndpoint({ …, handle: async (input, meta) => Ok.of(…) })`
- **THEN** декларация исполнима сразу, без гашения зависимостей

#### Scenario: Каррированная фабрика

- **WHEN** объявлено `httpEndpoint({ …, deps: [UserService, ILogger], handle: (users, logger) => async (input, meta) => … })`
- **THEN** типы `users` и `logger` выведены из токенов `deps`, а декларация
  несёт неразрешённые зависимости

#### Scenario: Класс-хендлер

- **WHEN** объявлено `httpEndpoint({ …, handle: CreateUserHandler })`, где
  `CreateUserHandler` — класс под `@Injectable([UserService])` с методом
  `handle`
- **THEN** код компилируется без `implements`, сигнатура `handle` сверяется
  со схемами `input`/`output` в точке декларации, а декларация несёт
  неразрешённую зависимость

#### Scenario: Несовпадение сигнатуры хендлера со схемами

- **WHEN** `handle` принимает тип, несовместимый с `InferInput<input>`, или
  возвращает тип, несовместимый с `InferOutput<output>`
- **THEN** это ошибка компиляции в точке декларации

### Requirement: Внешний вызов каррированной фабрики происходит один раз на сборке

Каррированная фабрика SHALL вызываться ровно один раз при гашении
зависимостей — не на каждый запрос. Замыкание, полученное этим вызовом,
SHALL играть роль инстанса хендлера.

#### Scenario: Фабрика вызывается один раз на много запросов

- **WHEN** декларация с каррированным `handle` погашена и обслужила
  несколько запросов
- **THEN** внешняя функция вызвана один раз, а внутренняя — по разу на
  запрос

### Requirement: Тип декларации несёт неразрешённые зависимости

`EndpointDefinition` SHALL иметь тип-параметр неразрешённых зависимостей
(дефолт `never`), симметричный `TNeeds` у `Pipeline`. Форма `handle`-функции
без `deps` SHALL давать `never`; каррированная форма SHALL накапливать
токены из `deps`; класс-форма SHALL накапливать конструктор класса.
Параметр SHALL накапливать также **классы-юниты пайплайна** декларации:
после слияния метаданных и декларации в одно значение это единственное
место, где различимы «пайплайн, требующий `bind`» и «исполнимый пайплайн»,
а без различия standalone-приём терял бы compile-time-гарантию.

#### Scenario: Классы-юниты пайплайна попадают в параметр

- **WHEN** объявлена декларация с `pipeline: makePipeline().pre(WithTracing)`,
  где `WithTracing` — класс-юнит
- **THEN** параметр неразрешённых зависимостей содержит `WithTracing`, и
  такая декларация в `server.route(...)` не проходит по типам

#### Scenario: Deps-free декларация

- **WHEN** объявлена декларация с `handle`-функцией и без `deps`
- **THEN** параметр неразрешённых зависимостей — `never`

#### Scenario: Декларация с зависимостями

- **WHEN** объявлена декларация с `deps: [UserService]`
- **THEN** параметр неразрешённых зависимостей содержит `UserService`

### Requirement: Транспорты принимают только deps-free декларацию

`ITransport.endpoint()` и `HttpTransport.route()` SHALL принимать только
декларацию с параметром неразрешённых зависимостей `never` — так же, как
уже принимают только исполнимый `Pipeline<_, _, never>`. Передача
декларации с зависимостями напрямую транспорту SHALL быть ошибкой
компиляции.

#### Scenario: Декларация с deps не проходит в standalone-транспорт

- **WHEN** декларация с `deps: [UserService]` передана в
  `server.route(...)` без гашения
- **THEN** это ошибка компиляции

#### Scenario: Deps-free декларация проходит

- **WHEN** декларация без зависимостей передана в `server.route(...)`
- **THEN** код компилируется, маршрут регистрируется и обслуживается

### Requirement: Гашение зависимостей — метод `resolve`, возвращающий новое значение

Декларация SHALL иметь метод `resolve`, возвращающий **новую** декларацию с
параметром неразрешённых зависимостей `never`; исходная декларация SHALL
оставаться неизменной. `resolve` SHALL принимать резолвер-функцию
`(token) => unknown` либо позиционный массив готовых инстансов,
соответствующих `deps`. Класс-форма `handle` и пайплайн с классами-юнитами
SHALL требовать резолвер-формы: позиционному массиву нечем их
инстанцировать, и попытка SHALL давать ошибку, называющую класс и
предлагающую резолвер-форму.

#### Scenario: Гашение резолвером

- **WHEN** у декларации с `deps: [UserService]` вызвано
  `resolve((token) => container.getOrThrow(token))`
- **THEN** возвращена deps-free декларация, принимаемая транспортом

#### Scenario: Гашение позиционным массивом

- **WHEN** у декларации с `deps: [UserService, ILogger]` вызвано
  `resolve([userService, logger])`
- **THEN** возвращена deps-free декларация, а зависимости переданы в
  каррированную фабрику в порядке объявления `deps`

#### Scenario: Исходная декларация не мутируется

- **WHEN** одна и та же декларация погашена дважды разными наборами
  зависимостей
- **THEN** получены две независимые декларации, а исходная по-прежнему
  несёт неразрешённые зависимости

#### Scenario: Резолвер не смог отдать зависимость

- **WHEN** резолвер не возвращает значение для токена из `deps`
- **THEN** `resolve` бросает ошибку, называющую токен

### Requirement: `App` гасит зависимости деклараций контейнером на старте

`App` SHALL на старте для каждой обнаруженной декларации гасить зависимости
контейнером и передавать транспорту deps-free значение. Зависимость (токен
из `deps` или класс-хендлер), недоступная в контейнере, SHALL приводить к
ошибке старта, называющей паттерн ручки, модуль-объявитель, недостающую
зависимость и способ починки, — до начала приёма запросов.

Резолв классов-юнитов пайплайна SHALL продолжать работать прежним
механизмом (`pipeline.bind`), вызываемым из `resolve` тем же резолвером:
для `App` это один шаг, а не два.

#### Scenario: Зависимость резолвится

- **WHEN** декларация с `deps: [UserService]` объявлена в модуле, где
  `UserService` зарегистрирован провайдером
- **THEN** приложение поднимается, ручка обслуживается, а хендлер получает
  инстанс из контейнера

#### Scenario: Класс-хендлер не зарегистрирован провайдером

- **WHEN** декларация объявлена с `handle: CreateUserHandler`, но класс не
  перечислен в `providers` ни одного модуля
- **THEN** `app.run()` завершается ошибкой, называющей класс, паттерн ручки
  и модуль-объявитель

#### Scenario: Токен из `deps` не зарегистрирован

- **WHEN** декларация объявлена с `deps: [ILogger]`, а провайдер для
  `ILogger` отсутствует
- **THEN** `app.run()` завершается ошибкой, называющей токен, паттерн ручки
  и модуль-объявитель

#### Scenario: Хендлер тестируется без фреймворка

- **WHEN** каррированная фабрика вызвана с фейками напрямую либо
  класс-хендлер создан через `new` с фейками
- **THEN** тест не требует ни контейнера, ни транспорта, ни импортов из
  `@nestling/app`
