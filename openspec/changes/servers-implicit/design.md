## Context

Сокетом владеет отдельный узел графа — сервер. Объявляет его
`httpServer({ name? })` из `@nestlingjs/transport.http`, а в сборку он
попадает двумя путями сразу: элементом списка `transports:` и полем
`server` объявления транспорта. Оба пути ведёт `collectServers`
(`packages/nestling.app/src/root/plan.ts:366`) с дедупликацией: один и тот
же объявленный сервер, названный дважды, даёт одну регистрацию.

Второй путь уже работает. `http()` без `server` объявляет собственный
сервер с именем транспорта, кладёт его в поле `server`, и сборка
регистрирует узел по ссылке — `transports: [http()]` поднимает сокет, не
упоминая сервер. Первый путь остался от записи
[ideas.md [2026-09-06]](../../../docs/decisions/ideas.md) «HTTP-сервер как
ресурс» и нужен ровно одному случаю: два транспорта на одном сокете.
Именно он и выглядит непоследовательно —
`transports: [api, http({ server: api }), mcp({ server: api })]` называет
`api` дважды, а список перестаёт быть списком транспортов.

Design-доки уже описывают целевое состояние:
[transports.md §4.2](../../../docs/design/transports.md) пишет
`server({ name? })` и «в `transports:` корня он не перечисляется».
Расходится с ними код, спеки `http-server-resource` и `transport-providers`,
README двух пакетов и два примера.

## Goals / Non-Goals

**Goals:**

- `server()` вместо `httpServer()`, `serverKeys()` вместо `httpServerKeys()`.
- `transports:` принимает только объявления транспортов — это проверяет
  компилятор, а при вызове из JavaScript отказ на фазе ASSEMBLE.
- Сервер попадает в сборку по ссылке `server` транспорта; сервер, на
  который не ссылается ни один транспорт, не создаётся.
- Спеки, README, гайд, рецепт и примеры называют те же имена, что код.

**Non-Goals:**

- Класс `HttpServer`, семейство DI-токенов `HttpServer$`, типы
  `HttpServerOptions` и `HttpServerSpec`. Имена остаются.
- Ключи секции: `HTTP_PORT`, `HTTP_HOST`, `HTTP_ADMIN_PORT`,
  `HTTP_ADMIN_HOST`.
- Опции адреса у фабрик. Порт и хост приходят только из конфига.
- Переименование `assemble` → `build` (change 86) и суффиксы имён
  переменных (change 87).

## Decisions

### 1. Фабрика называется `server()`, дескриптор ключей — `serverKeys()`

Оба имени пишет прикладной код, и пишет рядом: `const api = server()` в
декларации приложения, `config: [[dotenv('.env'), serverKeys()]]` в
привязках. Разнобой в паре был бы заметнее, чем потеря префикса: какого
протокола сервер, видно по строке импорта из `@nestlingjs/transport.http`,
а ключи `HTTP_*` называет сама секция.

Внутри фабрик транспортов имя импортируется под алиасом. Опция транспорта
называется `server`, и умолчание пишется деструктуризацией
(`const { server = httpServer({ name }) } = options`) — после переименования
фабрика и переменная совпали бы, а обращение к переменной до инициализации
падает. Поэтому `http()` и `mcp()` импортируют `server as declareServer`.

Внутренние имена префикс сохраняют. `Server` без префикса столкнулось бы с
`Server` из `node:http` в том же файле, а `ServerDeclaration` и
`ServerToken` уже заняты ядром. Отвергнутые варианты имени фабрики —
`http()` для сервера, `socket()`, сохранение `httpServer()` — разобраны в
записи [ideas.md [2026-09-13]](../../../docs/decisions/ideas.md) «Сервер:
`server()`, не перечисляется в `transports:`».

### 2. `TransportEntry` и `isTransport` удаляются

Поле `transports:` типизируется `readonly Branchable<TransportDeclaration>[]`.
Union `TransportEntry = TransportDeclaration | ServerDeclaration` исчезает
вместе с предикатом `isTransport`, который его разделял: разделять больше
нечего. Дискриминатор `kind` у обоих объявлений остаётся — он нужен
рантайм-проверке (решение 4) и читается в отладке.

`ServerDeclaration` и `makeServerDeclaration` остаются экспортами
`@nestlingjs/app`: транспортные пакеты объявляют серверы и кладут их в поле
`server`.

Альтернатива — оставить union и запретить сервер проверкой типа в
`makeApp` — отвергнута: тип поля и есть проверка, а второй способ сказать
то же самое стоит лишней сущности.

### 3. `collectServers` обходит только поле `server`

Функция принимает транспорты и собирает серверы из их полей `server`.
Дедупликация по ссылке остаётся: `http({ server: api })` и
`mcp({ server: api })` дают один узел. Два **разных** объявления с одним
именем остаются ошибкой ASSEMBLE — имя задаёт префикс секции, и оба
сервера читали бы один порт. Текст ошибки называет замену:
`const api = server({ name: 'api' })`.

Случай «два транспорта без `server`» этим и покрыт. `transports: [http(), mcp()]`
объявляет два разных сервера с именем `default`, и сборка отказывает,
называя имя — вместо того чтобы поднять два сокета или молча выбрать один.

Порядок серверов — порядок первого упоминания транспортом. Наблюдаемого
различия с прежним порядком нет: `listen` идёт последним шагом START,
после `serve` всех транспортов.

### 4. Сервер в `transports:` — отказ на ASSEMBLE

Компилятор отвергает такой список, но декларацию пишут и из JavaScript, а
принцип guarantee over convention требует отказа и там. `normalizeSpec`
проверяет элементы до `collectServers` и бросает на `kind === 'server'`.
Сообщение называет замену: передать объявление в опцию `server` транспорта.

Проверка идёт по кандидатам всех веток — там же, где уже проверяются имена
серверов и роль интеркома. Опечатка ловится на объявлении, а не в той
сборке, куда попала ветка.

### 5. Сервер без транспорта не создаётся

Следствие решения 3, а не отдельная проверка: узел берётся из ссылки,
ссылки нет — узла нет. Сокет без единого обработчика отвечал бы `404` на
всё, поэтому терять тут нечего.

## Risks / Trade-offs

- **Имя `server` общее и сталкивается с локальными переменными.** В спеках
  пакетов `server` — частое имя для экземпляра `HttpServer`. → Имя
  переменной в таких местах уточняется (`instance`), импорт остаётся
  прямым.
- **`serverKeys()` не называет протокол.** Читатель привязки конфига не
  видит, ключи какого сервера привязаны. → Ключи возвращаются вместе с
  дескриптором и видны в отказе валидации; импорт из
  `@nestlingjs/transport.http` стоит в том же файле.
- **Порядок узлов серверов в контейнере меняется** там, где сервер был
  первым элементом `transports:`. → Порядок `listen` наблюдаем только
  относительно `serve`, а он сохраняется; спека
  `openspec/specs/http-server-resource` фиксирует именно это отношение.

## Migration Plan

Публичных потребителей нет, поэтому миграция — один проход по репозиторию
внутри change'а: пакеты, спеки пакетов, примеры, документация. Переходных
имён не остаётся: `httpServer` и `httpServerKeys` исчезают из экспортов.
