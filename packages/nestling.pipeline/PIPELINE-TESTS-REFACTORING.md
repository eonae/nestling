# Рефакторинг типовых тестов Pipeline

## Цель
Улучшить покрытие типовых тестов пайплайна и консолидировать тесты в одном месте.

## Задачи

### 1. Консолидировать типовые тесты (`pipeline.types.spec.ts`)

Объединить тесты из `pipeline.negative.types.spec.ts` в основной файл `pipeline.types.spec.ts` и организовать по категориям.

#### 1.1. Базовая типовая совместимость
- Правильная последовательность middleware компилируется
- Типы корректно выводятся на каждом шаге
- Pipeline тип корректен

#### 1.2. Накопление input через цепочку
- Input поля добавляются на каждом шаге
- Input поля сохраняются при добавлении новых
- Порядок полей соответствует порядку middleware
- Сложные типы в meta (объекты, массивы, generic) работают корректно

#### 1.3. Защита от переопределения полей (НОВОЕ)
- Middleware не может добавить поле, которое уже существует в meta
- TypeScript должен выдавать ошибку компиляции при попытке переопределения
- Проверить для identity, requestId и других распространённых полей
- Проверить для custom полей через withMeta

#### 1.4. Проверка зависимостей middleware (НОВОЕ)
- Middleware, требующая поле identity, не может быть использована до withIdentity
- Middleware, требующая несколько полей, должна ждать их все
- TypeScript должен выдавать ошибку, если зависимости не удовлетворены
- Проверить для withPermissions (требует identity)
- Проверить для custom middleware с зависимостями

#### 1.5. Порядок и совместимость middleware
- validate() должен идти после всех raw-зависимых middleware
- withTiming работает в любом месте цепочки
- withIdentity должен быть до validate
- withRequestLogging должен быть до validate
- После validate нельзя использовать middleware, требующие raw.*

#### 1.6. Иммутабельность pipeline
- Базовый pipeline не изменяется при создании расширений
- Разные ветки от одного базового pipeline имеют разные типы
- Meta не "перетекает" между независимыми ветками

#### 1.7. Generic типы и type inference
- Разные типы User корректно выводятся
- Сложные generic типы в meta работают
- InferPipelineMeta корректно извлекает итоговый тип meta
- HasValidation корректно определяет наличие validate

#### 1.8. Edge cases
- Пустой pipeline имеет пустой meta и HasValidation = false
- Pipeline только с validate имеет HasValidation = true
- Множественные withMeta с одинаковыми именами (должна быть ошибка)
- Custom middleware с правильными типами работает
- Custom middleware с неправильными типами не компилируется

#### 1.9. Реалистичные сценарии
- Полная цепочка для REST API endpoint
- Переиспользование базовых pipelines
- Композиция pipelines для разных ролей
- Pipelines с условной логикой (через meta)

### 2. Улучшения типовой системы (опционально)

В процессе написания тестов могут выявиться необходимые улучшения:

#### 2.1. Защита от дублирования полей
- Добавить проверку на уровне типов, что новое поле не пересекается с существующими
- Использовать conditional types для валидации

#### 2.2. Улучшение сообщений об ошибках
- Более понятные типовые ошибки при неправильном порядке middleware
- Подсказки IDE о том, какие зависимости не хватает

#### 2.3. Utility types для проверок
- `RequiresMeta<M>` - помечает, какие поля требует middleware
- `ProvidesMeta<M>` - помечает, какие поля добавляет middleware
- `CheckDependencies<Required, Available>` - проверяет зависимости

## Приоритеты

1. **Высокий**: Консолидация существующих тестов (п. 1.1-1.2, 1.5-1.7)
2. **Высокий**: Новые проверки (п. 1.3-1.4, 1.8)
3. **Средний**: Edge cases и реалистичные сценарии в тестах (п. 1.9)
4. **Низкий**: Улучшения типовой системы (п. 2) - только если необходимо

## Что НЕ делать

- Не добавлять runtime тесты (jest) - только типовые тесты
- Не добавлять примеры кода в тесты - только проверки типов
- Не менять существующий API пайплайнов
- Не менять обратную совместимость без явного разрешения

## Дополнительные проверки

### Проверка на уровне типов
- Что нельзя дважды вызвать validate()
- Что нельзя использовать один и тот же withIdentity дважды
- Что middleware возвращает ResponseContext (не raw response)
- Что async/sync middleware оба работают

### Проверка порядка выполнения
- Что meta доступна в правильном порядке
- Что middleware имеют доступ к результатам предыдущих
- Что типы input/output согласованы между middleware

### Проверка композиции
- Что можно создавать factory функции для pipeline
- Что можно параметризовать pipeline через generics
- Что можно условно добавлять middleware
