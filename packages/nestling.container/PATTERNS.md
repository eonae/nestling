# DIP, DI, IoC и контейнер

Короткая справка по четырём терминам, которые встречаются в README пакета.
Цель — договориться, что каждое слово значит в Nestling, а не спорить о
строгости формулировок.

## DIP: принцип инверсии зависимостей

Буква D в SOLID. Сервису `PostsService` нужен репозиторий постов, но знать
конкретный класс `PostsRepository` ему не обязательно. Достаточно знать
интерфейс `IPostsRepository`: какие методы у репозитория есть. Какой класс
его реализует и где хранит посты, сервису не важно. Сервис зависит от
абстракции, а не от реализации.

В небольших приложениях строго следовать принципу не обязательно, но сама
идея полезна.

В JavaScript интерфейсов нет: TypeScript стирает их при компиляции.
Поэтому в рантайме интерфейс приходится представлять значением. В NestJS
это выглядит так:

```typescript
@Inject(SOME_STRING_OR_SYMBOL) readonly service: ISomeInterface
```

`SOME_STRING_OR_SYMBOL` здесь — токен. В Nestling токен создаётся
функцией `makeToken<ISomeInterface>('SomeInterface')`.

## DI: внедрение зависимостей

К DIP не относится, несмотря на похожую аббревиатуру.

Если `PostsService` создаёт репозиторий сам, вызывая `new PostsRepository()`
в конструкторе, заменить реализацию нельзя: например, подставить заглушку
в тестах, чтобы не ходить в базу. DI предлагает создавать репозиторий
снаружи и передавать в конструктор:

```typescript
const repo = new PostsRepository();
const service = new PostsService(repo);
```

Вместе с DIP конструктор принимает интерфейс, а не класс:

```typescript
constructor(private readonly repo: IPostsRepository) {}
```

Теперь реализацию легко подменить. В TypeScript со структурной типизацией
подмена возможна и без интерфейса, но интерфейс делает намерение явным.

## IoC: инверсия управления

DI требует где-то писать все `new` и собирать объекты друг из друга.
Инверсия управления — идея делать это декларативно: описать, что нужно, и
поручить создание фреймворку. Чтобы идея работала, нужен контейнер.

## IoC-контейнер (DI-контейнер)

Реализация инверсии управления для задачи DI: модуль, в котором
регистрируют все зависимости приложения и которому поручают их создание.

Известные реализации в JS и TS: InversifyJS, TypeDI, контейнер NestJS и DI
в Angular, на идеях которого контейнер NestJS построен. `@nestling/container`
— ещё одна реализация; чем она отличается, описано в README пакета.
