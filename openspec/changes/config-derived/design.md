## Context

Секция конфига — рекорд полей, у каждого поля своя схема. Читалка достаёт
значение ключа из снимка фазы 0, схема его проверяет, проекция замораживается.
Ни одного места, где значение поля получалось бы из других полей, в этой
цепочке нет.

Три запроса ревью [d/12](../../../docs/history/discussions/12-lifecycle-and-composition-review.md)
(пункты 7–9) упираются в это устройство:

- адрес базы собирается из хоста, порта, пользователя и пароля — сегодня для
  этого пишут класс-прокси поверх секции;
- один `.env` обслуживает несколько сервисов, каждый читает свои значения под
  своим префиксом — источника с префиксом нет;
- описания полей написаны `.describe()` внутри схемы, а снимок реестра схемы не
  раскрывает: `describeConfig()` отдаёт имена ключей и флаги, но не описания.

Ограничения, в которых работает решение:

- **Схема непрозрачна в рантайме.** Standard Schema покрывает валидацию и вывод
  типов; заглянуть внутрь можно только конвертером вендора
  ([schemas.md §2](../../../docs/design/schemas.md)).
- **Сборка синхронна.** Секции считаются из снимка фазы 0 на ASSEMBLE, без
  ввода-вывода.
- **Ключи статические.** `.keys` и глобы известны до запуска: на них держится
  привязка источников и генерация документации.
- **Реестр не хранит значений.** Снимок пригоден в артефактное время, когда
  графа не существует.

## Goals / Non-Goals

**Goals:**

- Вычисляемое поле объявляется внутри секции, без класса-прокси и без второго
  провайдера.
- Опечатка в имени зависимости и неверный тип её значения — ошибки компиляции.
- Один `.env` обслуживает несколько сервисов; секции остаются относительными.
- Снимок реестра несёт описания, умолчания и перечисления полей, когда
  передан конвертер, и честно говорит, когда конвертера нет.

**Non-Goals:**

- Генератор таблицы переменных: фреймворк отдаёт снимок, документацию пишет
  человек.
- Зависимости между секциями, цепочки вычисляемых полей, ленивое вычисление.
- Префикс приложения в `makeApp` или в объявлении секции.

## Decisions

### 1. Зависимости объявляются отдельным аргументом, а не листом рекорда

`makeConfig(prefix, record, derive)` принимает третий аргумент — функцию,
которая получает конструктор `derived` и возвращает рекорд вычисляемых полей:

```typescript
export const PgConfig = makeConfig('pg', {
  host:     z.string().default('localhost'),
  port:     z.coerce.number().int().default(5432),
  user:     z.string(),
  password: secret(z.string()),
}, (derived) => ({
  url: derived(['host', 'port', 'user', 'password'],
    (host, port, user, password) =>
      `postgresql://${user}:${password}@${host}:${port}/app`),
}));
```

Конструктор типизирован рекордом секции: `deps` — кортеж имён из
`keyof record`, а типы аргументов `fn` выводятся из схем этих полей.

Три правила из журнала держатся типами:

| Правило | Как держится |
| --- | --- |
| зависимость — поле этой секции | `deps` ограничен `keyof record` |
| тип значения зависимости | параметры `fn` выведены из схем |
| зависеть от другого `derived` нельзя | вычисляемых полей в `record` нет |

**Альтернатива — лист того же рекорда** (форма, записанная в
[config.md §1](../../../docs/design/config.md) до этого изменения):
`url: derived([...], fn)` рядом со схемами. Проверено компилятором на TS 5.7
strict: рекорд выводится тем же выражением, в котором стоит `derived`, поэтому
имена зависимостей остаются строками, а параметры `fn` — `any`. Файл с
опечаткой в имени, с обращением к несуществующему методу значения и с ложной
аннотацией `(port: string)` там, где поле `number`, компилируется без единой
ошибки. Все три дефекта пришлось бы ловить рантайм-проверкой в момент
объявления. Форма с отдельным аргументом ловит их компилятором, включая
подсказку «Did you mean 'host'?».

Цена решения названа прямо: секция перестаёт быть одним рекордом — схемы
объявляются первым аргументом, вычисляемые поля вторым. Порядок полей проекции
это сохраняет: сначала поля рекорда в порядке объявления, затем вычисляемые.

**Отвергнуто журналом и не пересматривается:** класс-прокси с геттерами,
обёртка `described(text, leaf)`, отслеживание зависимостей через `Proxy`.

### 2. Вычисление идёт после валидации всей секции

Порядок фиксирован: читаются ключи, валидируются поля, и только если не упало
ни одно — считаются вычисляемые. Иначе `fn` получал бы значения полей, которые
не прошли проверку, и падал бы вторым, более невнятным сообщением.

Ошибка `fn` — отдельный тип `ConfigDerivedError`, а не запись в
`failures` у `ConfigValidationError`. Причина в форме данных: запись отказа
несёт имя ключа и нормализованные issues схемы, а у вычисляемого поля нет ни
ключа, ни схемы. Ошибка называет секцию, поле и список зависимостей, исходную
ошибку кладёт в `cause`.

### 3. Секретность наследуется от зависимостей

Вычисляемое поле секретно, если секретна хотя бы одна его зависимость.
Секретность зависимости берётся эффективная — с учётом всех объявленных
читателей ключа, тем же `isSecretKey`, что и у обычных полей.

Правило одностороннее и намеренно грубое: `url`, собранный из пароля, секретен
целиком, даже если пароль в нём — четверть строки. Обратного правила («поле не
секретно, потому что автор так решил») нет: снять пометку нечем, и это дешевле
утечки.

Гарантия та же, что у обычного секретного поля, и граница у неё та же: печать
проекции показывает `***`, а `{ ...cfg }` и прямое чтение отдают настоящее
значение.

### 4. Пересчёт при перезагрузке — по сравнению зависимостей

У reloadable-секции обновление заменяет снапшот целиком. Вычисляемые поля
пересчитываются, если хотя бы одно значение зависимости изменилось; сравнение
поверхностное, по `Object.is` выходов схем.

Схема, возвращающая объект, при каждой проверке даёт новую ссылку, поэтому
такое поле будет считаться изменившимся всегда. Это принято: `fn` чистая и
дешёвая, лишний пересчёт стоит вызова функции, а пропущенный — устаревшего
значения в рабочем приложении.

Асимметрия старта и рантайма сохраняется: ошибка `fn` на старте останавливает
приложение, ошибка при перезагрузке оставляет последний валидный снапшот,
подписчиков не дёргает и пишет предупреждение — ровно как невалидное значение
ключа.

### 5. `env({ prefix })` — источник, а не свойство корня

Префикс живёт в источнике: `env({ prefix: 'SERVICE_1_' })` читает
`SERVICE_1_<KEY>` и отдаёт значение под `KEY`. Секции, `.keys` и глобы остаются
относительными — они по-прежнему не знают, откуда пришло значение.

Приоритет задаётся позицией привязки, как у любого источника. Неявный
`process.env` остаётся источником с низшим приоритетом, поэтому
`SERVICE_1_HTTP_PORT` перекрывает
`HTTP_PORT`, а `DATABASE_URL`, которого под префиксом нет, читается общим.

`init()`, `watch()` и `close()` у источника отсутствуют: читать нечего, следить
не за чем, освобождать нечего. `process.env` берётся живой ссылкой — тем же
способом, что и в читалке.

**Альтернатива — префикс в `makeApp` или в объявлении секции** — отвергнута
журналом: ключи перестали бы быть статическими, а `.keys` и глобы зависели бы
от корня.

### 6. Снимок несёт JSON Schema листа целиком

`describeConfig({ converters })` кладёт в описание ключа результат того же
диспетчера `leafJsonSchema`, что обслуживает OpenAPI: саму JSON Schema и исход
конвертации (`declared`, `converted`, `unconvertible`). Описание, умолчание и
перечисление читаются из неё полями `description`, `default`, `enum`.

Выцеженные поля вместо схемы не заводятся: их получение — три обращения к
свойствам, а список «важных» свойств пришлось бы фиксировать во фреймворке, и
`format` или `examples` потребовали бы отдельного изменения.

Диспетчер зовётся с `io: 'input'`: таблица описывает то, что человек пишет в
окружение, а не то, что получает хендлер после преобразований.

Без `converters` снимок остаётся прежним: полей JSON Schema в нём просто нет.
Исход `unconvertible` отличает «конвертера для этого вендора не передали» от
«описания у поля нет».

Вычисляемые поля попадают в снимок отдельным перечнем секции — с именем поля,
списком зависимостей и признаком секретности. В перечень ключей они не входят:
ключа у них нет, и привязать к ним источник нельзя.

## Risks / Trade-offs

- **Вывод типов кортежа зависимостей опирается на `const`-параметр типа
  (TS ≥ 5.0).** → Репозиторий на TS 5.7; форма проверена прототипом на
  настоящих zod-схемах, включая негативные случаи. Проверки типов на этот
  вывод входят в задачи.
- **Новые generics увеличивают бюджет типов.** → `yarn type-budget` входит в
  `yarn verify`; при росте сверх бюджета вывод упрощается до кортежа фиксированной
  длины.
- **Секция перестала быть одним рекордом.** → Цена названа в §1; форма
  повторяет `factoryProvider` и `@Component`, где список зависимостей тоже
  стоит отдельно от тела.
- **Объектное значение зависимости вызывает пересчёт на каждой перезагрузке.**
  → Принято в §4: цена — вызов чистой функции.
- **`env({ prefix })` не помогает секции с точным именем ключа.**
  `from('DATABASE_URL', …)` под префиксом читается как
  `SERVICE_1_DATABASE_URL` и, если такого ключа нет, падает на неявный
  `process.env`. → Это и есть желаемое поведение «общий ключ остаётся общим»;
  оно описывается в главе гайда явно.

## Migration Plan

Изменение аддитивно: третий аргумент `makeConfig` и аргумент `describeConfig`
необязательны, существующие объявления и вызовы остаются валидными.

- `docs/design/config.md`: §1 — форма `derived` (заменяет запись о листе
  рекорда), §3 — `env({ prefix })`, §8 — содержимое снимка.
- `docs/decisions/ideas.md`: в записи [2026-09-06] отметить, что форма
  вычисляемого поля уточнена при реализации, с причиной.
- `docs/guide/22-config-sources.md`: разделы про вычисляемое поле, префикс
  окружения и снимок с описаниями; дата сверки обновляется.
- `examples/users-service`: секция получает вычисляемое поле, чтобы глава
  гайда ссылалась на живой код.

Откат — снятие change'а целиком: отдельного флага у поведения нет.
