# Масштабирование

Один бинарник, разные топологии. Как вырасти от одной фичи до модульного монолита, разнесённого по процессам, **не переписывая бизнес-код**.
{.lead}

## Модульный монолит {#monolith}

Nestling рассчитан на модульный монолит, который умеет запускать выбранное подмножество фич. Локально все фичи работают в одном процессе; в проде тяжёлые фичи выносятся в отдельные поды.

Два свойства фреймворка дают большую часть этой модели сами по себе:

- **модули — значения**, поэтому фича — тоже значение, а «выбрать подмножество» означает отфильтровать массив в composition root;
- **контейнер жадный**, поэтому провайдеры невыбранной фичи не создаются.

### Прогрессивное раскрытие

Приложение из одной фичи выглядит так, будто фич нет вообще. Механизм фич, портов и шины необязателен и добавляется поверх: за него не платят, пока он не нужен. Composition root — одна функция `assemble(...)` с необязательными полями:

```ts assemble (сигнатура)
assemble({
  modules?,     // L0  модули
  config?,      // L1  привязка источников конфига
  features?,    // L2  наборы модулей
  select?,      // L2  какие фичи поднять: 'all' | 'orders,billing'
  transports?,  // L0+ транспорты как провайдеры
  policies?,    // инварианты на собранном графе
}): App         // app.run() · app.check() · app.close()
```

Политика диспатча портов задаётся не полем корня, а конфигом (`NESTLING_PORTS_DISPATCH`); шина подключается как транспорт (`nats()` в `transports:`).

## Прогрессия L0 → L4 {#levels}

Одна и та же система раскрывается слоями. Нижние уровни не меняются, когда вы подключаете верхние.

| Уровень | Что добавляется | Чего ещё нет |
| --- | --- | --- |
| **L0** | модули и транспорт | фичи, `select`, конфиг, порты, шина |
| **L1** | типизированный конфиг | фичи, `select`, порты, шина |
| **L2** | `makeFeature` и `select` | порты, шина; всё в одном процессе |
| **L3** | `makeRequest` / `makeCommand` / `makeEvent` и порты в одном процессе | шина; вызовы идут внутри процесса |
| **L4** | NATS и политика диспатча | — split-развёртывание |

:::note good Ключевое
**Код фич и endpoint'ов между L3 и L4 не меняется.** Разнесение по процессам — это разница в composition root и конфиге, а не в бизнес-коде. L0 нигде не упоминает `feature`, `port` и `select`.
:::

### L2 — фичи и `select`

Фича — набор модулей, тоже значение. `select` определяет, модули каких фич попадут в контейнер:

```ts main.ts
export const OrdersFeature  = makeFeature({ name: 'orders',  modules: [OrdersModule] });
export const BillingFeature = makeFeature({ name: 'billing', modules: [BillingModule] });

const cfg = load(RootConfig);             // чтение select до сборки контейнера (фаза 0)
await assemble({
  features: [OrdersFeature, BillingFeature],
  select: cfg.features,                   // 'all' локально, 'orders' в отдельном поде
  transports: [http({ port: 3000 })],
}).run();
```

Если фича не выбрана, её провайдеры не создаются, а её endpoint'ов нет: discovery обходит дерево выбранных модулей, а не глобальный реестр. Приложение по-прежнему живёт в одном процессе, шина не нужна.

## Порты и операции {#ports}

От того, как фичи общаются, зависит, можно ли будет разнести монолит по процессам. Nestling отвечает на это портами поверх операций. Одна и та же точка вызова из фичи A в фичу B работает и в одном процессе, и через сеть, без переписывания A.

### Как это сочетается с «no runtime magic»

Прозрачность расположения обычно требует рантайм-диспетчеризации. В Nestling выбор делается на сборке, а не на запросе: порт привязывается к локальной или удалённой реализации в composition root, по выбору фич и топологии. Во время запроса фича A вызывает конкретное значение; рантайм ничего не выбирает.

### Операция — значение, не зависящее от направления

```ts billing/operations.ts
export const ChargeCard = makeRequest({
  name: 'billing.charge',
  input:  z.object({ orderId: z.string(), amount: z.number() }),
  output: z.object({ chargeId: z.string() }),
});
```

| Вид | Семантика | Для чего |
| --- | --- | --- |
| `request` | запрос-ответ, может вернуть `Fail`, ровно один владелец | операция, которой нужен ответ |
| `command` | без ответа, ровно один обработчик, queue-group | команда; реплики делят нагрузку |
| `event` | факт, 0..N подписчиков | уведомление; выбор по умолчанию для связи фич |

### Половина портов уже есть

Реализация операции («я обрабатываю `billing.charge`») — это endpoint на транспорте-шине. Единственное новое — типизированный вызыватель. Владелец реализует операция, потребитель инжектирует `Contract.caller`:

```ts
// billing РЕАЛИЗУЕТ операция как endpoint
export const ChargeCardImpl = implement(ChargeCard, {
  deps: [PaymentGateway],
  handle: (gw) => async (input, meta) =>
    new Ok({ chargeId: await gw.charge(input, meta.signal) }),
});

// orders ВЫЗЫВАЕТ порт, не зная, где находится billing
export const CreateOrder = httpEndpoint({
  method: 'POST',
  path: '/orders',
  input: NewOrder,
  output: Order,
  pipeline: base,
  deps: [OrdersService, ChargeCard.caller],
  handle: (orders, billing: Port<typeof ChargeCard>) => async (input: NewOrder, meta): Output<Order> => {
    const charge = await billing.call({ orderId: input.id, amount: input.total }, meta);
    if (charge.isFail) return charge;     // отказ — обычный Fail, не исключение
    return new Ok(orders.create(input));
  },
});
```

:::note warn Правила для портов
Чтобы монолит можно было разнести по процессам, порты подчиняются трём правилам даже в одном процессе. Порт не участвует в транзакции вызывающего: общая транзакция не переживёт split. Локальный порт возвращает `Ok | Fail`: иначе потребители не будут обрабатывать отказ, и после split они сломаются. Согласованность между фичами обеспечивают события и outbox/saga, а не общая транзакция. Тип точки вызова одинаков для локального и удалённого порта, потому что завтра вызов может уйти в сеть.
:::

Через границу порта проходят и отказ, и контекст. Удалённый `Fail` восстанавливается на стороне вызывающего в настоящий `Fail`: идентичность доменной ошибки задаёт `code`, поэтому `OrderNotFound.is(x)` работает одинаково для локального отказа и для отказа, пришедшего по сети. [Переменные контекста](fundamentals.html#context) с `propagate: true` (traceId, requestId) передаются в заголовках сообщения, и транспорт на другой стороне открывает контекст заново.

### L4 — split без правки кода фич

Меняются только composition root и конфиг. Endpoint'ы и сервисы остаются теми же:

```ts main.ts
await assemble({
  features: [OrdersFeature, BillingFeature],
  select: cfg.features,                   // 'orders' здесь, 'billing' в другом поде
  transports: [http(), nats()],           // NATS — шина приложения
}).run();
// политика диспатча — в конфиге: NESTLING_PORTS_DISPATCH=local-first | always-remote
```

При `select='orders'` фича billing не выбрана, и `ChargeCard.caller` привязывается к удалённому вызову через NATS; billing в своём поде обслуживает `billing.charge` (реплики образуют queue-group). При `select='all'` без NATS всё работает в одном процессе, порт локальный. Один бинарник даёт разные топологии за счёт конфига.

## Транспорты {#transports}

Транспорт переводит байты в абстрактную модель запроса и обратно. Он строит `RequestContext` из входящих данных, вызывает пайплайн (не зная о его фазах) и сериализует `ResponseContext`. Всё, что связано с байтами — разбор, multipart, сжатие, CORS, таймауты, — живёт здесь, а не в пайплайне.

### Транспорты — провайдеры

Транспорт — синглтон с зависимостями и жизненным циклом, поэтому он объявляется как обычный провайдер, а не как отдельный список в конструкторе приложения. Отсюда следствия: набор транспортов приложения выводится из графа, endpoint ссылается на транспорт токеном, а проверка возможностей транспорта сводится к DI и проверке на сборке (нет транспорта для endpoint'а — ошибка сборки).

| Транспорт | Пакет | `pattern` | Возможности |
| --- | --- | --- | --- |
| HTTP | `@nestling/transport.http` | `'POST /orders'` | маршрутизация find-my-way, multipart через busboy, NDJSON и SSE, лимит тела, корректное закрытие |
| CLI | `@nestling/transport.cli` | `'process'` (команда) | одиночный запуск и REPL, stdin как `stream` |
| NATS | `@nestling/transport.nats` | subject операции | входящие и исходящие вызовы, queue-group, JetStream для `durable` |

Один пайплайн обслуживает все транспорты, потому что работает со значениями, а не с `IncomingMessage` и `ServerResponse`. Endpoint, который отвечает на HTTP, может отвечать на команду CLI и на сообщение NATS. NATS при этом — транспорт с двумя возможностями (принимать и отправлять), а не отдельная подсистема обмена сообщениями. Специфика NATS (JetStream, wildcard, ack) в API операций не попадает.

:::note Итог
Endpoint не знает ни источника конфига, ни транспорта. Один и тот же бизнес-код работает в одном процессе и в split, с конфигом из env или Vault, по HTTP или через шину — без правок. Ядро берёт на себя окружение; пользовательский код остаётся чистым. В этом суть Nestling: структура NestJS без его рантайм-магии, с гарантиями вместо конвенций.
:::
