## Context

Сборка payload в HTTP-транспорте сегодня — одна функция:

```typescript
// transport.http/src/merge.ts
mergePayload(body, query, params)  // одноимённый ключ → PayloadConflictError → 400
```

и один вызов в `transport.ts` (ветка `default` и ветка `withFiles`). Query
собирается в плоский объект перебором `url.searchParams.entries()` — повтор
ключа молча затирается (last-wins). Endpoint-декларация после change #24
(`endpoint-model`) — значение с типизированным HTTP-словарём
(`httpEndpoint({ method, path, … })`), в котором уже выведен
`PathParams<Path>` и оставлена явная точка расширения под bind-карту; ничего,
кроме `method`/`path`, словарь пока не несёт.

Ограничения площадки, определяющие форму решения:

- **Standard Schema (change #19) не даёт интроспекции** — в рантайме схема
  непрозрачна, перечня ключей нет ни у одного вендора
  (`docs/design/schemas.md`). Всё, что требует знания структуры, обязано
  быть объявлено явно. При этом **на уровне типов** ключи известны
  (`InferInput<I>`), и это асимметрия, которой можно пользоваться.
- Марка внутри вендорской схемы (`z.object({ expand: query(z.string()) })`)
  невыразима: zod принимает в shape только `ZodType`, а прочитать чужой
  shape нечем.
- Kernel обязан оставаться транспорт-слепым: `@nestling/pipeline` не знает
  слов `path`/`query`/`body`.
- TS 5.7 strict, ESM, `Pipeline<TReq, TAcc, TNeeds>` с фантомным
  `$types` — по нему `TReq` ведёт себя ковариантно, что важно для D6.

Потребителей карты трое, и двое из них ещё не написаны: транспорт (здесь),
генератор OpenAPI (#20) и типизированный клиент (#22). Клиент импортирует
**только контракт**, без серверного кода, — поэтому карта обязана быть
свойством значения-декларации, а не результатом регистрации в `App`.

## Goals / Non-Goals

**Goals:**

- Детерминированное правило «поле → место» и его материализация в плоскую
  bind-карту при создании декларации.
- Карта читается с значения декларации одинаково транспортом, OpenAPI и
  клиентом; ядро её не интерпретирует.
- Strict-приём: payload собирается только из канонических мест;
  `mergePayload`/`PayloadConflictError` уходят.
- Пометки `query()`/`body()` с местом под `header()` без смены носителя.
- Повторный query-ключ перестаёт молча теряться.
- `rawBody: true` даёт байты в **типизированном** стартовом контексте:
  забытая пометка — ошибка компиляции, а не рантайма.
- Максимум fail-fast, достижимый без интроспекции схем.

**Non-Goals:**

- `header()` и типизация ответных заголовков (deferred).
- Генерация OpenAPI (#20) и сборка запроса клиентом (#22).
- `makeContract`/`http:`-биндинг контракта (#11) — та же функция
  разворачивания будет переиспользована, но поле здесь не заводится.
- Коерсия провод-строк в `number`/`boolean` — ответственность схемы
  (`z.coerce`), открытый вопрос ideas.md.
- Формы io (#6): `stream`/`withFiles`/`files` работают как сейчас,
  bind-карта на них не распространяется (и запрещена fail-fast'ом).
- CLI: канон размещения — правило HTTP, `cliEndpoint` не трогается.

## Decisions

### D1. Карта — «явные размещения + правило для остального», а не полный список полей

```typescript
type BindPlace = 'path' | 'query' | 'body';

interface BindPlacement {
  readonly in: BindPlace;
  /** query-поле всегда массив (в т.ч. при одном вхождении) */
  readonly multiple?: boolean;
}

interface HttpBinding {
  readonly method: HTTPMethod;
  readonly path: string;                                     // шаблон с ':param'
  readonly fields: Readonly<Record<string, BindPlacement>>;   // path-параметры + пометки
  readonly rest: 'query' | 'body';                            // всё остальное
  readonly rawBody: boolean;
}
```

Перечислить все поля карта не может — ключей схемы в рантайме нет. Но она
**тотальна как правило**: у каждого поля есть место — либо явное в `fields`,
либо `rest`. Этого достаточно всем троим потребителям: транспорт собирает
payload, OpenAPI раскладывает поля по `parameter`/`requestBody` (структуру
схемы ему даёт вендор-конвертер), клиент собирает запрос.

`rest` вычисляется по методу: `GET`/`HEAD`/`DELETE`/`OPTIONS`/`TRACE` →
`query`, остальные → `body`. Множество «методов без тела» фиксировано в
одном месте и участвует и в `rest`, и в fail-fast для `body()`.

*Альтернатива — требовать полный список полей руками:* автор дублирует
перечень ключей схемы для каждой ручки, а сверить дубль со схемой нечем —
получается второй источник истины, расходящийся молча.

### D2. Пометка — значение в `bind`-записи словаря, не обёртка схемы и не строка

```typescript
export const UpdateUser = httpEndpoint({
  method: 'PATCH',
  path: '/api/users/:id',
  input: UpdateUserInput,            // { id, name?, email?, expand?, tags? }
  bind: {
    expand: query(),                 // вытащить из body в query
    tags: query({ multiple: true }), // ?tags=a&tags=b → string[]
  },
  …
});
```

**Почему не внутри схемы** (`z.object({ expand: query(z.string()) })`, как
`from()` в makeConfig): у makeConfig секция — **рекорд полей, которым владеет
фреймворк**, поэтому марку видно без интроспекции. У endpoint'а `input` — одна
вендорская схема; марку внутрь zod-shape не положить (там только `ZodType`), а
прочитать чужой shape нечем ни у одного вендора. Это и есть ответ на открытый
вопрос ideas.md «форма пометок для не-zod вендоров»: гарантированный минимум —
пометка живёт в декларации рядом со схемой; носитель (карта) от формы сахара
не зависит и переживёт появление рекорд-формы `input`, если она приедет с #6.

**Почему марка-значение, а не строка** (`bind: { expand: 'query' }`):
`header('If-Match')` при возврате из deferred требует аргумента (имя заголовка
≠ имя поля), а `query({ multiple: true })` — опций. Одна форма записи на все
случаи вместо двух; добавление `header()` аддитивно и носитель не меняет.

**Ключи `bind` типизированы схемой.** Рантайм ключей не знает, но
`InferInput<I>` знает: тип `bind` — `Partial<Record<Exclude<keyof
InferInput<I>, PathParams<Path>>, BindMark>>`. Отсюда бесплатно:

- опечатка в имени поля — ошибка компиляции;
- пометка на поле-path-параметре — ошибка компиляции (правило ideas
  «пометка на path-поле — ошибка сразу» становится статическим).

Рантайм-проверки тех же правил остаются для JS-потребителей и для случая
непрозрачного `input` (`AnyPayload` без вывода ключей).

### D3. Разворачивание — в конструкторе декларации; транспорт только читает

`httpEndpoint` вызывает `computeHttpBinding({ method, path, bind, rawBody })`
и кладёт результат на значение. Точка выбрана по требованию клиента: он
импортирует контракт и обязан получить карту без сервера
([ideas.md, «Типизированные клиенты», решение 1](../../../docs/decisions/ideas.md)).

Декларация, созданная kernel-примитивом `makeEndpoint({ transport: 'http',
pattern })`, карты не несёт. Транспорт в этом случае считает **тот же канон**
без пометок из `pattern` (метод и шаблон в нём уже есть) — та же функция,
детерминированный результат. Fail-fast здесь неуместен: канон полностью
определён парой (метод, путь), и запрещать kernel-примитив ради церемонии
незачем.

*Альтернатива — считать карту при регистрации в `App`:* клиенту она тогда
недоступна, а fail-fast срабатывает не у владельца декларации.

### D4. Strict-приём: три источника с фиксированным приоритетом

```
payload = { ...restSource, ...markedFields, ...pathParams }
```

- `pathParams` — только из совпадения с маршрутом;
- `markedFields` — каждое из своего места (`query()` → из URL,
  `body()` → из тела);
- `restSource` — **один** источник по `rest`: разобранный query или
  разобранное тело.

Приоритет фиксирован (path > пометка > rest) и в конфликт не превращается:
поле не в своём месте в payload просто не попадает. `PayloadConflictError`
исчезает как класс задач, а не переезжает.

Тело читается только если `rest === 'body'` **или** есть `body()`-пометки
**или** взведён `rawBody`. Для `GET` без пометок тело не читается вовсе —
приятный побочный эффект strict-приёма.

Для `withFiles` правило то же: поля формы играют роль `restSource` (эта
форма всегда body-ориентирована), path-параметры и query-пометки
подмешиваются в `data` до валидации схемой. Для `stream`/`files`/`primitive`
payload — не объект, подмешивать некуда: такая декларация с path-параметрами
или `bind` отвергается при создании (D5).

### D5. Fail-fast при создании: ровно то, что решаемо без интроспекции

| Правило | Проверка |
|---|---|
| пометка на поле-path-параметре | тип + рантайм |
| `body()` у метода без тела (`GET`/`HEAD`/…) | рантайм |
| `bind` при неструктурном `input` (`stream`/`files`/`primitive`) | рантайм (`analyzePayload`) |
| path-параметр в шаблоне при неструктурном `input` | рантайм |
| path-параметр в шаблоне при отсутствии `input` | рантайм |
| `rawBody: true` с `stream`/`files`/`withFiles` | рантайм |

Правило ideas «path-параметр без поля в схеме — ошибка сразу» в полном виде
недостижимо: перечня ключей у схемы нет. Реализуется его решаемая часть
(строки 4–5 таблицы) — случаи, когда параметру физически негде оказаться.
Остаток (`:id` есть, схема — объект без `id`) в рантайме проявится как
отсутствующее поле payload; кандидат на полную проверку — change `openapi`
(#20), где вендор-конвертер структуру уже знает. Ограничение фиксируется в
Purpose спеки и в риск-листе, а не замалчивается.

### D6. `rawBody: true` меняет тип стартового контекста

```typescript
const Webhook = httpEndpoint({
  method: 'POST',
  path: '/hooks/stripe',
  rawBody: true,                                   // ← без неё строка ниже не компилируется
  pipeline: compose(makePipeline<{ rawBody: Uint8Array }>().pre(verifySignature()), base),
  …
});
```

Словарь становится генериком по стартовому контексту:
`Start = rawBody extends true ? { rawBody: Uint8Array } : EmptyInput`.
Простой типизации слота (`pipeline?: Pipeline<Start, P, PN>`) **недостаточно**:
`TReq` у `Pipeline` ковариантен через фантомное `$types`, поэтому
`Pipeline<{ rawBody }, …>` присвоился бы слоту `Pipeline<EmptyInput, …>` и
забытая пометка прошла бы молча. Поэтому слот проверяется условным типом-
сторожем `ValidateStart<P, Start>` в позиции параметра — техника, которой уже
пользуется `compose` (`ValidateCompose`). Читаемость самой диагностики —
предмет change `pipeline-type-dx` (#23), закрывающего это же breaking-окно;
здесь фиксируется только срабатывание (type-тест на отрицательный случай).

Рантайм: байты читаются **один раз** (`readBody`, лимит `maxBodySize`
действует как обычно), кладутся в стартовый input, и значение парсится из тех
же байтов — второго чтения потока нет. Совместимо с `input`-схемой и
примитивами `text`/`binary`; с `stream`/`files`/`withFiles` — fail-fast (поток
уже потреблён парсером, а буферизовать multipart целиком неявно — не то, что
делают по умолчанию).

*Альтернатива — всегда класть байты в `raw`:* память платят все ручки, а
гарантия становится конвенцией («не забудь pre-юнит»).

### D7. Стартовый input — параметр `makeEmptyContext`

```typescript
makeEmptyContext<S extends AnyInput = EmptyInput>(
  raw, endpoint, signal?, input?: S,
): ExtendableContext<S>
```

Единственная точка, через которую транспорт кладёт `rawBody` в контекст.
Аддитивно (четвёртый параметр с дефолтом `{}`), симметрично тому, как
`signal` уже попадает в контекст от транспорта.

*Альтернатива — `Raw.rawBody`:* `raw` доступен пайплайну и так, но тип
стартового контекста от этого не меняется, а именно он даёт
compile-time-гарантию из D6.

### D8. Носитель на декларации — непрозрачное для ядра поле `binding`

`EndpointOptions`/`EndpointDefinition` получают `binding?: unknown`, которое
`makeEndpoint` переносит на значение без интерпретации; типизирует и читает
его транспорт (`httpBindingOf(definition): HttpBinding | undefined`).
`@nestling/pipeline` остаётся HTTP-слепым.

*Альтернативы:* пятый generic-параметр `EndpointDefinition` — тип-шум в
каждой сигнатуре, где декларация упоминается; складывать карту в
`EndpointMeta` (там есть index-signature) — это pipeline-facing структура,
а карта нужна клиенту, который пайплайна не импортирует.

### D9. Query-массивы: повтор всегда даёт массив, `multiple` — всегда массив

`url.searchParams.getAll(key)`: 0 вхождений → поля нет (отсутствие остаётся
отсутствием, чтобы `.optional()` и дефолты схемы работали); 1 → скаляр, если
нет `multiple`; ≥2 → массив. Пометка `query({ multiple: true })` даёт массив и
при одном вхождении.

Без `multiple` схема, ожидающая массив, на одиночном вхождении честно падает
на валидации — видимая ошибка вместо сегодняшнего тихого last-wins. Коерсия
«скаляр → массив» по типу поля потребовала бы интроспекции и остаётся за
автором схемы (`z.union`/`z.coerce`) — общий открытый вопрос коерсии.

## Risks / Trade-offs

- **Поле, присланное не в каноническое место, молча не попадает в payload**
  → ошибка приходит от валидации схемы («required») и называет поле; это
  цена детерминизма (warn-and-pass отвергнут ещё в модели ошибок). Канон
  описывается в гайде и в README транспорта.
- **`:id` в шаблоне при схеме без поля `id` не ловится** → решаемая часть
  проверок сделана (D5), остаток задокументирован как известное
  ограничение Standard Schema и передан кандидатом в `openapi` (#20).
- **Защита ключей `bind` — только на типах** → JS-потребитель получает
  подмножество проверок; рантайм-правила (пометка на path-поле, `body()` у
  GET) продублированы в рантайме именно поэтому.
- **Смена поведения повторного query-ключа** (last-wins → массив) может
  сломать код, полагавшийся на прежнее → осознанный фикс тихого бага внутри
  breaking-окна; отражён в спеке сценарием.
- **`rawBody` — память** → opt-in, лимит `maxBodySize` действует, тело
  читается один раз (без удвоения).
- **`ValidateStart` добавляет условный тип в горячую сигнатуру** → риск
  нечитаемой диагностики; смягчение — позитивные и негативные type-тесты
  здесь, читаемость литерала `__error` — #23 в том же окне.
- **Удаление `mergePayload`/`PayloadConflictError` ломает импорты** →
  breaking-окно, миграция в README и в записи об архивации; промежуточного
  режима «оба способа сборки» нет намеренно.

## Migration Plan

Каждый шаг оставляет репозиторий собираемым:

1. `@nestling/pipeline` — `binding?: unknown` в `EndpointOptions`/
   `EndpointDefinition` + перенос в `makeEndpoint`; четвёртый параметр
   `makeEmptyContext`.
2. `@nestling/transport.http` — пометки `query`/`body`, типы `HttpBinding`/
   `BindPlacement`, `computeHttpBinding`, `httpBindingOf`; fail-fast D5;
   `bind`/`rawBody` в словаре; `ValidateStart` для слота `pipeline`.
3. `@nestling/transport.http` — сборка payload по карте в `transport.ts`
   (ветки `default`, `withFiles`), разбор query через `getAll`, чтение
   `rawBody` и стартовый контекст; удаление `merge.ts`, `merge.spec.ts`,
   `PayloadConflictError` и их экспортов.
4. Тесты: юнит-тесты канона и fail-fast, интеграционные сценарии
   размещения (path/query/body, поле не в том месте, повтор ключа,
   multipart + path-параметр, webhook с `rawBody`), type-тесты `bind` и
   `ValidateStart`.
5. Примеры: `examples.app-with-http` (проверка существующих ручек под
   strict-приёмом + демонстрация `query()`-пометки и `rawBody`-ручки),
   `examples.simple-http-server`.
6. Доки: сверка `design/endpoints.md` §4 и `design/transports.md` §2 с
   реализацией (форма пометок, объём fail-fast), `design/schemas.md`,
   гайды с новой датой в плашке, README пакетов, статус #21 в roadmap.

Откат — ветка целиком; режима совместимости с merge нет намеренно.

## Open Questions

- **Коерсия провод-строк** (`?page=2` → `number`, `?flag=true` → `boolean`):
  ответственность схемы или канонное правило по месту биндинга. Влияет и на
  клиента (обратная сериализация) — решается вместе с #22; здесь
  сознательно не трогается.
- **Строковая форма записи** (`bind: { expand: 'query' }`) как альтернатива
  маркам — не заводится, чтобы не иметь двух форм; вернуть аддитивно, если
  марки окажутся многословными на практике.
- **Полная проверка «path-параметр ↔ поле схемы»** — реализуема только там,
  где есть вендор-конвертер; предлагается как boot-time-проверка change
  `openapi` (#20), но решение принимается там.
- **Рекорд-форма `input`** (как секция конфига) сделала бы пометки
  внутрисхемными и вернула бы полный fail-fast — тема формы io (#6); карта
  как носитель от этого не меняется.
