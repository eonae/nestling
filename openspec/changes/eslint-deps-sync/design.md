# eslint-deps-sync — дизайн

## Context

`@nestlingjs/eslint-plugin` содержит два синтаксических правила.
`import-through-barrel` читает файловую систему и полно, `endpoint-has-layer`
разбирает буквальные формы значения `pipeline` и молчит на непрозрачных.
Оба написаны против типов `estree` и `Rule` из `eslint`, рантайма
`@nestlingjs/*` в зависимостях нет.

Список зависимостей класса объявляется декоратором роли: `@Component([…])`,
`@Handler([…])`, `@Resource([…])`. Компилятор сверяет его с параметрами
конструктора по типам, порядку и длине (capability
`injectable-dependency-list`); у `@Resource` эталон — параметры
`static acquire` без последнего, сигнала. Необязательные параметры дают
диапазон длин, rest-параметр снимает верхнюю границу. В рантайме длина не
проверяется.

Соглашения об именовании ([conventions.md](../../../docs/conventions.md))
связывают тип параметра с DI-токеном: класс сам себе DI-токен, DI-токен
интерфейса `X` называется `X$`, семейства тоже носят суффикс `$` (`Logger$`,
`Counter$`), секция конфига инжектируется по своему значению и типизируется
`Config<typeof X>`, вызыватель операции — `Port<typeof Op>` по `Op.caller`,
эмиттер — `Emitter<typeof Op>` по `Op.emitter`.

Корпус репозитория: 44 класса с декоратором роли в `examples/*`, 4 в `src`
пакетов, 7 в сниппетах скилла. Формы параметров в нём: класс; `Config<typeof
X>`; `Port<typeof Op>`; `Emitter<typeof Op>`; `Logger` при `Logger$.auto` и
при `Logger$('scope')`; интерфейс при `X$`, включая член семейства
`Counter$('users')`; `readonly HealthCheck[]` при `HealthCheck$.all`;
`CtxReader<T>` при `Ctx(Var)`; `Set<string>` при `SeenKeys$`;
`PgConnection<S>` при `db.connection` и `Connection$`;
`OutboxEmitter<typeof Op>` при `outboxed(Op)`.

Декораторы, аннотации типов и свойства-параметры (`private readonly x: T`)
в дереве `estree` отсутствуют: их даёт `@typescript-eslint/parser`. Общий
конфиг репозитория и конфиг из `references/setup.md` скилла разбирают
`*.ts` этим парсером.

## Goals / Non-Goals

**Goals:**

- Автор видит в редакторе, какой DI-токен ожидается в каждой позиции
  списка, и получает список целиком, когда написал `@Component()`.
- Правило не даёт ложных срабатываний на формах из корпуса репозитория:
  прогон по всем пакетам и примерам печатает ноль предупреждений.
- Автофикс не меняет смысл компилирующегося кода: он дописывает
  недостающее, а не заменяет написанное.
- Правило остаётся синтаксическим и без рантайм-зависимостей, как два
  соседних.

**Non-Goals:**

- Типизированный линтинг, `reflect-metadata`, `emitDecoratorMetadata`,
  генерация списка шагом сборки.
- Вывод DI-токена для типов, которые его не называют (`CtxReader<T>`,
  `Set<string>`, типы сателлитов), и настройка таблицы опциями.
- Проверка функциональных провайдеров и классов без декоратора роли.
- Изменения контейнера и проверки в типах.

## Decisions

### D1. Правило синтаксическое; типы AST — `@typescript-eslint/utils` только в типах

Правило написано против дерева `@typescript-eslint/parser`: узлы
`Decorator`, `TSParameterProperty`, `TSTypeAnnotation`, `TSTypeReference`,
`TSTypeQuery`, `TSArrayType`, `TSTypeOperator`. Типы этих узлов берутся из
`@typescript-eslint/utils` (`TSESTree`) через `import type`; пакет попадает
в `devDependencies`, и в `dist` зависимости нет. Экспорт правила остаётся
`Rule.RuleModule` из `eslint`.

Под парсером без поддержки TypeScript декораторов в дереве нет, и правило
молчит. README называет требование к парсеру; для кода с декораторами оно
и так выполнено.

Отвергнуто: **правило с информацией о типах.** Отличало бы класс от
интерфейса надёжно, но требует программы TypeScript и делает плагин
зависимым от проекта; решение записи [2026-09-12].

Отвергнуто: **типы AST из `@typescript-eslint/types` напрямую.** Тот же
набор, но `utils` уже стоит в репозитории как зависимость `typescript-eslint`,
и второе имя в манифесте ничего не добавляет.

### D2. Таблица вывода и эквивалентность по голове выражения

Ожидаемый элемент выводится из аннотации типа параметра:

| Тип параметра | Канонический элемент | Совпадением считается |
|---|---|---|
| `X[]`, `readonly X[]`, `ReadonlyArray<X>`, в файле виден `X$` | `X$.all` | выражение с головой `X$` |
| `X`, в файле виден `X$` | `X$`; для `Logger` — `Logger$.auto` | выражение с головой `X$` |
| `X` — класс (D3) | `X` | идентификатор `X` |
| `Config<typeof X>` | `X` | идентификатор `X` |
| `Port<typeof Op>` | `Op.caller` | член `Op.caller` |
| `Emitter<typeof Op>` | `Op.emitter` | член `Op.emitter` |
| всё остальное | непрозрачно | любой элемент |

Строки проверяются по порядку.

Голова выражения — крайний левый идентификатор: у `X$` это `X$`, у
`X$('users')` и `X$.auto` тоже `X$`. Сравнение по голове нужно потому, что
семейство от DI-токена синтаксически не отличить: `Counter$` в одном файле
семейство, `UsersRepository$` в другом — DI-токен, а написанный автором
член `Counter$('users')` верен. Канонический элемент правило пишет только
там, где автор не написал ничего.

Правило пишет только имена, которые в файле уже есть, и документированные
члены `.auto`, `.all`, `.caller`, `.emitter`. `Logger` отличается от общей
строки одним: `Logger$` — семейство, голый `Logger$` не компилируется, и
канонический член — `.auto`. Без импортированного `Logger$` позиция
непрозрачна, а класс с именем `Logger` остаётся обычным классом. Строка с
массивом закрывает второй открытый вопрос записи для `Family.all`.

Отвергнуто: **сравнение текста элемента с каноническим.** `Logger$('db')`
и `Counter$('queries')` из примеров стали бы ложными срабатываниями.

Отвергнуто: **строка `Logger` без видимого `Logger$`.** Она дала бы автофикс
для `@Component()` и без импорта DI-токена, но вписывала бы в список имя,
которого в файле нет. Линтер не выдумывает имён: он пишет то, что автор
уже импортировал.

### D3. Класс и интерфейс различаются по объявлению и импорту

Для типа `X` без видимого `X$` правило ищет привязку `X` через
`sourceCode.getScope` вверх от класса, как `endpoint-has-layer` ищет
инициализатор слоя:

- объявление `class X` в файле или импорт значением (`import { X }`) —
  класс, ожидается `X`;
- объявление `interface X`, `type X` или импорт только типа
  (`import type { X }`, `import { type X }`) — интерфейс без DI-токена в
  области видимости, позиция непрозрачна;
- привязки нет (`Set`, `AbortSignal`, глобальные типы) — непрозрачно.

Видимый `X$` сильнее классификации: класс тоже бывает зарегистрирован под
DI-токеном (`classProvider(Database$, InMemoryDatabase)` при типе
параметра — абстрактный класс).

Отвергнуто: **различать только по видимому `X$`**, как в записи. Интерфейс,
импортированный через `import type` без `X$` рядом, считался бы классом, и
автофикс вписал бы в список имя типа — код перестал бы компилироваться.
Уточнение сужает случаи, где правило говорит, и не расширяет их.

### D4. Проверка по позициям; непрозрачная позиция принимает написанное

Список сверяется с параметрами позиция за позицией. Известная позиция
требует совпадения по D2, непрозрачная принимает любой элемент. Правило
молчит целиком только там, где сравнивать нечего: список не литерал
массива, в массиве spread, у класса нет собственного конструктора
(`@Component`, `@Handler`) или `static acquire` (`@Resource`).

Длина проверяется всегда. Допустимые длины — от числа обязательных
параметров до общего числа; rest-параметр снимает верхнюю границу. Класс с
пустым или отсутствующим списком при непустом конструкторе — расхождение
длины.

Отвергнуто: **молчать, если хоть один параметр непрозрачен**, как в записи.
`CtxReader<T>` стоит в каждом репозитории с контекстом запроса
(`DbUsersRepository`), и правило замолчало бы ровно на классах, где список
длиннее всего. Длина при этом остаётся тем, что компилятор сверяет тоже,
и ложного срабатывания на ней нет.

### D5. Автофикс дописывает; замену предлагает suggestion

Два сообщения:

- `length` — на аргументе декоратора: число написанных DI-токенов и число
  параметров. Автофикс дописывает недостающие позиции каноническими
  элементами, написанные оставляет как есть (`Logger$('db')` не
  превращается в `Logger$.auto`), лишние убирает; доступен он, только
  когда каждая недостающая позиция известна. Это покрывает `@Component()`
  с пустым списком, недостающий последний DI-токен и лишний.
- `mismatch` — на элементе: имя параметра, текст его типа и ожидаемый
  DI-токен. Автофикса нет; замена элемента каноническим текстом отдаётся
  suggestion ESLint (`meta.hasSuggestions`), которую применяют вручную в
  редакторе и которую `eslint --fix` не трогает.

Написанный элемент — решение автора, а таблица синтаксическая: для
`logger: Logger` DI-токен `RootLogger$` компилируется и бывает нужен.
Молчаливая замена, которая компилируется, — худший исход для линтера.
Дописанное на пустое место такого риска не несёт: ошибочный канонический
элемент падает на компиляции, а не меняет смысл.

Отвергнуто: **автофикс на любое расхождение**, как сформулировано в
записи. Намерение записи — чтобы пустой список из привычки NestJS
заполнился сам — сохранено.

### D6. Сообщения называют статус подсказки

Тексты на английском (capability `runtime-message-language`), с именем
класса, параметра, текста типа и ожидаемого DI-токена. Каждое сообщение
называет свой статус: подсказка в редакторе, гарантия — компилятор. Уровень
`warn` в README и в примере конфига.

### D7. Правило включено в общий конфиг репозитория

`.config/eslint.config.js` подключает `@nestlingjs/dependency-list` уровнем
`warn` рядом с `import-through-barrel`: соглашение общее для пакетов и
примеров, а не свойство одного приложения. Прогон по репозиторию в этом
change'е доводится до нуля предупреждений; класс, который правило
подсветило верно, приводится к таблице, а ложное срабатывание чинит
правило.

Отвергнуто: **уровень `error` в репозитории.** Правило может ошибиться на
нестандартном DI-токене, и подавление комментарием попало бы в пример, а
из него — в главу гайда.

### D8. Тесты — `RuleTester` с парсером `typescript-eslint`

Спека правила перечисляет валидные формы — все строки таблицы, включая
`Logger$('scope')`, член семейства, `X$.all`, непрозрачные позиции,
`import type` без DI-токена, класс без конструктора, список-идентификатор,
spread, необязательные параметры при обеих длинах, rest-параметр,
`@Resource` с `acquire` — и невалидные: пустой список с автофиксом,
недостающий последний DI-токен с автофиксом, лишний DI-токен с
автофиксом, расхождение длины при непрозрачной позиции без автофикса,
замена с suggestion. Валидных случаев больше, чем невалидных, и это
соотношение содержательно: каждая форма молчания зафиксирована тестом.

## Risks / Trade-offs

- **Интерфейс импортирован значением** в проекте без
  `consistent-type-imports` → правило считает его классом, и автофикс
  `length` впишет имя типа. Код упадёт на компиляции, а не изменит
  поведение; README называет допущение.
- **Видимый `X$` — семейство, а позиция пуста** → канонический `X$` не
  той формы (нужен член или `.auto`). Компилятор отвергнет; сообщение
  называет ожидаемый DI-токен, и починка — одна строка.
- **Нестандартный DI-токен известного типа** (`RootLogger$` для `Logger`
  при видимом `Logger$`) → подсказка `mismatch` на верном коде. Уровень `warn`, автофикса нет,
  подавление — `eslint-disable-next-line` с причиной.
- **Класс наследует конструктор** → правило молчит: параметры базового
  класса в файле не видны.
- **Парсер без TypeScript** → правило молчит; декораторы такой парсер не
  разбирает и без правила.

## Migration Plan

Change не ломающий. Новое правило подключают явно, как два соседних; у
пользователей без строки в конфиге ничего не меняется. В репозитории
правило включено общим конфигом уровнем `warn`.
