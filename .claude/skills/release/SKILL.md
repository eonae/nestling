# Выпуск версии

Версия одна на все публикуемые пакеты. Их выпускают вместе, и совместимы
они только внутри одной версии.

Роли разделены жёстко. Сессия проверяет готовность и поднимает версию.
Человек отправляет коммит и тег. Реестр публикует по тегу через прогон
`release.yml`.

Команды, реестр и разбор отказов — [`RELEASING.md`](../../../RELEASING.md).
Здесь записан порядок работы сессии и то, чего в инструкции нет.

## Чего сессия не делает

- Не пушит. `git push --follow-tags` из сессии не проходит: ключа нет.
  Команду отдай пользователю строкой с префиксом `!`.
- Не публикует пакеты с машины. Исключение — первая публикация нового
  имени, раздел «Первая публикация имени» инструкции.
- Не ставит тег на непроверенный `main`.
- Не правит версию руками. Её правит `yarn lerna version` сразу в
  восемнадцати манифестах и в `lerna.json`.

## Готовность к выпуску

Проверь всё до подъёма версии. После тега откатывать нечего: красный
прогон выпуск отменяет.

| Что | Чем проверить | Критерий |
| --- | --- | --- |
| Ветки влиты | `node .claude/skills/merger/scripts/scan.mjs` | ни одной `ready` |
| Код | `yarn verify:fresh` | код возврата 0 |
| Упаковка | `yarn nx run-many -t build && yarn pack:check` | код возврата 0 |
| Внешние службы | `yarn test:live` | код возврата 0 |
| Документация | `yarn docs:audit` | 0 ERROR, 0 WARN |
| Заметка о выпуске | `node .claude/skills/release-notes/scripts/check.mjs` | 0 ERROR |

Четыре ловушки, каждая стоила прогона:

1. **`yarn verify` берёт результат из кэша.** Однажды он отдал 105 задач
   из 105 кэшированными и показал зелёный на красном дереве. Гоняй
   `verify:fresh`.
2. **Смена инструмента сборки или прогона требует `npx nx reset`.** Флага
   `--skip-nx-cache` мало: он повторяет вывод уже удалённого инструмента,
   и в логе оказываются строки обоих сразу.
3. **Код возврата теряется в цепочке.** В `cmd > log; echo EXIT=$?; grep …`
   наружу уходит код `grep`, и красный прогон выглядит зелёным. Пиши код
   в отдельный файл и читай оттуда.
4. **Четыре задачи нестабильны**: `type-budget` у `@nestlingjs/app`,
   `test` у `@nestlingjs/otel`, `build` у `@examples/microservice` и
   `build` у `@nestlingjs/logging.pino`. Упала одна — перезапусти её
   отдельно с `--skip-nx-cache`. Зелено там — прогон зелёный; красно и
   там — это поломка.

`pack:check` и `test:live` в `yarn verify` не входят. Первый ставит
тарболы в проект вне репозитория и ловит пакет без сборки, оставшийся
протокол `workspace:` и зависимость из `devDependencies`, которую
импортирует `src`. Второй требует запущенного Docker и проверяет
совместимость с настоящей службой, а не с двойником.

## Порядок

1. **Заметка о выпуске.** Пишется до подъёма версии: сайт собирается по
   тегу, и тег должен нести заметку. Форма — скилл
   [`release-notes`](../release-notes/SKILL.md). Плашка называет обе
   границы диапазона тегами, своего тега ещё нет — сверь диапазон руками.
2. **Готовность.** Таблица выше, целиком.
3. **Подъём версии.** `git switch main && git pull`, затем
   `yarn lerna version <patch|minor|major> --force-publish`. Флаг
   обязателен: без него выпуск без правок в `packages/` заканчивается
   строкой «No changed packages found». Пуш выключен настройкой, поэтому
   до следующего шага всё локально и откатывается через
   `git reset --hard origin/main`.
4. **Отправка.** Отдай пользователю команду `! git push --follow-tags`.
   Она отправляет два указателя, и каждый запускает свой прогон: ветка —
   проверку, тег — релиз.
5. **Ожидание.** Порядок шагов прогона: установка, `yarn verify`,
   `yarn pack:check`, публикация. Публикация идёт последней, красный шаг
   до неё не доводит.
6. **Результат.** `npm view @nestlingjs/app version`. На странице пакета
   должен стоять значок provenance со ссылкой на прогон.

## Новое имя пакета

Доверенного издателя нельзя завести для имени, которого в реестре нет, а
застейджить новое имя реестр не даёт. Поэтому первую версию нового имени
отправляет человек со своей машины, между шагами 3 и 4 — версия поднята,
тег стоит, отправки ещё не было. Команды и заведение издателя — раздел
«Первая публикация имени» инструкции.

Переименованный пакет для реестра — новое имя. Старое после выпуска
помечают `npm deprecate` с указанием нового.

## Когда что-то пошло не так

Разбор отказов реестра — раздел «Когда что-то пошло не так» инструкции.
Два правила, которые важнее команд:

- **Упало до публикации** — не опубликовано ничего. Почини причину, влей
  в `main`, сними тег локально и на сервере, повтори с подъёма версии.
- **Упало в середине публикации** — часть пакетов уже в реестре.
  Публикация повторяема: скрипт спрашивает реестр о каждой версии и
  пропускает опубликованные. Перезапусти прогон тем же тегом.

Отката публикации нет. `npm unpublish` работает 72 часа и только пока
версией никто не пользуется. Дальше пара имени и версии занята навсегда,
и правильный ход — выпустить следующую версию, а сломанную пометить
устаревшей.
