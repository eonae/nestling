## Context

Сегодня `makeApp({ config: [[source, target], …] })` объявляет привязки
источников полем декларации. `ConfigInput` — объединение трёх форм
(`ConfigSource | ConfigBinding | ConfigBinding[]`), и приватный `isBinding()`
в `packages/nestling.app/src/config/source.ts` различает их структурой
массива. Читалка `config/reader.ts` дочитывает `process.env` последним шагом
`#lookup()` независимо от того, назвала его декларация или нет, — источник
координат для файловых/сетевых источников тот же: каждый источник сам читает
`process.env` в `init()`. `dotenv()` упомянут в JSDoc трёх пакетов, но нигде
не реализован. `check(args, { config })` уже принимает опцию, заменяющую
привязки целиком, — прецедент, на который опирается это решение;
`assembleTest` останавливается после фазы WIRE, и живому процессу конфиг
передать нечем, поэтому `examples/microservice/e2e/helpers/create-test-app.ts`
пересобирает `makeApp` вручную.

Решение зафиксировано записью
[ideas.md [2026-09-13]](../../../docs/decisions/ideas.md) «Конфигурация:
привязки на `run()`, `env()` и `dotenv()` умолчанием, `bind()`, `needs` у
источника», пп. 1–5, 9–10.

## Goals / Non-Goals

**Goals:**

- Конфигурация не влияет на состав процесса ни синтаксисом, ни семантикой:
  привязки живут на методе, который заводит машину (`run`, `check`,
  `assembleTest`), а не на декларации.
- Одна форма привязки (`bind`) вместо трёх форм `ConfigInput`.
- `process.env` — источник среди источников, а не источник читалки по
  умолчанию с неявным низшим приоритетом:
  герметичность теста с `vars()` гарантирована построением, а не
  соглашением не читать окружение руками.
- Источник, которому нужен путь к файлу (`dotenv`), получает его аргументом
  конструктора, а не чтением `process.env` в `init()`.
- Тестовый корень умеет довести приложение до реального сокета одним
  вызовом (`testApp.run()`), не заставляя e2e-тесты пересобирать `makeApp`
  вручную.

**Non-Goals:**

- `needs` у `ConfigSource`, топологический порядок подъёма источников по
  секциям, `watch`/`retries` источника, сателлит `@nestlingjs/config.vault`
  — change `config-source-needs` (пп. 6–8 записи ideas.md).
- `argv()` как аргумент сборки, уход `RootConfig`/`load()` из примеров —
  change `argv-args`.
- Переименование `assemble` → `build` — независимый change `terminology` в
  отдельной ветке; этот change не трогает имена методов.
- `baseUrl` для транспортов, отличных от HTTP: WS и gRPC не реализованы.

## Decisions

### 1. `keys` привязки по умолчанию `'*'`, а не обязательный таргет

Сегодня таргет (`ConfigKeys` или глоб) — второй, обязательный элемент
кортежа `[source, target]`. Новая форма `bind(source, { keys?, … })` делает
`keys` необязательным полем с умолчанием `'*'`: без него источник отвечает
за любой ключ любой секции — так же, как раньше неявно отвечал
`process.env`, будучи источником читалки с низшим приоритетом. Явный `keys`
остаётся способом сузить
источник до одной секции (`bind(vault(), { keys: db.keys })`) — например,
чтобы тест ограничил `vars()` одной секцией и не спрятал опечатку в имени
чужого ключа предупреждением "не покрыл ни одного ключа" на пустом месте.

**Альтернатива (отвергнута источником решения):** оставить `target`
обязательным — отвергнута тем же принципом, что убрал у `process.env`
неявный низший приоритет: `defaultSources = [bind(env()), bind(dotenv('.env'), {
optional: true })]` не должен перечислять секции, которых декларация не
знает на момент объявления умолчания.

### 2. `baseUrl` — способность листенера, а не поле ядра

`IListener` (`packages/nestling.app/src/transport/interfaces.ts`) сегодня
знает только роль — `listen()`/`drain()` — и не знает протокола: ни адреса,
ни схемы. `HttpServer` (`@nestlingjs/transport.http`) уже отдаёт
`address(): { host, port } | null` поверх `node:http`. Строка `baseUrl`
(`http://host:port`) — знание протокола, которого у ядра нет и не будет
(capability `http-transport-boundary`).

Решение: `IListener` получает необязательный метод `baseUrl?(): string`.
`HttpServer` его реализует поверх уже существующего `address()`; листенеры
без сетевого адреса (будущие CLI/bus-подобные роли) его не реализуют.
`TestApp`/`AssembledApp` не хранят и не форматируют URL сами — они находят
листенер и зовут его `baseUrl()`, либо явно отказывают, если способности
нет.

`testApp.baseUrl(name?: string): string` резолвит листенер так же, как уже
резолвит `assembled.servers.get(name)`:

- без аргумента — если объявлен ровно один сервер, его `baseUrl()`;
  ноль или больше одного сервера — явный отказ, перечисляющий имена
  доступных серверов;
- с аргументом — `servers.get(name)`, отказ с перечнем доступных имён, если
  такого сервера нет;
- сервер найден, но не реализует `baseUrl?()` — явный отказ, а не
  `undefined`: единообразно с остальными «явный отказ вместо магии»
  местами ядра.

Отвечает на открытый вопрос 1 записи ideas.md: форма `baseUrl(name)` вместо
единственного поля, потому что серверов может быть больше одного
(`transports: [http({ port: 3000 }), http({ port: 3001, name: 'admin' })]`),
а неявный выбор «первого» спрятал бы ошибку конфигурации транспортов за
случайно правильным одиночным сервером в большинстве примеров.

**Альтернативы (отвергнуты):**

- Единственное поле `testApp.baseUrl: string` — работает только для одного
  сервера, и сообщение об ошибке «серверов больше одного» пришлось бы
  бросать из геттера без места назвать нужное имя явно.
- `testApp.servers.get(name).baseUrl` полем на `HttpServer` (не методом
  `IListener`) — заставляет вызывающего импортировать `HttpServer` из
  `@nestlingjs/transport.http` и сужать тип `IListener`, хотя `servers`
  типизирован протокол-независимо.

### 3. `check()` без опции `config` поднимает `defaultSources`, не «источники декларации»

`structural-check` сегодня формулирует умолчание как «источники декларации»
— то, что естественно, пока `config:` — поле `makeApp`. После этого change
декларация источников не несёт вовсе, поэтому у `check()` без опции
`config` остаётся один осмысленный источник умолчания — тот же
`defaultSources`, что использует `run()`. Поведение не меняется для
приложений, которые сегодня не объявляют `config:` (большинство): что
раньше читалось из `process.env` неявным источником с низшим приоритетом,
то же самое читается из
`bind(env())` явным элементом умолчания.

## Risks / Trade-offs

- **[Risk]** Изменение затрагивает пять спек (`config-sources-binding`,
  `composition-root`, `test-composition-root`, `structural-check`,
  `health-probes`) и три примера — площадь легко недооценить в одном
  change. → **Mitigation**: `tasks.md` разбивает по пакетам и примерам
  отдельными пунктами; `yarn docs:audit` в Definition of Done ловит
  оставшиеся упоминания поля `config` у `makeApp`.
- **[Risk]** Rebase на `main` после `terminology` (переименование
  `assemble` → `build`) — эта ветка создана до его слияния и держит текущие
  имена. → **Mitigation**: переименование чисто механическое (символ →
  символ), конфликтов по содержанию не даёт; `/opsx:apply` начинается с
  `git rebase main` по правилу CLAUDE.md.
- **[Risk]** `bind()` с умолчанием `keys: '*'` восстанавливает поведение
  «любой источник отвечает за любой ключ», из-за которого сегодняшний
  неявный `process.env` с низшим приоритетом непрозрачен при опечатке в
  имени переменной. →
  **Mitigation**: предупреждение «таргет не покрыл ни одного объявленного
  ключа» (capability `config-sources-binding`, требование про непокрытый
  таргет) остаётся в силе и для `bind(source)` без `keys` — оно не зависит
  от формы привязки, только от пересечения имён.

## Migration Plan

Отдельного шага раскатки нет: библиотека без пользователей в проде.
Старое API (`config:` у `makeApp`, `objectSource` в ядре, три формы
`ConfigInput`) удаляется тем же change'ем, без промежуточного состояния,
где работали бы обе формы.
