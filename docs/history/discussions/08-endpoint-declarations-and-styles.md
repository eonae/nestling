# 08 · Нужен ли функциональный формат? → единая модель endpoint-деклараций

**Дата:** 2026-07-13.
**Формат:** архитектурная сессия по вопросу «многое заточено под формат на
функциях — без классов; не уверен, что он вообще нужен». Аудит кода +
сравнение с конкурентами + эволюция решения в диалоге.
**Итог:** записи в ideas.md [2026-07-13] «Endpoint-декларации: per-transport

## 1. Постановка: вопрос склеивает две оси

«Нужен ли функциональный формат» на деле — два вопроса с противоположными
ответами:

1. **Ядро из значений** (`make*`, токены, `EndpointDefinition`, модули-объекты) —
   не «стиль», а несущая архитектура: фича = значение → `select` = фильтрация
   массива; pipeline = значение → композиция константами и `explain()`; модуль =
   значение → параметризация функцией (смерть `forRoot`); видимость через
   ES-экспорты токенов → kernel/user-space и keys-capability; `overrides` в
   тестах. Даже «классический стиль» в L0–L4 использовал классы только для
   сервисов и endpoints — модули/конфиги/контракты/фичи всюду `make*`.
2. **Обещание двух полных симметричных авторских стилей** (прогрессия L0–L4
   дважды, каждая фича в двух формах) — реальный и вечный налог, уже названный
   в ревью d/06 §6.

## 2. Аудит кода (факты)

- Оба стиля сводятся к одному представлению: провайдеры — к
  `ProviderDefinition` (class/factory — одна ветка if/else в
  `container.builder`), endpoints — к `EndpointDefinition{handle}`
  (`makeEndpoint` — identity-функция ~7 строк), исполняемому единым рантаймом.
- **Классовый путь — обёртка ~600–650 строк** (декораторы, WeakMap-метаданные,
  `IEndpoint`, глобальный реестр, резолв инстансов, class-only lifecycle);
  функциональный — ~130 строк тонких фабрик (он и есть ядро).
- Классовый endpoint держится на **саморегистрации в глобальном `Set` при
  импорте** — паттерне, уже отвергнутом в d/05 §1 (change 8 его убивает).
- **Симметрия сломана в обе стороны**: `App` принимает только классовые
  endpoints (`AppModule.endpoints: Constructor<IEndpoint>[]`); `makeEndpoint`
  живёт только standalone и не покрыт тестами пакетов; `@OnInit`/`@OnDestroy` —
  только у классов, у factory-провайдеров lifecycle-механизма нет.

## 3. Сравнение с конкурентами

| Фреймворк | Форма | DI / lifecycle | Урок |
|---|---|---|---|
| NestJS | классы + legacy-декораторы + reflect-metadata | да / да | боли — причина существования nestling; прикован к `experimentalDecorators`: в стандартных ES-декораторах нет параметр-декораторов — нестовский инжект не переносится в принципе |
| Angular | классы для сервисов, **функции для юнитов** | да / да | естественный эксперимент: class-based guards/interceptors деприкейтили в пользу функциональных, `inject()`, standalone; классы остались сервисам — та же линия ролей |
| Fastify | функции + options | плагины / хуки | крошечное ядро победило без классовой обёртки |
| Hono / Elysia | функции, schema→inference | нет / нет | взрывной рост; ноль архитектуры |
| tRPC / ts-rest / oRPC | процедуры/контракты — значения | нет / нет | типизированный клиент из контракта — драйвер adoption; классовой формы нет ни у кого |
| Effect | всё — значения, включая DI (`Context.Tag`≈токены, `Layer`≈модули) | да / да | доказательство существования + предупреждение о FP-налоге |
| Encore.ts | функции + декларативная инфра | частично | целостный DX без классов |

Урок из фронтенда: Vue Options/Composition и React classes/hooks — «два
равноправных стиля» кончаются расколом экосистемы и одним «рекомендуемым».
**Два симметричных стиля не продал никто.** Дуализм дёшев только на уровне
провайдеров DI (Awilix `asClass`/`asFunction`).

Ключевой технический факт: **декоратор не влияет на типы** (перманентное
свойство TS). Всё продающее в дизайне nestling — schema-first вход/выход,
типизированная `meta` из пайплайна, `Output<T, E>`, контракты — течёт через
вывод типов из значений; классовой декларации это доставалось бы вечной
`implements`-церемонией. Ниша «декларации-значения + настоящий
DI/lifecycle/модульный монолит» — пуста (Hono/tRPC без архитектуры, Nest на
магии, Effect со сменой парадигмы).

## 4. Эволюция решения в диалоге

1. **Первый заход:** сломать симметрию по ролям — endpoints функционально
   (каррированный `handle: (deps) => (input, meta) =>`, `deps`-поле), сервисы —
   классы; декораторные endpoints убрать. Ключевая механика: у endpoint'а два
   момента времени (сборка/запрос) — как конструктор/метод у класса;
   каррирование выражает это честно. Отвергнуты: deps третьим аргументом
   per-call (смешивает singleton-сборку с per-request сигнатурой), service
   locator в meta / `inject()` / ALS (рантайм-резолюция, невидимая в графе),
   endpoint как токен + `factoryProvider` (три артефакта и токен, который
   никто не инжектит).
2. **Сомнение пользователя:** эстетика каррирования непривычна; команда
   переходит с NestJS. Переформулировка: **враг — не классы, а
   класс-как-носитель-метаданных** (декоратор + реестр). Класс как
   *реализация* хендлера легален — механизм уже есть (классы-юниты пайплайна,
   `TNeeds`): класс передаётся полем `handle` в типизированный вызов
   конструктора декларации — проверка типов в точке декларации, без
   `implements`. Итог: три формы `handle` (функция / каррированная фабрика /
   класс), декларация всегда одна. Настоящая цена миграции с Nest — схемы
   вместо DTO-классов, `Ok`/`Fail`, pipeline — одинакова при любой форме
   хендлера; сервисы переносятся почти дословно.
3. **Вопрос о транспорте:** «endpoint уже знает про транспорт?» — да, по
   построению: декларация и есть точка привязки, единственное место, где
   транспортный словарь легален. Этажность: декларация владеет **словарём
   вида** транспорта (не инстансом/конфигом); pipeline и handler —
   транспорт-слепые; контракты — транспорт-нейтральный этаж (нейтральность
   там, где она функциональна: co-located ↔ split). Следствие — **per-transport
   конструкторы** (`httpEndpoint`/`cliEndpoint`/`implement`) вместо generic
   `makeEndpoint({ transport: 'http', pattern })`, где поле притворяется
   нейтральным, а pattern втайне HTTP-шный: типизация path-параметров, канон
   размещения/bind-карта в конструкторе, ссылка на транспорт токеном →
   fail-fast на ASSEMBLE. Один handler на два транспорта = две тонкие
   декларации с общим значением (анти-Nest `ExecutionContext`-маскарад).
4. **Фиксация целевой картинки** (по уточнению «говорим только про целевую»):
   одна система деклараций; декораторы `@Endpoint`/`@HttpEndpoint`,
   `IEndpoint`, endpoint-registry удалены; `endpoints:` модуля принимает
   значения; сервисы — канонично классы; standalone-гарантия в типах
   (`server.route` — только deps-free, симметрично `Pipeline<any, never>`).

## Продолжение (2026-07-13): нужны ли endpoints вообще → контракт первичен

Следующая сессия того же дня довела вопрос до конца: если инлайн-декларация —
это «анонимный контракт + реализация» (d/07 решение 5), не является ли
endpoint вообще лишним первичным понятием?

### Разбор: две роли вместо двух сущностей

За «endpoint» прячутся интерфейс (= контракт) и узел реализации (pipeline +
deps + handle — неустраним ни в какой модели). Вопрос свёлся к тому, всегда
ли узел реализации прикреплён к контракту (иногда анонимному).

### Стресс-тест на неудобных кейсах

| Кейс | Разложение | Что вытащил |
|---|---|---|
| webhook (Stripe) | анонимный контракт (владелец схемы — внешняя система) | нужда в сырых байтах → пометка `rawBody: true`, типизированный стартовый контекст |
| SSE-лента | контракт `kind: request` + `output: events(T)` | валидация биндинга: HTTP умеет, шина v1 — нет → fail-fast на ASSEMBLE |
| multipart | форма `multipart({ fields, files })` во входе | io-декларация = дерево форм, листья — Standard Schema; лимиты файлов enforce'ит транспорт при парсинге |
| CLI-команда | контракт с `cli:`-биндингом | аргумент **за** контракты (тот же `db.migrate` — из CLI, порта, шины); интерактив = стратегия сбора input (`missing: 'prompt'`), диалог = plan/apply |
| статика, catch-all | **не контракт и не endpoint** — сантехника транспорта (конфиг) | третий этаж: escape hatch ниже деклараций |
| NATS wildcard | сантехника NATS-транспорта (наблюдатель паттерна, не операция) | `natsEndpoint` как третье понятие не нужен — тест на прочность пройден |

Ни один кейс не потребовал endpoint как отдельного первичного понятия.

### Итог

Принята онтология «контракт первичен»: контракт (именованный = capability
через экспорт / анонимный = транспортная поверхность) → биндинги
(валидируются против способностей транспорта на ASSEMBLE) → `implement`;
per-transport конструкторы — сахар «анонимный контракт + implement».
Три этажа: сантехника транспорта / контракты / реализации. Три починки
скрипов: `rawBody`-пометка с типовой гарантией, io-формы над Standard Schema,
интерактив как политика CLI-биндинга + паттерн plan/apply.
