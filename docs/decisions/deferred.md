Темы, которые **обсуждались и осознанно отложены**: не приняты (нет записи в
[ideas.md](./ideas.md)), не запланированы (нет change в [roadmap.md](./roadmap.md)),
но уже продуманы. Назначение файла — при возникновении потребности не начинать
с нуля и не переоткрывать уже пройденные развилки.

Открытые вопросы *уже принятых* решений сюда не дублируются — они живут в
соответствующих записях ideas.md (без двойной бухгалтерии). Здесь — только темы,
у которых своей записи в ideas.md нет.

Формат записи: контекст → что уже придумано → почему отложено → триггер возврата.

## [2026-07-13] `header()`: параметры операции в HTTP-заголовках

**Откуда:** обсуждение канонизации HTTP-input — конвенция размещения + bind-карта
([d/06, продолжение](../history/discussions/06-critical-design-review.md)).

**Граница, зафиксированная в обсуждении** (meta vs input для заголовков):

- **ambient / cross-cutting** заголовки (`Authorization`, `traceparent`,
  `X-Request-Id`) — это *контекст* запроса, одинаковый для всех ручек: живут в
  meta/ctx через pre-юниты (`withIdentity` и т. п.), как сейчас. На клиенте
  симметрично: конфигурируются один раз при создании клиента, не аргумент вызова.
- `Accept` / `Content-Type` / `Last-Event-ID` — концерн транспорта
  (content negotiation, SSE-реконнект), до пользователя не доходят вообще.
- **заголовок-«параметр операции»** — клиент обязан передать его осознанно
  per-call, без него вызов не имеет смысла (`If-Match`/expectedVersion для
  оптимистичной блокировки; данные в заголовках внешних контрактов, которые мы
  не контролируем) — кандидат в **input** через пометку
  `header('If-Match', schema)` в bind-карте. Тогда контракт остаётся
  transport-agnostic: на NATS то же поле едет просто в payload, заголовок —
  деталь HTTP-биндинга.

**Почему параметр операции нельзя оставить в meta:** декларация endpoint'а
интроспектируема, pre-юнит — непрозрачная функция. Заголовок, поднятый в meta
pre-юнитом, выпадает из статически выводимого контракта: OpenAPI не узнает об
обязательном заголовке, типизированный клиент не потребует аргумент. Всё, что
клиент передаёт per-call, должно жить в декларации (input + bind).

**Почему отложено:** реальных кейсов мало — правило «бизнес-данные в body/query,
не в кастомных заголовках» в силе; v1 HTTP-канона обходится path/query/body.
Bind-карта аддитивна: добавить `header()` позже — обратно-совместимо
(асимметрия рисков — тот же аргумент, что при отказе от `.after`).

**Триггеры возврата:**

- первый реальный кейс оптимистичной блокировки (`If-Match`) или интеграции с
  внешним API, возящим данные операции в заголовках;
- дизайн типизированного клиента / OpenAPI-генерации, если им понадобится полная
  модель заголовков;
- смежная отложенная под-тема, вернуть вместе: **типизация ответных заголовков**
  в output-декларации (`Location`, `ETag`) — сейчас `Ok.created(value, headers)`
  остаётся нетипизированным обогащением.

## [2026-07-13] Outbox / saga: точка интеграции с портами

**Откуда:** критическое ревью
([d/06 §5](../history/discussions/06-critical-design-review.md)). Дисциплина
портов ([ideas.md, 2026-07-08](./ideas.md)) уже фиксирует: кросс-фичевая
согласованность = события + outbox/saga, не общая транзакция — но точка
интеграции не определена.

**Что уже придумано:**

- **Outbox** — транзакционный emit: событие пишется в БД в одной транзакции с
  бизнес-изменением, отдельный relay доставляет его в шину. Вероятная точка
  интеграции — **не ядро, а satellite-пакет**: обёртка emitter'а поверх
  хранилища + relay-процесс, встроенный в lifecycle (стартует в RUN-фазе,
  корректно гасится на SHUTDOWN). Контрактный API потребителя (`.emit()`)
  не меняется — меняется биндинг на сборке, в духе dispatch-политик.
- **Saga** — уровень приложения поверх `command`/`event`; от фреймворка ей
  нужны идемпотентность (принята, см. [ideas.md, 2026-07-13](./ideas.md)) и
  correlation в meta — отдельного механизма в ядре не предполагается.

**Почему отложено:** нет реального кейса; черта «kernel 1.0» — ядро не тянет
хранилище; дизайн зависит от принятых, но ещё не реализованных вещей (порты,
NATS-транспорт, идемпотентность).

**Триггеры возврата:**

- первый реальный кейс кросс-фичевой согласованности с БД (событие обязано
  выжить при падении после коммита);
- ~~реализация L4/NATS в roadmap — спроектировать relay вместе с
  транспортом~~ — **сработал** 2026-07-31 (change 12 `transport.nats`) и
  сознательно не привёл к решению: транспорт даёт долговечную **доставку**
  (`durable` в контракте), но транзакционный emit остаётся про хранилище, а
  ядро хранилище не тянет. Точка интеграции подтверждена реализацией:
  обёртка эмиттера — обычный провайдер, relay — обычный `@OnStart`-хук,
  правок ядра ни то ни другое не требует;
- запрос transactional emit от пользователей портов.

## [2026-07-14] Health/readiness из фаз lifecycle

**Откуда:** критическое ревью, предложение №8
([d/06](../history/discussions/06-critical-design-review.md)).

**Что уже придумано:**

- Оба сигнала выводимы из фазовой модели без пользовательского кода:
  **readiness** = «процесс дошёл до RUN», **liveness** = «SHUTDOWN не
  начался». Никакой отдельной подсистемы — чтение текущей фазы App.
- Транспортная поверхность (`/healthz`, `/readyz`) — **сантехника
  HTTP-транспорта**, не endpoints: без схем и контрактов, включается
  опцией транспорта.
- Прикладные проверки (БД доступна, очередь жива) — уже спроектированный
  паттерн `IHealthCheck` + `Family.all` (multi-injection, ideas.md
  [2026-07-10]): вклады едут с фичами, состав массива следует за `select`.

**Почему отложено:** аддитивно по построению (опция транспорта + чтение
фазы) — не входит в закрытое breaking-окно фиксации API V1 (ideas.md
[2026-07-14] «Kernel 1.0»); дизайн тривиален после реализации фазовой
модели (change 10).

**Триггеры возврата:** реализация change 10 (`features`, фазы/go-live);
первый k8s-деплой nestling-приложения.

## [2026-07-14] Wire-формат ошибок: RFC 9457 (problem+json)

**Откуда:** критическое ревью, предложение №10
([d/06](../history/discussions/06-critical-design-review.md)).

**Что уже придумано:**

- `ErrorDetails` ложится на RFC 9457 почти один в один: `code` → `type`
  (URI-суффикс), `status` → `status` (через транспортный маппинг),
  `message` → `detail`, `details`/`requestId` → extension members;
  `Content-Type: application/problem+json`.
- Место в архитектуре очевидно: сериализация тела ошибки — **концерн
  HTTP-транспорта** (маппинг `ErrorStatus` → HTTP-статус уже там);
  модель ошибок (Fail, code-идентичность, `E ∪ UnknownError`) не меняется.

**Почему отложено:** чисто аддитивная сериализация — не влияет на
error-model (change 15) и не входит в breaking-окно; решать при реализации
транспортного маппинга ошибок, когда появится формат по умолчанию.

**Триггеры возврата:** реализация change 15 (`error-model`) — выбрать
дефолтный wire-формат; первый внешний потребитель ошибок (типизированный
клиент/OpenAPI-доки), которому нужен стандартный медиатип.

## [2026-07-31] Вариадический `compose(...layers)`

**Откуда:** change 23 `pipeline-type-dx` — переписывание сигнатуры `compose`
на прямой вывод тип-параметров ([roadmap](./roadmap.md), волна 2).

**Что уже придумано:** пока `compose` объявлен через `A extends AnyPipeline`,
вариадическая форма была нереалистична — каждый уровень переразворачивал всю
цепочку. После перехода на прямой вывод (`Pipeline<RA, AA, NA>` в позиции
параметра, накопление прямыми `AA & AB` в возвращаемом типе) variadic tuple
types становятся выполнимыми: `...rest: Pipelines<…>` с накоплением
свёрткой по кортежу. Замеры показали, что дорога именно вложенность, а не
арность: 50 слоёв вложенными вызовами — 64 286 инстанциаций против
476 561 514 до правки ([BUDGET.md](../../packages/nestling.pipeline/type-tests/BUDGET.md)).

**Почему отложено:** снятие потолка в 4 слоя за вызов — **расширение
публичного API**, а change 23 закрывал breaking-окно фиксации API V1.
Расширение аддитивно (перегрузки 2–4 остаются), поэтому спешить незачем;
цена ожидания — ноль.

**Триггеры возврата:** первый реальный композит, которому 4 слоя за вызов
тесны (вложенность работает, но читается хуже); появление слоёв,
собираемых программно (список известен только в рантайме сборки).

## [2026-07-31] Форма типа-ошибки `{ __error; … }` как правило фреймворка

**Откуда:** change 23 `pipeline-type-dx` — форма зафиксирована для pipeline
(точка композиции, pre-тракт) и её единственного существующего потребителя
(слот `pipeline` в `httpEndpoint`).

**Что уже придумано:** словарь формы — `__error` (строковый литерал с
проблемой на естественном языке) + рекорд «имя поля → его тип»
(`missing`, для перезаписи — `conflicting: { поле: [было, стало] }`),
опциональный `hint` там, где подсказка называет конкретное действие.
Инвариант печати: тип-ошибка обязана быть **анонимным развёрнутым литералом
в точке печати** (именованный дженерик-алиас TypeScript печатает именем, и
текст сообщения пропадает) — исполнимая проверка правила — снапшоты в
`packages/nestling.pipeline/type-tests/`.

**Почему отложено:** общее правило на весь фреймворк заводить рано — точек
всего две с половиной. Кандидаты (`endpoint`-словари, `bind`-карта, будущие
`makeContract`/`makeConfig`) приводятся к форме по мере надобности, по
месту.

**Триггеры возврата:** третья независимая подсистема, которой понадобился
свой тип-ошибка (тогда форма фиксируется записью в ideas.md и общим
хелпером в ядре); либо расхождение словарей между уже существующими
точками.

## [2026-07-31] `isOneOf([A, B])` — матчинг юниона определений отказа

**Откуда:** change 15 `error-model` — открытый вопрос design'а: нужен ли
`.catch`-юниту хелпер для разбора нескольких кодов сразу.

**Что уже придумано:** `isOneOf([OrderNotFound, CardDeclined])(res)` —
предикат, сужающий до юниона отказов; форма зеркалит `Definition.is`.

**Почему отложено:** на миграции примеров ни одного `.catch`-юнита,
разбирающего больше одного кода, не появилось — единственный
(`auditDeletions` в `examples.app-with-http`) матчит ровно один отказ.
Хелпер на гипотетическую потребность — лишняя поверхность API; пока
достаточно последовательных `A.is(res)`.

**Триггеры возврата:** первый реальный `.catch`, разбирающий три и более
кода (два ещё читаются цепочкой `if`); либо потребность в таком предикате
у клиента (`makeClient`), где ветвление по коду — основной способ работы
с ответом.

## [2026-07-31] `defineFail` без схемы деталей, но с произвольным `details`

**Откуда:** change 15 `error-model` — открытый вопрос design'а: разрешать
ли `defineFail('X', { status, message })` с нетипизированными деталями в
конструкторе.

**Что уже придумано:** решение — **не разрешать**. Формы ровно две: со
схемой (конструктор принимает детали, валидирует и выводит их тип) и без
неё (конструктор без аргументов). Проверено на миграции: отказы без
осмысленных деталей действительно оформляются как конструктор без
аргументов (`NothingToUpdate()`, `EmptyStdin()`), а всё, у чего детали
есть, схему объявляет — она же нужна OpenAPI (#20) и клиентам (#22).

**Почему отложено:** отложено не решение, а его пересмотр — запись
фиксирует, что вариант рассматривался и отвергнут по schema-first.

**Триггеры возврата:** случай, где детали отказа принципиально
не описываются схемой (например, произвольный payload чужой системы,
пробрасываемый как есть) — тогда нужна форма с `details: unknown` и явным
отказом от валидации, а не молчаливое ослабление правила.

## [2026-07-31] Гранулярность `bytesIn`/`bytesOut` в `summary`

**Откуда:** change 6 `streaming-v2` — открытый вопрос design'а: считать
байты до или после сжатия.

**Что уже придумано:** V1 считает **байты на проводе так, как их видит
транспорт**: HTTP дописывает прочитанное тело и записанные байты ответа.
Сжатия в V1 нет ([transports.md](../design/transports.md) — compression вне
скоупа), поэтому «до» и «после» сейчас совпадают и вопрос не наблюдаем.
Поле опционально (`bytesIn?`/`bytesOut?`) именно для того, чтобы транспорт,
который байтов не знает, ничего не выдумывал.

**Почему отложено:** решать нечего, пока нет второй точки отсчёта.
Выбирать семантику вслепую — значит зафиксировать её до появления
compression-сантехники, которая сама и определит, где стоит счётчик.

**Триггеры возврата:** появление сжатия в HTTP-транспорте (тогда решить:
две пары счётчиков или одна с явно документированной точкой замера);
транспорт, у которого байты и элементы принципиально не совпадают
(бинарный протокол с фреймами).

## [2026-07-31] `events` во входе: клиент льёт поток событий

**Откуда:** change 6 `streaming-v2` — форма `events(T)` объявлена
транспортно нейтральной, но HTTP объявляет её только в `output`.

**Что уже придумано:** механизм формы полностью симметричен — item-цепочки,
поэлементная валидация и счётчики написаны один раз и не знают о слоте.
Отсутствует не поддержка формы, а **способность транспорта**: у HTTP-запроса
нет входного канала с семантикой открытой подписки, и `capabilities.input`
это честно отражает. Значит, включение — это одна строка в capabilities
транспорта, у которого такой канал есть.

**Почему отложено:** нет реального кейса. Кандидат — WebSocket-транспорт,
которого в V1 нет; выдумывать под него семантику заранее — проектировать
без потребителя.

**Триггеры возврата:** появление транспорта с двунаправленным каналом
(WebSocket, gRPC streaming); запрос «клиент шлёт бесконечный поток
телеметрии», который сегодня решается `stream(T)` без семантики подписки.

## [2026-07-31] `throttle` при переполнении: буферизовать или ронять

**Откуда:** change 6 `streaming-v2` — открытый вопрос design'а о поведении
комбинатора, когда источник быстрее заданной частоты.

**Что уже придумано:** V1 **буферизует**: `throttle` растягивает элементы
во времени и не теряет ни одного. Это следствие pull-модели — комбинатор
просто не запрашивает следующий элемент, и backpressure распространяется
на источник сам. Ронять элементы в V1 умеет ровно одно место — `Topic`, и
только по своей явной политике `onSlowConsumer`, где потеря видна в
счётчике `dropped`.

**Почему отложено:** «ронять» имеет смысл только там, где источник
неостановим (push-источник без backpressure), а такой источник в
архитектуре ровно один — `Topic`, и у него политика уже есть. Заводить
второй способ терять данные без потребителя — плодить конфигурацию.

**Триггеры возврата:** push-источник вне `Topic`, который нельзя
притормозить (нативный поток внешней библиотеки); либо реальный кейс, где
буфер `throttle` растёт неограниченно — тогда решать: `sample`-семантика
отдельным комбинатором или опция на самом `throttle`.

## [2026-07-31] Инлайновый пайплайн в позиции аргумента: `TNeeds` схлопывает вывод

**Откуда:** change 6 `streaming-v2` — обнаружено при написании
интеграционных тестов транспорта.

**Что уже придумано:** декларация, созданная **прямо в аргументе**
`transport.route(...)`, получает контекстный тип, фиксирующий `TNeeds =
never` (это и есть гарантия «в транспорт едет только исполнимое»). При этом
TypeScript выводит тип-параметр юнита в цепочке `.finally(...)`/`.pre(...)`
из контекстного возвращаемого типа — и он схлопывается в `never`, а
диагностика читается как «Argument of type '(outcome: any) => void' is not
assignable to parameter of type 'never'». Обходной путь тривиален и
совпадает с каноном: пайплайн — отдельное значение
(`const observing = makePipeline().finally(…)`), как `basePipeline` во всех
примерах.

**Почему отложено:** канонический стиль от этого не страдает — пайплайны
переиспользуются константами по построению ([pipeline.md](../design/pipeline.md)),
и во всех примерах и гайдах инлайновой формы нет. Лечение затрагивает
сигнатуру `ITransport.endpoint`/`route` — то есть публичный API транспорта,
только что зафиксированный; цена — сомнительная ради стиля, который мы не
рекомендуем.

**Триггеры возврата:** третий репорт «непонятная ошибка `never` в
декларации» от пользователя; либо ревизия сигнатуры `endpoint()` по другой
причине (например, `serve(dispatch)` в change 10) — тогда починить заодно.

## [2026-07-31] Автонаследование бюджета вложенным вызовом через ALS

**Откуда:** change 27 `port-deadline-idempotency` — решение D4, зафиксировано
записью [ideas.md [2026-07-31]](./ideas.md) «Порты: бюджет вызова моментом».

**Что уже придумано:** модель gRPC context — вызов, сделанный внутри
обработчика, подхватывает бюджет вызывающего из ALS автоматически, и явная
передача `{ deadline: Ctx(Deadline).peek() }` не нужна. Поле `deadline` в
`meta` уже есть, переменная `Deadline` уже есть, читалка остатка уже есть:
менять пришлось бы **только правило по умолчанию** в вызывателях — «взять
`meta.deadline`, а при его отсутствии посмотреть в ambient-проекцию».

**Почему отложено:** три довода против. Прецедент `signal` — он сегодня
тоже не наследуется (`meta?.signal ?? NEVER_ABORTED`), и два однородных поля
одного конверта не должны жить по разным законам. Требование
`port-invocation`, что ambient-контекст вызывающего не протекает внутрь
реализации: подхват бюджета из ALS вызывающего — ровно протекание. И
`no runtime magic`: «где-то в глубине оборвалось по бюджету, которого я не
задавал» — худший класс диагностики. Явная передача при этом однострочная,
потому что переменная `Deadline` для того и введена.

**Триггеры возврата:** практика покажет, что явная передача шумна —
например, цепочка из трёх и более hop'ов, где каждый обязан протащить
`{ deadline }`, встречается в реальном коде регулярно; либо появление
`propagate` для ambient-переменных (change 12 `transport.nats`) сделает
наследование через провод штатным, и расхождение «по проводу наследуется, в
процессе нет» станет само по себе сюрпризом.

## [2026-07-31] Политика диспатча `balanced` (client-side spill)

**Откуда:** change 12 `transport.nats`. `contracts.md` §3 обещал, что
`balanced` «приедет вместе с настоящей remote-шиной»; шина приехала,
политика — нет, и обещание правится по факту.

**Что уже придумано:** `balanced` — вызов идёт в co-located реализацию,
пока она справляется, и «переливается» на remote-реплики, когда перестаёт.
Единственная политика из трёх, решение которой принимается **на вызове**, а
не на сборке: две другие замыкаются в константу при инстанцировании узла.

**Почему отложено:** решение на вызове требует метрик — насыщенности
локального обработчика, задержек реплик, — которых у транспорта нет и
которые он не должен выдумывать. Заводить политику с решением «по
таймауту» значило бы получить худший вариант обеих: и рантайм-выбор, и
отсутствие данных для него. Плюс `balanced` ломает инвариант «на вызове
выбора не происходит», зафиксированный capability `port-binding`, — а
инвариант этот и есть причина, по которой биндинг вообще читаем.

**Триггеры возврата:** первый реальный кейс, где co-located реализация
насыщается, а remote-реплики простаивают; появление у транспорта источника
метрик (например, вместе с health/readiness из фаз lifecycle) — тогда
станет видно, какие данные политика вправе требовать.

## [2026-08-01] `idempotencyKey` и `deadline` по HTTP

**Откуда:** change 22 `contract-clients`. У портов оба поля `meta` уже есть
и доезжают через NATS; у HTTP-клиента `deadline` работает **только
локально** (fail-fast до отправки и композиция в `AbortSignal`), а
`idempotencyKey` отсутствует вовсе.

**Что уже придумано:** обоим нужен согласованный слот на проводе и его
чтение серверной границей. Кандидаты очевидны — `Idempotency-Key` (черновик
IETF) и относительный timeout заголовком по gRPC-модели, — но выбрать слот
значит зафиксировать его в стороннем контракте: заголовки читают прокси,
шлюзы и логи.

**Почему отложено:** провезти ключ «каким-нибудь заголовком» значит
договориться с самим собой — обе стороны провода наши, и никакой
совместимости такой выбор не даёт. Пока внешнего потребителя
`command`-контракта нет, слот выбирать не на чем; выбранный наугад он
станет обязательством раньше, чем появится требование.

**Триггеры возврата:** первый внешний потребитель `command`-контракта по
HTTP (тогда становится видно, кто чеканит ключ и кто дедуплицирует);
появление ручки, для которой клиентский бюджет обязан обрезать **работу
сервера**, а не только ожидание клиента.

## [2026-08-01] Content-negotiation клиента: не-JSON тела

**Откуда:** change 22 `contract-clients`. `makeClient` говорит только JSON и
отвергает при создании контракт, объявивший `'binary'`/`'text'` в `input`
или `output`, — рядом с потоковыми и multipart-формами.

**Что уже придумано:** тело `'binary'` — это `Content-Type:
application/octet-stream` и `ArrayBuffer` на границе; `'text'` —
`text/plain` и строка. Обе формы уже описаны `mediaTypeOf`, то есть
транспортная сторона правило знает.

**Почему отложено:** непотоковые примитивы соседствуют с потоковыми в одном
вопросе — «что клиент умеет кроме JSON», — и открывать их поштучно значит
трижды возвращаться к сборке запроса и разбору ответа. Дешевле открыть их
вместе со streaming-клиентом, где framing проектируется целиком.

**Триггеры возврата:** проектирование streaming-клиента (NDJSON/SSE) —
первый же его шаг делает не-JSON тела частным случаем; либо ручка, у которой
`'binary'` это весь ответ (выгрузка файла) и обходной путь через обычный
`fetch` перестаёт быть приемлемым.

## [2026-08-01] Типизированный успешный статус декларации

**Откуда:** change 20 `openapi`. Успешный статус ответа объявляется в слоте
`doc.status` (`'CREATED'`, `'NO_CONTENT'`, …), из него генератор выводит код
успешного ответа. Никто не сверяет объявленное с тем, что реально вернул
хендлер: `Ok.created(...)` при `doc: { status: 'OK' }` даст документ,
расходящийся с проводом.

**Что уже придумано:** правильное решение — выразить статус **типом
выхода**, а не полем документации. `Ok.created(...)` и `new Ok(...)` уже
различаются в рантайме (`status` на значении), и различие можно поднять в
тип: `Output<T, E, S extends SuccessStatus = 'OK'>` либо отдельные типы
результата под каждый статус. Тогда `doc.status` перестаёт быть нужен вовсе
— документ читал бы статус из сигнатуры хендлера, как читает схемы.

**Почему отложено:** это трогает `Output`/`Ok` — центральный словарь любого
хендлера, — и потому breaking-изменение фазовой поверхности V1, которое в
change документации не помещается. Ослабление, снижающее цену ожидания:
дефолт (`OK`, а без `output` — `NO_CONTENT`) совпадает с самым частым
случаем, и расхождение видно в первом же вызове ручки.

**Триггеры возврата:** первое расхождение документа с проводом, замеченное
потребителем; либо следующее breaking-окно, если оно откроется по другой
причине — тогда изменение `Output` едет вместе с ним.

## [2026-08-01] Кластерная админ-плоскость подписок

**Откуда:** change 7 `subscriptions-registry`, находка №3 записи
[ideas.md [2026-08-01]](./ideas.md) «Реестр подписок: результат
dogfooding-замера». Реестр node-local: `list()` и `abort()` действуют на
подписки своего процесса. «Покажи все подписки кластера» и «убей подписку
на чужом узле» в V1 невыразимы.

**Что уже придумано:** дело не в реестре, а в **режимах подписки шины**.
Сегодня их два, и оба однополучательные по построению: `request`/`command`
имеют ровно одного владельца, `event` в split-топологии доставляется по
queue-group имени подписчика — то есть одной реплике группы. Нужен третий:
широковещательная подписка **без** группы (каждая реплика получает свою
копию) плюс сбор ответов с окном ожидания (scatter-gather), потому что у
админского запроса ответов столько, сколько узлов, и заранее это число
неизвестно. Наблюдение при этом уже работает кластерно: факты
`subscriptions.opened`/`closed` несут имя узла, и приёмник фактов со
стораджем собирает картину всего кластера без единой новой возможности.

**Почему отложено:** третий режим подписки — это изменение модели доставки,
а не фича одного пакета: он тянет за собой семантику ответа (сколько копий
ждать и сколько ждать по времени), поведение при разъезде реплик и вопрос,
что считать успехом такого вызова. Имитировать его `request`-контрактом
внутри пакета отвергнуто прямо: админ получал бы список подписок случайной
реплики, а молчаливо неверный ответ хуже отсутствующей возможности.

**Триггеры возврата:** первое эксплуатационное требование «убей подписку,
не зная узла» (обходной путь — kill через тот узел, который её показал,
перестаёт работать за балансировщиком без sticky-маршрутизации); либо
появление второго потребителя broadcast-подписки на шине — тогда режим
проектируется под оба сразу, а не под админ-плоскость одну.
