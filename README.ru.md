# Nestling

> TypeScript-фреймворк для бэкенда, написанный агентами. Он служит агенту и
> человеку на равных: сокращает обоим время между «код написан» и
> «известно, верен ли он».

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](https://opensource.org/licenses/MIT)

**[🇬🇧 English version](./README.md)**

## Что это

Nestling собирает приложение из деклараций-значений: endpoint, операция,
пайплайн, фича и модуль объявляются обычными константами. Декларацию читает
компилятор, следом её читает сборка, поэтому ответ «код верен» приходит
раньше первого запроса. Петля обратной связи короткая в трёх местах.

- **Приложение целиком поднимается в одном процессе.** Фича вызывает соседа
  [операцией](./docs/guide/14-features.md), а не по сети: поведение
  проверяется без брокера, контейнеров и развёртывания. Та же декларация
  [разрезается на процессы](./docs/guide/20-split.md), когда это
  понадобится.
- **Ошибка видна при компиляции.** Схема `output` типизирует хендлер,
  список [отказов](./docs/guide/04-errors.md) в декларации endpoint'а
  закрывает возврат незаявленной ошибки, а требования слоя к контексту
  сверяются в точке `compose`.
- **Сборка падает раньше, чем откроется сокет.** Цикл в графе,
  отсутствующая зависимость, endpoint без обязательного слоя и ненайденный
  ключ конфига останавливают старт. Что и когда проверяется, называет
  [таблица проверок](./docs/guarantees.md).
- **Фича проверяется без сервера.** Тестовая сборка `buildTest` проводит ту
  же декларацию по фазам до `WIRE` и
  [останавливается](./docs/guide/08-testing.md): endpoint вызывается через
  тот же пайплайн, но сокет не открывается.

Принципы, по которым принимаются решения, описаны в
[docs/design/principles.md](./docs/design/principles.md).

## Для кого

Фреймворк отвечает на вопросы, которые возникают у приложения в проде: где
проходит граница фичи, как ложится транзакция, что делать с отказом в
контракте, как разнести фичи по процессам. Отвечает он декларациями, и
писать их приходится раньше, чем вопрос станет срочным. Разработчику,
который этих вопросов ещё не задавал, декларации покажутся лишней работой.

Понятия при этом знакомы по другим фреймворкам: модуль, провайдер,
endpoint, пайплайн и слой вокруг хендлера называются здесь так же. Новая
только форма записи: декларация лежит значением, а не собирается из
декораторов при старте.

Nestling не нужен сервису на один процесс, который никто не вызывает
типизированным клиентом и документацию которого никто не читает. Там
декларация остаётся расходом, и такой сервис дешевле написать на Fastify.
Nestling окупается там, где фича переживает переезд в другой процесс, где
вызывающий хочет клиент из контракта и где документ OpenAPI обязан
следовать за кодом.

## Статус

Nestling находится в активной разработке: идёт работа над V1, API меняется.
Используйте в production на свой риск. Требуется Node 24.

## Работа с агентом

```bash
npx @nestlingjs/agent-skill
```

Команда пишет скилл Claude Code в `.claude/skills/nestling/` текущего
проекта. Скилл даёт агенту форму кода на Nestling и правила, которых он не
выведет из привычек NestJS: декларации значениями, явный список
зависимостей, отказы значениями вместо исключений, вызов соседней фичи
операцией. Подробности — в
[`@nestlingjs/agent-skill`](./packages/nestling.agent-skill/).

## Быстрый старт

```bash
npm install @nestlingjs/app @nestlingjs/transport.http zod
```

```typescript
import { makeApp, makeFeature } from '@nestlingjs/app';
import { http, httpEndpoint } from '@nestlingjs/transport.http';
import { z } from 'zod';

// Endpoint — значение: адрес, схемы и хендлер в одном объекте
const GetUser = httpEndpoint.get('/users/:id', {
  input: z.object({ id: z.string() }), // `id` берётся из пути
  output: z.object({ id: z.string(), name: z.string() }),
  handler: async ({ id }) => ({ id, name: 'Alice' }),
});

const UsersFeature = makeFeature({ name: 'users', endpoints: [GetUser] });

const app = makeApp({
  features: [UsersFeature],
  transports: [http({ port: 3000 })],
});

await app.build().run();
```

Приложение отвечает на `GET /users/42`, проверяет вход по схеме `input` и
останавливается по `SIGTERM`. Схема `output` типизирует хендлер и описывает
ответ; тело ответа сверяет с ней типизированный клиент на приёме. Дальше читайте
[гайд](./docs/guide/README.md): он ведёт от этого файла к приложению из
нескольких фич в нескольких процессах.

## Документация

Сайт — **<https://eonae.github.io/nestling/ru/>**; он выкладывается по тегу
релиза и описывает выпущенную версию. Те же тексты лежат в репозитории.
Точка входа — [`docs/README.md`](./docs/README.md): карта папок, список
пакетов и правила ведения документации. Папка определяет статус документа:

- [`docs/guide/`](./docs/guide/README.md) — гайд по текущему API; оглавление
  называет все главы, части, которые они образуют, и пример, с которым
  сверена каждая глава;
- [`docs/design/`](./docs/design/README.md) — целевое состояние V1, полное
  описание API;
- [`docs/decisions/`](./docs/decisions/ideas.md) — журнал решений: что, когда
  и почему;
- [`docs/guarantees.md`](./docs/guarantees.md) — что проверяется до первого
  запроса: таблица проверок, момента срабатывания и главы, где проверка
  вводится;
- [`docs/glossary.md`](./docs/glossary.md) — термины и правила их написания;
- [`docs/releases/`](./docs/releases/README.md) — заметки о выпусках: что
  изменилось в версии, код до и после.

Публикуемый текст существует парой: английский перевод лежит в `docs/en/`,
README пакета — в `README.md` рядом с русским `README.ru.md`. Правило
раскладки — раздел «Два языка» файла [`docs/README.md`](./docs/README.md).

Актуальное состояние кода описывают README пакетов.

## Разработка

```bash
yarn install
yarn verify          # build + typecheck + lint + test по всем пакетам
yarn verify:strict   # проверка собранных деклараций; перед выпуском
yarn docs:audit      # проверка консистентности документации
yarn docs:build      # сборка HTML-сайта документации
yarn docs:dev        # локальный сервер сайта с пересборкой при правке
yarn pack:check      # установка тарболов в проект вне репозитория
```

Монорепозиторий на Yarn workspaces и Nx: пакеты лежат в `packages/`,
примеры в `examples/`, документация в `docs/`.

Выпуск версии — [RELEASING.md](./RELEASING.md): версию поднимает человек,
публикует GitHub Actions по тегу.
