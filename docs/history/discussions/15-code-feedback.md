## 1. Prometheus-экспортёр живёт в коде примера

**Файл:** `examples/split-nats/src/metrics.ts`

**Оценка пользователя:** «полное безобразие».

**Суть:** экспортёр метрик (формат экспозиции Prometheus, endpoint `/metrics`,
агрегация счётчиков и гистограмм) написан прямо в приложении-примере. Прикладной
код не должен реализовывать транспорт метрик.

**Что не оспаривается:** адаптеру, возможно, не место в ядре — ядро не знает,
куда уходят числа.

**Чего не хватает:** отдельного пакета — `metrics.prometheus` или подобного, —
который даёт готовый экспортёр и endpoint. Приложение должно подключать пакет,
а не писать `render()`, экранирование меток и суффиксы `_count`/`_sum` у себя.

**Что сейчас в файле (для сверки):** `MetricsExporter` (расширяет `Metrics`
из `@nestlingjs/app` методом `render`), токен `MetricsExporter$`,
`prometheusExporter()` c Map'ами счётчиков и гистограмм, `metricsPlugin(exporter)`
с `httpEndpoint.get('/metrics', { output: 'text', detached: ... })`.
Комментарий в шапке файла прямо декларирует «адаптер живёт в примере, а не в
ядре» и объясняет это проверкой публичной границы — то есть текущее положение
дел зафиксировано намеренно, и фидбэк спорит именно с этим решением.

## 3. Хелперы `int`/`flag` — в `@nestlingjs/models`

**Цитата:** «Хелперы типа int/flag — выносим в @nestlingjs/models
(models.zod правильно имя ))».

**Суть:** минимальные Standard-Schema-значения, продублированные по пакетам,
должны жить в одном месте — в `@nestlingjs/models`.

**Факт в коде:** `export const int` / `export const flag` скопированы трижды —
`packages/nestling.drizzle.pg/src/schema.ts:49,84`,
`packages/nestling.inbox/src/schema.ts:33,68`,
`packages/nestling.outbox/src/schema.ts:34,69`. Все три — `StandardSchemaV1` с
`vendor: 'nestling'`, без zod; шапка файла прямо объясняет дублирование
(«не библиотека схем», пакету не нужен вендор).

**Про имя (толкование, проверить при сверке):** сегодняшний
`@nestlingjs/models` — zod-based (описание пакета: «Модели входных и выходных
данных на zod»). Ремарка «models.zod правильно имя» читается как переименование
текущего пакета в `@nestlingjs/models.zod` — по образцу `@nestlingjs/schema.zod` —
и освобождение вендор-нейтрального имени `@nestlingjs/models` под такие хелперы.

## 4. Открытый вопрос: чейнинг валидаций у `int`/`flag`

**Вопрос пользователя:** «а их можно чейнить дальше будет? Добавлять валидации?»

**Факт:** нельзя. Хелперы возвращают литерал `StandardSchemaV1` — объект с одним
`validate`. Standard Schema не описывает комбинаторов, наращивать нечего.
Давление уже проступило в сигнатуре: `int(fallback, min)` — граница `min`
затащена позиционным аргументом; следующими просятся `max`, `multipleOf`.

**Варианты (обсуждались, решения нет):**
1. fluent-билдер `int(0).min(1)` — фактически своя библиотека схем;
2. один комбинатор `refine(schema, predicate, message)`:
   Standard Schema → Standard Schema, композиция без fluent-API (рекомендация);
3. оставить как есть: нужна валидация сложнее — вендор (zod) в своей секции
   (сегодняшний задокументированный ответ в шапке `schema.ts`).

**Связано с записью 3:** если хелперы переезжают в `@nestlingjs/models`, этот
вопрос решается там же — публичный API пакета определит, есть чейнинг или нет.

## 5. Решение: `int`/`flag` — в `models.zod`, на zod, возвращают zod-билдер

**Цитата:** «не это сложно. Давай мы просто не будем пытаться делать это на
уровне схемы. Пусть это будет в models.zod просто и сделано на zod и возвращать
zod-билдер».

**Решение.** Вариант с собственным `refine`/`pipe` над Standard Schema отклонён
как сложный. Хелперы переезжают в `@nestlingjs/models.zod`, пишутся на zod 4 и
возвращают открытый билдер — чейнинг родной:
`int() = z.coerce.number().int()`, `flag() = z.union([z.boolean(), z.stringbool()])`.
Умолчание навешивает вызывающий и обязательно последним:
`int().min(1).max(10_000).default(500)`.

**Что это закрывает:** запись 4 (открытый вопрос о чейнинге) — чейнинг есть,
своей библиотеки схем не появляется. Дублирование `int`/`flag` в трёх пакетах
(`inbox`, `outbox`, `drizzle.pg`) уходит.

**Два следствия, требующие работы:**
1. Обработка пустой строки переезжает в читалку конфигурации
   (`packages/nestling.app/src/config/reader.ts`): `''` от источника — «пропускаю
   ход», как `undefined`. `z.coerce.number()` превратил бы `''` в `0` и умолчание
   бы не сработало. Место правильное: свойство окружения, а не числа.
2. `inbox`, `outbox`, `drizzle.pg` садятся на zod в peer-зависимостях. Тезис из
   шапки нынешнего `schema.ts` — «пакету не нужен ни zod, ни valibot, приложение
   не обязано выбирать того же вендора» — перестаёт действовать и должен уйти из
   документации. Ядро остаётся на Standard Schema.

## 6. Вопрос: даёт ли вендор-нейтральность реальный выигрыш

**Вопрос пользователя:** «может, желание не тащить zod и остаться на Standard
Schema — это всё только усложняет? А может ли быть реальный выигрыш?»

**Ответ (мой, решения пользователя пока нет).** Выигрыш реальный, но у правила
есть граница — она проходит по стыку с пользовательским кодом.

- **Схему пишет пользователь** (endpoints, модели, его секции конфигурации):
  нейтральность почти бесплатна, ядро только вызывает `validate`. Покупается:
  фреймворк не диктует валидатор (отличие от NestJS с `class-validator`), мажор
  zod не тянет мажор фреймворка, ядро тестируется схемами-пустышками. Оставить.
- **Ядру нужен JSON Schema** (openapi, mcp, cli): цена — конвертер на вендора,
  уже уплачена (`SchemaDocConverter` с полем `vendor`, пакет `schema.zod`, явная
  регистрация). Оговорка: обещание «любой вендор» выполнено наполовину —
  приложение на valibot валидирует, но OpenAPI не получит без `schema.valibot`.
- **Схему пишем мы сами** (секции `inbox`, `outbox`, `drizzle.pg`): выигрыш
  нулевой — пользователь эти схемы не пишет и не подменяет. Платится тремя
  копиями `int`/`flag`, отсутствием чейнинга, невозможностью механически
  задокументировать конфигурацию (вендор `'nestling'` не знает ни один
  конвертер) и своими сообщениями об ошибках.

**Правило, предложенное к записи:** нейтральны там, где схему пишет пользователь;
на вендоре там, где схему пишем мы.

**Связано:** подтверждает запись 5. Следствие то же — тезис «пакету не нужен ни
zod, ни valibot» из шапки `schema.ts` должен уйти, а не переехать в смягчённом
виде.

## 7. РЕШЕНИЕ: пользователю — выбор схемы, себе — zod

**Цитата:** «Пользователю сервиса мы даём выбор схемы. Но сами тоже делаем выбор
и этот выбор — zod».

**Правило.** Публичная граница остаётся на Standard Schema: приложение пишет
схемы на чём хочет, ядро только вызывает `validate`. Внутри фреймворка вендор
выбран — zod. Где схему пишем мы, пишем её на zod и не изобретаем нейтральных
заменителей.

**Что из этого следует (список к сверке с роадмапом):**
1. `@nestlingjs/models.zod` — новый дом хелперов, `int()`/`flag()` на zod,
   возвращают открытый билдер (запись 5).
2. Удаляются `packages/nestling.{inbox,outbox,drizzle.pg}/src/schema.ts`
   целиком — три копии `int`/`flag`; секции переезжают на билдеры zod.
3. zod уходит в peer-зависимости `inbox`, `outbox`, `drizzle.pg`.
4. Обработка пустой строки переезжает в читалку конфигурации
   (`packages/nestling.app/src/config/reader.ts`).
5. Секции конфигурации становятся конвертируемыми в JSON Schema штатным
   `schema.zod` — открывается механическая документация конфигурации.
6. Документация: тезис «пакету не нужен ни zod, ни valibot» уходит; правило
   «нейтральны на границе с пользователем, на вендоре внутри» записывается
   в `design/` и `decisions/`.
7. Открытый вопрос на сверку: как правило ложится на `@nestlingjs/models`
   (zod-based) и предложенное переименование в `models.zod` (запись 3).

## 8. `models.zod` — витрина удобств для пользователей zod, без навязывания

**Цитата:** «Для пользователей zod все удобства в пакете models.zod
предоставляем. Но никому не навязываем».

**Уточнение к записи 7.** `@nestlingjs/models.zod` — не только внутренний дом
хелперов, но и публичный пакет удобств: кто выбрал zod, ставит его и получает
готовое (`int()`, `flag()` и всё, что нарастёт дальше). Кто выбрал другого
вендора — не ставит и ничего не теряет из ядра: публичная граница остаётся на
Standard Schema.

**Где проходит граница (поправка пользователя).** Завязывается именно **ядро** —
там, где валидация нужна ему самому: свои секции конфигурации, внутренние
проверки. Не завязывается **API ядра**: типы и сигнатуры, которые видит
приложение, остаются на Standard Schema, и `models.zod` в них не упоминается.

**Чем это ограничивает дизайн:**
- `models.zod` может стоять в зависимостях ядра — это реализация, а не контракт;
- ни один публичный тип, параметр или возвращаемое значение ядра не назван через
  zod: приложение на другом вендоре собирается и работает, ничего не устанавливая
  дополнительно;
- удобства складываются в этот пакет, а не расползаются по ядру и транспортам;
- зависимость пакетов фреймворка от zod (запись 7, пункт 3) — наш выбор
  реализации, а не требование к приложению; формулировать в документации нужно
  именно так.

**К сверке:** соотношение трёх пакетов — `models` (сегодня zod-based),
`models.zod` и `schema.zod` (конвертер в JSON Schema). Границы между ними и
итоговые имена — открытый вопрос из записи 3.

## 9. Имена транспортов и лишний элемент в `transports:`

**Код:** `examples/app-with-http/src/app.ts:96-107` — `transports: [api, http({ server: api }), mcp({ server: api, ... })]`, где `api = httpServer()` (строка 78).

1. **Переименование: `http` → `rest`, `httpServer` → `http`.** Сокетом владеет
   сервер — он и есть `http`. Протокол поверх него — `rest`. Сегодняшняя пара
   имён (`api` для сервера, `http` для протокольного транспорта) названа задом
   наперёд.
   Цепочка, которую это тянет (к сверке): пакет `@nestlingjs/transport.http`,
   токен `HttpTransport$`, `httpEndpoint.get(...)`, `httpProbes()`, секция
   конфигурации `HTTP_PORT`/`HTTP_HOST`. Секция как раз встаёт на место:
   она принадлежит серверу, а сервер после переименования и есть `http`.
   Отдельный вопрос — probes и `/metrics`: они по-прежнему HTTP, но не REST.

2. **Сервер не должен перечисляться в `transports:`.** Желание сформулировано,
   механизм — нет («надо подумать»). Сейчас в списке три элемента, из которых
   один не протокол, а владелец сокета; в примере с одним протоколом
   (`examples/users-service/src/app.ts:56`) сервер вообще не упоминается —
   `transports: [http()]` поднимает его сам. Непоследовательность видна глазом.

**Предложение по пункту 2 (моё, решения нет):** сервер — значение-декларация,
и транспорт уже держит на него ссылку полем `server`. Сборщику достаточно
собрать серверы транзитивно из деклараций транспортов и развернуть их как узлы,
с дедупликацией по ссылке. Тогда `transports:` перечисляет только протоколы:
`transports: [rest({ server: api }), mcp({ server: api })]`, а `api = http()`
остаётся обычной переменной модуля. Это тот же приём, которым фичи затягивают
провайдеры: транзитивный сбор деклараций, никакой магии в рантайме. Сервер без
единого транспорта при этом просто не создаётся — и это правильно.

## 10. `as` в пользовательском коде: экстракторы подписок

**Код:** `examples/app-with-http/src/app.ts` — `appSubscriptions = subscriptions({ identity: (ctx) => (ctx.input as { requestId?: string }).requestId, ... })`.

**Оценка пользователя:** «очень плохо, что здесь есть `as`».

**Почему он там появился.** Экстрактор типизован общим контекстом:
`SubscriptionContext = ExtendableContext<AnyInput>`
(`packages/nestling.subscriptions/src/registry.ts:32`), а
`AnyInput = Record<string, unknown>`
(`packages/nestling.operations/src/io/io.ts:145`). Реестр объявляет, что
«конкретный input ему безразличен», и перекладывает приведение на приложение.
Приложение знает форму — но выразить её негде, поэтому пишет `as`.

**Масштаб.** Это не единичная строка примера: тот же `as` стоит в JSDoc-примере
пакета (`packages/nestling.subscriptions/src/module.ts:54`) и в спеках
(`registry.spec.ts:99,115`). То есть приведение сегодня — рекомендованный
способ, а не недосмотр примера.

**Что это нарушает:** «guarantee over convention» — `as` отключает проверку,
и расхождение формы всплывёт в рантайме молча (`requestId` станет `undefined`).

**Направление (моё, решения нет):** реестру нужен параметр типа —
`subscriptions<TInput>({...})` с `identity: (ctx: ExtendableContext<TInput>) => ...`,
где `TInput` называет приложение (или он выводится из общей формы контекста
приложения). Реестру знать конкретный input по-прежнему не нужно: он хранит
результат экстрактора, а не сам input. К сверке: где приложение берёт этот тип —
объявляет руками или получает из деклараций.

## 11. Именование переключателей: предикатами

**Код:** `examples/app-with-http/src/app.ts` — `export const Docs = makeSwitch('docs', { default: 'on' })`, далее `Docs.when(appOpenapi)`.

**Предложение пользователя:** называть переключатели предикатами —
`DocsEnabled.when(...)`. «Готов обсудить, но кажется это правильно».

**Оценка (моя): правильно, но ровно для двухпозиционных.** В API переключателей
две формы (`packages/nestling.container/src/switches/types.ts`):
- `ToggleSwitch` — значения `'on' | 'off'`, есть сокращение `when(items)`;
- `Switch` со словарём значений (`makeSwitch('storage', ['s3','local'])`) —
  только `pick({ s3: …, local: … })`.

Предикат читается там, где есть `when`: `DocsEnabled.when(appOpenapi)` —
«когда документация включена». Для многозначного переключателя предиката нет:
`Storage`, `Tier` называют измерение, а не условие, и `Storage.pick({...})`
существительным читается верно. Правило, годное к записи: **toggle — предикат,
многозначный — существительное-измерение.**

**Что не меняется:** строковое имя переключателя (`'docs'`) и аргумент сборки
`APP_DOCS=on|off`. Переименовывается переменная модуля, не ключ окружения:
«включённость» несёт значение, а не ключ.

**К сверке:** где живёт правило — `docs/design/` плюс, возможно, правило
`@nestlingjs/eslint-plugin`; и надо пройти все примеры и гайды (`Docs`,
`Debug` в type-test'ах и др.).

## 12. `openapiOptions` вынесены в общий экспорт — и сам скрипт `src/openapi.ts`

**Код:** `examples/app-with-http/src/app.ts` — `export const openapiOptions: OpenApiOptions = { info: {...}, converters: [zodConverter()] }`, который читают плагин `openapi({...openapiOptions})`, транспорт `mcp({ converters: openapiOptions.converters })` и скрипт `examples/app-with-http/src/openapi.ts`.

**Оценка пользователя:** «необходимость вот там объявлять — это ужас прямо.
Что это за скрипт такой?»

**Что за скрипт.** `examples/app-with-http/src/openapi.ts` — генерация
`openapi.json` для CI без подъёма приложения: `app.discover(args)` раскрывает
состав (ветки переключателей, выбор фич) на фазе 0, дальше чистая функция
`buildOpenApiDocument(endpoints, openapiOptions)` и `writeFileSync`.
Запуск — `yarn workspace @examples/app-with-http openapi [args]`
(`package.json:14`). То есть это ручной CLI, написанный приложением, потому что
фреймворк такого не даёт.

**Две проблемы, разделить их при сверке:**
1. **Опции подняты в общий экспорт**, чтобы их видели три потребителя.
   Причина — `buildOpenApiDocument` требует опции отдельным аргументом, хотя те
   же опции уже объявлены плагином `openapi()` внутри приложения. Декларация
   есть, но добраться до неё из результата `discover()` нельзя, поэтому
   приложение держит опции снаружи и передаёт дважды.
   **Направление:** документ строится из результата `discover()` вместе с
   опциями объявленного плагина — `app.discover(args).openapi()` или
   `buildOpenApiDocument(discovery)`. Тогда `openapiOptions` не нужен как
   отдельное значение, а `info` живёт ровно в одном месте.
2. **Скрипт генерации — заготовка фреймворка, а не код приложения.** Пятнадцать
   строк `argv` + `writeFileSync` + `console.log` одинаковы у всех. Просится
   штатная команда (`nestling openapi [args] > openapi.json`) или метод корня.

**Связь с решением 7 (внутри — zod):** `converters: [zodConverter()]` перестаёт
быть обязательной церемонией. Раз вендор выбран, конвертер zod может быть
умолчанием, а явный список — способом его переопределить. Это снимает и
дублирование `converters` в `mcp({...})`. Прежнее решение об
обязательном явном конвертере отменено — см. запись 14.

## 13. Суффикс `Switch` в именах переключателей — обсуждение (к записи 11)

**Вопрос пользователя:** «Может, по свичам тогда надо суффикс `Switch`?»

**Варианты:** `DocsEnabled` (предикат), `DocsSwitch` (суффикс),
`DocsEnabledSwitch` (оба), сигил по образцу токенов (`$` занят токенами).

**Оценка (моя): суффикс не нужен, предикат из записи 11 остаётся.** Разбор по
местам вызова:
- `DocsEnabled.when(appOpenapi)` — «когда документация включена»; читается лучше
  всего;
- `DocsSwitch.when(appOpenapi)` — «когда переключатель docs»: суффикс занял
  место условия и ничего не сказал;
- `Storage.pick({ s3, local })` — «выбери по storage»; `StorageSwitch.pick(...)`
  повторяет то, что уже сказал `pick`.

Вид значения на месте вызова уже назван методом (`when`/`pick`) и полем корня
`switches: [...]`. Токенам `$` нужен потому, что токен и его значение живут
рядом и путаются; у переключателя такого двойника нет.

**Аргумент за суффикс, единственный весомый:** механическая проверка. Правило
`@nestlingjs/eslint-plugin` умеет проверить суффикс и не умеет — «предикат ли
это имя». Если правило именования хочется автоматизировать, суффикс выигрывает;
если хватает ревью и примеров — выигрывает читаемость.

**Итог к сверке:** решение за пользователем; моя рекомендация — предикат для
двухпозиционных, существительное-измерение для многозначных, без суффикса.

## 14. РЕШЕНИЕ: прежнее решение про явный конвертер отменено

**Цитата:** «забей уже на это решение, я его перепринял только что».

**Что отменяется.** Правило из шапки `packages/nestling.schema.zod/src/index.ts`:
«реестра „вендор → конвертер“ нет ни у одного из них: список конвертеров — это
данные вызывающего, и даже в стопроцентно-zod приложении конвертер называется
явно одной строкой. Цена explicit over implicit посчитана в журнале решений и
принята».

**Что действует вместо.** Раз вендор фреймворка — zod (запись 7), конвертер zod
работает умолчанием. Явный список `converters` остаётся способом добавить или
заменить конвертер, а не обязательной строкой.

**Следствия к сверке:**
1. `converters: [zodConverter()]` уходит из `openapi({...})`, `mcp({...})` и из
   `openapiOptions` примера — вместе с полем `converters` в общем экспорте
   (запись 12);
2. переписать шапку `packages/nestling.schema.zod/src/index.ts`;
3. в `docs/decisions/` добавить запись, отменяющую прежнюю (журнал не
   переписывается, отмена оформляется новой записью);
4. проверить, откуда берётся конвертер-умолчание, чтобы `@nestlingjs/openapi`
   не стал жёстко зависеть от zod в обход правила «API ядра не завязано»
   (запись 8): умолчание — это зависимость реализации, а не типа.

## 16. Префикс `app` у плагинов

**Код:** `examples/app-with-http/src/app.ts:81-93` — `plugins: [appObservability, appAuth, appSubscriptions, httpProbes(), Docs.when(appOpenapi)]`.

**Оценка пользователя:** «не понимаю, зачем к плагинам мы добавляем префикс
`app` везде».

**Причина (она не смысловая, а техническая).** Каждое имя уже занято соседом:
- `appObservability` — потому что `observability` это **слой**
  (`examples/app-with-http/src/plugins/observability/index.ts:5-6` экспортирует
  оба);
- `appAuth` — потому что рядом слой `authed` и фабрика; сам плагин зовётся
  `'app-auth'`;
- `appSubscriptions`, `appOpenapi` — потому что `subscriptions` и `openapi` это
  импортированные **фабрики** пакетов.

То есть `app` не значит ничего: это способ разойтись с занятым именем.
Читатель же видит систему там, где её нет.

**Три направления (моё, решения нет):**
1. **Слои — причастия, плагины — существительные.** У auth так уже сделано
   наполовину: слой `authed`, плагин можно звать `auth`. Тогда у наблюдаемости
   слой `observed`, плагин `observability`.
2. **Фабрики пакетов — `make*`.** Проект уже держит `makePlugin`, `makeSwitch`,
   `makeConfig`, `makeToken`, `makeApp`, а плагины и транспорты экспортируются
   голыми существительными (`subscriptions()`, `openapi()`, `http()`, `mcp()`) —
   и занимают имя, которое нужно приложению. `makeSubscriptions({...})`
   освобождает `subscriptions` под экземпляр. Пункт большой: затрагивает все
   пакеты с фабриками.
3. **Суффикс `Plugin`** (`authPlugin`, `openapiPlugin`) — если первые два не
   проходят. Слабее: поле `plugins: [...]` уже называет вид значения (тот же
   довод, что в записи 13 против суффикса `Switch`).

**К сверке:** пункт 2 пересекается с переименованием транспортов из записи 9
(`http`→`rest`, `httpServer`→`http`) — решать одним заходом.

## 17. Направление по записи 16 одобрено

**Цитата:** «Да, разумно звучит» — на три направления из записи 16.

**Принято как направление** (не как готовая спецификация):
1. префикс `app` у плагинов уходит;
2. слои называются причастиями, плагины — существительными: `authed` / `auth`,

**Объём к сверке:** пункт 3 задевает все пакеты с фабриками и делается одним

## 18. РЕШЕНИЕ: суффикс `Plugin` у экземпляров плагинов

**Цитата:** «А что думаешь насчёт варианта с суффиксом plugin? Мне кажется в
данном случае это разумно».

**Согласие (моё, с исправлением рассуждения записи 16).** Критерий из записи 13:
суффикс оправдан там, где у имени есть двойник. У переключателя двойника нет —
у плагина есть, и не один: слой (`observability`), фабрика пакета

ради которой токенам дали `$`. Довод «поле `plugins: [...]` уже называет вид»
слабый: экземпляр живёт и в импортах между модулями, и в `Docs.when(...)`, и в

- пункт 3 (`make*` для фабрик пакетов) перестаёт быть обязательным: он был нужен
  ради освобождения занятого имени, а суффикс решает это локально. Вопрос
  остаётся, но как отдельный — про консистентность API пакетов;
- пункт 2 упрощается: выдуманные причастия не нужны, слой остаётся
  `observability`, `authed` остаётся как есть;
- инлайновые вызовы (`httpProbes()`) суффикса не получают: суффикс у
  именованных значений.

## 19. Суффикс `Layer` у слоёв — и правило «значение называет свой вид»

**Цитата:** «Честно говоря, я бы и слоям сделал бы суффикс layer...»

**Согласие (моё).** Вместе с записью 18 складывается одно правило вместо набора
приёмов: **значение-декларация называет свой вид.** В проекте это уже есть
наполовину — фичи `UsersFeature`, `QuotasFeature`, `OpsFeature`; токены `$`.

освобождается под папку и понятие — сегодня за него дерутся слой и плагин.

**Форма имени:** основа существительным, не причастием — `authLayer`, а не

## 21. Логгер вне приложения и pino-сателлит

**Вопрос пользователя:** «почему не могут? В чём проблема сконструировать логгер
самостоятельно? И кстати нам нужен внутри логгер на основе pino, консольный. Или
не внутри, а сателлитом. Как кстати думаешь?»

**Поправка к записи 20.** «Нечем» — неточно. Мешает не отсутствие возможности, а
приватность реализации по решению: интерфейс `Logger` публичный, а единственная
реализация `ConsoleLogger` — нет. Скрипт волен написать свой объект под
интерфейс, но делать это в каждом скрипте — работа на пустом месте.

**Предложение (моё):** открыть фабрику `makeConsoleLogger(options): Logger`,
класс оставить приватным. Интерфейс уже публичный, опция `makeApp({ logger })`
уже есть.

**pino — сателлитом `@nestlingjs/logger.pino`** с экспортом
`pinoLogger(options): Logger`. Доводы:
1. `makeApp({ logger })` — готовый шов; сателлит подключается без правок ядра;
2. ядро остаётся без зависимостей, а `ConsoleLogger` уже знает специфику
   фреймворка: пишет в `stderr` (у CLI-транспорта `stdout` занят результатом
   команды), подхватывает `ambientRequestId`/`ambientTraceId`;
3. мажоры pino ходят своим календарём — довод, принятый для `schema.zod`;
   решение 7 его здесь не отменяет: ядру схемы нужны самому, а логгер у него
   уже есть;
4. pino тянет транспорты, worker threads и `pino-pretty` в dev — платить этим
   во всех приложениях незачем.

**Триггер к пересмотру:** если `ConsoleLogger` начнёт обрастать тем, что у pino
уже есть (redaction, сериализаторы, семплирование, асинхронные назначения), —
дешевле сделать pino умолчанием внутри и удалить свой.

**Решение пользователя по сателлиту пока не дано.**

## 22. Вынос интерфейса логгера в отдельный сателлит

**Вопрос пользователя:** «не стоит ли интерфейс логгера вынести в отдельный
сателлит, чтобы можно было наш pino-логгер использовать где-то, не затягивая
весь app?»

**Ответ (мой): стоит, по схеме `models` / `models.zod`.**
- `@nestlingjs/logger` — `Logger`, `Fields`, `LogLevel`, `LogMethod`,
  `makeConsoleLogger`. Зависимостей нет (интерфейс — 67 строк,
  `packages/nestling.app/src/logger/interface.ts`).
- `@nestlingjs/app` зависит от него и реэкспортирует тип.
- `@nestlingjs/logger.pino` зависит только от него.
- Токены `Logger$`, `RootLogger$` **не выносятся**: им нужен
  `@nestlingjs/container`, и вне Nestling-приложения они бессмысленны.

Формально общий пакет для совместимости не обязателен — TypeScript структурен,
и своё объявление `Logger` подошло бы в `makeApp({ logger })`. Довод за вынос —
расхождение двух объявлений при первой правке, а не невозможность.

**Дефект, вскрывшийся по дороге (важнее самого выноса).** Шов
`makeApp({ logger })` неполный: `ConsoleLogger` штампует `requestId`/`traceId`
через `ambientRequestId()`/`ambientTraceId()`
(`packages/nestling.app/src/pipeline/core/context/reader.ts:173,201`), а они не
экспортируются ни из одного пакета. Внешний логгер корреляцию проставить не
может — подменённый логгер молча оказывается хуже штатного.

**Как чинить (предложение):** не экспортировать ambient-функции, а перенести
штамповку в ядро — корень оборачивает переданный логгер декоратором, который
подмешивает ambient-поля на каждой записи. Любая реализация получает корреляцию
даром и не знает внутренностей `app`; `makeConsoleLogger` становится честно
нулевым по зависимостям.

**Порядок работ:** декоратор корреляции в ядре → вынос `@nestlingjs/logger` →
`@nestlingjs/logger.pino` сателлитом.

## 23. Расширяемый перечень ambient-полей логгера

**Согласовано пользователем:** записи 21 и 22 целиком («согласен по всем
пунктам»). **Требование:** перечень ambient-полей, которые логгер приложения
добавляет к записи, должен быть расширяем.

**Предложение (моё):** декларация-значение `logFields` — список ключей
контекста, а не колбэк.

```ts
makeApp({
  logger: pinoLogger(),
  logFields: [RequestId, Trace, TenantId, logField(Caller, 'user')],
});
```

Декоратор корреляции (запись 22) идёт по списку и читает значения из
ambient-ячейки тем же чтением, что сегодня `ambientRequestId()`, но по
объявленным ключам. `requestId` и `traceId` перестают быть особым случаем —
становятся умолчанием списка.

**Четыре свойства к фиксации:**
1. **Объявляет и плагин, не только корень.** `route` нужен транспорту, `spanId` —
   трассировке, `subscriptionId` — реестру подписок. Поле `logFields` в
   `makePlugin({...})` собирается жадно при сборке, как провайдеры и endpoint'ы.
   Иначе приложение перечисляет чужие ключи руками.
2. **Переименование явным хелпером.** Умолчание — имя ключа (`RequestId.key` →
   `requestId`), `logField(Caller, 'user')` даёт другое: имена полей в логе не
   должны диктоваться внутренними именами ключей.
3. **Конфликт имён — отказ на ASSEMBLE**, не молчаливая перезапись. Два пакета
   с полем `id` — ошибка состава, видимая до открытия сокета.
4. **Отсутствующее значение поле не ставит** — ключа в записи просто нет.

**Не через этот механизм:** статические поля (`node`, `version`, `env`) — это
`logger.child({...})` при создании.

**Выигрыш:** `ambientRequestId`/`ambientTraceId` остаются внутренними навсегда —
автор пакета объявляет ключ и кладёт его в список, а не лезет в читалку

## 24. РЕШЕНИЕ: опция `logging`, pino умолчанием, `ConsoleLogger` удаляется

**Цитата:** «опцию logging. pinoLogger — по умолчанию (пусть app зависит от
@nestlingjs/logging.pino, но есть возможность переопределить), всё по аналогии
с zod. ConsoleLogger — убираем вообще».

**Согласие (моё).** Это то же решение, что по zod (запись 7), и одно правило
лучше двух. Свой логгер на 321 строку (`packages/nestling.app/src/logger/console.ts`)
держится не качеством, а нежеланием зависимости.

**Имена (расходились в записи 22, берём вариант пользователя):**
`@nestlingjs/logging` — интерфейс, `@nestlingjs/logging.pino` — реализация,
опция корня — `logging`.

**Форма опции (предложение; убирает отдельный `logFields` из записи 23):**
```ts
makeApp({
  logging: {
    logger: pinoLogger({ level: 'debug' }),  // умолчание — он же
    fields: [RequestId, Trace, TenantId],
  },
});
```

**Пять пунктов, решаемых до реализации:**
1. **Поток вывода.** Сегодня записи идут в `stderr` намеренно: у CLI-транспорта
   `stdout` занят результатом команды (`console.ts:5`). pino пишет в `stdout` —
   `pinoLogger` обязан быть на `pino.destination(2)`.
2. **Человекочитаемый вывод — сегодня умолчание** (`format: 'text'`,
   `config.ts:71`; JSON включают явно). У pino наоборот. `pino-pretty` не брать:
   это transport на worker-thread, а примеры собираются одним бандлом через
   esbuild. Вместо него `logging.pino` отдаёт свой синхронный writer с тем же
   форматом `<время> УРОВЕНЬ scope сообщение key=value` (~30 строк). Иначе
   «убрали ConsoleLogger» обернётся «в dev теперь JSON».
3. **Фаза 0.** Корневой логгер создаётся до контейнера (`makeKernelLogger`),
   значит `logging.pino` — обычная `dependency` пакета `app`, и её платят все,
   включая переопределивших логгер. Та же цена, что с zod; назвать её в
   документации.
4. **Секция `nestlingLog`** переезжает на опции pino: `format` выбирает
   назначение из пункта 2, `level` идёт как есть. Уровни у нас
   `debug|info|warn|error`, у pino шире (`trace`, `fatal`) — решить, расширяем ли
   словарь.
5. **Тестовый корень.** `@nestlingjs/testing` поднимает `level: 'silent'` по
   умолчанию, иначе прогон спеков зальёт вывод.

**Отменяет:** выбор «сателлит, ядро без зависимости» из записи 21 (пункты 1-4
там). Декоратор корреляции и вынос интерфейса из записи 22 остаются в силе.

## 25. Вопрос: опциональный пир для pino

**Вопрос пользователя:** «сможем сделать зависимость от pino опциональным пиром,
чтобы тот, кто захочет от него избавиться, мог не ставить пакет?»

**Ответ (мой): объявить можно, толку нет.** `peerDependenciesMeta.pino.optional`
yarn поддерживает. Но пакет с необязательной зависимостью не имеет права
импортировать её статически — падение происходит при загрузке модуля, до всякой
проверки опций. Значит умолчание надо резолвить лениво, а корневой логгер
создаётся **синхронно** на фазе 0 (`makeKernelLogger`), до контейнера: `await
import()` туда не вставить. Остаётся `createRequire(import.meta.url)('pino')` —
работает (pino 10.3.1 это CJS, `main: pino.js`), но:
- esbuild сквозь `createRequire` не видит: pino не попадёт в бандл и будет
  искаться в `node_modules` в рантайме. Примеры собираются одним файлом
  (`examples/*/esbuild.config.js`, `bundle: true`) — в тонком контейнере такой
  бандл упадёт на старте;
- «зависимость, которая может быть, а может не быть, выясняется в рантайме» —
  это no runtime magic наоборот.

**Два честных варианта вместо опционального пира:**
- **A. pino умолчанием, обычная зависимость `app`.** Ноль конфигурации, бандл
  статический, одно поведение у всех; переопределивший логгер всё равно несёт
  пакет. Совпадает с решением по zod, включая умолчание-конвертер (запись 15).
- **B. `app` не зависит от `logging.pino`.** Приложение пишет
  `logging: { logger: pinoLogger() }` одной строкой, в ядре остаётся писатель на
  ~30 строк умолчанием — не `ConsoleLogger`, а то самое форматирование из
  пункта 2 записи 24. «Не ставить pino» работает буквально.

**Рекомендация:** A — ради одного правила с zod. Если возможность выкинуть pino
важна по-настоящему — B; опциональный пир не даёт ни того, ни другого.
**Решение пользователя не дано.**

## 28. Условный спред: короткая запись вместо тернарника с `{}`

**Желание пользователя:** вместо `...(options.httpPort === undefined ? {} : { config: [...] })`
писать `...(options.httpPort && { config: [...] })`. «Может линтер есть на это
или написать свой».

**Важно: `&&` здесь менять поведение.** `options.httpPort && {...}` роняет поле
на `0`, а `HTTP_PORT: 0` в Node значит «дай свободный порт» и используется в
репозитории повсеместно — `packages/nestling.mcp/src/app.integration.spec.ts:87`,
`packages/nestling.transport.http/src/provider.spec.ts:76` и ещё десяток мест.
То же с пустой строкой для хоста. Замена «в лоб» тихо сломает ровно тот случай,
ради которого значение и передают.

**Короткая запись с сохранением гарантии:**
```ts
...(options.httpPort !== undefined && {
  config: [[objectSource({ HTTP_PORT: String(options.httpPort) }), httpServerKeys()]],
}),
```
Одна строка вместо пяти. Компиляция обеих форм под `--strict
--exactOptionalPropertyTypes` проверена — проходит.

**Готового правила нет** (проверено прогоном фрагмента):
`unicorn/prefer-logical-operator-over-ternary`, `consistent-empty-array-spread`,
`no-useless-spread` (unicorn 55) не срабатывают — они про `foo ? foo : bar`.

**Предложение: своё правило в `@nestlingjs/eslint-plugin`** (там уже три правила
со спеками), двустороннее:
1. `...(test ? {} : obj)` → `...(!test && obj)`, `...(test ? obj : {})` →
   `...(test && obj)`. Автофикс **только** если тест булев синтаксически
   (сравнение, `!x`, `Boolean(x)`, их комбинации); иначе сообщение без фикса.
2. `...(x && obj)` с небулевым по форме `x` — предупреждение с подсказкой
   `x !== undefined`. Эта половина ценнее: ловит ловушку с `0` и `''`.

**Масштаб:** паттерн `? {}` встречается 174 раза в `packages/*/src` и
`examples/*/src`.

**Что написано с точки зрения конфига (ответ на вопрос).** Три сущности:
1. `objectSource({ HTTP_PORT: '0' })` — **источник**: объект с `get(key)`;

3. пара `[источник, таргет]` — **привязка**: источник отвечает только за ключи

1. `String(options.httpPort)` не нужен: `ConfigSource.get` возвращает `unknown`,

2. Секция `http` уже написана на zod с чейнингом
   (`z.coerce.number().int().min(0).max(65_535).default(3000)`,

   тесту, и знает имя ключа чужого пакета. Соседний пример делает иначе:

   Опция `httpPort` в `DeclareOptions` лишняя — тест мог бы передавать готовую

## 30. Что такое `objectSource` и зачем он в ядре

**Вопрос пользователя:** «а зачем вообще objectSource — что это за источник
такой?»

**Факт.** Единственная реализация `ConfigSource` во всём репозитории
(`packages/nestling.app/src/config/source.ts:158`): объект в памяти с `get`,
`set`, `assign`, `watch`. Ввода-вывода нет.

**Три роли, в JSDoc названы две:**
1. тестовый двойник — значения без `process.env`, не мешая параллельным тестам;
2. **единственный способ отдать значения, уже лежащие в памяти**: порт,
   вычисленный при объявлении, секрет от родительского процесса, аргумент
   командной строки. Это не тестовая надобность, и в JSDoc она не упомянута;
3. минимальный пример интерфейса для читателя доков; он же демонстрирует
   `watch` — `set`/`assign` дёргают подписчиков и перепроецируют
   reloadable-секции.

**Почему в ядре, если «готовые источники живут пакетами».** Граница проходит
ровно: `objectSource` — источник без I/O, настраивать нечего; всё, что добавил
бы сателлит, — это ввод-вывод (файл, Vault, Consul). Правило точнее звучит так:
**в ядре — источник в памяти, в пакетах — источники с вводом-выводом.**

**Два наблюдения:**
- имя описывает реализацию, а не роль: ближе `values(...)` или `inline(...)`;
- **`dotenv(...)` из примеров JSDoc не существует** — встречается в
  `packages/nestling.transport.http/src/config.ts:35-36`,
  `packages/nestling.drizzle.pg/src/plugin.ts:192`,
  `packages/nestling.transport.nats/src/transport.ts:876`, но такой функции в
  репозитории нет. Читалка сама падает в `process.env` в конце цепочки, так что
  жить можно, но примеры обещают несуществующий API.

## 31. ДИСКУССИЯ: где живут источники конфигурации

**Позиция пользователя:** приложение читает конфиг из общей сумки переменных;
внутри — встроенный источник env; на уровне app можно добавлять источники и
биндить на них ключи. Но **переопределение источников — задача тестов**, и
тестового кода в `app.ts` быть не должно; может быть, источники принимать на
фазе assemble.

**Что уже есть (распутывание).** `@nestlingjs/testing` даёт ровно этот механизм:
`assembleTest(app, { args, config, overrides, stubs })`, где `config` **заменяет
привязки декларации целиком**, плюс `vars({...})` — именованный объектный
источник (`packages/nestling.testing/src/config.ts`). Тестового кода в `app.ts`
для этого не нужно.

**Дыра.** Тестовый корень останавливается после WIRE: сокет не открывается,
`run()` не идёт. Тестам с живым процессом (split-развёртывание на два узла, e2e
по HTTP) остаётся `app.assemble(args)`, куда конфиг передать нечем. Отсюда обе
кривые конструкции — `httpPort` в `DeclareOptions` (`examples/split-nats/src/app.ts`)
и `create-test-app.ts` (`examples/app-with-http/e2e/helpers/`), пересобирающий
`makeApp` из `app.spec.*`. Это один обход одной дыры, а не два решения.

**Предложенная линия (моя):** секция — свойство приложения (какие ключи, какие
схемы); привязка — свойство процесса (откуда значения). Значит привязки
переезжают в сборку:
```ts
await app.assemble(args, { config: [[dotenv('.env'), httpServerKeys()]] }).run(); // бой
await app.assemble(args, { config: vars({ HTTP_PORT: 0 }) }).run();               // тест
```
`discover()` и `check()` получают тот же второй аргумент. `create-test-app.ts`
исчезает целиком.

**Про встроенный env — сделан не так.** `process.env` не источник, а безусловный
хвост читалки: `reader.ts:86` держит живую ссылку, `reader.ts:289` читает её
последней и всегда. Следствие: тест с `vars({...})` **не герметичен** — ключ,
отсутствующий в `vars`, приедет из окружения машины. Сделать env обычным
источником `env()`: умолчание сборки `[[env(), '*']]`, тест его не включает.
Заодно из диагностики уходит особый элемент `'process.env'` в списке источников.

**Два вопроса пользователю (ответа пока нет):**
1. привязки на `assemble` — **заменяют** объявленные или добавляются? Моя
   позиция: заменяют; два уровня привязок с приоритетами не отлаживаются. Если
   декларация вообще перестаёт их принимать — вопрос снимается;
2. герметичность теста — по умолчанию или по требованию? Моя позиция: тестовый
   корень по умолчанию без `env()`.

## 32. ДИСКУССИЯ (продолжение): куда приходит конфиг, env-источник, argv

**Вопросы пользователя:** «assemble? Или run? И может быть дать опцию run
тестовому приложению, чтобы его можно было запустить с оверрайдами? env должен
быть источником, как все. Файловые источники с конфигурируемым путём сюда не
ложатся — такие параметры я бы принимал через argv, а они идут до всего
остального». Плюс: «а зачем check'у и discover конфиг?»

**ПРИНЦИП (формулировка пользователя, принят):** опции сборки влияют на состав
приложения, конфиг — не влияет никогда. Переключатели приходят аргументом сборки
(`APP_DOCS`), фичи — им же, значения секций доезжают до узлов на INIT.

**Кому конфиг на самом деле нужен:**
- **`discover()` не читает его вообще**: `discoverEndpoints(resolveComposition(this.spec, args).bundles)`
  (`app.ts:360`) — чистая функция от декларации и аргумента сборки, `#bootstrap`
  не зовётся;
- **`check()` принимает его как глушилку ввода-вывода**, а не как настройку:
  проверка идёт по фазам 0–1, фаза 0 поднимает источники, и без подмены она
  полезет в настоящий Vault или `.env` машины («с `config: vars({ … })` проверка
  обходится без источников», `app.ts:637-638`). Плюс на этих фазах валидируются
  секции;
- **`run()`** — единственный, кому значения нужны по существу.

**1. Конфиг принимает тот глагол, который заводит машину — `run()`, не
`assemble()`.** Технически возможны оба: источники поднимаются в `#bootstrap()`
внутри `run()` (`app.ts:568`), а `assemble(args)` только запоминает аргумент. Но
вешать конфиг на `assemble` — утверждать синтаксисом, что он участвует в составе,
то есть ровно против принципа. Форма:
```ts
app.assemble(args)                  // состав процесса
   .run({ config: [[env(), '*']] }) // откуда значения — свойство запуска
```
Симметрично: `run()` в бою, `assembleTest(...)` в тесте (идёт по фазам 0–3,
значения нужны до INIT), `check(args, { config })` в проверке. Опасение «а если
позвать `run()` дважды» снимается: он идемпотентен (`app.ts:561`, флаг
`#started`).

**Привязки заменяют объявленные, а не добавляются к ним** — по прецеденту:
`check()` и тестовый шов уже заменяют привязки декларации целиком
(`app.ts:636-641`). Это ответ на вопрос 1 записи 31.

**2. `run()` у тестового приложения — да, это закрывает дыру записи 31.**
Тестовый шов уже идёт по фазам 0–3 и встаёт перед START, `#announce()` и
установкой сигналов (`app.ts:708-711`): ресурсы захвачены, сокет не открыт.
Продолжение до LISTEN:
```ts
await using app = await assembleTest(declared, { config: vars({ HTTP_PORT: 0 }) });
await app.run();
app.baseUrl;
```
После этого `create-test-app.ts` удаляется целиком, `httpPort` уходит из
`DeclareOptions`.

**3. env источником — согласие.** Следствия: из диагностики уходит особый хвост
`'process.env'` (`reader.ts:190-192`); тестовый корень без `env()` герметичен по
построению, а не по обещанию.

**4. argv и координаты источников — предлагаю дальше, чем прозвучало.** Сегодня
контракт: «свои координаты источник берёт из первичного `process.env` в `init()`»
(`source.ts:12-16`). Убрать этот специальный случай: источник ничего не добывает
сам, координаты приходят аргументами — `dotenv(path)`, `vault({ addr, token })`.
Тогда «argv идут до всего остального» — не свойство фреймворка, а порядок строк
в `main.ts`:
```ts
const { config: path } = parseArgv(process.argv);
app.assemble(args).run({ config: [[dotenv(path), '*'], [env(), '*']] });
```
Фаза «до фазы 0» не нужна, приоритет виден глазами. `init()` у источника
остаётся, но честно только под ввод-вывод.

**5. К записи в design отдельной строкой:** документ OpenAPI и матрица топологий
не зависят от окружения — раз состав решает только аргумент сборки, документ из
CI гарантированно тот же, что у процесса с тем же аргументом. Сегодня верно по
факту, но гарантией нигде не названо.

**Открытый пункт:** аргумент сборки (выбор фич, переключатели) сегодня приходит
строкой «аргумент бинарника или переменная окружения» — argv уже кормит
`assemble`. Не пора ли аргумент сборки и координаты источников читать одним
разбором argv в `main.ts` вместо двух разных путей.

## 33. Путь к файлу источника: bootstrap-параметр, а не конфиг

**Вопрос пользователя:** «как быть с нюансом про путь к файлу источника?»
(продолжение пункта 4 записи 32).

**Ответ (мой): три отдельных вопроса, все решаются без механизма во фреймворке.**

**1. Кто разбирает argv — никто во фреймворке.** В Node 24 есть штатный
`util.parseArgs`, ноль зависимостей:
```ts
import { parseArgs } from 'node:util';

const { values } = parseArgs({
  options: { config: { type: 'string' }, select: { type: 'string' } },
  strict: false,
});
const path = values.config ?? process.env.CONFIG_FILE ?? '.env';

await app.assemble(values.select)
         .run({ config: [[dotenv(path), '*'], [env(), '*']] });
```
Видны оба приоритета: источников (список сверху вниз) и bootstrap-параметров
(`??` слева направо). Фаза «до фазы 0» не нужна — это обычный код точки входа.

**2. Путь из окружения — можно.** Правило «только читалка трогает `process.env`»
про **ядро**; `main.ts` — composition root процесса, ему положено знать, из чего
процесс собран. Важно, что чтение открыто и видно одной строкой, а не спрятано
в `init()` источника. Именно это и уходит из контракта `source.ts:12-16`.

**3. Файла нет — правило по тому, спрашивали ли его поимённо:**
- `dotenv()` без аргумента (умолчание `.env`): файла нет — **источник пропускает
  ход**, читалка идёт дальше. В контейнере `.env` отсутствует всегда, падать
  нельзя;
- `dotenv(path)` с явным путём: файла нет или не читается — **отказ на фазе 0** с
  путём в сообщении. Назвали явно — значит рассчитывают.

Это «guarantee over convention»: умолчание мягкое, явное требование жёсткое.

**Правило к записи в документации:** путь к файлу источника **не может быть
ключом секции конфигурации** — замыкание: чтобы прочитать путь, нужно прочитать
файл по этому пути. Bootstrap-параметр живёт вне конфига: argv, окружение или
константа. Фреймворку это нужно запретить и объяснить почему.

**В тестах вопрос не возникает:** argv не разбирается, файлов нет,
`run({ config: vars({...}) })`.

## 34. Источник, которому нужна настройка, — не источник, а ресурс графа

**Реплика пользователя:** «я вообще не хочу ничего брать из окружения. Только
args и конфиг... получается, что такой источник конфигурации не будет на самом
деле конфигом, а будет обычным провайдером (или ресурсом), да?»

**ОТМЕНЕНО записью 35** в части критерия («нужен I/O → ресурс»); сценарий
Vault как источника конфигурации пользователь подтвердил. Ниже — исходный
разбор, он нужен для истории рассуждения.

**Разбор (устаревший критерий).** Источник живёт на фазе 0, когда графа ещё
нет, — значит он не вправе требовать ничего, кроме литералов и аргумента сборки.
Всё, чему нужен клиент, учётные данные, повторы или значения из самого конфига,
— **ресурс в графе**, а не источник.

**Что остаётся источниками:** `vars({...})`/`inline({...})` (литерал),
`dotenv(path)` (путь из argv или константа; локальный файл не требует ни
секретов, ни сети), `env()` — если решим оставить его объявляемым.

**Что перестаёт быть источником:** Vault, Consul, AWS Parameter Store. Секрет не
обязан притворяться ключом секции — он приходит портом (`Secrets$`), обычным
узлом графа, и потребитель объявляет зависимость, а не ключ. Порядок соблюдается
сам: пул БД зависит от `Secrets$`, значит на INIT секреты захватываются раньше
пула. Особой фазы не нужно — граф уже упорядочивает ресурсы по зависимостям.

**Гарантия, которая из этого выпадает:** **фаза 0 не ходит в сеть.** До
построения графа читаются argv, литералы и, возможно, локальный файл; всё
сетевое — на INIT, под теми же правилами, что брокер или БД, с внятным отказом и
`release` на остановке. Сегодня не так: «источник поднимает соединение в
`init()`» прямо предусмотрено интерфейсом (`source.ts:38`).

**Интерфейс `ConfigSource`:** `init()` остаётся (чтение файла — тоже I/O),
`watch()` остаётся (файл меняется); уходит описание «свои координаты источник
берёт из первичного `process.env`» вместе с самой возможностью иметь координаты
сложнее пути.

**Требует формулировки пользователя.** «Ничего не брать из окружения» читаю как
**ядро не читает `process.env` само** — ни хвостом читалки, ни в `init()`
источников; хочешь окружение — объяви `env()` в списке. Более жёсткое прочтение
(`env()` не существует вовсе, переменные окружения не источник конфигурации ни в
каком виде) — другое решение и заметно радикальнее: контейнерные развёртывания
живут именно на переменных окружения.

## 35. Vault — это конфигурация: `.env` локально, Vault на стендах

**Требование пользователя:** «Vault — это конфигурация. Хочу локально брать
конфиг из `.env`, а на стендах — из Vault. Такой сценарий хочу поддерживать».

**Критерий записи 34 отозван.** «Нужен ввод-вывод → значит ресурс» отсекает то,
что отсекать не надо. **Правильная граница — чем значение является, а не как
добывается:**
- **источник конфигурации** отдаёт значения для **объявленных ключей**: набор
  ключей известен заранее, значения проецируются в секции на фазе 0, схемы их
  валидируют. Vault попадает сюда целиком: KV-путь → ключи → секции;
- **ресурс графа** — всё со своей жизнью во время работы: клиент с повторами,
  выдача коротких кредов на запрос, поток фича-флагов. Это поведение, а не ключи.

**Сценарий не требует нового механизма** — ветка в `main.ts`:
```ts
const sources = values.vault
  ? [[vault({ addr: values.vault, tokenFile: values.vaultToken }), '*']]
  : [[dotenv('.env'), '*']];

await app.assemble(values.select).run({ config: sources });
```
Обе половины перечислены в одном месте; никакого угадывания по `NODE_ENV`.

**Отозвана гарантия «фаза 0 не ходит в сеть»** (запись 34). Остаётся слабее, но
полезнее: **на фазе 0 случается ровно тот ввод-вывод, который перечислен в
`config:`** — весь он виден в одной строке `main.ts`, а не прячется по пакетам.

**Что нужно добавить фреймворку, раз сеть на фазе 0 узаконена:**
1. **таймаут подъёма источников** — недоступный Vault не должен подвешивать
   процесс; отказ с именем источника и адресом. Сейчас `init()` не ограничен;
2. **отказ с указанием источника** — список источников в диагностике есть
   (`reader.ts:190`), отказ фазы 0 должен называть, какой не поднялся;
3. **`close()` на источниках при остановке** — в интерфейсе есть, но с сетевым
   источником перестаёт быть формальностью.

**Правило, которое выживает и остаётся главным:** координаты источника не берутся
из конфигурации, которую этот источник наполняет. Только argv, литерал или
локальный файл.

## 36. Ступенчатое чтение конфига: источник как потребитель секции

**Ход мысли пользователя:** «мне нравилась концепция, что в assemble идут только
аргументы сборки; токен Vault — не аргумент сборки. А что если ввести механизм
зависимости между значениями (или секциями) конфига, чтобы задать порядок чтения:
путь и токен Vault прочитать из dotenv, а за остальным идти в Vault? Не годится —
эти параметры нужны источнику, а не секции…»

**Про assemble расхождения нет:** по записи 32 конфиг уже уехал в `run()`, токен
в аргументы сборки не попадает.

**Идея отвергнута на шаг раньше, чем следовало (моя позиция).** Параметры нужны
источнику, но **живут в секции**: `VAULT_ADDR`/`VAULT_TOKEN` — такие же ключи со
схемой, как `HTTP_PORT`. Разница лишь в том, что их потребитель — не узел графа,
а следующий источник. Отдельного «механизма зависимости между значениями» не
нужно: порядок уже задан списком.

```ts
const VaultConfig = makeConfig('vault', { addr: z.url(), token: z.string().min(1) });

await app.assemble(values.select).run({
  config: [
    [dotenv('.env'), '*'],                    // ступень 1
    [fromSection(VaultConfig, vault), '*'],   // ступень 2: координаты из секции ступени 1
  ],
});
```

**ИСПРАВЛЕНО записью 37:** утверждение «порядок задаёт и приоритет, и
очерёдность чтения, и это один смысл» неверно — сценарий записи 35 их разводит.
Порядок означает приоритет; очерёдность чтения выводится из зависимостей.

**Что делает читалка:** поднимает источники без зависимостей → проецирует секцию
`vault` (обычная валидация схемой: кривой адрес — обычный отказ конфигурации) →
строит отложенный источник фабрикой и поднимает → идёт дальше по списку.

**Главное правило становится проверкой, а не соглашением:** отложенный источник
может зависеть только от секции, **полностью покрытой источниками выше него**;
не покрыта — отказ на фазе 0 с перечнем недостающих ключей. Замыкание невозможно
по построению.

**Цена:** одно новое понятие в ядре — привязка, чей источник задан парой «секция
+ фабрика». Окупается: иначе координаты Vault тащатся через argv, то есть через
командную строку стенда и CI-секреты, а так лежат там же, где остальная
конфигурация стенда.

**К решению:** `fromSection` — общая обёртка ядра (любой источник становится
отложенным даром) или каждый сетевой источник экспортирует свою форму
(`vault.fromSection(VaultConfig)`). Моя позиция — общая обёртка: источников будет
несколько, механика одна.

## 37. Форма объявления источников: `bind(...)`, зависимость на самом источнике

**Реплика пользователя:** «`vault.fromSection` читается чуть лучше. Может, это
просто должна быть реализация интерфейса? Вопрос в том, как на что влияет порядок
источников. И может быть не массив массивов, а массив объектов — или функция
`source`, возвращающая объект? Может, из такой формы ещё что-то полезное
извлечётся?»

**1. Обёртка не нужна — зависимость объявляется на источнике.**
```ts
interface ConfigSource {
  get(key: string): unknown;
  readonly needs?: ConfigDeclaration;                 // секция, без которой не поднимется
  init?(values: Infer<this['needs']>): void | Promise<void>;  // значения уже провалидированы
}
```
`vault(VaultConfig)` — обычный источник, зависимость видна на значении, а не
внутри `init()`; проверка «секция покрыта источниками выше» остаётся статической.

**2. Порядок — только приоритет (исправление записи 36).** В записи 36 я написал,
что список задаёт и приоритет, и очерёдность чтения, «и это один смысл». Неверно:
сценарий записи 35 их разводит — на стенде Vault должен **перебивать** `.env`, но
**читается после** него, потому что берёт оттуда координаты. Значит: **порядок =
приоритет; очерёдность чтения выводится из `needs` топологической сортировкой**;
цикл обнаруживается до всякого I/O и даёт отказ с именами источников.

**3. Объектная форма убирает узел в ядре.** Сегодня
`ConfigInput = ConfigSource | ConfigBinding | readonly ConfigBinding[]`, а
`isBinding()` определяет форму, обнюхивая массив
(`Array.isArray(v) && v.length === 2 && typeof v[0]?.get === 'function'`,
`source.ts:64-68`). С единственной формой «массив привязок» исчезают и
`toBindings()`, и обнюхивание.

**Имя:** `bind`, а не `source` — функция строит **привязку**, источник ей
передают. `source(dotenv(...))` называет аргумент, `bind(dotenv(...))` — результат.

**4. Что вытаскивается из объектной формы:**
- **`optional: true`** — источник не поднялся (нет файла, недоступен Vault):
  пропускаем ход вместо отказа. Чище правила из записи 33 («`dotenv()` прощает,
  `dotenv(path)` не прощает»): разница переезжает из двух поведений конструктора
  в одно видимое поле привязки;
- **`timeout`** — граница ввода-вывода фазы 0; закрывает пункт 1 записи 35.

Кандидаты на отдельное обсуждение: `name` (сегодня имя живёт на источнике —
`objectSource(values, 'vars')`, хотя один источник можно привязать дважды и
различать их надо по привязке) и `watch: false` (источник читается, но не
инициирует перепроекцию reloadable-секций).

**Итоговая форма:**
```ts
config: [
  bind(vault(VaultConfig), { keys: '*', timeout: 3000 }),
  bind(dotenv('.env'), { keys: '*', optional: true }),
]
```

## 38. Ветка про конфигурацию закрыта в этом состоянии

**Цитата:** «Ок.. давай пока так».

Договорённости записей 31–37 приняты как рабочее состояние, дальше не
углубляемся. Что зафиксировано по конфигурации:
- конфиг принимает `run()` (и `assembleTest`, `check`), не `assemble` — состав
  решает только аргумент сборки (32);
- тестовому приложению нужен `run()`, после чего `create-test-app.ts` и
  `httpPort` в декларации исчезают (32);
- env — обычный источник, ядро само `process.env` не читает (32);
- координаты источника не берутся из конфигурации, которую он наполняет (34, 35);
- Vault — источник конфигурации, сценарий «локально `.env`, на стендах Vault»
  поддерживается (35);
- источник объявляет зависимость от секции полем `needs`, значения приходят в
  `init()` (37);
- порядок в списке = приоритет; очерёдность чтения выводится из `needs` (37);
- форма — `bind(источник, { keys, optional, timeout })`, три формы `ConfigInput`
  схлопываются в одну (37).
