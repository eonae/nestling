# @nestling/app

Composition root приложения Nestling. `makeApp(spec)` объявляет
приложение значением, `app.assemble(select)` собирает его для этого
процесса, а `run()` строит DI-контейнер, находит endpoint'ы проходом по
фичам и плагинам, проводит приложение по фазам жизненного цикла и
корректно останавливает его по `SIGTERM`/`SIGINT`.

> 🚧 Активная разработка, API меняется. Целевой дизайн:
> [`docs/design/composition.md`](../../docs/design/composition.md).
> Гайды: [глава 12. Выделить вторую область](../../docs/guide/12-features.md) (фазы, фичи,
> `select`) и [глава 5. Хендлеру нужен репозиторий](../../docs/guide/05-repository.md).

## Установка

```bash
npm install @nestling/app @nestling/container @nestling/pipeline
```

Транспорт устанавливается отдельно: `@nestling/transport.http`,
`@nestling/transport.cli` или `@nestling/transport.nats`.

## Минимальный пример

```typescript
// app.ts — чем приложение является
import { makeApp } from '@nestling/app';
import { http } from '@nestling/transport.http';

export const app = makeApp({
  features: [UsersFeature],
  plugins: [appLogging],
  transports: [http({ port: 3000 })],   // объявление экземпляра, не инстанс
});

// main.ts — что запускает этот процесс
await app.assemble().run();
```

## Словарь декларации

`makeApp` принимает объект с семью полями. Каждое поле опционально;
других полей нет.

| Поле | Что это |
|---|---|
| `features` | фичи приложения (`makeFeature`); подмножество выбирает аргумент `assemble` |
| `plugins` | сквозная инфраструктура (`makePlugin`); подключена всегда |
| `providers` | провайдеры корня, для которых не нужна отдельная единица |
| `transports` | объявления экземпляров: `http()`, `cli()`, `nats({ name })` |
| `intercom` | имя транспорта, переносящего операции между процессами |
| `config` | привязки источников конфигурации к ключам |
| `policies` | инварианты, которые проверяются на собранном графе |

Сквозная инфраструктура (логирование, метрики, документация) объявляется
плагином и перечисляется в `plugins:`. Подмена узлов графа (`overrides`)
есть только у тестового корня в
[`@nestling/testing`](../nestling.testing).

`makeApp` проверяет словарь при создании: бренды фич и плагинов, дубли
имён фич, закрытый перечень полей, интерком среди объявленных
транспортов. Предикат `isApp(value)` отличает декларацию от произвольного
объекта.

## Декларация и сборка

Выбор фич — аргумент сборки, а не поле словаря: он меняет состав
процесса, а не приложения.

| Метод | Где | Что делает |
|---|---|---|
| `assemble(select?)` | `App` | синхронно возвращает `AssembledApp`; ничего не читает и граф не строит |
| `check(select?, options?)` | `App` | фазы 0–1 и отчёт о составе; граф не сохраняется |
| `run()` | `AssembledApp` | фазы 0–5, затем приложение остаётся в RUN |
| `close()` | `AssembledApp` | фаза 6 SHUTDOWN в обратном порядке |

Формы выбора: `'all'`, `'users,ops'`, `['users', 'ops']` или
`{ features, includeDeps }`. Публичного конструктора у `AssembledApp`
нет: он принимает внутренний план сборки, поэтому единственный способ
получить собранное приложение — `app.assemble(...)`.

## Фазы

`run()` проходит фазы `0 BOOTSTRAP`, `1 ASSEMBLE`, `2 INIT`, `3 WIRE`,
`4 START` и оставляет приложение в `5 RUN`. `close()` выполняет
`6 SHUTDOWN` в порядке, обратном START.

| Фаза | Что происходит |
|---|---|
| 0 BOOTSTRAP | корень читает выбор фич через `load(section)`; выбор резолвится в начале `run()` |
| 1 ASSEMBLE | выбор фич, discovery, `build()`, проверка границы фич, проверка транспортов и форм io, проверка `policies` |
| 2 INIT | `@OnInit` в топологическом порядке; `dispatch` ещё не существует |
| 3 WIRE | декларации получают зависимости из контейнера; создаётся один `dispatch` на транспорт; порты привязываются к шине, шина подписывается на свои subject'ы |
| 4 START | `@OnStart` в топологическом порядке, затем `serve(dispatch, signal)` у каждого транспорта |
| 6 SHUTDOWN | `abort(signal)`, затем `close()` транспортов в обратном порядке, затем `container.destroy()` |

Фазы 0 и 1 падают при первой ошибке: отсутствующий транспорт,
неподдерживаемая форма io или незарегистрированная зависимость декларации
останавливают запуск до того, как какой-либо `@OnInit` захватит ресурс.
`run()` и `close()` идемпотентны.

### Модули ядра

Три модуля регистрируются всегда, и корень их не упоминает: конфиг
([`@nestling/config`](../nestling.config)), асинхронный контекст запроса
([`@nestling/pipeline`](../nestling.pipeline)) и порты
([`@nestling/ports`](../nestling.ports)). Их узлы — члены семейств токенов,
поэтому они создаются только тогда, когда кто-то их инжектит; приложение,
которое ими не пользуется, не получает ни одного лишнего узла.

Шина внутри процесса регистрируется, только если в приложении есть хотя бы
одна реализация операции и корень не назначил интерком. Так подключается
брокер: `nats({ name: 'events' })` регистрируется под тем же токеном, роль
ему даёт `intercom: 'events'`, и модуль ядра свою шину тогда не создаёт. У
приложения ровно одна шина.

Результат discovery регистрируется как значение под публичным токеном
`Discovery$`. Это единственный способ для плагина (например, генератора
OpenAPI) увидеть выбранную топологию целиком, не дублируя выбор фич.
Значение read-only и в типах, и в рантайме: списки заморожены, а `set`,
`delete` и `clear` бросают ошибку.

## Фичи и выбор

```typescript
import { makeFeature } from '@nestling/app';
import { load } from '@nestling/config';

export const OpsFeature = makeFeature({ name: 'ops', endpoints: [Health] });
export const UsersFeature = makeFeature({
  name: 'users',
  modules: [UsersModule],           // состав фичи: её модули
  endpoints: [GetUser, CreateUser], // декларации объявляет единица
});

export const app = makeApp({
  features: [UsersFeature, OpsFeature],
  plugins: [appLogging],
  transports: [http()],
});

const cfg = load(RootConfig);       // фаза 0: только process.env
// includeDeps подтягивает фичи, чьи операции вызывает выбранная
await app.assemble({ features: cfg.features, includeDeps: true }).run();
```

Фича — значение: её объявление ничего не регистрирует. Поля `dependsOn` у
фичи нет — связь с соседями выводится из объявленных операций; при
`assemble({ features, includeDeps: true })` выбор замыкается по вызовам.
Невыбранная фича в приложении отсутствует полностью: её провайдеры не
создаются, её endpoint'ы нигде не регистрируются.

Ошибки выбора обнаруживаются на фазе ASSEMBLE: неизвестное имя (ошибка
перечисляет доступные), две разные фичи с одним `name`, пустой выбор
(`''` или `[]`) и выбор при пустом списке `features`.

Модули выбранных фич и подключённых плагинов объединяются и
дедуплицируются по значению, как в `ContainerBuilder`. Два разных модуля с
одним `name` останавливают сборку. Модуль, достижимый из двух фич, обязан
быть плагином: иначе у него два владельца, и ребро в него нельзя
классифицировать.

## Состав единицы и endpoint'ы

```typescript
import { makeFeature } from '@nestling/app';

export const UsersFeature = makeFeature({
  name: 'users',
  providers: [UserService, CreateUserHandler],
  endpoints: [GetUser, CreateUser],        // значения-декларации
});
```

Состав задаётся **ровно одной** из двух форм: `providers` (плоская
единица) или `modules` (составная). Обе сразу отвергает компилятор.

`endpoints:` содержит значения-декларации (`httpEndpoint`, `cliEndpoint`,
`implement`), а не классы. `makeFeature` сохраняет этот список и ничего
не добавляет в `providers`. Зависимости класса-хендлера и классы юнитов
пайплайна — обычные провайдеры, и их нужно перечислить в `providers:`
явно. Сам класс-хендлер — исключение: его регистрирует endpoint.

Endpoint обслуживается, только если он указан в `endpoints:` выбранной
фичи или подключённого плагина. Импорт файла с декларацией сам по себе
ничего не регистрирует: глобального реестра нет.

Запуск останавливается с понятным сообщением, если:

- элемент `endpoints:` не является декларацией (ошибка называет единицу и
  индекс в массиве);
- у декларации нет зависимости в контейнере (ошибка называет зависимость,
  паттерн и единицу);
- декларация ссылается на токен транспорта, которого нет в контейнере
  (ошибка называет транспорт, паттерн, единицу и способ починки);
- ребро графа пересекает границу фичи (ошибка называет обе фичи, токен и
  предлагает объявить операцию).

На фазе WIRE приложение вызывает `endpoint.resolve(resolver)` для каждой
найденной декларации и собирает один `dispatch` на транспорт
([`@nestling/transport`](../nestling.transport)). Транспорт получает его
аргументом `serve` на фазе START.

Discovery доступен и отдельно: `discoverEndpoints(bundles)` возвращает
endpoint'ы с именами объявивших единиц и карту требуемых транспортов, без
контейнера и без транспортов.

## Транспорты

Транспорт — обычный узел графа. Корень перечисляет **объявления
экземпляров**: `http()`, `http({ name: 'admin', port: 3001 })`,
`nats({ name: 'events' })`. Декларация выбирает свой экземпляр полем `on:`;
без него это `'default'`. Набор транспортов приложения выводится из графа:
токены, на которые ссылаются найденные декларации, плюс токены объявленных
экземпляров. Транспорт без единого endpoint'а всё равно запускается.

Роль переносчика операций назначается полем `intercom:` — по имени уже
объявленного экземпляра. Годятся только транспорты, реализующие
`IMessageBus`; остальные отвергает компилятор. Объявленная шина без
назначенной роли — ошибка сборки.

Формы io каждой декларации сверяются со способностями транспорта
(`capabilities`) на фазе ASSEMBLE. `events` на CLI или `multipart` на
транспорте, который принимает только значения, останавливают запуск, а не
первый запрос. Сообщение называет endpoint, модуль, транспорт, слот и
форму. Ту же проверку выполняет сам транспорт внутри `serve`
([`@nestling/transport`](../nestling.transport)).

## Конфигурация

```typescript
export const app = makeApp({
  features: [OrdersFeature],
  transports: [http()],
  config: [
    [vault(), [ordersKeys]],          // ключи секции
    [file('config.yaml'), ['*_URL']], // и глобы ключей
  ],
});
```

Модуль ядра для конфига регистрируется всегда. Приложению, которому
хватает `process.env`, писать в корне про конфиг нечего. Другие источники
привязываются плоским списком, где порядок задаёт приоритет. `process.env`
опрашивается последним и в списке не указывается.

Секции, которые использует граф, проецируются и проверяются во время
`build()`. Неверный конфиг останавливает запуск до того, как транспорт
начнёт слушать сокет. Типы `ConfigBinding` и `ConfigTarget` реэкспортированы
отсюда, чтобы корень не импортировал `@nestling/config` ради одной
аннотации.

## Контекст запроса

Модуль ядра для чтения асинхронного контекста
([`@nestling/pipeline`](../nestling.pipeline)) регистрируется всегда. Узлы
семейства `Ctx` создаются только для тех переменных, которые кто-то указал
в `deps`; без единого `Ctx(...)` граф не получает ни одного узла. Класс с
`Ctx(RequestId)` в `deps` собирается и работает как обычно: зависимость —
обычное ребро графа, видимое в сериализованном графе.
Наличие переменной у каждого endpoint'а проверяется политикой
`everyEndpoint(…).hasVar(RequestId)`.

## Политики

```typescript
import { everyEndpoint } from '@nestling/pipeline';

makeApp({
  features: [UsersFeature],
  transports: [http()],
  policies: [
    everyEndpoint({ transport: HttpTransport$('default') }).hasLayer(authedBase, 'authedBase'),
    everyEndpoint({ transport: HttpTransport$('default') }).hasVar(RequestId, 'requestId'),
  ],
});
```

Набор предикатов живёт в [`@nestling/pipeline`](../nestling.pipeline). Этот
пакет только собирает endpoint'ы из discovery, вызывает проверку и
форматирует результат.

- Политики проверяются последними на фазе ASSEMBLE, после проверки
  транспортов и форм io. До `@OnInit` нарушение не доходит.
- Все политики выполняются до конца. Нарушения группируются по политике;
  сообщение называет их число, описание политики, каждый endpoint (паттерн,
  транспорт, модуль) и оба способа починки: подключить слой или пометить
  endpoint `detached: '<причина>'`.
- Проверяются только endpoint'ы выбранной топологии. Endpoint фичи, не
  попавшей в выбор, в набор не входит.

Endpoint'ы с `detached` исключаются из всех политик и печатаются при
запуске сразу после строки состава сборки:

```
[nestling] features: users, ops; transports: http
[nestling] detached from policies: GET /health (http) — liveness probe of the load balancer
```

Там же печатается ещё одна строка: если приложение объявляет `durable`
операции на шине, которая не умеет доставлять с персистентностью, при
запуске один раз выводится список таких операций. Сборка при этом не
падает.

## `check()`: структурная проверка

```typescript
for (const select of ['all', 'users', 'ops'] as const) {
  const report = await app.check(select);
  // report: {
  //   features,
  //   endpoints: [{ pattern, transport, module, detached? }],
  //   transports,
  //   operations: [OperationDescriptor],
  // }
}
```

`check()` живёт на декларации, а не на собранном приложении: это «собрать
и выбросить», результат сборки ему не нужен. Метод выполняет только фазы
0–1: выбор фич, регистрацию, discovery, `build()` (конструкторы
выполняются), проверку транспортов, форм io и `policies`. `@OnInit`,
`@OnStart`, `serve` и `@OnDestroy` не вызываются, поэтому ресурсы не
захватываются. `check()` бросает те же ошибки, что бросил бы `run()` на
этих фазах, не сохраняет контейнер и не влияет на последующий
`assemble()` той же декларации. Так его используют как матрицу топологий
в CI ([`checkTopologies`](../nestling.testing)).

Второй аргумент — конвертеры схем:

```typescript
const report = await app.check('all', { converters: [zodConverter()] });
```

`report.operations` — дескрипторы операций, которые эта топология
публикует. Они строятся из discovery по декларациям с привязкой к шине.
Операция, которая импортирована, но не реализована, в отчёт не попадает.
Отсутствие конвертера для вендора схемы — не ошибка: лист дескриптора
помечается непрозрачным. Дескрипторы — значения из
[`@nestling/ports`](../nestling.ports); из их матрицы `snapshotOperations` и
`diffOperations` строят отчёт о совместимости операций.

## Subpath `./testing`

Тестовый корень, который проводит приложение по фазам 0–3 и
останавливается, живёт в условном subpath `@nestling/app/testing`. Условие
`"testing"` включает только тест-раннер, поэтому в production-коде этот
импорт не резолвится на уровне Node. Код приложения не видит ни
`overrides`, ни способа остановиться на WIRE. Функция шва —
`wireApp(app, options)`. В тестах используйте
[`@nestling/testing`](../nestling.testing), а не этот subpath напрямую.

## Справочник API

| Экспорт | Что это |
|---|---|
| `makeApp(spec?)` | объявляет приложение; возвращает `App` |
| `App` | `spec`, `assemble(select?)`, `check(select?, options?)` |
| `AssembledApp` | `run()`, `close()` |
| `isApp(value)` | предикат декларации приложения |
| `AppSpec`, `NormalizedAppSpec` | типы словаря декларации |
| `CheckReport`, `CheckedEndpoint`, `CheckedOperation`, `CheckOptions` | отчёт `check()` и его опции |
| `makeFeature({ name, providers \| modules, endpoints? })` | объявляет фичу |
| `makePlugin({ …, dependsOn? })` | объявляет плагин |
| `Feature`, `Plugin`, `Bundle`, `FeatureOptions`, `PluginOptions`, `FeatureSelection` | типы единиц и выбора |
| `resolveSelection`, `modulesOf`, `reachablePlugins`, `reachableModules`, `injectedTokens` | разбор выбора фич, модули набора единиц, замыкание плагинов, модули единицы и токены её зависимостей |
| `buildOwnerMap`, `assertFeatureBoundary` | карта «модуль → владелец» и проверка границы фич |
| `discoverEndpoints(bundles)` | плоский проход по фичам и плагинам без контейнера |
| `Discovery$`, `EndpointDiscovery`, `DiscoveredEndpoint` | токен и типы результата discovery |
| `ConfigBinding`, `ConfigTarget` | типы привязки конфига (реэкспорт) |

Subpath `@nestling/app/testing`: `wireApp(app, options?)`, типы
`WireOptions`, `WiredApp`, `WiredEndpoint`, `TestSubstitutions`.

## Границы пакета

Пакет не содержит транспортов, валидации и пайплайна: транспорты живут в
`@nestling/transport.*`, пайплайн и декларации — в `@nestling/pipeline`,
тестовые подстановки — в `@nestling/testing`.
