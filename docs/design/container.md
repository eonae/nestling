## DI-токены и провайдеры

Зависимости объявляются явным массивом DI-токенов. Ни `reflect-metadata`,
ни инжекта «по типу» нет.

```typescript
@Component([UserRepository$, Logger$('users')])
export class UserService {
  constructor(
    private repo: UserRepository,
    private logger: Logger,
  ) {}
}
```

- Класс служит DI-токеном сам себе — в том числе класс с приватным
  конструктором: экземпляр ресурса создаёт `static acquire`, а DI-токеном
  остаётся тот же класс. Интерфейсы и значения регистрируются через явные
  DI-токены (`makeToken<T>(id)`) и примитивы
  `classProvider(token, Class)`, `factoryProvider(token, fn, deps)`,
  `resourceProvider(token, spec)`, `valueProvider(token, value)`. Это
  низкоуровневые примитивы контейнера для DI-токенов интерфейсов, конфига
  и тестов, а не отдельный стиль деклараций.
- **DI-токен — объект, идентичность у него ссылочная.** Строковый `id` служит
  отображению: текстам ошибок, отчётам и `toJSON()` графа. Совпадение `id`
  подмены не вызывает — DI-токены остаются разными, — но делает отчёты
  неоднозначными, и сборка об этом предупреждает. Каждый вызов `makeToken`
  даёт новый DI-токен, поэтому DI-токен объявляют один раз и импортируют
  значением. Второй аргумент `makeToken(id, { hint })` — текст починки на
  случай, когда провайдера для DI-токена в графе нет; на идентичность он не
  влияет. Класс тоже опознаётся по ссылке: два одноимённых класса из
  разных пакетов — два разных узла графа, а не молчаливая подмена.
- Список зависимостей дублируется в декораторе и в конструкторе. Это цена
  отказа от магии компилятора. Компилятор сверяет список с конструктором
  по типам, порядку и длине: аргумент другого типа, перепутанный порядок,
  недостающий и лишний DI-токен — ошибки компиляции.

## Роли классов

Класс в графе играет одну из трёх ролей. Роль задаёт декоратор, и у каждой
роли своя форма класса и свои позиции, в которых класс допустим:

| Роль | Декоратор | Форма | Где допустим |
|---|---|---|---|
| компонент | `@Component([deps])` | синхронный конструктор без ввода-вывода | `providers:` |
| ресурс | `@Resource([deps])` | `static acquire(...deps, signal)` и метод `release()` | `providers:` |
| хендлер | `@Handler([deps])` | конструктор с зависимостями и метод `handle` | слот `handler:` декларации ([endpoints.md §3](./endpoints.md)), `providers:` — для юнита пайплайна |

Позицию держат два механизма. **Форму класса проверяет компилятор:**
`@Handler` применим только к классу с методом `handle`, `@Resource` — к
классу со `static acquire` и `release`, а `@Component` отвергает класс с
`handle` или со `static acquire` и называет нужный декоратор. Слот
`handler:` со своей стороны требует метод `handle` с сигнатурой из схем,
поэтому компонент туда не проходит по типам. **Роль сверяется на фазе
ASSEMBLE:** сборка называет класс, позицию и декоратор, которого она ждёт.
Так ловится то, что форма не различает, — ресурс в слоте `handler:` и
класс без декоратора роли в `providers:`.

Типового бренда позиции на самом классе нет: в стандартных ES-декораторах
он недостижим — декоратор класса, возвращающий `T & Brand`, тип объявления
не меняет.

У класса без зависимостей форма короче: `@Component()`.

**Компонент** обещает, что его создание не трогает внешний мир:
конструктор получает зависимости и ничего не открывает. Компонент
создаётся через `new` на фазе INIT.

**Ресурс** держит что-то внешнее: пул БД, соединение с брокером, таймер.
Захват асинхронен и может провалиться, у ресурса есть освобождение.

```typescript
@Resource([AppConfig, Logger$.auto])
export class Database {
  static async acquire(
    cfg: Config<typeof AppConfig>,
    logger: Logger,
    signal: AbortSignal,               // SIGTERM во время старта отменяет захват
  ): Promise<Database> {
    const pool = new Pool({ connectionString: cfg.databaseUrl });
    await pool.query('select 1');
    logger.info('database connected');
    return new Database(pool);
  }

  private constructor(private readonly pool: Pool) {}

  release(): Promise<void> {
    return this.pool.end();
  }

  health(signal: AbortSignal): Promise<HealthStatus> {   // необязательный вклад в пробы
    return this.pool.query('select 1', { signal }).then(() => 'ok');
  }

  get users(): UsersTable {            // ни undefined, ни проверки
    return this.pool.table('users');
  }
}
```

- `@Resource([deps])` сверяет список зависимостей с параметрами
  `static acquire` так же, как `@Component` сверяет его с конструктором.
  Возвращаемый тип `acquire` обязан быть экземпляром класса.
- Потребитель ресурса создаётся после успешного захвата и получает в
  конструктор готовое значение. Состояния «ещё не инициализирован» у
  ресурса для потребителя нет.
- Функциональная форма для DI-токенов интерфейсов и чужих объектов:
  `resourceProvider(Database$, { deps: [AppConfig], acquire: (cfg, signal) => connect(cfg.databaseUrl, { signal }), release: (pool) => pool.end(), health? })`.
- Метод `health(signal)` у класса или поле `health` у `resourceProvider`
  регистрирует вклад `HealthCheck$(<id узла>)` без отдельного провайдера
  ([composition.md §6](./composition.md)).

**Хендлер** — класс с методом `handle`. Его две позиции: слот `handler:`
декларации endpoint'а и `providers:` — для юнита пайплайна
([pipeline.md](./pipeline.md)). Формы хендлера, интерфейсы `Handler<Op>` и
`HttpHandler<Op>` описаны в [endpoints.md §3](./endpoints.md). Endpoint
регистрирует свой класс-хендлер сам; тот же класс в `providers:` — ошибка
сборки, называющая класс, паттерн endpoint'а и модуль. Юнит пайплайна,
наоборот, объявляют в `providers:`: его резолвит `pipeline.bind`.

Хук `@OnStart(signal)` есть у компонента и у ресурса: начало фоновой
работы — не захват. Сигнал взводится на SHUTDOWN. Других хуков у классов
нет: захват и освобождение — `acquire` и `release` ресурса.

## Сборка и создание экземпляров

`build()` синхронен и не выполняет ввод-вывод. Он раскрывает фабрики
провайдеров модулей, разрешает ветки переключателей, создаёт узлы
семейств, проверяет циклы, отсутствующие DI-токены и роли классов в
позициях, вычисляет топологический порядок. Любая из этих ошибок
останавливает старт приложения; в рантайме они не возникают. Понятия
`forwardRef` нет. Экземпляров после `build()` ещё нет: граф проверен
целиком, и его можно показать, обойти и атрибутировать модулям.

`init()` создаёт экземпляры в топологическом порядке: компонент
конструируется, ресурс захватывается `await acquire`. Провал захвата
освобождает уже захваченное в обратном порядке и роняет старт. `start(signal)`
вызывает `@OnStart(signal)` в топологическом порядке. `destroy()` вызывает
`release` в обратном топологическом порядке; сигнал взводит тот, кто им
владеет, — приложение первым шагом SHUTDOWN.
Семантика фаз описана в [composition.md](./composition.md).

Отсутствующие зависимости перечисляются одной ошибкой. Проверка идёт до
создания экземпляров: сборка обходит `deps` всех провайдеров, собирает
DI-токены без провайдера вместе с их потребителями и выдаёт один список.
Под строкой перечня печатаются подсказки объявлений: недостающего
DI-токена и каждого потребителя, у которого она есть, по строке на
DI-токен. Починка зависит от пары «чего не хватило» и «кому»: DI-токен
знает, как его поставить, потребитель — как обойтись без него. Подсказку
шины `MessageBus$` даёт ядро: она называет транспорт из `transports:`.

Фабрика `factoryProvider` синхронна. Фабрика, вернувшая Promise, роняет
сборку с именем провайдера и подсказкой «захват ресурса — это
`resourceProvider`».

## Читающие методы билдера

`ContainerBuilder` отдаёт состав до `build()` двумя читающими методами.
`healthResources()` перечисляет провайдеры-ресурсы, объявившие `health`;
`familyMembers(family)` — зарегистрированных членов семейства. Оба ничего
не регистрируют и порядка сборки не меняют, оба видят раскрытые ветки
`when` и развёрнутые фабрики провайдеров модулей.

Ими пользуется ядро: узлы вкладов в пробы регистрирует оно, а не
контейнер. Про пробы контейнер не знает — он отвечает на вопрос «у каких
ресурсов есть `health`», смысл исходам задаёт `Health$`
([composition.md §6](./composition.md)).

## Подстановка и прунинг в тестовой сборке

`ContainerBuilder` принимает две опции для тестовой сборки: `overrides`
(пары «DI-токен и значение») и `familyOverrides` (замена рецепта семейства).
Публичный `makeApp` эти опции не принимает: подстановка узлов — свойство
тестового прогона ([testing.md](./testing.md)).

`build()` выполняет шаги в таком порядке:

1. раскрывает фабрики провайдеров модулей и ветки переключателей;
2. заменяет рецепты семейств (`familyOverrides`) — до создания членов,
   чтобы члены создавались уже по тестовому рецепту;
3. создаёт членов семейств (до неподвижной точки);
4. подставляет `overrides`: провайдер DI-токена заменяется на
   `{ provide, useValue }`, атрибуция к модулю сохраняется, поэтому
   визуализация и диагностика по-прежнему показывают владельца;
5. удаляет осиротевшие поддеревья (прунинг);
6. создаёт агрегаты `Family.all` — после прунинга, из оставшихся членов;
7. перечисляет отсутствующие зависимости, строит граф, проверяет циклы и
   роли.

Подстановка падает на сборке в двух случаях. Первый — override для DI-токена
без провайдера: например, провайдер переименовали, и тест заменил бы
пустоту; для члена семейства ошибка отдельно объясняет, что член становится
узлом графа только после того, как кто-то его инжектирует. Второй — два
override'а для одного DI-токена.

**Алгоритм прунинга.** Пусть `deps` — отношение зависимостей до
подстановки, `deps′` — после неё (для заменённых DI-токенов исходные `deps`
запоминаются). Ребро на `Family.all` при обходе разворачивается в рёбра ко
всем текущим членам семейства, чтобы потребитель агрегата не потерял их.

- `R` — DI-токены с нулевой входящей степенью в объединении `deps ∪ deps′`,
  плюс DI-токены, недостижимые из них по объединению. Так участники циклов
  остаются в графе и попадают в проверку циклов, а не исчезают.
- `Keep` — DI-токены, достижимые из `R` по `deps′`.
- Удаляются `All \ Keep`: их экземпляры не создаются, узла в графе нет,
  `acquire`, `@OnStart` и `release` не вызываются. Заменённый узел не
  удаляется никогда.

Объединение `deps ∪ deps′` при выборе `R` нужно для случаев вроде
«репозиторий заменён на in-memory, а пул БД зависел только от него». До
подстановки на пул ссылался репозиторий, после подстановки — никто, поэтому
пул выпадает из графа как осиротевший, а не остаётся в нём как корень.

Инвариант: без `overrides` `deps = deps′`, каждый узел достижим из узлов с
нулевой входящей степенью, поэтому `Keep = All`, и прунинг ничего не
меняет. Боевая сборка совпадает с тестовой сборкой без подстановок до
единого узла. Список идентификаторов удалённых узлов доступен как
`app.pruned`: на вопрос «почему мой ресурс не захвачен» отвечают
данные, а не чтение исходников.

## Модули

Модуль — значение: метка принадлежности провайдеров и единица упаковки.
Границей он не является, поэтому поля `exports` у него нет; endpoint'ов у
него тоже нет — их объявляет единица слоя приложения
([composition.md](./composition.md)). Модуль описывают `name`, `providers`
и `dependsOn`. Видимость держат ES-модули и границы пакетов:
если DI-токен не экспортирован из пакета, снаружи его невозможно
запросить.

```typescript
export const OrdersModule = makeModule({
  name: 'module:orders',
  providers: [OrdersService, OrdersRepository],
  dependsOn: [StorageModule],        // без чего этот модуль не работает
});
```

- `dependsOn` означает принадлежность, а не доступ: провайдеры видны
  всем, кто может импортировать DI-токен. Модули из `dependsOn`
  регистрируются вместе с этим модулем.
- Идентичность модуля — его значение. Одно и то же значение, встреченное
  повторно (через `dependsOn`, в двух фичах, в фиче и в плагине),
  регистрируется один раз. Имя модуля — ключ атрибуции его провайдеров,
  поэтому два разных значения под одним именем — ошибка сборки. Ошибка
  называет имя и способы починки: разделить одно значение импортом, дать
  конфигурациям разные имена, проверить дубли пакета в зависимостях.
  Сравнение значений ссылочное: структурного сравнения опций и мемоизации
  по аргументам нет.
- Параметризованный модуль — функция, которая возвращает модуль. Понятий
  `DynamicModule`, `forRoot` и `forRootAsync` нет. Результат такой функции
  создаётся один раз и разделяется импортом: повторный вызов фабрики, даже
  с теми же опциями, даёт другое значение под тем же именем и роняет
  сборку.
- `providers` модуля может быть синхронной фабрикой; она вызывается в
  `build()`. Ветка состава по значению, известному до сборки, — не
  фабрика, а переключатель: `Storage.pick({ … })` и `Metrics.when(…)` в
  `providers` и `dependsOn` ([composition.md §3](./composition.md)).
- Контейнер используется и автономно, без `App`: группировка провайдеров с
  меткой нужна там сама по себе.

## Семейства DI-токенов

Семейство DI-токенов — один рецепт и много экземпляров, различающихся
параметром. Семейства покрывают параметризованные провайдеры, зависимость
экземпляра от потребителя и multi-injection. Всё это решается при сборке.

```typescript
export const Logger$ = makeTokenFamily<Logger, [scope: string]>('Logger');

// инфраструктурный модуль регистрирует ОДИН рецепт на семейство:
familyProvider(Logger$, (scope) =>
  factoryProvider(Logger$(scope), (root) => root.child({ scope }), [RootLogger$]));

// бизнес-код запрашивает члена как обычную зависимость:
@Handler([UserService, Logger$('users')])
class CreateUserHandler { /* ... */ }
```

- `Logger$('users')` — мемоизированный DI-токен-член с идентификатором
  `Logger:users`. Мемоизация — часть обещания семейства: без неё каждое
  обращение заводило бы новый узел под тем же именем. Семейство и параметр
  член хранит **полями**, поэтому вопрос «чей это DI-токен» не зависит от
  того, как выглядит его `id`: DI-токен, собранный вручную через
  `makeToken('Logger:users')`, членом семейства не является. Сборка находит
  все члены, упомянутые в `deps`, и создаёт для каждого узел графа по
  рецепту. Это обычные узлы, и создаются они на INIT вместе с остальными.
- `.auto` — член, параметр которого равен имени потребителя. `Logger$.auto`
  в `deps` класса `CreateUserHandler` становится
  `Logger$('CreateUserHandler')` в момент регистрации, потому что
  потребитель известен статически. Так решается случай
  `transient + INQUIRER` из Nest без transient-скоупа.
- `.all` — multi-injection: агрегирующий DI-токен типа
  `Token<readonly T[]>`. Это выделенное значение, а не член с
  зарезервированным параметром: `HealthCheck$('all')` — обычный член и с
  агрегатом не сталкивается. Вклады — обычные провайдеры с членскими
  DI-токенами (`classProvider(HealthCheck$('db'), DbHealthCheck)`); их
  регистрируют независимо разные модули. На `build()` сборка создаёт
  синтетический узел-агрегат со списком экземпляров. Список заморожен;
  порядок — порядок регистрации вкладов: сначала явные, затем созданные по
  рецепту. Пустое семейство даёт `[]`. Узел-агрегат не принадлежит модулю;
  вклад не требует объявлений сверх провайдера члена. Если
  фича не выбрана, её вкладов в списке нет — тем же механизмом, который
  убирает из графа её провайдеры. Каждый вклад адресуем и по отдельности:
  `HealthCheck$('db')` — обычный DI-токен.
- Конфиг ([config.md](./config.md)), логгер ядра (ниже) и клиенты
  инфраструктуры по требованию (`GrpcClient$(server)` плюс
  unbound-ключи) — тоже семейства.

## Логгер ядра

`Logger` — интерфейс логгера, с которым работают и ядро, и приложение.

```typescript
type Fields = Record<string, unknown> & { err?: unknown };

interface Logger {
  debug(message: string, fields?: Fields): void;
  debug(error: Error, fields?: Fields): void;
  debug(fields: Fields): void;
  // info, warn, error — те же три формы
  child(bindings: Fields): Logger;
}
```

- Форма с `Error` первым аргументом берёт `message` из ошибки и кладёт
  саму ошибку в `err`. Ключ `err` зарезервирован за ошибкой; стек и
  `cause` сериализует реализация. `Fail` наследует `Error` и проходит той
  же формой.
- `child(bindings)` возвращает логгер, который добавляет `bindings` к
  каждой записи: серия записей об одном объекте пишется через
  `logger.child({ orderId })`.
- `RootLogger$` — DI-токен корня. Сам корень живёт **вне графа**: сборка
  создаёт его на фазе 0 — это значение опции `logger` корня или
  `ConsoleLogger` от снимка секции `nestlingLog` — и регистрирует
  `valueProvider(RootLogger$, root)`. Поэтому ядро пишет в один и тот же
  логгер на всех фазах, включая 0 и 1, когда узлов графа ещё нет.
  Провайдер приложения под `RootLogger$` — ошибка дубля: второго способа
  объявить корень нет.
  `Logger$(scope)` и `Logger$.auto` — члены семейства с рецептом
  `root.child({ scope })`, поэтому замена корня меняет все члены.
- Идентификатор запроса в интерфейс не входит: реализация читает его сама.
  `ConsoleLogger` ядра читает `requestId` из ambient-контекста напрямую, а
  не через узел `Ctx(RequestId)`: корень существует раньше графа и зависеть
  от его узлов не может.
- Контейнер от логгера не зависит: логгера у него нет. Предупреждения
  сборки (совпадающие `id` DI-токенов) он отдаёт значением
  `BuiltContainer.warnings`, а сборка приложения пишет их в корневой
  логгер после `build()`. Пользователь контейнера
  без `App` читает список сам — тот же приём, что у `pruned`.

## Ядро и пользовательский код

Граница проведена как в операционной системе. К ядру относятся источники
конфига, транспорты и серверы, шина и клиенты портов, механизм графа и
жизненного цикла, пробы и корневой логгер; их DI-токены экспортируются,
реализации остаются приватными. К пользовательскому коду относятся
сервисы, endpoint'ы, операции и конфиг как данные. Пересечь границу можно только через публичные
точки: инжект `Config<X>`, `Port` и `Emitter`, `Logger$`, `Health$`,
возврат значения из хендлера. Границу держит видимость ES-модулей, а не
проверка прав в рантайме. Пользовательский код не знает ни источника
конфига, ни транспорта: один и тот же бизнес-код работает в одном процессе
и в split-развёртывании, с конфигом из env или из Vault.

## Асинхронный контекст

Сервисам в глубине графа (логгер в репозитории тремя слоями ниже хендлера)
нужны значения из контекста запроса, например `requestId`. Для них есть
проекция контекста пайплайна через AsyncLocalStorage, доступная только для
чтения. Правило: значение приходит из окружения, но зависимость от него
объявлена явно; записывать значения могут только `.pre`-юниты.

Переменная контекста — типизированный ключ накопленного `input` пайплайна,
а не ячейка отдельного хранилища. Отдельного состояния, которое могло бы
разойтись с `input`, нет. Объявление — двойной вызов: `contextVar<T>()`
фиксирует тип, второй вызов задаёт ключ литералом.

```typescript
export const RequestId = contextVar<string>()('requestId');
// ключ 'requestId' — то же поле, что видит юнит в ctx.input.requestId
```

- Запись делает сама переменная: `Var.provide(compute)` возвращает обычный
  `PreUnitFn<TReq, { key: T }>`. Объявление переменной и запись значения —
  одно действие. Вторая форма, `Var.provide(deps, compute)`, даёт писателю
  значения из контейнера: список DI-токенов резолвится на `bind()` тем же
  резолвером, что и классы-юниты, и попадает в `TNeeds` пайплайна
  ([pipeline.md §5](./pipeline.md)); требования к контексту такой писатель
  объявляет аннотацией параметра `ctx`. `Family.auto` в списке
  отвергается: у писателя нет класса-потребителя, по имени которого
  выбирается член. Юнит, который кладёт то же поле в `input` вручную, для
  читателей работает, но объявителем переменной не считается, и политика
  `hasVar` его не засчитывает.
- Чтение — член семейства DI-токенов: `Ctx(RequestId)` в `deps` даёт
  `CtxReader<string>`. `Ctx` типизирован значением переменной:
  `Ctx('requestId')` со строкой не компилируется. Зависимость от контекста
  запроса — обычное ребро графа, и полный список чтений контекста известен
  на `build()`. В тестах читатель заменяется через `valueProvider`
  (сокращённая запись — `contextValue`, см. [testing.md](./testing.md));
  AsyncLocalStorage для этого не нужен. Рецепт семейства даёт модуль ядра,
  который composition root регистрирует всегда; поля для него в `makeApp`
  нет, как и для конфига.
- `get(): T` бросает ошибку с указанием текущей фазы, если значения нет.
  `peek(): T | undefined` предназначен для ответной фазы пайплайна,
  `@OnStart` и фоновых задач. Эта пара повторяет асимметрию контекста в
  пайплайне ([pipeline.md](./pipeline.md)).
- В проекции доступны накопленный `input`, `signal` и текущая фаза. `raw`,
  `endpoint` и `summary` в проекцию не попадают: транспорт не должен
  проникать в домен. Сигнал живёт вне `input`, поэтому доступен только для
  чтения: `Ctx(Signal)` читается, ключ `'signal'` зарезервирован, метода
  `provide` у этой переменной нет ни в типе, ни в рантайме. Проекцию
  обновляет только рантайм пайплайна; публичного сеттера нет.
- Присутствие переменной проверяется на сборке, opt-in:
  `everyEndpoint(…).hasVar(Var)` ([pipeline.md §7](./pipeline.md)). Типы
  закрывают чтение из юнита, политика — чтение из глубины графа, где типов
  входа нет.
- Передача переменной через порт — opt-in в объявлении:
  `contextVar<T>()('tenantId', { propagate: true })`. Флаг стоит на
  объявлении, а не в точке подключения: передаётся именно переменная, и
  решение об этом видно там же, где она объявлена. Контекст вызывающего в
  реализацию порта не попадает ни при одном способе привязки: вызов порта
  открывает собственный контекст запроса. `propagate` — именованное
  исключение из этого правила.
  - Сбор значений происходит на стороне вызывающего, из контекста текущего
    запроса. Значения отправляются полем конверта шины, а не подмешиваются
    в payload. Вне запроса (`@OnStart`, фоновая задача) передавать нечего,
    и это допустимо.
  - Приём идёт двумя каналами, как у профиля вызова
    ([operations.md §4](./operations.md)): безусловно в `ctx.raw.attributes`
    и в проекцию контекста через `Var.propagated()`. Этот писатель несёт ту
    же рантайм-пометку, что и `Var.provide`, поэтому
    `everyEndpoint(…).hasVar(Var)` засчитывает его, и присутствие
    переданного контекста проверяется на сборке.
  - Значение не валидируется: схемы у переменной контекста нет. Передача
    пересекает границу доверия; что передавать и что решать на основании
    переданного, остаётся ответственностью приложения.
  - Переменные только для чтения (`Signal`) передаваться не могут: их
    значение поставляет рантайм запроса на стороне получателя.
  - Передача работает только через шину. Через HTTP и CLI контекст не
    передаётся.
- Отдельного пакета `@nestlingjs/context` нет: писатель типизируется
  `ExtendableContext` пайплайна, проекцию обновляет его рантайм, предикат
  `hasVar` живёт в его наборе политик.

## Что в контейнер не попадает

- Состояние запроса. Типизированный контекст запроса — накопленный `input`
  пайплайна; для сервисов в глубине графа — асинхронный контекст (раздел
  выше). Провайдеров со скоупом запроса нет.
- Значения переключателей. У переключателя нет DI-токена: выбор состава
  виден в графе как выбранная ветка, а не как значение
  ([composition.md §3](./composition.md)).
- Ленивая инициализация и рантайм-подграфы (дочерние контейнеры) в V1 не
  входят (см. записи журнала).
