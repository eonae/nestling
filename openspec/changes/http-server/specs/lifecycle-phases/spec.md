# lifecycle-phases Specification (delta)

## MODIFIED Requirements

### Requirement: Приложение проходит фазы в фиксированном порядке

`App` SHALL проводить запуск по фазам в порядке
`0 BOOTSTRAP → 1 ASSEMBLE → 2 INIT → 3 WIRE → 4 START → 5 RUN`, где:

- **0 BOOTSTRAP** — вычисление `select` до построения контейнера, подъём
  привязанных источников конфига (`init()`) и чтение значений в снимок;
- **1 ASSEMBLE** — резолв выбора, discovery из дерева выбранных модулей,
  `build()` контейнера, сверка требуемых транспортов, проверка форм io и
  проверка уникальности паттернов (capability `pattern-uniqueness`);
- **2 INIT** — `@OnInit` в топологическом порядке; `dispatch` ещё не существует;
- **3 WIRE** — получение зависимостей деклараций из контейнера, создание
  `dispatch` на каждый транспорт и связывание вызывающих сторон операций
  local-биндинга с `dispatch` транспорта шины;
- **4 START** — `@OnStart` в топологическом порядке, затем
  `serve(dispatch, signal)` на каждом транспорте, затем `listen()` на
  каждом сервере;
- **5 RUN** — приложение обслуживает запросы.

Сокет SHALL открываться последним шагом START: `listen()` SHALL NOT
начинаться, пока `serve` не завершился на всех транспортах.

Фаза 0 SHALL быть единственным местом ввода-вывода до INIT. Фаза 1 SHALL
проходить синхронно и SHALL NOT выполнять ввод-вывода: `build()` синхронный
(capability `synchronous-assembly`), значения секций берутся из снимка
фазы 0 (capability `config-bootstrap-snapshot`).

Фазы 0 и 1 SHALL быть fail-fast: любая обнаруженная в них ошибка SHALL
завершать старт до захвата ресурсов.

Вызов порта раньше фазы WIRE SHALL быть ошибкой с понятным сообщением:
исполнимых ручек до WIRE не существует, поэтому связывать вызыватель не с
чем, а молчаливое ожидание скрывало бы нарушение фазовой модели.

#### Scenario: Ошибка сборки предшествует захвату ресурсов

- **WHEN** дерево модулей ссылается на транспорт, которого нет в графе, а
  один из провайдеров захватывает соединение в `@OnInit`
- **THEN** старт падает на фазе 1, и `@OnInit` не вызывается ни разу

#### Scenario: Фаза 1 не читает источники

- **WHEN** приложение собирается с привязанным источником, считающим вызовы
  `get()` и `init()`
- **THEN** `init()` вызван на фазе 0 ровно один раз, а `build()` не
  обращается к источнику вовсе: значения приходят из снимка

#### Scenario: `dispatch` создаётся после INIT

- **WHEN** провайдер в `@OnInit` пытается получить готовый `dispatch`
- **THEN** такого способа нет: `dispatch` создаётся в фазе WIRE и
  передаётся только аргументом `serve`

#### Scenario: Порядок фаз наблюдаем

- **WHEN** приложение поднимается с провайдером, отмечающим вызовы
  `@OnInit` и `@OnStart`, транспортом, отмечающим вызов `serve`, и
  сервером, отмечающим `listen`
- **THEN** порядок отметок: `@OnInit` → `@OnStart` → `serve` → `listen`

#### Scenario: Сокет открывается после всех `serve`

- **WHEN** два транспорта присоединены к одному серверу
- **THEN** `listen` вызывается один раз, после `serve` обоих транспортов

#### Scenario: Порт связан к моменту `@OnStart`

- **WHEN** провайдер зовёт порт в `@OnStart`
- **THEN** вызов исполняется: связывание произошло в WIRE

#### Scenario: Порт, вызванный в `@OnInit`

- **WHEN** провайдер зовёт порт в `@OnInit`
- **THEN** он получает ошибку, называющую операцию и фазу

### Requirement: SHUTDOWN — строгий реверс START

Фаза 6 SHALL выполняться в порядке, обратном START:

1. взводится `signal`, переданный транспортам в `serve` (новые запросы не
   принимаются, in-flight отменяются кооперативно);
2. вызывается `drain()` серверов — в порядке, обратном порядку `listen`;
   сервер перестаёт принимать соединения и дочитывает открытые;
3. вызывается `close()` транспортов — в порядке, обратном порядку `serve`;
4. вызывается `container.destroy()` (`@OnDestroy` в обратном топологическом порядке).

`close()` транспорта SHALL NOT начинаться, пока не завершился `drain()`
серверов. `container.destroy()` SHALL NOT начинаться, пока не завершились
`close()` всех транспортов.

#### Scenario: Реверс наблюдаем

- **WHEN** приложение с двумя транспортами на разных серверах и сервисом
  с `@OnDestroy` закрывается
- **THEN** порядок: `abort(signal)` → `drain()` второго сервера →
  `drain()` первого → `close()` второго транспорта → `close()` первого →
  `@OnDestroy` сервиса

#### Scenario: Отмена доходит до in-flight запроса

- **WHEN** идёт HTTP-запрос, хендлер которого уважает `meta.signal`, и
  вызван `testApp.close()`
- **THEN** сигнал взводится, хендлер завершается, и только после дренажа
  выполняются `@OnDestroy`
