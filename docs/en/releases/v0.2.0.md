# 0.2.0

> All `@nestlingjs/*` packages ship as one version. The release carries
> the commits from the `v0.1.3` tag to the `v0.2.0` tag, 12–13 September
> 2026. An old name is removed together with its replacement: there are
> no aliases or wrappers in the packages.

## Upgrading

```bash
yarn up '@nestlingjs/*'
yarn remove @nestlingjs/openapi.zod
yarn add @nestlingjs/schema.zod
```

The version is one for all packages: a package of the previous version
does not work next to a new one. The `@nestlingjs/openapi.zod` package
changed its name, so the old one is removed by a separate command. The
Node requirement is the same, 24 and above. Three new packages are
installed as needed:

```bash
yarn add @nestlingjs/drizzle.pg drizzle-orm pg  # PostgreSQL and the stores
yarn add @nestlingjs/inbox                      # the transactional intake
yarn add @nestlingjs/mcp                        # agent tools
```

`drizzle-orm` and `pg` are peer dependencies of `@nestlingjs/drizzle.pg`
with the `^0.45.0` and `^8.16.0` ranges. The full reference of the
environment is [compatibility.md](../compatibility.md).

## In brief

- An HTTP declaration is created by a constructor named after the
  method: `httpEndpoint.get('/users', { … })` instead of a dictionary
  with the `method` and `path` fields —
  [section](#the-endpoint-declaration).
- The form that implements an operation got its own name,
  `httpEndpoint.implement(Operation, { … })`, and the `operation` key is
  gone from the dictionary — [section](#the-endpoint-declaration).
- A command is named by the first argument of
  `cliEndpoint('users:list', { … })` —
  [section](#the-endpoint-declaration).
- A pre-step got a third outcome, the early success `done()` —
  [section](#the-pipeline-and-the-kernel).
- Three packages appeared: `@nestlingjs/drizzle.pg`,
  `@nestlingjs/inbox` and `@nestlingjs/mcp` —
  [section](#data-and-delivery).
- The kernel got traces and metrics — [section](#observability).
- The `@nestlingjs/openapi.zod` package is renamed to
  `@nestlingjs/schema.zod` — [section](#schemas-and-openapi).
- The barrels of seven packages list the names, and a name without a
  reader no longer leaves the package —
  [section](#barrels-list-the-names).
- The documentation went to a site in two languages —
  [section](#examples-and-documentation).

## Breaks silently

The compiler will not show these changes: the code builds and behaves
differently.

- Everything the process prints outwards is written in English: failure
  messages, logs and the reasons of `hidden`. Code that matched a
  message by its Russian text stops recognizing it —
  [section](#runtime-strings-are-english).
- The definition of a NATS stream carries a deduplication window, and
  the default is 5 minutes. An existing stream with a narrower window
  gives a `warn` entry, and the transport does not rewrite it —
  [section](#nats-msg-id-and-the-deduplication-window-of-a-stream).
- An empty HTTP response carries `content-length: 0` for every status
  except 204 and 304: a redirect stopped leaving with
  `transfer-encoding: chunked` — [section](#runtime-strings-are-english).
- A scalar path and query parameter is described in the OpenAPI document
  by the parsed shape: a field with `stringbool` became `boolean`
  instead of `string`. A client generated from the document changes the
  type of the field —
  [section](#a-parameter-is-described-by-the-parsed-shape).

## The endpoint declaration: before and after

Two files show both constructor forms: the anonymous one and the one
that implements an operation.

```typescript
// src/users/endpoints/upload-avatar.endpoint.ts — 0.1.3
export const UploadAvatar = httpEndpoint({
  method: 'POST',
  path: '/users/:id/avatar',
  input: multipart({
    fields: AvatarFields,
    files: { avatar: upload({ maxSize: 2 * MiB, mime: ['image/png'] }) },
  }),
  output: User,
  errors: [UserNotFound, AvatarRequired],
  doc: { summary: 'Загрузить аватар', tags: ['users'] },
  pipeline: transactional,
  handler: UploadAvatarHandler,
});

// src/users/endpoints/create-user.endpoint.ts — 0.1.3
export const CreateUser = httpEndpoint({
  operation: CreateUserOperation,
  pipeline: transactional,
  handler: CreateUserHandler,
});
```

```typescript
// src/users/endpoints/upload-avatar.endpoint.ts — 0.2.0
export const UploadAvatar = httpEndpoint.post('/users/:id/avatar', {
  input: multipart({
    fields: AvatarFields,
    files: { avatar: upload({ maxSize: 2 * MiB, mime: ['image/png'] }) },
  }),
  output: User,
  errors: [UserNotFound, AvatarRequired],
  doc: { summary: 'Загрузить аватар', tags: ['users'] },
  pipeline: transactional,
  handler: UploadAvatarHandler,
});

// src/users/endpoints/create-user.endpoint.ts — 0.2.0
export const CreateUser = httpEndpoint.implement(CreateUserOperation, {
  pipeline: transactional,
  handler: CreateUserHandler,
});
```

Each change is described separately below: what it became, how to use it
and where to read the details.

## The endpoint declaration

### A constructor named after the HTTP method

`httpEndpoint` stopped being a function and became a value with six
constructors: `get`, `head`, `post`, `put`, `patch` and `delete`. Each
takes the path as the first argument and the dictionary as the second.
The `method` and `path` fields are removed from the dictionary.

```typescript
// src/users/endpoints/list-users.endpoint.ts — 0.1.3
export const ListUsers = httpEndpoint({
  method: 'GET',
  path: '/users',
  input: ListUsersInput,
  output: z.array(User),
  doc: { summary: 'Список пользователей', tags: ['users'] },
  pipeline: observability,
  handler: ListUsersHandler,
});
```

```typescript
// src/users/endpoints/list-users.endpoint.ts — 0.2.0
export const ListUsers = httpEndpoint.get('/users', {
  input: ListUsersInput,
  output: z.array(User),
  doc: { summary: 'Список пользователей', tags: ['users'] },
  pipeline: observability,
  handler: ListUsersHandler,
});
```

The literal type of the path is taken from the first argument. Path
parameters are inferred from it, and the field placement rule is checked
as before.

The `endpoint-has-layer` ESLint rule recognises a member call and takes
the dictionary from the last argument. The creation failure texts name
the new form: `httpEndpoint.get('/users', { … })` instead of
`httpEndpoint({ method: 'GET', path: '/users' })`. Read more in
[chapter 1](../guide/01-first-service.md).

> Upgrade: mechanical — the method moves into the name of the
> constructor, the path becomes the first argument, and the rest of the
> dictionary does not change.
> Why: [deferred.md, `[2026-09-03] Конструктор HTTP-декларации с методом в имени`](../../decisions/deferred.md#2026-09-03-%D0%BA%D0%BE%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%82%D0%BE%D1%80-http-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8-%D1%81-%D0%BC%D0%B5%D1%82%D0%BE%D0%B4%D0%BE%D0%BC-%D0%B2-%D0%B8%D0%BC%D0%B5%D0%BD%D0%B8-httpendpointgetpath).

### The command name is the first argument of `cliEndpoint`

`cliEndpoint` takes the command name as the first argument. The
`command` field is removed from the dictionary.

```typescript
// src/commands/greet.command.ts — 0.1.3
export const Greet = cliEndpoint({
  command: 'greet',
  input: GreetInput,
  output: GreetOutput,
  handler: async ({ args, shout }) => ({ greeting: greet(args[0], shout) }),
});
```

```typescript
// src/commands/greet.command.ts — 0.2.0
export const Greet = cliEndpoint('greet', {
  input: GreetInput,
  output: GreetOutput,
  handler: async ({ args, shout }) => ({ greeting: greet(args[0], shout) }),
});
```

The address of an endpoint now stands in one place for both transports:
the first argument of the constructor. Read more in the recipe
[“A CLI tool on the same primitives”](../recipes/cli.md).

### `httpEndpoint.implement` instead of the `operation` key

The form that implements an operation got its own name. The operation
goes first, and the dictionary names only `pipeline`, `detached` and
`on`. The `operation` key is removed.

```typescript
// src/users/endpoints/create-user.endpoint.ts — 0.1.3
export const CreateUser = httpEndpoint({
  operation: CreateUserOperation,
  pipeline: transactional,
  handler: CreateUserHandler,
});
```

```typescript
// src/users/endpoints/create-user.endpoint.ts — 0.2.0
export const CreateUser = httpEndpoint.implement(CreateUserOperation, {
  pipeline: transactional,
  handler: CreateUserHandler,
});
```

Nine `never` fields left together with the key. They used to forbid
declaring what belongs to the operation: `method`, `path`, `bind`,
`rawBody`, `sse`, `input`, `output`, `errors` and `doc`. The dictionary
does not have them now. The runtime check stayed: it catches a
redeclaration by a JavaScript consumer, whom types do not help. Read
more in [chapter 14](../guide/14-features.md).

> Upgrade: mechanical — the `operation` key becomes the first argument of
> `httpEndpoint.implement`.
> Why: [ideas.md, `[2026-09-12] Две декларации HTTP вместо четырёх перегрузок httpEndpoint`](../../decisions/ideas.md#2026-09-12-%D0%B4%D0%B2%D0%B5-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8-http-%D0%B2%D0%BC%D0%B5%D1%81%D1%82%D0%BE-%D1%87%D0%B5%D1%82%D1%8B%D1%80%D1%91%D1%85-%D0%BF%D0%B5%D1%80%D0%B5%D0%B3%D1%80%D1%83%D0%B7%D0%BE%D0%BA-httpendpoint-%D0%B1%D1%80%D0%B5%D0%BD%D0%B4%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9-%D0%BD%D0%B5%D0%B7%D0%B0%D1%8F%D0%B2%D0%BB%D0%B5%D0%BD%D0%BD%D1%8B%D0%B9-%D0%BE%D1%82%D0%BA%D0%B0%D0%B7).

### An undeclared failure is named in the diagnostic

A handler that returns a failure beyond the `errors:` list is rejected
by the compiler with the text of the rule. The check is called
`ValidateHandlerFails` and prints three fields: `returned` with the
codes beyond the declared ones, `declared` with the codes from
`errors:`, and `hint` with the fix.

```text
Type '{ __error: "Handler returns a failure that is not declared in 'errors:'";
        returned: "conflict:alias_taken";
        declared: "not_found:link";
        hint: "add the definitions to 'errors:', or stop returning them from
               the handler"; }' ...
```

The literal is anonymous rather than a named alias. The compiler prints
the name of an alias instead of its contents, and the rule would not
reach the reader.

The position of the check differs between the two handler forms. For a
class it stands in the `handler` slot. For a function it stands in the
return type: the compiler needs the type parameter of the slot to type
the arrow parameters, so a check in the slot would see the whole set of
failures instead of the returned one.

## The pipeline and the kernel

### The early success of a pre-step, `done()`

A pre-step finishes with three outcomes instead of two: an addition to
the context, a failure, or an early success. The early success arrives
as the value `done()` from `@nestlingjs/app`. The following pre-steps
and the handler are not called, and the response phase starts with a
success that carries no value.

```typescript
// src/features/notifications/dedupe.layer.ts — 0.2.0
import { done, makePipeline } from '@nestlingjs/app';

const deduped = makePipeline().pre(
  async (ctx) => ((await seen(ctx)) ? done() : undefined),
  { done: true },
);
```

The step is attached with the `{ done: true }` marker. Without the
marker, returning `done()` fails the request: a pipeline that did not
declare an early success is required to reach the handler. The
declaration must have no `output` — an early success carries no value.

The change is additive: an application that never calls `done()`
behaves as before. The channel is general and belongs to the pipeline
rather than to deduplication: there is no key, no store and no retry in
it. The claim layer of `@nestlingjs/inbox` is built on top of it. Read
more in [chapter 16](../guide/16-durable-events.md).

> Why: [ideas.md, `[2026-09-12] Транзакционный приём: inbox как вторая половина гарантии outbox'а`](../../decisions/ideas.md#2026-09-12-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%BD%D1%8B%D0%B9-%D0%BF%D1%80%D0%B8%D1%91%D0%BC-inbox-%D0%BA%D0%B0%D0%BA-%D0%B2%D1%82%D0%BE%D1%80%D0%B0%D1%8F-%D0%BF%D0%BE%D0%BB%D0%BE%D0%B2%D0%B8%D0%BD%D0%B0-%D0%B3%D0%B0%D1%80%D0%B0%D0%BD%D1%82%D0%B8%D0%B8-outbox%D0%B0).

### A variable writer with dependencies from the container

`Var.provide` got a second form: a list of DI tokens as the first
argument and the computation as the second. The dependencies are
resolved on the WIRE phase by the same resolver that resolves the
classes of pipeline steps.

```typescript
// src/persistence.ts — 0.1.3
@Handler([Database])
export class ProvideDb {
  constructor(private readonly db: Database) {}

  handle(): { db: Database } {
    return { db: this.db };
  }
}

export const transactional = compose(
  authed,
  makePipeline()
    .pre(ProvideDb)
    .pre(Tx.provide<{ db: Database }>((ctx) => ctx.input.db.begin())),
);
```

```typescript
// src/persistence.ts — 0.2.0
export const transactional = compose(
  authed,
  makePipeline().pre(Tx.provide([Database], (_ctx, db) => db.begin())),
);
```

The bridge class that put the connection into the context only so that
the writer could read it from `ctx.input` is no longer needed. The
transaction layer consists of one step instead of two, and the
registration of the bridge in `providers:` goes away with it.

The `users-service` example does not write this layer at all: from this
release the transaction is carried by `db.transaction()` from
`@nestlingjs/drizzle.pg`. The form with dependencies stays for the
variables that an application builds itself.

### A DI token hint, `makeToken(id, { hint })`

`makeToken` takes a dictionary with a `hint` field as the second
argument. The hint is the text of the fix for the case when the graph
has no provider for the DI token. It is printed in the build failure and
does not affect the identity of the DI token.

```typescript
// 0.1.3: the text of the fix is written into the identifier
const OutboxBus$ = makeToken<IMessageBus>(
  "@nestlingjs/outbox relay (add a bus transport to 'transports:', or remove " +
    'the outbox plugin)',
);
```

```typescript
// 0.2.0: the identifier stays a name, the fix stands as a hint
const OutboxBus$ = makeToken<IMessageBus>('@nestlingjs/outbox relay', {
  hint: 'or remove the outbox plugin',
});
```

The failure about missing dependencies prints the hint of the missing DI
token and the hints of every consumer that declared one. Read more in
[design/container.md](../design/container.md).

### An idempotency key on an event and an own `meta` dictionary

`idempotencyKey` appeared in `meta` for operations of the `event` kind,
next to `command`. `request` still does not have it. The generation of
the key did not change: the kernel mints a missing key only for a
command, and an event has a key when the publisher passed one.

`Port<C, M>` and `Emitter<C, M>` take the `meta` dictionary as the
second type parameter, `MetaOf<C>` by default. A satellite package
declares its own dictionary and stays compatible with the kernel: a
value of `Emitter<C, MetaOf<C> & { partitionKey?: string }>` is
assignable to a variable of type `Emitter<C>`, because a method
parameter is contravariant. The partition key of an outbox record stands
on this.

## Data and delivery

### `@nestlingjs/drizzle.pg`

A new package: a connection to PostgreSQL, a request transaction and
store adapters on top of drizzle-orm. The `drizzle-orm` and `pg`
dependencies are peer dependencies.

```typescript
// src/persistence.ts — 0.2.0
import { drizzlePg } from '@nestlingjs/drizzle.pg';
import { pgOutboxStore } from '@nestlingjs/drizzle.pg/outbox';
import { pgInboxStore } from '@nestlingjs/drizzle.pg/inbox';

export const db = drizzlePg({ schema });
export const outboxStore = pgOutboxStore(db);
export const inboxStore = pgInboxStore(db);

export const transactional = compose(authed, db.transaction());
```

A connection is declared as a value. Several connections mean several
calls with different `name`, and the configuration section of each
becomes a member of a family: `DATABASE_URL` for the default connection
and `DATABASE_ANALYTICS_URL` for `name: 'analytics'`. A connection is a
resource: the pool opens on the INIT phase, closes on SHUTDOWN and
declares `health`, so every connection lands in `/readyz` as a separate
check.

The request transaction is the `db.transaction()` pipeline layer. It
takes a connection from the pool and opens a transaction, commits on
success, rolls back on failure, and returns the connection to the pool
on any outcome. The value of the `tx` context variable is a drizzle
instance bound to that transaction, so a repository writes an ordinary
query. The `db.requiresTransaction(filter)` policy stops the build on
the ASSEMBLE phase if an endpoint under the filter did not declare the
layer.

The `./outbox` and `./inbox` subpaths provide the `OutboxStore` and
`InboxStore` implementations: each carries a drizzle table declaration
and a DDL constant. Read more in
[chapter 11](../guide/11-database.md). In 0.3.0 the factories of the
package got the `make` prefix: [the 0.3.0 note](./v0.3.0.md).

> Why: [ideas.md, `[2026-09-11] Соединение с базой: сателлит drizzle.pg, транзакция запроса переменной контекста`](../../decisions/ideas.md#2026-09-11-%D1%81%D0%BE%D0%B5%D0%B4%D0%B8%D0%BD%D0%B5%D0%BD%D0%B8%D0%B5-%D1%81-%D0%B1%D0%B0%D0%B7%D0%BE%D0%B9-%D1%81%D0%B0%D1%82%D0%B5%D0%BB%D0%BB%D0%B8%D1%82-drizzlepg-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D1%8F-%D0%B7%D0%B0%D0%BF%D1%80%D0%BE%D1%81%D0%B0-%D0%BF%D0%B5%D1%80%D0%B5%D0%BC%D0%B5%D0%BD%D0%BD%D0%BE%D0%B9-%D0%BA%D0%BE%D0%BD%D1%82%D0%B5%D0%BA%D1%81%D1%82%D0%B0).

### `@nestlingjs/inbox`

A new package: a transactional claim of an incoming message. The
`inbox({ transaction, store })` plugin provides a layer, a prerequisite
policy and a configuration section. The package has no external
dependencies and no database drivers.

```typescript
// src/users/endpoints/welcome-email.endpoint.ts — 0.1.3
@Handler([Logger$.auto, SeenKeys$])
export class WelcomeEmailHandler {
  constructor(
    private readonly logger: Logger,
    private readonly seen: Set<string>,
  ) {}

  async handle(payload: UserCreatedPayload, meta: { idempotencyKey: string }) {
    if (this.seen.has(meta.idempotencyKey)) {
      return new Ok(undefined); // a repeat was cut off by an in-memory Set
    }

    this.seen.add(meta.idempotencyKey);

    return this.send(payload);
  }
}

export const WelcomeEmail = implement(UserCreated, {
  subscriber: 'welcome-email',
  pipeline: makePipeline().pre(withIdempotencyKey()),
  handler: WelcomeEmailHandler,
});
```

```typescript
// src/users/endpoints/welcome-email.endpoint.ts — 0.2.0
@Handler([Logger$.auto])
export class WelcomeEmailHandler {
  constructor(private readonly logger: Logger) {}

  async handle(payload: UserCreatedPayload, meta: { idempotencyKey: string }) {
    return this.send(payload); // a repeat does not reach the handler
  }
}

export const WelcomeEmail = implement(UserCreated, {
  subscriber: 'welcome-email',
  pipeline: compose(subscribed, appInbox.layer),
  handler: WelcomeEmailHandler,
});
```

The `appInbox.layer` layer reads the idempotency key from the envelope
of the message and calls `claim` of the store in the transaction of the
caller. A repeated message does not reach the handler: the layer answers
with an early success. The key of a record is composite, the pattern of
the endpoint plus the idempotency key. One event goes to several
subscribers with one outbox record identifier, and each of them
deduplicates on its own.

The `InboxStore` interface declares `claim` and `sweep`. The in-memory
implementation lives under the `./testing` subpath, and the PostgreSQL
adapter lives in `@nestlingjs/drizzle.pg/inbox`. The `sweep` resource
deletes the marks older than the retention period on an interval from
the configuration section. The `appInbox.requiresInbox(filter)` policy
checks on the ASSEMBLE phase that every subscriber under the filter is
composed from the layer.

A message without an idempotency key fails the processing. The layer
reads the envelope rather than a context variable: a minted key would
differ between two deliveries of one message.

The claim does not make sending an email happen once. It narrows the
window of a repeat down to the interval between the effect and the
commit of the mark. Read more in
[chapter 16](../guide/16-durable-events.md).

### The outbox on the new primitives

The partition of a record is set by an argument of `emit`. The
`partitionKey` option of `outbox({ … })` is removed.

```typescript
// src/users/endpoints/create-user.endpoint.ts — 0.1.3
await this.userCreated.emit({ id: user.id, name: user.name, email: user.email });

// src/app.ts — the partition was declared by a function on the plugin
export const appOutbox = outbox({
  transaction: Tx,
  store: OutboxStore$,
  operations: [UserCreated],
  partitionKey: (payload) => payload.id,
});
```

```typescript
// src/users/endpoints/create-user.endpoint.ts — 0.2.0
await this.userCreated.emit(
  { id: user.id, name: user.name, email: user.email },
  { partitionKey: user.id },
);
```

The partition is named at the call site, where the value already exists.
The dependency type of the handler is then called
`OutboxEmitter<typeof Op>`: it is the kernel emitter with an extended
`meta` dictionary, and it is assignable to a variable of type
`Emitter<C>`. A handler that does not need a partition declares the
dependency with the former type.

The DI token alias of the bus went away with the option. It existed for
the sake of the text of a fix inside the identifier; the fix is now
carried by the `makeToken` hint.

> Upgrade: mechanical — `partitionKey` moves from the `outbox({ … })`
> factory into the argument of `emit`, where the value is already at hand.
> Why: [ideas.md, `[2026-09-07] Транзакционный outbox: точка врезки, предпосылка транзакции и результат замера границы`](../../decisions/ideas.md#2026-09-07-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D0%BE%D0%BD%D0%BD%D1%8B%D0%B9-outbox-%D1%82%D0%BE%D1%87%D0%BA%D0%B0-%D0%B2%D1%80%D0%B5%D0%B7%D0%BA%D0%B8-%D0%BF%D1%80%D0%B5%D0%B4%D0%BF%D0%BE%D1%81%D1%8B%D0%BB%D0%BA%D0%B0-%D1%82%D1%80%D0%B0%D0%BD%D0%B7%D0%B0%D0%BA%D1%86%D0%B8%D0%B8-%D0%B8-%D1%80%D0%B5%D0%B7%D1%83%D0%BB%D1%8C%D1%82%D0%B0%D1%82-%D0%B7%D0%B0%D0%BC%D0%B5%D1%80%D0%B0-%D0%B3%D1%80%D0%B0%D0%BD%D0%B8%D1%86%D1%8B).

### `Nats-Msg-Id` and the deduplication window of a stream

A durable publication sets the `Nats-Msg-Id` header when the envelope
carries an idempotency key. The value is the same key that travels in
`Nl-Idempotency-Key`.

The stream definition carries a deduplication window. The value comes
from the `dedupeWindowMs` factory option, and the default is 5 minutes.

```typescript
// src/main.ts — 0.2.0
const bus = nats({ servers: ['nats://localhost:4222'], dedupeWindowMs: 600_000 });
```

An existing stream with a narrower window produces a `warn` record. The
transport cannot rewrite it: retention, storage and limits stay the area
of operations. The acknowledgement of a write carries the `duplicate`
field, and the broker double deduplicates the same way the real one
does, so the tests run without a network.

The deduplication of the broker narrows the flow of repeats and gives no
transactional guarantee: the transport has no transaction of the
application. The claim layer of `@nestlingjs/inbox` stays mandatory.

## Observability

### Traces

The kernel declared the well-known ambient variable `Trace` with the
value `{ traceId, spanId, parentSpanId?, sampled }` and the
`propagate: true` marker. The `withTracing()` pre-step reads the parent
context from `ctx.raw.attributes`, creates the identifier of a span and
puts the variable into the context.

```typescript
// src/observability.ts — 0.2.0
import { makePipeline, withRequestId, withTracing } from '@nestlingjs/app';

export const observability = makePipeline()
  .pre(withRequestId())
  .pre(withTracing())
  .finally(AuditOutcome);
```

The format is W3C trace-context: the `traceparent` header over HTTP and
a field of the envelope over the bus. A logger record carries the
`traceId` field next to `requestId`. The typed HTTP client sends the
`traceparent` of the current context: the client takes a reader as the
`trace` option, and the reader itself is exported by
`@nestlingjs/app`.

```typescript
// src/api/client.ts — 0.2.0
import { traceparent } from '@nestlingjs/app';

export const api = makeClient(
  { createUser: CreateUser, getUser: GetUser },
  { baseUrl, trace: traceparent },
);
```

The variable is put into the context by a step declared in a pipeline,
the same way as `requestId`. Read more in
[chapter 23](../guide/23-tracing.md).

### Metrics

The kernel got the `Metrics` interface with the `counter` and
`histogram` methods, the root DI token `RootMetrics$` and the
`Metrics$(scope)` family, modelled on `Logger$`. The default
implementation does nothing and allocates nothing on the hot path. A
real one is passed by the `makeApp({ metrics })` option.

```typescript
// src/app.ts — 0.2.0
const exporter = prometheusExporter();

export const app = makeApp({
  features: [UsersFeature, QuotasFeature],
  plugins: [metricsPlugin(exporter)],
  transports: [nats({ name: 'events' }), http()],
  metrics: exporter,
});
```

The kernel counts a counter and a duration per endpoint and per caller
invocation on its own. The write happens in the response phase of the
pipeline, where the outcome is known. Instrumentation is switched on by
comparing the root with the empty implementation by reference, so an
application without the option pays nothing for metrics.

The kernel does not know the exposition format. The `split-nats`
example got a Prometheus adapter of sixty lines and a `/metrics`
endpoint: this is how the public boundary of the kernel is shown to be
enough for a third-party exporter.

In 0.3.0 the subsystem is rewritten completely: a metric became a
declaration, and `Metrics`, `RootMetrics$`, `Metrics$` and the
`makeApp({ metrics })` option are removed. What to write today is in
[the 0.3.0 note](./v0.3.0.md).

> Why: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), point 2.

## MCP: an agent tool is an endpoint

The new package `@nestlingjs/mcp` is a satellite transport built on the
public primitives of the kernel. The transport is declared in
`transports:` of the root and attaches to an already declared HTTP
server. No second socket appears: the handler joins the chain of the
server next to the handler of `http()`.

```typescript
// src/app.ts — 0.2.0
import { mcp } from '@nestlingjs/mcp';

export const api = httpServer();

export const app = makeApp({
  features: [UsersFeature],
  transports: [
    api,
    http({ server: api }),
    mcp({
      server: api,
      info: { name: 'users-service', version: '1.0.0' },
      converters: [zodConverter()],
    }),
  ],
});
```

A tool is an endpoint of this transport, and it has two forms, like
every transport.

```typescript
// src/features/users/tools/get-user.tool.ts — 0.2.0
export const GetUserTool = mcpTool.implement(GetUserOperation, {
  annotations: { readOnlyHint: true },
  pipeline: observability,
  handler: GetUserHandler,
});

// src/features/users/tools/search-users.tool.ts — 0.2.0
export const SearchUsersTool = mcpTool('search_users', {
  description: 'Найти пользователей по подстроке в адресе почты',
  annotations: { readOnlyHint: true },
  input: SearchUsersInput,
  output: SearchUsersOutput,
  pipeline: observability,
  handler: SearchUsersHandler,
});
```

The set of tools is the endpoints declared on the MCP transport. There
is no separate `tools:` list: the set is visible where the set of any
other transport is visible. The `tools/list` protocol method is built in
`serve` from the route table, before the server opens the socket. The
schemas are translated into JSON Schema by the same converters that
OpenAPI uses, and the package depends on no validator. The `tools/call`
method executes an endpoint through the dispatch: a tool goes through
the pipeline of its declaration, its layers and its policies.

A failure of an operation reaches the agent as a separate outcome with
the code and the details, not as a protocol exception. Read more in the
recipe [“Expose the operations to an agent over MCP”](../recipes/mcp.md).

## Schemas and OpenAPI

### `@nestlingjs/openapi.zod` became `@nestlingjs/schema.zod`

The converter package is renamed. The exports did not change:
`zodConverter` and `ZodConverterOptions`.

```typescript
// 0.1.3
import { zodConverter } from '@nestlingjs/openapi.zod';

// 0.2.0
import { zodConverter } from '@nestlingjs/schema.zod';
```

The converter serves more than the document — from this release the
command line transport asks for it to build the questions about a
missing input.

> Upgrade: mechanical — the name of the package changes in the manifest
> and in the imports, and the exports are the same.
> Why: [ideas.md, `[2026-09-12] Имя пакета-конвертера не называет потребителя: openapi.zod → schema.zod`](../../decisions/ideas.md#2026-09-12-%D0%B8%D0%BC%D1%8F-%D0%BF%D0%B0%D0%BA%D0%B5%D1%82%D0%B0-%D0%BA%D0%BE%D0%BD%D0%B2%D0%B5%D1%80%D1%82%D0%B5%D1%80%D0%B0-%D0%BD%D0%B5-%D0%BD%D0%B0%D0%B7%D1%8B%D0%B2%D0%B0%D0%B5%D1%82-%D0%BF%D0%BE%D1%82%D1%80%D0%B5%D0%B1%D0%B8%D1%82%D0%B5%D0%BB%D1%8F-openapizod--schemazod).

### A parameter is described by the parsed shape

A parameter with `in: 'path'` or `in: 'query'` is described by the
schema of the parsed shape when that shape is scalar. Previously it was
always described by the input shape, and a field with a string on input
got `type: 'string'` in the document.

```typescript
// src/api/operations.ts — the schema of the field
const CreateUserInput = z.object({
  dryRun: z.stringbool().optional(),
});
```

```json
// openapi.json — 0.1.3
{ "name": "dryRun", "in": "query", "schema": { "type": "string" } }
```

```json
// openapi.json — 0.2.0
{ "name": "dryRun", "in": "query", "schema": { "type": "boolean" } }
```

The `input` schema is converted up to two times. The run with
`io: 'input'` stays the source of the body and of the requiredness of
parameters. The run with `io: 'output'` gives the parameter schemas and
starts only when the bind map moves at least one field into the path or
into the query. A property is carried over whole: `description`,
`default` and the constraints come along with the type.

A schema with a transform fails on the second run, and the parameter
stays described by the input shape. The build does not fall because of
that: the input is already described by the first run. The request body
is described by the input shape after the change as well — in JSON a
string is a string. Read more in
[chapter 13](../guide/13-openapi-and-client.md).

## CLI: a missing input is asked for

`cliEndpoint` takes the `missing: 'error' | 'prompt'` field. The default
is `'error'`, so a command without the field behaves as before.

```typescript
// src/commands/deploy.command.ts — 0.2.0
const DeployInput = z.object({
  env: z.enum(['dev', 'prod']).describe('Target environment'),
  force: z.boolean().describe('Skip the safety checks'),
  host: z.string().describe('Deployment host').meta({ default: 'localhost' }),
});

export const Deploy = cliEndpoint('deploy', {
  input: DeployInput,
  output: DeployOutput,
  missing: 'prompt',
  handler: async ({ env, force, host }) => ({ env, host, forced: force }),
});
```

The transport builds a plan of questions on `serve` for every command
with `missing: 'prompt'`. A question is derived from the shape of the
field: `enum` gives a choice from a list, `boolean` gives a
confirmation, and a scalar gives a string input. The description of a
field becomes the prompt, and the default becomes the value for
“Enter”. Only the missing required fields of the top level of a scalar
shape are asked about. The answer is substituted in the same form in
which a flag would have given it.

A non-interactive environment switches the questions off: the command
answers with a validation failure if the input stream is not a terminal
or the `CI` variable is set. A command with a streaming input and
`missing: 'prompt'` fails `serve`: the questions and the stream read one
`stdin`.

The `cli()` factory took four options: `converters` for the schemas of
commands with questions, `interactive` for an explicit decision instead
of detection by the environment, and `input` and `output` for the
streams instead of `process.stdin` and `console`. Read more in the
recipe [“A CLI tool on the same primitives”](../recipes/cli.md).

## Runtime strings are English

Everything that the process prints or hands outside is written in
English: failure messages, logs, the reasons of `hidden` and `detached`,
and the `summary` and `description` of the built-in operations. README
files, JSDoc, comments and documentation stay Russian.

The rule is held by the linter rather than by discipline: the shared
ESLint configuration forbids Cyrillic in string literals and template
strings of `src/` files. Specs, fixtures and examples are out of the
scope of the rule.

Four fixes shipped together with the translation. An empty HTTP response
carries `content-length: 0` for every status except 204 and 304, so a
redirect stopped leaving with `transfer-encoding: chunked`. The class
shape diagnostic of `@Component` stopped firing on `any`. Three JSDoc
comments stopped naming the non-existent `Ok.of` method. The
`find-my-way` package was raised to `^9.7.0`, where the
GHSA-c96f-x56v-gq3h advisory is closed.

## Testing

- `spyMetrics()` from `@nestlingjs/testing` records metrics as values,
  modelled on `spyLogger()`.
- The snippets of the agent skill are built rather than only compiled:
  the spec calls `assembleTest` for the application made of the
  snippets, so `yarn verify` catches a policy, an undeclared layer and
  an edge between features.
- The in-memory `InboxStore` implementation lives under the
  `@nestlingjs/inbox/testing` subpath.
- The NATS broker double deduplicates by the window of a stream, so the
  tests of durable delivery run without a network.
- The specs of the example with a database are skipped without the
  `DATABASE_URL` variable, and CI runs PostgreSQL as a service.

subsystem: [the 0.3.0 note](./v0.3.0.md).

## For those who build the repository

Publication to the registry goes through an OIDC exchange with a trusted
publisher. The `NPM_TOKEN` secret and the `NODE_AUTH_TOKEN` variable are
removed from the publication process. The first publication of a new
name is performed by a person from a workstation with
`node scripts/publish.mjs --interactive`, which asks for a 2FA code
before sending each tarball.

`@nestlingjs/eslint-plugin` got a third rule, `dependency-list`. It
derives the expected list of DI tokens from the types of the constructor
parameters and compares it with the list in the role decorator. The rule
is syntactic and works at the `warn` level: the compiler stays the
guarantee. A length mismatch is always reported, an empty list is fixed
by an autofix, and a replacement of a written DI token is offered as a
suggestion. The rule is enabled in the shared configuration of the
repository.
