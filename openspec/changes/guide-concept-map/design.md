## Context

Гайд (`docs/guide/`) сейчас открывается двумя абзацами философии («каждая
глава раскрывает ровно те возможности, без которых задача не решается») и
разделом «Как читать», который объясняет порядок частей и связь с
`packages/examples.*`. Дальше сразу идёт таблица «Что проверяется до
первого запроса» и оглавление по частям 1–5. Ни разу до части 1 читателя
не знакомят со словарём: термины (endpoint, фича, токен, слой…) появляются
только там, где их вводит соответствующая глава — это работает для
читателя без опыта, но читателя с опытом NestJS оставляет без ориентира,
чем Nestling отличается от знакомого словаря и какой объём понятий вообще
предстоит выучить.

Приложение Б (`appendix-b-from-nestjs.md`) уже отвечает на вопрос «чем в
Nestling записывается то, что в NestJS я делал вот так» построчными
соответствиями. Приложение В (`appendix-c-coverage.md`) уже содержит
полную карту «понятие → глава → файл примера» на 24 главы. Обоих
приложений не видно, пока читатель не долистает README до раздела
«Приложения» в конце.

Решение зафиксировано в `docs/decisions/ideas.md`, запись «[2026-09-04]
Подача гайда: соответствия из NestJS вторым документом, карта понятий в
начале» (строка 4705 на момент записи): README называет приложение Б
вторым документом сразу после вводного абзаца, а раздел «Карта понятий» —
сокращённая версия приложения В на один экран — переносится в начало
README. Формулировка принципа прогрессивного раскрытия в
`docs/design/principles.md` уже приведена к смягчённому виду («фича стоит
одну строку и не требует понимать, зачем она, пока фич одна») отдельной
синхронизацией design/ — здесь это факт, а не задача change.

Ограничение, из-за которого этот change вообще нужен как отдельный
документ, а не правка одной строкой: README гайда — не свободный текст, а
источник данных для `scripts/preview/build.mjs` (см. D3) и для инвариантов
`.claude/skills/docs-audit/scripts/check.mjs` (см. D4). Любая правка его
структуры обязана пройти через понимание того, что именно эти скрипты в
нём парсят.

## Goals / Non-Goals

**Goals:**

- README гайда сразу после вводного абзаца называет приложение Б вторым
  документом для читателя с опытом Nest, одной-двумя фразами со ссылкой.
- README гайда получает раздел «Карта понятий»: таблица «понятие | одно
  предложение | глава» на один экран (около 20–25 строк), понятия — из
  `docs/glossary.md`, порядок — порядок появления в частях 1–4.
- `yarn docs:preview` и `yarn docs:audit` остаются зелёными после правки:
  новый раздел не создаёт лишних страниц превью и не путает инварианты
  аудита.
- Приложение В остаётся единственным полным справочником: раздел в README
  не дублирует его состав построчно, а даёт сокращённый набор понятий с
  одним предложением на каждое.

**Non-Goals:**

- Переименование или слияние понятий (модуль, слой, юнит и другие) — вне
  объёма, отвергнуто записью ideas.md.
- Новые главы гайда.
- Перевод гайда.
- Правки глав 1–25 и приложений А, Б, В сверх двух текстов в README:
  меняется только `docs/guide/README.md`.
- Правка `docs/design/principles.md` — уже сделана отдельной
  синхронизацией, не задача этого change.

## Decisions

### D1. Место двух вставок в README

README сегодня открывается так: абзац философии → абзац о читателе и
глоссарии → раздел «Как читать» → «Что проверяется до первого запроса» →
части 1–5 → «Приложения».

Фраза про приложение Б встаёт сразу после первого (вводного) абзаца —
перед абзацем о читателе, а не внутри него. Первый абзац объясняет, что
такое гайд и как устроено раскрытие понятий, и ничего не говорит о
читателе; второй абзац впервые называет опыт Nest/Express и так уже несёт
ссылки на глоссарий и `design/` — удлинять его не нужно. Одна-две фразы,
без списка:

> Если вы писали на NestJS, начните со [приложения Б «Из
> NestJS»](./appendix-b-from-nestjs.md): там собраны построчные
> соответствия для знакомых понятий.

Раздел «Карта понятий» встаёт после «Как читать» и перед «Что
проверяется до первого запроса». «Как читать» — три коротких абзаца о
порядке частей; это первое, что нужно читателю механически, до любого
содержания. «Что проверяется до первого запроса» уже использует термины
(слой, фаза, ASSEMBLE, `select`) без определений. Карта понятий,
поставленная перед этой таблицей, даёт словарь до первого термина без
определения — в этом смысле она и «в начале» по записи ideas.md: до
первого содержательного раздела, но после навигационного.

Альтернатива — карта сразу после абзаца об опыте Nest, перед «Как
читать» — отклонена: читателю порядок частей нужен раньше словаря, а
таблица на 20+ строк раньше трёх абзацев навигации хуже держит внимание.

### D2. Состав таблицы «Карта понятий»

Колонки — «Понятие | Одно предложение | Глава», как задано в записи
ideas.md. Источник понятий — `docs/glossary.md`; формулировка предложения
для каждого — сокращение определения из глоссария до одной фразы с
глаголом (по правилу `docs-style` «одно предложение — одна мысль»).
Колонка «Глава» — ссылка на первую главу, где понятие вводится, в формате
`[N](./NN-имя.md)`, как в существующей таблице «Что проверяется до
первого запроса»: ссылка стоит в последней колонке, а не в первой.

Порядок строк — порядок появления понятия в гайде, части 1–4 (главы
1–18); часть 5 не входит — её понятия нишевые. Целевой размер — один
экран, около 20–25 строк: не полный список приложения В (70+ строк), а
понятия, без которых не читается ни одна из частей 1–4.

Черновой состав по частям (формулировки уточняются при `/opsx:apply`
прогоном `docs-style`; здесь фиксируется состав и источник, не текст):

проверяется до первого запроса», которая стоит сразу после карты понятий,
— повторять его здесь означало бы дублирование двух соседних разделов.

### D3. Почему раздел не ломает `yarn docs:preview`

`scripts/preview/build.mjs` строит навигацию функцией `readOutline`
(строки 145–178). Группу задаёт заголовок, прошедший регэксп
`^##\s+(Часть\s+\d+\.[^\n]*|Приложения)\s*$` (строка 150); «## Карта
понятий» под него не подходит — `group` после него не меняется, ошибки
это не вызывает само по себе. `BuildError` «стоит вне раздела „Часть N“
или „Приложения“» (строки 161–166) бросается только на строке таблицы,
похожей на ссылку на главу — а такая строка в разделе «Карта понятий» не
встречается (см. ниже), поэтому пустой `group` до части 1 не долетает до
проверки.

Строки таблицы становятся страницами, только если первая ячейка
совпадает с `^\|\s*\[([^\]]+)\]\(\.\/([\w-]+)\.md\)` (строка 156) —
ссылка на главу должна быть первой ячейкой. В таблице «Карта понятий»
первая ячейка — понятие (текст или код, `` `makeApp` ``), а ссылка на
главу стоит в последней колонке — тем же приёмом, что уже применён в
существующей таблице «Что проверяется до первого запроса» (её строки
тоже не становятся страницами). Ни одна строка «Карты понятий» не
попадёт в `pages`, `assertComplete` (строки 187–209) не увидит новых
страниц — новых `BuildError` нет.

`sectionsOf` (строки 245–259) при рендере README как `index.html`
соберёт «## Карта понятий» в список `##`-заголовков страницы — так же,
как уже собирает «## Как читать». Это добавляет пункт в подсписок
сайдбара `index.html`; `anchorHeadings` (строки 275–287) проставит ему
`id` тем же алгоритмом. Поведение аддитивное. Задача 3 в `tasks.md`
подтверждает это прогоном `yarn docs:preview` и просмотром
`docs/preview/index.html`.

Это поведение парсера сегодня нигде не зафиксировано как гарантия — оно
случайное следствие формы регэкспов. Раздел «Карта понятий» впервые
опирается на него по существу, поэтому по принципу «guarantee over
convention» change добавляет явное требование в
`specs/docs-preview-guide/spec.md` (`ADDED Requirements`, см. proposal.md,
Modified Capabilities): заголовки `##` вне «Часть N.»/«Приложения» не
создают группу и не ломают сборку; строка без ссылки на главу в первой
ячейке не становится страницей. Существующие три требования спеки не
меняются.

### D4. Почему раздел не ломает `yarn docs:audit`

`.claude/skills/docs-audit/scripts/check.mjs`, блок «Карты полны в обе
стороны» (строки 108–128), строит множество `listed` из **любых** ссылок
вида `](./имя.md` в README (строка 117), не только из первой ячейки
таблицы. Новые ссылки — на приложение Б (D1) и на 25 глав в колонке
«Глава» (D2) — все ведут на файлы, уже перечисленные в оглавлении.
Множество `listed` не теряет и не приобретает файлов сверх уже
перечисленных, проверки строк 118–127 остаются выполненными без
изменений.

Блок «Относительные ссылки резолвятся» (раздел 4 скрипта) проверяет
существование целевых файлов для каждой ссылки README, включая новые;
все они указывают на реально существующие файлы той же папки, битых нет.
Плашка «сверено с кодом» (блок 2 скрипта) README не касается: проверка
идёт только по главам вне `appendix-*` и `README.md` (`chapterFiles` в
скрипте).

### D5. Отношение к приложению В и повтору названия «Карта понятий»

Раздел README и приложение В называются одинаково — оба «Карта понятий»,
так решено записью ideas.md. Дублирования по содержанию нет: раздел
README — 25 строк с одним предложением на понятие и только для частей
1–4; приложение В — свыше 70 строк с главой и файлом примера для каждого
понятия всех пяти частей, без определений. Раздел README открывается
фразой, указывающей на приложение В как полный список (по образцу
абзаца, которым уже открывается само приложение В: «Собрано по главам
гайда»), чтобы читатель, которому нужен файл примера, сразу знал, куда
идти. Одинаковое название — сознательный выбор записи (короткая и полная
версии одного среза, а не два разных понятия), а не недосмотр; в
навигации превью (D3) это не создаёт технической коллизии — только
смысловую, снятую вводной фразой.

## Risks / Trade-offs

- [Читатель путает раздел README «Карта понятий» и одноимённое приложение
  В] → вводная фраза раздела сразу ссылается на приложение В как на
  полный список; кросс-ссылка достаточна, переименования не требует
  (см. D5, Non-Goals).
- [Таблица на 25 строк не умещается на «один экран» на узких ширинах
  превью] → строки короткие, а таблицы превью уже скроллятся по
  горизонтали (`table_open`/`table_close` в `build.mjs`); вертикальная
  прокрутка — обычное поведение README.
- [Формулировки «одно предложение» разойдутся с глоссарием при следующей
  правке терминов] → синхронность — предмет `docs:audit` (семантический
  слой) и будущих правок глоссария, а не разовая гарантия этого change.
- [Черновой состав таблицы D2 разойдётся с финальным при `/opsx:apply`] →
  состав и источник зафиксированы (глоссарий, порядок появления, части
  1–4), точная формулировка — предмет апрувной сессии, не архитектурный
  риск.

## Open Questions

- Нужна ли отдельная подпись над таблицей о том, что порядок — «порядок
  появления», или достаточно того, что колонка «Глава» уже читается по
  возрастанию. По умолчанию — не указывать отдельно.
- Стоит ли строка «вызыватель, эмиттер» разбиваться на две, если при
  апруве рецензент сочтёт склейку `Operation.caller` и `Operation.emitter`
  в одну строку вводящей в заблуждение. По умолчанию — одна строка
  (см. D2); решение принимается при ревью формулировок в `/opsx:apply`.
