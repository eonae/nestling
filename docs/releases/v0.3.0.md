# 0.3.0

> Все пакеты `@nestlingjs/*` выходят одной версией. В выпуск вошли
> коммиты от тега `v0.2.0` до тега `v0.3.0`, 13–14 сентября 2026. Старое
> имя удалено вместе с появлением замены: алиасов и обёрток в пакетах
> нет.

## Обновление

```bash
yarn up '@nestlingjs/*'
```

Версия одна на все пакеты: пакет прошлой версии рядом с новым не
работает. Требование к Node прежнее — 24 и выше. Три новых пакета
ставятся отдельно, по надобности:

```bash
yarn add @nestlingjs/logging.pino pino  # логгер поверх pino
yarn add @nestlingjs/prometheus         # экспозиция метрик
yarn add @nestlingjs/otel               # участки трассы и push метрик
```

`@nestlingjs/logging` приходит зависимостью ядра и отдельной установки
не требует. `pino` — peer-зависимость `^10.0.0`. Экспортёры
OpenTelemetry приложение ставит само: `@nestlingjs/otel` несёт SDK, но
не пакеты `exporter-*`. Полный справочник окружения —
[compatibility.md](../compatibility.md).

## Коротко

- Точка входа записывается `build(argv(process.argv))` вместо
  `assemble(load(RootConfig))`, и состав процесса приходит флагами
  командной строки — [раздел](#сборка-и-запуск).
- Привязки конфигурации переехали из `makeApp` в `run({ config })`,
  форма привязки одна — `bind()` — [раздел](#сборка-и-запуск).
- Сервер объявляется `server()` и в `transports:` не перечисляется —
  [раздел](#сборка-и-запуск).
- Успешный статус объявляется полем `status`, разные тела у разных
  исходов — развилкой `outputs({ … })` —
  [раздел](#декларация-endpointа).
- Отказ по HTTP уходит документом RFC 9457 под медиатипом
  `application/problem+json` — [раздел](#декларация-endpointа).
- Логгер объявляется опцией `logging`, поля корреляции ставит ядро;
  появились пакеты `@nestlingjs/logging` и `@nestlingjs/logging.pino` —
  [раздел](#логирование).
- Метрика стала декларацией с DI-токеном: экспозицию даёт
  `@nestlingjs/prometheus`, push и участки трассы — `@nestlingjs/otel` —
  [раздел](#метрики-и-трассы).
- Фабрика плагина называется `make*` — [раздел](#имена).
- Примеров три вместо шести, у сайта документации новая тема —
  [раздел](#примеры-и-документация).

## Точка входа: было и стало

Два файла показывают большую часть переименований разом.

```typescript
// src/app.ts — 0.2.0
import { makeApp } from '@nestlingjs/app';
import { openapi } from '@nestlingjs/openapi';
import { zodConverter } from '@nestlingjs/schema.zod';
import { http, httpServer } from '@nestlingjs/transport.http';

const api = httpServer();

export const app = makeApp({
  features: [UsersFeature],
  plugins: [
    openapi({
      info: { title: 'Users API', version: '1.0.0' },
      converters: [zodConverter()],
    }),
  ],
  transports: [api, http({ server: api })],
  config: [[vault, appConfigKeys]], // process.env читался последним всегда
  logger: pinoAdapter(pino()), // адаптер приложение писало само
  metrics: prometheusExporter(), // и экспортёр метрик тоже
});

// src/main.ts — 0.2.0
const cfg = load(RootConfig); // секция с APP_FEATURES, прочитанная до сборки

await app.assemble({ ...cfg, includeDeps: true }).run();
```

```typescript
// src/app.ts — 0.3.0
import { makeApp } from '@nestlingjs/app';
import { pinoLogger } from '@nestlingjs/logging.pino';
import { makeOpenapi } from '@nestlingjs/openapi';
import { makePrometheus } from '@nestlingjs/prometheus';
import { http, server } from '@nestlingjs/transport.http';

const api = server();

export const app = makeApp({
  features: [UsersFeature],
  plugins: [
    makeOpenapi({ info: { title: 'Users API', version: '1.0.0' } }),
    makePrometheus(),
  ],
  transports: [http({ server: api })],
  logging: { logger: pinoLogger() },
});

// src/main.ts — 0.3.0
import { argv, bind, defaultSources } from '@nestlingjs/app';

await app.build(argv(process.argv)).run({
  config: [bind(vault, { keys: appConfigKeys }), ...defaultSources],
});
// node main.js --features users --include-deps
```

Дальше каждое изменение описано отдельно: что стало, как этим
пользоваться и где читать подробности.

## Ломается молча

Эти изменения компилятор не покажет: код собирается и ведёт себя иначе.

- Список в `run({ config })` заменяет умолчание целиком, и прежнее
  неявное чтение `process.env` в конце списка пропадает —
  [раздел](#привязки-конфигурации--опция-run).
- Пустое значение ключа означает отсутствующее: `DB_POOL_MAX=` даёт
  умолчание, а не ноль —
  [раздел](#zod-внутри-фреймворка-standard-schema-на-границе).
- Тело отказа по HTTP сменило форму: поля `code` в нём нет, код отказа
  лежит в члене `type`. Чужой клиент, который читает `code`, ломается на
  рантайме — [раздел](#тело-отказа-по-http--документ-rfc-9457).
- `Ok` со статусом вне объявленного множества граница заменяет на
  `internal_error`: вызов из JavaScript типами не прикрыт —
  [раздел](#успешный-статус--поле-декларации).
- Тестовый прогон стал тихим: `buildTest` поднимает приложение с уровнем
  `silent`, и прежний вывод теста пропадает — [раздел](#тестирование).

## Сборка и запуск

### `build` вместо `assemble`

Метод декларации, который собирает приложение, называется `build`.
Аргумент называется `BuildArgs`, результат — `BuiltApp`. Фаза жизненного цикла
`1 ASSEMBLE` называется `1 BUILD`, и тексты отказов сборки называют её
так же. То же слово ушло из соседних пакетов: `assembleTest` стал
`buildTest`, `assemblePayload` — `buildPayload`.

Вместе с методом сменился словарь пайплайна. Единица пайплайна
называется шагом, и типы названы по нему: `PreStepFn`, `FinallyStepFn`,
`DeferredPreStepFn`, `StepResolver`, `InboxClaimStep`. Функция
`testUnit` из `@nestlingjs/testing` называется `testBundle`: она
поднимает фичу или плагин, а не шаг. Полный список —
[таблица переименований](#renames) в конце.

> Обновление: механическое — `assemble` заменяется на `build`, словарь
> пайплайна идёт за ним по [таблице переименований](#renames).
> Почему: [ideas.md, `[2026-09-13] Термины: шаг, токен семейства, build`](../decisions/ideas.md#2026-09-13-%D1%82%D0%B5%D1%80%D0%BC%D0%B8%D0%BD%D1%8B-%D1%88%D0%B0%D0%B3-%D1%82%D0%BE%D0%BA%D0%B5%D0%BD-%D1%81%D0%B5%D0%BC%D0%B5%D0%B9%D1%81%D1%82%D0%B2%D0%B0-build).

### Аргумент сборки приходит из командной строки

`argv(process.argv)` — значение-маркер из `@nestlingjs/app`. Точка входа
передаёт им командную строку в `build`, `discover` или `check`, а схему
флагов сборка выводит из декларации. `--features` принимает `all` или
имена фич через запятую, `--include-deps` добирает фичи, чьи операции
вызывают выбранные, каждый переключатель становится флагом со своим
именем и значениями из `makeSwitch`. Неизвестный флаг, неизвестная фича
и значение вне перечня — отказ до фазы 0. `--help` печатает схему и
завершает процесс кодом 0.

```typescript
// src/main.ts — 0.2.0
const RootConfig = makeConfig('root', {
  features: from('APP_FEATURES', z.string().default('all')),
  docs: from('APP_DOCS', Docs.schema),
});

const cfg = load(RootConfig);

await app.assemble({ ...cfg, includeDeps: true }).run();
```

```typescript
// src/main.ts — 0.3.0
await app.build(argv(process.argv)).run();
// node main.js --features users --include-deps --docs off
// node main.js --help
```

Объектная форма `build({ features: 'users', docs: 'off' })` остаётся: ею
пользуются тесты и приложение со своим разбором командной строки.
Строковая форма `build('users')` и массив имён
`build(['users', 'billing'])` удалены. Функция `load()` удалена: её
единственной ролью было чтение секции до сборки ради аргумента сборки.
Ядро больше не читает ни `process.argv`, ни `process.env` само: первое
передаёт точка входа маркером, второе читает источник `env()`.

Отсюда гарантия, записанная в [guarantees.md](../guarantees.md): состав
процесса определяет только аргумент сборки, конфигурация на него не
влияет. Подробнее — [глава 19](../guide/19-select.md).

> Обновление: требует решения — состав процесса приходит либо маркером
> `argv()`, либо объектной формой у приложения со своим разбором
> командной строки.
> Почему: [ideas.md, `[2026-09-13] Аргумент сборки: argv() по схеме декларации`](../decisions/ideas.md#2026-09-13-%D0%B0%D1%80%D0%B3%D1%83%D0%BC%D0%B5%D0%BD%D1%82-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B8-argv-%D0%BF%D0%BE-%D1%81%D1%85%D0%B5%D0%BC%D0%B5-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8).

### Привязки конфигурации — опция `run()`

Поле `config:` у `makeApp` удалено. Привязки источников принимает метод,
который запускает приложение: `run({ config })`. Та же опция есть у
`check(args, { config })` и `buildTest(app, { config })`.

```typescript
// src/main.ts — 0.2.0
const app = makeApp({
  features: [AppFeature],
  config: [
    [defaults, appConfigKeys],
    [runtime, runtimeConfigKeys],
  ],
}).assemble();

await app.run();
```

```typescript
// src/main.ts — 0.3.0
const app = makeApp({ features: [AppFeature] }).build();

await app.run({
  config: [
    bind(defaults, { keys: appConfigKeys }),
    bind(runtime, { keys: runtimeConfigKeys }),
    bind(env()),
  ],
});
```

Форма привязки одна: `bind(source, { keys?, optional?, timeout? })`.
`keys` — `.keys` секции или глоб, по умолчанию `'*'`. `optional`
пропускает привязку, если источник не поднялся. `timeout` ограничивает
`init()` источника, по умолчанию десятью секундами. Кортеж
`[source, target]`, объединение `ConfigInput`, `isBinding()` и
`toBindings()` удалены.

Без опции `run()` берёт `defaultSources` — публичное значение
`[bind(env()), bind(dotenv('.env'), { optional: true })]`: окружение
выше файла, файл необязателен. Список в опции заменяет умолчание
целиком, поэтому свой источник дописывается рядом с ним:
`config: [bind(vault, { keys }), ...defaultSources]`.

`env()` стал обычным источником: `process.env` ядро читает только внутри
него, неявного чтения в конце списка больше нет. `dotenv(path)` — новый
источник ядра на `parseEnv` из `node:util`; отсутствие файла у
обязательной привязки — отказ фазы 0 с путём в сообщении.

`objectSource` переехал в `@nestlingjs/testing` под именем
`vars(values, name?)`. Тестовое приложение доходит до фазы RUN:
`testApp.run()` открывает сокет, `testApp.baseUrl(name?)` отдаёт его
адрес. Умолчания у тестового корня нет: без `config` тест не читает ни
окружения, ни файла. Подробнее — [глава 7](../guide/07-config.md) и
рецепт [«Конфиг из файла и без перезапуска»](../recipes/config-sources.md).

> Обновление: требует решения — список в `config` заменяет умолчание
> целиком, поэтому свой источник дописывается рядом с `defaultSources`.
> Почему: [ideas.md, `[2026-09-13] Конфигурация: привязки на run(), env() и dotenv() умолчанием, bind(), needs у источника`](../decisions/ideas.md#2026-09-13-%D0%BA%D0%BE%D0%BD%D1%84%D0%B8%D0%B3%D1%83%D1%80%D0%B0%D1%86%D0%B8%D1%8F-%D0%BF%D1%80%D0%B8%D0%B2%D1%8F%D0%B7%D0%BA%D0%B8-%D0%BD%D0%B0-run-env-%D0%B8-dotenv-%D1%83%D0%BC%D0%BE%D0%BB%D1%87%D0%B0%D0%BD%D0%B8%D0%B5%D0%BC-bind-needs-%D1%83-%D0%B8%D1%81%D1%82%D0%BE%D1%87%D0%BD%D0%B8%D0%BA%D0%B0).

### Сервер объявляется `server()` и в `transports:` не входит

`httpServer()` называется `server()`, `httpServerKeys()` — `serverKeys()`.
Имя экземпляра по умолчанию осталось `'default'`, секция конфигурации —
семейством `http` (`HTTP_PORT`, `HTTP_HOST`).

```typescript
// src/app.ts — 0.2.0
export const api = httpServer();

export const app = makeApp({
  features: [UsersFeature, OpsFeature],
  transports: [api, http({ server: api }), mcp({ server: api })],
});
```

```typescript
// src/app.ts — 0.3.0
export const api = server();

export const app = makeApp({
  features: [UsersFeature, OpsFeature],
  transports: [http({ server: api }), mcp({ server: api })],
});
```

Поле `transports:` принимает только транспорты. Сервер попадает в сборку
по ссылке `server` транспорта: один сервер на два транспорта создаётся
один раз, а сервер без ссылок не создаётся вовсе. Сервер, перечисленный
в списке транспортов, отвергается на фазе BUILD сообщением с заменой.
Тип `TransportEntry` и предикат `isTransport` удалены.

> Обновление: механическое — `httpServer()` становится `server()`, а сам
> сервер уходит из списка транспортов.
> Почему: [ideas.md, `[2026-09-13] Сервер: server(), не перечисляется в transports:`](../decisions/ideas.md#2026-09-13-%D1%81%D0%B5%D1%80%D0%B2%D0%B5%D1%80-server-%D0%BD%D0%B5-%D0%BF%D0%B5%D1%80%D0%B5%D1%87%D0%B8%D1%81%D0%BB%D1%8F%D0%B5%D1%82%D1%81%D1%8F-%D0%B2-transports).

## Декларация endpoint'а

### Успешный статус — поле декларации

Успешный статус объявляется полем `status` верхнего уровня у
`httpEndpoint` и у конструктора операции. Поле `doc.status` удалено:
статус — контракт ответа, а не строка документации. Умолчание одно на
рантайм, документ и клиент: `ok` при объявленном `output`, `no_content`
без него.

```typescript
// src/users/operations.ts — 0.2.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: User,
  doc: { summary: 'Создать пользователя', status: 'created' },
});
```

```typescript
// src/users/operations.ts — 0.3.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: User,
  status: 'created',
  doc: { summary: 'Создать пользователя' },
});
```

Голое значение из хендлера получает объявленный статус. `Ok`
параметризован статусом: `Ok<TValue, TStatus>`. `new Ok(value)` даёт
`Ok<T, 'ok'>`, `Ok.created(value)` — `Ok<T, 'created'>`,
`Ok.accepted(value)` — `Ok<T, 'accepted'>`, `Ok.noContent()` —
`Ok<null, 'no_content'>`. `Ok` со статусом вне объявленного множества
граница заменяет на `internal_error`: вызов из JavaScript типами не
прикрыт.

Разные тела у разных исходов объявляет развилка в слоте `output`:

```typescript
// src/users/operations.ts — 0.3.0
export const CreateUser = makeRequest({
  name: 'users.create',
  input: CreateUserInput,
  output: outputs({ ok: User, created: User, no_content: none() }),
  // …
});
```

Ключи развилки — статусы из словаря ядра (`ok`, `created`, `accepted`,
`no_content`), значения — формы io, `none()` объявляет исход без тела.
Хендлер с развилкой выбирает исход явно, возвращая `Ok.created(user)`
или `new Ok(user)`; голое значение при развилке не компилируется, а
результат хендлера — union по полю `status`. Потоковые формы `stream` и
`events` объявляются только единственным исходом.

Документ OpenAPI печатает ответ на каждый объявленный исход со своей
схемой. Типизированный клиент валидирует тело схемой пришедшего исхода
и отвергает код вне объявленного множества как расхождение с
декларацией. Подробнее — [глава 4](../guide/04-errors.md) и
[глава 13](../guide/13-openapi-and-client.md).

> Обновление: механическое — `doc.status` поднимается на верхний уровень
> декларации полем `status`.
> Почему: [deferred.md, `[2026-08-01] Типизированный успешный статус декларации`](../decisions/deferred.md#2026-08-01-%D1%82%D0%B8%D0%BF%D0%B8%D0%B7%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D1%8B%D0%B9-%D1%83%D1%81%D0%BF%D0%B5%D1%88%D0%BD%D1%8B%D0%B9-%D1%81%D1%82%D0%B0%D1%82%D1%83%D1%81-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8).

### Тело отказа по HTTP — документ RFC 9457

HTTP-граница отвечает на отказ документом Problem Details под медиатипом
`application/problem+json`.

```bash
# 0.2.0
curl localhost:3000/users/9
# {"error":"User 9 not found","code":"not_found:user","details":{"id":"9"}}
```

```bash
# 0.3.0
curl -i localhost:3000/users/9
# HTTP/1.1 404 Not Found
# content-type: application/problem+json
#
# {"type":"urn:error:not_found:user","title":"Not Found","status":404,
#  "detail":"User 9 not found","details":{"id":"9"}}
```

Поля `code` в теле нет: код отказа лежит в члене `type`.

| Член | Что несёт |
|---|---|
| `type` | код отказа с префиксом `urn:error:` |
| `title` | фраза статуса HTTP |
| `status` | код HTTP числом |
| `detail` | сообщение отказа |
| `details` | детали по схеме определения |
| `stack` | расширение, только при `exposeErrorDetails` |

Форма одна на все три места, где граница пишет отказ: ответ хендлера, ошибка
до пайплайна (битый JSON, превышенный `maxBodySize`) и кадр
`event: error` в SSE.

Клиент `@nestlingjs/client` восстанавливает отказ из документа, документ
OpenAPI описывает отказы медиатипом `application/problem+json`. Сам
формат лежит в `@nestlingjs/operations` — `PROBLEM_MEDIA_TYPE`,
`PROBLEM_TYPE_PREFIX`, `problemOf`, `problemTypeOf`, `problemTitleOf` и
тип `ProblemDocument` — и реэкспортируется транспортом. Транспорты
NATS, CLI и MCP сериализуют отказ по-прежнему.

> Обновление: требует решения — свой потребитель API читает код отказа из
> члена `type`; типизированный клиент `@nestlingjs/client` переходит сам.
> Почему: [deferred.md, `[2026-07-14] Wire-формат ошибок: RFC 9457`](../decisions/deferred.md#2026-07-14-wire-%D1%84%D0%BE%D1%80%D0%BC%D0%B0%D1%82-%D0%BE%D1%88%D0%B8%D0%B1%D0%BE%D0%BA-rfc-9457-problemjson).

### `errorsOf` подключает отказы соседней операции

`errorsOf(operation)` из `@nestlingjs/operations` отдаёт список `errors:`
операции тем же значением; тип результата сохраняет union конкретных
определений `makeFail`.

```typescript
// src/users/operations.ts — 0.2.0: отказ соседа копировался руками
import { AddressRejected } from '../addresses/operations.js';

errors: [EmailTaken, AddressRejected, Unauthorized],
```

```typescript
// src/users/operations.ts — 0.3.0
errors: [EmailTaken, ...errorsOf(CheckAddress), Unauthorized],
```

Список читается с декларации, поэтому новый отказ у `CheckAddress`
попадает в `CreateUser` без правки. Подробнее —
[глава 14](../guide/14-features.md).

## Логирование

### Опция `logging` и пакет `@nestlingjs/logging`

Опция корня `logger:` заменена на `logging: { logger?, fields? }`.
`logger` — готовая реализация `Logger`, умолчание прежнее: штатный
логгер в `stderr`. `fields` — список переменных контекста, значения
которых ядро подмешивает в каждую запись. Умолчание —
`[RequestId, logField(Trace, 'traceId', (trace) => trace.traceId)]`.

```typescript
// src/app.ts — 0.2.0
export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logger: myLogger, // requestId и traceId писал только штатный логгер
});
```

```typescript
// src/app.ts — 0.3.0
export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logging: {
    logger: myLogger,
    fields: [
      RequestId,
      logField(Trace, 'traceId', (trace) => trace.traceId),
      logField(TenantId, 'tenant'),
    ],
  },
});
```

Поля корреляции ставит ядро декоратором вокруг логгера, поэтому любая
реализация получает `requestId` и `traceId`, не зная внутренностей
ядра. `logField(Var, name, select?)` задаёт имя поля и выбирает из
значения нужную часть; переменная без обёртки даёт поле с именем
переменной. Плагин объявляет свои поля полем `logFields`; два поля с
одним именем — отказ сборки с именами объявивших.

Интерфейс `Logger` и типы `Fields`, `LogLevel`, `LogMethod` переехали в
пакет `@nestlingjs/logging` без зависимостей. Там же лежит
`makeConsoleLogger({ level?, format? })`, штатный логгер для скрипта
вне приложения, и формат строки одним экземпляром: `formatLine`,
`serializeError`, тип `LogEntry`. `@nestlingjs/app` реэкспортирует типы
и `makeConsoleLogger`; `Logger$` и `RootLogger$` остаются в ядре.

Секция `nestlingLog` принимает уровень `silent`. Тестовый корень
`buildTest` поднимает приложение с ним по умолчанию; тест задаёт свой
уровень через `config`. Подробнее — [глава 9](../guide/09-logging.md).

> Обновление: механическое — `logger:` становится `logging: { logger }`, а
> поля корреляции уходят из своей реализации: их ставит ядро.
> Почему: [ideas.md, `[2026-09-13] Логгер: опция logging, пакет @nestlingjs/logging, поля-декларации, pino сателлитом`](../decisions/ideas.md#2026-09-13-%D0%BB%D0%BE%D0%B3%D0%B3%D0%B5%D1%80-%D0%BE%D0%BF%D1%86%D0%B8%D1%8F-logging-%D0%BF%D0%B0%D0%BA%D0%B5%D1%82-nestlingjslogging-%D0%BF%D0%BE%D0%BB%D1%8F-%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D0%B8-pino-%D1%81%D0%B0%D1%82%D0%B5%D0%BB%D0%BB%D0%B8%D1%82%D0%BE%D0%BC).

### `@nestlingjs/logging.pino`

Пакет с одним значением: `pinoLogger({ level?, format?, pino? })`
возвращает `Logger` поверх экземпляра pino.

```typescript
// src/app.ts
import { pinoLogger } from '@nestlingjs/logging.pino';

export const app = makeApp({
  features: [UsersFeature],
  transports: [http()],
  logging: {
    logger: pinoLogger({ format: 'json', pino: { redact: ['password'] } }),
  },
});
```

Записи уходят в `stderr` синхронным писателем. Формат `text` совпадает
со штатным логгером до байта: строку печатает одна функция. Формат
`json` пишет pino своей строкой с теми же ключами. `level` принимает и
уровни pino: `trace` отображается на `debug`, `fatal` на `error`. Поле
`pino` передаёт остальные опции библиотеке. Ключи, которыми держится
формат (`level`, `timestamp`, `formatters`, `base`, `messageKey`,
`errorKey`, `transport`, `serializers.err`), заняты адаптером и
отвергаются при создании логгера. `pino` — peer-зависимость `^10.0.0`.

## Метрики и трассы

### Метрика — декларация

Группа метрик объявляется значением `makeMetrics(prefix, { … })`. Имя
метрики складывается из префикса группы и ключа записи, других имён
нет.

```typescript
// src/orders/orders.service.ts — 0.2.0
@Component([Metrics$.auto])
export class OrdersService {
  constructor(private readonly metrics: Metrics) {}

  create(): void {
    this.metrics.counter('orders.created'); // ряд появлялся при первой записи
  }
}
```

```typescript
// src/orders/orders.metrics.ts — 0.3.0
import { counter, histogram, makeMetrics, open } from '@nestlingjs/app';

export const OrdersMetrics = makeMetrics('orders', {
  created: counter({
    help: 'Созданные заказы',
    attributes: { tier: ['free', 'paid'], source: open },
  }),
  'checkout.duration': histogram({
    help: 'Время оформления',
    unit: 'ms',
    buckets: [5, 25, 100, 500, 1000],
  }),
});

// src/orders/orders.service.ts — 0.3.0
@Component([OrdersMetrics])
export class OrdersService {
  constructor(private readonly metrics: MetricsOf<typeof OrdersMetrics>) {}

  create(): void {
    this.metrics.created.add({ tier: 'paid', source: 'web' });
    this.metrics['checkout.duration'].record(42);
  }
}

// src/orders/orders.feature.ts — 0.3.0
export const OrdersFeature = makeFeature({
  name: 'orders',
  metrics: [OrdersMetrics],
  providers: [OrdersService],
  endpoints: [CreateOrder],
});
```

Атрибут объявляется перечнем значений или пометкой `open`. Перечень
даёт набор рядов на сборке: экспозиция показывает нули до первого
запроса, а значение вне перечня не компилируется. Группа служит
DI-токеном: `@Component([OrdersMetrics])` даёт писателя, у которого
метрика выбирается полем, и незадекларированная запись невыразима.
Группа подключается вкладом `metrics:` у фичи, модуля, плагина или
корня; каталог собирается на фазе BUILD, совпадение имён между группами
— отказ сборки.

Накопленное держит ядро. `MetricsStore$` — узел графа, который есть
всегда, с единственным выходом `snapshot()`. Четыре метрики ядра
объявлены тем же механизмом, инструментовка включена всегда. Удалены
опция `makeApp({ metrics })`, DI-токены `RootMetrics$` и `Metrics$`,
интерфейс `Metrics` и `spyMetrics()` из `@nestlingjs/testing`. Тест
читает снимок:
`testApp.metrics.counter(OrdersMetrics.members.created, { tier: 'paid' })`;
юнит-тест класса без контейнера берёт писателя у `metricsFor`.

Формат экспозиции — пакет `@nestlingjs/prometheus`.
`makePrometheus({ path? })` в `plugins:` отдаёт `GET /metrics` на сокете
приложения; endpoint помечен `detached` и в документ API не попадает.
Гистограмма выводится рядами `_bucket`, `_sum` и `_count` с корзинами
из объявления. Подробнее — [глава 22](../guide/22-metrics.md).

> Обновление: требует решения — имя метрики складывается из префикса
> группы и ключа записи, а атрибуты объявляются перечнем значений.
> Почему: [ideas.md, `[2026-09-14] Метрика — декларация: группа-значение, каталог сборки, store в ядре`](../decisions/ideas.md#2026-09-14-%D0%BC%D0%B5%D1%82%D1%80%D0%B8%D0%BA%D0%B0--%D0%B4%D0%B5%D0%BA%D0%BB%D0%B0%D1%80%D0%B0%D1%86%D0%B8%D1%8F-%D0%B3%D1%80%D1%83%D0%BF%D0%BF%D0%B0-%D0%B7%D0%BD%D0%B0%D1%87%D0%B5%D0%BD%D0%B8%D0%B5-%D0%BA%D0%B0%D1%82%D0%B0%D0%BB%D0%BE%D0%B3-%D1%81%D0%B1%D0%BE%D1%80%D0%BA%D0%B8-store-%D0%B2-%D1%8F%D0%B4%D1%80%D0%B5).

### `@nestlingjs/otel`: участки трассы и push метрик

Сателлит экспорта телеметрии. Вход
`otel({ service, version?, traces?, metrics?, intervalMs? })` отдаёт две
части: слой пайплайна `spans` и плагин `plugin`.

```typescript
// src/telemetry.ts
import { otel, Span } from '@nestlingjs/otel';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';

export const telemetry = otel({
  service: 'orders',
  version: '1.0.0',
  traces: new OTLPTraceExporter(),
});

// src/observability.ts
export const traced = compose(
  makePipeline().pre(withRequestId()).pre(withTracing()),
  telemetry.spans,
);

// src/app.ts
export const app = makeApp({
  features: [OrdersFeature],
  plugins: [telemetry.plugin],
  transports: [http({ server: api })],
  policies: [everyEndpoint().hasVar(Span, 'span')],
});
```

Слой открывает участок pre-шагом и закрывает `.finally`-шагом, статус
выводит из исхода. Идентификаторы берутся из переменной `Trace`, которую
кладёт `withTracing()`, поэтому участки соседних процессов сходятся в
одно дерево; слой без `withTracing()` выше по композиции не
компилируется. Политика `everyEndpoint().hasVar(Span)` превращает
забытый слой в отказ сборки. Сервис читает участок через `Ctx(Span)` и
ставит атрибуты и события.

Плагин закрывает экспортёры на остановке. С опцией `metrics` он читает
`MetricsStore$.snapshot()` раз в `intervalMs` (по умолчанию 60 000 мс) и
отправляет снимок `PushMetricExporter`; на остановке уходит последний
снимок, и отказ экспортёра остановку не срывает. Корзины, `help` и
`unit` берутся из объявления, поэтому push и экспозиция Prometheus
показывают одно и то же. Экспортёры приложение ставит само: пакет
несёт SDK (`@opentelemetry/sdk-trace-base`, `sdk-metrics`,
`resources`), но не пакеты `exporter-*`. Подробнее —
[глава 23](../guide/23-tracing.md).

> Почему: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), пункт 2.

## Схемы

### zod внутри фреймворка, Standard Schema на границе

Публичная граница осталась на Standard Schema: приложение пишет схемы
на чём хочет, ни один публичный тип zod не называет. Схемы, которые
пишет сам фреймворк, написаны на zod: секции конфига ядра и сателлитов,
рекорды фактов `inbox` и `outbox`. Всё, что фреймворк делает с zod,
собрано в `@nestlingjs/schema.zod`: `zodConverter()`, билдеры полей
`int()` и `flag()`, `withZodDefault()`, модели `fromType`, `fromScratch`
и `makeModel`. Пакет `@nestlingjs/models` удалён, три его имени
переехали сюда.

Билдеры полей возвращают открытое значение zod, границу и умолчание
дописывает вызывающий:

```typescript
// src/db/db.config.ts — 0.2.0
poolMax: int(10, 1),
```

```typescript
// src/db/db.config.ts — 0.3.0
poolMax: int().min(1).default(10),
enabled: flag().default(true),
```

Правило «пустое значение ключа — отсутствующее значение» переехало из
рукописных хелперов в одну точку ядра: `DB_POOL_MAX=` даёт умолчание, а
не ноль.

Конвертер zod — умолчание у `makeOpenapi()`, `mcp()` и `cli()`: строка
`converters: [zodConverter()]` больше не нужна, поле `converters`
остаётся для схем другого вендора. Документ OpenAPI строит объявленный
плагин:

```typescript
// scripts/openapi.ts — 0.2.0
const { endpoints } = app.discover(args);
const document = buildOpenApiDocument(endpoints, openapiOptions);
```

```typescript
// scripts/openapi.ts — 0.3.0
const document = openapi.document(app.discover(argv(process.argv)));
```

`buildOpenApiDocument` удалён, `info` записывается в одном месте.
`describeConfig({ converters: [zodConverter()] })` отдаёт JSON Schema и
для секций фреймворка.

> Обновление: механическое — `int(10, 1)` записывается
> `int().min(1).default(10)`, строка `converters: [zodConverter()]`
> удаляется.
> Почему: [ideas.md, `[2026-09-13] Схемы: Standard Schema на границе, zod внутри; один пакет schema.zod`](../decisions/ideas.md#2026-09-13-%D1%81%D1%85%D0%B5%D0%BC%D1%8B-standard-schema-%D0%BD%D0%B0-%D0%B3%D1%80%D0%B0%D0%BD%D0%B8%D1%86%D0%B5-zod-%D0%B2%D0%BD%D1%83%D1%82%D1%80%D0%B8-%D0%BE%D0%B4%D0%B8%D0%BD-%D0%BF%D0%B0%D0%BA%D0%B5%D1%82-schemazod).

## Встраивание в чужой процесс

`@nestlingjs/transport.http` получил транспорт без сервера.
`adapter({ name? })` объявляется вместо `http()`, декларации
`httpEndpoint` переезжают на него без правок, а сокет приложение не
открывает.

```typescript
// src/app/api/[[...path]]/route.ts
import { adapter, toFetchHandler } from '@nestlingjs/transport.http';

const app = makeApp({ features: [Users], transports: [adapter()] }).build();

await app.run({ signals: false });

const handler = toFetchHandler(app);

export const GET = handler;
export const POST = handler;
```

Обработчик достаётся у запущенного приложения в двух формах.
`toFetchHandler(app, { name? })` отдаёт `(Request) => Promise<Response>`
для Next.js, Hono и Elysia. `toNodeHandler(app, { name? })` отдаёт
`(req, res) => Promise<boolean>` для Express и Fastify, где `false`
означает «маршрут не приложения». Формы io работают обеими: `value`,
`stream`, `events`, `multipart`, `rawBody`.

`BuiltApp` получил карту `transports: ReadonlyMap<string, ITransport>`
парой к `servers`. `run({ signals: false })` не ставит обработчики
`SIGTERM` и `SIGINT`: сигналы остаются хозяину процесса. Разбор запроса
и кадрирование ответа описаны интерфейсами пакета `HttpSource` и
`HttpSink`; `node:http` и `fetch` — две их реализации. Рантаймы помимо
Node пока вне границы: `multipart` читает `busboy`, тело собирается в
`Buffer`. Подробнее — рецепт
[«Приложение внутри чужого процесса»](../recipes/embedded.md).

> Почему: [ideas.md, `[2026-09-12] Разбор обзоров d/10 и d/13`](../decisions/ideas.md#2026-09-12-%D1%80%D0%B0%D0%B7%D0%B1%D0%BE%D1%80-%D0%BE%D0%B1%D0%B7%D0%BE%D1%80%D0%BE%D0%B2-d10-%D0%B8-d13-%D1%81%D0%B5%D0%BC%D1%8C-change%D0%B5%D0%B9-%D0%B8-%D0%BE%D0%B4%D0%BD%D0%BE-%D0%BE%D1%82%D0%BB%D0%BE%D0%B6%D0%B5%D0%BD%D0%B8%D0%B5), пункт 4.

## Имена

### Фабрика плагина — `make*`

Фабрика, которая возвращает плагин, называется с префиксом `make`.
Существительное освобождается под экземпляр:
`const openapi = makeOpenapi({ … })`.

| 0.2.0 | 0.3.0 | Пакет |
|---|---|---|
| `openapi()` | `makeOpenapi()` | `@nestlingjs/openapi` |
| `inbox()` | `makeInbox()` | `@nestlingjs/inbox` |
| `outbox()` | `makeOutbox()` | `@nestlingjs/outbox` |
| `subscriptions()` | `makeSubscriptions()` | `@nestlingjs/subscriptions` |
| `drizzlePg()` | `makeDrizzlePg()` | `@nestlingjs/drizzle.pg` |
| `pgOutboxStore()` | `makePgOutboxStore()` | `@nestlingjs/drizzle.pg` |
| `pgInboxStore()` | `makePgInboxStore()` | `@nestlingjs/drizzle.pg` |
| `httpProbes()` | `makeHttpProbes()` | `@nestlingjs/transport.http` |

Фабрики транспортов и сервера остаются существительными: `http()`,
`nats()`, `mcp()`, `cli()`, `server()`. Правила для кода приложения
записаны в [conventions.md](../conventions.md): экземпляр плагина —
существительное без префикса (`openapi`, `inbox`, `db`), слой —
причастие (`traced`, `authed`, `transactional`), двухпозиционный
переключатель — предикат (`DocsEnabled`). В гайде и примерах слой
`observability` называется `traced`.

> Обновление: механическое — восемь фабрик получают префикс `make` по
> таблице выше.
> Почему: [ideas.md, `[2026-09-14] Именование: вид называет часть речи, make у фабрики плагина`](../decisions/ideas.md#2026-09-14-%D0%B8%D0%BC%D0%B5%D0%BD%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5-%D0%B2%D0%B8%D0%B4-%D0%BD%D0%B0%D0%B7%D1%8B%D0%B2%D0%B0%D0%B5%D1%82-%D1%87%D0%B0%D1%81%D1%82%D1%8C-%D1%80%D0%B5%D1%87%D0%B8-make-%D1%83-%D1%84%D0%B0%D0%B1%D1%80%D0%B8%D0%BA%D0%B8-%D0%BF%D0%BB%D0%B0%D0%B3%D0%B8%D0%BD%D0%B0).

### Словарь

Единица пайплайна называется шагом. Один DI-токен семейства называется
«токен семейства»: `Logger$('orders')` и есть DI-токен. Оба
[глоссария](../glossary.md) обновлены, прежние слова стоят в колонке
запрещённых синонимов.

## Реестр подписок: `identity` — контекстная переменная

`makeSubscriptions({ identity })` принимает контекстную переменную.
Реестр читает её значение по ключу и формы `input` не знает.

```typescript
// src/ops/ops.plugin.ts — 0.2.0
identity: (ctx) => (ctx.input as { requestId?: string }).requestId,
```

```typescript
// src/ops/ops.plugin.ts — 0.3.0
identity: RequestId,
```

Функция осталась второй формой и типизируется накопленным контекстом.
Ключ из нескольких переменных собирает
`computed([TenantId, UserId], (_ctx, tenant, user) => …)`; та же форма
работает в `labels`. `@nestlingjs/app` экспортирует предикат
`isContextVar`. Что переменная есть у каждого endpoint'а, проверяет
политика `everyEndpoint({ … }).hasVar(RequestId)`. Подробнее — рецепт
[«Кто сейчас подключён и как его отключить»](../recipes/ops.md).

> Обновление: механическое — функция по `ctx.input` заменяется контекстной
> переменной; форма с функцией осталась второй.

  `@nestlingjs/app`. Замены нет: слой аутентификации с типизированной
  переменной `Caller` идёт отдельной работой.
- `load()`, строковая форма и массив имён у `build()`.
- Поля `config:`, `logger:` и `metrics:` у `makeApp`.
- `objectSource` и `ObjectSource` из `@nestlingjs/app`; в
  `@nestlingjs/testing` их место занял `vars`.
- `TransportEntry` и `isTransport`.
- `doc.status`.
- `RootMetrics$`, `Metrics$`, интерфейс `Metrics`, `spyMetrics()`.
- `buildOpenApiDocument` и пакет `@nestlingjs/models`.
- Сигнатуры билдеров `int(fallback, min)` и `flag(fallback)`.

## Тестирование

- `buildTest(app, options)` вместо `assembleTest`; опция `config` —
  список `bind()`, как у `run()`.
- `testBundle` вместо `testUnit`.
- `vars(values, name?)` — источник из объекта, привязывается через
  `bind(vars({ … }))`.
- `testApp.run()` доходит до фазы RUN, `testApp.baseUrl(name?)` отдаёт
  адрес сервера.
- Тестовый прогон тихий: уровень `silent` по умолчанию.
- `testApp.metrics` и `metricsFor` вместо `spyMetrics()`.
- Условие `testing` для subpath `@nestlingjs/app/testing` в vitest
  включается полем `resolve.conditions`:
  `['testing', 'node', 'node-addons', 'import', 'default']`.

Подробнее — [глава 8](../guide/08-testing.md) и
[глава 18](../guide/18-testing-features.md).

## Для тех, кто собирает репозиторий

Тесты репозитория гоняет vitest со swc вместо jest с ts-jest: те же
файлы и те же тесты, без `NODE_OPTIONS=--experimental-vm-modules`.
Прогон `@nestlingjs/app` сократился с 14,7 до 2,5 секунды. Конфиг пакета
называется `vitest.config.js` и создаётся
`createVitestConfig(import.meta.url)`.
