## 1. Онтология: три этажа

1. **Сантехника транспорта** — статика, CORS, сжатие, wildcard-подписки:
   конфиг/плагины транспорта, без схем и контрактов
   ([transports.md](./transports.md)). Escape hatch для сырых случаев живёт
   здесь — параллельной модели деклараций нет.
2. **Контракты** — все schema-first операции: интерфейс (`input`/`output`/
   `errors`) + адреса (`name`, `http:`, `cli:`, …)
   ([contracts.md](./contracts.md)).
3. **Реализации** — `implement(Contract, { pipeline?, deps?, handle })`.

**Иерархия деклараций — контракт первичен.** Per-transport конструкторы
(`httpEndpoint`, `cliEndpoint`, …) — сахар «анонимный контракт + implement
одним жестом»; на kernel-уровне всё компилируется в один и тот же узел графа.
Различие endpoint/контракт — **видимость**: экспортированный именованный
контракт — capability «меня можно позвать» (порты, клиенты, версии, шина);
анонимный — чисто транспортная поверхность. Деградация плавная: «дай ручке
имя и экспортируй — станет портируемой».

Декораторных деклараций (`@Endpoint`/`@HttpEndpoint`), интерфейса `IEndpoint`
и глобального endpoint-registry в V1 **нет**: декоратор не влияет на типы,
а всё продающее — schema-first вход/выход, типизированная `meta`,
`Output<T, E>` — течёт через вывод типов из значений. Канонический стиль
деклараций — функциональный (`make*`); классы остаются DI-формой
(провайдеры, юниты, хендлеры).

## 2. Декларация — значение, конструктор — у транспорта

```typescript
export const CreateOrder = httpEndpoint({
  method: 'POST',
  path: '/orders',
  input: NewOrder,
  output: Order,
  errors: [OrderLimitReached],       // типизированный канал E (errors.md)
  pipeline: basePipeline,
  deps: [OrdersService],
  handle: (orders) => async (input, meta) => new Ok(orders.create(input)),
});
```

- **Словарь вида транспорта легален и типизирован в декларации** — и только
  здесь: path-параметры выводятся из шаблона, канон размещения и bind-карта
  (см. §4) разворачиваются в конструкторе. Pipeline и handler —
  транспорт-слепые; контракт — транспорт-нейтральный этаж.
- Generic `makeEndpoint` — kernel-примитив, из которого транспортные
  конструкторы собирают свои; в пользовательский канон он не входит.
- **Ссылка на транспорт — токеном**: endpoint без своего транспорта в
  графе = fail-fast на ASSEMBLE.
- **Мультитранспорт**: именованный контракт с несколькими биндингами +
  один `implement` — канон; несколько тонких деклараций с общим
  хендлером — для анонимных поверхностей с разными словарями. Никакого
  `ExecutionContext`-маскарада: каждая декларация честно знает свой
  транспорт.
- **Endpoint — обычный узел графа** с синтетическим id
  (`endpoint:POST /orders`): рёбра `deps` видны в визуализации и
  `explain()`, циклы и `strictExports` — штатно; инстанцирование жадно
  на ASSEMBLE, регистрация паттернов — WIRE.

## 3. DI хендлера: `deps` и три формы `handle`

| Форма | Когда |
|---|---|
| `(input, meta) => …` | без зависимостей; единственная форма, которую принимают standalone-транспорты (`server.route`) — endpoint с `deps` туда не проходит по типам |
| `deps: […]` + `(…deps) => (input, meta) => …` | каррированная фабрика: внешний вызов — один раз на сборке (аналог конструктора), замыкание = инстанс |
| класс с `@Injectable` и методом `handle` | форма подключения DI: App резолвит из контейнера (механизм классов-юнитов) |

Классовая форма эквивалентна каррированной строчка в строчку и сохраняет
привычную после NestJS структуру — без декораторной декларации:

```typescript
@Injectable([OrdersService, ChargeCard.port])
export class CreateOrderHandler {
  constructor(
    private orders: OrdersService,
    private billing: Port<typeof ChargeCard>,
  ) {}
  async handle(input: NewOrder, meta: { signal: AbortSignal }): Output<Order> { /* ... */ }
}

export const CreateOrder = httpEndpoint({
  method: 'POST',
  path: '/orders',
  input: NewOrder,
  output: Order,
  pipeline: basePipeline,
  handle: CreateOrderHandler,   // класс — поле типизированного вызова:
});                             // сверка со схемами в точке декларации, implements не нужен
```

Unit-тест хендлера — без фреймворка: вызов каррированной фабрики с фейками
или `new CreateOrderHandler(fakes…)` — ноль импортов из `@nestling/*`.

**Standalone-гарантия в типах**: тип endpoint'а несёт неразрешённые deps;
`server.route()` принимает только deps-free endpoint (симметрично
`Pipeline<any, never>`); ручное гашение — `endpoint.resolve([...])`.

## 4. HTTP-канон: размещение input и bind-карта

Единый `input` переносим между транспортами; **куда каждое поле кладётся
в HTTP-запросе — детерминированная функция** `(pattern, метод, пометки) →
размещение`:

1. имя поля совпало с path-параметром шаблона → **путь**;
2. явная пометка (`query(...)`) → указанное место;
3. остальное — **query** для `GET/HEAD/DELETE`, **body** для
   `POST/PUT/PATCH`;
4. заголовки — **только по пометке, никогда конвенцией**; в V1 канона
   `header()` нет (граница meta vs input и триггеры возврата —
   [deferred](../decisions/deferred.md)).

```typescript
export const GetUser = httpEndpoint({
  method: 'GET',
  path: '/users/:id',
  input: z.object({
    id: z.string(),                        // совпало с :id → путь
    expand: z.enum(['profile', 'orders']).optional(),  // GET → query
  }),
  output: User,
  pipeline: basePipeline,
  deps: [UserService],
  handle: (users) => async ({ id, expand }) => Ok.of(await users.get(id, expand)),
});
```

- **Bind-карта — несущий уровень.** Пометки разворачиваются при **создании
  декларации/контракта** (не при регистрации в App) в плоскую карту
  «поле → место», которую потребляют транспорт, OpenAPI и типизированный
  клиент — клиенту она нужна из одного импорта, без сервера. При
  непрозрачной для интроспекции схеме bind-карта задаётся руками
  (`bind: {...}`).
- **Strict-приём**: payload собирается только из канонических мест — поле
  не в том месте не попадает в payload и проваливает обычную валидацию.
  Merge-отовсюду и `PayloadConflictError` не существуют.
- **Fail-fast при создании**: path-параметр без поля в схеме, пометка на
  path-поле, body-пометка у GET — ошибка сразу.
- **Query-массивы**: повтор ключа → массив; поле-массив оборачивает
  одиночное значение.
- **Ambient-заголовки** (`Authorization`, `traceparent`) — контекст запроса,
  живут в meta через pre-юниты; `Accept`/`Content-Type` — концерн
  транспорта, до пользователя не доходят.

## 5. Формы io: дерево форм над схемами

`input`/`output` — не всегда одна схема-значение. Верхний уровень —
**форма**; листья — Standard Schema (спека для значений не затрагивается):

| Форма | Семантика | HTTP media type |
|---|---|---|
| значение (схема как есть) | обычный запрос/ответ | JSON |
| `stream(T)` | конечный поток | NDJSON / chunked |
| `events(T)` | открытая подписка | `text/event-stream` (SSE) |
| `multipart({ fields, files })` | поля + файлы | `multipart/form-data` |

- Валидация по форме: значение — целиком; `stream`/`events` — поэлементно;
  `multipart` — поля схемой, файлы (`upload({ maxSize, mime })`) лимитирует
  транспорт **во время** парсинга, не буферизуя. Семантика потоков и
  item-цепочки — [streaming.md](./streaming.md).
- Маппинг форм на media types детерминирован — вход для OpenAPI-генерации.
- **Сырые байты — opt-in** `rawBody: true` в HTTP-словаре (webhook-подписи,
  HMAC): транспорт кладёт байты в типизированный стартовый контекст; слой
  проверки объявляет `makePipeline<{ rawBody: Uint8Array }>()` — забытая
  пометка ловится компилятором в точке композиции. Память платится только
  там, где запрошена.
- Контракту можно объявлять богатые формы; **биндинг валидируется против
  способностей транспорта** на ASSEMBLE (fail-fast с внятной ошибкой):
  HTTP умеет стримы и multipart, шина/порт V1 — только value-формы.

## 6. CLI-биндинг

Словарь `cliEndpoint` — имя команды + та же io-декларация. Стратегия сбора
недостающего input — **политика биндинга, не свойство операции**:
`missing: 'prompt'` выводит промпты из схемы (enum → select,
boolean → confirm, `.describe()` → подсказка, default → «Enter»); CI-режим
отключает промпты (нет флага = ошибка). Диалог посреди выполнения —
декомпозиция в пару операций plan/apply (паттерн подтверждаемой операции,
транспортно-нейтрален). Операция всегда остаётся `input → output`.
