## Context

`examples/` содержит шесть каталогов. Три — приложения (`users-service`,
`app-with-http`, `split-nats`), три — учебные заготовки (`container`,
`simple-cli`, `simple-http-server`). Заготовки существуют ради глав:
`container` поднимает приложение без транспорта, чтобы показать
контейнер, `simple-http-server` обрывается на трёх endpoint'ах.

Сцепка текста с примером держится тремя механизмами: плашка «сверено с
кодом `<пример>` (дата)» в каждой главе и каждом рецепте, подпись блока
кода путём файла примера, пометка «шаг главы N; итоговая версия: …».
Инварианты `guide-plate`, `guide-example` и `guide-stale` в
`docs-audit` проверяют первые два, требования об этом записаны в спеке
`examples-layout`.

Приложений три, но приложение по сути одно: `app-with-http` и
`split-nats` держат те же две фичи в двух копиях, различаясь транспортом
между процессами. Фича `quotas` в обоих придумана ради демонстрации
границы фич.

## Goals / Non-Goals

**Goals:**

- Три примера, каждый из которых можно взять за образец рабочего
  приложения: конфигурация, миграции, запуск в Docker, тесты, README.
- Имя примера отвечает на вопрос «зачем открывать».
- Глава и рецепт читаются без примера: код в блоках написан для текста.
- Один домен на все примеры и на гайд: пользователи и уведомления.
- Сигнал «текст пора пересверить» остаётся, но считается по коду
  фреймворка, а не по коду примера.

**Non-Goals:**

- Компилируемый каталог сниппетов.
- Изменения API фреймворка.
- Пересмотр состава и порядка глав.

## Decisions

### Р1. Границы между примерами: клиентское и топология

`microservice` держит всё, что видит внешний клиент: HTTP CRUD,
PostgreSQL с миграциями, проверка Bearer-токена, пайплайн наблюдаемости,
файлы и потоки, живая лента по SSE с реестром подписок, документ OpenAPI
и типизированный клиент, инструменты агента по MCP, метрики, пробы
`/healthz` и `/readyz`.

`modular-app` держит всё, что появляется от разнесения: две фичи,
операции и события между ними, транзакционные emit и приём, выбор фич,
переключатели состава, снимок операций для сверки совместимости, шина
NATS, два профиля `docker compose`.

`cli` держит командную строку: команды поверх операций сервиса, запуск по
аргументам и REPL, вызов сервиса типизированным клиентом.

Альтернатива — один пример на всё: отвергнута, потому что читатель тогда
не различает, что нужно любому сервису, а что появляется только при
разъезде по процессам.

### Р2. Домен: пользователи и уведомления

Вторая фича `modular-app` — `notifications`: письмо о регистрации,
шаблоны, повтор при отказе почты. Рассылка — честная причина вынести
процесс: она медленная, ретраится и масштабируется отдельно от API.

`quotas` удаляется. Квоты на регистрацию не решают ничьей задачи в
примере — фича заведена, чтобы у `users` появился сосед.

Гайд говорит теми же словами: главы 14–22 переезжают с квот на
уведомления.

### Р3. `cli` зависит от `microservice`

`@examples/cli` держит `@examples/microservice` в зависимостях и
импортирует его `src/api/operations.ts`. Клиент строится из тех же
деклараций операций, которые обслуживает сервис.

Альтернатива — копия деклараций в `cli`: отвергнута, копия разойдётся с
сервисом на первом же изменении схемы. Это же и есть содержание примера:
операции — общее знание клиента и сервера.

Цена: `yarn verify` строит `microservice` до `cli`, зависимость
фиксируется в графе nx.

### Р4. Глава пишет свой код

Блок кода в главе подписывается путём в проекте читателя:
`// src/users/create-user.endpoint.ts`. Путь внутри `examples/` в
подписи не появляется.

Пример упоминается ссылкой — в конце главы, одной строкой «целиком
собрано в `examples/microservice`». Пересказ файлов примера, пометки
«шаг главы N» и колонка «Пример» в оглавлении удаляются.

Альтернатива — компилируемый каталог сниппетов, из которого главы берут
код по маркеру: отвергнута по цене. Сверка остаётся периодической.

### Р5. Плашка называет точку сверки хэшем

Форма плашки: «сверено с кодом `a0056fb0`» и «verified against
`a0056fb0`». Хэш — короткий, семь-двенадцать знаков.

`docs-audit` делает три проверки:

1. хэш разрешается в коммит (`git rev-parse --verify <hash>^{commit}`) —
   иначе ERROR;
2. `git log <hash>..HEAD -- packages/*/src` непуст — WARN с числом
   коммитов; автор читает этот же диапазон, чтобы понять, что менять;
3. хэш английской пары — строгий предок русского
   (`git merge-base --is-ancestor`) — WARN «перевод отстал».

Дата отвергнута: она говорит «текст устарел», но не говорит, что
изменилось. Хэш даёт диапазон коммитов, который читается одной командой.

Свежесть считается по `packages/*/src`: главы описывают фреймворк, а
правка его тестов или README текст не просрочивает.

### Р6. Полная история для аудита в CI

`actions/checkout@v4` по умолчанию клонирует один коммит, и хэш плашки в
таком клоне не разрешается. Джоба `verify` получает `fetch-depth: 0`.

Скрипт остаётся работоспособным и в мелком клоне: обнаружив
`git rev-parse --is-shallow-repository` = `true`, он один раз печатает
WARN и пропускает проверки свежести, не выдавая ERROR на каждую главу.

### Р7. Два профиля `docker compose` в `modular-app`

Один файл `docker-compose.yml`, два профиля. `mono` поднимает PostgreSQL,
NATS и один процесс приложения со всеми фичами. `split` поднимает те же
PostgreSQL и NATS и два процесса: `APP_FEATURES=users` и
`APP_FEATURES=notifications`.

Два файла отвергнуты: общие сервисы пришлось бы держать в двух местах.

### Р8. Что переезжает из удаляемых примеров

- `simple-http-server` — целиком в главы 1–4: его код и есть первые шаги
  пути.
- `container` — в рецепты `token-families.md`, `config-sources.md`,
  `standalone.md`, `extending.md`; их сниппеты пишутся в тексте.
- `simple-cli` — в `cli`: режим по аргументам, REPL, вопросы команды из
  JSON Schema, обработка stdin.
- Скрипт `visualize` (граф зависимостей для `@nestlingjs/viz`) переезжает
  в `modular-app`: граф с фичами и переключателями нагляднее, чем граф
  учебного контейнера. README пакета `viz` меняет ссылку.

### Р9. Тесты примера

Спеки примера (`*.spec.ts`) входят в `yarn verify` и не требуют Docker:
те, что ходят в базу, гейтятся `TEST_DATABASE_URL`, как сейчас. Тесты
`e2e` поднимают приложение и запускаются отдельной командой
`test:e2e` — в `verify` они не входят.

## Risks / Trade-offs

- **Сниппеты глав сгниют: их никто не компилирует** → плашка с хэшем
  даёт диапазон правок фреймворка, а `/docs-audit` — повод пересверить.
  Риск принят сознательно: это цена независимости текста от примеров.
- **Объём: 32 файла гайда и рецептов, каждый с английской парой** →
  домен меняется только в девяти главах, остальное — механическая правка
  плашек и подписей. Порядок работ разводит код и тексты по фазам.
- **`cli` зависит от `microservice`** → оба остаются в одном репозитории,
  nx строит их по графу; удаление одного из них потребует правки второго.
- **Пример перестаёт быть проверкой главы** → ошибки в коде глав теперь
  ловит только чтение. Взамен примеры перестают нести код, написанный
  ради текста.
- **Пересборка домена** (`quotas` → `notifications`) **трогает и e2e, и
  снимок операций** → снимок пересоздаётся вместе с фичей; сверка
  совместимости проверяется на изменении операции `notifications`.

## Migration Plan

Порядок работ в ветке `change/examples-rework`:

1. `microservice` — переименование `users-service` и перенос клиентского
   из `app-with-http` (SSE, реестр подписок, MCP, метрики, пробы).
2. `modular-app` — `users` и `notifications` на базе `app-with-http` и
   `split-nats`, два профиля `docker compose`, снимок операций, скрипт
   `visualize`.
3. `cli` — из `simple-cli` поверх операций `microservice`.
4. Удаление шести старых каталогов, правка `ci.yml`, README пакета `viz`
   и корневых README.
5. Гайд и рецепты: подписи блоков, плашки, домен глав 14–22, оглавления;
   обе языковые половины.
6. `docs-audit`: инварианты плашки и свежести; `docs/README.md` — правило
   про README примеров и описание частей пути.

Откат — отказ от ветки: в `main` изменения попадают одним слиянием после
`/opsx:archive`.

  файла `app.ts`.
- Останется ли рецепт `alternatives.md` без кода-источника осмысленным,
  или его содержание переезжает в главу 2.
