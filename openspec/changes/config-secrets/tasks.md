## 1. Декларация: обёртка `secret()`

- [x] 1.1 `SecretField` и `secret(leaf)` в `packages/nestling.config/src/declaration.ts`: класс рядом с `FromField` (`instanceof`, не поле-дискриминант), приём `Schema | FromField`, прозрачность для вывода типа (`FieldOutput` разворачивает обе обёртки, `secret(z.string())` даёт `string`)
- [x] 1.2 Поле `secret: boolean` в `SectionField`; `toField` (`section.ts`) разворачивает вложенные обёртки в любом сочетании `secret(from(schema))` и называет секцию/поле в ошибке невалидного листа как раньше
- [x] 1.3 Fail-fast обратного порядка: `from(key, secret(schema))` в рантайме даёт ошибку в точке объявления с текстом, называющим секцию, поле и канонический порядок `secret(from(...))`; проверить, что тип уже отвергает такую запись (type-тест или `@ts-expect-error` в spec-файле)
- [x] 1.4 Экспорт `secret` и типа `SecretField` из `index.ts` пакета (по тем же соображениям, что и `FromField`: тип попадает в выведенный тип секции)

## 2. Реестр: индекс читателей и эффективная секретность

- [x] 2.1 Инкрементальный индекс в `registry.ts`: `Map<key, KeyReader[]>` (секция, поле, `exact`, `reloadable`, `secret`) и `Set` секретных ключей, дополняемые в `registerSection`, очищаемые в `resetConfigRegistry`
- [x] 2.2 `isSecretKey(key)` — внутренняя функция объединения по объявленным читателям; в публичный экспорт не выносится (потребителям хватает снимка)
- [x] 2.3 Расширить `describeConfig()`: `secret` на `ConfigKeyDescription` (эффективный, не «своё объявление») и key-центричный индекс `keys: ConfigSharedKeyDescription[]` рядом с `sections`; существующие поля не переименовывать
- [x] 2.4 Типы снимка (`ConfigKeyReader`, `ConfigSharedKeyDescription`) и их экспорт из `index.ts`
- [x] 2.5 Тесты `registry.spec.ts`: эффективная секретность видна у обоих читателей; индекс перечисляет всех читателей, включая непотреблённых; ключ с единственным читателем тоже в индексе; значений в снимке нет

## 3. Общие ключи: согласованность `reloadable` в границах сборки

- [x] 3.1 `ConfigSharedKeyError` в `errors.ts`: ключ, обе секции, оба поля, обе починки; текст симметричен относительно порядка материализации
- [x] 3.2 `claimKeys(declaration)` на `ConfigReader` (`reader.ts`): `Map<key, { section, field, reloadable }>` живёт на экземпляре читалки, то есть ровно одну сборку; несогласованный флаг — бросок `ConfigSharedKeyError`
- [x] 3.3 Вызов `claimKeys` из `projectSection` (`project.ts`) до чтения значений — конфликт обязан обнаруживаться раньше, чем провалится валидация
- [x] 3.4 Тесты (`shared-keys.spec.ts`): две секции читают ключ разными схемами и обе валидны; отказ у одного читателя роняет сборку; конфликт `reloadable` называет обе секции; согласованный `reloadable` конфликта не даёт; непотреблённая конфликтующая секция сборку не роняет; две последовательные сборки в одном процессе независимы

## 4. Редактирование в ошибках валидации

- [x] 4.1 `ConfigFieldFailure.redacted: boolean` и рендер в `ConfigValidationError`: при взведённом флаге сообщения issue'ев — `'<redacted>'`, пути сохраняются, имя ключа и поля остаются
- [x] 4.2 `readValues` (`project.ts`): вычислять `redacted = isSecretKey(field.key) && rawValue !== undefined` и складывать в отказ **уже редактированные** issue'ы — вендорский текст не покидает вызов валидации
- [x] 4.3 Та же логика в `load.ts` (примордиальное чтение) — одна общая функция редактирования на оба места, второй копии правила не заводить
- [x] 4.4 Тесты (`secrets.spec.ts`): заданное невалидное значение редактируется и в тексте, и в `error.failures[].issues[].message`; незаданный ключ показывается целиком; смешанная ошибка (секретное + обычное поле) в одном броске; редактирование работает в `load()`; warn о неудачном reload не содержит вендорского текста
