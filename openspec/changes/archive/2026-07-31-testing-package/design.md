# design — testing-package: ядро `@nestling/testing`

## Context

Что уже есть и на что опираемся:

- **`assemble(spec) → App`** (`packages/nestling.app/src/app.ts`) — единственный
  корень. `App.run()` идёт по фазам: `#assemble()` (регистрация kernel-модуля
  конфига, модулей, провайдеров, транспортов; `discoverEndpoints`;
  `builder.build()`; `#assertRequiredTransports`; `#assertFormsSupported`) →
  `container.init()` → `#wire()` (гашение зависимостей деклараций,
  `makeDispatch` на транспорт) → `container.start()` → `serve(dispatch, signal)`
  по каждому транспорту → `#announce()` + `#attachSignals()`.
  Тип `AssemblyPlan` **не экспортируется** — `new App({…})` невыразим.
- **`ContainerBuilder.build()`** — жадный: раскрывает фабрики провайдеров
  модулей, материализует членов семейств (fixpoint), материализует агрегаты
  `Family.all`, **инстанцирует всё зарегистрированное** (`instantiateAll`),
  строит `DIGraph`, проверяет ацикличность, опционально линтует `strictExports`.
  Хуки жизненного цикла читаются с инстанса (`getLifecycleHooks`) независимо от
  вида провайдера — значит, фейк с `@OnInit`/`@OnDestroy` работает как
  обычный узел.
- **`Dispatch`** (`packages/nestling.transport/src/dispatch.ts`) — `routes`
  (проекция без исполнимых полей) + `call(pattern, ctx, options)`. Обе ветки
  исполнения (с пайплайном и без) живут здесь; контекст строит транспорт через
  `makeEmptyContext(raw, endpointMeta, signal)`.
- **`objectSource(values, name)`** (`packages/nestling.config/src/source.ts`) —
  готовый `ConfigSource` с `watch`/`set`/`assign`; `configKernel(bindings)`
  регистрируется корнем всегда.

Ограничения, которые формируют дизайн:

1. **Контейнер жадный.** Инстанцируется всё зарегистрированное, а не только
   достижимое. Значит, подстановка сама по себе не спасает от pg-пула: нужен
   явный прунинг.
2. **`overrides` не должны существовать в бою** — даже как соблазн
   (ideas.md [2026-07-10], отвергнутые варианты). Публичный `assemble` о них
   не знает и знать не должен.
3. **Тестовый прогон обязан быть тем же прогоном.** Второй фазовый рантайм
   рядом с `App` разъедется с первым на первом же change'е волны 5.
4. **`await using` — целевая форма** (design-док §3), то есть `TestApp` несёт
   `Symbol.asyncDispose`.

## Goals / Non-Goals

**Goals:**

- тестовый корень — **тот же `App`**, остановленный на фазе 3, а не его копия;
- подстановка + прунинг как свойство графа, с проверяемым инвариантом
  «без `overrides` граф не меняется ни на один узел»;
- in-proc `call` через полный пайплайн, типизированный схемами декларации;
- структурная проверка топологий (`.check()`) на **честном** графе — тем самым
  прунинг компенсирован;
- граница «прод не видит тестового API» — структурная (Node resolution), а не
  конвенция;
- пакет остаётся тонким: вся его машинерия — швы, а не фреймворк.

**Non-Goals:** `stub(Contract)` и `app.emit` (нет контрактов до #11),
`policies:` в `.check()` (#28), раннер/матчеры, автоподстановка транспортов.
См. Non-goals в [proposal.md](./proposal.md).

## Decisions

### D1. Тестовый корень — `App`, а шов к нему — conditional subpath

`@nestling/testing` не строит контейнер сам. `@nestling/app` получает
внутренний шов, отдающий ровно две вещи: конструирование `App` с планом,
включающим `overrides`, и прохождение фаз 0–3 с доступом к `container` и
карте `dispatch`. Шов живёт в **`@nestling/app/testing`** — subpath,
объявленный conditional export'ом:

```jsonc
// packages/nestling.app/package.json
"exports": {
  ".":         { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
  "./testing": { "testing": { "types": "./dist/testing/index.d.ts",
                              "import": "./dist/testing/index.js" } }
}
```

Условие `"testing"` включено только в тест-раннере, поэтому прод-импорт
`@nestling/app/testing` **не резолвится на уровне Node** — это та же граница,
которую §5 design-дока предписывает пользовательским модулям. Мы её
догфудим: если конвенция не работает на собственном ядре, предлагать её
пользователю нечестно.

**Альтернативы:**

- *`overrides` в `ContainerBuilderOptions` публично* — контейнер это переживёт
  (в ручной сборке и так регистрируешь что хочешь), но публичная опция
  «подменить узел» в kernel-пакете читается как приглашение. Опция там
  **появится** (D2), но помечена как шов тестового корня и не экспортируется
  в форме, пригодной для прод-сборки: `assemble` её не пробрасывает.
- *Свой фазовый раннер в `@nestling/testing`* — 60 строк WIRE-логики в двух
  экземплярах и гарантированный дрейф. Отвергнуто: главная ценность
  `assembleTest` в том, что это **тот же** прогон.
- *`@internal`-функция в главном экспорте `@nestling/app`* — граница
  конвенцией, ровно то, чего мы не делаем.

### D2. Подстановка и прунинг — в `ContainerBuilder`

Опции билдера пополняются двумя полями:

```typescript
interface ContainerBuilderOptions {
  strictExports?: boolean;
  /** Шов тестового корня: подстановка узла графа до инстанциации */
  overrides?: readonly TokenOverride[];
  /** Шов тестового корня: подмена рецепта семейства */
  familyOverrides?: readonly FamilyOverrideEntry[];
}
```

Порядок в `build()` — единственное место, где всё это имеет значение:

1. раскрытие фабрик провайдеров модулей (как сейчас);
2. подмена рецептов семейств (`familyOverrides`) — до материализации, иначе
   члены родились бы по боевому рецепту;
3. материализация членов семейств (fixpoint, как сейчас);
4. **применение `overrides`**: провайдер токена заменяется на
   `{ provide, useValue }` c сохранением **атрибуции к модулю** (иначе
   `strictExports` и визуализация начали бы врать);
5. **вычисление прунинга** (алгоритм ниже) и удаление выпавших провайдеров;
6. материализация агрегатов `Family.all` — **после** прунинга, по оставшимся
   членам;
7. предвалидация недостающих зависимостей (D7), инстанциация, граф, циклы,
   `strictExports` — как сейчас.

**Алгоритм прунинга.** Пусть `deps′` — отношение зависимостей после
подстановки, `deps` — до неё (для заменённых токенов запоминаются исходные
`deps`). Ребро на `Family.all` при обходе разворачивается в рёбра ко всем
текущим членам семейства — иначе агрегат-потребитель терял бы своих членов.

- `R` = токены с нулевой входящей степенью в объединении `deps ∪ deps′`,
  плюс токены, недостижимые из этого множества по объединению (участники
  циклов — они обязаны дойти до детектора циклов, а не исчезнуть);
- `Keep` = достижимые из `R` по `deps′`;
- прунятся `All \ Keep`: провайдер не инстанцируется, узла в графе нет,
  `@OnInit`/`@OnDestroy` не выполняются.

Почему именно так, а не «оставить достижимое от корней»: в жадном контейнере
корней как понятия нет — зарегистрирован, значит нужен. Объединение `deps ∪
deps′` даёт ровно нужную асимметрию: pg-пул **не** корень (на него смотрел
репозиторий *до* подстановки), а после подстановки на него не смотрит никто —
и он выпадает. Отсюда же ключевой инвариант: **без `overrides` `deps = deps′`,
`R` — это все узлы с нулевой входящей степенью, а в ациклическом графе из них
достижим каждый узел ⇒ `Keep = All`, прунинг тождественен.** Инвариант
проверяется рантайм-тестом на нетривиальном графе.

`app.pruned` (список id выпавших узлов) отдаётся наружу: «почему мой
`@OnInit` не выполнился» должно отвечаться данными, а не чтением исходников.

### D3. Форма и типизация `overrides`

```typescript
await using app = await assembleTest({
  features: [UsersFeature],
  overrides: [
    [UsersRepository, inMemoryUsersRepo()],   // пара «токен → фейк»
    familyOverride(ILogger, () => noopLogger), // подмена рецепта семейства
  ],
  config: vars({ USERS_PAGE_SIZE: '10' }),
});
```

- **Право override — позиционное**: мокаешь то, на что у теста есть ссылка.
  Строкового доступа к токену (`overrideByName('...')`) не существует —
  это дыра в ES-видимости и обесценивание kernel/user-границы.
- **Пара типизирована**: `overrides` принимается через mapped-тип, который
  для каждого элемента `[InjectionToken<T>, unknown]` требует `[…, T]`.
  Фейк не того типа — ошибка компиляции; на это заводится type-тест
  (`packages/nestling.testing/src/*.type-test.ts` в стиле `TYPE-TESTS.md`).
- **Override токена, которого нет в графе, — ошибка сборки.** Иначе
  переименование провайдера оставляет тест, который «мокает» пустоту и
  молча гоняет боевой код. Текст ошибки называет токен и подсказывает
  проверить, зарегистрирован ли он выбранными фичами.
- **Два override'а одного токена — ошибка**: «последний выигрывает» здесь
  ничем не лучше явного отказа.
- **Член семейства** (`Config('ORDERS_MAX')`) — обычный токен *после*
  материализации, поэтому override работает и для него; но если член никем
  не инжектится, он не материализован и override падает как «нет в графе»
  с отдельной подсказкой про семейство. Это закрывает открытый вопрос
  ideas.md «форма `overrides` для членов семейств»: **точечно — да, поверх
  материализованного члена; рецепт целиком — `familyOverride`.**

### D4. Остановка после WIRE и `await using`

`assembleTest` проходит фазы 0 BOOTSTRAP → 1 ASSEMBLE → 2 INIT → 3 WIRE и
останавливается. Значит, **не происходит**: `container.start()` (`@OnStart`
не выполняется), `transport.serve(...)` (сокет не открывается),
`#attachSignals()` (обработчики `SIGTERM`/`SIGINT` не ставятся),
`#announce()` (тесты не пишут в stdout).

Следствие, которое нужно назвать вслух: ресурс, захваченный в `@OnStart`,
в app-тесте не захватывается. Это не баг, а цена фазовой модели: `@OnStart` —
хук go-live, а тестовый прогон в эфир не выходит.

`assembleTest` **асинхронна** (`build()` асинхронен), поэтому канон записи —

```typescript
await using app = await assembleTest({ … });
```

`await using` не ждёт инициализатор, он ждёт **dispose**; `await` перед
вызовом обязателен. Снипет в `docs/design/testing.md` §3 правится по факту.
Форма без `using` (`const app = await assembleTest(…)` + `await app.close()`)
поддерживается — для jest-хелперов вида `beforeEach`/`afterEach`.

`close()` идемпотентен и делает ровно SHUTDOWN тестового прогона: взводит
общий `AbortController` (его `signal` уезжает в каждый `call`, поэтому
in-flight отменяются кооперативно), затем `container.destroy()` — реверс
топосорта. Транспортов в `#serving` нет, дренаж пропускается.

### D5. `app.call` — in-proc кадр запроса

```typescript
const res = await app.call(CreateUser, { name: 'Alice' });
// res: ResponseContext<User> — { isSuccess: true, status, value } | { isSuccess: false, status, value: ErrorDetails }
expect(unwrap(res)).toEqual({ id: '1', name: 'Alice' });
```

Механика: декларация ищется по **идентичности значения** в карте, собранной
в WIRE (исходная декларация → её исполнимая копия + `dispatch` её транспорта),
после чего строится контекст `makeEmptyContext(raw, endpointMeta, signal)` и
зовётся `dispatch.call(pattern, ctx, options)`. Идентичность, а не паттерн:
у теста на руках то же значение, что в `endpoints:` модуля, и совпадение
строк тут не нужно. Декларация, которой нет в приложении (не выбрана фича,
не объявлена в модуле), — ошибка с перечнем доступных ручек.

- **Кадр теста честный, но пустой**: `raw.transport` — имя из токена,
  `raw.pattern` — паттерн декларации, `raw.payload` — то, что передал тест,
  `raw.attributes` — `{}` (можно задать через `options.attributes`). Слой,
  читающий заголовки HTTP, в app-тесте увидит пустоту — это цена in-proc
  вызова, и она документируется.
- **Транспортный биндинг не выполняется**: `app.call` принимает уже готовый
  payload, а не «запрос». Раскладка path/query/body по bind-карте —
  предмет e2e и юнит-тестов bind-карты, а не app-теста.
- **Возвращается `ResponseContext`, а не `Ok | Fail`.** Так тест видит ровно
  то, что увидел бы транспорт: статус, значение, а на ветке отказа —
  `code` из закрытого контракта `errors:` (страж границы уже отработал).
  Рематериализация `Fail` по `code` — это change `contract-clients` (#22);
  делать её здесь значило бы завести вторую, конкурирующую реализацию.
  `unwrap(res)` покрывает частый случай «ожидаю успех».
- Опции границы (`exposeErrorDetails`, `onUnknownFail`) пробрасываются;
  дефолт `exposeErrorDetails: true` — в тестах детали нужны.

`app.get(token)` отдаёт инстанс из графа (или `null`) — для узлов, ссылка на
токен которых у теста есть; `app.pruned` — что выпало прунингом.

### D6. `.check()` — метод `App`, а не `TestApp`

Структурная проверка обязана идти по **честному** графу: она и существует,
чтобы компенсировать прунинг (ideas.md [2026-07-10], «Цена»). Поэтому
`.check()` живёт на результате `assemble`, а не на тестовом корне:

```typescript
for (const select of ['all', 'users', 'logging'] as const) {
  await assemble({ features: [...], select, transports: [http()] }).check();
}
```

`check()` = фазы 0–1: резолв `select`, регистрация, дискавери,
`builder.build()` (конструкторы выполняются, `@OnInit` — нет), сверка
транспортов и форм io. Возвращает отчёт о составе (фичи, ручки по
транспортам, ключи конфига), бросает — на любом отказе сборки, теми же
ошибками, что бросил бы `run()`. Собственный контейнер `check()` не сохраняет
в `App` и не мешает последующему `run()`.

`checkTopologies(spec, selections)` из `@nestling/testing` — тонкая обёртка:
гоняет `.check()` по каждой топологии, **собирает все** отказы и падает одним
сообщением. Разделение намеренное: ядро фейлится быстро, тестовый хелпер
рассказывает всю историю.

Ограничение, которое надо помнить: конструктор с побочкой ломает `.check()`.
Это и так нарушение lifecycle (ресурсы — в `@OnInit`), и оно усиливает
кандидатуру policy-check «ресурсы только в `@OnInit`» (#28).

### D7. `testModule` и перечень недостающих зависимостей

`testModule(M, { stubs, config })` — мини-app вокруг одного модуля:
регистрирует `M` (с его `imports`), kernel-модуль конфига и стабы, проходит
те же фазы 0–3 и отдаёт тот же `TestApp`. Живёт внутри пакета модуля, поэтому
токены видны без экспорта.

Гарантия «неудовлетворённые импорты обязаны быть застабаны явно» требует
уметь перечислить **все** недостающие токены. Сейчас `instantiateAll` падает
на первом (`Provider for token 'X' not found`). Вводится предвалидация до
инстанциации: обход `deps` всех оставшихся провайдеров, сбор токенов без
провайдера, одна ошибка со списком (в стиле существующего `checkStrictExports`,
который уже сообщает все нарушения разом). Это улучшает и боевую диагностику —
разъехавшийся `assemble` теперь называет все дыры сразу.

`stubs` в V1 — те же пары `[Token, value]`, что и `overrides` (для модуля в
изоляции это не «подмена», а «поставка недостающего»). Форма выбрана
совместимой с будущим `stub(Contract, impl)`: он приедет элементом того же
списка.

### D8. `vars()` и `config: source`

`vars(record)` = `objectSource(record, 'vars')` — тонкая обёртка, не второй
источник: механика `watch`/`set` уже реализована и покрыта тестами конфига.
Ценность имени в другом — оно называет **шов**: «конфиг теста задаётся
объектом, `process.env` не трогается».

В тестовом корне `config:` принимает три формы: `ConfigSource` (сахар для
`[[source, '*']]`), одну привязку и список привязок. В боевом `assemble`
сахара нет: там привязка — акт с приоритетами, и умолчание «весь источник»
неуместно.

### D9. Обвязка условия `"testing"` в репозитории

- `jest.config.base.js`: `testEnvironmentOptions.customExportConditions =
  ['testing', 'node', 'node-addons']` — условие включено во всех тестах репо;
  `moduleNameMapper` получает правило для `@nestling/<pkg>/testing` **до**
  общего `^@nestling/(.*)$` (иначе subpath уедет в несуществующий путь);
  ts-jest'овый `tsconfig` — `lib: ['es2022', 'esnext.disposable']` для
  `await using`.
- `tsconfig` пакетов, которым нужен условный резолв при сборке
  (`nestling.testing`, `examples.app-with-http`), получает
  `customConditions: ['testing']` (`moduleResolution: 'bundler'` это
  поддерживает).
- Node ≥ 20 даёт `Symbol.asyncDispose` в рантайме; репо на Node 22.

## Risks / Trade-offs

- **Граф теста ≠ прод-граф (прунинг)** → компенсация — `.check()` на честном
  графе; `app.pruned` показывает разницу; в гайде это правило написано прямо:
  «мокаешь — проверь топологию `.check()`».
- **Условие `"testing"` в `tsconfig.customConditions` пакета делает subpath
  видимым при typecheck и прод-кода этого пакета** → граница остаётся
  структурной в рантайме (Node без условия не резолвит), а на уровне типов
  ограничена набором пакетов, которым условие реально нужно. Разносить
  `tsconfig.spec.json` по всем пакетам ради этого — цена выше пользы.
- **Подстановка теряет реальные зависимости фейка** (фейк — значение, у него
  нет deps) → это и есть смысл прунинга; узел с побочными зависимостями,
  который тест *хочет* сохранить, подменяется не value-фейком, а обычным
  провайдером с `deps` (форма `[Token, provider]` в `overrides` не вводится в
  V1 — не нашлось случая; при появлении добавляется аддитивно).
- **`app.call` не проходит транспортный биндинг** → сборка запроса из
  path/query/body проверяется e2e и юнит-тестами bind-карты; в гайде граница
  «что проверяет app-тест, а что — e2e» описана явно.
- **`@OnStart` в тестовом прогоне не выполняется** → задокументировано;
  ресурс, который нужен тесту, захватывается в `@OnInit` (что и предписано
  фазовой моделью).
- **Предвалидация недостающих зависимостей меняет тексты боевых ошибок** →
  существующие тесты на текст правятся в этом же change'е; форма ошибки
  становится строго информативнее (перечень вместо первой).
- **Пакет `@nestling/testing` попадает в прод-зависимости пользователя по
  ошибке** → импорт `@nestling/app/testing` в среде без условия `"testing"`
  падает на резолве, громко и на старте, а не тихо.

## Migration Plan

Change аддитивный: публичный API `assemble`/`App.run()`/`close()` не меняется,
поведение боевой сборки — тоже (кроме текста ошибки о недостающих
зависимостях, который становится перечнем). Порядок работ снизу вверх:
контейнер (подстановка, прунинг, предвалидация) → шов `@nestling/app/testing`
и `App.check()` → пакет `@nestling/testing` → обвязка jest/tsconfig →
витрина в `examples.app-with-http` → доки. Каждая ступень оставляет репозиторий
собираемым, откат — отбрасыванием верхних ступеней.
