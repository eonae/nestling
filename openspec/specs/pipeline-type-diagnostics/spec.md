# pipeline-type-diagnostics

## Purpose

Форма, в которой типовая машинерия pipeline отвергает аргумент. Вместо
трассировки дженериков компилятор печатает объектный литерал ровно из двух
полей — `__error` (текст проблемы) и `missing` (рекорд «имя поля → его тип»
недостающего контекста); для перезаписи существующего поля — `conflicting`
вместо `missing`. Форма едина во всех точках проверки: `compose`, приём
pre-юнита против накопленного input, слот `pipeline` транспортной декларации.
Тексты диагностик зафиксированы snapshot-тестами по каталогу фикстур заведомо
неправильных композиций.

## Requirements

### Requirement: Тип-ошибка pipeline — литерал `__error` + `missing`

При нарушении требований слоя тип параметра SHALL схлопываться в объектный
литерал ровно из двух обязательных полей:

- `__error` — строковый литерал, называющий проблему на естественном языке;
- `missing` — **рекорд «имя поля → его тип»** недостающего контекста.

`missing` SHALL быть рекордом с типами, а не юнионом имён ключей. В `missing`
SHALL попадать и поля, отсутствующие во внешнем контексте, и поля,
присутствующие с несовместимым типом.

Литерал SHALL NOT нести поля, дублирующие информацию, доступную наведением на
аргументы (полный внешний контекст, полные требования слоя). Необязательное
поле `hint` SHALL быть допустимо там, где подсказка называет конкретное
действие.

#### Scenario: Поле отсутствует во внешних слоях

- **WHEN** `inner` объявлен как `makePipeline<{ identity: User; requestId: string }>()`,
  а внешние слои дают только `{ requestId: string }`
- **THEN** ошибка компиляции называет параметр как
  `{ __error: "…"; missing: { identity: User; }; }`

#### Scenario: Поле есть, но несовместимого типа

- **WHEN** внешние слои дают `{ requestId: string }`, а `inner` объявлен как
  `makePipeline<{ requestId: number }>()`
- **THEN** ошибка компиляции называет параметр как
  `{ __error: "…"; missing: { requestId: number; }; }` — случай не
  схлопывается в пустой или `never`-результат

#### Scenario: Совместимая композиция литерала не порождает

- **WHEN** внешние слои покрывают требования `inner`
- **THEN** ошибки компиляции нет, а результирующий тип накапливает input
  обоих слоёв

### Requirement: Тип-ошибка печатается развёрнутым анонимным литералом

Тип-ошибка SHALL быть напечатана компилятором в развёрнутом виде: первая
строка диагностики SHALL содержать текст `__error` и состав `missing`.
Возврат из условного типа именованного дженерик-алиаса, который компилятор
печатает именем, SHALL NOT считаться выполнением требования.

Позиция параметра SHALL NOT содержать пересечения с типом самого слоя
(`& Pipeline<…>`): в неуспешной ветке параметр — только литерал ошибки.

#### Scenario: Текст сообщения виден в первой строке

- **WHEN** композиция несовместима
- **THEN** первая строка диагностики содержит текст `__error` и рекорд
  `missing`, и не содержит хвоста `& PipelineBuilder<...>`

#### Scenario: Вывод типов в успешной ветке сохраняется

- **WHEN** композиция совместима, а параметр объявлен условным типом без
  пересечения с типом слоя
- **THEN** тип-параметры внутреннего слоя (`TReq`, `TAcc`, `TNeeds`)
  выводятся из аргумента, и накопленный input результата равен пересечению
  накопленных input слоёв

### Requirement: Форма литерала едина во всех точках проверки pipeline

Все точки, где типовая машинерия pipeline отвергает аргумент, SHALL
пользоваться одной формой литерала: точка композиции (`compose`), проверка
pre-юнита против накопленного input и проверка слота `pipeline` в
транспортной декларации.

Для случая «юнит перезаписывает существующее поле» литерал SHALL нести поле
`conflicting` — рекорд конфликтующих полей — вместо `missing`.

#### Scenario: Pre-юнит требует отсутствующего поля

- **WHEN** pre-юнит объявлен как требующий `{ identity: User }`, а
  накопленный input его не содержит
- **THEN** диагностика имеет ту же форму `{ __error: "…"; missing: { identity: User; }; }`

#### Scenario: Pre-юнит перезаписывает поле

- **WHEN** pre-юнит добавляет поле, уже присутствующее в накопленном input
  с другим типом
- **THEN** диагностика имеет форму `{ __error: "…"; conflicting: { … }; }`

#### Scenario: Слот pipeline транспортной декларации

- **WHEN** пайплайн требует полей, которых стартовый контекст декларации не
  предоставляет (например, забыт `rawBody: true`)
- **THEN** диагностика имеет ту же форму `__error` + `missing`, дополненную
  полем `hint` с конкретным действием

### Requirement: Тексты диагностик зафиксированы snapshot-тестами

Репозиторий SHALL содержать каталог фикстур заведомо неправильных
композиций. Тесты SHALL компилировать фикстуры и сравнивать нормализованный
текст диагностик со снапшотами; расхождение SHALL валить прогон.

Нормализация SHALL приводить абсолютные пути к путям относительно корня
репозитория и приводить переводы строк к `\n`; номера строк и колонок SHALL
сохраняться. Усечение длинных типов компилятором SHALL NOT отключаться —
снапшот фиксирует текст в том виде, в котором его видит пользователь.

Набор фикстур SHALL покрывать как минимум: отсутствие поля во внешних слоях;
несовместимый тип существующего поля; неверный порядок слоёв; нарушение на
третьем слое при арности 3; `.pre` после ответного метода; перезапись поля
pre-юнитом; pre-юнит требует отсутствующего поля; нерезолвленный класс-юнит
у транспорта.

#### Scenario: Снапшот расходится с текущим текстом

- **WHEN** форма типа-ошибки изменена, а снапшоты не обновлены
- **THEN** прогон падает и показывает диф текста диагностики

#### Scenario: Фикстуры не участвуют в сборке и линте

- **WHEN** выполняется `build` или `lint` пакета `@nestling/pipeline`
- **THEN** каталог фикстур в них не входит, и намеренные ошибки компиляции
  их не валят

#### Scenario: Диагностики снимаются одной программой компилятора

- **WHEN** прогоняется набор снапшот-тестов
- **THEN** над каталогом фикстур создаётся одна программа компилятора, а
  диагностики группируются по файлам
