## 1. `Fail` — значение; `return` — канон, `throw` — доставка

Ожидаемая ошибка домена — это значение `Fail`. Хендлер возвращает его как
обычный результат; для пайплайна возврат и бросок равнозначны. Брошенное
исключение, которое не является `Fail`, считается внутренней ошибкой:
клиент получает `internal_error` без деталей. Модель повторяет пару
`Result` и `panic!` из Rust.

- Канон — `return`: возвращённый отказ виден в типе `Output` хендлера.
  `throw` — способ доставить `Fail` из глубины вызовов, где вернуть его
  некому; он заменяет отсутствующий в JS оператор `?`. Компилятор бросок
  не видит, поэтому рантайм проверяет его на границе (§4).
- `Output<T, E> = Promise<Ok<T> | E | KernelFail | T>` (есть и
  `OutputSync`). Голое значение `T` оборачивается в `Ok`. `KernelFail` —
  отказы ядра (§4): хендлер возвращает их без объявления, как и граница
  пропускает их без объявления. По умолчанию `E` равен `never`: endpoint
  без `errors:` не может вернуть доменный отказ. `E` записывается
  определениями отказов: `Output<User, typeof UserNotFound | typeof EmailTaken>`.
  У декларации без `output` тип результата принимает `void`: хендлер,
  которому нечего вернуть, не пишет `return undefined`. Там же остаётся
  допустим `Ok` без значения — `Ok.noContent()` и `new Ok(null)`; у
  декларации со схемой `output` такой возврат — ошибка компиляции.
- Дискриминант — поле `isFail`: `true as const` у `Fail`, `false` у `Ok`.
  Оно сериализуется, в отличие от проверки `instanceof`. Завернуть отказ в
  успех нельзя: `new Ok(fail)` — ошибка компиляции.
- Возвращённый `Fail` попадает в ветку ошибки до `.ok`-юнитов. Инвариант
  «`.ok` видит только успех» держится для обоих путей.
- `Fail extends Error`, поэтому у брошенного отказа есть стек вызовов.

## 2. Код отказа: категория и уточнение

У отказа одна ось — `code`. Код состоит из сегментов через двоеточие;
каждый сегмент соответствует `[a-z_]+`. Первый сегмент — категория,
остальные уточняют её: `not_found:user`, `conflict:email_taken`. Код из
одной категории допустим: `unauthorized`.

Перечень категорий закрыт и не зависит от транспорта:

| Категория | HTTP |
|---|---|
| `bad_request` | 400 |
| `unauthorized` | 401 |
| `payment_required` | 402 |
| `forbidden` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| `payload_too_large` | 413 |
| `too_many_requests` | 429 |
| `internal_error` | 500 |
| `not_implemented` | 501 |
| `service_unavailable` | 503 |
| `timeout` | 504 |

- `category` — производное поле `Fail`: первый сегмент кода. Его читают
  транспорты (перевод в HTTP-статус или код шины), `.catch`-юниты и
  генератор OpenAPI, где ответы группируются по категории. Отдельного поля
  `status` у отказа нет: категория входит в код, и написать код с одной
  категорией, а статус с другой невозможно.
- Тип кода — `${Category}` или `${Category}:${string}`. Категорию
  проверяет компилятор в точке `makeFail`, формат сегментов — рантайм там
  же.
- `cause?: unknown` — исходная ошибка, как у `Error` в ES2022.
- В сериализованном виде (`ErrorDetails`) уходят `code`, `message`,
  `details` и `requestId`. `requestId` кладут `.catch`- и
  `.finally`-юниты из контекста, так что ответ связывается с логами без
  кода пользователя. Категория отдельно не передаётся: она
  восстанавливается из кода.
- Статусы успеха живут на `Ok` и записываются в том же регистре: `ok`,
  `created`, `accepted`, `no_content`. Поле `status` контекста ответа —
  статус успеха либо категория отказа.

## 3. Доменные ошибки: `makeFail` и идентичность по `code`

```typescript
export const OrderNotFound = makeFail('not_found:order', {
  details: z.object({ orderId: z.string() }),   // schema-first — и для details
  message: (d) => `Order ${d.orderId} not found`,
});

return OrderNotFound({ orderId: '42' });
throw OrderNotFound({ orderId: '42' }, { cause: dbError });   // из глубины вызовов
// в .catch-юните:
if (OrderNotFound.is(res)) { /* ... */ }        // матчинг по code
```

Данные отказа берутся только из `details`. Конструктор принимает их с
типом, выведенным из схемы, и проверяет схемой на месте. `message` — строка
или функция от этих деталей. Если схемы нет, конструктор вызывается без
аргументов: `EmailTaken()`. Второй аргумент — опции, например `cause`.

Определение — значение со свойствами `code`, `category`, `schema` и
предикатом `is`; его можно вызывать как функцию. Регистрировать
определение не нужно: на приложение оно влияет только через `errors:`
декларации. Два определения с одним кодом — один и тот же отказ.

Отказ распознаётся по `code`, а не по `instanceof`. `Fail`, пришедший от
удалённого порта или в клиент, — это десериализованные данные: класса у
них нет, а `code` сохраняется. Поэтому `is` проверяет код у двух
носителей: у значения-отказа (в том числе разобранного из JSON) и у
контекста ответа-ошибки, который видит `.catch`-юнит. Второй носитель
описан минимальным структурным типом
`{ isSuccess: false; value?: { code?: string } }`, а не типом контекста
пайплайна; сужение типа в `.catch` от этого не меняется.

Порт и `makeClient` восстанавливают удалённый отказ в настоящий `Fail` на
своей стороне по одному правилу. `message` берётся из ответа, потому что
описывает конкретный случай. `details` берутся из ответа и проверяются
схемой определения. Если детали не прошли схему, код не объявлен в
операции, тело не JSON, сеть недоступна или ответ не прошёл
`output`-схему, клиент получает `InternalError` с оригиналом в `cause`.
Множество ответов у внешнего потребителя — `E ∪ InternalError`, то же, что
у порта. Ветка `default`, написанная для `.caller`, переносится на клиента
без правок ([operations.md](./operations.md)).

## 4. Ошибки — часть операции: `E ∪ InternalError`

Поле `errors: [EmailTaken, OrderLimitReached]` в декларации endpoint'а или
операции объявляет, какие отказы возможны. Отказы pre-юнитов объявляются на
слое, при подключении юнита ([pipeline.md §3](./pipeline.md)); эффективное
множество endpoint'а складывается из `errors:` декларации и отказов его
пайплайна. Гарантия держится на двух уровнях.

- Компилятор проверяет всё, что передаётся значениями. `makeFail`
  брендирует тип (`Fail<'conflict:email_taken'>`); `Output<T, E>` сверяет
  `return` с декларацией, в том числе проброс отказа порта: чужой `Fail`
  не попадёт в ответ, пока не задекларирован. Возвращаемый тип хендлера
  сверяется со списком `errors:` в точке декларации.
- Рантайм проверяет остальное на выходе из пайплайна: `throw`, отказы из
  глубины сервисов, обходы типов. Всё, что дошло до выхода
  незадекларированным, **заменяется на `InternalError`** — определение
  ядра с кодом `internal_error`. Ответ без кода незадекларирован по
  определению. Оригинал целиком передаётся диагностическому хуку
  `onUnknownFail` (по умолчанию — `console.error`), клиенту уходит общее
  тело ошибки.

Множество отказов доходит до рантайма как значение декларации: из
`errors:` в `EndpointMeta`, оттуда в контекст запроса. Глобального реестра
нет, поэтому пайплайн, выполненный без декларации, видит пустое множество.

Вызов порта закрыт тем же множеством и той же процедурой: на границе отказ
восстанавливается по `code` из `errors:` операции, незадекларированный
становится `InternalError`, а отказы ядра входят в операцию и там
([operations.md](./operations.md)).

Итог: ответ endpoint'а — закрытое множество `E ∪ InternalError`, где `E`
объединяет отказы из `errors:` декларации и отказы, объявленные слоями
пайплайна. `InternalError` входит в операцию каждого endpoint'а неявно (ответ
`default` в OpenAPI). Отказы ядра входят в множество тем же способом и
несут голую категорию, без уточнения: `BadRequest` (`bad_request`) у
проверки входа, `PayloadTooLarge` (`payload_too_large`) у лимита размера
входа и item-цепочек, `Timeout` (`timeout`) у бюджета вызова портов и
разрыва потока, `InternalError` (`internal_error`) у всего
незадекларированного. Определения ядра называются по категории.
Публичного способа объявить свой отказ отказом ядра нет; пользовательское
определение с тем же кодом (`makeFail('bad_request')`) — тот же отказ по
идентичности.

Проверка на выходе стоит после всех `.catch`-юнитов: `.catch` — то место,
где незадекларированный отказ превращается в задекларированный. Забытая
декларация проявляется сразу: клиент получает `InternalError` (500), а не
случайно работающий 404.

## 5. Заголовки `Ok`

`Ok` несёт необязательные `headers` — метаданные ответа, не зависящие от
транспорта. `Ok.created(order, { Location: '/orders/42' })` пишет хендлер,
который о транспорте не знает. Что с ними делает транспорт, описано в
[transports.md](./transports.md): HTTP пишет их в заголовки ответа, NATS —
в заголовки ответного сообщения, CLI отбрасывает.
