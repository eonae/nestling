# Гайд по Nestling

Гайд ведёт от первого сервиса к приложению из нескольких фич,
развёрнутому в нескольких процессах. Каждая глава начинается с задачи,
которую вы и так собираетесь решать, и раскрывает ровно те возможности
фреймворка, без которых задача не решается. Возможности, которые задаче
пока не нужны, глава не называет вовсе: понятие появляется там, где его
объясняют, а не раньше.

Читатель гайда знает TypeScript и писал сервисы на Nest или Express.
Термины берутся из [глоссария](../glossary.md). Целевое описание каждой
подсистемы лежит в [`design/`](../design/README.md), причины решений в
[`decisions/ideas.md`](../decisions/ideas.md); главы ссылаются на них в
плашке.

## Как читать

Части 1 и 2 читайте подряд: они собирают один сервис, и каждая глава
опирается на код предыдущей. Правила именования, которым следуют
примеры, собраны в [conventions.md](../conventions.md). Часть 3 нужна, когда областей в приложении
становится больше одной. Часть 4 нужна, когда одного процесса мало.
Часть 5 читается по потребности: каждая её глава самостоятельна.

Код всех глав лежит в `packages/examples.*`. Части 1 и 2 собирают
`examples.users-service`, части 3 и 4 продолжают его в
`examples.app-with-http` и `examples.split-nats`. Сниппет в главе
начинается с пути к файлу примера и совпадает с ним. Сниппет, который
показывает промежуточный шаг, помечен комментарием «шаг главы»; итоговая
версия файла названа рядом.

## Что проверяется до первого запроса

Nestling переносит проверки как можно раньше: часть ошибок приложения
нельзя написать, остальные останавливают старт, а не запрос. Таблица
называет проверку, момент срабатывания и главу, где проверка вводится.

| Что проверяется | Когда | Глава |
|---|---|---|
| Список зависимостей совпадает с параметрами конструктора по типам, порядку и длине | при компиляции | [5](./05-repository.md) |
| Требования слоя к внешнему контексту выполнены в точке `compose` | при компиляции | [8](./08-logging.md) |
| Хендлер возвращает то, что описывает схема `output` | при компиляции | [1](./01-first-service.md) |
| Хендлер возвращает только объявленные в `errors:` отказы | при компиляции | [3](./03-errors.md) |
| Путь endpoint'а непустой, без повторяющихся path-параметров | при создании декларации | [2](./02-input.md) |
| Ключи конфига заданы и проходят схемы | фаза BOOTSTRAP, до контейнера | [6](./06-config.md) |
| Все зависимости зарегистрированы, циклов в графе нет | фаза ASSEMBLE | [5](./05-repository.md) |
| Каждый endpoint подключил обязательный слой | фаза ASSEMBLE | [9](./09-auth.md) |
| Пайплайн объявил переменную, которую читают из глубины графа | фаза ASSEMBLE | [9](./09-auth.md) |
| Формы io деклараций поддержаны транспортом | фаза ASSEMBLE | [10](./10-files-and-streams.md) |
| Для каждой схемы есть конвертер в OpenAPI | фаза ASSEMBLE | [11](./11-openapi-and-client.md) |
| Между двумя фичами нет прямого ребра графа | фаза ASSEMBLE | [12](./12-features.md) |
| У каждой вызываемой операции есть владелец или шина | фаза ASSEMBLE | [17](./17-split.md) |
| Отказ вне `errors:` не уходит клиенту | на запросе, заменяется на `internal_error` | [3](./03-errors.md) |
| Вход соответствует схеме `input` | на запросе, ответ `400` | [2](./02-input.md) |

Проверки фазы ASSEMBLE выполняются до `@OnInit` и до открытия сокета:
нарушение останавливает процесс раньше, чем он захватит ресурсы. Те же
проверки прогоняет `app.check(select)` по матрице топологий в CI
([глава 16](./16-select.md)) и тестовая сборка `assembleTest`
([глава 7](./07-testing.md)).
