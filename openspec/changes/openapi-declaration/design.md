## Context

Документ OpenAPI строится двумя путями. В рантайме его строит плагин
`openapi()`: провайдер на фазе ASSEMBLE читает `Discovery$` и получает
выбранный состав приложения готовым значением. В CI документ строит чистая
функция `buildOpenApiDocument(endpoints, options)`, и вход к ней автор
собирает руками: `discoverEndpoints([...features, ...plugins])`.

Второй путь обходит фазу 0. Она разбирает аргумент сборки, считает
значения переключателей, раскрывает ветки, разрешает выбор фич и
замыкает его по вызываемым операциям при `includeDeps`. Сейчас эта фаза
живёт целиком в приватном методе `AssembledApp#select()`, и снаружи
пакета к ней нет доступа. Поэтому CI получает документ по составу
«все объявленные единицы», а прод поднимается по составу из аргумента.

Фаза 0 синхронна и не делает ввода-вывода: источники конфига поднимает
фаза `#bootstrap`, граф строит фаза 1. Значит вход генератора вычислим
без единого побочного эффекта — не хватает только публичной двери.

## Goals / Non-Goals

**Goals:**

- Состав документа в CI совпадает с составом сборки при том же аргументе.
- Вычисление остаётся чистым: без источников конфига, без графа, без
  транспортов и без `await`.
- Выбор фич и раскрытие веток считаются одним кодом для сборки и для
  генератора.
- У discovery одна публичная дверь.

**Non-Goals:**

- Перегрузка `buildOpenApiDocument(app, …)`.
- Изменения плагина `openapi()` и рантайм-пути документа.
- Проверки графа в новом методе: неудовлетворённые зависимости,
  политики и сверка транспортов остаются за `check()`.
- Кэш состава между вызовами.

## Decisions

### Р1. Поверхность — метод декларации `app.discover(args?)`

Декларация приложения получает третий вход рядом с двумя имеющимися:

| Вызов | Фазы | Результат |
|---|---|---|
| `app.discover(args?)` | 0 | `EndpointDiscovery` |
| `app.check(args?, options?)` | 0–1 | `CheckReport` |
| `app.assemble(args?).run()` | 0–5 | работающее приложение |

Все три принимают один и тот же аргумент сборки, и его тип выводится из
`switches:` декларации. Метод синхронный: фаза 0 не делает ввода-вывода,
а `check()` асинхронен только из-за подъёма источников конфига.

Альтернатива — перегрузка `discoverEndpoints(app, args?)`. Отвергнута:
сегодня эта функция обещает плоский проход по **уже выбранным**
единицам, а вторая форма затащила бы в неё фазу 0 целиком. Вторая
альтернатива — перегрузка `buildOpenApiDocument(app, { args, …options })`
из [design/schemas.md](../../../docs/design/schemas.md) §2.1. Отвергнута:
вызов `buildOpenApiDocument(app.discover(args).endpoints, options)` и так
однострочный, а перегрузка стоила бы второй сигнатуры, второго типа
опций и двух объяснений в документации. Таблица §2.1 правится этим
change'ем.

### Р2. Фаза 0 — одна функция на двух вызывателей

Тело `AssembledApp#select()` переезжает в чистую функцию
`resolveComposition(spec, args)` нового модуля `src/root/composition.ts`.
Она принимает нормализованную декларацию и аргумент, возвращает
значение: значения переключателей, выбранные фичи, единицы сборки,
имена выбранных фич, флаг `includeDeps`, объявления транспортов и
серверов.

`AssembledApp#select()` становится присвоением полей из результата.
`App.discover(args)` зовёт ту же функцию и передаёт её `bundles` в
`discoverEndpoints`. Одинаковый состав у сборки и у генератора — это
свойство одного кода, а не двух похожих реализаций.

Альтернатива — шов `DISCOVER_SEAM` на `AssembledApp` по образцу
`CHECK_SEAM`. Отвергнута: шов нужен там, где вызов проводит приложение
по фазам и оставляет за собой состояние. Фаза 0 — вычисление значения,
и заводить ради неё объект прогона нечем оправдать.

### Р3. `discoverEndpoints` уходит из публичных экспортов

Функция остаётся в пакете и остаётся тем же проходом по единицам, но
`src/root/index.ts` её больше не отдаёт. Пока она публична, у документа
есть законный способ разойтись со сборкой — тот самый, ради которого
change и заводится.

Потребителей в коде репозитория у неё нет: `@nestling/openapi`,
`@nestling/testing` и примеры её не вызывают. Упоминания живут в JSDoc
и README, и правятся вместе с кодом.

Публичными остаются тип результата `EndpointDiscovery`, элемент
`DiscoveredEndpoint` и DI-токен `Discovery$`: плагин по-прежнему читает
состав из графа.

### Р4. Результат — то же значение, что лежит под `Discovery$`

`discover()` возвращает `EndpointDiscovery`: список endpoint'ов с
атрибуцией к единице и карту «DI-токен транспорта → его endpoint'ы».
Значение заморожено, как и то, что регистрируется в графе.

Своего типа отчёта у метода нет. Отчёт есть у `check()`, и он про
другое: там строки для сравнения в тесте, здесь декларации для
генератора.

Равенство составов фиксируется тестом: `app.discover(args)` и
`Discovery$` из `app.check(args)` дают одинаковые паттерны и одинаковую
атрибуцию при любом аргументе.

### Р5. Что метод проверяет, а что нет

`discover()` бросает ошибки фазы 0, потому что они лежат на его пути:
неизвестное поле аргумента, неизвестное имя фичи, значение
переключателя вне словаря, ветка на необъявленном переключателе,
элемент `endpoints:`, не являющийся декларацией, две разные единицы с
одним именем, дубликат паттерна на экземпляре транспорта.

Ошибок графа он не бросает: экземпляров нет, контейнер не строится.
Неудовлетворённая зависимость, нарушенная политика, форма io вне
способностей транспорта и отсутствие требуемого транспорта — исходы
`check()`. Эта граница пишется в JSDoc и в README: метод отвечает на
вопрос «что обслуживается», а не «соберётся ли».

### Р6. Пример — `app-with-http`

Скрипт `src/openapi.ts` пишет `openapi.json` в корень пакета примера,
команда — `yarn workspace @examples/app-with-http openapi`. Аргумент
сборки скрипт берёт из аргумента командной строки, поэтому
`openapi users` даёт документ одной фичи, а вызов без аргумента — всех.

Пример выбран из-за состава: три фичи и переключатель `docs`, под
которым лежит сам плагин документации. На нём видно, зачем генератору
аргумент. В `users-service` одна фича и ни одного переключателя, и
скрипт там иллюстрировал бы только запись файла.

Файл `openapi.json` попадает в корневой `.gitignore`: сгенерированное в
git не хранится.

## Risks / Trade-offs

- [Фаза 0 разъедется между сборкой и генератором] → один код на двоих
  (Р2) плюс тест равенства составов (Р4).
- [`discover()` примут за проверку сборки] → граница названа в JSDoc,
  README и главе гайда; `check()` остаётся единственным способом
  проверить граф.
- [Снятие публичного экспорта ломает внешний код] → потребителей нет ни
  в пакетах, ни в примерах; проект в стадии проектирования, обратной
  совместимости нет.
- [Скрипт примера разойдётся с главой 12] → глава цитирует файл примера,
  `yarn docs:audit` сверяет цитаты.
- [`App` растёт третьим методом] → цена принята: три входа с одним
  аргументом читаются как одна лесенка, а альтернатива размывала бы
  чистую функцию.

## Migration Plan

1. Вынести фазу 0 в `resolveComposition` и перевести `AssembledApp` на неё.
2. Добавить `App.discover(args?)` и тесты.
3. Снять экспорт `discoverEndpoints`, переписать примеры в JSDoc и README.
4. Добавить скрипт примера и главу гайда.

Отката не требуется: изменение не покидает репозиторий.
